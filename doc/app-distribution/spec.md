# Family mruby アプリ配布 仕様 (最小版)

> 状態: 草案 | 2026-09-02 | 既存コードに合わせて書き直したもの。
> 元の構想は `family-mruby-app-distribution-design.md` にある。

## 0. この文書の立場

元の設計書は実装を見ずに書かれているため、既にあるものを作り直す形になって
いる箇所が多い。ここでは**新しく作る必要があるものだけ**を仕様にする。
判断の根拠 (どのファイルの何行目でそうなっているか) は各節に付ける。

## 1. 目的

Ruby (および Lua / BASIC / MicroPython) で書いたアプリを、Web で公開し、
ブラウザ版でそのまま試し、実機へ導入できるようにする。

### 作らないもの

| 作らない | 理由 |
|---|---|
| 新しいアプリ記述形式 (`manifest.json`) | `.app.toml` が既にあり、二重帳簿になる |
| 新しい転送手順 (BLE の 11 命令) | 実機が https を叩けるので、実機が取りに行けば済む |
| 束形式 (`.mrpkg`) | ランチャーが 3 階層目のディレクトリを既に束として扱う |
| 1 ファイル配布 | 埋め込み記述のアプリはランチャーに出ない (3.3 節、2026-09-02 実測) |
| 独自の配信基盤 | GitHub の raw と自前 nginx で足りる (6 節で実測) |
| 署名・権限・審査 | 最初の版では持たない |
| ファームウェアの変更 | 配布の鍵は導入のときに既存の鍵へ翻訳する (8.3 節) |

## 2. 前提 — 既にあるもの

| もの | 実体 | 何ができるか |
|---|---|---|
| アプリ記述 | `<名前>.app.toml` | 窓の大きさ、記憶域、スタック、表示名 (日本語別名つき) |
| 記述の埋め込み | `.rb` 冒頭の `#---fmrb` 囲み | 自分で起動する補助スクリプト用。**配布には使えない** (3.3 節) |
| 束 (複数ファイル) | `/app/<分類>/<名前>/` | ランチャーが 3 階層目まで歩き、素材を同居させた束を 1 アプリとして拾う (`launcher.rb:378`) |
| ユーザ用の置き場 | `/app/usr/` | 出荷ツリーに空で存在する。ブラウザ版では IndexedDB に残る (`wasm/web/main.js:469,475`) |
| 実機の https 取得 | `Net::HTTP` | Retro (Narya) / Modern / Linux で利用可 |
| 実機への押し込み | `/fs/put` `/app/launch` | WiFi 経由。開発用 (`rd_http.c`) |
| ブラウザへの流し込み | ページの `FS.writeFile` | `main.js:1165` |
| 環境の判別 | `FmrbConst::PLATFORM` と `BOARD` | 7 節 |

**したがって、配布の仕組みで新しく要るのは「一覧」と「取ってきて置く手順」
だけである。**

## 3. 配布単位

配布単位は `.app.toml` を持つファイル一式とする。新しい形式は作らない。

### 3.1 実機が実際に読む鍵

`fmrb_app_spawner.c` と `launcher.rb` が読む鍵は以下がすべて。ここに無い鍵は
黙って無視される (未知の鍵を足しても壊れない)。

| 鍵 | 既定 | 効果 |
|---|---|---|
| `app_screen_name` | ファイル名 | 表示名。**埋め込みからは読まれない** (3.3 節) |
| `app_screen_name_<言語>` | — | 言語別の表示名 (`_ja` など) |
| `icon` | 拡張子で決まる既定 | アイコンのパス |
| `launcher_visible` | true | 一覧に出すか |
| `default_window_mode` | — | `window` / `fullscreen` / `background` |
| `default_window_width` / `_height` | 100 | 窓の大きさ。**既定は 100x100 = 1 行 15 文字ほど**。狭い |
| `default_window_pos_x` / `_y` | 50 | 窓の位置 |
| `min_window_width` / `_height` | 0 | 縮小の下限 |
| `resizable` | 0 | 大きさを変えられるか |
| `rounded_corners` | 1 | 角の丸め |
| `fullscreen_switchable` | 0 | 実行中の全画面切替 |
| `large_memory` | 0 | 大きい方のプールを専有する |
| `task_stack_kb` | 16 | タスクの C スタック。`[16, 64]` KB に丸められる |

`app_handle_name` は 67 個の `.app.toml` に書かれているが、**どのコードも読んで
いない**。配布では使わない。

`task_stack_kb` は数値で範囲も決まっており、そのまま配布に乗せられる。
問題は `large_memory` が真偽値であることで、これは 8.3 節で扱う。

### 3.2 配布のために足す鍵

`[fmrb_app]` のような表は作らず、平の鍵として足す (既存の読み手が壊れない)。

| 鍵 | 必須 | 内容 |
|---|:--:|---|
| `app_id` | 要 | 一覧の中で一意。`[a-z0-9_]{1,31}`。変更不可 |
| `app_version` | 要 | `<数>.<数>.<数>` |
| `app_author` | 要 | 作者 |
| `app_description` | 要 | 一行の説明 |
| `app_description_ja` | — | 日本語の説明 |
| `app_category` | 要 | `game` `tool` `demo` `education` `media` `iot` `other` |
| `app_env` | 要 | 動くと分かっている環境 (7 節) |
| `app_min_width` / `app_min_height` | — | 必要な画面の大きさ (7.2 節) |
| `required_heap_kb_esp32` | — | 必要なヒープ。実機用 (8.2 節) |
| `required_heap_kb_linux` | — | 同、sim とブラウザ用 |
| `app_screenshot` | — | スクリーンショット (PNG)。既定は `<app_id>.png` (10.2 節) |
| `app_license` | — | SPDX の識別子。省略時はリポジトリの LICENSE (11.1 節) |
| `app_source` | — | ソースの URL |
| `app_files` | — | 束のときの同梱ファイル。省略時は `.app.toml` と同名の本体 1 つ |

`app_id` はファイル名と一致させる。ランチャーは `<base>.toml` に対して
`<base>.rb` / `.lua` / `.bas` / `.py` を探す規則なので (`launcher.rb:327,461`)、
`<app_id>.app.toml` と `<app_id>.app.rb` の組になる。

### 3.3 `.app.toml` は必須 (実測で判明)

実機は `.rb` 冒頭の `#---fmrb` 囲みに記述を埋め込む形も読む
(`fmrb_app_spawner.c:398`)。**しかし配布にはこれを使えない。**

**ランチャーの走査は `.toml` を歩き、`.rb` を開いて囲みを探すことはしない**
(`launcher.rb:372`)。埋め込みだけのアプリは、入っても走査に拾われず、
**一覧に現れない**。パス指定では起動するので、入れた本人が二度と辿り着けない
形で消える。

spawner 自身も同じ理由で拒否しており、警告まで出す。

```
W: app_screen_name in the comment toml of hello_store.app.rb is ignored
   (launcher metadata needs a .toml sidecar)
```

2026-09-02、sim で全走査させて確認した (report/p1b.md)。埋め込みだけの
`hello_store` は 37 件の一覧に 1 度も現れず、`.app.toml` を足すと出た。

**埋め込みの形は、エディタや shell から自分で起動する補助スクリプトのもの**
であって、配布の形ではない。`.rb` に囲みを残したまま `.app.toml` も置く形も
禁じる (sidecar が勝つので、2 つの複製が黙ってずれる)。

## 4. 置き場所

```
/app/usr/<app_id>/<app_id>.app.toml
                  <app_id>.app.rb
                  (素材)
/home/apps/<app_id>/     ... アプリが書くもの (設定・記録)
```

`/app/usr/` を使う理由:

- 出荷ツリーに空で存在する。
- ランチャーの 3 階層走査 (`/app` → `usr` → `<app_id>`) にそのまま乗るので、
  **走査側のコードを 1 行も足さずに済む**。
- ブラウザ版では `/flash/app/usr` が永続化の対象に入っている
  (`main.js:475` の `STORES`)。出荷物と混ざらない。
- 出荷物 (`/app/game` など) と分かれるので、版を上げたときに
  「配ったもの」と「あとから入れたもの」を区別できる。

アプリ本体は書き換えない。アプリが書くものは `/home/apps/<app_id>/` に置く。
入れ直しても記録が消えないのはこの分離による。

### 4.1 空き容量

| 機種 | storage | 出荷ツリー | 空き |
|---|---:|---:|---:|
| Retro (S3) | 5 MB | 約 2.6 MB | 約 2.4 MB |
| Modern (P4) | 8 MB | 約 2.6 MB | 約 5.4 MB |

1 アプリを 20 KB とすると 100 個以上入るが、先に頭を打つのは 8.4 節の一覧の
上限である。

## 5. 一覧 (`registry.json`)

置き場: `family-mruby-apps` リポジトリの `apps/<app_id>/` を歩き、
**CI が `.app.toml` から生成する**。人は書かない。

```json
{
  "format_version": 1,
  "generated_at": "2026-09-02T00:00:00Z",
  "apps": [
    {
      "id": "breakout",
      "version": "1.0.0",
      "name": "Breakout",
      "name_ja": "ブロック崩し",
      "description": "A simple breakout game",
      "category": "game",
      "author": "example",
      "env": ["retro", "modern", "web"],
      "min_width": 320,
      "min_height": 240,
      "required_heap_kb": { "esp32": null, "linux": null },
      "base": "apps/breakout/",
      "screenshot": { "path": "breakout.png", "size": 6120, "sha256": "..." },
      "thumb": { "path": "breakout.thumb.bmp", "size": 1846, "sha256": "..." },
      "files": [
        { "path": "breakout.app.toml", "size": 412,   "sha256": "..." },
        { "path": "breakout.app.rb",   "size": 14240, "sha256": "..." }
      ]
    }
  ]
}
```

`base` は一覧ファイルからの相対とし、取得側が配信元の URL と繋ぐ。将来
作者のリポジトリへ散らすとき (12 節) は、ここを絶対 URL にすれば形は変わらない。

絵 (`screenshot` / `thumb`) は `files` に入れない。**導入するときに端末へ
書かないもの**だからである。店が一覧を見せるためだけに取る。

### 5.1 CI の検査

- `app_id` の重複、およびディレクトリ名との一致
- 必須の鍵の有無、`app_version` の形式
- `.app.toml` と対になる本体ファイルの存在
- `app_env` / `app_category` の値が表にあること
- `.app.toml` が実機の toml 解析器で読めること
- 本体が `.rb` のとき、picoruby で構文検査 (`Regexp` は無いので使うと落ちる)

## 6. 取得元 (実測済み)

公開ページは `https://silentworlds.info/fmrb/` で、SharedArrayBuffer のために
`COOP: same-origin` と `COEP: require-corp` を返している。この下では外部から
取ってくるものに制限がかかるので、実際にヘッダを確認した (2026-09-02)。

| 取得元 | ACAO | CORP | 判定 |
|---|---|---|---|
| `raw.githubusercontent.com` | `*` | `cross-origin` | `fetch` も `<img>` も通る |
| `*.github.io` (Pages) | `*` | 無し | `fetch` は通る。`<img src>` は塞がれる |
| GitHub Releases の添付 | — | 無し | 通らない |

**配信元は `raw.githubusercontent.com` とする。** Pages から画像を出す場合は
`<img crossorigin="anonymous">` が要る。Releases に本体や素材を置く案は
成立しない。

## 7. 環境

### 7.1 環境の名前と判定

画面の大きさだけでは足りない。ハードウェアで条件が変わるうえ、同じ原稿を
翻訳するのに要る記憶量も環境で違う (8.2 節)。`app_env` に並べる名前は次の 3 つ。

| 名前 | 中身 | 判定 |
|---|---|---|
| `retro` | Narya (ESP32-S3) | `PLATFORM == "esp32"` かつ `HW_FAMILY == "retro"` |
| `modern` | Tab5 ほか (ESP32-P4) | `PLATFORM == "esp32"` かつ `HW_FAMILY == "modern"` |
| `web` | ブラウザ版 | `BOARD == "wasm"` |

Linux sim (`BOARD == "linux"`) は開発用なので判定に使わない。何も並んで
いなくても動かせる。

**`HW_FAMILY` だけで環境を判定してはいけない。** 定義のコメントにあるとおり
「this build is, **or -- in the simulator -- stands in for**」で、sim も
ブラウザも `retro` か `modern` を名乗る (`const.c:383`)。ブラウザを見分けるのは
`BOARD == "wasm"` だけである (`const.c:362`)。

`app_env` には**実際に動かして確かめた環境だけ**を並べる。並んでいない環境
では店が「未確認」と出す。倍率を掛けて予測はしない。外れたときに黙って落ちる
のが一番悪いため。

### 7.2 画面

| 環境 | 画面 (論理) | 既定の窓 |
|---|---|---|
| `retro` | 320x240 (固定。NTSC) | 280x180 |
| `modern` | 426x240 | 386x210 |
| `web` | 426x240 (ページで 640x360 / 852x480 に上げられる) | 386x210 |

Tab5 の液晶も NARYA v4 の HDMI も物理は 1280x720 だが、**画面の枠組みは
426x240 で、そこから引き伸ばして出している**。したがって Retro と Modern の
差は横 106 画素だけで、高さは同じである。**店の画面は 1 つの作りで両方に
収まる**。

`app_min_width` / `app_min_height` が画面に収まらなければ導入しない。
細かい機能の宣言 (`i2c` `gpio` など) は最初の版では持たない。

## 8. ヒープ

### 8.1 なぜ真偽値では配れないか

プールの大きさは環境ごとに違う (`fmrb_mem_config.h`)。

| 環境 | ポインタ | 通常プール | large プール |
|---|---|---:|---:|
| `retro` (S3) | 32 bit | 500 KB | 1024 KB |
| `modern` (P4) | 32 bit | 1024 KB | 2048 KB |
| `web` (wasm32) | 32 bit | 1536 KB | 3072 KB |
| Linux sim | 64 bit | 1536 KB | 3072 KB |

900 KB 要るアプリは、`modern` では `large_memory = 0`、`retro` では
`large_memory = 1` になる。**同じ真偽値がどちらかの機械で必ず間違う**ので、
配る側は正しい値を書けない。

さらに large プールは**1 つしかない排他の区画**である
(`fmrb_app_spawner.c:196`)。`large_memory = 1` は「多めに寄こせ」ではなく
「1 つしかない大部屋を占有する」という意味で、これを付けたアプリは同時に
1 本しか動かない。必要量を数値で言えば、収まる中で一番小さいプールを
割り当てられる。

### 8.2 2 つの数

消費量を決めるのはオブジェクトの器の大きさで、これはポインタ幅で決まる。
`retro` と `modern` は同じ 32 ビットなので**消費量が同じ** (違うのはプールの
大きさだけ)。sim とブラウザはプールの寸法が同一で、sim の方が消費が多い。
よって 2 つの数で足りる。

```toml
required_heap_kb_esp32 = 700    # retro / modern
required_heap_kb_linux = 1400   # Linux sim / web
```

接尾辞は `FmrbConst::PLATFORM` の値そのものなので、実機側の引き当ては
`required_heap_kb_#{FmrbConst::PLATFORM}` の 1 行で済む。

**どちらも省略できる。** 省略は「普通のアプリ」を意味し、導入側は
`large_memory` を書かない。これは今と同じ挙動なので、既存の `.app.toml` を
直す必要はない。

書くのは **Retro の 500 KB に収まらないと分かっているときだけ**でよい。
Retro に収まるなら他の 3 環境には必ず収まる (sim で倍になっても
1000 KB < 1536 KB)。**Retro が唯一の律速**である。

64 ビットで倍になることは実測されている。`fmrb_mem_config.h` のコメント:
「the compile peak doubles with them -- a 23 KB source that fits the device's
500 KB aborted the sim」。実機の 500 KB に収まる 23 KB の原稿が sim で落ちた。
翻訳中の峰も倍になるので、**必要量はアプリ単体の性質ではなくアプリ × 環境の
値**である。

なおブラウザ版は `CONFIG_IDF_TARGET_LINUX=1` を定義しているため Linux の
プール寸法を継いでいるが、wasm32 は 32 ビットなので消費は sim より少ない。
`required_heap_kb_linux` はブラウザに対しては多めに見積もる方向に外れる
(安全側)。

### 8.3 何を測るか

**起動から通常の操作を一巡させるまでの、プール使用量の最大値。原稿の翻訳中の
峰を含む。** 10 秒周期の `fmrb_app:` ダンプが VM プールを出しているので、
既存の計装で測れる。

将来 CI が 3 環境で自動計測できるようになったら、作者が書くのをやめて CI が
`registry.json` に埋める。配布形式は変えなくてよい。

### 8.4 導入のときに翻訳する

配る形は環境に依存しない数値、置かれる形は今のファームウェアが読める真偽値
とする。**変換は導入のときに行う**ので、ファームウェアの変更は要らない。

店アプリは自分の環境のプール寸法と `required_heap_kb_<PLATFORM>` を突き合わせ、
その機械用の `large_memory` を `.app.toml` に書き込む。

| 判定 | 動作 |
|---|---|
| 省略されている | 何も書かない (普通のアプリとして入れる) |
| 通常プールに収まる | 何も書かない |
| 通常を超え large に収まる | `large_memory = 1` を書く。「大部屋を使うので同時に 1 本」と表示 |
| large も超える | 導入を断る。必要量と機械の上限を数字で出す |

`task_stack_kb` は既に数値で範囲も決まっているので、翻訳せずそのまま運ぶ。

## 9. 導入

### 9.1 経路

| 経路 | 誰が取るか | 使える場面 |
|---|---|---|
| A. 実機が取りに行く | 実機の店アプリ (`Net::HTTP`) | `retro` / `modern`。**これを本命とする** |
| B. ページが置く | ブラウザ版の `FS.writeFile` | `web` |
| C. 手元から押し込む | `tab5_fs` / `/fs/put` | 開発中 |

**ブラウザから実機へ直接押し込むことはできない。** 公開ページは https で
なければならず (crossOriginIsolated の条件)、そこから LAN の
`http://192.168.x.x/fs/put` を呼ぶと混在内容として遮断される。これを越えるには
Web Bluetooth か Web Serial しかないが、A があるので最初の版では作らない。

ブラウザ版には `Net::HTTP` が無い (`family_mruby_wasm.rb:71`。ソケットが無い)
ので、B ではページ側が取得する。

### 9.2 実機側の手順 (経路 A)

```
一覧を取る          registry.json を取得して解析 (picoruby-json)
      |
確かめる            app_env に自分がいるか / 画面 / ヒープ (8.4 節)
      |
一時に受ける        /tmp/install/<app_id>/ へ全ファイルを書く
      |
照合する            大きさと sha256 が一覧と一致するか
      |
翻訳する            large_memory を書き込む (8.4 節)
      |
入れ替える          /app/usr/<app_id>/ を消してから改名
      |
一覧を捨てる        /var/cache/launcher_index を削除
```

`/tmp` を経由するのは、途中で切れたときに動いているアプリを壊さないため。

`Net::HTTP` の性質として押さえておくこと:

- **転送先の自動追跡をしない** (`redirect?` はあるが呼び出し側の仕事)。
  `raw.githubusercontent.com` は直接返すので問題ないが、`github.com/.../raw/`
  を指してはいけない。
- 応答を丸ごと文字列で受ける。1 ファイルの上限を **256 KB** とし、これを超える
  ものは最初の版では配らない。

### 9.3 一覧への反映 — 落とし穴

起動時のアプリ走査は `/var/cache/launcher_index` を**無条件に信じる**。
実際にディレクトリを歩くのは右クリックの再走査のときだけである
(`launcher.rb:200-256`。全走査 7.8 秒を 0.29 秒にするための作り)。

**入れただけでは一覧に出てこない。** 導入の最後にこのファイルを消し、
「ランチャーを右クリックして再走査するか、次回起動で出る」と表示する。

一覧ファイルの形式は次のとおりで、追記して即時反映させることもできるが、
表示名が言語ごとに解決される点と 16 KB の上限があるため、最初の版では
削除だけにする。

```
1<TAB>en                                     ← 版と言語
Breakout<TAB>/app/usr/breakout/breakout.app.rb<TAB>R<TAB>usr/share/icon/ruby.icon
```

- 読み出しは先頭 16384 バイトのみ (`CACHE_MAX_BYTES`)。1 行約 60 バイトなので
  **約 250 個で頭打ちになり、超えた分は黙って消える**。
- 言語が変わると一覧全体が捨てられ、再走査が走る。

### 9.4 削除

`/app/usr/<app_id>/` を消し、一覧ファイルを消す。
`/home/apps/<app_id>/` は消さない (別に「記録も消す」を用意する)。

## 10. 絵

### 10.1 アイコン

最初の版ではアイコンを配らない。`icon` を書かなければ、ランチャーが拡張子から
既定のアイコンを選ぶ (`rb` → ruby、`lua` `bas` `py` も同様)。

配るようになったら、Web 用の PNG と実機用の BMP の**両方を CI で作る**。
人手で 2 つ置くと必ず片方が古くなる。

### 10.2 一覧に出すスクリーンショット

一覧の行に小さな絵を出す。名前だけの一覧より選びやすいため。

**作者が置くのは PNG 1 枚だけ** (`<app_id>.png`、原寸= その環境の画面のまま)。
実機用の BMP は CI が作る。

| 配布物 | 誰が作るか | 用途 | 大きさ |
|---|---|---|---|
| `<app_id>.png` | 作者 | ブラウザの店 | 原寸 (320x240 / 426x240) |
| `<app_id>.thumb.bmp` | CI | 実機の店 | **32x24** |

#### 生成は全部 Ruby でできる

外部の画像処理は要らない。読む側は `tools/fmrb_png.rb`
(`FmrbPng.read_rgb` → `[w, h, 1 画素 3 バイトの行]`、zlib だけ)、書く側は
`tool/gen_icon_bmp.rb` の BMP 書き出しがそのまま使える。

BMP は 8 ビット、**画素の値はパレットの番号ではなく RGB332 そのもの**
(実機の読み手はパレットを無視する)。パレットは普通の画像ビューアで開ける
ように書いておく。透明色は 0。縦横比が合わない分は 0 で埋める
(Retro のスクリーンショットは 4:3、Modern は 16:9)。

#### なぜ実機だけ小さいのか

実機は**画面と転送の両方**で効く。

| | Retro (窓の中 約 276x164) |
|---|---|
| 文字だけの行 (8 px) | 16 行見える |
| 32x24 の絵つきの行 (26 px) | **6 行** |
| 64x48 の絵つきの行 (50 px) | 3 行 |

転送はもっと効く。**スプライト 1 枚を実機の描画側へ渡すのに約 160 ms**
かかる (`doc/reference/boot_performance.md`: アイコン 6 枚で 1.33 秒)。
20 件を一度に並べると 3.2 秒かかる。

したがって**見えている行の分だけ、見えたときに読み込む**。一度読んだものは
残す (ランチャーが `@icon_sprite_images` でやっているのと同じ)。最初の 1 画面が
約 1 秒、そこから先はスクロールした分だけ増える。

ブラウザの店はページなので、この制約が両方とも無い。`<img>` で PNG をその
まま並べる (`raw.githubusercontent.com` は CORP を返すので COEP 下でも
読める。6 節)。

#### 詳細でも同じ絵を使う

大きい版は作らない。要ると分かってから足す。増やすと CI の生成物と
`registry.json` の欄が増え、片方が腐る道が 1 本増える。

## 11. ライセンスと安全

### 11.1 ライセンス

`family-mruby-apps` は **MIT** とする。本体 3 リポジトリ (GPL-3.0) に揃えない。
アプリ集の値打ちは読んで真似して自分の作品に取り込めることにあり、copyleft は
そこに摩擦を作るため。周辺リポジトリが本体と別のものを選ぶ前例は既にある
(installer は Apache-2.0、文書サイトは MIT)。

本体の GPL-3.0 はアプリに及ばない。アプリはファームウェアが実行時に読んで解釈
する脚本であってファームウェアの一部ではない、という立場を fmruby-core の
README に明記した。作者は好きなライセンスを選べる。

**本体は中央リポジトリに置く** (12 節)。よってリポジトリの LICENSE が全部を
覆い、これは後の段でも変わらない。README に「ここに出すことは MIT で公開する
ことへの同意である」と書く。`app_license` は任意で、書く場合は SPDX の識別子、
CI は表にある値かだけを見る。`app_source` は表示のための任意の欄であって、
取得には使わない。

### 11.2 安全

最初の版で持つもの:

- `sha256` と大きさの照合 (9.2)
- 書き込み先を `/app/usr/<app_id>/` に限る。`..` と絶対パスを含む `app_files`
  は CI が弾き、導入側でも弾く
- `app_id` は変更不可

**持たないもの**: 署名、発行者の信頼、権限、隔離、審査。配布物は作者が書いた
Ruby がそのまま動くものであり、**入れる操作は「そのコードを信じる」ことと同義**
である。この点を店の画面に明記する。

なお現状、開発用の `/fs/put` は認証なしで既定で有効
(`FMRB_DEV_REMOTE_CTL`、リリースでは無効) である。店が常用の導入経路になる
なら、この口は先に閉じる。

## 12. 段取り

| 段 | 内容 | 新しく要るもの |
|---|---|---|
| 1 | `family-mruby-apps` リポジトリ、`.app.toml` への鍵追加、CI が `registry.json` を生成 | CI の Ruby 一式 |
| 2 | ブラウザ版で一覧から選んで走らせる | ページの取得と `FS.writeFile`、`?app=<id>` の受け口 |
| 3 | 実機の店アプリ (経路 A)。「探す」と「入れたもの」の 2 面 | Ruby のアプリ 1 本 |
| 4 | 束 (複数ファイル・素材)、`app_version` の比較と入れ替え | — |
| 5 | アイコン、絞り込み、Web Serial での書き込み | — |

**段 3 までで構想は成立する。** 元の設計書の到達条件 (BLE で実機に入るまで) は、
経路 A があるので不要。ファームウェアの変更も段 3 まで発生しない (8.4 節)。

ブラウザ版のページには現在 `?autostart=1` `?theme=` `?drive=1` がある
(`main.js:232,300,1108,1215`)。段 2 で足すのは `?app=<id>` の 1 つだけ。

### 12.1 中央リポジトリだけにする

**アプリの本体を作者のリポジトリへ散らす案は採らない** (2026-09-02 決定)。
本体は `family-mruby-apps` に置き、取得元は 6 節の 1 か所だけとする。

これで消えるもの: 取得元ごとのヘッダの確認、`app_source` の必須化、作者
リポジトリ側のライセンス確認、複数の取得元にまたがる版のずれ。**11.1 の
ライセンスの話が後の段でも変わらない**のはこの決定による。

## 13. 更新と「入れたもの」の管理

### 13.1 自動更新はしない

**版が上がっても勝手に入れ替えない** (2026-09-02 決定)。起動のたびに一覧を
取りに行くと網が要り、起動の速さを削るため。代わりに**入れたものを管理する
面**を店アプリに持たせ、ユーザが見たときに新しい版があると分かるようにする。

### 13.2 店アプリの 2 つの面

1 本のアプリが 2 つの面を持つ (別々のアプリにはしない。320x240 に 2 本の
一覧を置くと窓が足りない)。

| 面 | 中身 |
|---|---|
| 探す | `registry.json` の一覧。分類での絞り込み。取ってくる |
| 入れたもの | 導入済みの一覧。版、入れた日、**新しい版の有無**、更新、削除 |

「入れたもの」は取得の進み具合もここに出す。

### 13.3 導入済みの記録

導入済みの識別と版は、**入れた `.app.toml` がそのまま持っている**
(`app_id` / `app_version`)。別の台帳は要らない。

台帳が要るのは 13.4 の指紋のためだけで、`/home/appstore/installed.toml` に
1 ファイルで持つ。

```toml
[breakout]
version = "1.0.0"
installed_at = "2026-09-02T10:00:00Z"
files = [
  { path = "breakout.app.toml", sha256 = "..." },
  { path = "breakout.app.rb",   sha256 = "..." },
]
```

### 13.4 入れ替えるときの三分岐

ユーザが手を入れた複製を壊さない。`doc/wasm/storage_persistence.md` が
`/home` について決めた規則をそのまま使う。

| 今の状態 | 判定 | 動作 |
|---|---|---|
| ファイルが無い | ユーザが消した | 足さない |
| `sha256` が記録と一致 | 未編集 | 新しい版で置き換える |
| `sha256` が違う | ユーザが編集した | 触らない。隣に `.new` を置いて知らせる |

**指紋は無料で手に入る。** `registry.json` が全ファイルの `sha256` を持って
いるので、導入時に書き写すだけでよい (`/home` 側は crc32 を別に計算する必要が
あった)。

### 13.5 取得の一貫性

一覧と本体を別々に取るので、その間にリポジトリが更新されると `sha256` が
合わなくなる。**合わなければ一覧を取り直して 1 度だけやり直し、それでも
合わなければ失敗とする。** 中央の 1 か所しか取得元が無い (12.1) ので、これで
足りる。

### 13.6 ブラウザには一覧ファイルの落とし穴が無い

9.3 の「入れただけでは出てこない」は実機だけの話である。ブラウザ版の永続化の
対象は `/home` と `/app/usr` だけで `/var` は入っていない (`main.js:475`)。
再読み込みのたびに全走査が走るので、入れたアプリは自動で一覧に出る。

## 14. 決めていないこと

- **一覧の部品**。`FmrbUI` に `Label` `Button` `Toggle` `Stepper` `Enum`
  `Scrollbar` `TextField` はあるが、**スクロールする一覧が無い**。店アプリの
  中に書き、汎用に切り出せそうなら `FmrbUI::List` へ引き上げる (plan.md P3)。
- **必要ヒープをどう測るか**。手順を文書にするだけとし、CI での自動計測は
  やらない (8.3 節)。
