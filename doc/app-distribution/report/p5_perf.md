# 店を実機の速さに合わせる (2026-09-02)

> 状態: 完了 (NARYA v4 で実測) | 一覧を行形式に、絵を焦点の 1 枚に、選択を
> 部分描画に。**解析 7.6 秒 → 0.12 秒、選択 0.3-0.44 秒 → 0.078 秒。**

ユーザの指摘 4 点 (店のスタック / 選択時のちらつき / 読み込みが重い /
JSON が重い) から。**先に測った**ところ、想像と違う内訳だった。

## 測った (NARYA v4, ESP32-P4)

| 工程 | 前 | 後 |
|---|---:|---:|
| 一覧の取得 | 990 ms (2858 B) | 867-1229 ms (973 B) |
| **一覧の解析** | **7597 ms** | **124 ms** |
| **選択の移動** | 300-440 ms | **78 ms** (定常) |
| 見える行数 | 3-4 | **8** |
| 店のスタック | 32 KB | 既定 (16 KB) |

**「読み込みが重い」の中身はほぼ全部 `JSON.parse` だった。** 網でも描画でも
サムネイルでもない。2858 バイトに 7.6 秒。

## 1. 一覧を行形式にした

C の JSON パーサを足すより、**JSON をやめる**方を採った。この機械には前例が
ある — RPG の地図は JSON 39.5 秒を詰めた形式にして 55 ms になった。ランチャーの
キャッシュもタブ区切りの行である。

`registry.tsv` を `registry.json` と**同じ通しで CI が書く**ので、ずれない。
版の行、`A` がアプリ 1 件、`F` がそのファイル。知らない先頭の字は読み飛ばすので、
後から行の種類を足せる。

一覧を読むのは**端末の店だけ**になった (店が OS のアプリになり、ページは
読まなくなった) ので、JSON は人と道具のために残るだけになる。

### C のパーサは別テーマとして価値がある

これで店は速くなったが、**この機械で JSON が実質使えない**という事実は残る。
Web の API を叩くアプリ全部に効く問題なので、`doc/reference/` に測定を残して
独立したテーマにするのが筋。ここでやるには重すぎた。

## 2. 絵は焦点の 1 枚だけ (ユーザ判断)

行ごとに出すのをやめ、**選択中のアプリの絵を詳細欄の隅に 1 枚**出す形にした。

- 行が 26 px から 11 px に戻り、**見える行が 3-4 から 8 に倍増**
- 表示側の画像枠の心配が消える (8 枠しかない)
- **Retro と Modern が同じ配置**になった。違いは「その 1 枚を出すかどうか」だけ

## 3. 選択は部分描画

全面の描き直しが 300-440 ms かかっており、**それがちらつきの正体**だった
(sim では 32 ms で、私は軽いと誤認していた。**PNG の復号と表示側への往復が
実機では桁違い**)。

選択で変わるのは**行 2 つと詳細欄だけ**なので、そこだけ描く。さらに
**復号した絵を 4 枚まで持ち回る**ようにした (`DISPLAY_P4_MAX_IMAGES` が 8 なので
他のアプリの分を残す)。

推移は 755 → 592 → 159 → **78 ms**。3 枚が載りきると定常 78 ms になる。

## 4. 店のスタックを既定に (ユーザ判断)

`task_stack_kb = 32` を外した。**JSON をやめたことで、深いスタックが要ると
思っていた理由自体が消えた。** 既定 16 KB で起動し、動く。

これで店は内蔵 RAM を 40 KB ではなく 24 KB しか取らない。**店が抱えた分は、
店が入れたアプリが使えない分**なので、ここは効く。

## 5. 進捗

`fetching the list...` → `reading the list...` → `3 apps - modern` と段階を
出すようにした。ただし**解析が 7.6 秒から 0.12 秒になったので、見せる相手が
ほぼ居なくなった**のが実際のところ。
