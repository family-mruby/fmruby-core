| 環境 | 結果 | ticks |
|---|---|---|
| Linux sim | ok 200 in 207ms | **1** |
| ブラウザ | ok 200 in 389ms | **4** |

**ticks が設計そのものを示している。** sim では `request` の中で待つので、
返ってきたときには終わっている (1 回目の `on_update` で done)。ブラウザでは

のはこの数字で確かめた。

## 掘り当てたバグ: `Content-Length` を文字数で数えていた

最初、raw.githubusercontent.com から**何も取れなかった** (`SSL read failed`)。
example.com と api.github.com は取れたので、ホストか TLS を疑い、SNI の
設定漏れを疑って 30 分使った (**posix ポートは SNI を設定していた。私の
`head` で見落としただけ**)。

切り分けの結果は違った。

| 取得先 | 中身 | 結果 |
|---|---|---|
| raw の `/` (301) | ASCII | **ok** |
| raw の `LICENSE` | ASCII | **ok** 1069 B |
| raw の `paint_pad.app.toml` | 日本語を含む | 失敗 |
| raw の `registry.json` | 日本語を含む | 失敗 |

**ホストではなく中身が効いていた。** `http_client.rb` の

```ruby
remaining = content_length - (response.length - header_end - 4)
```

`Content-Length` はバイト数、mruby の `String#length` は**文字数**。日本語が
入ると受信済みを少なく数え、`remaining` が 0 にならず、空のソケットをもう
一度読んで `SSL read failed` になる。`bytesize` に変えて直った。

**これは配布計画の土台を止めていた。** 一覧にも manifest にも日本語の名前と
説明が入る以上、直さなければ実機でも 1 本も落とせない。
`doc/reference/picoruby_upstream_pr_candidates.md` に上流 PR 候補として
記録した (fmrb 固有の要素は無いのでそのまま出せる)。

教訓は前にも踏んだもの: **mruby の `String#length` を長さとして使うと、
内容依存で発火する怪現象になる。**

## ブラウザ側の作りと、詰まった 3 点

取得は**ページのスレッドで走らせる**。機械の各タスクは pthread (= Worker) で、
`emscripten_thread_sleep` で止まっている間その Worker の JS は 1 行も動かない
ので、そこで `fetch` を投げても promise が解決しない。ファイル系の
システムコールが既に同じ形 (`proxyToMainThread`) なので、作りとして一貫する。

詰まったのは全部 C と JS の継ぎ目だった。

1. **`EM_JS` の中に `MAIN_THREAD_EM_ASM` を書いた。** 前者は JS 関数を吐き、
   後者は C マクロ。`{ if (...) ... }` がそのまま JS に出て、式の位置の
   ブレースはオブジェクトリテラルと読まれ、acorn が落ちる。
   **素の C 関数の中で `MAIN_THREAD_EM_ASM` を使うのが正しい。**
2. **`{ next: 1, tab: new Map() }` のカンマ。** ブレースは C プリプロセッサ
   からカンマを隠さない (隠すのは括弧)。マクロが引数を数え間違えて、
   `use of undeclared identifier 'var'` という読みにくいエラーになる。
   **オブジェクトリテラルは括弧で包む。**
3. **`async` / `await` / `||=` / `?.`** は acorn を通らなかった。ES5 の形で書く。
