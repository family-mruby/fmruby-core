# F1 report: フラッシュの書き込みと青いちらつき

> 状態: 完了 (親の検収とユーザの目視待ち) | 更新: 2026-10-02 | **原因はアンダーランではなく、走査の DMA が止まること**。フラッシュの消去 1 回 (33-49 ms) の間、IDF がキャッシュと IRAM 外の割り込みを止めるので、1 フレームごとに走査の DMA を掛け直す割り込みが走れず、DSI への送り出しが 35-56 ms 途切れる (1-9 フレーム欠落)。**CONFIG_SPI_FLASH_AUTO_SUSPEND=y で欠落は 0** (40 回の書き込みで最大の間隔 15.5 ms = 1 フレーム)。静的な D/IRAM は +76 バイト。板には自動中断の試験版が載っている

指示書: ../instruction_f1.md / 計画: ../plan.md / 前提: ../../naryav4/report/p6.md、../../reference/dpi_frame_buffer_alignment.md

## 1. 要約

- 保存 1 回の中身は「4 KB の消去 0-5 回 + 256 バイト単位の書き込み 2-18 回」。消去 1 回ごとに、キャッシュと IRAM 外の割り込みが 33-49 ms 止まる。書き込み 1 回の停止は 2 ms 以下。
- esp_lcd の DPI は、走査の DMA (DW-GDMA) を 1 フレームごとに「転送完了」割り込みの中で掛け直している (`mipi_dsi_dma_trans_done_cb`)。この割り込みは IRAM 安全ではない (今の sdkconfig: `CONFIG_LCD_DSI_ISR_CACHE_SAFE` 無効)。消去の間は走れないので、DMA はフレームの終わりで止まったままになる。
- 実測: 消去を含む保存のたびに、DMA の掛け直しの間隔が 15.1-15.3 ms (1 フレーム) から 35-56 ms に伸び、1-9 フレーム分の送り出しが抜けた。DSI ブリッジのアンダーランの割り込みは 0 件 (どの計測でも)。LT8912B は MIPI の入力が途切れると画面を青で塗る (p6 の B1 と同じ見え方) ので、これが青い点滅と見る。
- 書き込みの元 (遠隔のファイル転送、設定の保存、エディタの保存) はどれも LittleFS 経由で同じ形。違うのは消去の回数だけ。消去が無い保存 (エディタで既存の小さいファイルを上書き) では欠落は 0 だった。
- 自動中断 (`CONFIG_SPI_FLASH_AUTO_SUSPEND=y`) では、IDF がキャッシュを止めなくなる (`SPI_FLASH_CACHE_NO_DISABLE`)。消去の時間はそのままで、停止の窓が 0 件、欠落も 0 件になった。
- 別案の「DSI の割り込みを IRAM 安全にする」(`CONFIG_LCD_DSI_ISR_CACHE_SAFE=y`) でも欠落は 0 になった。こちらは CPU が消去の間 33-43 ms 止まるのは変わらない。比べた結果は 5 節。

## 2. 計測の方法

### 計装 (main/drivers/display_p4/flash_flicker_probe.c)

IDF は変えずに、リンカの `--wrap` で 4 か所に割り込んで数える。`-DFMRB_FLASH_PROBE=ON` のときだけ入る (既定は OFF。OFF のビルドでは `__wrap_` が map に現れないことを確かめた)。結果は 5 秒ごとの `render:` の行の後に `flash_probe:` の 3 行で出る。区間の値で、何も起きなかった区間 (短い読み出しだけ) は出さない。

| フック | 数えるもの |
|---|---|
| `spi_flash_disable/enable_interrupts_caches_and_other_cpu` | キャッシュと IRAM 外の割り込みが止まっている窓 (回数、合計、最大、長さの分布) |
| `esp_flash_erase_region` / `esp_flash_write` | 消去と書き込みの回数、バイト数、時間 |
| `dw_gdma_channel_enable_ctrl` | DPI の走査 DMA の掛け直し (1 フレームに 1 回)。間隔の最大、1.5 フレームを超えた回数 (`late`)、欠落フレーム数 (`lost`) |
| `esp_intr_alloc` | DSI ブリッジの割り込みだけを差し替え、アンダーランのビットを数えてから元の処理に渡す (`brg irq` / `underrun`) |

- 計装の費用 (ON のとき): 静的な D/IRAM +528 バイト、flash +2,154 バイト。
- 時間は CPU のサイクルカウンタ (400 MHz) で測る。フレームの長さは掛け直しの間隔の最小値 (15.1-15.3 ms。1280x720 80 MHz の 64.65 Hz = 15.47 ms より少し短く出るのは割り込みの遅れのばらつき)。

### 手順

- 板は P4-Nano (NARYAv4)、flash chip_id `0xC84018` (GigaDevice GD25Q128、16 MB、QIO 80 MHz)。CPU 400 MHz。
- ファームは app 区画だけを書いた (/home はそのまま)。ミュートは保ったまま (音量 6、ミュート)。
- 書き込みの試験 (scratchpad の `f1/trial.rb`):
  - put: 2 KB のファイルを `/fs/put` で `/home/probe2k.txt` に 5 回 (8 秒おき)。
  - 設定の保存: ミュートのまま `/audio/volume?level=5|6` を交互に 6 回 (9 秒おき)。約 2 秒後に system_conf (`audio_volume`) が保存される。`/audio/mute?on=1` はすでにミュートなので保存されない (値が変わらないと書かない実装)。
  - エディタ: メニューの Editor で新しいファイルを開き、1 文字ずつ足して Ctrl+S を 4 回 (最初の 1 回は名前を付けて保存)。
- 速さ (`f1/perf2.rb`): 待機 30 秒の `render:` と、遠隔入力でマウスを 150 回動かす間 (2 回の put を含む) の `render:` と `cursor:`。
- 3 つのビルドはすべて同じソース (`feature/flash-write-flicker` の作業ツリー、計装 ON)。違いは sdkconfig だけ。
  - 基準: `config/sdkconfig.defaults.naryav4` のまま (`build/`)。
  - 自動中断 (AS): 追加の defaults `CONFIG_SPI_FLASH_AUTO_SUSPEND=y` (scratchpad の `f1/as.defaults`、`f1/build_as/`)。
  - DSI の割り込みを IRAM 安全に (CS): 追加の defaults `CONFIG_LCD_DSI_ISR_CACHE_SAFE=y` (`f1/cs.defaults`、`f1/build_cs/`)。
  - 試験のビルドは `idf.py -B <scratchpad> -DSDKCONFIG=<scratchpad>/sdkconfig "-DSDKCONFIG_DEFAULTS=config/sdkconfig.defaults.naryav4;<追加>"`。リポジトリの sdkconfig と sdkconfig.defaults* は触っていない。

## 3. 仕組み (T1)

### 保存 1 回の中身 (基準)

| 書き込み元 | 消去 (4 KB) | 書き込み | 停止の窓 (最大) | 走査の間隔 (最大) | 欠落フレーム | アンダーラン |
|---|---|---|---|---|---|---|
| put 2 KB (5 回 + 予備 3 回) | 1 回 33-42 ms | 9 回 計 6.8-7.6 ms (1 回 ≤2.0 ms) | 32.5-41.6 ms | 35.3-56.3 ms | 1-2 | 0 |
| 設定の保存 (6 回) | 2 回 計 66-73 ms (1 回だけ 5 回 198 ms) | 13 回 計 12-16 ms | 33.8-46.0 ms | 43.2-50.5 ms | 2-3 (5 回の時 9) | 0 |
| エディタ、新しいファイル | 3 回 計 117 ms | 3 回 計 3.9 ms | 40.6 ms | 47.4 ms | 4 | 0 |
| エディタ、既存の小さいファイル (3 回) | 0 | 2 回 計 1.4-1.7 ms | 0.2 ms | 15.5 ms | 0 | 0 |

- 停止の窓の長さはほぼ消去 1 回の時間と同じ。分布でも「20-50 ms の窓 = 消去の回数」「1-5 ms の窓 = 書き込み」と分かれた。
- **欠落は消去と一緒にしか出ない**。書き込みだけ (≤2 ms の窓) の保存では、走査の間隔は 1 フレームのまま。
- 消去の回数は LittleFS の状態で決まる。同じ put でも 1 回目が 2 回になることがある。system_conf の保存は毎回 2 回以上消去する。
- 読み出し (LittleFS の読み込み) も同じ関数でキャッシュを止める。起動から最初の 6 秒で 5,361 回あったが、どれも 0.4 ms 未満で、欠落は 0。
- 走査の間隔は「停止の窓 + 掛け直しを待っていた残り」で、窓より数 ms から 1 フレーム長い。

### なぜ止まるか

1. LittleFS の消去・書き込みは `esp_flash_*` → `spi1_start()` → `spi_flash_disable_interrupts_caches_and_other_cpu()` を通る。自動中断が無効なら、ここでキャッシュを止め、両方の CPU で IRAM 外の割り込みを止める (`esp_intr_noniram_disable`)。
2. esp_lcd の DPI は、フレームバッファ 1 枚分の転送が終わるたびに、DW-GDMA の「全転送完了」割り込みの中で同じ連結リストを掛け直す (`esp_lcd_panel_dpi.c` の `mipi_dsi_dma_trans_done_cb`)。循環する記述子ではないので、掛け直さないと次のフレームが送られない。
3. この割り込みは `CONFIG_LCD_DSI_ISR_CACHE_SAFE` (と、それが選ぶ `DW_GDMA_ISR_IRAM_SAFE`) が無効だと IRAM 外の割り込みとして登録される。1 の間は走れない。
4. 結果、消去の間 DSI ブリッジに画素が来ない。ブリッジのアンダーランの割り込みは出ない (0 件)。流れの制御は DMA 側なので、ブリッジは「遅れた」ではなく「来ない」状態になると見る。LT8912B は MIPI の入力が途切れると画面を青で塗る。

- 見えた症状と時間の桁は合う: 欠落は 1 回の保存で 35-200 ms。
- ブリッジ (LT8912B) の同期が外れたかどうかは、I2C のレジスタを読んでいないので確かめていない。読める口はある (`Detected MIPI input` を出すドライバの関数) が、保存の最中に読むには表示タスクと I2C を取り合うので、今回はしていない。

### p6 との違い

- p6 の青ちらつきは、PSRAM の読み出しが間に合わない**アンダーラン**だった (`underrun happens` がログに出る、FB の 4 KB 揃えで解消)。今回は**送り出しの停止**で、アンダーランの割り込みは 0 件。FB は揃っている (`fb @0x49150000 (aligned, pad 3712)`)。
- plan.md の「キャッシュが止まっている間は割り込みのログ自体が出せない」という見立ては半分正しい。出せないのではなく、アンダーランそのものが起きていなかった。割り込みを止めていたのは書き込みではなく、DMA の掛け直しの方だった。

## 4. 自動中断を試す (T2)

### Kconfig の変化

`CONFIG_SPI_FLASH_AUTO_SUSPEND=y` を足すと、sdkconfig は次のように変わる (基準との diff)。

- `CONFIG_SPI_FLASH_AUTO_SUSPEND=y`、`# CONFIG_SPI_FLASH_AUTO_CHECK_SUSPEND_STATUS is not set` (新たに現れる)。
- `CONFIG_ESP_HW_SUPPORT_FUNC_IN_IRAM=y` の行が消える (自動中断のときは選べない設定)。
- 次の「キャッシュが止まっている間も動く ISR」の設定が、意味が無くなって消える: `GPTIMER_ISR_CACHE_SAFE`、`MCPWM_ISR_CACHE_SAFE`、`RMT_TX/RX_ISR_CACHE_SAFE`、`RMT_ISR_IRAM_SAFE`、`TWAI_ISR_CACHE_SAFE`、`UHCI_ISR_CACHE_SAFE`、`LCD_DSI_ISR_CACHE_SAFE`、`GPTIMER/MCPWM/LCD_DSI_ISR_IRAM_SAFE`。どれも今は無効なので、動作は変わらない。
- `CONFIG_SPI_FLASH_SUSPEND_TSUS_VAL_US=50` / `TRS_VAL_US=50` は既定のまま。
- ブートローダは同じ (差はビルド時刻の文字列 37 バイトだけ)。

起動ログに `W spi_flash: Flash suspend feature is enabled` が出る。この flash (`0xC84018`) は IDF の GD の対応表に入っている (`spi_flash_chip_gd.c`)。

### IRAM の増減

| | 静的な D/IRAM | .text (IRAM) | .bss | flash | 起動 10 秒後の `IRAM free:` |
|---|---:|---:|---:|---:|---:|
| 基準 (計装 ON) | 126,052 | 85,552 | 25,456 | 6,222,078 | 209,932-209,948 (4 回) |
| 自動中断 | **+76** | +72 | +4 | +240 | 209,880 (2 回、-52 から -68) |
| DSI 割り込みを IRAM 安全に | **0** | 0 | 0 | +456 | 209,816 (1 回、-116 から -132) |

- 自動中断は IRAM のコードを 72 バイト増やす。`ESP_HW_SUPPORT_FUNC_IN_IRAM` が既定で n になって一部の関数が flash へ移る分と、中断の制御が IRAM に足される分の差し引き。
- CS は静的には 0 だが、DW-GDMA の管理領域が内蔵 RAM に置かれる (`DW_GDMA_OBJ_DRAM_SAFE`) ので、実行時に約 120 バイト減る。
- どちらも内蔵 RAM の決まり (増分 0 が最低線) からは外れるが、100 バイト前後。採るなら量を書いて親に判断を仰ぐ。

## 5. 2 つの案の比べ

| | 自動中断 (AS) | DSI 割り込みを IRAM 安全に (CS) |
|---|---|---|
| 青い点滅 (欠落) | 0 | 0 |
| 消去の間の CPU | 止まらない (コードの実行がフラッシュを読むときだけ消去を一時停止する) | 両 CPU が 33-49 ms 止まる (今と同じ。入力・音・描画も止まる) |
| 内蔵 RAM | 静的 +76、実行時 約 -60 | 静的 0、実行時 約 -120 |
| flash の型番への依存 | **ある**。IDF の対応表に無い flash だと、起動時に `esp_flash_init_default_chip` が失敗して assert で止まる (起動しない)。今の P4-Nano の GD25Q128 は表にある | 無い |
| 他の割り込み | 止まらなくなる (ほかの周辺も得をする) | DSI と DW-GDMA だけが救われる |
| 本家の注意書き | "READ DOCS FIRST"。対応する flash と SoC の組に限る、OTA 先のブートローダに対応が要る (IDF v4.3 以降。今は 5.5.4 で同じ版) | 特に無い |

- 見立て: **NARYAv4 は自動中断を第一に勧める**。点滅を消すだけでなく、保存の間に入力や音が 40 ms ずつ止まることも消える。ただし専用基板で flash の型番が変わると起動しなくなるので、部品表で型番を固定するか、そのときに CS に切り替える。
- CS は「型番に依存しない保険」として手札に残す。点滅は消えるが、CPU の停止は残る。
- Tab5 (`config/sdkconfig.defaults.p4`) は今回試していない。Tab5 の flash の型番を確かめてから (計装の起動時の `flash chip_id=` 行で読める) 判断する。Tab5 で点滅が出るかも未確認。

## 6. 採用するなら変える sdkconfig.defaults の差分 (案)

NARYAv4 だけ。sdkconfig.defaults* は編集禁止なので、ここに案として書く (コミットしていない)。

```diff
--- a/config/sdkconfig.defaults.naryav4
+++ b/config/sdkconfig.defaults.naryav4
@@
+# Let SPI flash erase/program suspend for cache misses instead of stopping
+# the cache and every non-IRAM interrupt. Without it each 4 KB erase (33-49 ms)
+# blocks the DPI scan-out DMA re-arm ISR and the HDMI picture blinks blue
+# (doc/flash_write_flicker/report/f1.md). The flash must be in IDF's suspend
+# list (P4-Nano: GD25Q128, 0xC84018) or the app asserts at boot.
+CONFIG_SPI_FLASH_AUTO_SUSPEND=y
```

代わりに CS を採るなら:

```diff
+# Keep the DSI/DW-GDMA ISRs running while flash writes stop the cache, so the
+# DPI scan-out DMA is re-armed every frame (doc/flash_write_flicker/report/f1.md).
+CONFIG_LCD_DSI_ISR_CACHE_SAFE=y
```

適用するときは `rake clean_all` から。

## 7. 見立てと違った点

- アンダーランではなかった。p6 の続きとして「保存の書き込みが PSRAM を混ませてアンダーラン」を疑っていたが、アンダーランの割り込みは 0 件で、FB も揃っていた。止まっていたのは送り出しの DMA の掛け直しだった。
- 消去でしか起きない。書き込み (256 バイトずつ、1 回 2 ms 以下) では 1 フレームも抜けない。エディタで既存の小さいファイルを上書きしたときは消去が無く、点滅の原因になる区間も無かった。ユーザの「保存のたびに」は、system_conf の保存が毎回 2 回以上消去することと、新しいファイル・大きめのファイルの保存で消去が入ることで説明できる。
- 自動中断で保存は速くならない。消去の時間は変わらない (CPU が止まらなくなるだけ)。
- `CONFIG_LCD_DSI_ISR_CACHE_SAFE` は自動中断を有効にすると選べなくなる (Kconfig の `if !SPI_FLASH_AUTO_SUSPEND`)。2 つは「どちらか」の関係。

## 板の状態と、ユーザに試してほしいこと

- **板 (P4-Nano / NARYAv4) のファーム: 自動中断の試験版**。ソースは `feature/flash-write-flicker` の F1 のコミット (計装 ON)、sdkconfig は `config/sdkconfig.defaults.naryav4` + `CONFIG_SPI_FLASH_AUTO_SUSPEND=y`。scratchpad の `f1/build_as/fmruby-core.bin` (md5 `5b3facf1...`)。app 区画だけ書いた。起動ログに `Flash suspend feature is enabled` が出ている。

- ユーザに試してほしい操作 (HDMI の画面を見ながら。どれも前は青く点滅していたもの):
  1. エディタで新しいファイルを作って保存する。続けて数文字足して Ctrl+S を数回。
  2. 音量を変える (メニューやダイアログから。ミュートのままでも保存される)。ミュートの切り替えも、音が出てよければ試す。
  3. Config など、system_conf を書く設定を 1 つ変えて保存する。
  4. (できれば) 少し大きめのファイル (数十 KB) の保存。
  - 見るのは「保存した直後に画面が青く点滅しないか」。点滅が消えていれば自動中断を採る判断材料になる。
