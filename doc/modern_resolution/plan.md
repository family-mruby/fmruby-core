# P4-Nano の画面を 640x360 にする (解像度を切り替えられるようにする)

> 状態: 進行中 | 更新: 2026-11-18 | P4-Nano (NARYAv4、HDMI) のデスクトップを、今の 426x240 (3 倍) から、エディタの全画面で使っている 640x360 (2 倍) を既定にする。Tab5 は 426x240 のまま。解像度は簡単に切り替えられるようにする。R0 (調査と計測) 済: 640x360 はデスクトップだけで 1 フレーム約 42 ms (426x240 は約 27 ms)。合成の手当て (R0b) 済: 426x240 は 27.4 → 約 20 ms、640x360 は 41.5 → 約 25 ms で、既定にする線 (手当ての前の 426x240 より遅くならない) は場面 1〜4 の平均で合格 (report/r0b.md)。残りの時間の 2/3 は拡大して出す SRM (16.7 ms)。さらに速くする調査は今は行わず課題に残した (doc/reference/TODO.md、成果の一枚は doc/reference/display_frame_time.md)。R1a 済: Config の「画面の解像度」で 426x240 / 640x360 を選べる (既定は 426x240)、Shift を押したまま起動すると 426x240 (report/r1a.md)。R1b 済: 640x360 のデスクトップで、属性の無い全画面のアプリの間だけ 426x240 に切り替わる。どの大きさでも描けるアプリは `.app.toml` の `fullscreen_any_size = true` で外す (report/r1b.md)。ユーザが P4-Nano の HDMI で 640x360 を確認 (問題なし。戻り道の Shift は押しっぱなしでは効かず連打で効いた)。R2 済: P4-Nano の既定は 640x360、Shift は押しっぱなしでも読む作りにした (report/r2.md。実物の押しっぱなしはユーザの確認待ち)。残り: ユーザの確認、sim の VM プール (regress:run)、develop への取り込み

## 1. 目的

P4-Nano は「作る機械」(HDMI のモニタ + キーボード) で、エディタと AI ヘルパーを並べる使い方が出てきた
(doc/editor_multi_file、doc/ai_coding)。426x240 では Window を 2 つ並べると窮屈で、物足りない。
640x360 は面積が 2.25 倍で、1280x720 にちょうど 2 倍で収まる。エディタの全画面ではもう使っている
(doc/reference/fullscreen_hires.md)。これをデスクトップごとの既定にする。

Tab5 は 5 インチのパネルで、640x360 にすると字とタッチの的が小さくなる。**Tab5 の既定は変えない**。

## 2. 決めたこと (2026-11-18 ユーザ)

1. 対象は P4-Nano (NARYAv4) だけ。Tab5 はそのまま (426x240)。
2. 解像度は、なるべく簡単に切り替えられるようにする。
3. 性能の計測を計画に含める (測ってから既定にする)。
4. 切り替えの操作は Config アプリの項目で、選ぶと再起動する (再起動なしの切り替えは範囲の外)。
5. 640x360 のデスクトップで、高解像度の属性の無い全画面のアプリが前にいる間だけ、画面を 426x240 に
   切り替える (4.3。成り立つかは R0 で確認する)。
6. 戻り道は、決まったキーを押しながら起動すると、設定を見ずに 426x240 で上がる形。
7. Tab5 にも切り替えの項目を出す (既定は 426x240 のまま)。
8. (R0 の結果を見て) **合成の手当てを先に行う** (R0b)。その後に測り直して R1 へ進む。
9. 既定にする線は **「手当ての後の 640x360 が、同じ場面で、手当ての前の 426x240 の実測より遅くならない」**
   (R0 の表: デスクトップだけ 27.4 ms、Window のエディタで打鍵 28.7 ms、Window 4 つのドラッグ 32.8 ms、
   動くデモ 1 つ 27.7 ms・2 つ 30.6 ms。report/r0.md 4.2)。
12. (HDMI で確認の後) デスクトップのアイコンの並びは今のまま。Window の最初の大きさと位置も今のまま
    (解像度で大きさを変える話は、ブラウザ版・ネイティブ版も併せて別に検討する)。戻り道の Shift は
    押しっぱなしでも効くように直す (作れなければ案内を「連打」に直す)。
11. (R0b の後) さらに速くする調査 (変わった所だけ合成、SRM、PSRAM の写しの DMA 化) は今は行わず、課題に残す
    (doc/reference/TODO.md)。R1 に進む。
10. PSRAM の写しが遅く見える件 (約 33 MB/s) は、原因を調べて提案までにする (sdkconfig は編集しない)。

## 3. 分かっていること (2026-11-18、コードと文書を読んだ範囲。試していない)

- 画面の大きさは `/etc/system_conf.toml` の `display_width`・`display_height` (元は
  `config/system_conf_naryav4.toml`・`system_conf_tab5.toml`、どちらも 426x240)。端末の
  `/etc/system_conf.toml` は `app_sync` で焼いても端末のものが残る。
- 表示の後段 (`main/drivers/display_local/`) は、フレームの大きさから倍率を決める
  (`display_scale_for`: 426x240 は 3 倍、640x360 は 2 倍)。640x360 のフレームを出す道は、全画面の
  高解像度モードで P4-Nano・Tab5・ブラウザ版・sim で動いている。
- デスクトップは 640x360 を知っている: 壁紙は 426x240・640x360・852x480・1280x720 が入っていて
  (`BG_SIZES`、`flash/usr/share/backgrounds/`)、ブラウザ版は 640x360 と 852x480 のページを選べる。
  つまり **640x360 のデスクトップで複数の Window を重ねる動きは、ブラウザ版では動いている**。
  ESP32 では動かしたことがない。
- 426x240 を決め打ちしている所 (grep の結果。R0 で全部洗う):
  - `main/app/fmrb_app.c` の `fmrb_app_fullscreen_hires_size`: `display_width == 426 && display_height == 240`
    のときだけ高解像度の全画面を許す。
  - `main/drivers/touch/touch_task.c` の `TOUCH_VIRTUAL_W` (Tab5 だけ。P4-Nano はタッチ無し)。
  - 遠隔の画面 (`main/drivers/remote_desktop/`): `rd_encoder_jpeg_init(426, 240, ...)`、流れの大きさの
    既定 426x240。高解像度の全画面のときに 640x360 へ切り替える道はある。
  - `mouse_scale_x/y = 0.5` (system_conf)。画素が細かくなると、同じ手の動きでポインタが進む距離が
    画面の上では 2/3 になる。
  - `main/ruby/default_app/appstore.app.rb` の端末の種類の表 (`modern` は 426x240)、
    `system_desktop/desktop_common.rb` のアプリの `screens` (`"426x240"`)。
- メモリ: canvas (Window 1 つ + デスクトップ) ごとに PSRAM を使い、端末では 8 個まで
  (`DISPLAY_LOCAL_MAX_CANVAS`)。合成のフレームバッファは 426x240 から 640x360 で約 2.25 倍。
  Window の canvas が Window の大きさか画面の大きさかは R0 で確認する。以前の見積もり
  (doc/editor_serious_mode/plan.md 4 章) は「fb +256 KB、全画面の canvas 1 枚 +460 KB、PSRAM 32 MB で
  問題なし。未知数は 2.25 倍になったキャッシュの同期と、遠隔の画面の写しのコスト」。
- 速さ: **測ったことがない**。今の計装 (`GFX STATS`) は 1 秒あたりのコマンドと present の数だけで、
  1 フレームを合成して出す時間が無い。以前の計画も「計測してから判断」のまま、全画面だけを
  高解像度にする形 (doc/fullscreen_hires) に置き換えて閉じた。
- 以前に全体の切り替えを見送った理由は、速さが未知だったことと、全画面だけの切り替えで足りたこと。
  今は「Window を並べたい」という新しい理由がある。

## 4. 方針

### 4.1 解像度は「選べる値」にする
- Modern の解像度は **426x240 と 640x360 の 2 つ** から選ぶ (ほかの値は受け付けない)。値は今と同じ
  `system_conf.toml` の `display_width`・`display_height`。
- コードの中の「426x240 なら」という決め打ちを、「今の画面の大きさ」か「Modern の解像度の表」を
  見る形に直す。どちらの解像度でも同じファームで動く (ビルドを分けない)。
- **切り替えの操作**: Config アプリに「画面の細かさ」(標準 426x240 / 細かい 640x360) を置き、選ぶと
  `/etc/system_conf.toml` を書き換えて再起動する (項目の名前は 9 章)。再起動なしの切り替えは、
  動いているアプリの Window と canvas を作り直す必要があり、この計画の範囲に入れない。
- 戻り道: 決まったキーを押しながら起動すると、設定を見ずに 426x240 で上がる (どのキーかは 9 章)。

### 4.2 既定は端末ごと
- `config/system_conf_naryav4.toml` を 640x360 にする (R0 の計測で合格した後)。
  `config/system_conf_tab5.toml` は 426x240 のまま。
- 今 426x240 で動いている P4-Nano は、`/etc/system_conf.toml` が端末に残るので、更新しただけでは
  変わらない。Config で選ぶ (か、設定を消して既定に戻す)。

### 4.3 640x360 のデスクトップでの、今あるアプリの見え方
- Window のアプリ: Window の大きさ (画素) はそのままなので、画面の上では約 2/3 の大きさに見える。
  HDMI のモニタでは読める見立て。小さすぎるものは R2 で個別に見る。
- **全画面のアプリ (高解像度の属性なし)**: 426x240 に合わせて描くゲーム・デモが多い。640x360 の
  画面の左上に小さく出るのを避けるため、**そのアプリが全画面で一番上にいる間だけ、画面を 426x240
  (3 倍) に切り替える** (今の高解像度モードの逆向き。同じ `SET_SCREEN_MODE` の道を使う見立て)。
  できるかどうかと、切り替えの一瞬の乱れは R0 で確認する。
- 全画面のアプリ (高解像度の属性あり。エディタ・麻雀など): 切り替えなしでそのまま 640x360。

### 4.4 速さを落とさない
- R0 で 1 フレームの時間を測る計装を入れ、426x240 と 640x360 を同じ場面で比べる。
- 合格の線 (7 章) に届かなければ、既定にはせず、切り替えの選択肢としてだけ残すか、合成の手当て
  (変わった所だけ合成する範囲の見直しなど) を別の段として起こす。どちらにするかはユーザが決める。
- 内蔵 RAM を増やさない (増える分は PSRAM だけ)。

## 6. 計測する場面 (R0)

P4-Nano の実機で、426x240 と 640x360 のそれぞれについて、同じコミットのビルドで測る。

1. デスクトップだけ (何もしない)。
2. Window のエディタで打ち続ける (1 打鍵から画面に出るまで、`spx: hid_lat`)。
3. Window を 4 つ重ねて (エディタ・AI ヘルパー・ファイルマネージャ・動くデモ)、一番上を動かす (ドラッグ)。
4. 動くデモ (毎フレーム描くもの) を Window で 1 つ・2 つ。
5. 全画面のエディタ (今と同じ道。変わらないことの確認)。
6. 遠隔の画面を見ながらの 3 (写しのコスト)。

取る値: 1 フレームの時間 (合成・出力・同期の内訳、平均と最悪)、1 秒あたりの present、入力の遅れ、
PSRAM と内蔵 RAM の空き、タスクのスタックの底。

## 7. 受け入れ条件

1. (R0) 6 章の場面の表が report にあり、426x240 と 640x360 を同じ場面で比べられる。決め打ちの一覧がある。
2. (R0b) 既定にする線 (2 章の 9): 手当ての後の 640x360 が、場面 1〜4 で、手当ての前の 426x240 の
   実測より遅くならない。手当ての前後で、出る絵が変わらない。
3. (R1) 同じファームで、Config から 426x240 と 640x360 を切り替えられる。どちらでも、デスクトップ・
   Window のアプリ・全画面のエディタ・遠隔の画面 (画面と入力の座標)・マウスの進み方が正しい。
4. (R1) 640x360 のとき、高解像度の属性の無い全画面のアプリが、小さく左上に出ない (4.3)。
5. (R1) Tab5 は何も変わらない (既定のまま、`rake regress`・`regress:screens`・`regress:size` が通る)。
   内蔵 RAM が増えていない。
6. (R2) P4-Nano を新しく焼くと 640x360 で起動する。組み込みのアプリと見本を一通り開いて、使えない
   ものが無い (小さいだけのものは一覧にして、直すかをユーザが決める)。
7. (R2) HDMI のモニタでのユーザの目視 (字の読みやすさ、デスクトップの並び)。

## 8. 範囲の外

- Tab5 の既定を変えること。Retro (320x240)。
- 640x360 より上の解像度 (852x480、1280x720) を ESP32 で出すこと。
- 再起動なしの解像度の切り替え。
- 426x240 向けに作ったアプリを 640x360 向けに作り直すこと (R2 で見つけた分は一覧にするだけ)。
- エディタ・AI ヘルパーの UI の細かい改善 (別に相談)。
