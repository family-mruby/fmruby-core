## 0. 先に書くこと (止まった所)

- **P4-Nano のシリアルが使えない**。11:45 ごろ、Windows の `usbipd list` で CH343 (4-2) が
  `0000:0002 不明な USB デバイス (デバイス記述子要求の失敗)` になった。それ以後は
  `rake attach` が「一致する機器が無い」で止まる。直すには **USB を物理的に差し直す必要がある
  (ユーザの作業)**。その前にも、同じポートでログの取り込みが 3 回止まっていた (5.4 節)。
- 計装の時間はシリアルのログにしか出ない。そのため **640x360 の場面 3 (Window 4 つ)・4 (動くデモ)・
  5 (全画面のエディタ)・6 (遠隔の画面) と、場面 1・2 の 2 回目は測れていない**。
  再開の手順は 9 章に書いた。
- 端末は WiFi では答えている。`/etc/system_conf.toml` は退避しておいた元のものに戻した
  (md5 `bd8b1036...` が一致)。再起動して 426x240 で上がることは、遠隔の画面
  (432x240 の JPEG) で確認した。ファームは計装入りのもの (このブランチの作業の木) のまま。
- 測っている間に、426x240 で **Interrupt WDT の panic が 1 回** 出た (5.5 節)。
  lwIP の tcpip タスクの中で起きたもので、解像度とも計装とも関係しない見立て。

  全画面の大きさの canvas 2 枚 (デスクトップの壁紙 z=0 と、メニューバーの層 z=254) の blend、

- 640x360 にすると、clear は 3.9 から 9.0 ms (2.3 倍)、blend は 7.5 から 14.8 ms (2.0 倍) に増えた。
  SRM は 15.0 から 16.7 ms (1.1 倍) でほぼ変わらない (出力は 1280x720 で同じ)。
  全体では 1.5 倍になった。
- **既定にする線 (plan 7 章の 2) に対しては不合格の見込み**。1 フレーム 33 ms 以内は、測れた場面 1・2 で
  既に超えている。3・4 も、区間の和から見積もると 42〜46 ms になる。入力の遅れの 1.5 倍以内は、
  エディタの処理 (`edit_lat`) は解像度で変わらなかった。画面に出るまでは 1 フレーム分の差
  (約 +14 ms) だけ遅れる見積もりで、1.3 倍前後になる (測っていない。4.2 節)。
- メモリは、PSRAM が見立てどおりに増え、内蔵 RAM は増えなかった。起動直後で 1.28 MB 減る
  (フレームバッファ +256 KB、デスクトップの canvas 2 枚 x 2 面で +1.0 MB)。Window 1 枚ごとに
  +512 KB。内蔵 RAM は起動の段ごとの値 (`M1|`) が同じだった。
- 640x360 でもデスクトップは起動する。ESP32 では、決め打ちの直しなしで起動・ランチャー・Window・
  ファイルマネージャまで動いた。sim は共有メモリの上限 (480x320) で起動しない。
  高解像度の属性が無い全画面のアプリは、左上に寄るか、中途半端な配置になった (3 章)。
- 全画面のアプリを 426x240 へ切り替える道は、今の `SET_SCREEN_MODE` を一般化すれば成り立つと判断した
  (7 章)。

## 2. 計装 (コミットするもの)

### 2.1 何を測るか

`main/drivers/display_local/display_local_task.cpp` の `render_frame` の区間ごとに時刻を読む
(`fmrb_hal_time_get_us`)。output backend の内訳は、`display_backend.h` に足した
`g_display_backend_timing` に PPA の backend が足し込む。

| 区間 | 中身 |
|---|---|
| `total` | `render_frame` 全体 |
| `clear` | フレームバッファの CPU による clear (`g_framebuffer->clear(0)`) |
| `compose` | 見えている canvas を全部 blend し、その上に sprite を合成するまで |
| `compose (sync)` | 上のうち、キャッシュの write-back と invalidate (`esp_cache_msync`: canvas の行・fb 全体の C2M、fb 全体の M2C) |
| `compose (hw)` | 上のうち、PPA Blend の実行 (blocking) |
| `capture` | 遠隔の画面のための写し (memcpy)。写したフレームだけで平均を取り、`n=` が写した数 |
| `out` | カーソルの焼き込み、拡大して出す処理、戻し。枠の黒塗り (大きさが変わったとき) も含む |
| `out (sync)` | 上のうち、fb の write-back (`present_flush`) |
| `out (hw)` | 上のうち、PPA SRM (拡大と RGB565 から RGB888 への変換) の実行 |
| `commit` | present (`PUSH_CANVAS` で画面へ) のたびの working から committed への memcpy。描画の外、コマンドの処理の中で起きる |

### 2.2 ログの出方

今ある 5 秒周期の `render:` の行の直後に 2 行を足した (同じ周期。描画が無い 5 秒には出ない)。

```
I (11:13:03.003) display_local: frame: n=5 fb=426x240 cv=2/2 blk=2 | us avg/max total=27462/30300 clear=3974/4160 compose=8469/10983 (sync=699/820 hw=7523/9779) capture=0/0 n=0 out=15015/15366 (sync=8/9 hw=14978/15322)
I (11:13:03.022) display_local: frame commit: n=5 avg=6251us max=6671us avg_bytes=204480
```

- `n` はその 5 秒のフレーム数。`fb` はログを出した時点の fb の大きさ。5 秒の間に高解像度モードへ
  出入りすると、大きさの違うフレームが混ざる。
- `cv=平均/最大` は合成した canvas の数、`blk` は blend の回数の平均 (viewport の canvas は 1 枚で最大 4 回)。
- 時間は µs で、`平均/最悪` の形。sync と hw は PPA の backend だけが入れる。CPU の backend、
  ブラウザ版、ネイティブ版では 0 になる。
- `GFX STATS` (`host` の行、debug_mode のときだけ出る) は core 側の present/s のまま。
  フレームの時間は display タスクの行に置いた。`GFX STATS` は core の host_task にあり、
  sim・ネイティブ版・ブラウザ版と共有している。表示の内訳を持っているのは display タスクだけなので、
  そちらに出した。
- ネイティブ版でも同じ行が出ることを確認した (`/tmp/fmrb-native-1000/core.log`。
  `total=200/266 ... (sync=0/0 hw=0/0)`)。

### 2.3 コスト

- 1 フレームで時刻を 6 回、blend 1 回ごとに 3〜4 回、SRM で 2 回読む (esp_timer)。
  ログは今の周期の行に 2 行を足しただけ。
- 静的な変数は PSRAM (`FMRB_EXT_RAM_BSS_ATTR`) に置いた。`s_ft` は約 130 バイト、
  `g_display_backend_timing` は 16 バイト。内蔵 RAM は `rake regress:size` で確認した (8 章)。
- 計った限り、計装の前後で 1 フレームの時間は変わらない。今ある `render: ... avg=27ms` (tick の ms) と
  `total` の平均 27.4 ms が一致している。

## 4. P4-Nano の計測

### 4.1 やり方

- ファーム: このブランチの作業の木 (計装入り)。`FMRB_HW_TARGET=NARYAv4 rake build:esp32` で作り、
  `FMRB_HW_TARGET=NARYAv4 FLASH_BAUD=115200 HOST=192.0.2.20 PORT=/dev/ttyACM0 rake flash:app_sync`
  で焼いた (flash 331 秒、sync 74 秒)。426x240 も 640x360 も同じビルド。
- 解像度は端末の `/etc/system_conf.toml` を書き換えて切り替えた。退避してから、
  `display_width`・`display_height` の 2 行だけを変えたものを `fmrb_rd_fs.rb put` で置き、
  `fmrb_rd_fs.rb reboot` で再起動した。権限の判定では断られなかった。
  **試しのビルドで解像度を上書きする形は使っていない**。
- 操作は `tools/fmrb_rd_input.rb`・`curl /app/launch`・`fmrb_rd_snap.rb`。場面ごとに
  開始と終了の時刻を記録し (端末とホストの時計は一致していた)、その間のログの行を集めた。
  台本と集計の道具は手元だけに置いた (`tmp/modern_resolution/scene.sh`・`agg.rb`、gitignore)。
  - 場面 1: 何もせず 31 秒 (2 回目は 21 秒)。
  - 場面 2: `default/editor` を開き、`key a` を 30 回打って Enter、を 8 回 (約 110 秒)。
    道具は 1 打鍵に 0.4 秒ほどかかるので、毎秒 2〜3 打鍵になった。
  - 場面 3: デスクトップのファイルマネージャを開き、エディタ・AI ヘルパー・StackChan (毎秒 12〜13 回描く) を開く。
    一番上の StackChan のタイトルバーを `drag 60 17 220 120` で往復させる (12 往復、約 25 秒)。
    AI ヘルパーは開くだけで、問いは送っていない。
  - 場面 4: StackChan だけ (4a)。StackChan と LED Matrix (4b)。21 秒。
  - 場面 5: エディタを開いて F11 で全画面にし、120 打鍵。
  - 場面 6: 場面 3 の間、`/stream` (MJPEG) を curl で受け続ける (切れたら繋ぎ直す)。
- 取った値: `frame:`・`frame commit:` (この段の計装)、`GFX STATS` (present/s)、
  `cursor:` (カーソルのコマンドの待ち)、エディタの `edit_lat`、10 秒周期の `IRAM free`・
  `PSRAM free`・タスクのスタックの底、`M1|`。`hid_lat` は 1000 件ごとにしか出ない。
  今回の打鍵は 1 場面で 500 件ほどなので出なかった。

### 4.5 入力の遅れ

- 打鍵から画面に出るまでを直接測る計装は無い。今あるのは次の 2 つ。
  - `edit_lat`: エディタが打鍵を受けてから present するまで。解像度で変わらなかった (4.3)。
  - `cursor: wait`: カーソルのコマンドが表示タスクに読まれるまでの待ち。
- present の後、表示タスクは次の描画で合成して出す。描画は 33 ms ごとに区切られる
  (`RENDER_MIN_INTERVAL_MS`)。そのため画面に出るまでは、おおよそ「`edit_lat` + 次の描画までの待ち
  (0〜33 ms) + 1 フレームの時間」になる。426x240 は 5〜7 + 0〜33 + 28.7、640x360 は 5〜5.5 + 0〜33 + 43.1 で、
  差は 1 フレームの時間の差 (約 14 ms) にほぼ等しい。待ちを平均 16 ms とすると、50 ms 前後と 64 ms 前後で
  約 1.3 倍になる。**1.5 倍の線の内側の見積もりだが、実測ではない**。
- 1 フレームが 33 ms を超えると描画は詰まる (次の描画まで待つ時間が無くなる)。
  そのため、動くデモと打鍵が重なる場面では、待ちの分がもっと増える見込み。

## 5. メモリとその他の観察

### 5.1 メモリ

| 項目 | 426x240 | 640x360 | 根拠 |
|---|---|---|---|
| 内蔵 RAM (起動の段ごと) | `M1|wifi_rd|internal=208624` | `internal=207636` | 2 回の起動の `M1|` の行。違うのは BLE の後の段からで (`ble_ready` 227848 / 227640)、解像度の前の段 (`system_config` から `spawn:Services`) は 1 バイトも違わない |
| 内蔵 RAM (待機、10 秒周期) | `IRAM free: 204096` | `203936` | 場面 1 の `fmrb_task: IRAM free` |
| PSRAM: fb を確保した後 | `M1|gfx_audio_init|psram=12244416` | `11988096` | 差 256,320 = 640x360x2 − 426x240x2 |
| PSRAM: 起動しきった所 | `M1|wifi_rd|psram=11357760` | `10076160` | 差 1,281,600 = fb の差 256,320 + デスクトップの canvas 2 枚 x 2 面 (働く面と確定した面) の差 1,025,280 |
| PSRAM: Window 1 枚 (canvas は画面の大きさで確保) | 2 x 204,800 | 2 x 460,800 | `Canvas alloc: ... (buffer 426x240)` / `(buffer 640x360)`。1 枚あたり +512,000 |
| PSRAM: 遠隔の画面の写し | 2 x 460,800 | 2 x 460,800 | `Capture enabled (up to 460800 bytes a frame, 2 slots)`。今でも高解像度の大きさで取っている |
| PSRAM: 高解像度の fb | 全画面のエディタで初めて 460,800 | 取らない | 640 では高解像度モードを使わないため |
| PSRAM の最小 (場面 3) | 7.81 MB | 未計測 (見積もり 約 5.0 MB) | 426 の `PSRAM free` の最小 7,808,732 から、Window 3 枚 x 512,000 と起動時の 1.28 MB を引いた |

- canvas は Window の大きさではなく、**画面の大きさで確保される** (`canvas_alloc`。全画面に切り替えても
  取り直さないため)。Window が多いほど PSRAM の差は大きくなり、8 枚 (`DISPLAY_LOCAL_MAX_CANVAS`) を
  全部使うと、426x240 の 3.3 MB に対して 640x360 は 7.4 MB になる。起動直後の PSRAM の空きは 15.3 MB
  (`M1|boot_start|psram=15274292`)。デスクトップで約 10 MB 残る。VM プール (AI ヘルパーは 1 MB、
  StackChan は 0.5 MB など) と合わせると、Window 8 枚は入るが余裕が薄くなる。計画の見立て
  (PSRAM 32 MB で問題なし) のうち、**使える PSRAM の heap は 15 MB ほど** という点が違った。
- タスクのスタックの底 (10 秒周期の最小) は、426x240 と 640x360 で差が無かった
  (system_desktop 3688、fmrb_kernel 3456 以上、fmrb_host 9920 以上)。表示タスク (`display_local`) は
  この表に入っていないので見ていない。
- VM プールは解像度で変わらない (Ruby 側の確保は画面の大きさに依らない)。

### 5.2 どこに時間が乗っているか

- **clear (426: 3.9 ms、640: 9.0 ms)**: CPU で fb 全体を 0 にする。最初の canvas が不透明な
  全画面の壁紙 (z=0) なので、デスクトップが見えている間は毎回上書きされる無駄な仕事。
- **全画面の 2 枚の blend (426: 7.5 ms、640: 14.8 ms)**: 壁紙 (z=0、不透明) と、メニューバー・
  ランチャー・ファイルマネージャを描く前面の層 (z=254、ほとんど透過色)。どちらも毎フレーム全面を blend する。
- **SRM (15〜17 ms)**: 1280x720 の RGB888 を書き出す時間で、解像度ではほぼ決まらない。
  blocking で待っているので、表示タスクはこの間ほかのことをしない。
- **commit の memcpy**: present のたびに canvas の働く面を確定した面へ写す。全画面の層は
  426 で 6.3 ms (204 KB)、640 で 14.4 ms (460 KB) かかる。デスクトップは時計のために毎秒 present する。
  描画の外 (コマンドの処理) で起き、その間は次のコマンドが読まれない。
- **PSRAM の帯域が遅い**: 204 KB の memcpy に 6.3 ms (約 33 MB/s)、clear は約 52 MB/s だった。
  P4 の PSRAM としては遅く見える。キャッシュの設定か PSRAM のクロックに理由があるかもしれない
  (sdkconfig は触らない。確かめていない)。
- **キャッシュの同期 (sync) は小さい**: blend の前後で 1 枚あたり 0.3〜0.4 ms ほど。見立てで
  未知数とされていた「2.25 倍になったキャッシュの同期」は問題にならなかった。

### 5.3 手当ての案 (見立てだけ。作っていない)

効きそうな順に書く。

1. 一番下の canvas が不透明で画面全体を覆うときは clear を飛ばす (640 で 9 ms)。
   あるいは壁紙を blend でなく DMA の写し (PPA SRM の 1 倍か 2D-DMA) で敷く。
2. 前面の層 (z=254) の blend を、中身のある範囲 (メニューバーの帯と、開いている
   ランチャー・ドロップダウン・ファイルマネージャ) に絞る。今は画面全体を毎回 blend している (640 で 7 ms 前後)。

5. 変わった所だけ合成する (変わった矩形の和だけ clear・blend・SRM する)。効果は一番大きいが、作りも大きい。
6. PSRAM の帯域の確認 (sdkconfig の提案になる。ユーザが判断する)。

1 と 2 だけで、640x360 の場面 1 は 41.5 ms から 25 ms 前後まで下がる見込み
(clear 9 ms + 前面の層の大半 7 ms)。426x240 の今の値より速くなる。

## 7. 全画面のアプリを 426x240 へ切り替える道 (plan 4.3)

**判断: 今の `SET_SCREEN_MODE` の作りを一般化すれば成り立つ。** 入る・出る・持ち主が消える・
打ち切り・遅れて出た絵・入力と写しの大きさの追従は、向きに依らない作りになっている。
決め打ちは「切り替え先 = 640x360」の 1 点にほぼ集まっている。

足りないもの・直す所:

1. **表示 (display_local)**: `DISPLAY_LOCAL_HIRES_W/H` を「今の切り替え先」の変数にする
   (`g_smode.alt_w/h`)。`screen_mode_request` は表の切り替え先 (基本 640 なら 426x240) を受ける。
   今ある「基本が 640 以上なら無視」は外す。`screen_mode_ensure_hires_fb` は大きさを引数に取る
   (426x240 の fb は 204 KB)。`screen_mode_tell_input` は切り替え先の大きさを渡す。
   `render_frame` の「基本の画面で 640x360 の canvas を外す」は「基本の画面で切り替え先の大きさの canvas を外す」
   にする。ただし基本が 640 のとき、426x240 の Window (例えば 426x240 の大きさの Window のアプリ) と
   区別が付かない。そのため持ち主の canvas (`g_smode.owner`・`late_owner`) に限るのが安全。
   `screen_mode_owner_showable` は fb の大きさとの比較なので、そのまま使える。
   倍率は `display_scale_for` が 3 倍を返す。写しの枠は基本の 640x360 の方が大きいので、そのまま入る。
2. **カーネル (C)**: `fmrb_app_fullscreen_size_for` が、基本が 640x360 で属性の無いアプリに 426x240 を返す
   (ネイティブ版の `fmrb_kernel_set_native_fullscreen(426, 240)` と同じ形。`fmrb_kernel_fullscreen_size` に
   Modern 版の上書きを足すのが近い)。`fmrb_app_fullscreen_hires_size` は表で引く。
3. **カーネル (Ruby)**: `screen_mode_for` は「属性あり → 640x360 (基本が 426 のとき)」に、
   「属性なし → 426x240 (基本が 640 のとき)」を足す。`sync_screen_mode` は大きさを表から取る。
   mruby 版と Spinel 版の両方 (`_fullscreen_hires_size` を「切り替え先の大きさ」に広げる)。
4. **どのアプリを切り替えるか**: 属性なしの全画面を全部 426x240 にすると、領域の大きさから配置する
   アプリ (shooter・welcome・picorabbit) まで小さくなる。既にある `FMRB_FULLSCREEN_HIRES_ANY`
   (「どの大きさでも描ける」、`fmrb_app.h:271`) を .app.toml で宣言できるようにし、宣言したアプリは
   切り替えない形が素直。既定 (宣言なし) は 426x240 にする。
5. **sim**: graphics-audio の SET_SCREEN_MODE にも同じ一般化と、共有メモリの上限 (6.1) が要る。
   ブラウザ版の 640x360 のページは今は切り替えない。合わせるかは別に決める。

難しい所:

- 切り替えの瞬間の一瞬の乱れ (doc/fullscreen_hires/report/h1.md 6 章で保留したもの) は、逆向きでも同じように出る。
  ゲームを起動するたびに起きるので、今より目に付くかもしれない。HDMI の目視が要る。
- F11 で Window と全画面を行き来するアプリは、426x240 と Window の大きさの両方で描ける必要がある
  (今の高解像度と同じ条件)。
- チェックポイント (アプリを運ぶ) で、426x240 の端末と 640x360 の端末の間を全画面のアプリが移るとき、
  運んだ先での大きさの決め直しが要る (今は 640x360 の全画面だけを考えている)。
- 別の道として、ネイティブ版 (doc/linux_native L9e) のように fb は 640x360 のまま、出すときに
  426x240 の部分だけを 3 倍で SRM する形 (PPA SRM の入力の block を使う) もある。ただし入力の座標・
  カーソル・写しも 426x240 に合わせる必要があり、結局 1 の作りと同じ所を直すことになる。そのため
  `SET_SCREEN_MODE` の一般化を推す。

## 9. 再開の手順 (640x360 の残り)

1. P4-Nano の USB (CH343) を差し直す (ユーザ)。`rake attach` で `/dev/ttyACM0` が出ることを確かめる。
2. 端末の `/etc/system_conf.toml` を退避し (今は元の 426x240)、`display_width = 640`・
   `display_height = 360` にしたものを put して `fmrb_rd_fs.rb reboot`。
3. シリアルの取り込みを始め、`tmp/modern_resolution/scene.sh` の場面を流す (`windows 38 125`・
   `demo1`・`demo2`・`fsedit`・`remote 38 125`、場面 1〜4 は 2 回)。集計は
   `ruby -rtime agg.rb <log> scenes.txt <label>`。取り込みが止まったら `robust.sh` がやり直す。
4. 終わったら `/etc/system_conf.toml` を戻して再起動する。

## 10. 見立て (plan 3 章) と違った点

- 「今の計装は present の数だけで、1 フレームの時間が無い」は半分違った。`render: N frames/5s avg max`
  (tick の ms) は前からあった。今回足したのは区間ごとの内訳と µs の精度。
- 「未知数は 2.25 倍になったキャッシュの同期」: 同期は 1 枚 0.3〜0.4 ms で、効いていない。
  効いているのは CPU の clear・PPA Blend・commit の memcpy (PSRAM の帯域) だった。
- 「PSRAM 32 MB で問題なし」: heap として使えるのは 15 MB ほどで、Window が多いと余裕が薄い (5.1)。
- 「426x240 の今は速い」という前提も成り立っていなかった。Window 4 つのドラッグ (場面 3) で平均 32.8 ms、
  遠隔の画面を見ながらでは 43 ms で、426x240 でも 30 fps に届いていない。
- 640x360 のデスクトップは、ESP32 では決め打ちの直しなしで起動した。
- sim は共有メモリの上限で起動しなかった。

## 11. R1 の作業の一覧 (指示書の材料)

640x360 で起動するための手元の直しは、ESP32 では要らなかった。sim だけ 1 つ要った (下の 1)。

   にする (7 章の 1〜3)。属性なしの全画面を 426x240 に切り替える (4.3、7 章の 4 を含む)。
