## 1. 手当て

### 1.1 (1) clear を飛ばす (コミット 1285b2dd)

- `render_frame` は毎回、CPU でフレームバッファ全体を 0 にしていた。デスクトップでは一番下の
  canvas (壁紙、z=0) が不透明で画面全体を覆うので、clear した画素は全部書き直されていた。
- 作り: 合成する canvas を上から見て、**色キーなし・viewport なし・確定した面が置かれた所から
  フレームバッファ全体を覆う** canvas があれば、clear を飛ばし、合成をその canvas から始める。
  その下の canvas は見えないので合成しない (sprite も、その canvas の blend で上書きされる)。
- 条件が外れる場合 (今のまま clear する): 覆う canvas が無い (起動の最初、壁紙の canvas の
  present の前)、一番下が画面より小さいか位置がずれている、色キーを持つ (全画面のエディタは
  色キー付きの canvas なので、場面 5 は今も clear する)、viewport の canvas、高解像度の全画面への
  切り替えで持ち主の canvas がまだ覆っていないとき。壁紙なしの設定でも、デスクトップは
  BG_COLOR で塗った不透明な canvas なので飛ばせる。
- 合成の外し方の規則 (高解像度モードの持ち主だけ、など) は `canvas_left_out` にまとめ、
  覆う canvas の探索と合成のループが同じ規則を読む。
- 守り: PPA の blend が失敗したとき、今までは黒 (clear の色) が見えていたが、今は前のフレームが
  残る。失敗はエラーのログが出る道で、R0・R0b の計測で 1 回も出ていない。

### 1.2 (2) 前面の層の blend を絞る (コミット f5acd263)

- デスクトップの前面の層 (z=254。メニューバー・ランチャー・ドロップダウン・ファイルマネージャ) は、
  ほとんどが色キーの全画面の canvas で、毎フレーム全面を blend していた。
- 範囲の持ち方: **present の写し (commit) のときに、画素そのものから行ごとに「色キーでない最初と
  最後の画素」を求めて、表 (ink) に持つ**。1 行 4 バイトで canvas のバッファの横に置く (PSRAM。
  640x360 で 1.4 KB)。写した直後の行 (キャッシュに乗っている) を読むので、読み直しの費用は小さい。
  描画のコマンドから矩形を集める形は採らなかった。描く道 (コマンド・GfxBlock・動画・canvas 同士の
  写し) のどれかを取りこぼすと絵が欠けるため。画素から求めれば取りこぼしは起きない。
  アプリが範囲を知らせる形 (desktop が graphics-audio に送っている SET_COMPOSITE_REGIONS) も、
  アプリの申告が正しいことに頼るので採らなかった。
- `render_frame` は表を帯 (色キーでない画素を含む行の連なりと、その行の横の範囲) に直し、帯だけを
  blend する。8 行より近い帯はつなぎ、8 本を超えたら一番近い 2 本をつなぐ。つないだ所は色キーの
  画素なので、blend しても背景は変わらない。色キーの画素は背景を残すので、帯の外を飛ばしても
  出る絵は同じ。
- 表が使えないとき (canvas の大きさが変わった、動画のフレームが写された、バッファを取り直した、
  まだ present が無い) は、次の present まで今までどおり全体を blend する。
- 色キーを持つ canvas すべてに効く (Window のアプリの canvas も色キー付きのものが多い)。
- PPA の backend: blend の前後のキャッシュの同期 (fb の write-back と invalidate) を、fb 全体から
  **その block の行だけ** (キャッシュの行に丸める) にした。帯が増えると block も増えるため。
  CPU が汚した行のうち block の外にあるものは PPA が書かないので、後の block か present_flush で
  書き戻されても PPA の出力を潰さない。
- 写しのときに ink を求める費用: 全面を書いた present では、一度 memcpy してから読み直すと PSRAM
  から読み直しになり、640x360 の写しの最悪が 15 ms から 22〜25 ms に延びた (計測で見つけた)。
  行ごとに写して読む形に直した (コミット de60fda5)。

### 1.3 (4) present のたびの写しを減らす (コミット 2ad2256d)

- present (PUSH_CANVAS で画面へ) のたびに、働く面から確定した面へ active area 全体を memcpy していた。
- 作り: canvas ごとに「働く面で書いたかもしれない行」の区間を 4 本まで持つ。働く面に書く
  コマンドは、書きうる行に 1 行の余白を付けて印を付ける。commit は印の行だけを写し、印を消す。
  - 図形 (点・線・矩形・角丸・円・楕円・三角・弧) は座標から。文字は、書き始めの 1 行上から、
    書き終わったカーソルの 1 行下まで (折り返しと改行でカーソルが下がる。8 px の字に切り替える
    混在の文字列も含めて、字の高さは大きい方)。画像・タイルはその高さ。canvas 同士の写しは
    写し先に。全面の塗り・GfxBlock のプログラム・マスク付きの描画は全面。
  - バッファを取ったとき・取り直したとき・大きさを変えたとき (行の幅が変わるので、同じだった
    行が同じ行でなくなる) は全面。動画のフレームは今までどおり全体を写し、印を消す。
  - 書き先が SpriteImage に向いているとき (SET_SPRITE_IMAGE_TARGET) は canvas に印を付けない。
- **working と committed の入れ替えは採らなかった**。アプリは前のフレームの絵に描き足すので、
  入れ替えると働く面が 2 フレーム前の絵になる。安全なのは「毎回全面を描くアプリ」だけで、
  表示の側からはそれが分からない。
- 取りこぼしの確かめ: 手元だけで、commit の後に働く面と確定した面の全体を memcmp する検査と、
  帯の外に色キーでない画素が無いかの検査を入れたネイティブ版を作り、デスクトップの場面に加えて
  flash/app のアプリ約 95 本を順に開いて叩いて閉じた (5.2 節)。commit 2,000 回以上・帯の検査
  2,800 回以上で、食い違いは 0。検査のコードはコミットしていない。
- frame commit の行の `avg_bytes` は、実際に写したバイト数を数えるようにした。

### 3.1 入力の遅れ

- `hid_lat` は今回も件数が 1000 に届かず出なかった (場面 2 は約 250 打鍵 = 500 件)。
- エディタの `edit_lat` (打鍵を受けてから present まで) は、426 後で平均 5.0〜5.7 ms、640 後で
  5.3〜6.2 ms (R0 の 426 前は 4.8〜7.3 ms)。解像度で変わらない。
- 画面に出るまでは R0 4.5 の見立てどおり「edit_lat + 次の描画までの待ち + 1 フレーム」。1 フレームが
  640 後 26.9 ms < 426 前 28.7 ms なので、**640 後の打鍵の遅れは 426 前より大きくならない見積もり**
  (実測ではない)。

### 3.2 メモリ

- 内蔵 RAM: 足した静的な変数は無い。canvas の表 (`g_canvases`) は PSRAM。帯の計算は表示タスクの
  スタックに 200 バイトほど。`rake regress:size` の結果は 7 章。
- PSRAM: 色キーの canvas ごとに ink の表 (1 行 4 バイト、426x240 で 1 KB、640x360 で 1.4 KB、
  キャッシュの行に丸める)。canvas の表の 1 行あたり 18 バイト増 (8 枚で約 150 バイト)。
- 起動の段ごとの値 (`M1|`) は 6.4 節。

## 4. 残った時間の内訳と、次に効く手

640x360 のデスクトップ (場面 1、25.4 ms):

| 区間 | ms | 割合 |
|---|---|---|
| SRM (1280x720 RGB888 へ拡大と変換) | 16.7 | 66% |
| 壁紙の blend (不透明、640x360 全面) | 約 8 | 32% |
| 前面の層の帯・同期・その他 | 約 0.7 | 3% |

Window 4 つのドラッグ (場面 3、31.4 ms): SRM 17.6、compose 13.7 (壁紙 8 + Window 4 枚 + 帯)。

- **(3) SRM の非 blocking**: SRM の 16.7 ms の間、表示タスクは待っているだけ。重ねられれば
  フレーム/秒は上がる (最大で 1 フレーム 17 ms ほど縮む見込み) が、1 フレームの遅れは縮まない。
  DSI の fb は 1 枚なので、書いている間の走査で tear が出ないかを先に詰める必要がある
  (doc/fullscreen_hires/report/h1.md 6 章)。**SRM に手を入れる話になるので、この段では止めた**。
- **(5) 変わった所だけ合成**: 時計だけが変わる 1 秒ごとのフレームは、変わった矩形 (時計の
  数十 x 10 画素) だけ blend と SRM をすれば 1 ms 前後で済む。打鍵・ドラッグでも、変わるのは
  Window 1 枚分。残りの 2 つの大きな区間 (壁紙の blend と SRM) の両方に効く唯一の手で、
  **次に効くのはこれ**。作りは大きい (変わった矩形の和の管理、SRM の block 出力、カーソルの焼き込み
  との整合、遠隔の画面の写し)。
- 壁紙の blend 単独なら、壁紙を SRM の 1 倍か 2D-DMA で敷く手もあるが、(5) が入れば要らない。
- 全画面のエディタ (場面 5) の clear 8.5 ms は、色キー付きの canvas が全面を覆っていても
  色キーの画素が残っている可能性があるので飛ばせない。commit のときに「色キーの画素が 1 つも
  無い行」も数えれば飛ばせる (行の全部を読む費用が増える)。今回は入れていない。
- 遠隔の画面の写し (場面 6、640 で 18 ms) は、下の 8 章の DMA の写しが効く候補。

## 5. 絵が変わらないことの確認

### 5.3 P4-Nano (遠隔の写し、JPEG)

- 手当ての前のファーム (R0 のもの) と後のファームで、同じ台本の写しを 426x240 と 640x360 で撮った

  から開き直して撮り、選択の印以外は同じ。欠け・残りは目で見ても無い。

## 6. P4-Nano の計測のやり方と罠

### 6.1 やり方

- ファーム: `FMRB_HW_TARGET=NARYAv4 rake build:esp32`、`FLASH_BAUD=115200 HOST=192.0.2.20
  PORT=/dev/ttyACM0 rake flash:app_sync` (flash 332 秒、sync 77 秒)。計測は、3 つの手当てと
  8 章の写しの速さの計測 (起動のときに 2 回だけ走る、コミットしていない) を入れたファームで行った。
  640x360 はコミット de60fda5 の前 (ink の読み直しの直しの前)、426x240 はその後のファーム。
  違いは commit の最悪の値だけ (1.2 節)。
- 終わった後、計測のコードを外したコミット済みのファーム (HEAD) を焼き直した。

## 8. PSRAM の写しの速さ (提案まで)

### 8.1 測ったもの

起動のときに 1 回、200 KB の PSRAM のバッファ 2 つで測った (手元だけ、コミットしていない)。
キャッシュは測る前に書き戻して捨て、冷えた状態から。`noscan` は表示タスクの最初 (パネルの初期化の前、
HDMI の走査が無い)、`scan` は最初のフレームの 8 秒後 (1280x720 RGB888 を走査中)。3 回の起動で同じ値。

| 操作 | noscan | scan |
|---|---|---|
| memcpy PSRAM → PSRAM | 51 MB/s | 31 MB/s |
| memset PSRAM | 100 MB/s | 59 MB/s |
| 読むだけ (32 ビットずつ足す) | 79〜83 MB/s | 54〜56 MB/s |
| DMA の写し (AXI GDMA、async memcpy) | 101〜104 MB/s | 60 MB/s |

設定 (ビルドでできた sdkconfig を読んだだけ): PSRAM は HEX (16 線) 200 MHz (`SPIRAM_SPEED_200M`)、
CPU 400 MHz、L2 キャッシュ 128 KB・行 64 B、memcpy は IDF の libc のもの (`LIBC_OPTIMIZED_MISALIGNED_ACCESS`、
語単位の C、IRAM)。

### 8.2 分かったこと

- **CPU から見た PSRAM の帯域そのものが小さい**。読むだけで 80 MB/s。HEX 200 MHz の生の値
  (16 ビット x 2 x 200 MHz = 800 MB/s) の 1 割。キャッシュの行 (64 B) ごとに待ちが入る形で、
  先読みが効いていない。memset は書き込みのための行の読み込みと書き戻しで 2 回、memcpy は
  読み・書き先の行の読み込み・書き戻しで 3 回 PSRAM を通る。memcpy 51 MB/s x 3 ≒ 150 MB/s、
  DMA の写し 100 MB/s x 2 = 200 MB/s が、走査が無いときに PSRAM が運べている量。
- **HDMI の走査との取り合い**: P4-Nano の DSI の fb は 1280x720 RGB888 で、60 Hz で読み続けると
  166 MB/s。走査が始まると、どの操作も 4 割ほど遅くなる (memcpy 51 → 31 MB/s)。R0 の
  「204 KB に 6.3 ms (33 MB/s)」はこの 31 MB/s と合う。Tab5 (720x1280 RGB565) は 110 MB/s。
- memcpy の作り (語単位か) は効いていない。キャッシュに乗った 64 KB の写しは 64 KB を 0.3 ms
  (200 MB/s 以上) で写す。
- DMA の写しは、走査中でも CPU の memcpy の 2 倍 (60 MB/s) で、その間 CPU は空く。

### 8.3 提案 (sdkconfig は編集していない。試していない)

1. **大きな写しを DMA に任せる (コードの側、次の段の候補)**: 遠隔の画面の写し (640 で 18 ms)、
   全面の commit、全画面の高解像度の写し。AXI GDMA の async memcpy で 2 倍速く、表示タスクは
   その間ほかの仕事ができる。キャッシュの同期 (写し元の書き戻し・写し先の捨て) が要る。
2. **`CONFIG_SPIRAM_SPEED_250M`** (今は 200M): IDF 5.5 で ESP32-P4 rev 3 以上に出ている選択肢
   (`!ESP32P4_SELECTS_REV_LESS_V3`。今のビルドは `ESP32P4_REV_MIN_301`)。帯域は最大 1.25 倍の見込み。
   副作用: 実験的な扱いで、DSI の fb を PSRAM に置く今の作りで安定するかは確かめる必要がある
   (今の sdkconfig.defaults に「DSI の fb は 200 MHz が要る」という書き付けがある)。Tab5 は
   チップの版を確かめてから。試していない。
3. **HDMI の走査を軽くする**: 1280x720 を 50 Hz か 30 Hz で出せば、走査の 166 MB/s が 138・83 MB/s に
   減る。モニタが受けるかと、動きの見え方を確かめる必要がある。Tab5 は対象外 (パネルの決まり)。
4. 採らない方がよいもの: L2 キャッシュを 256 KB にする (`CACHE_L2_CACHE_256KB`) と内蔵 RAM が
   128 KB 減る (内蔵 RAM を増やさない・減らさない方針に反する)。
