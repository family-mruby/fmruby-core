# fmrb_app_kill 到達不能問題の診断と修正

ビジーループするゲストアプリを kill すると、fmrb_app_kill の強制終了経路
(fmrb_app.c の "No response ... forcing termination") に到達せず、kill を
実行する側が固まる。発見の経緯と再現手順は
doc/gfx_unification/report.md の Phase C 申し送りを参照。

Phase 1 (診断) -> Phase 2 (修正) -> Phase 3 (強制経路の安全化) の順に進める。
**Phase 1 の結果をユーザに報告し、Phase 2 の方針を確定してから修正に入る。**
実装レポートは [report.md](report.md) に置く。

## なぜ重要か

phase2 (MicroPython) の「強制 kill でも Python の単一インスタンス排他が
解放される」は、この強制経路が動くことに依存している。経路が事実上
到達不能な現状では、ハングした Python アプリが 1 本出ると再起動まで
Python アプリ全体が起動不能になり得る。

## 調査済みの事実 (2026-08-01、この上で作業する)

- stop の伝達は 2 経路: メッセージ (request_app_exit、送信タイムアウト
  10 tick で満杯なら消える) と、fmrb_app_kill が直接立てる
  `ctx->should_exit` フラグ。フラグは相手の状態によらず必ず立つ。
- VM フックのある Lua / Python / BASIC は、should_exit さえ立てば
  ビジーループ中でも協調終了できるはず (phase2/3 で実証済み。ビジーな
  Python を 20ms で停止できている)。
- fmrb_app_kill 自体は有界: 猶予ループは KILL_GRACE_MS で必ず抜け、
  ロック保持も瞬間的。**固まるのは kill を実行する側のタスクが
  その手前のどこかで塞がっているため**、が現時点の見立て。
- 強制経路 (fmrb_task_delete + force_release_resources) は実装済み。
  課題は新設ではなく「到達させること」。

容疑は 3 つ (Phase 1 で確定する):

1. kill を実行するタスクの優先度がビジーなアプリタスク以下で、CPU を
   もらえない (飢餓)。
2. g_ctx_lock を別の誰かが長期保持していて、最初の take で永久待ち。
3. kill 呼び出しに至る上流 (debugd / カーネル) が、満杯になったアプリの
   メッセージキューへの送信などで塞がっている (ビジーなアプリは自分の
   キューを浚わないので、フォーカスされていると HID がそこに溜まる)。

## 再現手順

canvas を作ってから `while true do end` する Lua アプリを一時ファイルとして
作り (コミットしない)、spawn してから kill する。debugd
(DBG_CMD_SPAWN / DBG_CMD_KILL) 経由の手順は doc/gfx_unification/report.md
の Phase C に記載。

## Phase 1: 診断 (コードを直さない)

1. Linux シミュレーションで再現させ、**gdb を core プロセスにアタッチして
   `thread apply all bt` を取る**。固まっているタスクと、その待ち先
   (ロック / キュー / delay) を特定する。これが最短の確定手段。
2. kill の呼び出し経路を洗う: DBG_CMD_KILL はどのタスク上で
   fmrb_app_kill を実行するか。タスクモニタ (デスクトップ) からの kill は
   どのタスクか。両経路で同じか。
3. 優先度表を確認する: アプリタスク / カーネル / デスクトップ / host /
   debugd の優先度の並び。ビジーなアプリより低い優先度のタスクが kill を
   担っていないか。
4. 切り分け: 閉じるボタン経由 (カーネル経由) の kill でも同じ freeze が
   起きるか、debugd 経由固有か。
5. 結果 (スタックトレース、確定した原因、Phase 2 の修正方針案) を
   report.md に書き、**ユーザに報告して方針の了承を得てから Phase 2 へ**。

## Phase 2: kill 実行側の詰まりの修正

Phase 1 の確定原因に対して行う。類型ごとの指針 (該当するものだけ):

- **優先度飢餓**: アプリタスクの優先度をカーネル系より確実に下げる。
  ゲストの無限ループは常にあり得る前提なので、飢餓耐性は優先度設計で
  持つのが筋。ただし優先度変更は描画・音のレイテンシに波及し得るので、
  変更案を提示して了承を得てから適用する。
- **満杯キューへの送信ブロック**: 該当箇所に有限タイムアウトを入れる。
  HID のアプリ転送が容疑なら「満杯時に古いイベントから捨てる」等の方針を
  ユーザに確認してから実装する。
- **ロックの長期保持**: 保持区間を縮める。

完了条件:

- 再現ケース (Lua ビジーループ) が **協調終了で** 猶予内に死ぬ
  (VM フックが効く言語は本来こちらの網で死ぬのが正)。
- 協調終了が効かないケース (C バインディング内で無限ブロックする
  一時テストコードで模擬。ソースをビルド対象から外す方法は使わない) で、
  **強制経路のログが出て資源が回収され、同じアプリを再起動できる**。
  Python の場合は排他が解放されることも確認。
- 4 言語のデモ + Spinel デスクトップ構成に退行が無い (headless)。

## Phase 3: 強制経路の安全化 (2026-08-02 詳細化)

Phase 2 で強制経路 (fmrb_task_delete + force_release_resources) は到達可能に
なり、動くことも実証された。残っているのは「**消した瞬間に対象が握っていた
ものは回収できない**」という外部タスク削除の本質的な穴と、Phase 2 で見つかった
**INIT 状態のアプリを kill できない**穴の 2 つ。3a (調査) -> 3b (補償) ->
3c (INIT 対応) の順に進め、**3a の分類結果を report に書いてユーザ確認して
から 3b/3c を実装する**。

### 前提知識

- FreeRTOS の待ち行列 (queue / semaphore) で**ブロックしている**タスクを
  vTaskDelete するのは安全 (イベントリストから外される)。危険なのは
  「**返す義務のある資源を取得した状態**」で消される場合で、資源の種類ごとに
  出方が違う: カウンティングセマフォのスロットなら永久に 1 個減る (枯渇へ
  向かう)、mutex なら永久ロック、ヒープ確保物ならリーク。
- アプリのプール・canvas・メッセージキュー・VM 排他は
  force_release_resources が既に回収する (Phase 2 で実証)。対象は
  **それ以外の、共有資源の取得ウィンドウ**である。

### 3a: 危険ウィンドウの全数調査 (実装しない)

ゲストタスクが実行し得る C コード (5 バインディング + fmrb_gfx / fmrb_msg /
fmrb_hal の呼び出し面) を対象に、「取得してから返すまでのウィンドウ」を
全数列挙し、次の 3 分類で report に表を作る:

1. **ブロックのみ (削除安全)**: fmrb_msg_receive の待ち等。資源を持たない。
2. **共有カウント資源の保持**: 現時点で判明しているのは
   **GFX フローセマフォのスロット** (fmrb_gfx_submit の take から
   msg_send 成功まで。失敗時 give はあるが、その区間で削除されると
   スロットが 1 個消える)。同類が他に無いか (ctx->semaphore を使う
   file 転送の同期待ち等) を確認する。
3. **ヒープ・ハンドル類の保持**: send_file_cmd_sync 系の転送バッファ
   (fmrb_sys_malloc、所有権が host に渡る前に消されるとリーク) 等。

分類の判断基準も report に明記する:
**枯渇する資源 (分類 2) は補償必須。一回きりの有界リーク (分類 3) は
頻度と量を添えて「補償する / 制限事項として文書化する」を提案し、
ユーザ判断を仰ぐ。**

### 強制 kill の契約 (2026-08-02 改訂で確定)

**強制 kill は非常口である**。協調終了 (should_exit + VM フック) がほぼ
すべてのケースを救い、強制経路に落ちるのは「ゲストが C 内で固まる」という
ファームウェア不具合のときだけ。したがって契約は次のとおりとする:

- 強制 kill の保証は「**作業を保存しログを回収して再起動できる程度に
  系が生き残ること**」であり、無傷の続行ではない。
- 使用後は劣化し得る (GFX スロット -1、有界リーク)。**ログ回収と早めの
  再起動を推奨**。この推奨が目に見えるよう、`Killed by force` のログに
  「system may be degraded; consider reboot」の一行を足す (実装 1 行)。
- ただし「**非常口を使ったせいで前より悪化する**」ことだけは許さない。
  系全体の停止 (mutex 全損) とメモリ破壊 (削除後のスタック書き込み) は
  この線を越えるので対策する。有界リークは越えないので文書化に留める。

### 3a の結果と裁定 (2026-08-02、契約改訂を反映した最終版)

調査結果は report.md 参照。分類 2 は 3 件 (GFX フローセマフォのスロット /
MicroPython 排他 mutex s_lock / メッセージ登録簿 mutex g_registry_lock)。
裁定:

- **#1 (GFX スロットの消失) は補償しない**。1 回の強制 kill で最大 1/96、
  蓄積は遅く、再起動で全快する有界劣化なので契約の範囲内。既知の制限として
  文書化する (当初計画のカウンタ補償は取り下げ)。
- **#2/#3 (mutex) は対策する** (3b)。registry mutex が当たれば全タスクの
  送受信が止まり、保存もログ回収もできない = 非常口が事態を悪化させる
  唯一の全損モード。対策は kill 経路限定の十数行で常時コストゼロ。
- **#5 (同期コンテキストのメモリ破壊) は軽量版で対策する** (3d)。
  世代スロット再設計はやらない。破壊は「削除後にコールバックが届く」とき
  だけ起きるので、「同期 I/O 中は消さずに待つ」で十分 (詳細は 3d)。
- **#6/#7 (転送バッファ + FD の有界リーク) は制限事項として文書化で足りる**。
  1 回の強制 kill あたり有界で蓄積せず、発生条件も異常系の重なり。
- **GFX セマフォ計上の非対称 (fmrb_gfx.c の直接送出 6 箇所が take 無しで
  give される) は 3b の前に単独コミットで修正する** (下記 3b-0)。
  これは強制 kill と無関係に平常運転で HID 予約枠の保護を緩めている
  現行バグであり、Phase 3 の縮小とは独立に必須。

### 3b-0 (先行): GFX セマフォ計上の非対称の修正

fmrb_gfx.c の同期送出 6 箇所を fmrb_gfx_submit 経由に揃えるのを本命とする
(host 側除外案だと同期コマンドが HID 予約枠の保護を受けない穴が残る)。
着手前に 6 箇所の呼び出しコンテキストを確認し、フローセマフォで待っては
いけない文脈 (カーネル等) からの呼び出しがあれば、そこだけ理由コメント
付きの例外とし host 側除外を併用してよい。修正後、セマフォ残数が
アイドル時に定数に戻ることを確認する (3b の検証の前提になる)。

### 3b: mutex ガード — 「取ってから消す」

FreeRTOS の mutex は**所有者しか解放できない**ため、kill 側からの give に
よる補償は適用不能。代わりに、強制削除の直前に **kill 側がその mutex
(s_lock / g_registry_lock) を take してから fmrb_task_delete し、直後に
give する**。

- 相互排他がそのまま保証になる: killer が持てた = 対象は保持窓の外に居る。
  対象が take 待ちでブロックしていた場合の削除は FreeRTOS 的に安全。
- 保持窓が「数命令・ブロックなし」なので killer の take はすぐ通る。
  ホットパス (毎メッセージの registry 操作) に旗もカウンタも足さない。
- s_lock / g_registry_lock は static なので、fmrb_mp / fmrb_msg に
  ロックガード用の小さな API を 1 つずつ追加する。

(当初計画にあった GFX スロットのカウンタ補償は、契約改訂により取り下げ。
スロット消失は既知の制限として文書化する。)

### 3c: INIT 状態の kill 対応 (Phase 2 の申し送り)

fmrb_app_kill は RUNNING / SUSPENDED しか受け付けず、VM 生成中 (INIT) に
固まったアプリを殺せない。Python は fmrb_mp_acquire が INIT 中に走るので、
**排他を握ったまま INIT で固まると再起動まで Python 全滅**になる
(Phase 2 検証中に実際に発生した状態)。

- fmrb_app_kill の受け付け状態に INIT を追加する。INIT では協調終了は
  期待できない (create_vm の C 内で固まっている) が、猶予ループは
  そのまま回してよい (万一 create が完了して RUNNING に進めば協調で死ぬ)。
- 強制経路が部分生成状態で正しく動くことを確認する:
  transition_state の INIT -> STOPPING 遷移が許可されているか、
  destroy_vm / release_all / queue 削除が「まだ作られていない資源」に
  対して安全か (Phase C の release_all は再入安全設計なので期待できるが、
  検証で裏を取る)。
- 再現は Phase 2 と同じ手法: fmrb_mp_start に一時ブロックを仕込む
  (コミットしない)。

### 3d (軽量版): 同期 I/O 中は消さずに待つ

3a の #5 への対処。同期待ち (get_pixel / file_status / transfer /
define_prog 等) のコンテキストはアプリのスタック上にあり、強制削除の後に
host_task / transport のコールバックが `sc->result` への代入や
`fmrb_semaphore_give(sc->done)` を行うと、**再利用されたスタックへの
書き込み = メモリ破壊**になる。破壊が起きるのは「削除の後にコールバックが
届く」= ホスト側が生きていて遅いときだけ、という性質を使う:

- 同期待ちに入る箇所で ctx に「同期 I/O 中」の旗を立てる。同期送出は
  3b-0 で fmrb_gfx_submit 経由に集約されるので、**旗の設置場所は 3b-0 と
  ほぼ同じ 6 箇所 + ファイル転送系**に閉じる。
- 強制経路は旗が立っていたら削除せず待つ。応答が来ればアプリは目を覚まし、
  should_exit が立っているので **VM フックによる協調終了に化ける**
  (削除自体が不要になる)。応答が来なければリンク側が死んでいるので、
  コールバックは永遠に来ず、安全に削除できる。
- 待ち時間の上限は同期側のタイムアウトに合わせる (最長はファイル転送の
  30 秒)。上限で打ち切って削除した場合の残余リスク (打ち切り直後に
  応答が届く) は既知の制限として文書化する。

### 強制 kill の既知の制限 (2026-08-02 実装完了時点)

強制 kill は非常口である。使ったあとは次の劣化が起こり得る。**ログを回収して
早めに再起動することを推奨する**。`Killed by force` のログにも同じ趣旨の
警告を出している。

1. **GFX キューのスロットが 1 回につき最大 1 個減る**。`fmrb_gfx_submit` が
   フローセマフォを take してからホストのキューに載せ切るまでの窓で削除
   されると、そのスロットは戻らない。96 枠なので蓄積は遅く、再起動で全快
   する。契約により補償はしない (kill 経路にカウンタを足すより、有界劣化を
   許容するほうが平常時のコストがゼロで済むため)。
2. **転送バッファ (最大数十 KB) と FD 1 個の有界リーク**。ファイル転送の
   `fmrb_sys_malloc` 済みバッファの所有権がホストに移る前、または
   `file_open`〜`file_close` の間に削除された場合。1 回きりで蓄積しない。
3. **同期待ちの打ち切り後の残余リスク**。強制経路は同期 I/O 中なら最大 30 秒
   待つが (3d)、上限で打ち切って削除した直後にホストからの応答が届くと、
   再利用されたスタックへの書き込みが起こり得る。上限は同期側の最長
   タイムアウト (ファイル転送 30 秒) に合わせてあるので、応答が来るなら
   打ち切り前に来る設計だが、リンクが極端に遅い場合は残る。

補償しないと決めた根拠と、対策した項目 (mutex 全損とメモリ破壊) との線引きは
本書「強制 kill の契約」節を参照。

### 完了条件 (契約改訂版)

- **3b-0**: 修正後、アイドル時にセマフォ残数が定数へ戻る (幻スロット消滅)。
- **mutex ガードの実証**: 強制 kill を s_lock / g_registry_lock のガード
  経由にした上で、ビジーループ・同期待ち・INIT の各状態の kill 後に
  メッセージ送受信と Python 起動が正常なこと。
- **INIT kill の実証**: fmrb_mp_start で固めた Python アプリを kill でき、
  排他が解放されて次の Python アプリが起動できる。
- **3d の実証**: 同期待ち中のアプリに kill をかけたとき、(a) host 応答が
  来る場合は協調終了に化けること、(b) 応答を止めた場合 (一時的な仕込み、
  コミットしない) は上限まで待ってから安全に削除されること。
- `Killed by force` 時に degraded 警告ログが出ること。
- 「既知の制限」節が本 README に書かれていること。
- 4 言語デモ + Spinel デスクトップ構成の headless 回帰。
- 一時テストコードはコミットしない。結果は report.md の Phase 3 節へ。
