# 報告 E1 / E2: mrb_close と、同じ Spinel アプリの同時起動

> 状態: 完了 (親の検収待ち) | 更新: 2026-10-02 | コミット: E1 c8e3e181、競合の修正 42494d08、E2 a1b2ee50 | E1 で mruby アプリの正常終了に `mrb_close` → `mrc_ccontext_free` を入れた
> (1 本 9-28 ms、不正な解放 0、プールは周ごとに戻る)。その途中で、終了したアプリの削除が早すぎて端末が固まる競合を
> 見つけて直した。E2 の abort は「同じ Spinel プログラムの 2 つのインスタンスが、生成 C の翻訳単位の static
> (例外スタックなど) を共有する」ことが原因で、実機で再現・観測した。直し方は案 (1) 同時起動を止める。
> あわせて、Spinel エディタが終了のたびに文書の枠を 1 つ漏らし、起動 6 回目から編集できなくなる不具合を直した。
> 静的な D/IRAM は 3 機種とも develop と同じ

## 結論

- E1: 正常終了で `mrb_close` を呼ぶようにした。点検なしの版で 1 本 9-28 ms。終了全体 (kill の要求から戻りまで) の
  時間は前後で同じ範囲 (0.2-0.8 秒、アプリが停止要求に気づくまでの時間が大半)。不正な解放は 0 回、プールは戻る。
- E1 の副作用として、終了の後始末をロックの中で長くしたことで、もとからあった競合が表に出た (下の「E1 で見つけた
  競合」)。終了したアプリのタスクを、最後のログを書いている途中で消して、標準出力のロックが失われ、端末全体が
  止まった (1 回)。タスクが本当に待機に入ったことを示す印 (`parked`) を足し、それを見てから消すようにした。
- E2: 原因は確かめた。Spinel の設計文書 (フォークの docs/internals/multi-instance.md) は「1 つのコンパイル済み
  プログラムにつきインスタンスは 1 つ」を制約として書き、守らせるのは慣習だけだった。ホスト側がそれを守らせて
  いなかった。案 (1) で直した: 同じ Spinel プログラムが動いていれば、2 つ目の起動を断ってエラーの窓を出す。
- 別件で見つけて直したもの: Spinel エディタの文書の枠の漏れ (起動 6 回目から「Doc full」)。
- フォークへのコミットはしていない。根本の案 (2) と、強制終了の後に残る状態の掃除は、提案として下に書いた。

## E1: mruby アプリの正常終了で mrb_close を呼ぶ

### 変えたこと (c8e3e181)

- `execute_mruby_script` の末尾で `mrc_ccontext_free(cc)` を呼ばず、`ctx->mrc_cc` に残す (コンテキストに欄を 1 つ追加。
  `g_ctx_pool` は PSRAM なので内蔵 RAM は増えない)。
- `destroy_vm` の正常終了の経路で、上流 (r2p2 の `main`) と同じ順番 `mrb_close(mrb)` → `mrc_ccontext_free(cc)` にした。
  `mrc_ccontext_free` は `mrb_free(c->mrb, …)` を通るが、この版の `mrb_free` は `mrb_basic_alloc_func` に渡すだけで
  `mrb_state` を読まないので、閉じた後でも安全。念のため `ctx->mrb` を先に NULL にして、prism の確保の割り当て先
  (`fmrb_current_compile_mrb`) が閉じた VM を返さないようにした。
- 強制終了の経路では呼ばない。理由はコメントに書いた: (a) 消されたタスクがどの C 呼び出しの途中だったか分からず、
  `mrb_close` は全オブジェクトの解放関数と gem の後始末 (File の close を含む) を殺した側のタスクで走らせる。
  (b) mruby の解放は「今のタスクのヒープ」を使う (`mrb_basic_alloc_func` が今のタスクの est を読む) ので、殺した側の
  タスクから呼ぶと、解放が全部殺した側のプールに入る。
- 起動に失敗したときの巻き戻し (`unwind`) も、同じ (b) の理由で閉じない (起動した側のタスクで走るため)。コメントを
  書き直した。
- 上流の picoruby コマンド (`picoruby.c`) は `mrb_close` をコメントアウトしているが、r2p2 (`picoruby-bin-r2p2` と
  `picoruby-r2p2/ports/rp2040`) はこの順番で呼んでいる。後者に合わせた。

### 終了にかかる時間

`mrb_close` そのもの (新しいログ `mruby VM closed in N ms`、P4-Nano、点検なし、3 周):

| アプリ | 1 周目 | 2 周目 | 3 周目 | 点検あり (S2c の数え方を当てた版、参考) |
|---|---|---|---|---|
| Shell (irb で `42` → `exit` の後) | 13 ms | 21 ms | 13 ms | 1,470 ms |
| MML | 18 | 22 | 18 | 252 |
| BlockGame | 16 | 12 | 12 | 600 |
| Monitor | 10 | 11 | 11 | 249 |
| Spinel Hello (Spinel の gem を呼ぶ mruby アプリ) | 9 | 16 | 9 | 131 |
| 試験用アプリ (`eval` と `Sandbox` を使う mruby アプリ) | 20 | 17 | 17 | 142 |

`/app/kill` の要求から応答までの時間 (curl の `time_total`、要求 → アプリが停止に気づく → 後始末 → 回収):

| アプリ | 前 (develop 相当 a40c7fa9、2 周) | 後 (E1、3 周) | 最終版 (E1 + 競合の修正 + E2、5 周) |
|---|---|---|---|
| Shell | 0.19 / 0.29 | 0.27 / 0.20 / 0.26 | 0.19-0.38 |
| MML | 0.28 / 0.39 | 0.26 / 0.30 / 0.34 | 0.19-0.38 |
| BlockGame | 0.38 / 0.37 | 0.28 / 0.29 / 0.20 | 0.22-0.31 |
| Monitor | 0.81 / 0.79 | 0.82 / 0.77 / 0.71 | 0.61-0.88 |
| FM-Editor (Spinel、参考) | 0.20 / 0.12 | 0.18 / 0.28 / 0.25 | 0.27-0.38 |
| Spinel Hello | 0.50 / 0.41 | 0.33 / 0.58 / 0.37 | 0.40-0.59 |
| 試験用アプリ | 0.18 / 0.30 | 0.31 / 0.31 / 0.19 | 0.18-0.30 |

- 前後の差は揺れの範囲に収まる。`mrb_close` の 10-20 ms は全体から見えない。全体の大半は、アプリが `on_update` の
  1 回りで停止要求に気づくまでの時間 (Monitor は描画が重いので長い)。
- 点検あり (`est_free` が 1 回ごとにプールを先頭から走査する) では Shell が 1.5 秒かかり、kill の応答が 1.7 秒に
  なった。点検を通常のビルドから外した S2c の T2 があって初めて、終了で閉じても困らない。
- `mrb_close` は `g_ctx_lock` を持ったまま走る (`destroy_vm` の正常終了の経路は錠の中)。その間は `ps` やほかの kill が
  待つ。10-30 ms なので問題にしないが、もし重いアプリで長くなるなら、錠の外へ出すのが次の手 (出すには状態の
  公開の順番を見直す必要がある。下の競合の話と同じ所)。

### 不正な解放

測り方: `lib/patch/.../estalloc.c` の `est_free` の点検の塊を一時的に `#if 1` にし (検査で弾いた回数を数える変数を
追加、0xff 埋めは外した)、`destroy_vm` の `mrb_close` の前後と 10 秒ごとのダンプで累計を出した。`ESTALLOC_DEBUG`
そのものは定義していない (構造体の形が変わるため)。1 周 = Shell (irb で `42`、`exit`) → MML → BlockGame → Monitor →
FM-Editor (打鍵) → Spinel Hello → 試験用アプリ、を 3 周。

- `mrb_close` 1 回ごとの弾かれた解放: **全 18 回で 0**。累計も最後まで 0。
- 落ちない。強制終了も 0 回 (Shell も通常の終了)。
- 試験の後、計装は全部戻した (`git diff lib/` は空)。

### プールの戻り

アプリを起動するときの `M1|spawn:<名前>` 行の PSRAM の空きは、最初の Monitor の後は全部 11,226,576 で揃った
(1 周目の Monitor より前だけ 11,228,488。差の 1,912 B は Monitor が最初に開いたときに常駐側に残す分で、S2c と
同じ)。内蔵 RAM の空きも同じアプリなら周ごとに数十バイトの幅に揃っている。`mrb_close` を足しても漏れは出ない。

### E1 で見つけた競合 (端末全体が止まる) と直し方

最終版を試している途中で、端末が 1 回固まった (19:42)。状況:

- 起動・終了のくり返しの中で、Shell を `/app/kill` で閉じた直後。シリアルの最後の行は
  `[FM-Shell] mruby VM closed in 28 ms` → `Exited on request, reaping` → `State: STOPPING -> FREE` → `I (` で、行の途中で
  出力が止まった。ping は返るが HTTP は応答しない。再起動 (rst) も Guru も出ない。

原因 (コードを読んで確かめた。前からある競合で、E1 で起きやすくなった):

- アプリの後始末 (`app_task_main` の `cleanup:`) は、`g_ctx_lock` の中で状態を STOPPING にし、VM を閉じ、資源を
  返し、錠を放す。そのあと錠の外で「Resources cleaned up」のログを書き、終了の通知を kernel に送り、それから待機の
  ループに入る。
- 一方 `fmrb_app_kill` は 10 ms ごとに錠を取って状態を見て、STOPPING なら「後始末が済んで待機している」とみなして
  `fmrb_app_reap` でタスクを消す。kernel が終了の通知を受けたときの `fmrb_app_reap` も同じ。
- つまり、STOPPING が見えた時点では、アプリはまだ最後のログを書いている途中かもしれない。そこでタスクを消すと、
  ログ (標準出力) のロックが持ち主ごと消えて二度と放されず、以後ログを書くタスクが全部止まる。上の `I (` で止まった
  出力はまさにこの形 (消されたタスクが書きかけた行)。通知の送信の途中なら、メッセージの登録表のロックが同じように
  失われる。
- develop では錠の中の後始末が短く、kill 側の 10 ms の見回りは、たいていアプリが待機に入った後に来ていた。E1 で
  錠の中に `mrb_close` の 10-30 ms が入ると、kill 側はその間ずっと錠を待ち、アプリが錠を放した瞬間に取って
  STOPPING を見る。消す時刻がアプリの最後のログと重なりやすくなった。

直し方 (42494d08): コンテキストに `parked` (待機に入った印) を足した。アプリは最後の送信の後、待機のループの直前で立てる。

- `fmrb_app_kill`: STOPPING でも `parked` でなければ消さずに待つ。後始末が進んでいる間は猶予を 1 秒から
  `KILL_SYNC_WAIT_MS` (30 秒) に延ばす (後始末が始まっているのに強制の経路へ行くと、それこそ途中で消すことになる)。
- `fmrb_app_reap`: `parked` を待ってから消す (錠を放して 10 ms ずつ、最大 1 秒)。1 秒たっても立たないときは警告を
  出して消す (枠を持ったままにしない)。待っている間に kill 側が回収したら何もしない。
- 欄は PSRAM のコンテキストの中なので内蔵 RAM は増えない。

直した後の最終版で、起動・終了の 5 周とエディタの試験 (下) を通して、固まりも強制終了も `Not parked` の警告も
0 回。ただしこの競合は 1 回しか出ておらず、直したことを回数で示すのは難しい。根拠はコードの順番のほう。

## E2: エディタ (Spinel) の同時起動の abort

### 再現の条件

計測用の版 (E1 + 一時の計装: 例外スタックの深さの最大と、今の深さを 10 秒ごとのダンプと Spinel インスタンスの
終了時に出す) で試した。手順は「エディタを 2 つ開く → 2 つとも kill → 3 つ目を開く」。

| 環境 | 閉じる順 | 結果 |
|---|---|---|
| 実機 P4-Nano、develop 相当 (5 時間動かした後) | 新しい方から | 3 回中 0 回 |
| 実機、計測用の版 (焼いた直後) | 新しい方から | 5 回中 0 回 |
| 実機、計測用の版 | **古い方から** | 3 回中 1 回: **残った方のエディタが Guru (Stack protection fault)** |
| sim 標準構成、計測用の版 | 両方の順 | 各 3 回、計 6 回中 0 回 (共有は観測できた、下) |

実機で落ちた 1 回の記録:

```
I (18:54:26.180) spx: App FM-Editor received stop command      <- 古い方 (pid 5) に停止要求
I (18:54:26.208) spx: Script ended
E2TOP end hw=6 top=3                                           <- pid 5 のインスタンスの終了時、深さが 3 残っている
Guru Meditation Error: Core  1 panic'ed (Stack protection fault).
Detected in task "FM-Editor" at 0x4fc1b23c                     <- 残った方 (pid 6)
Stack pointer: 0x4ff97fe0
Stack bounds: 0x4ff99930 - 0x4ff9f8a0                          <- SP が自分のスタックの外
RA: sp_FmrbApp__spin (editor_combined.rb:2099)
```

残ったエディタが `_spin` の中から longjmp し、行き先の jmp_buf に入っていたスタックポインタが自分のスタックの外
(消えた方のエディタのスタック) を指していた。S2c の abort (3 つ目のエディタで `rescue` が効かずに `Errno::ENOENT`)
と、S2c の計測ビルドで起きた「片方を閉じると両方が終わる」(`NoMethodError: undefined method '<' for nil`) も、同じ
共有から来る壊れ方の別の現れ。

条件をまとめると:

- 必要なのは「同じ Spinel プログラムが 2 つ同時に動く」こと。長く動かすことは必要ない (焼いた直後に再現した)。
- 壊れ方は、どちらが先に終わるか、そのとき相手がどの深さで何をしているかで変わる。古い方を先に閉じたとき、
  残った方が次に例外を投げると、すでに無い相手の jmp_buf に飛ぶ。3 つ目で abort するのは、前の 2 つが残した
  深さ (sp_exc_top) が 0 以下になった後 (`rescue` を張っても深さが 0 以下のままで、「捕まえる所が無い」扱いになる)。
- sim で落ちないのは、Linux ポートでは FreeRTOS のタスクがほぼ 1 本ずつ動き、残った方がこの時に例外を投げる
  経路に入らなかったため (共有自体は sim でも観測できた)。

### 何が共有されているか

`ExcHW` の表示で直接見えた: エディタを 2 つ開いている間、2 つのインスタンスの「今の深さ」が常に同じ値
(計測用の版のダンプで `6/6` と `6/6`)。1 つ目が終わるとき深さは 3 (= 相手の分)。ひとつのエディタだけなら 3。
S2c で見えた「3 つ目のエディタの ExcHW が 6」も、最大値 (`sp_exc_hw`) が翻訳単位の static で、誰も戻さないため。

生成された `editor_combined.c` と Spinel の実行時 (`spinel_rt.h`、`sp_ctx.h`) を読んで、2 つのインスタンスで共有される
ものを分けた:

| 種類 | 例 | 置き場所 | 2 つ目の起動で戻されるか |
|---|---|---|---|
| 例外・catch・break のスタック | `sp_exc_stack[16]` (jmp_buf)、`sp_exc_top`、`sp_exc_cls/msg/obj`、`sp_rescue_sp`、`sp_exc_hw`、`sp_catch_*` | `spinel_rt.h` の static (翻訳単位ごと、`SP_TU_BSS` で PSRAM) | **戻されない** |
| 例外の受け渡し中の値 | `sp_pending_exc_obj`、`sp_pending_cause`、`sp_last_exc_cls`、`sp_unwind_kind` ほか | 同上 | 戻されない |
| クラスの ivar・定数・グローバル | `civ_FmrbApp_*`、`civ_EditorApp_*`、`cst_*` | 生成 C の static | **戻される** (`sp_reset_tu_statics`) |
| オブジェクトの使い回しのリスト | `sp_<Class>_pool_head` ほか (`SP_MULTI_CTX` ではスラブを使わないので実際に使われる) | 生成 C の static | 戻される |
| 動的シンボル表 | `sp_ndyn`、`sp_bigl` | 生成 C の static | 戻される |
| GC のヒープ・ルート、文字列ヒープ、正規表現の状態など | `sp_gc_*` | `sp_ctx` (インスタンスごと) | 共有されない |

- 1 段目と 2 段目は、同時に動く 2 つのタスクが 1 本のスタックを押し引きする。片方の例外が相手の jmp_buf に着地
  すれば、別のタスクのスタックへ飛ぶ (上の Guru)。深さの増減は 2 つのタスクから非原子的に行われるので、ずれると
  負にもなる (3 つ目の abort)。
- 3-5 段目は、2 つ目が起動したときの `sp_reset_tu_statics` が、1 つ目の動いている最中の値を nil に戻す。1 つ目の
  `civ_FmrbApp_user_area_*` などが突然 nil になる (S2c の `undefined method '<' for nil`)。オブジェクトの使い回しの
  リストは、片方のヒープの物を相手に渡しうる (その後で片方のヒープが消える)。
- Spinel の設計文書はこれを承知している: 「Category-(2) TU statics are shared by all instances of the *same* TU …
  Enforced only by convention」(フォークの docs/internals/multi-instance.md、Constraints)。この文書は「kernel /
  desktop / shell はそれぞれ 1 つなので問題ない」と書くが、エディタは 2 つ開けた (`/app/launch` でもランチャーの
  2 回押しでも、メニューの Editor でも)。`sp_ctx.h` の `statics_inited` の注記にも「2 つのプログラムが同じ
  インスタンスを共有すれば civ_ を共有する」とある。

### ESTALLOC_DEBUG を外して出やすくなったか

確かめた範囲では、`ESTALLOC_DEBUG` は条件ではない。

- 点検なしの版で、焼いた直後に再現した (古い方から閉じる順、3 回中 1 回)。逆の順では点検なしでも 5+3 回中 0 回。
  S2c の `dbl_editor.sh` も新しい方から閉じる順。点検の有無より順番の差の方が大きい。
- 点検の有無で変わりうる経路は 2 つあるが、どちらも原因ではなく「壊れ方の見え方」を変えるだけ:
  - 点検ありの `est_free` は解放のたびにプール全体を走査する (S2c で Shell の終了に 1.5 秒)。Spinel の GC も解放を
    `est_free` に流すので、2 つのエディタの動く時間の重なり方が変わる。
  - 点検ありの `est_cleanup` は、インスタンスの終了時にプール全体を 0 で埋める。共有された値 (例外のオブジェクトや
    メッセージ) が消えた方のヒープを指していても、点検ありなら 0 を読み、なしなら古い中身を読む。
- S2c で「長く動かした計測ビルドで 2/2」だったのは、計測の台本の (d) でエディタを開いたまま次の周に入り、同時に
  2 つ動いた状態から始まったため、と見るのが自然 (この報告では、長く動かしたこと自体が条件ではないことを、焼いた
  直後の再現で確かめた)。

### 直し方の選択

plan.md の候補 3 つ:

| 案 | 中身 | 判断 |
|---|---|---|
| (1) 同じ Spinel プログラムの同時起動を止める | ホスト側で 2 つ目を断る | **採用** |
| (2) Spinel 側でインスタンスごとに持つ | 翻訳単位の static を全部インスタンスごとの領域に移す | 大きい。案として返す (下) |
| (3) 終了時の後始末で状態を戻す | 終了時に static を戻す | 同時に動いている間の壊れ方 (相手の jmp_buf への着地、2 つ目の起動による 1 つ目の ivar の消去) を防げない。採らない |

(1) を選んだ理由:

- Spinel の設計がこの制約を前提にしている (上の Constraints)。足りなかったのはホスト側で守らせることだけ。
- (3) では直らない。壊れるのは 2 つが同時に動いている間で、終了時ではない。
- (2) は、例外・catch スタック (この設定では 16 段。jmp_buf だけで 16 × 304 B、スタック類の合計で翻訳単位あたり
  約 11 KB) を含む翻訳単位の static を、インスタンスごとの領域へ移し、生成コードのすべての参照を `SP_CTX()` 越しに
  する変更になる。エディタの翻訳単位にはファイルスコープの変数が約 800 あり、熱い経路 (例外の arm / disarm、クラス ivar の読み書き) が全部 1 段
  間接になる。Spinel の codegen と実行時の両方の作り直しで、上流の方針 (Constraints に書いた制約) とも違う。
- エディタを 2 つ同時に開く必要はない (1 つのエディタで複数のファイルを扱える)。断ったときは、Python のアプリを
  2 つ目で断るのと同じくエラーの窓を出す (ランチャーから押して何も起きないように見えないように)。

### 変えたこと (a1b2ee50)

- `fmrb_app_spinel_claim(ctx, program)` / `fmrb_app_spinel_release(ctx)` (fmrb_app.c):
  「同じプログラム」の印は、そのプログラムの `Init_<program>` 関数 (翻訳単位ごとに 1 つ)。`default/editor` と
  `default/editor_fs` は同じ `Init_editor` を使うので、どちらから開いても 1 つに数える。`g_ctx_lock` の中で全スロットを
  見て、動いているアプリが同じ印を持っていれば `FMRB_ERR_BUSY` を返し、「This app is already running. / Only one copy
  of it can run at a time.」のエラーの窓を出す。印はコンテキストの欄 `spinel_program` (PSRAM)。
- `fmrb_app_run_spinel_vm` (kernel、desktop、editor が使う Spinel の入口) が、インスタンスを作る前に claim し、
  インスタンスを壊した後に release する。強制終了ではそこまで来ないので、`destroy_vm` の NATIVE の経路で印を消す
  (消さないと、そのプログラムは二度と起動できなくなる)。
- `fmrb_app_run_spinel_vm` に `after` (プログラムの終了後、まだ claim を持っている間に呼ぶ後始末) の引数を足した。
  エディタの文書の枠の返却 (下) に使う。kernel と desktop は NULL。

### 別件で見つけて直したもの: Spinel エディタの文書の枠の漏れ

E2 の試験で「エディタを開いて 1 打鍵」を何度もくり返すと、sim で 7 回目、実機で 6 回目のエディタから、打鍵の
たびに「Doc full」(ログは `Editor document arena full (6444 bytes used)`) になって編集できなかった。develop と同じ
コードの部分で、E1/E2 の変更とは関係なく前からある。

- 原因: Spinel 版エディタの `EditorCore.slot` は、文書の枠を `@slot` (クラスの ivar) に覚えて初回に
  `ec_open_slot` で取る。閉じる処理はどこにも無い (mruby 版は VM ごとの表で取り返している)。そのうえ次の
  インスタンスの入口で `sp_reset_tu_statics` がこの ivar を nil に戻すので、毎回新しい枠を取る。枠は
  `FMRB_USER_APP_COUNT` (= 5) 個しか無いので、起動から 6 回目のエディタは枠が取れず、全操作が失敗を返す。
- 直し方: C 側 (fmrb_spx_editor.c) が、走っているエディタの枠を覚える (PSRAM の static 1 つ。同時に 1 つしか
  動かないことは上の claim が保証する)。プログラムの終了後に `after` で返す。強制終了で返せなかった枠は、次の
  エディタが枠を取るときに取り返す (1 つしか動かないので、記録に残っている枠は必ず死んだエディタの物)。
- 確認: sim で 20 回以上、実機で 49 回エディタを開いて、最後まで打鍵が入った (「Doc full」0 回)。

### ほかの Spinel アプリで同じ形が起きうるか

| 対象 | 同時に 2 つ動きうるか | 判断 |
|---|---|---|
| kernel (Spinel) | 起動時に 1 つだけ | 対象外 (claim も通る) |
| desktop (`FMRB_APP_ENGINE_DESKTOP=spinel` のとき) | `PROC_ID_SYSTEM_APP` 固定で 1 つ | 起きない。claim も効く |
| エディタ | 起きていた | 本件。claim で止めた |
| Spinel の gem (raycast、spinel_hello、fft) | gem 側の static で「インスタンスは 1 つ、作ったタスクだけが使う」作り (`s_open` など) | **同じ形の別の穴がある (未対処)**。2 つの mruby アプリが同じ gem を同時に使うと、2 つ目は `begin` で既存のインスタンスを使い回すが、そのインスタンスは 1 つ目のタスクでしか「今のインスタンス」になっていない。fft の注記は「単一の持ち主タスク」を制約として書いているが、守らせる仕組みは無い。また持ち主のアプリが `end` を呼ばずに終わると (強制終了など)、インスタンスが残り、次の別タスクの呼び出しがそれを使う。試していない。直すなら gem の `begin` で持ち主のタスクを記録し、違うタスクからの呼び出しを断る (claim と同じ考え方) のが小さい |

### 残ること (提案)

1. **強制終了の後に残る翻訳単位の状態** (フォークの変更、小さい): `sp_reset_tu_statics` は ivar・定数・
   使い回しのリストは戻すが、例外・catch・break のスタックの深さ (`sp_exc_top`、`sp_catch_top`、`sp_rescue_sp`、
   最大値 `sp_exc_hw`/`sp_catch_hw`、受け渡し中の値) は戻さない。正常終了なら深さは 0 に戻っているので困らない
   が、強制終了で消したエディタは深さを残す。次のエディタはその上に積むので、強制終了をくり返すと
   `SP_EXC_STACK_MAX` (この設定では 16) に近づき、`ExcHW` の表示も実際より大きく出る。codegen の `emit_tu_ctx_init` が作る
   `sp_reset_tu_statics` に、これらを 0 に戻す行を足せば直る (同時に 1 つしか動かない前提でだけ正しい。今回の
   claim でその前提が成り立つ)。今回は入れていない (フォークの変更で、SPINEL_PIN の更新は親の判断のため)。
2. **案 (2)** (大きい): 翻訳単位の static をインスタンスごとに持たせる。必要になるのは「同じ Spinel プログラムを
   本当に 2 つ同時に動かしたい」場面が出たとき。そのときは上の表の 1-5 段目を全部 `sp_ctx` (またはプログラムごとの
   インスタンス領域) に移す。スタック類は 1 インスタンス約 11 KB (今は翻訳単位ごとに PSRAM)。
3. Spinel の gem の持ち主タスクの確認 (上の表)。
4. `mrb_close` を `g_ctx_lock` の外に出すこと (今は 10-30 ms なので急がない)。

- 「エディタを 2 つ開く → 2 つとも kill → 3 つ目を開く」を、古い方から閉じる順と新しい方から閉じる順で 6 回ずつ →
  起動・終了の 1 周 (7 本) を 3 周 → 同じ試験を 3 回ずつ → 1 周を 2 周 → 同じ試験を 2 回ずつ (計 22 回、約 20 分)。

  条件は「同時に 2 つ」で、時間ではなかった。
