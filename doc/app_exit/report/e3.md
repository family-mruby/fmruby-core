# 報告 E3: Spinel アプリの同時起動の制限を外す

> 状態: 完了 (親の検収待ち) | 更新: 2026-10-03 | コミット: (このファイルと同じコミット) | E2 で入れた「同じ Spinel プログラムは 1 つしか起動できない」制限を外した。
> E1 (`mrb_close`)、競合の修正 (`parked`)、エディタの文書の枠の返し忘れの修正は残した。枠の修正は 1 つの変数で
> 「動いているエディタは 1 つ」を前提にしていたので、アプリの枠ごとに持つ形に直した。sim (標準・互換)、
> ブラウザ版、実機 P4-Nano、`rake test`、5 構成のビルドを通した。実機では 2 つ同時の手順で元からの落ち方が
> 2 回出た (E2 で記録したものと同じ)。新しい落ち方と「Doc full」は出ていない。静的な D/IRAM は develop と同じ

## 結論

- 制限は外した。エディタは develop と同じく 2 つ同時に開ける。断りの窓 (「This app is already running.」) は出ない。
- 外したあとの動きは**元に戻るだけ**。同じ Spinel プログラムの 2 つのインスタンスは、生成 C のファイル単位の変数
  (例外スタック、クラスの ivar、定数、オブジェクトの使い回しのリスト) を共有したまま。2 つ同時に動かすと、まれに
  落ちる・状態が混ざる (E2 の表のとおり。実機では古い方を先に閉じたとき 3 回中 1 回 Guru)。根本の直しは
  doc/spinel_multi_instance で別に計画する。新しい手当て (別の制限、警告の表示) は入れていない。
- 文書の枠の修正は、2 つ同時に開いたときにも正しく動くようにした。そのために、枠の番号を Ruby 側の ivar に
  覚えさせるのをやめ、C 側でアプリの枠 (app_id) ごとに持つようにした (下)。

## 変えたこと

### 外したもの (a1b2ee50 の制限の部分)

- `fmrb_app_spinel_claim` / `fmrb_app_spinel_release` (fmrb_app.c と fmrb_app.h の宣言・説明)。
- コンテキストの欄 `spinel_program`。
- `fmrb_app_run_spinel_vm` の claim と、失敗時・終了時の release。
- `destroy_vm` の NATIVE の枝での claim の解放 (develop の 1 行のコメントに戻した)。
- fmrb_app.c は a1b2ee50 の差分をそのまま逆に当てた。結果は 42494d08 と同じ内容。

### 残したもの

- E1 (c8e3e181、正常終了で `mrb_close` → `mrc_ccontext_free`)。
- 競合の修正 (42494d08、`parked` を見てからタスクを消す)。
- `fmrb_app_run_spinel_vm` の `after` の口。説明から「claim を持ったまま」「断られたときは呼ばない」を外し、
  「この app のタスクで、プログラムが終わりインスタンスを片付けた後に呼ぶ。インスタンスを作れなかったときと
  強制終了では呼ばない」にした。kernel と desktop は `NULL` を渡す (a1b2ee50 のまま)。
- エディタの文書の枠の返し忘れの修正 (下のとおり形を変えた)。

### 文書の枠の修正を、同時に 2 つでも正しく動くようにした

a1b2ee50 の形は、制限があることを前提にしていた:

- 枠の記録が `s_slot_plus1` の 1 つだけ (「Spinel エディタは同時に 1 つ」と注記)。
- `fmrb_spx_ec_open_slot` が最初に記録済みの枠を閉じてから開く (「記録があれば強制終了されたエディタの残り」と
  みなしていた)。2 つ目のエディタが開くと、動いている 1 つ目の枠を閉じてしまう。

さらに、制限を外しただけでは次の問題が出ることを sim で確かめた (計装を入れた版):

- エディタの Ruby 側 (`EditorCore.slot`) は枠の番号をモジュールの ivar `@slot` に覚えていた。ivar は同じプログラムの
  インスタンスで共有される。2 つ目のエディタが起動すると、入口で ivar が nil に戻り、2 つ目が開いた枠の番号が
  入る。1 つ目もその番号 (2 つ目の文書) を使う。
- develop では枠を誰も閉じないので、1 つ目は 2 つ目の文書を編集し続けるだけだった (状態が混ざる症状の一つ)。
  枠を返す修正が入ると、2 つ目が終わった時点でその枠が閉じられ、1 つ目は閉じた枠に書こうとして、打鍵のたびに
  「Doc full」になった (sim で再現: A を開いて "first" → B を開いて "second" → B を閉じる → A の画面が空で
  「Doc full」)。これは新しい落ち方なので、枠の修正と同時起動が両立する形に直した。

直し方:

- C 側 (fmrb_spx_editor.c) で、枠の番号をアプリの枠 (app_id) ごとの表 `s_slot_plus1[FMRB_MAX_APPS]` に持つ
  (PSRAM、36 B)。呼んだタスクの `fmrb_current()->app_id` で自分の欄を引く。
- `fmrb_spx_ec_open_slot`: 自分の欄に枠があればそれを返す。無ければ開いて記録する。ほかの欄には触らない。
- `EditorCore.slot` (main/prebuild_scripts/spinel/fmrb_editor_ffi.rb) は ivar に覚えず、毎回 C 側に聞く。mruby 版の
  バインディング (editor_core_mrb.c の `slot_of(mrb)`) が VM ごとに毎回引くのと同じ形。1 回の呼び出しで足されるのは
  TLS の読み出しと配列の参照だけ。
- `fmrb_spx_ec_release_slot` (自分の欄の枠を閉じて欄を空にする) を、エディタのタスク本体
  (`spinel_editor_native`) で**プログラムの開始前**と**終了後 (`after`)** に呼ぶ。
  - 終了後: 正常に終わったエディタが自分の枠を返す。
  - 開始前: 同じアプリの枠で前に動いていたエディタが強制終了された (強制の経路は `after` を通らない) ときの
    残りを回収する。開始前なので、この欄にあるのは必ず前のエディタのもので、ほかの生きているエディタの欄では
    ない。
- `fmrb_spx_ec_close_slot` (Ruby からは今は呼ばれていない) は、閉じるのが自分の欄の枠なら欄も空にする。
  後で終了時にもう一度閉じて、別のエディタが開き直した同じ番号の枠を閉じることを防ぐ。

2 つのエディタでの動き (sim 標準構成、計装の版で枠の番号をログに出して確かめた):

| 手順 | 結果 |
|---|---|
| A (app 5) を開く → B (app 6) を開く | A は枠 0、B は枠 1 (B の開始で A の枠は閉じられない) |
| 古い方 A を閉じる → B で打鍵 | A が枠 0 を返す。B は枠 1 のまま打鍵が入る ("bbb" に "ccc" が続く) |
| C を開く (app 5) → C で打鍵 → B を閉じる → C で打鍵 | C は枠 0 を新しく開く。B が枠 1 を返す。C は打鍵が続く |
| A を開いて "first" → B を開いて "second" → 新しい方 B を閉じる → A で打鍵 | A に "first" が残っていて "X" が続く (a1b2ee50 の形と ivar のままだと「Doc full」になった手順) |
| 1 つずつの起動と終了を 7 回 + 2 つ開いて閉じる (両方の順) を 4 組 + 各組の後に 3 つ目 | 開いた枠 21 回、返した枠 21 回 (開始前の回収は全部「記録なし」)。「Doc full」0 |

残ること (元からの症状で、根本の直しの対象):

- 2 つ同時に開いている間は、文書以外の状態 (カーソル位置などを持つクラスの ivar) は混ざりうる。上の 4 行目でも、
  A のステータス行の桁の表示は B の値になっていた。
- 強制終了されたエディタの枠は、同じアプリの枠で次のエディタが起動するまで残る。アプリの枠ごとに高々 1 つで、
  表の大きさ (`ED_MAX_DOCS` = ユーザアプリの数) を超えることはないが、5 つの異なる枠で強制終了が重なると、その間
  エディタが「Doc full」になりうる (develop では強制終了に限らず毎回漏れていた)。強制終了の経路で閉じないのは、
  錠を持ったまま消されたタスクの後始末を殺した側で走らせない、という E1 と同じ理由。

## 回帰の確認

| 対象 | 結果 |
|---|---|
| ビルド NARYAv4 / TAB5 / S3 (NARYAv3) | (下の「静的な D/IRAM」) |
| ビルド Linux 標準 (Spinel カーネル + Spinel エディタ) / 互換 (全部 mruby) | 通る (`file` で x86-64 を確認) |
| ビルド wasm (`spinel:gen` → `wasm:mruby` → `wasm:mrb` → `wasm:core` → `wasm:web`) | 通る |
| `rake test` | 全部通過 (golden 103 passed ほか) |
| sim 標準構成 | 上の表のエディタの手順。加えて Shell・MML・BlockGame・Monitor・エディタ・Spinel Hello・Kamon の起動と終了を 3 周。Guru・abort・`ENOENT`・`Not parked`・「Doc full」・起動失敗 0。終わった後のアプリは kernel・desktop・Services だけ |
| sim 互換構成 (エディタも mruby) | 1 つずつ 3 回 + 2 つ開いて閉じる 2 組、全アプリ 2 周。同じく 0。`mruby VM closed` 23 回 |
| ブラウザ版 | メニューからエディタを 2 つ開き、新しい方を閉じると古い方に自分の文書 ("one") が残る。続けて 1 つずつ 3 回開いて打鍵・閉じる。Monitor の起動と終了。落ちない、「Doc full」なし (起動時の paint_pad の「Failed to launch」は既存で無関係) |
| 実機 P4-Nano (最終版) | 下 |
| Retro (S3) 実機 | 未 (実機なし、ビルドだけ) |

実機 (最終版、NARYAv4、app パーティションだけ焼いた) の試験:

- 手で 1 回: A を開いて "first" → B を開いて "sec" → 新しい方 B を閉じる → A で打鍵。A に "first" が残り "x" が
  続いた。
- エディタ: 1 つずつの起動・打鍵・終了を 7 回 → 「2 つ開いて (それぞれ打鍵) 片方を閉じ、残りで打鍵して閉じる、
  続けて 3 つ目を開いて打鍵して閉じる」を、古い方から・新しい方からを交互に 6 組。
- 全アプリ (Shell・MML・BlockGame・Monitor・エディタ・Spinel Hello・Kamon) の起動と終了を 3 周 (21 回)。
- 新しく開いたエディタで打鍵が入ることを画面で確認 ("ok")。
- 続けてエディタ 1 つずつ 3 回 + 2 つの組をもう一度 (1 組目で落ちたのでそこまで)。
- エディタの起動は計 42 回 (アプリ全体の起動は 54 回)。

| 項目 | 結果 |
|---|---|
| 1 つずつの起動と終了 | 落ちない。「Doc full」は一度も出ない (最後に開いたエディタも打鍵が入る) |
| 全アプリ 3 周 | 落ちない。`Not parked` 0、強制終了 0 |
| 2 つ同時の組 | 8 組中 2 組で落ちた。どちらも E2 で記録した元からの症状 |

落ちた 2 回:

1. 新しい方 (B) を先に閉じた組 (01:10:35): B が停止の処理の中で `NoMethodError: undefined method '<' for nil` で
   終わり、A も同時に終わった (S2c で見た「片方を閉じると両方が終わる」)。続けて開いた 3 つ目が
   `/home/colors.toml` の `Errno::ENOENT` を `rescue` で捕まえられずに abort → 再起動 (S2c・E2 の 3 つ目の abort
   と同じ)。
2. 古い方 (A) を先に閉じた組 (01:14:34): 残った B が `Stack protection fault`、スタックポインタが自分のスタックの
   外。落ちた所 (0x4fc1b23c) も E2 の記録と同じ。→ 再起動。

どちらも再起動のあとは普通に起動し、続きの手順も通った。制限を外して元に戻った動きで、根本の直し
(doc/spinel_multi_instance) の対象。新しい落ち方 (別の場所での Guru、「Doc full」、`Not parked`) は無かった。

## 静的な D/IRAM

| ビルド | Used stat D/IRAM | 同じ環境で測った develop | 記録の develop (E1 報告) |
|---|---|---|---|
| NARYAv4 (最終版) | 125,612 | 125,612 (増減なし) | 125,604 |
| TAB5 | 130,194 | (未測定) | 130,186 |
| S3 (NARYAv3) | 126,259 | (未測定) | 126,251 |

- 3 機種とも記録の値より 8 B 多いので、原因を確かめた。NARYAv4 で、変えたソースを develop の版
  (`git checkout develop -- …` で一時的に戻す) と HEAD (a1b2ee50 の形) の版にしてそれぞれ作り直すと、どちらも
  125,612 になった。FFI の Ruby だけを元に戻しても 125,612。つまり 8 B はこの変更から来ていない (作業ツリーの
  ほかの状態の違い。submodule の未コミットの変更など)。同じ環境の develop と比べて増減なし。TAB5 と S3 は
  develop を同じ環境では測っていないが、増えた量が NARYAv4 と同じ 8 B なので同じ理由と見ている。
- 足した表 `s_slot_plus1` は PSRAM (`.ext_ram.bss`、36 B) に置かれていることを map で確かめた。

## 途中で止まった所 (解消済み)

- 最初の書き込み (計装の版) で、esptool が `/dev/ttyACM1` に接続できずに 900 秒で時間切れになった。端末は
  リセットされずに a1b2ee50 のまま動いていた (シリアルは 00:34 以降データが来ていなかった。E1 の報告と同じ USB
  シリアルの止まり方)。残った flash のコンテナを止めようとしたが権限の判定で止められず、先にビルドを進めた。
- その後コンテナは無くなっていた (自分では止めていない)。`rake attach` で付け直すと `/dev/ttyACM0` になったので、
  `.serial_port` (git の管理外) を `/dev/ttyACM0` にして、キャプチャを開き直し、最終版を焼いた。計装の版は
  実機に焼いていない (枠の番号のログでの確認は sim だけ)。
