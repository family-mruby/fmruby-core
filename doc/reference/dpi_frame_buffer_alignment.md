# DSI (DPI) フレームバッファの置き場所と走査のアンダーラン

ESP32-P4 の MIPI-DSI 出力 (NARYAv4 の LT8912B / HDMI、Tab5 のパネル) で、
フレームバッファの**先頭アドレスの揃い方**が走査の余裕を左右する、という知見。
実測と経緯は `doc/naryav4/report/p6.md` と
`doc/p4_display_flicker/report/tab5_fb_align.md`。

## 分かっていること

- esp_lcd の DPI パネルは、フレームバッファを自分で
  `heap_caps_calloc(SPIRAM | 8BIT | DMA)` で確保する。揃いはキャッシュライン
  (64B) だけで、呼び出し側からバッファも揃えも渡せない (IDF 5.5.4)。
- 走査の DMA はフレームバッファを PSRAM から読み続ける (NARYAv4 の
  1280x720 RGB888 80MHz で約 179MB/s)。
- **同じ帯域・同じ負荷のまま、先頭の置き場所だけで結果が分かれた**
  (NARYAv4、同じコミットのビルド):

  | 先頭 | 起動 0-120 秒 | 重負荷 60 秒 | 画面 |
  |---|---|---|---|
  | `0x49144dc0` (64B 揃い) | 16-18 件 | 6-7 件 | 青ちらつき |
  | `0x49146000` (4KB 境界) | 0 件 | 0 件 | ちらつき無し |

- Tab5 (720x1280 RGB565、帯域は NARYAv4 の約 2/3) は、揃っていなくても
  0 件だった。揃えても退行は無い。

## 見立て (直接は確かめていない)

AXI のバーストは 4KB 境界をまたげない。先頭がずれていると、走査の
バーストが 4KB ごとに 2 つに分かれて取引が増え、読み出しの余裕が減る。
そこへ別の PSRAM 書き込みの山が重なると、ブリッジの FIFO (1 ライン
未満) が尽きてアンダーランになり、LT8912B はフレームの残りを青で塗る。
バースト長の倍数 (256B など) に揃えれば足りる可能性があるが、試していない。
4KB に揃えればどの長さでもまたがない。

## 実装 (main/drivers/display_p4/dpi_fb_align.hpp)

`dpi_fb_align_next(fb_size, tag)` を、DPI パネルを作る**直前**に呼ぶ。

1. 同じ大きさ・同じ caps で試しに確保して離し、着地点を見る。
2. ずれていれば、その場所に PSRAM の詰め物を置く (大きく取ってから
   realloc で縮めて、同じ空き領域の先頭に固定する)。
3. 揃うまで詰め物を伸ばす (最大 8 回)。詰め物は解放しない。

- 費用は PSRAM の数 KB だけ (NARYAv4 4,608B、Tab5 3,648B)。内蔵 RAM は増えない。
- 失敗しても従来の場所で続行する。起動ログの
  `fb @... (aligned|UNALIGNED, pad N)` で確かめられる。
- 呼び出し元: NARYAv4 は `lgfx_naryav4.hpp`、Tab5 は `lgfx_tab5.hpp` の
  `Tab5AlignedPanel` (M5GFX の `Panel_DSI::init()` の入口。M5GFX は編集しない)。
- Tab5 の M5GFX はフレームバッファを 2 枚確保するが、走査されるのは 1 枚目
  だけ。揃えるのは 1 枚目。2 枚目 (1.8MB の PSRAM) は使われていない。

## 注意

- **ソースを変えなくても、PSRAM の確保の量や順番が変わるとフレームバッファの
  位置が動き、走査の余裕が変わる**。P3 (Spinel の ext 化) で件数が 0 から 17 に
  増えたのは、この副作用だった。
- 試しの確保から driver の確保までの間に、別のタスクが PSRAM を取ると外れうる。
  PSRAM の確保の順番を変える変更の後は、起動ログの `aligned` を確かめる。
- ちらつきやアンダーランを調べるときは、帯域や調停より先に、**同じ条件の
  ビルド同士の起動ログを 1 行ずつ比べて、フレームバッファの番地を見る**。
  今回の原因はそれで見つかった (下記)。

## 見つけた経緯

帯域を減らす計画 (RGB565、ピクセルクロックを下げる) を試している途中で、
「画面が映らない」の原因を探すために、保存してあった 4 つのビルドの起動ログを
1 行ずつ比べた。表示に関係する違いが「フレームバッファの番地」と
「アンダーランの件数」の 2 つだけで、それが連動していた。同じビルドを焼き直して
3 回測って偶然でないことを確かめ、今の版の先頭だけを揃えて 0 件になることと、
画面でちらつきが消えることを確かめた。それ以前の対策 (バスの調停の優先度を
上げる、帯域を減らす計画) は、どれも置き場所には触れていなかった。
