# VM の速さの測り方 (ホストの時間は信用しない)

> 状態: 計測済 | 更新: 2026-11-02 | mruby の `vm.c` を変えたときの速さは、ホスト (PC) では実行時間でなく命令数で比べる。ホストの時間は、命令が 1 つも変わらなくても、コードの番地だけで +30% まで動く。時間は本番の端末 (ESP32) で測る

## 1. 結論

- **ホストで VM の改造の前後を比べるときは、valgrind の命令数で比べる**。時間 (実行
  時間の中央値) は、改造の中身と関係なく、コードの番地しだいで大きく揺れる。
- 時間で比べるなら、ビルド 1 本ずつではなく、番地をずらしたビルドを十数本作り、
  時間の**幅**同士を比べる (§4)。
- 本当の速さは本番の端末 (ESP32-S3・P4) で測る。ホストの CPU の癖 (§3) は端末には
  そのまま当てはまらない (端末は端末で、flash から命令を読むキャッシュの当たり外れが
  番地で変わる)。

## 2. 何が起きたか (2026-11-02 の実測)

mruby 4.0.0 系 (`MRB_NO_BOXING`・`MRB_INT64`、64bit、x86-64) の `vm.c` で、タスク
切り替えの判定 (`RETURN_IF_TASK_STOPPED`) の形を変える実験をした。命令の境目ごとの
判定を「2 回の読み込みと 1 回の分岐」に縮め、遅い側を 1 か所の関数にまとめた。

| ベンチマーク | 命令数 (前) | 命令数 (後) | 命令数の差 | 時間の差 |
|---|---|---|---|---|
| bm_so_mandelbrot | 135.1 億 | 128.9 億 | −4.65% | **+10.2%** |
| bm_fib | 467.1 億 | 459.3 億 | −1.67% | −7.1% |
| bm_ao_render | 568.0 億 | 560.7 億 | −1.28% | 約 −3% |

命令数はどれも減ったのに、mandelbrot だけ時間が 10% 延びた。減ったのは、命令ごとの
`NEXT` で `mrb` をスタックから読み直す分と、MUL・ADD での `regs` の退避。

番地だけを変える対照実験 (実行されない詰め物を、使われない処理の中に 12 通り入れる。
命令数はビルドごとに一定):

| | 元の vm.c | 変えた vm.c |
|---|---|---|
| 詰め物 12 通り (GCC の並べ方のまま) | −2.8 〜 +0.4% | +3.2 〜 **+32.2%** |
| 処理の並び順を両方で揃えた | −2.7 〜 +0.7% | +2.6 〜 +4.6% |
| 並び順を揃え、OP_MOVE で型の印と値を別々に写す | +15.2 〜 +17.7% | +0.1 〜 +3.4% |

最後の行で速さの順位が入れ替わる。どちらの vm.c が速いかは、改造の中身でなく、
番地の当たり外れで決まっている。

試した中で、時間に効かなかったもの:
- バイナリ全体を 16〜2048 バイトずらす (相対の位置が変わらないので効かない)。
- 熱いコードの大きさ (変えた側が小さい: 64 バイト行で 55 対 66)、分岐の数 (932M 対
  1,269M)、模擬した命令キャッシュの外れ・分岐予測の外れ。どれも時間と連動しない。
- 時間の標本で「OP_MOVE の 16 バイトの格納が重い」と出たのは見かけ (skid)。本当は
  直前の 16 バイトの読み込みの待ちで、その量は前後で同じだった。

## 3. 仕組み (この CPU での見立て)

測った機械は Raptor Lake の P コア (WSL2 の上)。

1. MUL・ADD は Float の結果を **2 つの狭い書き込み** (型の印を 4 バイト、値を 8 バイト)
   で `regs` に置く。
2. 直後の `OP_MOVE` は、そのレジスタを **16 バイト 1 回**で読む。CPU の「書いた値を
   そのまま読み出す近道」(store forwarding) は 2 つの書き込みにまたがれないので、
   ここで待つ。これは前後どちらのビルドにもある。
3. 次の命令の処理が、`OP_MOVE` が書いたばかりのレジスタの型の印を読む。

この書いて読む鎖の重さが、命令の番地しだいで大きく変わる。悪い番地では、型の印を
読む命令に時間が積もる (100 万標本あたり MUL 14,697 → 32,361、ADD 2,598 → 14,602)。
命令の並びは同じで、番地だけが違う。番地で引く「読み込みと書き込みの依存の予測器」が
一番当てはまるが、WSL2 ではハードウェアの計数器が使えず断定はできない。

Family mruby の値の表現 (`MRB_NO_BOXING`、`mrb_value` は 16 バイトの構造体) と
`OP_MOVE` の作りから来る話なので、どの端末向けのビルドでも同じ命令の並びになる。
ただし重さが出るかは CPU による。

## 4. 測り方

### 命令数 (ホスト)

valgrind は docker の中で使う (ホストに入れなくてよい)。ホストの glibc に近い
Ubuntu のイメージに valgrind を入れておく:

```
docker run --name vg -it ubuntu:22.04 bash -c "apt-get update && apt-get install -y valgrind"
docker commit vg mruby-valgrind && docker rm vg
```

ビルドしたものを差し込んで数える:

```
docker run --rm -v $PWD:/w -w /w mruby-valgrind \
  valgrind --tool=callgrind --callgrind-out-file=/dev/null \
  build/host/bin/mruby benchmark/bm_so_mandelbrot.rb 2>&1 | grep Collected
```

- 数え方は決定的で、同じビルドなら毎回同じ数が出る。差 1% も読める。
- 遅いので (実時間の数十倍)、短いベンチマーク (`bm_mandel_term` など) から試す。
- `--callgrind-out-file` を残して `callgrind_annotate` にかければ、関数・行ごとの
  命令数が出る。どこで増えた・減ったかが分かる。

### 時間 (ホストでどうしても測るとき)

- 1 つの CPU に固定 (`taskset -c N`) し、前後のビルドを交互に何度も流して中央値を取る。
- それでも 1 本のビルド同士の比較は §2 のとおり ±30% 外れうる。番地をずらした
  ビルド (使われない所に詰め物) を十数本ずつ作り、時間の幅を比べる。

## 5. Family mruby での使いどころ

- `lib/patch/picoruby-mruby/lib/mruby/src/vm.c` (自前の時分割など) や mruby の上流
  追従で VM を変えたら、ホストでは命令数を前後で比べる。時間がホストで 10% 延びても、
  それだけで差し戻さない。
- 逆に、ホストの時間で速くなったという報告も、命令数か端末の時間で裏を取るまで
  成果に数えない。
- 同じ理由で、Linux 版・ネイティブ版の性能の比較 (ホストの CPU で動くもの) も、
  1 本ずつの時間の差を根拠にしない。
