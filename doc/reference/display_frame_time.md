# 表示の 1 フレームの時間 (P4、場面ごと・区間ごと)

> 状態: 計測済 | 更新: 2026-11-18 | P4-Nano (NARYAv4) の実測。表示の合成に 3 つの手当てを入れ、426x240 のデスクトップは 1 フレーム 27.4 → 約 20 ms、640x360 は 41.5 → 約 25.5 ms になった (640x360 が、手当ての前の 426x240 より速い)。残りの 2/3 は拡大して出す処理 (SRM、約 17 ms)。区間ごとの時間は 5 秒周期のログ `display_local: frame:` で読める

企画の経緯と細部は `doc/modern_resolution/` (plan.md、report/r0.md = 計装と最初の計測、
report/r0b.md = 手当てと測り直し)。ここは結果と、測り方・ログの読み方だけを置く。

## 1. 結論

- **手当ての後、640x360 のデスクトップは、手当ての前の 426x240 より速い** (場面 1〜4 の平均で全部)。
  画素は 2.25 倍になったが、1 フレームの時間は短くなった。
- **426x240 も 2〜3 割速くなった** (Tab5 も同じ道を通る。Tab5 の実機では測っていない)。
- 効いたのは 3 つで、どれも「毎フレーム全面に対してやっていた仕事を、要る所だけにする」直し。
  出る絵は変わらない (2 章)。
- 残った時間の約 2/3 は、拡大して HDMI へ出す処理 (PPA SRM、15〜17 ms でほぼ一定)。
  ここから先は「変わった所だけ合成して出す」作りが要る (5 章)。

## 2. 入れた手当て (2026-11-18、ブランチ modern-resolution)

| 手当て | やめた無駄 | 効いた区間 (640x360、場面 1) | コミット |
|---|---|---|---|
| clear を飛ばす | 一番下に画面全体を覆う不透明な canvas (壁紙) があるのに、毎フレーム fb を 0 で埋めていた | clear 9.0 → 0.02 ms | 1285b2dd |
| 色キー付きの canvas は中身のある所だけ blend | デスクトップの前面の層 (メニューバー・ランチャーなど。ほとんど透過色) を、毎フレーム全面 blend していた | compose 15.8 → 8.7 ms | f5acd263 |
| present は描いた行だけ写す | present のたびに canvas の全面を working から committed へ memcpy していた | commit 14.4 → 0.7 ms | 2ad2256d、de60fda5 |

- 範囲 (中身のある所・描いた行) は、アプリの申告でなく、表示の側が画素と描画コマンドから求める。
- 絵が変わらないことの確認: ネイティブ版で、手当ての前後を 12 場面 × 壁紙あり・なしで画素ごとに
  比べて同じ (時計を除く)。手元だけの検査版 (commit の後に 2 つの面を全面比較) でアプリ約 95 本を
  流して食い違い 0。P4-Nano は遠隔の写しで欠け・残りなし。内蔵 RAM は増えていない (`regress:size`)。
- 入れなかったもの: working と committed の入れ替え (アプリは前の絵に描き足すので壊れる)、
  全画面のエディタの clear (色キー付きの canvas で、透過の画素が残りうるので飛ばせない)。

## 3. 場面ごとの表 (P4-Nano、total の平均 / 最悪、ms)

「前」は手当ての前、「後」は 3 つを入れた後。同じ場面を同じ台本で測った (2 回測ったものは 1 回目)。

| 場面 | 426x240 前 | 426x240 後 | 640x360 前 | 640x360 後 |
|---|---|---|---|---|
| 1 デスクトップだけ | 27.4 / 31.0 | 19.7 / 22.7 | 41.5 / 45.4 | 25.4 / 28.9 |
| 2 Window のエディタで打鍵 | 28.7 / 33.1 | 21.3 / 25.6 | 43.1 / 54.7 | 26.9 / 31.5 |
| 3 Window 4 つを重ねてドラッグ | 32.8 / 42.7 | 25.3 / 33.6 | 48.8 / 64.5 | 31.6 / 39.5 |
| 4a 動くデモ 1 つ | 27.7 / 34.3 | 20.3 / 25.4 | (42.3 / 51.3) | 25.9 / 32.3 |
| 4b 動くデモ 2 つ | 30.6 / 38.2 | 23.1 / 39.0 | 47.4 / 52.8 | 29.8 / 43.9 |
| 5 全画面のエディタ (640x360 の 1 枚) | 34.3 / 65.1 | 34.2 / 42.2 | 34.5 / 42.7 | 34.0 / 42.7 |
| 6 遠隔の画面 (MJPEG) を見ながら 3 | 43.2 / 56.6 | 35.1 / 44.9 | 未計測 | 53.2 / 75.0 |

- 場面 4a の 640x360 前は、計測中に端末が再起動したので参考の値。
- 場面 4b の最悪は手当てで縮まない (2 つのアプリが同じフレームで大きく描くときの blend)。
- 場面 5 は、解像度の設定によらず 640x360 の 1 枚を出すので同じ値。commit は 13.9 → 2.1 ms に
  減ったが、clear (約 8.5 ms) と SRM が残る。
- 場面 6 は、遠隔の画面のための写し (capture) が 426x240 で 7.4 ms、640x360 で 18.0 ms かかる。
- 入力の遅れ: エディタ自身の処理時間 (`edit_lat`、平均 5〜7 ms) は解像度で変わらない。打鍵から
  画面に出るまでの実測は無い (`hid_lat` は 1000 件ごとにしか出ず、件数が足りなかった)。

## 4. 区間ごとの内訳 (場面 1、平均 ms)

| 区間 | 中身 | 426x240 前 → 後 | 640x360 前 → 後 |
|---|---|---|---|
| clear | fb を CPU で 0 にする | 3.9 → 0.02 | 9.0 → 0.02 |
| compose | 見えている canvas の blend (PPA Blend) とキャッシュの同期 | 8.6 → 4.4 | 15.8 → 8.7 |
| out | 拡大して RGB888 で出す (PPA SRM) | 15.0 → 15.2 | 16.7 → 16.7 |
| total | 1 フレーム (`render_frame`) | 27.4 → 19.7 | 41.5 → 25.4 |
| commit | present のたびの写し (フレームの外、コマンドの処理の中) | 6.3 → 0.5 | 14.4 → 0.7 |

- キャッシュの同期は 1 枚あたり 0.3〜0.4 ms で、問題にならない。
- SRM は解像度でほぼ変わらない (出力が 1280x720 の RGB888 で同じため)。

## 5. 残っている時間と、次の手 (作っていない)

640x360 のデスクトップ 25.4 ms の内訳は、SRM 16.7 ms (66%)、壁紙の blend 約 8 ms (32%)、その他 約 0.7 ms。

- **変わった所だけ合成して出す**: 時計だけが変わるフレームなら 1 ms 前後になる見込み。SRM と壁紙の
  blend の両方に効く唯一の手。作りは大きい (変わった矩形の管理、SRM の部分出力、カーソル、遠隔の画面)。
- **SRM を待たずに次のフレームの準備をする**: フレーム/秒は上がるが、1 フレームの遅れは縮まない。
  tear の扱いを先に詰める必要がある (doc/fullscreen_hires/report/h1.md 6 章)。
- **PSRAM の写しが遅い**: HDMI の走査中は memcpy が約 31 MB/s (走査の前は 51 MB/s)。CPU から見た
  PSRAM の実効の帯域が小さいことと、1280x720 RGB888 60 Hz の走査 (166 MB/s) との取り合いが原因。
  大きな写し (遠隔の画面の写し、全面の commit) を DMA に任せると、走査中でも約 2 倍 (60 MB/s) で、
  その間 CPU が空く見込み (未検証)。PSRAM の速度の設定は sdkconfig の提案 (r0b.md 8 章)。

## 6. メモリ (640x360 のデスクトップにしたとき)

- 内蔵 RAM は変わらない。
- PSRAM は起動直後で約 1.28 MB 多く使う (fb +256 KB、デスクトップの canvas 2 枚 × 2 面で +1.0 MB)。
  全画面の大きさの Window 1 枚ごとに +512 KB。**使える PSRAM の heap は約 15 MB** (32 MB ではない)。

## 7. 測り方とログの読み方

- 5 秒周期の `display_local: render:` の行の直後に 2 行出る (描画の無い 5 秒には出ない。
  P4 の実機とネイティブ版。計装は常設で、コストは時刻の読み取りだけ)。

```
display_local: frame: n=5 fb=426x240 cv=2/2 blk=2 | us avg/max total=27462/30300 clear=3974/4160 compose=8469/10983 (sync=699/820 hw=7523/9779) capture=0/0 n=0 out=15015/15366 (sync=8/9 hw=14978/15322)
display_local: frame commit: n=5 avg=6251us max=6671us avg_bytes=204480
```

- `n` は 5 秒のフレーム数、`fb` は fb の大きさ、`cv` は合成した canvas の数 (平均/最大)、`blk` は
  blend の回数。時間は µs で「平均/最悪」。`sync` はキャッシュの同期、`hw` は PPA の実行
  (PPA の backend だけ。ほかは 0)。`capture` は遠隔の画面のための写し (写したフレームだけ)。
  `frame commit` は present のたびの写しで、`avg_bytes` は 1 回に写したバイト数。
- 場面の台本と集計の道具は、作業した checkout の `tmp/modern_resolution/` (gitignore の下。
  `scene.sh`・`agg.rb`・`robust.sh`)。常設の回帰の道具にはしていない。
- 計測の罠: 遠隔の画面 (MJPEG) のクライアントをつないだ・切った直後や、ホストが重いときに、
  P4-Nano のシリアル (CH343) の取り込みが止まることがある。計測の間はホストで重い仕事を流さない。
  detach・attach を繰り返すと Windows 側で機器が読めなくなり、USB の差し直しが要る。
- 解像度の切り替えは、今は端末の `/etc/system_conf.toml` の `display_width`・`display_height` を
  書き換えて再起動する (640x360 を選べる設定の項目は doc/modern_resolution の R1 で作る)。
