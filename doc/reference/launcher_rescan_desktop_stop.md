# ランチャーの再走査でデスクトップが落ちる (NARYA v4, 2026-09-02)

> 状態: 進行中 | **デスクトップの VM プールが 67% -> 77% まで上がって戻らない**
> のが背景。走査を刻んだ後は 4 連続の再走査で落ちなくなった (断続的な症状なので
> 直ったとは言い切れない)。配布の店とは無関係。

## 症状

ランチャーを右クリックして再走査すると、**数秒後に system_desktop が消える**。
画面はアプリの窓だけが残り、メニューバーもデスクトップも無くなる。カーネルと
サービスは生きているので、機械そのものは動いたままになる。

## 背景: プールが 77% で張り付く

**デスクトップの mruby プール (819 KB) は再走査のあと 77% から戻らない。**

| 時刻 | 出来事 | プール used |
|---|---|---|
| 09:00 | 起動直後 (一覧はキャッシュから) | 549584 (67%) |
| 22:50:18 | 再走査の直前 | 552888 (67%) |
| 22:50:25 | **1 回目の再走査 完了** | |
| 22:50:38 | 走査後 | **632184 (77%)** |
| 22:50:43 〜 22:51:14 | `GC.start` が 5 回走る | **632184 のまま** |
| 22:51:22 | **2 回目の再走査** — `39 apps found` の直後に沈黙 | |
| 22:51:30 | `mrb_task_run` が戻る (例外なし) | VM 消滅 |

**1 回の再走査で 82.6 KB 増え、フル GC でも 1 バイトも戻らない。**
GC が回収できない = 到達可能 = 本当に生きている。残り 187 KB で 2 回目の
走査 (同じ 83 KB + 一時のごみ) を回すことになり、そこで尽きる。

39 本で 82.6 KB = **1 本あたり約 2.1 KB**。これは `.app.toml` 1 本の大きさで
ある。

### 外れた見立て: 共有文字列

mruby の `String#[]` と `String#split` は、埋め込み長を超える文字列に対して
親のバッファを指す「共有文字列」を返す。`parse_app_toml` は

    content = file.read                     # .app.toml 全体
    content.split("\n").each do |line|      # line は content の切片
      val = line[eq + 1, ...].strip         # val は line の切片
      label = val                            # これを app_entry に保持する

と書いていたので、`label` / `icon_file` がその .toml の中身を丸ごと生かして
いるのではないか、と考えた。1 本 2.1 KB という数字とも合う。

`val = "#{val}"` (補間は必ず新しいバッファを作る) を入れて実機で測った。
**プールは 67% -> 77% のまま変わらなかった。この見立ては外れ。**
写す変更自体は害がないので残してある。

**83 KB が何なのかはまだ分かっていない。** 次に測るなら、再走査を
`scan_categories` / 走査本体 / `ensure_icon_sprites` / `draw_foreground` に
分けて、それぞれの前後で `FmrbApp.pool_usage` を採る。

### ただし累積はしない (2026-09-02 実測)

刻んだ後の版で **4 回連続の再走査**を実機で走らせた。

| 回 | 走査前 | 走査後 |
|---|---|---|
| 1 | 67% | 77% |
| 2 | 76% | 77% |
| 3 | 76% | 77% |
| 4 | 76% | 77% |

**増えるのは 1 回目だけ**で、2 回目以降は横ばい。4 回とも落ちなかった。
以前は 2 回目で確実に落ちていたので状況は良くなっているが、症状はもともと
**断続的**なので、これで直ったとは言い切れない。

## 死に方が静かな理由

`mrb_task_run` が **例外なしで戻る** (`No exception detected`)。Ruby の
`main_loop` は `@running` が false のときしか抜けないので、Ruby の外で
タスクが終わっている。プール枯渇でこうなる経路を mruby-task 側で確認する
価値はあるが、**枯渇させなければ起きない**。

## 撤回した見立て

### 「4.75 秒のタイムアウト」ではなかった

走査完了からタスク終了までが 4.743 / 4.761 / 4.750 s と揃っていたのを
タイムアウトの署名と読んだ。**間違い**。この 4.7 秒は

```
mrb_task_run() 直後の "No exception detected"   <- ここでもう Ruby は終わっている
  mrb_vm_ci_env_clear / mrc_irep_free / mrc_ccontext_free   <- 4.7 秒はここ
"Task exiting normally"
```

で、**デスクトップの巨大な irep を解放する時間**である。同じ区間は
App Store だと 0.5 秒しかなく、デスクトップの正常終了でも毎回 4.2〜4.7 秒
かかっている。走査とは無関係。

**本当に見るべきなのは `No exception detected` の時刻**で、そこは走査完了の
80 ms 後 (2 回目の回では `39 apps found` の 8 秒後)。

### スタック +4KB では直らない

16KB → 20KB にしても、**8536 バイト空いた状態で落ちた**。スタックではない。
(内蔵 DRAM を食うだけなので 16KB に戻した。)

### 入力ハンドラから出しても直らない

右クリックは印を立てるだけにし、`on_update` から走らせるようにした。
**変わらず落ちた**。ただしこの変更は単独で正しいので残してある。

## 走査そのものの見直し (実施済み)

ユーザ報告: **走査中はマウスも数秒動かなくなる**。

### なぜ長時間固まるのか (実測)

39 本で **1.61 秒**、1 本あたり 41 ms。内訳は捕まえたログの時刻から:

- **アプリ 1 本 19〜34 ms** — `.app.toml` を開いて読んで行ごとに解析する
- **分類をまたぐところ 65〜83 ms** — `read_dir_entries` の 1 回ぶん
- **末尾 420 ms** — 並べ替えとキャッシュ (TSV) の書き出し

固まるのは合計時間そのものではなく**譲らないこと**による。デスクトップは
**優先度 8・コア 1 固定**で、走査中に譲るのは分類ごとの `Machine.delay_ms(1)`
だけ = 1.61 秒で 10 回、**160 ms 続けて走りっぱなし**の区間ができる。その間
コア 1 の下位 (status_led ほか) は一切動かず、メッセージ行列は溢れる
(`msg_send TIMEOUT ... waiting=64`)。カーソルも WiFi の仕事も止まる。

### 刻んだ (2026-09-02)

`scan_app_dir` を `scan_categories` + `scan_category` に割り、`tick_rescan` が
**`on_update` 1 回につき分類 1 つ**だけ進めるようにした。間に `_spin` が入る
ので機械は生きたまま走査する。タイトルバーに `Scanning 3/8...` と出る。

実機で確認: 走査中に遠隔デスクトップが画面を返し、進捗表示も見えた。
所要は 1.61 s → 2.03 s (刻みの待ちのぶん) で、**その間ずっと動いている**。

### 走査の後にもう一つ、9 秒の固まりがある (2026-09-02 に判明)

刻んだのは**走査だけ**だった。計装を入れて測ると、走査が終わってから
再走査が本当に終わるまでにもう一段ある。

```
23:09:16.842  rescan start, pool 67%
23:09:19.050  rescan no change (39 apps)     <- 走査ここまで 2.2 秒 (刻んである)
23:09:28.006  rescan done, pool 77%          <- ここまで さらに 9.0 秒 (刻んでいない)
```

**後半 9 秒は `ensure_icon_sprites` + `draw_foreground`。** 走査本体より長い。
一覧が変わっていない回はスプライトを 1 つも作り直さない (`next if
@icon_sprite_instances[idx]` で全部飛ばす) ので、**ほぼ `draw_foreground`**
とみてよい。この間 GFX へ出ているのは 7 cmds/s しかないので、描画待ちでは
なく Ruby 側で時間を使っている。

**デスクトップが落ちるときに落ちるのはこの 9 秒の中**である。落ちた回の
ログは `rescan no change` の次の行が `No exception detected` で、その間隔が
9 秒だった。

次の一手はここを刻むか、そもそも全面描画をやめること
(参照: 描画は画面に出る量に比例させる)。

### まだやっていない

**変わっていない .app.toml を読み直さない。** 一覧のキャッシュは
label/path/icon を持っている。ディレクトリを列挙して、**キャッシュに無いパス
だけ**開いて解析すれば、たいていの再走査 (1 本増減) は列挙だけで済む。

## 配布の店との関係

**店の不具合ではない**が、店は「入れたら右クリックで再走査してください」と
案内するので、**利用者がこの不具合に一番当たりやすい経路が店**になる。
