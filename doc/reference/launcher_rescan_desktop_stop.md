# ランチャーの再走査でデスクトップが落ちる (NARYA v4, 2026-09-02)

> 状態: 未解決 | 実機で再現。**断続的**。sim では再現しない。
> 配布の店とは無関係 (店を一度も起動していない起動でも起きる)。

## 症状

ランチャーを右クリックして再走査すると、**数秒後に system_desktop が消える**。
画面はアプリの窓だけが残り、メニューバーもデスクトップも無くなる。カーネルと
サービスは生きているので、機械そのものは動いたままになる。

## 分かっていること

| | |
|---|---|
| 例外 | **出ない** (`No exception detected`)。スクリプト末尾の rescue も通らない |
| stop 要求 | **無い** (`received stop command` が出ない) |
| 表示側のエラー | **無い** |
| VM プール | 544/819 KB。**274 KB 空いている** |
| タスクのスタック | 16384 中 **5256 B 空き** (最後の周期ダンプ) |
| メッセージ待ち | 落ちる直前に `msg_send TIMEOUT: dest=2 ... waiting=64` = 行列が溢れる |
| アプリ数の変化 | **関係ない** (`rescan no change` でも落ちた) |
| スプライトの作り直し | **関係ない** (作り直さない再走査でも落ちた) |
| 店の関与 | **無い** (店を起動していない起動でも落ちた) |

`main_loop` を抜ける道は `stop` だけなので、**Ruby の外で VM が終わっている**。
例外でもなく停止要求でもない終わり方をしている。

## 断続的である

同じ操作で生き延びた回もある。

| 時刻 | 走査の結果 | デスクトップ |
|---|---|---|
| 21:28 | no change (38) | 生存 |
| 21:29 | no change (38) | 生存 |
| 21:30 | rebuilt (38 -> 39) | 生存 |
| 21:31 | rebuilt (39 -> 38) | 生存 |
| 21:12 | rebuilt (39 -> 38) | **落ちた** |
| 21:38 | rebuilt (38 -> 39) | **落ちた** |
| 21:41 | **no change (39)** | **落ちた** |

## 試して外れたこと

### スタック +4KB では直らない (2026-09-02)

`FMRB_SYSTEM_APP_TASK_STACK_SIZE` の mruby 側を 16KB → 20KB にして焼いた。

```
fmrb_task: system_desktop  Y  1  20480  8536  IRAM  PIN1
```

**8536 バイト空いた状態で、それでも 1 回目の再走査で落ちた。** 16KB のときの
残りは 5256 B だったので、余裕を 1.6 倍にしても症状が変わらない。
**スタック不足ではない。**

(この 4KB は内蔵 DRAM で、アプリが使える分が減る。原因でないと分かった以上、
戻すかどうかは別途判断する。)

### 入力ハンドラから出しても直らない (2026-09-02)

`on_event` → `handle_launcher_right_click` → `rescan_launcher` と、7.8 秒の
仕事が**イベント処理の中**で走っていた。右クリックは印を立てるだけにして、
`on_update` から走らせるように変えた (再入も防いだ)。**変わらず落ちる。**

この変更自体は残してある — 深さも再入も減るので単独で正しい — が、
**原因ではない**。

## 一番強い手がかり: 約 4.75 秒のタイムアウト

走査が終わってからデスクトップが終わるまでの間隔が揃っている。

| 走査の完了 | タスク終了 | 差 |
|---|---|---|
| 21:41:35.036 | 21:41:39.779 | **4.743 s** |
| 22:21:04.323 | 22:21:09.084 | **4.761 s** |
| 22:30:40.663 | 22:30:45.413 | **4.750 s** |

**クラッシュではなくタイムアウトの署名**である。走査そのものの中で死ぬのでは
なく、**走査が終わったあと約 4.75 秒待って**終わっている。

(21:12 の回は 14 秒だったが、あれは間にスプライト 39 個の削除が挟まっている。)

`fmrb_msg` / `fmrb_app` / `fmrb_task_config.h` に 5000 ms 前後の定数は見つけて
いない。**この 4.75 秒がどこから来るのかを突き止めるのが次の一手**だと思う。

## 次に試すこと

1. **4.75 秒の出どころを探す。** 何のタイムアウトか。mruby-task の tick 監視、
   `_spin`、メッセージ待ちのいずれか。
2. `mrb_task_run` が例外なしで戻っている = **タスクそのものが終わっている**。
   Ruby の `main_loop` は `@running` が false のときしか抜けないので、
   **Ruby の外で終わっている**。mruby-task 側を見る。
3. sim で再現する道を探す (実機では gdb を当てられない)。今のところ sim では
   再現しない — **走査が実機より桁違いに速い**ので、7.8 秒詰まる状況が
   作れていないだけかもしれない。sim の走査に人工的な遅延を入れて試す価値がある。

## 走査そのものの見直し (別件だが関係する)

ユーザ報告: **走査中はマウスも数秒動かなくなる**。デスクトップが止まると
カーソルも止まるので、症状としては一貫している。落ちる件が直っても、
**7.8 秒固まること自体を直す価値がある**。

1. **刻んで走らせる。** 今は `/app` の下を一息に歩く。`on_update` 1 回につき
   分類ディレクトリ 1 つだけ進めれば、機械は生きたまま走査できる。
   進捗も出せる。
2. **変わっていない .app.toml を読み直さない。** 一覧のキャッシュは
   label/path/icon を持っている。ディレクトリを列挙して、**キャッシュに無い
   パスだけ**開いて解析すれば、たいていの再走査 (1 本増減) はほぼ列挙だけで
   済む。ブート計測では解析が 7.8 秒中 3.0 秒を占めていた。
3. 走査中に右クリックが増えても走査は 1 本だけ (**対応済み**)。

## 配布の店との関係

**店の不具合ではない**が、店は「入れたら右クリックで再走査してください」と
案内するので、**利用者がこの不具合に一番当たりやすい経路が店**になる。直るまで
は、店の案内を再起動に変えることも考えられる (体験は落ちるが確実)。
