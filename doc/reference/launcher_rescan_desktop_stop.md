# ランチャーの再走査でデスクトップが落ちる (NARYA v4, 2026-09-02)

> 状態: 解決 | 原因は **デスクトップの VM プール (800KB) が狭すぎたこと**。
> Modern のプールを 1536KB にして、8.8 秒の停止も落ちる症状も消えた。
> 配布の店とは無関係 (店を一度も起動していない起動でも起きていた)。

## 症状

ランチャーを右クリックして再走査すると、**数秒後に system_desktop が消える**。
画面はアプリの窓だけが残り、メニューバーもデスクトップも無くなる。カーネルと
サービスは生きているので、機械そのものは動いたままになる。走査中はマウスも
数秒動かない。

## 原因: プールの空きが足りず、回収器が空回りしていた

デスクトップの mruby プールは Modern でも **800 KB** だった (S3 時代の値)。
一方、デスクトップの生きているオブジェクトは **549 KB**。213 KB ある
`system_desktop_combined.rb` を積んだ irep がその大半で、**空きは 250 KB しか
ない**。

再走査はデスクトップが行う中で一番大きな確保の山 (39 本の `.app.toml` を開いて
解析し、一覧を作り直し、キャッシュを書き出す) なので、この狭い空きの上で
回収器が何度も全面回収を繰り返す。

| | 800 KB | 1536 KB |
|---|---|---|
| 走査開始時のプール | 67% | 38% |
| 走査 (刻んである) | 2.2 秒 | 2.2 秒 |
| **走査の後の停止** | **8.8 秒** | **0.1 秒** |
| 2 回目 | 8.8 秒、のち死 | 2.27 秒 |
| 3 回目 | ー | 2.09 秒 |

**フル GC 1 回は定常時 0.27 秒**なので、8.8 秒は「1 回が重い」のではなく
**何十回も走っている**。上限に張り付いた状態では、確保のたびに閾値を超えて
全面回収に入るため。

同じ壊れ方は既に記録があった。`fmrb_mem_config.h` の USER_APP の隣に

> the service host has outgrown it ... ran the pool dry at 90% full --
> **the host died during require with no exception to show for it**

とある。**このコードベースではプールを使い切った VM は例外を出さずに黙って
終わる**。デスクトップもそれだった。

### 直し

`FMRB_MEM_POOL_SIZE_SYSTEM_APP` に Modern の分岐を足して 1536 KB。
Modern の PSRAM は 32 MB で 12 MB 空いているので、これが一番安い。
Retro (S3) は 800 KB のまま (未計測なので触らない)。

## ごみはどこから出るのか (実測)

`FmrbApp.pool_used` (バイト) を段ごとに差分して測った。再走査 1 回、39 本。

| 段 | 生成したごみ |
|---|---|
| 走査 (8 分類) | **213 KB** |
| `save_launcher_cache` | **52 KB** |
| `ensure_icon_sprites` | 9 KB |
| `draw_foreground` | 5 KB |
| 並べ替え | 0 KB |
| **合計** | **279 KB** |

`.app.toml` は 39 本で平均 **265 バイト** (合計 10 KB)。つまり:

- **解析が 1 本あたり 5.5 KB** — 読んだファイルの **21 倍**
- **キャッシュ書き出しが 52 KB で 2.6 KB のファイルを作る** — 出力の **20 倍**

### 書き出しの 52 KB: `buf += ` の二乗

```ruby
apps.each { |a| buf += "...\n" }   # 毎回 buf 全体を作り直す
```

39 行を足すのに、長さ 1, 2, ... 39 行ぶんの String を 39 個作る。
`buf << ` (その場に足す) に変えて解消。**→ 52 KB が 3 KB に**。

### 解析の 5.5 KB/本: 行ごとの使い捨て

`parse_app_toml` は 11 行の toml に対して

- `content.split("\n")` — 配列 + 11 個の String
- 行ごとに `line.strip` — **要らない行にも 1 個ずつ**
- `=` のある行ごとに `line[0, eq]` + `.strip` — **2 個ずつ**
- 値のある 4 行で さらに 4 個ずつ

を作る。**知りたい鍵は 4 つなのに、11 行すべてを切って空白を落としてから
捨てている**。1 本あたり 35〜50 個の String になり、mruby の String は
ヘッダとブロック込みで 1 個 50〜70 B なので 2.5 KB、これに Hash・
`find_script_ext` の `"#{base}.#{ext}"` × 拡張子の数・`Log.info` の
組み立てが乗って 5.5 KB。

**まだ直していない。** 選択肢は 2 つ:

1. **キャッシュにあるアプリは開かない。** 一覧のキャッシュが
   label/path/icon を持っているので、ディレクトリを列挙して既知のパスは
   そのまま使い、**新顔だけ開く**。213 KB がほぼ 0 になり、走査の 2.2 秒も
   ほぼ消える。ただし **.app.toml を編集して名前を変えても拾わなくなる**。
   `File.size` を鍵に足せばたいていの編集は拾えるが、同じ長さの書き換えは
   漏れる。
2. **解析を軽くする。** 要らない行を切る前に捨てる (`getbyte` で判定)、
   `strip` を減らす、`find_script_ext` の interpolation をやめる。
   意味は変わらない。5.5 KB → 2.5 KB 程度、213 KB → 100 KB 程度。

## 停止時間の場所は当てにならない

計測すると、8.8 秒が乗る場所は回ごとに動いた。

| 回 | `map` + 配列比較 (39 要素) | `ensure_icon_sprites` (39 要素) |
|---|---|---|
| 23:23 | 素通り | **8833 ms** |
| 23:31 | **8750 ms** | 6 ms |

**同じ 39 要素のループが、片方の回では 6 ms、もう片方では 8833 ms。**
どちらも数十回のブロック呼び出しと配列参照しかしていない。停止時間は
**その瞬間に確保をしたところに乗る**ので、プロファイルの「重かった行」を
そのまま犯人にしてはいけない。

(ブロック呼び出しの実費は 0.4ms/回 なので 39 回で 16 ms。8.8 秒の 0.2%。)

## 撤回した見立て

### 「4.75 秒のタイムアウト」ではなかった

走査完了からタスク終了までが 4.743 / 4.761 / 4.750 s と揃っていたのを
タイムアウトの署名と読んだ。**間違い**。この区間は

```
mrb_task_run() 直後の "No exception detected"   <- ここでもう Ruby は終わっている
  mrb_vm_ci_env_clear / mrc_irep_free / mrc_ccontext_free   <- 4.7 秒はここ
"Task exiting normally"
```

で、**デスクトップの巨大な irep を解放する時間**である。App Store だと同じ
区間が 0.5 秒しかなく、デスクトップの正常終了でも毎回 4.2〜4.7 秒かかって
いる。走査とは無関係。**見るべきは `No exception detected` の時刻**。

### 共有文字列ではなかった

mruby の `String#[]` / `String#split` が親のバッファを掴む共有文字列を返す
ので、`.app.toml` の中身が丸ごと残っているのではないかと考えた
(1 本 2.1 KB という数字とも合った)。`parse_app_toml` で
`val = "#{val}"` と写して測ったが、**プールの数字は動かず外れ**。写す変更
自体は害がないので残してある。

増えた 83 KB の正体は、プールを広げた後の観測で**回収されていないごみ**と
分かった (広い方では 38% -> 57% -> 75% と上がり、閾値 70% の watermark GC が
41% まで戻す)。狭い方では回収を強制されていたので、あれは生きた分ではなく
「回収が追いつく前の数字」だった。

### スタック +4KB では直らない

16KB → 20KB にしても、**8536 バイト空いた状態で落ちた**。スタックではない。
(内蔵 DRAM を食うだけなので 16KB に戻した。)

### 入力ハンドラから出しても直らない

右クリックは印を立てるだけにし、`on_update` から走らせるようにした。
**変わらず落ちた**。ただしこの変更は単独で正しいので残してある。

### 走査後の GC.start は入れない

`rescan_finish` の末尾で `GC.start` を呼ぶ版を試したら、その回で落ちた。
狭いプールでは何の足しにもならず、回収の山を早めるだけだった。プールを
広げた今は watermark GC が拾うので不要。

## 走査そのものの見直し (実施済み)

### なぜ走査中に固まるのか (実測)

39 本で **1.61 秒**、1 本あたり 41 ms。内訳はログの時刻から:

- **アプリ 1 本 19〜34 ms** — `.app.toml` を開いて読んで行ごとに解析する
- **分類をまたぐところ 65〜83 ms** — `read_dir_entries` の 1 回ぶん
- **末尾 420 ms** — 並べ替えとキャッシュ (TSV) の書き出し

固まるのは合計時間そのものではなく**譲らないこと**による。デスクトップは
**優先度 8・コア 1 固定**で、走査中に譲るのは分類ごとの `Machine.delay_ms(1)`
だけ = 1.61 秒で 10 回、**160 ms 続けて走りっぱなし**の区間ができる。その間
コア 1 の下位 (status_led ほか) は一切動かず、メッセージ行列は溢れる
(`msg_send TIMEOUT ... waiting=64`)。カーソルも WiFi の仕事も止まる。

### 刻んだ

`scan_app_dir` を `scan_categories` + `scan_category` に割り、`tick_rescan` が
**`on_update` 1 回につき分類 1 つ**だけ進めるようにした。間に `_spin` が入る
ので機械は生きたまま走査する。タイトルバーに `Scanning 3/8...` と出る。

実機で確認: 走査中に遠隔デスクトップが画面を返し、進捗表示も見えた。
所要は 1.61 s → 2.2 s (刻みの待ちのぶん) で、**その間ずっと動いている**。

### まだやっていない

**変わっていない .app.toml を読み直さない。** 一覧のキャッシュは
label/path/icon を持っている。ディレクトリを列挙して、**キャッシュに無いパス
だけ**開いて解析すれば、たいていの再走査 (1 本増減) は列挙だけで済む。
2.2 秒がほぼ列挙だけになる。

## 「GC をもっと早く発動すれば」は効かない

早めても総量は変わらない。**ごみ (279 KB) が空き (250 KB) より大きい**限り、
走査を最後まで回すには途中で必ず回収が要り、そのあとも足りない分を回収し
続ける。実際 8.8 秒は「回収が遅れていた」時間ではなく「回収が何度も走って
いた」時間だった。効くのは**空きを増やす**か**ごみを減らす**かの二つだけ。

ただし別の意味で正しい点が一つある: **刻んだ走査中は on_update が
`return 50 if tick_rescan` で早期に戻るので、GC の予算 (64% 以上で 40ms/回の
`GC.step`) が一切回らない**。ここで回せば、溢れは防げないものの
「一度に 8.8 秒止まる」が「8 回に分散する」になる。

## 残る注意

- **デスクトップの生きている分は 549〜654 KB あり、その大半は自分の irep**。
  デスクトップの Ruby を増やすとそのまま効く。1536 KB でも余裕は無限では
  ない (走査の山で 75% まで行く)。
- **Retro (S3) は 800 KB のまま。今の本数でも同じことが起きるはず。**
  S3 も P4 も 32 bit なのでデスクトップの irep はほぼ同じ大きさ = 空きも
  同じ 250 KB 前後で、ごみ 279 KB はそれを超える。`buf <<` の分 (52 KB) を
  引いても 227 KB で、余裕が無い。**解析のごみを減らすか、Retro の
  SYSTEM_APP も上げるか**。上げる判断には Retro 実機の起動ログ
  (`fmrb_app: VM Pools` の行と `M1|...psram=`) が要る — 8 MB しかないので
  P4 のように気軽には積めない。
- `rescan start` / `rescan done` の 2 行がプール占有率を出す。ここが 70% に
  近づいていたら同じ道を辿っている。
