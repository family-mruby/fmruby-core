# 全画面の高解像度モード (使い方と仕組み)

> 状態: 完了 | 更新: 2026-11-18 | P4 系 (Tab5 / NARYAv4)、ブラウザ版と Modern の Linux sim で、属性を持つアプリの全画面だけ 640x360 になる。画面そのものが 640x360 のとき (P4-Nano の既定、ほかは Config で選ぶ) は逆に、426x240 向けの全画面のアプリ (属性なし) の間だけ 426x240 になる (どの大きさでも描けるアプリは `fullscreen_any_size` で外す)。アプリの書き方、エディタのフォント、遠隔の道具での見え方

企画の経緯は `doc/fullscreen_hires/` (plan.md と report/)。画面そのものの解像度を
選べるようにした経緯は `doc/modern_resolution/` (R1a。P4-Nano の既定を 640x360 にしたのは R2)。

## 何が起きるか

- 標準の画面は 426x240 で、Tab5 と NARYAv4 はそれを 3 倍して 1280x720 に出す
  (P4-Nano の既定は 640x360 の画面。次の「画面を 640x360 にした端末」)。
- `fullscreen_hires` を持つアプリが**全画面の一番上**にいる間だけ、画面は
  640x360 になり、2 倍して出る。物理の大きさは同じで、細かさだけが上がる。
- Window に戻る (F11)、別の全画面アプリが上に来る、park される (Ctrl+Tab)、
  終わる、のどれでも 426x240 に戻る。決めるのはカーネルで、アプリは
  「高解像度にしてよい」と宣言するだけ。アプリが実行中に切り替える口は無い。
- 対象は P4 系、ブラウザ版 (基本の大きさが 426x240 のページ) と Modern の
  Linux sim。Retro (S3) と Retro の sim では属性は無視され、従来の全画面になる。
- **画面を 640x360 にした端末** (Config > 表示 > 画面の解像度 で「高精細」、
  次の節) では向きが逆になる (`doc/modern_resolution` の R1b)。
  - 属性 (`fullscreen_hires`) を持つアプリは、切り替えずにそのまま 640x360 の
    全画面になる。
  - `fullscreen_any_size` を持つアプリ (どの大きさでも描ける) も、切り替えずに
    640x360 の全画面になる。
  - どちらも持たない全画面のアプリ (426x240 向けに描いたもの) は、426x240 の
    canvas で作られ、全画面の一番上にいる間だけ画面が 426x240 (3 倍) になる。
    Window に戻る・別の全画面アプリが上に来る・park される・終わる、で
    640x360 に戻る。規則 (待つ・打ち切る・遅れて出た絵を受ける) は 640x360 への
    切り替えと同じ。
- Modern の sim は graphics-audio が INIT_DISPLAY の ACK で対応を伝えたときだけ
  切り替える (古い graphics-audio と組んだときは従来の全画面)。
  ブラウザ版で 640x360 や 852x480 のページを選んでいるときは、どちらの向きも
  切り替えない。ネイティブ版も今までどおり。

## 画面の解像度 (Config)

Modern (P4-Nano・Tab5・Modern の sim) の画面は 426x240 と 640x360 から選べる。
既定は P4-Nano (`config/system_conf_naryav4.toml`) が 640x360、Tab5・Modern の sim が
426x240 (ブラウザ版・ネイティブ版は選ぶ項目が無く、426x240 のまま)。

- 選んだ値は端末の `/etc/system_conf.toml` にあり、`app_sync` などでファームを焼き直しても
  端末のものが残る。前から 426x240 で使っていた P4-Nano は、焼き直しても 426x240 のまま
  (Config で選ぶ)。既定が効くのは、設定の無い端末 (storage ごと焼いたとき) だけ。

- Config > 表示 > 画面の解像度: 「標準 (426x240)」「高精細 (640x360)」。
  `/etc/system_conf.toml` の `display_width`・`display_height` の 2 行に書かれ、
  起動のときに読まれる。ほかの起動時の項目と同じく「保存して再起動」で効く
  (sim には再起動のボタンが無い。保存して stack を起こし直す)。
- ほかの値 (手で書いた 800x480 など) は 426x240 として起動し、ログに
  `display WxH is not a Modern resolution` を出す。ファイルはそのまま。
- **戻り道**: 起動中に Shift を連打すると、設定を見ずにその回だけ 426x240 で
  上がる (ファイルは書き換えない。Config で選び直せば直る)。ログは
  `Shift held at boot: starting at 426x240 this time`。**押しっぱなしは、ユーザの
  P4-Nano の実機確認 (2026-11-18) では効かず、連打だけが効いた** (この形で受け入れ済み)。
  押しっぱなしのための作りは入っている: キーボードは状態が変わったときにしか報告しないので、USB の受け側は
  キーボードを認識したときに一度 GET_REPORT で今の状態を読み、押されている修飾キーを
  押下として流す (ログ `Keyboard state at connect (slot N): modifier=0x..`。0x02・0x20 が
  Shift)。キーボードの認識が画面の初期化より前 (P4-Nano で約 0.3 秒前) なら効く。
  sim では効かない (sim の入力は画面の初期化の後で開く)。
- PC から戻すときは、WiFi の遠隔操作で `/etc/system_conf.toml` の 2 行を
  426 / 240 に書き戻して再起動する (`tools/fmrb_rd_fs.rb <IP>` の get・put と
  `reboot`)。
- 640x360 のとき、マウスの倍率 (`mouse_scale_x/y`) は 426x240 に対する値の
  まま、画面の大きさの比 (640/426) を掛けて使う。同じ手の動きで、ポインタは
  モニタの上で同じ距離だけ進む。全画面の高解像度モードと同じ補正。
- 遠隔デスクトップのページは、Window の表示を基本の画面の 2 倍
  (426x240 は 852x480、640x360 は 1280x720) にする。

## アプリの書き方

`.app.toml` に 1 行足す。

```toml
default_window_mode = "fullscreen"   # 起動時から全画面にするなら
fullscreen_hires = true              # 全画面のとき 640x360 にしてよい (整数 1 も可)
fullscreen_any_size = true           # どの大きさでも描ける (整数 1 も可)
```

- `fullscreen_any_size` は「届いた大きさから配置を決めるので、640x360 の画面を
  426x240 に切り替えなくてよい」という宣言。426x240 の画面では何も変わらない。
  宣言の無い全画面のアプリは、640x360 の画面では 426x240 に切り替えて出す
  (既定)。両方を持つ組み込みのエディタは、ネイティブ版の広い画面では
  画面全体を使う。
- 組み込みとサンプルで `fullscreen_any_size` を持つもの: shooter、welcome、
  picorabbit、ntsc_color_test、walk_scroller、breakout (F で全画面)。

- 全画面で起動するアプリは、最初から 640x360 の canvas で作られる
  (`@window_width` / `@window_height` が 640 / 360)。
- Window と全画面を行き来するアプリ (F11 で `toggle_fullscreen` を呼ぶもの) は、
  大きさが `on_resize(w, h)` で届く。**大きさを定数で持たず、届いた値で
  配置を組み直す**。640x360 と Window の大きさの両方で描けること。
- 描画の座標は常に canvas の画素。640x360 のときは 1 画素が物理の 2x2、
  426x240 のときは 3x3 になる。フォントの見た目の大きさも 2/3 になる。
- マウスとタッチの座標は、そのときの画面の大きさで届く。画面上の速さは
  どちらの大きさでも同じになるよう補正してある。
- 組み込みでは `default/editor` と `default/editor_fs` (エディタ) が持っている。
- 試験用アプリ `flash/app/test/hires_test.app.rb` が最小の例 (起動時から
  640x360、F11 で Window と往復、試験用の図柄を描く)。

## エディタのフォント

- View > Font (日本語は「文字の大きさ」) で、本文のフォントを 3 つから選ぶ。
  小 (8、美咲) / 標準 (12、既定) / 大 (16)。Window と全画面で共通。
- 選んだ値は `/home/editor.toml` の `[editor]` の `font = 8|12|16` に残り、
  次の起動でも効く。ほかの行はそのまま残る。読めない値は 12 になる。
- 640x360 の全画面では、12 で 106 桁 x 28 行、8 で 159 桁 x 42 行、
  16 で 79 桁 x 21 行 入る。

## 表示側の守り

表示タスク (display_local) は、切り替えた画面の持ち主の canvas がおかしな状態でも
画面を止めない。以下は 426x240 の画面から 640x360 に切り替える場合で書いているが、
640x360 の画面から 426x240 に切り替える場合も、大きさを入れ替えて同じ規則になる。

- 持ち主の canvas は、与えられた位置にかかわらず (0, 0) に写す。
- 持ち主が消えた・隠れたら、すぐ 426x240 に戻る。
- 持ち主が 640x360 の絵を出せない状態 (別の大きさにされた、絵が無い) が
  500ms 続いたら、自分で 426x240 に戻る。ログは
  `screen mode: owner N has shown no 640x360 frame ...`。
- 打ち切りで戻ったあとでも、その持ち主が 640x360 の絵を present したら
  640x360 に入り直す (最初の絵が遅いアプリのため。初回起動の麻雀は手牌の
  シートを読む間 1 秒を超えることがある)。ログは
  `screen mode: 640x360 owner=N (owner presented late, ...)`。新しい要求か、
  その canvas が消える・隠れると、入り直しの対象から外れる。
- 自分で戻したときは、入力側 (タッチ・マウス・遠隔入力) の画面の大きさも
  合わせて戻す。
- 切り替えの完了は「resize を処理した後の present」で決める。その合図は
  FmrbApp (Ruby: mruby と Spinel) が resize の処理の中で送り直す sprite clip。
  MicroPython・Lua・wasm のアプリはこの合図を送らないので、F11 などで大きさが
  変わる切り替えは打ち切り (500ms) と遅れて出た絵を経て、1 秒ほどで終わる
  (起動時から全画面のアプリは大きさが変わらないので待たない)。

## 遠隔の道具での見え方

- 遠隔デスクトップのページ (端末の `http://<IP>/`): 画面の大きさに追従する。
  ページ上の見た目の大きさは変わらず (基本の画面の 2 倍)、クリックは画面全体に届く。
  H.264 も 640x360 を流す (符号化は 640x368、下の 8 行はページが隠す)。
- `tab5_screenshot`: `frame_size` が 640x360 になる。
- `tab5_input` / `web_input`: 座標はそのときの画面の大きさ。640x360 の
  ときに 426x240 のつもりの座標を送ると左上に寄る (板は拡大しない)。
  先に画面を取って大きさを見る。
- ブラウザ版のページ: 見た目の大きさは選んだ解像度とズームで決まり、
  640x360 に切り替わっても変わらない。

## Linux sim (Modern) での仕組み

- 画面は graphics-audio (Linux ビルド) が描く。SET_SCREEN_MODE の規則は
  display_local と同じ (「打ち切りで戻ったあと、持ち主が 640x360 の絵を
  出したら入り直す」も同じ。これは sim で先に入れ、あとで display_local にも
  入れた)。経緯は `doc/fullscreen_hires/report/h5_sim.md`。
- graphics-audio は INIT_DISPLAY の ACK の 2 バイト目で対応を伝え
  (`FMRB_LINK_DISPLAY_CAP_SCREEN_MODE`)、core はそれを見て初めて 640x360 を使う。
- 共有メモリは layout 2 (640x360 の枠、枠ごとの大きさ)。sdl2-display の
  イメージはヘッダを取り込んで作るので、変えたら `docker compose build
  sdl2-display`。sim_up はイメージの古さを見て止まる。
- `sim_screenshot` は高解像度中 640x360 を返し、`sim_input` の座標も 640x360。
- 画面そのものを 640x360 にした sim も起動する (共有メモリの基本の画面の上限を
  640x360 に上げた)。graphics-audio は大きさを次の起動で使うので、Config で
  変えた後は 2 回起こし直す (sim_up は 1 回目の食い違いを見て自分で起こし直す)。
- Window (GUI) の大きさは変わらず、640x360 の絵が同じ Window に拡大されて出る。
- 640x360 の画面から 426x240 に切り替える向きも同じ道 (R1b)。基本の画面で
  切り替え前後の 426x240 の canvas を重ねない規則は、display_local はアプリの
  文脈 (全画面のアプリの canvas か) で決め、graphics-audio は形 (原点にある
  色キー無しの 426x240) で決める (graphics-audio からは文脈が見えないため)。
