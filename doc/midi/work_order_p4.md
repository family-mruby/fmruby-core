対象: 実装セッション (Opus)
ブランチ: `feature/midi`
前提: [README.md](README.md)、[report/p1.md](report/p1.md)、

## 0. なぜ P3 より先か

P2 で `MIDI::Device` 経由の発音が動いた。ここに P1 が持っている SMF パーサと
テンポマップを載せると、**「.mid をアプリから再生・停止・操作できる」**が
完成する。README 方向C-b であり、当初の要求「内蔵音源を SMF で鳴らす」の
実時間側の答である。

P3 (sim の MIDI 経路) は外部機器へ流すための足場なので、**外部音源を扱う
P5 の直前で足りる**。

## 1. ゴール

デバイス上のアプリから、こう書けること:

```ruby
player = FmrbMidi::SmfPlayer.new(device)   # 名前は仮
player.load("/app/demo/song.mid")
player.start
# on_update から
player.tick                                 # 期限の来たイベントを送る
player.tempo_scale = 1.5                    # 速く (実時間再生の利点)
player.stop
```

**「実時間でやる意味」がある機能を通すこと**が主眼。単に鳴るだけなら
P1 の事前変換 (FMSQ) のほうが正確で軽い。停止・再開・テンポ変更・
途中からの再生・出力先の差し替えができて初めて C-b を作る意味が立つ。

## 2. 移植元と、そのまま持ってこられない理由

`tool/midi/smf2fmsq.rb` (797 行) のうち、**`SmfReader` と `TempoMap` が
そのまま使える部分**である。ただしホストの CRuby 用に書かれているので、
picoruby (mruby) に載せるには手当てが要る。

**既知の落とし穴** (メモリ済みの制約。踏むと分かりにくい壊れ方をする):

| 使っている物 | picoruby での扱い |
|---|---|
| `Array#pack` / `String#unpack` | **無い**。`getbyte` / `setbyte` で組む (パーサは読むだけなので `getbyte` で足りる) |
| `File.binread` | **無い**。`File.open(path, "r") { \|f\| f.read }` |
| `defined?` | **無い**。`const_defined?` か rescue |
| クラス内の裸の定数参照 | `::JSON` のように先頭 `::` を付ける |
| `a[i], a[j] = a[j], a[i]` | 壊れる。一時変数で入れ替える |
| `Integer#times` の数千回 | `while` のほうが軽い |

**判断してほしいこと**: パーサをどこに置くか。
(a) `lib/add/picoruby-fmrb-midi/` に Ruby で移植する、
(b) ホストで前処理して軽い中間形式にし、デバイスではそれを読む、
(c) C に降ろす。
**(a) を推奨**するが、SMF は可変長数値・ランニングステータス・複数トラックの
マージがあり、**曲の全イベントをメモリに持つと VM プールを圧迫する**
(P1 で 1284 音の曲があった)。プールは 512KB で、アプリの他の用途と共有である。
**メモリの見積りを先に出してから決めること**。(b) を選ぶ場合、
「実時間の利点」(1 章) が保てる形式であることが条件。

## 3. 時間の扱い (P2 の教訓を引き継ぐ)

P2 報告 2.1 が、**Ruby で予約を持つと「叩く間隔」が精度になる**ことと、
**早起きした分でシーケンスを進めると曲が速くなる**ことを実例つきで示している。
SMF プレーヤは予約の塊なので、ここが設計の中心になる。

- **時刻の権威は 1 つにする**。`Machine.board_millis` を基準に「次のイベントの
  絶対時刻」を持ち、`tick` は「現在時刻以前のイベントをすべて送る」だけにする。
  経過時間を足し込む方式にしないこと (呼ばれた回数に依存して曲が伸縮する)。
- `FmrbMidi.tick_delay` と同様に、**次のイベントまでの待ち時間をアプリに返す**
  口を用意する。`on_update` の戻り値に使えると、アプリ側が素直に書ける。
- **テンポ変更は SMF 側 (Set Tempo) とユーザ側 (`tempo_scale`) の 2 系統**が
  ある。両方が効く形にし、どちらが優先かを決めて報告に書くこと。
- 1 回の `tick` で大量のイベントが期限を迎えたとき (アプリが長く止まっていた
  場合) にどうするかを決める。**全部送る / 古いものは捨てる**のどちらかで、
  捨てるなら note_off は捨てないこと (音が残る)。

## 4. 出力先

`MIDI::Device` に送るだけにする。**送り先が APU か外部音源かをプレーヤは
知らない**こと。これが方向C-b を選んだ理由そのもの (P5 で Unit MIDI に
差し替えるときプレーヤを触らずに済む)。

- ドラム (ch10) や音色の解釈は **transport の仕事**であり、プレーヤは
  MIDI イベントを素通しする。P2 の `ApuTransport` が既にその形。
- 4 声に入り切らない曲をどうするかも transport 側の既存の規則
  (後着優先 + 復帰) に任せる。**プレーヤ側で間引かないこと**。

## 5. 検証

- **P1 の事前変換と同じ音になること**。`tool/midi/test/scale.mid` を
  両経路で鳴らして音高を比較する (P2 報告 5.3 と同じやり方)。
  P2 で音高テーブルを入れたので、**理屈の上では一致するはず**である。
- **テンポ変更に追従すること**。`tool/midi/test/tempo_change.mid` が
  120 BPM -> 240 BPM で用意してある。実時間側でも間隔が半分になることを、
  波形かログのタイムスタンプで確認する。
- **停止・再開が効くこと**。停止時に鳴っている音が消えること
  (note_off の取りこぼしが無いこと)。
- ホストで走るテストを優先する (`tool/midi/test/` に P1/P2 の前例がある)。
  パーサとスケジューリングは `FmrbAudio` を差し替えれば sim 無しで試せる。
- 音は `tools/fmrb_audio_probe.rb` で採れる。官能評価はユーザ。

## 6. 併せて拾ってほしいもの (P2 の申し送り)

- **異常終了したアプリの音が残る** (P2 報告 2.3)。`on_destroy` を通らないと
  SUB が鳴りっぱなしになる。**プレーヤは曲を鳴らしっぱなしにする道具なので、
  この問題を最も踏みやすい**。kernel 側でアプリ終了時に SUB を黙らせるのが
  本筋 (`destroy_vm` / `force_release_resources` の周辺が置き場所の候補)。
  P4 の範囲で直せるなら直す。難しければ理由とともに申し送る。

## 7. 守ること

- 実装中の気づき・実測値・申し送りは `doc/midi/report/p4.md` に書く。
- **`doc/midi/README.md` は書き換えない**。前提が覆ったら報告書に書く。
- 取り込んだ gem (`lib/add/picoruby-midi/`) は**引き続き無改変を保つ**。
  必要な追加は `picoruby-fmrb-midi` 側に置く。
- コメントは英語、コミットログは英文、ASCII 以外の記号は使わない。
- `lib/add/` を編集したらビルド前に `rake clean`。
- **作業ツリーは Linux ビルド** (`build/` = linux)。P4 は sim で完結する。
- 音の最終確認はユーザ。

## 8. 完了の条件

1. アプリから .mid を読み込んで再生・停止できる。
2. 曲中のテンポ変更に追従する (`tempo_change.mid`)。
3. `tempo_scale` のような**実時間ならではの操作**が 1 つ以上効く。
4. P1 の事前変換と同じ音高になる (`scale.mid`)。
5. メモリ使用量 (曲を読み込んだときのプール消費) を実測して報告に書く。
6. 報告書 `doc/midi/report/p4.md` に、2 章の置き場所の判断と 3 章の
   時間設計、6 章の扱いが書かれている。
