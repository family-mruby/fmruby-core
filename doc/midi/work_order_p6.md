## 0. この段の位置づけ

実機で動いた (P5) が、**sim では見えなかった 2 つの遅さ**が出た。
どちらも実測済みで、原因の見当もついている。**これを潰す**のが P6。

**実機は当面使えない**。したがって **sim と host で完結する範囲**で進める。
実機での確認は、次に実機が使えるときにまとめて行う (手順を報告書に残すこと)。

## 1. 直すもの (実測値つき)

### 1.1 曲の読み込みが 7.9 秒かかる (最優先)

```
/data/midi/joplin_entertainer.mid loaded in 31ms   (22,084 B)
channel_usage scan took 7900ms
```

**ファイル読み込みは 31ms なのに、`channel_usage` が 7.9 秒**。
`SmfPlayer#channel_usage` が曲全体を 1 バイトずつ可変長デコードして
走査するためで、実機の mruby ではここが支配的になる。
デモアプリは読み込み直後にこれを呼んでいる (`auto_map` のため)。

**目標: 体感で待たされない程度 (数百 ms 以下)**。

対策の候補 (**判断して理由を報告に書くこと**):

- **先頭 N イベントだけ走査する**。使用チャンネルと音域は曲の冒頭で
  ほぼ確定するので、全曲を舐める必要はない。最も安い。
  ただし「途中から入ってくるパート」を取りこぼす可能性があるので、
  **取りこぼしたときに何が起きるか** (その ch の音が出ない) を
  理解した上で N を決めること。
- **`collect_tracks` の 1 パスに相乗りさせる**。今はファイルを
  読み込みと走査で 2 回舐めている。
- **C に降ろす**。確実だが、P2 で「まず Ruby で」と決めた方針からの転換に
  なるので、上 2 つで足りないと分かってからにする。

**測ってから決めること**。sim でも同じ関数の相対コストは測れる
(絶対値は実機と桁が違うが、「どの案が何倍速いか」は分かる)。

### 1.2 演奏中に時々大きく詰まる

```
events=936 avg_late=10ms max_late=176ms stalls=4
```

- **平均 10ms は問題ではない** (16 分音符 100ms に対して聞き取れない)。
- 効いているのは **176ms のスパイク**と、**200ms 超でスケジュールを
  ずらした回数 (stalls) が 60 秒で 4 回**。
- **「常時間に合っていない」のではなく「時々止まる」**。GC が疑わしいが、
  **まだ裏が取れていない**。

#### まず裏を取る: GC プロファイルが既にある (調査済み)

`GC.stat` は実装済みで、**`MRB_GC_PROFILE` を有効にすると GC の停止時間の
ヒストグラムまで返る** (`mrbgems/picoruby-mruby/lib/mruby/src/gc.c`)。
現在 `lib/add/family_mruby_esp32.rb` / `family_mruby_linux.rb` の
どちらでも**有効になっていない**。

返るキー (プロファイル有効時):

| キー | 意味 |
|---|---|
| `prof_sync_count` / `_total_us` / `_max_us` / `_hist` | **同期的な停止** (これが演奏を止める犯人候補) |
| `prof_step_count` ほか | スケジューラのアイドル時 GC ステップに移された分 |
| `prof_step_jitter_*` | 同上のジッタ |

さらに **mruby-task にアイドル時 GC ステップの仕組みが既にある**
(`mrbgems/.../mruby-task/src/task.c` の `mrb_gc_step` / `mrb_incremental_gc`
呼び出し)。**停止をアイドルに逃がす道が既に用意されている**ので、
まずそれが効いているのか、効かせられるのかを調べる。

**手順**:

1. `MRB_GC_PROFILE` (必要なら `MRB_GC_STATS` も) を**まず Linux ビルドで**
   有効にし、sim で SMF を再生しながら `GC.stat` を定期的に読む。
2. **同期停止 (`prof_sync_max_us`) が 176ms スパイクと同じ桁か**を見る。
   同じなら GC 確定。違うなら別の犯人 (下記) を疑う。
3. GC が犯人なら、**アイドル時ステップに逃がす**か、**プレーヤの割り当てを
   減らす**かで対処する。プレーヤは 1 イベントごとに文字列や配列を作るので、
   減らせる余地があるはずである。

**GC 以外の容疑者** (GC で説明が付かなかったとき):

- **アプリタスクの優先度は 2 (最下位)**。desktop (8) / kernel (9) /
  host (10) に割り込まれる。メニューバーの時計は 1 秒ごとに再描画される。
- `_spin` は 1ms 粒度なのでここは白 (調査済み)。
- UART 書き込みは TX リングバッファ 1024B があるので白 (調査済み)。

### 1.3 sim と実機の差を埋める材料

**sim では 1.1 も 1.2 も再現しない** (host が速すぎる)。これが P4/P5-sim で
見落とした理由である。**同じ失敗を繰り返さないために**、次のどちらかを
用意することを勧める (判断してよい):

- **host で走る負荷計測**: プレーヤの 1 イベントあたりのコストを
  ホストで測り、**実機との比 (実測で約 250 倍)** を掛けて見積もる。
  `tool/midi/test/` に既にホストテストの前例がある。
- **sim で意図的に遅くする**: 難しければ無理をしなくてよい。

## 3. 守ること

- 報告は `doc/midi/report/p6.md`。
- **`doc/midi/README.md` は書き換えない**。前提が覆ったら報告書に書く。
- `lib/add/picoruby-midi/` は**無改変を保つ** (md5 一致を維持)。
  追加は `picoruby-fmrb-midi` 側へ。
- **sdkconfig 系は編集禁止**。`MRB_GC_PROFILE` は mruby のビルド定義
  (`lib/add/family_mruby_*.rb` の `conf.cc.defines`) なので、そちらで足す。
  **ただし ABI に影響する定義は dual build で揃える**こと
  (`doc/` の dual build 注意。片側だけ有効にして比較するのは構わないが、
  最終的な状態を報告に明記する)。
- 計測用の定義を**恒久的に有効にするかは判断**。オーバーヘッドがあるなら
  既定は無効にして、有効化の手順を報告に書く。
- コメントは英語、コミットログは英文、ASCII 以外の記号は使わない。
- `lib/add/` を編集したらビルド前に `rake clean`。
- **作業ツリーは現在 esp32 ビルド**である。sim を使うには
  `rake clean_all` -> `rake build:linux` が要る (10 分程度)。
  戻すときも同様。
- 音の最終確認はユーザ。

## 4. 完了の条件

1. **曲の読み込みが体感で待たされない**。sim で「変更前後で何倍速くなったか」を
   数字で示し、実機での見積り (約 250 倍のコスト差) も添える。
2. **1.2 の犯人が特定されている**。GC ならその証拠 (`prof_sync_max_us` 等)、
   別の原因ならその証拠。**「たぶん GC」で終わらせない**。
3. 犯人に対する対策が入っているか、入れられない理由が書かれている。
4. **実機での確認手順**が報告書にある (次に実機が使えるときにそのまま使える形)。
5. sim と host のテストが通る (既存の 78 項目を壊していないこと)。
