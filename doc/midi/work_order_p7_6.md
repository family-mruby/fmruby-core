# MIDI 対応 作業指示書 (P7.6: 演奏時刻の権威を C へ)

対象: 実装セッション (Opus)
ブランチ: `feature/midi`
前提: [report/p7.md](report/p7.md) (特に 9 章)、[report/p7_5.md](report/p7_5.md)。
背景の設計議論は README の P7.6 行と、Midori の
`tmp/midori/mrbgems/picoruby-midi/src/midi_scheduler.c` (参考実装)。

## 0. この段の位置づけ

**音楽においてテンポの正確さは最重要である (ユーザ方針)**。
P6/P7 で GC 由来の停止 (100〜205ms 級) は全部消したが、それでも
実機の実測は **avg_late 17〜20ms / max 71ms** — リズムの揺れの知覚閾
(数 ms〜10ms) を超えている。原因は方式そのもの: 発音時刻を
「アプリの `_spin` が起きた時に Ruby が配る」で決めているため、
精度がアプリタスクの都合 (スケジューリング、描画、他タスク) に縛られる。

このシステムには対照実験が既にある: **FMSQ 経路は正確に聞こえる**。
消費側 (WROVER の 60Hz フレーム) が時計の権威だからである。
本段はライブ MIDI に同じ性質を与える:

```
Ruby (SmfPlayer / transport):
  数百 ms 先まで復号し、「時刻つきの確定済みコマンド」を C のキューに積む
C (タイマー駆動):
  時刻が来たら C のまま発射 (mruby には一切入らない)
```

**Ruby は作曲家に徹し、時計係を降りる**。

## 1. 設計の要点 (ここは決定事項)

### 1.1 キューに積むのは「MIDI イベント」ではなく「確定済みコマンド」

P7.5 の声グループ (和音の解決、held の管理) は **Ruby 側・積む時点**で
済ませる。C のキューが運ぶのは解決後の最終形だけ:

```
{ due_us, kind, payload }
  kind = APU_NOTE  (ch, freq, vol, duty, sweep)   -- 既存 _send_audio_note の引数
       | APU_OFF   (ch)
       | SERIAL    (最大 3 バイトの MIDI メッセージ)
```

- 音楽的なロジック (声の割り当て・折り返し・グループ解決) は
  1 行も C に移らない。C は**時刻どおりに発射するだけの馬鹿な装置**。
- 送出の C 部品は両方とも既にある: APU は P7 の msgpack 組み立て
  (`_send_audio_note` の中身を関数として再利用)、serial は
  `fmrb_midi_serial_write`。
- エントリは固定長の小さな構造体 (16 バイト級)。リングは静的確保
  (64〜128 エントリ、内蔵 RAM で ~2KB)。**mruby オブジェクトは
  一切通らない** (積む API は位置引数の C バインディング)。

### 1.2 タイマーコールバックから mruby に入らない (絶対条件)

tick 破壊の歴史があるとおり、VM の外から Ruby を触る経路は作らない。
発射は C で完結する。`fmrb_msg_send` は timer task 文脈から呼べる
(非ブロッキングで) こと、UART 書き込みが短いことを確認して使う。

### 1.3 SMF は時刻順なのでソート不要

SmfPlayer が積む順は曲の時刻順なので、**キューは FIFO でよい**。
タイマーは先頭の due まで寝て、起きたら期限が来た分を全部発射し、
次の先頭で再武装する。

### 1.4 停止・テンポ変更・シークは「クリアして積み直し」

先読みは数百 ms しかないので、`stop` / `tempo_scale=` / 曲替えは
**C キューをクリアして Ruby が積み直す**のが最も単純で正しい。
クリア API を用意し、アプリ終了時の後始末 (kernel の
silence_notes_for) と整合させること (キューに残った音の note_off を
どう保証するかを設計に含める。クリア時に「鳴っている音を全部消す」
コマンドを発射する形が素直)。

## 2. 判断を任せる点 (理由を報告に書くこと)

- **タイマーの実体**: (a) esp_timer が有力 (調査済みの事実: タスクは
  既存で picoruby-machine が ESP_TIMER_TASK dispatch を使用中、スタック
  3584B は確保済みで新規消費ゼロ、priority 22 = kernel 9 / host 10 /
  desktop 8 の全てより上、core 0 固定 = kernel/desktop とは別コア。
  つまり**上位タスクに割り込まれない**。コールバックは短く保つこと)。
  (b) 専用タスク案は内蔵 RAM に ~2KB の新スタックが要る。
  ESP-IDF linux ターゲットの esp_timer 有無を確認し、**sim と実機で
  同じ挙動**になる方を選ぶ。
- **先読み深さ**: 目安 200〜500ms。深いほど app 側の遅れに強く、
  浅いほど停止/テンポ変更の応答が良い。測って決める。
- **アンダーラン処理**: Ruby の積み直しが間に合わずキューが涸れたら、
  音は遅れてよい (壊れないこと)。回数を統計に数える。

## 3. 計測 (この段の成否はここで決まる)

- **C 側で発射遅れを測る**: 発射時刻 - due の avg/max/回数を C の
  統計に持ち、Ruby から読めるようにして既存の 5 秒ログ行に足す
  (`SmfPlayerApp:` 行の形式に合わせる)。
- **目標: 再生中 avg ≤ 2ms / max ≤ 5ms** (desktop 稼働・計測ビルドで)。
  現状の 17〜20ms / 71ms からの改善を同じ曲で before/after。
- **sim でも独立に測れる**: serial 出力の到着間隔は
  `tools/fmrb_midi_monitor.rb` のタイムスタンプで実測できる
  (P5-sim の道具がそのまま効く)。音符間隔のばらつきが縮むことを
  sim で確認してから実機に行く。
- アンダーラン回数、キュー深さの高水位も統計に。
- **APU 経路は「発射 = 発音」ではない**: 発射後に kernel → UART リンク →
  WROVER を通る。この後段のジッタは **`audio_note_lat`** (P2 で入れた
  受信側計装、実機未測定のまま) で測る。C の発射統計が良いのに音が
  揺れるなら後段が犯人で、その場合の次の一手 (kernel を迂回して C から
  直接 transport へ) は**測ってから**の判断。serial 経路には後段が無い。

## 4. 壊さないこと

- **割り当て 0 個/イベント** (bench の alloc 計測で確認)。
- **P7.5 の声グループの正しさ**: 解決が「tick 境界」から「積む時点」に
  移るので、p7_5 のホスト A/B (最終状態一致) を**同じ枠組みで再実行**
  して 0 differ を維持する。
- FMSQ 経路、受信系、picoruby-midi (md5 一致)。
- 既存テスト 139 項目。
