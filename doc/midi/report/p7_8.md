# P7.8 報告書: 入力の詰まり対策

対象: [work_order_p7_8.md](work_order_p7_8.md) (計画・実装とも Claude)。
背景: [p7_6.md](p7_6.md) 6.2 の実測 (busy なアプリ + 30Hz move で
キュー満杯 → kernel の HID 転送が 100ms/件でブロックし入力系全体が麻痺)。

## 1. 入れたもの

| 変更 | 場所 | 中身 |
|---|---|---|
| キュー 32 → 64 | fmrb_task_config.h | user/system 両方。記憶域は PSRAM ヒープ (fmrb_msg.c) なので自動で +6.4KB/アプリ、内蔵 RAM 不変。30Hz move に対し ~2.1 秒の busy を吸収 |
| move の try-send + ラッチ | input_router.rb (subtype 3) | 満杯なら**待たずに**最新 1 件を保持 (座標は絶対値なので中間欠落は無害)。`_try_send_raw_message` は両カーネルに実装済みだったものを使用 |
| trailing 保証 | app_lifecycle.rb tick_process | kernel ループ周期でラッチをフラッシュ。ジェスチャの最終位置は必ず届く |
| 順序保証 | input_router.rb (subtype 4/5) | ボタン送信の直前に同一 pid のラッチを先に試し、入らなければ捨てる (古い move がボタンを追い越さない) |
| 再現アプリ | flash/app/test/busy_input.app.rb | on_update で 700ms 眠る「わざと詰まるアプリ」。受信 move 数と最終座標をログ |

ボタン・キー・ホイールは従来どおりブロッキング送信のまま (順序と回数に
意味があるため。64 化で実質詰まらない)。

## 2. sim での判定 (全項目クリア)

busy_input を前面にして move を洪水注入 (81〜150 発):

| 判定 | 結果 |
|---|---|
| `msg_send TIMEOUT` / `hid_event slow` | **0 件** (従来はここで連発) |
| 最終位置の trailing | **完全一致** — `move 231 117` (相対 191,57) が、81 発が 9 発に合流された後でも届いた |
| クリックの欠落 | **なし** (downs=2/2) |
| 再生との並走 | smf_player 再生中に 150 発注入して **stalls=0、avg 630us** — p7_6 の事故シナリオそのものが再現しなくなった |
| 既存テスト | 174 項目全通過 |

## 3. 実機での確認 (ユーザ)

再生中にマウスを乱打し、(1) 音が止まらない、(2) ログに
`msg_send TIMEOUT` / `hid_event slow` が出ない、(3) カーソル停止位置に
UI が正しく追従する、を見る。busy_input アプリでも同じ確認ができる。
