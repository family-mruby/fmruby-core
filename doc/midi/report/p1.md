# P1 報告書: SMF -> FMSQ 変換ツール

対象: `doc/midi/work_order_p0_p1.md` の P1。

## 1. 作ったもの

| ファイル | 中身 |
|---|---|
| `tool/midi/smf2fmsq.rb` | SMF (format 0/1) -> FMSQ v1 変換本体 |
| `tool/midi/fmsq_dump.rb` | FMSQ を読んでレジスタ書き込みと音符に復号する (どの FMSQ にも使える) |
| `tool/midi/wav_pitch.rb` | WAV から音高と音長を実測する (数値検証用) |
| `tool/midi/test/make_test_midi.rb` | 検証用 .mid の生成 |
| `tool/midi/test/verify.rb` | 変換結果と WAV 実測を期待値と突き合わせる自動テスト |
| `tool/midi/test/*.mid` | 検証用 .mid (5 本) |
| `tool/midi/test/README.md` | 各 .mid の期待値表 |

すべて Ruby、標準ライブラリのみ (ルート `CLAUDE.md` の「周辺ツールの言語」)。

```
ruby tool/midi/smf2fmsq.rb input.mid -o out.fmsq [--map 1:p1,2:p2,3:tri,10:drums]
ruby tool/midi/smf2fmsq.rb --list input.mid     # チャンネル使用状況を見る
ruby tool/midi/fmsq_dump.rb --notes out.fmsq    # 変換結果を音符として確認
ruby tool/midi/test/verify.rb                   # 回帰テスト
```

## 2. 設計判断とその理由

作業指示書 3.2 の 5 点について決めたこと。**指示ではなく判断が要る箇所なので、
覆す余地がある**。

### 2.1 命令の選び方: REG_WRITE のみを使う

FMSQ には NOTE_ON / NOTE_OFF / PARAM というチャンネル命令もあり、BASIC の
`PLAY` はそちらを使っている。それでも REG_WRITE だけで出すことにした。

- REG_WRITE は仕様書 (`fmsq_format.md`) に完全に書かれており、
  fmrb-audio-tools の `fmsq_player` と graphics-audio の再生器の両方が実装している。
  チャンネル命令は仕様書では「予約」扱いのままである。
- duty / 音量 / スイープ / ノイズ周期を 1 つの表現で完全に制御できる。
- `nsf2fmsq` の出力と同じ形なので、既存の道具がそのまま使える。

代償は容量で、音符あたり 6 バイト (発音) + 2 バイト (消音) になる。実測では
5 分半のピアノ曲 (704 音) で 6.5 KB だったので、FMSQ の 64 KB 制限には当たらない。

### 2.2 チャンネル割り当て

既定は README 方向B のとおり **ch1 -> pulse1、ch2 -> pulse2、ch3 -> triangle、
ch10 -> noise**。割り当てのない ch の音は捨て、捨てた数を ch ごとに表示する
(黙って減らさない)。

- `--map 1:tri,4:p1,...` で上書きできる。`--map 2:-` で明示的に捨てられる。
- `--auto` を付けると、音数の多い順に 3 ch を選び、平均音高の高い順に
  pulse1 / pulse2 / triangle へ割り当てる。ch10 は常にノイズ。
  実在の .mid はチャンネル番号が 1/2/3 とは限らないため
  (試したバッハの曲は ch1-5 を使っていた)、既定より `--auto` のほうが
  結果が良いことが多い。**既定を `--auto` にしなかったのは、既定は予測可能
  であるべきで、テストの期待値も固定できるほうがよいと判断したため**。
- `--list` でチャンネルごとの音数と音域を表示できるので、`--map` を決める
  材料になる。

### 2.3 声が足りないときに何を捨てるか: 後着優先 + 復帰

APU の 1 声はモノフォニックなので、**同じ MIDI チャンネル内で音が重なったら
新しい音が声を奪い、その音が離されたら「まだ押されている中で最も新しい音」に
戻る**ようにした。

- モノフォニックシンセの標準的な挙動 (last-note priority) であり、演奏として
  自然に聞こえる。
- 重要なのは「和音を鳴らそうとして 2 音目以降を単に捨てる」のと違い、
  **レガート (わずかな重なり) で書かれた旋律が途切れない**こと。実在の SMF は
  音符の終わりが次の音の頭とわずかに重なることが多く、単純な先着優先だと
  1 音おきに落ちる。
- 奪った回数は変換時に表示する (`overlapping notes resolved: pulse1=1`)。
- **和音を複数の声に散らす機能は入れていない**。散らすと旋律とベースの
  声が奪われて曲の骨格が壊れるため、散らすかどうかは人が `--map` で
  決めるほうがよいと判断した。

### 2.4 時間解像度とテンポ変更

- SMF の tick を、テンポマップ (Set Tempo をすべて積分した表) で秒に直し、
  秒を 60Hz フレームに **四捨五入**する。切り捨てではなく四捨五入にしたのは、
  誤差の期待値を 0 にするため (切り捨てだと平均 8ms 早まる)。
- **曲中のテンポ変更に追従する**。テスト `tempo_change.mid` で、120 BPM の
  4 音がフレーム間隔 30、240 BPM の 4 音が間隔 15 になることを確認している。
- SMPTE 単位の division (division の bit15 = 1) にも対応した。この場合は
  テンポイベントを無視して固定の秒/tick で計算する (仕様どおり)。
- フレーム 0 は初期化書き込み専用にし、時刻 0 の音はフレーム 1 に置く。
  16.7ms 遅れるが、初期化との順序が曖昧になるより確実である。

### 2.5 ベロシティ -> 音量

既定は**線形** (`volume = round(15 * velocity / 127)`、1 未満は 1)。
`--vel-curve log` で対数カーブも選べる。

- APU の音量レジスタは振幅に対して線形なので、線形写像は「ベロシティの比が
  そのまま振幅の比になる」。ドラムのアクセントが素直に出る。
- 一方、耳の感度は対数なので、線形だとベロシティ 60 以下がかなり小さく
  聞こえる。持続音主体の曲では `--vel-curve log` のほうが自然になる。
  どちらが良いかは曲によるので、**既定は素直な線形にして選べるようにした**。
- 三角波は音量制御を持たないので、ベロシティは無視される (仕様上の制約)。

### 2.6 ドラム (ch10)

GM のノート番号ごとに **ノイズ周期・短周期モード・減衰フレーム数**の表を持つ
(`DRUM_MAP`)。バスドラは低い周期 13、スネアは 8、クローズドハイハットは
短周期モードの 3、シンバル類は 1-2 で長め、という具合。

- 減衰は APU 内蔵のエンベロープではなく、**変換側が数フレームかけて音量
  レジスタを書いて作る**。内蔵エンベロープは必ず最大音量から始まるので、
  使うとベロシティが死ぬ。書き込みは 1 打あたり 2 バイト x 減衰段数で、
  実測 12 打のパターンで 220 バイトだった。
- ノイズは 1 声しかないので、**同じフレームに重なった打楽器は 1 つに潰れる**
  (後から書いたほうが鳴る)。テストではキックとハイハットが重なるフレームで
  これを確認している。潰れた数は「奪った回数」として表示される。

## 3. 検証結果

### 3.1 自動テスト

`ruby tool/midi/test/verify.rb` = **69 項目すべて成功**。内訳:

- 構造検証: 変換した FMSQ を復号して、フレーム位置・音高・音量・ドラム設定を
  手計算の期待値と比較する。期待値の音高は **APU のタイマ量子化を含めて
  別途計算**しており (`CPU / (16 * (timer + 1))`)、変換器の計算をそのまま
  使ってはいない (同じ間違いで打ち消し合わないようにするため)。
- 音響検証: `fmsq_player` で WAV に書き出し、`wav_pitch.rb` で実測する。
  8 音すべてが期待周波数に対し **±1 セント以内**、発音時刻は期待値に対し
  **±3ms 以内**、音長は 0.375s に対し ±40ms 以内。

実測値 (scale.mid、WAV 実測):

| 音 | 期待 (APU 量子化後) | 実測 | 差 |
|---|---:|---:|---:|
| C4 | 261.36 Hz | 261.35 Hz | -0.1 cent |
| D4 | 293.60 Hz | 293.58 Hz | -0.1 cent |
| E4 | 329.97 Hz | 330.15 Hz | +0.9 cent |
| F4 | 349.57 Hz | 349.62 Hz | +0.3 cent |
| G4 | 392.49 Hz | 392.35 Hz | -0.7 cent |
| A4 | 440.40 Hz | 440.63 Hz | +0.9 cent |
| B4 | 494.96 Hz | 494.91 Hz | -0.2 cent |
| C5 | 522.71 Hz | 522.69 Hz | -0.1 cent |

C4 = 261.35 Hz は、BASIC の PLAY を同じ方法で測ったときの値と一致する。

## 4. 申し送り

### 4.1 sim 実行のためにビルド状態を退避したこと

sim は `build/fmruby-core.elf` (Linux ビルド) を docker から直接実行する
構成なので、確認には fmruby-core の Linux ビルドが要る。作業時点のツリーには
esp32s3 向けの `sdkconfig` と `build/` があり、`rake build:linux` は
これを見て停止する。

`rake clean_all` は既存の esp32 ビルドを消してしまうため使わず、
**`sdkconfig` と `build/` を退避 (mv) してから Linux ビルドし、
検証後に戻した**。消していないので、esp32 側は元の状態のまま使える。

検証用に `flash/app/demo/` へ一時的に複写したもの (`sim_play.app.*`、
`audio_bench.app.*`、`smf_test.fmsq`) と、ランチャーの再スキャンで
2 行増えた `flash/data/launcher_index` も元に戻した。

**Linux ビルドは捨てずに `build.linux.saved` / `sdkconfig.linux.saved`
として残してある** (P2 以降でまた sim を使うため。再ビルドは約 10 分)。
不要なら消してよい。切り替えは:

```
mv build build.esp32.saved && mv sdkconfig sdkconfig.esp32.saved
mv build.linux.saved build && mv sdkconfig.linux.saved sdkconfig
```

### 4.2 sim 検証で分かった操作上のこと

- 新しいアプリを `flash/app/` に置いても、ランチャーは
  `flash/data/launcher_index` (ブート時に作られる索引) を見るので出てこない。
  **ランチャーウィンドウ内で右クリック (`--button 3`) すると再スキャン**され、
  索引が更新されて出てくる。
- ランチャーの一覧は**キーボードの `down` でスクロールする**。
  スクロールバーのドラッグでは動かなかった。
- sim の再起動は 3 コンテナまとめて (`docker compose down` してから
  `dev_run_check.sh`)。core だけ入れ替えても画面が出ない。

### 4.2 ツールの限界 (使うときに知っておくこと)

- `wav_pitch.rb` は単音しか測れない。和音や複数声が同時に鳴っている区間では
  最も強い成分を返すだけなので、音高を厳密に見たい場合は声を分けて出力する
  (`--map 2:-,3:-` のように他の声を落とす)。実在の曲の WAV を測ると
  「1 つの長い音」として報告されるのはこのため。
- `fmsq_dump.rb` はチャンネル命令 (NOTE_ON / NOTE_OFF / PARAM) を復号しない。
  引数の長さがチャンネルごとに異なり、仕様書では予約扱いのままなので、
  推測して読み進めるより明示的に停止するようにした。**BASIC の PLAY が
  出す FMSQ はこの命令を使うので、そちらを読むには実装の追加が要る**。
- SMF の format 2 は非対応 (エラーで落とす)。ピッチベンド、コントロール
  チェンジ、プログラムチェンジは読み飛ばす。

### 4.3 P2 に向けて分かったこと

- 変換器の中で「MIDI ノート -> APU レジスタ」の対応表 (音高、音量、ドラム、
  声の奪い方) を一通り作った。**P2 の APU transport はこれと同じ写像を
  実時間でやる**ことになるので、この規則をそのまま持っていける
  (`smf2fmsq.rb` の `PulseVoice` / `TriangleVoice` / `NoiseVoice` と
  `DRUM_MAP`)。
- ただし transport 側は `FmrbAudio#note_on` 経由になり、**引数の形が違う**
  (周波数は Hz、ノイズは period を freq の下位 4bit に載せる)。P0-2 報告の
  「設計への影響 4」を参照。
- 実時間再生 (C-b) をやるときは、**変換器が持っている「フレーム単位に
  まとめる」処理が不要になる代わりに、テンポマップの計算はそのまま要る**。
  テンポマップと SMF パーサは Ruby で書いてあるので、P4 で実機に載せる際は
  この Ruby を移植するか、C に書き直すかの判断が要る (P0-1 の結果次第)。
