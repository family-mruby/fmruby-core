# P7 報告書: 演奏を止めない (GC 停止の除去)

対象: `doc/midi/work_order_p7.md`。
前提: [p6.md](p6.md) の **10 章 (実機実測)**、[README.md](../README.md)。
GC の観測手段そのものは [../../gc_monitoring.md](../../gc_monitoring.md) にまとめてある。

実機で音を止めていたのは GC の一括停止 (1 回 110〜205 ms) だった。
**A で「停止をアプリの暇な時間の細かい歩みに割る」仕組みを入れ、B で
「MIDI 経路の GC の契機そのもの」を消した**。sim では A・B とも数字で出ている。

## 0. 結論だけ先に

| | 変更前 | 変更後 (sim 実測) |
|---|---|---|
| **A** 割り当てのあるアプリの同期停止 | 19 回 / 2.5 秒、最長 7.6 ms | **0 回**。同じ仕事が 195 回のステップ (最長 5.1 ms) に移った |
| **A** ステップが起床を遅らせた量 (jitter) | - | **0 回** |
| **A** GC の総時間 | 98 ms | 110 ms (**払う時期が変わっただけ**。測定ごとに 1 割ほどばらつく) |
| **B** `audio.note_on` の割り当て | 16.1 個/回 (P6 前) -> 3.1 個 (P6) | **0 個/回** |
| **B** ワイヤのバイト列 | - | **`MessagePack.pack` と完全一致** (8 通りで検証) |
| APU 再生中の GC | 5 秒に 1 回 (P6 後) | **1 回も起きない** (25 秒間 n 不変) |

**MIDI に関しては B だけで決着が付いた** (割り当てが無いので GC が来ない)。
A は「割り当てを消しきれないアプリ」のための仕組みとして残り、bench アプリの
合成ワークロードで効果を測ってある (3 章)。

## 1. A: `_spin` 前の GC ステップ (`FmrbApp#idle_gc`)

### 1.1 既存の API だけで足りた

指示書 2.1 のとおり、**mruby 本体にも mruby-task にも手を入れていない**。

| 使ったもの | 出どころ |
|---|---|
| `mrb_gc_scheduler_pending()` / `mrb_gc_step()` / `mrb_gc_scheduler_jitter()` | `mruby/gc.h` の組み込み向けプリミティブ |
| `GC.scheduler_driven=` / `GC.debt_limit=` / `GC.step_limit=` | mruby-task gem と mruby core (Ruby から見える) |
| `fmrb_msg_get_stats()` の `current_waiting` | `components/fmrb_msg/fmrb_msg.h` |
| `fmrb_hal_time_get_us()` | `components/fmrb_hal/fmrb_hal_time.h` |

### 1.2 入れた場所と形

`lib/add/picoruby-fmrb-app/ports/esp32/app.c` の `_spin`、**メッセージ待ちに
入る直前**。ループの先頭で `spin_idle_gc()` を呼び、1 ステップでも進めたら
`continue` して時計とキューを読み直す。

`spin_idle_gc()` が止まる条件は 3 つ:

1. **残り時間がステップ 1 回分を吸収できないとき**。これが要点で、
   `_spin` が予定より遅れて返ることが無い = **collect したせいでアプリが
   遅くなることが原理的に無い**。ステップの実測時間をアプリごとに持ち、
   長いほうへ即座に追従し、そうでなければ 1/8 ずつ減衰させる (外れ値が
   数ステップで抜ける)。
2. 残りが 2 ms を切ったとき。
3. **メッセージが積まれたとき**。そのメッセージはステップを待たされたので、
   `mrb_gc_scheduler_jitter()` に記録して抜ける。

有効にしていないアプリでは `mrb_gc_scheduler_pending()` が常に FALSE なので、
**`_spin` 1 周につき関数呼び出し 1 回**しか増えない。

### 1.3 スイッチ (指示書 2.4 の「切り替え方」)

**`GC.scheduler_driven=` は既に Ruby から見えている**ので、C 側には
スイッチを作らなかった。アプリからは `FmrbApp#idle_gc=` 一行で入る:

```ruby
def on_create
  self.idle_gc = true
  ...
```

`idle_gc=` は 3 つの設定を**まとめて**行う。個別に触らせると
`scheduler_driven` だけ有効で `debt_limit` が 0 (無効) という壊れ方を
するためである:

| 設定 | 値 | 理由 |
|---|---|---|
| `GC.scheduler_driven` | true | 割り当て経路の GC を止め、ステップ駆動にする |
| `GC.debt_limit` | 4096 | 暇が無いときの安全弁 (1.5) |
| `GC.step_limit` | 512 | 1 ステップの上限 (1.4) |

`.toml` のフラグにしなかったのは、C 側に読み出しと受け渡しを足す必要があり、
Ruby 一行で済むことに対して機構が重いからである。

**現状 ON にしているのは MIDI の 2 本** (`smf_player` / `midi_apu`)。
既定 ON にするかの判断は 1.6。

### 1.4 ステップの大きさ (`GC.step_limit`)

**ステップは開始したら中断できない**ので、その長さが「まだ残る唯一の遅れ」に
なる。bench アプリで上限を振って測った (同じ 24,000 オブジェクト):

| `GC.step_limit` | ステップ回数 | 最長 1 ステップ | GC 総時間 |
|---|---|---|---|
| (idle_gc 無し = 同期停止) | 19 回の停止 | 7.6 / 8.1 ms | 98 / 109 ms |
| 2000 (mruby の既定) | 65 | 9.3 / 6.3 / 10.5 ms | 107 / 92 / 111 ms |
| **512 (採用)** | 195 | 5.1 / 5.3 / 4.7 ms | 110 / 94 / 102 ms |
| 128 | 598 | 4.8 / 4.9 ms | 95 / 99 ms |
| 32 | 1885 | 3.8 / 4.9 ms | 93 / 99 ms |

(複数回の測定値。最長値も総時間も 1 割程度ばらつくので、**差が 1 ms しかない
行は同じと読むこと**)

**512 より下げても最長は縮まない**。サイクルごとに 1 回、分割できない
フェーズがあるのが床で、`prof_final_mark_max_us` は 1〜2 us なので
final marking ではない (root scan と見ている)。したがって **512 が膝**で、
これを `IDLE_GC_STEP_LIMIT` の既定にした。採用値は bench の `idle_default`
行 (`FmrbApp#idle_gc=` が選んだ値をそのまま使う行) でも確認してある。

総時間はどの設定でも変わらない = **idle_gc は GC を増やしも減らしもせず、
いつ払うかだけを変える**。

### 1.5 暇が無いアプリでどうなるか (指示書 2.3 / 完了条件 2)

`scheduler_driven` を有効にすると割り当て経路の自動 GC が止まる。
`_spin` に余裕が無いままだと debt が積み上がるので、**`GC.debt_limit` が
安全弁**になる (`gc.c` の `mrb_obj_alloc_core`: `auto_step` が off かつ
debt が limit を超えたら、その場で同期ステップを 1 回回す)。

**既定値は 0 = 無効**なので、`idle_gc=` が必ず一緒に設定する (4096)。
これを忘れると「暇が無いアプリはヒープが伸び続ける」ことになる。
なお free slot が尽きたときは `scheduler_driven` 中は**ページを足す**
(gc.c が明示的にそう書いてある。回収は idle ステップと安全弁に任せる方針)
ので、プール自体が尽きればアロケータ側の緊急 GC に落ちる
(`prof_emergency_count` で見える)。

**忙しいアプリの挙動をまとめると**:

- 停止はゼロにはならないが、**1 回の停止は `step_limit` で頭打ち**になる
  (以前は世代別 minor が 1 サイクル丸ごと不可分で、それが実機の 205 ms
  だった)。**最悪ケースはむしろ改善する**。
- 代わりにヒープは debt_limit の分だけ余分に膨らむ。500 KB プールに対し
  4096 オブジェクトなので、実測の live 2000〜3600 に比べて過大ではない。
- 世代別モードは有効化時に off になり、**戻すときも自動では戻らない**
  (`GC.generational_mode = true` を明示的に呼ぶ必要がある)。
  `idle_gc = false` は `scheduler_driven` と `step_limit` だけを戻す。
  現状の計測では全 GC が major だったので実害は見ていない。

### 1.6 既定 ON にするかの判断 (指示書 2.4)

**当面は opt-in のまま**にする。理由:

- sim で測った範囲では悪化が無い (総時間同じ、jitter 0、停止 0) が、
  **測ったワークロードは 1 種類**である。世代別モードが off になるのは
  全アプリの GC 特性を変える変更で、プールは既に窮屈である (5 章)。
- 効果が要るのは「時間を守る必要があるのに割り当てを消せないアプリ」で、
  現状それは MIDI の 2 本と、指示書が挙げた raycaster のような毎フレーム
  割り当て型のアプリに限られる。
- 逆に**既定化を正当化する材料もはっきりしている**: ゲーム数本を
  idle_gc ON で走らせ、(a) プールの高水位 (`FmrbApp.ps` の `mem_used`)、
  (b) フレーム時間、(c) `prof_step_jitter_max_us` の 3 つが悪化しないことを
  示せばよい。これは実機の余裕があるときの作業として残す。

## 2. B: 音声メッセージの C 化

### 2.1 やったこと

`FmrbAudio#note_on` / `#note_off` **だけ**を C で組む形にした。
Ruby の API は変えていない。

- `FmrbApp#_send_audio_note(on, ch, freq, vol, duty, sweep)` (app.c)。
  msgpack のバイト列をスタック上のバッファに直接書き、`fmrb_msg_send` に渡す。
  **mruby のオブジェクトを 1 つも作らない**。
- msgpack-c は引き込んでいない。整数 1 個・短い文字列 1 個・fixmap の
  ヘッダだけなので、**msgpack-c の `msgpack_pack_int64` と同じ幅の選び方**を
  する 30 行の関数で足りる (指示書 3.2 の「テンプレートに値をパッチ」より
  素直で、値の幅が変わっても正しい)。
- `FmrbAudio#initialize` が `respond_to?(:_send_audio_note)` を**一度だけ**
  見て経路を決める。desktop のように `send_message` しか持たない持ち主や
  ホストテストのスタブでは、従来の Hash 経路がそのまま動く。

### 2.2 バイト列が同じであることの検証

**受け手 (kernel の `audio_handler.rb`) から見て区別が付かないこと**が
この変更の前提なので、そこを読んで確かめるのではなく**実行して比較**した。

`FmrbApp#_audio_note_bytes` が同じ関数の出力を String で返す。
bench アプリがそれを `MessagePack.pack` の出力と突き合わせる:

```
midi_bench: audio wire matches MessagePack.pack: true (8 cases)
```

8 通りは note_on / note_off x 4 種の値で、**fixint (0〜127)・uint8 (128〜255)・
uint16 (256〜)** の境界をまたぐように選んである (整数の幅の選び方が
一致していないと落ちる)。

### 2.3 実測

| | P6 前 | P6 後 | **P7 後** |
|---|---|---|---|
| `audio.note_on` | 16.1 個/回 | 3.1 個/回 | **0 個/回** |
| `apu.note_on` + `note_off` | 25.1 個 | 6.1 個 | **0 個** |

音が本当に出ることは sim で確認済み (`tools/fmrb_audio_probe.rb`):
MIDI APU デモの SMF 再生で peak 4864 / 113 窓、piano アプリの鍵盤で
peak 2816 / 31 窓。**C 経路で鳴っている**。

## 3. A と B の関係: MIDI では A の出番が無くなった

B を入れた後、**APU 経路の再生中に GC が 1 回も起きない**:

```
MidiApu: events=394 avg_late=2ms max_late=84ms stalls=0
  [gc live=2317 n=3 major=2 pause=3x tot=0ms max=0ms step=0x tot=0ms max=0ms jit=0x max=0ms]
```

25 秒間 `n=3` のまま (3 回は起動時)。**割り当てが無いので契機が無い**。
serial 経路は P6 の時点で既にそうだった。

そのため **A の効果は MIDI では測れない**。bench アプリに合成の
ワークロード (1 更新あたり 200 オブジェクト、20 ms の余裕、120 更新) を
足して測ったのが 0 章と 1.4 の数字である。**これは「割り当てを消せない
アプリ」の代理**であって、MIDI アプリの姿ではない。

## 4. posix 側について (指示書 2.2 / 3.2)

**両方に入れる必要は無かった**。`_spin` も `_send_audio_note` も
`ports/esp32/app.c` にあり、`components/picoruby-esp32/CMakeLists.txt` は
**linux ターゲットでも同じ `ports/esp32/*.c` をコンパイルしている**
(`if(IDF_TARGET STREQUAL "linux")` の分岐で同じ glob を使っている)。
`ports/posix` は存在しない。したがって sim と実機は同じコードで動く。

## 5. ついでに分かったこと: tetris が sim でだけ起動できない (P7 以前から)

**実機では起動する** (ユーザ確認 2026-08-05)。sim でだけ、
**`/app/game/tetris.app.rb` が起動時に `NoMemoryError` でコアプロセスごと
落ちる**。

sim 限定である理由の有力な仮説は**ポインタ幅**: sim は x86-64 で
ポインタ 8 バイトのため、コンパイル時の構造 (AST・irep・オブジェクト) が
32bit 実機の 1.5〜2 倍のバイト数になる。プールは両者 500 KB なので、
**同じソースが sim では溢れ、実機では収まる**。p6.md 1 章の
「sim はオブジェクト数と GC 回数を実機とそのまま比較できる」は正しいが、
**バイト数は 64bit 側が常に不利**という但し書きが要る。境界近くの
アプリは sim が先に落ちる (安全側の誤差ではある)。

```
[Tetris] Script size: 14240 bytes
(unknown):0: Out of memory (NoMemoryError)
Aborted (core dumped)
```

**P7 の変更とは無関係**である。変更を `git stash` で全部外したビルドで
同じ手順を実行し、**同じところで同じように落ちることを確認した**。
14 KB のスクリプトをコンパイルした時点で 500 KB プールが尽きる、
P6 6 章と同じ問題の別の現れ方である (あちらは 9.5 KB + 曲データ)。

対処は 3 通りあるが、**どれも P7 の範囲外なので手を付けていない**:

- `tetris.app.toml` に `large_memory = 1` (1 MB プールへ)。1 行だが、
  1 MB プールは同時に 1 アプリしか使えない。
- コンパイル時のメモリを減らす (スクリプトを分割 / 事前コンパイル)。
- プール構成の見直し。

**アプリ起動でコアプロセスごと落ちる**点も別途の問題である
(mruby のコンパイル中の `NoMemoryError` は Ruby の `rescue` に届かない)。

他のゲーム (shooter, piano) と MIDI の 2 本は正常に動作する。

## 6. 実機での確認手順

**計測ビルドで焼くこと**。手順は p6.md 7 章と同じ形式。

### 6.1 準備

```
cd fmruby-core
rake clean_all
FMRB_GC_PROFILE=1 rake build:esp32
FLASH_BAUD=115200 rake flash
python3 ../tools/fmrb_serial_capture.py -t 60 play.log
```

### 6.2 B の効果 (MIDI が GC を呼ばなくなったか)

SMF プレーヤか MIDI APU デモで曲を再生し、5 秒ごとの行を見る。

```
grep "events=" play.log
```

- **期待: `n=` (GC 回数) が再生中ずっと増えない**。P6 実機では APU 経路で
  47 秒に 9 回だった。
- **`stalls=0` かつ `max_late < 50ms`** が目標値 (P6 実機は 198 ms / 6 回)。
- APU 経路と serial 経路の両方で見る (「7 Out」で切り替え)。
  **両方とも 0 のはず**である。

### 6.3 A の効果 (停止が細かい歩みに割れているか)

B が効くと MIDI では GC 自体が起きないので、**A は別のもので見る**。
`n=` が増える場面 (曲の読み込み、選曲の走査、他のアプリ) で:

- `pause=` の回数と `tot`/`max` が**増えないこと**。
- 代わりに `step=` が増えていること。
- `jit=` (ステップが起床を遅らせた回数と最大) が**小さいこと**。
  これが大きいなら `IDLE_GC_STEP_LIMIT` を下げる。

**実機の 1 ステップが何 ms かはここで初めて分かる**。sim では 4.7 ms、
実機の倍率 (p6.md 10.2 の 20〜40 倍) を掛けると 100〜200 ms になる計算だが、
**それは「サイクル丸ごと」から出した倍率なので、ステップに掛けるのは
過大なはず**である。`step= ... max=` の実測が答になる。
もし本当に 100 ms 級なら、`IDLE_GC_STEP_LIMIT` を 128 / 32 に下げて
同じログを見る (1.4 の表の形で比較できる)。

### 6.4 A の安全弁 (暇が無いとき)

`idle_gc` を ON にしたアプリを**わざと忙しくする** (SMF を x2.0 で再生し、
同時に別のアプリを動かす) と、`pause=` が増え始めるはずである。
これが 1.5 の安全弁が働いている姿で、**そのときも `max=` は
`step_limit` 相当に収まっている**ことを確認する。

### 6.5 tetris (5 章)

`large_memory = 1` を付けた版で起動するかを見る。落ちるなら
コンパイル時メモリの問題として別途扱う。

## 9. 実機実測 (2026-08-05 追記)

6 章の手順を S3 実機で実行した (整合済みの計測ビルド。なお最初の焼きで
ABI ガードが発火してブートループになった。`rake clean` では cmake の
configure が古いままになるためで、詳細は p6.md 1.1 に追記した)。

### 9.1 B は完全に決着

同じ曲を APU で 31 秒 (329 イベント)、serial で 21 秒、続けて別の曲を
APU で 20 秒 (407 イベント) 再生して、**GC 回数 `n` が一度も増えなかった**
(n=18 のまま。曲間の読み込みで 1 回だけ 19 に増えた)。
P6 実機の「47 秒に 9 回」が **0 回**になった。
**「割り当てが無ければ GC は来ない」が実機で成立**した。

### 9.2 A も効いたが、実機の 1 ステップに床がある

曲間 (読み込み + 選曲) の 1 回の GC は **12 ステップに割れ、同期停止は
1 回も増えなかった** (pause=18x のまま、jit=0)。A は設計どおり動いている。

ただし **1 ステップの最大が 336ms** だった (12 ステップ合計 341ms のうち
1 つが 336ms、残り 11 で 5ms)。sim の床 4.7ms のおよそ 70 倍で、
**サイクル中の分割できないフェーズは実機ではこの大きさ**ということである。
p6.md 10.2 の倍率 (20〜40 倍) を上回っており、`step_limit` では切れない。

含意:

- ステップ実測の追従により、**この後の idle_gc は 338ms 以上の暇が
  ないと歩を進めない** (安全側に倒れる設計どおりだが、事実上停止する)。
  debt が積もれば安全弁の同期ステップに戻り、そこにこの 336ms が来得る。
- **A の実機での実用性は「336ms の分割不能フェーズを縮められるか」に
  懸かっている**。何のフェーズか (root scan か sweep の塊か) の特定が
  次の課題。mruby 側に手を入れずに縮める道があるかも含めて未解決。
- MIDI には影響しない (B により契機が無い)。

### 9.3 新しい発見: GC ではない ~190ms の停止が残っている

再生中に `stalls` が 1〜3 回、`max_late` 186〜196ms を記録したが、
**その間 GC の全カウンタが凍結している** (n も pause も step も不変)。
つまり **GC 以外に ~190ms 止める何かがいる**。

- 発生は 10〜30 秒に 1 回程度。avg_late は 8〜16ms で常時は健全。
- **デバッグモード時のみの現象である**: 周期ダンプは
  `fmrb_debug_mode_enabled()` のときしか走らない (status_led.c)。
  通常運用ではこの停止は最初から存在しない。**計測しているときだけ
  観測を乱す**、観測者効果である。ただし計測の邪魔になるので直す価値は
  ある (下記)。
- **犯人はほぼ特定できた**: 周期ダンプは status_led タスクから呼ばれ、
  status_led は **priority 3・core 1** — アプリ (priority 2・core 1) の
  1 段上・同一コアである。ダンプは数十行を UART 115200 へ同期出力する
  ので、**core 1 を 100〜200ms 連続占有**する。周期・長さ・単発性が
  観測と一致する。
- P6 実機の stalls=6 のうち何割かは、GC ではなくこれだった可能性がある
  (当時は GC が 9 回あったため区別できなかった)。

**目標の再設定 (ユーザ指摘)**: アプリは低優先度が設計であり、
割り込まれること自体は正常。「stalls=0」は目標として過大だった。
正しい目標は (1) アプリ自身の実行系 (GC) が止めない — 達成、
(2) **システム側の占有が短く刻まれている**こと。数 ms の割り込みの
積み重ねは無害で、1 回 190ms の連続占有だけが問題である。

**対処済み (a3fa59a) — ただし話はそこで終わらなかった**。ダンプは
行間 yield + スロット単位のロック/yield に刻んだ (優先度を落とす案は
「busy なアプリに飢餓させられるとハートビートごと死ぬ」というユーザ
指摘で棄却)。実機で再測すると:

- **ダンプは容疑者から外れた**: ダンプ時刻と stall が重ならなくなり、
  ダンプ時の遅れは 2 桁 ms に落ちた。計装 (`dump took: tasks=Xms
  pools=Yms`) でアイドル時 75/31ms、細切れは 5〜7ms/行。
- **しかし stall (>200ms) は依然 ~10 秒周期で残る**。アプリの GC は 0、
  ダンプも無関係、となると **残る容疑者は同じ core 1 の上位 Ruby VM
  (desktop prio 8 / kernel prio 9) 自身の GC** である。desktop は時計を
  毎秒描画して割り当てており、その GC (1 回 100〜200ms 級) が周期的に
  走れば、アプリから見た観測と一致する。**未確認の仮説**。
- 確認と修正が一手で済む見込み: **desktop に idle_gc を入れる** (P7 の
  A の本来の適用先はアプリではなく desktop/kernel だったことになる)。
  stalls が消えれば犯人確定 + 修正完了。desktop の待ち窓は広いので
  336ms ステップ問題 (9.2) にも当たりにくい。
- 別件: アプリ起動中の `dump took: pools=453ms` を 1 回観測。コンパイル中
  の 1MB プールの空きリスト走査は 1 スロットでも長い。統計走査自体の
  上限が要る (未対処)。

### 9.4 まとめ

| 目標 (6 章) | 結果 |
|---|---|
| 再生中 `n=` が増えない | **達成** (両経路とも 0 回) |
| stalls=0 / max_late < 50ms | **未達 — ただし原因は GC ではない** (9.3) |
| A が停止を歩みに割る | **達成** (pause 増 0、ただし 336ms の床を発見) |

P7 の主題 (GC が音を止める) は**実機で解決を確認**。残った揺らぎは
別の犯人 (9.3) であり、追跡は別件とする。
