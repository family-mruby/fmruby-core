各項目は「何を判断するための数字か」を先に書き、次に手順と結果を書く。

## P0-1: APU 発音の遅延とスループット

### 何を判断するためか

P2 で SMF プレーヤを C に置くか Ruby に置くか。より根本的には、
方向B (APU transport) が実時間演奏に耐えるか。

### 測り方

計測アプリ `tool/midi/test/sim_play/audio_bench.app.rb` を書き、
`FmrbAudio#note_on` / `#note_off` を 200 回ずつ全速で呼んで
`Machine.board_millis` で所要時間を測った。3 パターン:
単発の note_on、note_on + note_off の対、3 音の和音 (note_on を 3 連続)。

**測っているのはアプリ VM から見た送出コスト** (msgpack 符号化 + kernel への
メッセージ投入) であり、音が出るまでの時間ではない。実際に link を通ったかは
core 側の `fmrb_transport: stats` の `tx_msg/s` で確認した。

### 結果 (Linux sim、2 回実行)

| パターン | 1 回あたり | 換算レート | メッセージ数/秒 |
|---|---:|---:|---:|
| note_on 単発 | 115-130 us | 7,700-8,700 回/s | 同左 |
| note_on + note_off | 210-215 us | 4,650-4,760 対/s | 9,300-9,500 |
| 3 音の和音 | 340 us | 2,940 和音/s | 8,800 |

- **メッセージ 1 通あたり約 115 us** で頭打ちになる (どのパターンでも
  メッセージ数/秒がほぼ同じ)。
- **取りこぼしは無かった**。計測中の 5 秒窓で `tx_msg=283/s`
  (定常は 10-93/s)、5 秒で約 1,415 通。バーストで投入した音声メッセージ
  1,200 通 + 定常の GFX 分に一致する。キュー (長さ 128) は溢れていない。
- 1 メッセージは約 13.7 バイト (`tx=3875 B/s` / `283 msg/s`)。

### 実機での上限 (計算による見積り、未実測)

**sim の link は Unix ソケットで、実機の UART 921600 bps とは桁が違う**。
実機側の上限は概算で:

- 921600 bps = 約 92 KB/s、1 メッセージ 13.7 バイト + COBS の枠 ->
  理論上 **6,000-6,500 通/s 程度**。
- ただし **GFX が同じ link と同じ host メッセージキューを共有する**。
  実測で GFX は 160 cmds/s 級を流している。

MIDI 側の必要量は、密な曲でも 50 イベント/s、非常に密でも 200 イベント/s
程度である。**理論上限とは 1 桁以上の開きがあるので、イベント数は
律速にならない**見込み。ただし実機での実測は S3 接続時に行う必要がある。

### 判断: SMF プレーヤは Ruby でも成立する見込み

送出 1 回 115 us なら、64 分音符 (テンポ 120 で 31ms) ごとに和音 3 音を
送っても 1ms 程度しか食わない。**P2 の実装深度を上げる (C に降ろす) 理由は
現時点では無い**。ただし以下は未確認:

- **発音までの遅延 (end-to-end) は測れていない**。core と graphics-audio は
  別プロセスで、ログのタイムスタンプは各プロセス起点なので突き合わせられない。
  実機でも同じ問題がある。
  **P2 で音声側に受信時刻の計装を入れることを勧める** (入力側の
  `spx: hid_lat` と同じ形で、note_on 受信のレイテンシと件数を周期ログに出す)。
- 実機 (S3 + WROVER、UART 921600) での送出コストと上限。

## P0-2: FMSQ 再生中の note_on の挙動

### 何を判断するためか

方向B (APU transport) で **BGM を鳴らしながら MIDI で実時間演奏できるか**。
できないなら、チャンネル割り当て表の設計も、アプリの作り方も変わる。

### 結果: 両立する (奪い合わない)

**MAIN と SUB は独立した APU エミュレータインスタンスであり、それぞれが 4 声を持つ。
出力は加算合成される。したがって FMSQ の BGM と note_on の実時間演奏は同時に鳴り、
声を奪い合わない。合計 8 声。**

根拠 (fmruby-graphics-audio):

| 音源 | インスタンス | 位置 |
|---|---|---|
| NSF 再生 | MAIN | `main/tasks/audio_task.c` `audio_task_nsf_play` (`apuif_select(APUIF_INSTANCE_MAIN)`) |
| FMSQ slot instance=0 | MAIN | 同 `audio_task_fmsq_play_slot` (instance 0 -> MAIN) |
| FMSQ slot instance=1 | SUB | 同 (instance 1 -> SUB) |
| `note_on` / `note_off` | **SUB 固定** | 同 `audio_task_note_on` / `audio_task_note_off` |

- 声の割り当ては**インスタンス単位**である。MAIN の 4 声と SUB の 4 声は別物で、
  `$4015` (チャンネル有効化) もインスタンスごとに独立している。
- 混ぜているのは `apuif_process_mix` (`components/apu_emu/src/apu_if_linux.c` /
  `apu_if.cpp`)。両インスタンスを別々に `apu_process` してから
  **単純加算 + int16 クリップ**で合成する
  (コード中のコメントは "average" だが、実際の演算は加算である。
  `mixed = main[i] + sub[i]` の後にクリップ)。

### 奪い合う組み合わせ (注意点)

- **NSF 再生と FMSQ instance=0 は MAIN を共有する**。`audio_task_fmsq_play_slot` は
  instance=0 のとき、再生中の NSF を明示的に停止する。
- **note_on/off と FMSQ instance=1 は SUB を共有する**。こちらは停止処理が無いので、
  SUB で FMSQ を鳴らしながら `note_on` を撃つと、同じ APU の同じレジスタを
  奪い合う (後から書いたほうが勝つ)。
- したがって MIDI の実時間演奏は **SUB を占有する前提**で設計するのが素直。
  BGM は MAIN (FMSQ instance=0) に置く。

### 設計への影響

1. **APU transport は note_on/note_off 経路 = SUB に載る**。BGM (MAIN) と両立する。
   README 方向B の「BGM + 実時間演奏」は成立する。
2. **チャンネル割り当て表は SUB の 4 声に対して作ればよい**。MAIN の使用状況を
   気にする必要はない。
3. **音量はクリップに注意**。加算合成なので、BGM と演奏が両方大音量だと歪む。
   APU transport 側のベロシティ変換に上限を設けるか、BGM 側を下げる運用が要る。
4. `note_on` の引数は音源に直結した形をしている (`apu_helper.c`)。
   - pulse: `freq` は **Hz** (内部で `CPU/(16*freq)-1` へ変換)、`duty` 0-3、
     `sweep` は `$4001`/`$4005` の生値、音量は定値音量 (envelope 無効)。
   - triangle: `freq` は Hz (32 分周)。`note_off` は `$4015` のビットを落とす。
   - **noise だけ引数の意味が違う**。`freq` の下位 4bit が period、bit7 が
     短周期モードのフラグとして使われる (`audio_task_note_on` が
     `apu_noise_note_on(freq & 0x0F, (freq & 0x80) ? 1 : 0, volume)` と呼ぶ)。
     APU transport でドラムを鳴らすときはこの変換規則に合わせる。

### 実測による追認 (sim)

コードから導いた結論を、実際に音を採って確かめた。sim の音声出力は
共有メモリのリングに書かれるので、**ヘッドレスでも波形を読める**
(そのための道具として `tools/fmrb_audio_probe.rb` を追加した)。

| 鳴らしたもの | ピーク振幅 | 平均 RMS | 音のある窓 |
|---|---:|---:|---:|
| 無音 (待機中) | 0 | 0.0 | 0/12 |
| FMSQ の BGM のみ (MAIN) | 3,072 | 2,477.8 | 40/40 |
| note_on のみ (SUB) | 11,520 | 1,987.4 | 20/30 |
| **両方同時** | 11,264 | **3,337.3** | **50/50** |

同時に鳴らしたときの平均 RMS が単独のどちらよりも大きく、かつ全窓に音がある
(note_on 単独では音の切れ目があった窓が、BGM で埋まっている)。
**加算合成されており、声の奪い合いは起きていない**。構造から導いた結論と一致する。

### 未確認

- 実機 (S3 + WROVER) での追認。コードは共通 (`audio_task.c`、ESP32 側は
  `apu_if.cpp`) なので同じ挙動になるはずだが、実機は未接続のため未確認。

## P0-4: gem 追加後の flash サイズ見積り

### 何を判断するためか

P2 で `picoruby-midi` 群を入れたとき、S3 の app パーティションに収まるか。
収まらないならパーティション変更 (フル書き込みが必要) を先に決める必要がある。

### 測り方

**実際には入れずに**、gem の中身を個別に測って足した。

- **Ruby 部分 (mrblib)**: ホストの `mrbc`
  (`components/picoruby-esp32/picoruby/build/host/bin/mrbc`) で各 gem の
  `mrblib/*.rb` をバイトコードに落とし、サイズを合計した。**実測値**である。
- **C 部分**: OS 非依存の 3 ファイルを ESP-IDF イメージの
  `xtensa-esp32s3-elf-gcc -Os` でコンパイルして `.text + .rodata + .literal`
  を測り (601 行 -> 2228 バイト = 3.7 バイト/行)、残りは行数から比例で概算した。
  バインディングや ESP-IDF 呼び出しを含む部分は密度が上がるので 6-7 バイト/行
  を当てている。**ここは概算**。

### 結果

| gem | Ruby バイトコード (実測) | C 概算 | 小計 |
|---|---:|---:|---:|
| picoruby-midi | 18.2 KB | 約 10.5 KB | 約 28.7 KB |
| picoruby-midi-mml | 10.9 KB | 0 | 10.9 KB |
| picoruby-uart_midi | 1.2 KB | 約 2.2 KB | 約 3.4 KB |
| picoruby-sam2695 | 1.3 KB | 0 | 1.3 KB |
| **UART 経路の合計 (P2 + P5 相当)** | **31.6 KB** | **約 12.7 KB** | **約 44 KB** |
| picoruby-usb_midi_host (P7 で追加) | 0.9 KB | 約 8 KB | 約 9 KB |

これに APU transport (新規、小さい) と Ruby 側の `FmrbMidi` 層が乗るので、
**P2 + P5 で 45-50 KB、P7 まで入れて 55-60 KB** と見ておけばよい。

### 結論: flash は P2 の制約にならない

ただし**残量の記録が食い違っている**ので、実測での確認を勧める。

- `doc/midi/README.md` と作業指示書は「app パーティション 4M で残り 24%
  (約 1MB)」としている。
- `doc/reference/internal_ram_budget.md` の 2026-08-03 節は「app パーティション残が
  22% -> **6% (約 200 KB)**」と書いている。
- `config/partitions_n16r8.csv` のコメントは「factory は 3M だったが
  networking gem で溢れたので 4M にした。4M で約 1MB の余裕が戻る」とある。

順序から見て、6% は 3M 時代の値、24% は 4M にした後の値と思われる
(3M で残 200KB + 1MB = 約 1.2MB = 4M の約 30%、README の 24% と近い)。
**どちらであっても 60 KB は入る**ので P2 は進められるが、200 KB 側が正なら
余裕は 3 分の 1 以下になるため、gem を入れた直後にイメージサイズを実測する
(README の「3. 先に潰すべき制約」の指示どおり)。

現作業ツリーには app のイメージ (`build/fmruby-core.bin`) が無く、
サイズの直接確認はできなかった。

## P0-5: MML 方言の差分表

### 何を判断するためか

方向D (MML 共通化) で、片方に寄せられるのか、中間表現を挟む必要があるのか。

### 材料

- Family mruby BASIC: `components/basic/core/basic_mml.cpp` (実装を読んだ)。
- picoruby-midi-mml: `tmp/midori/mrbgems/picoruby-midi-mml/`
  (**作業指示書は「Midori のソースはこのマシンに無い」としていたが、
  ユーザが clone 済みで実在した**ので、README ではなく実装を読んだ)。

### 差分表

| 項目 | BASIC の PLAY | picoruby-midi-mml |
|---|---|---|
| 音名 | 大文字 `CDEFGAB` | 小文字 `cdefgab` (大小どちらでも可) |
| 変化記号 | **音名の前** `#C`。フラット無し | **音名の後** `c+` `c#` `c-` |
| 休符 | `R` | `r` |
| 音長 | 音名の後の 1 桁が**長さコード** (0-9)。コード -> 4 分音符の 1/8 単位で `[1,2,3,4,6,8,12,16,24,32]`。既定はコード 5 (= 4 分音符) | 音名の後の数値が**分母** (`c8` = 8 分音符)。`l<n>` で既定長。既定は `l4` |
| 付点 | 無し | `.` (複数可、半分ずつ加算) |
| タイ | 無し | `&` |
| 繰り返し | 無し | `[ ... ]<n>` (n 省略時 2) |
| テンポ | `T1`-`T8` の**番号**。フレーム数 = 15*T/2 なので `T4` = 4 分音符 30 フレーム = 0.5 秒。**T が大きいほど遅い** | `t<n>` は解析するが**無視**。BPM は `MIDI.start!` が持つ |
| オクターブ | `O0`-`O5`。**`O3` の C が中央ハ (C4)** | `o1`-`o8`、既定 `o4`。**`o4` の c が中央ハ (60)**。`<` `>` で上下 |
| 音量 | `V0`-`V15` (APU の音量レジスタそのもの) | `v0`-`v127` (MIDI ベロシティ) |
| 音色 | `Y0`-`Y3` (デューティ)、`M0`/`M1` (エンベロープ) | 無し (音色は音源側の Program Change) |
| 複数声 | 1 つの文字列を `:` で区切って最大 3 声 (pulse1 / pulse2 / triangle) | 文字列では区切らない。`Sequence` を複数作って `CombinedPlayer` に足す |
| 出力先 | FMSQ に事前変換 (フレーム駆動) | 実時間で MIDI イベントを送出 (PPQ = 24) |
| 空白・未知の文字 | 無視 | 無視 |

### 結論: 片方に寄せるのは無理。中間表現を挟むしかない

同じ字面で意味が違う箇所が 2 つあり、しかも**どちらも黙って音がずれる**種類の
非互換である。

1. **音長の意味が違う**。`C4` は BASIC ではコード 4 (= 4 分音符の 6/8 =
   付点 8 分音符相当)、picoruby では 4 分音符。同じ文字列が別の長さになる。
2. **オクターブの基準が 1 つずれている**。中央ハは BASIC が `O3`、
   picoruby が `o4`。

したがって README 方向D の「中間イベント列を定義して前後を分ける」案が妥当で、
**前段 (方言パーサ) を 2 つ持ち、後段 (FMSQ 書き出し / MIDI 送出) を共有する**
のが素直な形になる。共通化の利得は後段と、音高・音長の計算部分に出る。

なお BASIC 側の記法は Family BASIC 互換のために動かせないので、
**寄せるとしたら picoruby 側に BASIC 方言のパーサを足す方向**になる。

### 未確認

- picoruby-midi-mml の `t` を「無視」と書いたのは実装 (`midi_mml.rb`) と
  README の両方の記述による。**BPM を外から与える前提の設計**なので、
  FMSQ に落とす用途では別途テンポの持ち主を決める必要がある。
- BASIC 側の `T` の絶対値 (T4 = 0.5 秒) は実装値であり、実機の
  Family BASIC との絶対一致は未確定のまま (`doc/fmrb_basic/known_differences.md`
  の扱いと同じ)。
