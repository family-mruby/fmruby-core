# P2 報告書: MIDI 中核層 + APU transport

対象: `doc/midi/work_order_p2.md`。
前提: [README.md](../README.md)、[p0.md](p0.md)、[p1.md](p1.md)。

ゴール (アプリから `MIDI::Device` 経由で内蔵 APU が鳴る) は達成した。
sim で音階・和音・打楽器・BGM との同時再生を波形で確認している。

アプリから見た形は Midori と同じ:

```ruby
device = FmrbMidi.device(self)      # FmrbApp の中で
device.note_on(60, 100)             # channel: 0 が既定
device.note_off(60)
device.trigger(36, 110, duration: 90, channel: 9)
```

## 2. 判断したこと

### 2.1 `trigger` の扱い: (b) Ruby で同等品を書いた

作業指示書 2 章の選択肢のうち **(b)** を選んだ。`MIDI._trigger` /
`MIDI._send_batch` を Ruby で実装し、**取り込んだ gem を改変せずに**
`device.trigger` / `trigger_batch` が動くようにした。

- (a) 未対応にすると `device.trigger` が `NoMethodError` になる。Midori 向けに
  書かれたコードをそのまま動かしたい (指示書 1 章) という前提と噛み合わない。
- (c) C 移植は、まず Ruby で様子を見るという方針と逆行する。
- 実装は「note_on を送り、`Machine.board_millis` で期限を覚えておき、
  期限が来たら note_off を送る」だけ。**C 版と違い、誰かが定期的に叩かないと
  note_off が出ない**。叩く口は 2 つ:
  - `FmrbMidi.tick` — アプリの `on_update` から呼ぶ。
  - transport への送信そのもの (`send_packet` の先頭で必ず走る)。

**精度は叩く間隔で決まる**。実際に打楽器で問題になった: `on_update` が
180ms 間隔だと `duration: 90` の音が 180ms 鳴り、隙間が消えた。そのため
`FmrbMidi.tick_delay(希望の待ち時間)` を用意し、**次の note_off の期限と
希望値の小さいほうを返す**ようにした。

ただしこれだけでは足りない。**早起きした分でシーケンスまで進めてしまう**と
曲が速くなる (デモで実際にそうなった)。アプリ側は「次の音を出す時刻」を
自分で持ち、叩くために早起きしたときは進めないようにする:

```ruby
def on_update
  FmrbMidi.tick                       # 期限の来た note_off を出す
  now = Machine.board_millis
  if @mode && now >= @next_at         # 進めるのは時刻が来たときだけ
    @next_at = now + step
  end
  FmrbMidi.tick_delay(@next_at - Machine.board_millis)
end
```

この形にして打楽器 8 発が分離した (5.2 の波形)。
**Ruby で予約を持つ以上、この 2 つの時計を分ける必要がある**というのが
今回の教訓で、C に降ろせば呼び出し規約ごと消える。

### 2.2 gem の取り込み方: 無改変 + ファクトリは別 gem

`picoruby-midi` の `mrblib/midi_constants.rb` と `mrblib/midi_device.rb` を
**1 バイトも変えずに**取り込んだ。改変一覧は 3 章のとおり (= 空)。

`mrblib/midi.rb` は**取り込まなかった**。中身は
`MIDI.usb_host_device` / `MIDI.sam2695_device` / `MIDI.input` / `MIDI.clock` の
4 つのファクトリだけで、いずれも Family mruby に無い transport とクラスを
指す。**そこに APU 用のファクトリを足すと gem を改変することになる**ので、
`FmrbMidi.device(app)` として自前の gem 側に置いた。`MIDI::Device.new(transport)`
を直接使う道も当然使える。

`midi_clock.rb` (C タイマ依存) と `midi_input.rb` (C 受信タスク依存) も
取り込んでいない。今回は送信専用。

### 2.3 所有権: 当面はアプリ持ち、後勝ち

指示書 3.3 のとおり `FmrbAudio` 経由なので、既存の音の所有権の枠組みに乗る。
**2 つのアプリが同時に MIDI を鳴らすと、後から鳴らしたほうが勝つ**
(APU のレジスタを直接上書きするため)。排他は入れていない。

さらに 2 点、実際に踏んだので書いておく:

- **transport は SUB インスタンスを占有する前提**である。`FmrbAudio#note_on` が
  SUB 固定 (p0.md の P0-2) なので、FMSQ を `play_slot(instance: 1)` で
  鳴らすと奪い合う。BGM は MAIN (instance 0) に置くこと。
- **アプリが異常終了すると音が鳴りっぱなしになる**。`on_destroy` は
  `all_off` を呼ぶが、例外で落ちた場合はそこを通らない。sim で実際に
  D4 が鳴り続けたまま残った。アプリ終了時に kernel 側で SUB を黙らせる
  のが本筋だが、P2 の範囲外として申し送る。

### 2.4 音高テーブル (P1 との一致のため)

**実時間側と事前変換側で音高がずれる**という、指示書 4 章が警告していた
不一致が実際に起きるので、テーブルで潰した。

- 事前変換 (`smf2fmsq.rb`) は APU タイマを**四捨五入**で直接書く。
- 実時間側は `FmrbAudio#note_on` に **Hz** を渡し、音声側が
  `timer = CPU / (16 * freq) - 1` と**整数除算**で求める (`apu_helper.c`)。

素直に `round(440 * 2**((n-69)/12.0))` を渡すと、この 2 つが別のタイマに
着地する。C2-C7 で平均 6.5 セント、最悪 30.6 セントずれる。さらに低音では
タイマが 11bit を超えて**マスクされ、まったく違う高さで鳴る**。

そこで **「事前変換側と同じタイマに着地する整数 Hz」を音ごとに選んだ表**を
持たせた (`tool/midi/gen_apu_note_table.rb` で生成)。結果:

| | 平均 | 最悪 |
|---|---:|---:|
| 素直に Hz を丸める | 6.5 セント | 30.6 セント |
| **本実装のテーブル** | **2.0 セント** | **10.1 セント** |

残差は「1 Hz 刻みがタイマ 1 段より粗い低音域」で出るもので、原理的に
消せない (C2 で 1 Hz ≒ 10 セント、C6 では 1 セント未満)。61 音中 38 音は
**完全一致**する。11bit を超えるタイマは 1 つも出ない (テストで担保)。

### 2.5 チャンネル割り当てと写像

既定は README 方向B のとおり。**`MIDI::Device` の channel は 0 起点**なので、
音楽で言う 1/2/3/10 番はコード上 0/1/2/9 になる。

| MIDI ch (0 起点) | APU 声 |
|---|---|
| 0 | 矩形波 1 |
| 1 | 矩形波 2 |
| 2 | 三角波 |
| 9 | ノイズ (GM 打楽器) |

- `transport.map_channel(ch, :pulse1 / :pulse2 / :triangle / :noise / nil)` で
  実行時に差し替えられる (P1 の `--map` 相当)。割り当ての無い ch は捨てる。
- 和音・音量・打楽器・声の奪い方 (後着優先 + 復帰) は **P1 の変換器と同じ規則**。
- 反映する Control Change は 3 つだけ: CC7 (音量)、CC70 (デューティ 0-3)、
  CC120/123 (消音)。Program Change とピッチベンドは受け取って捨てる
  (APU に音色もピッチホイールも無い)。

## 3. 取り込んだ gem への改変

**無し**。`mrbgem.rake` / `midi_constants.rb` / `midi_device.rb` は
Midori の内容と md5 一致。取り込みの経緯と、取り込まなかったファイルの
理由は `lib/add/picoruby-midi/FAMILY_MRUBY_PORT.md` に置いた。

ただし upstream に返す価値のある発見が 1 つある:

- **`MIDI::Device#pitch_bend` はこのビルドでは動かない**。
  `(value + 8192).clamp(0, 16383)` の `clamp` が `mruby-comparable-ext` の
  メソッドで、Family mruby のビルドには含まれていない。実際に呼ぶと
  `NoMethodError: undefined method 'clamp' for Integer` になる (sim で確認)。
  `clamp` を使わない書き方に直せば、小さい mruby ビルドでも動くようになる。
  **Midori 側に返す候補**。
- 同様に `Integer#zero?` / `#positive?` (`mruby-numeric-ext`) も無い。
  取り込んだ 2 ファイルは使っていないので今回は影響しないが、
  gem を増やすときに引っかかる。

## 4. 見つけた不具合 (P2 の作業中に判明)

### 4.1 sim の APU で「同時に複数の声が鳴らない」 (修正済み)

**症状**: MIDI で和音を鳴らすと、最後に鳴らした 1 声しか出ない。

**原因**: `fmruby-graphics-audio/components/apu_emu/src/apu_if_linux.c` の
`apuif_read_reg` が**選択中のインスタンスではなく main から読んでいた**。
`apuif_write_reg` は書き込み後に必ず main をアクティブに戻すため、
read は常に main を見ていた。`apu_helper.c` は

```c
apuif_write_reg(0x4015, apuif_read_reg(0x4015) | status_bit);
```

と read-modify-write でチャンネル有効ビットを立てるので、**sub の
有効ビットが main の値で作り直され、直前まで鳴っていた声が消えていた**。

**1 声ずつ鳴らす限り正常に見える**ため、効果音用途だった今までは表に出て
いなかった。MIDI で和音を鳴らして初めて露出した。

**修正**: `apuif_read_reg` を write と対称にし、選択中のインスタンスから
読むようにした。ESP32 版 (`apu_if.cpp`) と P4 版 (`apu_if_p4.c`) は
**元から正しく**、Linux 版だけの問題だった。修正後、和音の 3 声が
同時に出ることを波形で確認 (5.2)。

### 4.2 transport が「アプリ自身」を音声オブジェクトと誤認 (修正済み)

`ApuTransport.new(owner)` が `owner.respond_to?(:note_on)` で
FmrbAudio かどうかを見分けていた。ところが**アプリが自前の `note_on` を
持っていると一致してしまい**、アプリ自身に音声コマンドを送りにいって
`ArgumentError` で落ちた (計測アプリで実際に発生)。MIDI を扱うアプリほど
`note_on` という名前を使いがちなので、罠として致命的だった。
`owner.is_a?(FmrbAudio)` に変更した。

### 4.3 `tools/fmrb_audio_probe.rb` のオフセット誤り (修正済み)

P1 で追加した音声プローブが、共有メモリ構造体のパディングを 1 バイト
多く見積もっていて、リングの読み出し位置が 2 バイトずれていた。音の
有無 (ピーク / RMS) の判定は正しかったが、**取得サンプル数と秒数が
過大**になっていた (実時間の約 4 倍)。構造体末尾からオフセットを逆算する
形に変え、パディングの推測をやめた。p0.md / p1.md に載っている
ピークと RMS の結論は影響を受けない (秒数は載せていない)。

## 5. 検証結果

### 5.1 ホストでの単体テスト

`ruby tool/midi/test/transport_test.rb` = **28 項目すべて成功**。
`FmrbAudio` を差し替えた状態で Ruby 層だけを動かすので、ビルドも sim も
要らない。チャンネル割り当て / 音量変換 / 後着優先と復帰 / 和音 /
打楽器 / CC / `trigger` の予約と発火、そして**事前変換側とのタイマ一致**を
見ている。期待値は APU の式から別途計算しており、実装をそのまま
使ってはいない。

### 5.2 sim での音 (波形)

すべて `tools/fmrb_audio_probe.rb` で共有メモリから採取した実際の音。

**和音** (C4 = 矩形波1、E4 = 矩形波2、G4 = 三角波を同時):

| 成分 | 4.1 の修正前 | 修正後 |
|---|---:|---:|
| C4 261 Hz | 0.0001 | **0.0586** |
| E4 330 Hz | 0.0012 | **0.0494** |
| G4 392 Hz | 0.0619 | **0.0415** |

修正前は三角波 (最後に鳴らした声) しか出ておらず、矩形波 2 声が
消えていた。

**打楽器** (`device.trigger` で 8 発、20ms ごとの音量。`#` が鳴っている区間):

```
######....#######...#######....######....######....#######...#######....######
```

8 発が分離している。2.1 の対策前は 1 つの塊になっていた。

**BGM (FMSQ) と MIDI の同時再生** (完了条件 2):

| 状態 | ピーク | 平均 RMS | 音のある窓 |
|---|---:|---:|---:|
| BGM のみ | 6,400 | 3,161 | 30/30 |
| BGM + MIDI 音階 | **9,472** | **3,969** | **119/119** |

同時再生時のピークと RMS が BGM 単独より大きく、かつ音階の各音が
期待周波数の位置に出ている (C4 0.043 / D4 0.046 / E4 0.047 / F4 0.052 /
G4 0.047 / A4 0.051)。**P0-2 の結論 (MAIN と SUB は加算合成) が
実際の経路でも成立**。

### 5.3 P1 の変換器との一致 (完了条件 3)

同じ音階を、事前変換 (FMSQ) と実時間 (MIDI) の両経路で鳴らして実測した。

| 音 | P1: FMSQ 経路 | P2: MIDI 経路 | 差 |
|---|---:|---:|---:|
| C4 | 261.35 Hz | 261.35 Hz | 0.0 セント |
| D4 | 293.58 Hz | 293.58 Hz | 0.0 |
| E4 | 330.15 Hz | 330.81 Hz | +3.5 |
| F4 | 349.62 Hz | 349.62 Hz | 0.0 |
| G4 | 392.35 Hz | 392.37 Hz | +0.1 |
| A4 | 440.63 Hz | 440.51 Hz | -0.5 |
| B4 | 494.91 Hz | 494.91 Hz | 0.0 |
| C5 | 522.69 Hz | 523.13 Hz | +1.5 |

4 音は完全一致、残りも 3.5 セント以内。**テーブル上は 8 音すべてが同じ
タイマに着地する**ことをホストのテストで確認しているので、この差は
sim の音声取得 (リングが埋まるとサンプルが落ちる) による測定のばらつきで

(D4 と B4 は測り直しで一致、E4 は再現)。

音の長さはアプリが決めるものなので比較していない (P1 の 0.375 秒に対し、
デモは 200ms + 60ms の休みで鳴らしている)。

## 6. 計測の準備 (指示書 5 章)

**受信側の計装を入れた。実機が繋がれば数字が採れる状態**である。

- 位置: `fmruby-graphics-audio/main/audio/audio_latency.{h,c}` (新規)。
  comm 層 (`comm_socket_server.c` / `comm_uart_slave.c` / `comm_spi_slave.c`)
  がフレーム復号時に `message_data_t.rx_us` へ時刻を打ち、
  `message_handler_task.c` が note_on / note_off の処理後に差分を記録する。
- 出す形は core 側の入力遅延統計に倣った:

```
audio_note_lat: n=1124 on=924 avg_us=317 max_us=1178 sum_ms=357 ge1=282 ge5=0
```

  n は窓内の note コマンド数、on はうち note_on、ge1 / ge5 は 1ms / 5ms
  以上かかった件数。1000 件たまるか、バーストが途切れた時点で出る
  (最短 2 秒間隔)。

- 上の数字は **sim で実際に採れたもの**である。負荷で大きく変わる:

  | 状況 | n | 平均 | 最大 | 1ms 超 |
  |---|---:|---:|---:|---:|
  | 演奏程度の頻度 | 15 | 36 us | 93 us | 0 |
  | 全速のバースト | 1,279 | 300 us | 1.10 ms | 314 |

  詰めて送るとキューで待つぶん平均が 1 桁上がるが、5ms を超えたものは
  一度も無かった。実機の数字は P5 で採る。
- **この計装が見ているのは「graphics-audio に届いてから APU に書くまで」**
  である。アプリ VM から link を渡るまでの時間は含まない。

### 送出側のコスト (MIDI 層のオーバーヘッド)

P0-1 の計測アプリに MIDI 経路の case を足して比べた
(`tool/midi/test/sim_play/audio_bench.app.rb`、200 回ずつ、sim):

| 呼び方 | 1 回あたり | 換算レート |
|---|---:|---:|
| `FmrbAudio#note_on` (素) | 125 us | 8,000/s |
| **`MIDI::Device#note_on`** | **145 us** | 6,896/s |
| `FmrbAudio` note_on + note_off | 220 us | 4,545/s |
| **`MIDI::Device` note_on + note_off** | **255 us** | 3,921/s |

**Ruby の transport 層が乗せているのは 1 音あたり約 20us** (16%) である。
MIDI が必要とするイベント数 (密な曲でも 50-200/s) とは 1 桁以上の開きが
あるので、**「まず Ruby で書く」という判断は成立している**。C に降ろす
理由が出るとすれば速度ではなく、2.1 の予約の精度のほうである。

## 7. 申し送り

- **`trigger` の精度はアプリの叩く間隔で決まる**。`FmrbMidi.tick_delay` を
  使えば期限に合わせて起きられるが、C タイマのような独立性は無い。
  多声の打楽器を詰めて鳴らす用途が出てきたら C に降ろす判断をする。
- **異常終了したアプリの音が残る** (2.3)。kernel 側での後始末が要る。
- **`MIDI::Clock` / `MIDI::Input` は未取り込み**。外部同期と受信は P5 以降。
- **ピッチベンドは 2 重に効かない**: transport が捨てるうえ、
  `MIDI::Device#pitch_bend` 自体がこのビルドで動かない (3 章)。
- **2 つのアプリが同時に鳴らすと後勝ち**。排他が要ると分かった時点で
  kernel 側へ持ち上げる。
- P4 (Modern) では未確認。`apu_if_p4.c` は 4.1 の問題を持たないので、
  そのまま動く見込みだが、実機確認は P5 と同じセッションで行う。
