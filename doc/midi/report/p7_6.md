# P7.6 報告書: 演奏時刻の権威を C へ

対象: `doc/midi/work_order_p7_6.md`。
前提: [p7.md](p7.md) 9 章 (実機実測)、[p7_5.md](p7_5.md)。

**Ruby は作曲家に徹し、時計係を降りた**。プレーヤは数百 ms 先まで復号して
「時刻つきの確定済みコマンド」を C のリングに積み、C のタイマーが時刻どおりに
発射する。sim の実測で、**線上に出る音符の間隔のばらつきが 12.5 ms から
0.05 ms へ (2 桁以上) 縮んだ**。

## 0. 結論だけ先に

sim、serial 出力、scale.mid (0.5 秒間隔の 8 音)、モニタのタイムスタンプ実測:

| | 音符間隔の標準偏差 | 最悪 | 平均ずれ |
|---|---|---|---|
| 変更前 (アプリのタスクが送る) | **12.5 ms** | +19.9 ms | -2.71 ms |
| 変更後 (C のタイマーが送る) | **0.05 ms** | +0.10 ms | +0.00 ms |

同じ実行での C 側の発射遅れ: **平均 67〜607us / 最大 104us〜1.5ms** (4 回の
測定)、アンダーラン 0、取りこぼし 0。**目標 (avg <= 2ms / max <= 5ms) を
sim では満たしている**。実機の数字はユーザが焼いて採る (5 章)。

| 壊していないこと | 確認 |
|---|---|
| 1 イベントあたりの割り当て 0 個 | bench 実測 (4.3) |
| P7.5 の声グループ (最終状態一致) | ホスト A/B で 0 differ を維持 (4.2) |
| 既存テスト | 139 -> **143 項目**、全通過 |

## 1. 形

```
Ruby (SmfPlayer -> transport)
  300 ms 先まで復号し、声を解決し、
  「due_us つきの確定済みコマンド」を積む
C (fmrb_midi_sched.c、128 スロットのリング)
  時刻が来たら発射。mruby には一切入らない
    APU    -> fmrb_app_send_audio_note()  (P7 で C 化した msgpack 組み立て)
    serial -> fmrb_midi_serial_write()
```

- **キューが運ぶのは MIDI イベントではなく確定済みコマンド**。和音の解決も
  声の割り当ても折り返しも Ruby 側・積む時点で終わっている。C は
  「時刻どおりに発射するだけの装置」で、音楽的な判断は 1 行も無い。
- エントリは 16 バイト固定 (due_us 8 + kind 1 + pid 1 + payload 6)。
  128 スロットで 2 KB、静的確保。**mruby オブジェクトは一切通らない**
  (積む API は整数だけの位置引数)。
- **タイマーコールバックから mruby に入らない** (指示書 1.2 の絶対条件)。
  発射は C で完結する。

### 1.1 積む単位は「瞬間」

P7.5 で入れた声グループの区切りが、そのまま時刻の単位になった。

- P7.5: グループ = 「1 回の `tick` で配った分」
- P7.6: グループ = **1 つの楽譜上の瞬間** (`due_us` が同じイベント)

先読みすると 1 回の `tick` が数百 ms 分・複数の瞬間を積むので、区切りを
瞬間ごとに細かくする必要があった。`defer_voices(due_us)` が時刻を受け取り、
`flush_voices` で解決した最終形をその時刻で積む。**P7.5 の正しさは
そのまま**で、解決の結果が「今送る」から「その時刻に送る」に変わっただけ
である (4.2 で検証)。

## 2. 判断したこと (指示書 2)

### 2.1 タイマーの実体: ESP32 は esp_timer、sim は専用タスク

**ESP-IDF の linux ターゲットには esp_timer の実装が無い**。調べた事実:
`components/esp_timer/CMakeLists.txt` は `if(${target} STREQUAL "linux")` の
分岐で **`INCLUDE_DIRS include` だけを登録**しており、ソースを 1 つも
コンパイルしない (ヘッダはあるがリンクできない)。本体側の
`fmrb_hal_time.c` が linux で `gettimeofday` を使っているのもこれが理由。

したがって「同じ実体」は選べない。選んだのは:

| | 起床の仕組み | 理由 |
|---|---|---|
| ESP32 | `esp_timer` one-shot、発射のたびに再武装 | 指示書の調査どおり、**新規スタック消費ゼロ** (タスクは既存)、priority 22 で全 Ruby タスクより上、core 0 固定でアプリ (core 1) と別コア |
| sim | 専用タスク (prio 20、スタック 4 KB) | POSIX タイマーは使えない (FreeRTOS シミュレータが SIGALRM で自分のスケジューラを回している。mruby-task の posix port を外したのと同じ理由) |

**違うのは起床の仕組みだけ**で、リング・順序・発射・統計は同じ `fire_due()`
を通る。sim で論理と相対的な改善を確かめ、絶対精度は実機で採る、という
分担になる。内蔵 RAM を 2 KB 使う専用タスク案を実機側で採らなかったのは、
`doc/reference/internal_ram_budget.md` のとおり内蔵 RAM が最も逼迫した資源だからである。

### 2.2 先読み 300 ms

- アプリ側の遅れは実機で数十 ms (p7.md 9 章の `max_late` 71 ms)。その
  **約 10 倍**を確保しておけば、通常の遅れは音に出ない。
- 停止・曲替えは「キューを捨てて積み直す」ので、深さがそのまま反応の
  悪さになる。300 ms なら停止は即時に感じられる。
- 実測のキュー深さ高水位は **2〜4 エントリ** (The Entertainer で 4)。
  128 スロットに対して余裕が大きい。深さは音符密度で決まるので、
  もっと密な曲でも桁は変わらない。

### 2.3 アンダーランは「遅れてよいが壊れない」

Ruby の積み直しが間に合わずキューが涸れたら、音は遅れる。壊れないことだけ
保証し、**回数を数える** (`under=` として 5 秒ログに出る)。判定は
「5 ms 以上遅れて積まれ、かつそのときキューが空だった」。5 ms の閾値は、
曲の最初の瞬間が定義上「今」due であることを誤検出しないためである。

### 2.4 テンポ変更はキューを捨てない (指示書 1.4 からの逸脱)

指示書は「停止・テンポ変更・シークはクリアして積み直し」としているが、
**テンポ変更だけは捨てない**ことにした。捨てると、積んであった 300 ms 分の
音楽が失われて**穴が開く**。捨てなければ、新しいテンポは 300 ms 後から
効き始める — つまり**ユーザから見て 0.3 秒遅れて効くが、音は途切れない**。
0.3 秒の遅れは操作の応答としては知覚の境目、穴は確実に聞こえるので、
後者を避けた。

停止・一時停止・曲替え・出力先変更は指示書どおり**キューを捨てる**。

### 2.5 消し方の順序 (指示書 1.4 の「鳴っている音をどう保証するか」)

**捨てたキューには、鳴っている音を止めるはずだった note off が入っている**。
だから捨てる側が代わりに黙らせなければならない。

- `stop` は **先にキューを捨て、後から note off を送る**。逆にすると、
  捨て損ねた note on が note off の後に発射されて音が残る。
- アプリが死んだ場合は VM の終了時 (gem finalizer) に**そのアプリの
  コマンドだけ**をリングから抜く (`clear_pid`)。他のアプリが同時に鳴らして
  いても巻き添えにしない。
- **`clear_pid` 自身が黙らせる**。APU のコマンドを捨てたら 4 声に note off
  を、serial のコマンドを捨てたら 16 チャンネルに all notes off を、
  C から直接送る。理由は 4.4 (これが無いと実際に音が残った)。

### 2.6 曲の時計は「最初の tick」で合わせる

`start` の時点ではなく、**最初に `tick` が来た時刻**を曲の原点にする。
アプリが `start` の直後に画面を描くと (デモアプリの `draw` は sim で
約 90 ms)、その間に曲の時間が進んでしまい、最初の数音が生まれた瞬間から
遅れる。実測でそれが `max_late=96 ms` として出たので直した。

## 4. 検証

### 4.1 sim: 線上の音符間隔 (指示書 6-1)

`flash/app/debug/midi_time.app.rb` が scale.mid を 2 回鳴らす。1 回目は
先読みあり、2 回目は `lookahead_us = 0` で従来の経路。ホスト側は
`tools/fmrb_midi_monitor.rb --log` が全バイトに時刻を付けて記録し、
`tool/midi/midi_interval.rb` が間隔のばらつきを出す。

```
run 1:  8 notes  gap 500.0 ms  error mean +0.00 ms  sd 0.05 ms  worst +0.10 ms
run 2:  8 notes  gap 497.3 ms  error mean -2.71 ms  sd 12.54 ms  worst +19.90 ms
```

**同じ曲・同じ実行・同じ計測系での前後比較**である。4 回測った内訳:

| 測定 | run 1 (積む) の sd | run 2 (自分で送る) の sd | 比 |
|---|---|---|---|
| 1 | 0.10 ms | 6.83 ms | 69x |
| 2 | 0.10 ms | 6.45 ms | 65x |
| 3 | 0.05 ms | 12.54 ms | 235x |
| 4 | 0.06 ms | 0.66 ms | 10x |

**読み方**: run 1 は毎回 0.05〜0.10 ms に収まる。run 2 は 0.7〜12.5 ms と
大きく揺れる — ホストが暇なときは良く、混んでいるときは悪い。それが
まさに本段の主張である: **アプリのタスクが送っている限り、拍は
システムの都合を拾う**。C のタイマーに移すと拾わなくなる。

### 4.2 P7.5 の声グループが生き残っているか (指示書 4)

解決の場所が「tick 境界」から「積む時点」に動いたので、p7_5 の A/B を
**同じ枠組みで再実行**した。ホストには C のキューが無いので、**積み先を
偽物に差し替えて**記録する (`FakeSched`)。

```
every instant ends on the same note it used to (0 of 988 instants differ)
the writes it drops are the ones nobody could hear (2898 writes to the APU became 988)
the filed commands are the ones the immediate path plays (988 commands identical)
due times never go backwards (0 out of order)
the song is filed ahead of itself, not on the beat (180 s of music filed)
```

**積まれたコマンド列が、その場で送る経路の出力と 1 個ずつ一致する**
(末尾は先読みのぶん最大 8 個だけ先行する)。P7.5 の性質は移動しても
変わっていない。

なお p7_5.md の「1517 -> 500」は 90 秒で打ち切った計測で、今回テストの
上限を曲の最後まで伸ばしたので数字は 2898 -> 988 になった。比率
(約 3 分の 1) は同じである。

### 4.3 割り当て 0 の維持 (指示書 4)

bench アプリの alloc 計測で、**積む経路も 0 個/イベント**である。

```
play: 0 objects/10 events (4 over 303)      プレーヤ本体
alloc apu grouped chord (6 events):  16/100 その場で送る経路 (P7.5)
alloc apu scheduled chord (6 events): 16/100 積む経路 (P7.6)
sched stats after alloc: {pushed: 50, dropped: 0, depth_max: 50}
```

25 回の反復 (150 イベント) で 4 個、これは測定枠そのものの分で、
その場で送る経路とまったく同じ値である。積む API は整数だけの位置引数で、
C 側は静的リングに memcpy するだけだから当然ではあるが、**測って確かめた**。

### 4.4 停止・曲替え・kill で音が残らないか (指示書 6-3)

sim で、再生中に停止・kill を実行してから `tools/fmrb_audio_probe.rb` で
無音を確認した (`peak=0 sounding_windows=0`)。

**最初の実装では kill で音が残った**。probe が peak=5120 のまま鳴り続け、
アプリが 1 つも生きていないのに音楽が止まらない。順序を追うと:

1. アプリを kill -> kernel が「終了したアプリ」を掃除し、
   `silence_notes_for(pid)` で 4 声に note off を送る。
2. **その後で**、VM の終了処理 (gem finalizer) が走るまでのわずかな間に、
   キューに残っていた note on が発射される。
3. その note を止める note off は、同じ finalizer が捨てた。

つまり **kernel の掃除がキューの掃除より先に来る**と、掃除の後に鳴り始めた
音が永遠に残る。直し方は 2.5 のとおり、**キューを捨てる側が黙らせる**
こと。`clear_pid` は自分が捨てたコマンドの種類を見て、APU なら 4 声の
note off を、serial なら 16 チャンネルの all notes off を C から送る。
これなら**音を出しうる最後のコマンドより必ず後**に黙らせることになり、
kernel との順序に依存しない。

直した後の確認:

| 操作 | 結果 |
|---|---|
| 停止 (デモの「5 SMF」トグル) | `peak=0` |
| 再生中の kill | `peak=0`、kernel の `Silenced note voices left by pid=4` も出る |
| 曲替え / 出力先変更 | `load` と `device=` がキューを捨てる (同じ経路) |

## 5. 実機での確認手順

**計測ビルドで焼く** (p6.md 1.1 の ABI の罠に注意: `rake clean` では
足りず、`build/` ごと消してから焼くこと)。

```
cd fmruby-core
rm -rf build && rake clean_all
FMRB_GC_PROFILE=1 rake build:esp32
grep -c MRB_GC_PROFILE build/compile_commands.json   # 0 でないことを確認
FLASH_BAUD=115200 rake flash
python3 ../tools/fmrb_serial_capture.py -t 60 play.log
```

### 5.1 C 統計 (指示書 6-2 の本体)

SMF プレーヤかデモで曲を再生し、5 秒ごとの行を見る。

```
grep "events=" play.log
```

行の形はこうなる:

```
SmfPlayerApp: events=196 fired=56 avg_late=472us max_late=543us stalls=0
              under=0 q=2/4 drop=0/0 [gc ...]
```

- **目標は `avg_late <= 2000us` / `max_late <= 5000us`**。
  P7 実機の 17〜20 ms / 71 ms からの改善を、同じ曲で比べる。
- `under=` が増えるなら Ruby の積み直しが間に合っていない
  (先読みを深くするか、アプリ側の負荷を疑う)。
- `drop=A/B` の A はキュー満杯、B は送出失敗。**どちらも 0 のはず**。
- `q=いま/最大` が 100 に近づくなら先読みが深すぎる。

### 5.2 APU 経路は「発射 = 発音」ではない (指示書 3 の注意)

上の数字は**発射まで**である。APU はこの後 kernel -> UART リンク ->
WROVER を通るので、そこのジッタは別に出る。切り分けは:

- **serial 経路で測る**: 後段が無いので、C の統計がそのまま音の正確さ。
  「7 Out」で切り替えて同じ曲を鳴らし、Unit MIDI の音で聴く。
- **APU 経路で `audio_note_lat` を読む** (P2 で入れた受信側計装、実機
  未測定のまま):

  ```
  grep audio_note_lat play.log
  ```

  C の発射統計が良いのに APU の音が揺れるなら後段が犯人で、その場合の
  次の一手 (kernel を迂回して C から直接リンクへ) は**この数字を見てから**
  判断する。

### 5.3 音が残らないこと

再生中に Stop、曲替え、アプリの終了 (閉じるボタン)、`kill` を順に試す。
**いずれも音が残らないこと**。残るならキューの掃除が漏れている。

## 6. 残っていること

- **実機の数字は未取得**。sim で目標を満たしていることと、実機で何を
  見るかまでが本段の成果である。
- **APU 経路の後段 (kernel -> リンク -> WROVER) のジッタ**は未測定
  (5.2)。serial 経路にはこの問題が無い。
- テンポ変更が 300 ms 遅れて効く (2.4 の判断の裏返し)。気になるなら
  「捨てて積み直す」に変えられるが、穴と引き換えになる。
- 一時停止からの再開は、捨てた先読みのぶん (最大 300 ms) 曲が先に進む。

## 6. 実機実測 (2026-08-06 追記)

### 6.1 テンポ精度: 目標達成

ユーザ聴感: **「テンポ安定した」**。数字も裏付ける (S3 実機、計測ビルド):

- 定常の発射遅れ **avg 183〜931 us** (目標 2ms 以下を大幅クリア)。
  max_late 17〜33ms は**曲の開始直後の過渡のみ**で、定常では増えない。
- under / drop / send_failed すべて 0 (通常再生時)。
- **設計の証明が 1 つ取れた**: 2 回目の再生中、smf_player 自身の
  idle_gc ステップが **max 382ms** 走った 5 秒窓があるが、その間も
  stalls=0・avg 350us — **Ruby が 382ms 止まっても C キューが演奏を
  守った**。ポンプ方式なら確実に音が止まっていた場面である。

### 6.2 一度だけ起きた「再生が止まった」の解析

joplin_entertainer (serial) の 1 回目で発生、2 回目は再現せず。
ログには痕跡が残っている:

```
W fmrb_msg: msg_send TIMEOUT: dest=4, type=3, src=0, waiting=32   (数秒間連続)
W spx: hid_event slow: subtype=3 capture= 100ms
```

- **アプリ (dest=4) の受信キューが HID イベントで満杯** (32 件) になり、
  kernel の HID 転送が 100ms タイムアウトを繰り返した。約 10 秒間、
  アプリの on_update が痩せ、Ruby の補充が 1/3 のペースに落ちた。
- **C スケジューラは正しく動き続けた**: fired は増え続け、under=0。
  音が「止まった」と聞こえたのは補充の追いつかない断続再生で、
  スケジューラの欠陥ではない。
- 機序 (ユーザ指摘で訂正): move は host 層で既に **30Hz に間引き済み**
  (host_task.c の MOUSE_MOVE_THROTTLE_MS=33、leading+trailing ラッチつき)
  で、アプリ向け転送も同じ絞りの下流にある。したがって「125Hz の洪水」
  ではなく、**アプリが数秒 busy の間に 30Hz の move が 32 深のキューを
  ~1.1 秒で満たした** (busy の原因は再生・GC 等の複合とみられる。
  ドラッグは不要)。増幅器は kernel 転送の 100ms タイムアウト待ち。
  対処案 (P7.8 候補): (1) キュー 32→64 (~2.1 秒吸収、PSRAM +45KB)、
  (2) kernel 転送で move のみ「待たずに捨てて最新をラッチ」
  (host 層の既存パターンを流用) — 多秒ジャムでも麻痺の連鎖が消える。

### 6.3 未測定のまま残ったもの

- **audio_note_lat** (APU の発射後の後段): 1000 イベントごとの出力で、
  今回の APU 再生は 329 イベントで終わったため 1 行も出ていない。
  次の実機セッションで **APU 出力のまま 1000 イベント以上** (長い曲か
  2〜3 曲連続) 再生すれば初の実測が出る。
