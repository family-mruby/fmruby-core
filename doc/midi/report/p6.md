# P6 報告書: 実機で出た 2 つの遅さを潰す

対象: `doc/midi/work_order_p6.md`。
前提: [p5s.md](p5s.md) の 7 章 (実機での計測)、[README.md](../README.md)、[p4.md](p4.md)。

実機で出た「読み込みに 7.9 秒」と「演奏中に時々詰まる」は、**どちらも同じ
一つの原因**だった。**GC であり、その GC を呼んでいたのは 1 イベントあたりの
オブジェクト割り当て**である。裏は取れている (2 章)。割り当てを消したので、
どちらも sim では消えた。実機での確認手順は 7 章。

## 0. 結論だけ先に

| 項目 | 変更前 (sim) | 変更後 (sim) | 実機の見込み |
|---|---|---|---|
| `channel_usage` (22 KB / 5284 イベント) | **24 ms**、GC 4 回・停止 19 ms | **2 ms**、GC **0 回** | 7900 ms -> **450 ms 以下** (2.3) |
| 演奏 1 イベントの割り当て (プレーヤ) | 2.4 個 | **0 個** | 同じ (個数は CPU に依らない) |
| 演奏中の GC (serial 出力) | - | **0 回 / 22 秒** | 停止する要因が無い |
| 演奏中の GC (APU 出力) | 3 回 / 16 秒 | **2 回 / 48 秒** | 頻度 約 1/4.5 |
| APU 経路の 1 イベントの割り当て | 12.5 個 | **3 個** | 同上 |

sim の絶対時間は実機の 1/330 程度なので、そのままでは何も言えない。**効いたのは
「何個割り当てたか」「GC が何回走ったか」で、これは CPU 速度に依らない**。

## 1. 計測の道具 (先に作ったもの)

指示書 1.3 の「同じ見落としを繰り返さない材料」として、**ホストではなく sim に**
計測を置いた。理由は 2 章の結論そのもので、**効いていたのが GC だから**である。
ホスト (CRuby) の GC もアロケータも実機とは別物なので、ホストで per-event の
時間を測って 250 倍しても、実機で支配的だった量は再現しない。sim は**実機と
同じ mruby・同じ 500 KB の VM プール**で動くので、**オブジェクト数と GC 回数は
そのまま比較できる**。違うのは CPU 速度と PSRAM だけである。

### 1.1 `FMRB_GC_PROFILE` (計測ビルド)

`GC.stat` に GC の停止時間 (`prof_sync_*` ほか) を出す `MRB_GC_PROFILE` は
mruby 側に実装済みだったが、どのビルドでも有効になっていなかった。

**環境変数 1 つで両側に入る形**にした:

```
rake clean_all && FMRB_GC_PROFILE=1 rake build:linux
```

- `Rakefile` がコンテナに `-e FMRB_GC_PROFILE` を渡す。
- rake 側 (`lib/add/family_mruby_{linux,esp32,esp32p4}.rb`) と CMake 側
  (`components/picoruby-esp32/mruby_abi_defines.cmake`) が**同じ変数を
  コンテナ内で読む**ので、片側だけ有効になることが起こり得ない。
  これは ABI に効く定義 (`mrb_gc` が大きくなる = `mrb_state` が大きくなる)
  なので、食い違うと起動時の ABI ガードで abort する。
- **既定は無効**。オーバーヘッド (GC のたびに `clock_gettime` 2 回) を常時
  払う理由が無く、ABI を変えるものを既定で持ち歩きたくないため。
- 切り替えたときは `rake clean` が要る (cmake は configure 時に環境変数を
  焼き込むため、環境変数を変えただけでは再 configure されない)。

**最終状態: 3 ターゲットとも既定は無効**。今回の計測はすべて
`FMRB_GC_PROFILE=1` の linux ビルドで採った。

GC の観測方法・キーの意味・調整つまみは MIDI に限らず使えるので、
[../../gc_monitoring.md](../../gc_monitoring.md) にまとめてある。
以下はその適用例と読める。

### 1.2 `flash/app/debug/midi_bench.app.rb`

sim の中で走る計測アプリ。debugd から起動する:

```
python3 tool/debug/fmrb_dbg_client.py localhost:5555 spawn path=/app/debug/midi_bench.app.rb
docker compose logs fmruby-core | grep midi_bench
```

測るもの:

- **scan**: `channel_usage` を、GC 有効・無効の両方で。**GC を止めて同じ処理を
  させると何が起きるか**が、原因の切り分けそのものになる。
- **play**: 曲全体を 100 倍速で、何も鳴らさない transport に流し、
  1 イベントあたりの時間と GC 回数。
- **alloc**: `GC.disable` してから N 回呼び、`GC.stat[:live]` の増分を数える。
  **1 回の呼び出しが何オブジェクト残すか**が正確に出る。

このアプリは**大プール (1 MB) で動かしている**。自分のソース (12 KB) を
コンパイルするだけで 500 KB プールの 325 KB を使ってしまい、計測を始める前に
NoMemoryError になったためである。これ自体が 6 章の話につながる。

### 1.3 `flash/app/demo/midi_apu.app.rb` の計装

実機で 7.9 秒を出したのはこのアプリなので、**同じアプリ・同じ 500 KB プール**で
前後を比べられるようにした。`channel_usage` の時間と 5 秒ごとの `timing_stats` に
GC の行が付く:

```
MidiApu: events=971 avg_late=0ms max_late=18ms stalls=0 [gc live=2209 n=5 major=4 pause=5x tot=9ms max=4ms]
```

`n` は GC 回数、`pause`/`tot`/`max` は同期停止の回数・合計・最大 (計測ビルド時のみ)。
**「その詰まりは GC か」を、次に実機を触るときログ 1 行で判定できる**。

## 2. 犯人の特定 (指示書 1.2 の「たぶん GC で終わらせない」)

### 2.1 読み込み 7.9 秒 — GC が 5/6

sim で `channel_usage` を測ると (変更前、実機と同じ demo アプリ、500 KB プール):

```
channel_usage scan took 24ms [gc n=3->7 major=2->6 pause=3x->7x tot=0ms->19ms]
```

**24 ms のうち 19 ms が GC の同期停止**である (`prof_sync_total_us` の増分)。
さらに bench アプリで**同じ処理を `GC.disable` して**測ると:

| | 時間 |
|---|---|
| `channel_usage` (GC 有効) | 22.7 ms |
| `channel_usage` (GC 無効) | **2.8 ms** |

**8 倍違う**。処理そのものは 2.8 ms で、残りは全部集めていた時間である。
実機の 7900 ms も同じ内訳と考えてよい (実機のプールは PSRAM なので、
マーク・スイープが舐めるコストはさらに不利になる)。

割り当てていたのは:

- `varlen` が毎回 `[value, pos]` を返していた -> **1 イベント 1 配列**
- 使用チャンネルを `{ch => [count, sum]}` の Hash に貯めていた

5284 イベントの曲で 5000 個以上の配列である。

### 2.2 演奏中の詰まり — 同じ原因

プレーヤが 1 イベントで残すオブジェクトを数えると **2.4 個**だった。内訳:

| 出どころ | 個数 |
|---|---|
| `varlen` の `[value, pos]` | 1.0 |
| `device.note_on(note, vel, channel: ch)` の**キーワード引数の Hash** | 1.0 |
| `@sounding << [channel, note]` | 0.5 (note on のみ) |

**キーワード引数が 1 イベント 1 オブジェクト**なのは測って初めて分かった
(`device.note_on` = 1.02 個/回、同じ内容を `transport.send_packet` で呼ぶと
0.02 個/回)。

これで sim では、曲を通して流すと GC が 7 回・合計 54 ms 走っていた
(実時間で聴かせると 16 秒に 3 回)。
**演奏中に同期停止する要因は GC しか無い** (`_spin` は 1ms 粒度、UART は
リングバッファ、いずれも P5s で白と確認済み)。

実機の数字との対応:

- 実機 `stalls=4` は「200 ms 超の遅れ」を 4 回数えたもの。**`max_late=176ms` が
  200 ms を超えないのは当たり前で、超えたものは stall として別に数える実装
  だから**である (`STALL_MS = 200`)。つまり実機の停止は **200 ms 以上**が
  60 秒に 4 回。
- sim では同じ再生で GC が 11 回/60 秒 程度 (16 秒に 3 回)。回数のオーダーは合う。
- 停止の長さは sim の値を単純に 330 倍すると実機の観測より大きく出る。
  **この倍率は「GC が支配的な処理」から出したものなので、停止 1 回の長さの
  外挿には使えない**。ここは正直に「実機での停止の実測値はまだ無い」と
  しておく。7 章の手順で `prof_sync_max_us` を直接読めば一発で分かる。

**したがって断定できるのは「演奏を止めていたのは GC であり、GC を呼んでいたのは
1 イベントあたりの割り当てである」まで**。停止 1 回が実機で何 ms かは、次に実機を
触るときに読む。

### 2.3 実機の見積り (指示書 1.3 の「実機との比を掛けて見積もる」)

倍率は**同じアプリ・同じプール・同じファイルで測った同じ処理**から出した:

```
実機 7900 ms / sim 24 ms = 330 倍
```

これを書き直し後の走査 (bench アプリで 1.36 ms、マイクロ秒分解能) に掛けると
**約 450 ms**。ただしこの倍率は GC が 5/6 を占める処理から出したものなので、
GC を出さなくなった処理にそのまま掛けるのは**過大に出るはず**である。

GC を除いて見積もっても同じあたりに来る:

- 変更前の走査は sim で 22.7 ms、うち処理そのものは 2.8 ms (2.1)。
  実機 7900 ms の同じ比率が処理そのものだとすると約 990 ms。
- 書き直し後の処理量はその 2.3 分の 1 (1.2 ms 対 2.8 ms) なので約 420 ms。

**上からも下からも 400 ms 台**に来るので、報告としては「7900 ms が 450 ms 以下に
なるはず」とする。実測は 7.2 で採る。**足りなければ 4.1 の打ち切り版で
さらに 4 分の 1 にできる**。


## 4. 判断したこと

### 4.1 「先頭 N イベントだけ走査する」は採らなかった

**全部走査しても間に合うようになったから**である。書き直した `channel_usage` は
sim で 1.2 ms、上限側の見積りでも実機 450 ms 以下 (2.3)。ここで頭を打ち切ると
「途中から入ってくるパートが無音になる」という**音で分かる劣化**を、
測れば要らないと分かる速度のために買うことになる。

bench アプリには打ち切り版 (`scan_fast(..., 600)`、各トラック 600 イベント) も
入れてあり、sim で 0.31 ms である。**もっと大きい曲で足りなくなったときの
手は残してある**が、今は使わない。

### 4.2 「`collect_tracks` の 1 パスに相乗りさせる」は前提が違っていた

指示書は「読み込みと走査でファイルを 2 回舐めている」としているが、
**`collect_tracks` はイベントを舐めていない**。チャンクヘッダ (8 バイト) を
辿って長さの分だけ飛ぶだけで、3 トラックなら 3 回のジャンプで終わる。
相乗りさせても消える仕事が無い。実際に高かったのは走査そのものではなく、
**走査が出していたゴミ**だった (2.1)。

### 4.3 C に降ろさなかった

Ruby のまま 10 倍以上速くなり (24 ms -> 1〜2 ms)、GC が消えた。
C に降ろす理由が無い。P2 の「まず Ruby で」は据え置く。

### 4.4 `MIDI::Device` を迂回せず、チャンネル引数版を足した

キーワード引数の Hash を避けるだけなら `device.transport.send_packet(...)` を
直接呼べば済むが、それだと**プレーヤが transport を知る**ことになり、
「同じプレーヤが APU にも外部音源にも流せる」という P2/P4 の設計が崩れる。

`picoruby-midi` は無改変を保つ約束なので、**`picoruby-fmrb-midi` 側で
`MIDI::Device` を開いて 4 つのメソッドを足した**。中身は `send_channel_message`
と同じ計算で、同じ `send_packet` に渡す。アプリが書くときは今まで通り
`note_on(60, 100, channel: 3)` でよい (読みやすさの価値のほうが大きい)。
**1 イベントごとに呼ぶプレーヤだけがこちらを使う**。

### 4.5 `FmrbAudio` のキーを Symbol にした

`{"cmd" => "note_on", ...}` は 1 回ごとに Hash 1 + String 7 個である。
最初は Hash を使い回して値だけ差し替える実装にしたが、**String をキーにした
代入は 1 回 2 オブジェクト**で、5 個差し替えると 10 個かかり、ほとんど
改善しなかった (16 -> 12.4)。凍結されていない String をキーにすると
mruby が複製して凍結するためである (`src/hash.c` の `h_key_for`)。
bench アプリの `hash store, String key` / `hash store, Symbol key` が
この 2 個 対 0 個 を直接出す。

Symbol キーの Hash リテラルに変えたところ **3 個/回**になった。
`fmrb_msgpack` は Symbol を String と同じに符号化するので、
**ワイヤ上のバイト列も kernel 側も一切変わらない**。
`note_on` / `note_off` の 2 つだけがこの形で、理由はコメントに書いてある
(このファイルで唯一、連打されるメソッドだから)。

### 4.6 `MRB_GC_PROFILE` は既定で無効

1.1 のとおり。ABI を変えるものであり、常時のオーバーヘッドを払う理由が無い。
**有効化は環境変数 1 つで両側に入る**ようにしたので、必要なときの手間は
`rake clean` を挟むだけである。

## 5. 残っているもの

- **APU 経路の 3 個/イベント**。`FmrbAudio#note_on` -> `MessagePack.pack` ->
  `_send_message` の経路で、Hash 1 + pack 2 である。`_send_message` 自体は
  0 個 (C で構造体に memcpy するだけ)。これを 0 にするには音声メッセージを
  C 側で組む必要があり、`picoruby-fmrb-app` の設計変更になるので P6 では
  やらない。**sim では 25 秒に GC 1 回まで下がっており、実機で問題が残るかは
  7 章で確かめてから決める**。
- **実機での停止 1 回の長さ**が未実測 (2.2)。
- **`_spin` 前の GC ステップ (ユーザ発案、試したい)**。アプリの暇な時間は
  すべて `_spin` (C の `fmrb_msg_receive`) の中で寝ていて mruby から見えず、
  GC は「発音の瞬間の同期停止」しか機会が無い。`on_update` が返した待ち時間に
  余裕があるなら、`_spin` に入る前に GC を 1 歩進めれば、掃除を暇な時間に
  移せる。mruby-task の `GC.scheduler_driven` 一式 (`mrb_gc_step`、
  ジッタ計測つき) が既にあるので部品は揃っている。APU 経路の 3 個/イベントが
  実機でまだ詰まる場合の次の一手。
- `smf_player` アプリは選択を動かすたびに読み込みと走査をやり直す。
  7.9 秒だった頃は矢印キー 1 回ごとにそれを待たされていたはずである。
  今は 2 ms (sim) なので放置したが、実機で気になるようなら
  「再生するときだけ走査する」に変えられる。
- 受信 (MIDI IN)、USB-MIDI host は従来どおり対象外。

## 6. ついでに見つけて直したもの: SMF プレーヤが NoMemoryError で死ぬ

変更後の確認中に、`smf_player` アプリが**曲を選び替えていくと落ちる**ことが
分かった。しかも**ログに何も出ずにタスクが終わる**。`NoMemoryError` は
`StandardError` ではないので、アプリ雛形の `rescue => e` を素通りしていた。

原因は VM プールの使い切りである:

- アプリのソースをコンパイルした時点で 500 KB プールの **300 KB 強**を
  使っている (MIDI APU デモで実測 308 KB。smf_player もソースの大きさは
  同じくらいである)。
- `File#read` はファイルサイズ分の C バッファを確保してから String に複製する。
  **前の曲を持ったまま次を読むと、22 KB の曲で 3 つ分 (66 KB) が同時に生きる**。
- 選択を動かすたびに読み込み + 走査をしていたので、これが積み上がる。

直したのは 2 点:

1. `SmfPlayer#load` が**読む前に前の曲を手放す**。
2. `smf_player.app.rb` の最上位 `rescue` を `Exception` にして、
   落ちたときに理由がログに出るようにした。

これは P6 の変更で持ち込んだものではない (**変更前のビルドでの再現確認は
していない**が、今回の変更は割り当てを**減らす**方向にしか働いておらず、
`load` の割り当ての形 (File#read + String) には触れていないので、変更前は
これと同じか、走査のゴミの分だけ悪かったはずである)。
**実機でも同じ 500 KB プールなので、実機でも起きていた可能性が高い**
(7 章で確認する)。

## 7. 実機での確認手順

実機が使えるようになったら、上から順に。**計測ビルドで焼くこと**
(そうしないと GC の停止時間が読めない)。

### 7.1 準備

```
cd fmruby-core
rake clean_all
FMRB_GC_PROFILE=1 rake build:esp32
rake check-port                  # 初回のみ
FLASH_BAUD=115200 rake flash
```

`FMRB_GC_PROFILE=1` を付け忘れると `[gc ... pause=0x tot=0ms max=0ms]` が
ずっと 0 のままになる (回数 `n` と `live` は付けなくても出る)。

### 7.2 読み込み時間 (指示書 1.1 の完了条件)

MIDI APU デモを起動し、「5 SMF」を押してログを見る。

```
python3 ../tools/fmrb_serial_capture.py -t 40 play.log
grep "loaded in\|channel_usage" play.log
```

- 期待: `channel_usage scan took` が **7900ms から数百 ms へ**。
  同じ行の `[gc ...]` で `n` (GC 回数) が**増えていない**こと。
- もし数百 ms に収まらない場合: `[gc ...]` の `n` が増えていなければ純粋な
  CPU 時間なので、4.1 の打ち切り版 (bench アプリの `scan_fast(..., 600)`) を
  gem に入れる。`n` が増えているなら、まだどこかで割り当てている。

### 7.3 演奏の詰まり (指示書 1.2 の完了条件)

同じログの 5 秒ごとの行を見る。

```
grep "events=" play.log
```

- 期待: `stalls=0`、`max_late` が 2 桁 ms 以内。
- **`[gc ...]` の `pause` と `max` が、この判定の証拠になる**。
  `max=`(GC の最大同期停止) と `max_late=`(音の最大遅れ) が同じ桁なら
  依然 GC、離れていれば別の原因である。**ここが 2.2 で埋められなかった穴で、
  この 1 行で埋まる**。
- APU 経路と serial 経路の両方でやる (「7 Out」で切り替え)。
  **serial 経路は GC 0 回のはず**である。ここで GC が走るなら、
  プレーヤ以外 (アプリ側) にまだ割り当てがある。

### 7.4 SMF プレーヤアプリ (6 章)

`/app/tool/smf_player.app.rb` を起動し、**上下キーで一覧を端まで往復する**。

- 期待: 落ちない。曲情報 (`N trk M ch K notes`) の表示が待たされない。
- 落ちた場合はログに `Exception caught: NoMemoryError` が出るようになった。
