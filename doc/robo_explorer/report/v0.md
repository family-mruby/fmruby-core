## 2. 計画・指示書との食い違い

- **置き場所**: 計画書は `flash/app/robo_explorer/`。作業中の指示で
  `flash/app/game/robo_explorer/` に変更した。ランチャーの 3 段目走査
  (カテゴリ配下のアプリ束ディレクトリ) が効くので、この深さでも
  そのまま一覧に出る。
- **`mixed: true` は使わなかった**。指示書 2 章は efontJA_12 と併記して
  いるが、`mixed:` は「ASCII を Font0、多バイトを misaki_8」に固定する
  経路 (gfx.c の hybrid_mode、fmrb_link_protocol.h のコメント) で、
  set_font(:ja, 12) を無視して漢字が 8px に落ちる。efontJA_12 は ASCII を
  6px、全角を 12px で自前に描き分けるので、`set_font(:ja, 12)` + 素の
  `draw_text` で混在文字列がそのまま正しく出る。**混在だから mixed: を
  付ける、は誤り**。
- **ターン処理の描画**: 指示書 5 章は「1 ターン = 1 回の再描画」。盤面
  全面を描くと 144 個の fill_rect が毎ターン線に乗るので、ロボットが
  出た/入ったマスだけ描き直し、盤面が変わったとき (鍵を拾う・扉が開く)
  と R のときだけ全面を描く形にした。

## 3. 実測: ターン周期

pilot が cmd を publish した時刻と、対応する result を受けた時刻の差
(`Machine.board_millis`)。連続 10 手:

```
rtt 1 = 1 ms   rtt 2..9 = 0 ms   rtt 10 = 1 ms
```

**1 往復 0-1 ms**。目安の 100ms から 2 桁下で、ターン制の前提は余裕で
成立する。Linux sim の値なので実機 (S3/P4) はこれより遅い。実機での
再測定は未実施。

なお state は操作のたび + 無操作でも 1 秒周期で publish している。後から
起動した pilot が「まってます」から実際の状態表示に変わるまで最大 1 秒。

## 4. 面 (level 1) の性質

- 12x12、外周は壁。start (1,1)、鍵 (5,8)、扉 (8,9)、ゴール (8,10)。
- ゴールの隣接 4 マスは扉以外すべて壁。**鍵なしでは絶対にクリアできない**。
- 最短は 18 手 (ホスト側 BFS で確認)。今回の手動検証は寄り道込みで 24 手。

## 6. 作業中の気づき

- **ランチャーはブート時のキャッシュを読む**。アプリを追加した直後の
  ブートでは一覧に出ない (`Launcher: 43 apps from cache`)。ランチャー窓で
  **右クリックすると再走査**され、以後はキャッシュに載る。検証手順に
  入れておくとよい。
- graphics-audio の build/ が esp32 (Xtensa) のままだったので、こちらも
  `rake clean_all` + `rake build:linux` が要った。指示書は「変更しないので
  ビルド済みならそのまま」としているが、直前が実機ビルドだと成立しない。
- ターゲット切替直後の 1 回目の起動は前の解像度 (320x240) で上がる。
  down/up をもう一度やると 426x240 になる (既知)。
- pilot は **`turn == 0` の state を「世界がリセットされた」合図**として
  扱い、前回の返事の表示を消している。プロトコルに reset トピックを
  足さずに済む。段階 2 以降を書く子供も同じ手が使える。
