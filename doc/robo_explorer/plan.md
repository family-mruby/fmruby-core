# ロボットエクスプローラー: Pub/Sub で操作する二人羽織パズル

作成: 2026-08-16。状態: 検討段階 (実装未着手)。

## 1. 背景と目的

Pub/Sub デモの発展形。**アプリ 1 (世界)** はロボットが迷路を進むパズル
ゲームだが、そのアプリ上でユーザはロボットを操作できない。ロボットの状態と
受け付ける操作だけが Pub/Sub で公開される。**アプリ 2 (制御)** はその情報を
購読し、操作を publish してロボットをゴールへ導く。

アプリ 2 の書き方は自由で、それがこの企画の主題:

- キー入力を操作にただ転送するだけの数行 (手動遠隔操作)
- 「前が壁なら曲がる」を混ぜた半自動
- 状態だけから解く完全自動

つまり **アプリ 2 を書くこと自体が教材**になる。同時に、多重 VM +
カーネル Pub/Sub + 2 窓同時表示という、この機械でしか成立しないデモになる。

### 教材として成立する構造的理由

- 世界と制御が別プロセスなので、**見えるのは公開された状態だけ、できるのは
  公開された操作だけ**。情報隠蔽が説教ではなく構造で保証され、ズルが書けない。
- 「命令する → 結果が返る → 次を決める」の因果が 1 ターンずつ見える。
- 段階 1 (転送 10 行) の成功が近く、段階 3 (完全自動) の天井が高い。
- 状態/操作/結果のトピック分離は ROS のトピック設計と同型。将来の Zenoh
  接続 (doc/zenoh/plan.md) で実ロボットに話が接続できる。

## 2. 使う土台と確定している事実 (2026-08-16 時点)

- Pub/Sub API は FmrbApp にある: `subscribe(topic)` / `unsubscribe(topic)` /
  `publish(topic, data)`。mruby / Spinel 両基底に同じ形で存在する。
- 配信はカーネル経由。購読者には `on_control(msg)` に
  `{"cmd"=>"topic_data", "topic"=>..., "data"=>..., "src_pid"=>...}` が届く。
  **publisher 自身には届かない** (カーネルが送信元を除外する)。
- payload は Hash を MessagePack で往復する。**キーは文字列で届く**
  (Symbol で publish しても受信側は String)。
- **保持 (retained) は無い**。購読開始前に流れたメッセージは知れない。
  後から起動したアプリ 2 は、次の publish まで世界を知らない。
- アプリ枠は 5 (2026-08-16 に 3→5 化)。**エディタ + アプリ1 + アプリ2 を
  同時に載せて、エディタの F5 で回す反復ループが今の実装のまま成立する**
  (run_parent がキーボードをエディタへ返す)。
- 2 窓の同時表示は Modern (426x240) で実績あり (PubDemo + SubDemo 並置)。
  Pub/Sub はカーネル機能なので Retro (320x240) でも同じに動くはずだが、
  2 窓のレイアウトは要調整。
- 配信ループは while 化済み (24b32ae)。ただし**ターンごとに複数トピックが
  往復する負荷は未計測**。ターン制なら余裕の見込みだが、実装初週に
  ターン周期の実測を 1 回入れる。

## 3. 設計方針 (提案)

### 3.1 ターン制にする

リアルタイムにしない。理由は 2 つ。

- 教材: 「1 手 → 結果を読む → 次の手」の因果が明確。ログも読める。
- 負荷: publish 1 通ごとに MessagePack の往復がある。毎フレーム流す設計は
  この土台の重い操作 (確保・ブロック呼び出し) を踏む。ターン制なら消える。

アニメーション (ロボットが 1 マス滑る等) はアプリ 1 の内部だけの話で、
プロトコル上は 1 ターン = 1 状態。

### 3.2 センサは局所、ただしゴールの方角は教える (決定 2026-08-16)

全マップを配ると経路探索の演習に矮小化する。見えるのは
「前方 1 マスに何があるか」まで。探索・壁伝い・記憶 (自前の地図作り) という
「試して知る」プログラムに誘導する。

ゴールの方角 (`goal`) は**最初から教える**。壁伝いより賢い戦略への
入口になり、使わない自由もある。全体図 (`map` トピック) は作らない
(上級面で解放する案は 7 章)。

### 3.3 操作には必ず返事を返す

`move` に対して `ok` / `blocked` を返す。子供のデバッグの唯一の手掛かりで
あり、「命令は失敗しうる。結果を見て判断する」というロボティクスの核心。
黙って無視される操作を作らない。

### 3.4 状態は毎ターン publish する

retained が無いので、アプリ 2 が後から subscribe しても最初の状態を
知れない。アプリ 1 が毎ターン (操作が無ければ 1 秒周期でも) 状態を流す
だけで解決する。ハンドシェイク (hello/welcome) より単純で壊れにくい。

### 3.5 面は seed で決定的に

「同じ面でプログラムを直して再挑戦」ができないと教材にならない。
面は seed から生成 (または固定データ)。クリアターン数が成績になる。

## 4. プロトコル案 (v0)

題材 (決定 2026-08-16): 迷路状の NxM マップで、**鍵を集め、扉を開けて
ゴールに到達する**。鍵と扉は v0 から入れる。将来ギミックを足す。

トピック名は `robo/` 接頭。すべて Hash。

```
robo/state   アプリ1 -> 全員。毎ターンと、操作の処理後。
  { "turn" => 12, "x" => 3, "y" => 5, "dir" => "N",
    "front" => "wall",          # "floor" | "wall" | "goal" | "key" | "door"
    "goal" => "NE",             # ゴールの方角 (8方位) — 距離は教えない
    "keys" => 1,                # 持っている鍵の数
    "keys_left" => 1,           # 盤上に残っている鍵の数 (全部要るとは限らない)
    "view" => [[1,1,"floor"], [1,0,"floor"], [1,1,"door"]],
                                # 正面の廊下の見え方 (2026-08-16 追加)。
                                # [左が壁, 右が壁, そのマスの物] が手前から
                                # 並ぶ。扉とゴールで走査は止まり、リストが
                                # 床で終わればその先は壁。地図ではなく視線
                                # (廊下の外は見えない)。pilot はこれで
                                # Wizardry 式のワイヤフレーム視界を描く
    "done" => false, "steps" => 12, "level" => 1 }

robo/cmd     アプリ2 -> アプリ1。
  { "op" => "move" }                    # 前進 1 マス
  { "op" => "turn", "to" => "L" }       # "L" | "R" (相対回転のみ)
  { "op" => "wait" }                    # 1 ターン消費 (将来のギミック用)
  { "op" => "reset" }                   # 最初から (手詰まり脱出。done 後も効く)

robo/result  アプリ1 -> 全員。cmd 1 つごとに必ず 1 つ。
  { "turn" => 12, "op" => "move", "ok" => false, "reason" => "wall" }
  # reason: "wall" | "locked" (鍵なしで扉) | "edge"
```

鍵と扉の意味論 (v0):

- 鍵のマスに move で乗ると拾う (`keys` +1、マスは床になる)。
- 扉のマスへ move すると、鍵があれば 1 本消費して開き、そのマスへ進む
  (扉は床になる)。無ければ `ok: false, reason: "locked"`。
- 専用の `pick` / `unlock` 操作は作らない。「move がすべて」のほうが
  段階 1 の転送プログラムが単純になり、扉の学びは reason で得られる。

方針:

- **操作は相対のみ** (`move` / `turn L|R`)。絶対座標へのテレポートを
  作らない。座標は状態として見えるが、操作は一人称。
- state と result を分けるのは、result が「あなたの操作への返事」で
  state が「世界の事実」だから。混ぜると転送プログラム (段階 1) が
  書きにくくなる。
- turn 番号を全メッセージに載せる。ログを突き合わせる唯一の軸。
- **プロトコルの語彙 (トピック名・キー・値) は英語のまま**。画面表示は
  日本語専用だが、メッセージはプログラムが読むものであり、段階 2 以降で
  子供が書く比較 (`if front == "wall"`) を素直に保つ。表示側で
  「壁」「扉」に訳すのはアプリ 1 の仕事。

## 5. アプリ 1 (世界側) の骨格

- **表示は日本語専用 (漢字あり)** (決定 2026-08-16)。i18n 表は持たず、
  日本語リテラルを直接書く (単一言語なら i18n は手間なだけ)。フォントは
  efontJA_12 (12x12) を基本にする — 8px の misaki より読みやすく、
  Modern の横幅なら盤面の右に 12px 文字の状態欄が収まる。両フォントとも
  アプリの draw_text から使える (fmrb-gfx.rb の :ja フォント)。
  文言は普通の日本語 (漢字を普通に使う。決定 2026-08-16)。
- 窓アプリ。盤面 (例 12x12 マス、16px タイル) + 状態表示。
  タイル描画は TileSheet/TileMap の既存部品が使える。
- 地図 (盤面) を隠すボタンを持つ (2026-08-16 追加)。隠すと迷路の形を
  誰も見られなくなり、ロボットのセンサ情報だけで解く遊び方になる
  (地図を見ないでクリアさせたいことがある)。状態パネルは常時表示。
- on_control で `robo/cmd` を受け、1 ターン進めて state/result を publish。
- 操作を直接受けるキー入力は持たない (それがこのゲームのルール)。
  ただし R (リセット) と面選択だけはアプリ 1 側の操作とする。
- クリア時は `done: true` の state を流し、盤面に成績 (steps) を出す。

## 6. アプリ 2 の教材段階 (これがカリキュラム)

| 段階 | 内容 | 書く量の目安 |
|---|---|---|
| 0 | 見る: state を購読して画面に出すだけ | 10 行 |
| 1 | 手動: 矢印キーを cmd に転送 | +10 行 |
| 2 | 半自動: 「前が壁なら右を向く」ボタン | +10 行 |
| 3 | 自動: 壁伝いでゴールまで | 数十行 |
| 4 | 記憶: 通った場所を覚えて自前の地図を作る | 発展 |

操縦側は 2 ファイルに分かれる (2026-08-16 に再構成):
`robo_pilot.app.rb` は枠組み (購読・描画・送信・think の駆動) で、
**プレイヤーが書くのは require される `my_pilot.rb` だけ**。MyPilot の
3 フック (on_key / think / on_result) が段階 1 以降の全てで、出荷時の
my_pilot.rb が段階 1 (キー転送)、think を埋めるのが段階 2 以降。
自動運転は S キーで開始/停止し (枠組みの機能)、走行中は think が
0.2 秒ごとに呼ばれる。起動即走行にしないのは、見てから走らせるため。
頭脳の例外は枠組みが受け止めて「頭脳でエラー」と表示するので、
壊れた頭脳でアプリごと落ちることはない。

## 7. 決定済み (2026-08-16)

- **題材**: 迷路 NxM + 鍵 + 扉 + ゴール。v0 から鍵と扉を入れる。
- **`goal` (ゴール方角)**: 最初から教える。
- **操縦者**: 一人想定。排他制御は作らない (カーネルの素の挙動のまま)。
- **表示**: 日本語専用 (漢字あり)。i18n 表は持たない。フォントは
  efontJA_12 基本 (5 章)。
- **名前**: ロボットエクスプローラー。置き場所は flash/app/game/robo_explorer/
  (世界側 robo_explorer.app.rb、操縦サンプル robo_pilot.app.rb)。
  トピック接頭辞は robo/ のまま。
- **Retro のレイアウト**: 2 窓が重なってよい。専用の縮小レイアウトは
  作らない。

## 9. 将来 (v0 では作らないが、設計が塞がないようにする)

- **対戦**: ロボット 2 台 + 操縦者 2 人 (競走、鍵の取り合い)。トピックを
  `robo/1/state` のように台番号で名前空間化すれば載る。v0 は 1 台なので
  `robo/state` のままとし、多台化の時に一斉改名する (v0 の購読側は
  トピック名を定数 1 箇所に置いておくこと)。
- **ギミック追加**: 動く床、スイッチ、一方通行。state の `front` の語彙と
  result の `reason` を増やすだけで載る形を保つ。
- **MicroPython の操縦者** (いずれ対応したい): 専用の publish/subscribe
  ラッパは無いが、土台は既にある —
  `fmrb.send_message(pid, type, dict)` と `on_control` への APP_CONTROL
  配送 (dict 化込み) は実装済み (components/micropython/modules/
  fmrb_module.c)。カーネルの subscribe/publish は APP_CONTROL の
  {"cmd" => ...} を読むだけなので、**必要なのは Python 側のラッパ 3 つと
  メッセージ種別定数の公開のみ**。新しい橋は要らない。対応したら
  「同じロボットを別言語で操縦する」デモがそのまま成立する。

## 10. 進め方

1. アプリ 1 を v0 プロトコル (4 章) で実装。面は固定 1 枚
   (鍵 1・扉 1 の小さな迷路)。
2. 段階 0/1 のサンプル (robo_pilot) を書く — これがプロトコルの検収になる。
3. ターン周期の実測 (state+cmd+result の 3 通/ターンで何 ms か)。
4. 面を seed 生成に。成績表示。
5. 遊ばせてから 8 章を決め直す。MicroPython ラッパ (9 章) はその後。
