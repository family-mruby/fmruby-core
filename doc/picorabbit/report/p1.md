# P1 report: うさぎと亀のスプライト化

対象: `tool/gen_picorabbit_sprites.rb` (新規)、
`flash/usr/share/picorabbit/*.bmp` (8 コマ)、
`flash/app/tool/picorabbit.app.rb`、
`lib/add/picoruby-fmrb-picorabbit/mrblib/picorabbit_renderer.rb`。

## 絵

### BMP が正、生成ツールは下書き

**`flash/usr/share/picorabbit/` の BMP が正であり、生成ツールは正ではない。**
ここに置いた 8 コマは Claude が起こした下書きで、最終的な絵はユーザが
sprite_editor で直したものになる。したがって:

- `tool/gen_picorabbit_sprites.rb` は**出力先にファイルがあれば書かない**。
- **`--force` は今後使わない**。使うとユーザの直しが下書きに戻る。
  (P1 の作業中、絵を詰める間だけ使った。絵を確定させて以降は使わない。)
- 走りの歩幅や万歳の腕といった微修正もツール側ではやらない。editor で直す。

この旨はツール冒頭のコメントにも書いてある。

### 形式 (指示書の「資産の形式」との突き合わせ)

生成した BMP を読み返して確認した結果:

| 項目 | 結果 |
|---|---|
| サイズ | 全 8 コマ 16x16 (sprite_editor が 1 タイルとして開ける) |
| 形式 | 8bit インデックス BMP、画素バイト = RGB332 値 |
| 色 | sprite_editor の 16 色パレットのみ (1 コマあたり 5-7 色) |
| 透明 | 0x00 のみ。絵の中に純黒なし (輪郭は 0x48) |
| 接地行 | **全 8 コマとも最下端が row 14**、row 15 は空 |
| 向き | 全コマ右向き (ゴール方向) |

接地行を全コマで揃えたのは、亀とうさぎが同じ帯の上に並ぶため。1 コマでも
接地が上下すると、整数 3 倍で 3px 跳ねて見える。

### sprite_editor での直し方

1. ランチャーから **Sprite Editor** を起動する。
2. ファイル選択で `/usr/share/picorabbit/<名前>.bmp` を開く
   (16x16 なので 1 タイルのシートとして開く)。
3. 右のパレットから色を選んで塗り、**`S` で保存**する。

直すと効きそうなところ (候補。好みで構わない):

- **`usagi_run2` の前脚を 1-2px 前へ**。今は run1 との差が脚の位相と耳の
  跳ねだけなので、3 倍でも走っている感じが薄い。前脚をもう少し前に出すと
  2 コマの差が出る。
- **`kame_banzai` の腕を 1px 外へ**。上げた両腕と頭が上部で近く、混んで
  見える。左右へ 1px 開けると万歳が読みやすい。
- `usagi_sleep` の黄色い Z と `usagi_hurry` の水色の汗は、状態を一目で
  分かるように足したもの。要らなければ消してよい (どちらもパレット内)。

**輪郭が 0x48 (暗い緑褐色) なのは仕様上の制約**。0x00 が透明キーなので
純黒が使えない。`theme: dark` の黒地では輪郭のコントラストが弱いが、
胴が白・茶なので形は読める。

## アプリ側

### 帯の塗り直しを消した

`redraw_timer_area` と `render_timer` を削除した。スライドの canvas に
残るのはトラック線だけ (`render_track`、`render_slide` の中で 1 回)。
走者は canvas の外のスプライト層で合成されるので、動いても本文を汚さない。

**P0 で残していた `update_rabbit` の 2 回進みは、これで消えた**
(`render_timer` の中の呼び出しが無くなったため)。

### 帯の高さ

スプライトが 16px あるので `TIMER_H` を 4 -> 16 にした。連動して
フッタが 12px 上がり、本文の高さが 12px 減る (240 のうち 5%)。

- トラック線: `@track_y = @h - 2`
- スプライトの y: `@sprite_y = @track_y - 14` (絵の接地行が 14)
- x: トラック上の点にスプライトの中心が来るように `-8`、両端で画面内に収める

### 読み込みと後始末

`on_create` の `load_presentation` の後に `FmrbRenderer#load_sprites` を
1 回。`sync_file` で `/usr/share/picorabbit` から `/cache/app/picorabbit` へ
写し、`SpriteImage` を 8 枚 (`transparent_color: 0`, `use_transparent: true`)、
`SpriteInstance` を 2 体だけ作る (うさぎ z=3、亀 z=2)。
**`allotted_time` の無い発表では 1 枚も読まない**。
`on_destroy` で `destroy_sprites`。

### on_update

1000ms 周期。毎回やるのは位置と表情の計算だけで、
**位置かコマが前回と変わったときだけ present する**。

- 亀: x は経過時間、コマは 1 秒ごとに walk1/walk2 交互、時間切れで banzai
- うさぎ: x はスライド番号 (ページ送りで動く)
- うさぎの表情: 直近のページ送りから 3 秒は run1/run2、それ以降は
  「うさぎ進捗 - 亀進捗」が +0.10 以上で sleep、-0.10 以下で hurry、
  その間は run1 で静止

ページ送りの present は `render_slide` の中の 1 回のまま。スプライトの
`move` はその present の**前**に済ませてある。

### ジャンプ

1 秒周期では跳ねて見えないので、跳んでいる間だけ `on_update` が 100 を
返す。物理 (`@usagi_jump_y` / `@usagi_vy`) は従来のまま、跳躍中のコマは
`usagi_jump`。着地したら 1000 に戻る。

### park (Ctrl+Tab)

スプライトは canvas とは別の層で合成されるので、suspend で canvas が
隠れてもそのまま残る。`on_suspend` で `visible = false`、`on_resume` で
`true` に戻して再描画する。

## 検収 (Linux sim, headless, 426x240)

`allotted_time: 2` の一時 .md (タイトル + 本文 5 枚) で通した。
どのコマが出ているかは目視ではなく、**画面の該当 16x16 を 8 枚の BMP と
突き合わせて**判定した (`fmrb_screenshot` と同じ RGB332 -> RGB888 展開で
比較し、透明画素は除く)。100% = 透明でない全画素が一致。

### 4 つの局面

| 局面 | うさぎ | 亀 |
|---|---|---|
| 起動直後 | 出発点 (x=4) | 出発点 (x=4) |
| 約 1 分後 (ページ送りなし) | 出発点のまま **`usagi_hurry` 100%** | トラックの 63% (実測 63.4%、期待 63.3%)、`kame_walk1` 100% |
| 最後まで送った直後 | ゴール (x=406) `usagi_run1` 100% | - |
| 送った 3 秒後 (時間はまだ残っている) | ゴールで **`usagi_sleep` 100%** | 出発点付近 |
| 2 分経過 | - | ゴール (x=406) で **`kame_banzai` 100%** |

「時間より進んでいれば居眠り、遅れていれば焦り」が数字で出ている。

### ジャンプ (u)

100ms 周期に落ちて跳ね、着地して 1000ms に戻る。連続キャプチャで:

| 撮影 | 判定 |
|---|---|
| 押す前 | `usagi_hurry` y=224 (100%) |
| +1 | `usagi_jump` y=215 (100%) |
| +2 | `usagi_jump` y=210 (100%) |
| +3 | `usagi_jump` y=209 (100%) — 頂点 (jump_y = -15) |
| 着地後 | `usagi_hurry` y=224 (100%) |

`GFX STATS` は跳躍中だけ 2.6 presents/s に上がり、着地後 1.0 に戻った。

### 放置中の present と帯の塗り直し

| 状態 | presents/s | cmds/s |
|---|---|---|
| **P0 (帯を 200ms ごとに塗り直していた頃)** | **5.0** | 44.9 - 49.1 |
| **P1 PicoRabbit 放置中** | **1.0** | **3.0** |
| 参考: デスクトップだけ (PicoRabbit 終了後) | 1.0 | 10.0 |

放置中の present は **1/s** で、内訳は亀が 1 秒ごとに 1px 単位で進み、
歩きコマが交互になる分だけ。cmds/s が 45 -> 3 に落ちているのが
**帯の塗り直しが無くなった証拠** (塗り直しは fill_rect 1 回 + フッタの
draw_text 一式を毎回出していた)。デスクトップ単独の 1.0 presents/s は
メニューバーの時計なので、この 1/s とは別勘定。

### park (Ctrl+Tab)

- 退避中のデスクトップのスクリーンショットに**スプライトは無い**
  (`on_suspend` の `visible = false` が効いている)。
- 復帰でうさぎ・亀とも元の位置・コマに戻る (`usagi_hurry` y=224 100%、
  `kame_banzai` x=406 100%)。

### ログ

- `PicoRabbit: 8 sprite frames loaded` が 1 回出る。
- `grep -cE "^E \(|Exception"` = **0**。

### 使わなくなった色を消したあとの再確認

スプライト化で `timer_turtle` / `timer_rabbit` は誰も見なくなったので
theme から消した (走者の色は BMP が持つ)。この削除だけ上の検収より後だった
ので、ビルドし直して煙試験を通した: 8 コマ読み込み、3/6 のスライドで
うさぎ x=104 (期待 25% -> 104) `usagi_run1` 100%、亀は歩行中、放置
0.8-1.2 presents/s、ジャンプ中 3.2 presents/s、E / Exception は 0。

## 追いかけて空振りだったこと

検収の途中で **`t` (タイマーを戻す) を取りこぼしたように見えた**ので、
入力経路の不具合を疑って再現を試みた。結論は**アプリ側の問題ではなく、
私の計測の誤り**:

- スタート地点ではうさぎ (z=3) が亀 (z=2) を隠すので、「亀が戻っていない」
  ように見えていた。
- 前後のキャプチャの間に解析の時間が挟まり、比較していた 2 枚が想定した
  時間差ではなかった。

1 コマンドの中で時刻つきに撮り直すと、**亀がゴールで止まって長く present
していない状態からでも、`t` は 0.8 秒以内に出発点へ戻る** (407 -> 7、
その後 3.4px/s で歩き出す)。取りこぼしは無い。
