# P6 指示書: 走査帯域を減らしてアンダーランを緩和する

> 状態: 計画済 | 更新: 2026-09-01 | 未着手。実機 (P4-Nano + Olimex) が要る。
> P5 は実基板の差し替え用に予約済みなので、この作業は P6 とする

## 何をする話か

起動時・重負荷時に画面下部が一瞬青くちらつく。機構は P4 で確定している
(report/p4.md 項目 6): **PSRAM への書き込みバーストが DSI の走査読み出しを
飢えさせるアンダーラン**で、ブリッジがそのフレームの残りを青で塗る。
`esp_lcd` が `can't fetch data from external memory fast enough` を出すので
**件数で定量観測できる**。

P4 で潰した対策と、残したリードは report/p4.md にある。**残したリードは
3 つとも「供給を増やす」側** (DMA の先読みを深くする / 書き手を平準化する /
ブリッジ FIFO)。この指示書は**それに載っていない 4 つ目**を扱う。

> **需要そのものを減らす。**
> 走査 DMA は「1 フレームのバイト数 x リフレッシュ」を毎秒必ず要求する。
> 本プロジェクトは高解像度も高 FPS も要件ではない (ユーザ判断、2026-09-01)
> ので、ここは掛け算がそのまま効く。

現状の要求は **1280x720 x 3 バイト x 64.65Hz = 178.7 MB/s**
(report/p4.md の 166MB/s は 60Hz で丸めた値)。

## レバーは 2 つ + 最後の札

| 手 | 帯域 | 効き | 危険 |
|---|---|---|---|
| **B1** ピクセル形式 RGB565 | 119.1 MB/s | -33%。DSI リンクの逼迫も同時に解ける | ブリッジが DSI の 16bit を受けるか未確認 |
| **B2** ピクセルクロック 80→60MHz | 134.0 MB/s | -25%。変更は 2 行 | リフレッシュ 48.5Hz をモニタが飲むか |
| B1 + B2 | 89.3 MB/s | **今の半分** | 上の 2 つ |
| (最後の札) 640x480 / 24MHz | 52.6 MB/s | -71% | 4:3 に戻る。16:9 を捨てる |

**B1 と B2 は独立**なので、別々のコミットにして 3 点 (B1 のみ / B2 のみ /
両方) を比べられる形にすること。

## B1: ピクセル形式を RGB565 にする

### 「ブリッジは RGB888 しか受けない」は測った話ではない

`display_backend_ppa.cpp` のコメントと、bring-up コミット 61895b9a の
「the RGB565 -> RGB888 conversion **the bridge requires**」が出どころだが、
**測った記録はどこにもない**。状況証拠は「Espressif の
`esp_lcd_lt8912b` の設定マクロが全部 RGB888」「M5GFX も
`Panel_LT8912B.cpp` は RGB888」の 2 つで、どちらも**そう出荷している**
だけで、できないとは書いていない。

コードを読むと、むしろ逆向きの証拠が出る。

- **ブリッジの DSI 受信側の初期化に bpp を教えるレジスタが無い**。
  `_panel_lt8912b_send_mipi_basic_set()` が書くのは term / settle /
  レーン数 / レーン入替 / hshift / vshift だけ。**入力形式は DSI パケットの
  データ型 (DT) から読んでいる**と考えるのが自然で、それはまさに
  `_dpi.pixel_format` を変えると変わるもの。
- `/* PB1:RGB888 */` (`io_avi` の 0x44 <- 0x10) は **HDMI 出力側の AVI
  InfoFrame**。モニタへの申告であって、DSI 入力の制約ではない。名前が
  紛らわしいだけ。
- **P4 側は在庫内で実証済み**: Tab5 が同じ DPI を RGB565 で回している
  (M5GFX `Panel_DSI.cpp`)。未知はブリッジ 1 個所だけ。

### 触るところ

`display_backend_ppa.cpp` は既に `DSI_FB_BPP` で媒介変数化されている
(Tab5 が 2、NARYAv4 が 3) ので、変更は小さい。

1. `DSI_FB_BPP` 3 -> 2 (NARYAv4 の分岐)
2. `srm.out.srm_cm` を `PPA_SRM_COLOR_MODE_RGB565`
   (入力は元々 RGB565。**SRM の色変換が要らなくなる**)
3. `lgfx_naryav4.hpp` の `_dpi.pixel_format` を
   `LCD_COLOR_PIXEL_FORMAT_RGB565`
4. 初回の黒塗り (`first_frame`) と、LGFX の `Panel_FrameBufferBase` 側の
   色深度が RGB888 前提になっていないかの確認

### 得られるもの

- PSRAM 読み出し **178.7 -> 119.1 MB/s**
- **DSI リンクの占有 96% -> 64%**。2 レーン x 1000Mbps に対し
  80MHz x 24bpp = 1920Mbps で、いまリンクはほぼ満杯。これは
  ちらつきとは別の潜在的な弱点で、B1 はそれも同時に解く
- PPA の書き込みも 2.76MB -> 1.84MB/フレーム。report/p4.md の
  リード 2 (書き手の平準化) に無料で効く

### 外したときの見え方が 2 通りある

原因ごとに顔が違うので、**どちらなのかを必ず記録する**こと。

- **画がずれる / 横に流れる / 端が回り込む** -> DT は通っている。
  `0x1a` / `0x1b` の **hshift / vshift = 3** が 24bpp 前提の値、という筋。
  入力形式で変わる LT8912B の癖どころなので、この 2 つを振って直す。
- **まったく映らない / 砂嵐** -> DSI RX が 16bit の DT を解さない。
  そのときは B1 を捨てて B2 だけ採る。

どちらも一目で分かり、ハードは壊れない。

## B2: ピクセルクロックを 80 -> 60MHz にする

`lgfx_naryav4.hpp` の `_dpi.dpi_clock_freq_mhz` と
`vendor.video_timing.pclk_mhz` の **2 行**。タイミングは 720p の形
(1650x750) のまま、リフレッシュが 64.65 -> **48.5Hz** に下がる。

**P0/P2 の教訓は守られる**: 240MHz PLL の整数分周でなければ LT8912B の
DDS が暴れる、という制約に対し 240/4 = きっかり 60MHz。APLL は使わない。

### モニタ側の下限は垂直ではなく水平

ここが判断の分かれ目。リフレッシュ 48Hz は今どきのモニタならまず通るが、
**効くのは水平周波数の下限** (一般に 30kHz 前後) で、割ると素直に
"out of range" になる。

| pclk | リフレッシュ | 水平周波数 | 帯域 (RGB888) | 見込み |
|---|---|---|---|---|
| 80MHz (現) | 64.65Hz | 48.5kHz | 178.7 MB/s | - |
| **60MHz** | 48.5Hz | **36.4kHz** | 134.0 MB/s | 安全圏 |
| 48MHz | 38.8Hz | 29.1kHz | 107.2 MB/s | 際どい |
| 40MHz | 32.3Hz | 24.2kHz | 89.4 MB/s | まず映らない |

**この 30kHz は一般論であって実測ではない**。48MHz が通るモニタもある。
B2 が効いて、なお足りないときに 48MHz を試す価値はある。

## B3: 計測 (この作業の本体)

**変更を入れることではなく、帯域と件数の関係を知ることが目的**。

- A/B のプロトコルは report/p4.md にある**アンダーラン計数 + 負荷
  プロトコル**をそのまま使う (起動+安定の窓、重負荷 1 分)。
- 比較は **B1 のみ / B2 のみ / B1+B2 / 現状** の 4 点。
- **同一コミットのビルド同士で比べる** (別日の記録と突き合わせない)。

### 何が分かれば成功か

- **件数が帯域に比例して減る** -> 需要削減が効く筋。B1+B2 を採用し、
  それでも残るならリード 1 (DMA 先読み) へ進む。
- **帯域を半分にしても件数が変わらない** -> 律速は平均帯域ではなく
  **書き込みバーストの瞬間風速**。その場合 B1/B2 は採用してもしなくても
  よく (B1 は DSI リンクの余裕として単体で価値がある)、**リード 2
  (書き手の平準化) が本命**と分かる。撤退の判断ができることが価値。

## 受け入れ条件

- 4 点の計測値が report/p6.md に残ること (件数 / 秒、負荷条件つき)。
- 採用した構成で、デスクトップとエディタが安定表示され crash マーカー 0。
- **TAB5 が退行しないこと** (`DSI_FB_BPP` の分岐は NARYAv4 側だけ)。
- モニタ 2 機種以上で映ること (B2 を採るなら必須。48.5Hz の相性は
  plan.md の未確定事項「モニタ相性」と同じ枠)。

## やらないこと

- **ダブルバッファ**。P4 で機構的に無効と結論済み (直すのはティアリング
  であって飢えではない)。混ぜない。
- **640x480 への退避**。16:9 と整数倍拡大を捨てる札なので、B1/B2 が
  どちらも駄目だったときに初めて検討する。
- sdkconfig の PSRAM 設定。既に HEX 200MHz で上限。

## 未確定事項

- LT8912B の DSI RX が 16bit の DT を受けるか (B1 の全部がこれ次第)。
- hshift / vshift が入力形式に依存するか、依存するなら正しい値。
- 48.5Hz を実際のモニタが飲むか (B2)。
