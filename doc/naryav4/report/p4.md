### 見つけた課題 (新規)

1. ~~I2S 再設定の NULL ハンドル~~ → **追調査で無害と判明** (同日)。
   これは esp_codec_dev が open 時に「まだ初期化していない録音側」の
   slot 設定を試みて失敗するログで、録音の実データ経路 (mic_enable 時に
   初期化する RX チャネルの直読み) には関与しない。ログ衛生課題として
   残る (esp_codec_dev へ渡す構成の整理はやるなら別途)。
   **マイクの実測**: 読み出しを L/R ミックスに変更し、有効化のたびに
   スロット別エネルギーを 1 行ログする診断を追加して再検証した結果、
   **入力経路は生きている** — L スロットに変動する実データ
   (暗騒音 msq=1329、別ブートで 1791。R=0 → ES8311 のモノラルは
   左スロットと確定)。スペクトラムが黒く見えるのはこのレベルが表示
   スケールに満たないため。**音への応答 (声・拍手) と、スピーカ実装の
   有無だけが未確認** — MML 連続再生中もレベルが上がらなかったが、
   スピーカが物理的に繋がっていなければそれが正常。ユーザの実機確認
   (Mic Spectrum を開いて声を出す) で決着する。
2. ~~**timesync の RTC 書き戻しが失敗ログを出す**~~ → **解決済み
   (2026-08-30)**。書き側の「チップ無しなら黙って諦める」は P3 で既に
   入っていた (`TimeSync.rtc_board?`) が、**実機に届いていなかった**:
   `flash app_only` は storage 区画を書かないので、flash/ 配下の Ruby は
   古いままだった。`tab5_fs put` で送って再起動し、`RTC write failed` が
   0 件になることを確認した。詳細は report/p3.md の「app_only は
   storage を更新しない」。
3. SD 未挿入時の `sdmmc_card_init failed (0x107)` x2 はカード無しの
   想定内だが、ログ衛生の観点では要検討 (Tab5 も同様のはず)。
4. tab5_input の SCAN 表に `.` (ピリオド) が無く、エディタでの
   ファイル名 `.rb` が打てない (エディタの F5 は拡張子なしだと
   `Run failed`)。SCAN 表への追記で解決する類 (ルート CLAUDE.md 記載の
   手順)。
5. `system_api: 2 mac type is incorrect` が 1 回 (BT MAC。Tab5 でも既知)。
6. **起動時と重負荷時に画面下部が一瞬青くちらつく (既知・許容)**。
   機構は確定済み: PSRAM の書き込みバースト (起動処理・スプライト読み込み)
   が DSI の走査読み出しを飢えさせるアンダーランで、ブリッジがその
   フレームの残りを青で塗る。esp_lcd の割り込みが
   `can't fetch data from external memory fast enough, underrun happens`
   を出すので**件数で定量観測できる** (起動+安定の窓で 20-26 件 ≒
   0.3 件/秒、重負荷 1 分で +8 件。Tab5 でも起動時の同種のちらつきは
   以前からあるとのユーザ証言 — 帯域が 1.5 倍で色が青な分 NARYAv4 で
   目立つ)。
   **試して効かなかったこと** (A/B は同一プロトコルのアンダーラン計数):
   AXI-ICM (sys_icm) のマスタ調停優先度を h264_m1/m2=15、さらに
   gdma_mst1/2=15 まで上げても件数不変 (レジスタ書き込みは reg0 読み返しで
   確認済み)。sys_icm の調停はこの症状の律速ではない。
   **上流確認済み**: esp_lcd の DW-GDMA 設定 (outstanding 5/2、
   chan_priority 1、ブリッジ burst 256 + 空き閾値 768) は IDF master と
   v5.5.4 で同一 — 移すべき修正は無い。
   **効かない対策を先に消しておく (2026-08-31 評価)**:
   - **ダブルバッファは効かない**。二面化が直すのは「書きかけの FB を
     走査してしまう」ティアリングで、書き手と読み手の分離にしか意味が
     ない。今回の飢えの原因は FB への書き込みではなく**無関係な PSRAM
     への書き込みバースト**であり、走査 DMA はどちらの面を読んでいても
     166MB/s を要求し続ける。二面化してもバスの取り合いは変わらず、
     PSRAM を 2.76MB 余計に使うだけ。将来ティアリングを消したくなった
     ときの札としては有効 (この症状とは別物と明記しておく)。
   - AXI-ICM (sys_icm) の調停優先度も上記のとおり実測で無効。

   **残るリード** (再挑戦するならこの順):
   1. **DW-GDMA の outstanding requests (現在 src=5) / chan_priority を
      上げる IDF パッチ実験**。メモリ遅延のスパイクを先読みの深さで吸収
      する方向。esp_lcd は IDF 本体なので、プロジェクト components/ に
      同名コンポーネントを置いて影で上書きする形になる。パッチは数行、
      A/B の計測基盤 (アンダーラン計数 + 負荷プロトコル) は整備済みなので
      実験 1 本 1-2 時間。期待値は「件数が減る」止まりで、ゼロになる
      根拠はない。
   2. **書き手側の平準化**。根本は書き込みバーストの瞬間風速なので、
      スプライト一括読み込み等の大きな PSRAM コピーを分割して息継ぎを
      入れるのが機構的には一番素直。ただしローダ/アプリ側に手が入り
      工事範囲が広い。
   3. DSI ブリッジの FIFO 閾値調整・Espressif への問い合わせ。構造的な
      弱点はブリッジ FIFO が実質 1 ライン未満 (1024 画素 ≒ 80MHz で
      約 13µs) しかないことで、メモリ遅延スパイクへの耐性はここで
      頭打ちになっている。

   **4 つ目のリード (2026-09-01 追加)**: 上の 3 つは全部「供給を増やす」
   側だが、**需要を減らす**手がある。高解像度も高 FPS も要件ではないので、
   RGB565 化 (-33%) とピクセルクロック 60MHz 化 (-25%) で走査要求を半分に
   できる。「ブリッジは RGB888 のみ」が測った話ではないことの確認も含めて
   instruction_p6.md に書いた。

   現状は「致命的でない」のユーザ判断で許容・記録のみ。

## 5. 基板設計への反映事項 (NARYA v4 実基板向けの確定知見)

### 映像 (LT8912B + MIPI-DSI)

- 構成は Olimex 参照回路どおりで成立: 3.3V 単一給電 (1.8V LDO と
  HDMI 用 5V 昇圧はブリッジ側)、25MHz 水晶、DSI 2 lane、I2C 3 面
  (0x48/49/4A)。リセット線は不要だった (GPIO 消費ゼロのまま)。
- HDMI コネクタ回りは 5V/EDID 給電・ESD 保護を Olimex 同等に。
- **表示モードは 1280x720 実 80MHz (64.6Hz)**。ソフト側制約
  (DPI は PLL_F240M の整数分周のみ、APLL 不可) は SoC 由来なので
  実基板でも同じ。64.6Hz のモニタ相性調査 (項目 2) は未了で、
  基板判断には影響しないがリリース判断には要る。
- LT8912B は LCSC C2892102 (QFN-64、Economic 実装可)。発注前に
  部品ライブラリへ先行確保 (hdmi_video_output_study.md の残項目)。

### 電源・リセット

- **PI4IO のような電源シーケンサは不要と実証済み** (常時給電レールで
  display/C6/audio 全部動く)。単純な設計でよい。
- C6 (または無印 ESP32) の EN を P4 の GPIO 1 本で握る形は有効
  (esp_hosted のスレーブリセットに使用。NARYAv4 では GPIO54)。

### 無線スレーブ

- P4-Nano の C6 + SDIO 配線 (CLK=18/CMD=19/D0-3=14-17/EN=54) で
  esp_hosted 1.4.0 が無改造で動くことを実機確認済み (WiFi 接続・NTP・
  HTTP・remote desktop まで)。
- 最終基板は技適表示の都合で**無印 ESP32 が第一候補** (plan 参照)。
  その場合の基板要件: スレーブ側 SDIO 固定ピン (CLK=14/CMD=15/D0=2/
  D1=4/D2=12/D3=13)、全ラインに外付け 51kΩ プルアップ、D2=GPIO12 の
  フラッシュ電圧ストラップ対策 (eFuse VDD_SDIO)。**事前疎通 (項目 4) は
  未実施** — 基板発注前に必ず devkit で行う。

### 音声

- **ES8311 1 チップ + NS4150B (EN は GPIO 直結)** で確定。PI4IO 経由に
  しない。I2C はディスプレイと共有バスで問題なし (0x18 と 0x48 系)。
- 47160Hz はコーデックの係数表に無いため「48000 として設定 → I2S のみ
  実レートへ再設定」で運用 (ソフト対応済み。基板要件なし)。
- マイクは ES8311 の MIC1 にアナログ接続 (P4-Nano 同等)。入力経路は
  数値で生存確認済み (L スロット・モノラル、暗騒音レベルまで観測)。
  **マイク回路の最終確定は声への応答の実機確認後** (課題 1 参照)。

### その他

- **デバッグ USB は CH343 (UART ブリッジ) 方式を推奨**。稼働中に
  リセット無しで覗ける S3 型の観測性が NARYAv4 の開発体験を大きく
  改善した (Tab5 の USB-Serial-JTAG はポートを開くだけでリブート)。
- chip rev: 新しいロットの P4 は v3.1 (rev 範囲は sdkconfig で
  基板ごとに固定。Tab5 v1.0 とバイナリ非互換な点を運用に織り込む)。
- RTC: 最終基板で搭載するなら RX8130 が既存ドライバ互換で最小工数。
  非搭載でも timesync で運用可能なことは実証済み (課題 2 の後始末は
  どちらでも必要)。
- SD ピンは Espressif 参照設計 (Tab5/P4-Nano と同一) を踏襲する。
