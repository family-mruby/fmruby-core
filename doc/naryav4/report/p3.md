## WiFi とリモートは無改造で通っていた

P2 の時点で既に C6 が上がっており (`Base transport is set-up`)、**P3 で手を入れる前から
WiFi 接続・IP 取得・mDNS・remote desktop がすべて動いていた**。P1 で入れた SDIO ピンと
esp_hosted 1.4.0 の適合はこれで実証された。

```
I wifi: mDNS hostname: fmruby.local
I esp_netif_handlers: sta ip: 192.168.10.15, mask: 255.255.255.0, gw: 192.168.10.1
W rd_http: development remote control is enabled (/app/launch, /app/kill, /app/list, /fs/*)
I rd_http: Remote desktop ready: http://192.168.10.15/ (fps_cap=15 q=80)
```

**注意 (instruction の罠が現実だった)**: mDNS 名 `fmruby.local` は Tab5 と共通なので、
両方が同じネットワークにいると tab5_* ツールがどちらに繋がるか分からない。今回は
Tab5 が繋がっていなかったため素直に解決したが、**IP を直指定するのが安全**
(`tab5_ip` の `ip` 引数)。

boot.c の `modern_radio_init_task` からは NARYAv4 の分だけ display 待ちを外した。
Tab5 は C6 の電源が PI4IO 経由で display に依存するが、**NARYAv4 の C6 EN は
esp_hosted 自身が握る GPIO (`CONFIG_ESP_HOSTED_SDIO_GPIO_RESET_SLAVE=54`)** なので、
待つ理由がないどころか、無関係な故障に無線を巻き込むだけだった。

## Tab5 固有ドライバの除去

- `main/CMakeLists.txt` の P4 ソース一覧を分岐し、NARYAv4 から `touch_task.c` と
  `tab5_keyboard.c` を外した。boot.c の init 呼び出しと include も同じ条件で囲った。
- **これは「ログが減る」話ではない**。P2 report に書いた「tab5_kbd が I2C_NUM_0 を
  取りに来るが、NC ピンで先に失敗するので衝突していないだけ」という順序頼みの安全を
  根絶するのが目的。I2C_NUM_0 は display が所有するバスである。

## RTC は静かに諦める

NARYAv4 に RTC チップは無い。`fmrb_rtc_sync_system_clock()` は NARYAv4 で
`FMRB_ERR_NOT_SUPPORTED` を返して I2C を触らない (呼び出し側の kernel は元から
この戻り値を黙って受ける実装だった)。timesync サービスの `write_rtc` も
`FmrbConst::BOARD` を見て何もせず戻る。結果、毎ブート出ていた 3 本の警告
(`RTC did not answer` / `Clock not set from RTC` / `RTC write failed`) が消えた。

時刻は timesync が毎ブート入れる。**電源を切ると時刻は失われる**のが仕様。

## 音声: ES8311 1 チップ構成

`audio_p4_hw.c` をボード分岐した。Tab5 (ES8388 + ES7210 + PI4IO アンプ) の経路は
そのまま、NARYAv4 は:

- コーデックは **ES8311 1 個** (I2C 0x18)。再生も録音も同じチップなので
  `codec_mode = BOTH` / `dev_type = IN_OUT` で開く。
- I2C は **display が作った I2C_NUM_0 のバスを借りる**。ハンドルが取れなければ
  諦める (同じピンに 2 本目のバスを作らない)。
- I2S は pin_assign の値 (MCLK=13 / SCLK=12 / LRCK=10 / DOUT=9 / DIN=11)、
  ポートは Tab5 と同じ I2S_NUM_1 の全二重。
- アンプ EN は **GPIO53 を esp_codec_dev の `pa_pin` に渡す**。コーデックの設定が
  終わってから上がるので、電源投入の過渡音を鳴らさずに済む。

### 罠 1: 47160Hz は ES8311 の係数表に無い

最初の実機ログ:

```
E ES8311: Unable to configure sample rate 47160Hz with 12072960Hz MCLK
```

ES8311 ドライバは (MCLK, レート) で引く係数表を持ち、**標準レートしか載っていない**
(8k / 11.025k / 12k / 16k / 22.05k / 24k / 32k / 44.1k / 48k / 64k / 88.2k / 96k)。
APU 由来の 47160Hz は無い。ES8388 は算術で分周を出すのでこの問題が無かった。

**表の中身は MCLK に対する比**であり、MCLK = 256 x LRCK であれば 48000 の行の比が
そのまま使える。よって:

1. `esp_codec_dev_open` には **48000 と伝えて表を引かせる**
2. その直後に **I2S のクロックだけ 47160 に戻す**

ES8311 はスレーブで LRCK に従い、MCLK も同じ比で下がるので、**音程は正確なまま**。

### 罠 2: レートを戻すにはチャンネルを止める必要がある

上の 2 を素直に書くと失敗した:

```
E i2s_std: i2s_channel_reconfig_std_clock(381): invalid state, I2S should be disabled
E audio_p4: could not restore the 47160 Hz link clock: 259
```

`esp_codec_dev_open` はチャンネルを有効のままにして返る。`i2s_channel_disable` →
reconfig → `i2s_channel_enable` で囲って解決。まだ何も再生していない時点なので
音は途切れない。

```
I audio_p4: link clock back to 47160 Hz (codec configured from the 48000 Hz coefficients, same 256x ratio)
I audio_p4: audio ready: ES8311 47160 Hz 16-bit stereo (APU 15720 Hz x3)
```

### 罠 3: 音量設定が Tab5 のチップ直叩きだった

`audio_p4_hw_set_volume` は ES8388 のレジスタ (0x1A/0x1B) を display の I2C サービス
経由で直に書く実装だった。**NARYAv4 では存在しないチップに書きに行くので、音量を
下げることも消すこともできない**。Tab5 でこの実装になっているのは lgfx が同じ
コントローラをレジスタ直叩きするからで、**NARYAv4 にはその制約が無い**。標準 API
(`esp_codec_dev_set_out_vol` + 0 のとき `set_out_mute`) に分岐した。

### マイク: 経路は開いたが無音のまま (未解決)

`/app/modern/mic_spectrum.app.rb` を遠隔起動して確認した結果:

```
I audio_p4: i2s full duplex constituted: yes
I audio_p4: microphone on: ES8311 47160 Hz 16-bit stereo
```

全二重は成立し RX も回っているが、**スペクトラムは完全に無音**。ES8311 の
アナログ PGA が既定 0dB なので `esp_codec_dev_set_in_gain(30dB)` を入れたが、
**変化なし** (呼び出し自体はエラーを返していない)。

静かな部屋で音源が無かっただけの可能性も**まだ排除できていない** (確認時にユーザが
実機の傍にいなかった)。次に試す順:

1. 実際に音を立てて確認する (これが未実施)。
2. 効かなければマイクの接続先を疑う。回路図では ES8311 の MIC1 だが、
   ドライバの既定入力が別系統なら `es8311_codec_cfg_t` の設定で選び直す必要がある。
3. `digital_mic` フラグ、`hw_gain`、デジタル側のゲイン
   (`esp_codec_dev_set_in_channel_gain`) も未検証。

## USB 入力は P2 の時点で動いていた

受け入れ条件 3 は**すでに満たされていた**。P2 で起動時の乱れを切り分けたとき、
ユーザが実機で「NSF プレーヤ起動」「ランチャー右クリック再スキャン」を行っている。
これは USB キーボードとマウスがなければできない操作である。usb_task は S3/P4 共通で、
P4-Nano の USB-A (HS OTG PHY) でも無改造で列挙されている。

**記録の読み落としだった**: 実機の観察はユーザの操作記録の中にも入っている。
「未確認」に積む前に、それまでのやりとりで何が実証済みかを見ること。
