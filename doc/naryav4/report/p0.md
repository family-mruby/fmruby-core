# P0 report: 部材と単体疎通

> 状態: 完了 | 更新: 2026-08-29 | P0 完了。採用モード 800x600@60 をユーザ目視 + DDS テレメトリの両方で確認。720p60 は APLL ジッタで不成立と確定

部材 (ESP32-P4-Nano / Olimex MIPI-HDMI / FPC-15) は調達・接続済み。
両ボードの公開回路図を取得して照合した
(取得物は family-mruby/tmp/naryav4_hw/ に置いた。Olimex は KiCad ソースつき)。

## P0-2: DSI コネクタの照合 — 互換 OK

両者とも **Raspberry Pi 15pin DSI と同一のピン配置**だった
(Waveshare 側は回路図に "15PIN--PI4B"、Olimex 側は
"Raspberry Pi 1,2,3 and 4 Compatible" と明記)。

| pin | P4-Nano (J1) | Olimex MIPI-HDMI | 一致 |
|---|---|---|---|
| 1,4,7,10,13 | GND | GND | o |
| 2,3 | DSI_D1_N / D1_P | DSI_DATA1N / 1P | o |
| 5,6 | DSI_CLK_N / CLK_P | DSI_CLKN / CLKP | o |
| 8,9 | DSI_D0_N / D0_P | DSI_DATA0N / 0P | o |
| 11,12 | I2C SCL (GPIO8) / SDA (GPIO7) | I2C_SCL / I2C_SDA | o |
| 14,15 | 3.3V | +3.3V 入力 | o |

- Olimex 側は 3.3V 単一給電で、HDMI 用 5V と LT8912B 用 1.8V は
  基板上で生成する。P4-Nano の 3.3V レール (3A 級 DCDC) で賄える。
- I2C は Olimex 基板上で 3.3V→1.8V レベルシフトされる。プルアップは
  P4-Nano 側に 2.2k 実装済み。
- 残る実物確認は **FPC ケーブルの接点面の向き**のみ (RPi DSI 用の
  同面接点 15pin type A が正)。

## P4-Nano の実ピン (回路図から確定。P1 の pin_assign に使う)

- **DSI**: 専用パッド 2 lane (D0/D1/CLK)。
- **I2C (GPIO7=SDA / GPIO8=SCL)**: DSI コネクタ・CSI コネクタ・
  ES8311 codec (0x18)・ヘッダに共通の 1 バス。LT8912B (0x48 系) と
  ES8311 が**同居**するので、Tab5 の「display が I2C を所有し audio が
  バスハンドルを借りる」パターンがそのまま使える (ピンだけ 31/32→7/8)。
- **C6 (esp-hosted SDIO)**: CLK=GPIO18, CMD=GPIO19, D0=14, D1=15,
  D2=16, D3=17 (C6 側 IO19/18/20/21/22/23 に対応)、C6 EN=GPIO54。
  Tab5 (CMD=13/CLK=12/D0=11/D1=10/D2=9/D3=8/RST=15) と全部違う。
- **SD (SDMMC)**: CLK=43, CMD=44, D0=39, D1=40, D2=41, D3=42 —
  **Tab5 と同一** (Espressif 参照設計どおり)。
- **audio (ES8311)**: MCLK=13, SCLK=12, LRCK=10, DSDIN(P4→DAC)=9,
  ASDOUT(ADC→P4)=11。アンプ NS4150B の EN=GPIO53。マイクは
  ES8311 の MIC1 にアナログ接続。
- **USB-A ホスト**: HS OTG PHY 専用パッド (Tab5 と同じ)。VBUS は
  電源スイッチ IC 経由。
- **USB-C (デバッグ)**: **CH343P の UART ブリッジ** (UART0=GPIO37/38) +
  DTR/RTS 自動リセット回路。つまり**シリアル運用は S3 型**
  (ポートを開いてもリセットされない attach が可能なはず)。Tab5 の
  USB-Serial-JTAG (開くだけでリブート) とは逆で、観測性は良くなる。
  要実機確認。
- **Ethernet PHY (IP101GRI)**: GPIO28-31, 34, 35, 49-52 を基板上で占有
  (RMII)。Ethernet 非対応方針でもこれらのピンは NARYAv4 では
  予約扱いにする。GPIO35 は BOOT ボタン兼用。
- flash は外付け 16MB (GD25Q128E)、C6 モジュールは C6-MINI-1-N4。

## P0-4: chip revision 実測 — v3.1 (2026-08-29)

- usbipd 経由で attach (rake attach を CH343 1a86:55d3 対応に拡張、
  .env の VIDPID は Tab5 と併記)。/dev/ttyACM1 に **cdc_acm** で認識
  (CH343 は CDC-ACM 準拠。専用ドライバ不要)。
- esptool 実測: **ESP32-P4 revision v3.1**。Tab5 (v1.0) と違い、IDF の
  rev <3.0 / >=3.0 相互排他により **Tab5 用バイナリは P4-Nano に焼けない**。
  sdkconfig.defaults.naryav4 では `ESP32P4_SELECTS_REV_LESS_V3` を外し、
  REV_MIN を v3.x 系にする。
- DTR/RTS 自動リセットで esptool が問題なく入った。「シリアルは S3 型
  (開きっぱなし運用が不要、attach 中リセットなしで覗ける見込み)」を実機で
  裏づけ。注意: `rake check-port` は全ポートをプローブするので attach 中の
  Tab5 をリセットしてしまう。P4-Nano と Tab5 を併用する間はポート直指定。

## P0-3: LT8912B サンプルの HDMI 表示 (2026-08-29、完了)

作業場所: family-mruby/tmp/naryav4_hw/display/ (公式 EV ボード BSP の
display example。改変は components/ 配下へのローカル化で行い、
managed_components は触っていない)。

### 確定した成果

- **HDMI 出力は出る**: 800x600@60 で LVGL デモが表示された。ロゴ・文字の
  判読も確認。FPC の向き・DSI 2 lane・I2C 共有バス・LT8912B ブリッジの
  動作はここで実証済み。**ただし「安定」の観察は短時間で確度が低く、
  追試が必要** (起動後しばらく横滑りの残像があり、その後安定して
  見えた、が長時間の確認はしていない)。
- **IDF 5.5.4 のビルド摩擦 4 件** (すべて回避策あり):
  1. esp_lvgl_port 2.9.0 が「IDF 5.5.0 以上なら on_frame_buf_complete が
     ある」と仮定するが v5.5.4 の esp_lcd に無くコンパイル失敗。版ガードを
     5.6 に上げて旧コールバック (on_refresh_done) を使わせる 1 行パッチ。
  2. HDMI は RGB888 必須 (`CONFIG_BSP_LCD_COLOR_FORMAT_RGB888`)。
  3. 画像アセット生成の pip install が IDF の venv に書けず黙って失敗
     (undefined reference になる)。`pip install --target` + PYTHONPATH で
     手動生成して回避。
  4. デモの main が HDMI 構成 (タッチ無し) で NULL の入力デバイスを触って
     即パニック。NULL ガードで回避。
- **720p が出ない根本原因を 1 つ特定**: IDF 5.5.4 の DPI クロックは
  PLL_F240M (240MHz) の**整数分周 + 丸め**で作られる
  (hal の mipi_dsi_hal_host_dpi_calculate_divider)。
  要求 64MHz → 実 60MHz (-6.25%)、要求 70MHz → 実 80MHz (+14%)。
  40MHz (800x600) だけが正確で、症状 (800x600 安定 / 720p 常時破綻 /
  1280x800 間欠ロック) と完全に一致した。**公式 FAQ の「HDMI は IDF 5.4
  以前推奨」の実体はこれではないかと疑っている (5.4 との差分は未検証)**。
- **DPI クロック源は APLL に切替可能** (`dpi_clk_src`)。APLL 128MHz→64MHz、
  148.5MHz→74.25MHz の正確なクロックを供給できることを確認 (表示が出る
  ようになった)。
- **シリアル観測**: CH343 はポートを開く際に DTR で自動リセットが掛かる
  場合と掛からない場合がある (毎回ではない)。稼働中の attach 観測は可能。
  ブート冒頭からのログ採取は手順が要る (未整備)。

### 未解決: 720p での LT8912B DDS ハンチング

APLL で正確な 74.25MHz (CEA 標準 1650x750, VIC 4) を入れても、
**LT8912B の DDS (HDMI クロック合成) が収束しない**。ドライバに常駐の
DDS 読み出しログ (毎秒) を仕込んで計測した結果:

- 入力側は健全 (vsync 計数 751 ≒ vtotal 750、hsync 計数も一定)。
- **DDS 出力が 73.6〜74.4MHz を毎秒揺れ続ける** (±0.5% のハンチング)。
  このジッタをモニタが拒否し「ほぼ無表示・まれに 1-2 秒映る」となる。

試して**撤回した仮説**:

- ティアリング (描き換え起因) → 静止画でも乱れるので棄却。
- 描画時の PSRAM 帯域競合 → LVGL の再描画を完全停止しても変わらず棄却。
- DDS の初期値 (種) を実クロックで再シード → ドライバの DDS 表は約 29MHz
  相当の種で始まり追従ループ任せと判明し、種の上書きを 3 方式試したが、
  0x51 レジスタの意味 (0x80 で終えると表示するが周期スリップ、
  0x00 で終えるとほぼ無表示) が黒箱で、**いずれも改善せず撤回**。
  ドライバは純正テーブルに戻した。
- なお標準 CEA タイミング化には効果があった (64MHz CVT-RB 時代の
  「10 秒周期の左シフト (モニタ再ロック)」は消えた)。

### 現在の仮説 (未検証、優先順)

- H1: **APLL のジッタ**。APLL は分数分周 (SDM) の音声用 PLL で、整数分周の
  PLL_F240M よりジッタが大きい。DDS がそれを追って発振している。
  800x600 (PLL_F240M 整数分周) だけ安定するのと整合。
- H2: DDS 追従ループの定数 (しきい値・ステップ、レジスタ 0x1e-0x5c) が
  高ピクセルクロックに不適。Lontium 非公開領域。Linux カーネルの
  lontium ドライバの設定列と突き合わせる価値がある。
- H3: 段階的フォールバック: 800x600 は完全動作するので、720p が解けなくても
  P0/P2 は前へ進める (fmruby の 3x 整数スケールは崩れるが、
  2x スケール + 余白などの代案は P2 で検討可能)。

### 要件の緩和 (2026-08-29 ユーザ判断)

**解像度と FPS は強く求めない。緩和で安定するならそちらを取る。**
この前提での選択肢の整理:

| モード | クロック | 安定性 | fmruby 426x240 の載せ方 |
|---|---|---|---|
| 800x600@60 | 40MHz = PLL_F240M/6 (正確・低ジッタ) | **実証済み安定** | 1.5x = 639x360 + 黒縁 (PPA は 1/16 刻みで 1.5x 可)。2x は 852 幅で入らない |
| 1024x768@60 | 65MHz (APLL 130/2 が必要) | 未検証 (APLL ジッタ懸念は 720p と同じ) | **2x = 852x480 + 黒縁** (整数スケール) |
| 1280x720@30 | 37.125MHz (APLL 148.5/4) | 未検証。低クロックで DDS の位相余裕が増え、APLL でもロックする可能性 | 3x (回転なし)。ただし 30Hz をモニタが受けるかは機種依存 |
| 1280x720@60 | 74.25MHz (APLL) | **DDS ハンチングで不成立** (現状) | 3x (理想形) |

PLL_F240M の整数分周で正確に作れる標準モードは実質 800x600@60 のみ。
緩和方針なら **800x600@60 が第一候補**で、これは既に動いている。

### 追試と切り分けの結果 (2026-08-29 実施) — 原因確定

計画した実験を実施し、**原因は P4 の APLL のジッタ**と確定した。

1. **800x600 追試**: 目視安定 + テレメトリで裏づけ。DDS は約 20 秒
   ハンチング (39.4-39.9MHz) の後、**ワードが ±8 カウントで静止**する
   完全ロックに収束。過去の「しばらくして安定した」観察と一致し、
   ロックの数値的定義 (ワード静止) が得られた。
2. APLL 297MHz÷4 = 74.25MHz: 100 秒後も ±0.3% でハンチング。VCO を
   上げても直らない。
3. 720p30 (CEA VIC 62, 37.125MHz): **不成立**。htotal 3300 のライン周期
   (88.9µs) が LT8912B のライン周期測定 (16bit、hsync 計数が 65535 で
   飽和) のレンジ外で、DDS は 55-62MHz を彷徨う。長い htotal のモードは
   使えない。
4. Linux カーネルの lontium ドライバと突き合わせ: 構造・順序はほぼ同一で、
   **差分は DDS の種の値のみ** (Linux は約 74MHz 相当、esp 版は約 29MHz
   相当)。種を 74.25MHz 相当に直し、video_on 相当の順序 (video setup →
   DDS 設定 → RX リセットをストリーム開始後に再送) も再現したが、
   74.25MHz のハンチングは解消せず。
5. **決定打 (クロック源の分離実験)**: 同じ 40MHz・同じ 800x600 で
   クロック源だけを替えた。PLL_F240M/6 → 完全ロック、APLL 120MHz/3 →
   60 秒後も ±0.3% で揺れ続けロックせず。**LT8912B の DDS は APLL
   (分数 SDM) 由来の DPI クロックにロックできない**。
   なお APLL 160MHz は範囲外らしくエラーなしでクロックが死に、DSI 初期化
   で main タスクがスピンして task_wdt が出る (地雷として記録)。

### 結論

- 74.25MHz は APLL でしか作れず、APLL では DDS がロックしない。よって
  **IDF 5.5.4 では 720p60 は不成立**。
- **採用モード: 800x600@60 (PLL_F240M/6 = 正確な 40MHz)**。二度の検証で
  安定を確認済み。fmruby は 426x240 の 1.5x = 639x360 + 黒縁で載せる
  (P2 で実装)。
- 将来の再挑戦条件: IDF が整数分周で 74.25MHz を作れるクロック源を
  提供する、または LT8912B の DDS ループを APLL ジッタに耐える設定に
  できる資料が得られたとき。1024x768@60 (65MHz、2x 整数スケール) も
  同じ理由 (APLL 必須) で現状不成立である点に注意。

### 受け入れ (2026-08-29)

最終構成 (800x600@60、PLL_F240M/6、静止画テスト) で、ユーザ目視
「静止して見える」+ DDS テレメトリのロック (ワード静止) を確認し、
P0 の受け入れ条件 (HDMI モニタへの安定表示) を満たした。P0 完了。
