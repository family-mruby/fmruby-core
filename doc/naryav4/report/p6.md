# P6 report: 青ちらつき (DSI アンダーラン) の解消

> 状態: 完了 | 更新: 2026-09-27 | **フレームバッファの先頭を 4KB 境界に揃える (B0) だけで、アンダーランが全窓で 0 件になった** (前は起動で 16-18 件、重負荷 1 分で 6-7 件)。ユーザの目視で表示良好・ちらつき消失を確認。B1 (RGB565) はブリッジが映さず不採用。B1' と B2 は行わず、手札として残す。コミット 858f6aa0 (feature/naryav4-p6)

## 要約

- 指示書の本筋は「帯域を減らす」(B1 RGB565 / B2 60MHz) だった。途中で、アンダーランの件数を決めているのは**帯域ではなくフレームバッファの先頭の揃い方**だと分かり、B0 (4KB 境界に揃える) を採った。
- B0 は RGB888・80MHz・1280x720 のまま、形式もタイミングも変えない。変更は `main/drivers/display_p4/lgfx_naryav4.hpp` の 1 ファイル (NARYAv4 専用)。
- 内蔵 RAM の増分は 0 (静的な D/IRAM は同値、待機時の空きは誤差内)。PSRAM は 4,636 バイト減る (詰め物 4,608 + 管理領域)。
- B1 (RGB565 を DSI にそのまま流す) では、アンダーランは 0 件になったが、**ブリッジがモニタに映さなかった** (青と黒の繰り返し)。これが P6 の途中で出た「映らない」の唯一の原因だった (下の切り分け)。

## 1. 計測の手順

report/p4.md には手順の実体 (窓・負荷) が書かれていなかったので、ここで定めた。
スクリプトは scratchpad の `protocol.rb` (Ruby 標準ライブラリのみ。取り込むなら tools/ へ)。

- 毎回 `serial_start reset:true` で板をリセットし、そこを 0 秒とする。
  シリアルの記録に出る `can't fetch data from external memory fast enough, underrun happens` の行を数える。
- 窓 A (起動と安定): 0-120 秒。操作なし。
- 窓 B (待機): 120-180 秒。デスクトップのまま操作なし。
- 窓 C (重負荷): 180-240 秒。10 秒ごとに、HTTP (`/app/kill` → `/app/launch`) でアプリを入れ替える。
  raycaster → rpg_demo → kamon を 2 周。起動時の画像読み込みと全画面描画が PSRAM への書き込みの山を作る。
- 同じコミットのビルド同士で比べる。書き込みは app 区画だけ (/home は保つ)。

## 3. 切り分け (「映らない」はいつからか)

B1 を焼いた直後、ユーザから「青と黒を繰り返している」、続いて「ちょっと前から表示されていなかった」との報告があった。それまで P4-Nano に焼いたファームは、シリアルだけで「起動した」と判断していて、モニタは誰も見ていなかった。そこで、保存してあったビルドを app 区画 (factory 0x10000) だけに書き戻し、ユーザの目視で二分探索した。

| 順 | ファーム | 版 | FB の先頭 | 起動窓のアンダーラン | V sync の検出値 | 目視 |
|---|---|---|---|---|---|---|
| 1 | P2b-2 基準 (上流 Spinel 取り込み前) | ac860133 | (ログ取得なし) | (ログ取得なし) | - | 映る |
| 2 | P2b-2 修正版 | b2126ae1 + 6391833f | 0x49146000 | 0 | 750 | 映る |
| 3 | P3 最終 | 8d1c38b3 | 0x49144dc0 | 17 | 750 | 映る |
| 4 | develop | adced507 | 0x49144dc0 | 16 | 314 | 映る |
| - | B1 (RGB565) | adced507 + B1 | 0x49144dc0 | 0 | 29 | **映らない** |

- **映らなかったのは B1 だけ**。「ちょっと前から」は B1 を焼いたとき (この作業の中) だった、ということになる。
- ブリッジの `Detected MIPI input` の V sync の値 (750 / 314 / 29) は、映るかどうかと対応しない。ドライバが初期化の途中で 1 回読んでログに出すだけの値で、同じビルドでも起動ごとに変わる (develop で 750 と 314)。判定には使えない。
- 1 の起動ログは取っていない (書き込みの時点で serial_start の許可が無かった)。
- **副産物**: 2 と 3 の間で、FB の先頭が 0x49146000 から 0x49144dc0 に動き、アンダーランが 0 件から 17 件に変わった。形式もタイミングも同じ。これが B0 の手がかりになった。修正版を焼き直した 3 回の計測でも、全窓 0 件で再現した (偶然ではない)。

## 4. B0: フレームバッファを 4KB 境界に揃える

### 機構の見立て

- DPI の走査 DMA (DW-GDMA) は、フレームバッファを PSRAM から毎秒 178.7 MB 読み続ける。
- AXI のバーストは 4KB 境界をまたげない。先頭が 64B 揃い (0x...4dc0 = 4KB 境界から 3,520 バイト) だと、バーストが 4KB ごとに分割されて取引の数が増え、読み出しの余裕が減る。そこへ他の PSRAM 書き込みの山が重なると、ブリッジの FIFO (1 ライン未満) が尽きてアンダーランになる。
- 4KB に揃うと分割が起きず、同じ帯域・同じ負荷でも尽きない。
- 確かめたのは「4KB に揃うと 0 件、64B 揃いだと 16-18 件」まで。256B 揃いで足りるか、どの粒度で効くかは試していない (分割が起きるかだけなら、バースト長の倍数に揃えば足りるはず)。

### 実装

- IDF 5.5.4 の esp_lcd DPI は、フレームバッファを `heap_caps_calloc(SPIRAM | 8BIT | DMA)` で自分で確保する。揃えはキャッシュライン (64B) だけで、呼び出し側からバッファも揃えも渡せない。
- IDF は変えずに、確保の直前にヒープの形を整える (`align_next_frame_buffer()`)。
  1. 同じ大きさ・同じ caps で試しに確保して離し、着地点を見る。
  2. 境界からずれていれば、その場所に PSRAM の詰め物を置く。大きく取ってから realloc で縮めると、試しの確保と同じ空き領域の先頭に固定できる (小さい malloc はどの穴に入るか分からない)。
  3. 着地が揃うまで、詰め物を realloc で伸ばす (最大 8 回)。
- 詰め物は解放しない (パネルは終了まで生きる)。ポインタも持たないので内蔵 RAM は増えない。
- うまくいかなければ詰め物を捨て、従来どおりの場所で続行する。起動ログの `HDMI 1280x720 up, RGB888 fb @0x49146000 (aligned, pad 4608)` が aligned / UNALIGNED を示す。
- 実測では 1 回の調整で揃い、詰め物は 4,608 バイトだった。
- 前提: パネルの生成はブート初期に表示タスクが行う。試しの確保から driver の確保までの間に、別のタスクが PSRAM を取ると外れうる。その場合も UNALIGNED のログが出るだけで、表示は従来どおり。

### TAB5 の退行確認

- 変更したのは `lgfx_naryav4.hpp` だけで、このヘッダは `FMRB_HW_NARYAV4` のときだけ include される。
- TAB5 を clean_all からビルドし、静的な D/IRAM とサイズを P2c / P3 の TAB5 (183,448) と比べた。結果は 7 節。

## 5. 見立てと違った点

- 指示書は、アンダーランを「平均帯域」か「書き込みの瞬間風速」のどちらかで説明できるとしていた。実際には、**同じ帯域・同じ負荷のまま、フレームバッファの置き場所だけで 16-18 件と 0 件に分かれた**。律速は走査の読み出しの効率 (バーストの分割) で、帯域はその次だった。
- B1 がアンダーランを 0 件にしたのは、帯域を 2/3 にして余裕を取り戻したためと見る (揃い方は基準と同じ 64B)。帯域を下げても直るが、揃えれば帯域を下げずに直る。
- 「ブリッジは RGB888 しか受けない」は、少なくとも DSI にそのまま 16bit を流す形では**本当だった**。指示書の「レジスタに bpp を教える口が無いので DT から読むはず」という推論は外れた。
- p4.md の「DMA の先読みを深くする (リード 1)」「書き手の平準化 (リード 2)」は、どちらも手を付けずに済んだ。
- 同じソースでも、PSRAM の確保量が変わるだけでフレームバッファの位置が動き、件数が 0 件と 17 件の間で跳ぶ。P3 以降のビルドで件数が増えていたのは、Spinel ext 化などで確保量が変わった副作用だった。

## 6. 手札 (今回は行わない)

B0 で全窓 0 件になったので、帯域を下げる手は採らない。将来、解像度・リフレッシュ・負荷が上がって足りなくなったときの手札として残す。

- **B1: RGB565 を DSI にそのまま流す**。ブリッジ (LT8912B) がモニタに映さなかった (青と黒の繰り返し)。esp_lcd と lt8912b のエラーは無く、同期の検出値も出ているので、DSI の 16bit の DT をブリッジが画素として受けないと見る。変更は `scratchpad/p6/b1_rgb565.patch` に退避した。PPA の出力形式・カーソルの部分書き・LGFX の色深度まで含めて動作は確認済み (描画は回り、アンダーランは 0 件)。
- **B1': フレームバッファは RGB565、DSI の上は RGB888**。esp_lcd DPI の `in_color_format = LCD_COLOR_FMT_RGB565` / `out_color_format = LCD_COLOR_FMT_RGB888` で、P4 の DSI ブリッジが変換して送る (IDF 5.5.4 の esp_lcd_panel_dpi.c が対応している)。ブリッジから見た入力は今と同じなので映る見込み。PSRAM の読み出しは 119 MB/s (-33%)、フレームバッファは 1.84MB (-0.92MB)。DSI リンクの占有 (96%) は下がらない。B1 の patch の backend 側はそのまま使える。
- **B2: ピクセルクロック 80 → 60MHz** (240/4 で PLL の整数分周。リフレッシュ 48.5Hz、水平 36.4kHz)。`lgfx_naryav4.hpp` の 2 行。帯域 134 MB/s (-25%)、DSI リンクの占有も下がる。モニタが 48.5Hz を受けるかは未確認 (plan.md の「モニタ相性」の枠)。

## 8. 提案

- **Tab5 のフレームバッファの揃い方を調べる価値がある** (今回は調べていない)。Tab5 にも起動時の同種のちらつきがあるというユーザ証言がある (p4.md)。Tab5 は 720x1280 RGB565 で帯域は 2/3 だが、M5GFX の Panel_DSI 経由で同じ esp_lcd DPI が同じ方法でバッファを確保するので、置き場所しだいで同じ分割が起きうる。確かめ方: 起動ログにフレームバッファの番地を出し、アンダーランの行を同じ手順で数える。揃っていなければ、同じ詰め物の方法が使える。
- **上流 (Espressif ESP-IDF) への PR / Issue 候補**: esp_lcd の DPI (`esp_lcd_dpi_panel_config_t`) にフレームバッファの揃えを指定する口が無い。案は 2 つ。
  - `fb_alignment` のような設定を足し、`heap_caps_aligned_calloc` で確保する。
  - 呼び出し側が確保したバッファを渡せるようにする。
  - 理由は上流の関心で書く: 「DW-GDMA の読み出しバーストが 4KB 境界で分割され、PSRAM が混んだときにアンダーランしやすくなる。揃えると、同じ条件でアンダーランが 16-18 件から 0 件になった (1280x720 RGB888 80MHz、2 lane)」。
  - あるいは、driver が既定で 4KB (または DMA のバースト長) に揃えて確保するのが一番簡単。
  - 上流の master も同じ確保のしかたかは、提出前に確かめる。
  - 台帳 (Spinel の pr_candidates.md とは別) に入れるかは親の判断。
