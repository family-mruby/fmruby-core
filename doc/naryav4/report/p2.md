# P2 report: NARYAv4 表示 bring-up (HDMI)

> 状態: 完了 | 更新: 2026-08-30 | P4-Nano + LT8912B の HDMI に 1280x720 で起動時から安定表示。**P0 の採用モード 800x600@60 は覆した** (要求 40MHz が実機では 39.70MHz しか出ていなかった)

## 結果

`FMRB_HW_TARGET=NARYAv4` のバイナリを P4-Nano に焼くと、HDMI モニタに
fmruby のデスクトップが **1280x720 で、起動した瞬間から安定して**出る。

| 受け入れ条件 | 結果 |
|---|---|
| デスクトップが安定表示 (最終判定は目視) | **満たした**。「起動時から安定してる」(2026-08-30) |
| 内部 426x240 を整数倍で中央配置、回転なし | **3x = 1278x720**。黒縁は左右 1px のみ |
| crash マーカー 0、GFX STATS が出る | 0 件。`render: 5 frames/5s avg=28ms max=29ms`、`GFX STATS: 10.5 cmds/s, 1.0 presents/s` |
| TAB5 退行なし | ビルド成功 (0x58f3c0 → 0x58f3f0、+48 バイト)。sim スモーク (デスクトップ + エディタ起動 + 打鍵)、`rake test` (golden 103/103 ほか) とも通る |

## 確定した表示構成

| 項目 | 値 | 備考 |
|---|---|---|
| 解像度 / タイミング | 1280x720、CEA 720p (htotal 1650 / vtotal 750、hfp 110 / hs 40 / hbp 220、vfp 5 / vs 5 / vbp 20、両極性 +) | |
| DPI クロック | **80MHz、クロック源は PLL_F240M (既定) の整数分周 (÷3)** | 実測で要求どおり出ていることを確認済み |
| 実リフレッシュ | **64.6Hz** (80MHz / (1650x750)) | 60Hz は諦める。AVI の VIC は 4 |
| DSI | 2 lane、1000Mbps/lane、`disable_lp = true` | ペイロード 1920Mbps = 容量の 96% |
| 色形式 | DSI フレームバッファは RGB888、1280x720x3 = **2.76MB** (PSRAM) | LT8912B は RGB888 入力のみ |
| スケール | PPA SRM で **3x**、回転なし | 426x240 → 1278x720 |
| LT8912B I2C | GPIO7=SDA / GPIO8=SCL、アドレス 0x48/0x49/0x4A | 基板に 2.2k プルアップ |
| 電源シーケンス | 不要 (PI4IO なし)、リセット GPIO もなし | |

**この「実 80MHz + 64.6Hz」は M5GFX が M5Unit-PoE-P4-HDMI (実製品) で使って
いる構成そのもの**である。60Hz ちょうどに固執しないのが要点。

## 起動時の画面の乱れ: 原因と決着

### 症状

800x600 で bring-up した当初、**起動から約 2 分間、画面が残像のように
横にずれて歪んだ**。その後は安定し、以後どんな負荷をかけても乱れない。
別のモニタでは「真っ暗 / 一瞬表示」を繰り返してから安定する、という
違う出方をしたが根は同じ。

### 原因: 要求した 40MHz が実機では出ていなかった

P0 は「LT8912B の DDS は整数分周の正確なクロックにしかロックできない、
APLL のジッタでは駄目」と正しく突き止めていた。**その条件に 800x600 自身が
違反していた**のが見落としである。40MHz を要求していたが、実機の DPI
クロックは **39.70MHz** (要求比 -0.76%) しか出ていなかった。

独立した 2 つの実測が一致する。

**(1) ブリッジのライン計数** — LT8912B の main 面 0x9c/0x9d は入力の
1 ライン長を約 800MHz の基準で数えている。これが実クロックの物差しになる。

| モード | 実測 hsync | 要求どおりなら | 逆算した実クロック |
|---|---|---|---|
| 800x600 (要求 40MHz、htotal 1056) | **21281** | 21120 | **39.70MHz** |
| 1280x720 (要求 80MHz、htotal 1650) | **16500** | 16500 | **80.00MHz** |

**(2) DDS のワード** — cec_dsi 面 0x0c-0x0f。0x3875F4 = 39.70MHz、
0x71C9A0 = 80.00MHz (ワード / 0x16C16 = MHz)。

半端なクロックを入れられた DDS は、それを追い続けて収束できずにいた。

### 効果

| | DDS ワードの揺れ | 見え方 |
|---|---|---|
| 800x600 @実 39.70MHz | ±0.1〜0.7% が約 2 分続き、その後ようやく静止 | 2 分ほど横ずれ・歪み |
| **1280x720 @実 80.00MHz** | **t=2 秒以降ずっと ±0.01% 以内** | **起動時から安定** |

720p での実測 (180 秒):

```
t=  2- 20s: n= 18  振れ幅  725 カウント (0.0097%)  平均 80.00 MHz
t= 20- 60s: n= 40  振れ幅 1087 カウント (0.0146%)  平均 80.00 MHz
t= 60-180s: n=120  振れ幅  499 カウント (0.0067%)  平均 80.00 MHz
```

**P0 が記録した「ワードが ±8 カウントで静止 = ロック」は必要条件では
なかった。** 720p では静止に至らず ±0.01% で微動を続けるが、目視では
完全に安定している。完全静止は、半端なクロックを追わされていたときにだけ
現れる状態だった。

### 外した仮説

同じ道を二度通らないための記録。**どれも効かなかった**。

| 試したこと | 結果 |
|---|---|
| DDS の種を実測ロック値 0x3875F4 に差し替え | 周波数は 1 秒で目標に到達するが、**ロック時刻は変わらない** (最終値と 3 カウント = 0.8ppm 差なのに 155 秒かかった)。「出発点が遠いから遅い」説はこれで死んだ |
| ストリーム開始後に MIPI RX + DDS リセットを再送 | 変化なし |
| P0 末期の tmp 構成の再現 (種 0x699BE2 を上から + 3 秒後にテーブル一式再送 + リセット) | このモニタでは 180 秒以内にロックせず |
| PSRAM 帯域の競合 | 無関係。ロックの前後でシステムは同じ待機状態 (周期ダンプのみ)。ロック後に NSF 再生やランチャー再スキャンをしても乱れない |
| ティアリング | 症状が位相ずれ (横方向の歪み) であって裂け目ではない |

なお **DDS の種に実在の欠陥はあった**: esp_lcd_lt8912b は静的表の
0x293E93 (= 29.00MHz) しか書かない。ピクセルクロックから種を作るコードは
`_panel_lt8912b_send_test` の中にあり `ENABLE_TEST_PATTERN 0` で到達不能。
M5GFX の Panel_LT8912B も 45 エントリすべて同一の表を積んでおり種も同じ。
ただし上記のとおり**これは症状の原因ではなかった**。

### 測定上の教訓

**ロック時間はモニタと実行ごとに大きくばらつく。**

| 実行 | ファーム | モニタ | ロック |
|---|---|---|---|
| 1 | stock (800x600) | A | 155 秒 |
| 2 | tmp 再現 (800x600) | A | 180 秒以内にロックせず |
| 3 | tmp 再現 (800x600) | B | 115 秒 |

**同じファームでモニタを替えただけで >180 秒 → 115 秒**。したがって
**n=1 の A/B は結論にならない**。この件では、そうと気づかずに 1 回の
実行で「tmp 構成は悪い」と報告して撤回した。

**再起動は書き込み不要で計装が毎回走る**ので、統計は安く取れる。1 サイクル
(ビルド + app_only 書き込み) が約 12 分かかるのに対し、再起動は数秒。

### 計測用コードは残していない

DDS ワード (cec_dsi 面 0x0c-0x0f) とライン計数 (main 面 0x9c-0x9f) の
読み出しは一時的に入れて外した。再び必要になったら上の表の読み方ごと
ここを見ればよい。

## パネル実装の選択: esp_lcd_lt8912b + M5GFX のタイミング値

**M5GFX の `Panel_LT8912B` をそのまま使う案 (案 A) は不採用**にしたが、
理由は当初考えたものとは違った。

- 不採用の直接の理由は**タイミング表**。`make_lt8912b_timing()` は
  1280x720 と 1920x1080@30 の 2 つしか持たず、それ以外は false を返して
  init が失敗する。当時の採用モードだった 800x600 が無かった。
- しかし**初期化列は両者で完全に同一**だった (45 エントリの DDS 設定表を
  含め、レジスタと順序が 1 バイト違わない)。つまり「M5GFX 側に我々が
  使えていない設定がある」わけではない。
- **本質は M5GFX のタイミング値の方にあった**。M5GFX は 720p も 1080p も
  pclk を 80MHz に置き、宣言するリフレッシュレート (60 / 30) は名目に
  すぎない。**PLL_F240M の整数分周で正確に出せる周波数を選び、
  リフレッシュのずれを受け入れる**という戦略で、これが今回の答えだった。

最終的な構成は「Espressif の esp_lcd_lt8912b (P0 で 800x600 を実際に
出した現物) に、M5GFX の 720p タイミング値を渡す」形になった。
`main/idf_component.yml` に `espressif/esp_lcd_lt8912b ^0.2.0` を
`target == esp32p4` ルールで追加している。TAB5 も同じターゲットなので
取り込まれるが、参照が無いためリンカが落とす (実測 +48 バイト)。

**esp_lcd_lt8912b 自身の 720p エントリは使えない**: CVT-RB の 64MHz で、
P4 は 240/64 = 3.75 を丸めて 60MHz にしてしまう (P0 が「破綻する」と
測ったのがこの構成)。

### LovyanGFX との接続

構造は Tab5 と同じ形を保った (`lgfx_naryav4.hpp`)。

- DSI バスは lgfx の `Bus_DSI` のまま (DPHY の LDO 確保 +
  `esp_lcd_new_dsi_bus` をやってくれる)。`LGFX_Device::init()` が両ボードを
  同じ順序で駆動する。
- パネルは `Panel_FrameBufferBase` 派生の自前クラス。init の中で I2C の
  3 面を開き、`esp_lcd_new_panel_lt8912b` → reset → init →
  `esp_lcd_dpi_panel_get_frame_buffer` で FB を取り、行ポインタ表を張る。
  **PPA が FB へ直接書く構造は Tab5 と同じ**。
- LovyanGFX からも同じ FB に描ける (ブート画面がこれ)。合成済みフレームは
  この経路を通らず PPA SRM が直接書く。

`LT8912B_IO_CFG` などの提供マクロは**そのままでは C++ から使えない**
(designated initializer の順序が宣言順と違う)。値は同じまま構造体に
1 フィールドずつ入れた。

## PPA の 1 パス検証 (plan.md の最後の技術リスク) — 成立

**PPA SRM は「RGB565 入力 → RGB888 出力 + 拡大」を 1 パスでできる。**

- 根拠: IDF の SRM ドライバは入力と出力の色モードを独立に設定する
  (`ppa_ll_srm_set_rx_color_mode` / `set_tx_color_mode`)。組合せの制限は
  YUV 系にしかない。
- 出力バッファの整列条件も通る: 1280x720x3 = 2,764,800 バイトは
  キャッシュライン 64 の倍数。
- 実機で成立を確認 (`PPA SRM initialized: 426x240 -> DSI fb 1280x720`)。
  **代替案 (2 パス、DMA2D、blend 段の RGB888 化) はどれも不要**。

800x600 時代に必要だった 1.5x の端数スケールも、720p で 3x に戻ったので
不要になった (カーソル patch も整数複製で済む)。

## step 0: P1 バイナリのブート観測

P2 に入る前に P1 のバイナリ (中身は Tab5 ドライバ) で観測できたこと:

```
I display_p4: Tab5 display: power on
E i2c.master: i2c_new_master_bus(1043): invalid SDA/SCL pin number
W display_p4: panel probe: no touch controller answered, assuming ILI9881C
I display_p4: Tab5 display: LGFX init
W boot: Display not ready, skipping BLE/WiFi init
E kernel: waiting host timeout!   /  E boot: Failed to start kernel
```

**Tab5 の I2C ピン (GPIO31/32) は P4 では i2c_master に受け付けられない**
(`invalid SDA/SCL pin number`)。PI4IO シーケンスは 1 行目から不成立で、
パネル探索も空振りし、LGFX init が返らないまま kernel 起動が timeout する。
P1 の想定どおりで、P2 で置き換える範囲と完全に一致していた。

## 実測

- `render: 5 frames/5s avg=28ms max=29ms` (デスクトップ静止時)。
  800x600 のときは 12ms だったが、FB が 690KB → 2.76MB と 4 倍になった
  分で順当。1 present/s の待機では問題なく、Tab5 の 3x パスと同等。
- `GFX STATS: 10.5 cmds/s, 1.0 presents/s`。
- `IRAM free: 138124 bytes`、PSRAM は FB の 2.76MB を引いて十分残る。
- バイナリ: NARYAv4 0x58b7e0 (区画 8% 残)、TAB5 0x58f3f0 (7% 残)。

## 踏んだ罠

### 要求した周波数が出ている前提で議論しない

今回の全て。**ブリッジのライン計数 (main 面 0x9c/0x9d) が実測手段になる**。
IDF は要求したクロックが作れないとき黙って近い値に丸める。

### GPIO31/32 は P4 の i2c_master に通らない

step 0 のとおり。Tab5 では LovyanGFX がレジスタ直叩きでこのバスを握るので
問題にならないが、`i2c_new_master_bus` は受け付けない。

### I2C の所有者が変わった

Tab5 は「lgfx がバスを握り、他は lgfx のヘルパ経由で直列化」だった。
NARYAv4 は**タッチが無いので lgfx はこのバスを一切触らない**。よって
`display_p4_i2c_*` は i2c_master ドライバで実装し直した (ミューテックスは
そのまま。呼ぶ側が複数タスクなのは変わらない)。ポートは I2C_NUM_0。

- hw_proxy の「unit 1 は display に仲介させる」判定のピンは 31/32 直書き
  だったので `FMRB_PIN_I2C1_SDA/SCL` に変えた (ボード追従)。
- **tab5_kbd が I2C_NUM_0 を取りに来る**。今は NC ピンで先に失敗するので
  衝突しないが、順序に頼った安全でしかない。P3 で tab5_kbd を NARYAv4 の
  ビルドから外すときに解消する。

### 4:3 の信号は 16:9 モニタで縦につぶれる

800x600 時代、内部の 639x360 自体は正しい 16:9 だったが、4:3 の信号を
16:9 モニタが全画面に引き伸ばすため縦につぶれて見えていた。720p 化で
同時に解消した。

### ビルドターゲットの取り違え

`.env` を TAB5 に戻したまま `rake build:esp32` して、**Tab5 のバイナリを
P4-Nano に焼いた**。ログの `panel probe:` で気づくまで 1 サイクル無駄に
した。P1 report にも書いてある罠を自分で踏んだ形。焼く前に
`HW target: NARYAv4 (Modern` をビルドログで確認すること。

## このフェーズで触っていないもの (想定内の失敗ログ)

いずれも P3 の担当で、ハングもリブートもしないため boot.c のガードは
**入れていない**。

- `audio_p4: es8388 codec create failed` / `I2C_If: Fail to write to dev 20`
  — Tab5 のコーデック構成のまま。NARYAv4 は ES8311 1 個。
- `tab5_kbd: I2C0 bus init failed` — 内蔵キーボードは無い。
- `vfs_fat_sdmmc: sdmmc_card_init failed` — カード未挿入。

**副産物: C6 が SDIO で上がった。** `sdio_wrapper: Function 0 Blocksize: 512`
/ `transport: Base transport is set-up` / `Slave chip Id[12]` / WLAN と
HCI over SDIO の capability 応答まで確認できている。**P1 で入れた SDIO
ピン (CMD=19/CLK=18/D0=14/D1=15/D2=16/D3=17、EN=54) は正しかった**。
P3 の無線はここから始められる。

## P0 report への訂正 (実施済み)

1. 「DDS は約 20 秒ハンチングの後に静止」→ **誤記**。「20 秒以上」という
   口頭報告を取り違えたもので計測値ではない。実際は 2 分程度。
2. 「採用モード: 800x600@60 (PLL_F240M/6 = 正確な 40MHz)」→ **覆った**。
   40MHz は正確ではなかった。採用モードは 1280x720 @実 80MHz。
