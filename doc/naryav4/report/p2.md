# P2 report: 表示 bring-up (HDMI 800x600)

> 状態: 完了 | 更新: 2026-08-30 | P4-Nano + LT8912B の HDMI にデスクトップが 800x600@60 で表示。ユーザ目視で受け入れ

## 成果

`FMRB_HW_TARGET=NARYAv4` のバイナリを P4-Nano に焼くと、HDMI モニタに
fmruby のデスクトップが出る。crash マーカー 0、GFX STATS も回っている。

| 受け入れ条件 | 結果 |
|---|---|
| デスクトップが 800x600 で安定表示 (最終判定はユーザ目視) | **満たした** (2026-08-30、ユーザ確認「デスクトップが安定表示」) |
| 426x240 を 1.5x=639x360、黒縁で中央配置、回転なし | 実装どおり。PPA SRM 1 パス (`PPA SRM initialized: 426x240 -> DSI fb 800x600`) |
| crash マーカー 0、GFX STATS が出る | 0 件。`render: 5 frames/5s avg=12ms max=13ms`、`GFX STATS: 10.9 cmds/s, 1.0 presents/s` (静止デスクトップ、最終イメージで再確認) |
| TAB5 退行なし | ビルド成功 (bin 0x58f3c0 → 0x58f3e0、+32 バイト)。sim スモークでデスクトップ表示 + エディタ起動 + 打鍵まで確認。`rake test` も通る (golden 103/103 ほか) |

NARYAv4 の bin は 0x590700 (P1) → 0x58b880 と**約 19KB 小さくなった**。
LT8912B ドライバが増えた分より、Tab5 のパネル/タッチ/バックライトの
LovyanGFX クラス (Panel_ILI9881C / ST7121 / ST7123 / Touch_GT911 /
Touch_ST7123 / Light_PWM) を誰も参照しなくなってリンカが落とした分の方が
大きい。

## step 0: P1 バイナリのブート観測

P2 に入る前に P1 のバイナリで観測できたこと (実測):

```
I display_p4: Tab5 display: power on
E i2c.master: i2c_new_master_bus(1043): invalid SDA/SCL pin number
W display_p4: panel probe: no touch controller answered, assuming ILI9881C
I display_p4: Tab5 display: LGFX init
W boot: Display not ready, skipping BLE/WiFi init
E kernel: waiting host timeout!   /  E boot: Failed to start kernel
```

**Tab5 の I2C ピン (GPIO31/32) は P4 では i2c_master に受け付けられない**
(`invalid SDA/SCL pin number`)。つまり PI4IO シーケンスは 1 行目から
不成立で、パネル探索も空振りし、LGFX init が返らず表示が上がらないまま
kernel 起動が timeout する。P1 の想定 (「表示初期化は失敗してよい」) の
とおりで、P2 で置き換える範囲と完全に一致していた。

## パネル実装の選択: 案 A を捨てて esp_lcd_lt8912b (案 B 相当)

**採用条件を満たさなかったので案 A (m5gfx の `Panel_LT8912B`) は不採用**。

理由は初期化列ではなく**タイミング表**だった。m5gfx v0.2.28 の
`make_lt8912b_timing()` は 1280x720@60 と 1920x1080@30 の 2 つしか持たず、
それ以外は false を返して init が失敗する。**800x600 が無い** —
そして 800x600@60 は P0 で「この機材で唯一成立するモード」と確定した
ものなので、ここは譲れない。managed_components は改変しない方針なので
表を足す選択肢も取らない。

代わりに **espressif/esp_lcd_lt8912b 0.2.0 を managed 依存に追加**した
(`main/idf_component.yml`、`target == esp32p4` ルール)。P0 で実際に
800x600 を出した現物と同じドライバで、`ESP_LCD_LT8912B_VIDEO_TIMING_800x600_60Hz()`
と 800x600 の DPI 設定を持っている。TAB5 も同じターゲットなので取り込まれるが、
参照が無いためリンカが落とす (実測 +32 バイト)。

構造は Tab5 と同じ形を保った (`lgfx_naryav4.hpp`):

- DSI バスは lgfx の `Bus_DSI` のまま (DPHY の LDO 確保 + `esp_lcd_new_dsi_bus`
  をやってくれる)。`LGFX_Device::init()` が両ボードを同じ順序で駆動する。
- パネルは `Panel_FrameBufferBase` 派生の自前クラス。init の中で
  I2C の 3 面 (0x48/0x49/0x4A) を開き、`esp_lcd_new_panel_lt8912b` →
  reset → init → `esp_lcd_dpi_panel_get_frame_buffer` で FB を取り、
  行ポインタ表を張る。**PPA が FB へ直接書く構造は Tab5 と同じ**。
- LovyanGFX からも同じ FB に描ける (ブート画面がこれ)。合成済みフレームは
  この経路を通らず PPA SRM が直接書く。

`LT8912B_IO_CFG` などの提供マクロは**そのままでは C++ から使えない**
(designated initializer の順序が宣言順と違う)。値は同じまま構造体に
1 フィールドずつ入れた。

## PPA の 1 パス検証 (plan.md の最後の技術リスク) — 成立

**PPA SRM は「RGB565 入力 → RGB888 出力 + 1.5 倍拡大」を 1 パスでできる。**

- 根拠: IDF の SRM ドライバは入力と出力の色モードを独立に設定する
  (`ppa_ll_srm_set_rx_color_mode` / `set_tx_color_mode`)。組合せの制限は
  YUV 系にしか無い。
- スケール 1.5 は 1/16 刻みで正確に表現できる (整数部 1 + 端数 8/16)。
- 出力バッファの整列条件も通る: 800x600x3 = 1,440,000 バイトは
  キャッシュライン 64 の倍数。
- 実機で成立を確認 (`PPA SRM initialized: 426x240 -> DSI fb 800x600`、
  表示あり)。**代替案 (2 パス、DMA2D、blend 段の RGB888 化) はどれも不要**。

これで plan.md の未確定事項からこの項目を消せる。

## 実測

- `render: 5 frames/5s avg=12ms max=13ms` (デスクトップ静止時)。
  Tab5 の 3x + 回転 (720x1280 RGB565 = 1.8MB) に対して、こちらは
  639x360 RGB888 = 690KB しか書かないので、SRM の仕事は軽い。
- `GFX STATS: 10.5 cmds/s, 1.0 presents/s` (静止デスクトップ)。
- `IRAM free: 146124 bytes, PSRAM free: 13356320 bytes`。RGB888 FB の
  1.44MB は PSRAM から出ている。
- LT8912B の DDS ロックは P0 のとおり起動後しばらくかかる。今回は
  常設のログを入れていない (P0 の計測用ログは恒久コードに残さない方針)。

## 踏んだ罠・注意

### GPIO31/32 は P4 の i2c_master に通らない

上の step 0 のとおり。Tab5 では LovyanGFX がレジスタ直叩きでこのバスを
握るので問題にならないが、`i2c_new_master_bus` は受け付けない。
**NARYAv4 では触る必要が無いので今回は回避しただけ**だが、Tab5 側で
i2c_master を使おうとしたときに同じ壁に当たる。

### I2C の所有者が変わった

Tab5 は「lgfx がバスを握り、他は lgfx のヘルパ経由で直列化」だった。
NARYAv4 は**タッチが無いので lgfx はこのバスを一切触らない**。よって
`display_p4_i2c_*` は i2c_master ドライバで実装し直した (ミューテックスは
そのまま。呼ぶ側が複数タスクなのは変わらない)。ポートは I2C_NUM_0。

- hw_proxy の「unit 1 は display に仲介させる」判定のピンは 31/32 直書き
  だったので `FMRB_PIN_I2C1_SDA/SCL` に変えた (ボード追従)。
- **tab5_kbd が I2C_NUM_0 を取りに来る**。今は NC ピンで先に失敗するので
  衝突しないが、順序に頼った安全でしかない。P3 で tab5_kbd を NARYAv4 の
  ビルドから外すときに解消する。

### カーソルの patch は「PPA と同じ丸め」を手で書く必要がある

Tab5 は 3 倍の整数倍なので画素を複製するだけでよかった。1.5 倍では
出力列 ox が入力列 `ox*2/3` から来る (最近傍) という規則を patch 側でも
再現しないと、カーソルの下だけ 1 画素ずれる。RGB888 のバイト順は
**B,G,R** (lgfx の `rgb888_nonswapped` の意味そのままで、PPA も DPI も
同じ順序)。

### そのほか

- ソフトウェアフォールバック (SRM が無いとき) と CPU バックエンド
  (`FMRB_DISPLAY_BACKEND=cpu`) も 1.5 倍に追従させた。CPU バックエンドは
  既定では選ばれないが、3 倍固定のまま残すと NARYAv4 では画面外に描く。

## このフェーズで触っていないもの (想定内の失敗ログ)

実機のログに以下が出るが、いずれも P3 の担当:

- `audio_p4: es8388 codec create failed` / `I2C_If: Fail to write to dev 20`
  — Tab5 のコーデック構成のまま。NARYAv4 は ES8311 1 個。
- `tab5_kbd: I2C0 bus init failed` — 内蔵キーボードは無い。
- `system_api: 2 mac type is incorrect` — C6 が上がっていない。
- `vfs_fat_sdmmc: sdmmc_card_init failed` — カード未挿入。

ハングもリブートもしなかったので、**boot.c のガードは入れていない**
(instruction が許可した最小変更は不要だった)。
