## 8. 追記: T4 の取り残しと VM プールの +4 KB (2026-11-15)

### 8.1 wl の settings と checkpoint の `wide`

原因は同じ 1 つ。T4 の機械的な入れ替えで、単独の `@user_area_x0`・`@user_area_y0` が `0` になり、区画の場所を言うログの行が定数になっていた: 設定アプリ (`native/apps/linux_settings.app.rb`) の `user area WxH at (x,y)` と、ckpt_wide・ckpt_full の `user=x,y,WxH`。

- この行の約束は「区画が Window の中のどこにあるか」(試験はそれで押す場所を出し、復元の後に枠の分の (1, 11) がそろっているかを見る)。試験の側の期待を (0, 0) に合わせると、何を言っても通る検査になる。そこで**アプリが `@gfx.origin_x`・`origin_y` (区画の原点の Window 座標、mruby・Spinel の両方にある) を書く**ようにした。試験と checkpoint の期待値 (`user=1,11,...`) は変えていない。
- 同じ形の行は built-in にも 2 つ残っている (`default_app/wifi.app.rb` の `wifi: user area ... at (0,0)`、`shell.app.rb` の `user_area: x0=0, y0=0`)。読む試験は無いので今回は触っていない。直すなら同じ書き換え。

### 8.2 wl の open (note.txt がエディタで開かない)

T4〜T6 ではなく **T3 (ac15911b、ファイルが定義するアプリのクラスを起こす) の取り残し**。

- 証拠 (前の回の `tmp/wl_check/open-standard-pixman/core.log`): 直前に開く `hello.rb` はクラスの無い 1 行のスクリプトで、T3 からは `Not started: No app class in /mnt/host/hello.rb.` になり、エラーのダイアログが出る (`Desktop overlay: active=true keyless=true`)。次の File Manager を開くクリックがそれに取られ、20 秒のあいだ File Manager のログが 1 行も無い。最後の画面もデスクトップだけ。その後の odd.fmnone は、ダイアログが消えた後なので開く。
- クラスの無いファイルをエラーにするのは T3 の決定 (t3.md の「黙って何も起きない、を無くす」) なので、試験の側を直した: `hello.rb` をログを書いて `stop` する小さなアプリにした。見るもの (.rb は「run」、note.txt は「edit」) は同じ。

### 8.3 Modern のデスクトップの VM プール +4 KB

結論: **FmrbSystem のせいではなく、デスクトップの bytecode の中の symbol 名の番地の偶奇がずれた結果**。mruby は、bytecode の中の名前を指して symbol を作るとき、名前が奇数番地にあると (下位ビットを印に使うので) 4 KB 単位の symbol pool に写す。デスクトップでは写す名前が 3 つ目の chunk (4,096 B) の 3,990 B まで来ていて、呼び出しの書き換え (`FmrbApp` 7 字 → `FmrbSystem` 10 字) で後ろの名前の偶奇が入れ替わり、写す名前が 174 B 増えて 4 つ目の chunk を取った。段差で効くので、デスクトップのソースのどんな小さな変更でも ±4 KB 動きうる (T5+T6 の 2 回めの +5,376 も同じものの見込み。こちらは測っていない)。

分け方: 変更前の木 (84703a2c) に一時的な計装 (symbol 表・Object の定数表・スタック・symbol pool の chunk の数と、irep を読んだ直後の pool をログに出す。コミットしていない) を入れ、`ruby tools/regress/sim_run.rb --only modern` を流した (used、idle の点):

| 木 | デスクトップ | ほかの mruby の VM (Kamon・MML ほか) | 見えたこと |
|---|---|---|---|
| 変更前 (84703a2c) | 814,960 | — | symbol 1,618 個・表の容量 1,826 |
| (a) C の登録だけ (FmrbSystem に 34 個を足す。FmrbApp からは消さない、Ruby は今のまま) | +920 | +888〜+1,032 (全部の VM、コンパイル直後も +888) | モジュール 1 つと、34 個の表 (16 B × 64 枠) |
| (b) (a) + デスクトップの呼び出しの書き換えだけ | (a) から +4,176 | ±0 | irep を読んだ直後で既に +4,176 (601,208 → 605,384)。生きているオブジェクトの数 (5,232)・symbol の数 (1,619)・Object の定数表 (155/256)・スタックは (a) と同じ。symbol pool の chunk が 3 (最後の使用 3,990) → 4 (68) |
| 今の木 (T5+T6、12a8ec69。変更前と比べて) | +4,032 | -64〜-136 (コンパイル直後 -160) | FmrbApp の特異クラスの表が 82 個 → 48 個で 128 枠 → 64 枠に縮み (-1,024 B)、(a) の分をほぼ打ち消す |

- bytecode の差は 160 B だけ (`FmrbSystem` を使う irep が 7 つで symbol が 1 つずつ増え、名前が 3 字ずつ長い)。命令列・pool・irep の数は同じ。
- FmrbSystem そのものの費用は VM ごとに +888 B、FmrbApp の表が縮む分と合わせて -160 B。アプリごとに実行時に表を作っているわけではない (C の登録は VM を作るときの 1 回で、今までの FmrbApp の表と同じ形)。直すものは無い。
- 偶奇の当たり外れそのものを無くすなら、mrbc が symbol 名を偶数番地にそろえる (または読む側が奇数の名前をまとめて写さない) という上流 (picoruby-mruby) の話になる。デスクトップでは今 3〜4 chunk (12〜16 KB) がこれに使われている。今回は手を付けていない。
- 実機 (ESP32) でも bytecode を読む経路は同じ (名前を指す読み方) なので、同じ段差が起きうる。
