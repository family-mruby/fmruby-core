> 親: plan.md の T4、指示: instruction_t4.md | 2026-11-14 | fmruby-core develop、skill (`.claude` リポジトリ)。

## 1. 原点の持ち方

| 場所 | 中身 |
|---|---|
| C (`lib/add/picoruby-fmrb-app/ports/esp32/gfx.c`) | `mrb_gfx_data` (VM の pool に `mrb_malloc`) に `int16 ox, oy`・`uint16 area_w, area_h`・`uint8 to_image` を足した (1 つの FmrbGfx あたりフィールド 9 B、ESP32 で構造体は 16 → 28 B。静的な変数は足していない)。描く命令の座標はすべて `GX(d, x)`・`GY(d, y)` (原点を足す。描く先が sprite image の間は足さない) を通って canvas に行く。Ruby に `_set_origin(x, y, w, h)`・`origin_x`・`origin_y`・`area_width`・`area_height` を出した。app.c 向けに `fmrb_gfx_origin_of` |
| 区画の計算 | `FmrbApp#_layout_user_area` 1 か所 (mruby `fmrb-app.rb`)。`initialize`・app.c の resize (今までの C の写しを消して、これを `mrb_funcall`)・checkpoint の復元 (今までは大きさが変わったときだけ、今は毎回) が呼ぶ。全画面・枠なし・desktop (壁紙の canvas を持つ Window) は区画 = Window (原点 0)、枠つきは (1, 11) と幅 w-2・高さ h-12。`@gfx._set_origin` と `@window_gfx` の大きさ、sprite clip まで済ませる。Spinel (`fmrb_app_base_spinel.rb`) も同じ名前の 1 メソッドにして、初期化と resize の 2 つの写しを消した。Python (`fmrb_app.py`) も `_layout_user_area` 1 つ |
| ivar | `@user_area_x0/y0/x1/y1` は消した (読み手 `user_area_x0` も)。`@user_area_width/height` は残す。消し忘れた呼び出しは nil の足し算で落ちるので、黙って二重にずれることはない |
| Spinel の FmrbGfx | Ruby の包みが `@ox, @oy, @aw, @ah` と、描くときに足す `@dx, @dy` (sprite image に描いている間は 0) を持つ。AOT で C になるので加算 1 回 |
| Python の FmrbGfx | 同じく `origin_x`・`dx` などを属性で持つ |
| `@window_gfx` | 同じ canvas の 2 つめの FmrbGfx、原点は Window の左上 (区画の大きさ = Window)。基底の枠 (GfxBlock 2 つ・閉じるボタンの押し込み・resize の印)、ネイティブ版の linux_window の枠が使う。書体は canvas に 1 つなので、`set_font` は `@gfx` で呼ぶ (基底の枠も `@gfx` で保存・戻し) |
| イベント | マウス・タッチ・ホイールの `ev[:x]`・`ev[:y]` は区画の座標、`ev[:wx]`・`ev[:wy]` に Window の座標。mruby は app.c が Hash を作るときに `@gfx` の原点を引く (動きの Hash の使い回しも同じ)。Spinel は `_parse_hid_event`、Python は基底の `_dispatch_event` (ブリッジが `on_event` の代わりにこれを呼ぶ)。基底の `_frame_event` (閉じるボタン・タイトルバーの右クリック) と枠なしの右クリック・長押しのメニューは wx/wy を使う |
| FmrbUI | `@ox/@oy` と `set_origin` を消した。部品は渡された座標のまま (= 区画) を持ち、描くのは `@gfx` の原点、当たりは区画の事件に任せる。全画面の出入りで原点が古いまま残る不具合はこれで無くなった。範囲の検査は区画の大きさで |
| GfxBlock (mruby) | 記録のときに原点を足して定数に焼く。`draw` で原点が変わっていたら (全画面の出入り) program を作り直す。Spinel は即時描きなので何もしない |
| P5 | `width`/`height` は区画の大きさ (`area_width`) |

| `P5#width`・`height` | 区画の大きさ | |
| `canvas_width`・`canvas_height` | canvas の大きさ | 意味は変えていない |

## 3. 入れ替えた数

- 全部で 142 ファイル (基底・道具・試験 27、アプリ 108、sig・文書 6、比べる道具 1)。アプリの入れ替えは道具で機械的に行った: `@user_area_x0 +`・`+ @user_area_x0`・`- @user_area_x0` を消し、単独の `@user_area_x0` は `0`、`@user_area_x1`/`y1` は `@user_area_width`/`height` (Python の `self.user_area_*` も同じ)。その後、Window・画面の座標を扱う所 (pos_x、当たりの形、合成の区画、`@bg_gfx`、作った canvas、GfxBlock の recorder) に入っていないことを差分で見た。
- 手で直したもの: robo_explorer の定数 (`BOARD_X/Y`・`PANEL_X/Y` を区画の座標に)、stackchan と picoruby の閉じるボタンの真似 (`ev[:wx]`/`ev[:wy]`)、linux_window の自前の枠 (`@window_gfx`)、desktop 2 本の `@ui.set_origin(0, 0)` (消した。desktop は区画 = Window)、pub_demo と tmp_writer のボタンの定数 (5 章で見つけた)。
- `draw_window_frame` の呼び出し (アプリ 76 か所) は、`clear_user_area` の直後で間に何も描かない 4 か所 (kamon・midi_apu・shell 2) だけ消した。`clear_user_area` が中で枠を描くので二重だった。ほかは残した: `clear_user_area` の後にアプリが描いたもの (区画の下の隅) が枠の角の丸みの線 (区画の内側にかかる) を塗るので、描き終えたあとの枠の描き直しは今も要る。基底に任せるには「区画の描画が角の線を塗らない」仕組みが別に要る。
- 描画の記録の道具 (`tools/regress/recorder.rb`) は C と同じく原点を足して canvas の座標を記録し、`scene.rb` は app.c と同じく事件を区画の座標にする (場面のクリックは今までどおり Window の座標)。アプリの ivar から場所を取ってクリックする場面 5 つ (board・othello 2・stackchan_remote・monitor) は `s.ox`/`s.oy` を足すようにした。

## 7. 見立てと違った点・T5 以降への注意

- `set_sprite_clip` を区画の座標にした (t0 の案は Window のまま)。flappy がアプリから呼んでいたため。スプライトと同じ座標なので、使う側には自然。
- 区画の外に描く口は `@window_gfx` にした。書体は canvas に 1 つなので、`@window_gfx.set_font` は `@gfx` の覚えている書体とずれる。基底の枠は `@gfx` で書体を保存・戻ししている。アプリにも sig と skill で「set_font は gfx で」と書いた。
- Python のブリッジは `on_event` の代わりに基底の `_dispatch_event` を呼ぶ。名前は生成済みの qstr 表 (`rake micropython:gen`) に足さず、`qstr_from_str` で引いている (静的な RAM を増やさないため)。次に `micropython:gen` を流すときに表へ入れてよい。
- Lua (`lua.app.lua`) は自前の描画で、この段では触っていない。
- `@gfx.clear` は今も canvas 全体を消す (枠ごと)。ruby_profile・fft_bench はこれで枠が消えたまま描く。区画だけ消す `clear_user_area` に替えるかは、アプリの見た目の判断なので触っていない。
- `draw_window_frame` の呼び出しはほとんど残した (3 章)。基底に任せるには、区画の描画が角の丸みの線を塗らないようにする仕組み (区画のクリップ、または枠を角の線だけ描き直す口) が要る。
- 一回きりの道具 (`tools/regress/origin_compare.rb`) は残した。比べた絵は `tmp/regress/origin/` (git の外)。

## 10. 追記: VM プールの増分と checkpoint (親の検収の後)

### 10.1 直したこと

- `@window_gfx` を必要になったときに作る (`window_gfx` メソッド)。枠を描く Window は枠を組むときに作るので今も持つが、全画面・枠なし・desktop は持たない。基底の中の参照はこのメソッドを通す (linux_window も)。Spinel の基底は前のまま作っておく (VM プールに乗らない)。
- GfxBlock: 記録した座標に原点を足すのを Recorder の中 (block の中の各呼び出し) から、block が返ったあとの記録の一覧への一回の手入れ (`_at_origin`) に移した。作り直しも別のメソッドを挟まず `initialize` を呼び直す形にした。block の中の呼び出しは、FmrbApp#initialize の中で枠の block を組むところで、アプリの起動のいちばん深い所に当たる。
- `ckpt_window` のクリックのログは Window の座標 (`ev[:wx]`) にした。checkpoint の確かめは Window の中の (40, 50) をクリックしてその数を待つ。区画の座標では (39, 39) と出て合わなかった (1 回めの checkpoint はこれで standard・mruby が落ちた)。

### 10.3 +2.2 KB の正体 (説明)

**VM のスタック (mruby の値の並び) が 1 段 (2,048 B) 伸びた分**と判断した。根拠:

- mruby の VM スタックは足りなくなると `MRB_STACK_GROWTH` = 128 値ずつ伸びる (`lib/patch/picoruby-mruby/lib/mruby/src/vm.c`)。この構成は `MRB_NO_BOXING` で、sim (x86-64) の `mrb_value` は 16 B なので 1 段は 2,048 B。一度伸びたスタックはアプリが終わるまで縮まないので、GC の後でも used に残る。
- 4 本とも、変更で持つ物が増えた分は 200〜300 B (枠を描く Window の `@window_gfx` = RObject・ivar・フォントの配列 2 つ・C の data)。Kamon と StackChan は直した後これだけ (+216〜+312)。MML と Spinel Hello の残り +2,232・+2,240 は、これに 2,048 B 足したものとちょうど合う。
- StackChan Remote は、いちばん深い所 (枠の GfxBlock を組む: FmrbApp#initialize → `_build_frame_block` → GfxBlock#initialize → block → Recorder#draw_text → ...) からメソッドの 1 段と Recorder の中の足し算を除いただけで +2,360 → +216 に下がった。物の数は変えていないので、下がった 2,144 B はスタックの 1 段と見る。
- MML と Spinel Hello は 2 本とも自分の `initialize` から `super()` を呼ぶので、同じ道筋がもう 1 段深い。それでぎりぎり 128 値の境を越えたままと見ている。どのフレームの何レジスタが越えさせているかまでは確かめていない。候補は `_build_frame_block` に足した局所変数 (`wg = window_gfx`) と、GfxBlock#initialize の中の `@ox = gfx.origin_x` などの一時レジスタ。
- 実機 (ESP32 は 32 bit) では `mrb_value` が小さいので、1 段はもっと小さい。

この 2 本については「スタックの境を越えるかどうか」の話で、アプリごとにかかる固定の構造ではない。0 に戻すなら、上の候補を消して測り直す (regress:run 1 回、5 分) のが次の一手。今回は親の指示 (原因を説明して止まる) でここまでにした。
