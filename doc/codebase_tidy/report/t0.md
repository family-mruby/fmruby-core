## 1. T3 の材料: 起動の流れ

### 1.1 エンジンごとの流れ

| エンジン | 読み込み | 末尾の起動コードを実行する所 | `start` に入る所 | 起動しなかったとき |
|---|---|---|---|---|
| mruby (ファイル) | `main/app/fmrb_app.c:937` `execute_mruby_script` → `mrc_load_string_cxt` (1006) で compile | `mrc_create_task(... top_self)` (1068) → `mrb_task_run` (1084) がファイルの top level をそのまま走らせる | 末尾の `app.start` (`lib/add/picoruby-fmrb-app/mrblib/fmrb-app.rb:1337`) が `on_create` → `main_loop` → `destroy`。`main_loop` が終わるまで `mrb_task_run` は戻らない | `report_mruby_result` (867) が「No exception detected」と INFO を出すだけ。画面には何も出ない (**黙って何も起きない**、の実体) |
| mruby (組み込み、bytecode) | `fmrb_app_spawner.c:155` `builtin_app_table` の irep (shell・editor・desktop・monitor など) | 同じ `execute_mruby_script` (BYTECODE は compile しない) | 同上 | 同上 |
| Spinel (desktop・editor を Spinel で組むとき) | `tool/spinel/gen_app_combined.rb` がベース+ライブラリ+mixin+本体を 1 本に連結 (99-121) → `spinel --ext-init Init_<app>` | 末尾の top level が `Init_<app>()` の中身になる (`gen_app_combined.rb:6-9` のとおり) | `fmrb_app_spawner.c:141-146` が `fmrb_app_run_spinel_vm(ctx, Init_system_desktop)` | 末尾が無いと Init が空で戻る。今は検査なし |
| MicroPython (`.app.py` 5 本) | `fmrb_app.c:1204` `execute_micropython_script` | Python の top level (`PyTestApp().start()` 等) | `components/micropython/prelude/fmrb_app.py:570` `start` | 同様に黙って終わる |
| BASIC・Lua | クラスが無い (BASIC は `fmrb_basic_run`、Lua は `FmrbApp` 表の関数群) | — | — | T3 の対象外でよい |
| checkpoint の復元 | `fmrb_app.c:1650` `FMRB_LOAD_MODE_CHECKPOINT` → `execute_mruby_checkpoint` (900) | **走らない**。イメージの中の Task (`main_loop` の途中) をそのまま続ける | `_checkpoint_restored` (`fmrb-app.rb:612`) → `on_resize`? → `on_restore` | — |

起動の知らせ (`app_started`) は `fmrb_app_notify_started` (`fmrb_app.c:781`) が、メインの canvas を作ったとき (= `FmrbApp#_init`) に送る。つまり「インスタンスが作られたか」は C の ctx から既に分かる。ctx は `g_ctx_pool` (`fmrb_app.c:109`、`FMRB_EXT_RAM_BSS_ATTR` = PSRAM) にあり、旗を 1 つ足しても内蔵 RAM は増えない。headless アプリは canvas を作らないので、`started_notified` とは別の旗 (`_init` で立てる) が要る。

### 1.3 「新しく定義された子を見つけて起動する」の入れ場所

| 候補 | 中身 | 良い所 | 気になる所 |
|---|---|---|---|
| **A (推奨)** mruby: `FmrbApp.inherited(k)` で子を記録 (mruby は `inherited` を呼ぶ: `picoruby-mruby/lib/mruby/src/class.c:628`)。C は `mrb_task_run` (1084) の後、ctx の「インスタンスを作った」旗が立っていなければ、小さな文 `FmrbApp._autostart` を compile して同じ VM で Task として走らせる | 走るのは Task の中なので、`sleep`・タイマ・checkpoint の扱いが今の `start` と同じ | 記録は「スクリプトを読み始めてから」の分だけにする (gem の mrblib が定義する子があれば除く。今は 0)。mahjong のような開き直しは `inherited` が 1 回なので 1 つに数えられる |
| B mruby: compile する前にソースへ末尾の 1 行を足す | 単純 | bytecode の組み込み (11 本) は compile しないので効かない。行番号がずれない形にする必要 |
| C mruby: C が `top_self` で定数を走査して FmrbApp の子を探す | Ruby 側の変更なし | 定数の走査は重く、ネストしたクラスを見落とす |
| **Spinel (推奨)**: `tool/spinel/gen_app_combined.rb` が本体の `class X < FmrbApp` を拾い、末尾に起動コードが無ければ `X.new.start` を足す | **コンパイル時に分かる** (結合は 1 本で、本体ファイルが決まっている)。型推論も今と同じ形 | Spinel 側で実行時に子を探す手段は実質無い: `inherited` の呼び出しは無く (`vendor/spinel/src` に該当なし)、`Base.subclasses` は箱詰めのクラスを返すので `.new` が poly になり AOT の型が崩れる。`ObjectSpace` は使えない (`codegen_call.c:1423`) |
| Python | prelude の `FmrbApp` に `__init_subclass__` で記録、C が実行後に `_autostart` を呼ぶ | 同じ形 | MicroPython の版で `__init_subclass__` が効くか要確認。効かなければ C が globals を走査 (5 本しかないので T3 の外にする選択もある) |

**二重起動の防ぎ方**: 「この VM で FmrbApp のインスタンスを 1 つでも作ったら自動起動しない」。C の ctx に旗 (PSRAM、増分は bool 1 つ) を置き、`FmrbApp#_init` (C) で立てる。

- 末尾の起動コードが残っていると、`mrb_task_run` が戻るのはアプリが終わった後なので、旗は立っていて二重にならない。
- `initialize` や `on_create` で例外が出ても旗は立つので、壊れたアプリを 2 回起動しない。
- checkpoint の復元は `execute_mruby_checkpoint` を通り、自動起動の経路を通らない。`restart: true` (同じプログラムでイメージから起動し直す) もこの経路。
- 起動に失敗した理由 (子が無い・2 つ以上で `class =` が無い・`class =` の名前が無い) は `set_last_error` + `notify_error_to_kernel` (`fmrb_app.c:885-888` と同じ口) に流せば、ログとエラーのダイアログに出る。

**`class =` の読み方**: ctx に文字列を足すと `g_ctx_pool` が `FMRB_MAX_APPS` 倍に増えるので避ける。子が 2 つ以上のときだけ Ruby が自分の `.app.toml` を読む (`FmrbApp.script_path` と `FmrbToml` は既にある)。

### 1.4 T3 の危ない所

- Spinel の desktop・editor: 末尾を消すと `Init_*` が空になる。生成の検査 (末尾が無い・子が無いなら生成を止める) を `gen_app_combined.rb` に入れる。
- 組み込みの bytecode も同じ経路なので一緒に消せるが、`linux_window.app.rb` はネイティブ版だけで組まれる。
- `flash/app/debug/compile_err.app.rb` と `exception.app.rb` は「壊れ方の見本」。新しいエラー表示の試験に使える。
- checkpoint の移動先では、`requires` の確認 (`fmrb_app_checkpoint.c:1127`) より前に自動起動が入らないことを `rake regress:checkpoint` で確認する。

### 1.5 ユーザに選んでもらうこと

1. 自動起動に失敗したときの見せ方: (a) エラーのダイアログ+ログ (**推奨**。今の `app_error` と同じ口)、(b) ログだけ。
2. MicroPython を T3 に含めるか: (a) 含める、(b) Ruby だけにして Python は後で (**推奨**。5 本で、版の確認が要る)。
3. 末尾の起動コードを消す範囲: (a) 全部 (flash 107+組み込み 11+テンプレート 3、**推奨**)、(b) 残っても二重にならないので新しく書くものだけ。
