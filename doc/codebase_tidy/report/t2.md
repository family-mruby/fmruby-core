# T2 プロトコルヘッダの一本化

> 親: plan.md の T2、指示: instruction_t2.md | 2026-11-14 | fmruby-core develop、fmruby-graphics-audio develop、ワークスペース (family-mruby) develop。

## 1. 共有にしたヘッダ (正は fmruby-core の `components/fmrb_wire/include`)

線の形のヘッダだけを集めた置き場を新しく作った (ESP-IDF の部品 `fmrb_wire`、ヘッダだけ)。前の置き場には中身の違う同名のヘッダ (fmrb_pin_assign.h・fmrb_task_config.h・fmrb_eintr.h など) が graphics-audio 側にもあり、`components/fmrb_common/include` を graphics-audio から丸ごと include すると取り違えるため、共有するものだけの置き場にした。

| ヘッダ | 前の正 (core) | graphics-audio の写し | 揃え方 |
|---|---|---|---|
| `fmrb_link_protocol.h` | `components/fmrb_common/include/` | `main/common/` (消した) | core のもの (上位: `SET_CANVAS_VIEWPORT 0x57`・`VIDEO_OPEN/CONTROL/STATUS 0xA0-0xA2`)。共通の値は同じだったので、graphics-audio には enum と構造体が増えるだけ |
| `fmrb_link_version.h` (新) | `fmrb.h` の `FMRB_LINK_VERSION 6` | `fmrb_ga_version.h` の `FMRB_LINK_VERSION 6` | 1 か所に。`fmrb.h` と `fmrb_ga_version.h` はこれを include する。`tool/spinel/gen_const_rb.rb` (Spinel の `FmrbConst::LINK_VERSION`) もここを読む |
| `fmrb_link_cobs.h` | `components/fmrb_cobs/` | `main/common/` (消した) | バイト単位で同じだった。`fmrb_link_cobs.c` も同じだったので、graphics-audio は core の `components/fmrb_cobs/fmrb_link_cobs.c` をコンパイルする (写しを消した) |
| `spi_frame.h`・`uart_link_frame.h` | `components/fmrb_hal/platform/esp32/` | `main/common/` (消した) | 同じだった。`_Static_assert` を `static_assert` (`<assert.h>`) にした (C++ からも読めるように。中身は同じ) |
| `fmrb_hid_event.h` | `main/include/` | `main/include/` (消した) | core のもの (`HID_EVENT_IME_TEXT 0x20` が多い、`#ifndef` の guard) |
| `shm_display.h` | (なし) | `main/common/` (core へ移した) | graphics-audio のものをそのまま移し、注の Dockerfile の説明だけ直した |

- `components/fmrb_msg/fmrb_hid_event.{h,c}` (同じ名前の別物、解いた後の `fmrb_hid_event_t` と decode) は `fmrb_hid_decode.{h,c}` に改名した。include していた `lib/add/picoruby-fmrb-app/ports/esp32/app.c`・`components/micropython/modules/fmrb_module.c` と `hosted/hosted.cmake` を直した。型と関数の名前は変えていない。これで `#include "fmrb_hid_event.h"` は include の順に関係なく線の形の方を指す (前はネイティブ版が `../../main/include/...` と相対で逃げていた。今は普通に include する)。
- `MAX_TEXT_LEN`: graphics-audio の `main/common/fmrb_gfx.h` の `FMRB_GFX_MAX_TEXT_LEN` を 256 → 128 にした。graphics-audio の中でこの名前を使っている所は無い (定義だけ) ので、ファームの中身は変わらない (3 章で測った)。`fmrb_gfx.h` 自体は 5 本に入れていないので graphics-audio に残る (古い写し、T0 の 4.1)。
- core の中の付け替え: `fmrb_common` が `fmrb_wire` を REQUIRES (これを使う部品はみな fmrb_common を通して見える)、`fmrb_cobs` も REQUIRES。空になった `main/include` と、ヘッダの無くなった `fmrb_hal` の `PRIV_INCLUDE_DIRS platform/esp32`、`hosted.cmake` の `main/include`・`fmrb_cobs`・`platform/esp32` を外し、`fmrb_wire/include` を足した。

## 2. 参照の仕組み

| 読み手 | 仕組み |
|---|---|
| graphics-audio の CMake | `main/CMakeLists.txt` が `${CMAKE_CURRENT_LIST_DIR}/../../fmruby-core` を `FMRB_CORE_DIR` とし、`components/fmrb_wire/include` を INCLUDE_DIRS に、`components/fmrb_cobs/fmrb_link_cobs.c` を SRCS に足す。無ければ FATAL_ERROR で理由を出す |
| graphics-audio のビルドのコンテナ | `Rakefile` の docker run (通常・特権・対話、menuconfig) に `-v ../fmruby-core:/fmruby-core:ro`。`/project/../fmruby-core` なので相対の位置が中と外で同じ。`build:*`・`set_target:*` は始める前に core の有無を見て止まる |
| ルートの docker-compose.yml | graphics-audio のサービスに `./fmruby-core:/fmruby-core:ro` (今の command は elf を動かすだけで読まないが、同じコンテナで組み直す人のために揃えた) |
| sdl2-display のイメージ | compose の `additional_contexts` に `wire: ./fmruby-core/components/fmrb_wire/include` を足し、Dockerfile は `COPY --from=wire shm_display.h fmrb_hid_event.h /app/include/`。context を core 全体にすると build/ ごと送りかねないので、このディレクトリだけにした |
| MCP の sim_up (古いイメージの検査) | `tools/mcp/lib/sim.rb` の 3 つのパスをワークスペースからの道に (`fmruby-core/components/fmrb_wire/include/...`、`fmruby-graphics-audio/sdl2-display/main.c`)。**MCP サーバは起動し直すまで古いコードのまま**で、古いパスを読もうとして sim_up が落ちる見込み (4 章) |
| Dockerfile.vnc (ルート) | 1 段目で fmruby-core も隣に clone (`--depth 1`、submodule なし) し、3 段目は core の `fmrb_wire/include` から写す。main の枝から作るので、これが main に入るまでは試していない |
| graphics-audio の CI (`.github/workflows/build.yml`) | 2 つの job で checkout を `path: fmruby-graphics-audio` にし、fmruby-core を同じ枝 (`base_ref` か `ref_name`) で `path: fmruby-core` に並べ、steps を `working-directory: fmruby-graphics-audio` で流す。CI を足したのではなく、隣が要るようになったので今の 2 つの job を直したもの。流してはいない (push しない) |
| リリースの workflow (ルート) | `rake fetch` で両方を並べてから組むので変えていない |

## 3. 検査の仕組み (`rake wire:check`、core の `rakelib/wire.rake`)

`rake test` の前提に入れたので `rake regress` (ホストの試験) と CI の test-host でも流れる。要約は 1 行 (`wire: 7 headers self-contained, one copy, 13 tool numbers agree`)。

1. `fmrb_wire/include` の各ヘッダを 1 本ずつ、C (gnu11) と C++ (gnu++17) で `-Wall -Wextra -Werror -fsyntax-only` にかける (include path はこのディレクトリだけ)。core 側の都合の include (fmrb.h など) を足すと graphics-audio で組めなくなるのを、ここで止める。
2. 写しが無いこと: core と graphics-audio の `git ls-files --cached --others --exclude-standard` (追跡していない物も。graphics-audio の `main/common` に写しが残ると、include の順でそちらが勝つため) に同じ名前のファイルが無いこと、graphics-audio に `fmrb_link_cobs.c` が無いこと、`#define FMRB_LINK_VERSION` が `fmrb_link_version.h` の外に無いこと。submodule の中は見ない。
3. 参照が外れていないこと: graphics-audio の `main/CMakeLists.txt` が fmrb_wire を include している、`Rakefile` が `/fmruby-core:ro` を mount している、sdl2-display の Dockerfile が `--from=wire` で写している、ルートの compose に `wire:` の context と graphics-audio の mount がある。
4. 道具の直書きの数: ルートの `tools/fmrb_input.rb` (EV_* 6 つと inject の socket のパス)、`tools/fmrb_screenshot.py` (magic 2 つ・layout の版・640x360)、`tools/fmrb_audio_probe.rb` (標本化の周波数) をヘッダの `#define` と比べる。
- 2 の graphics-audio 側・3・4 は、隣に checkout があるときだけ (ワークスペースの形)。core だけの checkout (CI) では自分の分だけ見て、見なかったことを 1 行出す。
- 試した落ち方: graphics-audio の `main/common/spi_frame.h` に空のファイルを置くと `FAIL fmruby-graphics-audio/main/common/spi_frame.h: a copy of the wire header ...` で止まる。C++ の検査は最初 `spi_frame.h`・`uart_link_frame.h` の `_Static_assert` で落ちた (1 章で直した)。

入力イベントの型を 1 つ足すのに直すのは、ヘッダ `fmrb_hid_event.h` 1 つと graphics-audio の中継の switch (`main/input_linux/input_handler_ipc.c`) と core の受け (`usb_task_linux.c`)。switch は残した (消す・既定で中継にするかは T0 4.5 のとおりユーザの判断、今回は触っていない)。CLAUDE.md (ルート・core・graphics-audio) をこれに合わせた。

## 5. launcher の画面の基準

- `tools/regress/screens.rb` の sim の起動 (`bring_up`) の前に `flash/var/cache/launcher_index` を消すようにした。デスクトップは起動時にキャッシュが無ければ /app を走査して書き直すので、毎回その時点の木から作られる (ランチャーの読み方そのものを通る)。キャッシュの中身を道具が別に作る形は、ランチャーの名前・絵の決め方 (`FmrbApp.app_meta`) を Ruby で写すことになるので採らなかった。
- ブラウザ版はキャッシュを持たない (束ねるのは追跡分だけ) ので、もともと毎回作り直しで、T1 でも通っていた。
- 流れるのは手元の flash/app の中身なので、git に入っていないアプリを flash/app に置いているとそれも載る (今は無い)。

## 6. 残件

- **画面の基準の更新 (親)**: `regress:screens` の `retro/launcher`・`modern/launcher` (Avatar が一覧に出る)。差分の絵は `tmp/regress/screens/diff/{retro,modern}/launcher.png`。`rake regress:screens:update` は前回の落ちた写しだけを写すので、流し直さずにそのまま使える。
- **`regress:run` の基準 (親)**: T2 の前から古い (4 章の表)。更新するなら T2 とは別に、変化を見て決める。
- **MCP サーバの起動し直し (ユーザ)**: 動いている fmrb MCP サーバは古い `sim.rb` を読み込んだままで、`sim_up` が消えたパス (`fmruby-graphics-audio/main/common/shm_display.h`) を開こうとして `Errno::ENOENT` で止まる (確かめた)。サーバを起動し直せば新しいパスで動く (新しいコードは直接呼んで通ることを確かめた)。
- **graphics-audio の CI と Dockerfile.vnc は流していない**。CI は push のあと、Dockerfile.vnc は main に入ってから (main の枝を clone するため)。
- graphics-audio の `main/common/fmrb_gfx.h` は古い写しのまま残る (5 本に入れていない。`MAX_TEXT_LEN` だけ揃えた)。ほかの同名のヘッダ (audio_commands・wav・bmp332・eintr) も T0 の決定どおり範囲の外。
- 入力の中継の switch (graphics-audio `input_handler_ipc.c`) は残した。知らない型を既定で中継にするかはユーザの判断 (T0 4.5)。
- `doc/README.md` の索引 (`rake docs:index`) は流していない。作業ツリーの `doc/README.md` にほかのセッション (wasm_apps) の未コミットの変更があるため。
- sdl2-display のイメージを作るとき `usleep` の暗黙の宣言の警告が出る (main.c の前からのもの、今回は触っていない)。
