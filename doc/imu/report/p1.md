# P1: six-axis sensor (BMI270) on Modern

Tab5 carries a BMI270 that the firmware never touched. This adds a driver and
a demo app for it. Written on the desk, without the hardware: everything below
that says "verified" was verified without a Tab5, and the open items at the end
are the ones only the device can answer.

## What is here

| File | Role |
|---|---|
| `lib/add/picoruby-bmi270/mrblib/bmi270.rb` | The driver. Pure Ruby, needs only an I2C object |
| `flash/usr/share/imu/bmi270_config.bin` | The 8192-byte configuration image the sensor needs before it measures anything |
| `tool/gen_bmi270_config.rb` | Regenerates that image from the array in the M5Unified component |
| `flash/app/demo/imu.app.rb` | Demo: bubble level plus the raw values |
| `tool/imu/test/verify.rb` | Host-side check of the driver against a fake device |

Registered for the P4 build only (`lib/add/family_mruby_esp32p4.rb`); Retro has
no IMU.

## Three decisions

Pure Ruby, no C. The Ruby I2C class already reaches the internal bus: on
Modern, unit 1 is routed through the display driver's serialized I2C service
(`hw_proxy_i2c.c`), which is what keeps the touch controller, the IO expanders,
the codec and the RTC from colliding on that bus. An app joins that queue like
any other user. The RTC driver set the precedent (`picoruby-rx8130`), and it
means the whole feature is Ruby that can be edited on the device.

The configuration image is a file, not a literal. The BMI270 answers on the bus
straight after reset but produces nothing until 8 KB of configuration is
written into its internal memory. As a Ruby literal that would sit in the
firmware; as a file it stays in the filesystem and is streamed in 256-byte
chunks. Init cost is 32 I2C transactions, once.

Bytes are moved with `getbyte`, never with `String#[]`. The build defines
`MRB_UTF8_STRING`, so slicing a binary string counts characters, not bytes.
This is the kind of bug that would have shown up as a sensor that initialises
on some images and not on others.

## What was verified, and how

`ruby tool/imu/test/verify.rb` loads the driver on the host and drives it
against a fake BMI270 that records every write. 22 checks, all passing: the
reset and enable bracket, the load address arithmetic (the address counts
16-bit words, so the test rebuilds the image from the recorded addresses and
compares it byte for byte against the file), even-sized chunks, the four ways
init can fail, and the sign and scale of the measurements.

The demo app was run in the Linux simulation, where there is no sensor: it
falls back to a synthetic tilt and says so on the status line. The launcher
lists it, the window draws, the ball tracks the synthetic tilt across frames,
the values update, and Ctrl+Q exits with no exception in the log. That covers
the drawing and the app lifecycle, nothing about the sensor.

Note for anyone repeating this: the simulation needs both repositories built
for Linux. A stale graphics-audio binary reports the wrong version and the
kernel stops at the version check, which looks nothing like a version problem
on screen -- the display just sits at "Waiting for Core".

## What the hardware said (first run)

The sensor answered on the first try, so it is on the internal bus and the
probe finds it. What failed was the configuration load, and the reason was
worth the trip: on Modern every I2C transaction goes through
`display_p4_i2c_write`, which takes the length in a byte and refuses anything
past 255. The upload was sending a register byte plus a 256-byte chunk, so
every one of those transactions was rejected before it reached the bus.

It looked like nothing at all from the outside: reads are one byte, so the
probe succeeded, and the failure came back as a plain false 143 ms after the
app started. That is why the driver now records which step gave up
(`BMI270#error`) and the demo shows it -- three different failures used to
arrive as one word.

Chunks are 128 bytes now, 64 transactions for the image, and
`tool/imu/test/verify.rb` checks that a whole transaction stays inside 255.

The second run got past that and stopped at the next step: the read that
follows the soft reset. The datasheet calls it a dummy read, there to keep the
interface in I2C mode, and the driver did it once. The real part refuses reads
for the first few milliseconds after a reset, so that one attempt hit a NACK
and init gave up. M5Unified polls there rather than reading once, which is the
tell. The driver now asks up to twenty times, 2 ms apart, until the chip
identifies itself.

Both of these passed every host check before they failed on hardware, because
the fake device answered everything immediately. The fake now refuses reads
after a reset the way the real one does, and both failures have a check.

## Working on the machine

The sensor answers at 0x68 on the internal bus. Lying flat it reads
z = -0.99 g with the gyro at rest and the die at 39 degrees, so the axis that
reads +1 g points down and +z points into the screen.

The screen axes are not the sensor axes, as expected from a panel mounted
portrait and turned 90 degrees. Measured by tilting the machine and reading the
app: lowering the right edge gives y = -0.49, lowering the near edge gives
x = +0.78. So the sensor's +x runs down the screen and its +y runs to the left,
and the level maps `screen_x = -y`, `screen_y = +x`.

That mapping was then checked against a prediction rather than by eye: with the
right edge down at y = -0.56 the ball should sit 21.3 px right of centre, and it
measured 21.0.

## Cross-check against M5's own firmware

Read after the fact, and it holds up. `M5Tab5-UserDemo`'s `hal_imu.cpp` swaps
x and y the same way this app does, and negates z -- which is the same
observation from the other end, that the part reports +1 g on the axis pointing
down.

One difference worth writing down so nobody 'fixes' it later. M5 scales the
accelerometer as if the range were +-4 g; this driver assumes +-8 g. The
reason is that they configure the range explicitly through a vendor wrapper
while this driver leaves the register alone, so the BMI270 default (+-8 g)
stands. Gravity settles which is right for us: lying flat we read -0.99 g. At
+-4 g the same counts would read -0.495 g, which is not a thing gravity does.
M5Unified's own BMI270 class also assumes +-8 g.

## Open items (need the hardware)

1. Load timing. The driver waits up to 40 ms for the sensor to report a good
   load. That is the datasheet figure with margin, not a measured one.
2. Whether the demo's 20 reads a second disturb anything else on that bus
   (touch is polled on the same service).

Verification does not need a serial cable: the remote desktop can start the app
and take the screen, and the sensor values are on the screen.
