## やったこと(すべて display_p4_task.cpp)

### A. present 順序化(バーのちらつき)
- `flush_pending_render()` を新設し、**`process_gfx_command` の先頭で呼ぶ**。
  present で立った保留 render を、次コマンドの適用前に in-order で消化。
- タスクループの**受信前タイマー render を撤去**。代わりに**受信タイムアウト
  (アイドル)時のみ** trailing フレームを描く(保留中は timeout=5ms)。
- CLEAR ケースの重複 flush(旧 998-1002)を削除(先頭 flush に包含)。
- 未使用になった `RENDER_MIN_INTERVAL_MS` と、書くだけになった `g_last_render_ms`
  を削除。render 統計はファイルスコープ(`g_stat_*`)+ `note_render()` に集約し、
  全 render 経路で数えるようにした。

### B. カーソルのフレーム合成(カーソルのちらつき)
- `framebuffer_bake_cursor()` / `framebuffer_restore_cursor()` を新設。
- render_frame の **capture 後・scale-out(PPA/software push)前**にカーソル 16x16 を
  g_framebuffer へ焼き込み、push 後に 16x16 を復元。カーソルはフレームの一部として
  1 回の DMA で g_dsi_fb に書かれる → 「消して再パッチ」の隙間が消える。
- 旧 post-PPA パッチ(`g_cursor_drawn=false; cursor_overlay_update()`)を廃止。
  焼き込み後に `g_cursor_drawn` と drawn 座標を更新。
- **fast-path(move/visible 変更時の cursor_patch)は温存**。g_framebuffer は常に
  復元されカーソルなしなので、capture・fast-path・次合成すべて従来どおり。

## 実機で確認すること(ユーザ)

1. Mic Spectrum で**バーのちらつきが消える**こと。
2. **マウスカーソルのちらつきが消える**こと(特にスペクトラム窓の上で動かした時)。
3. 退行なし: 通常のデスクトップ操作・カーソル移動・ウィンドウ操作・文字化けなし。
4. r1.md の quick-tap 壁紙ちらつきが**再発しない**こと。
5. 体感で重くない/カクつかないこと。`docker`/シリアルの `render: N frames/5s` で
   fps を確認できる(全 render 経路が数えられる)。

## 補足
- 実機 elf は RISC-V **single-float**。P4 の FPU が単精度である裏付け
  (別件: track_a の Spinel 精度深堀)。
- レート上限(フレームドロップ)は未実装。present ごとに render するので、極端に
  present 頻度が高いアプリでは render 回数が増える。必要なら順序を壊さない drop を
  後追いする。

## 追記 v2: 実機確認で残ったちらつきと再修正(2026-08-14)

実機確認: **カーソルのちらつきは解消**(フレーム合成 B が有効)。バー/文字は
大きく改善したが**数秒に一回残る**。決め手=「バーがちらつく時カーソルはちらつか
ない」→ テアリングではなくコンテンツ(合成時にバーが欠けている)。

真因(A の穴): `g_needs_render` はグローバルで、**どのアプリの present でも全
キャンバスを render** する。当初の「`process_gfx_command` 先頭で flush」は、別アプリ
(デスクトップのメニューバー時計/メモリ表示が毎秒 present)が**前景アプリの描画
バースト途中**に割り込むと、次の描画 op の flush が**半分描いたバー**を合成して
しまう(数秒に一回=desktop present がバースト窓に当たる確率)。

再修正: **先頭 flush を撤去し、render は「コマンドキューが静穏(受信タイムアウト)」
の時だけ**に一本化。静穏=全アプリがバースト外=全キャンバス完成、なのでどの
アプリのバースト途中も拾わない。これはユーザ原則(割り込ませない)の純粋形。
esp32 ビルド通過・実機再 flash 済み・**バーの残ちらつきの実機再確認待ち**。

既知の残リスク(稀): 前景アプリが GC 等でバースト途中に >5ms 停止し、かつその瞬間に
他アプリの present で needs_render が立っていると、idle render が半描画を拾いうる。
完全解は**キャンバスごとに present 済み状態だけを合成**(per-canvas commit)だが重い
ので、残れば次段で検討。
