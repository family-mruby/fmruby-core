# 作業レポート r1: 調査と Stage 1 スパイク

計画書: `../plan.md`。ブランチ `feature/p4-display-doublebuffer`。随時追記。

## 調査で確定したこと

- 合成タイミングは無罪。`display_p4_task.cpp` に一時ログ(P4SEQ)を入れ、実機
  シリアルで `CLEAR(needs_render=0) -> PRESENT -> RENDER` の順を確認。render は
  clear と present の間に割り込まない = 常に完全フレームを合成。(ログは撤去済み)
- 真因は表示ハンドオフ: PPA SRM が `g_dsi_fb`(パネル走査中の唯一の FB、
  m5gfx `num_fbs=1`)へ直接全面書込。二重バッファ/vsync 同期なし → テアリング。
- GC 仮説(navigate 前の scan の GC が clear と present の間に挟まる)は**誤り**
  だった(計装で反証)。アプリ側の部分再描画(fmgr_repaint 等、develop の
  eba5576)は「更新面積を小さくして症状を目立たなくする」緩和で、根本ではない。

## Stage 1 進捗

### esp_lcd DPI 二重バッファ API 確定 (IDF v5.5, コンテナ内ヘッダ実見)

- `esp_lcd_dpi_panel_config_t.num_fbs`: 0/1=単, 2=二重。
- `esp_lcd_dpi_panel_get_frame_buffer(panel, fb_num, &fb0, &fb1, ...)` で複数取得。
- スワップ: `esp_lcd_panel_draw_bitmap(panel, 0,0,W,H, fb)` に**内部 FB ポインタ**を
  渡すと、その FB を表示側に切替(vsync 境界で反映)。
- 完了通知: `esp_lcd_dpi_panel_register_event_callbacks` で `on_refresh_done`
  (内部 FB の画面反映完了)/ `on_color_trans_done`。ping-pong の再利用可否は
  これで同期。
- IDF 5.5 は `flags.use_dma2d=true`(6.0 以降は enable_dma2d API)。

### 採用アプローチ

### 決定的観察 (ユーザ, 実機物理タップ)

- A: **全画面が壁紙**になる(前景 cid=1 が丸ごと欠落した1フレーム)。
- B: **離した瞬間**。かつ **軽い(素早い)タップだけ**再現、長押ししてから離すと出ない。
- 解釈: 前景 cid=1 を全面 clear(0x01=透過)→再描画する draw_foreground が、軽い
  タップでは押下/クリック/選択で**数回連射**され、render レート制限
  (RENDER_MIN_INTERVAL=33ms)で遅延した render が**クリア途中(cid=1 全面透過)**で
  発火 → 前景欠落=壁紙のみの1フレームを表示。長押しは各 draw_foreground の間隔が
  開き render が即時なので出ない。
- DSI 二重バッファ(1a/1b)が効かないのは当然(完全に「壁紙のみの1フレーム」を
  綺麗に表示するだけ)。P4DIRTY=0 だったのは採取中に軽い連射タップをしていなかった
  ため(次に再現して確認)。
- 想定する修正: CLEAR 処理の前に保留中 render を flush(前フレームを確定表示)し
  g_needs_render をリセット → クリア途中に render が発火しない。per-canvas 二重
  バッファよりも小さく、managed component 非依存。DSI 二重バッファは撤去。

### 機序 確定 (P4DIRTY 実測)

ユーザの軽いタップ再現中、`P4DIRTY cid=1 composited mid-draw` を **4 回**記録。
render が cleared(全面透過)cid=1 を合成した = 前景欠落の1フレーム。観察
(全画面壁紙・離した瞬間・軽いタップ・1フレーム)と一致し、根本原因を確定。

**修正方針**: display_p4_task の CLEAR 処理の冒頭で、保留中 render があれば
flush(前フレームを確定表示)+ g_needs_render リセット → クリア途中に render が
発火しない。DSI 二重バッファ(1a/1b)と計装(P4SEQ/P4DIRTY/dirty_since_present)は
撤去。アプリ側部分再描画(eba5576)はこのブランチで revert 済みのまま(根治後は
クリア方式のままで良い、というユーザ方針)。

## 解決 (根治完了)

真の根本原因は **DSI テアリングではなく、レート制限で遅延した render が
draw_foreground のクリア途中(cid=1 全面透過)で発火し、前景欠落=壁紙のみの
1フレームを合成・表示**していたこと(P4DIRTY 実測で確定)。DSI 二重バッファ
(1a/1b)は層違いで無効だったため撤去。

### 修正(2点、実機確認済み)

1. **flush-before-clear**(`display_p4_task.cpp` の CLEAR/FILL_SCREEN 処理):
   クリア適用前に、保留中 render があれば flush(前フレームを確定表示)+
   g_needs_render リセット → クリア途中に render が発火しない。保留 render が
   あるとき(=軽いタップの連射)だけ働くので、定常 30fps アプリは無コスト。
   → **全画面が壁紙になるちらつきが消えた**(ユーザ確認)。操作の重さ増なし。
2. **選択反転の点滅**(`file_manager.rb` の handle_file_manager_click):
   #1 で中間フレームも描くようになったため、押下ハイライト→(had_pressed の)
   無ハイライト再描画→選択ハイライト、が「反転オン→オフ→オン」と点滅した。
   中間の無ハイライト再描画を削除し、押下→選択が同じ行のハイライトのまま
   繋がるように。クリックが行に当たらなかった時だけ末尾で押下ハイライトを消す。
   → **反転の点滅も消えた**(ユーザ確認)。
