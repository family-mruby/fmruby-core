## 3. 道具に足した規則 (`tools/boundary/gen.rb`)

### 3.1 足したもの

| 規則 | 中身 |
|---|---|
| 受け手の番号なしのクラス | `NO_RECEIVER = FmrbApp, FmrbAudio`。インスタンスメソッドでも第 1 引数を取らない (plan の「FmrbApp のインスタンスメソッドとモジュールの関数は番号なし」を FmrbAudio に広げた。FmrbAudio はアプリしか持たない)。Lua・Python ではオブジェクトのメソッドのまま (`audio:note_off(0)`、self は読まない) |
| 書き込みのメソッド | `main_volume=` は C・wasm・Lua・Python で `set_main_volume`。mruby は `main_volume=` で登録 |
| `int64` の結果 | `-> int64` は C で `int64_t` を返す (負はエラー)。mruby `mrb_int_value`、Lua `lua_pushinteger`、Python は small int に入れば int (入らなければ OverflowError、4.3)、wasm は結果 `I`、Spinel `:int64`。ABI のハッシュに `->int64` を入れる |
| クラスごとの取り込み (mruby) | `fmrb_boundary_mrb.inc` をクラスごとに `#ifdef FMRB_GEN_MRB_<Class>` で囲んだ。gem の C ファイルは欲しいクラスを定義してから include する (gfx.c は FmrbGfx、app.c は FmrbApp と FmrbAudio、picoruby-fmrb-log は Log)。受け手の番号の要らないクラスはフックも要らない |
| 段の途中のクラス | `STAGED = { 'FmrbApp' => [...] }`。印の無いクラスの、並べたメソッドだけを載せる。W4b-3 で FmrbApp にクラスの印を付けたら消す (印と STAGED が両方あると道具が止まる)。並べたものに internal・hook が付いていても止まる |

`int64` 以外の結果の型・記録・バイト列の規則は W4a のまま使った (`clipboard_raw` は「呼ぶ側のバッファ、全体の長さを
返す」。本体はクリップボードの錠の下で 1 つの版を読み、バッファが足りなければ入るだけの**文字の途中で切らない**
長さを書く。mruby・Lua・Python のつなぎが長さを知って取り直す間に中身が変わっても、壊れた UTF-8 にならない)。

### 3.2 そのまま残した手書き

- mruby の `Log.info` など: gem の C の包みのまま (タグを先に渡す 2 引数の形を読む。使っている所は無いが、無くすのは
  書き方の変更なので残した)。`present` と並ぶ「mruby の包みが C」の例外 (sig/README.md に書いた)。
- Spinel の `FmrbApp.clipboard_raw`: Spinel のバイト列の適合は 256 バイトまで (W4a の規則) なので、64 KB の
  クリップボードは前と同じ 4 KB ずつの FFI (`fmrb_spx_app_clipboard_chunk`) で読む。世代と書き込みは境界の関数。

## 4. 各言語の変化

### 4.1 Ruby (mruby・Spinel)

- **書き方は変わらない** (名前・引数・既定値・返り値の Hash の鍵は同じ)。境界の `_raw` などは公開の API として増えた。
- 戻り値: `play`・`stop`・`pause`・`resume`・`load_fmsq*`・`play_slot`・`note_on`・`note_off` は、前は `send_message` の
  true/false を返していた (sig は `void`)。今は nil。戻り値を使うアプリは無い (`play_wav` だけが使われ、true/false の
  まま)。カーネルの待ち行列が満ちたときは前と同じく落として記録に書く (例外にしない。音符が流れの途中で
  アプリを止めないため)。1 メッセージ (176 バイト) を超える `load_fmsq` は前と同じく ArgumentError。
- Spinel: `nsf_status` が本当の答えを返すようになった (前は常に nil)。`FmrbApp.uptime_us` が 64 ビットになった
  (前は 32 ビットの µs で 71 分ごとに一周)。
- ログの行のタグが、全エンジンでアプリの名前になった (mruby は前から。Spinel のアプリは "spx"、MicroPython は
  "fmrb_mp_mod" だった)。カーネル (Spinel のカーネルの基底の Log) は変えていない。
- mruby の `FmrbApp#_send_audio_note`・`_audio_nsf_status`、Spinel の同じ名前の Ruby と FFI
  (`fmrb_spx_app_send_audio_note`・`clipboard_gen`・`set_clipboard`・`wallclock`) は消した。`_audio_note_bytes`
  (midi_bench の検査) は残した。

### 4.2 Lua

全部新しく使えるようになった (前は無かった)。`FmrbAudio.new()` と `audio:note_on(...)` など (既定値は小さな
前置きで Ruby と同じ)、定数 `FmrbAudio.MAIN`・`CH_*`・`NSF_*`、`Log.info(msg)` など、`FmrbApp.clipboard([limit])`・
`set_clipboard`・`clipboard_gen`・`uptime_us()`・`wallclock()` (表か nil)。README に書いた。

### 4.3 MicroPython

- `FmrbAudio`・`Log`・`FmrbApp` は、生成したクラス (`_FmrbAudioBoundary`・`_LogBoundary`・`_FmrbAppBoundary`) を継ぐ。
  手書きは既定値を持つ包み (`play`・`play_slot`・`note_on`・`Log.info` など・`FmrbApp.clipboard`) だけ。
- 増えたもの: `nsf_status()`・`load_fmsq`・`set_main_volume`・`play_wav`・`stop_wav`・`NSF_*`、
  `FmrbApp.clipboard`・`set_clipboard`・`clipboard_gen`・`uptime_us`・`wallclock`、`Log.info_raw` など。
- 消したもの: `_fmrb.log`・`_fmrb.audio_note` (bridge の 2 つも)。`_send` の dict の経路も無くなった。
  直す要のある Python のアプリは無かった。
- **`FmrbApp.uptime_us()` の注意**: この MicroPython は長い整数を持たない (small int だけ)。ESP32 では small int が
  31 ビットなので、起動から約 18 分を過ぎると OverflowError になる (sim の 64 ビットでは起きない)。`ticks_ms()` は
  前のまま。長い整数を入れるか、µs を一周させるかは決めていない (6 章)。
- qstr の表を作り直した (`rake micropython:gen`、35 増え 1 減った)。`doc/micropython/known_limitations.md` を直した。

### 4.4 wasm (C の SDK)

`sdk/c/fmrb_boundary.h` に 22 関数と 2 つの記録が増えた (ABI のハッシュ `d34fea71`)。`ruby tools/wamr_poc/run.rb boundary`
の巡回 (`tour.h`) に、受け手なし・書き込みの名前・int64 の結果・バイト列の結果・FmrbApp の記録・Log の呼び出しを
足した (呼び出し 13 → 23)。

## 5. ファイルのまとまり (止めて返す。ユーザが決める)

境界に載せる形を決めるには、アプリの書き方・名前の選択がある。

**分かったこと**:

- Ruby の `File` は picoruby の `File < IO` (fd を持つ IO のクラス) で、`read(n)`・`gets`・`each_line`・ブロックの
  `open` など sig (`sig/fmrb_misc.rbs` の 7 つ) より広い。`class File` に印を付けると、生成した mruby のつなぎが IO の
  メソッドを sig の簡略の形で**上書きする** (例: `f.read(10)` が引数の数の誤りになる)。今のまま印を付けることはできない。
- ファイルは状態 (読む位置) を持つ。W4a の「呼ぶ側のバッファ、全体の長さを返す」規則は、同じ答えを 2 回聞ける前提
  (足りなければ長さを知って取り直す)。fd から読む `read` に当てると、1 回目で読む位置が進む。
- `gets` の `String?` (終わりで nil) は今の規則で書けない (`?` の結果は記録だけ)。`free_bytes` の nil も同じ。
- 他の言語は既に自分の形を持つ: Lua は標準の `io` (書ける)、MicroPython は `_fmrb.read_file`・`file_size` (読むだけ)。

**案** (推奨を先に):

| 案 | Ruby | 境界の関数 | 他の言語 | 気になる所 |
|---|---|---|---|---|
| **A (推奨)** 丸ごと読み書きする関数を新しいモジュールに | `FmrbFile.read(path)`・`write(path, data)`・`append`・`size(path)`・`exist?`・`delete`・`list(dir)` などを**足す** (`File` は今のまま) | パスで呼ぶ、状態を持たない形。読むのは「呼ぶ側のバッファ、全体の長さ」(読み直しても同じ答え)。読み書きできる範囲の判定は本体 (HAL) | Python の `read_file` をこれに置き換える。Lua は `io` と並ぶ | Ruby に名前が 1 つ増える (どちらで書くか迷う)。大きいファイルは丸ごとメモリに載る (MicroPython の今の上限と同じ考え) |
| B `File` を境界に載せ、mruby は IO のまま | 変わらない | `File.open` が fd の番号を返し、`read(fd, out, size)` は読んだ分を返す (snprintf 型でない規則を足す)。`gets` は規則を足す | Lua・Python に `File` | 道具に「mruby のつなぎを作らないクラス」の印が要る (独自の記法が増える)。`gets` の nil・読む位置と規則の食い違いの 2 つを足す |
| C 載せない (各言語の形のまま) | 変わらない | 無し | 今のまま | wasm のアプリにファイルが無い (決定 6 に反する) |

あわせて決めること: `FmrbApp.path_read_only?`・`free_bytes` をファイルのまとまりで載せるか (W4b-3 の FmrbApp に回すか)、
`free_bytes` の「分からない」を何で表すか (例: `-> int64` で -1 を「分からない」にすると、負はエラーの規則と食い違う)。

## 6. 命令数 (mruby、ホスト)

W4b-1b と同じ測り方 (本体の mruby をホスト向けに `-O2`、何もしない平らな関数、callgrind、`ghost-valgrind`、

## 8. W4b-3 (FmrbApp) への注意

- FmrbApp に `%a{fmrb.boundary}` を付けたら、`tools/boundary/gen.rb` の `STAGED` を消す (両方あると道具が止まる)。
  今の 5 つ (`clipboard_raw` など) はそのまま載る。
- FmrbApp のインスタンスメソッドは受け手の番号を取らない (`NO_RECEIVER` に入れ済み)。Lua・Python ではオブジェクトの
  メソッドとして呼ぶ形になる (FmrbAudio と同じ)。Lua のアプリにはアプリのオブジェクトが無いので、FmrbApp のインスタンス
  メソッドを Lua にどう出すかは決める必要がある (今の Lua は `FmrbApp.xxx()` の関数)。
- mruby の app.c は `FMRB_GEN_MRB_FmrbApp` を定義して include 済み。手書きの C のメソッドを消して生成に寄せれば
  よい。`fmrb_app_*` (アプリの task の API) と名前はぶつからない (本体の実体は `fmrb_bnd_app_*`)。
- `FmrbApp.language` は Spinel が実行時に読む (FFI)、mruby は定数。境界に載せると mruby も C を呼ぶ。
- 結果に nil があり得る整数 (`free_bytes`・`battery_level`・`linux_exit_code` など) と `String?` (`linux_read`・
  `checkpoint`) は今の規則で書けない。規則を足すか、記録にするかを決める (5 章の `free_bytes` と同じ問題)。
- 文字列の結果が 256 バイトを超えうるもの (`script_path`・`ps` など) は、Spinel のバイト列の適合の上限に当たる。
  クリップボードは Spinel の手書きの分割読みで逃げた。数が増えるなら適合の作り (呼び出しごとに確保する、など) を
  見直す。
- `Hash` を返すもの (`heap_info`・`wifi_info` など) は記録型を書けばそのまま載る。`ps` (`Array[Hash]`) は
  記録の配列を結果にする規則が無い。
