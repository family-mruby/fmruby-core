# アプリの境界と型定義からの生成 計画

> 状態: 進行中 | 更新: 2026-11-15 | アプリと本体の間の境界を、型定義 `sig/*.rbs` の 1 か所から全エンジン (mruby・Spinel・Lua・MicroPython・wasm の各言語・C のヘッダ) のつなぎを生成する形に整え、Window の枠と一生の処理を本体の C の殻に置く。doc/wasm_apps から W3 (殻) と W4 (生成) を分けたテーマ (wasm_apps の決定 16)。W3・W4a を wasm_apps の W1b より先に進める (決定 15)。W3 完了 (殻と Lua)。次は W4a (W4a の 3 点はユーザが決める)

## 目的

- アプリから使える本体の API を、**型定義 (`sig/*.rbs`) の 1 か所**から、全エンジンのつなぎと
  他の言語の bindings を生成する形にする。今はエンジンごとに同じ仕事をする C のつなぎを手で
  書いている (doc/wasm_apps/report/w0.md 1.6)。
- その結果、Ruby (mruby・Spinel)・Lua・Python (MicroPython)・Rust・Go (TinyGo)・Zig・C が、同じ
  定義から同じ範囲の API を持つ。wasm のアプリ (doc/wasm_apps) はこの上に乗る。
- Window の枠と一生の処理 (アプリの殻) を本体の C に置き、言語ごとに枠を書かずに済むようにする。
- この仕事の価値は WAMR と同じくらいある (ユーザ)。WAMR は言語を増やす部品で、この計画は
  全言語を 1 つの定義でつなぐ仕事。RBS に価値が生まれる。

## 方針

### 考え方の芯 (迷ったらここに戻る)

- **Ruby が中心。** RBS を IDL として扱うのは、Ruby が中心の企画だから (プロジェクトの名前の
  とおり)。専用の IDL のほうが技術的に楽な所でも採らない。ほかの言語は、Ruby の定義を通じて
  加わる (doc/rbs_types の「なぜ RBS か」)。
- **定義は `sig/*.rbs` の 1 か所だけ。** Ruby から見える API の型定義がそのまま唯一の元で、平らな
  層のための別の定義や、別の形式のマスタは作らない。エディタに見せる情報 (メソッドの形と
  説明文) が一番価値のある定義なので、それを正とし、本体に載せる型データベースと各言語の
  つなぎはそこから作る。
- **RBS として自然に読めること。** 規則を決めるときは、独自の記法を増やさないことを判断の軸に
  する。
- **Ruby のアプリの書き方は変えない。** 境界は単純な形にし、使い勝手は Ruby の薄い包みで保つ。

### 境界と包み (2026-11-14 ユーザ)

- **境界の関数は単純な形にし、Ruby らしい使い勝手は Ruby の薄い包みで保つ。** 境界の関数は
  整数・文字列・記録だけを受け渡しする。省略できる引数・キーワード引数・Symbol などの Ruby
  らしい形は、その上の Ruby の包みが境界の形へ直す。**今の実装は mruby も Spinel も既に
  この 2 段の作りになっている**: mruby は mrblib の Ruby のメソッド (`draw_text` など) が
  `_` で始まる C のメソッド (`_draw_text` など) を呼び、Spinel は基底の Ruby のメソッドが
  平らな関数を呼ぶ (doc/wasm_apps/report/w0.md 1.7)。境界の関数に当たるものが内部用として
  隠れているだけなので、作り直しではなく、それを公開の形に整える作業になる。形が最初から
  単純な関数 (`fill_rect`・`present` など) は包みが無く、境界の関数がそのまま公開の API に
  なっている。
- **境界の関数は Ruby のアプリからも呼んでよい。** 包みを通ると呼び出しが 1 段深くなるので、
  速さが気になる所 (毎フレーム何度も呼ぶ描画など) では、アプリが包みを使わずに境界の単純な
  関数を直接呼べる。そのため境界の関数は内部用として隠さず、公開の API として型定義に説明文
  つきで書き、エディタにも出す。
- **システム側と Ruby で書かれたライブラリは、境界の関数を呼ぶ。** 包みは利用者のアプリのための
  使い勝手で、カーネル・デスクトップ・標準アプリ・基底クラス・ライブラリ (FmrbUI・FmrbText
  など) は、包みを持つ関数については境界の関数を直接呼ぶ。mruby では今より速くなる見込みが
  ある (包みの 1 段と、キーワード引数のたびに作られる Hash が無くなる)。順番は、利用者の
  アプリの VM の中で動くライブラリ → 基底クラスの枠の描画 → デスクトップと標準アプリ。最後の
  2 つは標準構成では Spinel で動き、効果が小さい見込みなので、計測してから置き換えるかを決める。
- **包みは状態を持たない。** 今の包みは、選んだフォントと文字の大きさを Ruby の変数で覚えて
  いる (mruby・Spinel とも)。このままでは、包みを通さずに境界の関数でフォントを変えたときに
  値がずれる。状態は境界の下 (C の側) に置き、境界の関数で読めるようにする。包みと境界の
  関数を混ぜて使っても壊れないことが、上の 2 つの方針の条件になる。
- **描画の原点も境界の下に置く (wasm_apps の決定 17)。** mruby は既に C の gfx 構造体
  (`mrb_gfx_data`) が原点を持って C で足している。Spinel と Python (MicroPython) の FmrbGfx は
  包みが原点を持って足しているので、これを C の側へ移す。他の言語のアプリが足し算を自分で
  書かずに済む。W4b で行う。

### 前提と線引き

- **アプリの API の整理 (doc/codebase_tidy、2026-11-15 完了) の結果を前提にする。** そちらで
  引いた線と同じ線を使い、この計画で別の線を引かない。
  - system 用のクラスメソッドは、整理の T5 で `FmrbSystem` (モジュール) に分けた。端末の設定と
    サービスを変える 34 本 (一覧は doc/codebase_tidy/report/t5.md 1 章) で、sig は
    `sig/fmrb_system.rbs`。`FmrbSystem` に入るもの = 境界に載せないもの。
  - **`FmrbApp` に残ったクラスメソッドのうち、状態を読むだけのもの (音量を知る、USB の一覧、
    プロセスの一覧、Wi-Fi の状態など) は境界に載せる。状態を変えるものは FmrbSystem の側と
    して載せない (wasm_apps の決定 18)。** checkpoint と `move` は下の「載せないもの」のまま。
  - 描画の座標の原点は、整理の T4 で「そのアプリが描いてよい区画」の左上 (枠のある Window は
    user area、全画面・枠なし・desktop は Window そのもの) にした (doc/codebase_tidy/report/t4.md)。
    区画の外 (Window の座標) に描く口は 2 つめの描き手 (`@window_gfx`・`window_gfx`)、
    イベントの Window の座標は `ev[:wx]`・`ev[:wy]` で、`ev[:x]`・`ev[:y]` は区画の座標。
- **ファイルと音は境界に載せる範囲に入れる (wasm_apps の決定 6)。** ファイルの読み書きできる
  範囲は Ruby のアプリと同じで、判定は境界の下に置く。I2C・GPIO などの HW は最初には含めない
  (決定 8。doc/hw_resources の H6 で、境界に関数を足す形で全言語に出す)。
- **つなぎは全エンジンで生成する。** wasm の 3 言語・Lua・MicroPython・Spinel の宣言に加えて、
  mruby の gem のつなぎ (引数の取り出しの部分) も、境界が単純な形なので生成に切り替える。
- Ruby の基底クラスの 2 つの実装 (mruby 用・Spinel 用) を 1 つにすることは、この計画の目的に
  しない。ただし両方が「同じ境界の関数を呼ぶ Ruby」になるので、包みを共用できる範囲は共用する。
  枠の描画を C の関数へ差し替えるかは、殻ができた後に判断する。
- **進め方: 機能のまとまりごとに実装する。計測と重い回帰は要所だけにする (2026-11-14 ユーザ)。**
  - まとまりは、描画の基本図形・文字・画像とスプライト・アプリと Window・時刻とログと
    クリップボード・ファイル・音、の 7 つ (決定 6)。
  - 日々の確認は軽い回帰 (`rake regress`)。まとまりの終わりもこれで足りる。
  - 重い回帰 (`regress:screens`・`regress:run`・`regress:size`) は、段 (W4a・W4b など) の
    終わりに 1 回。ただしカーネルの標準の経路 (Spinel の基底・平らな関数) を触った
    まとまりだけは、その終わりに `regress:screens` を 1 回足す (エディタの 1 打鍵が入っている)。
  - 命令数の比較は、最初のまとまりで代表の関数を 2〜3 個 (`draw_text`・`draw_image` など) だけ
    測る。結果が見立てどおりなら、以後のまとまりでは測らない。
  - 関数ごとにコミットを分け、落ちたときに原因を絞れるようにする (回帰の回数を減らす代わり)。
  - 印の無い関数は他の言語からまだ呼べないだけなので、途中の段階でも定義が 2 か所になることは
    無い。

## 作るもの

### 1. アプリの殻 (本体の C)

- **アプリは本体がループを回す。** アプリは `on_create`・`on_update`・`on_event` などに当たる
  関数を公開するだけで、自分ではループを持たない (2026-11-14 ユーザ)。
- 殻が持つもの: Window とキャンバスの生成、枠の描画、枠のイベント (閉じるボタン・Window の
  メニュー)、user area の位置、メッセージ待ちと解析、タイマー、中断と再開、終了の印。
- アプリが公開する関数を、殻が用のあるときだけ呼ぶ。`on_update` が次に呼ばれるまでの ms を
  返す点は Ruby のアプリと同じ。
- **最初の利用者は Lua のアプリにする。** 今は枠を自分で描いているので、殻に乗せれば、wasm と
  切り離して sim で殻を確認できる。整理で入った自動起動と描画の原点の仕組みと、どうつながるかを
  最初に確かめる。MicroPython の prelude を殻に寄せるかは、その後に判断する。
- wasm のアプリを殻に乗せるのは、wasm_apps の W1b (本体への組み込み) の後。W1b の最初の試作は
  殻なしの枠なし・全画面で動かしてよい。
- アプリの一生とイベントの受け渡しは生成の外で、殻が受け持つ。

- **Lua のアプリの書き方 (2026-11-15 ユーザ、report/w3.md の 1.6)**: Ruby のアプリと同じ形にそろえる。
  大域の関数 `on_create`・`on_update` (次までの ms を返す)・`on_event(ev)`、任意で `on_destroy`・`on_suspend`・
  `on_resume`・`on_resize(w, h)`・`on_quit_request`。トップレベルは最初に 1 回だけ走る。`ev.type` は文字列
  (`"mouse_down"` など)、ほかの鍵は Ruby と同じ名前。今の書き方 (自分のループ・自分で Window を作る) は残さず、関数を
  1 つも定義しないスクリプトはエラーの Window にする。描き手は殻が作った大域の `gfx` (`create_canvas`・`FmrbGfx.new` は
  消す)、原点は区画の左上、`clear_user_area`・`user_area_width`/`height`・`stop` を足す、枠は描かずタイトルはアプリの名前、
  `FmrbApp.sleep` は残して `on_update` の返り値で待つよう勧める。`draw_text` の引数の順の違いは W4a の課題。
- **作り (W3 で決まった形、report/w3.md 2 章)**:
  - 殻は `main/app/fmrb_app_shell.c`、ヘッダは `components/fmrb_common/include/fmrb_app_shell.h`。殻はエンジンを
    知らず、エンジンは呼び出しの表 (`fmrb_shell_engine_t`: フックがあるか・フックを呼ぶ・`on_update`・`on_event`・
    `on_resize`・区画が変わった知らせ) を渡す。入口は `fmrb_app_shell_run`。Lua のつなぎは
    `components/lua/fmrb_lua_shell.c`。
  - 殻の状態はアプリの task のスタックに置き、PSRAM の ctx の `shell` から届く。静的な変数は無い。
  - 区画と原点の正は殻 (Ruby の `_layout_user_area` と同じ計算)。原点はエンジンの描き手が持って C で足す
    (Lua は `lua_gfx_data` の `ox, oy`)。イベントの `x`・`y` は殻が区画の座標にし、`wx`・`wy` は Window の座標。
  - 枠は Ruby の GfxBlock と同じ絵を 1 命令ずつ送る。描くのは作ったとき・`clear_user_area`・
    `draw_window_frame`・大きさが変わったとき。
  - 長く戻らない呼び出しの止め方: 殻は呼び出しの間で止まる印を読む。1 秒以上戻らない呼び出しだけ、
    エンジンの止めのフックが待ち行列から stop を拾って巻き戻す (`fmrb_app_shell_unwind_now`)。

- 回帰の道具に Ruby 以外 (Lua など) のアプリの画面の場面は、今は加えない (2026-11-15 ユーザ)。殻の枠と Ruby の枠の食い違いは、枠を変えるときに両方を直して目で確かめる。

### 2. 型定義から bindings を生成する

- **元は `sig/*.rbs` だけ。** 境界に載せるメソッドに印を付ける (書き方は未確定事項)。範囲は、
  Ruby で実装されたライブラリとアプリに公開しない機能を除く全部。今の平らな関数の表
  (`fmrb_spx_*`) のうち一般のアプリ向けの 55〜60 個が最初の目安 (内訳は
  doc/wasm_apps/report/w0.md 1.1)。
- 載せないもの: 状態を変えるシステムの関数 (`FmrbSystem` のもの: 再起動・電源・Wi-Fi の接続・
  BLE・音の設定など。決定 18)、Ruby で書かれたライブラリ、checkpoint と `move_to`、アプリの
  一生の内側 (`app_init`・`recv_message` など。殻と各エンジンの基底の内部で使うもので、今の
  手書きの宣言のまま残す)。
- **平らな関数の形は、型定義から決まった規則で導く。** 今の関数表の形に定義を合わせるのでは
  なく、規則が出した形に C の実装を合わせる。

  | Ruby 側の型 | 平らな関数での形 |
  |---|---|
  | レシーバ (`FmrbGfx` など) | 第 1 引数の番号。`FmrbApp` のインスタンスメソッドとモジュールの関数は、番号なし |
  | Integer・bool | 整数 |
  | String | ポインタと長さ |
  | Symbol の選択肢 (`:default` など) | 番号。選択肢は RBS のリテラルの型で書く |
  | 記録 (今は `Hash` と書いてあるもの) | 記録型として書き、固定の並びのバイト列を導く |
  | 要素の決まった配列 (四角の一覧など) | 要素の型を書き、ポインタと個数 |
  | 中身の決まらない値 (`send_message` の `data`) | バイト列 |
  | 本体からバイト列を返すもの (ファイルの読み込みなど) | アプリが用意したバッファのポインタと大きさ。本体が書き、長さを返す (決定 6) |

- **記録型の整数と小数の幅は、ROS 2 と同じ名前の型の別名で書く (決定 10)。** `int8`〜`int64`・
  `uint8`〜`uint64` (`= Integer`)、`float32`・`float64` (`= Float`)、バイト列は `bin` (`= String`)。
  幅を書かない `Integer` は int32、`Float` は float64 として扱い、範囲の外の値は詰めるときに
  エラー。別名の定義は `sig/` の中の 1 つのファイルにまとめ、道具は名前で見分ける。境界の固定の
  並びのバイト列・ROS 2 の形式・Asterism の型の宣言 (doc/rbs_types) で共通に使う。本体の mruby
  は、全部のビルドで整数が 64 ビットの符号つき、小数が 64 ビット (確認済み)。
- **Ruby らしい形のメソッドは、境界の関数と Ruby の包みに分ける。** 省略できる引数・
  キーワード引数を持つもの (`draw_text` など) は、単純な形の境界の関数を型定義に書き、今の
  名前のメソッドは Ruby の包みとして mrblib と Spinel の基底に書く。境界の関数も公開の API
  なので、`_` で始まる名前にはせず、エディタに出す。説明文には「引数を省略できない単純な形。
  速さが要る所で使う」ことと、対になる包みの名前を書く。名前の付け方 (包みとの見分け方) は
  未確定事項。他の言語には境界の関数を出す。
- **FmrbApp のメソッドは 3 種類に分けて扱う。** 今の型定義 (`sig/fmrb_app.rbs`) は 1 つの
  クラスに並べているので、生成の道具が見分けられるよう、印か置き場所で区別する (書き方は
  未確定事項)。Ruby のアプリから見た書き方 (`class MyApp < FmrbApp` に `on_*` を書く) は
  変えない。他の言語には、言語ごとに自然な形で出す (Python は継承、Rust は実装すべき関数の
  一覧と、頼みごとの関数の集まり)。

  | 種類 | 例 | 行き先 |
  |---|---|---|
  | アプリが書くフック | `on_create`・`on_update`・`on_event`・`on_resize`・`on_destroy`・`on_control` | アプリが公開する関数。型定義に書き、殻が呼ぶ |
  | 本体への頼みごと | `subscribe`・`publish`・`set_timer`・`request_fullscreen`・`set_hit_shape` | 境界の関数。レシーバは「今のアプリ」なので、番号の引数は付けない |
  | 枠と一生の内側 | `draw_window_frame`・`main_loop`・`start`・`stop` | 本体の C の殻と各エンジンの基底。境界に載せない |

- **平らな関数の表を 1 組にする。** Spinel 用の表 (`fmrb_spx_*`) を土台にし、MicroPython 用の表
  (`fmrb_mp_*`、`components/micropython/modules/fmrb_bridge.c`) をそこへ寄せる。
- 生成するもの:

  | 出力 | 中身 |
  |---|---|
  | 平らな関数のヘッダ | 整数とポインタだけの宣言 (本体のヘッダを読めない MicroPython のモジュールからも使える形) と、記録を詰める・読む関数 |
  | 本体に載せる型データベース | 型定義から印を落としたもの (エディタ用。今の `rake ti` の入力) |
  | wasm のつなぎ | raw の形の import 関数と登録の表 |
  | wasm の各言語の bindings | TinyGo・Rust・Zig。説明文は型定義のものを出す |
  | C のヘッダ | 境界の基準の資料 (決定 12)。W4a の最初から、ほかの出力と同じ品質で作る。関数ごとの説明文 (日本語と英語)、記録型の構造体、選択肢の定数、ABI の版の定数を含める。C でアプリを書く人への案内は wasm_apps の W5 で 3 言語の後 |
  | Lua のつなぎ | 引数を取り出して呼ぶ関数と登録の表 (今の `components/lua/extension/fmrb_lua_gfx.c` の置き換え) |
  | MicroPython のモジュール | 引数を取り出して呼ぶ関数・関数オブジェクト・登録の表 (今の `fmrb_module.c` の該当部分の置き換え) と、Python の側のクラス (prelude の `FmrbGfx` など) |
  | Spinel の宣言 | `ffi_func` の並び (今の `main/ruby/spinel/fmrb_app_ffi.rb` の該当部分) |
  | mruby の gem のつなぎ | 引数を取り出して平らな関数を呼ぶ部分 (今の gem の `gfx.c`・`app.c` の該当部分の置き換え) |

- **生成の道具は、呼び出しの届け先を差し替えられる作りにする (2026-11-14)。** 「RBS のクラスと
  メソッドの定義から、各言語の呼ぶ側と呼ばれる側のコードを作る」道具は 1 つで、届け先が本体の
  C の関数ならこの計画、Asterism の網なら別の端末のオブジェクトを他の言語から呼ぶ話
  (doc/rbs_types) になる。値の運び方 (固定の並びのバイト列か MessagePack か) も届け先ごとに
  差し替える。
- **生成の道具は Ruby のスクリプトで作り、`rake` のタスクとしてホスト (PC) で動かす。**
  今の型データベースの生成 (`rake ti:gen`) と同じ段 (docker の前) に置く。ESP-IDF のコンテナ
  には ruby が無いため。
  - 読み取りは `rbs` gem の解析器を使う (メソッドの形・説明文・注釈・記録型・リテラルの型を
    構文木で受け取る。文字列の一致で自作しない)。
  - 規則を当てた結果を、出力先によらない中間の表 (平らな関数の名前・引数・戻り値・記録型・
    説明文) にまとめる。出力先ごとの違いは型紙 (ERB) だけに置く。言語を足すときは型紙を
    1 つ足す。
  - タスクは、全部を生成するものと、出力先を 1 つだけ生成するものを用意する。
- **生成物の置き方 (2026-11-14 決定)**:
  - 本体の中のつなぎ (平らな関数のヘッダ、wasm・Lua・MicroPython・mruby のつなぎ、Spinel の
    宣言) は、**ビルドのたびに作り、リポジトリに入れない**。型定義より古い生成物を検出して
    作り直す仕組みを最初から入れる (型データベースと wasm のビルドにある「生成物を作り直さ
    ない」罠を増やさない)。
  - 各言語の SDK (TinyGo・Rust・Zig の bindings と C のヘッダ) は、**リポジトリに入れる**。
    アプリを書く人が PC で使う配り物で、差分をレビューで読めるようにするため。型定義と
    一致しているかは軽い回帰 (`rake regress`) で検査する。配り方は wasm_apps の W5。
- **ビルドの流れの注意 (決定 9 の下、ビルドの流れを読んだ結果)**: 生成した C は CMake の側
  (`ports/esp32/`、ファイル名は固定) に置く (libmruby の側は作り直しを検出しない)。本体の
  ソースの一覧は `hosted/hosted.cmake` にもある (ビルドの入口が複数)。生成は、Spinel の結合・
  `rake micropython:gen`・checkpoint の表の生成より前に 1 回。MicroPython は、生成したソースを
  置いてから `rake micropython:gen` を流す順になる。
- エラーの返し方は言語ごとに型紙で決める (Lua はエラーを投げて自分を返す、MicroPython は例外、
  wasm は負の数、など)。他の言語の使い勝手は Ruby より素朴でよい (境界の形がそのまま見える)。
- 今の rbs はエディタの型支援のために簡略にしてあり、実際の API とずれている所がある
  (`publish` のデータ、`draw_text` のキーワード引数、`on_event` の `Hash`、要素の型の無い
  配列)。境界に載せる過程で直す。イベントの記録型を 1 つ書くと、`Hash` と書かれた 6 つの
  メソッドが埋まり、エディタの補完にもイベントのキーが出る。
- **ABI に版を付ける**。型定義から生成するので、版は型定義の内容から決める。大きい番号と
  小さい番号の判定は生成の道具が前回のリリースの型定義と比べて行う (決定 14。アプリの側での
  使い方は wasm_apps の W5)。

## 受け入れ条件

- 生成の元になる定義は `sig/*.rbs` の 1 か所だけである。印の無い別の定義・別の形式のマスタが無い。
- Lua・MicroPython・mruby のつなぎと Spinel の宣言、wasm のつなぎと 3 言語 (TinyGo・Rust・Zig)
  の bindings、C のヘッダが、同じ定義から生成したものである (手書きの bindings が無い)。
- Ruby で実装されたライブラリとアプリに公開しない機能を除く API が、Lua のアプリから呼べる
  (wasm のアプリから呼べることは wasm_apps の受け入れ条件)。
- Lua のアプリが本体の C の殻の上で動き、枠を自分で描いていない。
- Ruby のアプリの書き方が変わっていない (今のアプリが直さずに動く)。包みを通した呼び出しの
  mruby の命令数が今より増えていない。
- 包みと境界の関数を混ぜて呼んでも、フォントや文字の大きさ・描画の原点がずれない。
- Ruby で書かれたライブラリと基底クラスが、包みを持つ関数について境界の関数を呼んでいる。
- 本体の中の生成物は、型定義を直すと次のビルドで作り直される。リポジトリに入れた SDK の生成物が
  型定義と一致しているかを `rake regress` が検査する。
- 境界の関数をひととおり呼ぶ C のアプリが、ABI の確認として回帰の道具に入っている。
- 内蔵 RAM が増えない (`rake regress:size`)。今の回帰の道具 (`rake regress`・`regress:run`・
  `regress:screens`) が通る。重い方は各段の終わりと最後の受け入れで確認する。

- BASIC は生成の対象に入れない (2026-11-15 ユーザ: BASIC は特別)。
