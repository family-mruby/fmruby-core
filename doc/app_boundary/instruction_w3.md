# W3 指示書: アプリの殻を本体の C に作り、Lua のアプリを乗せる

> 親: plan.md の作るもの 1 と段 W3。考え方の芯は plan.md の方針。整理で入った仕組みは doc/codebase_tidy の report/t3.md
> (自動起動)・t4.md (描画の原点)。時間の目安は doc/regression/usage.md 0 章。

## 目的

Ruby 以外のアプリ (まず Lua) が、Window・枠・枠のイベント・user area・メッセージ待ち・タイマー・中断と再開・終了の印を
自分で持たず、本体の C の「殻」に任せられるようにする。アプリは `on_create`・`on_update`・`on_event` に当たる関数を公開する
だけで、ループは殻が回す。

## やること

1. **調べて、作りを決めて書く** (report の最初の章。ここで止まる条件に当たれば返す):
   - 今の Lua のアプリの一生 (起動・ループ・枠を自分で描く所・イベント・終了) と、Ruby のアプリの一生 (FmrbApp の基底、
     T3 の自動起動、T4 の原点と `window_gfx`) の対応表。
   - 殻を C のどこに置くか (`main/app/` の今の構成と、エンジンごとのつなぎ)。Ruby の基底 (mruby・Spinel) が今持っている
     枠の描画・枠のイベント・user area の計算と、殻の C がどう並ぶか (今回は Ruby の側は変えない。重複は報告に一覧)。
   - 描画の原点: 殻が C の gfx の原点 (T4 の `mrb_gfx_data` の考え方) を Lua のアプリにも当てるか。Lua の描画の口が原点を
     足すようにする場所。
2. **殻を作る**: Window とキャンバスの生成、枠の描画、閉じるボタン・Window のメニュー、user area、メッセージ待ちと解析、
   タイマー (`on_update` の返り値の ms)、中断と再開、終了。checkpoint で運べるかは今回は対象外 (Lua のアプリは今も
   movable でない前提。違えば報告)。
3. **Lua のアプリを乗せる**: Lua の側は関数 (`on_create` など) を公開するだけにし、枠を自分で描くコードを消す。今ある Lua の
   アプリを全部入れ替える。**Lua のアプリの書き方が変わる所は、変える前に一覧にして止まって返す** (仕様の変更はユーザが決める)。
4. 文書: plan.md の作るもの 1 に決まった作りを書き、アプリの書き方の文書 (Lua) を直す。

## 確かめること (これだけ)

- `rake regress` (35 秒)。
- sim で Lua のアプリを起動し、枠・閉じるボタン・Window のメニュー・ドラッグ・タイマー・終了が Ruby のアプリと同じように
  動くこと (画面を撮る)。
- `rake regress:screens` を最後に 1 回 (Lua のアプリの場面があれば。無ければ足すかを report に)。
- `rake regress:size` を最後に 1 回 (内蔵 RAM の静的な増分 0)。`rake regress:run` は Ruby のアプリに触らないなら不要。
- 直しのやり直しでは、変えた所が影響する道具だけを流し直す。

## 触ってよい範囲

- fmruby-core (develop)。Ruby の基底 (mruby・Spinel の FmrbApp) と Ruby のアプリは変えない。MicroPython は今回は変えない。
  作業ツリーの既存の未コミット (components/ のサブモジュール 2 つ、wasm/vendor/) には触らない。
- コミットは件名 `<種類>(<場所>): <要約>`、英語、Co-Authored-By、pathspec を明示。push しない。基準の更新はしない。
- 終わったら Linux のビルド (x86-64)、sim を片付け、裏の処理を残さない。

## 止まる条件

- Lua のアプリの書き方が変わる (一覧にして返す)。仕様が変わる選択 (枠の見た目・操作が Ruby のアプリと違う形になる)。
- 内蔵 RAM の増分。VM プールや PSRAM の KB 単位の増分で理由が説明できないもの。ユーザの作業が要るとき。

W4a への注意。開始と終了の時刻は `date` で書く。
