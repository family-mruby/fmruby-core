# W4a 指示書 (前半): 関数 1 つで全部のビルドを通し、決めることの案を作る

> 親: plan.md の作るもの 2 と段 W4a、決定 9・10・12 (doc/wasm_apps/plan.md)。W3 の結果は report/w3.md。
> 時間の目安は doc/regression/usage.md 0 章。**この前半は案を作って止まる**。道具の作り込み (後半) はユーザが 3 点を決めてから。

## やること

1. **関数 1 つで通す** (決定 9): 代表の関数 1 つ (`fill_rect` など、包みを持たないもの) を `sig/*.rbs` に印を付け、そこから
   mruby・Spinel の宣言・Lua・MicroPython のつなぎと C のヘッダを生成し、今の手書きのつなぎをその 1 つだけ置き換えて、全部の
   ビルド (Linux・ブラウザ版・esp32 の S3 と P4、ネイティブ版) が通ることを確かめる。生成の道具は最小でよい (後半で作り込む)。
   wasm の側の出力は、W1a の試作 (`tools/wamr_poc/`) の本体役で、C で書いた最初のアプリから呼べることだけ確かめる。
   PicoRuby のビルドとの相性 (生成した C の置き場、ビルドの入口が複数、生成の順) を書く。
2. **決めることの案** (選択肢の形、推奨を先頭。それぞれ RBS として自然に読めるか、独自の記法を増やさないかで比べる):
   - 印の書き方 (RBS の注釈 `%a{...}` を型データベースを作る道具が受け付けるかを確かめてから)。
   - 境界の関数の名前の付け方 (包みと並んでエディタに出るので見分けがつき、他の言語でも自然な名前)。
   - フック・頼みごと・内側の 3 種類を型定義でどう区別するか (印か、ファイルや名前空間を分けるか)。
   - BASIC を生成の対象に入れるか。
   - 生成に切り替えると今の Lua・MicroPython のアプリの書き方が変わる所 (引数の順、省略できる引数、名前。`draw_text` の順の
     違いを含む) の一覧と、どちらに揃えるかの案。
3. report の 1 章に 1 の結果、2 章に 2 の案を書き、**ここで止まって返す**。

## 確かめること (これだけ)

- `rake regress`、関数 1 つを置き換えた後のビルド (Linux・ブラウザ版・esp32 2 台・ネイティブ版。`regress:size` で esp32 を
  兼ねてよい)、その関数を呼ぶ所が動くこと (描画の記録で足りれば記録で)。

## 触ってよい範囲

- fmruby-core (develop)。置き換えるのは選んだ関数 1 つのつなぎだけ。作業ツリーの既存の未コミット (components/ のサブモジュール
  2 つ、wasm/vendor/) には触らない。`~/toolchains/` は消さない。道具のキャッシュは `~/toolchains/cache` に向ける。
- コミットは件名 `<種類>(<場所>): <要約>`、英語、Co-Authored-By、pathspec を明示。push しない。
- 終わったら Linux のビルド (x86-64)、裏の処理を残さない。
