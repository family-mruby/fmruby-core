# 報告 P2b-2: 実機で確かめ、SPINEL_PIN を確定し、develop に入れる準備

> 状態: 完了 | 更新: 2026-09-26 | 実機は Tab5 ではなく **P4-Nano (NARYAv4 基板)**。Tab5 での確認は別の機会に回す。**SPINEL_PIN を fmrb-next `0b350247` に確定** (`b2126ae1`)。最初の新ファームは kernel のスタック溢れ (Guru) で起動しなかった。上流の小さな葉メソッドの強制インラインが原因で、全 Spinel プログラムの生成に `--no-inline-hot` を付けて直した (`6391833f`)。**直した後は Guru 0 件、待機時の内蔵 RAM 空きは基準 +6,812 バイト、/home は元どおり (17 本、ハッシュ一致)**。速度の退行 (エディタ `edit_lat` 1.6-1.9 倍、FFT 倍精度 +27%、raycaster +8-22%) は**ユーザ判断で許容**した (RAM 削減を優先)。原因の見立ては 13 節

## 変化点の要約 (先に読む)

1. **強制インラインで kernel が起動しなかった**。
   - 上流の codegen は、小さな葉メソッドを `always_inline` で出す。
   - kernel の `handle_app_control` がそれを 10 個以上吸収し、C フレームが 4,192 → 12,448 バイトになった。
   - 16 KB の kernel タスクスタックが起動直後に溢れた (Stack protection fault)。
   - sim では出ない (Linux の pthread スタックが大きいため)。CI もビルドまでなので見つからない。
2. **`--no-inline-hot` を 6 本全部に付けた**。
   - 対象は kernel / editor / desktop / fft / hello / raycast。付ける範囲とその根拠は 3 節。
   - `handle_app_control` は 4,048 バイトに戻った。
   - 実機の kernel スタックの最悪 Free は 6,488 (基準 6,952)。
3. **内蔵 RAM は予測どおり**。待機時の `IRAM free:` は 150,020 で、基準 143,208 より +6,812。
   P2c の静的な見込み (P4 で -6,812 の使用) とバイト単位で一致した。
4. **速度は退行した (許容した退行、13 節)**。
   - `edit_lat` の平均: 8,710 / 7,907 us → 13,556 / 14,887 us。
   - 描画の実測 `draw_mean`: 8,033 / 7,125 us → 12,882 / 13,869 us。
   - FFT (Spinel、倍精度): 9,153 → 11,598 us。
   - raycaster の cast: +10-17%。
   - GFX 側の `render` (描画タスク) は変わらない。Spinel で生成したコードそのものが遅くなっている。
   - 指示書の目安 (中央値 10% 悪化) を超えた。切り分けは sim の比較まで行い、ユーザ判断で許容して区切った (13 節)。

## 3. `--no-inline-hot` を付ける範囲と根拠

### 変更 (`6391833f`)

- `rakelib/spinel.rake`: `gen_flags = "--no-inline-hot"` を足し、6 本の生成行
  (kernel / editor / fft / hello / raycast / desktop) すべてに渡す。
- `main/prebuild_scripts/compile_ruby_to_spinel.cmake`: `SPINEL_BIN` がある時の CMake 側の
  再生成経路にも、同じく全プログラムに `--no-inline-hot` を渡す。
  `generate_ruby_spinel_command` の共通の COMMAND に入れたので、6 本の呼び出しはそのまま。
- 生成後の C で `always_inline` が 0 か所であることを確かめた
  (kernel / editor / fft / hello / raycast、ESP 向けの `rake spinel:gen`)。

### 関数ごとのフレームの比較

測り方は次のとおり。
- 対象: 3 つの ELF (基準 / 新 = 強制インライン / 修正 = `--no-inline-hot`)。
- 方法: 逆アセンブルの各関数の入口で下げる sp の量を足した。`addi sp` と `lui/li t0` + `add sp,sp,t0` を拾う。
- 所属: 生成 TU への所属は map の `.text.<関数>` から決めた。
- スクリプト: `$S/tuframes.rb` と `$S/tucompare.rb`。結果は `$S/tu_{base,new,fix}.tsv`。
- desktop は標準構成では mruby なので、ELF に入っていない。3 通りの生成 C を実機と同じフラグで
  1 本ずつコンパイルして測った (`$S/desk_{base,new,fix}.o`)。
  - 基準は develop のソースと旧コンパイラ (`$S/spinel_old` = `622750c`) を使った。

### 呼び出し経路の合計 (逆アセンブル、直接呼び出しのみ)

生成 TU の中の関数 (プログラムのメソッドと、TU に static で入るランタイムの補助) だけを辿った
最深経路 (`$S/callgraph_tu.rb`)。ランタイムのライブラリや libc への呼び出しは辿らない
(raise → sprintf → dtoa の報告経路で全部が同じ値になるのを避けるため)。再帰は 1 周で打ち切る。

| 起点 | 基準 | 新 | 修正 |
|---|---:|---:|---:|
| `fmrb_kernel_entry` | 8,656 | 21,536 | **10,416** |
| `handle_app_control` 以下 | 7,552 | 19,872 | **9,312** |
| `handle_hid_event` 以下 | 5,536 | 11,024 | 8,176 |
| `handle_audio_message` 以下 | 4,272 | 6,576 | 6,448 |
| `editor_entry` | 12,128 | 15,664 | **13,408** |
| `fmrb_fft_spinel_entry` | 2,016 | 1,264 | 1,264 |
| `spinel_hello_entry` | 96 | 112 | 112 |
| `raycast_entry` | 1,152 | 720 | 720 |

**「基準以下」は kernel と editor で満たしていない**。
- 修正後の kernel の最深経路は基準 +1,760 バイト、editor は +1,280 バイト。
- 残りの差は、`MessagePack_s_pack_value` (912 → 1,232) と `sp_poly_*` の比較経路
  (`poly_eql` → `poly_eq_deep` → `poly_hash_eq_cross`、上流で新しく深くなった)。
- 強制インラインの分 (約 11 KB) は全部消えた。
- この静的な最深経路は、実際には通らない例外の経路を含む過大な見積もりである。
- 実機の high-water は次節のとおり (kernel は基準より 464 バイト少ない空き、editor は 864 バイト多い空き)。
- ランタイム全体を含めた最深経路 (`$S/callgraph.rb`、raise → sprintf 込み):
  kernel 12,368 / 25,456 / 14,400、editor 21,568 / 21,520 / 20,640。

## 4. T1 / T2: 基準と修正後の比較 (P4-Nano (NARYAv4))

### 13.2 FFT の原因 (生成 C の比較で特定)

- 基準と新で、`FftCore#forward` の生成 C を比べた (`$S/fftcmp/fwd_{base,new}.c`)。
- 違いは、浮動小数の四則演算ごとに入る `SP_FLOAT_NIL_CK` の 9 か所だけだった。
  配列の読み書き・整数演算の数は同じ。
  - 例: `tr = rb * wr - ib * wi` が、各掛け算の前に両辺の nil 番兵 (特定の NaN のビット列) を比べる形になる。
- `FloatArray` から読んだ値は「隙間 (nil) でありうる」と解析されるので、検査が入る。
- `--int-overflow=wrap` は整数の検査を外すだけで、この浮動小数の検査は外さない。
  **FFT の退行には wrap は効かない**。
- 整数の FFT (spinel_q15) が変わらないのと合う。
  整数の nil 検査 (`SP_INT_NIL_CK`) は、この経路の整数演算 (添字の加算) には入っていなかった。

### 13.3 整数の nil 検査と `--int-overflow` (見立てとして記録のみ)

- **基準 (旧フォーク) の意味**:
  - 整数の `+ - *` は `--int-overflow` の既定 `raise` (桁あふれで RangeError)。
  - 両辺の nil 番兵の検査は無い。nil の整数枠は `INTPTR_MIN` のまま計算に入っていた。
  - fmrb のビルドはどちらも `-DSP_INT_OVERFLOW_MODE_*` を渡しておらず、`#else` の raise 側を通る。
- **新 (上流) の意味**: 桁あふれの raise に加えて、`+ - *` ごとに両辺の nil 検査 (`SP_INT_NIL_CK`) が入る。
- **wrap の意味**: 桁あふれの検査も nil 検査も外れる。
  - 基準と違い、桁あふれしても raise せずに黙って折り返す。
  - 32bit の実機では ±2^31 で折り返す。`Machine.board_millis` のような時刻の積算、FNV などのハッシュ計算、
    大きな整数を掛ける箇所で意味が変わりうる。
  - 使う箇所は洗い出していない。**今回は採らない**。
- **基準と同じ意味になる設定**は「raise のまま、`SP_INT_NIL_CK` だけ空にする」になる。
  ただしスナップショットのヘッダを直す必要があり (フォーク側の口が要る)、試していない。
- sim ではエディタが遅くならなかったので、エディタの退行の主因は整数の nil 検査ではない見込み
  (検査の命令数は x86 でも同じだけ増える)。

### 13.4 実機で 1 つだけ試したこと

- P2c で PSRAM に移した nil 番兵の枠 (`SP_TU_NIL_SLOT`) を内蔵 RAM に戻したビルド (実験 A) を、
  P4-Nano に app 区画だけ書いて測った。
  - スナップショットの `spinel_rt.h` を一時的に書き換えて作り、測った後に戻した。コミットしていない。
- 結果 (`$S/dev_expA.log`):
  - `edit_lat` 平均は 13,404 / 13,717 / 14,737 us。
  - 同じ手順の修正後 (`$S/dev_fix_ref.log`) は 14,781 / 16,158 / 13,308 us。揺れの中で差が無い。
  - 待機時の内蔵 RAM は 5.5 KB 減った (150,020 → 144,508)。
- **PSRAM に置いた nil 番兵の枠は、エディタの退行の原因ではない**。
- `SP_RT_COLD` を空にするビルドは試していない。中身は診断用の数え上げで、通常は触られない。

### 13.5 エディタの退行の見立て (未確定)

sim に出ず、nil 番兵の枠の置き場所でもない。残る実機だけの要因の候補:

1. **コードの大きさと命令キャッシュ**。
   - 生成コードは kernel +147 KB、editor +87 KB、ランタイム +132 KB (P2b-1 の P4 の size-files)。

2. **凍結リテラルと 1 文字文字列の表が flash (.rodata) に移ったこと** (P2c)。

3. 32bit の RV32 だけで重くなる上流のランタイムの経路 (64bit の整数やハッシュの演算)。
   - 文字列のハッシュ関数は基準と同じ (FNV-1a 64bit) なので、それ以外。

次に確かめるなら、同じファームで 2 を戻したビルド
(凍結リテラルを `.data` に戻す。内蔵 RAM が約 30 KB 増える) と、

### 13.6 kernel スタックの最悪 Free が 464 バイト減った件 (記録)

- 差の内訳 (3 節):

  - 上流で新しく通る比較の経路 `poly_eql` → `poly_eq_slow` → `poly_eq_deep` → `poly_hash_eq_cross`

  - `handle_app_control` の前段が `main_loop` / `dispatch_message` の形になったことによる入口の差。
- 実機の high-water は 6,952 → 6,488 (-464)。16 KB のスタックに対して 6.5 KB の余裕がある。
