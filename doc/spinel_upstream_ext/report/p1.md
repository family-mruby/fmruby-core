## T1: raycast を型付きエントリで書く

`tool/spinel_ext_poc/raycast_kernel.rb` (52 行、コード 19 行)。

```ruby
require_relative "../../lib/add/picoruby-fmrb-raycast/mrblib/raycast_core"
module RaycastKernel
  def self.load_map(map, w, h)
    if w < 1 || h < 1 || map.bytesize < w * h
      raise ArgumentError, "bad map w=#{w} h=#{h} bytes=#{map.bytesize}"
    end
    @core = RaycastCore.new(map, w, h, 0)
    w * h
  end
  def self.cast(px, py, pa)
    core = @core
    raise RuntimeError, "load_map has not been called" if core.nil?
    core.cast_packed(px, py, pa)
  end
end
if __FILE__ == $0 ... end   # 型推論用
```

生成されたヘッダ (`spinel raycast_kernel.rb -c --ext-init Init_raycast
--ext-entry RaycastKernel.load_map,RaycastKernel.cast`):

```c
void Init_raycast(void);
int Init_raycast_try(void (*fn)(void *), void *ctx, const char **cls, const char **msg);
sp_int sp_RaycastKernel_s_load_map(const char * lv_map, sp_int lv_w, sp_int lv_h);
const char * sp_RaycastKernel_s_cast(sp_int lv_px, sp_int lv_py, sp_int lv_pa);
```

- **状態の持ち方**: 大域変数ではなくモジュールのインスタンス変数 `@core` に
  した。生成 C では TU の `static sp_RaycastCore *civ_RaycastKernel_core` に
  なり、GC のルートとして印が付く。トップレベルは init で 1 回しか走らない
  ので、エントリ呼び出しの間で自然に残る。`--persistent-statics` も世代番号も
  要らない。map の差し替えは `load_map` をもう一度呼ぶだけ。
- raycast_core.rb は gem の mrblib を相対パスで読み、**1 文字も変えていない**。
  生成 C と 32bit の生成 C は同一 (`--cc='cc -m32'` を付けても出力は変わらない)。
- **文字列リテラルの凍結**: raycast_core.rb が書き換える文字列は `@out =
  "\x00" * (NUM_RAYS * RAY_BYTES)` の 1 つで、これは `String#*` が返す新しい
  文字列なので凍結されない。`setbyte` は通った (FrozenError なし)。他に
  リテラルを書き換える箇所は無い。fft の 2 コアも同じ形 (`"\x00" * (half * 2)`)。
  止まる条件には当たらない。
- **型推論**: 引数は `if __FILE__ == $0` の呼び出しから `String` / `Integer` に
  決まり、PolyArray や `sp_RbVal` に落ちたものは無い。`--warn-widen` の指摘は
  fft の 2 コアの `initialize` の戻り値 (使われない) だけ。plan.md の未確定事項の
  「PolyArray に落ちた場合の性能」は raycast / fft では起きない。
- **spinel-doctor が ext カーネルを必ず ERR にする** (PR 候補 N-9)。
  `spinel-doctor raycast_kernel.rb` は `behavior: compiled output differs from
  CRuby` を出す。原因は型推論用ブロックで、CRuby では `__FILE__ == $0` が真で
  中身が走るが、コンパイルした実行ファイルでは `$0` が実行ファイルのパスなので
  偽になり、何も出力しない。上流の文書 (docs/spin.md) が勧める形そのもので
  起きる。P3 で gem のカーネルを `rake spinel:doctor` にかけるなら許可表が要る。

## T2: 試験用ホストで答え合わせ

`raycast_host.c` がケースファイルを読み、`Init_raycast()` の後に
`load_map` / `cast` を `Init_raycast_try` で包んで呼び、光線の出力を 1 本の
バイナリに連結して書く。CRuby は同じケースを `raycast_kernel.rb` (つまり同じ
raycast_core.rb) で動かし、同じ形式で書く。両者を `==` で比べる。

| 項目 | 内容 |
|---|---|
| map | ゲームの地図 (`flash/app/game/raycaster.app.rb` の `WORLD_MAP` 32x32 を実行時に読む) と手書きの 7x5 (正方形でない、縁が空き、壁の値 1-4) |
| 固定姿勢 (map ごと 469) | 1 地点から全方位 360 度 / 壁に正対・斜め 8 方向 x 3 地点 / セルの角と辺ちょうど 4 地点 x 10 角度 / マップ端と外 (負の座標、w*256+50 等) 10 地点 x 5 角度 / 0..359 の外の角度 8 個 (-719, 1080 等) |
| 乱数姿勢 | ゲームの地図 1,200 + 200、手書き 300 + 20。座標は map の外 1 セルまで、角度は -720..720 (seed 20260926) |
| map 差し替え | ゲーム → 手書き → (不正 2 件) → ゲーム。`load_map` 5 回 |
| raise | 読み込み前の `cast` (RuntimeError)、不正な map 2 件 (ArgumentError)。不正な map の後も前のコアで cast が続くこと |
| 合計 | 2,685 回の cast (成功 2,684)、出力 644,160 バイト |

結果 (x86_64 / i386 とも、3 通りの環境で):

| 環境 | x86_64 | i386 |
|---|---|---|
| そのまま | 一致 | 一致 |
| `SPINEL_GC_STRESS=1` (2KB ごとに回収。6-7 回の回収が map 差し替えをまたいで走ったことを `SPINEL_GC_STATS` で確認) | 一致 | 一致 |
| `SPINEL_GC_SLAB=0` (slab アロケータ無し。機器への移植で要る形) | 一致 | 一致 |

- 3 件の raise は、クラス名とメッセージまで CRuby と同じ文字列で届いた
  (`RuntimeError: load_map has not been called`、
  `ArgumentError: bad map w=4 h=4 bytes=3`、`ArgumentError: bad map w=0 h=3 bytes=3`)。
- 不一致は 0 件。

ホストを書いて分かった約束事 (README にも書いた):

- `const char *` の String 引数は **ランタイムの文字列** でなければならない。
  長さを前置ヘッダから読む (`sp_str_byte_len` が `s[-1]` の印を見る) ので、
  素の C バッファを渡すと壊れる。`sp_str_from_bytes(buf, len)` で作れば NUL を
  含むバイト列もそのまま渡せる。ヘッダには書かれていない契約。
- **try で包まずに raise するとプロセスが終了する** (`load_map has not been
  called (RuntimeError)` を出して終了コード 1)。機器ではファームごと落ちる。
  包むコストは計測で見えない程度 (下の時間の表)。
- 戻りの String はコアの持つ `@out` そのもので、次の `cast` で上書きされる。
  ホストはすぐ写す (今の `raycast_spx_output` の memcpy と同じ扱い)。

### 生成 C の大きさ

`size -A`、`-O2 -ffunction-sections -fdata-sections`。各列は同じ系統の節の
合計。`.data.rel.ro` はホストの位置独立コードで出る節で、機器の非 PIC ビルド
では `.rodata` 側に入るので分けて載せた。フォークは `vendor/spinel/bin/spinel`
で生成した今の `raycast_entry.c` (`--persistent-statics` 付き) をフォークの
ヘッダでコンパイルしたもの。

raycast:

|---|---|---|---|---|---|
| ext x86_64 | 39,354 | **180** | 5,153 | 656 | 100,705 |
| ext i386 | 41,193 | **124** | 5,156 | 328 | 59,397 |
| フォーク x86_64 | 27,159 | 20 | 3,704 | 752 | 98,633 |
| フォーク i386 | 28,602 | 12 | 3,668 | 376 | 57,333 |

fft (T4、ext は `fft_kernel.rb`、フォークは今の `fft_spinel.rb`):

| 対象 | .text | .data | .rodata | .data.rel.ro | .bss |
|---|---|---|---|---|---|
| ext x86_64 | 52,360 | 164 | 5,632 | 656 | 100,769 |
| ext i386 | 54,843 | 120 | 5,625 | 328 | 59,429 |
| フォーク x86_64 | 38,461 | 28 | 3,937 | 720 | 98,633 |
| フォーク i386 | 39,324 | 16 | 3,893 | 360 | 57,333 |

- `.data` の増分 (raycast、i386 で +112 バイト) の中身は、凍結リテラルの
  静的オブジェクト 2 個 (`"\x00"` と raise のメッセージ、x86_64 で 32 + 56 バイト)
  と、**Integer 定数 7 個が `SP_INT_NIL` で初期化されて `.bss` から `.data` に
  移った分** (1 個 1 語)。gem では小さい。後者は P0 で見ていなかった要因で、
  P0 の生成物で数えると kernel 128 個、editor 251 個、desktop 329 個
  (32bit で 0.5-1.3KB)。凍結リテラル (editor で 490 個、24.6KB) に比べれば小さい。
- `.bss` はほぼ全部が TU ごとの例外スタック等 (`SP_TU_BSS` が PSRAM へ逃がして
  いるもの)。ext でも変わらない。
- `.text` は ext で約 1.4 倍。整数演算ごとの検査 (下) は 1KB 程度しか
  寄与しておらず、残りは上流の生成コードの一般的な増加 (P0 の -O1 の表とも同じ傾向)。

### 速度の目安

同じ姿勢で `cast` を 1,000 回、20 巡の最小値。**ホストでの相対比較で、実機の
値ではない**。このホストは計測中ずっと負荷平均 20-27 (24 CPU) で、絶対値は
回によって 2 倍ほど揺れた。順位は毎回同じ。姿勢 1 は長い廊下 (光線が
MAX_STEPS まで走る)、姿勢 2 はスタートの部屋で 45 度。

| エンジン | 姿勢 1 (ns/回) | 姿勢 2 (ns/回) |
|---|---|---|
| CRuby 3.2 (参考) | 92,967 | 118,819 |
| ext x86_64 | 4,038 | 4,847 |
| ext i386 | 4,766 | 5,083 |
| ext x86_64、毎回 try で包む | 4,257 | 4,468 |
| ext i386、毎回 try で包む | 5,086 | 5,603 |
| フォーク x86_64 (今の gem、FFI 込み) | 3,538 | 3,669 |
| フォーク i386 | 4,107 | 4,462 |

- try の有無は揺れの中に埋もれる (setjmp 1 回)。毎フレーム包んでよい。
- **ext はフォークより 15-45% 遅い** (FFI の往復が無くなったのに)。原因を
  切り分けた (`$S/exp/`、同じ生成 C のヘッダ側の定義だけを変えて同じ CPU で
  交互に 5 回):

  | 変種 | 姿勢 1 | 姿勢 2 |
  |---|---|---|
  | 既定 (`SP_INT_OVERFLOW_MODE_RAISE`) | 4,164-4,552 | 4,288-4,929 |
  | nil 検査だけ外す (`SP_INT_NIL_CK` を空に) | 2,217-3,663 | 2,413-4,210 |
  | `SP_INT_OVERFLOW_MODE_WRAP` (桁あふれ検査も外す) | 2,086-3,470 | 2,406-3,704 |
  | フォーク | 2,000-3,475 | 2,183-3,846 |

  上流は `9fa647ef` (2026-07-29) から、既定のモードで `+ - *` のたびに両辺が
  nil の番兵 (`SP_INT_NIL`) でないかを検査する。解析で素の Integer と分かって
  いる局所変数どうしでも入る。フォークにはこの検査が無く、桁あふれ検査だけ
  ある。**差の大半はこれ**。`--int-overflow=wrap` にすればフォーク並みに
  なるが、桁あふれで raise しなくなるので意味が変わる。P3 で gem だけ wrap に
  するかは決めていない (下の提案)。

## T4: fft

`fft_kernel.rb` に `FftKernel.run(samples, n, iters)` (double のコア)、
`run_q15(samples, n, iters)` (Q15 のコア)、`level_db(i, floor_db)` を置いた。
2 つのコアは今の gem と同じく別のモジュール変数 (`@core` / `@q15`) に持ち、
大きさが変わったときだけ作り直す。`level_db` は Float を引数と戻り値の両方で
越えさせるためのエントリで、今の gem には無い。

境界の型 (生成ヘッダ):

```c
const char * sp_FftKernel_s_run(const char * lv_samples, sp_int lv_n, sp_int lv_iters);
const char * sp_FftKernel_s_run_q15(const char * lv_samples, sp_int lv_n, sp_int lv_iters);
sp_float sp_FftKernel_s_level_db(sp_int lv_i, sp_float lv_floor_db);
```

`sp_float` は `double` の typedef (`lib/sp_types.h`、32bit でも double)。
`sp_int` は `intptr_t` なので、32bit ではエントリの整数引数も 32bit になる。

ケース: n = 64-1024 の 5 通り x 7 信号 (無音、直流、インパルス、最大振幅の
矩形、正弦、2 音、最大振幅の雑音) に加えて乱数 200 件 (大きさも乱数で変わり、
コアの作り直しが起きる)、`iters` 3 の反復、不正な要求 5 件 (raise)。
run 238 回、q15 238 回、level_db 413 回。

許容誤差: 振幅 (int16 のバイト列) は両コアともバイト一致を要求。`level_db`
は `|ext - CRuby| <= 1e-9 dB`。

| | 振幅のバイト列 | level_db (411 件) | raise 6 件 |
|---|---|---|---|
| x86_64 | 一致 | 411 件がビットまで一致 | 一致 |
| i386 | 一致 | 392 件がビット一致、19 件が最大 7.1e-15 dB の差 | 一致 |

- i386 の差は `Math.log10` を 32bit の libm で計算した末尾の違い
  (CRuby は 64bit の libm)。double のコア自体 (掛け算・加算・`Math.sqrt`) は
  `-msse2 -mfpmath=sse -ffp-contract=off` のおかげで 32bit でもビット一致した。
- Q15 は 32bit の整数で桁あふれせず (raise 無し)、CRuby の多倍長と同じ値。

## P3 で gem を移すときの形 (提案)

### ファイル構成

```
lib/add/picoruby-fmrb-raycast/
  mrblib/raycast_core.rb        変えない (mruby の :ruby と共用)
  mrblib/raycast.rb             変えない (Fmrb::Raycast。RaycastNative を呼ぶ)
  spinel/raycast_kernel.rb      新: raycast_entry.rb と raycast_ffi.rb を置き換える
  native/raycast_native.c       受け手。FFI 面を消し、生成ヘッダの型付き関数を呼ぶ
  native/raycast_native.h       公開 API はそのまま (begin / set_map / run / end)
```

`raycast_kernel.rb` は `require_relative "raycast_core"` にし、今と同じく rake が
mrblib からコピーして並べる (試作は相対パスで直接読んだが、生成物の `#line`
に絶対パスが入るので、本番はコピーする今の方式のほうが良い。`--no-line-map`
でも消せる)。fft / spinel_hello も同じ形。

### 受け手の C

```c
#include "raycast_kernel.h"   /* 生成ヘッダ。ext 1 本につき .c 1 つ (固定 include guard) */

int raycast_begin(void) {
    ... fmrb_spinel_instance_begin(...);
    Init_raycast();            /* インスタンスを作るたびに呼ぶ */
}
int raycast_set_map(const uint8_t *cells, int w, int h) {
    load_ctx c = { sp_str_from_bytes((const char *)cells, w * h), w, h };
    if (Init_raycast_try(do_load, &c, &cls, &msg)) { FMRB_LOGE(TAG, "%s: %s", cls, msg); return -1; }
}
const char *raycast_run(int px, int py, int pa, int *out_len, uint32_t *out_us) {
    uint32_t t0 = raycast_micros();
    if (Init_raycast_try(do_cast, &c, &cls, &msg)) { ...; return NULL; }
    *out_us = raycast_micros() - t0;
    *out_len = (int)sp_str_byte_len(c.buf);
    memcpy(s_out, c.buf, *out_len);   /* 次の cast で上書きされる */
}
```

- **すべてのエントリ呼び出しを try で包む**。包まない raise は `exit(1)` に
  なり、機器ではファームが落ちる。コストは見えない程度。
- 文字列はインスタンスの中で `sp_str_from_bytes` で作る (その文字列は
  インスタンスの pool に載る)。
- `sp_net_bin_len` の定義 (`main/kernel/fmrb_spx_common.c`) は gem からは
  要らなくなる (VM 型の `:binstr` が使う限り残る)。

### P3 で解くべきこと (P1 で見つかった論点)

1. **init はモジュールの状態を戻さない**。`Init_raycast()` を 2 回呼んでも
   `civ_RaycastKernel_core` はそのまま残り、2 回目の後も `cast` が前のコアで
   動いた (`$S/exp/reinit.c`)。上流は「ヒープは 1 つで壊さない」前提なので
   それで正しい。しかし fmrb はインスタンス (pool) を作り直すので、
   **pool を捨てた後の再 init で `@core` が解放済みの領域を指す**。フォークの
   `c7de66c` (`sp_reset_tu_statics`) を ext の init にも効かせる必要がある。
   モジュール変数・クラス変数・大域変数の static がすべて対象。
2. **ext TU の多重リンク** (P0 の F-2、40 シンボル) と固定 include guard
   (N-7) は P1 では避けた (1 本ずつリンク)。gem 3 本を同居させる P3 の本題。
3. **速度**: 既定モードの nil 検査で 15-45% 遅くなる。gem は「エンジンの差を
   見せる」デモなので、フォーク比で遅くなるのは見せ方に響く。選択肢は
   (a) gem だけ `--int-overflow=wrap` で生成する (桁あふれの raise を諦める。
   raycast / fft は値域を文書で押さえてあるので実害は小さい)、
   (b) 上流に「型が確定した Integer どうしでは nil 検査を省く」を提案する
   (PR 候補 N-10)、(c) そのまま受け入れる。まず機器で測ってから決めるのが
   よい (ホストの 15-45% が RV32 / Xtensa で同じとは限らない)。
4. **doctor**: ext カーネルは必ず behavior の ERR が出る (N-9)。
   `rake spinel:doctor` に gem カーネルを入れるなら許可表に足す。
5. slab: `SPINEL_GC_SLAB=0` でも一致したので、機器で slab を切っても gem の
   動きは変わらない見込み。切る口 (コンパイル時の切替) は P2 の仕事。

### rake の生成手順

```ruby
# rakelib/spinel.rake (と main/CMakeLists.txt の generate_ruby_spinel_command)
{
  "lib/add/picoruby-fmrb-raycast/spinel/raycast_kernel.rb" => "raycast_kernel.rb",
  "lib/add/picoruby-fmrb-raycast/mrblib/raycast_core.rb"   => "raycast_core.rb",
}.each { |src, dst| cp src, "#{SPINEL_SRC_DIR}/#{dst}" }
sh "#{bin} #{SPINEL_SRC_DIR}/raycast_kernel.rb -c --no-line-map " \
   "--ext-init Init_raycast --ext-entry RaycastKernel.load_map,RaycastKernel.cast " \
   "-o #{SPINEL_GEN_DIR}/raycast_kernel.c"      # raycast_kernel.h も同じ場所に出る
```

- 出力が .c と .h の 2 つになる。CMake 側の生成規則の OUTPUT に .h を足し、
  受け手の include path に生成ディレクトリを足す。
- エントリの一覧は rake と CMake で 2 重に持つことになる。今の
  `--persistent-statics` の一致と同じ種類の注意なので、1 か所 (例えば
  カーネルの .rb 冒頭のコメント行や gem の小さな設定) から両方が読む形に
  すると事故が減る。

## 見立てと違った点・撤回した仮説

- **「ext にすれば FFI の往復が消えるので速くなる」を撤回**。FFI の往復は
  1 フレームに 10 本程度で、光線 40 本の計算に比べて小さかった。逆に上流の
  既定の整数検査で 15-45% 遅くなった。速さは移行の動機にならない
  (動機は境界の簡潔さ)。
- 「状態は大域変数 `$raycast` に置く」(plan.md の例) より、モジュールの
  インスタンス変数のほうが自然だった。生成 C でも TU の static 1 個で、大域
  変数と同じ扱い (GC のルート) になる。
- 「`.data` の増加は凍結リテラル」(P0) に、Integer 定数の初期値 `SP_INT_NIL`
  という 2 つ目の要因があった (gem では数十バイト、editor で約 1KB)。
- 「String 引数は `const char *` なので C の文字列を渡せる」は誤り。
  ランタイムの文字列でないと長さが読めない (ヘッダには書かれていない契約)。
- 最初の実装で、フォークの出力の抜き取り検査が「不一致」になった。原因は
  CRuby 側の文字列の符号化 (UTF-8 と ASCII-8BIT の `==`) で、バイトは同じだった。
  比較は `.b` に揃えた。
