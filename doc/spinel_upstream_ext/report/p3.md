# 報告 P3: gem と VM を上流の ext 機構に移す

> 状態: 完了 | 更新: 2026-09-26 | gem 3 本 (fft / raycast / spinel_hello) と VM 3 本 (kernel / editor / desktop) をすべて `--ext-init` で生成するようにした。**fmrb は `--no-main` / `--entry` / `--persistent-statics` と gem の FFI 迂回を使っていない**。静的な D/IRAM は S3 147,387 / TAB5 183,448 で P2c と同値、P4-Nano の待機時の内蔵 RAM 空きは 150,068-150,088 (P2b-2 は 150,020)、各タスクのスタックの最悪 Free は P2b-2 と同じか多い。Guru 0。フォークは `fmrb-ext` に 2 本、fmruby-core は `feature/spinel-ext` に 2 本 (どちらも push していない)。**SPINEL_PIN はまだ `fmrb-next` を指す**ので、push するまでビルドには `SPINEL_DIR` が要る

## 変化点の要約 (先に読む)

1. **ext の変換結果を複数リンクできる形は、codegen の設計変更なしで作れた**。`SP_MULTI_CTX` の下では、上流の ext 出力が外に出すもののうち、
   多重インスタンスの経路 (`e0fd181` = `985103ba`) に乗っていなかったのは 4 個のフック
   (`sp_sym_to_s` `sp_sym_intern_n` `sp_sym_intern` `sp_class_to_s`) だけだった。P0 の「40 個」の残り 36 個は
   `SP_TU_STATIC` と sp_ctx への移設で既に TU 内に閉じていた。4 個は `SP_EXT_HOOK` という連結指定で出し、MC では `static` にした。
2. **ext の init での状態の戻しは、既に効いていた**。ext の init も `--no-main` の入口と同じ `emit_tu_ctx_init`
   (`sp_tu_ctx_init` + `sp_reset_tu_statics`) で始まる。P1 の「init を再度呼んでもモジュールの状態は戻らない」は
   MC でない構成の話で、MC ではインスタンスを作り直すと `@core` は nil、整数の `@calls` も nil から始まる
   (`SP_TU_NIL_SLOT`)。試験 `test/multi_ctx/ext3.sh` で確かめた。
3. **gem を ext にすると S3 の内蔵 RAM が 16 バイト増えた**。原因は ext の `_try` が読む `sp_last_exc_cls` と、init が書く
   `sp_program_name` ($0) で、どちらも初期値つきの static なので .data に残った (1 本 8 バイト)。フォークで
   `_try` がフレームの `sp_exc_cls` の枠から読むようにし、$0 を MC では `SP_TU_BSS` に置いて、P2c と同値に戻した。
4. **VM の入口の整理でスタックが 16 バイト減った (直した)**。3 つの VM のタスク本体を 1 関数
   (`fmrb_app_run_spinel_vm`) にまとめたところ、ログの引数でフレームが 32 → 48 バイトになり、kernel と
   editor の最悪 Free が 16 バイトずつ減った。ログを別関数に出して 32 バイトに戻し、実機で P2b-2 と同値を確かめた。
5. 速度は P2b-2 と同等か良い (エディタ 11.6-12.5 ms、FFT 倍精度 9,580 us、raycaster 313-318 us)。ext 移行で遅くなった所は無い。

## 2. P3a: フォーク側の土台

### 2.1 多重リンク (P3a-1)

MC で ext の TU を 2 本コンパイルし、外に出る記号を数えた (`$S/exp1/`)。

| | 外に出る記号 |
|---|---|
| 変更前 (MC) | `Init_ka` `Init_ka_try` `sp_KA_s_greet` + **`sp_class_to_s` `sp_sym_intern` `sp_sym_intern_n` `sp_sym_to_s`** |
| 変更後 (MC) | `Init_ka` `Init_ka_try` `sp_KA_s_greet` のみ |

- ランタイムは MC ではこの 4 個を sp_ctx の vtable (`sp_sym_name_fn` など、`sp_tu_init` が入れる) 経由で呼ぶので、
  TU の外に出す理由はホスト TU からの名前解決だけだった。
- codegen は 4 個の定義に `SP_EXT_HOOK` を付ける。`spinel_rt.h` は上流の構成 (MC でない ext) で空、MC で `static` に展開する。
  上流の構成の前処理後の C は変わらない。プロトタイプの宣言も同じ条件 (`SP_EXT_HOOKS_EXTERN`) で切り替えた。
- ホスト TU (生成ヘッダを include する側) は、MC ではプログラム TU と同じ見え方になる。`sp_str_from_bytes` などの
  インライン関数は使えるが、ホストから raise はできない (呼べばリンクで分かる)。entry は `_try` で包む前提。

### 2.2 init での状態の戻し (P3a-2)

変更は要らなかった。ext の init (`codegen.c` の `g_ext_init_name` の腕) は他の入口と同じく `emit_tu_ctx_init` を最初に出し、
MC では `sp_tu_ctx_init()` と `sp_reset_tu_statics()` を呼ぶ。`SP_TU_NIL_SLOT` の番兵の書き込みもこの中にある。
`$S/exp1/host2.c` でインスタンスを壊して作り直すと、呼び出し回数を数える `@count` が 1 から数え直された。

### 2.3 include guard (P3a-3)

`SPINEL_EXT_H` 固定を、init 名から作る `SPINEL_EXT_INIT_RAYCAST_H` などにした。1 つのホスト TU で 3 本のヘッダを include できる (ext3 の試験)。

### 2.4 試験とゲート (P3a-4)

`test/multi_ctx/ext3.sh` を足し、`make test-multi-ctx` から呼ぶ。

- 題材は自前の 3 本 (文字列と String キーの Hash と raise / 整数配列と Float とキャッシュした物 / ユーザクラスとシンボル)。
  シンボルとクラスの表をわざと違えてあり、別のプログラムのフックを呼ぶと違う名前が出る。
- 検査: nm (init・try・entry 以外を出さない)、1 スレッドで順に動かして CRuby と一致、3 スレッドで同時に動かして一致
  (`SPINEL_GC_STRESS=1` でも)、インスタンスの作り直しで状態が初期値に戻る。
- 最初は `Hash#inspect` の書式 (Ruby 3.4 と 3.2 の違い) で CRuby と食い違ったので、表示を手で組む形にした。

## 3. P3b: gem 3 本

### 3.1 形

| gem | kernel (`spinel/<name>_kernel.rb`) の entry | 受け手 (`native/`) がすること |
|---|---|---|
| spinel_hello | `SpinelHelloKernel.greet(name)` → String | 名前を `sp_str_from_bytes` で作って渡し、戻りを 64 バイトまで写す |
| raycast | `RaycastKernel.load_map(map, w, h)`、`cast(px, py, pa)` → String | `set_map` で map を渡し、`run` は cast の前後で時間を測って戻りの buffer をそのまま返す (次の cast か end まで有効) |
| fft | `FftKernel.load(samples, n)`、`run(iters)`、`magnitudes` と `_q15` の 3 つ | load → 計時した run → magnitudes の 3 呼び出し。変換だけを測る範囲は今までと同じ |

- 状態はモジュールのインスタンス変数 (`@core` / `@q15`)。`--persistent-statics`、世代番号、「キャッシュのキーはオブジェクト自身」の規約はすべて消えた。
- init と entry は **すべて `Init_<name>_try` で包む**。raise はクラス名とメッセージをログに出して、失敗値を返す。
- init 名と entry は kernel の先頭の 2 行 (`# spinel-ext-init:` / `# spinel-ext-entry:`) に書き、rake と CMake の再生成経路の両方がそこから読む。2 か所に同じ一覧を持たない。
- 受け手は生成ヘッダを include するので、生成プログラムと同じフラグ (`SPINEL_GEN_TU_FLAGS`、`-w` を含む) と gen/ の include path でコンパイルする (ESP、sim、wasm とも)。
- mruby から見た API (`Fmrb::Raycast` / `Fmrb::Fft` / `Fmrb::SpinelHello`) は変えていない。mrblib の変更はコメントだけ。
- `rake spinel:doctor` に gem の kernel 3 本を足した。gem はリンクが単独で通るので全部の脚を回し、behavior の ERR (U-14) だけ許可表で除く。3 本とも他の指摘は無い。system_desktop が落ちるのは P2a から変わらない既知の件。

### 3.2 消えた行・足した行

「全行 (コメントと空行を除いた行)」。develop `94cf41f2` → HEAD。

| gem | Ruby (entry + FFI → kernel) | C 受け手 | FFI 関数 |
|---|---|---|---|
| fft | 114 (45) → 109 (64) | 262 (162) → 229 (154) | 7 → 0 |
| raycast | 86 (39) → 56 (19) | 207 (142) → 174 (126) | 10 → 0 |
| spinel_hello | 22 (10) → 30 (9) | 148 (97) → 142 (99) | 2 → 0 |

- 生成の配線 (P3 全体、rake +79 / -78、`main/CMakeLists.txt` +45 / -30、`compile_ruby_to_spinel.cmake` +50 / -27、wasm +10 / -3) は
  行数ではほぼ変わらない。数字より、同じ名前の一覧 (entry と `--persistent-statics`) を 2 か所で合わせる約束が消えたことが大きい。
- fmruby-core 全体 (スナップショットを除く、コード 2 コミット) は +704 / -776 行。

## 4. P3c: VM 3 本

- 生成を `--ext-init Init_fmrb_kernel` / `Init_editor` / `Init_system_desktop` にした (entry は無し)。init が Ruby の top level
  (`SomeApp.new.start` → main_loop) を走らせるので、タスクは entry を呼んでいた所で init を 1 回呼ぶ。
- 3 つの NATIVE タスク本体 (pool からインスタンスを作る・走らせる・壊す) は写しだったので、`fmrb_app_run_spinel_vm(ctx, init)`
  (`main/app/fmrb_app_spawner.c`、宣言は `fmrb_app.h`) にまとめた。行数は kernel.c +7 / -40、spawner +52 / -50
  (まとめた関数の説明のコメントを含む)、`fmrb_app.h` +12。3 つの写しにあったプールの閾値の説明は 1 か所にまとめた。
- `fmrb_spinel_host.c` と `fmrb_spx_*.c` は変えていない。FFI も同じ。
- 生成 C の関数フレーム (逆アセンブル、`$S/tu_*.tsv`): kernel は 271 関数・最大 4,048・合計 39,616 で P2b-2 と全関数同じ。
  editor は `Init_editor_try` の 1 関数 (16 バイト) が増えただけで、`Init_editor` のフレームは `editor_entry` と同じ 3,696。
- 入口の関数: `Init_fmrb_kernel` 128 バイト (旧 `fmrb_kernel_entry` 128)。

### 4.1 スタックが 16 バイト減った件 (直した)

最初の P3c のファーム (`$S/dev_p3c.out`) で kernel の最悪 Free が 6,488 → 6,472、FM-Editor が 10,628 → 10,612 になった。
逆アセンブルで、新しい `fmrb_app_run_spinel_vm` のフレームが 48 バイト (旧 `spinel_kernel_native` は 32) と分かった。
エラーログの引数が 9 個になり、出力用のスタック領域と退避レジスタが増えたため。ext 移行そのものではなく入口の整理の副作用なので、
止まる条件には当たらないと判断して直した。ログを `noinline, cold` の別関数に出して 32 バイトに戻し、実機で 6,488 / 10,628 を確かめた。

## 6. フォークから `--no-main` / `--entry` / `--persistent-statics` を消せるか (判断材料)

- **fmrb はもう使っていない** (rakelib / CMake / C のどこにも無い。`grep` で確認)。残る参照は

## 7. 見立てと違った点・撤回した仮説

- **「P3a-1 には codegen の設計変更が要るかもしれない」は外れ**。MC では 40 個のうち 36 個が既に閉じていて、残る 4 個は
  連結指定の差し替えだけで済んだ。P0 / P1 の「40 個重複」は MC でない構成で数えた数字。
- **「ext の init はモジュールの状態を戻さない」は MC では外れ** (P1 は上流の構成で観察した)。MC の ext init は最初から
  `sp_reset_tu_statics` を呼んでいた。
- **「ext に移せば内蔵 RAM は変わらない」は、そのままでは外れ**。`_try` と init が、初期値つきの static (`sp_last_exc_cls`、`sp_program_name`) を
  各 gem の TU に残した (S3 +16 バイト)。P4 (TAB5) では .sdata の詰め物に吸収されて見えなかった。
- 実機の最初の P3b の待機時の空き 149,824 は、ext 移行の影響ではなかった (静的な RAM は同じで、起動し直すと 150,012)。
  待機時の空きは起動ごとに 200 バイト程度揺れる (BLE / WiFi の初期化)。基準との比較は 1 回の起動で判断しないほうがよい。
- VM の入口を 1 関数にまとめるのは「綺麗にする」だけのつもりだったが、フレームが 16 バイト増えた。生成 TU の外の C も
  スタックの勘定に入る (VM 全体がその下で走る)。
