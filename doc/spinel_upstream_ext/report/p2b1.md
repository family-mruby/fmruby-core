## 変化点の要約 (先に読む)

1. **S3 は入り、Tab5 が入らない**。見立て (flash +0.95MB で S3 が危ない) と逆だった。
   S3 のアプリ区画は 6MB で基準の空きが 34% あり、増分 +339KB を吸収した (28% 残る)。
   Tab5 は同じ 6MB の区画に基準で 95% 使っていて、増分 +427KB で 114,256 バイト溢れた。
   memory の「S3 flash 残 6%」は区画を広げる前の記録で、今は当てはまらない。
2. **flash の増分は見立ての 3 分の 1 強**。ホストの `-m32 -O2` の見込み +0.95MB に対し、
   実機は S3 +339KB、P4 +427KB。`--gc-sections` が上流ランタイムの大部分を落とす。
3. **内蔵 RAM は +54KB (両機種ほぼ同じ)**。内訳は凍結リテラル `.data` 30KB (editor 19.2KB、
   kernel 10.8KB)、1 文字文字列の表 `sp_hdr_char_cache` 16KB (見立ての 12KB より大きい)、
   slab の worker 表 2KB (SP_NO_SLAB では使わない)、生成プログラムごとの `sp_bt_buf` 1KB×5 ほか。
   Tab5 の待機時空き 152,612 バイトは、静的な分だけで約 98,800 バイトになる見込み。
4. **fmrb の Ruby を 5 ファイル直した**。文字列リテラルに `setbyte` で書き込む箇所が
   FrozenError になった (起動音の APU メッセージで 17 行、マウスの転送で全クリック)。
   **`.dup` では直らなかった**: kernel の `handle_hid_event` では Spinel が変数を
   String ハンドルで持ち、そのハンドルを作る `sp_String_new_shared` が非バイナリ文字列の
   長さを strlen で測るので、NUL で始まる 6 バイトの複製が空文字列になった。`.b` にした。
5. **ESP newlib で直したものは 7 点** (fmrb-next `88465f2a`、全部ガードの追加)。
   想定していた fopencookie は問題なく、`poll.h` の置き場所、`__freadahead`、AF_UNIX/PF_UNIX、
   getline、getpriority、WCOREDUMP、signal が引っかかった。最後の 1 点は newlib ではなく
   Xtensa の窓付き呼び出しの制約で、上流の `sp_poly_eq_deep` がフックを検査せずに呼ぶ所に
   GCC が「アドレス 0 への呼び出し」を出していた (PR 候補)。

## 2. remembered / pinned 集合とプールの関係

0 のまま (1024 / 256 エントリ)。32bit で 1 エントリ 4 バイトなので、インスタンスごとに
4KB + 1KB を**そのインスタンスのプールから**取る (内蔵 RAM ではない)。

| インスタンス | プール | 5KB の割合 |
|---|---|---|
| kernel | 512,000 | 1.0% |
| editor | 1,572,864 | 0.3% |
| fft | 196,608 | 2.5% |
| raycast / spinel_hello | 131,072 | 3.8% |

溢れても次の回収が全体の印付けになるだけなので、既定で困る理由は見当たらない。
sim の `ps` で kernel の使用量は待機時 19-21 万バイト / 512,000 (64bit の値。32bit ではもっと小さい)。

### 1 回目 (取り込んだだけ): 起動はするが kernel が FrozenError を出す

デスクトップは出たが、`docker logs fmruby_core` に
`spx: Error in msg_handler: FrozenError: can't modify frozen String: "\t\u0000..."` が 17 行
(起動音の `note_on` / `note_off` を APU に送るメッセージ)。静的に探す小さなスクリプト
(`$S/scan_frozen.rb`: リテラルを代入した変数に同じメソッド内で setbyte / `<<` / 破壊的
メソッドを使う所を探す) で、kernel 9 か所、editor 1 か所、desktop 1 か所を見つけた。

### 2 回目 (`.dup` で直した): キー入力は通るがクリックが全部落ちる

エディタは起動し「puts 1」の打鍵も通った (`shots/02_editor_typed.png`)。しかしメニューが
開かない。ログに `Error in handle_hid_event: IndexError: index 0 out of string` が 9 行。
生成 C を読むと、`handle_hid_event` の `relative_data` だけ `sp_String *` (ハンドル) で
持たれていて、代入が
`sp_String_new_shared(sp_str_dup(<凍結リテラル>))` になる。`sp_String_new_shared` は
バイナリでない文字列の長さを `strlen` で測る (`sp_string.h`) ので、`"\x00"*6` の複製は
長さ 0 になる。`"\x00" * 6` に書き換えても同じ形 (`sp_str_repeat` の結果を strlen) になる
ことを生成 C で確かめた。`.b` にすると `sp_String_new_shared(sp_str_b(...))` になり、
バイナリの印が付くのでヘッダの長さで測られる。

ホストで小さく再現しようとしたが (メソッド内、begin/rescue、case の分岐、poly 引数、
ハッシュのメッセージ)、いずれも変数が `const char *` のままで再現しなかった。どの条件で
ハンドルに昇格するかは突き止めていない (6 節)。

## 5. ESP newlib で直したこと (fmrb-next `88465f2a`)

コミット件名 `runtime: compile and link on ESP-IDF newlib (Xtensa / RISC-V)`。
全部ガードの追加で、ホストの既定ビルドは同じコードを通る。`make lib/libspinel_rt.a
lib/libspinel_rt_mc.a` と `make check-mc-globals` (PASS、203 個) を通した。`make test` は
回していない。

| 症状 | 場所 | 直し方 |
|---|---|---|
| `poll.h: No such file` | sp_cold.c / sp_io.c / sp_sched.h | ESP-IDF は `<sys/poll.h>` だけを持つ。`__has_include` で選ぶ |
| `__freadahead` 未宣言 | sp_io.c 2 か所 | newlib の FILE は BSD と同じ形なので `fp->_r` を読む (`__NEWLIB__`) |
| `PF_UNIX` 未定義 (AF_UNIX はある) | sp_io.c の定数表 | AF_UNIX と PF_UNIX を別々に `#ifdef` |
| `AF_UNIX` 未定義 | sp_cold.c `sp_addrinfo_new` | `#ifdef AF_UNIX` |
| `getpriority` 未宣言 | sp_cold.c | `SP_NO_PROCESS` では NotImplementedError |
| `getline` 未宣言 | sp_cold.c `sp_argf_gets` | newlib は `__getline` だけを宣言する |
| `WCOREDUMP` 未宣言 | sp_process_status.c | 無ければ常に偽 |
| リンク時 `signal` 未定義 | sp_gc.c (GC verify の障害報告。**プロセスのコンストラクタから**参照される) | `SP_NO_MMAN` では登録しない |
| リンク時 `dangerous relocation: windowed longcall crosses 1GB boundary ... *UND*` | spinel_rt.h `sp_poly_eq_deep` | 下の説明 |

最後の 1 件: `sp_poly_eq_deep` の末尾が `else r = sp_obj_eq_hook(a, b);` で、コメントは
「sp_poly_eq の object の腕が先に検査している」と言うが、配列・ハッシュの腕からも
ここへ来る。`sp_obj_eq_hook` は生成 TU の `static` で、オブジェクトの `==` を持たない
プログラム (kernel / editor) では一度も代入されないので、GCC は NULL と確定して
**アドレス 0 への呼び出し**を出す。x86 ではリンクが通る (実行されない経路なので気づかない)。
Xtensa の窓付き call は 0 番地に届かず、リンカが止める。呼ぶ所で検査するように直した。

想定していた `fopencookie` は newlib の stdio.h にあり、問題にならなかった。
`sys/wait.h` の WIF* も WCOREDUMP 以外は揃っていた。

ESP の反復は、1 回ごとに `rake clean_all` を回さず、構成済みの build/ でコンテナの
`ninja -k 0` を回した (`$S/ninja_k.sh`)。サイズの表の数字は、修正を全部入れた後の
`clean_all` からのビルドで採り直したもの。

## 6. P2b-2 の判断に要る材料

1. **Tab5 が入らない (114,256 バイト)。先に決めることになる**。候補:
   - 区画を広げる: Tab5 は 16MB flash。アプリ区画 6MB と storage 5MB の割り振りを見直せるか。
     sdkconfig / パーティション表の変更なので提案まで (CLAUDE.md の規約)。
   - `-Os` (生成プログラムとランタイムだけ): p2a で残した宿題。未計測。kernel と editor で
     +233KB (P4) の増分があり、ここが一番効くはず。
   - 生成コードの増分の中身を詰める (上流の生成 C は整数演算ごとの nil 検査が増えている。
     P1 の「ホストで 15-45% 遅い」と同根)。
   - 凍結リテラルを `.rodata` に移す (N-16) は flash を減らさない (RAM を減らす)。
2. **S3 は今の構成のまま入る** (空き 28%)。mruby カーネルに戻す必要は flash の面では無い。
   内蔵 RAM は DIRAM の静的な残りが 187,637 → 133,589。S3 の待機時の実測空きは今回の手元に
   無いので、実機で M1| の値を見て判断する。
3. **Tab5 の内蔵 RAM**: 静的に +54KB、待機時空きの見込みは約 98,800 バイト。回収できる
   見込みのあるもの:
   - 凍結リテラル 30KB: N-16 (生成時にハッシュを入れて const に)。上流の変更が要る。
   - `sp_hdr_char_cache` 16KB: 起動時に同じ値で埋まる表。PSRAM に置く口 (SP_TU_BSS と
     同じ形のランタイム用の属性) をフォーク側で足せば 16KB 戻る。遅い PSRAM に置いてよいかは
     1 文字文字列の生成頻度次第。
   - `sp_bt_buf` 5KB: 生成プログラムごとの static。`SP_TU_BSS` を付ければ PSRAM に行く
     (フォーク側の修正)。
   - `sp_slab_wk` 2KB: SP_NO_SLAB では参照されないはずの表が残っている (gc-sections で
     落ちないのは同じ TU の `sp_gc_alloc` と同じ節にいるか、参照が残っているため。未調査)。
   これで最大 53KB。凍結リテラル以外はフォーク側だけで済む。
4. **SPINEL_PIN / push**: fmrb-next は `88465f2a` (b259d0a3 + 1)。push 後に SPINEL_PIN を
   それに向け、`vendor/spinel` から import し直せば `IMPORT_INFO` の `fork_dir` も元の
   形に戻る。
5. `-ffp-contract=off` の影響の見立て: **どの対象でも実質無い**。Ruby の Float は倍精度で、
   S3 (Xtensa) は単精度 FPU のみ、P4 (RISC-V) も F 拡張 (単精度) のみなので、倍精度の
   積和は常にソフトウェアで、縮約される命令が無い。x86-64 の sim も `-mfma` 無しでは
   FMA を出さない。差が出るのは aarch64 などのホストで答え合わせをする時だけ。
6. 実機で見るべきこと (sim では確かめられないもの): プロセスのコンストラクタ
   (`sp_gc_debug_env` `sp_alloc_install_hooks` `sp_alloc_report_boot`) がブート時に走ること
   自体は ESP でも問題ないはずだが、getenv が NULL を返す前提で書いてある。
   GC.start が `sp_nosched.c` 経由で回収すること (sim は本物の sp_sched.c を通る)。

## 7. 見立てと違った点・撤回した仮説

- **「flash +0.95MB で S3 が入らない可能性が高い」は外れ**。実機の増分は S3 +339KB、
  P4 +427KB。ホストの `size -A` 合計は gc-sections 前の量で、実機では大部分が落ちる。
  さらに「S3 は残り 6%」は区画を 6MB に広げる前の記録だった。入らないのは Tab5 の方。
- 「内蔵 RAM の増加は `.data` の約 +47KB」: `.data` は +30KB で、代わりに `.bss` が +24KB
  あった (1 文字文字列の表が 12KB でなく 16KB、`sp_bt_buf` と `sp_slab_wk` が新顔)。
  合計は見立てと近い。
- **「`.dup` を付ければ凍結リテラルの問題は片付く」は成り立たなかった**。複製が
  String ハンドルに入ると strlen で測られ、NUL で始まるバイナリは空になる。`.b` が要る。
- 一度「上流には `# frozen_string_literal: false` と `--disable=frozen-string-literal` の
  逃げ道がある」と読んだ (`e432b19b` のコミット文)。今の上流では両方とも拒否される
  (コマンドラインはエラー、マジックコメントは警告して無視)。P0 の「オプトアウト無し」が正しい。
- 「newlib で危ないのは fopencookie と sys/poll.h」: fopencookie は無事で、代わりに
  7 か所の非互換と、newlib と無関係な Xtensa のリンク制約が出た。
