## 上流の作法 (必ず守る)

上流の README の Contributing 節を最初に読み、そこに書かれた作法に従う。
p0 時点で分かっていること:

- 焦点を絞った小さい変更 (1 PR 1 問題)。既定の出力を変えない
  (P-3 は `-D` を付けないとき 1 バイトも変わらないこと)
- `make` の自己ホストが一致すること、`make test` と `make bench` が通ること
- `test/` に回帰テストを足す (`<name>.rb` + `<name>.rb.expected` の形。
  既存のテストの流儀に合わせる)
- コミットメッセージは上流の履歴の書き方に合わせる (件名の形、本文の長さ)。
  Issue 参照の trailer が作法にあるなら、Issue が無いことを report に書く
  (Issue はこちらで作らない)
- コメントは英語

## 各候補ですること

1. 基点 `01521b1e` で最小再現が失敗することを確かめる
2. 修正する。フォークの修正は**そのまま cherry-pick せず**、上流の今の
   コードに合わせて書き直す (フォークは 3,371 コミット前が基点)。
   フォーク固有の事情 (`SP_MULTI_CTX` など) を持ち込まない
3. 回帰テストを足す。最小再現を上流のテストの流儀に書き直してよい
4. `make` (自己ホスト一致)、`make test`、`make bench` を通す。
   失敗が修正前からあるものか (基点でも落ちるか) を区別して記録する
5. 32bit に関わるもの (P-9) は、report/p0.md の手順の 32bit ランタイムで
   確かめる。上流の `make test-corpus CC='cc -m32'` が i386 の libcrypt 不足で
   回らない場合は、そう書いて代わりの確認方法を記録する
6. P-9 では、上流が該当テストを 32bit から外している印 (`# spinel: int64`
   など) を外せるかも確かめる
7. U-6 は「解析を直す (`ca0709c` 相当)」と「崩れたら止める検査
   (`622750c` 相当)」を別ブランチ (`pr/U-6`、`pr/U-6-check`) に分ける。
   検査だけでも価値があるかを report に書く

U-12 はフォークにも修正が無い。原因を突き止めて直す。直し方が大きく
なる (codegen の設計に踏み込む) と分かったら、修正はせず原因の説明と
最小再現だけを残して次へ進む (Issue で出す候補にする)。

## report/pr1.md に書くこと

候補ごとに:

- ブランチ名と commit、変更したファイルと行数
- 原因の説明 (PR 本文の下書きとして使える粒度。英語で書いた PR 本文の
  下書きも添える)
- 回帰テストの名前、`make test` / `make bench` の結果 (修正前・後の件数)
- 見込みの見直し (出しやすさ、懸念)

全体として:

- 出す順番の提案 (小さく通りやすいものから)
- 作業中に見つけた別の不具合 (**PR 候補**節。内容・最小再現・確認した上流 commit)
