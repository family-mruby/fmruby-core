# 報告 E1: sim の起動の EINTR

> 状態: 完了 (親の検収待ち) | 更新: 2026-10-05 | コミット: graphics-audio 2eb4ad9、core (このファイルと同じコミット)。どちらも `fix/sim-boot-eintr` | 原因は FreeRTOS の POSIX ポートの SIGALRM (SA_RESTART なし) が、graphics-audio のソケットの bind / listen をカーネルの中で割り込むこと。strace で `ERESTARTSYS` と直後の SIGALRM を確かめた。直す前は 60 回中 6 回 (10%) 起動に失敗し、EINTR で再試行する形 (display_shm.cpp と同じ) に直したあとは 64 回中 64 回 (strace 下でも 10 回中 10 回) 起動した。

## 結論

- 失敗の頻度: 直す前、標準構成 30 回中 2 回、互換構成 (カーネル・エディタとも mruby) 30 回中 4 回。合わせて 60 回中 6 回。
- 失敗した呼び出し: graphics-audio の `input_handler_ipc` の bind が 5 回、`socket_server` (comm_socket_server.c) の
  listen が 1 回。strace の下では `input_socket` の bind も割り込まれた。core の側は、graphics-audio の listen が
  失敗した回に `fmrb_hal_link: Failed to connect after retries` が連鎖して出た (後述)。
- 割り込んでいる信号: SIGALRM だけ。graphics-audio のプロセスに届いた信号は全部 `SIGALRM {si_code=SI_KERNEL}`
  (ITIMER_REAL の tick) で、ほかの信号は 1 件も無い。ハンドラは `sa_flags=SA_RESTORER` で SA_RESTART が無い。
- 起きるプロセス: graphics-audio と core (どちらも FreeRTOS の POSIX ポートで動く)。sdl2-display は FreeRTOS を
  使わず SIGALRM が無いので起きない。
- 直し方: EINTR で再試行する (plan.md の候補 1)。両リポジトリに `fmrb_eintr.h` (再試行のマクロ) を足し、洗い出した
  所を同じ形で直した。
- 直したあと: 標準構成 32 回中 32 回、互換構成 32 回中 32 回起動した。エディタの起動と 1 打鍵は 16 回とも通った。

## T1: 確かめた結果

### 繰り返しの起動

起動ごとに 3 つのコンテナを `docker compose -f docker-compose.yml -f docker-compose.headless.yml up -d` で上げ、
core のログに `main_loop started` が出るまで最大 90 秒待ち、3 つのログを保存して `down` した (dev_run_check.sh と
同じ起動の判定)。一部の回ではエディタを起動して `a` を 1 打鍵し、編集域の画素の変化とエディタの生存
(debugd の ps) を確かめた。スクリプトは使い捨てなのでコミットしていない。

| 構成 | 直す前 | 失敗した回と失敗 |
|---|---|---|
| 標準 (Spinel カーネル + Spinel エディタ) | 28/30 | 8 回目・22 回目: `input_handler_ipc: Failed to bind socket: Interrupted system call` → core が `INIT_DISPLAY ACK timeout` |
| 互換 (全部 mruby) | 26/30 | 10・13・20 回目: 同じ `input_handler_ipc` の bind。28 回目: `socket_server: Failed to listen on socket: Interrupted system call` |

- `input_handler_ipc` の bind は、core から INIT_DISPLAY を受けたあとの `full_display_init` の中で走る。ここで
  失敗すると graphics-audio は表示の初期化を諦め、ACK を返さないので core が `INIT_DISPLAY ACK timeout` で止まる。
- 28 回目は listen が失敗したが、ソケットのファイルは bind で既にできていたので、graphics-audio の healthcheck
  (`test -S`) は通ってしまい core が起動した。core の `fmrb_hal_link` は ECONNREFUSED で 10 回 (各 100ms 待つ
  つもり) 再試行したが、10 回が**約 10ms で尽きた** (`Failed to connect after retries`)。`usleep(100000)` も
  SIGALRM で EINTR になって 1ms ほどで戻っているため。これも同じ原因の別の現れ。
- 互換構成の方が少し多いが、失敗は graphics-audio の中で core とつながる前に起きているので、構成の差というより
  起動の時間の揺らぎの差と見ている (母数が小さいので差は言えない)。

### strace

strace を足した使い捨てのイメージ (`fmrb-eintr-strace:tmp`、ビルド用のイメージに `apt-get install strace`) と、
graphics-audio のサービスだけ `strace -f -tt` の下で起動する上書きの compose ファイルを scratchpad に作って
起動した。リポジトリの compose と sdl2-display には手を入れていない。

直す前は 1 回目で失敗した (strace で呼び出しが遅くなり、割り込まれやすくなる)。

```
111 10:29:31.498282 unlink("/var/run/fmrb/fmrb_input_socket") = -1 ENOENT
111 10:29:31.498347 socket(AF_UNIX, SOCK_STREAM, 0) = 4
111 10:29:31.498410 bind(4, {sa_family=AF_UNIX, sun_path="/var/run/fmrb/fmrb_input_socket"}, 110) = ? ERESTARTSYS (To be restarted if SA_RESTART is set)
111 10:29:31.498476 --- SIGALRM {si_signo=SIGALRM, si_code=SI_KERNEL} ---
111 10:29:31.499076 close(4) = 0
111 10:29:31.499311 +++ exited with 0 +++
```

- bind はカーネルの中で眠っていて、SIGALRM で `ERESTARTSYS` になった。ハンドラに SA_RESTART が無いので、
  利用者には EINTR として返る。errno が後から書き換わったのではなく、本当に系統呼び出しが割り込まれている。
- Unix ソケットの listen も同じように `ERESTARTSYS` になる (直したあとの strace で 3 回見た)。
- FreeRTOS の POSIX ポート (IDF の `components/freertos/FreeRTOS-Kernel/portable/linux/port.c`) は tick の
  ハンドラを `sigtick.sa_flags = 0` で付ける。走っているタスクのスレッドだけが SIGALRM を受け付けるので、
  系統呼び出しをしているタスクに tick が当たる。ハンドラの中でタスクの切り替え (スレッドの停止) まで行う。
- 最後の `exited with 0` は graphics_task が `input_socket_start` の失敗で `return` してスレッドが終わったもの。

### EINTR を扱っていない所 (Linux の経路)

「起動に効く」は今回の失敗に直接つながる所。○は今回直した所。

graphics-audio:

| 所 | 呼び出し | 扱い | 対応 |
|---|---|---|---|
| input_socket.c | bind / listen | 失敗として返す (実際に起きた) | ○ |
| input_socket.c | accept (2 か所、非ブロッキング) | 次の機会まで待つだけ (害は小) | ○ (揃えるため) |
| input_handler_ipc.c | bind / listen | 失敗として返す (bind は実際に起きた) | ○ |
| input_handler_ipc.c | accept (非ブロッキング) | 害は小 | ○ |
| input_handler_ipc.c | recv の読み捨て (packet の消費、大きすぎる packet の破棄)、2 回目の MSG_PEEK | 消費が割り込まれると同じ入力を 2 度処理する | ○ |
| comm_socket_server.c | bind / listen | 失敗として返す (listen は実際に起きた) | ○ |
| comm_socket_server.c | accept (非ブロッキング) | EINTR をエラーとしてログに出す | ○ |
| display_shm.cpp | ftruncate / mmap | tmpfs 上で眠らないので起きない見込み | 対応しない |
| main_linux.cpp | sleep(1) のループ、シグナルハンドラの usleep | ループ・終了時なので害なし | 対応しない |

既に扱っていた所: display_shm.cpp の shm_open / sem_open、audio_handler_shm.c の shm_open (と usleep の代わりの
vTaskDelay)、input_socket.c の send、comm_socket_server.c の read / write、input_handler_ipc.c の最初の MSG_PEEK。
send / read / write の do-while は新しいマクロに置き換えた (動きは同じ)。

fmruby-core:

| 所 | 呼び出し | 扱い | 対応 |
|---|---|---|---|
| fmrb_hal_link_posix.c (components/fmrb_hal/platform/posix) | connect | EINTR を致命の失敗として返す (`Failed to connect to socket server`) | ○ |
| 同 | usleep(100ms) の再試行の間隔 | EINTR で約 1ms で戻り、再試行が 10ms ほどで尽きる (実際に起きた) | ○ (タスクの遅延へ) |
| usb_task_linux.c | connect | EINTR を致命の失敗として返す | ○ |
| 同 | usleep(100ms) | 同上 | ○ (タスクの遅延へ) |
| fmrb_debug_transport_tcp.c | bind / listen | `transport init failed`。debugd が上がらない | ○ |
| 同 | accept | 害は小 | ○ |
| 同 | recv / send | EINTR でクライアントを切断する | ○ |
| fmrb_hal_time_posix.c | `fmrb_hal_time_delay_us` の usleep | 短く戻る。呼び出しは 1 か所、起動の経路ではない (wasm と共有) | 対応しない |
| fmrb_hal_uart_posix.c | select / read | EINTR を失敗として返す。sim の起動の経路ではない | 対応しない |
| lib/patch・lib/replace の picoruby の posix ポート (task_hal.c の usleep / nanosleep、machine.c の nanosleep、picoruby-socket の tcp_socket.c / ssl_socket.c の select) | | 多くは「短く戻ってよい」作り。recv は V2 で対応済み | 対応しない (lib/ の変更は `rake clean` が要り、起動の経路でもない) |
| components/fmrb_spinel_rt (Spinel の実行時) | poll / nanosleep / waitpid | 大半は EINTR を扱っている | 対応しない |

既に扱っていた所: fmrb_hal_link_posix.c の send / recv (2 か所)、usb_task_linux.c の recv、
fmrb_debug_transport_tcp.c の select (EINTR → 0)。

## T2: 直し方

### 選んだ形と理由

plan.md の 3 つの候補から (1) EINTR で再試行する、を選んだ。

- 既存の手当て (display_shm.cpp・audio_handler_shm.c、core の fmrb_hal_link_posix.c の send) が全部この形で、
  揃えられる。
- (3) SA_RESTART は FreeRTOS の POSIX ポートのハンドラの付け方を変えることになり、IDF の部分の変更で範囲外。
  しかもタスクの切り替えをハンドラの中で行うポートなので、再開の意味が変わる影響を読み切れない。
- (2) SIGALRM をブロックする区間を作る案は、その間 tick が止まり (他のタスクに切り替わらない)、ブロックを外し
  忘れる危険も増える。今回の呼び出しは再試行で足りるので、そこまで要らない。

### 変えたもの

- graphics-audio `main/common/fmrb_eintr.h` (新規): `FMRB_RETRY_EINTR(expr)` (戻り値が -1 で errno が EINTR の
  間、式を評価し直す。glibc の TEMP_FAILURE_RETRY と同じ形を、_GNU_SOURCE に頼らず書いたもの) と、
  `fmrb_unix_bind()` (Unix ソケットの bind を EINTR で再試行。再試行の前にソケットのファイルを消す)。
  - bind の前の unlink は念のため。今回の strace では、割り込まれた bind はファイルを残していなかった
    (再試行の前の unlink が ENOENT)。残った場合は再試行が EADDRINUSE になるので、呼び出し元が最初に
    unlink しているのと同じ扱いにした。
- graphics-audio の input_socket.c / input_handler_ipc.c / comm_socket_server.c: 上の表の所をマクロ /
  `fmrb_unix_bind` に置き換えた。
- core `components/fmrb_common/include/fmrb_eintr.h` (新規): 同じ `FMRB_RETRY_EINTR`。fmrb_common に置いたのは、
  main と fmrb_hal の posix の実装、wasm のビルド (debug transport を含む) の全部から見えるため。
- core の fmrb_hal_link_posix.c / usb_task_linux.c: connect を再試行し、EISCONN (割り込まれた試みが実は
  つながっていた場合) を成功として扱う。再試行の間隔を `usleep(100000)` から `fmrb_task_delay_ms(100)` に
  変えた (audio_handler_shm.c の「usleep でなく vTaskDelay」と同じ理由)。
- core の fmrb_debug_transport_tcp.c: bind / listen / accept / recv / send を再試行する。

どのファイルも Linux (と wasm) の経路でだけコンパイルされる。ESP32 のビルドに入るファイルは変えていない。
利用者から見た動きは変わらない。

  いたので、再試行の経路が実際に通っていることもこれで確かめられた。

## 残したこと・気づいたこと

- graphics-audio の healthcheck は `test -S` (ファイルがあるか) なので、listen が失敗してもソケットのファイルが
  あれば healthy になり、core が起動して接続に失敗する。今回の修正で listen は失敗しなくなったが、
  healthcheck が「受け付けられるか」までは見ていないことは残る (親のリポジトリの compose の話なので触っていない)。
- graphics_task は `input_socket_start` の失敗で `return` する (FreeRTOS のタスクの関数から戻る)。失敗が
  起きなくなったので触っていないが、失敗したときの後始末としては行儀が悪い。
- 表で「対応しない」とした所は、起動の経路でなく、短く戻っても害の無い作りか、既に扱っているもの。
  `fmrb_hal_time_delay_us` と UART の posix は、使う機能が増えたら同じマクロで直せる。
- 調べるのに使ったもの (scratchpad、コミットしない): 繰り返しの起動のスクリプト、strace の上書きの compose
  ファイル、`fmrb-eintr-strace:tmp` のイメージ。
