## 3. Zenoh (Asterism Z2 / Z3 の手順)

`/home/zenoh_echo.txt` に `tcp/192.168.10.2:7447` を置いた (この 1 つは残してある)。

### 3.1 zenoh_echo の往復と開き直し

手順: パスで起動 -> 5 秒 -> get を 2 回 -> put `hello<N>` -> 画面を撮る -> 窓の閉じるボタン -> 3 秒、を 5 回
(最初の 1 回は put `t5hello`)。

| 回 | 接続にかかった時間 | get の値 | 画面の in | 接続中の IRAM free | 接続中の PSRAM free |
|---|---|---|---|---|---|
| 0 (最初) | 35 ms | 9 -> 11 | t5hello | 179176 / 179088 | 9850384 -> 8928776 |
| 1 | 32 ms | 5 -> 7 | hello1 | 178652 | 8928764 |
| 2 | 45 ms | 5 -> 7 | hello2 | 178452 | 8928764 |
| 3 | 50 ms | 5 -> 7 | hello3 | 178220 | 8928764 |
| 4 | 550 ms | 5 -> 6 | hello4 | 178008 | 8928764 |
| 5 | 110 ms | 5 -> 7 | hello5 | 178016 | 8928764 |

- 毎回 `received: 1  dropped: 0`。閉じた後の一覧はカーネル・デスクトップ・Services の 3 つだけ。
- アプリの VM プールの使用は 272-279 KB (アプリのログの `pool_used`、`sys_used=4496` で一定)。
- 4 回目の 550 ms はほかより長いが、1 回だけで、続く回は 110 ms に戻った。

### 3.2 zenoh_nodes の問い合わせと生存の印

| 確かめたこと | 結果 |
|---|---|
| 接続 | `zenoh_nodes: tab5 connected (tcp/192.168.10.2:7447, 22 ms)`。画面に `self: tab5 (alive)` |
| `alive` | `fmrb/alive/tab5` |
| `query fmrb/node/tab5/info` | `tab5 up=7s pool=280KB answered=0` (1 件、141 ms) |
| `query "fmrb/node/*/info"` | `tab5 up=7s pool=279KB answered=1` (1 件、43 ms) |

閉じる (窓の閉じるボタン) と開く (パスで起動) を 3 回。PC で `alive` を 0.2 秒ごとに読んで測った (ruby の起動の分を含む)。

| 回 | 閉じてから消えるまで | 起動してから戻るまで | 接続にかかった時間 |
|---|---|---|---|
| 1 | 0.52 s | 1.05 s | 24 ms |
| 2 | 0.53 s | 1.05 s | 134 ms |
| 3 | 0.50 s | 1.03 s | 85 ms |

最後の開き直しの後の `query` も答えた (`tab5 up=0s pool=282KB`)。

### 3.3 内蔵 RAM

| 状態 | IRAM free | PSRAM free |
|---|---|---|
| 起動して落ち着いた後 (アプリなし) | 197640 | 10277648 |
| zenoh_echo、接続中 | 178008-179176 | 8928764-8928776 |
| zenoh_echo を閉じた直後 (開き直しの間) | 196288-197136 | 9356040 |
| zenoh_nodes、接続中 | 176232-178452 | 8927844 |
| zenoh_nodes を閉じた後 20 秒 -> 40 秒 | 196924 -> 197136 -> 197368 | 9356040 |
| **zenoh_nodes を閉じて 3 分 (11:35:09 -> 11:38:29)** | **197356 (起点との差 -284 B)** | 9356040 |

- 接続中の減り (約 18.5 KB) はアプリ 1 つ分 (タスクのスタック 16 KB ほか) と接続 1 本。P4-Nano の Z2 と同じ程度。
- 開き直しを続けると、接続中の値が 1 回ごとに 200 B ほど下がる (179176 -> 178652 -> 178452 -> 178220 -> 178008)。
  閉じた側の TCP の TIME_WAIT (2 分) の分で、閉じて 1 分ほどで 197356 まで戻った。Z2 の 4.3 と同じ動き。
- 閉じて 3 分の値は起点から -284 B。P4-Nano の Z2 (mempool あり) で見た「最初の接続で一度だけ減る 3,336 B」は
  Tab5 (mempool なし) では出ていない。
- PSRAM は最初のアプリの起動で 921 KB 減り (10277648 -> 9356040)、その後はどのアプリを閉じても 9356040 に戻る。
  最初の 1 回だけの確保で、開き直しで増えない。

zenohd は最後に `docker compose ... stop zenohd` で止めた。

## 4. ESP-Hosted の mempool なし (hosted_mempool M1 と同じ負荷)

手順は report/m1.md の 5 章と同じスクリプト (IP だけ Tab5 に変えた): 64 KB (乱数、固定の種) を
`/home/m1_test.bin` に put して get して照合、を 5 回 -> 消す -> Breakout (Python) を起動 -> `/stream` を 30 秒 ->
`/ws_video` を 30 秒 -> Breakout を終了 -> 3 分待つ -> Kamon を起動して 25 秒後に一覧で確かめて終了。これを 2 回続けた。

### 4.1 内蔵 RAM

| 時点 | 1 回目 | 2 回目 |
|---|---|---|
| 負荷の前 (アプリなし) | 197356 | 189652 |
| 転送の後 / MJPEG の最中 | 177572 / 158304-151804 | 169340 / 153608-152040 |
| H.264 の最中 (最小) | 124716 | 121628 |
| **負荷の後 3 分** | **189652** | **189652** |
| Kamon の起動中 | 172020 | 172020 |
| Kamon の終了後 | 189632 | 189652 (この後の項目 3 の起点) |

- 1 回目の負荷で -7,704 B、**2 回目の負荷では 1 B も減らない**。P4-Nano の M1 (mempool なし、-7,880 B が 1 回目だけ)
  と同じ形で、最初の通信で一度だけ取られる分と見る。
- 負荷を止めた直後 (H.264 の終了から 10 秒) で既に 189652 で、そこから 3 分間一定だった。mempool ありの
  P4-Nano で見た溜め置きの塊のような戻りの遅れは無い。

### 4.2 速さ

| 項目 | 1 回目 | 2 回目 | P4-Nano の M1 (なし) |
|---|---|---|---|
| 64 KB の put (範囲 / 平均) | 0.427-0.596 / 0.497 s | 0.491-0.592 / 0.527 s | 平均 1.056 s |
| 64 KB の get (範囲 / 平均) | 0.203-0.302 / 0.257 s | 0.221-0.370 / 0.284 s | 平均 0.298 s |
| 照合 | 5/5 一致 | 5/5 一致 | - |
| MJPEG `/stream` 30 秒 | 9.53 fps (286 枚、すべて新しい画面)、209 KB/s | 9.62 fps (289 枚)、211 KB/s | 9.30-9.41 fps |
| H.264 `/ws_video` 30 秒 | 15.08 fps (453 枚、鍵の画面 17)、7.8 KB/s | 14.99 fps (450 枚、16)、7.3 KB/s | 15.10-15.32 fps |

- put は P4-Nano の約半分の時間だった (Tab5 の flash の書き込みが速いのか、自動中断が無いためかは切り分けていない)。
- MJPEG と H.264 は P4-Nano と同じ水準。

### 4.3 BLE と落ちないこと

- BLE は起動ログで `BLE initialized (with file service)` -> `ble_on_sync: synced=1` -> `BLE advertising started`。
- 64 KB の put / get 10 回 (あわせて 640 KB の書き込み) で Guru / abort / 再起動は 0 件。P4-Nano の M1 4 章の
  「64 KB の put / get の直後に core 0 が落ちる」は Tab5 (自動中断なし) では起きなかった。自動中断を疑う見立てと矛盾しない。
- 試験のファイル `/home/m1_test.bin` はスクリプトが毎回消した (最後に /home を ls で確認)。

## 5. アプリの終了と Spinel の多重起動

### 5.1 起動と終了のくり返し

Shell (`default/shell`)、BlockGame、BASIC (`/app/basic/basic.app.bas`、全画面)、Flappy を順に起動し、4 秒後に一覧で
RUNNING を確かめてから閉じる。奇数の周は Ctrl+Q (通常の終了)、偶数の周は `/app/kill` (強制の終了)。

| 周 | 閉じ方 | 結果 |
|---|---|---|
| 0 (手で) | Ctrl+Q | Shell で `ls` が動き、BlockGame でキーが効き、BASIC はプログラムを最後まで実行 |
| 1、3 | Ctrl+Q | 4 本とも起動・終了、閉じた後はアプリ 3 つ (カーネル・デスクトップ・Services) |
| 2、4 | kill | 同上 |

16 回すべて合格。アプリなしの IRAM free は各周の間で 189120-189652 (189652 に戻る)。

続けて Shell + BlockGame + エディタ + Flappy を同時に起動し、4 つとも RUNNING (IRAM free 103128、PSRAM 5361632)。
4 つを kill した後は 183184 (5.3 の Mic Spectrum の分を引いた値に戻った)。

### 5.2 エディタの 2 つ目

| 手順 | 結果 |
|---|---|
| エディタ (pid 5) を開いて `abc` | 入る |
| 遠隔で `default/editor` をもう 1 つ | 断りの窓「This app is already running. / Only one copy of it can run at a time.」。ログ `[FM-Editor] Already running as pid 5; one at a time`。一覧はエディタ 1 つ |
| 断りの窓をクリックで閉じて `xyz` | 入る (`abcxyz`、Ln 1, Col 7) |
| `default/editor_fs` (全画面の起動) をもう 1 つ | 同じく断られた |
| 窓を閉じて `12` | 入る (`abcxyz12`) |
| Ctrl+Q -> 保存の確認 -> N | 閉じて一覧から消える |
| 開き直して `ok` | 入る。その後 kill で閉じた |

断られた起動にも `/app/launch` は `{"ok":true,"pid":6}` を返す (断りの判定がアプリのタスクの中で起きるため。
c1.md の作りどおりで、不具合とは見ていない)。

### 5.3 Mic Spectrum の 2 つ目 (exclusive_group "fft")

### 5.4 内蔵 RAM と VM プール

| 時点 | IRAM free |
|---|---|
| 項目 3 の前 (4 章の後) | 189652 |
| 5.1 のくり返しの後 | 189652 |
| エディタ 2 回を閉じた後 | 189564 |
| Mic Spectrum の 1 回目を閉じた後 | 183184 |
| Mic Spectrum の 2 回目 (kill)・3 回目 (Ctrl+Q) の後、4 つ同時の後 | 183184 (11:53:25 から 11:56:38 まで一定) |

- Mic Spectrum の初回だけ -6,468 B。`audio_p4_hw.c` の `mic_init_rx` は、受信側の I2S を最初の `mic_enable` で
  初期化してそのまま持つ作り (起動の音を変えないため、という注記つき)。2 回目以降は減らないので漏れではない。
  内蔵 RAM を減らす方向から見ると、マイクを一度使うと 6.4 KB が戻らないことは覚えておく値。
- VM プール (10 秒ごとのダンプ、Used): 項目 3 の前 kernel 132480 / desktop 666136 / Services 349600、
  後 kernel 129016-132840 / desktop 644184-671672 / Services 348968-349760。GC の揺れの幅の中で、増えていない。
- タスクのスタックの残り (最後のダンプ): system_desktop 4296 B (起動直後 6724)、fmrb_host 9892、Services 7320、
  audio_p4 4432、hw_proxy 4220。
- PSRAM は 4 つ同時に動かしたときに予備の USER_APP の枠 (#7、#8、起動時は未確保) が確保されて約 2.1 MB 減り、
  そのまま (7047712)。枠を初めて使ったときの確保で、くり返しでは減らない。

## 6. ログの点検

- `Guru`、`abort()`、`Stack protection`、`arena full`: 0 件 (11:28:47 の起動から 11:56 まで)。
- `rst:0x` は capture を開いたときの `rst:0x17` の 1 件だけ。
- `/app/launch` の断られた起動は 4 回 (エディタ 2、Mic Spectrum 1、FFT Bench 1)、どれも窓とログが出た。

## 7. 後片付け

- zenohd は止めた (`docker ps` に出ない)。
- 試験のアプリは動いていない (一覧はカーネル・デスクトップ・Services)。ミュートのまま (`muted:true`)。
- /home は `zenoh_echo.txt` (22 B) と、もとからある `music/` だけ。`/home` への書き込みは 64 KB x 10 と 22 B で約 640 KB。
- コードと設定は触っていない。

## 8. 見立てと違った点

- Tab5 の 64 KB の put は P4-Nano の約半分の時間だった。
- Zenoh の最初の接続で一度だけ減る分 (P4-Nano の Z2 で 3,336 B) は、Tab5 では出なかった (-284 B)。Z2 の測定は
  mempool ありのファームだったので、あの分も ESP-Hosted の溜め置きだった可能性がある (切り分けはしていない)。
- 項目 3 の内蔵 RAM の差は、アプリの終了ではなくマイクの初回の初期化だった。
