# T1: 受け口の再送 (受け手の位置を正にする)

> 状態: 実装済・検収待ち | 更新: 2026-11-08 | 片を何度届いても同じ結果になる受け口 (前の片は読み捨て、先の片は取らず、どちらも受け手の位置を返す)、失敗したら待ちを倍にしながら `begin` し直して受け手の位置から続ける送り手、`/tmp` に残す片のファイルと控えで接続の切れ目と受け手のアプリの起動し直しから続ける再開、`begin` で宣言した SHA-256 を `commit` で照合。仕組みは asterism gem の `data/transfer/transfer.rb` (Asterism::Transfer。mrbgem には入れず、端末は実行時に読む)。転送のアプリはその上に載せ替え、checkpoint の移動 (ネイティブ版・sim・ブラウザ版) は通る。`rake regress:transfer` でネイティブ版どうしの 8 つの場面が通る

## 1. 置き場所と pin

- 仕組みは asterism gem (作業用 checkout `family-mruby/asterism`) の `data/transfer/transfer.rb` と `data/transfer/sha256.rb`。gem のコミット `4a39108` (未 push)。
- **mrbgem (`mrblib/`) に入れなかった**。mrblib は picoruby-asterism を持つ全部の mruby の VM に入る (F5 で、3 つの C のメソッドを全部の VM に足しただけで `regress:run` の幅 512 B を超えた)。ファイルを運ばないアプリまで 850 行の Ruby を持つことになるので、`data/msgs` (ROS 2 の型) と同じ「端末が実行時に読む」形にした。
  - Family mruby は `rake setup` で `data/transfer` を `flash/usr/share/asterism/transfer/` へ写す (生成物、gitignore。`msgs` と同じ扱い)。ブラウザ版の束 (`wasm:webflash`)・.deb の木 (`native:root`) とその検査 (`wasm:scan`・`native:scan`) にも足した。
  - 端末では転送のアプリが `require "/usr/share/asterism/transfer/transfer"`。CRuby は `require "asterism/transfer"` (`lib/asterism/transfer.rb` が同じファイルを読む)。同じ 1 つのファイルが両方で動く (方針 1・5)。
- pin: `lib/add/ASTERISM_PIN` を `4a39108` に上げた。**gem はまだ push していない** (push はユーザの指示語のみ)。そのため `rake asterism:setup` は公開リポジトリからこのコミットを取れない。手元では `vendor/asterism` に作業用 checkout から fetch して置いた (`git -C vendor/asterism fetch ../asterism main`)。**push は gem → fmruby-core の順**が要る。pin を上げたことで 0.8.0 から 0.11.0 までの gem の変更 (CLI・CRuby 3.4 以上。`mrblib/` の差分は無し) も一緒に入る。

## 2. 決まり (受け口)

`<ノード>/<アプリ>/<オブジェクト>` に `caller: :from` で出す。転送のアプリは `<ノード>/transfer/inbox`。

| 呼び出し | 答え |
|---|---|
| `begin(kind, meta)` | meta `{"name", "size", "sha256" (全体、16 進 64 桁), ...種類のもの}` → `{"id", "piece" (受け手が取る最大の片), "pos" (この同じファイルについて受け手が既に持つバイト数)}`。同じ送り手が同じファイル (名前・大きさ・SHA-256 が同じ) を begin し直したら、止まった所から続ける |
| `chunk(id, pos, bytes)` | 受け手の今の位置を返す。`pos` が位置と同じなら書く。前 (もう持っている) なら読み捨て、一部だけ重なる片は先の分だけ書く。先 (抜けがある) なら書かない |
| `commit(id)` | 全部そろっていれば SHA-256 を照合し、合えば種類の処理 (`received`) の答え、合わなければ `{"status" => "refused", "reason"}` (置かない、片のファイルも消す)。足りなければ `{"status" => "more", "pos"}`。同じ id の commit をもう一度聞かれたら同じ答え (答えが失われたとき) |
| `cancel(id)` | 捨てる (片のファイルと控えも) |

エラー (送り手には `RemoteError` の `remote_class` で届く):

| クラス | 送り手の扱い |
|---|---|
| `Asterism::Transfer::Refused` | 諦める (理由を返す)。種類・相手を受けない、大きさが空きに入らない、名前・大きさ・SHA-256 の形が違う、書けない |
| `Asterism::Transfer::Busy` | 別の相手のファイルを受けている。待って begin し直す |
| `Asterism::Transfer::Unknown` | その id を受け手が持っていない (受け手のアプリが起動し直した、期限で消えた)。すぐ begin し直す |

- 同時に 1 つだけ。別の相手の begin は、受けているものに 10 秒 (STALE_MS) 片が来ていなければ前のものを捨てて受ける。それまでは Busy (決定事項)。
- 片のファイル `/tmp/<name>.<kind>.part` と控え `/tmp/<name>.<kind>.xfer` (送り手・種類・名前・大きさ・SHA-256・meta、JSON 1 行) を begin で作る。commit で控えを消し、片のファイルは種類の処理が付け替える。
- 60 秒 (KEEP_MS、`keep_ms:` で変えられる) 片が来なければ片のファイルと控えを消す。受け手のアプリが終わるときは消さない (起動し直したら `resume_held` が控えを読んで、その時から 60 秒待つ)。端末が再起動したら `/tmp` ごと消える (最初から)。
- 受け手の空き: フックの `room` が数を返せば、begin で大きさと比べて断る。返さなければ (今の Family mruby。3 章) 書けなくなった所で断る。
- 種類ごとの決まりはフック 3 つ: `refused(kind, from, meta)`・`room`・`received(t)`。転送のアプリは `KINDS` と `receive.toml` (今までどおり) を `refused` に、checkpoint のイメージを置いて起動を頼む処理を `received` にした。`check`・`status` (checkpoint のもの) は転送のアプリの側に残した。

## 3. 送り手

`Asterism::Transfer::Sender.new(to, kind, path, name:, meta:, piece:, window:, timeout_ms:, tries:)` を作り、アプリの更新の度に `step`。待たない (1 回の `on_update` で全部を待つとネイティブ版の協調のスケジューラでほかのタスクが止まる、F5 の 6 章)。

- 作るときにファイル全体の SHA-256 を計算する (1 MiB で mbedTLS 3 ms、t0.md)。
- `window` 個までの片を投げておき、答えを送った順に受け取る。答えの位置がその片の終わりより前なら、そこから送り直す (残りの答えは捨てる。受け手では読み捨てか取らずになるので害が無い)。既定は 1 (今までと同じ 1 つずつ)。2 以上は T3 で受け手が決める形にする (t0.md の速さ)。
- 送り直しのために、ファイルを開き直して読み飛ばす (端末の `File` に seek が無い)。直近の片 (window + 2 個) は手元に持っていて、多くの送り直しはそこから出る。
- 失敗 (期限切れ・つながらない・Busy・そのほかの RemoteError) は、200 ms から倍々で 4 秒までの待ちのあと begin し直す (受け手が今の位置を返す)。進まないまま 8 回 (TRIES) 続けば諦める (待ちの合計は約 18 秒。これに各呼び出しの期限切れの待ちが足される。相手がいなければ Asterism はすぐ「nobody answers」を返す)。1 バイトでも進めば数え直す。Refused は諦める。Unknown はすぐ begin し直す。
- 終わり: `ok?` なら `answer` (commit の答え = 種類の答え)、でなければ `reason`。`stats` に呼び出しの数・片の数・送り直した回数・待った回数・begin の回数・続けた位置 (`resumed_at`)。
- 転送のアプリの `move_send` はこの Sender に置き換えた。commit の後の `status` を待つところ、遅れた写しを止める `move_cancel` は今までどおり。commit を投げた後に失敗したら (`committing?`) 相手で起動しているかもしれないので move_cancel を積む。

## 4. 試験 (ネイティブ版どうし、`rake regress:transfer`)

`tools/regress/transfer.rb` (`rake regress:transfer`、`ENGINE=mruby`、`ONLY=<場面>`)。試験のアプリ `/app/test/xfer_probe.app.rb` が転送のアプリと同じ Asterism::Transfer を使い、`<ノード>/xfer_probe/inbox` (種類 `probe`、`/tmp/<name>.probe` に置く) を出し、`/tmp/xfer_probe.job` の頼みで送る。A が 1 MiB のでたらめなバイト列を B へ送る。B は道具の中の中継 (`CutRelay`) を通ってルータにつなぐので、道具が B の接続を切れる。壊し方 (抜け・重なり・入れ替え) は送り手の `fault` (試験のアプリが上書き) で入れる。

| 場面 | 起こし方 | 確かめたこと |

| straight | 何もしない | B から取り出したファイルの SHA-256 が元と同じ |
| drop (1 割落とす) | 10 片に 1 つ (4 番目、14 番目、…) を送らず次の片を送る | 34 片が落ち、送り直しが 34 回、B が見た抜けが 34。抜けた片は B の位置から 1 回だけ送られる |
| twice (2 回送る) | 5 片に 1 つを 2 回 | B が読み捨てた片が 69 (2 回送った数と同じ) |
| swap (順の入れ替え) | 7 片に 1 つを次の片の後に | 入れ替えた 49 組がどれも B の位置から並び直った |
| cut (接続を 2 回切る) | A のログの 256 KB と 640 KB で B の接続を切り、1.5 秒つながせない | A は 276,480 と 663,552 から続けた。B のログの「goes on with probe cut at N」と同じ位置 (0 からではない)。1 回の切断から戻るのに約 4.5 秒 (中継の 1.5 秒 + B のつなぎ直し) |
| restart (受け手を止めて戻す) | 256 KB で B の試験のアプリを止め、起動し直す | 起動し直した B が控えから 374,784 バイトを持っていると読み、A はそこから続けた |
| mismatch (照合が合わない) | 送り手が違う SHA-256 を宣言 | 全部届くが置かれない (B に `/tmp/mismatch.probe` が無い)。A に理由 |
| kept (期限) | 256 KB で A の試験のアプリを止める | B は 3 秒 (この場面だけ keep_ms を 3 秒にした) で片のファイル (384,000 B) と控えを消した |

- 届いたものは全部、B の `/tmp/<name>.probe` を道具で取り出して SHA-256 を比べた (受け手の照合とは別に)。
- cut・restart・kept は送り手の歩みを 10 ms ごとに絞って (試験のアプリの `pace_ms`) 1 MiB を 4 秒ほどにし、壊すのが途中に来るようにした。絞らないと 1 MiB が 0.6 秒で届き、止める頃には終わっている。
- gem の側の試験 `rake test:transfer` (CRuby、Zenoh なし、呼び出しの代役で 14 件): 上の場面に加えて window 4、答えだけ失われる (commit の答えも)、空きに入らない、別の相手が Busy から STALE_MS 後に受けられる、plain Ruby の SHA-256 が Digest と同じ。
- 全部 mruby の構成でも同じに通る (上の 2 つ目)。
- 気づき (道具の作り):
  - 切断は、つないだ TCP を閉じるだけでは足りなかった。zenoh-pico は数 ms でつなぎ直すので、呼び出しと呼び出しの間で切ると送り手は何も気づかない (全部 mruby の構成で 1 回だけ「続けた」になって落ちた)。中継が 1.5 秒つながせないようにした。本番でも短い切断は送り手から見えない (見えなくてよい)。
  - 切断から戻るのに数秒かかるので、試験の keep_ms を 3 秒にしていた最初の形では、B が戻る前に片のファイルを消して 0 からやり直しになった。60 秒 (本番の値) に戻し、kept の場面だけ短くした。60 秒は TLS のつなぎ直し (Tab5 で 10〜20 秒) より長い。
  - 中継 (Ruby の TCPSocket) に TCP_NODELAY を付けないと 1 往復 22 ms になった (t0.md の 2 章)。

## 6. 捨てた案

- **mrblib に置く**: 全部の VM に入る (1 章)。
- **受け口の位置を聞く専用の呼び出し (`resume`・`where`)**: begin が「同じファイルなら今の位置」を返すので、begin し直すことが位置を聞くことになる。受け手のアプリが起動し直して id が変わっても同じ道で済む。
- **片ごとの CRC**: 決まったこと (片の破損は Zenoh の TCP / TLS が守る)。全体の SHA-256 だけ。
- **中継で片を落とす・入れ替える**: Zenoh の枠を読む必要がある。送り手の `fault` で起こした (受け手から見れば同じ)。切るのだけ中継で。
- **転送のアプリそのものに試験の種類を足す**: 試験のためだけの種類を配る受け口に入れたくない。試験のアプリが同じ部品を使う形にした。そのため「受け手の転送のアプリを止めて起動し直す」は、試験のアプリを止めて起動し直す形で確かめた (控えから続ける仕組みは同じ部品)。

## 7. ネイティブ版 ⇔ ESP32 (実機がつながったとき)

まだ流していない。手順:

1. 端末 (P4 / S3) に今のコミットの storage を入れる (`/usr/share/asterism/transfer/` と `/app/test/xfer_probe.app.rb` が要る。`rake setup` の後にビルド・flash。app_only では storage が更新されないので、Tab5 は `tab5_fs` で `/usr/share/asterism/transfer/*.rb`・`/app/test/xfer_probe.app.*`・`/usr/share/transfer/transfer.app.rb` を put してもよい)。
2. 端末の `/home/asterism/receive.toml` に `from = ["rg-xfer-a"]` を足し、`/home/xfer_probe.job` に `{"keep_ms": 3000, "recv_piece": 4096}` を置く。
3. 端末で試験のアプリを起動する (Tab5: `tab5_app` で `/app/test/xfer_probe.app.rb`。S3: Shell から)。シリアルのログ (`serial_start`) で `xfer_probe: ready as <ノード>` を待つ。
4. PC で `ruby tools/regress/transfer.rb --peer <端末のノード> --router tcp/<端末のつなぐルータ>:7447`。straight・drop・twice・swap・cut (A の接続を切る)・mismatch を流す。送り手の側で判定できる (commit で端末が SHA-256 を照合している)。`--bench` で呼び出しの上限と速さ。
5. restart・kept は手で: 送っている途中に `tab5_app` で端末の試験のアプリを止めて起動し直し、送り手のログの `went on from` が 0 でないこと。送り手 (A の試験のアプリ) を途中で止め、端末のログに `dropped ... no piece for 3000 ms` が出ること。
6. 逆向き (ESP32 が送り手): 端末の `/home/xfer_probe.job` に `{"to": "rg-xfer-a", "path": "/tmp/x.bin", "name": "x"}` (ファイルは `bench hash` の `make` で作る、t0.md)、A の試験のアプリを受け手として起動しておく。

- S3 では試験のアプリの VM が足りないかもしれない (転送のアプリが大きいプールを使う。試験のアプリの `.app.toml` に `large_memory = 1` を足す。S3 は大きいプールが 2 つ)。
- 転送のアプリが起動のときに読む Ruby が増えた (アプリ 18 KB + transfer.rb 27 KB。前はアプリ 20 KB)。S3 の大きいプール (1 MB) で compile が足りるかは実機で確かめる (F6 の S3 で「500 KB のプールでは足りなかった」記録がある)。ログの `transfer: start (N bytes of its pool used)` を見る。

## 8. 残件・親に決めてほしいこと

### 残件

- **gem の push と pin**: asterism `4a39108` を push してから fmruby-core を push する。pin の更新は fmruby-core の 498783ee に入っている (push の前に `rake asterism:setup` が公開リポジトリから取れることを確かめる)。
- ネイティブ版 ⇔ ESP32 (7 章)。ESP32 の SHA-256・CRC32・速さ (t0.md の 7 章)。
- S3 で転送のアプリが起動できるか (プールが 72 KB 増えた。t0.md の 6 章)。
- 受け手の空き: `/tmp` の空きを Ruby から知る手段が無い (C に `fmrb_tmpfs_usage` はあるが、アプリに出ていない)。今は `room` が nil で、begin では断らず、書けなくなった所で断る (Refused)。「空きを見て入らなければ begin で断る」(決定事項) には、`FmrbApp` に `/tmp` の使用量を返すメソッドを足す必要がある (main/ の C。今回の触ってよい範囲の外なので止めた)。決定事項の「固定の上限は設けない」に合わせて、前の 1 MiB の上限は外した。
- 種類 `file`・`receive.toml` の種類ごとの許可・送り手の口は T2。片の大きさと同時に送る片の数を受け手が決める形は T3 (Sender の `window:` は入れてあり、既定は 1)。

### 親に決めてほしいこと

1. `regress:transfer` を `regress:full` に入れるか。提案: 入れる (作るのはネイティブ版だけで regress:checkpoint と同じもの、2 構成で約 6 分。試験のアプリと道具だけで、sim も実機も要らない)。
2. `/tmp` の空きを返す C のメソッドを足すか (上の残件。足すなら T2 の前に。内蔵 RAM は増えない)。
3. ブラウザ版の SHA-256 (t0.md の 8 章の 1): C の実装を入れるか、送り手の計算を分けるか。T3 の数 MB の前に。
4. 送り手の再試行の上限 (8 回、待ちは 200 ms から倍々で 4 秒まで) と、片のファイルを残す時間 (60 秒)、別の相手を待たせる時間 (10 秒) は仮決め。
5. 「受け手の転送のアプリを止めて起動し直す」は試験のアプリで確かめた (6 章の最後)。転送のアプリそのもので確かめる必要があるか (転送のアプリには試験のために送らせる口が無い。T2 の送り手の口ができれば道具から頼める)。
