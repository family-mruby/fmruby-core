# T0: 調べる・測る (実機なしでできる分)

> 状態: 実装済・検収待ち | 更新: 2026-11-08 | 1 回の呼び出しで運べる文字列は 4,044 B まで (ネイティブ版 → ネイティブ版。4,048 B は断られずに答えが来ないまま期限切れ。ブラウザ版も 4,032 B 通り 4,064 B 通らない)。片 3,072 B・1 つずつで 1 MiB がネイティブ版どうし 0.55 秒、同時に 4〜8 片で 0.19〜0.21 秒 (往復が約 1.6 ms で、片を大きくするより同時に投げる方が効く)。ブラウザ版が受け手だと 3.6〜4.5 秒で、受け手の plain Ruby の SHA-256 (1 MiB 3.3 秒) で決まる。SHA-256 はネイティブ版の mbedTLS で 1 MiB 3 ms (CRC32 の 26 ms より速い)。転送のアプリは Asterism::Transfer を読む分プールが 72 KB 増えた (ネイティブ版 64 bit、GC の後)。抜け・重なり・入れ替え・切断・受け手の起動し直しを起こす試験の道具を作った (`rake regress:transfer`)。ESP32 の値は台本だけ用意した

T1 の作りは `t1.md`。数字は `rake regress:transfer BENCH=1` (ネイティブ版)、`BENCH=1 WEB=1` (ブラウザ版が受け手) で出る。

## 1. 1 回の呼び出しで運べる大きさ

`xfer_probe` の `size(bytes)` (文字列を受けて長さを返すだけ) に大きさを変えて 1 回ずつ投げた。期限 5 秒。

| 端末 | 通った最大 | 通らなかった最小 | 通らないときの様子 |
|---|---|---|---|
| ネイティブ版 → ネイティブ版 (同じ PC のルータ) | 4,044 B | 4,048 B | 答えが来ず期限切れ (5 秒)。エラーは返らない |
| ネイティブ版 → ブラウザ版 (ルータの ws/、ヘッドレスの Chromium) | 4,032 B | 4,064 B | 同じ (期限切れ)。間は測っていない |
| sim | 測っていない (4 章) | | |

- 上限は受け手 (と送り手) の zenoh-pico の `Z_FRAG_MAX_SIZE` (4,096。picoruby-asterism-zenoh の `zenoh_generic_config.h`、どのビルドも上書きしていない)。呼び出しの鍵 (`asterism/<ノード>/<アプリ>/<オブジェクト>/call/<呼び手>`)・メソッド名・MessagePack の枠を含めて 4 KB に入る必要がある。`chunk(id, pos, bytes)` は `size` より引数が 2 つ多いので、片の上限は 4,000 B 前後。
- **大きすぎる呼び出しは断られずに黙って落ちる** (送り手は期限まで待つ)。送り手は片をこの上限より小さく保つこと (受け手が begin で `piece` を返す形は T1 で入れた。上限そのものを受け手が知る手段は今は無い)。今の 3,072 B は余裕が約 970 B。
- 片 3,840 B (上限から鍵の分を引いた辺り) も 1 MiB を通して運べた (2 章)。

## 2. 片の大きさと同時に送る片の数 (ネイティブ版 ⇔ ネイティブ版)

1 MiB (でたらめなバイト列) を Asterism::Transfer の Sender で。`begin` + 片 + `commit`。受け手は B (中継を通る。中継は TCP_NODELAY)。単位は ms。

| 片 \ 同時に送る片の数 | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| 512 B (2,050 呼び出し) | 3,833 | 2,047 | 1,123 | 642 |
| 1,024 B (1,026) | 1,812 | 989 | 553 | 339 |
| 2,048 B (514) | 933 | 496 | 317 | 281 |
| 3,072 B (344) | 555 | 328 | 211 | 186 |
| 3,840 B (276) | 440 | 307 | 167 | 156 |

- 1 つずつ (今の転送のアプリ) では 1 回の往復が約 1.6〜1.9 ms で、時間はほぼ呼び出しの数で決まる。片 3,072 B で毎秒約 1.9 MB。
- 同時に 2・4・8 片を投げると、往復の待ちが重なって 1.7〜3 倍速い。片を 3,072 → 3,840 B にするより、同時に 2 片にする方が効く。T3 で「受け手が同時に受ける片の数を決める」の材料。
- ESP32 では受け手が片を書く速さ (PSRAM の tmpfs) と WiFi の往復で決まるはず。F5 の実測 (ネイティブ版 → ESP32 で 30 KB に 326〜488 ms、1 呼び出し 30〜40 ms) から、1 つずつでは毎秒 70〜100 KB 程度。同時に送る効き目は ESP32 で大きいと見ている (未測定、5 章)。

### 試験の道具で気づいたこと: Nagle

最初は 1 つずつで 1 MiB に 7.5 秒 (1 往復 22 ms) かかった。試験の道具が B とルータの間に置く中継 (Ruby の TCPSocket) が TCP_NODELAY を付けていなかったため (片の最後の切れ端が前の ACK を待つ)。中継に付けて 0.55 秒になった。zenoh-pico と zenohd は自分で付けている (`Z_FEATURE_TCP_NODELAY` 1) ので、本番の道には関係ない。間に何かを挟む道具 (将来の console の中継など) は同じことに気を付ける。

## 3. ブラウザ版

`rake regress:transfer BENCH=1 WEB=1`: 公開のブラウザ版のビルド (`wasm/build/dist`、gem 入り) を自前の開発サーバとヘッドレスの Linux の Chromium で開き、試験のアプリを受け手にして、ネイティブ版から送った。ルータは同じ PC の zenohd の ws/。

| 片 \ 同時に送る片の数 | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| 512 B | 9,925 | 5,415 | 4,834 | 4,937 |
| 1,024 B | 7,301 | 4,344 | 3,898 | 3,981 |
| 2,048 B | 4,962 | 3,822 | 3,781 | 3,690 |
| 3,072 B | 4,479 | 3,695 | 3,632 | 3,612 |
| 3,840 B | 4,230 | 3,698 | 3,534 | 3,674 |

(1 MiB、ms)

- 同時に 2 片以上では 3.5〜3.7 秒で頭打ち。受け手が片ごとに plain Ruby で SHA-256 を足していく時間 (1 MiB で 3.3 秒、5 章) で決まっている。1 つずつのときの往復は片 512 B で約 4.8 ms。
- checkpoint の移動 (23 KB) では、ブラウザ版との運ぶ時間が F5 の 26〜38 ms から 102〜120 ms に伸びた (`regress:checkpoint` の web の場面)。

## 4. sim

測っていない。sim の zenoh-pico はネイティブ版と同じ Linux の posix の部品・同じ `Z_FRAG_MAX_SIZE` なので、上限は同じはず。checkpoint の sim の場面 (`regress:checkpoint SIM=1`、23 KB を 3,072 B の片で) が新しい受け口で通ることは確かめた (t1.md)。測るなら、sim の中で試験のアプリを受け手として起動し (`sim_app` で `/app/test/xfer_probe.app.rb`、sim の `/home/asterism/receive.toml` に送り手のノード)、ネイティブ版の試験のアプリから `{"bench": "sizes", "to": "<sim のノード>"}`。

## 5. SHA-256 と CRC32 の費用

1 MiB のファイルを 4 KB ずつ読んで。

| 端末 | SHA-256 (使うもの) | SHA-256 (plain Ruby) | CRC32 (`CRC.crc32`) | 読むだけ |
|---|---|---|---|---|
| ネイティブ版 | 3 ms (mbedTLS) | 1,132 ms | 26 ms | 0〜1 ms |
| ブラウザ版 (ヘッドレスの Chromium) | — (mbedTLS が無い) | 3,253 ms | 17 ms | 9 ms |
| ESP32 (S3・P4) | 未測定 (台本は 7 章) | | | |

- ネイティブ版では mbedTLS の SHA-256 の方が CRC32 (picoruby-crc、表を使わない実装) より 9 倍速い。片ごとの CRC を省いて全体の SHA-256 だけにした決まり (決まったこと) は費用の面でも問題ない。
- ブラウザ版のビルドには picoruby-mbedtls が無い (ソケットの gem を入れないので一緒に入らない)。plain Ruby の SHA-256 (`data/transfer/sha256.rb`) を使う。checkpoint のイメージ (23 KB) で、ブラウザ版との運ぶ時間が F5 の 26〜38 ms から 102〜120 ms に伸びた (受け手は片ごと、送り手は始める前に全体を計算する)。数 MB を運ぶ T3 では重い (8 章)。

## 6. 転送のアプリのメモリ

| 何を | ネイティブ版 (64 bit) | ブラウザ版 (32 bit) |
|---|---|---|
| アプリの compile の後 (`VM pool after compile`)、今 / 前 | 574,472 B / 587,704 B | — |
| 起動の後 (`transfer: start`、Asterism::Transfer を読んだ後)、今 / 前 | 732,824 B / 601,048 B | 538,392 B / — |
| 起動の後に GC.start してから、今 / 前 | 671,960 B / 599,728 B (+72,232 B) | — |

- 前は受け口の全部がアプリの中にあった。今はアプリが `require` で transfer.rb (27 KB) を読む。前より残る分が 72 KB 多い (64 bit)。読んだ直後は compile の残りがあって 131 KB 多い。前の数字は、前の転送のアプリに同じログを足した写しを同じネイティブ版で起動し直して測った (コミットしていない)。
- 受け手だけの端末は送り手の部品 (Sender) を使わない。ファイルを受け口と送り手に分けて、要る方だけ読む形にすれば減らせる (T3 で、S3 で足りないと分かったら)。
- ESP32 の S3 は「大きいプール (1 MB) で 20 KB のアプリの compile がやっと」(transfer.app.toml の注、F6)。今は読む Ruby が 45 KB (アプリ 18 KB + transfer.rb 27 KB) になったので、S3 で起動できるかは実機で確かめる (t1.md 7 章)。足りなければ transfer.rb を前もって bytecode (.mrb) にして読む形を考える。

## 7. ESP32 で測る手順 (実機がつながったとき)

試験のアプリ (`/app/test/xfer_probe.app.rb`) は端末でも同じに動く。頼みは `/home/xfer_probe.job` (`/tmp` に置けないとき)。結果はシリアルのログの `xfer_probe:` の行。

1. SHA-256・CRC32・plain Ruby の SHA-256 (端末だけで済む):
   `/home/xfer_probe.job` に `{"bench": "hash", "path": "/tmp/xfer_hash.bin", "make": 262144}` (S3 の `/tmp` は 448 KB なので 256 KB。P4 は 1048576 でよい)。Tab5 は `tab5_fs` で put、`tab5_app` で起動。S3 は Shell から (`/home` への書き込みは 1 回だけにする)。`xfer_probe: bench hash sha256 mbedtls N bytes M ms` などが出る。
2. 呼び出しの上限・速さ (ネイティブ版 → ESP32): 端末の `/home/xfer_probe.job` を `{"recv_piece": 4096}` にして試験のアプリを起動し、PC で
   `ruby tools/regress/transfer.rb --bench --peer <端末のノード> --router tcp/<ルータ>:7447`。
   (端末の `receive.toml` に `rg-xfer-a` を足す。速さの表は 2 章と同じ形で出る)
3. 逆向き (ESP32 → ネイティブ版) の速さ: 端末の頼みを `{"bench": "speed", "to": "rg-xfer-a", "path": "/tmp/xfer_hash.bin", "pieces": [1024, 3072], "windows": [1, 2, 4]}` にし、PC 側は `transfer.rb` の A の試験のアプリを受け手として起動しておく (手で: `fmrb_native.rb app spawn /app/test/xfer_probe.app.rb`)。
4. 転送のアプリのメモリ: 起動ログの `[Transfer] VM pool after compile` と `transfer: start (N bytes of its pool used)`、周期ダンプの `fmrb_app:`。

## 8. 方針への影響

- 方針を揺るがす値は無かった (instruction の例の「SHA-256 がネイティブ版で異常に重い」「呼び出しの上限が片より小さい」のどちらでもない)。呼び出しの上限 (約 4 KB) は片 (3 KB) より大きく、SHA-256 はネイティブ版で軽い。
- 気になる点 (親に):
  1. **ブラウザ版の SHA-256 が plain Ruby**。1 MiB で 3.3 秒、受け手の速さがこれで決まる (3 章)。送り手は始める前に全体を一度に計算するので、数 MB では秒の単位で止まる。ブラウザ版のビルドに SHA-256 の C を入れる (picoruby-mbedtls だけを足す、または小さな C の gem) か、送り手の計算を分けて少しずつにするか。T3 で決める。
  2. **大きすぎる呼び出しは黙って落ちる**。片の上限を送り手と受け手で取り違えると、期限切れ → 送り直しを繰り返して諦める。受け手が begin で返す `piece` は 4,000 B を超えない値にすること (T3 で受け手が片を決めるときの決まりに書く)。
  3. **転送のアプリのプールが 72 KB 増えた** (64 bit)。S3 の大きいプールで起動できるかは実機で確かめる (6 章)。
