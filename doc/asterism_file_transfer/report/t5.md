# T5: アプリの移動 (checkpoint) を新しい受け口の作りに揃える

> 状態: 実装済・検収待ち | 更新: 2026-11-08 | アプリの移動はもう T1〜T3b の受け口の上にあった (送り手は `Asterism::Transfer::Sender`、受け手は `TransferInbox`: 片の大きさと同時に送る数は受け手が決め (片 3,840 B・4 つ)、全体の SHA-256 を照合し、`[checkpoint]` (古い書き方も) で許し、`/tmp` の空きを見て `begin` で断る)。残っていたのは「止めておく時間が切れた後も送り続ける」古い流れだけで、これを取りやめに揃えた: カーネルが転送のアプリに `move_stop` を送り、まだ確定していなければ Sender#cancel で送るのをやめ (受け手は持っていた分を捨てる)、確定済みなら今までどおり起動した写しを止める。`regress:checkpoint` に途中でやめる方を必ず起こす場面 asterism given up を足した。速さは T3b と同じ (ネイティブ版どうし運ぶ 23〜26 ms)。gem・main/ の C は変えていない

指示は `../instruction_t5.md`。T4 までは `t0.md`〜`t4.md`、移動の作りは `doc/checkpoint/report/f5.md`。

## 1. 調べたこと (載せ替えの残り)

T1 で転送のアプリの `move_send` は Sender に置き換わっており、T2・T3 で受け手の側も揃っていた。範囲の項目ごとに今の作りを見た:

| 項目 | 今の作り | T5 で |
|---|---|---|
| 片の大きさ・同時に送る数を受け手が決める (T3) | `TransferInbox#window` (checkpoint は最大 4)、片は呼び出しの鍵の長さから。送り手 `start_send` は `piece:`・`window:` を渡さず (上限は既定 3,840 B・16)、受け手に従う。ログ `takes pieces of 3840 bytes, 4 at a time` | そのまま |
| 全体の SHA-256 (T1) | Sender が作るときに計算し `begin` で宣言、受け手が `commit` で照合 | そのまま |
| 種類ごとの許可 (T2) | `refused` が `[checkpoint] from` と古い上の `from` の和を読む | そのまま |
| 空きを見て `begin` で断る (T2) | `room` が checkpoint なら `FmrbApp.free_bytes("/tmp/")` | そのまま |
| 片の置き場所 | checkpoint は `/tmp/<名前>.checkpoint.part` (再起動で最初から、の決定どおり) | そのまま |
| 期限 | 受け手: 60 秒 (KEEP_MS) で片と控えを消す、10 秒 (STALE_MS) で別の相手に譲る。送り手: 待ちを倍にしながら 8 回 | そのまま |
| **取りやめ** | 止めておく時間 (hold) が切れてアプリがこちらで続いた後も、転送のアプリは送り続け (失敗の再試行も含めて最大 20 秒ほど)、相手で起動したらその写しを止めていた (F5 の 5 章の「返事が遅れたとき」) | **揃えた** (2 章) |

- 古い経路 (1 片ずつ・照合なし・1 MiB の上限・`pos == got` だけ受ける片) は、fmruby-core の中にはもう無い (T1 で消えている)。`grep` で `3072`・`1 MiB` を探して、残っているのは試験の道具の T1 の場面の固定値 (`T1_SENDER`、数えた値の前提) と速さの測りの候補だけ。
- カーネルの送り手: カーネル (標準の構成では Spinel のプログラム) は Asterism の接続を持てないので、運ぶのは今までどおり転送のアプリ。転送のアプリの中で、アプリの移動 (`move_send`) とファイルの送信 (`file_send`、FmrbTransfer の頼み) は同じ `Asterism::Transfer::Sender` を使っている。カーネルが FmrbTransfer (Pub/Sub の口) を使う形にはしなかった: FmrbTransfer は「ファイルを種類 file で /home/inbox/ へ」の口で、移動の前後の段取り (check・hold・status・写しを止める) を持たない。両方とも同じ Sender の上なので、決まりの食い違いは起きない。

## 2. 作ったもの

| どこ | 何 |
|---|---|
| `main/prebuild_scripts/kernel/fmrb_kernel.rb` | `move_stop_send`: hold が切れて移すアプリが続いたとき (`note_checkpoint_continued` で段が MV_SEND)、と MV_SEND の期限切れ (`tick_move`) に、転送のアプリへ `{"cmd" => "move_stop", "to"}`。`start_move` の説明に 5 の段の作り (Sender、受け手が決める片と数、SHA-256、move_stop・move_cancel) |
| `flash/usr/share/transfer/transfer.app.rb` | `move_stop` は列に積まずにすぐ扱う (`stop_move`): まだ始めていない `move_send` は列から外し、`move_sent` {ok: false} を返す。送っている最中なら、`begin` の答えが来ていて (受け手が id を知っている) まだ `commit` を投げていなければ Sender#cancel (受け手は持っていた片と控えを消す) → `move_sent` {ok: false, "the hold ran out"}。`begin` の答えがまだなら印を付け、答えが来た所で取りやめる (受け手が id を知らないまま片のファイルを 60 秒残さないため)。`commit` を投げた後と `status` を待っている間は何もしない (相手で起動するかもしれず、今までどおり起動したら `move_cancel` で止める)。頭の説明に `move_stop` |
| `tools/regress/checkpoint_asterism.rb` | asterism late を 2 通りの結末のどちらでも通す形に (`LATE_THERE`)。場面 asterism given up を足した (3 章) |
| `tools/regress/checkpoint_web.rb` | web late も同じく 2 通り |
| `tools/regress/checkpoint.rb` | B の home を覚える (`@home_b`。given up が B の `receive.toml` を一時に書き足す) |
| `doc/regression/usage.md` | asterism late・given up・web late の説明 |

- 利用者から見た動き (止めておく時間が切れたらこちらで続き、相手に写しは残らない、D15) は変わらない。変わるのは、まだ届き終わっていないイメージが相手で起動されずに捨てられること (前は届け終えて起動してから止めた)。
- `move_stop` が来た時に、受け手は既に何片か持っていることがある: Sender は `begin` の答えを受けたその歩みで片を投げる (window 個) ので、取りやめはその後になる。given up の場面では B が 15,360 B (4 片) を持った所で捨てた。受け手が捨てるので害は無い。gem を変えれば (begin の後に止まる口) 防げるが、要らないと見た。
- asterism gem は変えていない。pin (`lib/add/ASTERISM_PIN` の `c221b08`) も動かしていない: 0.12.0 (`e8bf867`) との差は CRuby だけのもの (`FileInbox`・`Endpoint`、片をバイナリで書く) で、`data/transfer/` は同じ。
- main/ の C・sdkconfig は変えていない。カーネルの Ruby は Spinel で C になる (ESP32 では flash) ので `regress:size` を流した (4 章)。

## 3. 試験の場面

- asterism late (`--hold 1`) は、ネイティブ版どうしでは 23 KB が数十 ms で届くので、カーネルが hold の切れに気づく頃 (次の tick) にはもう確定している。今回の 3 回 (標準・全部 mruby・ブラウザ版) とも「確定済み → 起動した写しを止めた」の方だった。どちらの結末でも通るようにして、要約に結末を出す (`the copy there stopped` / `the image dropped on its way`)。
- 途中でやめる方は、時間の運では起こらないので場面 **asterism given up** を足した: 道具 (CRuby の Asterism、ノード `rg-ckpt-pc`) が B の受け口に種類 `file` の `begin` だけを投げて片を送らず、B を 10 秒 (STALE_MS) 使用中にする。`--hold 1500` で移すと、A の送り手は `busy` で待ちを倍にしながら `begin` し直し (200・400・800・1,600・3,200・4,000 ms)、その間に hold が切れて A でアプリが続き、`move_stop` が来る。10 秒の後に B が A の `begin` を受けた所で取りやめ、B はイメージを捨て (`checkpoint ckpt_counter from rg-ckpt-a dropped at 15360 of 23072 bytes: cancelled by rg-ckpt-a`)、写しは起動しない。場面の間だけ B の `receive.toml` に `[file] from = ["rg-ckpt-pc"]` を足し、終わったら戻す。1 場面 14 秒ほど。
- sim・実機 (`BOARD=`) の場面には late が無いので触っていない。

## 5. 速さ (アプリの移動、23 KB のイメージ)

| いつ | ネイティブ版どうし: 運ぶ / 止めている時間 | ブラウザ版へ運ぶ / 止めている | sim との asterism calls (聞く + 運ぶ + 起動) |
|---|---|---|---|
| F5 (前の受け口、1 片ずつ・照合なし) | 22〜35 ms / 56〜66 ms | 26〜38 ms / 60〜79 ms | 200〜262 ms |
| T1 (Sender、1 つずつ、ブラウザ版は plain Ruby の SHA-256) | 32〜39 ms / 55〜62 ms | 102〜120 ms | 228〜249 ms |
| T3 (受け手が決める片 3,840 B × 4) | 20〜23 ms / 42〜45 ms | 39 ms | - |
| T3b | 23〜25 ms / 48〜49 ms | - | - |
| **T5** (2 回の通し) | **23〜26 ms / 46〜49 ms** (移す全体 59〜72 ms) | **39〜42 ms / 63〜64 ms** (戻り 25〜29 ms / 48〜54 ms) | **191〜239 ms** |

- 運ぶ速さは T3b から変わらない (T5 は運ぶ所を変えていない)。T1 で SHA-256 と送り手の分だけ遅くなったものは、T3 の片と同時に送る数で F5 と同じかそれより速く戻っている。
- 取りやめの速さ: given up の場面で、B が `begin` を受けてから A が取りやめて B が捨てるまで 5 ms (ログの時刻)。

## 6. ESP32 (実機がつながったとき)

まだ流していない。手順:

1. この木のファームを焼く (`rake build:esp32`、P4 は NARYAv4/Tab5、S3 は NARYAv3)。カーネルの Ruby を変えたので **app だけでなく storage も**新しくする (転送のアプリ `/usr/share/transfer/transfer.app.rb` が要る。Tab5 は `tab5_fs` で put してもよい)。fmrb の MCP の `serial_start` でシリアルを開いておく。
2. `rake regress:checkpoint BOARD=<端末>` (ネイティブ版 ⇔ 実機の Asterism の移動、F6 の場面)。ログで、転送のアプリが `takes pieces of N bytes, W at a time` (受け手の決めた片と数) を出し、`sha256 matches` で受けていること。
3. 取りやめ (実機が受け手): ネイティブ版から実機へ `ruby tools/fmrb_native.rb app move <pid> --node <実機のノード> --hold 1` を数回。実機では WiFi の往復で運ぶのに数百 ms かかるので、途中でやめる方 (ネイティブ版のログ `given up at N of M bytes (the hold ran out)`、実機のログ `dropped at ... cancelled by rg-ckpt-a`) が出るはず。実機の `ps` に写しが無いこと。
4. 取りやめ (実機が送り手): 実機のアプリを `POST /app/move` で `hold` 1 ms にしてネイティブ版へ。実機のログに `given up at` か `stopping it there` のどちらかが出て、ネイティブ版に写しが残らないこと。
5. S3 は転送のアプリの起動 (`transfer: start (N bytes of its pool used)`) と、`/tmp` の空きで断る (`begin`) ことを見る (T3 の手順のとおり)。

## 7. 残件・親に決めてほしいこと

### 残件

- ESP32 (6 章)。
- asterism gem の `Transfer::PIECE` (3,072、「片を名乗らない古い受け手のための値」と説明されている) は、どこからも使われていない (`begun` は受け手が名乗らなければ自分の上限を使う)。消すなら gem の次の版の Unreleased で。今回は gem に触らない範囲なので残した。

### 親に決めてほしいこと

1. **公開済みの 3.0.0 の端末との移動**: 3.0.0 (2026-11-07) の端末は F5 の受け口 (SHA-256 の照合なし、`window`・`pos` を返さない) を持つ。コードを読んだ見立てでは (流していない)、今の送り手から 3.0.0 の端末へ移すと、受け手は `sha256` を読み捨て、片 3,072 B・1 つずつで届き、照合なしで起動する (動くが照合されない)。逆向き (3.0.0 の端末から今の端末へ) は `begin` が「sha256 is not 64 hex digits」で断られる。送り手で古い受け手を断る (`begin` の答えに `pos` が無ければ諦める) と「照合なしの古い経路」は消えるが、3.0.0 の端末へは移せなくなる (利用者から見た動きが変わる) ので、選ばずに止めた。提案: 次のリリースで全部の端末が揃うので、今のまま (古い受け手には従う) にして、リリースの案内に「3.0.0 とそれより後の端末の間では移動の照合が片側だけ」と書く。
2. asterism late の場面は、ネイティブ版どうしでは「確定済み → 写しを止める」の方にしかならない (3 章)。途中でやめる方は given up で必ず確かめているので、late は結末を問わない形にした。これでよいか。
