## 2. console: Members の行で選ぶ

- 行の Edit に欄「Receives files from」。種類ごとに 2 つ: 「Files (to /home/inbox)」(種類 file) と「Apps moved here (checkpoint)」。
  - 候補は台帳の全部の行のノード (行が代わりに話すノード) と console (`ASTERISM_CONSOLE_NODE`、既定 `console`) のチェックボックス。client の行は自分のノードを候補から外す (家のルータの行は後ろのノードどうしで送れるので外さない)。
  - その下に「Patterns and other nodes」(1 行に 1 つ、`fmruby-*`、`*` は全員)。英数字と `.` `_` `-` `*` だけ、64 行まで (端末の側の決まりと同じ)。
- 行のページ: 「Receives files from」「Receives apps (checkpoint) from」(選んでいなければ「not chosen (only what its receive.toml has by hand)」、選んで空にしたら「nobody (an empty list is sent)」)、「The list on its machines」(ノードごとに「has this list (since ...)」・「not delivered: <端末の理由>」・「not sent yet」)。表「What its marks and lists for files allow」に ACL に入る行。Members の一覧の列「Files with the console」に `takes from members`。
- T4b の 2 つの印 (「May send files to the console」「Receives files from the console」) はそのまま。
- 表の列: `receive_files_from`・`receive_checkpoints_from` (行の一覧)、`receivers_changed_at` (一覧が変わった時刻。端末へ `at` として渡り、これがある行を「管理している行」とする)、`receivers_delivered` (bridge が各ノードに渡せたか、JSON)。migration は列を足すだけで中身は空 (選ぶまで何も配らない・ACL も変わらない)。

### 選んだ内容が作る ACL の行 (Apply)

受け手の行 R の一覧 (2 種類の和) が、ACL に入っている行 S のノード s を名指しか型で含むとき、R のノード r ごとに (r ≠ s):

| 誰の規則 | 規則 id | 何 | 鍵 |
|---|---|---|---|
| 送り手の行 S | `<S>__sends_files_ask` | query・ingress | `asterism/<r>/transfer/inbox/call/<s>` |
| 送り手の行 S | `<S>__sends_files_answer` | reply・egress (T4b の教訓: 答えを呼び手に通す) | 同じ |
| 受け手の行 R (一覧を一度でも選んだ行) | `<R>__receives_files_rw` | 全部・両方向 | `asterism/<r>/transfer`・`asterism/<r>/transfer/**` |

- 2 つの種類は同じ受け口なので ACL では分けない (分けるのは端末)。
- 受け手の rw は一覧を空にしても残す (空の一覧を端末に届けるため。行の `receivers_changed_at` で決まる)。
- 型 `*`・`fmruby-*` は Apply の時の台帳のノードに当てて行を作る (ブラウザ版の `wasm-*` は台帳の行ではないので作らない)。
- 試験 (`AclEvaluator` で zenohd の判断を再現): 選んだ名前でだけ呼べる、選んでいない受け口は呼べない、無効・証明書の無い行は何もしない、空の一覧でも受け手の鍵は残る、家のルータの後ろのノードどうし、`*`。

## 3. 配る道 (bridge → 端末)

- `Bridge::Receivers` (`lib/bridge/receivers.rb`、bridge の本体の周期で `sync`、呼び出しは専用のスレッドで 1 つずつ、待ち 10 秒)。
- 相手: 有効で一覧を選んだことのある行 (`RelayPeer.managed`) の、今ネットワークにいるノードの転送のアプリ (`<node>/transfer`)。
- 送るもの: `<node>/transfer/inbox` の `policy_set({"file" => [...], "checkpoint" => [...], "at" => "<一覧が変わった時刻 (UTC ISO 8601)>"})`。呼び手は bridge の object layer の接続 (ノード `console`)。
- いつ: 一覧が変わった (中身と時刻の digest が前に渡したものと違う)、ノードの転送のアプリが現れた (いったん消えて戻ったときも)、渡せていれば 10 分ごと、失敗したら 30 秒後。
- 結果は行の `receivers_delivered` (渡せた digest と時刻、断られた理由) とログの 1 行 (`bridge: receivers: <node> has the list of <row> (written there)`、`... not delivered: <理由>`。同じことは繰り返し言わない)。
- `ASTERISM_TRANSFERS=0` で送受といっしょに外れる。

### 端末が「console から来た」と確かめる方法

- 転送のアプリは `policy_set` を `caller: :from` で出す (今までの `begin` などと同じ)。呼び手のノード ID が `console` (端末の `/home/asterism/config.toml` の `console = "..."`、無ければ `console`) でなければ断る (`<node> takes the senders' list from console only, not <from>`)。
- **さらに、端末の接続が証明書つき (`tls/` のルータ) のときだけ受ける**。`tls/` のルータには証明書が要り (設定が無ければ接続しない)、クラウドのルータの ACL が呼び手のノード ID (鍵の最後の chunk) と証明書の名前を結ぶ (台帳の ask の行は自分の名前でしか呼べない)。console を名乗れるのは console の証明書だけになる。
- **証明書なしの接続** (家のルータの `tcp/`、`peer`・`listen` の P2P、ブラウザ版の `ws/`) では、誰でも `console` を名乗れるので受けない: `<node> takes no list from console over a connection without certificates (its router is not tls/)`。console の行のページにこの理由が出る。その端末は手で書いた分 (と、前に `tls/` で受けて書いてあった写し) で受ける。これは決定の「自動で受け入れる」を証明書つきの接続に限る安全の線で、受け入れ方の仕様は変えていない。
- 残る前提: 端末のつなぐ `tls/` のルータ自身が、証明書なしの相手からの呼び出しを通さないこと (クラウドのルータは mTLS だけを受けるので満たす。`tls/` で受けつつ別に `tcp/` も受ける自前のルータに証明書でつなぐ構成は、ルータの側の設定の問題として残る)。

## 4. 端末 (fmruby-core)

### receive.toml の形

```toml
# 手で書いた分 (T2 の書き方そのまま。この上は転送のアプリが触らない)
[file]
from = ["pc-desk"]

# ---- managed by the console (below this line; edit above it) ----
[managed]
by = "console"
at = "2026-11-08T15:40:24Z"

[managed.file]
from = ["fmruby-t6b", "fmruby-*"]

[managed.checkpoint]
from = []
```

- `FmrbReceiveConf` (`/usr/share/transfer/receive_conf.rb`): 印の行 (`# ---- managed by the console`) で 2 つに分けて**別々に** TOML として読む (手書きの側に TOML でない行があっても console の写しは生きる。逆も)。印より下は転送のアプリが書く。
- 判断: 種類ごとに「手書きの一覧」と「console の一覧」の和。どちらも無い (表が無い) 種類は受けない (T2 のまま)。一覧の項目はノード ID と型 (`*` は任意の文字の並び。`*` 1 つは全員)。手書きの側も型が使えるようになった。
- 断りの文言: 手書きだけのときは今までどおり (`takes no file from X (file from in /home/asterism/receive.toml)`)。console の写しがあるときは `takes no file from X (not in receive.toml, by hand or from console)` (送り手の Shell に出るのは 110 バイトほどなので短くした)。表がどちらにも無いときは `takes no file (no [file] in /home/asterism/receive.toml, nor from the console)`。
- 書くのは中身が変わったときだけ: 書くはずの印より下の文字列が今のものと同じなら書かない (`at` は console で一覧が変わった時刻なので、10 分ごとに配られても同じ)。書くときは `/home/asterism/.receive.toml.new` に書いて置き換える (手書きの分はそのまま前に付く)。
- 受け付ける値の決まり: 項目は英数字と `.` `_` `-` `*`、64 バイトまで、64 項目まで。`at` は数字・`T` `Z` `:` `+` `-` `.` で 40 バイトまで。違えば断る (TOML に書けない値を入れない)。
- 期限は無い: console に届かない間 (P2P・console が止まっている・端末の再起動の後も) 最後に書いた写しで動く。

### 転送のアプリを起動する条件 (カーネル)

- 今まで: `/home/asterism/receive.toml` があれば起動時に起動。
- T6: それに加えて、`/home/asterism/` に credentials の `.tar` があれば起動時に起動 (`asterism_credentials?`、Spinel のカーネルの `Dir.open`)。決定の「Members にいる端末は自動で受け入れる (端末側で opt-in を書かない)」のため: receive.toml の無い端末にも一覧が届くように。ESP32 では起動時に TLS の接続が 1 つ増える (8 章、親に決めてほしいこと 2)。

## 6. 手元の通し (2026-11-09)

### 何がつなげなかったか

指示の通し (zenohd の mTLS と ACL、console、ネイティブ版の端末 2 つ) は、そのままでは組めなかった: **ネイティブ版は `tls/` につなげない** (起動の時に転送のアプリが `connect: TLS is not built in on this platform (Z_FEATURE_LINK_TLS)`)。picoruby-asterism-zenoh は TLS の接続を ESP-IDF の Mbed TLS でだけ作り (`zenoh_generic_config.h`)、ネイティブ版 (ホストに Mbed TLS が無い) と sim (ESP-IDF の linux では zenoh の port を作らない) には無い。安全の線 (証明書つきの接続のときだけ受ける) を守ると、ホストの端末は console の一覧を受けられない。ネイティブ版に TLS を足すのはビルドと .deb の依存を変える別の仕事なので、ここではしていない (8 章 1)。

そこで、**ネイティブ版の端末が実際につなぐ形 (家のルータの後ろ)** で通した。console から写しが届くところ (書かれる・digest が合う) は ESP32 の実機が要る。

### 組んだもの

- 使い捨ての CA (console の `Relay::CertAuthority`) で、クラウドのルータ `zenohd-cloud`・`console`・家のルータ `home-t6` の証明書。
- console: 作業用の写し (DB は空から)。台帳に `console` (rw `asterism/**`) と `home-t6` (router、`fmruby-t6a`・`t6b`・`t6c` の 3 つを代わりに話す) を証明書の行つきで。puma と bridge (console の証明書で `tls/`)。
- クラウドの zenohd 1.10.1 (docker): 写しの台帳から作った `cloud.json5` (mTLS、ACL 有効)。家の zenohd: `tcp/` で待ち、`home-t6` の証明書でクラウドへ mTLS。
- ネイティブ版 3 つ (標準の構成): 家のルータへ `tcp/`、`/home/asterism/` に各自の credentials の `.tar` (receive.toml は置かない)。

### 結果

1. **起動の条件**: receive.toml の無い 3 つとも、`.tar` があるので起動時に転送のアプリが起動して接続した (`spx: Transfer app started (pid=4)`、`transfer: fmruby-t6a/transfer connected (tcp/127.0.0.1:17447, 14 ms)`)。
2. **console で選ぶ**: ヘッドレスの Chromium (console の `script/headless/run`) で `home-t6` の行の Edit を開き、Files の `fmruby-t6b` に印を付けて Save。行のページ: 「Receives files from fmruby-t6b」「Receives apps (checkpoint) from nobody (an empty list is sent)」、ACL の表に `receives_files` の rw (3 ノード分) と `sends_files` の ask (`asterism/fmruby-t6a/transfer/inbox/call/fmruby-t6b`・`asterism/fmruby-t6c/transfer/inbox/call/fmruby-t6b`)。
3. **Apply** (写しの台帳から `cloud.json5` を作り直してクラウドの zenohd を起動し直す。Apply のボタンの代わり): 規則 `home_t6__receives_files_rw`・`home_t6__sends_files_ask`・`home_t6__sends_files_answer` が入った。Save だけの間 (Apply の前) は、家のルータの後ろの転送のアプリがクラウドに見えず、配られなかった。
4. **配る → 断られる**: Apply の 1 秒後、bridge が 3 つに `policy_set` を呼び、3 つとも断った。bridge のログ `receivers: fmruby-t6a: not delivered: fmruby-t6a takes no list from console over a connection without certificates (its router is not tls/)` (t6b・t6c も)。行のページの「The list on its machines」に同じ理由が 3 行。端末の receive.toml は作られない (書かない)。
5. **手元の写しで判断**: t6a の receive.toml に、転送のアプリが書くのと同じ形の印より下 (`[managed.file] from = ["fmruby-t6b"]`、`at` は console の行の時刻) と、手書きの分 (`[checkpoint] from = []` だけ、file の表は無し) を置いた。
   - t6a の Shell の `asend -l`: `file: fmruby-t6b from console`、`checkpoint: (none) by hand / (none) from console`、`managed by console, changed there at 2026-11-08T15:40:24Z`。
   - t6b の Shell で `asend fmruby-t6a /home/hello_b.txt` → t6a の `/home/inbox/hello_b.txt` (`placed ... from fmruby-t6b`)。
   - t6c の Shell で `asend fmruby-t6a /home/hello_c.txt` → `not sent (fmruby-t6a: fmruby-t6a takes no file from fmruby-t6c (...))`、t6a に何も置かれない。
   - Shell に出る断りの文言が長すぎて途中で切れていた (`by hand or from )`) ので、console の写しのあるときの文言を短くした (4 章)。
6. **console を止めても同じ**: bridge を止め、t6a を再起動 (down → up)。t6b からもう一度送ると `hello_b(1).txt` が置かれ、t6c は `takes no file from fmruby-t6c (not in receive.toml, by hand or from console)` で断られた。receive.toml の更新時刻は 5 の時のまま。
7. **書く口を端末の上で**: console からは届けられないので、t6a の Shell の irb で `FmrbReceiveConf.write_managed("console", at, l)` (転送のアプリの `policy_set` が確かめた後に呼ぶもの) を 2 回呼んだ。1 回目 `true` (印より下が `["fmruby-t6b", "fmruby-t6c"]` と新しい `at` に置き換わり、手書きの分はそのまま)、2 回目 `false` (同じ一覧は書かない。ファイルの更新時刻が変わらないことを確かめた)。続けて t6c から送ると置かれた (毎回読むので、書いた時から効く)。
8. 起動したものは全部止めた (ネイティブ版 3 つ、zenohd の container 2 つと docker network、puma、bridge)。`/tmp/t6a` などの run のディレクトリは消した。

撮った画面とログ (検収用、リポジトリには入れていない): scratchpad の `e2e/` (`t6_edit.png` 行の Edit、`t6_show.png` 保存の後、`t6_show2.png` 断りの理由、`t6a_list.png` asend -l、`t6b_send.png`・`t6c_send.png`・`t6c_send2.png` Shell、`t6a_irb.png`、`logs/`、`bridge.log`)。

## 8. 気づき・親に決めてほしいこと

### 親に決めてほしいこと

1. **ホストの端末 (ネイティブ版・sim・ブラウザ版) は console の一覧を受けられない**。安全の線 (証明書つきの接続のときだけ) と、今のビルドにホストの TLS の接続が無いことの組み合わせ。選択肢:
   - (a) 今のまま: 写しを受けるのは ESP32 の端末だけ。ホストの端末は手書きで受ける (行のページに断りの理由が出るので、管理者には分かる)。
   - (b) ネイティブ版に TLS の接続を足す (ホストの Mbed TLS を .deb の依存に、picoruby-asterism-zenoh の TLS をネイティブでも作る)。足せば、ネイティブ版が自分の証明書でクラウドのルータへ直に `tls/` でつなぎ、写しを受けられる。別の仕事として計画が要る。
   - ESP32 の実機での通し (console で選ぶ → 実機の receive.toml に書かれる → 実機どうしで送る) はまだしていない (実機が要る)。手順は 6 章と同じで、端末は `/home/asterism/` に `.tar`、config.toml の router をクラウドの `tls/`。
2. **`.tar` のある端末は起動時に転送のアプリを起こす** (決定の「端末側で opt-in を書かない」のため)。ESP32 では起動時にアプリ 1 つと TLS の接続 1 つ (内蔵 RAM を使う) が増える。ビルドの大きさ (regress:size) は変わらないが、動いている時の内蔵 RAM は増える。ESP32 の実機で起動の M1 の行と空きを見てから決めたい。代わりに「receive.toml があるときだけ (今まで)」に戻すと、写しを受けたい端末は空の receive.toml を置く必要がある (opt-in)。
3. **console の行の一覧に `console` も出す**: T4b の「console から受ける」の端末の側の鍵 (`[file] from = ["console"]`) は、一覧で `console` に印を付けても満たせる。自動で入れることはしていない (T4 の決定「二重の鍵」をそのまま)。自動で入れるか。
4. 一覧は行ごと (家のルータの行なら後ろのノード全部に同じ一覧)。ノードごとに分けたいなら行を分ける (T4b の印と同じ考え)。
5. 受け手の行の transfer の rw は、一覧を一度でも選んだら空にしても残す (空の一覧を端末に届けるため)。行の一覧を空にした後も、その端末の transfer の鍵は ACL に残る。
6. 配る間隔 (10 分ごと・失敗の後 30 秒・呼び出しの待ち 10 秒) は仮決め。

### 気づき

- Save の後 Apply の前は、受け手の rw が ACL に無いので、ルータの ACL に入っていない端末の転送のアプリにはそもそも届かない (6 章の 3)。行のページは「not sent yet」のまま。Apply の後、端末が現れた時に配られる。
- 型 (`fmruby-*`) は ACL では Apply の時の台帳のノードに当てて行を作り、端末には型のまま渡す。台帳に後から足した端末は、Apply するまでルータで通らない (端末の側は型で通す)。
- 端末の受け口は 2 つの種類を同じ鍵で受けるので、ACL は種類を分けない。種類で分けるのは端末の判断 (一覧の種類ごと)。
- 手書きの側でも型 (`fmruby-*`) が使えるようになった (前は名前と `*` だけ)。
- 起動の条件のために、カーネル (Spinel) で `Dir.open` を使った。ネイティブ版で動くことは確かめた (6 章の 1)。ESP32 の実機ではまだ (Spinel のカーネルで `Dir` を使うのはこれが初めて。失敗しても rescue で「無い」と見なし、今までの条件に戻るだけ)。
- 新しい `flash/` のファイルは git に入れるまでブラウザ版の束に入らない (5 章の checkpoint の 1 回目)。ネイティブ版は木をそのまま読むので気づかない。
- `pkill -f bin/bridge` は、その文字列を含む自分のシェルまで止める (通しの途中で踏んだ)。止めるときは pid で。
