## 2. 種類 file の片の置き場所

- 片のファイル: `/home/inbox/.<名前>.file.part` (`.` で始まる名前。種類 file の名前は `.` で始まれないので、送られたファイルとは重ならない)。名前は最長で 1 + 48 + 10 = 59 バイトで、LittleFS の名前の上限 (63) に入る。
- commit: SHA-256 が合えば `File.rename` で置く名前へ。上書きのときは元を消してから付け替える (照合が合った後だけ)。写しが無くなったので、ESP32 の LittleFS で数 MB を写して送り手の期限 (10 秒) を越えるおそれは無くなった。
- 空き: `room` は種類 file なら `FmrbApp.free_bytes("/home/inbox/")` だけ (前は `/tmp` と `/home` の小さい方)。checkpoint は今までどおり `/tmp`。
- **控え (`.xfer`) は `/tmp` のまま**にした。片だけが置き場所の隣へ行く (gem のフック `part_path`)。理由: 決まったこと「受け手の端末が再起動したら最初から」をそのまま保つため。控えが `/tmp` にあれば、再起動で控えが消え、`/home/inbox/` に残った隠しの片は転送のアプリの起動時に消す (`sweep_inbox`。`resume_held` が控えから拾い直した片だけ残す)。控えも `/home/inbox/` に置くと、再起動の後も続きから受ける形になる (利用者から見た動きが変わるので選ばなかった。9 章)。控えは 200 バイトほどの JSON で、片のバイト列は `/tmp` を通らない。
- 期限切れ (60 秒)・取りやめ・照合が合わない・別の相手に譲る、はどれも `t["part"]` (隠しの片) と `t["note"]` (`/tmp` の控え) を消す。gem の `resume_held` は、拾わない控えを消すときに、その控えが指す片 (フックで求めた場所) も消す。
- 受け手のアプリの起動し直しからの再開: 控えを読み、フックで片の場所を求め、その大きさから続ける (gem の試験 `test_pieces_beside_where_they_go` と、今までの restart の場面)。
- `/home/inbox/` は `begin` の許可の確認 (`refused`) の中で作る。作れなければ理由つきで断る。

## 3. 受け手の決め方

`begin(kind, meta)` → `{"id", "piece", "window", "pos"}`。

### 片の大きさ (`piece`)

- 1 回の呼び出しは鍵と枠を含めて 4,096 B (zenoh-pico の `Z_FRAG_MAX_SIZE`)。超えると黙って落ちる (t0.md 1 章)。
- 受け手は自分の鍵 `asterism/<ノード>/<アプリ>/<オブジェクト>/call/<送り手>` の長さを知っている (`Inbox#path=` を link_up で入れる。送り手は begin の `from`)。`piece = floor256(4096 - 160 - 鍵の長さ)`、512〜3,840。
  - 160 B は chunk の呼び出しの枠 (メソッド名・id・位置・バイト列の頭で 40 B 弱) と余裕。T0 の実測 (鍵 50 B で文字列 4,044 B まで通った) から見ると、片の本当の上限は約 4,079 - 鍵の長さで、この式は 140 B ほど内側。
  - 例: `rg-xfer-b/transfer/inbox` に `rg-xfer-a` から → 鍵 49 B → 3,840 B。ノード名が長く鍵が 200 B なら 3,584 B。
- `path` を知らない受け手 (CRuby の試験の受け手など) は鍵を 128 B とみなす (3,584 B)。`new` の `piece:` は上限として残る (試験のアプリの `recv_piece`)。

### 同時に送る片の数 (`window`)

- 転送のアプリ: 自分の VM プールの空き ÷ (3,840 × 4)、1〜8。checkpoint は最大 4。
  - 4 倍は、受けている片が呼び出しの payload・Ruby の String・答え・次の GC までのごみとして数回分プールに居ることの見積もり (測っていない。ESP32 で確かめる、6 章)。
  - 空きは `FmrbApp.pool_used` と `pool_usage` (百分率) から求める (C は足していない)。ネイティブ版の転送のアプリでは 8 になった (ログの `pieces of 3840 bytes, 8 at a time`)。
  - 上限 8: 4 MiB でネイティブ版どうしは 8 と 16 が同じ速さ (4 章)。片は zenoh-pico の受け口の列 (アプリごとに 32、ESP32 では PSRAM) に並ぶので、内蔵 RAM は使わない。
  - checkpoint の最大 4: イメージは数十 KB (片で 10 前後) で、それ以上は効かない。移動の間のプールを落ち着かせておく。
- gem の既定: `window:` (既定 4)、どの受け手も 16 まで (`WINDOW_MAX`。列 32 の半分)。
- 送り手は `min(受け手の値, 自分の上限)`。`window` を返さない古い受け手には 1 つずつ (今までどおり)。begin し直すたびに読み直す (受け手のアプリが起動し直して値が変わっても従う)。

## 4. 速さ

`ruby tools/regress/transfer.rb --bench --speed --file --size N --pieces ... --windows ...`。受け手 (試験のアプリ) は `recv_window` 16・`recv_piece` 65,536 にして、送り手の上限の側で片と数を変えた。1 MiB を超える分は送り手・受け手とも `/home` (ネイティブ版はホストのディレクトリ、ブラウザ版はページの中) に置いた。単位 ms。

### ネイティブ版 → ネイティブ版 4 MiB

受け手 B は道具の中継 (Ruby の TCP 中継、切断の試験のためのもの) を通る。

| 片 \ 同時に送る片の数 | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 1,024 B | 9,553 | 4,848 | 2,595 | 1,472 | 1,141 |
| 2,048 B | 4,779 | 2,601 | 1,434 | 1,121 | 1,120 |
| 3,072 B | 3,274 | 1,760 | 975 | 764 | 747 |
| 3,840 B | 2,617 | 1,356 | 808 | 602 | 601 |

種類 file で B の転送のアプリへ (受け手が決めた 3,840 B × 8): 1,174 ms (毎秒約 3.6 MB)。

### ネイティブ版 → ネイティブ版 16 MiB

| 片 \ 同時に送る片の数 | 1 | 4 | 8 | 16 |
|---|---|---|---|---|
| 2,048 B | 19,379 | 5,506 | 4,497 | 4,445 |
| 3,840 B | 10,482 | 3,042 | 2,388 | 2,351 |

種類 file で転送のアプリへ (3,840 B × 8): 4,547 ms。

### ネイティブ版 ⇔ ブラウザ版 4 MiB (ブラウザ版はヘッドレスの Chromium、ルータの ws/ に直に)

| 片 \ 同時に送る片の数 | → ブラウザ版 1 | 4 | 8 | 16 | ブラウザ版 → 1 | 4 | 8 | 16 |
|---|---|---|---|---|---|---|---|---|
| 2,048 B | 4,215 | 1,260 | 758 | 571 | 4,316 | 1,335 | 1,098 | 1,088 |
| 3,840 B | 2,314 | 691 | 412 | 311 | 2,283 | 723 | 581 | 578 |

種類 file でブラウザ版の転送のアプリへ (受け手が決めた 3,840 B × 8): 635 ms。

### ネイティブ版 ⇔ ブラウザ版 16 MiB (3,840 B)

| 同時に送る片の数 | → ブラウザ版 | ブラウザ版 → |
|---|---|---|
| 1 | 9,123 | 9,278 |
| 8 | 1,640 | 2,324 |
| 16 | 1,250 | 2,314 |

種類 file でブラウザ版の転送のアプリへ (3,840 B × 8): 2,346 ms。

- 時間は呼び出しの数 × 往復で決まり、大きさに比例する (4 MiB → 16 MiB でほぼ 4 倍)。1 MiB を超えても頭打ちや崩れは無い (どの場面も `again` 0・`retries` 0)。
- 同時に 8 で 1 つずつの 4〜6 倍。8 と 16 の差は、ネイティブ版どうし (中継を通る) では無く、ブラウザ版が受け手のときは 16 が 2〜3 割速い。上限を 8 にしたのは小さい端末の側に合わせたため (16 は ESP32 で測ってから考える)。
- ネイティブ版どうしがブラウザ版より遅く見えるのは、試験の B が道具の Ruby の中継を通るため (片ごとに Ruby のスレッドが 2 回動く)。本番の道 (zenohd に直に) にはこの中継は無い。
- 種類 file (転送のアプリ) が試験のアプリより 2 倍ほど遅いのは、転送のアプリの更新の間隔 (呼び出しが来ている間 2 ms) のため。ESP32 では WiFi の往復の方が長いので、ここは効かない見込み。

### 4 MB 以上を切って続きから、`/tmp` を使わない証拠 (big の場面)

`regress:transfer` の big: A の試験のアプリが B の転送のアプリへ種類 `file` で 4,194,304 B を送り (歩みを 40 ms ごとに絞る)、A のログが 1 MiB と 3 MiB を持ったところで B の接続を切る (1.5 秒つながせない)。それぞれの切る時に道具が見たもの:

- B の `/home/inbox/.big.bin.file.part` がある (1,101,824 B と 3,170,304 B)。
- B の `/tmp/big.bin.file.part` が無い。控え `/tmp/big.bin.file.xfer` はある。
- B のログ: `transfer: rg-xfer-a sends file big.bin (4194304 bytes) to /home/inbox/.big.bin.file.part, pieces of 3840 bytes, 8 at a time`。

終わったあと: A は 1,351,680 と 3,409,920 から続けた (B のログの `goes on with file big.bin at` と同じ位置、0 からではない)。B の `/home/inbox/big.bin` の SHA-256 が元と一致し、`/home/inbox/` に隠しのファイルは残らず、`/tmp` に片も控えも残らない。A の終わりの行の「pieces of 3840, 8 at a time」は B が名乗った値と同じ。

quick の big も同じことを CRuby の送り手から 1 回の切断で確かめる (19 秒の内、この場面は約 5 秒)。

### 空きより大きいもの

種類 file の受け手の空きが `/home` (ネイティブ版はホストのディスク) になったので、quick の「空きより大きいものを begin で断る」は 64 MiB から 8 TiB (送り手の側は疎なファイル、SHA-256 は宣言だけ) にした。ブラウザ版の `/home` は空きを教えない (`FmrbApp.free_bytes` が nil、T2) ので、ブラウザ版ではこの確認を外した (9 章)。

## 6. ESP32 で残っていること (実機がつながったとき)

まだ流していない。

### 置ける大きさの見込み

種類 file は `/home/inbox/` (内蔵 flash の LittleFS) だけ (決定事項)。SD (`/sd`) は使わない。

| 端末 | storage の区画 | `/home` の空きの見込み | 4 MB |
|---|---|---|---|
| NARYAv3 (S3、n16r8) | 5 MB | storage の木 (配布物) を除いた残り。1 MB 前後かそれ以下の見込み | 入らない見込み (`begin` で「do not fit (N bytes free)」と断られる) |
| AtomS3R・StickS3 | 2,496 KB | 約 790 KB (partitions の注) | 入らない |
| Tab5・NARYAv4 (P4) | 8 MB | storage の木を除いた残り | 入る見込み (空き次第) |

数字は begin の断りの文 (`N bytes free`) で分かるので、最初にそれを読む。

### 手順

1. 今のコミットを組んで焼く (storage も。`/usr/share/transfer/transfer.app.rb`・`/usr/share/asterism/transfer/`・`/app/test/xfer_probe.app.rb`。C は変えていないので、Tab5 は `tab5_fs` で put でもよい)。
2. 端末の `/home/asterism/receive.toml` に `[file] from = ["fmrb-send", "rg-xfer-a"]`。
3. 空き: PC で 4 MB のファイルを作り `ruby tools/fmrb_send.rb <端末のノード> big.bin --router tcp/<端末のつなぐルータ>:7447`。S3 では begin で断られ、空きが出る (それを記録)。Tab5 では置かれ、終わりの行に端末が決めた片と数 (`pieces of N, W at a time (the receiver's)`) と時間が出る。シリアルのログ (`serial_start`) の `transfer: fmrb-send sends file big.bin (...) to /home/inbox/.big.bin.file.part, pieces of N bytes, W at a time` と `transfer: placed`。
4. 切って続きから: `ruby tools/regress/transfer.rb --peer <端末のノード> --router tcp/<ルータ>:7447 --only big` (A の試験のアプリから端末の転送のアプリへ 4 MiB、A の接続を 1 MiB と 3 MiB で切る。端末の receive.toml の `[file]` に `rg-xfer-a`。送り手の側で判定する: 端末の commit が SHA-256 を照合している)。S3 では空きに入る大きさで (道具の `BIG` を変える)。
5. 切っている間に端末の `/tmp` に片が無く `/home/inbox/.big.bin.file.part` が育つこと: Tab5 は `tab5_fs` の list (`/tmp`・`/home/inbox`。隠しのファイルが一覧に出るか確かめる)。
6. 速さ: 端末の `/home/xfer_probe.job` を `{"recv_piece": 65536, "recv_window": 16, "recv_dir": "/home/xp/"}` にして試験のアプリを起動し、`ruby tools/regress/transfer.rb --bench --speed --peer <ノード> --router tcp/<ルータ>:7447 --size 1048576 --pieces 1024,2048,3840 --windows 1,2,4,8,16`。S3 は `/home` の空きに合わせて `--size` を小さく。逆向き (ESP32 → PC) は t0.md 7 章の 3。
7. 気にしておくこと (ログと時間で):
   - window の見積もり (片 × 4 がプールに居る): 4 MB の間の `fmrb_app:` の周期ダンプで転送のアプリのプールを見る。8 で足りなくなるなら `PIECE_COST` を上げる。
   - LittleFS へ 3,840 B ずつ書く速さ。片の答えが遅れても送り手は待つだけ (期限 10 秒)。
   - 受け手のアプリが起動し直したときは、控えから続ける前に片全体を読み直して SHA-256 を作り直す (begin の呼び出しの中)。4 MB の LittleFS の読みが 10 秒を越えないか (接続が切れただけなら読み直さない。ファイルを開いたまま持っている)。
   - 送り手が始める前に全体の SHA-256 を計算する間 (4 MB を LittleFS から)、転送のアプリの更新が止まる。
8. ネイティブ版 ⇔ ESP32、T1・T2 からの ESP32 の残り (t1.md 7 章、t2.md 8 章) も同じ機会に。

## 7. 捨てた案

- **控えも `/home/inbox/` に置く**: 再起動の後も続きから受けられるが、「再起動したら最初から」(決まったこと) が変わる。flash への書き込みも少し増える (控えは begin のたびに書く)。
- **片の大きさを固定の 3,840 B にする**: ノード名が長いと呼び出しが 4 KB を越えて黙って落ちる。受け手が鍵から決める形にした。
- **プールの空きを返す C のメソッドを足す**: `pool_used` と `pool_usage` (百分率) で足りる (1 % の粗さは window の決め方には十分)。
- **window の上限を 16 にする**: ブラウザ版が受け手のときだけ速くなる。ESP32 で測る前は 8 に留めた。

## 8. 気づき

- 試験の B は Ruby の中継を通るので、ネイティブ版どうしの数字は本番より遅い (4 章)。中継を通らないブラウザ版の方が速い。
- `kill_probes` がブラウザ版の bench で起きていない B に問い合わせて止まっていた (`--web` のとき B を見ないようにした)。
- 道具を直した後に `regress:transfer` (標準・mruby) と quick をもう一度流して通った (big: 標準 1,332,480 と 3,452,160、quick 1,098,240 から続けた)。

## 9. 残件・親に決めてほしいこと

### 残件

- **gem の push と pin**: asterism `4a39108`・`22c1cd4`・`d442ba8` を push してから fmruby-core を push する。
- ESP32 (6 章)。S3 の `/home` に 4 MB が入らない見込み。
- ブラウザ版の `/home` は空きが分からず、種類 file の大きなものは書けなくなった所で断る (begin では断らない)。前は片が `/tmp` (約 7 MB) にあったので begin で断れていた。

### 親に決めてほしいこと

1. **控え (`.xfer`) を `/tmp` に残した** (2 章)。片だけが `/home/inbox/` に行く。再起動したら最初から (今の決まったこと) を保つため。控えも隣に置いて再起動の後も続ける形にするなら、決まったことの変更になる。
2. **S3 の 4 MB**: 種類 file の置き場所は `/home/inbox/` だけ (決定事項) なので、S3 (storage 5 MB) では 4 MB が入らない見込み。受け入れ条件「ESP32 へ 4 MB (受け手の空きがある範囲で)」は P4 で確かめ、S3 は空きの範囲で、としてよいか。SD を置き場所にするのは決定事項の変更。
3. **window の決め方** (3 章): プールの空き ÷ (片 × 4)、最大 8 (checkpoint 4)。4 倍は見積もりで、ESP32 で確かめる。
4. **ブラウザ版の `/home` の空き** (残件): Emscripten の statvfs が使えないので、ページの持てるメモリなどから空きの目安を返すか、今のまま書けなくなった所で断るか。
