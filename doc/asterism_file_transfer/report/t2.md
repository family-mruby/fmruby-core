## 2. 空きを知る口 (`FmrbApp.free_bytes`)

`FmrbApp.free_bytes(path)` → その場所にあと書けるバイト数 (Integer)、分からなければ nil。

| 端末 | `/tmp` | `/home` |
|---|---|---|
| ESP32 (S3・P4) | tmpfs の数え (`fmrb_tmpfs_usage` の容量 - 使用量) | LittleFS の空き (`fmrb_hal_file_statfs`。SD の下なら SD) |
| ネイティブ版・sim | 同じ (posix の tmpfs の数え) | ホストのディレクトリの statvfs |
| ブラウザ版 | 同じ | nil (Emscripten の statvfs は固定の値で意味がない) |

- `/tmp` を statfs に渡すと、ESP32 では LittleFS の、Linux ではホストの空きが返ってしまう。それで `/tmp` だけは tmpfs 自身の数えを使う (HAL の statfs は変えていない)。
- メソッドを 1 つ足しただけで、静的な領域は増えない (表は VM のプールにあり、PSRAM)。内蔵 RAM の確認は 6 章。
- 転送のアプリの `room`: 片のファイルの置き場 `/tmp` の空き。種類 `file` はそれと `/home` の空きの小さい方。nil なら今までどおり書けなくなった所で断る (ブラウザ版の `/home`)。`begin` で「`N bytes do not fit (M bytes free)`」と断る。
- Spinel のアプリ (`fmrb_app_base_spinel.rb`) には足していない。今のところ使うのは転送のアプリ (mruby) だけ。

## 3. 種類 file

- 受け手は `/home/inbox/` (無ければ作る) にだけ置く。片のファイルは今までどおり `/tmp/<name>.file.part`。照合が合ったら `/home/inbox/.<置く名前>.part` に写し、それを置く名前に付け替える。上書きのときも、元のファイルを消すのは照合が合って写し終えた後。写す途中でアプリが終わったときの隠しファイル (`.*.part`) は次の起動で消す。
- 名前 (`Transfer.file_name?`): `/`・`\`・`..` を含まない、`.` で始まらない、制御文字なし、1〜48 バイト (日本語の名前も可)。48 バイトは ESP32 の tmpfs の名前の上限 (63 バイト) に `<name>.file.part` が入るように。
- 同じ名前: 送り手の meta `"overwrite" => true` なら置き換える。無ければ `foo(1).txt`、`foo(2).txt`、… の空いている最初の名前で置く (`Transfer.free_name`。拡張子の前に付ける)。置いた名前は commit の答え `{"status" => "placed", "name", "path"}` で送り手に返る。

## 4. receive.toml の書き方

新しい書き方 (種類ごとの表。書いていない種類は受けない):

```toml
[checkpoint]
from = ["fmruby-abcdef", "wasm-123456"]   # アプリを移してよい相手

[file]
from = ["fmruby-abcdef", "fmrb-send"]     # /home/inbox にファイルを置いてよい相手
```

今までの書き方 (表の外の `from`) は **checkpoint の許可として読む**:

```toml
from = ["fmruby-abcdef"]                  # = [checkpoint] from。file は受けない
```

- 両方あるときは、どちらかに入っていれば checkpoint を受ける (2 つの和)。
- 今までの書き方だけの端末は、今までどおりアプリを受け、ファイルは「`takes no file (no [file] in /home/asterism/receive.toml)`」で断る。
- 断る理由: 「`takes no <kind>`」(転送のアプリが知らない種類)、「`takes no <kind> (no [<kind>] in ...)`」、「`takes no <kind> from <node> (<kind> from in ...)`」。どれも `begin` の 1 回の呼び出しで、片を送る前に断る。
- カーネルが起動時に転送のアプリを起こす条件 (`receive.toml` があること) は変えていない。
- `"*"` は今までどおり誰でも。

## 5. 送り手の口

### アプリの API (`FmrbTransfer`)

```ruby
require "/usr/share/transfer/fmrb_transfer"
@xfer = FmrbTransfer.new(self)
id = @xfer.send_file("fmruby-abcdef", "/home/notes.txt", overwrite: false, name: nil)
# on_control:  return if @xfer.on_control(msg)
# on_update:   @xfer.update; st = @xfer.status(id)   # {"state", "sent", "size", "name", "reason"}
@xfer.cancel(id)
```

- state: asking → queued → sending → done (name: 置かれた名前) / failed (reason)。
- 送るのは転送のアプリ (端末の Asterism の接続を持つ)。頼みは Pub/Sub の topic `transfer/ctl` で、答えは転送のアプリから頼んだアプリへの message (`transfer_queued`・`transfer_progress` (250 ms ごと)・`transfer_done`)。転送のアプリが動いていなければカーネルに spawn を頼む (起こしたものはカーネルが自分のものとして引き取る。`adopt_transfer`)。まだ受けてもらえない頼みは 1 秒ごとに出し直し、20 秒で諦める。同じ頼みの出し直しは転送のアプリが 1 回だけ受ける (アプリごとに増えていく id)。
- 頼みは message 1 つ (176 バイト) に入る必要があり、ノードとパスを合わせて 90 バイトほどまで。超えると `send_file` が ArgumentError。
- 取りやめ: 転送のアプリが `Sender#cancel` を呼び、受け手に `cancel` を送る (受け手の片のファイルと控えが消える)。
- 転送のアプリは頼みを 1 つずつ、カーネルの頼み (移動) と同じ列で順に処理する。つながっていない間に頼まれたものは 30 秒で諦める。
- この API の Ruby は `/usr/share/transfer/` にあり、使うアプリだけが読む (mrblib に入れず、全部の VM には入らない)。

### Shell

```
asend <node> <file> [-o]    ファイルを相手の /home/inbox へ (-o: 上書き)
asend -c                    送っている途中のものを止める
```

`move <pid> <node>` に合わせて相手を先に書く。名前は `send`。1 つずつで、4 分の 1 ごとと終わりに 1 行出る (`send: /home/hello.txt is in rg-xfer-b's /home/inbox as hello(1).txt`)。ネイティブ版 2 つで、送る側の転送のアプリを止めておいて `send` を 2 回打ち、転送のアプリが起こされて 2 回とも届くこと (2 回目は `hello(1).txt`) を画面とログで確かめた。

### PC の道具 (`tools/fmrb_send.rb`)

```
ruby tools/fmrb_send.rb <node> <file> [--router tcp/127.0.0.1:7447] [--node fmrb-send] [--overwrite] [--name NAME]
```

- CRuby の Asterism (`ASTERISM_DIR`、なければこの木の `vendor/asterism`、なければ入っている gem) に、端末と同じ `Asterism::Transfer::Sender`。相手の `receive.toml` の `[file] from` に `--node` の名前 (既定 `fmrb-send`) を書く。
- 4 分の 1 ごとの進み具合と置かれた名前を出し、置かれたら終了コード 0。Ctrl+C で取りやめ (受け手の片のファイルは消える)。
- ネイティブ版へ 700 KB を 3 回 (そのまま・`--overwrite`・`--name renamed.bin`) と、許していないノードから 1 回送って確かめた (約 0.5 秒ずつ。最後は 1 回の呼び出しで「`takes no file from someone`」)。

## 7. ブラウザ版の SHA-256

- 小さな C の mrbgem `picoruby-fmrb-sha256` (FIPS 180-4、`Digest::SHA256` の `new`・`update`・`<<`・`hexdigest`・`digest`・`.hexdigest`) をブラウザ版の構成だけに入れた。Asterism::Transfer は Digest::SHA256 を最初に探すので、gem の側は変えずにこれを使う。
- mbedTLS にしなかった理由: ブラウザ版には picoruby-mbedtls が無い (ソケットの gem と一緒に入るもの)。入れると mbedTLS の 100 余りのファイル全部 (TLS・NET・乱数の port を含む) と、その git clone (gem の rake が初めて組むときに取る) がブラウザ版の組み立てに加わる。SHA-256 の C は 150 行ほどで、ホストで sha256sum と 0〜100,001 バイトの 11 通り (区切り 7 バイトと 4 KB) が一致し、ブラウザ版の中で plain Ruby と同じ値を出した。
- 1 MiB (ヘッドレスの Chromium): C 18 ms、plain Ruby 2,683 ms (T0 では 3,253 ms)。
- ブラウザ版が受け手のときの 1 MiB (`rake regress:transfer BENCH=1 WEB=1`、ms):

## 8. ESP32 で残っていること (実機がつながったとき)

## 9. 残件・親に決めてほしいこと

### 残件

- **gem の push と pin**: asterism `4a39108`・`22c1cd4` を push してから fmruby-core を push する。
- **大きなファイルの置き方 (T3)**: 片のファイルは `/tmp` に置く決まり (決まったこと) なので、受けられる大きさは `/tmp` の空きまで (S3 は 448 KB、P4 は 8 MB)。`/tmp` から `/home/inbox/` への写しは commit の呼び出しの中で行う。ESP32 の LittleFS に数 MB を写すと commit の答えが送り手の期限 (10 秒) を越えうる (越えると送り手は begin し直し、最初から送ることになる)。T3 で、写しを commit の外 (「置いている」の答えと status) にするか決める。
- ネイティブ版 ⇔ ESP32 (8 章)、T1 からの ESP32 の残り (t1.md の 7 章)。
- ブラウザ版の cut・api の場面は quick に無い (6 章)。

### 親に決めてほしいこと

1. **SHA-256 を mbedTLS でなく小さな C にした** (7 章)。指示書は「同じ mbedTLS、無理なら小さい C」。無理ではないが、ブラウザ版に mbedTLS 全部とその clone を入れる重さを避けた。mbedTLS に揃えるなら、picoruby-mbedtls のうち SHA-256 (`sha256.c`・`md.c`・`platform_util.c`) だけを組む小さな gem にする手がある (その clone を取る手順が要る)。
2. 種類 `file` の名前の決まり: `.` で始まる名前を断る (隠しファイルは写しの途中のものに使う)、48 バイトまで (ESP32 の tmpfs の名前の上限から)。日本語の名前は通す。
3. 古い書き方と新しい書き方が両方ある receive.toml では、checkpoint はどちらかに入っていれば受ける (和) にした。
4. Shell のコマンド名 `asend <node> <file> [-o]`・`asend -c` (2026-11-08 ユーザ: Asterism の送信と分かる短い名前。最初は send)、PC の道具の既定のノード名 `fmrb-send`。
5. `regress:transfer:quick` はネイティブ版 1 つと道具の CRuby で 15 秒になった (1 分の枠の内)。`regress:transfer` (3 分) は `regress:full` に入れていない。
