# M1 報告: 文書の組と、文書ごとの状態の出し入れ

> 状態: 完了 | 更新: 2026-11-17 | 1 つのエディタが 5 つまでの文書を持ち、切り替えても本文・カーソル・スクロール・選択・変更の印・ファイル名・ハイライトが混ざらない土台を作った。C の束ねが文書の組 (`ec_docset_t`) と今の文書を持ち、Ruby 側は `editor/docs.rb` が文書ごとの ivar を 2 本の平らな配列に出し入れする。仮のキーは Ctrl+N・Ctrl+W・Alt+. / Alt+, (sim 用に Ctrl+PageDown / Ctrl+PageUp)。標準構成 (Spinel) と全部 mruby の構成の両方で、保存したファイルの中身で確認した。指示書は instruction_m1.md

## 1. 足した口

### 1.1 C (lib/gems/picoruby-fmrb-editor-core)

`editor_core_api.h` に文書の組を足し、組の操作は `editor_core.c` に 1 つだけ書いた。mruby の束ね (`editor_core_mrb.c`) と Spinel の束ね (`main/app/fmrb_spx_editor.c`) はどちらもこれを呼ぶだけで、同じ形になる。

```c
#define EC_DOCSET_MAX 5
typedef struct {
    int count;                  /* documents held */
    int cur;                    /* index of the current one, 0..count-1 */
    int slots[EC_DOCSET_MAX];   /* in the order they were opened */
} ec_docset_t;

int  ec_docset_slot(ec_docset_t *s);          /* current slot; opens the first on demand */
int  ec_docset_add(ec_docset_t *s);           /* new empty doc, becomes current; index or EC_ERR_RANGE / EC_ERR_NOMEM */
int  ec_docset_switch(ec_docset_t *s, int idx);
int  ec_docset_close(ec_docset_t *s);         /* closes the current; answers the new current index */
void ec_docset_release(ec_docset_t *s);       /* closes all (editor ended / killed) */
void et_release_answers(void);                /* type helper's kept tables (editor_ti_bridge.c) */
```

- 文書はエディタから見て「開いた順の番号」(0 から) で呼ぶ。slot の番号は外に出さない。閉じると後ろの番号が 1 つずつ詰まる (Ruby 側の配列も同じ詰め方をする)。
- `ec_docset_add`: 組が 5 つなら `EC_ERR_RANGE`、slot が空いていない・空の 1 行を取る領域も無いなら `EC_ERR_NOMEM`。どちらも組は変えない (開けた slot は閉じて返す)。成功したら新しい文書が今の文書になる。
- `ec_docset_close`: 最後の 1 つは閉じずに空にする (`ec_reset`)。エディタは必ず 1 つ持つ。
- `ec_docset_release`: 組の全部を閉じ、`released N document(s); arena in use X bytes` をログに出す。どのエディタも文書を持っていなければ、型支援が要求の間で持ち続ける答えの表 (`g_items`・`g_diags`) も返す (2.4)。
- 組の表は PSRAM (`FMRB_EXT_RAM_BSS_ATTR`)。Spinel 版は `s_slot_plus1` (int 1 つ) を `ec_docset_t s_docs` (28 バイト) に替えた。mruby 版は VM ごとの表 `g_vm_slots[4]` (8 バイト × 4、内蔵 RAM) を `g_vm_docs[4]` (32 バイト × 4) にして PSRAM へ移した。ESP32 の内蔵 RAM は 32 バイト減る見込み (`regress:size` は流していない)。

### 1.2 Ruby (EditorCore)

今の呼び方 (slot を渡さない) はそのまま。足したのは次の 5 つで、mruby 版は gem の C、Spinel 版は `fmrb_editor_ffi.rb` の shim (`FmrbSpxEc.fmrb_spx_ec_doc_*`) が同じ名前で答える。

| 口 | 答え |
|---|---|
| `EditorCore.doc_add` | 新しい文書の番号 (今の文書になる)。-1 は 5 つ開いている、-2 は slot か領域が無い |
| `EditorCore.doc_switch(i)` | 0、範囲の外は -1 |
| `EditorCore.doc_close` | 閉じた後の今の文書の番号 |
| `EditorCore.doc_count` | 持っている数 (最初の文書をまだ開いていなければ開く) |
| `EditorCore.doc_index` | 今の文書の番号 |

Spinel 版の口の名前: `fmrb_spx_ec_slot` (旧 `fmrb_spx_ec_open_slot`)、`fmrb_spx_ec_doc_add`・`_doc_switch`・`_doc_close`・`_doc_count`・`_doc_index`、`fmrb_spx_ec_release_docs` (旧 `fmrb_spx_ec_release_slot`。spawner の 2 か所の呼び出しを名前だけ替えた)。使われていなかった `fmrb_spx_ec_close_slot` は消した。

### 1.3 文書の本体の直し (1 か所)

`editor_core.c` の `doc_clear` で折り返しのキャッシュの印 (`g_wrap_stamp`) を進めるようにした。キャッシュの鍵は (slot, 行, 幅, 印) で、文書を空にしても印が進まなかったため、閉じた slot を次の文書が使うと前の文書の 1 行目の折り返しを読む余地があった (`ec_reset` でも同じ。今まではエディタの起動時にしか呼ばれず、表に出ていなかった)。`g_docs` と `ED_MAX_DOCS` は変えていない。

### 2.2 持ち方と理由

- `@doc_ints`: 文書ごとに 12 個の整数を並べた平らな配列 (`DOC_ST_CX` から `DOC_ST_HL_MANUAL`、`DOC_ST_N` = 12)。`@doc_files`: 文書ごとに 1 つの文字列。要素の型が 1 種類ずつなので、Spinel は `sp_IntArray *` と `sp_StrArray *` に絞れる (生成 C の `struct sp_EditorApp_s` で確認)。
- 保存・戻しは `docs_save`・`docs_save_flags`・`docs_restore`・`docs_restore_flags` の 4 つに分けた (強制インラインで 1 つのフレームが大きくならないように)。
- **生成 C を読んで確認した** (`main/ruby/spinel/gen/linux/editor_combined.c`): 保存は `sp_IntArray_set(..., sp_poly_elem_i(self->iv_cx))` (`@cx` などは元から poly)、真偽は `(self->iv_wrap_on ? 1LL : 0LL)`、選択は `sp_poly_truthy(lv_sx) ? lv_sx : sp_box_int(-1)`、ファイル名は `sp_StrArray_set`。戻しは `sp_box_int_or_nil(sp_IntArray_get(...))`、無題は `sp_box_str(NULL)` で、これは nil を作る (`sp_alloc.h` の `sp_box_str`)。黙って 0 になる所は無かった。
- 閉じた文書の分は、配列を作り直して詰める (`docs_remove_entry`。`delete_at` を Spinel で使うのを避けた)。
- 試してやめた持ち方: なし (最初の形で両方の構成が通った)。
- ivar は `EditorApp` に `@doc_ints`・`@doc_files` の 2 つが増えただけ (mixin の ivar はクラスの構造体に入る)。基底 (`FmrbApp`) には足していない。標準構成で開いて 1 打鍵 (3 章、と `regress:screens` の `editor_type`) を確認した。

### 2.3 ブレークポイント・デバッグのペイン・型支援の診断の今の持ち方

- **ブレークポイント** (`@bp`、mruby 版だけ): `{ パス => { 行 => bp_id } }` で、ファイル名付き。表示 (`bp_on_line?`) と F9 は `@current_file` を引くので、切り替えるとその文書のファイルのブレークポイントが見える。つまり、名前のある文書については今のままで文書ごとに分かれている。無題の文書には置けない (今のまま "open a file first")。持ち方は変えていない。
- 気をつける所 (変えていない): デバッグを始めたとき (`dbg_attach`) に仕掛けるのは今の文書のファイルの分だけ。また、対象のソースを今の文書に読み込む (今の文書が変更なしのとき)。ほかに開いている文書のブレークポイントは、その文書に切り替えて F9 で置き直すまで対象に仕掛からない。止まった行の印は「止まったファイルと今の文書のファイル名 (パス無し) が同じとき」に出る。セッション (`@dbg_active`・`@dbg_pid`・ペイン) はエディタに 1 つ。
- sim ではデバッグのセッションを動かしていない (確認していない)。Spinel 版にはデバッガが無い (`editor_debug_stub.rb`)。
- **型支援の診断** (`@diag_*`): 文書ごとの性質だが 1 組しか持たないので、切り替えで消す (`clear_diagnostics`)。戻ってから Ctrl+E か保存で出し直す。

### 2.4 型支援が、複数の文書で領域が詰まっているときにどう断るか (コードを読んだ範囲)

- 型支援は文書を丸ごと写す作業の領域を、同じ 1 MB の領域 (`POOL_ID_EDITOR_DOC`) から要求ごとに取って返す (`et_begin`)。量は文書の大きさから見積もり、空きの 3/4 までに抑え、96 KB を下回るなら `no room for a parse: N bytes free in the document pool` を出して `EC_ERR_NOMEM` で断る。大きい文書を複数開いて領域が詰まったときは、この断り方になる (ほかの文書は壊れない)。`et_max_source_bytes` の上限 (`COMP_TOO_LARGE`) は文書ごとで、今のまま。試していない。
- 答えの表 (`g_items` = 補完の候補、`g_diags` = 診断) は最初の要求で取ってエディタが終わっても持ち続ける作りだった (64 件 × 176 バイト = 11,264 バイトなど)。M1 の最初の確認で、終えた後の `ec_mem_used` が 0 に戻らず 11,264 バイト残ったのはこれ (slot の返し忘れではない)。どのエディタも文書を持たなくなった時点で返すようにした (`et_release_answers`)。その後は 0 に戻る (3 章)。

## 3. 受け入れ条件の結果

sim は Modern (TAB5、426x240) の標準構成と全部 mruby の構成で 1〜5 を、Retro (NARYAv3) の標準構成で 1 回 (2 文書の切り替えと、全画面 F11 での切り替え) を見た。ビルドは `targets.rb` の `FIRMWARE_ENV` と、mruby の構成は `screens.rb` の `MRUBY_ENV` と同じ環境変数で `rake build:linux`。

### 3.1 打ったキーの列 (回帰の場面にするとき用)

保存先は sim の `/tmp` (ホストでは `fmruby-core/flash/tmp/`、gitignore)。保存の窓はパスを打って Enter。

```
# エディタを開く: デスクトップの Editor をダブルクリック (Modern は 37,72)
text "alpha one" key enter text "alpha two" key enter text "alpha three"
key ctrl+s  text "/tmp/m1a.rb" key enter                  # A を保存
key ctrl+n  text "bravo line" key enter text "bravo end"    # B (2/2)
key ctrl+n  text "c01" key enter ... text "c22"             # C (3/3): 22 行でスクロールさせる
key up x5                                                   # C のカーソルを 17 行目へ (表示は c09 から)
key ctrl+pageup key ctrl+pageup                             # A へ: [1/3] m1a.rb Ln 3, Col 12
text "!" key ctrl+s                                         # A を上書き保存
key ctrl+pagedown  text "?" key ctrl+s text "/tmp/m1b.rb" key enter   # B
key ctrl+pagedown                                           # C: [3/3] [New] Ln 17, Col 4 *、表示は c09 から
text "#"
key ctrl+pagedown  key home key shift+end key ctrl+c        # A の 3 行目をコピー
key ctrl+pageup    key enter key ctrl+v                     # C に貼る
key ctrl+s text "/tmp/m1c.rb" key enter
key ctrl+n text "d4"  key ctrl+n text "e5"  key ctrl+n      # 6 つ目: "Max 5 files open"
text "x" key ctrl+w                                         # 変更あり: "Unsaved: Ctrl+S first"
key ctrl+pagedown key ctrl+pagedown key ctrl+w              # B (保存済み) を閉じる: [2/4] m1c.rb
```

## 4. 仮の操作 (M2 で作り直す)

| キー | 動き |
|---|---|
| Ctrl+N | 無題の文書を足して移る (空いていたキー。新規の慣例) |
| Ctrl+W | 今の文書を閉じる。変更があれば断る。最後の 1 つは空の無題になる |
| Alt+. / Alt+, | 次 / 前の文書 (端で回る) |
| Ctrl+PageDown / Ctrl+PageUp | 同じ。**sim とネイティブ版は Alt を運べない**ので、確認のために足した (ブラウザのタブの切り替えと同じ並び)。今まで Ctrl+PageUp/Down は修飾なしの PageUp/Down と同じ動きだった |
| 状態行 | 2 つ以上のとき、左に `[2/3] ` |

- Ctrl+, はデスクトップのアプリの切り替え (Ctrl+Tab の代わり) なので使わなかった。
- 知らせの文字列 ("Max 5 files open"・"Unsaved: Ctrl+S first") は i18n に載せていない (指示どおり)。

## 5. 見積もりと測れたもの

- 文書の領域: 空の文書を 1 つ足すごとに約 2.1 KB (`doc_add` のログの差: 15,528 → 17,688 → 21,024 → 23,128。行の表の最初の 64 行分)。
- VM のヒープ: 配列 2 本 (整数 12 × 5、文字列 5) と ivar 2 つで、5 文書でも 1 KB 未満の見込み。`regress:run` は流していない (親が M3 の後に流す)。
- PSRAM の静的な表: Spinel 版 +24 バイト、mruby 版 +96 バイト (内蔵 RAM から 32 バイトが移る)。

## 6. チェックポイントでエディタを移せるか (読んだ範囲。試していない)

今のエディタは移せない。(1) 組み込みのアプリ (`default/editor`) で `.app.toml` が無く、`movable = true` を宣言できない、(2) 標準構成のエディタは Spinel で、移せるのは mruby の VM のアプリだけ (spawner の `movable` は `vm_type == FMRB_VM_TYPE_MRUBY` のときだけ)、(3) 本文は VM のヒープの外 (C の領域) にあり、運び方の登録が無い。複数の文書にしても、この事情は変わらない。

## 7. 見立てと違った点・踏んだ罠

- Alt が sim (とネイティブ版) で運べない。指示の Alt+. / Alt+, は sim で確かめられないので、Ctrl+PageDown / Ctrl+PageUp を同じ動きで足した (4 章)。
- MCP の sim_up は `.env` の機種 (NARYAv3) で解像度を照合するので、Modern のビルドでは「426x240 だが 320x240 のはず」で失敗を返す。ただしスタックは上がっていて、sim_screenshot・sim_input・sim_app は 426x240 で使えた。
- 型支援の答えの表が残って `ec_mem_used` が 0 に戻らなかった (2.4)。
- Spinel の罠 (型の絞れない配列・ivar の並び・逃げる proc) は踏まなかった。
