# V1 報告: WAV 再生の口 (play_wav)

指示書 `../instruction_v1.md` の実装記録。sim (Modern / Retro) の検収まで
完了、Tab5 実機の聴取はユーザ待ち。

## できたこと

```ruby
audio.play_wav("/usr/share/sounds/sine440_16k.wav")   # true / false
audio.stop_wav
```

PCM 16bit・モノラル・8000〜48000Hz・2MB までの WAV を、APU の音に重ねて
鳴らす。同時に鳴らせるのは 1 本で、鳴っている最中に呼ぶと入れ替わる。
Retro は呼び手側で false を返し、音側にメッセージを送らない。

## 置き場所

| もの | fmruby-core | fmruby-graphics-audio |
|---|---|---|
| protocol (0x0D/0x0E, 構造体, `FMRB_APU_MIX_RATE`) | `components/fmrb_audio/audio_commands.h` | `main/common/audio_commands.h` |
| 変換ロジック (ヘッダ読解 + リサンプル + 飽和加算) | `components/fmrb_audio/fmrb_wav.{h,c}` | `main/common/fmrb_wav.{h,c}` |
| 再生の実体 | `main/drivers/audio_p4/audio_p4_task.c` | `main/tasks/audio_task.c` |
| コマンド受け | `main/drivers/audio_p4/audio_p4_handler.c` | `main/audio/audio_handler_shm.c` (Linux) / `audio_handler_esp32.c` (WROVER: 1 行ログで拒否) |

**変換ロジックは 1 ファイルにまとめ、両リポジトリに同じ中身で置いた**
(`audio_commands.h` と同じ流儀。冒頭の相互参照コメントだけが違う)。
両方から使える形にするため、この共有ファイルには**ファイルを開くことと
確保を入れていない**: パスの接頭辞 (`/flash` と `flash`) も確保先も
両側で違うので、読み込みは各々が持ち、バイト列を渡してもらう形にした。

読み込みは `load_fmsq_file` と同じ型 — 大きさを見てから確保先へ直接
`fread`。ヘッダを読んだあと、本体を確保の先頭へ `memmove` して int16 の
整列を保証している (data チャンクの開始位置は偶数なのが普通だが、
RISC-V でそれを前提にしない)。中間バッファは作らず 1 サンプルずつ
補間して既存バッファへ加算するので、**音のタスクに増えるスタックは
ローカル数個だけ**。VLA / alloca は無い。非再生時は `playing` を見て
すぐ戻るので、定常状態で走る追加コードは実質ゼロ。

`char full_path[256]` を積むのはコマンド処理の側で、Tab5 ではこれは
**display タスク**で走る (`display_p4_task.cpp` の
`FMRB_LINK_TYPE_AUDIO`)。同じ関数の並びにある `process_load_fmsq_file`
が既に同じ大きさの配列を積んでいるので、そのタスクの山も変わらない。

## 落ちた設計判断

- **後始末をカーネルに足した**。`play_wav` を出した pid を覚え、その
  アプリが落ちたら `stop_wav` を送る (`stop_wav_for`)。音側のバッファから
  鳴り続けるだけで誰も止められない状態を作らないため。曲用の
  `@audio_music_pids` とは別の集合にした: STOP は APU の再生を止め、
  STOP_WAV は PCM を止めるので、WAV しか鳴らしていないアプリの死が
  他人の曲を切ってはいけない。
- **`FmrbApp#sync_file` を足した**。`play_wav` は音側が読める場所へ
  ファイルを置いてからパスを送る (スプライトと同じ型) が、`sync_file` は
  これまで `FmrbGfx` にしかなく、**キャンバスを持たない headless の
  アプリからは呼べなかった**。サービスホストがまさにそれで、指示書の
  使い道 (hourly_chime が `/home/voice/*.wav` を鳴らす) が成立しない。
  同じ C 関数を `FmrbApp#_sync_file` からも引けるようにした。
- **音側の WAV 状態には mutex を置いた** (graphics-audio)。既存の
  プレイヤ群は「ポインタか旗を渡すだけだから排他は要らない」という
  作りだが、WAV の入れ替えは**混ぜている最中のバッファを解放する**ので
  同じ理屈が通らない。P4 側は既存の engine lock に相乗りしている。

## 検収 (sim, Modern)

音は `tools/fmrb_audio_probe.rb --dump` で採り、周波数は 4096 点の DFT
(20-3000Hz を 1Hz 刻み) で測った。

| 見たこと | 結果 |
|---|---|
| 16000Hz の 440Hz を再生 | **440 Hz** (同じ採取に APU の 220Hz を同時に鳴らし、そちらも 220 Hz) |
| 8000Hz の 440Hz を再生 | **440 Hz** (同上、基準も 220 Hz) |
| APU と同時 | 440 と 220 が両方立つ (peak 22220、飽和せず) |
| 飽和 | 振幅 0.98 の WAV + APU: peak が 32768 (レール) で頭打ち、スペクトルは 440 が支配的なまま崩れない |
| 置き換え | 440 の再生中に 880 を投げる → 前半 440 のみ、後半 880 のみ (比は 2.002) |
| stop_wav | 3 秒の採取で鳴った窓 21/60、後半は振幅ゼロ |
| 終了後の放置 | 1 秒のクリップの 2 秒後: `sounding_windows=0 peak=0` |
| ステレオ | `play_wav: ... rejected: not PCM 16-bit mono 8-48 kHz` 1 行、アプリは生存 |
| 壊れたファイル | `play_wav: ... rejected: not a WAV file` 1 行、アプリは生存 |
| 無いパス | 呼び手側で 1 行 + false (音側へは飛ばない) |

### 測り方の注意 (次に測る人へ)

**sim の採取は数 % 速いことがある**。Linux の音タスクは 16ms 周期で
回るので毎秒 63 フレーム = 262 x 63 = **16506 サンプル**を吐くが、
probe が付ける WAV のラベルは公称の 15720Hz。この差はその採取に
乗った音**すべてに同じだけ**かかるので、`440Hz のはずが 450Hz` と
読める採取が普通に出る (実測: 起動直後は 14〜30 フレーム/秒しか
出ておらず、落ち着くと 63 で安定する)。

**確かめ方は「同じ採取の中に APU の既知の音を一緒に鳴らす」**。上の表の
440Hz はすべてこの形で測っており、基準の 220Hz が 220 と出た採取で
WAV も 440 と出ている。基準なしで測ると自分の変換を疑うことになる
(実際に 1 時間溶かした)。APU 側の音高が正しいことは別に裏を取ってある:
220 -> 220、440 -> 440、1000 -> 1008 で、1008 は NES の分周器の
量子化 (`1789773/(16*111)` = 1007.8) と一致する。

## 検収 (sim, Retro)

`FMRB_HW_TARGET=NARYAv3` でビルドして起動。

- `play_wav` が **false**、`play_wav: not supported on this machine (...)`
  が 1 行。graphics-audio 側のログに `play_wav` は 1 件も出ない
  (メッセージ自体が飛んでいない)。
- 既存の音の回帰なし: `note_on(440)` が 440 Hz、鳴った窓 40/40。

## host テスト

`rake test` に `wav:test` を足した (`test/wav/main.c`、ホストの cc で
ビルド、docker も実機も不要)。見ているのは黙って壊れる 2 か所:

- ヘッダ読解: 正規の形、fmt と data の間の未知チャンク (奇数長の LIST を
  含む — 詰め物 1 バイトを数え損ねる walk はここで落ちる)、ステレオ /
  8bit / WAVE_FORMAT_EXTENSIBLE / 4kHz / 96kHz / 空 data / 非 WAV /
  途中で切れたファイルの拒否。
- リサンプル: 16000→15720、8000→15720、48000→15720、15720→15720 の
  4 通りで、**ゼロ交差から測った音高が入力と 2Hz 以内で一致すること**
  (レート誤りは音程に出る、を装置なしで検査する形)。飽和が両側の
  レールで頭打ちになること、加算であって上書きでないこと、終わった
  ストリームが何度呼ばれても無音を足すこと。
- 同梱の 2 本の WAV そのものも読ませている (生成スクリプトが
  `play_wav` の受け付ける形から外れたらここで落ちる)。

`fmrb_wav.c` は両リポジトリで同一なので、これで graphics-audio 側も
覆っている。

## 同梱したもの

- `tool/gen_sine_wav.rb` — 440Hz 正弦の生成。既定で
  `flash/usr/share/sounds/sine440_16k.wav` と `sine440_8k.wav` (各 1 秒) を
  書く。引数で任意の周波数・レート・長さも出せる。頭と尻に 5ms の
  出入りを付けてある (立ち上がりの段差はそれ自体が広帯域の音になるため)。
  ホストの Ruby なので `pack` を使っている (端末側の picoruby には無いが、
  これは PC で走る道具)。
- `flash/home/services/hourly_chime.rb` — `[hourly_chime.config] wav = "..."`
  があればそれを鳴らし、`play_wav` が false を返したら従来の note に
  落ちて 1 行ログ。`flash/home/services.toml` に書き方をコメントで置いた。

## 検収 (Tab5 実機)

WiFi で put + launch (再 flash なし)、ログはシリアルで採取。

- アプリから `play_wav("/usr/share/sounds/sine440_16k.wav")` を 2 回。
  `play_wav -> true`、音側に
  `play_wav: /flash/cache/audio/usr/share/sounds/sine440_16k.wav
  (16000 frames @ 16000 Hz)`。`Guru`/`abort` は 0 件。
- **hourly_chime の wav 設定**: `/home/voice/hour.wav` を置き
  `[hourly_chime.config] wav = "..."` を有効にして再起動 → 時計を
  xx:59 に進めて正時を作り、`svc[hourly_chime] chime for 17:00` の直後に
  `play_wav` が飛んで鳴った。**サービス (headless) から鳴らせることの
  実証**でもある。翌時も同じく鳴る。
- **audio タスクのスタック**: `fmrb_task: audio_p4 Y 0 8192 4436` が
  **再生の前後で 4436 バイト free のまま不変** (high-water は単調悪化
  なので、この値がセッションの最悪値)。混合の側は作業バッファを持たない
  ので、設計どおり増分ゼロ。ファイル読みの `char full_path[256]` は
  display タスクの側にあり、そこは `process_load_fmsq_file` が既に同じ
  大きさを積んでいる。
- 官能 (音として妥当か) はユーザ確認。

### この計測のために足したもの

**audio タスクは `fmrb_task:` の表に出ていなかった** (`xTaskCreatePinnedToCore`
で直接作られており、監視に登録されていない)。指示書の検収が前提にして
いる数字が取れないので、`fmrb_task_create_pinned` に替えて登録した
(`FMRB_TASK_MONITOR_MAX` も +1)。ハンドルを渡さないと登録されない実装
なので、`&s_audio_task` を渡している。副作用として Monitor の Tasks 表に
1 行増える。

### 一度だけ高い chime

初回の chime で `svc[hourly_chime] took 353 ms (over 50)` が出る。
`play_wav` が中で `sync_file` する (32KB の複製) ぶんで、**2 回目以降は
警告が出ない** (CRC が一致するので複製が飛ぶ)。置いたファイルを差し替えた
直後の 1 回だけ、サービスホストがその時間ふさがる。

### 音量について (聴いた印象と実測)

「APU に比べて WAV が小さく聞こえる」という指摘があったので、**実機の
マイク (ES7210) で実際に出た音を測った**。1024 サンプル (47160Hz なので
21.7ms) の RMS。

| 鳴らしたもの | RMS | peak |
|---|---|---|
| 無音 (基準) | 1 | 1 |
| WAV 0.30 FS の 440Hz 正弦 | 117 | 300 |
| WAV 0.60 FS (同梱のテスト音と同じ振幅) | 198 | 476 |
| WAV 0.98 FS | 321 | 654 |
| APU の 440Hz、音量 15 (最大) | 151 | 530 |

- **振幅に対して線形**に出ている (暗騒音を引くと 0.30:0.60:0.98 が
  ほぼ 1:2:3.3)。混合の側で減衰は起きていない。
- **同梱の 0.60 FS のテスト音のほうが、APU の最大音量より大きい**
  (198 対 151)。出力段にも利得は無く、`audio_p4_hw_write` は
  3 倍に伸ばして左右へ複製するだけ。
- では何が「小さく」聞こえたか。**同じ RMS でも矩形波のほうが明るく
  聞こえる**のがいちばん効いている: APU は矩形波で倍音が上まで伸び、
  こちらの試験音は倍音のない純音。加えて、比較したときの APU の音は
  押しっぱなしの持続音で、WAV は 1 秒で切れる短い音だった。
- 実用上の答え: **PC 側で作る声のファイルは正規化しておく**。同梱の
  テスト音を 0.6 にしてあるのは経路の途中で頭打ちにならないことを
  はっきりさせるためで、聴き比べには小さめ。音量指定 (`play_wav` の
  引数) は V1 の「やらないこと」なので入れていない。

## 後日の変更 (V2b で分かったこと)

**Modern では `sync_file` をやめた**。音のドライバは同じファームウェアで
同じファイルシステムを読むので、複製は「**flash への書き込みと 1.9 秒**」を
払っていただけだった。上の表の 1899ms はこれで消える。sim は Modern の顔を
していても音が別プロセスなので、そこでは転送が要る (`FmrbConst::PLATFORM`
で分ける)。

**`fmrb_wav_parse` が data の長さをファイル長で切り詰めるようになった**。
流しながら書かれた WAV は長さが決まらないので data チャンクに 0xFFFFFFFF を
書く (OpenAI の TTS がそう)。以前はそれを壊れた WAV として弾いていた。
途中で切れたダウンロードも同じ扱いで、届いた分を鳴らす。

**Retro では WAV を鳴らさないことに確定した**。音が WROVER の側にあり、
毎回リンクで送ってあちらの flash に書くことになるため。`play_wav` が false
を返す従来の動きはそのまま、方針として plan に明記した。
