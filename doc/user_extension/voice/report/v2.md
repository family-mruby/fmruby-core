# V2 報告: tts サービス (文字列 → WAV の解決役)

指示書 `../instruction_v2.md` の実装記録。

## T0: 生死に関わる下調べ

### 1. TCPSocket にタイムアウトは掛かるか — **掛かる。ただし既定 10 秒で、Ruby から変える口が無かった**

`lib/patch/picoruby-socket/ports/{esp32,posix}/tcp_socket.c` は既に
Family mruby の patch が当たっており、ソケット生成時に
`SO_RCVTIMEO` / `SO_SNDTIMEO` を、connect には select による待ちを
設定している。既定はどちらも `10000` ms。

- `readpartial` は時間切れで `SocketError "read timeout"` を上げる
  (`PICORB_RECV_TIMEOUT`)。**無制限にブロックする読みではない**ので、
  指示書が心配していた「ホストごと固まる」形にはならない。
- `read_nonblock(maxlen)` (would-block なら nil) と `ready?` も公開済み。
- ただし**値を変える口が無い**。10 秒は「死んだ相手」に対する保険としては
  妥当だが、サービスホストは全サービスを順に回すので、1 回の不達で
  10 秒黙るのは長い。

**採った策**: `TCPSocket.timeout_ms=` / `TCPSocket.timeout_ms` を足した
(指示書の選択肢のうち「小さな C の timeout setter」)。

- ポート側 (`ports/{esp32,posix}/tcp_socket.c`) の固定マクロを静的変数に
  変え、`TCPSocket_set_timeout_ms()` / `_get_` を足した。**connect と
  recv/send の両方**に効く。
- Ruby への登録は**patch 済みの `src/mruby/socket.c` の gem_init 内**で
  行った (`tcp_socket_init` の後にクラスを引いて class method を足す)。
  こうすると**上流の `src/mruby/tcp_socket.c` を patch セットに増やさずに
  済む** — 追随の手間が増えないほうを選んだ。
- **ソケット 1 個の属性ではなく、以後に開くソケットの既定値**。connect こそ
  縛りたいのに、それは `TCPSocket.new` の中で起きて設定する対象がまだ
  無いため。使う側は「設定 → 仕事 → 戻す」で囲む。UDP (SNTP) は別ファイル
  なので影響しない。

### 2. VOICEVOX の素振り

**この作業機に VOICEVOX は無い** (localhost:50021 も Windows ホスト側も
応答なし)。そこで**偽サーバを先に作り**、そちらで経路を固めた
(`tool/fake_voicevox.rb`。指示書は tools/ か test/ とあるが、core 側の
道具は `tool/`)。

- `POST /audio_query?text=..&speaker=N` → JSON (`Content-Length` つき)
- `POST /synthesis?speaker=N` → WAV (`Content-Length` つき)
- 返す WAV は **24000Hz 16bit mono** (本物の既定と同じ。play_wav の
  対応内で、APU の 15720Hz とは違う値なので、変換を間違えれば音程に出る)。
- 文面から音高を決めている (`base + (bytes.sum % 8) * 55Hz`) ので、
  別の文が来たことをスペクトルで判別できる。
- `--delay-ms` で応答を遅らせ、`--truncate` で「Content-Length は本物、
  中身は 1/3 で切断」を再現できる (時間切れと半端ファイルの検査用)。

**本物との差で注意すべき点**: 実 VOICEVOX は uvicorn なので既定で
keep-alive。こちらは常に `Connection: close` を返す。クライアント側は
`Connection: close` を送って本物にも閉じさせる形にする (下記 T1)。

### 3. キャッシュ鍵のハッシュ

`MbedTLS::Digest` は gem に存在する (`update` / `finish`)。ただし
**`picoruby-mbedtls` は現在の gembox に入っていない** (`picoruby-socket`
が引き込む形で ESP32 側にはあるが、Linux sim の構成では確認が要る)。
依存を増やさない判断で、**鍵は djb2 系の自前ハッシュ + 文字列長**にした
(指示書が許している代替)。衝突しても実害は「別の文が同じキャッシュに
当たる」だけで、確率も実用上無視できる。

### T0 のあと分かった追補 (実装中に踏んだ)

上の「タイムアウトは掛かる」は**半分しか本当でなかった**。実際に動かして
2 つ出た。

1. **posix / esp32 とも、ブロッキングの `recv` が `EINTR` を再試行して
   いなかった**。FreeRTOS の Linux ポートはティックを signal で駆動する
   ので、sim のブロッキング読みは**始終割り込まれる**。結果、相手が数 ms
   でも考えると読みが即座に失敗し、`RuntimeError: read failed` が返る
   (`send` 側は既に再試行していた。読みだけ抜けていた)。
2. **`SO_RCVTIMEO` の満了 (`EAGAIN`) を `-1` に潰していた**ので、mruby 層に
   ある `PICORB_RECV_TIMEOUT` → `SocketError "read timeout"` の枝は**存在
   するのに誰も到達できなかった**。時間切れが「読み失敗」と区別できない。

両方を patch セットで直した (`ports/{esp32,posix}/tcp_socket.c`)。さらに、
**EINTR で再試行すると `SO_RCVTIMEO` のタイマーが引き直される**ため、
signal が絶えない環境では socket 側の時間切れが永遠に来ない。再試行の
経過時間を自前の単調時計で数え、上限を越えたら時間切れとして返す。

これを入れる前後の実測 (応答を 6 秒遅らせるサーバ、timeout_ms=3000):

| | 呼び出しが戻るまで |
|---|---|
| 入れる前 | **6015 ms** (socket の時間切れが効かず、Ruby 側の締切だけが頼り) |
| 入れた後 | **3010 ms** (`SocketError: read timeout`) |

## T1: 最小 HTTP クライアント

`TtsHttp` を **tts.rb と同じファイル**に置いた (指示書は実装者判断)。
理由: 80 行しかなく、他に使い手がまだ居ない。サービスは 1 ファイルで
require が 1 回で済むほうが分かりやすい。汎用 gem 化はしない。

- POST のみ。`Content-Length` の本文だけ (chunked 非対応)。`Connection:
  close` を送るので、本物の VOICEVOX (keep-alive 既定) にも閉じさせる。
- 応答上限 2MB (play_wav と同じ)。ヘッダは 16KB で打ち切り。
- **二重の締切**: 1 回の `readpartial` は socket の時間切れで縛られ、
  やり取り全体は `Machine.board_millis` の締切で縛る。相手が 1 バイトずつ
  垂らしても、サービスホストを設定値より長くは塞がない。
- `TCPSocket.timeout_ms` は使う前に設定し、`ensure` で元に戻す
  (プロセス共通の既定値なので、他のソケット利用者に持ち越さない)。

**picoruby には `Regexp` が無い**。最初はステータス行と Content-Length を
正規表現で取っていて、host テストは通るのに実機で
`NameError: uninitialized constant Regexp` になった。今は手で切り出して
いる。**host テストに「サービスのファイルに正規表現リテラルが無いこと」を
1 つ足した** — ホスト側には Regexp があるので、これが無いと同じ穴に何度でも
落ちる。

## T2: tts サービス

`flash/usr/share/services/tts.rb` (`config/services.toml` に既定 enable で
登録)。契約は指示書どおり: `tts/say` を購読、`{"text"=>..}` (任意で
`"speaker"`)、解決して `ctx.audio.play_wav`。

**キャッシュ鍵に落とし穴が 1 つ**。鍵は指示書どおり server + speaker + text
なので、**設定から `server` の行を消すとキャッシュが引けなくなる**
(鍵が変わるため)。オフラインで運用したいときは**行を残したまま届かない
ままにする**のが正解で、その場合は 1 回の接続拒否 (即座) とログ 1 行で
済み、既に言ったことは全部鳴る。config と service の両方に書いた。

## T3: 検収 (sim, Modern)

偽サーバ `tool/fake_voicevox.rb` を使用 (指示書は tools/ とあるが、core 側の
道具は `tool/`)。**docker から PC へは `host.docker.internal`
(= 192.168.65.254) で届く** — Docker Desktop 構成なので、bridge の
gateway (172.19.0.1) では届かない。設定には数値で書いた
(`http://192.168.65.254:50021`)。

| 見たこと | 結果 |
|---|---|
| `tts/say` → 合成 → 再生 | 鳴った。鳴った窓 60/60 |
| 音高 (24000→15720 の変換) | 偽サーバの公称 990Hz が **1013Hz**、同じ採取の APU 基準 220Hz が **225Hz**。**比は 1.0232 と 1.0227 で一致** = 変換は正確 (V1 の教訓どおり、絶対値ではなく基準との比で読む) |
| 2 回目の同文 | `cache hit`、**偽サーバを止めた状態で鳴る** |
| 不達 (サーバ停止) | `audio_query failed (SocketError: connect(...): Connection refused)` 1 行、ホスト健在 (heartbeat 継続) |
| 応答が遅い (6 秒) | `audio_query failed (SocketError: read timeout)`、**3010 ms で戻る**、ホスト健在 |
| 途中切断 (`--truncate`) | `synthesis failed (truncated: 16014 of 48044 bytes)` 1 行。**キャッシュは増えず `.part` も残らない** |
| server 未設定 | `tts ready (cache only)` / `not cached and no server` 1 行 |
| 50ms 警告 | `svc[tts] took 3010 ms (over 50); count=1` — **pid ではなくサービス名**が出る (S1 のまま) |

### 所要時間の実測と、その中身

| | 実測 |
|---|---|
| キャッシュヒット → 再生開始 | **10 ms** |
| キャッシュミス (合成込み) → 再生開始 | **1934 ms** |

1.9 秒の内訳を計装して測ると、**HTTP は 29-32 ms** (audio_query +
synthesis、48KB)、キャッシュへの書き込みは 0 ms、残り **1899 ms は
`play_wav` の中の `sync_file`** だった。つまり**遅いのはネットワークでは
なく、音側へファイルを渡す V1 の経路**。sim では graphics-audio が別
プロセスなので 48KB の転送に 1.9 秒かかる。Modern 実機は同一 FS の複製で、
V1 の実測では 32KB が 353 ms、2 回目以降は CRC 一致で 0。

指示書の「合成中 (~1-2 秒) は他のサービスを待たせる」は満たしているが、
**待たせている理由は合成ではなく転送**である点は記録しておく価値がある
(速くしたいなら手を入れる先が違う)。

## V2b: クラウド TTS (調査のみ、実装せず)

指示書の 4 点について。

- **CA の焼き込み方 — 要らない**。esp32 の SSL ポートは
  `esp_crt_bundle_attach` を**既定で呼んでいる** (`ports/esp32/ssl_socket.c`)
  ので、公開サイトへの HTTPS は最初から検証が通る。私設 CA が要るときだけ
  `SSLContext#set_ca_pem` (非 POSIX では `ca_file=` が Ruby 側で
  File.read → set_ca_pem に化ける)。検証を切るなら
  `verify_mode = SSLContext::VERIFY_NONE`。既定は
  `MBEDTLS_SSL_VERIFY_REQUIRED`。
- **時刻の前提 — 満たしている**。証明書の有効期間の判定に正しい時計が
  要るが、SYS1 の timesync が起動直後 (net/state を受けて) に合わせる。
  順序だけ注意: TLS を使うサービスは timesync より先に走らせない
  (`tts` が実際に喋るのは topic 到着時なので実害は無い)。
- **鍵の置き場**: `/home` に平文。開発ビルドでは rd_http の `/fs` から
  読めることも含め、plan の方針どおり個人機として許容。
- **応答サイズ**: 本 HTTP クライアントの上限は 2MB。16kHz 16bit mono なら
  約 60 秒ぶんで、1 文には十分。ただし**返し方が社によって違う**:
  - 生の音声を本文で返すもの (OpenAI TTS の wav/pcm、Amazon Polly の pcm)
    → **そのまま今の経路に乗る**。
  - JSON の中に base64 で入れて返すもの (Google Cloud TTS の LINEAR16)
    → **復号が要り、転送量も 4/3 になる**。`picoruby-base64` は picoruby に
    存在するが**現在の gembox には入っていない**ので、採るなら gembox に
    足す 1 行が要る。
- 未確認で残るもの: **TLS 1 接続あたりのヒープ実測** (plan の見積もりは
  ~50KB)。サービスホストの VM は 512KB なので、実装するなら最初に測る。

## やらなかったこと

指示書の「やらないこと」のまま: クラウドの実装、再試行、読み上げの
待ち行列 (同時に来たら後勝ちで置き換え)、キャッシュの自動掃除、

警告するだけ (掃除は `rmr /home/voice/cache`)。

## T3: 検収 (Tab5 実機)

WiFi で put + launch、ログはシリアル。

- **キャッシュヒットで喋る**: 鍵 (server+speaker+text の djb2) を PC 側で
  計算して WAV を `/home/voice/cache/` に置き、同じ文を `tts/say` に流す →
  `tts: cache hit (おはようございます)` →
  `audio_p4: play_wav: ... (36000 frames @ 24000 Hz)`。**24000Hz の WAV を
  実機が読み込んで鳴らすところまで確認**。`Guru`/`abort` は 0 件。
- **接続の時間切れが実機でも効く**: 届かないサーバに対して
  `SocketError: connect(...): Connection timed out` が **3048 ms** で返り
  (`timeout_ms = 3000`)、`svc[tts] took 3048 ms` の警告つきでホストは健在。
  T0 で足した設定機構が実機で効いていることの確認でもある。

### 実機での LAN 合成は未確認 (環境の都合)

**この作業機からは偽サーバを実機に見せられなかった**。WSL は mirrored
networking で LAN の 192.168.10.2 を直接持っているが、**Windows の
firewall が受信を塞いでおり、Windows 自身からも 192.168.10.2:50021 へ
繋がらない**。開けるには管理者権限が要るのでこちらでは触っていない。

ユーザ側で確かめるなら、どちらかで届く:

- 管理者の PowerShell で 1 回だけ穴を開ける
  `New-NetFirewallRule -DisplayName "fake-voicevox" -Direction Inbound
  -LocalPort 50021 -Protocol TCP -Action Allow`
  そのうえで `ruby tool/fake_voicevox.rb`、実機の
  `[tts.config] server = "http://192.168.10.2:50021"`。
- あるいは**本物の VOICEVOX を Windows 側で動かす** (こちらが本来の使い方。
  ポートは既定で 50021、`server` にその PC の LAN IP を書く)。

sim 側では同じ経路 (audio_query → synthesis → キャッシュ → 再生) を
すべて通してあるので、残っているのは**実機から LAN 越しに繋ぐ 1 点**と
**官能評価**だけ。
