# 実装報告: Raycaster の計算を Spinel gem 化 (R1-R5)

対象: `doc/raycast_spinel/plan.md` / 実施: 2026-08-14 / ブランチ: `develop` (未コミット)
実機: M5Stack Tab5 (ESP32-P4)、`FMRB_HW_TARGET=TAB5`

## 結果: 実機で 49 倍

**R1-R5 全て完了**。同じ Ruby ソースを mruby と Spinel で走らせ、**絵は 1 ピクセルも
変わらないまま、レイキャストの時間だけが変わる**デモになった。

### 実機 (Tab5 / ESP32-P4) — 1 フレーム 25 本のレイ

同一視点で 3 回ずつ (`right`+`left` で角度を戻して再計算させた値):

| engine | 実測 (us) | 比 |
|---|---:|---:|
| `:ruby` (mruby VM) | 11,327 / 11,824 / 11,957 | 基準 |
| `:spinel` (AOT)    | 227 / 230 / 246 | **約 49x 速い** |

- 中央値でおよそ **11.8ms → 0.23ms**。
- 視点によって DDA のステップ数が変わるので比も動く。起動直後の視点では
  `:spinel` 189us だった (`:ruby` の起動直後 1 回目は 16,146us だが、これは
  mruby の暖機を含むので比較には使わない)。
- Guru/abort ゼロ。IRAM 空きは 71,440 バイトで一定 (受け皿の static は全て
  PSRAM、インスタンスのプール 128KB も `fmrb_sys_malloc` = PSRAM)。

### Linux sim (x86-64、同一ビルド)

| engine | 実測 (us) |
|---|---:|
| `:ruby`   | 48〜57 |
| `:spinel` | 6 |

**ホストでは約 8 倍**。実機で 49 倍まで開くのは、ホストの mruby VM が速い
(分岐予測とキャッシュが効く) 一方、**MCU では VM のバイトコード解釈が相対的に
ずっと高くつく**ため。

### FFT との対比 (このデモの主張)

| 題材 | 演算 | mruby 対 Spinel |
|---|---|---:|
| FFT (double) | 浮動小数点 | 11.5x |
| FFT (Q15) | 整数 | 76.9x |
| **Raycaster** | **整数 (元から固定小数点)** | **49x** |

FFT の double 版で差が 11.5 倍に留まったのは、**両者とも double ソフトフロート税を
払っていた**ため (`doc/mic_spectrum/report/track_a.md` E1)。raycaster は元から
固定小数点なのでその税が無く、**言語処理系の差がそのまま出る**。plan の
「整数主体のコードでこそ Spinel が効く」がそのまま数字になった。

## 正しさ

2 段階で確認した。**どちらも「絵が似ている」ではなく厳密一致**。

1. **抽出が忠実か (CRuby)**: 元アプリの `cast_ray` を git から取り出し、
   抽出した `RaycastCore` と総当たりで比較。**開いているセル全部 x サブセル
   3 位置 x 7 度刻みの全方位 = 13,884 フレーム、不一致 0**。
   `{dist:, wall:, side:}` が 25 本とも完全一致。
2. **2 エンジンが一致するか (実機同等の Linux sim)**: **同一プレイヤー状態**で
   `:spinel` と `:ruby` の画面を撮り、HUD 行を除いた描画領域を PNG 比較 →
   **差分ピクセル 0**。実機でも同一視点の 2 枚が目視で一致。

## 境界設計

- 入力: マップ (`:binstr` + w/h/世代)、プレイヤー (px/py/pa の `:int` 3 本)。
- 出力: 深度バッファ (`:binstr`)。**1 レイ 6 バイト = dist(int32 LE) + wall + side**。
  `dist` を int32 にしたのは `VP_H*CELL_SIZE/dist` の分母で、実測で 6 桁に達するため。
- **Float は 1 つも境界を渡らない**。三角 LUT の Float は core の初期化内だけ。

## つまずいた点 (次に効く知見)

- **`::Math.sin` は Spinel で黙って壊れる**。`::` 付きだと型が unknown になり、
  コンパイラは**エラーを出さずに `.to_i` の位置に NoMethodError の raise を
  埋め込む**。生成 C を読んで初めて分かる:
  ```c
  sp_IntArray_push(self->iv_sin_tbl, (sp_raise_cls("NoMethodError",
    sp_stage_args_msg("undefined method 'to_i' for unknown", ...)), 0));
  ```
  実機では entry 初回で firmware ごと落ちる (Spinel の raise は捕まえる人が
  いない)。**裸の `Math.sin` / `Math.cos` を使う** (fft_core.rb が実証済み)。
  → `ruby_writing_constraints.md` に追記した。
- **`rake` 側の `any_spinel` が CMake 側とずれていた**。SpinelHello と raycast は
  「常にビルドされる」Spinel gem なのに、生成は `FMRB_FFT_SPINEL` 等が真のときだけ
  走る条件になっていた。`FMRB_FFT_SPINEL=0` かつ全エンジン mruby の構成で
  **cmake が FATAL_ERROR** になる。CMake の `FMRB_ANY_SPINEL` は既に常時 TRUE
  だったので、rake 側も常時 true に揃えた。
- **アプリ側にも三角 LUT が要る**。plan は「LUT をアプリから削除」としているが、
  移動 (`update_player`) と敵の描画 (`draw_enemies`) が `fp_sin`/`fp_cos` を使う。
  境界の向こうの core の LUT は毎フレーム引けないので、**`Fmrb::Raycast` が
  mruby 側に自前の LUT を持ち**、アプリはそれを使う形にした。backend に依存
  しないので、**B を押しても移動と敵の挙動は変わらない** (比較対象がレイ
  キャストだけに絞られる、という利点もある)。

## 残り

- `NUM_RAYS` がアプリと core の両方にある (アプリは描画の帯幅、core はレイ数)。
  片方だけ変えると壊れるので、アプリ側にコメントを入れてある。定数を 1 か所に
  するなら gem の値をアプリが読む形にできる。
- マップは可変にしてあるが (`set_map` + 世代)、**デモは 12x12 固定でしか
  試していない**。上限は `RAYCAST_MAP_MAX` = 64x64。
- プールは 128KB 固定。`begin` は成功しているが、**下限は詰めていない**。
