### 移したものが安全と言える理由

共通の前提: PSRAM に置いてはいけないのは (a) DMA が読み書きするもの、(b) 割り込み (特に IRAM の ISR) から触るもの、(c) flash の書き込み中 (キャッシュが止まっている間) に読むもの、(d) flash 書き込みの元になるもの (このプロジェクトの経験則: `s_file_write_bounce` のコメント)。
普通のタスクのコードは flash 上にあるので、キャッシュが止まっている間はそもそも走らない。よって「タスクからしか触らず、DMA にも flash 書き込みにも渡らない」なら PSRAM で問題ない。各項目で次を確かめた。

- **ISR が無いこと**: 対象のファイル (display_p4、audio_p4、usb、fmrb_hal、transport、midi、editor、spx) を `IRAM_ATTR` / `FromISR` / 完了コールバックで検索し、該当は SPI リンク (`fmrb_hal_link_esp32.c`、今回触っていない) だけだった。budget.md の「コードベース全体に *FromISR 送信が無い」(2026-08-02) とも合う。
- **tmpfs**: ファイル本体は既に `POOL_ID_TMPFS` (PSRAM) にあり、表はその索引。VFS 経由でタスクからしか呼ばれない。
- **display_p4**: `g_progs` はバイトコードの解釈器が読むだけ、`g_recv_buf` はメッセージバッファの memcpy 先、`g_canvases` は POD の管理表 (PPA に渡るのは別に確保したバッファのポインタ)、`s_cursor_save` はフレームバッファ (PSRAM) との CPU の写し合い、`g_sorted` は並べ替えの作業領域、`g_masks` は管理表 (ビット列は別確保)。PPA / pushImage に直接渡る `block` と `scaled` は移していない。
- **link_local**: `xMessageBufferReceive` は CPU の memcpy。
- **editor**: 行の本文は PSRAM のアリーナ。表は 1 タスクからだけ。`g_oom` (jmp_buf) は setjmp/longjmp で CPU が読み書きするだけ。
- **MIDI**: esp_timer の `ESP_TIMER_TASK` (タスク文脈) で取り出す。serial の出口は `fmrb_hal_uart_write` → UART ドライバが自分のリングへ写す。この関数には元から mruby の文字列 (PSRAM) が渡っている。
- **spx**: Spinel に返すレコード。呼んだタスクが書き、同じタスクが読む。`fmrb_spx_app_config` のバッファは P2 から既に PSRAM で同じ扱い。
- **usb**: HID ホストのコールバックはドライバのタスク文脈。レポートは `hid_host_device_get_raw_input_report_data` でスタックの配列に写してから使う。`g_input_reports` は以前から PSRAM。
- **transport**: 文脈はコールバック表・保留表・同期要求表・分割の管理情報で、中身はポインタと長さ。フレームは別の確保。
- **reps (flash)**: `mrb_irep.reps` の型は `const struct mrb_irep *const *` で、静的な irep (`MRB_IREP_STATIC`) は解放も書き換えもしない。Linux ではこの配列が読み取り専用の区画に入るので、書き込みが残っていれば sim で SIGSEGV になる。sim の 2 構成で起動・エディタ・アプリまで通った。

## 5. mruby の gem_init / picogem_init の .data

- 生成しているのは host の mrbc (`mrbc -B`)。使っているのは picoruby の `mrbgems/mruby-compiler/src/cdump.c` で (mruby 本体の `lib/mruby/src/cdump.c` はターゲット側に入るだけ)、472 行目が `static const mrb_irep *%s_reps_%d[%d]` と配列自体を const にしていなかった。
- `lib/patch/compiler/mruby-compiler-cdump.c` (丸ごとの写し、1 行だけ `*const` を足した) を `rakelib/setup.rake` で既存の compile.c / ccontext.c と同じように上書きする。submodule は直接触っていない。mruby-compiler の submodule が動いたら写しを取り直す必要がある (setup.rake のコメントに書いた)。
- 残る .data: `*_proc_syms_*` 568 B は presym でない記号を起動時に書き込むので const にできない (生成器もそう判断して const を外している)。`prebuilt_gems` 220 B は `picoruby-require/templates/mruby/picogem_init.c.erb` の `const char *prebuilt_gems[]` を `const char *const` にすれば flash に行くが、`src/mruby/require.c` の `extern` も合わせて直すことになり、写しが 2 本増える。量が小さいので今回は見送った (判断してほしい点 2)。

| `s_fs_buf` (devctl) | 4,096 | PSRAM | ここから fwrite する。LittleFS は書く前に自分のキャッシュ (内蔵) へ写すはずで、SD は sdmmc が DMA 可能でない元を跳ね返す。`s_file_write_bounce` のコメント (「PSRAM の元から flash に書くと黙って失敗する」) がどの経路の話かを確かめる。同じ理由が消えれば `s_file_write_bounce` 自体も要らなくなる |
| `scaled` / `block` (PPA の経路) | 4,608 + 512 | PSRAM | LovyanGFX の pushImage が DMA を使うか。使うなら残す |
| `s_stereo_buf` / `s_mic_buf` | 4,192 | PSRAM | i2s_channel_read/write が写すことの確認と、音の途切れ (実時間) |
| `pm_binding_powers` | 1,980 | flash | prism.c を丸ごと写すのは重い。libmruby は `add_prebuilt_library` の輸入ライブラリで ldgen の対象外 (`build/ldgen_libraries` に無い) なので、配置の断片 (.lf) も効かない。rake で作った libmruby.a の prism.o に `objcopy --rename-section .data.pm_binding_powers=.rodata.pm_binding_powers,...` を当てる後処理なら元を触らずに済む。新しい仕組みなので判断を仰ぐ |
| Spinel の `cst_*` / `pool_count` / `pool_max` | 689 (173 個) | PSRAM | フォークの変更が要る。`SP_TU_NIL_SLOT` と同じく `SP_TU_BSS` を付けて出す。P4 (RISC-V) では明示の区画属性を付けた変数は gp 相対の小さいデータ扱いにならないので、それで .sbss から外れる。`cst_` のポインタは GC の根として印付けのたびに読むので、GC の停止時間を前後で測る |
| apu_emu の `apu` / 表 | 1,000 | PSRAM / const | 外部由来のコード。`apu` は 1 サンプルごとに触るので速度を測る。`trilength_lut` は起動時にサンプル数から計算するので const にはできない |
| link_local のメッセージバッファ (実行時の確保) | 8 KB + 2 KB (チャネルごと) | PSRAM | map に出ない実行時の確保。キューの PSRAM 化 (6ea5911) と同じ `xMessageBufferCreateStatic` + PSRAM の手でいける見込み。FromISR が無いことは確認済み |
| 小物 (`g_put_cache` `s_sync_cmd_buf` `g_file_transfer` `prebuilt_gems` など) | 約 1 KB | PSRAM / flash | 量が小さいので後回し |

## 8. sdkconfig の提案 (編集していない)

IRAM (コード) と IDF の配置は sdkconfig でしか動かせない。どれも「その機能を割り込みから、または flash 書き込み中に使わない」ことが条件で、速度が落ちる。P4 の IRAM 87,936 B の内訳は esp_hw_support 20.8 KB、freertos 17.5 KB、spi_flash 9.9 KB、hal 8.3 KB、heap 5.9 KB、ringbuf 3.0 KB、rmt 2.7 KB ほか。S3 は freertos 13.4 KB、btdm 13.3 KB、esp_hw_support 12.9 KB、spi_flash 10.9 KB、hal 10.7 KB、heap 5.2 KB、spi_master 4.4 KB、ringbuf 2.6 KB、rmt 2.5 KB ほか。

| 設定 | 見込み | 条件・懸念 |
|---|---:|---|
| `CONFIG_RMT_TX_ISR_HANDLER_IN_IRAM` / `RX` / `CONFIG_RMT_ENCODER_FUNC_IN_IRAM` を off | 約 2.5 KB | RMT (状態 LED など) が flash 書き込み中に止まってよいなら |
| `CONFIG_SPI_MASTER_ISR_IN_IRAM` / `SPI_SLAVE` を off (S3) | 約 4.4 KB | SPI の転送が flash 書き込み中に止まってよいなら。SPI リンクを使う構成では要確認 |
| `CONFIG_RINGBUF_PLACE_FUNCTIONS_INTO_FLASH` | 約 2.6-3.0 KB | UART ドライバの ISR がリングバッファを使うので、UART の ISR を IRAM に置く設定とは両立しない |
| `CONFIG_HEAP_PLACE_FUNCTION_INTO_FLASH` | 約 5 KB | IRAM の ISR から確保しないこと。確保が遅くなる |
| `CONFIG_FREERTOS_PLACE_FUNCTIONS_INTO_FLASH` | 10 KB 以上 | 全体が遅くなる。最後の手段 |
| `CONFIG_LWIP_*` の PSRAM 配置 / `CONFIG_MDNS_TASK_CREATE_FROM_INTERNAL` を off | 約 3-4 KB | lwIP の表を PSRAM へ。mDNS のタスクの確保先 |
| P4 の `CONFIG_ESP_WIFI_*_IRAM_OPT` | 不明 | P4 は esp_hosted で WiFi ライブラリを持たないので、効いていないはず。IRAM の map に libpp などが無いことで確認できる |

## 10. 判断してほしい点

1. **R2 の最初の対象**: 量で選ぶなら `s_fs_buf` + `s_file_write_bounce` (8 KB、flash 書き込みの元の条件を確かめれば両方消せる可能性)、次いで link_local のメッセージバッファ (実行時 10 KB、手はキューと同じ)。
2. **`prebuilt_gems` (220 B)** のために写しを 2 本 (テンプレートと require.c) 増やすか。
3. **`pm_binding_powers` (1,980 B)** を、rake で作った libmruby.a への objcopy の後処理で flash に出す方式を採るか (元のソースを触らない新しい仕組み)。
4. sdkconfig の提案 (8 章) のうち、試す価値があるもの。RMT と SPI の IRAM の ISR を外すのが条件の軽い順。
