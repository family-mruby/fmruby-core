## 3. T1: sdkconfig を変えた場合の見積もり (変更はしていない)

### 3.1 1 設定ずつの値 (develop に対する静的な D/IRAM の差、バイト)

どれも減るのは IRAM (コード) で、同じだけ flash のコードが増える (flash の増え方は減り方とほぼ同じ)。
S3 の IRAM は 16 KB の専用区画が埋まっていて、溢れた分が D/IRAM に載っているので、S3 でも減った分はそのまま D/IRAM の空きになる。

### 3.3 条件・懸念・推奨

「条件」はコードで確かめたこと。「flash 書き込み中に動く必要があるか」は、IRAM に置く意味がそれだからである (キャッシュが止まっている間は flash のコードは走れない)。

| 設定 | 条件 (確かめたこと) | 速さへの見込み | 懸念 | 推奨 |
|---|---|---|---|---|
| RMT | RMT を使うのは RMT gem (`lib/add/picoruby-rmt-proxy` → `main/drivers/hw_proxy/hw_proxy_rmt.c`) だけで、使うアプリは LED マトリクスのデモ (WS2812) だけ。**状態 LED は GPIO** (`status_led.c`)、RMT ではない。受信 (RX) は使っていない。チャネルは割り込みの IRAM 指定なしで作っていて、`RMT_TX_ISR_CACHE_SAFE` も n なので、今でも flash 書き込み中は RMT の割り込みは止まる。しかも符号化のコールバック `encoder_callback` は今でも flash にある (IRAM_ATTR が無い) | RMT の割り込み (シンボルの補充) が flash から走る。キャッシュを外すと数 us 遅れうる | WS2812 は補充が遅れると色が崩れる。ただし符号化のコールバックは既に flash なので、増える遅れは割り込みの入口の分だけ | **採用** (LED マトリクスを実機で 1 回点ければ十分) |
| SPI (S3) | S3 で SPI master を使うのは SD カード (SDSPI、`fmrb_hal_file_esp32.c`) と、既定では使わない SPI リンク (`CMAKE_OPTS=-DFMRB_LINK_TRANSPORT=SPI`)。どちらも `spi_bus_initialize` の割り込み指定は 0 (IRAM 指定なし) なので、今でも flash 書き込み中は止まる。SPI リンクの GPIO の割り込み (`ready_gpio_isr_handler`、IRAM_ATTR) は `xSemaphoreGiveFromISR` だけで、SPI ドライバの ISR ではない。P4 は SPI master を使っていない | SD の 1 回の転送ごとに割り込みが flash から走る。SD over SPI の速さが少し落ちうる | 一緒に外れる GDMA の制御関数を S3 で使うのは SPI の DMA だけ (S3 の core に I2S / LCD は無い) | **S3 は実機で確かめてから** (SD の読み書きの速さ)。P4 は効果 0 |
| ringbuf (タスク用) | タスク用の関数をキャッシュが止まっている間に呼ぶところは無い (自前のコードに ringbuf の直接の利用は無い。使うのは IDF の UART / USB シリアル / I2C / ADC ドライバ) | リングバッファを使うドライバ (UART リンク、コンソール) の送受信が少し遅くなる | 無し | **採用** |
| ringbuf (ISR 用) | ISR 用を flash に置けるのは、IRAM 指定の割り込みから ringbuf を呼ぶドライバが無いとき。リンクされている利用者は UART (`UART_ISR_IN_IRAM` は 3 機種とも n。Kconfig がこれと両立させない)、USB シリアル (`esp_intr_alloc(..., 0, ...)`、IRAM 指定なし)、I2C (`I2C_ISR_IRAM_SAFE` n)、ADC (`ADC_CONTINUOUS_ISR_IRAM_SAFE` n)。S3 の BT のライブラリは ringbuf を参照していない | S3 の UART リンク (921,600 bps) の受信割り込みがリングへ積む処理が flash から走る。UART の割り込み自体が既に flash なので、性質は変わらない | **将来 `UART_ISR_IN_IRAM` を y にしたくなったら (S3 で flash 書き込み中の UART の取りこぼしを減らすなど)、この設定とは両立しない** | **採用候補** (S3 は UART リンクの取りこぼしが増えないかを実機で見る) |
| heap | IRAM の ISR から heap を呼ぶ自前のコードは無い (自前の IRAM_ATTR は SPI リンクの GPIO の割り込み 1 つだけ)。Kconfig: `SPI_MASTER_ISR_IN_IRAM` が `!HEAP_PLACE_FUNCTION_INTO_FLASH` に依存するので、これを y にすると SPI master の ISR も必ず flash に行く。S3 の `libbt` は `heap_caps_malloc` を参照している (どの文脈から呼ぶかは追えていない) | **確保と解放が全部 flash から走る**。lwIP、msgpack-c (素の malloc)、fmrb_sys_malloc、newlib。描画の命令ごとの確保がある経路は遅くなりうる | S3 の BLE (コントローラ・ホスト) の中で IRAM の割り込みから確保しないかが未確認 | **実機で確かめてから** (P4 は描画と WiFi の速さ、S3 は加えて BLE と SD) |
| FreeRTOS | ISR 用の関数は IRAM に残る (`FREERTOS_PLACE_ISR_FUNCTIONS_INTO_FLASH` は `SPI_FLASH_AUTO_SUSPEND` が要るので選べない)。キャッシュが止まっている間にタスク用の API を呼ぶ自前のコードは無い。Kconfig: `SPI_MASTER_IN_IRAM` がこれと両立しないが、使っていない | **キュー・セマフォ・メッセージバッファ・遅延の全部が flash から走る**。このファームはメッセージ駆動 (描画の命令ごとにキューとセマフォ) なので、4 つの中で一番速さに効く見込み | 大きな Spinel / mruby のコードで flash のキャッシュが入れ替わると、RTOS の呼び出しのたびに読み直しになる | **実機で速さを測ってから** (単独で最大の -11.9 KB。ユーザの方針 (速度より RAM) なら候補) |
| lwIP の PSRAM 配置 | S3: 既に `SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` で、lwIP の .bss も PSRAM (内蔵に残るのは 12 B)。**P4: lwIP の .bss (約 4,093 B: `dns_table` 1,184 B ほか) は sdkconfig では動かせない**。lwip/linker.lf の `* (extram_bss)` が使う scheme `extram_bss` は esp_wifi の linker.lf が定義していて、WiFi をローカルに持たない P4 のビルドではそれが登録されないため、何も起きない (生成された sections.ld に liblwip の規則が無いことを確認)。`SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` は実行時の確保 (lwIP の mem_malloc) を PSRAM 優先にするだけで、静的には +100 B | 実行時の確保が PSRAM になると、送受信の経路が PSRAM を触る | P4 で lwIP の pbuf が esp_hosted の SDIO の DMA にそのまま渡るかが未確認 (渡るなら PSRAM で良いかを確かめる要がある) | P4 の `SPIRAM_TRY_ALLOCATE_WIFI_LWIP`: **実機で確かめてから** (空きの増え方と WiFi の転送)。P4 の静的な lwIP は、自前の linker fragment で scheme を足す別の手が要る (sdkconfig の範囲外、R4 の候補) |
| mDNS | `MDNS_TASK_CREATE_FROM_SPIRAM` は `FREERTOS_TASK_CREATE_ALLOW_EXT_MEM` (3 機種とも既に y) が要る。mDNS のタスクは flash に触らない (送信は静的な `packet` から lwIP へ)。TCB (`mdns_task_buffer` 348 B) は内蔵のまま | mDNS の処理が PSRAM のスタックで走る。頻度は低い | PSRAM のスタック (軸 B) の一種。スタック上のバッファを DMA に渡していないかは mdns の中を読み切っていない | **実機で確かめてから** (`fmruby-XXXXXX.local` で届くか。実行時に約 4 KB + 確保分) |
| P4 の WiFi の IRAM 最適化 | P4 は WiFi のライブラリ (libpp / libnet80211) をリンクしていない | - | - | **不要** (効果 0) |

まとめ: **すぐ入れてよいのは RMT と ringbuf (タスク用)、S3 はさらに ringbuf の ISR 用と SPI を実機の確認つきで**。heap と FreeRTOS は合わせて P4 約 18 KB / S3 約 14 KB と大きいが、速さへの影響を実機で測ってから決める。

## 5. T3: Spinel の生成 C の定数を PSRAM へ

### 5.1 変更

フォーク (`/home/kishima/fmrb/wt/spinel-rebase`、`fmrb-ext`) に **`654c9fd5`** (codegen, runtime: place zeroed file-scope slots and pool statics with SP_TU_BSS) をコミットした。push はしていない。

- 生成器 (`src/codegen.c` の `emit_tu_nil_slot`): 初期値がゼロのファイルスコープの領域を `static T name = 0;` ではなく `SP_TU_BSS static T name;` と出す。値は同じ (静的な領域は元からゼロ)。初期値が nil の番兵の領域は既に `SP_TU_NIL_SLOT` で `SP_TU_BSS` だったので、それと揃った。
- ランタイム (`lib/spinel_rt.h` の `SP_POOL_DEFINE`): クラスごとの pool の変数 (head / count / max / pushes / pops / freed / hwm) を `SP_TU_BSS` に置き、上限 (`pool_max`) は静的な初期値ではなく既存のコンストラクタで `SP_POOL_DEFAULT_MAX` を書く (そうしないと .data に残る)。
  ESP-IDF では PSRAM の .bss のゼロ埋め (`esp_psram_bss_init`、cpu_start.c) がコンストラクタの実行 (`do_global_ctors`、startup.c) より先なので、上限は正しく入る。
- `SP_TU_BSS` は既定で空なので、それを定義しないビルドは上限をコンストラクタで書くことだけが違う。

指示書の対象は `cst_*` と `pool_count` / `pool_max` だったが、同じ関数を通る**クラスの ivar (`civ_*`、105 個 420 B) も一緒に移った**。生成器の同じ 1 か所で決まる形で、範囲は広げていない (生成器の変更は 1 関数、ランタイムは 1 マクロ)。

fmruby-core ではランタイムのスナップショットを取り直した (`66f75fe0`、`import_from_fork.rb /home/kishima/fmrb/wt/spinel-rebase`)。変わったのは `spinel_rt.h` と IMPORT_INFO だけ。

### 5.2 減り方 (3 機種とも同じ)

| `pool_max` | 58 | 232 | .sdata |
| `cst_*` | 57 | 225 | .sbss |
| pool を持つ 7 クラスの `head` / `pushes` / `pops` / `freed` / `hwm` | 35 | 140 | .sbss |

- **P4 (RISC-V) で .sbss / .sdata から本当に外れたか**: 最終の TAB5 の ELF で、該当の 729 シンボル (カーネルと editor で同名があるので重複を含む) の番地は全部 `0x48...` / `0x49...` (PSRAM の .ext_ram.bss、`_ext_ram_bss_start` = 0x48000000 〜 `_ext_ram_bss_end` = 0x4914dd70) にあり、内蔵 RAM に残ったものは 0。明示の区画属性が付いた変数は gp 相対の小さいデータにはならない、という見立てどおり。

## 6. GC の停止時間 (sim)

### 方法

- 同じコードで、T3 だけを変えた 2 版を比べた。前 = `c3a341b0` のスナップショット + vendor/spinel (`daef484b`) のコンパイラ、後 = `66f75fe0` のスナップショット + `654c9fd5` のコンパイラ。どちらも Linux の標準構成 (Spinel kernel + Spinel editor)。
- 一時的な計装 (コミットしていない、scratchpad の `gc_instr.rb`): スナップショットの `sp_gc.c` の、収集 1 回の時間を `sp_gc_stat_seconds` に足す 2 か所で、その 1 回の時間をインスタンスごとに集計 (回数、合計、最大、分布) し、`[gcm]` 行で出す。既存の `sp_gc_stat_seconds` (`SPINEL_GC_STATS` の元の数) と同じ区間を測っている。計測後に外した。
- 1 回の測定 = sim を新しく起動 → 5 秒待つ → editor を起動 → 25 行 (各 56 文字 + 改行) を打つ → マウスを 150 回動かす → 3 秒待つ。各版 5 回 (editor の起動に失敗した回は除いて取り直した)。i=0 が kernel、i=1 が editor。

### 結果

| | 前 (5 回) | 後 (5 回) |
|---|---|---|
| kernel: 回数 | 13 / 13 / 13 / 13 / 13 | 12 / 13 / 13 / 12 / 13 |
| kernel: 1 回の平均 (us) | 365 / 383 / 289 / 377 / 348 (平均 352) | 315 / 339 / 339 / 276 / 217 (平均 297) |
| kernel: 最大 (us) | 748 / 1,247 / 808 / 852 / 904 | 853 / 943 / 739 / 810 / 403 |
| editor: 回数 | 48 / 49 / 49 / 49 / 49 | 49 / 49 / 49 / 48 / 49 |
| editor: 1 回の平均 (us) | 2,636 / 2,689 / 2,410 / 2,641 / 2,690 (平均 2,613) | 2,606 / 2,908 / 2,620 / 2,728 / 1,997 (平均 2,572) |
| editor: 最大 (us) | 5,708 / 6,701 / 7,115 / 5,477 / 5,591 | 6,733 / 6,692 / 5,046 / 7,795 / 4,150 |

- **はっきりした悪化は無い**。平均は前後とも回ごとの揺れ (kernel 217-383 us、editor 1,997-2,908 us) の中に収まる。
- ただし sim ではこの比較で PSRAM の影響は見えない。Linux では `SP_TU_BSS` が空なので、前後で配置は同じで、違うのは pool の上限をコンストラクタで書くことと、ゼロの初期値の書き方だけである。この計測が示すのは「生成されるコードが変わって GC が遅くなっていない」ことまで。
- 実機での見込み: GC の印付けは根として `cst_` / `civ_` を 1 回ずつ読む。1 本の生成 C で数十から 200 個程度の読みが PSRAM (キャッシュ経由) になる。一方、Spinel のヒープ (estalloc のプール) は実機では元から PSRAM にあり (`fmrb_mempool.c`)、印付けの本体はそこを歩いているので、増える分は 1 回の印付けの中でごく一部の見込み。`pool_max` は pool から回収するときに読むが、slab が有効な間は pool を通らない。**実機で GC の停止時間を測るのは R4 に回す** (P4 の周期ダンプの ExcHW の隣に数えを出すのが既存の案、spinel_gc_notes.md 4 章)。

## 8. 見立てと違った点・撤回した仮説

- **P4 の lwIP の .bss は sdkconfig で PSRAM へ動かせない** (3.3)。R1 では「sdkconfig の配置」で動く見込みとしていた。IDF の lwip の配置規則は esp_wifi の scheme に頼っていて、P4 の構成では空振りする。
- **P4 は SPI の ISR の設定の効果が 0**。R1 では S3 だけの話として挙げていたが、P4 でも既定の y のままで、ただ SPI master がリンクされていないので何も載っていない。
- **heap を flash に置くと S3 では SPI master の ISR も必ず外れる** (Kconfig の依存)。単独の値 (-13,440) の約 6 割は SPI の分。
- T3 は指示書の対象 (`cst_` / `pool_count` / `pool_max`、689 B) より多く、**1,249 B** 減った。同じ関数を通る `civ_` (420 B) と、pool を持つクラスの残りの数え (140 B) が一緒に移ったため。
- T1 の試しのビルドを並べて走らせると、picoruby の共有のビルド物を取り合って壊れる (2 章)。

## 9. 判断してほしい点

1. **sdkconfig**: まず RMT と ringbuf (タスク用) を入れるか (P4 -4.0 KB / S3 -3.7 KB、条件は満たしている)。S3 の ringbuf の ISR 用と SPI、P4/S3 の heap と FreeRTOS は実機で速さを測ってからか。
2. **SPINEL_PIN を `654c9fd5` に上げるか** (フォークの push が要る)。上げないと cst_ / civ_ の 645 B は出ない (pool の分はスナップショットだけで出る)。
3. P4 の lwIP の静的な 4 KB を、自前の linker fragment (scheme を足して liblwip の .bss を extern_ram へ) で動かすか。sdkconfig の外の新しい仕組みになる。
4. ble の GATT の定義 (224 B) を const にするか。NimBLE の中を読んで、実機で BLE を確かめる必要がある。
