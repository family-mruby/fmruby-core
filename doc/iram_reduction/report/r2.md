## 2. s_file_write_bounce がなぜ内蔵 RAM にあったか

### 2.1 入った経緯

`10e80148` (2026-04-19, "fix File#write silently redirected to UART stdout") で、ほかの修正と一緒に入った。
このコミットの本当の原因は picoruby-machine が IO#write を UART への出力に差し替えていたことで
(`File#write` のバイトが全部 UART に流れて、ファイルには何も残らなかった)、それは machine.c 側で直っている。
同じコミットで、推測の対策として次の 2 つも足されている。

- 書き込み用に開いたファイルに `setvbuf(_IONBF)` (「newlib の FILE バッファが PSRAM に取られうる」)
- 書き込み元が PSRAM なら内蔵のバッファに写してから fwrite (「SPI flash は PSRAM の元から書くと黙って失敗する」)

このあと (boot_performance の原因 1) で `_IONBF` は書き込み用に絞られたが、前提は検証されないまま残った。
ほかに経緯を書いた記録 (report、memory) は無い。

### 2.2 前提はコードの上で成り立たない

書き込みの経路ごとに、IDF とその部品のコードで確かめた (IDF は v5.5.4 のイメージの中身)。

| 経路 | 書き込み元がどう扱われるか | 場所 |
|---|---|---|
| LittleFS (内蔵 flash) | 呼び出し元のデータは、flash に触る前に必ず LittleFS 自身のキャッシュへ memcpy される。flash に渡るのはそのキャッシュだけ | `lfs_bd_prog` (memcpy で `pcache` へ) → `lfs_bd_flush` → `cfg->prog(pcache->buffer)`。ファイルのキャッシュは `vfs_littlefs_file_t::lfs_buffer` (`esp_littlefs_calloc` で確保)、全体のキャッシュは `lfs_malloc`。設定は `CONFIG_LITTLEFS_MALLOC_STRATEGY_INTERNAL=y` なので**どれも内蔵** |
| esp_flash_write (さらに下) | 元が内部 DRAM でなければ、キャッシュを止める**前に** 32 バイトずつスタックの一時領域へ写してから書く | `esp_flash_write()`: `direct_write = esp_ptr_in_dram(buffer) \|\| supports_direct_write()`、偽なら `memcpy(temp_buf, buffer, …)` してから `rom_spiflash_api_funcs->start()`。`CONFIG_SPI_FLASH_ROM_IMPL` は 3 機種とも無効 (この C 実装が使われる) |
| SD カード (SDMMC / SDSPI) | 元が PSRAM か、DMA の整列を満たさなければ、DMA 可能な一時バッファへ写してから 1 セクタずつ書く | `sdmmc_write_sectors()`: `!esp_ptr_external_ram(src)` と `check_buffer_alignment` を見て、外れたら `heap_caps_malloc(block_size, MALLOC_CAP_DMA)` に memcpy |
| FAT (SD の上) | FatFS の作業領域 (`win`) 自体が PSRAM (`CONFIG_FATFS_ALLOC_PREFER_EXTRAM=y`)。部分セクタの書き込みは毎回 PSRAM の元から `sdmmc_write_sectors` に届いており、上の跳ね返しで処理されている | sdkconfig |
| newlib の FILE バッファ | `CONFIG_SPIRAM_USE_CAPS_ALLOC=y` (`USE_MALLOC` ではない) なので素の malloc は PSRAM を返さない。FILE バッファは内蔵。10e80148 の時点の設定でも同じ | sdkconfig (当時の sdkconfig.defaults.n16r8 も確認) |

「flash の書き込み中はキャッシュが止まって PSRAM が読めない」は正しいが、書き込み元の PSRAM を読むのは
どの経路でも**キャッシュを止める前** (LittleFS の memcpy、esp_flash_write の memcpy) なので当たらない。
DMA の制約は SD の経路にだけあり、そこは IDF が自分で跳ね返している。
S3 と P4 で PSRAM と flash がキャッシュを共有するかどうかは、この順序 (写してから止める) の上では効かない。

### 2.3 P4 ではそもそも跳ね返しが動いていなかった

跳ね返すかどうかは書き込み元の番地が `0x3C000000`-`0x3E000000` かで決めていた。これは **S3 の外部データの窓**
(`SOC_EXTRAM_DATA_LOW/HIGH`、PSRAM と flash の rodata が同じ窓に載る) で、P4 では PSRAM が `0x48000000`、
flash の rodata が `0x40000000` にあるので**一度も当たらない**。P4 (Tab5 / NARYAv4) は 2026-06 の対応以来、
PSRAM の Ruby の文字列もエディタの行 (PSRAM のアリーナ) も、そのまま fwrite してきたことになる。
エディタの保存や File#write が P4 で問題なく動いてきたこと自体が、前提が成り立たない実例になっている。

### 2.4 判定

| バッファ | 判定 | 根拠 |
|---|---|---|
| `s_file_write_bounce` (4 KB) | **P4 では外す** (コードごと S3 だけに限る)。移すのではなく、要らない | P4 では元から死んだコード (2.3)。前提も IDF のコードの上で成り立たない (2.2) |
| `s_fs_buf` (devctl、4 KB) | **P4 では PSRAM へ** | 触るのは memcpy だけ。受信は `httpd_req_recv` (lwIP から写す)、送信は `httpd_resp_send_chunk` (lwIP が写す)、書き込みは fwrite → LittleFS がキャッシュへ写す (2.2)。DMA にも割り込みにも渡らない |
| S3 の両方 | **据え置き** | 理屈は S3 でも同じだが、S3 の実機がつながっていないので確かめられない (7 章の判断点) |

## 3. 変えたもの

コミット `0f021d6f` (hal, devctl: keep the file write buffers out of internal RAM on the P4)。

- `components/fmrb_hal/platform/esp32/fmrb_hal_file_esp32.c`: 跳ね返しのバッファと分岐を
  `#if CONFIG_IDF_TARGET_ESP32S3` の中に入れた。P4 ではそのまま fwrite する (これまでと同じ動き)。
  コメントを実態 (2 章) に書き直した。
- `main/drivers/devctl/devctl_http.c`: `s_fs_buf` を P4 では `EXT_RAM_BSS_ATTR`。S3 は内蔵のまま。

P4 で振る舞いが変わるのは `s_fs_buf` (遠隔のファイル転送) だけ。File#write とエディタの保存は、
P4 ではもともと跳ね返していなかったので同じ。map の比較でも、動いたのはこの 2 つのシンボルだけ
(3 機種とも、ほかの節は 1 バイトも動いていない)。

`fopen` 後の `setvbuf(_IONBF)` のコメント (「FILE バッファが PSRAM に取られうる」) も 2.2 のとおり
当たらないが、`_IONBF` は書き込みの順序と即時性にも効いているので今回は触っていない。

## 4. 実機での試験 (P4-Nano = NARYAv4)

SD カードは刺さっていない (`sdmmc_card_init failed (0x107)`)。よって LittleFS (/home) だけ。

| 経路 | 内容 | 結果 |
|---|---|---|
| File#write (Ruby の文字列 = PSRAM が元) | 1 / 100 / 4,095 / 4,096 / 4,097 / 8,191 / 10,000 / 65,537 B は 1 回の write、1 MB と 2 MB は 16,396 B ずつの write。書いた直後に読み戻して比較。回ごとに中身をずらす (前の回の中身が残っていれば見つかる)。**BlockGame を動かしながら** 6 回 | 60 / 60 一致。最後の回の 10 ファイルを遠隔で取り出し、ホストで作った期待値とバイト単位で一致 |
| 遠隔のファイル転送 (`/fs/put`、`s_fs_buf` = PSRAM) | 同じ区分 (1 B-1 MB の 9 種) を PUT して GET し、ホストで比較。BlockGame を動かしたまま 1 回 | 9 / 9 一致 |
| エディタの保存 (行は PSRAM のアリーナ、改行は flash の rodata が元) | 2 行を打ち、Save as で /home に保存 | `Saved file: … (15 bytes)`、取り出した中身も一致 |

- 書き込み中も描画は続いた (render avg 27-47 ms、Guru / abort 0)。
- 大きさごとの書き込みの時間: 1 MB 8.7-13.4 s、2 MB 17-27 s (BlockGame と並行)。読み戻しは 1 MB 0.56 s。

### 内蔵 flash に書いた量

最初の版の試験アプリに、終わったあとも回を数え直して書き続ける誤りがあり、止めるまで書き続けた
(中身が回ごとに変わって見えたので気づいた。flash の不具合ではない)。
**LittleFS に書いたデータの総量はおよそ 66 MB** (File#write の試験 209 件で 65,981,593 B、止めたときに書きかけだった 2 MB 以下、
遠隔の転送 約 1.1 MB、試験アプリの転送とエディタの保存で数 KB)。LittleFS のメタデータの書き換えは含まない。
8 MB の区画の約 8 周分で、NOR flash の書き換え寿命 (1 区画あたり 10 万回が目安) に比べれば小さいが、
必要以上に多かった。試験で作ったファイル (/home/r2t、/home/r2p) は全部消した。

### 気づいたこと (既存の問題、今回の変更と関係ない)

ファイルの書き込み中 (2 MB の途中) のアプリを `/app/kill` で止めたら、その後の遠隔の要求がすべて応答しなくなった
(ping は通る、httpd だけ止まる)。止められたタスクが LittleFS のロック (esp_littlefs の `sem_take`) か HAL の
`s_file_mutex` を持ったまま消えて、次の fopen がずっと待っている、というのが一番ありそうな筋。gdb は実機に当てられないので
確かめてはいない。リセットで戻った。アプリの kill がロックを持ったタスクを消しうる、という問題として別に扱う価値がある。

## 6. g_recv_buf (R1 で PSRAM へ移したもの) の速さ

親からの追加の依頼。`g_recv_buf` は描画の命令が毎回通る経路で、link のメッセージバッファから memcpy して
表示タスクが解釈する。R1 では render の時間しか比べていなかった。

### 方法

- 同じコミット (`0f021d6f`) に一時的な計装を入れ、`g_recv_buf` だけを変えた 2 版を作って NARYAv4 で比べた。
  A = PSRAM のまま (`buf=0x48005350`)、B = 内蔵 (`buf=0x4ff3abd0`)。map の差は `g_recv_buf` の +4,096 だけ。
- 計装 (測定後に外した。コミットしていない):
  - `recv` = メッセージバッファに既にデータがあるとき (`xMessageBufferIsEmpty` が偽) の
    `fmrb_hal_link_local_receive_cmd` の時間。待ちを含まない、受け取り (memcpy とロック) の時間。
  - `proc` = `process_message(g_recv_buf, …)` の時間。バッファの解釈と、命令の実行 (キャンバスへの描画) を含む。
  - CPU のサイクル数で測り、5 秒ごとに平均と最大を出す。
- 1 回の測定 = 待機 30 秒 → エディタに 380 打鍵 (edit_lat が 100 打鍵ごとに出る) → BlockGame を 40 秒 (起動したまま、操作なし)。
  各版 2 回ずつ。起動直後に同じ手順。

### 結果

| | A1 (PSRAM) | A2 (PSRAM) | B1 (内蔵) | B2 (内蔵) |
|---|---:|---:|---:|---:|
| 待機: recv の平均 | 2,333 ns | 2,331 ns | 2,589 ns | 2,559 ns |
| 待機: proc の平均 | 678 us | 703 us | 679 us | 701 us |
| 打鍵中: 1 メッセージの大きさ | 約 22 B | 同 | 同 | 同 |
| 打鍵中: recv の平均 | 2,534 ns | 2,500 ns | 2,474 ns | 2,469 ns |
| 打鍵中: proc の平均 | 517 us | 526 us | 523 us | 531 us |
| 打鍵中: GFX STATS cmds/s | 50.5 | 50.6 | 50.4 | 50.0 |
| 打鍵中: presents/s | 5.0 | 5.1 | 5.0 | 5.0 |
| edit_lat の平均 (100 打鍵ごと) | 10.8 / 10.6 / 11.2 / 11.4 ms | 11.2 / 11.8 / 12.6 / 11.0 ms | 11.8 / 11.9 / 12.3 ms | 11.0 / 11.1 / 12.0 / 12.1 ms |
| BlockGame: recv の平均 | 2,592 ns | 2,529 ns | 2,481 ns | 2,486 ns |
| BlockGame: proc の平均 | 369 us | 418 us | 389 us | 444 us |
| BlockGame: cmds/s / render 平均 | 32.8 / 27.5 ms | 33.9 / 27.5 ms | 33.0 / 27.4 ms | 34.3 / 27.5 ms |
| 待機時の IRAM free | 198,204 | | 194,152 | |

- 受け取りは 2.3-2.6 us で、どちらの版でも同じ幅に収まる。1 メッセージが約 22 B と小さく、
  memcpy より FreeRTOS のメッセージバッファの手続きが大半を占めている。
- 解釈と実行 (proc) も差が無い。同じ版の 2 回の間のばらつき (BlockGame で 369 → 418 us) の方が、版の差より大きい。
- edit_lat は内蔵の方がむしろ少し大きいくらいで (平均 11.3 ms 対 11.7 ms)、ばらつきの範囲。
  cmds/s は打鍵の速さで決まる量なので、両方 50 で同じ。
- 目安 (5% 以上の悪化) に当たるものは無い。**`g_recv_buf` は PSRAM のまま**にした (コードは変えていない)。
- 内蔵に戻すと待機時の IRAM free が 4,052 B 減る (map の +4,096 とほぼ同じ)。

注意: BlockGame は操作していないので、落下とタイトルの描画だけ (presents/s 2.7-2.9)。
全画面を毎フレーム描き直すような負荷ではない。表示タスクの受け取りの経路にかかる負荷としては
打鍵中 (250 メッセージ / 5 秒) が一番多い。

## 7. 判断してほしい点

1. **S3 で同じことをするか**。理屈 (2.2) は S3 でも同じで、S3 では跳ね返しが実際に動いている
   (PSRAM と flash の rodata が元のとき)。外せば S3 の静的な D/IRAM も -8,192 になる
   (`#if` を外すだけ)。Retro の実機で、File#write の大きさ違い (4 KB 前後と 64 KB 超) と BLE のファイル同期、
   エディタの保存、`/fs/put` を 1-2 回ずつ試せば判定できる。書き込み量は数 MB で足りる。
2. **アプリの kill とファイルのロック** (4 章の気づき)。書き込み中のアプリを kill すると LittleFS か HAL の
   ロックが残ってファイルの操作が全部止まるらしい。今回の範囲外なので記録だけ。
3. `setvbuf(_IONBF)` のコメントの前提も当たらない (2.2)。書き直すだけにするか、書き込み用のバッファリングを
   戻すか (書き込みが速くなる見込み) は別の話として残した。
