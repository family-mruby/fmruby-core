# T3 レポート: clear_user_area に後始末を内蔵する

計画は `plan_s3.md` の T3、背景は `issues_s3.md` の課題 B。**ユーザ確認の
関門 2**。

## 入れたもの

契約 5 (全面を消したら `invalidate_all` + `draw_window_frame`) を基底へ移した。

### 両基底に同じ変更 (1 コミット)

`lib/add/picoruby-fmrb-app/mrblib/fmrb-app.rb` と
`main/prebuild_scripts/spinel/fmrb_app_base_spinel.rb`:

```ruby
def clear_user_area(color = FmrbConst::THEME_WINDOW_BG)
  return unless @gfx
  @gfx.fill_rect(@user_area_x0, @user_area_y0,
                 @user_area_width, @user_area_height, color)
  draw_window_frame unless @bg_canvas || @fullscreen
  _invalidate_attached_uis
  nil
end
```

- `@bg_canvas` ガードは必須。デスクトップは枠を持たないので、素通しすると
  `_build_frame_block` が走って**壁紙の上にタイトルバーが描かれる**。
- `@fullscreen` は `draw_window_frame` 側でも弾かれるが、理由が呼び出し側で
  読めるように名前を出した。
- `attach_ui(ui)` と `_invalidate_attached_uis` (while で回して
  `invalidate_all`) を両基底に追加。`@attached_uis = []` は `initialize`
  でのみ確保する。

### FmrbUI

`initialize` の末尾で `app.attach_ui(self)`。アプリ側の配線は要らない。
将来ページごとに UI を分けても複数受かる。

### ホストテスト

`FakeApp` に `attach_ui` / `window_width` / `window_height` を追加 (T4 でも
使う)。「生成した UI がアプリに申告される」「2 つ目も申告される」を検査。
**152 項目全通過**。

## shell のスクロールの費用 (実測)

**測り方**: 同一ビルドの中で `draw_less_view` を 3 区間に分けて
`Machine.board_millis` を挟み、`less /app/tool/nsf_player.app.rb` を開いて
下矢印を 120 ms 間隔で 40 回送り、41 回分の再描画をログから集計した
(計測コードは一時的なもの。コミットしていない)。

- `clear+frame` = `clear_user_area` 全体 (塗り + **T3 で入った枠再描画** +
  invalidate_all)
- `frame_only` = その直後に shell が従来から呼んでいる `draw_window_frame`
  **単独**の時間 = T3 が 1 回の clear_user_area に足した分そのもの
- `body` = 本文の行描画 + ステータス行

| 区間 | n | 平均 | 最大 |
|---|---|---|---|
| clear+frame | 41 | **0.27 ms** | 4 ms |
| frame_only | 41 | **0.20 ms** | 2 ms |
| body | 41 | 1.15 ms | 4 ms |
| 合計 (1 回の再描画) | 41 | **1.61 ms** | - |

**T3 が足したのは 1 再描画あたり 0.20 ms** (合計 1.61 ms の約 12%)。T3 前の
同じ再描画は約 1.41 ms。押鍵 1 回につき 1 回の再描画なので、連打しても
体感は変わらない (sim 実測)。

結論: **縮小版 (`_repair_corners`) は入れない** (関門 2 で承認)。

ただし**この数字は sim (x86) のもの**で、S3 実機では枠の GfxBlock 再生が
これより重い可能性がある。実機で shell のスクロールが渋くなったら、
plan_s3.md T3 にある退避先 -- 枠全体でなく**丸縁 4 隅 + 透明キーの再打刻
だけ**の縮小版 `_repair_corners` -- に落とす。実機確認は段 3 の受け入れでは
ユーザ側の範囲なので、ここでは測り直していない。

### shell の重複した枠描画を消した

`draw_less_view` は `clear_user_area` の直後に `draw_window_frame` を
自分でも呼んでいたので、T3 のあとは**枠を 2 回描いていた** (上表の
frame_only がその 2 回目)。この 1 行を消したので、**費用は T3 前と完全に
同じ**に戻る。

plan_s3.md の「冗長な後始末は消さない」と矛盾しない。あちらの判断は
「害が無いので触る理由ができるまで」で、条件が違う:

- nsf/smf の冗長呼びは on_create / イベント時にしか走らず費用ゼロ -> 残す
- shell の分は**毎再描画の経路**にあり、今回の計測で費用 (0.20 ms) が
  特定された -> 触る理由ができた

shell の `on_create` にも同じ組み合わせが 1 か所あるが、起動時 1 回で
費用ゼロなので nsf/smf と同じ扱いで残している。

消したあとの確認 (sim): less を開いて下矢印 40 回。**枠・スクロールバー
とも保たれる** = `clear_user_area` が内蔵で描く枠だけで足りている。
