# 段 3 の課題: FmrbUI の残っている難しさ

段 1 (U1-U4) と段 2 (S1-S4) で 8 本のアプリとデスクトップの 5 ダイアログが
FmrbUI に乗った。座標をアプリから追い出すという狙いは達成できている
(kamon で座標を書いている行が 40 -> 14、しかも全部 `build_panel` の中)。

一方で**新しい難しさが増えた**。本書はその棚卸しと、段 3 で何を直すかの案。
着手前にユーザと方針を決めること。

## 実績から: 何を間違えたか

ユーザ指摘で見つかった描画の不具合 6 件の内訳:

| # | 症状 | 原因の所在 |
|---|---|---|
| 1 | ダイアログのボタンが枠の外 (11px 下) | 呼び出し側: 座標系の思い込み (`set_origin`) |
| 2 | 左上・中央に白い矩形 / 余計なスクロールバー | **FmrbUI 本体**: `invalidate_all` が非表示部品も dirty に + 閉じるときの `set_visible(false)` 漏れ |
| 3 | ファイル選択の右枠線が消える | 呼び出し側: バーを枠線の列に重ねた |
| 4 | スクロールが 2 段送り / 端で無反応 | **FmrbUI 本体**: 押下で発火する部品が離しでも発火 |
| 5 | config のボタンが枠の外 | **既存** (移植前から。フッタの塗りが枠を消していた) |
| 6 | NSF の角の丸みが消える | **既存** (移植前から。全面を消して枠を描き直していなかった) |

4 件が FmrbUI 由来 (本体 2 / 契約違反 2)、2 件が既存。**契約違反 2 件は
部品群を作った本人が踏んでいる**ので、他の作者はもっと踏む。

## 課題 A (最重要): `set_visible(false)` が背景を塗る仕様

### いまの挙動

`flush` は「非表示かつ dirty」の部品に当たると、その矩形を `@bg` 1 色で
塗りつぶす。部品を消したときに絵が残らないようにするため。アプリに
`fill_rect` を書かせると部品の矩形をアプリが知ることになり、FmrbUI が座標を
持つ意味が薄れる、という理由で部品側に後始末をさせた。monitor の Tasks
ページはこれに依存している (タスクが減ったら `set_visible(false)` だけで跡が
消える)。

### 何が問題か

**部品は自分の後ろに何があるかを知らない。** 知っているのは `@bg` という
1 色だけで、地が「絵」の場所に置かれた瞬間に嘘になる。上の表の 2 と 3 は
これが直接の原因、6 も「地を 1 色と見なす」同じ考え方から出ている。

- デスクトップの地は**壁紙**
- ダイアログの右端の列は**枠線**
- 窓の四隅は**丸い輪郭**

段 2 で足した `bg:` は「地は 1 色だが白ではない」までしか解いていない。

### 案

1. **塗るのをやめ、アプリに知らせる**。`flush` は消えた部品があったことを
   返し、アプリが自分の地を描き直す。ただし**確保しない**制約があるので
   矩形の配列は返せない。「消えた部品があったか」のフラグ + アプリが
   `redraw_background(x, y, w, h)` を実装する契約、が現実的か。
2. **`bg:` を渡したときだけ塗る**。地が 1 色だと作者が明示した場合に限る
   折衷案。monitor は今のまま、デスクトップは自分で塗り直す。
3. 1 と 2 の併用 (既定は塗らない、`bg:` があれば塗る)。

**案 2 が移行コストは小さい**が、「既定が安全側かどうか」で決めるべき。

## 課題 B: 全面を消したあとの後始末が契約になっている

アプリが `clear_user_area` や全面 `fill_rect` をしたら、

- `@ui.invalidate_all` を呼ぶ (呼ばないと部品が消えたまま)
- `draw_window_frame` を呼ぶ (呼ばないと角の丸い輪郭が消える。**resizable
  でなくても必要**。skill には resizable の話としてしか書いていなかった)

この 2 つを作者が覚えている。段 2 で nsf_player と smf_player が後者を
忘れていた (既存バグ、6 番)。

### 案

- 基底に `clear_user_area` の対になる 1 メソッドを置き、そこで
  `draw_window_frame` + `@ui.invalidate_all` をまとめて行う。
- あるいは `FmrbUI#flush` が「前回から地が消されたか」を知る術を持つ
  (アプリが `@ui.background_cleared` を立てる等)。

## 課題 C: イベント列のテストが無かった

ホストテストは 112 項目あるが、**`press` -> `release` を続けて流す**検査が
無く、2 段送り (4 番) を通してしまった。個々のメソッドは正しく、
**組み合わせだけが誤っていた**。

### 案

- 部品ごとに「1 クリック = down + up」を必ず 1 本書く。
- できれば `handle` に渡すイベント列を配列で書いて回すヘルパを用意する。

## 課題 D: 座標系の契約が暗黙

`FmrbUI.new(app)` は user area 原点を足す。デスクトップのように
キャンバス絶対座標で考えているアプリは `set_origin(0, 0)` が要る
(1 番)。**間違えても静かにずれるだけ**で、例外も警告も出ない。

### 案

- `FmrbUI.new(app, origin: :user_area | :canvas)` のように明示させる。
- あるいはデスクトップのような「枠を描かない窓」を基底が判定して既定を
  変える (`@bg_canvas` があれば canvas 原点、など)。

## 課題 E: 確認手順

静止画を眺める確認では 6 件中 5 件を見逃した。数え方を固定する。

- **枠と部品の境界はピクセルで数える** (目視しない)。修正の確認は
  「境界の y を走査して D/W の並びを読む」形で行う。
- **「自分の変更が原因か」は、変更前の版を同じビルドに一時アプリとして
  同梱して並べる**。費用はビルド 1 回で、確実。PicoRuby の OOM と NSF の
  角の 2 件はこれで確定した。コードを読んだだけの判断は 2 回とも外しかけた。

## 段 3 でやらないこと (いまのところ)

- List 部品。段 2 で確認したとおり、共通なのはスクロール量の 3 整数だけで、
  行の中身はアプリ固有。
- Slider。ツリーに手描きのものが 1 つも無い。
- config の設定行 / clock の日付フィールドの部品化。値が型付きで表示が
  導出され、選択ハイライトを持つ。アプリ側に対応表が要る。

## 補足: 段 2 までに分かっている契約 (作者が知る必要のあるもの)

段 3 の目標は**この数を減らすこと**。

1. 毎フレーム描かない (`on_update` から描かない)
2. ブロックを渡さない (`handle` の戻り値を `case`)
3. 座標系 (課題 D)
4. 閉じるときは隠してから `flush` (課題 A)
5. 全面を消したら `invalidate_all` + `draw_window_frame` (課題 B)
6. 暗い背景なら `bg:` (課題 A)
7. poly 受信で呼ぶメソッド名は一意に (Spinel)
8. `text_width` は family 明示

## 段 3 のあとの契約 (改訂版)

T1-T4 を入れた結果。**8 -> 7 に減り、1 つは静かに間違えられなくなった**。

| # | 契約 | 段 3 での扱い |
|---|---|---|
| 1 | 毎フレーム描かない | 変わらず |
| 2 | ブロックを渡さない (`handle` の戻り値を `case`) | 変わらず (方針として維持) |
| 3 | 座標系は user area 原点 | **残るが検出可能**。窓の外に出る部品は生成時に warn が出る (T4) |
| 4 | 閉じるときは隠してから `flush` | **残る**が説明が変わった。消えた跡を塗るのは `bg:` の色か `bg_painter` (T2) |
| 5 | ~~全面を消したら `invalidate_all` + `draw_window_frame`~~ | **消えた**。`clear_user_area` が枠の再描画と部品の再描画指示を内蔵する (T3) |
| 6 | 暗い背景なら `bg:` | **狭まった**。`bg:` は「部品が自分の中を塗る色」。地の色ではない (T2) |
| 7 | poly 受信で呼ぶメソッド名は一意に (Spinel) | 変わらず。`paint_bg_rect` もこの理由で固定名 |
| 8 | `text_width` は family 明示 | 変わらず |
| 新 | `bg_painter` を渡すなら `paint_bg_rect` の契約 | 描くだけ・present しない・確保しない・変えたサイズ/フォントは戻す・名前は固定 (T2) |

新しい 1 本は**渡した人だけが負う**契約 (既定は nil) なので、
既存アプリの作者が知る必要のある数は 8 -> 7。
