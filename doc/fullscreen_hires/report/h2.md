## 1. 結果の要約

- 実機: つながっていたのは今回も **P4-Nano (NARYAv4) だけ**。Tab5 (303a:1001) は見えなかった。**Tab5 の実機確認は未**。
- NARYAv4 (最終のビルド) での確認:
  - 組み込みのエディタを全画面で起動すると 640x360 になる (画面取得も 640x360)。打鍵できる。
  - F11 で窓 (426x240 の画面、窓は 240x200) に戻り、もう一度 F11 で 640x360 に戻る。
  - 窓で起動したエディタ (`default/editor`) も、F11 で 640x360 の全画面になり、F11 で元の窓の位置と大きさに戻る。
  - Ctrl+Tab でデスクトップへ (426x240)、もう一度で 640x360 のエディタへ戻る。
  - 窓のアプリ (kamon) を起動するとエディタが park され、Ctrl+Tab でエディタと kamon を行き来できた。
  - 入れ子: エディタ (高解像度) → 試験用アプリ (高解像度) → レイキャスター (通常の全画面) を重ねた。レイキャスターでは 426x240 になり、終了すると試験用アプリの 640x360 に戻り、それを閉じるとエディタの 640x360 に戻った。
  - Ctrl+Q → 保存しない (N) でエディタを閉じ、デスクトップ (426x240) に戻った。
  - 試験用アプリ (hires_test) は `.app.toml` の `fullscreen_hires = true` だけで、起動時から 640x360 になった (試験用の口は使っていない)。
  - 切り替えは合計 35 回以上。Guru 0、abort 0、アンダーランの記録 0、500ms の打ち切り 0。完了の理由はすべて「持ち主が present した」か「持ち主が隠れた/消えた」。
- ブラウザ版 (web_*): メニューからエディタを起動 → F11 で 640x360 (取得した画面も 640x360) → マウスを (630, 350) に動かすと画面の右下にカーソルが出る → F11 で窓 → F11 → Ctrl+Tab 2 回 → Ctrl+Q で閉じる。すべて期待どおり。ページはキャンバスの大きさに自動で追従した (H0 の見立てどおり)。見た目の大きさの追従は H4。
- sim (標準構成 Spinel カーネル + Spinel エディタ): エディタの全画面は従来どおり 426x240。打鍵、F11 の往復、Ctrl+Tab の往復、閉じる (kill) → 再起動 → 打鍵を確認した。試験用アプリも 426x240 のまま。カーネルは画面モードの命令を 1 度も出していない (ログに `Screen mode:` が無い)。

## 2. 実装

### 2.1 属性と構成の判定

- `fmrb_app_task_context_t` と `fmrb_spawn_attr_t` に `fullscreen_hires` (fmrb_app.h)。
  - ctx の置き場は PSRAM (`g_ctx_pool`)。組み込みの表は flash。内蔵 RAM は増えない。
- spawner (fmrb_app_spawner.c):
  - `.app.toml` の `fullscreen_hires` を読む。`true` でも `1` でも受ける (既存の旗は整数で書かれているため)。
  - `default/editor` と `default/editor_fs` に `.fullscreen_hires = true`。
  - 全画面で起動する窓の大きさを `fullscreen_window_size()` 1 か所で決める。属性があり構成が対応していれば 640x360、それ以外は表示の大きさ。起動時から全画面のアプリは最初から 640x360 の canvas で作られ、カーネルの切り替えでリサイズが要らない。
- 構成の判定: `fmrb_app_fullscreen_hires_size(&w, &h)` (fmrb_app.c)。`FMRB_HW_MODERN || FMRB_PLATFORM_WASM` かつ system_conf の `display_width/height` が 426x240 のときだけ真 (640x360)。
- カーネル Ruby への口 (mruby 版と Spinel 版の両方):
  - `_fullscreen_hires_size` → nil か [640, 360]。Spinel 版は C から `(w << 16 | h)` の 1 整数で受けて配列に戻す。
  - `_set_app_screen_mode(pid, w, h)` → bool。`fmrb_app_set_screen_mode` を呼ぶ。
  - `_get_app_info` に `:fullscreen_hires`。Spinel 版の記録は 167 番目のバイトを足し、168 バイトにした (fmrb_spx.h の表も直した。以前の表は expected_stop の行が抜けていた)。
  - Spinel の生成 C を読み、`sync_screen_mode` 等が型の既定値に落ちずに組まれていることを確かめた (記号の番号も照合)。

### 2.2 カーネル (app_lifecycle.rb)

- `screen_mode_for(pid)`: その app が全画面の一番上になったら高解像度にするか (構成が対応し、属性がある) → pid か nil。
- `screen_mode_want`: `screen_mode_for(fs_top_pid)`。park 中の app は積みから外れているので、一番上にならない。
- `sync_screen_mode(want)`: 判定と送信の 1 か所。状態は `@screen_hires_pid` (高解像度を持つ pid、無ければ nil)。
  - 取るとき: `SET_SCREEN_MODE(want, 640, 360)`。別の高解像度の app から直接移るときも、通常へ一度戻さない (表示側が持ち主を付け替える)。全画面なのに 640x360 でない場合だけ、送った後で 640x360 にリサイズする (安全網。今の経路では起きない)。
  - 返すとき: `SET_SCREEN_MODE(cur, 0, 0)`。
- 呼ぶ場所 (report/h1.md 3 章の順番を守る):
  - `enter_fullscreen(pid)`: 先頭で、その app が取るなら `sync_screen_mode(pid)` (他を隠す前)。末尾で `sync_screen_mode(screen_mode_want)` (通常の全画面が高解像度の app の上に重なったとき、下の app が隠れた後で返す)。
  - `pop_fullscreen_frames(pid)`: 先に、降ろした後に一番上になる app を求め、それが取るなら resume の前に送る。末尾 (resume の後) で `sync_screen_mode(screen_mode_want)`。
  - `request_enter_fullscreen(pid)` (F11): リサイズより前に送る。`_set_app_fullscreen` が失敗したら戻す。
  - park / unpark / 終了 / F11 で窓へ は、上の 2 つを通るので個別の追加は無い。
- `fullscreen_size` を `fullscreen_size(pid)` にした (高解像度の app には [640, 360])。

### 2.3 切り替えの完了の条件 (report/h1.md 6.4 の i)

- 表示側 (display_p4_task.cpp) に `owner_resize_unacked` を足した (`g_smode` の中、PSRAM)。
  - 持ち主の canvas が UPDATE_WINDOW で大きさを変えたら立てる。
  - 持ち主から SET_SPRITE_CLIP が来たら下ろす。FmrbApp は resize の処理の中で必ず sprite clip を送り直す (mruby 版 app.c と Spinel 版 `_dispatch_control` の両方)。これはアプリの present と同じ順序付きの列 (host_task の batch queue) を通る。
  - 立っている間の持ち主の present は「新しい大きさの絵」とみなさない (`committed_fresh` を立てない)。
- これで「resize を読む前の on_update が出した古い配置の絵」で切り替えが完了することは無くなった。ログでは、リサイズを伴う切り替えは毎回 `owner N handled its resize` の後に `owner presented` で完了している。
- 1 枚方式の切り替えの一瞬の乱れが減ったかは、目視でしか分からない (ユーザに依頼する点の 1 つ)。
- 安全網として、通常の画面では「viewport なしで大きさがちょうど 640x360 の canvas」を合成しないようにした。起動時から 640x360 の app が、カーネルの切り替えより先に present しても、426x240 の画面に左上だけが出ることは無い (report/h1.md 3 章の c)。
- ログの `waited` は、待っていなかった切り替え (持ち主が隠れた/消えた) では 0 を出すようにした (前は前回の待ちの開始からの時間が出ていた)。

### 2.4 入力

- host_task に「いまの画面の大きさ」を 1 つ置いた: `fmrb_host_set_screen_size(w, h)` / `fmrb_host_get_screen_size(&w, &h)`。
  - `(w << 16 | h)` を 1 語に詰めて PSRAM に置く。0 は基本の画面 (system_conf の大きさ)。
  - 書くのは `fmrb_app_set_screen_mode` (カーネルが SET_SCREEN_MODE を送る時)。**持ち主がもういない (終了した) ときの「戻す」も記録する**。表示側はそのときは自分で基本の画面へ戻っているので、入力側に知らせる経路はここしかない。
- タッチ (touch_task.c、Tab5): 仮想画面の大きさを host から読み、変わったらカーソルを比率で直す。指の移動量を割る数を `720 / 仮想画面の高さ` (3 または 2) にした。**指の移動と画面上のカーソルの移動の比は両方のモードで同じ**。Tab5 は未接続なので実機では確かめていない。
- USB マウス (usb_task.c、S3 と P4): 一度読みの大きさをやめ、報告のたびに host の大きさと比べ、変わったら全デバイスのカーソルを比率で直す。**速さは `mouse_scale × 今の幅 / 基本の幅` (縦も同様) にし、画面上の速さを今と同じに保つ**。絶対座標のデバイスは今の大きさに写す。
- 遠隔入力 (rd_input.c): 固定の 426x240 をやめ、今の大きさで切り詰める。座標の変換はしない (ブラウザの remote.js は 426x240 のまま送るので、高解像度中は左上 2/3 にしか届かない。remote.js と info の追従は H4)。
- ブラウザ版: ページが canvas の大きさで割るので追従する (上記 1 章で確認)。
- 増えた static はすべて PSRAM (`FMRB_EXT_RAM_BSS_ATTR` / `EXT_RAM_BSS_ATTR`)。

### 2.5 試験用アプリ

- `hires_test.app.toml` に `fullscreen_hires = true`。
- `hires_test.app.rb`: 起動時の大きさが 640x360 なら、最初の状態を HIRES、基本の大きさを 426x240 とする (前は起動時の大きさを基本とみなしていたので、状態行が「BASE 640x360」と出た)。Space の手動切り替え (試験用の口) は残した。これはカーネルが知らない切り替えなので、表示側だけを試す道具として使う。

## 3. 内蔵 RAM とビルド

| | H1 | H2 | 差 |
|---|---|---|---|
| TAB5 静的な D/IRAM | 183,008 | 183,008 | 0 |
| NARYAv4 静的な D/IRAM | 178,410 | 178,410 | 0 |
| S3 (NARYAv3) 静的な D/IRAM | 146,995 | 146,995 | 0 |

- 各構成とも `rake clean_all` から `FMRB_HW_TARGET=... rake build:esp32` でビルドし、`idf.py size` の DIRAM 行を読んだ。TAB5 は同じ手順で H1 のソース (0f653ff6) も作り直して 183,008 を再現し、同じ条件で比べた。
  - 途中で一度、存在しない sdkconfig.defaults を渡した `idf.py size` で CMake の cache を汚し、180,328 という誤った値を読んだ。作り直して上の値を得た。報告の数字は作り直した後のもの。
- アプリの大きさ: TAB5 +10.7KB (0x6025e0 → 0x604f90)、区画の空きは 14% のまま。
- NARYAv4 の待機時の `IRAM free` (起動 12-13 秒後): 158,016 / 157,652 (2 回の起動)。H1 は 157,664。差は起動ごとの揺れの範囲。
- Linux (x86-64 を確認)、wasm (`rake wasm:mruby` → `wasm:mrb` → `spinel:gen` → `wasm:web`) も通った。
  - 注意: wasm のビルドは Spinel の生成物 (gen/) を作り直さない。esp32 のビルドの後に `rake wasm:web` だけを走らせると、esp32 用に生成したカーネルが入る。今回は `rake spinel:gen` (linux) をしてから作った。
- PSRAM: 640x360 の fb 460,800 B (最初の切り替えのとき)。ほかは H1 と同じ。

## 4. 気づいたこと・残したこと

- **Tab5 は未確認** (タッチの倍率、tab5_screenshot の 640x360)。つながり次第、同じ手順で見る。
- 遠隔操作の道具 (MCP の tab5_screenshot) の返す `frame_size` が、640x360 の絵でも "426x240" と出た。H1 で親リポジトリの tools/mcp/lib/tab5.rb を直したが、動いている MCP サーバが古いままだと思われる (サーバの再起動が要る)。絵そのものは 640x360。
- ブラウザ版で起動したとき、`/app/usr/paint_pad/paint_pad.app.rb` が無いという起動失敗の表示が出た。ページの保存領域に残っていた設定によるもので、今回の変更とは関係ない。
- F11 で窓に戻るとき、全画面で起動したエディタには覚えた窓の大きさが無いので、既定の 240x200 になる (従来どおり)。
- park するとき、一瞬「持ち主が隠れて基本の画面に戻ったが、デスクトップはまだ隠れている」状態がある (report/h1.md 3 章の a)。これは通常の全画面の park でも同じで、順番は変えていない。目視で気になるなら、park で「先に下を resume し、後で持ち主を suspend する」順に変える案がある。
- 遠隔入力は座標の変換をしない。remote.js が 426x240 前提のままなので、ブラウザの遠隔デスクトップから高解像度の全画面を操作すると、クリックの位置がずれる。H4 で info と VIRT_W/H を追従させる。

## 5. ユーザに見てほしい点 (NARYAv4、HDMI)

板は最終のビルドを書いてあり、デスクトップが出ている。USB キーボードとマウスで次を行い、見た目を確かめてほしい。

1. ランチャーの Editor (窓) を開き、F11 を押す。
   - エディタが画面いっぱいに出て、文字が今までより小さく細かくなる (640x360)。四辺に黒い帯や前の絵の残りが無いか。
2. 何文字か打ち、F11 を数回押して窓と全画面を行き来する。
   - 切り替えの瞬間の一瞬の乱れが、H1 のときより減ったか (同じか、減ったか、増えたか)。
   - 窓に戻ったとき、デスクトップと窓が崩れずに出るか。
3. 全画面で Ctrl+Tab を押してデスクトップへ、もう一度 Ctrl+Tab でエディタへ。数回。崩れが残らないか。
4. 全画面のエディタでマウスを動かす。
   - 画面の四隅まで届くか。
   - 速さが窓のとき (426x240) と同じくらいに感じるか。カーソルの絵は小さくなる (許容済み)。
5. Ctrl+Q → N でエディタを閉じ、デスクトップが従来どおり出るか。

## 6. 判断してほしい点

1. park の順番 (4 章)。今のままでよいか。
2. 試験用アプリの Space (試験用の口) を残すか。カーネルの状態と食い違う切り替えになるので、H4 の後始末で外す案もある。
3. `fullscreen_hires` の .app.toml への書き方を、`fullscreen_hires = true` を正とし、整数も受ける形にした。これでよいか (既存の旗は整数で書かれている)。
