# H0 実施報告: 調査と設計 (全画面の高解像度モード)

指示書: ../instruction_h0.md / 計画: ../plan.md

コードは変えていない。行番号は 2026-09-28 時点の feature/fullscreen-hires
(develop と同じ中身) のもの。観察は Tab5 実機で一覧・画面取得だけ行った
(tab5_app ps / tab5_screenshot。画面は 426x240 のまま、デスクトップと
サービスだけが動いている状態)。sim とブラウザ版は起動していない。

## 要約

- 全画面のアプリは、今は「426x240 の canvas を 1 枚、デスクトップを隠して
  3 倍で出す」だけで、表示側には全画面という概念が無い。表示側が知るのは
  canvas の大きさと見える/隠れるだけ。
- 高解像度は「**合成先のフレームバッファを 640x360 のものに差し替え、SRM の
  倍率を 2 にする**」で実現できる。合成 (render_frame) の手順はそのまま使える。
  全画面中は他のアプリの canvas は suspend で隠れているので、合成されるのは
  全画面アプリの canvas (と sprite) だけになる。倍率はフレームバッファの
  高さから決まる (パネルの短辺 720 / fb の高さ = 3 または 2) ので、定数を
  やめて導出にできる。
- 入り口と出口は**カーネルが決める**。全画面の積み (`@fs_stack`) の一番上が
  何か、park 中か、を知っているのはカーネルだけだから。表示側へは
  **新しい GFX コマンド**で伝え、表示側は「持ち主の canvas が新しい大きさで
  present するまで前の絵を保つ」ことでちらつきを防ぎ、「持ち主の canvas が
  消えた/隠れたら自分で元に戻す」ことで異常終了の後始末を引き受ける。
- 426x240 / 3 倍を前提にしている箇所は、コードで **16 ファイル・約 30 か所**
  (一覧は 7 章)。多いのは遠隔の画面取得 (5 ファイル) と入力 (3 ファイル)。

## 1. 今の全画面の経路

### 1.1 spawner と .app.toml (main/app/fmrb_app_spawner.c)

- .app.toml は `default_window_mode = "fullscreen"` で全画面になる
  (L710-721。キー名は `window_mode` ではなく `default_window_mode`)。
  .bas は既定で全画面 (L659)。
- 全画面なら窓の大きさを `display_width - display_margin_x` x
  `display_height - display_margin_y` にする (L725-731)。システム設定の値
  そのもので、P4 は 426x240。
- `fullscreen_switchable` (L753-756) は「Ctrl+Tab で park してよい」宣言。
- 組み込みの表 `builtin_app_table`:
  - `default/editor` (L167-192): 窓。resizable、240x200、min 220x80。
  - `default/editor_fs` (L193-234): fullscreen = true、
    fullscreen_switchable = true、resizable、window 0x0 (起動時に表示の大きさ
    で埋める)、rounded_corners = false。
  - 0x0 の埋め方は `spawn_builtin_app` (L362-374) で、.app.toml の経路と
    同じ計算。
- デスクトップのランチャーとファイル管理は `default/editor` (窓) を起動する
  (system_desktop/launcher.rb L25、file_manager.rb L663)。全画面の
  `default/editor_fs` は shell の `edit -f` 相当 (shell_commands.rb L634)
  からだけ。**ふだんの全画面は F11 で入る**。
- アプリの文脈 (ctx) には `fullscreen` / `fullscreen_switchable` が入る
  (main/app/fmrb_app.c L1724-1725)。窓の大きさは attr の値、0 なら
  default_user_app_* (L1707-1716)。

### 1.2 canvas の作られ方

- `fmrb_app_canvas_init` (components/fmrb_gfx/fmrb_app_canvas.c L87-127) が
  `ctx->window_width x window_height` で本体の canvas を作る。**色キー透過は
  「全画面でなく、角丸あり」のときだけ**。起動時に全画面なら不透明の canvas
  になる。F11 で後から全画面にしても透過の設定は作成時のまま。
- canvas を作った時点で `fmrb_app_notify_started` がカーネルに
  `app_started` を送る (同 L79)。

### 1.3 カーネル (main/prebuild_scripts/kernel/fmrb_kernel/app_lifecycle.rb)

- 全画面は積み: `@fs_stack = [{pid:, suspended: [...]}, ...]`、
  `@fullscreen_pid` は一番上、`@parked_fullscreen_pid` は park 中の 1 本
  (L290-305、初期化は fmrb_kernel.rb L82-87)。
- `enter_fullscreen(pid)` (L326-369): 他のユーザアプリとデスクトップを
  suspend し、積みに 1 段載せ、`_bring_to_front`。suspend は C の
  `fmrb_app_suspend` (fmrb_app.c L2175-) で、**task を止めるのと同時に
  その app の全 canvas を SET_CANVAS_VISIBLE(0) で隠す**。resume は見せる。
- `pop_fullscreen_frames(pid)` (L373-392): その段 (と上の段) を降ろし、
  その段が suspend したものだけを resume する。
- 入り口は 4 つ:
  1. 起動時の全画面: `on_app_started` (L121-150) と、起動報告が来ない時の
     保険 `tick_starting` (L172-180) が `enter_fullscreen`。
  2. 実行時の切り替え (F11): アプリの `request_fullscreen` →
     `{"cmd":"enter_fullscreen"}` → `request_enter_fullscreen` (L424-447)。
     窓の位置と大きさを `@window_geometry` に覚え、`fullscreen_size`
     (L413-422、**デスクトップの窓の大きさ = 426x240**) で
     `_set_app_fullscreen(pid, true, w, h)` → `enter_fullscreen`。
  3. spawn 要求に "fullscreen" が付いた場合: `take_spawn_fullscreen` 経由で
     2 と同じ `request_enter_fullscreen` (L137-146)。
  4. park からの復帰 (Ctrl+Tab、F5 で起動した窓アプリの終了):
     `unpark_fullscreen` (L547-557) = `enter_fullscreen` → `resume_app`。
- 出口:
  - F11 で窓へ: `request_exit_fullscreen` (L449-463)。覚えた大きさで
    `_set_app_fullscreen(false)` → 位置 → `pop_fullscreen_frames`。
  - park: `park_fullscreen` (L525-543)。suspend (canvas も隠れる) →
    `pop_fullscreen_frames`。ctx の fullscreen フラグは立ったまま。
  - 終了 (異常終了も): `cleanup_terminated_app` (L681-) が `fs_frame?` なら
    `pop_fullscreen_frames`。
  - 窓アプリを全画面から起動した時: `after_spawn` (L34-80) が park する。
- 入れ子: 全画面の editor から F5 で全画面のゲーム → ゲームが 2 段目。
  ゲーム終了で editor が戻る (desktop は suspend のまま)。

### 1.4 fmrb_app_set_fullscreen と resize メッセージ

- `fmrb_app_set_fullscreen(pid, on, w, h)` (fmrb_app.c L2897-2985):
  ctx の fullscreen / fullscreen_switchable / 窓の大きさを書き換え、
  **UPDATE_WINDOW** (canvas の有効範囲の変更) を表示へ、
  `{"cmd":"resize","width","height","fullscreen"}` をアプリへ送る。
  カーネル Ruby からは `_set_app_fullscreen` (mruby 版
  lib/add/picoruby-fmrb-kernel/ports/esp32/kernel.c、Spinel 版
  main/kernel/fmrb_spx_kernel.c L167 `fmrb_spx_set_app_fullscreen`)。
- アプリ側 (mruby): lib/add/picoruby-fmrb-app/ports/esp32/app.c L566-619 が
  `@_fullscreen`、`@window_width/height`、user area (全画面は枠なしで
  0,0 から全部、窓は x0=1,y0=11,幅-2,高さ-12) を書き、sprite の切り抜きを
  出し直してから `on_resize(w, h)` を呼ぶ。Spinel 版は
  main/app/fmrb_spx_app.c と spinel/fmrb_app_base_spinel.rb に同じ処理がある。
- つまり**アプリの canvas と user area の大きさは、カーネルが渡す w,h で
  決まる**。640x360 を渡せば、アプリ側 (FmrbApp、エディタの
  `recompute_layout`) は追加の仕事なしで 640x360 を使う。
- コア側 (fmrb_gfx) に画面の大きさで描画を切る処理は無い
  (components/fmrb_gfx の screen_width はログだけ)。

### 1.5 組み込みのエディタ

- `default/editor` と `default/editor_fs` は同じ irep (Spinel 既定)。
- F11: editor.app.rb L679-684 (`toggle_fullscreen`)。デバッグ中の F11 は
  ステップ実行。メニューからも (menu.rb L223)。
- 配置は user area から `recompute_layout` (editor.app.rb L201-219) で
  毎回求める。行の高さ `LINE_H = 12`、桁の幅 `CELL_W = 6`、
  `EDIT_FONT_SIZE = 12` は定数 (editor/const.rb L110-120)。**フォントを
  選べるようにするには、この 3 つを変数にする必要がある** (参照 87 か所)。

## 2. display_p4 の表示経路 (main/drivers/display_p4/)

### 2.1 確保

- INIT_DISPLAY (display_p4_task.cpp L2428-2460): カーネルが送る
  display_width x height (426x240) で合成先 `g_framebuffer` (RGB565、
  整列 PSRAM、`ppa_alloc_buffer`) を**一度だけ**作り、`display_backend()->init`
  を呼ぶ。2 回目以降は `if (!g_framebuffer)` で何もしない。
- canvas (`canvas_alloc` L299-388): 作業用 `sprite` と確定済み
  `render_sprite` の 2 枚 (present で作業用→確定用へコピー)。**大きさは
  「表示の大きさと要求の大きさの大きい方」**で取る (L312-313)。窓は後から
  全画面に広がれるよう 426x240 で取り、全画面より大きい要求ならその大きさ。
  1 枚 204,480 B x 2。
- UPDATE_WINDOW (L1611-1647): 有効範囲を確保済みの中で動かすだけ。**確保より
  大きい要求は切り詰める** (L1621-1622)。いまは 640x360 を渡しても 426x240
  止まり。

### 2.2 合成と SRM

- `render_frame` (L712-859): fb を 0 で塗り、見えている canvas を z 順に
  `blend_canvas_block` → `display_backend()->blend_block` (PPA Blend、
  色キーつき) で重ね、sprite を重ね、遠隔用の取り込み (L810-830)、カーソルを
  焼き込み (L839-842)、`present` (L846)、焼いた所を戻す。
- 描画は PRESENT などで `g_needs_render` を立て、task のループで 33ms 以上
  空けて行う (L3450-3460)。所要時間は `note_render` が 5 秒ごとに
  `render: N frames/5s avg max` を出す (L1097-1113)。H1 の比較に使える。
- 出力 (display_backend_ppa.cpp):
  - Tab5 `ppa_present` (L356-409): 90 度回転 + 3 倍で DSI の 720x1280
    RGB565 へ。426x3 = 1278 なので長辺に 1 行ずつ余白 (L375, L392)。
  - NARYAv4 `ppa_present` (L254-301): 回転なし、3 倍、RGB565→RGB888 変換、
    1280x720 の中央 (426x3 = 1278、左右 1 列ずつ余白)。
  - SRM が使えない時は `present_software` (L236-245、pushRotateZoom)。
- CPU 版 (display_backend_cpu.cpp): 合成は display_blend_cpu.c、出力は
  pushRotateZoom。倍率定数は L215-225 (NARYAv4 の 1.5 倍の記述は古く、
  いまの PPA 版は 3 倍)。
- 余白の黒は `ppa_first_frame` (L100-110) で**一度だけ**塗る。

### 2.3 カーソル

- 16x16 の sprite (L442-530)。
- 描画のついでに fb に焼いて SRM と同時に出す (L832-858)。
- 移動だけの時は `cursor_patch` (L542-580) → `present_patch`: fb の 16x16 を
  取り出してカーソルを重ね、バックエンドが倍率をかけて DSI のバッファへ直に
  書く。Tab5 (L416-471) / NARYAv4 (L308-352) / CPU (L256-284) とも
  **倍率は定数**。一時バッファは 3 倍の大きさ (DISPLAY_PATCH_MAX_W/H と
  SCALE_FACTOR) で、2 倍でも足りる。
- 高解像度ではカーソルは画面上 32x32 になる (今は 48x48)。

### 2.4 DSI フレームバッファの 4KB 揃えとの関係

- 揃えは DSI バッファの**先頭番地**の話で、確保は LGFX の初期化時
  (lgfx_tab5.hpp の `Tab5AlignedPanel`、lgfx_naryav4.hpp) に一度だけ。
  以後の PSRAM 確保 (高解像度の fb や canvas) はこの番地を動かさない。
- 走査の帯域も変わらない (DSI 側は同じ 1280x720)。変わるのは SRM が読む量
  (204KB → 460KB/枚) と、合成・確定コピーの量。NARYAv4 は帯域に余裕が
  少ない側なので、H1 でアンダーラン件数 (起動ログ・周期ログ) を見る。
- 注意: 426 モードは余白 1 行/1 列を残す。**高解像度で全面に描いた後、
  426 モードへ戻ると余白に高解像度の絵が残る** (first_frame の黒は一度きり)。
  戻る時に余白を塗り直す必要がある。

## 3. ブラウザ版 (wasm) の表示経路

- 共有: display_p4_task.cpp を丸ごとそのまま使う (canvas、合成、カーソル、
  GFX コマンド)。合成は display_blend_cpu.c。フォントも同じ。
- 別: 出力だけが wasm/backend/display_backend_wasm.cpp。`wasm_init` で
  fb と同じ大きさの RGBA を calloc (L41-48)、`wasm_present` は fb を RGBA に
  変換して番号を進める (L84-91)。**fb の大きさが init の時と違うと何もしない**
  (L88)。`wasm_present_patch` は 1:1。
- ページ側 (wasm/web/main.js): `paint` (L38-57) が毎フレーム幅・高さを読み、
  変わっていれば canvas の大きさを付け替えて `applyZoom`。表示の大きさ
  (CSS) は `canvas.width x 倍率` (L372-393)。マウスとタッチは
  `canvas.width/height` 基準の座標で送る (L61-67, L101-107)。
- 起動時に 426x240 / 640x360 / 852x480 を選べる (L233-237、
  `--fmrb-res` → system_conf の display_width/height、
  wasm/backend/page_settings_wasm.c L114)。
- したがって wasm では:
  - 入力座標は fb の大きさに自動で追従する (ページが canvas.width で割る)。
  - ただし**画面の見た目の大きさが fb に比例して変わってしまう** (2 倍表示
    なら 852 px 幅 → 1280 px 幅)。ページ側で「最初の fb の大きさ x 倍率」に
    固定する必要がある。
  - RGBA の取り直し (free/calloc) は、別スレッドのページが古い番地を読む
    危険がある。最大 (640x360) で一度取るのがよい。
  - 起動時に 640x360 以上を選んでいる場合は、高解像度モードは意味が無い
    (あるいは小さくなる) ので使わない。

## 4. 入力の座標

座標は発生源ごとに「画面の座標 (426x240)」で作られ、host_task
(main/kernel/host/host_task.c L1653-1750) がそのまま表示 (カーソル位置) と
カーネルへ流す。カーネル (input_router.rb L60-160) は全画面中は全画面アプリへ
直接送り、窓の位置 (全画面なら 0,0) を引いてアプリ座標にする。**変換は
発生源の中だけ**で、倍率が絡むのは次の 4 つ。

| 発生源 | 場所 | 426x240 の持ち方 |
|---|---|---|
| USB マウス | main/drivers/usb/usb_task.c `ensure_screen_size` L693-713、相対 L840-873、絶対 L875-895 | 起動時に system_conf の display_width/height を一度だけ読んで保持。デバイスごとのカーソル位置を持つ |

| 遠隔入力 | main/drivers/remote_desktop/rd_input.c L17-26 `RD_VIRT_W/H` | 定数で切り詰め |
| ブラウザ | wasm/web/main.js `canvasPos`、wasm/backend/input_wasm.c | fb の大きさに自動追従 |

- マウスの速さ (mouse_scale_x/y = 0.5) は仮想画素あたりなので、高解像度では
  画面上の動きが 2/3 に遅くなる。倍率に合わせて補正するかは H2 で決める。
- i2c_keyboard.c のカーソルキー移動は ATOM (M5GFX) 用で P4 には無関係。

## 6. Linux sim と Retro での条件

- `FMRB_HW_FAMILY_MODERN` は **Linux の sim でも立つ** (fmrb_hw_defines.cmake)。
  これで判定すると sim が高解像度を要求して壊れる。
  `FmrbConst::HW_FAMILY` も sim で "modern" を返すので使えない。
- 使える条件は、動画再生の関門 (lib/add/picoruby-fmrb-app/ports/esp32/gfx.c
  L1052-1066) と同じ **`FMRB_HW_MODERN || FMRB_PLATFORM_WASM`** (表示が
  同じプロセスの display_p4 である構成)。system_conf の display_mode が
  tab5_dsi / naryav4_hdmi であることとも一致する (wasm の conf も tab5_dsi)。
- 加えて実行時に「基本の大きさが 426x240 であること」を条件にする
  (wasm で 640x360 以上を選んでいる時は無効)。
- この判定は C (カーネル) で一か所にまとめ、カーネル Ruby へは
  「高解像度の大きさ、または nil」として出す。nil なら何もしない = 従来の
  全画面。Retro の graphics-audio と sim の graphics-audio には新しい GFX
  コマンドが一度も届かない。

## 8. 決めること (推奨案と代わりの案)

### 8.1 入り口と出口: カーネルが決める

推奨: **カーネルが、全画面の積みが変わるたびに「いま画面を持つアプリ」を
見て決める**。アプリは .app.toml / 表の属性で「高解像度にしてよい」と
宣言するだけで、実行時の要求はしない。

- 画面を持つアプリ = `fs_top_pid` (park 中でないもの)。その ctx が
  高解像度の属性を持ち、構成が対応していれば高解像度、それ以外は通常。
- 判定を 1 か所 (`sync_screen_mode`) にまとめ、積みを変える所から呼ぶ:
  `enter_fullscreen`、`pop_fullscreen_frames`、`park_fullscreen`、
  `unpark_fullscreen`。入れ子 (高解像度の editor から通常のゲーム) も、
  ゲーム終了で editor が戻る時に自然に高解像度へ戻る。
- F11 で入る時の大きさ: `fullscreen_size` を `fullscreen_size(pid)` にして、
  高解像度の app には 640x360 を返す。起動時の全画面は spawner が
  640x360 の窓で作る (canvas も 640x360 で確保される。2.1 の規則のまま)。

理由: 全画面の積み・park・入れ子・異常終了を正しく知っているのはカーネルだけ。
アプリが要求する形にすると、park や入れ子で「今は誰の解像度か」をアプリと
カーネルの両方が持つことになる。

代わりの案: アプリが `request_hires(true)` を送る。フォントを変えた時だけ
高解像度にする等の細かい制御はできるが、上の理由で採らない。

### 8.2 表示タスクへの伝え方: 新しい GFX コマンド

推奨: **GFX 型の新コマンド `SET_SCREEN_MODE`** (番号は空きから。
`{ uint16 owner_canvas_id; uint16 width; uint16 height; uint8 flags }`)。

- GFX のコマンド列に載せる理由: UPDATE_WINDOW・SET_CANVAS_VISIBLE・
  PUSH_CANVAS と**同じ列で順序が保たれる**。INIT_DISPLAY (CONTROL 型) は
  一度きりの確保の握手 (`if (!g_framebuffer)`) で、繰り返しの切り替えに
  延長すると意味が混ざる。
- 表示側の動き:
  1. 受けたら「切り替え待ち」にする。待ちの間は**描画 (render_frame) を
     止めて前の絵を保つ**。カーソルの移動は前の倍率のまま patch する。
  2. 持ち主の canvas が要求した大きさで present (PUSH_CANVAS) したら、
     fb を差し替え、カーソル位置を比率で直し、描画する。
  3. 待ちが 500ms 程度を超えたら、そのまま切り替える (固まり防止)。
  4. **高解像度中に持ち主の canvas が消された (DELETE_CANVAS) か隠された
     (SET_CANVAS_VISIBLE 0) ら、表示側が自分で通常へ戻す**。これで異常終了
     と park はカーネルの順序に頼らず後始末される。
  5. 通常へ戻す時は DSI バッファの余白 (Tab5 は上下 1 行、NARYAv4 は左右
     1 列) を黒で塗り直す。
- カーネルからの送り方: 入る向き (高解像度へ) は**画面を変える操作
  (他を suspend して隠す、UPDATE_WINDOW) より先に**送り、表示を止めてから
  中身を入れ替える。戻る向き (通常へ) は操作の後に送る (または 4 に任せる)。
  C 側にまとめるなら、`fmrb_app_set_fullscreen` に hires の引数を足して
  その中で順序を守る形もある。

代わりの案:
- INIT_DISPLAY を切り替えにも使う: 一度きりの前提を崩すうえ CONTROL 型で
  GFX の列と順序が保証されないので採らない。
- 表示側が自分で判断する (「見えている canvas が 1 枚で 640x360 なら
  高解像度」): 推測で動くのは避けたい。ただし 4 の自動復帰だけはこの形で
  持っておく。

### 8.3 全画面の canvas と fb の確保

推奨:
- **fb は 640x360 用を別に 1 枚持つ** (460,800 B、PSRAM)。最初に高解像度に
  入る時に取り、以後持ち続ける。426x240 の fb も残し、差し替えるだけ。
  合成 (render_frame)・取り込み・EXPORT_FRAME・カーソルの焼き込みは
  「いまの fb」を相手にするので、ほぼそのまま動く。
- **canvas は必要になった時に取り直す** (UPDATE_WINDOW が確保より大きい時に
  作業用・確定用の 2 枚を 640x360 で取り直す。中身は消えるが、アプリは
  resize で描き直す)。一度大きくしたら canvas が消えるまで縮めない
  (F11 の往復で取り直さない)。起動時から全画面の app は、CREATE_CANVAS の
  時点で 640x360 になる。
- PSRAM の増分 (見積もり): fb 0.46MB + 高解像度 canvas 1 本あたり
  +0.51MB (2x460,800 - 2x204,480)。遠隔の取り込みが有効なら +0.51MB、
  JPEG の作業領域が約 +0.4MB。合計 2MB 前後。内蔵 RAM は増えない
  (カーソルの一時バッファは 3 倍の大きさのまま足りる)。
- 実機の PSRAM の空きは今回測っていない (シリアルを開くと Tab5 がリセット
  されるため)。H1 の起動ログ (Free PSRAM) と M1 行で確かめる。

代わりの案:
- fb を使わず、確定済みの canvas から直接 SRM する: 合成 1 回 (約 0.9MB の
  読み書き) を省ける。代わりに取り込み・EXPORT・カーソル・sprite の経路を
  分ける必要があり、H1 では採らない。速さが足りなければ後で。
- 全 canvas を最初から 640x360 で取る: canvas 8 枚で +4MB。無駄が大きい。

### 8.4 .app.toml のキーと表の属性

推奨: .app.toml は **`fullscreen_hires = true`** (既定 false)、
spawner の表と `fmrb_spawn_attr_t` / ctx は **`.fullscreen_hires`**。
既存の `fullscreen_switchable` と並ぶ名前にする。

- `default/editor` と `default/editor_fs` に `.fullscreen_hires = true`。
  表は全構成共通で持ち、効くかどうかは 6 章の判定で決まる (P4 系と wasm
  だけ既定オン、sim と Retro は黙って無視)。
- ctx の値はカーネルへ `_get_app_info` の `:fullscreen_hires` で出す。
  **mruby 版 (lib/add/picoruby-fmrb-kernel/ports/esp32/kernel.c L440 付近) と
  Spinel 版 (fmrb_spx_kernel.c の記録、buf[164] の隣の空き) の両方**に
  足す (片方だけだと既定の Spinel カーネルで効かない)。
- 構成の判定は C に `fmrb_kernel_fullscreen_hires_size(&w, &h)` のような
  関数を 1 つ置き、カーネル Ruby へは `_fullscreen_hires_size` (nil か
  [640, 360]) で出す。これも mruby / Spinel の両方。
- `default_window_mode = "fullscreen_hires"` のような窓モードの値にする案も
  あるが、「窓でも起動でき、全画面の時は高解像度」(エディタ) を表せない
  ので採らない。

### 8.5 カーソル・入力座標・遠隔の画面取得

推奨:
- **「いまの画面の大きさ」を host_task に 1 つ置く**
  (`fmrb_host_set_screen_size(w, h)` / `fmrb_host_get_screen_size`、世代番号
  つき)。カーネルが SET_SCREEN_MODE を送るのと同時に更新する。
- 発生源はこれを読む: touch_task は仮想の大きさと倍率 (720 / 高さ) を、
  usb_task は `g_screen_width` の一度読みをやめ、世代が変わったらデバイス
  ごとのカーソルを比率で直す。rd_input は切り詰めに使う。ブラウザはページ
  が自動で追従する。
- 表示側のカーソル (`g_cursor_x/y`) は切り替えの瞬間に表示側が比率で直す。
  次の入力で発生源の値に揃う。
- 倍率は定数をやめ、**fb の高さから導出** (720 / fb_h) してバックエンドに
  渡す (Tab5 と NARYAv4 のどちらも短辺 720)。
- 遠隔の画面取得:
  - 取り込みバッファは最大 (640x360) で取り、枠ごとに幅・高さを記録して
    `capture_acquire` で返す (今は acquire 時の fb から読んでいて競合する)。
  - JPEG は符号化のたびに大きさを渡し、違えば作り直す (または最大で取って
    有効範囲だけ使う)。EXPORT_FRAME も同じ。
  - info は大きさが変わったら送り直し、remote.js は VIRT_W/H を info から
    取る。H.264 は大きさが変わったら作り直して IDR。
  - tab5_screenshot は JPEG の大きさを読んで返す (定数をやめる)。
  - H1 で要るのは静止画 (tab5_screenshot = MJPEG 経路) だけ。H.264 と
    remote.js は H4。

### 8.6 エディタのフォントの候補と保存場所

推奨:
- 候補は**今あるものだけ**: [:ja, 12] (既定)、[:ja, 16]、[:ja, 8] (misaki)。
  新しいフォントは flash が足りないので足さない。
- 1 つの設定値にし、窓でも全画面でも同じものを使う (窓で 16 は大きいが、
  選ぶのは本人)。全画面の時だけ効かせる案もある (下の判断事項)。
- 保存場所は **`/home/editor.toml`** (`[editor] font = 12` の形)。エディタは
  Spinel 既定で、File の読み書きはできる (menu.rb L299 で既に使っている)。
- エディタ側は `LINE_H` / `CELL_W` / `EDIT_FONT_SIZE` を変数にする
  (87 か所)。ja 8 は半角 4 px で `CELL_W` = 4、全角 8。ja 16 は 8 / 16。

代わりの案: 既存の `/home/colors.toml` の `[editor]` に `font` を足し、
FmrbColors.set で書く。仕組みは既にある (mruby 版 fmrb-colors.rb と Spinel 版
fmrb_app_base_spinel.rb L164) が、色の表にフォントが混ざり、Colors
ダイアログの一覧 (EDITOR_COLOR_KEYS) との関係も整理が要る。

### 8.7 想定される落とし穴

- **ちらつき**: 入る時に「隠す → 大きくする → 描き直す」の途中が描かれると、
  黒や切り取られた絵が一瞬出る。8.2 の「持ち主の present まで前の絵を
  保つ」で防ぐ。起動時の全画面は、カーネルの切り替えより先にアプリが
  640x360 で present すると、426 モードで左上だけが一瞬出る。これも
  「426 モードでは fb より大きい canvas は合成しない」規則を足せば消せる。
- **余白の残り**: 8.2 の 5 (戻る時に余白を塗り直す)。
- **PSRAM の帯域**: 高解像度では合成 (460KB x 3) と確定コピー (460KB)、SRM
  の読み (460KB) が増える。30fps でも数十 MB/s で、NARYAv4 の走査
  (約 179MB/s) の余裕の中だと見込むが、H1 で `render:` の平均・最大と
  アンダーラン件数を 426 モードと比べる。
- **描画の重さ**: エディタの全面描き直しは面積が 2.25 倍。差分描画
  (本気モード P1) があるので打鍵は軽いはずだが、スクロールと全面描き直しの
  時間を H3 で測る。
- **F11 / Ctrl+Tab の途中**: park・unpark・入れ子の出入りで切り替えが重なる。
  8.1 の「積みが変わったら 1 か所で決める」と、表示側の「最後の要求が
  勝つ」「持ち主が消えたら戻す」で扱う。Ctrl+Tab の復帰は
  `enter_fullscreen` → `resume_app` の順なので、切り替えは resume の後の
  present で完了する形にする。
- **異常終了**: canvas は app の後始末で消える → 表示側が自動で通常へ。
  カーネルの `cleanup_terminated_app` → `pop_fullscreen_frames` からも
  `sync_screen_mode` が走る。二重でも害はない。
- **入力のずれ**: 切り替えの瞬間に各発生源のカーソルがまだ古い座標系に
  いる。8.5 の比率変換。マウスの速さの補正は判断事項。
- **wasm の RGBA**: 取り直すと別スレッドのページが古い番地を読む。最大で
  一度取る。
- **Spinel の 2 本立て**: カーネルの C API と app info の記録は mruby 版と
  Spinel 版の両方に足す (過去に片方だけで効かなかった例あり)。

## 9. 段の分け方の見直し

今の H1-H4 はおおむね妥当だが、次のように組み替えると各段が単独で確かめ
られる。

| 段 | 内容 | 確かめ方 |
|---|---|---|
| H1 | 表示: fb の 2 枚持ちと差し替え、倍率の導出 (PPA・CPU・wasm のバックエンド)、canvas の取り直し、SET_SCREEN_MODE (待ち・自動復帰・余白の塗り直し)、カーソル、取り込みと JPEG (静止画) と EXPORT_FRAME の大きさ追従、wasm の RGBA。**試験用に、アプリから SET_SCREEN_MODE を直接出す口** (開発用の gfx メソッドか試験アプリ) を付ける | Tab5 と NARYAv4 で試験アプリを 640x360 にして tab5_screenshot、`render:` の数値、アンダーラン件数。wasm は web_screenshot |
| H2 | カーネルとアプリ: `fullscreen_hires` 属性 (.app.toml、表、ctx、app info の mruby/Spinel 両方)、構成判定 `_fullscreen_hires_size`、`fullscreen_size(pid)`、`sync_screen_mode` と各呼び出し元、入力の大きさ (host_task + touch/usb/rd_input) | Tab5 で F11・Ctrl+Tab・F5 入れ子・kill。sim で従来どおり (高解像度にならない) |
| H3 | エディタ: 既定オンの確認、フォント選択 (メニュー、/home/editor.toml)、`LINE_H`/`CELL_W` の変数化 | Tab5 で打鍵・スクロール・メニュー。sim で窓とフォント選択 (sim は 426 のまま) |
| H4 | ブラウザ版のページ (表示の大きさを固定、640x360 以上の起動では無効) と遠隔の動画 (H.264、info の送り直し、remote.js)、道具 (tab5_screenshot の大きさ、MCP の説明文と selftest)、文書 | web_* と tab5_* で一通り |

変更点は 2 つ: (1) 入力の追従を H1 から H2 へ移す (カーネルの切り替えと
同時に動かす物なので)。(2) 遠隔の画面取得を「静止画は H1、動画と
ページは H4」に分ける (H1 の検証に tab5_screenshot が要るため)。

## 10. 親とユーザに判断してほしい点

1. 入り口をカーネルが決める案 (8.1) でよいか。アプリからの実行時の要求は
   作らない。
2. 表示側への伝え方を新しい GFX コマンド + 「持ち主の present まで前の絵を
   保つ」+「持ち主が消えたら自動で戻す」(8.2) でよいか。
3. キー名 `fullscreen_hires` (8.4) でよいか。
4. エディタのフォント: 候補を 12 / 16 / 8 (misaki) の 3 つにするか (8 は
   半角 4 px で読みにくい)。設定は窓と全画面で共通にするか、全画面の時
   だけ効かせるか。保存先を /home/editor.toml にするか colors.toml に
   相乗りするか。
5. 高解像度でのマウスの速さ: 画面上の速さを今と同じに保つ (倍率で補正) か、
   仮想画素あたりの速さを保つ (画面上は 2/3) か。
6. カーソルが画面上 48 px から 32 px に小さくなるのを許すか (大きい
   カーソル画像を別に持つこともできる)。
7. 段の組み替え (9 章) でよいか。
