# H1 実施報告: 表示 (display_p4 と wasm の C 側)

> 状態: 完了 | 更新: 2026-09-28 | SET_SCREEN_MODE で 426x240 (3 倍) と 640x360 (2 倍) を行き来できる。NARYAv4 実機 (Tab5 は未接続) とブラウザ版で試験用アプリの往復を確認し、表示はユーザ目視で合格。切り替えの瞬間に 1 フレーム乱れる件は保留 (6 章、2 枚方式の差分は h1_dualbuffer.patch)。5 構成のビルド済み、静的な D/IRAM はどれも基準より減った (s_pins を PSRAM へ)。H2 の入口は `fmrb_app_set_screen_mode`

指示書: ../instruction_h1.md / 計画: ../plan.md / 調査: h0.md

## 1. 結果の要約

- 実機: つながっていたのは **P4-Nano (NARYAv4) だけ**。Tab5 (303a:1001) は Windows 側に見えず、**Tab5 の実機確認は未 (H2 以降でまとめて)**。表示の経路 (display_p4 + PPA) は同じなので、NARYAv4 で確かめた。
- 試験用アプリで 426x240 と 640x360 を往復した。
  - A キーの自動切り替え 20 回 (10 往復) を、最終のビルドで行った。Guru 0、アンダーラン 0、500ms の打ち切り 0 で、最後は 426x240 に戻った。
  - 切り替えのたびの待ち (持ち主が新しい大きさで present するまで) は 19-169ms。
- ユーザの目視: 「表示と切り替え、問題なさそう」(枠・四隅・市松・文字)。ただし**切り替えの瞬間に一瞬乱れる**。原因は分かっているが、直しは保留にした (6 章)。
- 遠隔の画面取得 (tab5_screenshot、MJPEG) では、640x360 と 426x240 の絵が両方取れた。
- ブラウザ版 (web_*、426x240 で開いたページ):
  - 試験用アプリを /home に置き、エディタから F5 で起動した。
  - Space で 640x360 に入り (取得した画面も 640x360)、もう一度押して 426x240 に戻った。
  - 置いたファイルは確認の後に消した。
  - ページの見た目の大きさの追従は H4 で扱う。
- 描画時間 (`render:`、試験用アプリが 100ms ごとに present):
  - 426x240 で avg 23-27ms / max 24-34ms。
  - 640x360 で avg 34-35ms / max 66-67ms。
  - 切り替えを繰り返している間は avg 27-29ms / max 35-41ms。

## 2. 実装

- 表示 (main/drivers/display_p4/)
  - `display_backend.h/.cpp`: 倍率を fb の大きさから導く `display_scale_for()` と、LovyanGFX 経由の余白塗り `display_lcd_clear_outside()` を足した。`DISPLAY_MAX_SCALE` (3) は一時バッファの大きさにだけ使う。
  - `display_backend_ppa.cpp`:
    - 倍率の定数をやめ、present / present_patch (Tab5・NARYAv4) とソフトの代替を導出にした。絵の位置は `dsi_image_rect()` の 1 か所で決める。
    - present の fb の大きさが前回と違えば、SRM の後で絵の外側 (余白) を黒で塗る。
  - `display_backend_cpu.cpp`: 同じく導出と余白塗り。
  - `display_p4_task.cpp`:
    - 640x360 の fb を、最初の要求のときに PSRAM に取る。
    - `SET_SCREEN_MODE` の状態機械: 持ち主の present まで前の絵を保つ、500ms で打ち切る、持ち主の削除や非表示で自動的に戻る。
    - 高解像度中は、持ち主の canvas だけを合成する。
    - canvas の取り直し (`canvas_grow`、縮めない)。
    - カーソル位置を比率で直す。
    - 取り込みを最大の大きさで取り、枠ごとに幅と高さを記録する。
  - 新しい状態は、すべて PSRAM (`FMRB_EXT_RAM_BSS_ATTR`) に置いた。
- プロトコル: `FMRB_LINK_GFX_SET_SCREEN_MODE = 0x59` と `fmrb_link_graphics_set_screen_mode_t{owner_canvas_id, width, height, flags}`。
  - graphics-audio には送らないので、リンクの版数は上げていない。graphics-audio のコードは変えていない (0x59 は向こうでも空き)。
- 遠隔:
  - `rd_encoder_jpeg_init` を呼び直すと、大きさに追従する (バッファは伸ばすだけ)。MJPEG は枠ごとに init する。
  - H.264 は 426x240 以外の枠を飛ばす (追従は H4)。
  - 画面取得をつなぎ直したときの最初の 1 枚が古い絵になる競合を直した (最初の利用者が来たら枠を空にする)。2 枚方式とは関係なく残した直し。
- wasm: RGBA を最初から 640x360 以上で取り、present で大きさを追従させる。
- 試験用の口: `FmrbGfx#_dev_screen_mode(w, h)` (lib/add/picoruby-fmrb-app/ports/esp32/gfx.c)。
  - 実機では `FMRB_DEV_REMOTE_CTL` (リリースで外す既存の開発用スイッチ) のときだけ入る。ブラウザ版には常に入る。
  - picoruby-esp32 の CMake にも同じ option を宣言して、gem に届けた。
- 試験用アプリ `flash/app/test/hires_test.app.rb` / `.toml`。キーは Space/H で切り替え、A で 20 回の自動切り替え、F で 30ms ごとの描画、Q で終了。
- 道具: tools/mcp/lib/tab5.rb の tab5_screenshot は、`frame_size` を JPEG の SOF から読む。432x240 は 426x240 と表示する。説明文にも 1 文足した (親リポジトリ)。selftest_tab5.rb は、80 番ポートを使えないこの環境では走らなかった。
- 内蔵 RAM の相殺: `s_pins` (ピンの管理表、fmrb_hal_pin_manager_esp32.c) を PSRAM へ移した。ピンを取る・放すときのタスクからしか触らない冷たい表。

## 3. H2 から呼ぶ入口

- C: `fmrb_err_t fmrb_app_set_screen_mode(uint8_t pid, uint16_t width, uint16_t height)` (fmrb_app.h / fmrb_app.c)。
  - pid の本体 canvas を持ち主にして、SET_SCREEN_MODE を送る。
  - 640x360 で高解像度、0x0 で通常。
  - P4 と wasm 以外では何も送らず、`FMRB_ERR_NOT_SUPPORTED` を返す。
- 順番:
  - 入るとき: `fmrb_app_set_screen_mode(pid, 640, 360)` → `fmrb_app_set_fullscreen(pid, true, 640, 360)` (UPDATE_WINDOW と resize) → 他を隠す。
  - 戻るとき: `fmrb_app_set_fullscreen(pid, ..., 426, 240)` → `fmrb_app_set_screen_mode(pid, 0, 0)`。
  - 持ち主の canvas が消えるか隠れたら、表示側が自分で通常へ戻す。
- H2 で気を付けること:
  - (a) 426x240 に戻るときに、デスクトップと他の canvas がまだ隠れていると、その 1 枚だけで合成される (resume の後に描き直しが走る)。
  - (b) アプリの on_update が、resize を受け取る前に present すると、新しい大きさの present として扱われて切り替えが完了する。中身は古い配置のままなので乱れる (6 章の見立て 3)。
  - (c) 起動時から全画面のアプリは、カーネルの切り替えより先に 640x360 で present すると、426 モードで左上だけが一瞬出る。

## 4. 内蔵 RAM とビルド

| | 基準 | 今回 | 差 |
|---|---|---|---|
| TAB5 静的な D/IRAM | 183,448 | 183,008 | -440 |
| NARYAv4 静的な D/IRAM | 178,850 | 178,410 | -440 |
| S3 (NARYAv3) 静的な D/IRAM (0a272f54 で測り直し) | 147,387 | 146,995 | -392 |

- 最終のソースで、TAB5 / NARYAv3 / NARYAv4 (esp32、FMRB_HW_TARGET を環境変数で指定、clean_all から)、Linux (x86-64 を確認)、wasm (`rake wasm:web`) のビルドが通った。
- 差は `s_pins` を移した分。表示の追加分は、すべて PSRAM に置いたので 0。
- NARYAv4 の待機時の `IRAM free` (起動 13 秒後): 157,664。基準 (157,200-157,212) より約 +450。
- PSRAM: 640x360 の fb が 460,800 B (最初の切り替えのとき)。持ち主の canvas の取り直しで +約 0.5MB。取り込みを有効にしたときは、2 枠を最大の大きさで取る。

## 5. 試したが外したもの

- 切り替えの瞬間の乱れを消すための、黒塗りと 2 枚方式。6 章に記録した。
- NARYAv4 の DSI バッファは 1 枚、4KB 揃え (`dpi_fb_align_next`) のまま。

## 6. 保留: 切り替えの瞬間の乱れ

ユーザの判断で保留にした (時間がかかり過ぎるため)。後で再開できるよう、分かったことを残す。

### 6.1 原因

DSI のフレームバッファは 1 枚で、走査が常に読んでいる。切り替えの最初の present で、SRM が新しい倍率の絵を、そこへ上から直接書く。SRM は NARYAv4 で 15.5-18.8ms かかり、走査 1 周 (15.5ms) より遅い。フレームの切れ目とも合っていない。そのため 1 枚の中で、古い倍率の古い絵と新しい倍率の新しい絵が継ぎはぎになる。

- 同じ倍率の連続したフレームでも同じ裂け目はできるが、前後の絵がほぼ同じなので見えない。

### 6.2 黒塗りの試み (不採用: 青が出た)

切れ目を待って (DPI の `on_refresh_done` を待つ間だけ登録)、DSI バッファ全体を黒にしてから SRM した。

| 黒塗りの方法 | 時間 | ログのアンダーラン |
|---|---|---|
| CPU の memset | 55ms | 0 |
| PPA fill を一度に | 7ms | 4 回の切り替えで 4 件 |
| PPA fill を 16 の帯に分け、帯と同じ時間休む | 16ms | 4 回で 1 件 |
| PPA fill を 16 の帯に分け、帯の 2 倍休む | 24ms | 20 回で 0 件 |

ユーザの目視は「黒と青のフレームが混ざる。崩れも数回に 1 回まだある」だった。

- 青が出た理由の見立て (確かめていない):
  1. 黒塗りと SRM の書き込みが 40ms ほどの間に集中し、ブリッジが青を出す程度に走査が飢えた。ログの件数が 0 でも、割り込みが立つ条件 (FIFO が完全に空) に届かない途切れは残りうる。
  2. VSYNC 割り込みを出し入れしていた影響。
  3. アンダーランのログは、1 回の割り込みで状態をまとめて消すので、1 フレームに何度途切れても 1 行にしかならない。件数の下限にすぎない。
- 崩れが残った理由: SRM が走査に追い越されていた。

### 6.3 2 枚方式の試み (不採用: 映らない件が未解明、乱れも残った)

DSI のフレームバッファを 2 枚にし、present ごとに裏へ書いて `esp_lcd_panel_draw_bitmap` (fb[i] の中のポインタ) で入れ替える形にした。入れ替える前に、前の入れ替えから `on_refresh_done` が 2 回来るのを待つ。

- Tab5 は M5GFX がもとから 2 枚持っていて、2 枚目は使われていない。
- NARYAv4 は num_fbs = 2 にし、`dpi_fb_align_pair` で 2 枚とも 4KB に揃えた。2 枚が続けて取られると、2 枚目がヒープの見出しの分だけずれるため。
- 仕組みは IDF v5.5.4 のソースで確かめた。draw_bitmap は面の番号を記録するだけで、フレーム終わりの DMA 完了割り込みがその面の DMA の列に張り替える。

経過:

1. 最初の版 (普段の present も入れ替え): 20 回の切り替えでログは正常、描画時間も悪化なし。しかし**ユーザの目視で HDMI に何も映っていなかった**。本体の中の絵 (画面取得) は正常。
2. 試験 A (2 枚確保・コールバック登録はそのまま、入れ替えだけ止める): 映った。
3. 試験 B (起動後に fb1 へ 1 回だけ入れ替え、以後 fb1 に直接書く): 映った。2 枚目の走査そのものは正常。
4. 試験 C (2 秒に 1 回だけ入れ替え): 映り続け、ちらつきも無い。fb0 へ戻る張り替えも正常。
5. 試験 D (間隔を 1000 → 250 → 100ms → 描画ごと、毎秒約 21 回と自動で縮める。2 秒ごとに LT8912B の MIPI 入力の同期を I2C で読む):
   - どの段階でも映った。約 12,000 回入れ替えても正常。
   - ブリッジの入力は H `0x40 0x74` / V `0x02 0xee` で一定だった。
   - 640x360 との切り替えでも映った。ただし**切り替えの瞬間の一瞬の乱れは残った**。
6. 最初の版と試験 D は、描画ごとの段階ではソースの上で同じ動きをする。違いは次の 3 つだけ。
   - 2 秒ごとのブリッジの I2C 読み出し
   - 描画の頻度 (毎秒 10 回と 21 回)
   - 映らないと言われたときの状態 (640x360 と切り替えを多数経た後か、426x240 のままか)
   - **最初の「映らない」は再現せず、原因は特定できていない**。

- 内蔵 RAM: num_fbs = 2 では、DPI ドライバが 2 枚目の DMA のために作る管理用のデータ (`dw_gdma_new_link_list`、IDF の中で内蔵 RAM に固定) で、待機時の空きが約 70-80 バイト減った。静的な D/IRAM は変わらない。
- 差分: **h1_dualbuffer.patch** (このディレクトリ)。今の 1 枚方式の作業ツリーに `git apply` で当たる。試験用の印 (EXPERIMENT) は取り除き、普段の present も入れ替える形にしてある。
  - 対象: display_backend_ppa.cpp、dpi_fb_align.hpp、lgfx_naryav4.hpp、lgfx_tab5.hpp、display_backend.h、display_p4_task.cpp。

### 6.4 再開するときの手がかり

1. **2 枚方式でも乱れが残る理由を先に確かめる**。2 枚方式なら、走査中の面に書かない限り乱れは出ないはず。候補:
   - (i) 切り替えの直後に来る present の中身が古い配置。アプリの on_update が resize の処理より先に present すると、新しい大きさの present とみなされ、切り替えが古い配置の絵 (取り直した直後の黒い canvas に状態行だけ、あるいは幅の違う並びで読んだ絵) で完了する。試験用アプリは 30-100ms ごとに present するので、起きうる。直すなら、切り替えの完了条件を「resize を処理した後の present」にする。たとえば、アプリの resize の処理 (app.c) が送る SET_SPRITE_CLIP の後、あるいは専用の合図の後の present を待つ。**この件は 1 枚方式でも同じ乱れの原因になっている可能性がある**ので、1 枚方式のまま先に試す価値がある。
   - (ii) カーソルの小さな書き込み (present_patch) が、切り替え直後から次の描画までの間に、新しい倍率で表の面に書く。
   - (iii) 面ごとの余白の黒塗り (裏の面に書いているはずだが、確かめていない)。
2. 上流 (release/v5.5 の HEAD と master) には、面の入れ替えの仕組みの修正は無い。master には `on_frame_buf_complete` (DMA 完了割り込みの中で「その面を再利用してよい」を知らせる) があり、入れ替えの完了を DMA 側で知る形にするならこれを取り込む。v5.5.4 には口が無いので、components/ での上書きが要る。
3. 最初の「映らない」を再現させるなら、最初の版で 640x360 と切り替えを多数経た状態、描画が毎秒 10 回、ブリッジの I2C 読み出しなし、の条件でそろえる。
4. 2 枚方式は、内蔵 RAM が約 80 バイト増える (上記)。相殺の候補は doc/spinel_upstream_ext/report/p2c.md 10 節。
