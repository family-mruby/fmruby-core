## 2. 表示側の守り (h3.md 9.5)

### 2.1 再現の試み (直す前の版)

直す前の版 = 今のソースから d35973b8 (全画面のドラッグの直し) だけを作業ツリーで戻したもの。NARYAv4 に焼き、遠隔入力 (tab5_input) と遠隔の kill (tab5_app) で操作した。

| 手順 | 結果 |
|---|---|
| 試験用アプリ (起動時から 640x360) の上端をドラッグでずらして kill | 固まらない。`owner deleted` で 426x240 に戻る |
| エディタ (窓から F11 で 640x360) の上端をドラッグでずらして kill | 固まらない |
| エディタを大きくずらし (canvas が (300,10)) kill | 固まらない |
| **エディタの 640x360 の全画面で、右下の角をドラッグ** | **画面が止まる** (下記) |
| エディタ (640x360) の上に `default/editor_fs` を重ね、上のほうをずらして kill (h3.md 9.5 のログと同じ形。3 回) | 固まらない。下のエディタの 640x360 に戻る |

- h3.md 9.5 のときのログを、MCP の capture.log から読み直した。
  - 固まったのは、**エディタ (640x360) の上に 2 つ目のエディタ (`default/editor_fs`) を重ねた状態**で、上の方をずらして kill したときだった (1 つだけのときではない)。
  - kill の後、表示側は持ち主を下のエディタの canvas へ付け替え (`SET_SCREEN_MODE: owner=6 640x360 (now 640x360)`)、上の canvas を消し、`STOPPING -> FREE` の行でログが切れていた。
  - 次の行は電源投入のリセットで、それまでの時間は分からない。`Reaped` と `dev ctl: kill ... ok` の行も出ていない。
- 同じ形を 3 回試したが、再現しなかった。**原因は特定できていない**。
- 直した後の版でも、同じ形の操作はこれまでの確認の範囲では起きていない。ただし再現しない以上、直ったとは言えない。

### 2.2 見つけた穴: 持ち主の大きさが 640x360 でなくなると画面が止まる

- 直す前の版では、全画面のエディタは「リサイズできる窓」のままだった。右下 10x10 を押すとリサイズが始まり、canvas が 405x205 になった。
- 表示側は高解像度の間、「持ち主の committed の絵が 640x360」のときしか描かない (`screen_mode_can_render`)。そのため、以後いっさい描かなくなった。
- ログ: `End resize: PID 5, final=(405x205)`、`UPDATE_WINDOW: id=6 405x205`、`owner 6 handled its resize` の後、`render:` の行も GFX の統計も出ない。
- 遠隔の画面取得も、新しい枠が来ないので失敗した (`could not grab a frame`)。
- 10 秒ごとの定期のログと WiFi は生きていた。**板が固まったのではなく、画面だけが止まった**。
- kill すると `SET_SCREEN_MODE 0x0` で 426x240 に戻り、元どおり動いた。
- 記録: scratchpad に保存したシリアルの全文 (hang_resize_before_fix.log)。今の版では d35973b8 で全画面のリサイズの経路は無いが、表示側の穴としては残っていた。

### 2.3 直し方 (display_p4_task.cpp)

1. **止まらない**: 高解像度の間、持ち主が 640x360 の絵を出せない状態を `owner_unshowable_since_ms` で数える。出せない理由は、消えた、隠れた、大きさが違う、リサイズ後の絵が無い、のどれか。これが `SCREEN_MODE_WAIT_MS` (500ms) 続いたら、表示側が自分で 426x240 に戻り、1 回描く。
   - ログ: `screen mode: owner N has shown no 640x360 frame for Nms (wrong size|hidden|gone|no frame), back to the base screen`。
   - 普通の出口 (カーネルが canvas を縮めてから `SET_SCREEN_MODE 0x0`) は数ミリ秒で進み、切り替え中 (pending) は数えないので、この守りは働かない。今回の確認では、正常な切り替え 20 回で一度も出ていない。
   - 持ち主を付け替えたとき (高解像度のまま別のアプリへ) は数え直す。
2. **位置を無視する**: 高解像度の持ち主の canvas は、与えられた位置にかかわらず (0,0) に写す。本体、viewport、sprite、clip の 4 か所を同じ変数にした。
3. **入力の大きさを合わせる**: 表示側が自分で決めた切り替えでも、host_task の「いまの画面の大きさ」(入力が読むもの) を書き換える。自分で決めた切り替えは次の 3 つで、以前はカーネルの要求のときだけ書いていた。
   - 持ち主が消えた・隠れた
   - 切り替えの取り消し
   - 上の守り
   これが無いと、守りが働いた後もマウスが 640x360 の座標のままになる。

- 増えた状態は `g_smode` (PSRAM) の中の 4 バイトだけ。

### 2.4 直した後の確認 (NARYAv4)

- 直す前と同じ版 (d35973b8 を戻したまま) に守りを足したものを焼き、同じ操作をした。
  - 右下のドラッグで 405x205 にすると、534ms 後に `wrong size` で 426x240 に戻った。エディタは 405x205 の窓として見え、打鍵もできた。kill で正常に終わった。
  - 試験用アプリの上端をずらしても、画面は (0,0) のまま動かなかった (ログには `Start drag` が出る)。kill で正常に終わった。
- 最終の版 (d35973b8 を戻さない、ふつうのソース) で、次の操作をした。守りのログは 0 件、Guru と abort も 0 件。
  - エディタの F11 の往復、Ctrl+Tab の往復、Ctrl+Q での終了
  - 試験用アプリの F11 の往復と kill

## 3. 遠隔デスクトップ (ブラウザ) と H.264

### 3.1 端末側

- `rd_http.c`
  - WS の `info` の `w`/`h` を固定の 426/240 から、いまの画面の大きさ (`fmrb_host_get_screen_size`) にした。
  - `cur` にも `w`/`h` を足した。カーソルが動かなくても、大きさが変われば送る。
  - 前回の値は PSRAM に置いた。
- `rd_stream.c`
  - 枠の大きさがエンコーダの設定と違えば、エンコーダを作り直す。作り直すと最初の枠が IDR になる。
  - 送信の組み立て用のバッファは、大きい枠が来たときに伸ばす。
  - 426x240 以外の枠を飛ばす処理は外した。
  - 見出しを 8 バイトから 14 バイトにした: `[0x01][flags][enc_w16][pts32][vis_w16][vis_h16][enc_h16]`。ページも同じファームウェアに入っているので、互換は気にしていない。
- `rd_encoder_h264.c`: 高さも 16 の倍数に詰める (640x360 → 640x368、下の 8 行は黒)。PPA の出力の大きさ、YUV の黒塗り、バッファの大きさを詰めた高さで計算する。`s_pad_h` は PSRAM。

### 3.2 ページ (tool/web/remote/remote.js)

- `VIRT_W/H` の定数をやめ、`screenW/H` を `info`、`cur`、H.264 の見出しから更新する。
- 見た目の大きさは画面の大きさに比例させない。窓では幅 852px 固定、全画面の表示では 16:9 で埋める。倍率は `852 / screenW` になる。
- クリックの座標は `screenW/H` で割り戻す。H.264 の詰めた下の行は、`#view` が隠す。

### 3.3 確認

- H.264 の流れを Ruby の小さな受け手で 25 秒読んだ。その間に F11 で 640x360 → 426x240 → 640x360 と切り替えた。
  - 見出しの大きさは `640x360 (640x368)` → `426x240 (432x240)` → `640x360 (640x368)` と変わり、各区間の最初の枠が IDR だった。
  - 各区間を ffmpeg で読み、どちらも誤りなく読めた (640x368 と 432x240)。
- Windows の Chrome を headless で動かし、端末のページを開いた。
  - H.264 (安全な接続とみなす指定を付けた) で 640x360、MJPEG で 640x360 と 426x240 を撮った。どれも同じ 852x480 の枠に出た。詰めた下の行は見えない。
  - CDP でページ上のマウスを動かし、640x360 の (600,330)、(20,20)、(639,359) を狙った。端末が返したカーソルは (600,329)、(20,20)、(639,359) だった。1 のずれは、枠が 479px に丸められたため。

## 4. ブラウザ版のページ (wasm/web/main.js)

- `applyZoom` の大きさの基準を、fb の大きさから**選んだ解像度** (`baseSize()`、選択欄の値) に変えた。どちらも 16:9 なので、640x360 の絵を同じ枠に描いても歪まない。初回のズームの既定 (画面が狭ければ fit) も同じ基準で決める。
- 入力はもとから、canvas の画素と表示の大きさの比で割り戻している。
- 確認 (web_* とは別に、Windows の Chrome を CDP で動かした):
  - 起動: fb 426x240、枠 852x480
  - エディタ (窓): 426x240、852x480
  - F11: fb 640x360、枠 852x480
  - F11: fb 426x240、枠 852x480
- web_* での確認: エディタを F11 で 640x360 にした。(620,340) への移動で右下にカーソルが出た。打鍵もできた。

  - S3: 0x43ab50、空き 30%
