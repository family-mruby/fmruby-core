## 2. 実装

### 2.1 文字の大きさを変数にした

- `CELL_W` / `LINE_H` / `EDIT_FONT_SIZE` の定数をやめ、`@cell_w` / `@line_h` / `@edit_font_size` にした。
  - H0 の「87 か所」は、枠 (メニュー・状態行・対話) の 6x8 フォントの `CHAR_W` / `CHAR_H` も数えていた。枠はフォントを選んでも 6x8 のままなので、実際に変えたのは本文の格子に関わる 20 か所 (editor.app.rb の配置・クリック、render.rb の行・選択・カーソル・フォント指定、ti_ui.rb の補完の窓の位置、debug_pane.rb の区切り点の縦位置)。
  - 3 つのフォントはどれも半角 : 全角 = 1 : 2 で、高さが大きさそのもの。よって `@cell_w = 大きさ / 2`、`@line_h = 大きさ`。misaki の半角は 4px、全角 8px で、ASCII と全角が同じ格子に並ぶことを画面で確かめた。
- 配置の計算は `recompute_layout` 1 か所のまま。フォントを変えたときは `relayout_for_font` が、桁数・行数を出し直し、折り返しの区切り (EditorCore の折り返しの cache は幅ごとに持つので古い値は出ない) に合わせて表示の起点の区切りを詰め、カーソルが見えるように動かす。
  - 小さいフォントに変えると、文書の終わりより下が空き、起点より上の行が隠れたままになる。そこで空いた行の数だけ起点を上へ戻す (`fill_view_bottom`)。カーソルは下へずれるだけなので見えたまま。
- 窓と全画面の切り替え (F11)、窓の大きさの変化は、これまでどおり `on_resize` → `recompute_layout` で、新しい `@cell_w` / `@line_h` を使う。

### 2.2 選ぶ口と保存 (editor/font.rb、新設)

- `EditorMenu` を開き直して足した (別の module にしない理由は 3 章)。
- `edit_font_size_at(i)` が候補 (8 / 12 / 16) を返す。候補の数と既定は整数の定数 `EDIT_FONT_COUNT` / `EDIT_FONT_DEFAULT` (const.rb)。
- 設定ファイルの読み書きは FmrbColors と同じ手書きの解析 (Spinel 側に TOML の読み手が無いため)。
- i18n に `m_font`、`font_small` / `font_standard` / `font_large`、保存に失敗したときの `b_font_save_failed` を英日で足した。

### 2.3 Spinel の set_font が 16 を捨てていた

- `fmrb_spx_gfx_set_font` (main/app/fmrb_spx_gfx.c) が `:ja` の大きさを 8 と 12 だけ受け、16 は `FMRB_SPX_ERR_RANGE` で**何も送らずに**返していた。Ruby 側に戻り値は届かない。
  - 症状: 16 を選ぶと、直前の `set_font(:default)` のまま 6x8 で描かれ、日本語は豆腐になった (sim で発見)。格子は 8px なので字の間が空く。
- mruby 版 (lib/add/picoruby-fmrb-app/ports/esp32/gfx.c) は 8 / 12 / 16 を受けていたので、同じ集合にそろえた。表示側 (display_p4 と graphics-audio) は元から 16 を描ける。

## 3. 内蔵 RAM とビルド

| | H2 | H3 | 差 |
|---|---|---|---|
| TAB5 静的な D/IRAM | 183,008 | 183,008 | 0 |
| NARYAv4 静的な D/IRAM | 178,410 | 178,410 | 0 |
| S3 (NARYAv3) 静的な D/IRAM | 146,995 | 146,995 | 0 |

- 各構成とも `rake clean_all` から `FMRB_HW_TARGET=... rake build:esp32` (標準構成: Spinel カーネル + Spinel エディタ) でビルドし、`idf.py size` の DIRAM 行を読んだ。
- **最初の版は NARYAv4 で +24 バイト (178,434) だった**。同じ手順で H2 の元 (9c440686) を作り直し、`idf.py size-components` と map を比べて原因を特定した。
  - Spinel の生成 C では、整数以外の定数 (配列・文字列) が 1 つにつき 4 バイトのポインタとして内蔵 RAM の小さいデータ区画 (`.sbss.cst_*`) に置かれる。配列 4 つと文字列 1 つで 20 バイト。
  - 新しい module (EditorFont) 1 つにつき、インスタンスの数え (`.sbss.sp_EditorFont_pool_count` / `.sdata...pool_max`) で 8 バイト。
  - 生成 TU の BSS を PSRAM へ送る仕組み (SP_TU_BSS) は、この小さいデータ区画には効かない。
  - 直し: 候補の表を配列の定数から `edit_font_size_at` (case) にし、設定ファイルのパスは文字列リテラルを直接使い、フォントの一覧の文字キーは `menu_hotkeys` の中で配列を組む (メニューを開いた時だけ)。module は増やさず `EditorMenu` に足した。整数の定数は生成 C で即値になるので残した。これで 3 機種とも H2 と同じ値。
  - **Spinel のアプリに「配列や文字列の定数を 1 つ足す」と内蔵 RAM が 4 バイト増える**。今後も同じ予算で見るなら、spinel の書き方の文書に足す価値がある (5 章)。
- アプリの大きさ: TAB5 0x604f90 → 0x608d80 (+15,856 B)、区画の空きは 14% (0xf7280) のまま。NARYAv4 0x603660、空き 14%。S3 0x43a850、空き 30%。
- NARYAv4 の待機時の `IRAM free` (起動 13 秒後): 157,652。H2 は 157,652 / 158,016。
- Linux (x86-64 を確認、標準構成と全 mruby 構成)、wasm (`rake wasm:mruby` → `wasm:mrb` → `spinel:gen` → `wasm:web`) も通った。`rake test` も通った。
- 新しいフォントは足していない。sdkconfig と graphics-audio は変えていない。

## 5. 気づいたこと・残したこと

- **半角カタカナの幅**: EditorCore の幅の表は半角カタカナを 2 セルと数える (efontJA_12 に字形が無く、全角の豆腐で描かれるため。editor_core.c の cp_cells)。misaki は半角カタカナを 4px で持つので、misaki のときだけ 1 セルで描かれ、同じ行のその後ろがずれるはず。エディタのかな入力は半角カタカナを出さないので、ふつうの使い方では出ない。efontJA_16 での描かれ方は測っていない。直すなら幅の表をフォントごとにする (EditorCore の口が増える) ので、今回は見送った。
- **記号の幅**: U+2000-2E7F (○ や → など) は幅の表で 1 セル。efont では半角で描かれることを前提にしている。misaki はこの範囲を全角で描く字があり得るので、小 (8) では後ろがずれる可能性がある。測っていない。
- **折り返しの cache**: EditorCore の折り返しの cache は 24 行分 (EC_WRAP_CACHE_N、内蔵 RAM の static)。640x360 では 12 で 28 行、8 で 42 行が画面に出るので、全面の描き直しのたびに cache から溢れて数え直しになる。正しさには影響しない (打鍵 1 回の描き直しは行単位で、sim の計測で平均 1ms 未満)。増やすと内蔵 RAM が増えるので触っていない。PSRAM へ移すなら別の段で。
- 全画面で起動したエディタを F11 で窓へ戻すと、既定の窓 (240x200) になる (H2 と同じ)。
- sim の起動で一度、graphics-audio の入力ソケットの bind が EINTR で失敗して立ち上がらなかった。`sim_down` → `sim_up` で直った。今回の変更とは関係ない。
- 検索で見つかった語は、カーソルが動くだけで選択の色は付かない (従来どおり)。

## 7. 判断の結果 (ユーザ、2026-09-28)

1. 半角カタカナと記号の幅 (5 章) は今は直さず、記録だけにする。
2. 「Spinel では整数以外の定数 1 つで内蔵 RAM 4 バイト、module 1 つで 8 バイト」を doc/spinel_aot/ruby_writing_constraints.md の C 節に足した。
   - 生成器の側で定数のポインタ (`.sbss.cst_*`) と module の数え (`pool_count` / `pool_max`) を PSRAM に置く手当ては、**内蔵 RAM の削減候補**として残す。
   - NARYAv4 の最終のビルドの map で数えると、`.sbss/.sdata.cst_*` が 57 個で 225 バイト、`pool_count` / `pool_max` が 116 個で 464 バイト、合わせて約 690 バイト。回収できる量は大きくないが、新しいアプリや定数を足すたびに増える分を止められる。
   - 移すときの注意: P4 (RISC-V) ではこの区画は gp 相対でたどる小さいデータ区画なので、属性で区画を付け替えるか、生成器が小さいデータにしない形で出す必要がある。S3 (Xtensa) では区画の作りが違うので、別に確かめる。
3. 窓と全画面のフォントは共通のまま。
4. フォントの 3 つの見え方は、ユーザの目視で合格。

## 9. 追加: 全画面の上端をドラッグすると窓が動く

### 9.1 症状と再現

ユーザの報告: 全画面のとき、画面の上のほうをドラッグすると窓が動いてしまう。

- sim の標準構成 (426x240 の通常の全画面): エディタの全画面 (`default/editor_fs`) で、(300, 4) を押して (340, 80) まで動かして離すと、全画面の canvas ごと右下へずれた。デスクトップの壁紙が見えた。
- NARYAv4 実機 (640x360 の高解像度の全画面): 同じ操作で canvas がずれ、画面の左と上に黒い帯が出た。ログにも `Start drag: PID 6, offset=(400,4)` が出た。
- **高解像度かどうかに関係なく起きる**。640x360 の座標を 426x240 として判定していたのではない。

### 9.2 原因

- カーネルの input_router.rb の mouse_down の経路。
  - 全画面のときは、押された位置に関係なく全画面のアプリへ回す (エディタ本気モードの P1 で入れた、上端の行をデスクトップへ回さない処理)。
  - ところが、その後の窓の操作の判定は窓のときのままだった。全画面のアプリでも、窓の中の相対の y が 11 未満ならタイトルバーとみなしてドラッグを始めていた。全画面の canvas は (0, 0) にあるので、画面の上 11 行がすべて当たりになる。
  - 同じ理由で、リサイズできるアプリ (エディタ) なら、右下の 10x10 でリサイズも始まり得た。

### 9.3 直し方

- 押された窓が全画面のアプリ (`@fullscreen_pid`) なら、リサイズの取っ手とタイトルバーの判定をどちらも飛ばす。クリックはそのままアプリへ届く (エディタのメニューは開く)。
- カーネルの 1 か所だけの変更。mruby 版と Spinel 版のカーネルは同じ Ruby のソース。

### 9.4 確認

- sim の標準構成 (426x240)
  - 全画面で上端をドラッグしても、右下の角をドラッグしても、canvas は動かない。
  - 上端をクリックするとエディタの View が開く。
  - F11 で窓に戻すとタイトルバーのドラッグで動く。もう一度 F11 で全画面にすると、上端のドラッグでは動かない。
- NARYAv4 実機
  - 640x360 の全画面で、上端と右下の角をドラッグしても動かない。
  - F11 で窓に戻すと、タイトルバーのドラッグで動く (`Start drag` は窓のときの 1 回だけ)。F11 で全画面に戻すと、また動かない。
  - 通常の全画面のアプリ (ntsc_color_test、426x240) でも、上端のドラッグで動かない。
  - どちらのアプリも kill で正常に終わった。Guru 0、abort 0。
- NARYAv4 の静的な D/IRAM: 178,410 (変わらず)。アプリの大きさ 0x603750、空き 14%。TAB5 と S3 は測り直していない (カーネルの Ruby に定数も module も足していない)。
- 全 mruby 構成の sim では、この直しを試していない (カーネルの Ruby は両方の構成で同じソース)。

### 9.5 直す前の版で一度だけ固まった

- 直す前の版の NARYAv4 で、次の順に操作した。
  1. 640x360 の全画面のエディタをドラッグでずらした。
  2. ずれたまま kill した。
- すると `State: STOPPING -> FREE` のログを最後に、10 秒ごとの定期のログも止まった。WiFi も応答せず、固まったと見られる。
- 再現を取る前に、直した版を焼くためにリセットしたので、原因は調べていない。
- 見立て: 表示側が、高解像度の持ち主の canvas が (0, 0) 以外にある状態を想定していないのかもしれない。持ち主が消えて通常の画面へ戻る経路での、合成の範囲の計算などを疑っている。
- 直した版では全画面の canvas を動かす経路が無いので、この状態には入らない。ただし、表示側の穴は残っている可能性がある。
