# 作業指示書 H4: 残り (守り・遠隔・ページ・道具・試験用の口)

対象: 実装担当のサブエージェント。前提: plan.md、report/h1.md (6 章の保留)、
report/h2.md、report/h3.md (9.5 章の固まった件)。report は `report/h4.md` へ。

## やること

1. **表示側の守り (report/h3.md 9.5)**: 直す前の版で、640x360 の全画面の
   エディタをドラッグでずらし (canvas が (0,0) 以外)、そのまま kill したところ、
   `STOPPING -> FREE` のあとで板が固まった (ログも WiFi も止まった)。今の版では
   全画面の canvas がずれる経路は無いが、表示側の穴として残っている可能性がある。
   - 表示側で、高解像度の持ち主の canvas が (0,0) 以外にある・大きさが合わない・
     消えた、のどの場合でも安全に通常へ戻るようにする (位置を無視して写す、
     戻す経路で待ち合わせが永久に続かない、など)。
   - 可能なら、試験用の口で同じ状態 (持ち主の canvas をずらしてから kill) を作り、
     直す前に固まることと、直した後に固まらないことを確かめる。固まったら、
     再起動の前にシリアルの出力と、できれば状態を記録する。
2. **遠隔デスクトップ (ブラウザ、tool/web/remote/remote.js) と H.264**:
   高解像度の間もクリックが画面全体に届くよう、画面の大きさに追従する。
   H.264 のエンコーダを大きさの変化に追従させる (H1 では 426x240 以外の枠を飛ばしている)。
3. **ブラウザ版のページ (wasm/web/main.js の applyZoom)**: 見た目の大きさが
   fb の大きさに比例して変わらないようにする。
4. **MCP の道具**: tab5_screenshot は H1 で frame_size を JPEG から読むように
   直してある (親リポジトリ 9b3172c)。MCP サーバの再起動後に 640x360 と出ることを
   確かめる。web_screenshot / web_input / tab5_input の座標の説明の追従。
5. **試験用の口を外す** (H2 の判断): `FmrbGfx#_dev_screen_mode` と試験用アプリの
   Space の直接の切り替え。試験用アプリは `.app.toml` の属性だけで高解像度になる形で残す。
6. **文書**: plan.md の受け入れ条件の確認、使い方 (`.app.toml` の
   `fullscreen_hires`、エディタのフォント) をアプリの手引き (fmrb-app-new の
   スキルが参照する文書や doc/reference) に足す。
