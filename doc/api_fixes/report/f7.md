# F7 アプリごとの「今いる場所」(Dir.chdir を全端末で使えるように)

> 2026-11-25 | サブ (Opus) の報告。指示書は instruction_f7.md、計画は plan.md の「F7 の設計」(決定 21)。
> ブランチ `api-fixes-f7`。push していない。

## 1. 結果

plan.md の設計 1〜6 をそのとおり入れた。今いる場所はファイルの HAL がアプリの枠ごとに持ち、相対パスはそこから解く。
絶対パスの解決の結果は 1 バイトも変わっていない (直す前の resolver から取った表とホストの試験で照合。4 章)。
プロセスの `chdir()`・`getcwd()` はどこからも呼ばなくなった。止まる条件 (同梱のアプリが相対パスに頼っていて動きが
変わる所・設計の外の動きの変化) には当たらなかった。

## 2. 置き場所と、直した関数

**置き場所: ファイルの HAL の中の表** (`components/fmrb_hal/fmrb_hal_file_cwd.c`)。`char s_cwd[FMRB_MAX_APPS][128]`
(空文字が "/")。ESP32 では `FMRB_EXT_RAM_BSS_ATTR` で PSRAM に置く。

- アプリの文脈 (`fmrb_app_task_context_t`) に欄を足す形は採らなかった。HAL が `fmrb_app.h` を読むことになり、
  今の層の作り (HAL は libc と fmrb の下の層だけ) が崩れるため。文脈の構造体は内蔵 RAM の `g_ctx_pool` にあるので、
  欄を足すと内蔵 RAM も増える。
- HAL は「アプリとは何か」を知らない。アプリの層が起動時に「呼んだタスクの枠の番号を返す関数」を入れる
  (`fmrb_hal_file_set_cwd_slot`。変更の hook と同じ形)。HAL が読むヘッダは `fmrb_limits.h` (`FMRB_MAX_APPS`) と
  `fmrb_attr.h` だけで、どちらも下の層。
- 枠の番号の関数 (`main/app/fmrb_app.c` の `cwd_slot_of_current`) は `fmrb_current()` の `app_id` を返し、文脈の無い
  タスクとカーネル (0)・ホスト (1) には -1 を返す。-1 のタスクはいつも "/" で、chdir は断る (`FMRB_ERR_NOT_SUPPORTED`)。
- 消す: アプリの普通の終わり (`close_owned_files`) と kill (`force_release_resources`) で `fmrb_hal_file_cwd_forget`。
  どちらも枠が FREE に戻る前。表は自分の枠を自分だけが書き読むので鍵は要らない。
- 長さの上限は `FMRB_HAL_FILE_CWD_MAX` = 128 (NUL を含む。ESP32 の HAL の経路の上限 `MAX_PATH_LEN` と同じ)。

直した関数・ファイル:

| 所 | 中身 |
|---|---|
| `fmrb_hal_file.h` | `FMRB_HAL_FILE_CWD_MAX`、`fmrb_hal_file_set_cwd_slot`、`fmrb_hal_file_cwd_forget`、chdir・getcwd と resolve_path の説明 |
| `fmrb_hal_file_cwd.c`・`.h` (新規、全端末) | 表、`fmrb_hal_file_normalize` (相対なら今の場所を前に付け、`//`・`.`・`..` をまとめ、"/" より上に出ない。posix の `normalize_virtual` の手順をそのまま移した)、`fmrb_hal_file_cwd_apply` (絶対パスはそのまま返す)、`fmrb_hal_file_chdir` (まとめた後のパスを HAL の stat で確かめる。仮想のフォルダ `/mnt` も通す)、`fmrb_hal_file_getcwd` |
| `platform/posix/fmrb_hal_file_posix.c` | `normalize_virtual` を共通の物に (読み取り専用・`/mnt/host` の歩き・仮想のフォルダの判定が全部これを通るので、相対パスもまとめた後で判定される)。平らな表の resolve で相対パスに今の場所を付ける。chdir・getcwd を消した |

| `platform/esp32/fmrb_hal_file_esp32.c` | open・stat で、相対パスを hw_proxy に渡す前に呼んだタスクの中で絶対パスにする (hw_proxy のタスクはアプリでないので、そこで解くと "/" から解いてしまう)。build_path は解けないとき空文字にする。chdir・getcwd を消した |
| `CMakeLists.txt` (fmrb_hal)・`hosted/hosted.cmake`・`rakelib/native.rake` | 新しいソースを足した |
| `lib/upstream/hal-esp32-dir/dir_hal.c` (ESP32・ネイティブ版) | chdir・getcwd を HAL へ (errno: 無い ENOENT、フォルダでない ENOTDIR、長すぎる ENAMETOOLONG、入らない ERANGE) |
| `lib/upstream/patch/.../mruby-dir/ports/posix/dir_hal.c` (sim・ブラウザ版) | 自前の "flash" の付け方をやめ、HAL の resolve_path で解く。chdir・getcwd を HAL へ |
| `lib/upstream/family_mruby_linux.rb`・`family_mruby_wasm.rb`・`family_mruby_native.rb` | mruby-dir に HAL のヘッダの場所を渡す (linux・wasm の rb は picoruby の build_config/ に写されて読まれるので、上へたどって探す。ネイティブ版は posix の port を外しているが、presym の走査がそれを前処理するので要る) |
| `lib/gems/picoruby-fmrb-filesystem` | `File._getwd` (C、`fmrb_hal_file_getcwd`) を足し、`File.expand_path` の基準を `ENV["PWD"]` からそれに。File が mruby-dir に頼らないように Dir.getwd でなくこれにした |
| `main/app/fmrb_app.c` | 枠の番号の関数を入れる、終わりで消す |
| `sig/dir.rbs`・`sig/fmrb_file.rbs` | getwd・chdir・expand_path の説明 |

`Dir.chdir` のブロックの形は mruby-dir の Ruby (`getwd` → `_chdir` → ensure で `_chdir(wd)`) のままで動く。前は sim で
getwd が "/project/flash/tmp" のようなホストの場所を返していたので戻せず RuntimeError だった。`Dir.pwd` は mruby-dir の
別名で同じ。`File.absolute_path?`・`File.realpath`・`File.absolute_path` は File に無い (前と同じ)。

## 3. 変わる動き (前 → 後)

| 式 | sim 前 | ESP32 前 | 後 (sim・ESP32 とも) |
|---|---|---|---|
| `Dir.getwd` (起動直後) | `"/project"` (コンテナの場所) | `"/"` | `"/"` |
| `Dir.chdir("/tmp")` | 0、**プロセスの場所が動き全アプリのパスが外れる** | RuntimeError | 0 (このアプリだけ) |
| chdir の後の `Dir.getwd` | `"/project/flash/tmp"` | `"/"` | `"/tmp"` |
| chdir の後の `File.open("a.txt","w")` | ホストの `flash/tmp/flash/a.txt` | `/a.txt` (= flash の根) | `/tmp/a.txt` |
| chdir の後の `File.expand_path("a.txt")` | `"/a.txt"` | `"/a.txt"` | `"/tmp/a.txt"` |
| chdir の後の、ほかのアプリの絶対パス | 外れる | 変わらない | 変わらない |
| `Dir.chdir("/nope")` | RuntimeError | RuntimeError | RuntimeError "/nope" (場所は変わらない) |
| `Dir.chdir("/tmp/a.txt")` (ファイル) | RuntimeError | RuntimeError | RuntimeError |
| `Dir.chdir("/home") { Dir.getwd }` | RuntimeError | RuntimeError | `"/home"`、後の getwd は元のまま |
| 2 つのアプリの場所 | 共有 (プロセス) | - | 別々 |
| アプリを閉じて開き直す | 戻らない | - | `"/"` |
| `File.expand_path` の基準 | `ENV["PWD"]` か "/" | 同じ | `Dir.getwd` (`ENV["PWD"]` は見ない) |
| 相対パスの `..` (場所 "/") | `flash/../x` (flash の外のホストの場所) | `/flash/../x` | `/x` ("/" より上に出ない) |
| ESP32 で場所 "/" の相対 `tmp/x`・`sd/x`・`mnt/sd/x`・`flash/x` | (sim は前から `/tmp/x` などと同じ) | `/flash/tmp/x` ほか (flash の中) | `/tmp/x` (RAM)・SD・SD・`/flash/x` (絶対パスの "/tmp/x" ほかと同じ所) |
| `Dir.entries(".")`・`Dir.exist?("mnt")` (ESP32) | - | flash の根・false | 今の場所・仮想の `/mnt` を見る |

最後の 2 行は「相対パスは今の場所 + パス」という設計からそのまま出る変化で、ESP32 で前は相対パスだけが別名の表を
通らなかった食い違いが消える。同梱のコードにこの形の相対パスは無い (5 章)。ネイティブ版 (層の表) は前から相対パスを
"/" からまとめていたので、変わるのは chdir の後だけ。

## 4. 試験と確認

- **ホスト** `test/api_fixes/cwd/cwd_test.c` を `test/api_fixes/run.rb` から 2 通りに組む (posix の HAL + tmpfs + cwd、
  ESP32 の namespace + cwd + stat の代役)。posix 570 件・esp32 217 件、全部通る。中身:
  - **絶対パスが変わらない**: 直す前の resolver (posix の平らな表・層の表、ESP32 の表を写した物) で 41 個の絶対パスの
    解決結果・仮想のフォルダの子の数・読み取り専用の 2 つの答えを取って表にし、直した後に、場所が "/" のときと
    別の場所のとき (`/home`・`/sd/music`) の両方で同じになることを確かめる。`/home/../x`・`//a`・`/..` など
    まとめていない形もそのまま。
  - 相対パス、`.`・`..`、"/" より上、127 バイトちょうどは通る・1 バイト多いと断る、相対の chdir が上限を越える、
    2 つのアプリで別々、アプリが終わると "/"、アプリでないタスクは "/" で chdir できない、枠の関数が無いとき、
    範囲外の枠、無い所・ファイルへの chdir は場所を変えない、プロセスの作業ディレクトリが動かない。
  - 平らな表で相対の open・rename・remove・mkdir・opendir が今の場所で効く。ほかのアプリは影響されない。
  - 層の表 (ネイティブ版): 場所 `/home` から `../usr/a.txt`・`../../../../usr/a.txt` は読み取り専用、書き・mkdir・
    rename は `FMRB_ERR_READ_ONLY` でホストに何もできない。場所 `/usr` (配布の木) で `x.txt` に書けない。
    `/mnt/host` から書いた物はホームに入り、`../root/...` は読み取り専用、`/mnt/root/etc` に入って書けない。
    `..` の仮想のフォルダの答え。
  - `File.expand_path` (run.rb の Ruby、`File._getwd` を差し替え): "/"・"/tmp" での相対、`..`、`.`、絶対、
    2 番目の引数が相対・絶対、`ENV["PWD"]` を見ないこと (9 件)。
- `rake regress`: host 36 suites 全部通過、描画の記録 310 件通過 (ネイティブ版の file_hal の試験は新しいソースで通る)。
- `rake sig:coverage`: 「3. doc gaps」0 のまま、基準から変化なし。`rake sig:test` 通過。
- **sim** (NARYA v3、`rake clean` → `rake build:linux`、シェルの irb):
  `Dir.getwd` → "/"、`Dir.chdir("/tmp")` → 0、`Dir.getwd` → "/tmp"、`File.open("a.txt","w"){...}` → 2、
  `File.exist?("/tmp/a.txt")` → true、`File.expand_path("a.txt")` → "/tmp/a.txt"、
  `Dir.chdir("/nope")` → `[RuntimeError, "/nope"]`、`Dir.chdir("/tmp/a.txt")` → RuntimeError、
  `Dir.chdir("/home") { Dir.getwd }` → "/home" で後の `Dir.getwd` は "/tmp"、`Dir.entries(".").size > 0` → true、
  `Dir.chdir(".."); Dir.getwd` → "/"。
  シェルが /tmp にいる間に、デスクトップのファイルマネージャが "/" と "/app" を普通に並べ、エディタが起動して 1 打鍵
  入った。2 つ目のシェルは "/" から始まり、そこで `/home` に移っても 1 つ目は "/tmp" のまま (`File.exist?("a.txt")` も
  1 つ目だけ true)。kill して開き直すと "/"、ウィンドウの閉じるボタンで普通に終わらせて開き直しても "/"。core の
  ログに abort・Guru は 0 件。
- `rake regress:screens` (`rake clean` の後): sim の retro 6/6・modern 6/6・ブラウザ版 5/5 が通り、ネイティブ版は
  libmruby が組めずに落ちた (posix の port を外しているのに presym の走査が前処理し、新しい include が見つからない)。
  `family_mruby_native.rb` に include の場所を足して `ONLY=native` で流し直し、native 6/6・native-keys 5/5 が通った。
  直した後に全部の構成を 1 回で流し直してはいない。
- `rake clean` は sim 用に流した (指示で許された物)。これは ESP32 の `build/esp-idf/picoruby-esp32/libpicoruby-esp32.a`
  も消す (rake の決まった動き)。ESP32 のビルドはしていない。
- ESP32 だけのコード: IDF のコンテナで既存の `build/compile_commands.json` (P4) の引数を読み、`-fsyntax-only` で
  `fmrb_hal_file_esp32.c`・`fmrb_hal_file_path_esp32.c`・`fmrb_hal_file_cwd.c` が通る (build/ には書いていない)。
  `fmrb_hal_file_path_esp32.c` と `fmrb_hal_file_cwd.c` はホストの試験でも組んで動かしている。

## 5. 同梱のアプリ・カーネルほかの相対パス

grep した所: `flash/`・`main/ruby/`・`lib/gems/` の Ruby で File・Dir・IO の呼び出しに "/" で始まらない文字列を渡す所、
`main/`・`components/`・`lib/` の C で `fmrb_hal_file_*` に "/" で始まらない文字列を渡す所、`Dir.chdir`・`Dir.pwd`・
`Dir.getwd`・`ENV["PWD"]`・`chdir(`・`getcwd(` の使い所、変数を渡す所のうち名前だけを渡していそうな物。

| 所 | 中身 | 影響 |
|---|---|---|
| `flash/app/game/rpg_demo/generate_world.rb` | `File.expand_path("../../../../tools/...", __dir__)` | PC の Ruby で走る生成の道具。端末では動かない。なし |
| `lib/gems/picoruby-fmrb-filesystem/mrblib/file.rb` | `ENV["PWD"]` | 直した本体 |
| シェル (`main/ruby/default_app/shell/shell_commands.rb`) | `cd` は自前の `@current_dir` を持ち、コマンドは全部絶対パスにしてから File・Dir を呼ぶ | なし。シェルの中の irb の `Dir.chdir` はシェルのアプリの HAL の場所を動かすが、シェルのコマンドは絶対パスしか使わないので影響しない (`cd` とは別のまま。設計 6) |
| `receive_conf.rb`・`ai_helper/editor.rb` | 変数を渡すが、中身は定数の絶対パス | なし |

`Dir.chdir`・`Dir.pwd`・`Dir.getwd` を使う同梱のコードは無かった。相対パスの文字列を File・Dir・HAL に渡す所も無かった。
アプリは chdir しない限り場所が "/" なので、仮に相対パスがあっても sim では前と同じ所、ESP32 では `tmp`・`sd`・`mnt`・
`flash`・`..` で始まる物だけが変わる (3 章)。**止まる条件には当たらない。**

## 6. メモリ

- 内蔵 RAM: 静的には 0 (表 9 × 128 バイトと関数の指し先 4 バイトは `FMRB_EXT_RAM_BSS_ATTR` で PSRAM。全 ESP32 の
  sdkconfig.defaults に `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY=y` があることを確かめた)。ESP32 のビルドは
  していないので `regress:size` の実測は無い (親が流す)。
- PSRAM: 1,156 バイト (9 枠。ブラウザ版は `FMRB_MAX_APPS` に比例)。
- スタック: 絶対パスの経路は前と同じ (相対パスのときだけ外に出した関数が 128 バイトを持つ。hw_proxy のタスクには
  絶対パスしか届かない)。`Dir.chdir` はアプリのスタックで 128 + `fmrb_file_info_t` (約 280) バイト。
- VM プール: `File._getwd` のメソッド 1 つ分。`regress:run` は流していない。
- ESP32 だけでコンパイルされる直したファイル: `components/fmrb_hal/platform/esp32/fmrb_hal_file_esp32.c`・
  `fmrb_hal_file_path_esp32.c` (新規。ホストの試験でも組む)・`fmrb_hal_file_esp32_paths.h` (新規)、
  `lib/upstream/hal-esp32-dir/dir_hal.c` (ESP32 とネイティブ版)。`fmrb_hal_file_cwd.c` は全端末。

## 7. 親が P4-Nano で流す式 (/tmp だけ)

```
Dir.getwd                                  # => "/"
Dir.chdir("/tmp")                          # => 0
Dir.getwd                                  # => "/tmp"
File.open("a.txt", "w") { |f| f.write("x") }   # => 1
File.exist?("/tmp/a.txt")                  # => true
File.read("/tmp/a.txt")                    # => "x"
File.expand_path("a.txt")                  # => "/tmp/a.txt"
File.exist?("/home")                       # => true (絶対は前と同じ)
Dir.chdir("/tmp") { Dir.getwd }            # => "/tmp"
Dir.chdir("/home") { Dir.getwd }           # => "/home"
Dir.getwd                                  # => "/tmp"
begin; Dir.chdir("/nope"); rescue => e; e; end  # RuntimeError
Dir.getwd                                  # => "/tmp"
Dir.chdir(".."); Dir.getwd                 # => "/"
Dir.entries("tmp").include?("a.txt")       # => true (tmp は RAM の /tmp)
File.delete("/tmp/a.txt")                  # => 1
```

続けて、シェルを閉じて開き直した irb で `Dir.getwd` → "/"。シェルが /tmp にいる間にファイルマネージャとエディタが
普通に開くこと。

## 8. 見つけた別の物・確かめていないこと

- irb で `Dir.chdir("/nope") rescue $!` (後置の rescue に `$!`) の結果の行が出なかった (`begin ... rescue => e` の
  形では出る)。chdir とは関係なさそうな irb の表示の癖と見て、追っていない。
- posix の `fmrb_hal_file_stat` は層の表の仮想のフォルダ (`/mnt` など、配布の木に実物の無い所) をフォルダと答えない
  (ネイティブ版で `File.directory?("/mnt")` が false になりうる。ESP32 の stat は答える)。前からの動きで直していない。
  chdir は仮想のフォルダを先に見るので `/mnt` に入れる。
- ESP32 の絶対パスは前から `..` をまとめない (`/home/../x` → `/flash/home/../x`、`/..` → `/flash/..`)。絶対パスは
  変えない約束なのでそのまま (相対パスはまとめる)。
- 確かめていないこと: 実機 (P4-Nano ほか) 全部、ESP32 のビルドと `regress:size`・`regress:run`、ブラウザ版の手での
  確認 (`regress:screens` の中だけ)、SD がある端末の `/sd` への chdir、Spinel のアプリからの Dir.chdir。
