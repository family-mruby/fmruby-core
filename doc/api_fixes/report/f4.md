## 2. 直さなかった項目・止まった項目と理由

止まる条件に当たった項目は無い。ただし C1 で、指示書の「それ以外のシステムのピン (画面・SD・USB・I2S・リンクほか) の
`GPIO.new` は例外」が**台帳に載っているピンにしか効かない**ことが分かった。台帳にピンを足すのは「区別を足す」の外で、
I2C・RMT・シリアルの MIDI など GPIO 以外の口の動きも変わるので、足していない。**親とユーザが決めること**:

| 機種 | 台帳に載っているシステムのピン | システムが使うのに台帳に無いピン (`fmrb_pin_assign.h`・sdkconfig から) |
|---|---|---|
| P4-Nano (NARYAv4) | 35 (BOOT)・37・38 (コンソール) | **SD 39〜44**、I2S 9〜13、アンプ 53、C6 の EN 54、**C6 の SDIO 14〜19**、Ethernet 28〜31・34・49〜52、I2C 7・8 (画面の線。アプリが I2C を開くまで空き) |
| Tab5 | 24・25 (USB-Serial-JTAG) | SD 39〜44、キーボード 0・1・50、タッチ 23・31・32、背光 22、I2S (`audio_p4_hw.c` の中の定数) |
| NARYA v3 | 23 本 (1 章の表) | I2C 14・21 (RTC。開くときだけ取る)、47・48 (Grove 2) |
| AtomS3R | 11 本 | I2C 0・45、IMU の INT 16、IR 47 |
| StickS3 | 11 本 | I2C 47・48、I2S 14〜18、PM1 の IRQ 13、IR 42・46、背光 38 |

今のファームで、これらのピンに `GPIO.new` すると台帳は空きと答え、**取れてしまい、ピンを設定し直す** (P4-Nano の
SD・WiFi が止まる)。直し方の候補:

- (a) 各機種のシステムのピンを台帳に足す (`register_system_pin`。SDMMC・I2S・SDIO・アンプ・EN など、ドライバが
  直に持つ物)。gpio_viewer では灰色になる。I2C・RMT を同じピンで開くことも (今の作りでは台帳を見ないので) 変わらない。
- (b) GPIO だけが見る「システムが使うピン」の表を別に持つ (gpio_viewer の表示は変わらない)。
- (c) 今のまま、sig と文書に「台帳に無いピンは守られない」と書く。

## 3. 動きが変わる所と同梱のアプリへの影響

- **GPIO** (ESP32 だけ):
  - `GPIO.new`: システムのピン → IOError "GPIO n is used by the system"、ほかのアプリ・別の使い方 (I2C など) が持つ
    ピン → IOError "GPIO n is in use by another app or driver"、端末に無い番号 (P4 は 55 以上、S3 は 49 以上) →
    ArgumentError "GPIO n does not exist on this board"。**断られたときピンの設定は変えない** (前は台帳の結果を見ずに
    向きを変えていた)。
  - 本体のボタン: `IN` (プルつきも) なら通る (台帳には取らない、リセットもしない。前と同じ)。`OUT`・`OPEN_DRAIN`・`ALT`、
    後からの出力の `set_dir`・`write`・`write_at` → IOError "GPIO n is a system button: input only"。
  - `set_dir_at`・`pull_up_at`・`pull_down_at`・`open_drain_at`・`set_function_at`・`write_at`: `GPIO.new` と同じ判定。
    **空いているピンはこのアプリの物として台帳に取る** (前は台帳を通らなかった)。gpio_viewer で緑になり、アプリが
    終わると返る。
  - 読むだけの `read_at`・`high_at?`・`low_at?`: **どのピンも読める** (台帳に取らず、hw_proxy も通らない。gpio_viewer は
    もともと `GPIO` でなく `FmrbHw.pin_status_all` で台帳を読んでいるので、どちらにしても全ピンを表示できる)。
  - `read`・`high?`・`low?` と `*_at` の読み: 読めないと IOError "GPIO n could not be read" (前は -1、`high?` が true)。
  - `high_at?`・`low_at?` の引数の読み方を `read_at` と同じにした (前は Integer だけ。文字列は TypeError → ArgumentError
    "Wrong GPIO pin name")。
  - 例外のクラス: 上流の流儀 (ピンの名前が悪い = ArgumentError、周辺機器の失敗 = `GPIO::Error.peripheral_error` が出す
    IOError) に合わせ、番号が無いのは ArgumentError、それ以外は IOError。
- **I2C** (ESP32 だけ): クラスは IOError のまま、文が "Invalid I2C unit: 名前" / "I2C unit 名前 is in use by another app" /
  "... is fixed to other pins on this board (not SDA n / SCL n)" / "... is not ready yet" / "... did not start on SDA n /
  SCL n"。文を見て分ける同梱のアプリは無い (i2c_kbd は文を画面に出すだけ)。`fmrb_hal_i2c_init` が負の値を
  `FMRB_I2C_ERROR` (-1) 1 つでなく fmrb_err_t で返す (呼び手の RTC は `!= FMRB_I2C_OK` で見るので変わらない)。
- **MIDI**: `playing?` が、ほかのプレーヤー・ほかのアプリが鳴らしている間も、自分の予約が鳴り終われば false。
  `Sched._depth` は引数なしなら前と同じ (全体)、持ち主の番号を渡すとそのアプリのそのプレーヤーの分。
  遅れの数え方 (underrun) も自分の分の 0 で見る。`_free` (入れられる残り) は全体のまま (待ち行列は全員で共有なので)。
  同梱のアプリはどれもプレーヤーを 1 つしか持たず、1 つのときの動きは前と同じ (host の試験)。
- **IO**: 1 章の表。`$stdout.read`・`STDIN.write` も IOError。
- **JSON**: `JSON.generate` に NaN・Infinity・-Infinity (入れ子も) を渡すと `JSON::GeneratorError` "NaN not allowed in
  JSON" など (CRuby と同じ文)。同梱で Float を JSON に書く所で NaN になり得る物は探していない。
- **TableClient#leave**: false → nil。同梱のゲームは値を使っていない。

C1 の同梱のアプリへの影響 (`flash/app`・`flash/usr/share/samples`・`flash/lib`・`sdk`・`main/ruby`・`lib/gems` を grep。
`GPIO` を使うのは step_sensor だけ。led_matrix は RMT、gpio_viewer は `FmrbHw`):

| アプリ | 呼び方 | NARYA v3 | Tab5 | P4-Nano | AtomS3R | StickS3 |
|---|---|---|---|---|---|---|
| step_sensor | `GPIO.new(11, GPIO::IN)` → `read` | 11 はリンクの SPI (システム): IOError、rescue して `@key1 = nil` (前は向きを変えていた) | 11 は空き: 前と同じ | 11 は I2S の DIN (台帳に無い): 前と同じに取れる | 11 は空き: 前と同じ | **KEY1 (ボタン): 前と同じに読める** |
| gpio_viewer | `FmrbHw.pin_status_all` | 変わらない | 変わらない | 変わらない | 変わらない | 変わらない |

step_sensor は StickS3 用 (BMI270 を I2C で読む)。ほかの機種で開くことは想定していないが、開いても落ちない。

## 4. C1: 入力として読んでよいピン、実機で確かめる手順

### 機種ごとの、入力として読んでよいシステムのピン (本体のボタン)

`fmrb_pin_assign.h` の `FMRB_PIN_BUTTON_UP`・`_DOWN`・`_ENTER` のうち番号のある物。host の試験が実物のヘッダから出した一覧:

| 機種 | ボタン (IN だけ) | ほかのシステムのピン (台帳) |
|---|---|---|
| NARYA v3 | 6 (UP)・7 (DOWN)・8 (ENTER) | 0・1・3・4・5・9・10・11・12・13・15〜20・35〜39・45・46 |
| Tab5 | なし | 24・25 |
| P4-Nano (NARYAv4) | なし | 35・37・38 |
| AtomS3R | 41 | 14・15・19・20・21・35・36・37・42・46・48 |
| StickS3 | 11 (KEY1)・12 (KEY2) | 0・19・20・21・35・36・37・39・40・41・45 |

ボタンかどうかはビルドのときにヘッダの定数と比べて決める (表も RAM も持たない)。

### P4-Nano で親が確かめる手順

シェルの irb で 1 行ずつ。**P4-Nano には本体のボタンが無いので、ボタンの確認は StickS3 か AtomS3R でしかできない**。
**今の台帳の穴 (2 章) のため、39〜44 (SD)・14〜19 (WiFi)・9〜13・53・54・28〜31・34・49〜52 には `GPIO.new` しない**。
48 は led_matrix が使うピンの見出しのピン (何もつながっていない前提。つながっていれば別の空きピンに)。

| 打つ式 | 期待 |
|---|---|
| `g = GPIO.new(48, GPIO::IN)` | GPIO のオブジェクト |
| `g.read` | 0 か 1 |
| `FmrbHw.pin_status(48)` | 2 (USER_GPIO) |
| `GPIO.new(35, GPIO::IN) rescue $!` | `#<IOError: GPIO 35 is used by the system>` |
| `GPIO.new(37, GPIO::OUT) rescue $!` | 同じ形の IOError。**シリアルのログが止まらない** |
| `GPIO.set_dir_at(38, GPIO::OUT) rescue $!` | 同じ形の IOError。ログが止まらない |
| `GPIO.read_at(35)` | 0 か 1 (読むだけは通る) |
| `GPIO.new(60, GPIO::IN) rescue $!` | `#<ArgumentError: GPIO 60 does not exist on this board>` |
| (別のシェルを開いて) `GPIO.new(48, GPIO::IN) rescue $!` | `#<IOError: GPIO 48 is in use by another app or driver>` |
| (最初のシェルを閉じてから、もう一度同じ式) | GPIO のオブジェクト |
| gpio_viewer を開く | 35・37・38 が灰色 (SYS)、48 が緑 (GPIO)、ほかは空き。55 本 |
| `Dir.entries("/mnt/sd").size` と画面 | SD が読め、画面が乱れていない |

StickS3 があれば: `k = GPIO.new(11, GPIO::IN)` → `k.read` が 1、KEY1 を押したまま 0。`GPIO.new(11, GPIO::OUT) rescue $!` →
`#<IOError: GPIO 11 is a system button: input only>`。`k.write(1) rescue $!` も同じ。step_sensor の KEY1 で歩数が 0 に戻る。

## 5. C7: 相対パス (直さない)

sim (NARYA v3、シェルの `run` で流したスクリプト。結果はログ) と、ESP32 の読み:

| 式 | sim | ESP32 (読み) |
|---|---|---|
| `Dir.getwd` | `"/project"` (コンテナの中の作業場所がそのまま) | `"/"` (ESP-IDF の `getcwd` はいつも "/"。`components/newlib/src/realpath.c`) |
| `ENV["PWD"]` | nil | nil の見込み (設定する所が無い) |
| `File.expand_path("a.txt")` | `"/a.txt"` | `"/a.txt"` (`ENV["PWD"] \|\| "/"`) |
| `File.open("b.txt", "w")` (chdir の前) | 端末の `/b.txt` に出来る (`flash/b.txt`) | `/b.txt` (= `/flash/b.txt`。HAL が相対パスを flash の頭に付ける) |
| `Dir.chdir("/tmp")` | 0 (**プロセスの作業場所が `flash/tmp` に動く**) | RuntimeError "/tmp" の見込み (ESP-IDF の `chdir` は ENOSYS) |
| chdir の後の `Dir.getwd` | `"/project/flash/tmp"` | `"/"` |
| chdir の後の `ENV["PWD"]` | nil | nil |
| chdir の後の `File.open("a.txt", "w")` | 出来るが、場所はホストの `flash/tmp/flash/a.txt` (端末のどこにも見えない) | `/a.txt` (chdir が効かないので前と同じ) |
| chdir の後の `File.expand_path("a.txt")` | `"/a.txt"` | `"/a.txt"` |
| chdir の後の `File.exist?("a.txt")` | true | (書いた物が `/a.txt` なので) true |
| `File.exist?("/tmp/a.txt")` | false | false |
| chdir の後の `File.exist?("/home/f4/c7.rb")` (在る物) | **false** | true |
| `Dir.chdir("/home") { Dir.getwd }` | RuntimeError "/project/flash/tmp" | RuntimeError "/home" の見込み |

**食い違いと、sim の不具合**: sim では `Dir.chdir` が通ってしまい、ファイル HAL が相対の `flash/` を頭に付けているので、
**その後は全アプリの全てのパス (絶対パスも) が `flash/tmp/flash/...` を指し、端末のファイルが見えなくなる**
(シェルを閉じても戻らない。sim を起こし直した)。ESP32 では chdir は失敗し、相対パスはいつも flash の根。どちらも
`File.expand_path` は `ENV["PWD"]` を見るが、誰も PWD を設定しない。

### 親が P4-Nano で流す式 (/tmp だけを使う)

```
File.open("/tmp/a.txt", "w") { |f| f.write("x") }
Dir.getwd
ENV["PWD"]
File.expand_path("a.txt")
begin; Dir.chdir("/tmp"); rescue => e; e; end
Dir.getwd
File.exist?("a.txt")
File.expand_path("a.txt")
Dir.chdir("/tmp") { Dir.getwd } rescue $!
File.delete("/tmp/a.txt")
```

読みどおりなら: `"/"`、nil、`"/a.txt"`、`#<RuntimeError: /tmp>`、`"/"`、false (`/a.txt` を見る)、`"/a.txt"`、RuntimeError。

### そろえ方の案

- (a) **chdir はできない、にそろえる**: sim の dir HAL (`lib/upstream/patch/picoruby-mruby/.../mruby-dir/ports/posix/dir_hal.c`)
  の chdir を ESP32 と同じく失敗させ、getcwd を "/" にする。利用者から見ると、どこでも「相対パスは根から」「chdir は
  例外」。直すのは数行。sim が壊れる道が消える。CRuby の書き方 (chdir してから相対で開く) は使えないまま。
- (b) **アプリごとの作業場所を持つ**: `Dir.chdir` がディレクトリの有無を確かめてアプリの作業場所 (と `ENV["PWD"]`) を
  変え、ファイル HAL・dir HAL・`File.expand_path` が相対パスをそれに付ける。CRuby に近い。アプリごとにパスの置き場
  (100 バイトほど) と、HAL の解決の入口の変更が要る。シェルの `cd` (今は自分の `@current_dir` だけ) ともつなげられる。
- (c) **`ENV["PWD"]` だけで足す**: `Dir.chdir` を Ruby の側で包み、在るか確かめて `ENV["PWD"]` を変える。`File.open` などは
  `File.expand_path` を通してから HAL に渡す。C は sim の chdir を止めるだけ。ENV が全アプリで共有なら、あるアプリの
  chdir がほかのアプリに見える (ENV の持ち方は確かめていない)。

## 6. メモリ・ESP32 だけの所

- C1: 台帳 (PSRAM の `s_pins`) は変えていない。ボタンの区別はコード (定数との比較) で、**内蔵 RAM の増分 0 バイト**
  (静的な領域は増えない)。hw_proxy の要求の引数が 4 → 16 バイト (+12) と判定の受け 4 バイトで、`GPIO.new` などを
  呼んでいる間だけアプリのタスクのスタックに置く。VM プール: 増える ivar・定数は無い (gpio.rb の `_init` の引数が 1 つ
  増えるだけ)。
- C2: 増分なし (文は .rodata)。C3: 予約 1 件は 16 バイトのまま。`_depth(owner)` は待ち行列 (最大 128 件) をロックの
  中で数える (呼ぶのは曲の終わりの待ちの 20 ms ごとと、遅れたときだけ)。C4〜C6: 増分なし。
- 素の malloc は使っていない。

**sim でコンパイルされていない (ESP32 だけの) 直したファイル** (sim のビルドのログでコンパイルされたのは posix の pin
manager・posix の GPIO HAL・`fmrb_io.c`・`fmrb_filesystem.c`・`fmrb_midi_sched.c` だけ):

- `main/drivers/hw_proxy/hw_proxy.c`・`hw_proxy_gpio.c`・`hw_proxy_i2c.c`
- `components/fmrb_hal/platform/esp32/fmrb_hal_gpio_esp32.c`・`fmrb_hal_pin_manager_esp32.c` (ホストの試験では組んで動かした)・`fmrb_hal_i2c_esp32.c`
- `lib/upstream/picoruby-gpio-proxy/gpio.c`・`lib/upstream/picoruby-i2c-proxy/i2c.c` (`PICORUBY_SRCS`)

これらはホストの gcc で `-fsyntax-only -Wall` を通した (ESP-IDF・FreeRTOS の見出しは scratchpad の代役、mruby の
presym は sim のビルドの物に足りない名前を足した物)。型や名前の誤りは見られるが、ESP-IDF の本物の見出しとの
食い違いは見られない。checkpoint の表 (`rake checkpoint:table`) は picoruby-gpio の posix port で組むので、
`GPIO_claim` は代役 (0 を返す) になる見込み (`tools/ckpt_table/ckpt_table.rb` が未定義の名前に作る)。ESP32 のビルドで
一緒に確かめてほしい。

## 7. 途中で見つけた別の不具合・確かめていないこと

見つけたもの (直していない):

- **sim で `Dir.chdir` すると、そのプロセスの全てのファイルのパスが外れる** (5 章)。
- **台帳に無いシステムのピン** (2 章)。P4-Nano の SD・WiFi (SDIO) は `GPIO.new` で設定し直せてしまう。
- **I2C の初期化が台帳を見ない**: `hw_proxy_i2c.c` は `fmrb_pin_manager_acquire` の結果を捨てる。システムのピンや
  ほかのアプリの GPIO のピンでも I2C を開ける。`frequency:` も開くときには調べない (0 などは読み書きのときに失敗する見込み)。
  RMT (`hw_proxy_rmt.c`) も acquire の結果を捨てる。
- 先に初期化された I2C の線を引き継ぐ道 (owner が NULL) は、渡されたピンを見ずに通す (I2C1 を `sda_pin` なしで開ける)。
- `TableClient#forget` も false を返す (sig は void。指示に無いので触っていない)。
- `GPIO.new` に方向の無い flags を渡すと、ArgumentError の前に `_init` がピンを取る (上流の順番。アプリが終わると返る)。

確かめていないこと:

- ESP32 のビルドと実機 (C1・C2 の全部)。台帳の判定は host の試験だけ。
- 2 つのアプリで GPIO の同じピンを取り合う形、アプリが終わって返る形 (読みと host の試験だけ)。
- C3 の SmfPlayer の sim (host の試験だけ。sim は MmlPlayer で見た)。シリアルの MIDI 出力での `playing?`。
- C7 の ESP32 の欄は全部読み。
- Modern の sim・ブラウザ版・ネイティブ版 (C3〜C5 はどれも共通のコードなので同じになる見込み)。`rake regress:run`・
  `regress:size`・`regress:screens`。
