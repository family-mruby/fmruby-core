# F6 GPIO だけが見る「アプリが触ってはいけないピン」の表

> 2026-11-25 | サブ (Opus) の報告。指示書は instruction_f6.md (決定 20)。ブランチ `api-fixes-f6`。push していない。

## 1. 結果

- 機種ごとに「アプリが GPIO として設定してはいけないピン」の 64 ビットの定数を、`fmrb_pin_assign.h` の名前から
  ビルド時に組み立てる (`fmrb_hal_pin_manager_esp32.c` の `GPIO_RESERVED`)。RAM を持たない。
- `fmrb_pin_manager_claim_gpio` が台帳より先にこの表を見る。表のピンの `GPIO.new`・`set_dir`・`set_pull`・`write`・
  `*_at` の設定は `FMRB_PIN_GPIO_NO_SYSTEM` (IOError "GPIO n is used by the system")。読むだけ (`read_at`・`high_at?`・
  `low_at?`) は今までどおり通る。台帳 (`s_pins`)・`register_system_pin`・I2C・RMT は変えていない。
- 名前の無かったピンに名前を足した (番号は変えていない): P4-Nano の SDIO 6 本と Ethernet の RMII 9 本、Tab5 の SDIO 6 本・
  C6 のリセット・I2S 5 本。SDIO と C6 の EN/リセットは、実機のビルドのときに sdkconfig の `CONFIG_ESP_HOSTED_SDIO_*` と
  `_Static_assert` で照合する (ずれたらビルドが止まる。ホストで正しい値と、わざとずらした値の両方を確かめた)。
- `FmrbHw.pin_status`・`pin_status_all` は表のピンを `PIN_SYSTEM_EXCLUSIVE` と答え、`pin_available?` は false (4 章)。

## 3. 表に入れなかった・分からなかったピン

| 機種 | ピン | 入れなかった理由 |
|---|---|---|
| NARYA v3 | UART0 (コンソール) のピン | sdkconfig は既定の UART0 だが、ピン番号がヘッダにも文書にも無い |
| NARYA v3 | flash の 26〜32、PSRAM の 33・34 | 名前が無い (`FMRB_PIN_RESTRICTED_*` は 35〜37 だけ。AtomS3R のヘッダの注記は「33-37」) |
| AtomS3R・StickS3 | 33・34 (Octal PSRAM) | 同上。外には出ていない (h0.md・m3s.md) |
| P4-Nano・Tab5 | strap・flash のピン | ヘッダは「PSRAM はパッケージ内」とだけ。strap の番号は文書に無い |
| P4-Nano | 24・25 (P4 の USB-Serial-JTAG) | この基板のコンソールは UART0 (37・38)。24・25 の配線は文書に無い |
| AtomS3R | 16 (BMI270 の INT1) | システムは使っていない。IMU を読むアプリが入力に使える線なので、親の判断に残す |
| StickS3 | 13 (M5PM1 の割り込みの出力) | システムは使っていない (電源の制御は I2C 経由)。出力にするとチップの出力とぶつかる心配はある。親の判断に残す |
| Tab5 | PI4IO の先 (C6 の電源・アンプ・LCD の reset) | GPIO ではない (I2C の拡張 IC) |

NARYA v3 の I2C1 (14・21) は doc/hw_resources/report/h0.md では「アプリに開放する候補」側に書かれているが、RTC が載った
システムの I2C なので表に入れた。`I2C.new` でこのバスを開くことは今までどおりできる。

## 4. `FmrbHw.pin_status` ほかの扱い

**表のピンを「システム」と答えるようにした。** sig の `PIN_SYSTEM_EXCLUSIVE` は「アプリは使えない」、`pin_available?` は
「アプリが取れるか」と説明していて、`GPIO.new` の sig も「使ってよいピンは `FmrbHw.pin_available?` で調べる」と案内して
いる。台帳のままだと P4-Nano の SD・SDIO が `pin_available? == true` なのに `GPIO.new` が IOError になり、説明と食い違う。
gpio_viewer も同じ値を色にするので、灰色 (SYS) のピンが「使えないピン」とそのまま読める。

- 新しい関数 `fmrb_pin_manager_get_app_status` (台帳の値。ただし台帳が空きで表にあるピンは `PIN_SYSTEM_EXCLUSIVE`) を
  `pin_status`・`pin_status_all` が使う。`pin_available?` は「台帳が空き かつ 表に無い」。
- 台帳が持っているピンは台帳の値のまま (アプリがシステムの I2C を開いている間は `PIN_USER_I2C`、閉じれば SYS)。
- `fmrb_pin_manager_get_status`・`is_available` (台帳そのもの) は変えていない。I2C・RMT・gpio-proxy の自分のピンの判定は
  台帳を読むので動きは同じ。
- sim・ネイティブ版・ブラウザ版 (posix の pin manager) は表が空で、今までどおり全部 `PIN_UNUSED`。
- これで変わる利用者から見た動きは「表のピンの `pin_status` が 1、`pin_available?` が false、gpio_viewer で灰色」。
  指示書 2 の選択肢の範囲。

sig: `sig/fmrb_hw.rbs` (冒頭に `pin_available?` で確かめる案内、`PIN_SYSTEM_EXCLUSIVE` の説明に無線・音・システムの
I2C と「I2C.new では開ける」、`pin_status`・`pin_available?`・`pin_status_all`)、`sig/gpio.rbs` (冒頭、`GPIO.new` の
「システムのピン = `pin_status` が `PIN_SYSTEM_EXCLUSIVE`」)。機種ごとのピンの一覧は書いていない。

## 5. 同梱のアプリと見本への影響

`flash/app`・`flash/usr/share/samples`・`flash/lib`・`sdk`・`main/ruby`・`lib/gems/*/mrblib` を grep。samples と lib に
ピンを渡す所は無い。表は GPIO だけが見るので、I2C・RMT の欄はどれも変わらない。

| アプリ | 呼び方 | NARYA v3 | Tab5 | P4-Nano | AtomS3R | StickS3 |
|---|---|---|---|---|---|---|
| step_sensor | `GPIO.new(11, GPIO::IN)` | 前と同じ IOError (リンクの SPI) → rescue | **新しく IOError** (SDIO の D0) → rescue して `@key1 = nil` | **新しく IOError** (I2S の DIN) → rescue | 前と同じに取れる | 前と同じ (KEY1 を入力で) |
| step_sensor | `I2C.new(I2C1)` | 変わらない | 変わらない | 変わらない | 変わらない | 変わらない |
| gpio_viewer | `FmrbHw.pin_status_all` | SYS が 14・21 増える | SYS が 25 本増える | SYS が 30 本増える | SYS が 3 本増える | SYS が 10 本増える |
| led_matrix | `RMT.new(48)` (Tab5 は 54) | 変わらない | 変わらない | 変わらない | 変わらない | 変わらない |
| i2c_kbd・imu・encoder8・時計の設定 | `I2C.new(I2C1)` | 変わらない | 変わらない | 変わらない | 変わらない | 変わらない |

**新しく動かなくなる組み合わせは無い。** step_sensor は StickS3 用のアプリで、Tab5・P4-Nano では前から rescue の道がある
(しかも前は 11 番を取って `gpio_reset_pin` していたので、Tab5 では WiFi の SDIO、P4-Nano ではマイクの線を設定し直して
いた)。

気づいたこと (直していない):

- led_matrix は StickS3 では RMT を 48 (システムの I2C の SCL) に開く。RMT は台帳の結果を捨てる (F4 の 7 章) ので
  今までどおり通ってしまう。F6 の範囲外。
- sig の例 `GPIO.new(7, GPIO::IN | GPIO::PULL_UP)` (と flash/help) の 7 は、P4-Nano ではシステムの I2C で IOError になる
  (NARYA v3 ではボタンで通る)。例の番号は変えていない。

## 6. 試験と確認

- host の試験 (`test/api_fixes/pin_ledger/`・`test/api_fixes/run.rb`): 5 機種を本物の `fmrb_pin_assign.h` で組み、
  機種ごとに「表の全体」「台帳のシステムのピンが全部表にある」「代表のピンが入っている」「ボタンと Grove・ヘッダの
  ピンが入っていない」を照合。C の側で、表の各ピンについて 読む = 通る・入力と出力 = NO_SYSTEM・台帳の値が変わらない・
  アプリから見ると SYS、表に無いピンはアプリから見た値が台帳と同じ、表で台帳が空きのピンを I2C で取れて SYS → I2C →
  SYS と見え、その間も GPIO は断る、範囲外と負の数は表に無い。`api_fixes: 145 checks passed` (前は 120)。
  判定の 3 行を外したファイルで組むと P4-Nano で 93 件落ちることも確かめた。
- `rake regress`: `host: 36 suites, 36 passed, 0 failed`、`regress: 310 runs (82 scenes on 5 profiles), 310 passed, 0 failed`。
- `rake sig:coverage`: 「3. doc gaps」は全部 0、基準との差なし。
- `rake clean` → `rake build:linux` (NARYA v3、320x240) → sim: gpio_viewer が開いて 49 本 (全部空き) を表示、標準構成の
  エディタを起動して 1 打鍵 (`a` が入る)。core のログに `Guru`・`abort`・`panic`・`stack overflow` は 0 件。sim_down した。
  sim のビルドで `const.c` と posix の pin manager がコンパイルされたことをログで確かめた。

## 7. メモリ・ファームの大きさ・ESP32 だけの所

- **内蔵 RAM の増分 0 バイト**。表は式の定数で、判定ではシフトと比較になる (静的な領域は増えない。ホストで組んだ
  オブジェクトの bss・data は前後で同じ)。素の malloc は使っていない。VM プールの増分も無い (Ruby の側は変えていない)。
- ファームの増分: ESP32 のビルドをしていないので測っていない。ホストの gcc -Os で pin manager のオブジェクトの text が
  P4-Nano 623 → 740 バイト、StickS3 757 → 883 バイト (+117・+126。関数 2 つと判定)。ESP32 でも同じ桁 (数百バイト以内) の
  見込みで、AtomS3R・StickS3 の空き (約 520 KB) には十分入る。
- **ESP32 だけでコンパイルされる直したファイル**:
  - `components/fmrb_hal/platform/esp32/fmrb_hal_pin_manager_esp32.c` (ホストの試験で 5 機種とも組んで動かした。
    sdkconfig との照合の `_Static_assert` は、`sdkconfig.defaults.naryav4`・`tab5` の値を `-D` で渡して通ることと、
    ずらした値で止まることをホストで確かめた)
  - `components/fmrb_common/include/fmrb_pin_assign.h` の TAB5・NARYAV4 の分岐 (同上)
  - `lib/gems/picoruby-fmrb-const/ports/esp32/const.c` は sim でもコンパイルされる (同じコード)。
- 親が P4-Nano 用のビルドで確かめてほしいこと: `_Static_assert` が通ること (本物の `sdkconfig.h` で)、Tab5 のビルドも
  同じく。

## 8. 親が P4-Nano で流す式

シェルの irb で 1 行ずつ。表のピンには `GPIO.new` の段階で断られ、ピンの設定は変わらない (SD・WiFi を止めない)。

| 式 | 期待 |
|---|---|
| `GPIO.new(39, GPIO::IN) rescue $!` | `#<IOError: GPIO 39 is used by the system>` |
| `GPIO.new(14, GPIO::OUT) rescue $!` | 同じ形 (14)。WiFi が切れない |
| `GPIO.set_dir_at(11, GPIO::OUT) rescue $!` | 同じ形 (11) |
| `GPIO.new(7, GPIO::IN) rescue $!` | 同じ形 (7)。画面・音が乱れない |
| `GPIO.new(53, GPIO::OUT) rescue $!` | 同じ形 (53) |
| `GPIO.read_at(39)` | 0 か 1 (読むだけは通る) |
| `g = GPIO.new(48, GPIO::IN)` | GPIO のオブジェクト |
| `FmrbHw.pin_status(48)` | 2 (PIN_USER_GPIO) |
| `FmrbHw.pin_status(39)` | 1 (PIN_SYSTEM_EXCLUSIVE) |
| `FmrbHw.pin_available?(14)` | false |
| `FmrbHw.pin_available?(20)` | true |
| `FmrbHw.pin_status_all.count(1)` | 33 |
| `Dir.entries("/mnt/sd").size` | 数が返る (SD が読める) |
| gpio_viewer を開く | 7〜19・28〜31・34・35・37〜44・49〜54 が灰色、48 が緑 |

- `regress:size`・`regress:run`・`regress:screens`。
- 3 章の分からなかったピン。
