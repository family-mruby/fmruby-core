## 2. 直さなかった項目と理由

### B3 GPIO (止まる条件: 動いているアプリが動かなくなる組み合わせがある)

同梱のアプリと見本 (`flash/app`・`flash/usr/share/samples`・`flash/lib`、`sdk/`・`main/ruby` も) で `GPIO.new` を使うのは 1 つだけ。

| アプリ | 呼び方 | 端末 | 台帳 | 直した後 |
|---|---|---|---|---|
| `flash/app/test/step_sensor.app.rb:297` | `GPIO.new(11, GPIO::IN)` (KEY1、押すと歩数を 0 に) | StickS3 | `FMRB_PIN_BUTTON_ENTER` = GPIO 11 (`fmrb_pin_assign.h:331`) が `register_system_pin` でシステムのピン (`fmrb_hal_pin_manager_esp32.c:68`) | 例外。アプリは rescue して `@key1 = nil` で続くので落ちないが、**KEY1 で歩数を 0 にする機能が無くなる** |

この使い方は設計どおりで、`doc/headless_s3/report/m3s.md:112` が「ピンはシステムのピンとして pin manager が持っているので
`GPIO_init` の reset は BUSY で断られるが、入力の設定と読みは通る (AtomS3R の G41 と同じ振る舞い)」と書いている。
起動時に KEY1 を押すと BLE の設定のモードに入る (システムもこのピンを読む)。ほかの端末で GPIO 11 は、P4-Nano は I2S の
DIN (172 行)、NARYA v3 は SPI の MOSI と UART の TX (390・397 行) で、step_sensor はそれらの端末では使わない。

調べた事実 (直すときに要る):

- 実装の場所: 上流の `picoruby-gpio` (`src/mruby/gpio.c`、`GPIO_init` は void) と Family mruby の port
  (`lib/upstream/picoruby-gpio-proxy/gpio.c`、`PICORUBY_SRCS` で管理)。台帳の取得は HW プロキシの
  `HW_PROXY_OP_GPIO_RESET` (`main/drivers/hw_proxy/hw_proxy_gpio.c:14`) が `fmrb_pin_manager_acquire(pin, FMRB_PIN_USER_GPIO, 呼んだタスク)`
  でしていて、失敗は `req->result` に返るが、port の `GPIO_init` が戻り値を捨てる。直すなら `lib/upstream/patch/picoruby-gpio/`
  に `include/gpio.h` と `src/mruby/gpio.c` を置き、`rakelib/setup.rake` で写す (picoruby-i2c の `I2C#close` と同じ形) のがよい。
- `GPIO::Error` は例外のクラスではない (`class Error` に親が無く、`peripheral_error` が IOError を出すだけの入れ物)。
  上流の gem の流儀ではピンの番号が悪いと ArgumentError ("Wrong GPIO pin name")、周辺機器の失敗は IOError。
- ピンを台帳へ返す道はある: アプリが終わるとき (`fmrb_app.c:1802`、Spinel は `fmrb_spx_app.c:192`) と kill
  (`force_release_resources`、`fmrb_app.c:2417`) で `hw_proxy_release_resources` → `fmrb_pin_manager_release_by_owner`。
  同じタスクが同じ使い方で 2 回取るのは OK を返す (`acquire` の owner と usage の一致)。2 回目の起動で「使用中」にはならない。
- `read` が失敗するのは HW プロキシが動いていないときだけ (`fmrb_hal_gpio_esp32.c:37`。プロキシの READ はいつも FMRB_OK)。

親とユーザが決めること (直し方の候補):

- (a) 台帳に「システムが持つが、アプリが入力として読んでよいピン」(ボタン) の区別を足し、`GPIO.new(pin, GPIO::IN)` だけ
  通す。それ以外のシステムのピンと、ボタンへの OUT は例外。step_sensor はそのまま動く。
- (b) 例外にするのは指示書どおりにし、step_sensor の KEY1 を別の口 (システムのボタンのイベント) で読むように変える。
- (c) システムのピンの `GPIO.new` は今のまま通し、ほかのアプリが使用中のピンと `read` の失敗だけ例外にする。

### 直した物の中で止まらなかった判断

- B2: 今の作りは「入れ物の色を写しただけ」と「部品に明示した色」を区別できなかった (`@bg_theme` が false になるのは
  どちらも同じ)。指示書の「区別できる形にする」に従い、部品の `@bg_theme` (boolean) を `@bg_from` (Integer 3 値) に置き換えた。
  ivar を 1 つ足す形 (`@bg_own`) も作ったが、TextField と Scrollbar が ivar 16 個で mruby の ivar 表 (2 倍ずつ伸びる) の
  境目にあり、1 つ足すと 1 部品あたり 320 バイト増える (5 章) ので、数が増えない形にした。

## 3. 動きが変わる所と同梱のアプリへの影響

- `IO#puts`・`File#puts`・Kernel の `puts` (ログ・シェルの画面・irb) が配列を 1 要素 1 行で書く (1 章の表)。
  irb の `$stdout.puts` が引数を 2 つ以上受ける。同梱のアプリで `puts` に配列を渡す物は、ログの行の形が変わる
  (grep で全部は拾えないので数えていない)。`File#puts` に配列を渡す同梱のアプリは見つけていない。
- `FmrbUI#bg=` が、既にある部品の写した色も変え、見えている部品を次の flush で描き直す。`Widget#bg=` で色を渡した部品は
  そのまま。使っている同梱のアプリはシェルの `color bg` だけ (`shell_commands.rb:251`) で、スクロールバーの溝が地の色に
  なる。シェルの `invalidate_all` は要らなくなったが残してある (害は無い)。
- `FmrbApp._get_last_error` は無くなり `FmrbApp.last_error` になる。呼び手はデスクトップ 2 か所・AI ヘルパー・回帰の代役で、
  全部切り替えた。カーネルの `FmrbKernel#_get_last_error` (FmrbApp ではない、カーネルの中の口) はそのまま。
- チェックポイントのイメージ: 直す前に書いたイメージの部品は `@bg_from` を持たないので、別の端末のテーマに合わせる
  動き (`follow_theme_ground`) をしない。開発中のイメージだけの話。

## 4. 上流に出せる直し

無い。B1・B2・B4 は Family mruby の gem・アプリの中。B3 を直すときの `picoruby-gpio` の差し込み (`GPIO_init` が結果を返す、
`read` の失敗で例外) は上流の関心にもなり得るが、作っていない。

## 5. メモリ

- B2: 部品の ivar の数は変わらない (host で数えた: Label 18・Button 19・Toggle 24・Stepper 24・Enum 25・TextField 16・
  Scrollbar 16、直す前と同じ)。ESP32 の mruby (MRB_NO_BOXING・MRB_INT64・32 ビット) の ivar の 1 枠は
  mrb_value 16 バイト + mrb_sym 4 バイトの見込みで、`@bg_own` を足していたら TextField・Scrollbar は 16 枠から 32 枠になり
  1 つあたり +320 バイトだった。Spinel の部品の構造体は `iv_bg_theme` (sp_bool) が `iv_bg_from` (sp_int) になり、
  1 部品あたり数バイト大きくなる (Spinel のエディタは部品を作っていないので、実際に増える物は無い見込み。測っていない)。
  定数 3 つ (`FmrbUI::BG_THEME` ほか) が増えた。
- B1: 常駐の増分なし。呼んでいる間も要素ごとの to_s の文字列だけで、1 つの大きな文字列に連結しない (host の試験で
  write が要素ごとに来ることを固定)。
- B4: なし (名前の付け替え)。
- 内蔵 RAM・VM プールの基準は測っていない (`rake regress:run`・`rake regress:size` は親が流す)。

## 6. 途中で見つけた別の不具合・確かめていないこと

見つけたもの (直していない):

- **GPIO: 台帳で断られた `GPIO.new` も、その後の `set_dir_at` でピンの向きを設定してしまう**
  (`GPIO_set_dir` → `fmrb_hal_gpio_config` は台帳を見ない)。SD の CS などシステムのピンを入力に変えられる。
  `GPIO.set_dir_at`・`write_at`・`read_at`・`high_at?` などのクラスメソッドも台帳を通らない。B3 を直すときに一緒に決めること。
- Spinel 側の `FmrbApp.last_error` は name を 64 バイト、error を 112 バイトで切る (`fmrb_spx_app.c` の `pack_name`)。mruby 側は
  切らない (1023 バイトまで)。前からの違い。
- irb で、配列を `puts` した直後の画面に空行が出て見えたことがあった (3 回)。その後同じ入力で出ず、全体の描き直しの後の
  履歴にも空行は無かった。出力の中身 (`["5", "\n"]`) は正しかったので、描画の途中の画面と見ている。原因は追っていない。

確かめていないこと:

- ESP32 のビルド (`app.c` の名前の変更)。AI ヘルパー (Modern 専用) を実際に動かしての「直して」の確認 (sim は Retro)。
- Modern の sim・ブラウザ版・ネイティブ版での動き。
- `rake regress:run` (VM プール) と `rake regress:size`。

## 7. B3 を実機で確かめる手順

直していないので、今の動きの確認と、直した後に見る物を書く。どちらもシェルの irb で打つ。

1. StickS3 (今の動き): `g = GPIO.new(11, GPIO::IN)` が例外なしで返り、`g.read` が 1、KEY1 を押したまま `g.read` が 0。
   ログに `pin_manager: Pin 11 already in use (usage=1)` の警告が出る。step_sensor を起動して KEY1 で歩数が 0 になる。
2. どの端末でも: gpio_viewer (`/app/tool/gpio_viewer.app.rb`) で台帳の色を見て、空いているピン (StickS3 なら Hat2 の G1 など)
   で `GPIO.new(n, GPIO::IN)` → gpio_viewer で GPIO (緑) になる → irb を閉じる (シェルを終える) と空きに戻る。
3. 直した後: 案に従って、システムのピンの `GPIO.new` が例外 (文にピンの番号と理由) になるか、ボタンの IN だけ通るか、
   step_sensor の KEY1 が動くかを 1 と同じ手で見る。**今のファームでは SD・USB などのシステムのピンに `GPIO.new` を
   打たない** (6 章の 1 つ目のとおり、向きが変わる)。
