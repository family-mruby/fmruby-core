## 2. 直さなかった項目と理由

- **A9 `GPIO#read` の -1 (B として止めた)**: `high?`・`low?`・`read` は上流の `picoruby-gpio/src/mruby/gpio.c`
  (submodule) にあり、`GPIO_read() == 0` で分けるので -1 は `high?` が true。HAL (`fmrb_hal_gpio.h:53`) は
  「0 か 1、失敗は -1」、上流の README は `read` が「0 か 1 を返す」と書くだけで、失敗のときにどうするか
  (例外・false・nil) を書いた所が無い。直し方の候補: (a) `GPIO_read` (lib/upstream/picoruby-gpio-proxy/gpio.c) で
  -1 のとき例外 (IOError など) を出す、(b) 上流の gpio.c を差し込みで直し `high?`・`low?` とも false にする、(c) 今のまま
  sig に書く。sim に GPIO は無いので、どれも確かめられるのはホストの試験 (C の単体) までになる。
- **A11 `Asterism::ROS::Subscription#handler=` (止まる条件)**: 元は `ruby-asterism/asterism` (`lib/upstream/ASTERISM_PIN`
  で取り込み、`vendor/asterism` は clone)。読みで確認: `Node#subscribe` だけが `@handled` に足し (ros.rb:469-475)、
  `Node#deliver` は `@handled` しか回さない (ros.rb:537-555)。`node.subscription` で作った物に `handler=` を付けても
  呼ばれない。なお accessor の注釈は「node.subscribe のブロック (node.subscription では nil)」とあり、仕様とも読める。
  再現の方法: `sub = node.subscription(topic, type); sub.handler = ->(m, a) { ... }` の後に相手から送り、`node.poll` で
  ブロックが呼ばれないことを見る。直し方の案: (a) `Subscription` が node を覚え、`handler=` で非 nil を入れたら
  node の `@handled` に足す (nil で外す)、(b) `deliver` が `@entities` のうち handler のある Subscription を回す。
  (a) の方が今の `@handled` の仕組みのままで済む。

## 3. 動きが変わる所

- `File.path(name)` が name を返す (前は nil)。
- `File.open(p, "a+")` が追記になり、無いファイルを作る (前は先頭から上書き、無いと RuntimeError)。`"rb+"`・`"ab+"`
  など `+` が 3 文字目の mode が読み書きになる (前は `rb+` は読むだけ、`ab+` は書くだけ)。
- `Kernel.send_message`・`receive_message`・`broadcast_message` の受け手に届く `size`・`data` が正しくなり、
  src_pid が入る。receive がスタックを壊さない。
- `JSON::Digger#dig` が範囲の外の位置 (空の Array を含む) で `JSON::DiggerError` を出す (前は別の要素か nil か
  ParserError)。`JSON.parse` の `\uXXXX` が UTF-8 の文字になる (前は 1 バイト)。
- `MIDI::Device#pitch_bend` が NoMethodError でなく送る。
- `SmfPlayer` の transpose を鳴らしている途中で変えると、鳴っている音は始めた高さで止まる。
- `MmlPlayer#load_text` が音のあるパートを読めたとき `error` が nil。
- gpio_viewer が P4 (55 本) で 5 行の表になる (Retro は前と同じ)。
- 同梱のアプリへの影響: mode は上の表のとおり変わらない。`Kernel.*_message`・`File.path`・`JSON::Digger`・
  `pitch_bend` を呼ぶ同梱のアプリは無い (grep)。`JSON.parse` は使う所があるが、`\u` の入った JSON を読む物だけ結果が
  変わる (正しくなる)。SmfPlayer の transpose を変えるのは MIDI のアプリで、止まらない音が残らなくなる方向。

## 5. 途中で見つけた別の不具合・確かめていないこと・止まった所

見つけたもの (直していない):

- `Kernel::MSG_TASK_HOST` が 0、`MSG_TASK_SYSTEM` が 1 だが、本体の番号は 0 が kernel、1 が host、2 が system app
  (`fmrb_task_config.h:418`)。名前と番号が合っていない。値を変えると利用者の動きが変わるので B。
- `Kernel.receive_message(自分の番号)` は、そのアプリに来た HID の伝言 (type 3) も取る (sim で `[3, "\x02\r(\x00\n"]`
  を受けた)。sig の長文が「`_spin` と同じ行列を取り合う」と書いているとおりで、不具合ではない。
- `"a"`・`"w"` など書くだけの mode で `read` が例外でなく "" を返す (CRuby は IOError)。
- Lua の `components/lua/fmrb_lua_hal_stdio.c:23` のコメントが「HAL に読み書き+追記が無いので `a+` は読めない」と書き、
  `a+` を書くだけで開いている。HAL は今回 `a+` を開けるようになったので、Lua 側も読めるようにできる (範囲の外)。
- 調べている途中、このセッションの道具が書いたファイルの `あ` を文字 (あ) に変えてしまうことがあった。
  一度「単一引用符の中の `\u` を compiler が解く」と疑ったが、ファイルのバイト列を見て道具の側だと分かった。
  compiler の不具合ではない。試験 (test/api_fixes/run.rb) は `\` を実行時に組み立てて、この影響を受けないようにした。

確かめていないこと:

- ESP32 のビルド (`fmrb_hal_file_esp32.c`・`kernel.c`・`fmrb_io.c` の変更を ESP32 でコンパイルしていない)。
  ESP32 の LittleFS・/tmp (RAM の VFS) で `"a+"` が追記になるか (tmpfs は `O_APPEND` を見る作りなのを読んだだけ)。
- gpio_viewer の P4 (55 本) の表示 (sim は Retro の 49 本だけ見た)。
- A7・A8 を sim で実際の曲で鳴らしての確認 (host の試験の note on/off の列と error だけ)。
- ブラウザ版・ネイティブ版での動き (作っていない)。

止まった所: A9 (B)、A11 (Asterism の元のリポジトリ)。

## 6. 確認の結果

- `rake regress`: host 36 suites 全部 pass (新しい `api_fixes:test` を含む)、描画の記録 310 runs pass。
- `rake sig:coverage`: 「3. doc gaps」は全部 0、基準との差なし (baseline.json の更新は不要だった)。
- `rake clean` → `rake build:linux` → sim: シェルの irb で `File.path('x')` → "x"、
  `Kernel.send_message(4, 42, 'hi'); Kernel.receive_message(4, 50)` → `[42, "hi"]`、エディタを起動して 1 打鍵 (表示された)。
  core のログに crash の印 (Guru・abort・panic) は 0 件。sim は止めた。
- 直す前後の sim の出力 (mode の表・JSON・Kernel) は scratchpad に置いた (リポジトリには入れていない)。
- host の試験は、直す前のファイル (file.rb・json.rb・fmrb-smf.rb・fmrb-mml.rb、picoruby-midi の pitch_bend) で流して落ちることも確かめた。
