# 指示書: エディタの長文ヘルプ (F1) を書き足す

> 状態: 進行中 | 更新: 2026-09-01 | **方針変更: 全メソッドに置く**
> (下記)。書くのは文章で、コードは (原則) 触らない

## 頼みたいこと

エディタで **Tab で補完 → F1 で開く長文ヘルプ**が、いま **30 個しかない**。
これを増やす。**FmrbGfx から**。

書く場所は **`sig/*.rbs` の doc コメントの 2 行目以降**。ビルド時に
`rake ti:help` が `flash/help/<クラス名>/<メソッド名>.md` へ書き出す。

## いまの状況 (数えた結果、2026-09-01)

**1 行要約はほぼ埋まっている**。触る必要は無い。

| ファイル | メソッド | 要約あり |
|---|---|---|
| fmrb_app.rbs | 73 | 73 |
| fmrb_midi.rbs | 57 | 57 |
| fmrb_ui.rbs | 54 | 54 |
| fmrb_gfx.rbs | 52 | 52 |
| string.rbs | 53 | 53 |

**足りないのは長文の方**。`flash/help` にあるのは 30 ファイルだけで、
内訳は FmrbUI 19 / FmrbGfx 5 / FmrbApp 2 / FmrbUI__Stepper 2 /
FmrbAudio 1 / SpriteInstance 1。**FmrbUI だけが厚く、他は薄い**。

## 大きさに気を付ける

全部書くと help は **71 → 573 ファイル**になる。いまの平均が 1.1KB
(散文つき) なので、**例だけのページを 300 バイト前後に収める**こと。
散文つきのものが増えるほど膨らむ。

置き場所は端末の storage 区画と、ブラウザ版の bundle (いま 6.4MB)。
**クラスを 1 つ書き終えるごとに `du -sh flash/help` を見る**。
1MB を超えたら、そこで一度報告して判断を仰ぐ。

ファームウェア本体の文字列プールは太らない (help はファイル) ので、
そこは気にしなくてよい。

## 順番

1. **FmrbGfx** (52 メソッド中 5 つだけ)。最優先。
2. **FmrbApp** (73 中 2 つ)。ライフサイクル (`on_create` / `on_update` /
   `on_event`) と窓まわり。
3. **FmrbAudio** / **FmrbSprite** / **FmrbTile**。
4. 組み込み (String / Array / Hash) は**後回し**。要約で足りることが多い。

## 何を書くか — 全メソッド、ただし二層で

**方針変更 (2026-09-01、ユーザ判断)**。当初は「つまずくところだけ」だったが、
**全メソッドに置く**。理由は説明ではなく**例**にある:

> 引数の型がシグネチャからは読み取りにくい。素直なメソッドでも、
> ヘルプ画面に**呼び方が 1 行**あるほうが速い。

だから二層に分ける。**この区別が守れないと 573 個ぶんの水増しになる。**

**素直なメソッド = 例だけ。散文を書かない。**

```
# 四角のわくを描く <<en>> draw a rectangle outline
#
# ```ruby
# gfx.draw_rect(10, 20, 60, 40,
#               FmrbGfx::WHITE)
# ```
```

**「引数 x は x 座標です」は書かない。** 何も足さずに読む時間だけ奪う。
書くことが無いなら例 1 行で終える。**それでよい。**

**つまずくメソッド = 散文 + 例。** 実装を読まないと分からない振る舞い

FmrbGfx で実際につまずくのは、たとえばこういうところ (書く前に実装を読んで
確かめること):

- **描いたものが出ない** — `present` を呼ぶまで画面に出ない。
  ([[feedback-sprite-needs-present]] の話は sprite だけでなく描画全般)
- **座標の意味** — 窓の中の座標なのか画面全体なのか。
  `@user_area_x0` との関係。
- **前の絵の消し方** — `clear_user_area` と `fill_rect` の使い分け。
- **色** — RGB332 の 1 バイト。`FmrbGfx::WHITE` などの定数と、
  テーマ色 (`FmrbConst::THEME_*`) のどちらを使うべきか。
  **0x01 は使わない** ([[feedback-theme-color-key-0x01]])。
- **重い呼び出し** — ブロック呼び出しは 1 回 0.4ms
  ([[feedback-picoruby-times-vs-while]])。描画ループで効く。

**API の説明を機械的に埋めない**。「引数 x は x 座標です」だけの長文は
価値が無く、読む人の時間を奪う。**書くことが無いメソッドには書かない。**

## 書き方の規約 (sig/README.md が正、要点だけ)

- **1 行目 (要約) は触らない**。**両言語あわせて 112 バイト**の制限があり、
  超えると黙って切れる。増やすのは 2 行目以降。
- **2 行目以降に上限は無い**。db には入らないので、ファームウェアの
  文字列プールは太らない。
- **二か国語は `<<en>>` だけの行**で日本語側と英語側を区切る。
  長文はこの形。要約のインライン形式 (`日本語 <<en>> English`) とは別。
- ` ```ruby ` のコードブロックが書ける。**短い例は効く**。
- **例のコードは 39 桁以内**。ヘルプ画面がその幅で、散文と違って
  **コードは語の途中で割れる**。
- **markdown は表示される** (2026-09-01 から。`**強調**` `` `code` ``
  ` ``` ` `#` は記号が消えて色が付く)。記号のぶんの空きは残るので、
  強調は語の切れ目に置く。
- **実在するものだけ**書く。実装 (mrblib の Ruby と C バインディング) を
  読んで書き、推測で書かない。
- **文体**: 大人が読んで普通の説明。子供向けの言い回し
  (「〜してみよう」等) は使わない。用語は実装に合わせる。
  会話は丁寧語、doc は常体 ([[feedback-plain-japanese-terms]])。

## 確かめ方

```bash
rake ti:help                      # flash/help を作り直す
ls flash/help/FmrbGfx | wc -l     # 増えたか
```

**実際に開いて見る**のが本番。ブラウザ版が速い:

```bash
source ~/emsdk/emsdk_env.sh
rake wasm:dist
```

そのあと `web_up` → エディタを開く → 例えば

```ruby
ui = FmrbUI.new
ui.
```

と書いて **Tab** で補完、**F1** で長文ヘルプ。FmrbGfx を確かめるときは、
型推論が受け手の型を決められる書き方にすること。**`@gfx` は効かない**
(picoruby-ti は ivar を追わない)。

- 実機で確かめるなら **`rake clean` を挟んでからビルド**。挟まないと
  古い型 db がリンクされ続け、画面が変わらない理由が分からなくなる。
- ブラウザ版は毎回作り直すので、この罠は無い。

## やらないこと

- 1 行要約の書き換え (112 バイトの箱を割る事故のもと)。
- `sig/*.rbs` のシグネチャ自体の変更。型が間違っていると気付いたら、
  **直さずに report に書いて残す**。
- エディタ側のコード変更。

## 終わったら

- `doc/editor_ti/report/help_<範囲>.md` に、**何を書いたか**ではなく
  **書きながら分かったこと** (実装と食い違っていた点、書けなかったもの、
  つまずきの見つけ方) を残す。
- `rake docs:index`。
