## サイズ実測 (S3 / NARYAv3、標準エンジン構成)

**今のバイナリの増分はほぼ 0**。誰もエンジンを呼んでいないので、リンカが
オブジェクトを丸ごと捨てる。elf に残るのは空の gem_init / gem_final
(10 バイト x 2) だけで、`ti_` で始まる関数は 1 つも入っていない。

- ビルド後の bin: `0x361a00` = 3,545,088 バイト、パーティション
  `0x400000` に対し **15% (0x9e600) 空き**。
- 実際に呼び始めたときに増える量は、S3 用に生成されたオブジェクトから測った:

| 内訳 | text | bss |
| --- | --- | --- |
| エンジン本体 (22 ファイル) | 12,121 | 16,424 (静的作業領域 16KB) |
| 型データベース (sig/ 17 ファイルから生成) | 36,846 | 0 |
| 合計 | 48,967 | 16,424 |

読み取り: **flash 側 49KB は S3 でも問題にならない** (残 648KB)。効いてくるのは
内蔵 RAM の 16KB 静的領域のほうで、これは計画どおり P5 の PSRAM 化案件。
型データベースが本体の 3 倍あるので、**sig/ を増やすと flash が増える**
(P4 で RBS を充実させるときの見積り根拠: 現在 17 ファイルで 37KB)。

## sig/ に置いたファイル

- 基本型 15 個 (`array` `class` `false_class` `float` `hash` `integer`
  `kernel` `nil_class` `object` `proc` `range` `string` `symbol`
  `true_class` `untyped`): エンジンの example/rbs をそのまま (MIT)。
  **上流のテストが文字列一致で見るので書き換え禁止**。
- `enumerable.rbs` / `gpio.rbs`: 上流の host_test が前提にしている最小定義。
- `fmrb.rbs` (新規): `FmrbApp` と `FmrbGfx`。
  lib/add/picoruby-fmrb-app の mrblib と gfx の C 拡張を読んで、
  **実在するメソッドだけ**を書いた。

### P4 に回した未定義 API

- Sprite / Sound (APU) / MIDI / Tilemap / FmrbI18n / p5 互換層 は未着手。
- `FmrbGfx` のうち、キーワード引数が本質のもの (`draw_image` の x/y/scale、
  `create_canvas_gfx`、`load_image`、`set_composite_regions`、`set_viewport`)
  は必須引数だけの形で置いた。エンジンが省略可能引数もキーワード引数も
  持たないため、正確には書けない。
- 定数 (`FmrbGfx::BLACK` など) は RBS に書いても取り込まれない
  (生成側が定数宣言を読まない)。補完に出したいなら上流への機能追加が要る。

## 詰まった点・判断した点

### 1. elf に ti シンボルは出ない (受け入れ条件 1 の前提が違った)

呼び出し側が P2 まで存在しないので、静的ライブラリのメンバーはリンク時に
1 つも引き込まれない。エンジンを CMake 側で直接コンパイルしても同じで
(コンポーネントも静的ライブラリになる)、結果は変わらなかった。

代わりに次で確認した:

- `nm components/picoruby-esp32/picoruby/build/family-mruby-linux/lib/libmruby.a
  | grep " T ti_"` -> 61 個。
- elf に `mrb_picoruby_ti_gem_init` が入っている = gem として本当に
  ビルドに参加している。

P2 で呼び出し側が入った時点で、この条件は自然に満たされる。

### 2. CMakeLists への src 追加はしない (指示書 T3-4 から変更)

指示は `src/**/*.c` を PICORUBY_SRCS に足す形だったが、picoruby-ti は
自前の mrbgem.rake を持つ**普通の mrbgem** なので、rake の mruby ビルドが
既に全ソースをコンパイルしている。両方に書くと 22 ファイルが二重に
コンパイルされ、同じシンボルが 2 つの静的ライブラリに入る (実測: 61 個 x 2)。
バイナリは変わらないが無駄なので、**公開ヘッダの include だけ**を
コンポーネントに足した。editor-core も同じ形 (src は mruby ビルド、
ESP-IDF のヘッダが要る ports/ だけ CMake) なので、既存の作法にも合う。

P2 で C の橋渡しを書く場所は、この判断の影響を受ける:

- gem の中 (editor-core など) から呼ぶなら何もしなくてよい。
- main/ 側 (Spinel の FFI 実装) から呼ぶ場合も、libmruby は同じリンク行に
  いるので解決する。

### 3. 型データベースの生成に rbs gem が要る (計画の記述と違った)

plan.md には「tidbgen は純 Ruby、rbs gem 不要」と書いたが、実際は
`tidbgen/signature_parser.rb` が `require "rbs"` する。つまり
**ホストの ruby に rbs gem が入っていることがビルドの前提**になる
(このマシンは 3.6.1 が入っていた)。`rake setup` の中で毎回動くので、
入っていないと LoadError で止まる。分かりやすいように、生成の直前に
存在確認して `gem install rbs` を案内する形にした。

将来 CI に載せるなら、ここが新しい依存として効く。

### 4. インスタンス変数の型は RBS で宣言できない

エンジンの生成側は RBS のメソッド定義・include・alias しか読まず、
`@gfx: FmrbGfx` のようなインスタンス変数宣言を無視する。ところが
`FmrbApp` は `gfx` を公開しておらず (attr_reader に無い)、アプリは
`@gfx` を直接触る。`@gfx` は `FmrbApp#initialize` の中で代入されるが、
その定義はユーザのソースに無いので、エンジンからは型が見えない。

**P2 の最初の判断事項**になる。案は 3 つ:

1. `FmrbApp` に `attr_reader :gfx` を足す (本体を 1 行変える。Spinel 側の
   基底にも同じものが要る)。
2. エディタが補完のときだけ、`@gfx = FmrbGfx.new` 相当の短い前置きソースを
   先読み側に足す (本体を変えない。エンジンは複数ソースを受けられる)。
3. 上流にインスタンス変数宣言の対応を提案する。

2 が一番安く、1 が一番素直。plan.md の「アプリ基底を RBS に寄せるか
Ruby 先読みにするか」は、この形で P2 に持ち越す。

### 5. ホスト回帰の prism をどこから持ってくるか

host_test は `../lib/prism` を前提にしているが、その submodule は
展開しない方針なので、`components/.../mruby-compiler/lib/prism` を
`vendor/ti_prism` に複製して `make static` し、`PRISM_ROOT` で差し替えた。
submodule を直接 make しないのは汚さないため。2 回目以降は
`vendor/ti_prism/build/libprism.a` があれば作り直さない
(`rake ti:clean` で消せる)。

生成した型データベースは、テスト時だけは engine checkout の
`src/generated` に置く (host_test の Makefile がそこを見るため)。この
ディレクトリは picoruby-ti 側の gitignore に入っているので、
vendor の checkout は clean のままになる。

## 動作確認に使ったコマンド

```
rake ti:setup            # 素の状態から clone (0b95b8a)
rake ti:test             # 3 本 green
rake clean && rake build:linux                        # 標準 (Spinel)
FMRB_KERNEL_ENGINE=mruby FMRB_APP_ENGINE_EDITOR=mruby \
  FMRB_APP_ENGINE_DESKTOP=mruby rake build:linux       # 全 mruby
FMRB_HW_TARGET=NARYAv3 rake clean_all && FMRB_HW_TARGET=NARYAv3 rake build:esp32
tools/dev_run_check.sh                                 # sim 起動 + 画面
```

## P2 への申し送り

- `@gfx` の型 (上記 4) を先に決める。決めないと補完の目玉が出ない。
- 補完の起動キーは Ctrl+Space が使えない (かな入力)。Tab か Ctrl+N。
- 全ソース再解析なので、エディタの本気モードで測った打鍵 -> present の
  時間 (2ms) とは桁が違うはず。P2 で実測してから、要求時のみ実行を
  続けるか決める。
- 生成物のサイズは型データベースが支配的 (37KB / 49KB)。P4 で RBS を
  増やすときは、Retro に載せる分と Modern だけの分を分けることも検討する。
