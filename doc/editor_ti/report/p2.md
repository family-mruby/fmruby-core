## prism のアロケータ: 今のままエディタから呼ぶと落ちる

### 経路

- prism は `PRISM_XALLOCATOR` 付きでビルドされ、
  `xmalloc(size)` = `mrb_malloc(global_mrb, size)`
  (mruby-compiler/include/prism_xallocator.h)。
- `global_mrb` は**グローバル変数 1 個**で、`mrc_ccontext_new(mrb)` が呼ばれる
  たびに最後にコンパイルした VM で上書きされる (mruby-compiler/src/ccontext.c)。
- `mrb_malloc` -> `mrb_realloc` -> `mrb_realloc_simple`。実バイトは
  `mrb_basic_alloc_func` に落ち、これは family-mruby のパッチで
  **呼び出しタスク自身の est ヒープ** (`fmrb_get_current_est` の TLS、
  lib/patch/picoruby-mruby/src/alloc.c) を使う。**ここは安全側**で、
  他 VM のヒープは壊さない。確保と解放が同じタスクで完結する限り整合する
  (ti は 1 回の呼び出しの中で pm_parser_init から pm_parser_free まで済ませる)。

### 危ないのは mrb_state 側

`mrb_realloc_simple` / `mrb_realloc` は `global_mrb` の中身を触る:

1. `global_mrb == NULL` (mruby アプリを一度もコンパイルしていない状態。
   Spinel カーネル + Spinel エディタ構成の起動直後がまさにこれ) の場合、
   確保成功後の `mrb->gc.malloc_increase += len` で **NULL 参照。最初の
   確保で即死する**。
2. 非 NULL でも、それは**他タスクの VM**である。そこへエディタタスクから
   gc の統計を書き込み、閾値を超えると
   **`mrb_incremental_gc()` / `mrb_full_gc()` を他タスクの VM に対して走らせる**。
3. 確保に失敗すると `mrb_raise_nomemory(global_mrb)` =
   **他タスクの jmpbuf へ longjmp**。
4. その VM が既に終了していれば `global_mrb` は**ぶら下がりポインタ**。

全 mruby 構成でも安全ではない (エディタの VM が global_mrb だとは限らない)。
ついでに分かったこととして、**2 つの VM が同時にコンパイルすると
global_mrb が入れ替わる**素地が現状もある (P2 とは独立の潜在的な問題)。

### 対策案 (どれかを選んでから T2 の実装に入る)

- **A**: `prism_xallocator.h` を lib/patch で差し替え、xmalloc を
  `mrb_basic_alloc_func` (呼び出しタスクの est) に直結する。単純だが
  **アプリのコンパイル経路も同時に変わる**ので、prism 側が確保失敗を
  自前で扱えるか (raise が無くなる) の確認が要る。
- **B (推奨)**: `global_mrb` をタスクごとの値にし (fmrb のタスク文脈に置く)、
  VM を持たないタスクでは est 直結にフォールバックする。エディタが直り、
  上記の同時コンパイル問題も一緒に消える。
- **C**: ti 呼び出しの間だけ global_mrb を差し替える。**Spinel エディタには
  VM が無いので解決にならない**。

## 1 回の補完要求の実測 (ホスト x86-64、`rake ti:probe`)

エンジンは 1 回の要求で**同じソースを 3 回パースする** (評価 2 周 + 補完 1)。
時間はその 3 回分、メモリの山は 1 本分。

| ソース | prism の山 | 1 要求 | 候補 |
| --- | --- | --- | --- |
| 2.2KB | 41KB | 0.14ms | 2 |
| 4.2KB | 78KB | 0.35ms | 2 |
| 8.3KB | 155KB | 0.96ms | 2 |
| 16KB | 304KB | 2.9ms | 2 |
| 33KB | 608KB | 9.7ms | 2 |
| 66KB | 1.2MB | 36ms | 2 |
| 105KB | 1.9MB | 86ms | 2 |
| 134KB | 2.5MB | 58ms | **0 (arena 16KB 溢れ)** |

読み取り:

- **AST はソースの約 18 倍** (64bit ホスト)。実機は 32bit なので概ね半分、
  9-10 倍と見込む。
- **エディタ (Spinel) のタスクが使うのは USER_APP プールの 500KB**
  (fmrb_app_spawner.c の `default/editor` は APP_TYPE_USER_APP)。prism を
  そこから取ると、8KB のソースで既に実機 ~75KB を UI のヒープと奪い合う。
  もともと「200KB の文書を編集中に、プールの 1/4 ずつを GC 閾値にしたら
  メモリが尽きた」と記録があるプールなので、**取り先の選び直し
  (EDITOR_DOC の 1MB へ寄せる等) と、補完を諦めるサイズ上限が要る**。
- 溢れの限界はバイト数ではなく**定義の個数**で決まる (arena 16KB)。合成した
  ソース (クラスとメソッドだらけ) では 134KB で候補 0 になった。実際の
  アプリはもっと持つはず。**溢れても UI は壊れない** (エンジンが結果を
  0 件にして返す) ことは確認済み。
- 400 回繰り返しても増え続けない (残差は繰り返し回数に対して対数的にしか
  増えない = アロケータの箱の成長であって漏れではない)。

計測に使った C は `tool/ti/ti_probe.c`、実行は `rake ti:probe`
(`REPS=5 SIZES="4 16 40"` で回数とサイズを変えられる)。

### T2-0: prism アロケータの B 案

`lib/patch/compiler/` に 2 ファイル追加 (`rake setup` がコピーする):

- `prism_xallocator.h`: `xmalloc` 等を `fmrb_prism_realloc` /
  `fmrb_prism_calloc` に差し替え。
- `mruby-compiler2-ccontext.c`: そのフックの実装。呼ぶ先を 1 回ごとに選ぶ。
  1. **呼び出し側が差し込んだ確保関数** (エディタのブリッジが使う)
  2. 無ければ**そのタスク自身の VM** (`fmrb_current_compile_mrb()`)。
     アプリのコンパイル経路はここを通り、**NoMemoryError を上げる挙動も
     GC への圧力の伝わり方も従来どおり**。
  3. VM の無いタスクは est 直結 (失敗は NULL)。

**差し込んだ確保関数はタスクごとに持つ** (`__thread`)。ここを平のグローバル
で書いていたのがレビューで指摘された欠陥で、補完 1 回 (最長 34ms) のあいだに
別のタスクがアプリをコンパイルすると、そのコンパイルの確保がエディタの
使い捨てヒープに迷い込み、補完が終わった瞬間に解放される = コンパイル中の
アプリから見て use-after-free になる。ブリッジのロックは補完どうしを
直列化するだけで、コンパイル経路はそのロックを通らない。差し込む側と
それを使う prism は必ず同じタスクなので、TLS が正しい意味論になる。

`fmrb_current_compile_mrb()` は `main/app/fmrb_app.c` に置いた。タスク文脈の
`vm_type` を見て mruby VM でなければ NULL を返すだけ。**新しいフィールドは
足していない** (VM ポインタは既に文脈にある)。`global_mrb` 自体は
picoruby の front-end と picoruby.h のマクロが代入するので残してある。

**prism は xmalloc の NULL に耐えない**。`pm_node_alloc` は確保に失敗すると
`fprintf` して `abort()` する (他の経路 — バッファ、ノード配列 — は false を
返して素直に諦める)。VM 経由なら raise で抜けるので届かないが、est 直結では
届く。そこでブリッジ側は「予測して断る」のではなく「失敗しても安全に
抜ける」形にした (次項)。

### T2: ブリッジ (`ports/esp32/editor_ti_bridge.c`)

`et_suggest(slot, y, x)` が (1) 文書を 1 本のバッファへ直列化 (2) (y,x) を
バイト位置へ変換 (3) エンジン呼び出し (4) 結果を自前領域へコピー。
`et_suggestion(i, field, &len)` で label / detail / doc を読む。
名前が重複する候補は落とす (オーバーライドすると自前と継承で 2 件出るため)。
`static` な mutex で 1 要求ずつに直列化する。

メモリの扱いが設計の中心:

- 要求のあいだだけ **EDITOR_DOC プール (1MB) から作業ブロックを借り**、
  その上に `fmrb_mem_create_handle` で使い捨てのヒープを作って prism を
  そこへ向ける。エディタアプリ自身の 500KB ヒープには触れない。
- 借りたブロックが尽きたら、確保関数は NULL を返さず **`longjmp` で
  et_suggest まで戻る**。prism が abort する前に抜け、ブロックごと解放するので
  漏れも残らない。**大きすぎる文書の代償は「候補 0」であって落ちることではない**。
- 文書が 32KB を超えたらエンジンを呼ばずに `ET_ERR_TOO_LARGE` を返す。

ファイルの置き場所は指示書の `src/` ではなく `ports/esp32/`。fmrb のメモリと
エンジンのヘッダが要るので、editor_core.c と同じ側に置くのが既存の作法。

### T3: バインディング

`EditorCore.suggest` / `.suggestion` / `.max_source_bytes` を mruby 側
(`editor_core_mrb.c`) と Spinel 側 (`fmrb_spx_editor.c` +
`fmrb_editor_ffi.rb`) の両方に。**これで初めてエンジンが image に入った**
(P1 の積み残し。`nm build/fmruby-core.elf | grep " T ti_"` が 59、S3 は 60)。

### T4: エディタ UI

- Tab の直前が名前か `.` `?` `!` なら補完、それ以外は従来どおりインデント。
  判定は scancode (0x2B)。
- ドロップダウンはカーソル直下 (下端に入らなければ上)。最大 8 件、上下で
  スクロール。上下で選択、Enter/Tab で確定、Esc で閉じる。**それ以外のキーは
  閉じてから通常処理へ流す**ので、打鍵が詰まらない。
- 確定時はカーソル直前の名前を候補で置換 (`.` 直後は素の挿入)。
- 選択中の候補の doc コメント (無ければシグネチャ) をステータス行に出す。
- 候補 0 / 大きすぎは、ポップアップを開かずステータス行に一言 (i18n 済み)。
- 要求ごとに `ti_lat: N ms (M candidates, K bytes)` を出す。**info で出す**:
  debug はビルドから落ちていて sim にも実機にも出ないため (edit_lat と同じ)。
- カーソルの画面位置は `cursor_cell_box` に切り出し、カーソル描画と
  ポップアップの位置決めが同じ経路を使うようにした (折返しや全画面でずれない)。

ti_lat の実測 (Linux sim):

| --- | --- |
| 43 バイト | 0 ms |

20KB で 34ms なら、上限の 32KB でもホスト実測 (24ms x 数割増し) の範囲。
**実機の数字は P5 で測る** (S3 は数倍遅い見込みなので、上限の見直しはそこで)。

回帰 (受け入れ条件 5): 標準構成でランチャーから Ruby アプリを起動して
`Ruby script compiled successfully` を確認。全 mruby 構成では shell と
ゲーム (Dodge) の起動まで確認した。

scratch を `__thread` にした後の取り直し (両構成): **補完を 1 回動かした
あとに Ruby アプリを起動**して、実行時コンパイルが通ることを確認した
(標準構成 = ti_lat のあと `Ruby script compiled successfully`、全 mruby 構成も
同じ順で確認)。補完そのものも両構成で従来どおり出る。

longjmp からの復帰経路も目で追い直した:

- `fmrb_prism_set_scratch_allocator(NULL)` は setjmp の両側の後ろに 1 回だけ
  あるので、正常終了でも longjmp 復帰でも必ず解除される。
- `done:` ラベルで使い捨てヒープの破棄・ブロックの解放・直列化バッファの
  解放・ロック解放をまとめて行う。longjmp 復帰はこのラベルを必ず通る。
- setjmp と longjmp のあいだで書き換わる自動変数を復帰後に読んでいないこと
  (`want` や `src` は setjmp より前で確定、`result` は復帰後に代入) も確認した。
- ついでに、確保ブロックの半減ループが下限を割って成功してしまう経路を
  塞いだ (半減後も下限以上のときだけ試す)。

### S3 (NARYAv3) のサイズ

| | P1 (誰も呼ばない) | P2 (リンクされた) | 差 |
| --- | --- | --- | --- |
| bin | 0x361a00 (3,545,088) | 0x370d70 (3,608,432) | **+63,344** |
| パーティション空き | 15% | 14% | |
| .bss (内蔵 RAM) | 34,088 | 50,680 | **+16,592** |
| DIRAM 空き | 191,513 | 174,921 | -16,592 |

P1 の見積り (flash +49KB / bss +16.4KB) と比べて **bss はほぼ予想どおり**
(エンジンの静的 arena 16KB)、flash は 14KB 多い (ブリッジと、生成 db が
丸ごと引き込まれた分)。**内蔵 RAM 16.6KB は arena そのもの**なので、
P5 の PSRAM 化 (EXT_RAM_BSS) がそのまま効く。ここでは対処しない。

## 残した制限と次への申し送り

- **`@gfx.` は補完されるが `gfx.` は出ない**。FmrbApp が gfx を公開して
  いないため。テンプレートや doc を `@gfx` 表記に寄せるかは P4 の判断。
- 補完中はステータス行が候補の説明で占められるので、**かなモードのバッジが
  隠れる**。実害は小さいが、P3 でホバーを足すときに置き場所ごと考え直す。
- 絞り込み入力は無し (v1 の方針どおり)。開き直しは 20KB でも 34ms なので、
  実機の数字を見てから必要性を判断する。
- 文書サイズの上限 32KB は定数 1 か所
  (`editor_ti_bridge.c` の `ET_MAX_SOURCE_BYTES`)。
- ついでに分かった既存の限界: **短い行ばかりの 200KB ファイルは
  EDITOR_DOC (1MB) に入らない** (1 行あたりの最小確保が効く)。行が長めなら
  204KB でも 322KB しか使わない。補完とは無関係だが、エディタの上限の
  実像として記録しておく。
- hover.c は外側クラスを context に設定しないので、`@gfx` のホバーは
  P3 で suggest と同じ解決を入れる必要がある (指示書の指摘どおり)。
