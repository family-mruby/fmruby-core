| 条件 | 結果 |

| 2. S3・P4 とも esp32 ビルド通過 + arena が PSRAM へ移った数字 | 両方 **ちょうど 16,384 バイト**内蔵 RAM が減った |

## T1/T2: arena を PSRAM へ

fork 側は「host がセクション属性を差し込めるフック」だけを足した
(`TI_ARENA_INCLUDE` / `TI_ARENA_ATTR`、既定は素の static)。

core 側は esp32 の build config だけで `TI_ARENA_INCLUDE="ti_arena_esp32.h"`
を定義し、そのヘッダが `.ext_ram.bss` セクションを指定する。**IDF の
esp_attr.h は使っていない**: この gem を焼くのは rake 側の mruby ビルドで、
IDF の include ツリーも生成された sdkconfig.h も見えないため。IDF の
リンカ断片は `.ext_ram.bss+` を拾うので、素のセクション名でも同じ場所に載る
(`CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY` は 3 ターゲットとも既に y)。

内蔵 RAM の実測 (.bss、定義前 → 定義後):

| ターゲット | .bss | DIRAM 合計 | 空き |
| --- | --- | --- | --- |
| NARYAv3 (S3) | 51,344 → **34,960** | 167,583 → 151,199 | 174,177 → **190,561** |
| TAB5 (P4) | 104,232 → **87,848** | 222,880 → 206,496 | 353,584 → **369,968** |

どちらも差はちょうど 16,384 バイト。`nm` でも `arena_bytes` が
内蔵 (0x3fcab874 / 0x4ff44274) から外部 (0x3c9db5c4 / 0x4866ea44) へ移った。
flash は不変。linux ビルドは従来どおり。

## T3 の途中で見つけた欠陥: エディタタスクのスタック不足

**焼いた直後の Tab5 で、signature help を出そうとした瞬間に落ちた**。

```
Guru Meditation Error: Core 1 panic'ed (Stack protection fault).
Detected in task "FM-Editor"
```

直前のタスク表:

```
FM-Editor   Y  1  12288  2888  IRAM  PIN1
```

エディタは shell と同じ 12KB のスタックで動いており、**平常時で残り 2.9KB**
しかなかった。型支援はその同じタスクで prism を走らせる — パーサも
エンジンの木の走査も再帰なので、そこへ入った時点で足りない。
**sim では出ない** (Linux のタスクは桁違いに広い)。

対処: エディタ専用のスタック定数を作って **24KB** にした
(`FMRB_EDITOR_APP_TASK_STACK_SIZE`)。shell や他の内蔵アプリは 12KB のまま。
**この 12KB は arena を PSRAM へ逃がして空いた 16KB から出ている**ので、
内蔵 RAM は P5 前より減っていない。

修正後の実測 (21KB のファイルを開いて補完まで叩いた後の最悪値):

```
FM-Editor   Y  1  24576  9564  IRAM  PIN1
```

ピーク使用は 15,012 バイト。**12KB では 2.8KB 足りなかった**ことになる。
残り 9.5KB。

補足: この不足は P4.5 で入った signature help に固有ではない。P2 の補完も
同じ経路を通るので、**実機では以前から紙一重だった** (P2 の実機確認が
通っていたのは、当時の文書が 8 バイトで解析が浅かったため)。

## T3: Tab5 実機の動作確認 (標準構成 = Spinel エディタ)

| # | 内容 | 結果 |
| --- | --- | --- |
| 1 | `@gfx.dr` + Tab | draw_* の一覧 + 日本語 doc |
| 2 | メソッド上で Ctrl+T | `draw_text: (Integer x, Integer ...` |
| 3 | 誤引数 + Ctrl+E | 行が赤く + `1 problem: type mismatch...` + `[!1]` |
| 4 | `FmrbGfx::B` + Tab | BLACK / BLUE / BLEND_ADD / BLEND_XOR + doc「黒 (RGB332)」 |
| 5 | `@gfx.draw_text(10,` | `draw_text(x, >>y: Integer<<, str, ...`、`sig_lat: 4 ms` |
| 6 | 補完候補で F1 | `[Help] draw_text.md` が開く (flash/help が storage に載っている) |
| 8 | ログの静けさ | 使い捨てヒープのログは**ブート時の 3 行だけ**。要求ごとには出ない |

セッション全体で `Guru` 0 件。

### 実機レイテンシ (T3-7)

| 文書 | 実機 (P4) | 参考: sim (64bit ホスト) |
| --- | --- | --- |
| 85 バイト | 5 ms | 0 ms |
| 4.1KB | **79 ms** | — |
| 21.9KB | **417 ms** | 34 ms (20.5KB) |

**実機は sim の 10 倍以上遅い**。数 KB までは体感一拍以内だが、
**20KB の文書では Tab を押してから 0.4 秒画面が止まる**。

→ **申し送り (判断が要る)**: ブリッジの受付上限は今 32KB
(`ET_MAX_SOURCE_BYTES`)。実機の数字からすると、**8KB 前後まで下げるか、
上限は残したまま「大きい文書では時間がかかる」と割り切るか**を決めたい。
P5 の指示範囲外なので変更していない。

## T4: S3 は未実施 (実機が繋がっていない)

**S3 (NARYAv3) の実機検証はできていない**。接続されているのは Tab5
(`/dev/ttyACM0`) だけで、S3 のボードが無いため焼けなかった。

済んでいるのは:

- **ビルド通過** (0x37f160 = 3,633,504 バイト、パーティション残 13%)
- **内蔵 RAM の実測** (上表: .bss 51,344 → 34,960、空き 190,561)

判断材料としては「arena が PSRAM に移り、S3 の内蔵 RAM は ti 導入前と同じ
水準に戻っている」ところまで数字が出ている。**残るのはブート健全性の確認
だけ**なので、S3 を USB に繋いでいただければ次の手順で完了できる:

```
cd fmruby-core
FMRB_HW_TARGET=NARYAv3 rake clean_all && FMRB_HW_TARGET=NARYAv3 rake build:esp32
FMRB_HW_TARGET=NARYAv3 FLASH_BAUD=115200 rake flash
python3 ../tools/fmrb_serial_capture.py -t 40 boot.log   # Guru 0 と IRAM free を見る
```

**Modern 限定ゲートは作っていない**。arena が外に出た今、S3 の内蔵 RAM は
P5 前と同じなので、作る根拠がまだ無いため (指示書どおり「要らなければ
作らない」)。

## 途中で踏んだ実機作業の罠 (次回のため)

- **Tab5 は `fmrb_serial_capture.py --no-reset` でもリセットする**
  (USB-Serial-JTAG)。UI 検証の最中にログを掴み直すと、そこで実機が再起動して
  検証がやり直しになる。**先に長めの capture を開始し、切らさないまま
  UI を操作する**。今回これで 2 回やり直した。
- `rake flash` の前に capture を必ず止める (ポートは排他)。止め忘れると
  「device reports readiness to read but returned no data」で失敗する。
- **`pkill -f fmrb_serial_capture` は自分のシェルまで殺す** (パターンが
  コマンドライン文字列に一致する)。`ps -eo pid,cmd | grep "[f]mrb_..."` で
  PID を取ってから kill する。
- `tools/fmrb_rd_input.rb` に **backspace / delete / home / end / F1-F12 /
  International1 (`_` 用)** が無かったので足した。未登録のキー名を渡すと
  ツールはコマンド列ごと中断するので、**打鍵が全く効かない**という形で出る。
- デスクトップのメニュー座標は sim と同じだが、**窓が開いていると同じ座標が
  別の物を掴む**。クリック前にスクリーンショットで確認するほうが速い。
