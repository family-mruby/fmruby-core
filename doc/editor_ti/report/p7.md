## できたこと

ブラウザだけで、実機のエディタと同じ 4 つが効く。**デバイスにつながって
いなくても効く** (BLE 不要)。

- Ctrl+Space の補完 (候補の説明つき)
- マウスを重ねると型/シグネチャ
- 入力が止まると診断 (赤い下線 + 件数)
- F1 で長文ヘルプ
- 説明文の言語トグル (日本語/English)

元は 1 か所 `sig/*.rbs`。ファームの型 db も F1 も同じ場所から作る。

## 指示書どおりに進んだところ (確認できた前提)

- **WASM に mruby は入らない**。`PRISM_XALLOCATOR` を定義しないので
  prism/defines.h の既定 (`xmalloc = malloc`) に落ちる。プールも
  global_mrb も longjmp も不要で、wrapper は editor_ti_bridge.c から
  それらを引いた形になった。
- **fork 無改修**。変更は tool/web/ + Rakefile + tool/ti/gen_help.rb のみ。
- ビルドは gcc → emcc のターゲット違いで済んだ。engine の src/**/*.c +
  prism の src/*.c と src/util/*.c + 生成 db + wrapper を 1 回のリンクで
  出す。エラーはゼロ (一度も直していない)。

## 指示書と変えた点

1. **UI は app.js ではなく `js/ti-editor.js` に置いた**。sprite-editor.js /
   map-editor.js と同じ並びで、app.js からは `tiEditorOpened` /
   `tiEditorTextChanged` / `tiEditorClosed` の 3 つを呼ぶだけ。app.js に
   500 行足すより、既存の分け方に合わせた方が読みやすい。
2. **T5 (help.json) はやった**。gen_help に `--json` を足すだけで済んだ
   (ページの組み立てを `build` に切り出し、ファイル出力と JSON 出力が同じ
   結果を使う。既存の flash/help と 1 バイト差なしを diff で確認)。
3. **JS 側の API は同期にした**。指示書は Promise を返す形だったが、
   非同期なのはモジュールの読み込みだけなので `createTi()` で 1 回待ち、
   以後 `suggest` / `hover` / `diagnose` は普通の関数呼び出しにした。
   打鍵のたびに待つ理由がない。
4. **F1 ページの言語切りは ti_ui.rb と同じ 2 段**にした。指示書の
   「二国語 split を JS に移植」を素直に「マーカー行で割る」だけにすると、
   英語側にページの頭 (タイトル・シグネチャ・要約) が残らない。実機の
   `help_filter_language` と同じく、**頭 (メソッド 6 行 / クラス 2 行) は
   残して要約だけインライン置換、長文は片側を捨てる**形にした。
   これは実装中にスクリーンショットを見て気づいた (下記)。

## 画面での配置は「計算」ではなく「計測」

エディタは `white-space: pre-wrap` で**行を折り返す**ので、桁 x 文字幅で
座標を出すと折り返した瞬間に外れる。代わりに、textarea の裏にある
**ハイライト用の overlay (同じ文字が同じ場所にある)** を DOM Range で測る。

- 補完の一覧の位置 = カーソル直前の文字の矩形
- 診断の下線 = 診断範囲の Range の `getClientRects()` (折り返し 1 行につき
  1 矩形なので、そのまま並べる)
- ホバー = ポインタ座標から文字位置への二分探索 (文字の矩形は読み順に
  並ぶので比較できる)

1 つの仕掛けで 3 つとも片付く。

## 速さ (Node/V8、同一ソースで実機と比較可能)

| ソース | 候補 | 1 リクエスト |
| --- | --- | --- |
| 14 B | 2 | 0.0 ms |
| 2,236 B | 2 | 0.3 ms |
| 8,374 B | 2 | 2.0 ms |
| 22,718 B | 2 | 11.4 ms |
| 32,816 B | 2 | 23.0 ms |

**P5 で Tab5 実機が 21.9KB = 417 ms だったのと同じ形の測り方**で 11.4 ms。
約 37 倍速い。つまり P5 の申し送り (受付上限 32KB、明示操作のみ) は
ブラウザには要らない。ブラウザ側の上限は 256KB
(`TW_MAX_SOURCE_BYTES`。engine の arena が 100KB 超で諦めるので、
それより上は「答えない」が正しい)。診断は入力が止まって 600ms で自動、
補完は Ctrl+Space、ホバーは 250ms 停止で走る。

実測の footer 表示では、この報告の例 (64B〜86B) は 0〜5 ms。

## 実装中に見つけたこと

- **候補一覧の detail はラベルを含む** (`abs: () -> Integer`)。2 列に
  すると名前が二重に出るので、detail からラベル分を落として表示する。
  実機は 1 行表示なので出ない問題。
- **F1 のヘルプ面は非同期**。パネルを先に開いて help.json を待つので、
  待つ間は "loading..." を出す (テストがそこを掴んで空文字を読んでいた)。
- **file:// では型支援だけ動かない**。ブラウザが file:// から ES モジュール
  を読めないため。既存機能は従来どおり動き、エディタ下端に理由が出る。
  README に「http で配信して開く」と書いた。
- Node で `ti.js` を ES モジュールとして読ませるために
  `tool/web/package.json` (`"type": "module"`) が要る。ブラウザはこの
  ファイルを見ない。

## 残件・やらなかったこと

- **`rake setup` には繋いでいない**。emcc は普通のビルド依存ではないので
  `rake ti:wasm` は手動。sig/ を直したら打ち直す (README に記載)。
- 候補一覧は演算子から始まる (engine の順そのまま)。実機と同じなので
  触っていない。気になるなら並べ替えは UI 側でできる。
- 実機 (Tab5/S3) 側の変更はゼロ。debugd over BLE 経路は不要のまま。
