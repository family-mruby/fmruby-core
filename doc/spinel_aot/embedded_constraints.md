# Ruby AOT ランタイムを MCU に載せるときの制約 (Spinel 実装知見)

Spinel (Ruby → C の AOT コンパイラ) を ESP32 実機に載せる過程で判明した、
**組み込み固有の制約と失敗モード**の集約。発表・共有時の参照元を想定している。

対象読者: AOT / VM ランタイムを MCU に移植する人。
本書は**ランタイムと移植層**の話で、**Ruby ソースの書き方の制約は
`ruby_writing_constraints.md` が正**。両者は独立している。

検証環境: ESP32-P4 (riscv32) / ESP32-S3 (Xtensa) / ESP-IDF v5.5.4 /
内部 SRAM 約 500 KB + PSRAM 32 MB。比較対象は同一アプリの mruby 実行。

---

## 0. 一行で言うと

**AOT ランタイムは「ホストのヒープとスタックは実質無限」という前提を、
コードのあちこちに固定サイズの数値として埋め込んでいる。**
MCU ではその数値のひとつひとつが、プール全体やタスクスタック全体に
匹敵する。移植作業の実体は、その埋め込まれた前提を発見して外に出すことだった。

Spinel 固有の話に見えるが、同じ形の前提は多くのランタイムにある。

**なぜアプリ側の工夫では済まず、ランタイム本体 (fork) を触る必要があったのか**は
12 章にまとめた。発表で問われやすい論点なのでそちらを参照。

---

## 1. 固定サイズバッファ — 最大の落とし穴

ホストでは「気にする必要のない定数」が、MCU では致命傷になる。
実際に潰した 4 種を挙げる。**全て同じ形 (`#define` を `#ifndef` ガードにして
ポートが縮める) で解決した**。

| 対象 | 既定値 | 32bit での実サイズ | 何と比べて致命的か |
|---|---:|---:|---|
| スタック上の一時バッファ (`SP_STACK_SCRATCH_MAX`) | 65536 | `sp_sprintf` の一時が 4 KB | タスクスタックが 12〜24 KB |
| 実行時 intern シンボル表 (`SP_DYN_SYMS_MAX`) | 8192 エントリ | 32 KB / 生成TU | 内部 SRAM の空きが 160 KB |
| 例外/catch ハンドラスタック (`SP_EXC_STACK_MAX` 他) | 64 | 42 KB / 生成TU | 同上 |
| GC マーク作業リスト (`SP_GC_MARK_STACK_MAX`) | 65536 エントリ | **256 KB を単一連続ブロック** | インスタンスのプールが 512 KB |

### 1.1 実測されたスタックフレーム

`-fstack-usage` による実測 (ILP32, -O2)。ランタイム側:

| 関数 | フレーム |
|---|---:|
| `expand_path` | 24,672 B |
| 行読み (stdin/ARGF/File) | 8 K〜64 K B |
| `glob_rec` | 6,352 B |
| `readlines` / `pwd` / `realpath` / `sprintf` | 4,144〜4,192 B |
| `caller` | 1,072 B |

**生成された Ruby メソッドのフレームが支配的**という点が重要:

| 生成関数 | フレーム |
|---|---:|
| `system_desktop_entry` | 6,256 B |
| `handle_app_control` | 4,368 B |
| `handle_hid_event` | 4,064 B |
| `FmrbApp#initialize` | 1,952 B |

`on_create` のチェーンだけで約 11 KB。この実測により
**タスクスタックを 12 KB → 24 KB (system app) / 16 KB (kernel) に引き上げた**。

### 1.2 「縮めて透過」と「縮めたら意味が変わる」を分ける

一時バッファを縮めるとき、2 種類を区別する必要があった。

- **透過なもの**はクランプしてよい。`sp_sprintf` の一時 (溢れたら
  フル幅で再レンダリングする)、`IO.copy_stream` のチャンク、`caller` の捕捉段数
- **バッファ長が意味論そのもの**なものはクランプしてはいけない。
  行読み (長い行が黙って分割される)、パス操作 (パスが黙って切り詰められる)。
  こちらは**縮めるのではなくコンパイルエラーにした** — 実行時 raise にすると
  失敗が実機まで持ち越されるため、使っていたらビルドが落ちる方がよい

この方針の副産物として、`make check-stack` ゲート
(ポート構成でコンパイルし `-fstack-usage` が 1 KB 超なら失敗) を用意した。

### 1.3 GC マーク作業リストが最悪だった

これは他と質が違う。`sp_gc_mark_all` が作業リストを
**65,536 エントリ = 256 KB、単一連続ブロックで遅延確保**していた。
カーネルのプールは 512,000 B なので**プールの半分**。

皮肉なことに `sp_gc_mark` には**再帰フォールバックが元から実装されていた**:

```c
if (sp_gc_mark_stack && sp_gc_mark_top < SP_GC_MARK_STACK_MAX) { push }
else { h->scan(obj); }
```

つまり作業リストは「あれば速い」最適化であって NULL でも動く設計なのに、
**確保に失敗するとアロケータがプロセスを殺していた** (下記 3.1)。
設計意図と実装の間にこの種の断絶があると、移植時に一気に表面化する。

## 2. スタックの扱い — ヒープに逃がせない事情

MCU の RTOS タスクスタックは数十 KB しかない。単純に
「大きなローカルはヒープへ」としたいところだが、**この種のランタイムでは
それが安全でない**ことが分かった。

**理由: 例外が `longjmp` で実装されている。** `malloc` したローカルは
raise を跨ぐと確実に漏れる。実際 fork のコードには、この問題と
格闘した痕跡がコメントとして残っていた。加えて、失敗経路が数百箇所増える。

結果として採用したルール:

- ローカル配列は **128 B** まで
- 関数フレームは実測 **512 B** まで (ゲートは 1024 B で運用)
- **VLA / `alloca` は全面禁止**
- **再帰は要許可** (12〜16 KB スタックでは Ruby の再帰は実質 3 段程度で尽きる)
- プールから取ったバッファは、「大きく、同一関数内で確実に解放でき、
  raise を跨がない」ものにだけ使う

「16 バイト境界で全部ヒープへ」という案は上記の理由で**却下**した。

## 3. アロケータ — 契約が違う

### 3.1 OOM が回復可能でない

`sp_mem_malloc` は確保に失敗すると `sp_oom_die()` = `exit(1)` を呼ぶ。
ホストでは「そこまで来たらどうせ終わり」で妥当だが、MCU では
**ファームウェア全体が落ちてリブートする**。しかも上記 1.3 のように、
呼び出し側が NULL を許容する設計になっている箇所でも殺される。

**移植時のチェックポイント**: ランタイムの OOM 契約を確認し、
「NULL を返して呼び出し側が対処できる」経路と
「即死」経路がどう分かれているかを把握しておく。

### 3.2 素の malloc は使えない

ESP32 では `CONFIG_SPIRAM_USE_MALLOC` を有効にしない限り、
素の `malloc` は**内部 DRAM しか返さない**。PSRAM はプール経由でしか触れない。
ランタイムの全確保をプールに向ける必要がある。

呼び出し箇所は約 490 あったため、書き換えではなく
**`-include` で libc 名を関数形式マクロで差し替える**方式を採った
(`sp_mem_override.h`)。これで lib/*.c、ヘッダ内 inline、生成 TU まで
一括でカバーでき、codegen も呼び出し箇所も無改修で済んだ。

適用範囲の制御が重要で、**消費側コンポーネントに波及させてはいけない**。
消費側は DMA 可能メモリや PSRAM を `heap_caps_*` で指定して確保するので、
そこまで差し替えると壊れる。PRIVATE に限定し、
`nm` で未定義 libc 参照がゼロであることをゲート化した (`make check-mc-syms`)。

**同じ手が他のライブラリにも効いた**: vendored な msgpack-c も
生 `malloc` を直接呼んでおり、同じ `-include` 方式でプールに寄せた。
ただし**ヘッダの `static inline` は呼び出し側 TU に展開されるので届かない**。
そこは固定バッファ方式に書き換える必要があった。

### 3.3 「総量不足」と「連続領域が取れない」は別物

実機のクラッシュで最も誤診しやすかった点。
GC が 256 KB を要求して落ちたとき、**プールの使用率は 17〜21% だった**。
総量では余裕があるのに、TLSF に live が散った状態では
単一連続ブロックとして取れなかった。

計装を入れてプール使用率を出すまで、これは切り分けられなかった。
**移植の早い段階でプールごとの used/free を定期的に出す計装を入れるべき**だった。

## 4. 32bit 特有 — 64bit では絶対に見えないバグ

ホストが 64bit だと、以下は**まったく現れない**。

### 4.1 クロス TU での整数幅の不一致

最悪の 1 件。`mrb_int` が 2 箇所で別々に定義されていた:

- bignum 内部用ヘッダ: `int64_t` (bignum の内部演算には正当)
- 生成 TU 用ヘッダ: `intptr_t` (32bit では 4 B)

公開 API の引数が `mrb_int` だったため、**32bit では TU 間で引数がずれ**、
mod / exp がガベージポインタ化して SIGSEGV。64bit では両方 8 B なので不可視。

**対策**: クロス TU の公開 API に処理系依存の整数 typedef を使わない。
境界は `intptr_t` か明示幅で固定する。

### 4.2 可変長引数の昇格

codegen が int 可変長引数を `(long long)` に強制昇格していた。
C の可変長引数昇格は int → int のままなので、32bit では
8 B スロットが `%d` (4 B) とずれ、後続の引数が全部 4 B シフトし、
`%s` が整数をポインタとして解釈して SIGSEGV。

### 4.3 型の最大値の決め打ち

`depth = INT64_MAX` が 32bit の `mrb_int` (= `intptr_t`) で -1 に truncate。
`INTPTR_MAX` (その型の最大値) にすれば両幅で正しい。

### 4.4 対策としての 32bit ゲート

**`make test32`** を用意した。ランタイムと全生成 TU を `-m32` で
再ビルドして全テストを走らせる。ILP32 は Xtensa / riscv32 の
proxy として十分機能し、上記 3 件はすべてこのゲートで捕捉された。

実装上の要点: 64bit のビルドツリーを一切触らない独立ツリーにする
(回帰リスクをゼロにする)。コンパイラ自体はホストネイティブでよい
(生成 C はアーキ非依存)。

## 5. ホスト facility への依存

ランタイムは POSIX を前提に facility を使っている。ESP-IDF / newlib には
無いものが多い。実際に対処したもの:

| 依存 | 対処 |
|---|---|
| `sys/mman.h` (fiber の mmap fallback) | 機能マクロ `SP_NO_MMAN` でガード。fiber モジュールごとビルド除外 |
| `execinfo.h`, `sys/ioctl.h` | `__has_include` で自動検出 |
| `ucontext.h` | `SP_NO_MMAN` 下でスタブ化 |
| `poll.h` (スケジューラ) | モジュールごとビルド除外 |
| `lstat` | `stat` に置換 (symlink が無いので等価) |
| `malloc_trim` | 既存のマルチインスタンスガードで自動的に非到達 |

### 5.1 「ヘッダが存在する」≠「シンボルが定義されている」

`sys/ioctl.h` は ESP-IDF に**スタブとして存在する**ため `__has_include` は真になるが、
`TIOCGWINSZ` / `struct winsize` は未定義でコンパイルエラーになった。

**しかもこれは単体プローブでは見つからなかった** — IDF の include path が
無い状態では `__has_include` が偽になり、素通りしていた。
**実ビルドでしか出ない**種類の問題である。

対策として、機能の有無は**ヘッダの存在ではなくシンボル/マクロの定義で判定**するようにした。

### 5.2 ホストチェックの落とし穴

`gcc -fsyntax-only` では未定義参照を拾えない。
`gcc -c` して `nm -u` で照合する必要がある。

さらに、**ポートのフラグとポートのコンパイル対象集合で照合しないと意味がない**。
Linux のフラグ (fiber をコンパイルする構成) でチェックしていたため、
ポート固有の欠落を検出できていなかった。

## 6. ファイルシステム

ランタイムの `File` / `Dir` は生の POSIX パスを使う。MCU には POSIX FS が無く、
仮想パス解決 (HAL) を通す必要がある。

**対処**: ランタイムに io backend フック (open/read/write/seek/tell/close/stat +
opendir/readdir/closedir) をアロケータフックと同型で追加し、
未設定なら POSIX 既定にした。ホストのビルドはバイト同一を維持できる。

コンソールストリーム (stdout/stderr) は backend を経由させず stdio に直結する
分離が必要だった。

## 7. マルチインスタンス化

1 プロセスで複数の Ruby プログラム (カーネルとデスクトップ) を
独立ヒープで動かすために必要だった作業。組み込みでは
「1 プロセス = ファームウェア全体」なので避けて通れない。

- ランタイムのグローバル状態をコンテキスト構造体へ移動。
  互換マクロ (errno 方式) を使えば **codegen と生成 C は無改修**で済む
- **生成 TU が entry 以外にグローバルを出す**と、2 プログラムを
  1 バイナリにリンクしたとき多重定義になる。これも同じ手法で潰した
- process constructor で コンテキストのフィールドを書く初期化子があると、
  main 前にクラッシュする (その時点でカレントコンテキストが無い)
- **`__thread` はポインタ 1 本なら Xtensa でも riscv32 でも動く**
  (ESP-IDF の TLS ポート実装は不要だった)。ただし `.tbss`/`.tdata` は
  全タスクに複製されるので、ポインタ 1 本以外を置かないこと

## 8. オブジェクトモデルのコスト

AOT にしても**メモリは減らない**。同一アプリで mruby と比較した結果:

| | Spinel / mruby |
|---|---|
| live footprint | **約 1.9 倍** |
| GC churn | 約 11 倍 (しきい値設定に依存) |

1.9 倍の主因は GC ヘッダ (48 B)。**AOT の利点は速度と遅延分散であって
メモリではない**、という点は移植を判断する上で重要。

参考: 同アプリの描画 1 回あたり Ruby 実行時間は Spinel 2.0 ms / mruby 4.8 ms、
最大値は 3 ms / 14 ms。**最大値の差が大きい** (mruby のスパイクは GC pause 由来)。
組み込みでは平均より最悪値が効くので、ここが AOT の実利になる。

## 9. 診断の教訓 (発表向けに一番効く部分)

移植で時間を溶かしたのは、コードの難しさではなく**誤診**だった。

### 9.1 エラーコードの意味を確認する

`msgpack unpack failed` というログを見て、フレーム破損 (32bit 固有の
シリアライズ差など) を疑った。**誤りだった**。
戻り値 `-2` は NOMEM であってパースエラー (-1) ではなく、
実際にはヒープ枯渇だった。ダンプしたフレームは完全に正常だった。

**症状名から原因を推定しない。エラーコードの定義を見る。**

### 9.2 OOM は 2 種類ある

3.3 のとおり。プール使用率 20% で OOM が起きる。

### 9.3 見積もりでサイズを決めない

「タスクスタックが 24 KB で Ruby フレームが 2〜6 KB だから、
ネストは数段しか起きない」と推論して例外スタックを 64 → 32 にしたところ、
**GC のルート管理領域を破壊した**。ネスト深さは呼び出しグラフの性質であって、
スタックサイズからは導けない。

**計測してから決める。** 併せて、境界チェックの無い書き込みが
隣接領域を壊す構造になっていないかを先に確認する
(この件では push 側に境界チェックが無く、pop 側にはあった)。

### 9.4 ホストとポートで容量を変えない

上記の悪い値は、**同じ設定を Linux ビルドにも一律適用していたおかげで
headless テストで即座に露見した**。ポート専用フラグにしていたら
実機まで持ち越していた。dual build に容量差を作らないこと。

### 9.5 ホストのテストで再現しない負荷がある

実マウスのドラッグが流す連続的な移動イベントのレートは、
入力注入では再現できなかった。イベントごとに確保するコードでは
このレート差がそのままメモリ圧の差になる。
**ホスト側で再現しないことをもって「問題なし」としない。**

### 9.6 「ビルドしたもの」と「焼いたもの」は違いうる

ビルドとフラッシュでエンジン選択の環境変数がコンテナに渡っておらず、
**Spinel をビルドした直後に焼いても mruby が載る**という状態があった。
実機ログを読む前に、成果物 (バイナリサイズ、`readelf` のシンボル、
ログのタグ) で「何を焼いたか」を検証する習慣が要る。

## 10. 数値サマリ (before / after)

移植で回収した内部 DRAM:

| | 修正前 | 修正後 |
|---|---:|---:|
| 生成 TU 2 本の静的 `.bss` 合計 | 192,168 B | 88,392 B |
| 実機 IRAM free (desktop のみ, アイドル) | 実質 0 | 76,108 B |

比較: 同一アプリの mruby 構成では IRAM free 163,372 B。
**残る約 87 KB の差はほぼ例外/catch スタック** (生成 TU 1 本 42,304 B × 2)。
ここは計測に基づいて縮める作業が残っている。

## 11. 移植チェックリスト (一般化)

他の AOT / VM ランタイムを MCU に載せる場合の要点。

1. **固定サイズバッファを全部洗い出す**。`grep` で `[1024`, `[4096`,
   `MAX]` 等。それぞれ「ホストの何を前提にした数値か」を問う
2. **スタックフレームを実測する** (`-fstack-usage`)。ランタイムだけでなく
   **生成コード**も。生成コードの方が大きいことがある
3. **OOM の契約を確認する**。回復可能か即死か。即死なら、
   呼び出し側が NULL 許容の設計になっている箇所と矛盾していないか
4. **アロケータの差し替え口を作る**。呼び出し箇所の書き換えではなく
   `-include` によるマクロ差し替えが有効。適用範囲は厳密に限定する
5. **32bit ゲートを CI に入れる**。`-m32` で十分な proxy になる
6. **ホスト facility を棚卸しする**。ヘッダの存在ではなくシンボルで判定する
7. **プールごとの使用量を出す計装を最初に入れる**。後から入れると、
   それまでの誤診の時間が丸ごと無駄になる
8. **ホストとポートで容量パラメータを変えない**。差を作ると
   問題が実機まで持ち越される

## 12. なぜランタイム本体 (Spinel) の改造が必要だったのか

移植にあたっての方針は **「統合側 (fmruby) で回避できるものは fork しない」**だった。
それでもランタイム本体に手を入れたのは、以下は**アプリ側からは原理的に手が届かない**
ためである。分類ごとに「なぜ回避不能だったか」を示す。

### A. 値がランタイム内部に固定されていて、外から変えられない

対象: 1 章の 4 種 (スタック一時バッファ / intern 表 / 例外・catch スタック /
GC マーク作業リスト)。

**回避不能な理由**: これらは `#define` としてランタイムのヘッダと .c の中にあり、
しかも `#ifndef` ガードが無いので `-D` でも上書きできなかった。
配列の実体は**生成 TU 側**に出るため、ランタイムを差し替えずに
サイズだけ変える方法が存在しない。アプリの書き方をどう変えても影響しない。

**やったこと**: `#ifndef` ガードを足してポートが `-D` で縮められるようにした。
既定値は不変なので、ホストのビルドはプリプロセス結果まで同一。

補足として、4 種のうち `SP_DYN_SYMS_MAX` **だけは既にガードが付いていた**。
上流も「組み込みでは縮めたくなる値がある」ことを認識し始めていたと読める。
残り 3 種を同じ形に揃えた、という位置づけになる。

### B. 確保の宛先がランタイム内部にある

**回避不能な理由**: ESP32 では素の `malloc` が内部 DRAM しか返さないため、
ランタイムの全確保をプールに向ける必要がある。しかし呼び出し箇所は
ランタイム内に約 490 あり、**生成 C の中にもある**。
アプリからは 1 箇所も触れない。

**やったこと**: `-include` でマクロ差し替えするフックを追加。
呼び出し箇所と codegen は無改修で済ませた。

### C. `#include` とプラットフォーム分岐がランタイム内部にある

**回避不能な理由**: `sys/mman.h` などの include はランタイムのヘッダが行う。
アプリ側から止める手段がない。またモジュールをビルド対象から外すだけでは、
他モジュールからの参照が未定義シンボルとして残る
(`--gc-sections` が必ず落としてくれるとは限らず、実際 1 件残った)。

**やったこと**: 機能マクロと `__has_include` によるガード。
参照側にも同じ条件のガードを入れた。

### D. codegen / ランタイムのバグ

対象: 32bit の 3 件 (整数幅の不一致 / 可変長引数の昇格 / 型最大値の truncate)、
および poly ディスパッチの欠落数件。

**回避不能な理由**: **誤ったコードが生成される**ので、Ruby を書き換えても直らない。
特に重要なのは、**レシーバ側の poly ディスパッチ欠落は、引数や結果に `.to_s` を
付けても治らない**という点。一度この誤診で「直したつもり」になっており、
症状が別経路で再発して初めて根本原因に到達した。

**やったこと**: codegen とランタイムを修正。いずれも 32bit / 動的型に関する
汎用のバグで、fmruby 固有の事情は入っていない。

### E. I/O バックエンドが差し替えられない

**回避不能な理由**: `File` / `Dir` が POSIX を直接呼んでおり、
仮想 FS を挟むフックが存在しなかった。MCU には POSIX FS が無い。

**やったこと**: アロケータフックと同型の io backend 契約を追加。
未設定なら POSIX 既定なので、ホストは無影響。

### F. マルチインスタンス化

**回避不能な理由**: 1 プロセスに 2 つの Ruby プログラムを独立ヒープで載せる、
という要件自体がランタイムの前提の外にあった。状態がグローバル変数として
持たれているため、外側からインスタンスを分ける方法がない。
組み込みでは「1 プロセス = ファームウェア全体」なので、この要件は避けられない。

**やったこと**: グローバル状態をコンテキストへ移動。互換マクロにより
codegen と生成 C は無改修。

### 対照: fork せずアプリ側で回避したもの

判断の基準を示すため、**あえて fork しなかった**例も挙げる。

| 事象 | アプリ側の対処 |
|---|---|
| 保存して後で呼ぶブロックが外側ローカルをキャプチャできない | 即時描画に書き換え |
| poly 配列要素からの多重代入が通らない | 明示ループに展開 |
| `Integer#chr` 未実装 | `setbyte` で組み立て |
| `setbyte` のレシーバが poly 化して誤ディスパッチ | 具体型のローカルを経由 |

**基準**: 「Ruby の書き方で自然に回避でき、その書き方が他の利用者にとっても
妥当」ならアプリ側で対処する。「言語として正当な Ruby が動かない」
「アプリからは到達できない」なら fork する。

### 全ての fork 変更に共通する設計方針

**既定値・既定動作を変えないガードとして実装した**。その結果:

- ホストのビルドはプリプロセス結果までバイト同一を維持でき、
  64bit のテストは全パスのまま
- 組み込み対応が「ホストを犠牲にする」形にならない
- そのまま上流に提案できる形になっている
  (一覧は `reports/fork_pr_candidates.md`)

移植のために本体を触るとき、この「既定不変 + ポートが明示的に選ぶ」形を
守れるかどうかが、fork が塩漬けになるか上流に還元できるかの分かれ目になる。
