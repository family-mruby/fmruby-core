# U0 調査の結果

> 2026-11-26。読むだけの調査 1 本と、その結果を受けた決定。計画への反映は plan.md 4 章・7 章。

## 1. 上流 (`picoruby-uart`) の形

- `UART.new(unit:, txd_pin: -1, rxd_pin: -1, baudrate: 9600, data_bits: 8, stop_bits: 1, parity: PARITY_NONE,
  flow_control: FLOW_CONTROL_NONE, rts_pin: -1, cts_pin: -1, rx_buffer_size: nil)`。`unit` は名前 (`:ESP32_UART0`〜)。
- 読む側はどれも待たない (リングバッファから取るだけ)。`read(len)` は len バイトそろうまで nil、`readpartial(max)`・
  `getbyte` は空なら nil、`gets` は `"\n"` が届くまで nil で `"\n"` 込みで返す。`write` は書き終わるまで待つ。
- ほか: `putc`・`puts`・`ungetbyte`・`bytes_available`・`line_ending=`・`setmode`・`set_format`・`flush`・
  `clear_rx_buffer`・`clear_tx_buffer`・`break`・`baudrate`。`close` は無い。
- 上流の中の食い違い: 型定義と README が実装と違う所がある (パリティの値が逆、`readpartial` の戻り値、速さの既定を
  115200 と書いている)。**実装に合わせる**。ESP32 の port には、1 回の受信が 128 バイトを超えると読んでいない分まで
  積む不具合がある (自前で書くので引き継がない)。
- 互換の確認に使える物: gem の `test/uart_test.rb` (unit の名前を置き換えて流す) と README の使用例。

## 2. 本体の今の UART

- HAL は `components/fmrb_hal/fmrb_hal_uart.h` (open・close・read・write・read_byte)。8N1 固定、受信量の問い合わせ・
  形式の変更・break は無い。使い手はシリアルの MIDI 出力だけ (UART2、TX だけ)。
- 機種ごとの使われ方:

| 機種 | コンソール | 描画側とのリンク | MIDI |
|---|---|---|---|
| NARYA v3 (S3) | UART0 | UART1 | UART2 |
| NARYA v4 (P4-Nano) | UART0 + USB-JTAG | 無し | 無し |
| Tab5 (P4) | UART0 + USB-JTAG | 無し | UART2 (TX が Grove) |
| AtomS3R・StickS3 | USB-JTAG | 無し | UART2 (TX が Grove) |

- UART の数は S3 が 3、P4 が 5 (+ LP が 1)。アプリに回せる番号: NARYA v3 は 2、S3 のミニ機種は 1・2、P4 は 1〜4。
  UART0 と LP は出さない。

## 3. 見立てと違った点

| 見立て | 実際 | 決めたこと |
|---|---|---|
| 受信のバッファは PSRAM に置ける | ESP-IDF のドライバのバッファは必ず内蔵 RAM (全機種が `SPIRAM_USE_CAPS_ALLOC`) | ドライバの受信は 1 KB (開いている間だけ内蔵 RAM 約 2 KB)、その後ろに PSRAM のリング (既定 4 KB) を置き、アプリが呼ぶたびに汲み上げる。静的な増分は 0 |
| sim に HW の偽物がある | GPIO・I2C はログを出すだけで、sim には入っていない。sim ではアプリが終わったときの HW の片付けも走らない | UART の偽物を sim に作る: 既定はループバック (書いた物が読める)、FIFO (`uart<N>_in.fifo`・`_out.fifo`) があればそちら。片付けの経路を sim にも通す |
| GPIO・I2C は境界の関数 | 上流の gem に自作の下の層をつないだ形で、境界の関数ではない | UART は最初から境界の関数にする (`sig/` に書き、wasm・MicroPython に自動で出る。Lua は 1 行足す) |
| MIDI と UART は台帳で取り合うだけ | シリアルの MIDI 出力は、一度開くと再起動まで UART2 とピンを持ち続ける (持ち主なし) | 今回は両方向とも理由つきで断るだけ。MIDI の側を直すか (開いたアプリが終わったら放す) はユーザに聞く (未確定 3) |
| 機種ごとに UART 用のピンの表を持つ | GPIO はシステムのピンの表 (`GPIO_RESERVED`) で守っている | **UART も GPIO と同じ表で守る** (システムのピンは断る、入力だけの線は RX だけ)。別の表は持たない |
| I2C は台帳を見ている | I2C はピンの取得の結果を見ていない (UART が持つピンを上書きできる) | 今回は直さない (hw_resources の H1・H2)。記録だけ |

## 4. 作る物の大きさ (見積もり)

手で書く分で約 1,400 行: HAL の拡張 (ESP32・POSIX)、ピンの台帳 (`claim_uart`・システムの番号)、境界の関数
(`main/app/fmrb_boundary_uart.c`。unit の表・PSRAM のリング・判定・片付け)、`sig/uart.rbs`、Ruby の包み、ホストの試験。
ほかに生成物 (SDK・MicroPython の表) の作り直し。
