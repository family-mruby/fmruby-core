# U1・U2 の結果 (UART の API とシリアルターミナル)

> 2026-11-26。指示は instruction_u1.md。本体の checkout (ブランチ app-uart) と sim (Retro・Modern)、ネイティブ版で確認した。
> ESP32 のビルド・実機は触っていない (U3)。

### 1.1 メソッドごとの動き (上流との違い)

| メソッド | 動き | 上流との違い |
|---|---|---|
| `UART.new(unit:, txd_pin: -1, rxd_pin: -1, baudrate: 9600, data_bits: 8, stop_bits: 1, parity:, flow_control:, rts_pin:, cts_pin:, rx_buffer_size: nil)` | 本体で開く。受信の箱は既定 4096 | `unit:` に整数も受ける。`FLOW_CONTROL_NONE` 以外は ArgumentError。`rx_buffer_size` の誤りは ArgumentError (上流は IOError)。`@unit_num` を持つ (上流の試験が読む) |
| `read(len=nil)`・`readpartial`・`getbyte`・`gets` | 待たない。無ければ nil。`gets` は `"\n"` 込み | 同じ。上流の ESP32 版の「128 バイトを超えると読んでいない分まで積む」不具合は無い |
| `ungetbyte` | 下位 8 ビットを先頭へ。一杯なら IOError | 同じ |
| `write` | 4096 バイトずつ境界へ渡し、ドライバに渡し切るまで待つ。長さを返す | 同じ (分ける所だけ自前) |
| `putc`・`puts`・`line_ending=` | 上流と同じ | 同じ |
| `setmode`・`set_format`・`set_flow_control` | 上流と同じ (形式は省くと 8N1 に戻る) | 流れの制御は無しだけ。速さの範囲 300〜5000000 を確かめる |
| `flush` | 送り終わるまで待つ (1 秒まで) | 上流は 100 tick |
| `clear_rx_buffer`・`clear_tx_buffer` | 受信を空に / 送信は何もしない | 同じ (上流の ESP32 版も送信は何もしない) |
| `break(time=nil)` | Float は秒、Integer は ms、既定 100 ms、10 秒まで。TX の線を反転して低く保つ | 上流の ESP32 版はドライバの break にビット数として ms を渡していて短すぎる。sim では何もしない |
| `baudrate` | 頼んだ速さ (setmode の後は実際の速さ) | 上流は開くときも実際の速さ |
| `close`・`closed?`・`dropped` | 自前の拡張 | — |

境界の関数 `FmrbUart`: `open`・`close`・`read(unit, max)`・`read_line`・`write`・`bytes_available`・`unget`・`flush`・`clear_rx`・
`clear_tx`・`send_break`・`set_baudrate`・`set_format`・`dropped`・`unit_mask`。`read` は「呼ぶ側の箱が小さければ何も取らずに全体の
長さを返し、次にその長さの箱で呼ぶと同じバイトを取る」(生成のつなぎが 2 回呼ぶ間に新しいバイトが届いてもずれない)。
**`unit_mask` は計画に無い足し物** (その端末で開ける番号を先に知るため。ターミナルのアプリが使う。hw_resources の
「アプリが起動の前に確かめられる問い合わせ」に当たる)。

### 1.2 断る理由 (`FmrbUart.open` の答え、`fmrb_app_uart.h`)

| 番号 | 意味 | Ruby の例外と文 |
|---|---|---|
| 1 | その機種に無い番号 | ArgumentError "no UARTn on this board" |
| 2 | 無いピン (次のバイトに TX=1 / RX=2) | ArgumentError "TX pin p does not exist on this board" |
| 3 / 4 | ピンが両方 -1 / TX と RX が同じ | ArgumentError |
| 5 / 6 / 7 | 速さ / 形式 / 受信の箱の大きさ | ArgumentError |
| 8 | 本体の番号 | IOError "UARTn is used by the system" |
| 9 | ほかのアプリが開いている | IOError "UARTn is in use by another app" |
| 10 | MIDI の serial 出力が番号かピンを持つ | IOError "... is used by the MIDI serial output" |
| 11 / 12 / 13 | システムのピン / 入力だけの線を TX に / ピンが使用中 | IOError "TX pin p is used by the system" ほか |
| 14 | ドライバが開かない・メモリ | IOError "UARTn could not be opened" |
| 15 | この環境に無い (ブラウザ版・ネイティブ版) | IOError "not available in this environment" |

Ruby の包みの前の名前の誤り (`:RP2040_UART0` など) は ArgumentError "unknown unit"。開いた後の呼び出しで、自分が開いていない番号は
RuntimeError (生成のつなぎの "read failed: -1")。閉じた後は IOError "closed"。

## 2. シリアルターミナル (U2)

1 段目に番号 (`unit_mask` から)・TX・RX (ステッパー、-1 は無し)・Open/Close、2 段目に速さ (9600〜115200)・行末 (LF・CRLF・無し)、
その下に状態の 1 行、受信の行、下に打つ欄と「送る」。開いている間は番号とピンを変えられない (速さは setmode で変わる)。
1 回の `on_update` で読むのは 1024 バイトまで (50 ms ごとで 20 KB/s、115200 ボーより速い)、残す行は 60、描くのは見える行だけ。
`"\n"` で行を分け、`"\r"` は飛ばし、表示できないバイトと壊れた UTF-8 は `.`、読みの切れ目で切れた UTF-8 の 1 文字は次へ持ち越す。
長い行は桁で折り返す。送った行は `> ` を付けて色を変えて出す。捨てたバイトがあれば状態の行に数を出す。
選んだ物は `app_settings` (`/home/serial_terminal.toml`) に残す。Retro の 320x240 で 316x210 の Window。

## 3. 確認の結果

- `rake test` の新しい組 `app_uart:test`: 95 checks 通過。`rake regress`: host 39 suites・310 runs 全部通過 (U1 の後と U2 の後の 2 回)。
  描画の記録の基準の変化は無し。`rake sig:coverage`: doc gaps 全部 0、アプリが使って sig に無いクラスは増えていない
  (`IOError` を足した)。`rake ti:test`・`rake ti:site:test`・`ruby tools/boundary/gen.rb --check` 通過。
- ビルド: `rake clean` → `rake build:linux` (Retro・Modern)、`rake native:mruby` → `native:core` が通った。ブラウザ版
  (wasm) は作っていない (ネイティブ版と同じ `FMRB_PLATFORM_HOSTED` の道を通る)。
- sim (Retro) の試しのアプリ (残していない) で: ループバックの `puts`・`write`・`putc` (整数・かな) と `gets`、5000 バイトを
  書くと箱 4096 が一杯で `dropped` 904、`read(300)`・`readpartial`・`ungetbyte`・`break`・`setmode`、UART0 の断り
  ("UART0 is used by the system")・ピン 43 の断り・番号 7 の ArgumentError、開き直し、`close` 後の IOError、すべて期待どおり。
  2 つ目のアプリが同じ番号を開くと "UART2 is in use by another app"。kill した後に別のアプリが同じ番号を開けた。
- sim (Retro) のターミナル: ループバックで打った行が戻る。FIFO を置いて外から ASCII・かな・150 字の行 (折り返し)・1 KB
  (16 行) と制御バイト・壊れた UTF-8 (`.` で出る) が出た。送った行が `uart2_out.fifo` に出た (`to the fifo\n`)。
  2 つ目のターミナルからの Open は "UART2 is in use by another app"、TX 43 は "TX pin 43 is used by the system"。
  Close ボタンで閉じた後に開き直せた。Window の閉じるボタンでも閉じた (ログ "UART2 closed")。
- sim (Modern 426x240): 同じアプリが開き、FIFO の送り受け (かな) が出た。ネイティブ版: "No UART in this environment"。
- 画面 (リポジトリの外の作業用の場所 `scratchpad/shots/`): u1_second_app_refused・u2_retro_loopback・u2_retro_fifo_text・
  u2_retro_fifo_1kb・u2_retro_burst_dropped・u2_retro_second_app_refused・u2_modern_fifo・u2_native_no_uart。
  TX 43 の断りの画面は目で見たが保存していない。

## 4. 測った数

- 内蔵 RAM の静的な増分: **0**。足した大域の変数は `fmrb_boundary_uart.c` の 2 つ (`s_slots` 5 枠 約 180 B、`s_lock` 4 B) で、
  どちらも `FMRB_EXT_RAM_BSS_ATTR` (PSRAM)。ピンの台帳・HAL (ESP32) に大域の変数は足していない (番号の表はマクロの定数)。
  Spinel の構成でだけ、生成のアダプタが `read`・`read_line` 用の 256 B の箱 2 つを PSRAM に持つ。
- 開いている間だけ使う物: ドライバの受信 1 KB・送信 1 KB (内蔵 RAM、ドライバが取る)、リング (PSRAM のシステムのプール、
  既定 4 KB)、最初に UART を開いたときに mutex 1 つ (内蔵 RAM のヒープ、以後そのまま)。
- 境界: 関数 142 → 157 (+15)、ABI のハッシュ `0eaa155d` → `6c83d35f`。
- 手で書いた分 (C・Ruby・sig・試験・アプリ): 約 2,300 行 (見積もりは 1,400 行。sig の長文と試験が大きい)。

## 5. 見立てと違った点・撤回した仮説

| 見立て | 実際 | したこと |
|---|---|---|
| 同じアプリの開き直しは「先に閉じてから開く」で足りる | 開き直しが断られても前の物が閉じてしまう (試しのアプリで見つけた) | 新しい方が判定を通ってから前の物を閉じる形に直した |
| 開き直した後の前の `UART` は使えなくなる | 同じ番号・同じ持ち主なので、前の物の呼び出しは新しい物に効く | 直していない (区別するには世代の番号が要る)。残件 |
| sim の FIFO で大きな塊を流しても落ちない | 汲み上げはドライバ (FIFO) にある分を全部読み、箱に入らない分を捨てる。30 KB を一度に書くと 24,880 B 捨てた | 仕様どおり (4 章 7)。実機は線の速さが上限で、ターミナルは 20 KB/s で読むので 115200 では落ちない見込み。U3 で確かめる |
| 結果がバイト列の関数は生成の規則 (全体の長さを返す) にそのまま乗る | 受信は読むと消えるので、つなぎが 2 回呼ぶ間にずれる | 「箱が小さいときは取らずに長さを返し、次の呼び出しでその長さだけ取る」形にした (1.1) |

## 6. 仮に決めた所 (親が戻せる)

- ネイティブ版も UART 無し (計画は「sim は偽物、ブラウザ版は使えない」だけ。偽物は sim にだけ置く方針に合わせた)。
- この環境に無いときの例外は IOError (hw_resources の未確定「例外の種類」。NotImplementedError にもできる)。
- `rx_buffer_size` の誤りは ArgumentError (上流は IOError)。`FmrbUart.unit_mask` を足した。
- sim は NARYA v3 の役 (Modern の sim でも UART2 だけ。ピン番号は 0〜48)。

## 7. 残件 (U3 の実機で見る事)

- ESP32 のビルド (S3・P4) が通るか (HAL の ESP-IDF の関数 `uart_set_line_inverse`・`uart_get_buffered_data_len` などは
  読んで書いただけ)、`regress:size` で内蔵 RAM が増えていないか。
- Tab5 の Grove (G53・G54) と P4-Nano で、115200・9600 の送り受け、1 KB を続けて受けて `dropped` が 0 のまま、`break` の長さ、
  `flush`、閉じる・アプリを kill した後に開き直せる、システムのピンの断り、MIDI の serial 出力との両方向の断り。
- P4-Nano で使うピン (計画 7 章の 4)。ターミナルの既定のピンは `FmrbHw::PIN_I2C2_SDA/SCL` (P4-Nano は無いので -1)。
- 開き直した後の前の `UART` オブジェクトの扱い (5 章)。
- ブラウザ版のビルドと画面 ("No UART in this environment")。
