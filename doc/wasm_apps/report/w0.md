# W0: 机上の調査 (2026-11-14)

手元のコードと、WAMR の main (2026-11-06 時点) のソース・公式の文書を読んだ結果。
何も作っていない。数字のうち自分で測ったものは無く、WAMR 側の数字は上流の公表値である。

## 1. 手元のコードで分かったこと

### 1.1 wasm の import の土台は既にある

Spinel 用の C の関数表 (`fmrb_spx_*`、`main/app/fmrb_spx_app.c`・`fmrb_spx_gfx.c`・
`main/kernel/fmrb_spx_common.c`、宣言は `main/prebuild_scripts/spinel/fmrb_app_ffi.rb`) が
約 115 個ある。引数は整数と「文字列 + 長さ」だけで、構造を持つ値 (イベント、一覧) は固定の
並びのバイト列で渡す。箱に入った値を渡さない作りなので、wasm の import にほぼそのまま写せる。

内訳 (概数):

| 分類 | 個数 | wasm のアプリに渡すか |
|---|---|---|
| 描画 (点・線・四角・円・角丸・楕円・三角・弧、塗りと合成) | 17 | 渡す |
| 文字 (フォント・大きさ・`draw_text`) | 3 | 渡す |
| 画面 (`present`、テーマの色) | 2 | 渡す |
| 画像・マスク・タイル・スプライト | 16 | 渡す |
| アプリ (メッセージの送信、キャンバス、Window の設定、当たりの申告) | 8 | 渡す |
| 時刻・ログ・時計・言語 | 5 | 渡す |
| クリップボード・設定の読み取り・音符の送信 | 6 | 渡す |
| システム専用 (再起動・電源・WiFi・BLE・音量・USB・プロセスの一覧・プールの情報) | 約 40 | 渡さない |
| 映像の出力の調整、動画、ファイルの同期 | 約 10 | 最初の版では渡さない |

渡すのは 55〜60 個。ファイルの読み書きはこの表に無く、別に設計が要る。

### 1.2 rbs に書かれた API の大半は Ruby で実装されている

`sig/fmrb_*.rbs` の 410 メソッドのうち、同名の C の定義があるのは約 90 個 (名前の一致で
数えた概算)。

| ファイル | メソッド | 同名の C の定義 |
|---|---|---|
| fmrb_app | 106 | 43 |
| fmrb_gfx | 56 | 24 |
| fmrb_ui | 59 | 4 |
| fmrb_midi | 59 | 6 |
| fmrb_p5 | 42 | 2 |
| fmrb_sprite | 30 | 4 |
| fmrb_tile | 27 | 1 |
| fmrb_audio | 20 | 2 |
| fmrb_misc | 11 | 4 |

FmrbUI の部品・P5・タイルマップ・MIDI と SMF のプレーヤ・FmrbApp の基底の多くは mrblib の
Ruby で、rbs から bindings を生成しても wasm からは呼ぶ先が無い。
**Ruby 以外のアプリは機能が絞られてよい (2026-11-14 ユーザ)** ので、API は C で実装された
範囲に限る。

### 1.3 rbs は生成に使いやすいが、実際の API とずれている

- オーバーロード・ブロック・union は 0 件。型はほぼ Integer (431) と String (77)。
- エディタの型支援のために簡略にしてある: `publish` にデータの引数が無い、`draw_text` の
  キーワード引数が無い、`on_event` の引数が `Hash` のまま (中の形が書かれていない)。
- 生成の元にするなら、範囲の印と、イベントの形の定義を足す必要がある。

### 1.4 Window の枠と一生の処理はエンジンごとに別々にある

| エンジン | 枠と一生の処理 |
|---|---|
| mruby | `lib/add/picoruby-fmrb-app/mrblib/fmrb-app.rb` (1358 行) |
| Spinel | `main/prebuild_scripts/spinel/fmrb_app_base_spinel.rb` の FmrbApp (1642 行) |
| MicroPython | `components/micropython/prelude/` (Python) |
| Lua | 無い。アプリが枠を自分で描いている (`flash/app/lua/lua.app.lua`) |

mruby と Spinel の FmrbApp は共通のメソッドが 77 個あり、うち 41 個はコメントを除くと同じ。
FmrbHitMask は差が 0 行。差は「C の呼び出し方」(`_spin`・メッセージの解析) と mruby だけの機能
(checkpoint・設定の保存) に集まっている。

Ruby の 2 つを 1 つにしても wasm からは使えない。wasm のためには、枠と一生の処理を本体の C に
置く必要がある (方針は plan.md)。

### 1.5 アプリの種類を足す場所

`fmrb_vm_type_t` (`components/fmrb_common/include/fmrb_app.h`) に Lua・BASIC・MicroPython が
並んでおり、`main/app/fmrb_app.c` の `switch` (5 か所) に 1 種類足す形になる。

### 1.6 同じ仕事をする C のつなぎがエンジンごとにある

`fill_rect` 1 つを取っても、つなぎが 4 か所に手で書かれている。

| エンジン | 場所 | 形 |
|---|---|---|
| mruby | gem の `gfx.c` | mruby の値を取り出して描画の命令を作る |
| Spinel | `main/app/fmrb_spx_gfx.c` | 整数だけの平らな関数 |
| MicroPython | `components/micropython/modules/fmrb_bridge.c`・`fmrb_module.c` と Python の prelude | 整数だけの平らな関数を Python の関数で包み、さらに Python のクラスで包む (関数は 46 個) |
| Lua | `components/lua/extension/fmrb_lua_gfx.c` | Lua の値を取り出して描画の命令を直接作る (12 個だけ) |

平らな関数の表が Spinel 用と MicroPython 用に 2 組あり、中身はほぼ同じ。Lua と MicroPython の
つなぎはどちらも「引数を取り出す・呼ぶ・登録の表に載せる」の定型で、型定義から機械的に書ける。
MicroPython のモジュールのソースは、ビルドの途中で本体のヘッダを読めない状態で処理されるので、
今も「整数とポインタだけのヘッダ」を間に挟んでいる。生成するヘッダはその形になる。

**決定 (ユーザ)**: Lua・MicroPython のつなぎと Spinel の宣言も、同じ型定義から生成する
(plan.md)。mruby の gem のつなぎは手書きのまま残す。

### 1.7 mruby も Spinel も、既に「Ruby の包み + 単純な関数」の 2 段になっている

mruby 用の `draw_text` は C のメソッドではなく、mrblib の Ruby のメソッドで、その下で
`_draw_text`・`_draw_text_hybrid` という C のメソッドを呼んでいる。FmrbGfx の mrblib には Ruby の
メソッドが 44 個あり、26 か所で `_` で始まる C のメソッドを呼ぶ。`fill_rect`・`present` などの
単純なものは C のメソッドが直接公開されている。Spinel の基底も同じ形 (Ruby のメソッドが平らな
関数を呼ぶ)。

- 境界の関数に当たるものは既にあり、内部用として隠れているだけ。「mruby だけが C の中で
  2 段を一度にやっている」という途中の見立ては誤りだった。
- 包みは状態を持っている。mruby・Spinel とも、選んだフォントと文字の大きさを Ruby の変数で
  覚えており (`@current_font` など)、枠の描画がそれを読んで描いた後に戻している。
- キーワード引数つきの呼び出しは、mruby では呼ぶたびに Hash を作る。`draw_image` と
  `draw_image_masked` はキーワード引数が必須。
- システム側の `draw_text` の呼び出しは、カーネルとデスクトップに 211 (うちキーワード引数つき
  96)、標準アプリに 140 (同 18)、ライブラリに 11 (同 4)。

どれだけ速くなるかは測っていない。描画の命令をグラフィックス側へ送る費用のほうが大きければ、
呼び出し 1 段の差は見えにくい。Hash の確保が無くなる効果は、GC の頻度と VM のプールの使用量に
出るはず。

**決定 (ユーザ)**: 境界の関数は Ruby のアプリからも呼んでよい。システム側と Ruby で書かれた
ライブラリは境界の関数を呼ぶ (plan.md)。

## 2. WAMR について分かったこと

### 2.1 版と ESP32 の対応

- 最新のリリースは 2.4.5 (2026-06)。中身は脆弱性の修正だけ。
- ESP-IDF のコンポーネントとして配られている版は 2.4.0 (2025-08) で止まっており、上の修正が
  入っていない。P4 は対象に入っている (RISC-V 32 ビット、`RISCV32_ILP32F`)。
- 上流の支援の段は、ESP-IDF が 2 番目、ESP の RISC-V のツールチェーンは最下位 (実験的)。
  脆弱性として扱うのは最上位の段だけ。
- 未修正の報告: ESP32 の `os_realloc` がブロックを移すときにデータを 4 バイトずらす、
  IDF 6.1 と GCC 15 でビルドできない (P4 で再現)。

**見立て**: 配られているコンポーネントは使わず、ソースを版を固定して取り込み、土台の層
(メモリ・時刻・ミューテックスなど) を `fmrb_hal` の上に自分で書く。ブラウザ版のためにどのみち
自作が要る (2.6) ので、3 つの環境で同じ 1 つにできる。

### 2.2 インタプリタ

- fast は classic の約 2 倍速く、事前に変換したコードを持つので約 2 倍のメモリを使う (上流の
  説明)。古い実測では x86-64 で 2.1〜2.5 倍、Cortex-M7 で 1.3〜2.0 倍。
- コードの大きさ (Cortex-M4 での公表値): fast 約 59 KB、classic 約 56 KB。RISC-V の数字は無い。
- classic は wasm のバイナリを**書き換えながら**使う。読み込みの間も動いている間も、書ける
  メモリに置いたままにする必要がある。flash から直接は動かせない。
- fast は読み込みの後でバイナリを解放できる。
- ここ 2 年の脆弱性は fast の読み込み部に偏っている。

**見立て**: classic から始める。バイナリの写しは PSRAM に置く。

### 2.3 メモリ

- 確保の方法 (固定のプール・自前の関数・システムの関数) は**ランタイム全体で 1 つ**。
  インスタンスごとには分けられない。
- wasm のメモリ (linear memory) は既定では別の経路 (`os_mmap`) で取る。設定
  (`WAMR_BUILD_ALLOC_WITH_USAGE`) を入れると、同じ自前の関数を「wasm のメモリ用」という印つきで
  通るので、PSRAM へ向けられる。
- ESP-IDF 用の既定の `os_mmap` は、P4 では PSRAM を指定しないように読める (条件の分岐までは
  確認していない)。土台の層を自作すればこの問題は消える。
- 演算のスタックは実行環境を作るときに大きさを渡す (既定 12 KB)。アプリ用のヒープは
  インスタンスを作るときに渡す (既定 8 KB、アプリが自分の `malloc` を持っていれば使われない)。
- ページは 64 KiB。小さいページの提案は入っていない。メモリを伸ばさないアプリは、実際に
  使う所まで切り詰める機能 (既定で有効) がある。
- 境界の検査をソフトで行う構成 (32 ビットと ESP-IDF は常にこれ) で、境界の切り上げに関する
  未修正の報告がある。切り詰めたメモリで実際に踏むかは未確認。

**見立て**: 計画書の「アプリごとのプール」はそのままでは作れない。確保先は全体で 1 つ
(PSRAM)、アプリごとの上限は wasm のメモリの最大ページ数とスタックの大きさで縛る。

追って確認したこと (同日):

- ランタイムは 1 つのプロセスに 1 つだけ。確保の方式と関数・本体の関数の登録表・読み込んだ
  モジュールの一覧がすべてファイル内の static 変数で、初期化は回数を数えるだけ (2 回目に渡した
  設定は使われない)。ランタイムを複数動かしてアプリごとに確保先を分ける方法は取れない。
- その上で、モジュール・インスタンス・実行環境は何個でも持てる。アプリ 1 つがインスタンス 1 つと
  タスク 1 つに当たる。同じアプリの多重起動は、1 つのモジュールからインスタンスを複数作る。
- 固定のプール方式では、起動時に渡した領域の中だけで確保する。使用量 (全体・空き・最大) を
  読む API がある。インスタンスを作るときに、演算のスタックの大きさと wasm のメモリの
  最大ページ数を渡せる。
- プール方式でも、wasm のメモリだけはメモリの写像の関数 (土台の層) を通る。自分で書く部分
  なので、置き場所は選べる。

**決定 (ユーザ)**: 固定のプール方式にする (plan.md)。確保の関数を自作してタスクごとに
振り分ける案は採らない。

### 2.4 複数のアプリ

- インスタンスごとに別のスレッドで動かせる。実行環境をスレッド間で共有しない、自分で作った
  スレッドは始めと終わりに決まった関数を呼ぶ、という決まりがある。
- 共有されるのは全体のヒープ (中で排他している)・本体の関数の登録表・モジュール。

### 2.5 暴走の止め方とスタック

- 外から止める API (`wasm_runtime_terminate`) は例外の印を立てるだけで、インタプリタが分岐の
  たびに印を見る処理は、スレッド管理の機能を有効にしたときだけ入る。無しでは密なループを
  止められない (ソースで確認、実験はしていない)。
- 命令の数を数えて上限で止める機能 (`WAMR_BUILD_INSTRUCTION_METERING`) がインタプリタで使える。
  止めた後に続きから再開できるかは未確認。
- 本体のスタックの溢れの検査は、ESP-IDF では FreeRTOS の設定によって境界が取れず、
  **黙って無効になる**。境界を手で設定する API がある。

**見立て**: 本体がアプリの関数を呼ぶたびに命令数の上限を渡し、超えたら理由つきで止める。
スタックの境界は手で設定する。

### 2.6 WAMR を emscripten でビルドする (ブラウザ版)

- 上流に対応が無い。土台の層に emscripten 用が無く、ビルドの対象にも無い。
- 対応を足す変更が上流に出ているが、1 年ほど取り込まれていない。
- 最大の障害は、本体の関数をアプリから呼ぶ仕組み (引数の型を見て呼び分ける部分)。wasm は
  関数の型に厳密なので、この仕組みは wasm の上では成り立たない、と上流で言われている。
- 回避の見込み: 本体の関数を「引数を配列で受ける固定の型」で登録する形 (raw) は、この仕組みを
  通らない。3 つの環境とも raw で揃えれば足りる見込み。**動くと確認できていない**。
- 土台の層として要る関数は少ない (メモリの確保と解放、出力、時刻、自分のスレッド、スタックの
  境界、ミューテックス、メモリの写像)。

**見立て**: 計画の最大のリスク。最初の試作で sim と同時に試す。C のつなぎは rbs から生成する
ので、生成器が raw の形を出せばよい。

### 2.7 本体の関数とアプリの関数

- 本体の関数は読み込みの前に表で登録する。バッファと文字列は、境界を検査して本体の番地へ
  変換する指定ができる。アプリがメモリを伸ばすと本体の番地は無効になる。
- アプリが公開した関数は名前で探して何度でも呼べる。1 回の費用の公表値は無い。

### 2.8 各言語の出力

| 言語 | 向いている対象 | 既定で使う wasm の機能 | 注意 |
|---|---|---|---|
| TinyGo 0.44 | `wasm-unknown` | 古い機能に近い (符号拡張・飽和する変換だけ追加) | **解放しない GC が既定**。本体が `_initialize` を 1 回呼び、その後は公開した関数を何度でも呼べる |
| Rust | `wasm32-unknown-unknown`、または古い機能だけの `wasm32v1-none` | 1.82 以降は参照型・多値、1.87 以降はメモリの一括操作も | 1.82 以降の既定の出力は、WAMR の既定の設定では読めない (間接呼び出しの表の番号の符号化が変わる)。`WAMR_BUILD_CALL_INDIRECT_OVERLONG` が要る |
| Zig 0.15 | `wasm32-freestanding` | `lime1` という機能の組 (拡張された定数式を含む) | WAMR に同じ名前の設定がある |

WAMR のインタプリタは、多値・符号拡張・飽和する変換・書けるグローバルは常に有効、メモリの
一括操作は既定で有効、参照型と拡張された定数式は設定が要る。SIMD は classic では使えない。

**見立て**: WAMR のビルド設定と、各言語の SDK のコンパイル指定を 1 つの組に固定する。合わない
アプリはインストールのときに理由つきで断る。TinyGo の GC を替えられるかは最初の試作で見る。

### 2.9 checkpoint

- 上流には無い。試みの変更は止まっている。別の派生の実装が研究として続いている。
- アプリが動いていないとき (本体からの呼び出しの合間) に取るなら、wasm のメモリ・書ける
  グローバル・表を写せば原理的には足りる (推測)。
- メモリと、公開されたグローバルは API で読み書きできる。公開されていないグローバル (各言語の
  スタックの位置など) を読む API は無い。内部の構造に触るか、言語の側で公開する必要がある。

**見立て**: 本体がループを回す形にしておけば、呼び出しの合間はスタックが空なので道は残る。
今は作らない。

### 2.10 ライセンスと安全

- Apache-2.0 (LLVM の例外つき)。
- wasm のバイナリは信頼しない前提で作られているが、無限ループは対象外。支援の段が最上位で
  ない環境 (ESP32) は、脆弱性としての扱いの外。

**見立て**: 「他人が作ったアプリを安全に配れる」は「アプリは自分のメモリと渡した関数にしか
触れない作りである」までに留める。
