# W2: P4 で wasm のアプリを測る (メモリ・上限・速さ) (2026-11-16)

> 親: plan.md の段 W2 と決定 25 | 2026-11-16 22:24〜22:55 (`date`) |
> 端末 P4-Nano (NARYAv4、`board":"naryav4"`、cpu 400 MHz・PSRAM 200 MHz)、develop の開発のビルド (親が app_sync で焼いた)。
> ファームウェアのコードは変えていない。計測の道具とアプリは `flash/app/test/` (下の 1 章)。

## 0. まとめ

- **アプリ 1 つの重さ (wasm)**: 共通のプールが 20〜29 KB (うち 16 KB は演算のスタック)、アプリの枠 (PSRAM 1 MB) の
  中で wasm のメモリ 1〜2 ページ (64〜128 KB) + バイナリの写し (1〜29 KB)、**内蔵 RAM が 25.1 KB** (タスクのスタック
  24 KB + 管理)。タスクのスタックの最大の使用は **6.6 KB** (tour の 10 ページを全部めくったとき)。
- **Ruby (mruby) のアプリ** (同じ hello を Ruby で、と kamon): VM プール 325〜366 KB (ピーク 336〜428 KB) / 1 MB、
  内蔵 RAM 16.8 KB (タスクのスタック 16 KB)、スタックの最大の使用 9.1 KB。**wasm の方が PSRAM は 1/3 以下、
  内蔵 RAM は +8 KB 多い** (スタックの既定が 24 KB のため。使っているのは 1/4)。
- **同時に動く数の上限は、共通のプールではなくアプリの枠 (4 つ)**。tour を 4 言語そろえて動かしても共通のプールは
  109 KB / 256 KB。5 つ目は `No free context slots available` (err -9) で断られる。
- **共通のプールを食うのはバイナリの大きさより関数の数**。小さな関数 1,000 個の 44.8 KB のアプリで 146 KB
  (関数 1 つあたり約 120 B)、tour (24〜29 KB) は 25〜29 KB。4,000 個 (183 KB) は 1 つでも入らず、
  `WASM module load failed: allocate memory failed` で**きれいに断られる** (ほかのアプリは動き続け、後から小さな
  アプリは入る)。ただし文言からはプールが足りないと分からない。
- **命令数の上限 2,000 万は P4 で約 3.5 秒** (1 命令 約 175 ns)。暴走したアプリが止められるまで、その間アプリの
  タスクが回り続ける。tour の全ページは上限のはるか下 (フックの最大は 0.63〜0.74 秒だが、ほぼ全部がファイルの
  境界の関数の時間)。
- **演算のスタック 16 KB で、再帰は 100 段は通り 200 段で止まる** (`wasm operand stack overflow`)。きれいに止まるが、
  浅い。
- **速さ (P4)**: 整数のループ 10 万回が **wasm 約 0.2 秒 (4 言語でほぼ同じ)、Ruby 約 1.5 秒 (約 7 倍遅い)**。
  境界の関数の呼び出しは wasm 3.4 µs / 回、Ruby 6.0 µs / 回。描画 (fill_rect・draw_text) は 1 回 80〜160 µs で
  言語にほぼよらない (本体の描画の経路が大半)。

## 1. 方法

### 1.1 アプリ

| 置き場 | 中身 |
|---|---|
| `flash/app/test/w2bench_src/{c,go,rust,zig}/` | 速さの試験の元 (同じ処理を 4 言語で)。`c/gen_big.rb` は関数を N 個持つ C のアプリを生成する。`c/w2b_spin.c` (終わらないループ)・`c/w2b_deep.c` (再帰を 25・50・100…段と深くする) |
| `flash/app/test/w2b_{c,go,rs,zig}.app.wasm` | 速さの試験 (上の元を SDK の手順でビルドしたもの。Go・Rust・Zig は SDK の checkout の写しの examples に置いて `*/build.rb` で、C は `zig cc` を `c/build.rb` と同じ指定で) |
| `flash/app/test/w2b_rb.app.rb` | 同じ速さの試験の Ruby 版 (mruby のアプリ) |
| `flash/app/test/w2b_hello.app.rb` | SDK の hello を Ruby で書いたもの (メモリの比較用) |
| `flash/app/test/w2b_big1000.app.wasm` | 関数 1,000 個 (44,781 B) の C のアプリ (共通のプールの端)。4,000 個 (183,066 B) の `w2b_big4000` は大きいのでリポジトリに入れていない (`ruby c/gen_big.rb 4000` で作り、`w2b_c` と同じ指定でビルドする) |
| `flash/app/test/w2b_spin.app.wasm`・`w2b_deep.app.wasm` | 命令数の上限・演算のスタックの端 |
| `flash/app/test/w2b_probe.app.rb` | シリアルのログが途中で止まったときの予備 (1 秒ごとに内蔵 RAM・wasm の統計を `/tmp/w2p.txt` へ)。結局使わなかった |

速さの試験は、`on_update` 1 回で 1 種類を測り (`FmrbApp.uptime_us` / `app_uptime_us` の差)、4 種類を 3 巡して
自分で止まる。結果は `W2B <言語> <種類> n=<回数> us=<µs> sum=<検算>` をログと `/tmp/w2b.txt` に出す。

| 種類 | 処理 | 回数 |
|---|---|---|
| int | `s = ((s * 31 + i) ^ (s >> 3)) & 0xFFFFF` (32 ビット、全言語で sum=783728 で一致) | 10 万 |
| fill | `fill_rect` 8x8 (present は計時の外) | 200 |
| text | `draw_text` 10 文字 (透明の背景、present は計時の外) | 100 |
| call | `area_width` (何もしない境界の関数) | 1,000 |

### 1.2 測り方

- 端末に `ruby tools/fmrb_rd_fs.rb <IP> tests push w2b_...` で送り、`POST /app/launch` で起動し、21 秒 (10 秒ごとの
  ダンプが 2 回入る) 置いて `POST /app/kill`。その間のシリアルのログ (MCP の capture、`~/.fmrb_mcp/current.log`) を
  切り出して読む (道具は scratchpad の `w2run.rb`・`parse.rb`・`tourpages.sh`。リポジトリには入れていない)。
- 読んだ行: 起動前の `internal RAM ok: free=` と `M1|spawn:<名前>|internal=` の差 (内蔵 RAM)、
  `wasm: [<名前>] loaded ... shared pool used N` (共通のプール。ランタイムの土台 2,400 B を含む)、
  `fmrb_task: <名前> ... Stack Free` (スタック)、`fmrb_wasm:   pid=...` (ページ数・フックの時間)、
  `fmrb_app: <名前> mrb Used Free Total Peak` (Ruby の VM プール)。
- tour は起動後に `tools/fmrb_rd_input.rb` で `2 3 4 5 6 7 8 9 0 1` を 1.5 秒おきに押し、全ページを通した
  (Sound のページでは音を出すキーは押していない)。
- 途中 22:35〜22:40 にシリアルの capture が止まり (USB の切断、親が付け直した)、端末が 1 回起動し直した。
  表の数字はすべて付け直した後 (22:40 以降) に測り直したもの。

| Rust tour | 25,389 B | 25.0 KB | 1 ページ | 25,112 B | 5,048 (全ページで 6,568) | 6.7 ms |
| Zig hello | 2,828 B | 21.1 KB | 1 ページ | 25,112 B | 4,916 | 13.6 ms |
| Zig tour | 24,162 B | 26.6 KB | 1 ページ | 25,112 B | 5,048 (全ページで 6,600) | 3.4 ms |

| Ruby のアプリ (mruby) | VM プール 使用 / ピーク / 枠 | 内蔵 RAM | タスクのスタック |
|---|---|---|---|
| Ruby hello (`w2b_hello`、上の hello と同じ画面) | 325,376 / 336,352 / 1,048,576 | 16,832 B | 7,328 残り / 16,384 (使用 9,056) |
| kamon (`/app/demo/kamon.app.rb`) | 365,808 / 428,152 / 1,048,576 | 16,844 B | 使用 9,056 / 16,384 |

- wasm のアプリも Ruby のアプリも PSRAM の枠 (1 MB) を 1 つ取る。wasm はその中で wasm のメモリとバイナリの写しの
  ほかは使わないので、枠の大半 (約 900 KB) が空いたままになる (最大ページ数 14 = 枠の空きから 64 KB を引いた分)。
- 内蔵 RAM の差はタスクのスタックの大きさの差 (24 KB と 16 KB) そのもの。WAMR の側に内蔵 RAM の増分は無い
  (`IRAM free:` は起動前の値に戻る)。
- 「native stack room」は 17,196 B (24 KB のスタックから境界の余裕 6 KB を引いた残りのうち、読み込みの時点で
  空いている分)。実際の最大の使用 6.6 KB は、その中に十分に収まる。
- hello のフックが 13〜38 ms と tour (3〜7 ms) より長いのは、毎回 Window の区画全体を `fill_rect` で塗って
  present するため (描画の待ちで、wasm の命令の時間ではない)。

### 2.1 組み合わせ

| 組み合わせ | 共通のプール | 内蔵 RAM の空き (`IRAM free:`) | 結果 |
|---|---|---|---|
| なし (デスクトップだけ) | 0 (ランタイムは止まっている) | 約 202 KB | |
| tour 4 言語 (C・TinyGo・Rust・Zig) | 109,440 B (4 つで 107 KB) | 約 99 KB | 4 つとも動く。5〜7 つ目 (hello) は `fmrb_app: No free context slots available for app_type=2` で断られる (`/app/launch` の答えは `{"ok":false,"err":-9}`) |
| big1000 + C tour + big1000 + Zig hello | 146,080 → 171,264 → (断る) → 192,848 | | 2 つ目の big1000 は `did not load: WASM module load failed: allocate memory failed`。ほかの 2 つは動き続け、その後の Zig hello は入る |
| big4000 (1 つだけ) | 端 (high mark 261,840 / 261,864) | | 同じ文言で断られる。ランタイムはすぐ終わる |

- アプリの枠の数 (この構成で 4 つ) が先に効く。tour の大きさの 4 つで共通のプールの 4 割ほど。
- 内蔵 RAM は wasm のアプリ 1 つで約 26 KB ずつ減り、4 つで約 100 KB 減った (最大の塊は 143 KB → 45 KB)。
- 共通のプールの使用はほぼ「16 KB (演算のスタック) + 4〜6 KB (インスタンス・exec env) + モジュールの解析結果」。
  解析結果は関数の数に比例し (1,000 個で約 120 KB)、バイト数とは比例しない (tour は 24 KB のバイナリで 9〜12 KB)。

## 3. 上限とその既定値

| 値 | 置き場 | 今の値 | 測った結果 |
|---|---|---|---|
| 共通のプール | `components/fmrb_wamr/fmrb_wasm.c` `FMRB_WASM_POOL_SIZE` | 256 KB (最初の wasm のアプリで PSRAM から取る) | tour 4 つで 107 KB。枠の数の上限 (4) までなら、関数が数百個のアプリは入る |
| 演算のスタック | 同 `FMRB_WASM_OPERAND_STACK` | 16 KB / アプリ (共通のプールから) | 再帰 100 段は通り 200 段で `wasm operand stack overflow` (小さな関数で 1 段 80〜160 B) |
| 1 回の呼び出しの命令数 | 同 `FMRB_WASM_CALL_INSN_LIMIT` | 2,000 万 | P4 で 3.48 秒 (`W2B spin go` 22:47:13.947 → `instruction limit exceeded` 22:47:17.427)。ネイティブ版 (x86) では 29 ms |
| 本体のスタックの余裕 | 同 `FMRB_WASM_NATIVE_STACK_GUARD` | 6 KB | 余裕を除いて 17 KB 空き、使用の最大 6.6 KB |
| アプリのタスクのスタック | `components/fmrb_wamr/include/fmrb_wasm.h` `FMRB_WASM_APP_TASK_STACK_SIZE` (`.app.toml` の `task_stack_kb` が勝つ、下限 16 KB) | 24 KB (内蔵 RAM) | 使用の最大 6.6 KB (tour 全ページ) |
| wasm のメモリの最大 | 同 `fmrb_wasm.c` (枠の空き − `FMRB_WASM_POOL_MARGIN` 64 KB) | P4 で 14 ページ (896 KB) | 使っていたのは 1〜2 ページ |
| アプリの数 | `max_apps` (system_conf) / `FMRB_MAX_APPS` | ユーザのアプリ 4 つ | 5 つ目は err -9 |

- tour は 10 ページ全部で、トラップ 0、命令数の上限に届かない。フックの最大 0.63〜0.74 秒は Image〜Files の
  ページ (ファイルの写し・書き込み) の 1 回で、時間は境界の関数 (ファイル) の中。
- 命令数で止めたときの文言 (`on_update stopped: Exception: instruction limit exceeded`)・スタックの文言
  (`wasm operand stack overflow`)・プールの文言 (`allocate memory failed`) は、どれもログと spx の終了の理由に出る。

## 4. 速さ

P4 (400 MHz)、1 つだけ動かし、3 巡の中央値。括弧は 1 回あたり。

| 言語 | int 10 万回 | fill 200 回 | text 100 回 | call 1,000 回 |
|---|---|---|---|---|
| C | 206 ms (2.06 µs) | 15.9 ms (80 µs) | 16.1 ms (161 µs) | 3.38 ms (3.4 µs) |
| TinyGo | 249 ms (2.49 µs) | 16.2 ms (81 µs) | 16.4 ms (164 µs) | 3.58 ms (3.6 µs) |
| Rust | 202 ms (2.02 µs) | 15.9 ms (79 µs) | 3.5 ms (35 µs) ※ | 3.44 ms (3.4 µs) |
| Zig | 212 ms (2.12 µs) | 16.0 ms (80 µs) | 16.3 ms (163 µs) | 3.65 ms (3.7 µs) |
| Ruby (mruby) | 1,494 ms (14.9 µs) | 21.7 ms (108 µs) | 44.5 ms (445 µs) | 6.05 ms (6.0 µs) |

- ※ Rust の text は 3 巡で 22.4・3.4・3.5 ms とばらついた。境界の関数は 4 言語とも同じ (`gfx_draw_text_raw`、
  同じ引数) なので、言語の差ではなく、描画の命令の送り先の詰まり具合の差と見る (理由は追っていない)。
- 整数の計算は wasm が Ruby より約 7 倍速い。4 言語の差は 2 割以内 (TinyGo がやや遅い)。
- 境界の関数の呼び出しは wasm で 3.4 µs。ネイティブ版 (x86) では 30 ns なので、P4 では 100 倍。命令の速さ
  (int) の比もほぼ同じ (x86 で 1.8〜2.1 ms)。
- 描画は 1 回 80 µs (四角) 〜160 µs (10 文字) で言語によらない。本体の描画の経路が支配的で、wasm にしても
  描画は速くならない。Ruby は四角で +35%、文字で約 2.8 倍 (文字列の扱いの分)。
- 命令の速さ: 約 570 万命令 / 秒 (上限 2,000 万が 3.48 秒)。int の 1 回は約 11 命令。

## 5. 気付いたこと・意外だったこと

1. **同時の数を決めるのはアプリの枠**。256 KB の共通のプールは、枠の上限 (4) に対して余っている。
2. **共通のプールは関数の数で食われる**。`.app.wasm` のバイト数で縛ると、小さな関数が多いアプリ (Rust・C++ の
   ジェネリクス、TinyGo の大きなライブラリ) を見落とす。関数 1 つ約 120 B。
3. **内蔵 RAM はタスクのスタック 24 KB の分だけ増える**が、使っているのは 6.6 KB。Ruby のアプリ (16 KB で 9 KB 使用)
   より余らせている。
4. **命令数の上限 2,000 万は P4 で 3.5 秒**。「暴走の検知」としては長い (その間 Window は固まる)。ふつうのフックは
   1〜7 ms (= 1 万〜4 万命令ほど) なので、桁が 3 つ違う。
5. **演算のスタック 16 KB で再帰 100〜200 段**。木を再帰で歩くアプリ (JSON の入れ子など) では足りなくなりうる。
6. プールが足りないときの文言が `allocate memory failed` で、利用者にはプールの不足と分からない。
7. ネイティブ版 (x86) での同じ試験 (確認のため 1 回): int 1.8〜2.1 ms、call 30 ns、Ruby の int 6 ms。
   P4 との比は wasm で約 100 倍、Ruby で約 250 倍。

## 6. 提案 (未確定事項への仮の値。決めるのはユーザ)

| 未確定事項 | 提案 (仮) | 根拠 |
|---|---|---|
| WAMR の共通のプールの大きさ (機種別) | **P4: 256 KB のまま** (枠 4 つ × tour 級 28 KB = 112 KB に、大きめのアプリ 1 つ分の余裕)。ネイティブ版・ブラウザ版・sim は枠が多いなら枠の数に合わせて増やす (目安 `32 KB × 枠の数 + 128 KB`)。S3 (W1d) は枠が小さいので 128 KB を候補に、実機で測ってから | 2.1 章 |
| アプリごとのメモリの上限の既定値 | **wasm のメモリ 4 ページ (256 KB) を既定、上限は今の「枠の空きから」**。`.app.toml` に `wasm_memory_pages = N` (1〜枠の空き) を足し、全環境で同じページ数の既定にする (P4 の枠に合わせる、plan の推奨と同じ)。今のアプリは 1〜2 ページで、4 ページなら倍の余裕 | 2 章 |
| `.app.toml` での書き方 | `wasm_memory_pages` (上の既定を上書き)、`task_stack_kb` (今のまま) | |
| `.app.wasm` の大きさの上限 | **バイト数ではなく、読み込みのときの共通のプールの空きで判定** (今もそう動いている。文言を「共通のプールが足りない (N KB 要る / 空き M KB)」に直す)。バイト数で決めるなら目安 **64 KB** (関数の多いアプリで 256 KB の半分を食う所) | 2.1 章・5 章の 2 |
| 命令数の上限 | **500 万 (P4 で約 0.9 秒)** に下げる案。ふつうのフックの 100 倍以上の余裕があり、固まって見える時間を 1 秒未満にできる。機種で命令の速さが違うので、値は全機種で同じ (命令数で決め、時間では決めない) | 3 章・5 章の 4 |
| 演算のスタック | **16 KB のまま**、`.app.toml` で増やせるようにする案 (`wasm_stack_kb`)。再帰の深いアプリは自分で宣言する | 3 章・5 章の 5 |
| タスクのスタックの既定 | **16 KB に下げる案** (Ruby のアプリと同じ。使用 6.6 KB + 余裕 6 KB で 12.6 KB に収まる)。内蔵 RAM を 1 つあたり 8 KB 返せる (4 つで 32 KB)。境界の関数のうち深いもの (画像・ファイル・音) を全部通してから決める | 2 章・3 章 |
| 速さの目安 | **「整数の計算が Ruby の 5 倍以上、描画は Ruby と同じかそれ以上」を合格**とする案。今は 7 倍・描画は同等以上で満たしている | 4 章 |
| classic と fast | **classic のまま**。描画は本体の経路が支配的で、fast にしても描画のアプリは速くならない。計算の重いアプリが出てきたら、fast (約 2 倍速・メモリ約 2 倍) を共通のプールの増分と合わせて測る | 4 章 |
