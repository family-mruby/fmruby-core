## 1. フックとイベントの形

`components/fmrb_wamr/fmrb_wasm.c` の表を生成のヘッダ (`sdk/c/fmrb_boundary.h` の終わり) に合わせた。

| 殻のフック | export | 形 |
|---|---|---|
| LOAD | `_initialize` (あれば) | `() -> ()` |
| CREATE | `on_create` | `() -> ()` |
| UPDATE | `on_update` | `() -> i32` (次までの ms、負は既定 330) |
| EVENT | `on_event` | **`(const fmrb_app_event_t *ev) -> ()`** (i32 1 つ。前は i32 8 つ) |
| DESTROY・SUSPEND・RESUME・QUIT_REQUEST | 同名 | `() -> ()` |
| RESIZE | `on_resize` | `(new_width, new_height) -> ()` |

- **番号の読み替え**: 殻の `kind` (HID の番号) を `FMRB_BND_APP_EVENT_TYPE_*` (選択肢の番号 0〜9) に
  読み替える。並びと、種類ごとに埋める欄は Lua の `e_call_event` と同じ (key: keycode・scancode・
  modifier・character、mouse: button (押す・離すだけ)・x・y・wx・wy、wheel: さらに delta、
  gamepad: gamepad_id・button、axis: gamepad_id・axis・value、kana: mode)。ほかの欄は 0。
- **記録を置く場所**: アプリのスタックポインタ (モジュールが定義する最初の可変の i32 の大域変数。
  LLVM の `__stack_pointer` で、TinyGo・clang・zig・Rust はどれも持つ) の値の下、16 バイトに揃えた所に
  60 バイトを書き、呼び出しの間だけスタックポインタを下げ、呼んだ後に戻す。C の呼び手が局所変数の
  ポインタを渡すのと同じ。アプリに何も求めない (仕様は変えない)。
  - 選ばなかった形: `wasm_runtime_module_malloc` は、TinyGo (wasm-unknown) も zig (freestanding) も
    `malloc`・`__heap_base` を export しないので、WAMR のアプリ用ヒープを 1 ページ (64 KB) 足す形に
    なる。そのページは TinyGo のヒープが `memory.size` まで自分のものとして使うので壊し合う。
  - スタックポインタの大域変数は WAMR の公開 API では読めない (export されていない) ので、
    インタプリタの内部の構造 (`WASMModuleInstance` の `global_data`) を読む。WAMR の版を上げるときに
    見る所。
  - `on_event` を持つのにその大域変数が無いモジュールは、読み込みの時点で理由つきで断る。
- **型は生成のもの**: 本体の生成のヘッダ (`fmrb_gen/fmrb_boundary.h`) にフックの記録と選択肢の番号を
  出すようにした (`tools/boundary/templates/fmrb_boundary.h.erb`。`fmrb_bnd_app_event_t`、
  `FMRB_BND_APP_EVENT_TYPE_*`、60 バイトの `_Static_assert`)。写しは作っていない。ABI のハッシュは
  変わらない (`b7957f81`。記録はもともとハッシュに入っている)。
- **殻の上でだけ動く関数 (`ctx->shell`)**: どのフックも `fmrb_app_shell_run` の中から呼ばれるので、
  FmrbApp の Window の関数はどのフックからも動く。c_check が `fmrb_app_user_area_width/height` を
  毎フレーム読み (`area 138x68`)、`q` で `fmrb_app_stop()`、bounce も `q` で `App.Stop()` し、
  どちらも殻が終わらせた (`on_destroy` のログ → `wasm app ended`)。

**強制の kill**: 試しのアプリ (`kill_test`、scratchpad の `w1b2/kill_test/`、`h` で `on_event` の中から
present を呼び続ける。命令数が少ないので命令数の上限に届かない) を一時的に `flash/app/test/` に置いて
試し、終わってから消した。

- 直す前 (W1b のまま) は、kill がタスクを消すと `fmrb_wasm_app_run` の後片付けを通らず、利用者の数が
  戻らなかった (ランタイムと共通のプールが終わらない)。
- 直した形: `destroy_vm` の強制の道で `fmrb_wasm_app_forget(ctx)` を呼ぶ。利用者の数を戻し、最後の
  1 つならランタイムを終える (`wasm_runtime_destroy` が共通のプールを丸ごと捨て、次の起動で敷き直す)。
  **殺したタスクの物は kill する側から 1 つも free しない** (消されたタスクが共通のプールの割り当ての
  錠やアプリのプールの錠を持っていた恐れがあるため)。線形メモリとバイナリの写しはアプリのプールごと
  消え、モジュールとインスタンスはランタイムが終わるまで共通のプールに残る (2 つ目以降の wasm の
  アプリが動いている間、1 つにつき約 22〜26 KB)。
- ランタイムの錠 (`s_lock`) は起動と forget で 2 秒の時間切れつきで取る。起動か終わりの最中に
  強制で消されたタスクが錠を持ったままでも、次の起動は理由 (`the runtime's lock is held`) を出して
  断り、止まらない (この窓は起動と終わりの一瞬だけで、sim では起きていない)。
- ログ: `wasm: [kill_test] killed by force: its use of the runtime is given back (1 wasm app left)`、
  最後の 1 つの時は `runtime ended (pool high mark 26448 ...)` が先に出る。その後の起動で
  `runtime started` → 普通に動いた。

**気付いたこと (直していない)**:

- 強制の kill に 8 秒ほどかかり、`sim_app kill` (デバッグの道具) は応答待ちの時間切れになった
  (kill そのものは成功)。present を毎秒 4,500 回ほど出し続けるアプリが優先度 2 で回り、kill を進める
  側が sim の上で CPU を待つため。wasm に限らない (同じことをする Lua のアプリでも同じはず)。
  P4 では命令の重いフックは命令数の上限 (2,000 万) で止まるので、こちらの形が先に出る見込み。
- `kill_test` の読み込みで WAMR が `Cannot override max memory with value greater than module max memory`
  と出した。`memory.grow` を使わないモジュールは WAMR が最大を初めのページ数に縮めるため。害はないが、
  ログの `up to 22` はその場合は正しくない。
- `sim_app ps` (debugd) の wasm のアプリの `mem_used`・`mem_total` は 0 (表示の残り。W1b から)。

## 8. 残ったこと
