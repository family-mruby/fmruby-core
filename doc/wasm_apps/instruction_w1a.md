# W1a 指示書: 本体の外で WAMR の単体の試作をする

> 2026-11-14。実装はサブ、検収は親。計画は plan.md、前提の調査は report/w0.md。

## 目的

机上 (W0) で決まらなかった点を、ファームウェアの外の小さなプログラムで確かめる。一番知りたいのは
**emscripten でビルドした WAMR のインタプリタが動くか**。動かなければ、ブラウザ版を主戦場とする
計画の前提が変わるので、そこで止まって返す。

ファームウェアに組み込むのは次の段 (W1b) で、この段ではやらない。

## 作るもの

置き場は `tools/wamr_poc/` (fmruby-core の中)。

1. **本体役のプログラム** (C)。1 つのソースから 2 つのビルドを作る。
   - Linux (x86-64) のプログラム。
   - emscripten でビルドし、node で動かす版 (ブラウザは使わない)。
2. **土台の層** (WAMR が要求する、メモリ・時刻・ミューテックスなどの関数)。この試作のために
   自分で書き、**上の 2 つのビルドで同じソースを使う**。WAMR に付いている Linux 用の層は使わない
   (計画では `fmrb_hal` の上に 1 つ書いて 3 つの環境で共用するので、その縮小版になる)。
   どの関数が要ったかの一覧を report に載せる。
3. **本体の関数** (アプリから呼ばれる側)。引数を配列で受ける固定の型 (raw) で登録する。
   - ログを出す (ポインタと長さ)。
   - 点を打つ (x, y, 色)。本体役は 64x64 のバイトの配列に書くだけでよい。
   - ミリ秒の時刻を返す。
4. **アプリ** (wasm)。Rust・TinyGo・Zig の 3 つで、同じ動きのものを書く。
   - 公開する関数は `on_create` と `on_update` (次に呼ばれるまでの ms を返す)。本体役がループを
     回し、`on_update` を決まった回数だけ呼んで終わる。
   - 中身は、ログを 1 行出し、呼ばれるたびに決まった模様の点を打つ。
   - 本体役は最後に 64x64 の配列のチェックサムを出す。**3 つの言語・2 つのビルドで同じ値になる**
     ことが、動いた証拠になる。
5. **ビルドと実行の手順** を 1 つのスクリプト (Ruby) にまとめる。WAMR のソースは、版を固定して
   `tools/wamr_poc/` の下の git で無視される場所へ取ってくる (リリース 2.4.5)。取ってくる処理も
   スクリプトに入れる。

WAMR の設定: インタプリタは classic、AOT・JIT・WASI・スレッド管理は無し。メモリは固定のプール方式。

## 確かめること (受け入れ条件)

判定は、スクリプトを 1 回流した出力で読める形にする。

| 番号 | 確かめること | 判定 |
|---|---|---|
| A1 | Linux のプログラムで、3 言語のアプリが動く | 3 つともチェックサムが同じ |
| A2 | emscripten の版 (node) で、**同じ `.wasm` ファイル**が動く | A1 と同じチェックサム |
| A3 | 本体の関数が、両方のビルドで raw の形で登録されている | ソースで確認できる。型を見て呼び分ける仕組みを使っていない |
| A4 | 終わらないループのアプリが、命令数の上限で止まる | 両方のビルドで、理由の文字列つきで止まる。本体役は落ちない |
| A5 | 固定のプールで動く | 使用量 (全体・空き・最大) を出す。プールの外から確保していない (wasm のメモリを除く。それがどこから取られたかを report に書く) |
| A6 | アプリを 2 つ同時に持てる | 別のモジュール 2 つと、同じモジュールからのインスタンス 2 つを、交互に `on_update` して両方正しく動く |
| A7 | アプリごとの上限が効く | wasm のメモリの最大ページ数を超えて伸ばそうとしたアプリだけが失敗し、もう 1 つのアプリは動き続ける |

## 調べて report に書くこと

計測は**それぞれ 1 回**でよい (繰り返して統計を取らない)。

- emscripten で動かすまでに要った変更 (WAMR 側への手当て、ビルドの指定)。上流に出ている
  emscripten 対応の変更を参考にしたか、何を使い何を使わなかったか。
- A4 の後、止めたアプリを続きから再開できるか (次の `on_update` を呼べるか、インスタンスを
  作り直す必要があるか)。
- wasm の機能の組: 3 言語を同じ WAMR の設定で読むために要った、WAMR のビルド設定と各言語の
  コンパイルの指定。既定のままで読めなかった組み合わせと、そのエラー。
- TinyGo: 組み込み向けの対象で、解放する GC を選べるか。選べる場合と選べない場合で、確保を
  繰り返すアプリの wasm のメモリがどう増えるか。
- 大きさ: 3 言語の `.wasm` の大きさ、WAMR を足したことによる本体役の増分 (Linux は text、
  emscripten は出力の wasm)、アプリ 1 つを動かしたときのプールの最大使用量と wasm のメモリの
  大きさ。
- 速さ: 整数の計算だけのループ (たとえば 100 万回) を 1 つ決め、Linux の版と node の版で時間を
  1 回ずつ。あわせて、同じ計算を C で書いて直接コンパイルした場合の時間 (比の目安)。本体役から
  アプリの空の関数を 10 万回呼ぶ時間と、アプリから本体の関数を 10 万回呼ぶ時間。
- 使った道具の版 (emscripten・Rust・TinyGo・Go・Zig・node・WAMR)。
- W0 の見立て (report/w0.md) と違った点。撤回した仮説。残った課題。
