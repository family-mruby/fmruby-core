# wasm のアプリ (WAMR で TinyGo・Rust・Zig) 計画

> 状態: 進行中 | 更新: 2026-11-15 | WAMR (インタプリタ) を本体に入れ、TinyGo・Rust・Zig などで作った wasm のアプリを P4・sim・ブラウザ版で動かす。この文書は WAMR と SDK に絞り、アプリの殻 (W3) と型定義からの生成 (W4) は doc/app_boundary に分けた (決定 16)。W0・W1a 済 (emscripten の上で WAMR が動いた)。次は doc/app_boundary の W3・W4a、その後に W1b (決定 15)。W1a の後の決定 (18 個) は「W1a の後に決まったこと」の章にあり、本文に織り込み済み

## 目的

- Ruby 以外の言語 (TinyGo・Rust・Zig、ほかに C・AssemblyScript など wasm を出せる言語) で書いた
  アプリを、Family mruby のアプリとして動かす。言語ごとにエンジンを足す今の形 (BASIC・Lua・
  MicroPython) と違い、WAMR 1 つで wasm を出せる言語がまとめて入る。
- **API は型定義 (`sig/*.rbs`) から各言語の bindings を自動で生成する。** 言語ごとに API を設計しない
  ためであり、「rbs をインタフェース定義言語として使う」こと自体が Ruby の関係者に見せられる技術に
  なる (2026-11-03 ユーザ)。
- wasm のアプリは自分のメモリと、渡した関数にしか触れない作りにする (他人が作ったアプリを配る
  ときの土台。安全の保証までは言わない: report/w0.md 2.10)。

## 方針

2026-11-03 ユーザ:

- **主戦場はブラウザ版と P4**。sim でも動かす。ネイティブ版 (Linux の PC のコンポジタ) は優先度を
  下げる (使うのは主に作者だけのため。Cardputer Zero は別に考える)。
- **ブラウザ版でも、ブラウザの wasm エンジンは使わず、WAMR の C を wasm (emscripten) にして動かす。**
  本体の C を wasm にしているブラウザ版の作りにそのまま乗り、ブラウザ・P4・sim で同じインタプリタが
  動く (動きの違いを追わずに済む。将来 wasm のアプリを checkpoint で運ぶときも実装が 1 つで済む)。
- **速さはほどほどでよい**。WAMR はインタプリタで使い、AOT (事前に機械語にする方式) は使わない。
  AOT は実行できるメモリが要り、ESP32 では内蔵 RAM (IRAM) を食いやすく、内蔵 RAM を増やさない決まり
  とぶつかる。
- **内蔵 RAM は +0**。WAMR の本体のコードは flash、ヒープ・スタック・wasm のメモリは PSRAM に置く。
- アプリのコンパイルは PC で行う (TinyGo・Rust・Zig のコンパイラは端末では動かない)。端末の上で書いて
  動かす Ruby のアプリとは別の、「配る側」の道として位置づける。

2026-11-14 ユーザ (W0 の結果を受けて):

- **Ruby 以外で書いたアプリは、機能が絞られてよい。** ただし **Ruby で実装されたライブラリ
  (FmrbUI の部品・P5・タイルマップ・MIDI と SMF のプレーヤ) と、アプリに公開しない機能 (システム
  専用) を除いて、原則すべて wasm などの他の言語からも使えることを目標にする。**
  - **ファイルと音は境界に載せる範囲に入れる** (決定 6)。ファイルの読み書きできる範囲は Ruby の
    アプリと同じで、判定は境界の下に置く。
  - **I2C・GPIO などの HW は、この計画の最初には含めない** (決定 8)。HW の資源の競合の管理を
    別の計画 (doc/hw_resources) で先に整え、整えば境界に関数を足すだけで全言語に出せる。
- **wasm のアプリは、本体がループを回す。** アプリは `on_create`・`on_update`・`on_event` などに
  当たる関数を公開するだけで、自分ではループを持たない。
- **Window の枠と一生の処理は本体の C に置く (アプリの殻)。** 言語ごとの SDK に枠を書かない。
  本体に組み込む最初の試作 (W1b) だけは、殻なしの枠なし・全画面で動かしてよい。
- **型定義は `sig/*.rbs` の 1 か所だけにし、全エンジンのつなぎと各言語の bindings をそこから
  生成する。境界の関数は単純な形にし、Ruby らしい使い勝手は Ruby の薄い包みで保つ。**
  殻・境界と包みの方針 (境界の関数は Ruby のアプリからも呼んでよい、システム側とライブラリは
  境界の関数を呼ぶ、包みは状態を持たない、アプリの API の整理 doc/codebase_tidy の線を前提に
  する、つなぎは全エンジンで生成する) は、全言語に効く仕事なので doc/app_boundary/plan.md に
  分けた (決定 16)。この文書は、その上に wasm のアプリを載せる部分 (WAMR と SDK) を受け持つ。

## W1a の後に決まったこと (2026-11-14)

W1a の結果 (report/w1a.md) と、その後の相談で決まったこと。決定の表と根拠 (計測の数字) を
記録として残す。本文 (方針・作るもの・段・受け入れ条件・未確定事項) には織り込み済み。殻と
生成に関する決定 (6・9・10・12・14・15・17・18 の該当部分) は doc/app_boundary/plan.md の本文に
織り込み、そこから番号で参照している。

### W1a で分かったこと

- emscripten でビルドした WAMR 2.4.5 の classic インタプリタが動いた。WAMR のソースは変えて
  いない。要ったのは、自作の土台の層と、ビルドの指定 3 つ (対象を X86_32 にする、型を見て
  呼び分ける部分を差し替える、スタックの境界を渡す)。
- Rust・TinyGo・Zig の同じ `.wasm` が、Linux の版と emscripten の版で同じ結果になった。
- Rust と Zig の既定の出力は、WAMR の既定の設定では読めない。参照型の設定が要る。W0 に書いた
  設定の名前 (間接呼び出しの表の番号の符号化) は、この版には無い。
- TinyGo は、組み込み向けの対象でも解放する GC を選べる。選ぶと、確保を繰り返しても wasm の
  メモリが増えない。
- Rust は、スタックの大きさの指定をしないと、wasm のメモリが初めから 17 ページになる。
- wasm のメモリの置き場所は、土台の層のメモリの写像の関数を自分で書けば自由に決められる。
  W0 に書いた別の設定は要らなかった。
- 命令数の上限で止めた後、同じインスタンスで次の関数を呼べる。ただし止めるたびにアプリの
  スタックの位置がずれる (Zig で 16 バイト)。
- 数字 (PC で 1 回の計測): アプリは Rust 1.3 KB・TinyGo 3.2 KB・Zig 0.7 KB。WAMR を足した
  増分は emscripten の出力で約 128 KB、Linux の text で約 225 KB (W0 の目安より大きい。ESP32 の
  数字は W2 で測る)。アプリ 1 つの管理データとスタックが 22〜28 KB、wasm のメモリが 1〜2 ページ。
  整数の計算 100 万回が Linux の版で約 20 ms、emscripten の版で約 77 ms (C を直接動かすと
  約 0.8 ms)。本体とアプリの間の呼び出しは 1 回 20〜45 ナノ秒。
- 残った確認: 複数のタスクから同時に使う場合 (試作はスレッドなし)、インタプリタが本体の
  スタックをどれだけ使うか、プールの空きの数字が全体を 96 バイト超えて出た件。

### 決定

| 番号 | 決定 |
|---|---|
| 1 | **wasm の機能の組は WAMR の側で合わせる。** 参照型と拡張された定数式を有効にする (`WAMR_BUILD_REF_TYPES=1`・`WAMR_BUILD_EXTENDED_CONST_EXPR=1`、約 17 KB 増)。各言語の既定の出力がそのまま読める。SDK の側では、TinyGo の既定を解放する GC に、Rust にスタックの大きさの指定を入れる |
| 2 | **wasm のメモリは、WAMR の共通のプールとは別の領域から取る。** その領域は下の 5 のアプリの枠 |
| 3 | **命令数の上限で止めたアプリは、理由を出して終了させる。** 続けては使わない (スタックの位置がずれる問題は解かない) |
| 4 | **WAMR のタスクは必要なときだけ起動する。** 常時動くタスクは作らない。ランタイムの初期化は最初の wasm のアプリの起動時に行い、最後の 1 つが終わったら終了する。wasm のアプリのタスクだけ、スタックの既定値を大きくする (`task_stack_kb` と同じ経路)。PSRAM の領域は事前に確保するのが基本 (下の 5) |
| 5 | **PSRAM は Ruby のアプリと共用する。** wasm のアプリも Ruby のアプリと同じ枠 (doc/reference/app_memory.md。P4 で通常 1 MB・`large_memory` 2 MB) を 1 つ取り、今の仕組みにそのまま乗せる (先頭 3 つは静的、4 つ目以降は初めて使うときに取って持ち続ける、上限は枠の数)。wasm のメモリとバイナリの写しはその枠から切り出す。管理データと演算のスタックだけ、WAMR 用の小さな共通のプール (数百 KB、これだけ起動時に確保) から取る。wasm 専用の大きな領域は持たない。W1b で枠から切り出せるかを確かめ、だめなら wasm 専用の領域を事前に確保する形に戻す |
| 6 | **ファイルと音を、境界に載せる範囲に入れる。** ファイルの読み書きできる範囲は Ruby のアプリと同じ (判定は境界の下に置く)。W4b の機能のまとまりは 7 つになる: 描画の基本図形、文字、画像とスプライト、アプリと Window、時刻・ログ・クリップボード、ファイル、音。型定義の規則に「本体からバイト列を返す形」(アプリが用意したバッファに本体が書き、長さを返す) を足す |
| 7 | **機能のグループの宣言は入れない。** `.app.toml` で使う機能のグループ (権限のようなもの) を宣言させない。import の照合は決定 14 のとおり行う (2026-11-16 ユーザ、前の文言「import との照合もしない」を直した) |
| 8 | **I2C・GPIO などの HW は、この計画の最初には含めない。** HW の資源の競合の管理を先に整える (別の計画: doc/hw_resources)。整えば、境界に関数を足すだけで全言語に出せる |
| 9 | **W4a の最初に、関数 1 つ (`fill_rect` など) だけで全部のビルドを通す。** 型定義から生成し、mruby・Spinel・Lua・MicroPython のつなぎを差し替え、sim・ネイティブ版・ブラウザ版・ESP32 (ビルドだけ) を通す。PicoRuby のビルドとの相性を、道具を作り込む前に見るため |

9 の注意点 (ビルドの流れを読んだ結果): 生成した C は CMake の側 (`ports/esp32/`、ファイル名は
固定) に置く (libmruby の側は作り直しを検出しない)。本体のソースの一覧は `hosted/hosted.cmake`
にもある。生成は、Spinel の結合・`rake micropython:gen`・checkpoint の表の生成より前に 1 回。
checkpoint の表と、メソッド名のシンボルの扱いは未確認。型データベースを準備の段で型定義から
生成して gem に入れる前例がある (`rakelib/setup.rake`)。

| 10 | **記録型の整数と小数の幅は、ROS 2 と同じ名前の型の別名で書く。** `int8`・`int16`・`int32`・`int64`・`uint8`・`uint16`・`uint32`・`uint64` (`= Integer`)、`float32`・`float64` (`= Float`)、バイト列は `bin` (`= String`)。幅を書かない `Integer` は int32、`Float` は float64 として扱う。範囲の外の値は詰めるときにエラー。別名の定義は `sig/` の中の 1 つのファイルにまとめ、道具は名前で見分ける。境界の固定の並びのバイト列・ROS 2 の形式・Asterism の型の宣言で共通に使う (doc/rbs_types)。本文の例に `u8`・`u16` と書いた所は、この名前に直す |

| 11 | **コンパイルする言語の優先度は、Rust・TinyGo・Zig が高い。** C はその後。C でアプリを作る人はあまりいない見込み |
| 12 | **C の扱い。** ヘッダ (平らな関数の宣言と記録型の構造体) の生成は W4a に含める (本体の側のつなぎに要るので、追加の手間が無い)。対応する言語としての案内は 3 言語の後。コンパイルの道具は Zig に付属の C コンパイラ (`zig cc`) を、動作を確認したものとして案内する。**標準ライブラリは、まずアプリの側に同梱する** (本体は変えない) |

| 26 | **W6 の細部 (2026-11-16 ユーザ)。** 「自動」は利用者ごとの証明書 (T8) で相手が確かめられた接続のときだけ効き、ほかは確認を出す。確認の Window は今のまま (クリックで入れる、Esc・閉じるで断る、60 秒で断る、Enter は割り当てない)。画面の無い端末で「確認する」のときは、すぐ理由つきで断る。console のメンバーの一覧で選ぶのは後で |

決定 12 の補足 (2026-11-14 ユーザ): **C に対応することには、派生開発の土台と、イメージの共有の
ための意味がある。** C でアプリを書く人は少なくても、C のヘッダは境界の基準の資料になる。

- 派生開発の土台: 多くの言語は C のヘッダから bindings を作る道具を持つので、こちらが対応して
  いない言語でも、使う人が自分で対応できる (Swift・C++ がそのまま使えるのも同じ理由)。既存の
  C のコードを持ち込む入口にもなる。
- イメージの共有: RBS や各言語の SDK は、その言語を知らない人には読みにくい。C のヘッダは
  組み込みに関わる人ならほぼ誰でも読め、本体とアプリの間で実際に何が行き来するかを示す。
  記録型は構造体として出るので、バイト列の並びも読める。
- 確認の道具: C のアプリは平らな関数をそのまま呼ぶので、問題が本体の側か SDK の側かを
  切り分けられる。

そのため、扱いを 2 つに分ける:

| | 位置づけ |
|---|---|
| C のヘッダ | 境界の基準の資料。W4a の最初から、ほかの出力と同じ品質で作る。関数ごとの説明文 (日本語と英語)、記録型の構造体、選択肢の定数、ABI の版の定数を含める |
| C でアプリを書く人への案内 | 3 言語の後 (変更なし) |

- W4a の最初の通し試験 (決定 9) では、wasm の側の最初のアプリを C で書く。
- 境界の関数をひととおり呼ぶ C のアプリを 1 つ用意し、ABI が壊れていないかの確認として

決定 12 の根拠 (標準ライブラリの計測、2026-11-14、PC で 1 回、W1a の試作に足して測った):

| 方式 | アプリ | 本体の増分 | Linux の版 | emscripten の版 |
|---|---|---|---|---|
| WAMR の組み込みの標準ライブラリ (57 個の関数) を有効にする | 620 バイト | Linux の text で +14.6 KB、emscripten の出力で +8.2 KB | 試作では止まる | 動かない |
| アプリの側に標準ライブラリを入れる (`zig cc -target wasm32-wasi -mexec-model=reactor`) | 20.4 KB | 無し | 動いた | 動いた |

- WAMR の組み込みの標準ライブラリは、型を見て呼び分ける形で登録されるので、emscripten の上では
  動かない (関数の型が合わないというエラー)。使うなら、raw の形の包みを自分で書く必要がある。
- アプリの側に入れる方式は、本体から見てアプリが使う関数が増えない。`snprintf`・`malloc`・
  文字列の関数が両方の本体役で動いた。増える約 20 KB の大半は `snprintf` の実装。
- `printf` (標準出力) を使うと、OS の機能 (WASI) の関数が 4 つ要り、本体に無いので動かない。
  ログは SDK の関数で出す。
- 測っていないもの: 小さな標準ライブラリを自作して SDK に同梱した場合の大きさ。20 KB が問題に
  なったら検討する。

ほかの言語の見立て (2026-11-14、動かして確かめてはいない。どれも計画の段には入れない):

- **C++**: C のヘッダをそのまま使う (ヘッダに `extern "C"` を入れる)。道具は `zig c++`。専用の
  SDK は作らない。クラス・テンプレート・ラムダなどコンパイルの時点で片が付く機能は使える。
  例外と実行時の型の情報は無効にする (`-fno-exceptions`・`-fno-rtti`) のを勧める。標準
  ライブラリは使えるがアプリが大きくなり、`iostream` は避ける。例外が WAMR のインタプリタで
  動くかと、標準ライブラリを使ったときの大きさは未確認。
- **AssemblyScript**: 条件に合う見込み (素の wasm、小さい、npm で入る)。型紙 1 つと、文字列の
  変換 (内部が UTF-16 なので UTF-8 へ) で足せる。3 言語と C の次の候補。
- **Swift**: 使えるのは組み込み向けの Swift だけ (通常の Swift は数 MB で OS の機能が要る)。
  C のヘッダを取り込めるので C の SDK を流用する。言語の側が実験的で、追従の手間がある。
- 位置づけ: AssemblyScript と Swift は、使う人のためというより、企画の広がりを示すため。
  「言語を足す費用は型紙 1 つ」を確かめる例にもなる。足すなら W4a の道具ができた後に、
  小さな実演として。

そのほか、配布について:

- 公開しているブラウザ版に `.app.wasm` を読み込ませて試せるようにする。端末が無くても開発を
  始められる。
- 型定義の説明文 (日本語と英語) から、言語ごとの API の一覧が出る。
- 名前 (リポジトリ・crate・モジュール) は未定。Go のモジュールの名前はリポジトリの場所
  そのものなので、後から変えられない。リポジトリはまだ作っていない。

決定 10 で、W4a で決める事項は 3 つになった: 印の書き方、境界の関数の名前、フック・頼みごと・
内側の区別のしかた。

W4a の設計の注意 (2026-11-14): **生成の道具は、呼び出しの届け先を差し替えられる作りにする。**
「RBS のクラスとメソッドの定義から、各言語の呼ぶ側と呼ばれる側のコードを作る」道具は 1 つで、
届け先が本体の C の関数ならこの計画 (FmrbApp・FmrbGfx を他の言語から使う)、届け先が
Asterism の網なら別の端末のオブジェクトを他の言語から呼ぶ話 (doc/rbs_types) になる。値の運び方
(固定の並びのバイト列か MessagePack か) も届け先ごとに差し替える。FmrbApp は、アプリが本体を
呼ぶ向き (頼みごと) と本体がアプリを呼ぶ向き (フック) の両方を 1 つのクラスで使う例で、言語
ごとに自然な形で出す (Python は継承、Rust は実装すべき関数の一覧と、頼みごとの関数の集まり)。

確認したこと (決定 10 の前提): 本体の mruby は、全部のビルドで整数が 64 ビットの符号つき、
小数が 64 ビット。

### 考え方 (ユーザ)

- **W4 (型定義からの生成と境界の整理) の価値は、WAMR と同じくらいある。** RBS に価値が
  生まれるのが技術的にうれしい。規則を決めるときは、RBS として自然に読めること、独自の記法を
  増やさないことを判断の軸にする。
- この計画が済むと、Ruby (mruby・Spinel)・Lua・Python (MicroPython)・Rust・Go (TinyGo)・Zig・C が
  同じ定義から同じ範囲の API を持つ。BASIC は独自のエンジンで、生成の対象に入れていない。

- **RBS を IDL として扱うのは、Ruby が中心の企画だから** (プロジェクトの名前のとおり)。専用の
  IDL のほうが技術的に楽な所でも採らない。ほかの言語は、Ruby の定義を通じて加わる。決まりを
  足すときに迷ったらここに立ち返る (doc/rbs_types の「なぜ RBS か」)。

### アプリを書く人から見た姿 (Rust の例、案。名前や細部は確定ではない)

1. Rust と wasm 向けの対象 (`wasm32-unknown-unknown`) を入れ、型定義から生成された SDK の
   crate を依存に足す。
2. アプリの型を 1 つ作り、`on_create`・`on_update`・`on_event` を書く。枠の描画とループは本体が
   受け持つ。Ruby の `class MyApp < FmrbApp` が、Rust では「実装すべき関数の一覧」(トレイト) に
   なり、本体への頼みごとは渡されるハンドルの関数になる。書かなかったフックは何もしない。
3. Ruby のアプリと同じ `.app.toml` を添える。
4. `cargo build --release --target wasm32-unknown-unknown` でビルドし、`.app.wasm` にする。
   スタックの大きさなどの指定は SDK が入れる。
5. 入れ方は Ruby のアプリと同じ (ブラウザ版に読み込む、sim に置く、P4 へ WiFi で送る、店、
   Asterism)。同じ `.app.wasm` がどの環境でも動き、Ruby のアプリと同じ枠の Window で並ぶ。
6. ログは Ruby のアプリと同じ場所に出る。パニック・終わらないループ・メモリの使いすぎは、
   そのアプリだけが理由つきで止まる。
7. 使えないもの: Ruby で書かれたライブラリ、端末の上で書いてその場で動かすこと、HW
   (別の計画の後)、OS に頼る標準ライブラリ、checkpoint。

試作 (W1a) で動いたのは、SDK を使わず本体の関数を直接宣言する生の形まで。上の姿は W4a の
道具ができてから。

W1a の後に新しく出た未確定事項のうち、段の順と W3・W4 を別の文書に分けるかは決定 15・16 で
決まった。BASIC は doc/app_boundary の未確定事項へ、メモリの上限のページ数と SDK の名前は本文の
「未確定事項」へ移した。

## 作るもの

### 1. WAMR を本体に入れる

- sim (Linux x86-64)、P4 (RISC-V 32bit、ESP-IDF)、ブラウザ版 (emscripten) の 3 つで同じ WAMR を
  インタプリタで組み込む。
- **ソースを版を固定して取り込み、土台の層 (メモリ・時刻・ミューテックスなど) を `fmrb_hal` の
  上に自分で書く。** ESP-IDF のコンポーネントとして配られている版は使わない (古く、脆弱性の修正が
  入っていない)。土台の層は 3 つの環境で同じ 1 つにする。
- **インタプリタは classic から始める。** fast は約 2 倍速い代わりにメモリも約 2 倍で、最近の
  脆弱性が読み込み部に偏っている。classic は wasm のバイナリを書き換えながら使うので、写しを
  PSRAM に置く。
- **本体の関数は、引数を配列で受ける固定の型 (raw) で登録する。** 型を見て呼び分ける仕組みは
  emscripten の上で成り立たないため。3 つの環境で同じにする。
- **メモリは Ruby のアプリと同じ枠を使う (決定 2・5)。** ランタイムは 1 つのプロセスに 1 つしか
  持てず (状態がすべて static 変数)、その上に wasm のアプリを何個でも並べる形になる。
  - wasm のアプリも Ruby のアプリと同じ枠 (doc/reference/app_memory.md。P4 で通常 1 MB・
    `large_memory` 2 MB) を 1 つ取り、今の仕組みにそのまま乗せる (先頭 3 つは静的、4 つ目以降は
    初めて使うときに取って持ち続ける、上限は枠の数)。
  - wasm のメモリ (linear memory) とバイナリの写しは、その枠から切り出す。wasm のメモリは土台の層の
    メモリの写像の関数から取られ、この関数は自分で書くので置き場所を自由に決められる (W1a で確認)。
  - 管理データ (モジュールの解析結果・インスタンス) と演算のスタックだけ、WAMR 用の小さな共通の
    プール (数百 KB、これだけ起動時に確保) から取る。wasm 専用の大きな領域は持たない。
  - W1b で枠から切り出せるかを確かめ、だめなら wasm 専用の領域を事前に確保する形に戻す。
  - アプリごとの上限は、インスタンスを作るときに渡す wasm のメモリの最大ページ数と、演算の
    スタックの大きさで縛る。管理データはアプリごとには縛れないが、バイナリの大きさにほぼ比例する
    はずなので、`.app.wasm` の大きさの上限で抑える。共通のプールの使用量 (全体・空き・最大) は
    WAMR の API で読める。
- **ランタイムは必要なときだけ動かす (決定 4)。** 初期化は最初の wasm のアプリの起動時に行い、
  最後の 1 つが終わったら終了する。常時動くタスクは作らない。wasm のアプリのタスクだけ、スタックの
  既定値を大きくする (`task_stack_kb` と同じ経路)。
- **暴走は命令数の上限で止める。** 本体がアプリの関数を呼ぶたびに上限を渡し、超えたら理由を
  出して**そのアプリを終了させる** (続けては使わない。止めるたびにアプリのスタックの位置がずれる
  問題は解かない。決定 3)。本体のスタックの境界は手で設定する (ESP-IDF では検査が黙って無効に
  なるため)。
- **wasm の機能の組は WAMR の側で合わせる (決定 1)。** 参照型と拡張された定数式を有効にし
  (`WAMR_BUILD_REF_TYPES=1`・`WAMR_BUILD_EXTENDED_CONST_EXPR=1`)、各言語の既定の出力がそのまま
  読めるようにする。SDK の側では、TinyGo の既定を解放する GC に、Rust にスタックの大きさの指定を
  入れる。
- 新しいアプリの種類として、今のアプリの一生 (起動・イベント・終わり)・ランチャーに乗せる
  (`fmrb_vm_type_t` に 1 種類足す)。

### 3. 型定義から bindings を生成する → doc/app_boundary

doc/app_boundary/plan.md の「作るもの 2」へ移した (決定 16)。境界に載せる範囲、平らな関数の形の

### 4. アプリの形と配り方

- アプリの包み: `.app.wasm` と `.app.toml` (言語と、作ったときの SDK の版を書く。雛形が入れる)。
- **使用の宣言は入れない (決定 7)。** `.app.toml` での機能のグループの宣言も、wasm の import との
  照合もしない (基本は自己責任)。
- **版は大きい番号と小さい番号に分ける (決定 14)。** 大きい番号は既存の関数の形が変わった・消えた
  とき、小さい番号は関数が増えただけのとき。どちらの変更かは、生成の道具が前回のリリースの
  型定義と比べて判定する。新しい SDK で作ったアプリが古い本体に無い関数を使っていたら、起動の
  前に理由つきで断る。wasm の機能の組は WAMR の側で合わせる (決定 1) ので、アプリごとには
  確かめない。
- **SDK の配り方 (決定 13)。** SDK を配るのは Rust・TinyGo・Zig・C (Lua・MicroPython・Ruby は本体に
  組み込まれているので配らない)。中身は bindings・ビルドの設定 (スタックの大きさ、TinyGo の GC
  など)・アプリの雛形・見本のアプリ。置き場所は SDK 専用のリポジトリ 1 つで、言語ごとにそのまま
  各言語の公式の置き場 (crate など) へ公開できる配置にしておく。公式の置き場への公開は API が
  固まってから。
- 入れる道:
  - **店** (`doc/app-distribution/`、完了済み): 正式な配布。`.app.wasm` も同じ店で配る。店がバイナリを
    正しく扱えるかを確かめる (picoruby の文字列でバイト列を扱うときの罠)。一覧に言語と ABI の版を出す。
  - **Console のファイル転送**: 開発中に PC で作ったものを端末へ送る。Console の許可表と記録に乗る。
  - **Asterism でのインストール**: 下の 5。
  - 開発の手早い道: Tab5 は今の `tab5_fs` の put → launch でも足りる。

### 5. Asterism の受け口 (インストールと checkpoint のイメージで共用)

- 受け口のサービスが Asterism で `begin` / `chunk` / `commit` を公開し、`caller:` で送り手を絞る。
  Zenoh の 1 回の上限 (4 KB) に合わせて分けて送る。端末の証明書による相手の確認がそのまま効く。
- 受け取ったものは種類に応じて処理する:
  - `.app.wasm` と `.app.toml` → 置いて、ランチャーの一覧に足す (インストール)。
  - checkpoint のイメージ → 着いた先で続きから起動する (doc/checkpoint の F5、決定 D13 と同じもの)。
- 店は「使う人が自分で選んで入れる」、Asterism は「管理する側 (Console・別の端末) が配る・移す」と
  向きで分ける。
- 受け口は checkpoint の F5 で作った (2026-11-04): 転送のアプリ
  `/usr/share/transfer/transfer.app.rb` が `<ノード>/transfer/inbox` に `check` / `begin` / `chunk` /
  `commit` / `status` / `cancel` を出す。W6 は種類の表に `.app.wasm` の種類を足し、`commit` で置き場所へ
  移してランチャーの一覧に足す処理を書く形になる。
- (W6 で作った、report/w6.md) 種類 `app`: アプリのフォルダを tar 1 つにして送り、受け手は
  `/app/usr/.<名前>.new/` に開いて中を見て (wasm は本体に無い関数を import していないか)、設定で確認してから
  `/app/usr/<名前>/` に置き、ランチャーに読み直させる。wasm に限らず Ruby・Lua・Python・BASIC のアプリも同じ形。

### 6. 将来: wasm のアプリを checkpoint で運ぶ

- WAMR の上流には無い。本体がループを回す形なので、呼び出しの合間はアプリのスタックが空で、
  wasm のメモリ・書けるグローバル・表を写せば原理的には足りる見込み。
- 公開されていないグローバルを読む API が無く、WAMR の内部の構造に触るか、言語の側で公開する
  必要がある。今は作らない。

## 受け入れ条件

殻と生成の受け入れ条件 (定義が `sig/*.rbs` の 1 か所、全エンジンのつなぎが生成物、Ruby のアプリの
書き方が変わらない、包みと境界の関数を混ぜても壊れない、など) は doc/app_boundary/plan.md。
この文書の受け入れ条件:

- P4・sim・ブラウザ版で、TinyGo・Rust・Zig のアプリが同じ `.app.wasm` のまま動く。
- その 3 言語の bindings は、doc/app_boundary の生成の道具で `sig/*.rbs` から生成したものだけを
  使っている (手書きの bindings が無い)。
- Ruby で実装されたライブラリとアプリに公開しない機能を除く API が、wasm のアプリから呼べる。
- wasm のアプリが、Ruby のアプリと同じ枠の Window でデスクトップに並ぶ。
- 終わらないループのアプリが、理由を出して止められる。
- 内蔵 RAM が増えない (`rake regress:size`)。今の回帰の道具 (`rake regress`・`regress:run`・
  `regress:screens`) が通る。重い方は各段の終わりと最後の受け入れで確認する。
- 店から `.app.wasm` のアプリを入れて動かせる。各言語の既定の出力のまま (機能の組は WAMR の側で
  合わせてある) 読める。本体に無い関数を使う新しい SDK のアプリは、起動の前に理由つきで断られる
  (版の大きい番号・小さい番号)。

## 未確定事項

殻と生成の未確定事項 (W4a で決める 3 点: 印の書き方・境界の関数の名前・フック/頼みごと/内側の
区別、BASIC を生成の対象に入れるか、ほか) は doc/app_boundary/plan.md。

- ブラウザ版の速さが足りるか (動くことは W1a で確認。整数の計算 100 万回が emscripten の版で
  約 77 ms)。
- WAMR の共通のプールの大きさ (機種別)、アプリごとのメモリの上限の既定値と `.app.toml` での
  書き方、`.app.wasm` の大きさの上限 (W2 の計測を見て決める)。
- wasm のアプリのメモリの上限を、全環境で同じページ数にするか (P4 の 1 MB の枠に合わせる。
  推奨)、枠の大きさに従わせるか。Linux とブラウザ版の枠は 1.5 MB / 3 MB で、wasm の中は常に
  32 ビットなので、従わせると sim とブラウザ版だけ緩くなる。W1b で決める。
- SDK のリポジトリ・crate・モジュールの名前。公式の置き場の名前を先に確保するか (Go のモジュールの
  名前はリポジトリの場所そのもので、後から変えられない)。
- 速さの目安 (ほどほどの基準。W2 の計測を見て決める)。classic で足りなければ fast を検討する。
- ネイティブ版・Cardputer Zero での扱い。
- wasm のアプリの checkpoint をやるか、やるならいつか。
