# wasm のアプリ (WAMR で TinyGo・Rust・Zig) 計画

> 状態: 計画済 | 更新: 2026-11-14 | WAMR (インタプリタ) を本体に入れ、TinyGo・Rust・Zig などで作った wasm のアプリを P4・sim・ブラウザ版で動かす。机上の調査 (W0) 済み。本体の C の殻がループを回し、型定義は `sig/*.rbs` の 1 か所で、境界の関数を単純な形にして全エンジン (wasm・Lua・MicroPython・Spinel・mruby) のつなぎを生成し、Ruby は薄い包みで使い勝手を保つ。着手は VM の checkpoint (doc/checkpoint) が落ち着いてから

## 目的

- Ruby 以外の言語 (TinyGo・Rust・Zig、ほかに C・AssemblyScript など wasm を出せる言語) で書いた
  アプリを、Family mruby のアプリとして動かす。言語ごとにエンジンを足す今の形 (BASIC・Lua・
  MicroPython) と違い、WAMR 1 つで wasm を出せる言語がまとめて入る。
- **API は型定義 (`sig/*.rbs`) から各言語の bindings を自動で生成する。** 言語ごとに API を設計しない
  ためであり、「rbs をインタフェース定義言語として使う」こと自体が Ruby の関係者に見せられる技術に
  なる (2026-11-03 ユーザ)。
- wasm のアプリは自分のメモリと、渡した関数にしか触れない作りにする (他人が作ったアプリを配る
  ときの土台。安全の保証までは言わない: report/w0.md 2.10)。

## 方針

2026-11-03 ユーザ:

- **主戦場はブラウザ版と P4**。sim でも動かす。ネイティブ版 (Linux の PC のコンポジタ) は優先度を
  下げる (使うのは主に作者だけのため。Cardputer Zero は別に考える)。
- **ブラウザ版でも、ブラウザの wasm エンジンは使わず、WAMR の C を wasm (emscripten) にして動かす。**
  本体の C を wasm にしているブラウザ版の作りにそのまま乗り、ブラウザ・P4・sim で同じインタプリタが
  動く (動きの違いを追わずに済む。将来 wasm のアプリを checkpoint で運ぶときも実装が 1 つで済む)。
- **速さはほどほどでよい**。WAMR はインタプリタで使い、AOT (事前に機械語にする方式) は使わない。
  AOT は実行できるメモリが要り、ESP32 では内蔵 RAM (IRAM) を食いやすく、内蔵 RAM を増やさない決まり
  とぶつかる。
- **内蔵 RAM は +0**。WAMR の本体のコードは flash、ヒープ・スタック・wasm のメモリは PSRAM に置く。
- アプリのコンパイルは PC で行う (TinyGo・Rust・Zig のコンパイラは端末では動かない)。端末の上で書いて
  動かす Ruby のアプリとは別の、「配る側」の道として位置づける。

2026-11-14 ユーザ (W0 の結果を受けて):

- **Ruby 以外で書いたアプリは、機能が絞られてよい。** ただし **Ruby で実装されたライブラリ
  (FmrbUI の部品・P5・タイルマップ・MIDI と SMF のプレーヤ) と、アプリに公開しない機能 (システム
  専用) を除いて、原則すべて wasm などの他の言語からも使えることを目標にする。**
- **wasm のアプリは、本体がループを回す。** アプリは `on_create`・`on_update`・`on_event` などに
  当たる関数を公開するだけで、自分ではループを持たない。
- **Window の枠と一生の処理は本体の C に置く (アプリの殻)。** 言語ごとの SDK に枠を書かない。
  最初の試作 (W1) だけは、殻なしの枠なし・全画面で動かしてよい。
- **型定義は `sig/*.rbs` の 1 か所だけにする。** Ruby から見える API の型定義がそのまま唯一の
  元で、平らな層のための別の定義は作らない。エディタに見せる情報 (メソッドの形と説明文) が
  一番価値のある定義なので、それを正とし、本体に載せる型データベースと各言語のつなぎは
  そこから作る。
- **境界の関数は単純な形にし、Ruby らしい使い勝手は Ruby の薄い包みで保つ。** 境界の関数は
  整数・文字列・記録だけを受け渡しする。省略できる引数・キーワード引数・Symbol などの Ruby
  らしい形は、その上の Ruby の包みが境界の形へ直す。**今の実装は mruby も Spinel も既に
  この 2 段の作りになっている**: mruby は mrblib の Ruby のメソッド (`draw_text` など) が
  `_` で始まる C のメソッド (`_draw_text` など) を呼び、Spinel は基底の Ruby のメソッドが
  平らな関数を呼ぶ (report/w0.md 1.7)。境界の関数に当たるものが内部用として隠れているだけ
  なので、作り直しではなく、それを公開の形に整える作業になる。形が最初から単純な関数
  (`fill_rect`・`present` など) は包みが無く、境界の関数がそのまま公開の API になっている。
- **境界の関数は Ruby のアプリからも呼んでよい (2026-11-14 ユーザ)。** 包みを通ると呼び出しが
  1 段深くなるので、速さが気になる所 (毎フレーム何度も呼ぶ描画など) では、アプリが包みを
  使わずに境界の単純な関数を直接呼べる。そのため境界の関数は内部用として隠さず、公開の API と
  して型定義に説明文つきで書き、エディタにも出す。
- **システム側と Ruby で書かれたライブラリは、境界の関数を呼ぶ (2026-11-14 ユーザ)。** 包みは
  利用者のアプリのための使い勝手で、カーネル・デスクトップ・標準アプリ・基底クラス・ライブラリ
  (FmrbUI・FmrbText など) は、包みを持つ関数については境界の関数を直接呼ぶ。mruby では今より
  速くなる見込みがある (包みの 1 段と、キーワード引数のたびに作られる Hash が無くなる)。
  順番は、利用者のアプリの VM の中で動くライブラリ → 基底クラスの枠の描画 → デスクトップと
  標準アプリ。最後の 2 つは標準構成では Spinel で動き、効果が小さい見込みなので、計測して
  から置き換えるかを決める。
- **包みは状態を持たない。** 今の包みは、選んだフォントと文字の大きさを Ruby の変数で覚えて
  いる (mruby・Spinel とも)。このままでは、包みを通さずに境界の関数でフォントを変えたときに
  値がずれる。状態は境界の下 (C の側) に置き、境界の関数で読めるようにする。包みと境界の
  関数を混ぜて使っても壊れないことが、上の 2 つの方針の条件になる。
- **アプリの API の整理 (doc/codebase_tidy) の結果を前提にする。** そちらで決まる線と同じ線を
  使い、この計画で別の線を引かない。
  - system 用のクラスメソッドを `FmrbSystem` に分ける段 (T5) の線引きを、そのまま「境界に
    載せる・載せない」の線にする。`FmrbSystem` に入るもの = 載せないもの。読み取り系で
    `FmrbApp` に残るもの (時計・電池・言語など) は境界に載せる候補になる。
  - 描画の座標の原点 (user area の左上を原点にする整理) は、境界の下 (C の側) に置く。Ruby の
    包みで足している場合は、フォントの状態と同じく境界の下へ移す。他の言語のアプリが足し算を
    自分で書かずに済むようにするため。
- **つなぎは全エンジンで生成する。** wasm の 3 言語・Lua・MicroPython・Spinel の宣言に加えて、
  mruby の gem のつなぎ (引数の取り出しの部分) も、境界が単純な形なので生成に切り替える。
  今は同じ仕事をする C のつなぎをエンジンごとに手で書いている (report/w0.md 1.6)。
- Ruby の基底クラスの 2 つの実装 (mruby 用・Spinel 用) を 1 つにすることは、この計画の目的に
  しない。ただし両方が「同じ境界の関数を呼ぶ Ruby」になるので、包みを共用できる範囲は共用する。
  枠の描画を C の関数へ差し替えるかは、殻ができた後に判断する。

## 作るもの

### 1. WAMR を本体に入れる

- sim (Linux x86-64)、P4 (RISC-V 32bit、ESP-IDF)、ブラウザ版 (emscripten) の 3 つで同じ WAMR を
  インタプリタで組み込む。
- **ソースを版を固定して取り込み、土台の層 (メモリ・時刻・ミューテックスなど) を `fmrb_hal` の
  上に自分で書く。** ESP-IDF のコンポーネントとして配られている版は使わない (古く、脆弱性の修正が
  入っていない)。土台の層は 3 つの環境で同じ 1 つにする。
- **インタプリタは classic から始める。** fast は約 2 倍速い代わりにメモリも約 2 倍で、最近の
  脆弱性が読み込み部に偏っている。classic は wasm のバイナリを書き換えながら使うので、写しを
  PSRAM に置く。
- **本体の関数は、引数を配列で受ける固定の型 (raw) で登録する。** 型を見て呼び分ける仕組みは
  emscripten の上で成り立たないため。3 つの環境で同じにする。
- **メモリは固定のプール方式にする (2026-11-14 ユーザ)。** ランタイムは 1 つのプロセスに 1 つしか
  持てず (状態がすべて static 変数)、その上に wasm のアプリを何個でも並べる形になる。起動時に
  PSRAM から大きな領域を 1 つ取って WAMR に渡し、モジュールの解析結果・インスタンス・演算の
  スタックはすべてその中から取らせる。
  - WAMR 全体の上限は領域の大きさ。使い切っても、本体の他の部分 (mruby のアプリ・デスクトップ) の
    メモリには波及しない。使用量 (全体・空き・最大) は WAMR の API で読める。
  - アプリごとの上限は、インスタンスを作るときに渡す wasm のメモリの最大ページ数と、演算の
    スタックの大きさで縛る。
  - 管理データ (モジュールの解析結果など) はアプリごとには縛れない。バイナリの大きさにほぼ
    比例するはずなので、`.app.wasm` の大きさの上限で抑える。
  - wasm のメモリ (linear memory) だけは、プール方式でもプールの外 (土台の層のメモリの写像の
    関数) から取られる。この関数は自分で書くので、同じ領域から取るか、wasm のメモリ用の領域を
    別に用意するかを選べる (未確定事項)。
- **暴走は命令数の上限で止める。** 本体がアプリの関数を呼ぶたびに上限を渡し、超えたら理由を
  出して止める。本体のスタックの境界は手で設定する (ESP-IDF では検査が黙って無効になるため)。
- **wasm の機能の組を 1 つに固定する。** WAMR のビルド設定と各言語の SDK のコンパイル指定を
  揃え、合わないアプリはインストールのときに理由つきで断る。
- 新しいアプリの種類として、今のアプリの一生 (起動・イベント・終わり)・ランチャーに乗せる
  (`fmrb_vm_type_t` に 1 種類足す)。

### 2. アプリの殻 (本体の C)

- 持つもの: Window とキャンバスの生成、枠の描画、枠のイベント (閉じるボタン・Window のメニュー)、
  user area の位置、メッセージ待ちと解析、タイマー、中断と再開、終了の印。
- アプリが公開する関数を、殻が用のあるときだけ呼ぶ。`on_update` が次に呼ばれるまでの ms を返す
  点は Ruby のアプリと同じ。
- **最初の利用者は Lua のアプリにする。** 今は枠を自分で描いているので、殻に乗せれば、wasm と
  切り離して sim で殻を確認できる。MicroPython の prelude を殻に寄せるかは、その後に判断する。

### 3. 型定義から bindings を生成する

- **元は `sig/*.rbs` だけ。** 境界に載せるメソッドに印を付ける (書き方は未確定事項)。範囲は、
  Ruby で実装されたライブラリとアプリに公開しない機能を除く全部。今の平らな関数の表
  (`fmrb_spx_*`) のうち一般のアプリ向けの 55〜60 個が最初の目安 (内訳は report/w0.md 1.1)。
- 載せないもの: システム専用の関数 (再起動・電源・WiFi・BLE・音量・USB・プロセスの一覧など)、
  Ruby で書かれたライブラリ、checkpoint と `move_to`、アプリの一生の内側 (`app_init`・
  `recv_message` など。殻と各エンジンの基底の内部で使うもので、今の手書きの宣言のまま残す)。
- **平らな関数の形は、型定義から決まった規則で導く。** 今の関数表の形に定義を合わせるのでは
  なく、規則が出した形に C の実装を合わせる。

  | Ruby 側の型 | 平らな関数での形 |
  |---|---|
  | レシーバ (`FmrbGfx` など) | 第 1 引数の番号。`FmrbApp` のインスタンスメソッドとモジュールの関数は、番号なし |
  | Integer・bool | 整数 |
  | String | ポインタと長さ |
  | Symbol の選択肢 (`:default` など) | 番号。選択肢は RBS のリテラルの型で書く |
  | 記録 (今は `Hash` と書いてあるもの) | 記録型として書き、固定の並びのバイト列を導く |
  | 要素の決まった配列 (四角の一覧など) | 要素の型を書き、ポインタと個数 |
  | 中身の決まらない値 (`send_message` の `data`) | バイト列 |

- **Ruby らしい形のメソッドは、境界の関数と Ruby の包みに分ける。** 省略できる引数・
  キーワード引数を持つもの (`draw_text` など) は、単純な形の境界の関数を型定義に書き、今の
  名前のメソッドは Ruby の包みとして mrblib と Spinel の基底に書く。境界の関数も公開の API
  なので、`_` で始まる名前にはせず、エディタに出す。説明文には「引数を省略できない単純な形。
  速さが要る所で使う」ことと、対になる包みの名前を書く。名前の付け方 (包みとの見分け方) は
  未確定事項。他の言語には境界の関数を出す。
- **FmrbApp のメソッドは 3 種類に分けて扱う。** 今の型定義 (`sig/fmrb_app.rbs`) は 1 つの
  クラスに並べているので、生成の道具が見分けられるよう、印か置き場所で区別する (書き方は
  未確定事項)。Ruby のアプリから見た書き方 (`class MyApp < FmrbApp` に `on_*` を書く) は
  変えない。

  | 種類 | 例 | 行き先 |
  |---|---|---|
  | アプリが書くフック | `on_create`・`on_update`・`on_event`・`on_resize`・`on_destroy`・`on_control` | アプリが公開する関数。型定義に書き、殻が呼ぶ |
  | 本体への頼みごと | `subscribe`・`publish`・`set_timer`・`request_fullscreen`・`set_hit_shape` | 境界の関数。レシーバは「今のアプリ」なので、番号の引数は付けない |
  | 枠と一生の内側 | `draw_window_frame`・`main_loop`・`start`・`stop` | 本体の C の殻と各エンジンの基底。境界に載せない |

- **平らな関数の表を 1 組にする。** Spinel 用の表 (`fmrb_spx_*`) を土台にし、MicroPython 用の表
  (`fmrb_mp_*`、`components/micropython/modules/fmrb_bridge.c`) をそこへ寄せる。
- 生成するもの:

  | 出力 | 中身 |
  |---|---|
  | 平らな関数のヘッダ | 整数とポインタだけの宣言 (本体のヘッダを読めない MicroPython のモジュールからも使える形) と、記録を詰める・読む関数 |
  | 本体に載せる型データベース | 型定義から印を落としたもの (エディタ用。今の `rake ti` の入力) |
  | wasm のつなぎ | raw の形の import 関数と登録の表 |
  | wasm の各言語の bindings | TinyGo・Rust・Zig。C のヘッダも。説明文は型定義のものを出す |
  | Lua のつなぎ | 引数を取り出して呼ぶ関数と登録の表 (今の `components/lua/extension/fmrb_lua_gfx.c` の置き換え) |
  | MicroPython のモジュール | 引数を取り出して呼ぶ関数・関数オブジェクト・登録の表 (今の `fmrb_module.c` の該当部分の置き換え) と、Python の側のクラス (prelude の `FmrbGfx` など) |
  | Spinel の宣言 | `ffi_func` の並び (今の `main/prebuild_scripts/spinel/fmrb_app_ffi.rb` の該当部分) |
  | mruby の gem のつなぎ | 引数を取り出して平らな関数を呼ぶ部分 (今の gem の `gfx.c`・`app.c` の該当部分の置き換え) |

- **生成の道具は Ruby のスクリプトで作り、`rake` のタスクとしてホスト (PC) で動かす。**
  今の型データベースの生成 (`rake ti:gen`) と同じ段 (docker の前) に置く。ESP-IDF のコンテナ
  には ruby が無いため。
  - 読み取りは `rbs` gem の解析器を使う (メソッドの形・説明文・注釈・記録型・リテラルの型を
    構文木で受け取る。文字列の一致で自作しない)。
  - 規則を当てた結果を、出力先によらない中間の表 (平らな関数の名前・引数・戻り値・記録型・
    説明文) にまとめる。出力先ごとの違いは型紙 (ERB) だけに置く。言語を足すときは型紙を
    1 つ足す。
  - タスクは、全部を生成するものと、出力先を 1 つだけ生成するものを用意する。
- **生成物の置き方 (2026-11-14 決定)**:
  - 本体の中のつなぎ (平らな関数のヘッダ、wasm・Lua・MicroPython・mruby のつなぎ、Spinel の
    宣言) は、**ビルドのたびに作り、リポジトリに入れない**。型定義より古い生成物を検出して
    作り直す仕組みを最初から入れる (型データベースと wasm のビルドにある「生成物を作り直さ
    ない」罠を増やさない)。
  - 各言語の SDK (TinyGo・Rust・Zig の bindings と C のヘッダ) は、**リポジトリに入れる**。
    アプリを書く人が PC で使う配り物で、差分をレビューで読めるようにするため。型定義と
    一致しているかは軽い回帰 (`rake regress`) で検査する。
- エラーの返し方は言語ごとに型紙で決める (Lua はエラーを投げて自分を返す、MicroPython は例外、
  wasm は負の数、など)。他の言語の使い勝手は Ruby より素朴でよい (境界の形がそのまま見える)。
- アプリの一生とイベントの受け渡しは生成の外で、殻 (上の 2) が受け持つ。
- MicroPython は、生成したソースを置いてから `rake micropython:gen` を流す順になる。
- 今の rbs はエディタの型支援のために簡略にしてあり、実際の API とずれている所がある
  (`publish` のデータ、`draw_text` のキーワード引数、`on_event` の `Hash`、要素の型の無い
  配列)。境界に載せる過程で直す。イベントの記録型を 1 つ書くと、`Hash` と書かれた 6 つの
  メソッドが埋まり、エディタの補完にもイベントのキーが出る。
- **進め方: 機能のまとまりごとに実装する。計測と重い回帰は要所だけにする (2026-11-14 ユーザ)。**
  長い計測や回帰が重なると全体の時間が大きくなるため。
  - まとまりは、描画の基本図形・文字・画像とスプライト・アプリと Window・時刻とログと
    クリップボード、の 5 つ程度。
  - 日々の確認は軽い回帰 (`rake regress`、約 17 秒) だけ。まとまりの終わりもこれで足りる。
  - 重い回帰 (`regress:screens`・`regress:run`・`regress:size`) は、段 (W4a・W4b など) の
    終わりに 1 回。ただしカーネルの標準の経路 (Spinel の基底・平らな関数) を触った
    まとまりだけは、その終わりに `regress:screens` を 1 回足す (エディタの 1 打鍵が入っている)。
  - 命令数の比較は、最初のまとまりで代表の関数を 2〜3 個 (`draw_text`・`draw_image` など) だけ
    測る。結果が見立てどおりなら、以後のまとまりでは測らない。
  - ESP32 での計測 (内蔵 RAM・flash・速さ・スタック) は W2 の 1 回と、最後の受け入れの 1 回。
  - 関数ごとにコミットを分け、落ちたときに原因を絞れるようにする (回帰の回数を減らす代わり)。
  - 印の無い関数は他の言語からまだ呼べないだけなので、途中の段階でも定義が 2 か所になることは
    無い。
- **ABI に版を付ける**。型定義から生成するので、版は型定義の内容から決める。

### 4. アプリの形と配り方

- アプリの包み: `.app.wasm` と `.app.toml` (言語と ABI の版を書く)。
- 起動の前に ABI の版と wasm の機能の組を確かめ、端末と合わないアプリは理由を出して断る。
- 入れる道:
  - **店** (`doc/app-distribution/`、完了済み): 正式な配布。`.app.wasm` も同じ店で配る。店がバイナリを
    正しく扱えるかを確かめる (picoruby の文字列でバイト列を扱うときの罠)。一覧に言語と ABI の版を出す。
  - **Console のファイル転送**: 開発中に PC で作ったものを端末へ送る。Console の許可表と記録に乗る。
  - **Asterism でのインストール**: 下の 5。
  - 開発の手早い道: Tab5 は今の `tab5_fs` の put → launch でも足りる。

### 5. Asterism の受け口 (インストールと checkpoint のイメージで共用)

- 受け口のサービスが Asterism で `begin` / `chunk` / `commit` を公開し、`caller:` で送り手を絞る。
  Zenoh の 1 回の上限 (4 KB) に合わせて分けて送る。端末の証明書による相手の確認がそのまま効く。
- 受け取ったものは種類に応じて処理する:
  - `.app.wasm` と `.app.toml` → 置いて、ランチャーの一覧に足す (インストール)。
  - checkpoint のイメージ → 着いた先で続きから起動する (doc/checkpoint の F5、決定 D13 と同じもの)。
- 店は「使う人が自分で選んで入れる」、Asterism は「管理する側 (Console・別の端末) が配る・移す」と
  向きで分ける。
- 受け口は checkpoint の F5 で作った (2026-11-04): 転送のアプリ
  `/usr/share/transfer/transfer.app.rb` が `<ノード>/transfer/inbox` に `check` / `begin` / `chunk` /
  `commit` / `status` / `cancel` を出す。W6 は種類の表に `.app.wasm` の種類を足し、`commit` で置き場所へ
  移してランチャーの一覧に足す処理を書く形になる。

### 6. 将来: wasm のアプリを checkpoint で運ぶ

- WAMR の上流には無い。本体がループを回す形なので、呼び出しの合間はアプリのスタックが空で、
  wasm のメモリ・書けるグローバル・表を写せば原理的には足りる見込み。
- 公開されていないグローバルを読む API が無く、WAMR の内部の構造に触るか、言語の側で公開する
  必要がある。今は作らない。

## 受け入れ条件

- P4・sim・ブラウザ版で、TinyGo・Rust・Zig のアプリが同じ `.app.wasm` のまま動く。
- その 3 言語の bindings は、`sig/*.rbs` から生成したものだけを使っている (手書きの bindings が
  無い)。生成の元になる定義は `sig/*.rbs` の 1 か所だけである。
- Lua・MicroPython・mruby のつなぎと Spinel の宣言も、同じ定義から生成したものを使っている。
- Ruby で実装されたライブラリとアプリに公開しない機能を除く API が、wasm と Lua のアプリから
  呼べる。
- Ruby のアプリの書き方が変わっていない (今のアプリが直さずに動く)。包みを通した呼び出しの
  mruby の命令数が今より増えていない。
- 包みと境界の関数を混ぜて呼んでも、フォントや文字の大きさがずれない。
- Ruby で書かれたライブラリと基底クラスが、包みを持つ関数について境界の関数を呼んでいる。
- wasm のアプリが、Ruby のアプリと同じ枠の Window でデスクトップに並ぶ。
- 終わらないループのアプリが、理由を出して止められる。
- 内蔵 RAM が増えない (`rake regress:size`)。今の回帰の道具 (`rake regress`・`regress:run`・
  `regress:screens`) が通る。重い方は各段の終わりと最後の受け入れで確認する。
- 店から `.app.wasm` のアプリを入れて動かせる。ABI の版か機能の組が合わないアプリは理由つきで
  断られる。
