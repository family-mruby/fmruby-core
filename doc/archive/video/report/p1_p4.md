## 2. 計画から変えたこと

### 動画に専用の canvas を持たせるのをやめ、canvas 内の矩形に置く形にした

計画では「動画は自分専用の canvas を 1 枚持つ」としていたが、アプリが
自分の窓とは別に canvas を作る道が Ruby 側に無く、作るとしたら窓の仕組み
(枠・移動・重なり) を二重に持つことになる。

実装は **VIDEO_OPEN に (x, y) を渡し、アプリの canvas のその位置へ毎コマ
書き込む**形にした。canvas の作業中の面に矩形だけを書いて確定させるので、
アプリが同じ canvas に描いた枠・ボタン・文字はそのまま残る。約束は一つだけ
「**再生中はその矩形の中に自分で描かない**」。

窓を動かせば動画も一緒に動く (canvas ごと動く) のも、この形の利点。

### 書き込みは表示タスクが行う

再生器は別タスクだが、**canvas のメモリには一切触らない**。復号し終えたコマ
を置いて知らせるだけで、canvas への転記と確定は表示タスクのループ
(`video_service`) が行う。合成器が前提にしている「canvas の書き手は一つ」を
崩さないため。

コマの受け渡しは 2 枚の枠の所有権 (空き/書込中/準備完了/使用中) で行い、
表示側が追いつかないときは古い準備完了を捨てる (落としたコマ数として数える)。

### 表示中の窓の可視状態には触らない

最初 `is_visible = true` を毎コマ立てていたが、これだと Ctrl+Tab で退避した
窓が動画のせいで復活する。**可視の管理はアプリ側に任せる**ように直した。

### Retro では即座に諦める

未知の命令は graphics-audio 側で `-1` になり、**ACK が返らない**
(`message_handler_task.c` は result==0 のときだけ ACK する)。つまり Retro で
`video_open` を呼ぶと同期待ちのタイムアウト (10 秒) までアプリが止まる。
そこで結び付け側を `FMRB_HW_MODERN` で囲い、**Modern 以外では通信せずに
nil を返す**ようにした。アプリは戻り値で分岐できる。

## 3. 実装で確定した事実

### Tab5 の SD (P1)

- 足: CLK=43 / CMD=44 / D0=39 / D1=40 / D2=41 / D3=42。**SDMMC の slot 0**。
- **挿抜検出の線は P4 に来ていない**。よって「検出できない = 挿さっている
  つもりで mount を試す」に変えた (空なら mount が失敗するだけ)。
- **SD の IO 電源は内蔵 LDO の 4 番**。これを起こさないとカードは応答しない。
  ここが今回いちばん見落としやすい点だった。
- 速度は高速モード、4 本線で試して駄目なら 1 本線へ落とす。
- `/sd` の道 (別名表・Ruby の File・fatfs 依存) は既にあったので、
  足すのは host の起こし方だけで済んだ。
- 起動時の SD 接続確認 (`sd_conn_check.c`) は SPI 専用なので、SDMMC の板では
  丸ごと外した (NC の足に SPI を出すため)。

### JPEG の復号 (P2)

- 出力は RGB565 を直接選べる。canvas と同じ並びなので変換は要らない。
- **出力の 1 行は 16 画素の倍数に切り上げられる**。転記のときは幅ではなく
  この歩幅で読む。高さも 16 の倍数に切り上がるので、確保はその分を見る。
- 入出力とも専用の確保関数が要る (整列の条件があり、素の malloc では駄目)。
  プロジェクトの決まりでは `fmrb_mem` を使うが、ここは**ハードウェアの
  条件が優先**なので専用の確保関数を使っている。
- 既存の `CREATE_IMAGE_FROM_FILE` は先頭が FFD8 なら JPEG として扱うよう
  分岐を足した。PNG の道はそのまま。
- ついでに、パスが `/sd` `/tmp` `/mnt` `/flash` で始まるときに `/flash/` を
  前置しないよう直した (今までは何でも flash の下に押し込んでいた)。

### コマの切り出し (P3)

`FFD8` から `FFD9` までを 1 コマとして読む。実体部の `FF` は `FF 00` に
詰め替えられ、再同期の印は `FFD0`〜`FFD7` なので、`FFD9` は末尾にしか
現れない。**ただし metadata の中に小さな JPEG (見本画像) を持つファイルは
この前提を壊す**。後述の変換手順はそれを作らない。

## 5. 使い方

### 素材を作る

```
ffmpeg -i source.mp4 -vf "scale=320:176,fps=15" -q:v 4 -f mjpeg demo.mjpg
```

- **縦横とも 16 の倍数**にする (復号器の格子。転記が素直になる)。
- 画面は 426x240 なので、窓の枠とボタンを置くと 320x176 くらいが上限。
- SD の `/sd/movie/demo.mjpg` に置く。カードは FAT32。
- **長いファイル名は LFN を入れてから**しか見えない (上記 8 の 3 件目)。
  古い firmware で試すなら `demo.mjp` のように 8.3 に収まる名前にする。
- 変換元が無いときは `ffmpeg -f lavfi -i "testsrc2=s=320x176:r=15:d=10"
  -c:v mjpeg -q:v 4 -pix_fmt yuvj420p -f mjpeg demo.mjpg` で試験素材を作れる。
  時刻とコマ番号が焼き込まれるので、画面 1 枚から再生位置が読める。

### デモアプリから

`/app/modern/video_play.app.rb` は起動時に `/sd/movie/demo.mjpg` を開き、
**「Open」で任意のファイルを選べる** (2026-08-20 追加)。選択は desktop の
ファイル選択を借りるので、答えは `on_control` に `file_selected` として届く。
**SD はファイル選択の中では `/mnt/sd`** の下にある (仮想の根に `/sd` は並ばない)。

コマ数はファイルに書かれていないのでアプリが決める。「15fps」の札は
**1 / 5 / 10 / 15 / 20 / 30** を巡回し (右ボタンで逆回り)、押した時点で開き
直して反映する。30 コマ秒の素材を 15 で再生すればゆっくり動くだけで、誤りでは
ない。1 コマ秒は素材を 1 枚ずつ眺めるのに使える。

低いコマ数を入れるにあたり、再生器の待ちを **20ms 刻み**にした
(`VIDEO_WAIT_SLICE_MS`)。停止・一時停止・巻き戻しは再生の輪の先頭でしか
見ておらず、開き直しは表示タスクが再生器の終了を待つ作りなので、1 コマ秒で
次のコマまでを一度に寝ると**表示タスクが最大 1 秒止まる** (合成も止まる)。

なお、**JPEG が 1 枚だけのファイルも開ける** (1 コマの動画として繰り返す)。
静止画がそのまま出るので、素材の色や大きさの確認に使える。

### Ruby から

```ruby
@video = @gfx.video_open("/sd/movie/demo.mjpg",
                         x: @user_area_x0 + 4, y: @user_area_y0 + 25,
                         fps: 15, loop: true)
if @video                      # Modern 以外・ファイルが無い場合は nil
  @video.play
  @video.pause
  @video.rewind
  st = @video.status           # { state:, shown:, dropped: }
  @video.stop                  # 終了時に必ず呼ぶ
end
```

再生中はその矩形の中に描かない。外側 (枠・ボタン・状態表示) は普通に描いてよい。

**位置は canvas の座標**なので、アプリが自分の描画に使っている原点
(`@user_area_x0` / `@user_area_y0`) から足すこと。定数だけを渡すと、窓枠の
ぶんずれてボタンの上に picture が乗り、毎コマ塗り潰される (作例が最初これで
壊れていた)。

## 7. 実機で確認した結果 (2026-08-19)

計画で挙げた確認項目は全て通った。

1. **SD の mount**: `SD card mounted at /sd (SDMMC 4-bit)`。SL16G / SDHC /
   15193MB / 40MHz。**足も LDO も机上の想定どおりで、直しは要らなかった**。
2. **色**: 元ファイルと画面の画素を突き合わせ、6 色すべて一致 (差は RGB565 の
   量子化ぶんのみ)。ただし最初は入れ替わっていた (下記 8 の 1 件目)。
3. **再生**: 320x176 / 15 コマ秒が動き続ける。実測 **14.77 コマ/秒**、
   21.3 秒で落としたコマは **1**。
4. **無線との同居**: 問題なし。**C6 との連絡も SDIO だが足が別**
   (無線 CLK[12] CMD[13] D0[11] D1[10] D2[9] D3[8]、SD 43/44/39-42) で、
   両方立ち上がったまま遠隔操作しながら再生できる。
5. **止め際**: Ctrl+Q で `Deleted window canvas 3` → `STOPPING` → `FREE`。
   起動と終了を 3 回繰り返して内蔵 RAM は 155,060 → 155,080 バイト、PSRAM は
   同値に戻る。**資源は完全に返る**。なお `stopping playback` のログは出ない
   (アプリの `on_destroy` が先に stop を投げ、canvas 削除の経路まで来ないため)。

## 8. 実機でだけ出た不具合 (5 件、いずれも修正済)

**どれも机上・ビルド・シミュレーションでは出ない種類だった**。
5 件目はファイル選択を付けたときに出たもので、同じ性質のため合わせて記す。

### 1. 色が入れ替わる — RGB565 のバイト順

症状は赤青の入れ替えではなく channel の回転 (赤→青、緑→赤、青→緑) で、
要素順の誤りでは説明できなかった。元ファイルの色と画面の画素を突き合わせると、
6 色すべてが「RGB565 をバイト順逆で読んだ場合の予測値」と一致した。

IDF の列挙値がそのまま答えで、`JPEG_DEC_RGB_ELEMENT_ORDER_BGR` が "small
endian"、`..._RGB` が "big endian" と定義されている。**RGB565 は 1 画素が
16bit 一語なので、この項目は要素順ではなくバイト順**。canvas はリトル
エンディアン (だから遠隔画面の符号化器は canvas メモリを順序指定なしで直接
食える) なので `BGR` が正しい。

上記 6 の「入れ替わっていたら BGR にする」という当初の想定は、症状の見立てが
違っただけで対処は同じだった。

### 2. 1 秒ほど再生して止まる — 1 バイトずつの読み出し

`read_next_frame` が `fgetc` で 1 バイトずつ読んでおり、1 コマ 9KB につき
9000 回の stdio 呼び出しになっていた。実測で **1 コマ約 40ms (約 220KB/s)**。
15 コマ秒に必要な 66ms/コマ を切っているように見えるが、復号と転記を足すと
間に合わず、遅れ判定の「復号せず読み飛ばす」経路に入る。読み飛ばしも同じ
速度なので**二度と追いつけない**。

- 16KB 単位のまとめ読みにして、走査は RAM 上で行う (`fseek` の際は緩衝も空に
  する。忘れると次のコマが化ける)。
- 遅れが 4 コマ分を超えたら時計を現在時刻へ合わせ直す。読み飛ばし続けて
  何も映らない状態に落ち込まないようにする。

### 3. 長いファイル名が見えない — fatfs の LFN が無効

`/sd/movie/demo.mjpg` が開けなかった。カードにもファームのパス処理にも問題は
なく、**`CONFIG_FATFS_LFN_NONE` (IDF の既定値) のせいで 8.3 名しか見えて
いなかった** (`demo.mjpg` は拡張子が 4 文字なので `DEMO~1.MJP` になる)。

`config/sdkconfig.defaults.p4` と Retro の 2 つに `CONFIG_FATFS_LFN_HEAP` +
`MAX_LFN=255` を足した。firmware の増分は 4752 バイト。名前は OEM の
codepage 437 のままなので、**長い名前でも ASCII のみ**。日本語のファイル名は
UTF-8 の API encoding と可変 codepage が要るので別件。

### 4. 状態の問い合わせが常に nil — payload の無い命令が受け口に届かない

`@video.status` が必ず nil を返していた。往復自体は成功しており
(`send_sync: timeout` は出ない)、応答が **0 バイト**だった。

原因は動画固有ではなく `display_p4_task.cpp` の入り口:

```c
case FMRB_LINK_TYPE_GRAPHICS:
    if (payload && payload_len > 0) {   // <- payload が無いと受け口を呼ばない
        int result = process_gfx_command(...);
        ...
    } else if (ack_required) {
        send_ack(type, seq, nullptr, 0);  // 空の ACK だけ返る
    }
```

`VIDEO_STATUS` は graphics 命令で唯一 payload を持たないため、常にここへ
落ちていた。**payload の長さで受け口を呼ぶかどうかを決めない**ように直した
(68 個ある case のうち `data` を触るものは全て先に `size` を確認しているので
安全)。今後 payload の無い命令を足しても黙って無視されない。

### 5. 選択したファイルを開けない — 表示側が自前でパスを組んでいた

デモアプリにファイル選択を付けたら、選んだ `/mnt/sd/movie/demo.mjpg` が
`cannot open` になった。カードもファイルも問題なく、`/sd/movie/demo.mjpg`
なら開ける。

原因は表示側のパス処理で、`/sd` `/flash` `/tmp` `/mnt` で始まるかどうかを
**自前の表で判定していた**こと。`/mnt` は「そのまま渡す」側に分類されるが、
VFS に `/mnt` という mount は無い。`/mnt/sd` を `/sd` に読み替える別名表を
持っているのは HAL (`fmrb_hal_file_resolve_path`) で、File もそれを通る。
つまり表示側だけが別の規則で動いていた。

3 か所 (VIDEO_OPEN / LOAD_SPRITE_BMP / CREATE_IMAGE_FROM_FILE) を HAL の
解決関数に寄せた。ついでに **CREATE_IMAGE_FROM_FILE は無条件に `/flash/` を
前置していた**のも直っている (SD の画像を `create_image_from_file` で開けな
かった)。**パスの規則を二か所に持たない**、というのがこの件の教訓。

## 9. 実測値 (P5 完了、2026-08-20)

### 段階ごとの内訳

再生器に常設の計装を入れた (`p4_video: profile ...` が 60 コマごとに出る)。
読みと復号は再生タスク、転記は表示タスクの計測で、いずれも 60 コマの平均と最大。

| 構成 | 置き場 | 読み | 復号 | 転記 | 合計 | 1 コマの持ち時間 |
|---|---|---|---|---|---|---|
| 320x176 @15 | SD | 8.2ms (最大 21.4) | 1.65ms (最大 3.1) | 7.3ms (最大 14.4) | 17.2ms | 66.7ms (26%) |
| 416x240 @15 | flash | 5.9ms (最大 11.6) | 2.1ms (最大 4.2) | 11.0ms (最大 12.3) | 19.0ms | 66.7ms (28%) |
| 416x240 @30 | flash | 7.5ms (最大 14.2) | 2.9ms (最大 5.8) | 11.9ms (最大 24.0) | 22.3ms | 33.3ms (67%) |

読めること:

- **復号は問題にならない**。全画面でも 3ms 弱で、ハードウェア復号器の
  取り分は全体の 1 割強しかない。
- **効くのは転記**。canvas への行ごとの写しに加えて、確定用の面へ canvas
  全体を写すので、**動画の大きさではなく canvas の広さに比例する**。全画面
  (426x240) では 11〜12ms で、ここが最大の一項。
- **読みは媒体で変わり、揺れも大きい** (SD は平均 8ms・最大 21ms)。16KB
  まとめ読みにした後でも最大値は平均の 2.5 倍まで振れる。flash (littlefs)
  の方が速く安定している。

### 大きさとコマ数の上限

- **416x240 / 30 コマ秒まで通る**。60 コマを 2.00 秒で処理しており、
  実測でも 30.0 コマ/秒を保つ。合成側も 140 コマ/5 秒 (平均 18ms) で追随する。
- 画面は 426x240 だが**幅は 16 の倍数**という復号器の条件があるので、
  実質の上限は 416x240 (全画面)。窓に入れるなら枠のぶん小さくなる。
- 30 コマ秒では**表示側が取りこぼす**: 60 コマのうち転記できたのは 53〜57 コマ
  (7〜11%)。落ちるのは合成が 33ms 間隔で回るためで、再生の時計はずれない
  (古い準備完了を捨てて新しい方を出す設計どおり)。**滑らかさを優先するなら
  15 コマ秒、動きの速さを優先するなら 30 コマ秒**という選び方になる。
- 実装上の上限は 448x256 / 1 コマ 512KB のままでよい (画面より広い)。

### そのほか (2026-08-19 の測定)

対象: 320x176 / 15 コマ秒 / 150 コマ / 1.3MB の試験素材、窓表示。

| 項目 | 値 |
|---|---|
| 再生速度 | 14.77 コマ/秒 (公称 15、-1.5%) |
| 落としたコマ | 21.3 秒で 1 |
| 繰り返しの継ぎ目 | 1 回あたり約 0.15〜0.26 秒 |
| 合成 | 86 コマ/5秒、平均 22ms / 最大 29ms |
| 内蔵 RAM (SD 追加ぶん) | +3KB (`gpio_led_proxy` → `littlefs_mount` の差) |
| 内蔵 RAM (再生中) | 空き 135,900B (待機時 155,060B) |
| firmware の増分 | LFN で +4752B |

測り方: 段階の内訳は上記の常設ログ。再生速度はアプリの状態表示に出る
`shown` を時刻つきで 2 点読む (画面に焼き込んだ時刻を読むより正確)。
試験素材は `testsrc2` に時刻とコマ番号が焼き込まれるので、画面 1 枚からでも
再生位置が分かる。

計測は Tab5 実機 (旧個体) で遠隔操作により実施。上限の確認だけは SD の抜き差し
を避けるため素材を flash に置いて行った (媒体が違うぶん、読みの値は SD より
速い側に出ている)。

## 10. 分かっている制限

- **同時に 1 本だけ**。2 本目を開くと 1 本目は閉じられる。
- **音は無い**。動画の音は別課題。
- 巻き戻しは先頭のみ。途中への飛び込みは索引が無いのでできない。
- 1 コマ 512KB / 448x256 画素を上限にしている。
- 再生器が読むのは表示側の経路なので、`/sd` が mount されていることが前提。
- ファイルの metadata に JPEG を含む素材は切り出しを誤る (上記 3 参照)。
