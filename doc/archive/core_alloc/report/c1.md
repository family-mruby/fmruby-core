## 2. 測り方

### 仕組み

- 試験用のビルドで FreeRTOS の実行時間の統計を有効にした。追加の defaults ファイル (scratchpad、下の 6 行) を
  `SDKCONFIG_DEFAULTS` の後ろに足し、別の build ディレクトリと別の sdkconfig で作った
  (`idf.py -B <scratch>/build -DSDKCONFIG=<scratch>/build/sdkconfig "-DSDKCONFIG_DEFAULTS=config/sdkconfig.defaults.naryav4;<scratch>/stats.defaults" -DFMRB_HW_TARGET=NARYAv4 build`)。
  リポジトリの sdkconfig と sdkconfig.defaults* は触っていない。

  ```
  CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=y
  CONFIG_FREERTOS_USE_TRACE_FACILITY=y
  CONFIG_FREERTOS_USE_STATS_FORMATTING_FUNCTIONS=y
  CONFIG_FREERTOS_VTASKLIST_INCLUDE_COREID=y
  CONFIG_FREERTOS_RUN_TIME_COUNTER_TYPE_U64=y
  CONFIG_FREERTOS_RUN_TIME_STATS_USING_ESP_TIMER=y
  ```

- 計装は `main/drivers/led_status/cpu_stats.c` (コミット済、既定では空の関数)。`CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS`
  が有効なビルドでだけ、`cpustat` タスク (core 0 固定、優先度 7) が 5 秒ごとに `uxTaskGetSystemState` を取り、前回との
  差を `cpu:` 行に出す。
  - `cpu: win=<ms> c0=<%> c1=<%> gone=<%> n=<タスク数> probe=<µs>`: c0/c1 は 100% からその core の IDLE を引いた値。
    gone は一覧のどのタスクにも乗らなかった時間 (窓の途中で消えたタスクと、取得の瞬間に走っていた分)。
  - `cpu: t <名前>/<core> <%> ...`: 0.1% 以上のタスクを大きい順に。core はタスクの固定先 (`-` は固定なし)。
- 時計は esp_timer (1 MHz)。タスクの切り替えのたびに計上されるので、**割り込みの時間は割り込まれたタスクに乗る**。
- 実行中の区間は次の切り替えまで計上されないので、1 つの窓の値は最大でその区間の長さだけ前後する (表示の描画 1 枚の
  CPU は 10-30 ms で、5 秒の窓の 0.6% 以下)。gone は (e1) の 1.7% を除いて 0-0.2%。

### 計装の負荷

| 項目 | 値 |
|---|---|
| `cpustat` タスク自身 (core 0) | 0.3-0.6% (5 秒に 1 回の取得と、3-4 行のログ出力) |
| `uxTaskGetSystemState` の時間 (probe) | 1.8-3.0 ms / 5 秒。この間 core 0 のスケジューラは止まる (全タスクのスタックの残りも歩くため) |
| タスク切り替えごとの計上 | 見えない。Breakout.py だけの場面で、計測版と develop 版の描画が同じ (137 枚/5 秒・平均 29 ms、presents 28.2-28.4/秒、どちらも) |
| 静的な D/IRAM | develop 125,612 B → 計測版 128,356 B (+2,744。FreeRTOS の統計の関数と TCB の欄)。既定のビルドは develop と同じ 125,612 B、.bin も同じ大きさ |

- 常設の 10 秒ごとのダンプ (デバッグモードの `fmrb_task:` と VM プール、status_led、core 1) は計測中も動いている。1 回 130 ms
  前後で、status_led の 1-3% はほぼこれ。全場面に同じだけ乗っている。

### 場面の作り方

- 板は P4-Nano (NARYAv4)、ミュートのまま。ファームは develop (`08350af6`) + 計装 + 上の sdkconfig。app 区画だけ書いた。
- 各場面 30-45 秒。表は 5 秒の窓 6-11 個の平均。
- 打鍵: 遠隔の入力 (`/ws`) で 100 ms ごとに `a`〜`h` と Backspace 8 回を 24 回 (384 打鍵、約 38 秒)。s1 と同じ台本。
- (b) エディタは `default/editor` を起動 (窓)、(b') は続けて F11 で全画面 (640x360 の高解像度モード)。
- (c) は s1 と同じ組み合わせ: `/app/demo/mml.app.rb`・`default/monitor`・`/app/game/breakout/breakout.app.py`・`default/shell`。
  MML はミュートで演奏中、Breakout.py は操作なし (ボールが動き続ける)。
- (d) は `flash/app/modern/video_play.app.rb` の写しで、読むファイルだけを板にある
  `/usr/share/samples/slides/movies/demo.mjpg` (288x160、30 枚、繰り返し) に変えたもの (`/home` に置いて起動、終了後に消した)。
- (e) は Breakout.py を動かした状態で、(e1) `curl` で `/stream` を 36 秒受け続ける (tab5_screenshot と同じ MJPEG の経路。
  受けたのは 6.9 MB、約 190 KB/秒)、(e2) `/ws_video` に WebSocket でつないで 36 秒受ける (ブラウザの遠隔デスクトップと
  同じ H.264 の経路。517 フレーム、14.4 フレーム/秒、7.3 KB/秒)。

## 3. 表示 (display_p4) の描画: 経過時間と CPU

既存の `display_p4: render:` 行 (描画 1 枚の経過時間、tick 単位) と、今回の CPU の割合を並べた。

| 場面 | 描画 枚/5 秒 | 1 枚の経過時間 平均 (最大) | 経過時間の合計 / 5 秒 | display_p4 の CPU | 1 枚あたりの CPU |
|---|---:|---:|---:|---:|---:|
| (a) 待機 | 5 | 27 ms (30) | 3% | 1.5% | 15 ms |
| (b) エディタ (窓) | 38 | 29 ms (34) | 22% | 9.0% | 12 ms |
| (b') エディタ (全画面) | 36 | 33 ms (62) | 24% | 21.4% | **30 ms** |
| (c) アプリ 3 本 + Shell 打鍵 | 122 | 35 ms (50) | **85%** | **28.9%** | 12 ms |
| (c) 打鍵なし | 128 | 34 ms (43) | 87% | 26.3% | 10 ms |
| (d) 動画 15fps | 83 | 29 ms (45) | 48% | 22.5% | 14 ms |
| (d') 動画 30fps | 116 | 30 ms (35) | 69% | 33.4% | 14 ms |
| (e0) Breakout.py | 137 | 29 ms (33) | 79% | 25.8% | 9 ms |
| (e1) + MJPEG 配信 | 117 | 37 ms (49) | 86% | 40.3% | 17 ms |
| (e2) + H.264 配信 | 118 | 37 ms (44) | 87% | 38.7% | 16 ms |

読み方:

- **経過時間の合計 (s1 の「85-90%」はこれ) と CPU は別物**。(c) では描画が 5 秒の 85% を占めるが、display_p4 が CPU を
  使っているのは 29% で、残りの 2/3 は眠っている。合成は PPA を `PPA_TRANS_MODE_BLOCKING` で呼んでいる
  (display_backend_ppa.cpp) ので、PPA の完了待ちで眠っている時間と見ている (どこで待っているかは測っていない)。
  眠っている間は同じ core の低い優先度のタスクが動ける。
- 1 枚あたりの CPU は 9-17 ms。例外は全画面・高解像度のエディタ (b') の 30 ms で、経過時間 33 ms のほとんどが CPU。
  この形の合成は待ちではなく計算で時間を使っている。
- 遠隔の配信中は 1 枚あたりの CPU が 9 → 16-17 ms に増え、display_p4 が core 1 の 26% → 39-40% になる (画面の写しを
  配信用に作る分。MJPEG と H.264 でほぼ同じ)。

## 4. Shell の打鍵の遅れ (c)

s1 の計装 (host と app.c の C の変更、lib/ の再ビルドが要る) は使わず、Shell の Ruby だけに一時的な計装を入れて測った
(コミットしていない。差分は scratchpad の `c1/shell_lat_probe.diff`)。

- **e2d**: Shell の `on_event` が打鍵を受けてから、その打鍵を含む描き直しの `present` を送り終えるまで。
- **届きの遅れ**: 打鍵 i が `on_event` に届いた時刻 − (最初の打鍵の時刻 + i × 100 ms)。送る側は 100 ms 間隔で送るので、
  これの最小値を「いちばん早く届いた場合」とみなし、そこからの差を遅れとした。host・app の列での待ちと、WiFi の揺れの
  両方が入る。

| 条件 | e2d 平均 / 最大 | 届きの遅れ 平均 / 最大 (全体) | 同 (後半 15 秒) |
|---|---:|---:|---:|
| (c) アプリ 3 本 + Shell | 15 ms / 113 ms | 236 ms / 642 ms | 165 ms / 642 ms |
| (c) の 2 回目 | 18 ms / 137 ms | 230 ms / 555 ms | 146 ms / 373 ms |
| 対照: Shell だけ | 14 ms / 61 ms | 254 ms / 761 ms | 177 ms / 761 ms |

読み方:

- **届きの遅れは、アプリ 3 本があってもなくても同じ**。どちらも最初の 15 秒ほどで早まっていく傾向 (送る側か WiFi の
  立ち上がり) があり、ばらつき (数百 ms) は経路の揺れが主で、負荷の差を読める分解能が無い。
- 負荷で変わったのは e2d の最大 (61 → 113-137 ms) だけ。平均は 14 → 15-18 ms。
- s1 の負荷時の 2.5-6 秒は、この計測では出なかった。s1 の後に、割り当て器 (estalloc) の解放ごとの全走査が止められ
  (doc/shell_input_lag の S2 系。負荷時の 50 ms 超えの打鍵 98% → 10%)、その分の違いの可能性が高い (同じビルドでの比較はしていない)。
- 打鍵 1 回で Shell は core 1 を約 5 ms 使う ((c) と「打鍵なし」の FM-Shell の差 5.1% × 5 秒 / 50 打鍵。描き直しと GC を含む)。

## 5. 表示を core 0 へ移したらどうなるか (見込み、試験はしていない)

display_p4 の CPU 時間が移った先でも同じだけかかり、ほかのタスクはそのまま、とした単純な足し算。

| 場面 | core 0 今 | core 0 移した後 | core 1 今 | core 1 移した後 |
|---|---:|---:|---:|---:|
| (a) 待機 | 4.1 | 5.6 | 4.0 | 2.5 |
| (b) エディタ (窓) | 11.4 | 20.4 | 14.9 | 5.9 |
| (b') エディタ (全画面) | 13.8 | 35.2 | 26.3 | 4.9 |
| (c) アプリ 3 本 + Shell | 17.2 | 46.1 | 50.9 | 22.0 |
| (d') 動画 30fps | 16.7 | 50.1 | 37.5 | 4.1 |
| (e0) Breakout.py | 9.5 | 35.3 | 32.0 | 6.2 |
| (e1) + MJPEG 配信 | 31.6 | **71.9** | 50.9 | 10.6 |
| (e2) + H.264 配信 | 13.4 | 52.1 | 49.2 | 10.5 |

読み方と注意:

- **平均の量では、core 0 は足りる**。MJPEG 配信 (e1) 以外は 52% 以下。core 1 は 2-22% になり、アプリの VM にほぼ丸ごと空く。
- ただし core 1 は今でも半分近く空いているので、**移して増えるのは「空き」の量より「表示に割り込まれない」こと**の方。
  優先度 5 の display_p4 は今、同じ core の VM (2-3) に対して、1 枚 9-30 ms の計算を割り込みなしで続けられる。
- core 0 では display_p4 (5) の上に host (10)・audio_p4 (6)・hw_proxy (6)、同じ 5 に USB host / HID・rd_httpd がいる。
  - 描画 1 枚の途中で host と音の処理に割り込まれる。描画の時間は少し伸び、ぶれる見込み (音は上なので影響を受けない)。
  - 同じ優先度の USB の入力処理とは順番待ちになる。1 枚 9-30 ms の計算の間、USB の処理が tick の区切りまで待つ
    可能性がある (入力の遅れとして出るなら `spx: hid_lat` で見える)。
  - rd_mjpeg (4)・p4_video (4)・BLE (4) は display_p4 より下になる。(e1) では core 0 に display 40% と rd_mjpeg 11% が
    同居して 72% になり、MJPEG の枚数が落ちる見込み。MJPEG は開発用の道具 (tab5_screenshot) の経路で、ブラウザの
    遠隔デスクトップは H.264 (e2) の方。
- 表示の経過時間の大半は PPA の待ちなので、core を移しても描画 1 枚の時間はほとんど縮まない (CPU の部分が割り込まれる
  分、むしろ伸びうる)。
- 非固定のタスク (tiT・sdio_write など。e1 で計 8%) は今ほぼ core 0 で走っている。移した後は空いた core 1 に寄る見込み。
- 割り込みは core 0 に寄っている (esp_timer の割り込みも core 0 の設定)。その時間はすでに core 0 の数字に入っている。

## 6. 見立てと違った点

- **「表示が core 1 の 85-90% を使う」は経過時間の見積もりで、CPU は 26-29%**。core 1 は (c) でも約半分が空いている。
  s1 の負荷時の遅れ (2.5-6 秒) は「core 1 が埋まって Shell が CPU をもらえない」というより、当時の Shell の重い処理
  (GC と、後で分かった割り当て器の全走査) が表示に細かく割り込まれて引き伸ばされたもの、と読み直すのが数字に合う。
- アプリの VM 自体は軽い: Breakout.py 3-4%、Monitor 6%、MML 0.3%、Shell は打鍵中 9%。
- 全画面・高解像度のエディタは、描画 1 枚の CPU が 30 ms と、ほかの場面の 2-3 倍。
- 遠隔の画面の配信は display_p4 の CPU を 1.5 倍にする。
- audio_p4 はミュート中も合成を続けている (2.6-7.4%)。

## 7. 計測版の注意: 大きなファイルの書き込みで落ちた

- 計測版で 352 KB のファイルを `/fs/put` で `/home` に書いたところ、**2 回とも core 0 が `Instruction access fault` で落ちた**
  (MEPC はどちらも flash 上の普通のコード: 1 回目 `mruby_tick_task` (task_hal.c:154)、2 回目 `apu_process` (nes_apu.c:1015)。
  2 回目は Net::HTTP が PUT を自動でやり直したもの)。6 KB 以下の書き込みは問題なかった。
- 同じ 352 KB の書き込みは develop 版 (計装なし) では通った (1 回)。develop の defaults には `CONFIG_SPI_FLASH_AUTO_SUSPEND=y`
  が入っているので、**実行時間の統計 (タスク切り替えのたびの計上) と flash の自動中断の組み合わせ**で起きている疑いがあるが、
  原因は追っていない。
- 計測の場面は書き込みを避けて組み直した (動画は板にあるファイルを読む)。計測版を使うときは大きな書き込みをしないこと。
  develop の動作には関係しない (既定のビルドには統計が入らない)。

## 8. 案 (この段階では何も変えていない)

1. **C2 の前に、困りごとがまだあるかを確かめる**。今回の計測では、アプリ 3 本 + Shell の打鍵が Shell だけのときと区別
   できなかった。ユーザが USB キーボードで (c) の組み合わせを打って、遅れを感じるかを見るのが先。感じなければ C2 の
   優先度は下がる。
2. 割り振りを変えるなら、**display_p4 を core 0 へ**は平均の量では成り立つ (core 0 は 52% 以下、MJPEG 配信だけ 72%)。
   試すときは同時に次を測る: core 0 の USB 入力の遅れ (`spx: hid_lat`)、描画 1 枚の時間のぶれ、MJPEG の枚数。
   MJPEG の rd_mjpeg (4) を core 1 へ移すかどうかも一緒に決める。
3. 表示の CPU を減らす候補: 全画面・高解像度の合成 (1 枚 30 ms) と、配信用の画面の写し (+7-8 ms/枚)。こちらは core を
   変えずに両方の core に効く。
4. 計装 (`cpu_stats.c`) は既定で無効のまま残した。C2 で割り振りを変える前後の比較に同じ物差しで使える。7 の問題があるので、
   使うときは大きな書き込みを避ける。
