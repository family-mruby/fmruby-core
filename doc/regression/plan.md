# 回帰の確認を、安く・コマンド 1 つで

> 状態: 計画済 | 更新: 2026-10-25 | リファクタリングや機能の直しのたびに、サブエージェントが sim・ブラウザ版を立ち上げて画面を撮り、ゲームホストを手で動かして前後を見比べている (app_refactor の R4〜R6 で 1 段 30〜45 万トークン、その多くが確認の往復)。確認を「コマンド 1 つ、結果は短い要約」にして、トークンと人の手間を減らす (2026-10-25 ユーザ)

## 1. 目的

- 「振る舞いを変えない」直しの確認を、決まったコマンドで機械的に済ませる。人 (とエージェント) が見るのは落ちたものだけにする。
- 結果は短い要約 (通った数・落ちた数・落ちたものの場所) にし、画像や長いログは場所だけを返す。エージェントが読む量を小さくする。
- 安い確認ほど先に、頻繁に回す (ホストの Ruby → 描画の記録 → sim・ブラウザ版の画面 → ゲームホストとの通し → 実機)。

## 2. 今あるもの

| 層 | もの | 費用 |
|---|---|---|
| ホストの試験 | `rake test` (Link・TableClient・FmrbToml・FmrbText・一歩の検知・サービス・関連付け・型の db ほか)。CI の test-host ジョブ | 安い (docker も sim も要らない) |
| 描画の記録 | `tools/mahjong_overflow/check.rb` (`rake mahjong:overflow`): 麻雀のアプリのファイルを CRuby に読み込み、描画を記録する代役で全場面を描き、はみ出し・重なりを検査。`--dump` で記録を書き出せ、R5 では記録の前後比較 (210 ファイル一致) で画面を撮らずに確かめた | 安い |
| 画面と入力の道具 | `tools/fmrb_screenshot.py`・`fmrb_input.rb` (sim)、`fmrb_web.rb` (ブラウザ版)、`fmrb_pngdiff.rb`・`fmrb_pngscan.rb`、MCP の sim_*・web_* | 中 (sim・ブラウザを起こす)。組み合わせは毎回手作業 |
| ゲームホスト | asterism-games を手元で起こす (`rake mahjong:up` など)、端末のクライアント `asterism-games play ...` | 中〜高。毎回手で操作 |
| 実機 | serial_* / flash / tab5_*、起動ログの要約 (flash ツールの boot summary) | 高 (人の手も要る) |

## 3. 方針

| 段 | 内容 |
|---|---|
| RG1 | **描画の記録の比較を広げる**: 麻雀の check.rb の仕組み (アプリのファイルを CRuby に読み、描画を記録する代役、決まった場面の台本) を共通の道具にし、オセロの卓・ボード・walk_scroller・FmrbUI の画面 (デスクトップのダイアログ、ランチャーなど mruby で動くもの) に広げる。記録を基準 (git に入れる) と比べ、違えば差分の行を出す。基準の更新もコマンド 1 つ (`rake regress:update` のような形)。sim を起こさないので CI でも回す |
| RG2 | **台本で動かす画面の比較**: 「アプリを起動 → キー・クリックを送る → 撮る」を台本ファイル (Ruby か TOML) に書き、`rake regress:screens` で sim (Modern・Retro) とブラウザ版を順に動かして基準の PNG と画素で比べる。時計・秒数など変わる部分は台本で隠す範囲を書ける。出力は「通った N / 落ちた M」と落ちた場面の差分画像の場所だけ |
| RG3 | **ゲームホストとの通し**: 手元のゲームホストを立て、CPU 同士や端末のクライアントで、一覧 → 入る → 打つ/描く → ホストを止めて戻す → 出る、を自動で流し、卓の状態 (ホストの記録) と端末のログで確かめる。オセロ・ボード・麻雀。R4a/R4b でサブが手でやっていた部分 |
| RG4 | **実機の起動の確認**: 起動ログを前回の基準と比べる (crash マーカー、M1| の内蔵 RAM の段の値、周期ダンプの IRAM free、タスクの stack high-water) のを 1 コマンドに。実機を使ってよいときだけ |
| RG5 | **入口をそろえる**: `rake regress` (RG1 + ホストの試験、安いものだけ)、`rake regress:full` (RG2・RG3 も)。サブの指示書の「確認」の節の型を「`rake regress` を流し、落ちたものだけ見る」に変える (fmrb-dev-flow の skill と CLAUDE.md の案内も) |

- 順番は RG1 → RG5 (入口だけ先に作ってよい) → RG2 → RG3 → RG4。
- 基準 (記録・PNG) は git に入れる。大きくなりすぎるなら PNG は外し、記録の比較を主にする。

## 4. 決まり・気をつけること

- **基準を勝手に更新しない**: 落ちたときに基準を更新してよいのは、変化が意図したものだと人が確認したときだけ。指示書にも書く。
- **決まった結果になるように**: 時刻・乱数・WiFi の状態など揺れるものは固定するか隠す (麻雀の check.rb は偽のホストと固定の場面)。揺れる試験は信用されなくなるので、揺れたら直すか外す。
- **アプリの作りに手を入れすぎない**: 記録の代役で読めない作り (FFI を直接呼ぶ、Spinel 専用など) は、まず道具の側で受ける。アプリに試験用の分岐を足すのは最後の手段。
- **内蔵 RAM・ファームに影響しない**: 道具はホストと tools/ に置く。ファームに試験用の仕組みを足す場合は別に決める。
- 実装はサブ、親が検収 (fmrb-dev-flow)。段ごとに instruction_rgN.md と report/rgN.md。

## 5. 受け入れ条件 (案)

- RG1 の後: オセロの卓・ボード・walk_scroller・FmrbUI の主な画面が記録の比較に入り、`rake regress` が CI で回る。わざと 1 画素ずらした直しで落ち、元に戻すと通る。
- RG2 の後: 台本で 5 アプリ以上の画面を sim とブラウザ版で比べられ、時計などの揺れで落ちない (同じ版で 3 回流して全部通る)。
- RG3 の後: 3 つの卓のアプリの通しが自動で流れ、ホストを止めて戻す場面を含む。
- 全体: 「振る舞いを変えない」直しの確認が、サブの指示書で `rake regress` (と必要なら `:full`) を流すだけになり、確認にかかるトークンが目に見えて減る (次のリファクタリングで前後を比べる)。
