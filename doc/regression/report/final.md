# RG 最終報告: 回帰の確認の道具と、トークンの節約の見積もり

> 状態: 完了 | 更新: 2026-10-26 | RG1〜RG6 で作った回帰の確認の道具 (`rake regress` とその仲間) のまとめ。道具の一覧・分からないこと・端末を足す手間・受け入れ条件・残件と、plan.md 5b 章の決め方 (再計測はせず、今ある記録だけで数える) によるトークンの節約の見積もり。見積もりの要点: 道具の前の段 (R4a・R4b・R5) では使ったトークンの約 7 割が確認だった。R6 では道具のおかげで約 3,800 万トークン (読み直しを含む累計) を使わずに済んだと見積もる。道具を作るのにかかったのは約 1 億 4,200 万で、R6 並みの段なら 4 段ほど、異常系の確認が手に残る段なら 7〜10 段で元が取れる

## 1. 要点

- **何を作ったか**: 「振る舞いを変えない」直しの確認を、決まったコマンドを流して短い要約を読むだけで済ませる道具 (2 章)。安い順に、ホストの Ruby で描画の記録を比べる `rake regress` (20 秒・2 行)、ファームの大きさと内蔵 RAM の `rake regress:size`、sim の VM プールの `rake regress:run`、sim とブラウザ版の画面を画素で比べる `rake regress:screens`、相手 (ゲームホストなど) を道具が立てて流す `rake regress:live`、実機の起動ログを比べる `rake regress:boot` がある。
- **道具の前の確認の費用** (R4a・R4b・R5 のサブの記録から数えた): 確認のためのツール呼び出し 1 回あたり **13〜16 万トークン** (その時点の文脈の読み直しを含む)。画面の写し 1 枚 (撮るための操作を含む) あたり **31〜36 万**。段全体の **71〜72%** が確認だった。
- **R6 での節約**: 道具が無ければ、画面の前後の写しが 118 枚ほど (59 場面 × 前後)、端末 3 台のサイズの比べ、VM プールのログ読みが要った。合わせて **約 4,400 万** (幅 2,900 万〜7,100 万) と見積もる。実際にそれを受け持った道具の分は **約 600 万**。差し引き **約 3,800 万** (幅 2,300 万〜6,500 万) が節約になり、R6 は実際の 4,070 万に対して、道具が無ければ 8,000 万ほどかかった見込み。
- **1 回の直しあたり**: 前は、確認を 1 巡するだけで画面の写し数十枚、つまり **1,000 万〜2,000 万**かかった (R6 の最初の試みは、Modern とブラウザ版の「前」の写しの半分だけで 941 万を使った)。今は `rake regress` 1 回で **約 25 万** (その時点の文脈を 1 回読み直す分) になる。R6 は `rake regress` を 8 回流しても 200 万で済んでいる。
- **元が取れる点**: RG1〜RG6 の合計は累計で **1 億 4,200 万** (ハーネスの表示では 166 万。数え方の違いは 5.1)。R6 並みの段 (画面の確認がほぼ道具に移る) なら **4 段ほど**で取り返せる。R4a・R4b のように異常系の手の確認が残る段なら **7〜10 段**。app_refactor (7 段) の大きさのテーマ 1 つ分にあたる。
- **言えないこと**: 道具なしで R6 をやり直してはいない。R6 の「道具が無ければ」の数は、R6 の最初の試み (道具の前に始めて 15 分で止めたもの) の進み方と、R4a〜R5 の 1 枚あたりの費用から組み立てた見積もりである。また R6 の時点では画面の比較 (RG2) と相手のいる通し (RG3) はまだ無く、R6 は写しを 19 枚手で撮っている (5.4)。

- build/ は道具が退避して戻すので、作業中のビルドを壊さない。
- 使い方の詳細は [usage.md](../usage.md)。

## 3. 道具で分からないこと

| 道具 | 分からないこと |
|---|---|
| 描画の記録 (`rake regress`) | 本当の画素 (字形、角丸の描き方、合成、透過色)。記録は「何をどこに描くよう頼んだか」まで。音、実機の入力、表示の後段 (HDMI・NTSC)。Spinel のプログラム (デスクトップ・エディタ・シェル。CRuby では読めない) |
| 画面 (`regress:screens`) | 音、実機の入力、表示の後段、実機だけの初期化。Retro の実機は WROVER の側で描くので、その画素は見ていない。時計の中身 (隠している) |
| 相手のいる通し (`regress:live`) | 本当の網の揺れ (遅延・切断の途中)、TLS と資格情報の付いた接続 (VPS・常設の卓)、ブラウザ版の ws の経路、Retro。HTTP の相手 (天気のアプリは外の HTTPS に決め打ちで、偽の相手に向ける口が無い)。音の善し悪し (鳴ったか・長さだけ)。MIDI の時刻は PC に届いた時刻 |
| sim の VM プール (`regress:run`) | 起動ログの M1\| (Linux のビルドは出さない) と周期ダンプの IRAM free (sim では出ない)。閉じた直後のカーネルの使用量 (ごみを集めたかで 40 KB 動くので比べない) |
| 実機の起動 (`regress:boot`) | 基準があるのは P4-Nano だけ。起動の秒数と VM プールは表に出すだけで比べない |
| 全体 | 音の官能評価、実タッチ、操作感。これらは今までどおり人が見る |

## 4. 端末を 1 台足すときの手間

**今**:

1. `tools/regress/targets.rb` に 1 行足す (名前・種類・画面の大きさ・config・ファームの種類・つなぎ方)。
2. `rake regress` を流すと、新しい画面の大きさなら「基準が無い」と出る。記録を読んで `rake regress:update`。画面の大きさが既存の組と同じなら、記録は 1 つも増えない (Tab5・NARYAv4・ブラウザ版は 1 組を共有している)。
3. `rake regress:size ONLY=<端末>` (2 分) → `rake regress:size:update`。
4. 実機をつないだときに `rake regress:boot:calibrate BOARD=<端末>` (2〜3 分、10 行) → 要約を読んで `APPLY=1`。

- 一度きりの手間はコマンド数回と記録の読み取りで、トークンにすると数十万〜200 万ほど (読む記録の量による)。**その後の各段の確認では、端末が増えても要約の行数がほとんど増えない**。サイズの表が 1 行増え、描画の記録の本数が増えても `rake regress` の出力は 2 行のまま。増えるのは道具の走る時間 (`ALL=1` で 1 端末 2 分ほど) だけ。

**前**:

- 段ごとに、サブが端末ごとに `rake clean_all` → `FMRB_HW_TARGET=<端末> rake build:esp32` → `idf.py size` を前後で回して表を手で作っていた。R4a (3 端末) でこの分が 261 万、R4b (2 端末) で 222 万。**1 端末を足すたびに、各段で 90〜110 万が増える**計算になる。
- 新しい画面の大きさの端末は、画面の前後比較の組がその大きさの分だけ増える (1 組 70 万ほど、5.2)。実際には StickS3 (240x135) と AtomS3R (128x128) の画面は app_refactor の各段で一度も見られていなかった。今は描画の記録でこの 2 つの大きさも毎回比べている。
- 実機の起動ログは、シリアルのログを人かエージェントが読んで、前の値と見比べていた。

## 5. トークンの節約の見積もり

### 5.1 数え方

**データの出どころ**: このセッションのサブの記録 (トランスクリプト、`subagents/agent-<id>.jsonl` と、どの段かを示す `.meta.json`)。使ったのは R1〜R6・RG1〜RG6 の記録と、R6 の最初の試み (後述)。新しく計り直したものは無い。記録は大きいので、Ruby の小さなスクリプトで集計した (スクリプトは作業用の場所に置き、リポジトリには入れていない)。

**1 回の呼び出しの費用**: サブの API 呼び出し 1 回ごとに、記録には使用量 (新しい入力・読み直した文脈 (cache read)・文脈の書き込み (cache creation)・出力) が残っている。その和を「その呼び出しの費用」とした。エージェントは呼び出しのたびにそれまでの文脈を全部読み直すので、この和は **その時点の文脈の読み直しを含む**。ツールを 1 つ呼ぶと、その結果を読むためにもう 1 回の呼び出しが要る。そこで、ツールを呼んだ API 呼び出しの費用を、そのツール呼び出しの費用とした (1 回で複数のツールを呼んだときは等分した)。こうすると、段の全部の呼び出しの費用の和が、段の累計にちょうど一致する。

**ハーネスの数字との関係**: 頼まれたときに示された数字 (R4a 約 32 万、RG1 約 46 万など) は、**最後の呼び出しの文脈の大きさ**であって、使った量の累計ではない。記録の最後の呼び出しの使用量の和を取ると、どの段もこの数字と一致した (R4a 32.2 万、R4b 30.2 万、R6 34.8 万、RG1 45.8 万など、6 章の表)。累計はその 100 倍ほど (R4a は 3,941 万) になる。この報告では、効果を数えるのに累計を使う。確認の呼び出しが 1 回減れば、その時点の文脈 1 回分 (十数万) の読み直しが減るからである。

**値段に寄せた数え方 (参考)**: 累計の大部分は文脈の読み直しで、値段は新しい入力の 1/10 ほどになる。そこで、読み直し 0.1・書き込み 1.25・新しい入力 1・出力 5 の重みを付けた数 (以下「重み付き」) も併記した。重み付きでも、確認の割合と節約の割合はほぼ同じになった (5.2・5.4)。

**確認の呼び出しの分け方 (規則)**:

| 分類 | 入れたもの |
|---|---|
| 画面 | MCP の sim_*・web_* (起動・撮影・入力・アプリの起動と停止)、画像ファイルの Read、Bash の `fmrb_input`・`fmrb_web`・`fmrb_screenshot`・`fmrb_pngdiff`・`fmrb_pngscan`・`fmrb_dbg_client`、sim の docker compose・`docker start/stop`、確認のための `rake build:linux`・`wasm:*`、前後比較のための写しの保存 (`sim_screen.png` の cp) と前の版のアプリの置き場 (`tmp_r4a` など) |
| サイズ | `idf.py size`・`esp_idf_size`・size-components・size-files、比べるための `rake build:esp32` (clean_all を含む)、それを回すスクリプト (`ram.sh`・`sizes.sh`) |
| 相手 | ゲームホスト (`asterism-games`) の起動・停止、打ち手の台本、zenohd の停止・再開、SIGSTOP、MIDI のモニタ、音の探り |
| ログ | `docker logs`・`docker exec`、ログファイルの grep・tail、`docker ps`・`pgrep` などの状態の確認 |
| 道具 | `rake regress*`、`tools/regress/` (R6 以降。RG の段では道具そのものを作って試す呼び出し) |
| ホストの試験 | `rake test`、`table_run.rb`、`rake mahjong:overflow` と `--dump` の比較、`spinel:doctor` |
| その他 | ソースの読み書き (Read・Edit・Write)、grep、git、ツールの読み込みなど |

- 「確認」として数えたのは画面・サイズ・相手・ログの 4 つ。ホストの試験は道具の前から安く回っていて、道具で置き換わったものではないので外した (R4a〜R5 で 200〜420 万。入れると確認の割合は 76〜78% に上がる)。
- 確認のための台本を Write で書いた呼び出しや、ビルドの終わりを待つ呼び出しの一部は「その他」に落ちている。したがって確認の割合は少なめに出ている。
- 確認の結果 (写しやログ) は文脈に残り、その後の実装の呼び出しの読み直しも膨らませる。この分はその後の呼び出しの側に数えられ、確認の分には入っていない。これも確認の費用を少なめに見せる。

### 5.3 R6 で道具が無ければ要った確認

**手がかり: R6 の最初の試み**。R6 は最初、道具の前の指示書 (「5 アプリと FmrbUI を使うもの (デスクトップのダイアログ、エディタ、シェル、NSF・SMF プレイヤ、appstore)、長い文字 (ja/en) を、sim の Modern・Retro とブラウザ版で前後の画素を比べる」) で始め、15 分で止めて RG1 に移った。その 15 分の記録が残っている:

- 91 回の API 呼び出しのうち、画面の呼び出しが 111、累計 941 万、画像 47 枚。最後の文脈は 23.6 万。
- その間にしたのは、**Modern の「前」の写し 24 場面とブラウザ版の「前」の写し 6 場面の保存だけ**だった。コードはまだ 1 行も変えておらず、5 つの載せ替えるアプリと Retro にはまだ手を付けていない。
- 1 枚あたり 20 万 (文脈がまだ小さい段の初めなので、R4a〜R5 の 31〜36 万より安い)。

**道具が無ければ要った回数の見積もり**:

| 確認 | 回数 | 根拠 | 見積もり (累計) |
|---|---|---|---|
| 画面の前後 | Modern 34 場面 (最初の試みの 24 + 5 アプリ × 2)、ブラウザ版 8 (最初の試みの 6 + 2)、Retro 17 (Modern の半分。R5 の Retro は Modern の 13 組に対して 6 組だった) → 59 場面 × 前後 = 118 枚 | 最初の試みの場面の一覧と指示書 | 118 枚 × 31〜36 万 = **3,660 万〜4,250 万** (中ほどを 3,900 万とする) |
| サイズ | 指示書の 3 端末 (Tab5・Retro・StickS3) の前後 | R4a が同じ 3 端末で 261 万 | **260 万** |
| Spinel のプログラムごとの内蔵 RAM | R6 の止まる条件 (1 本あたり 16 B まで) を確認するには size-files を TU ごとに読む必要があった | 3 回ほどと仮定 | **50 万** |
| VM プール | 30 秒ごとのログを読んで前後を比べる (R4a〜R5 のやり方) | R4a〜R5 のログの分 110〜370 万 | **150 万** |
| 合計 | | | **約 4,400 万** |

- 幅: 下は、R5 並みに 40 組 (80 枚) に絞り 1 枚 31 万とした場合で 2,500 万 (+ サイズほか 460 万 = 2,900 万)。上は、R6 の実際の文脈の大きさ (R6 の手の写しは 1 枚 56 万だった) で 118 枚を撮った場合で 6,600 万 (+ 460 万 = 7,100 万)。
- 数えていないもの: 画面の確認で見つかった違いを調べる往復 (R5 では時計・秒数・前の版の並びの違いを除くための撮り直しがあった)、文脈が大きくなりすぎたときの要約し直し。どちらも道具なしの側を重くする向きなので、見積もりは少なめである。

### 5.4 実際に使った分と、R6 の節約

R6 の記録 (API 呼び出し 168、最後の文脈 34.8 万、累計 4,070 万) の確認の分:

### 5.7 前提と言えないこと

- **やり直してはいない**: 道具なしで R6 を、道具ありで R4a〜R5 をやり直してはいない。「道具が無ければ」の数は見積もりである。
- **作業の大きさの違い**: 段ごとに作業の中身が違う。だから段全体の使用量ではなく、確認の呼び出しの数とその単価で比べた (plan.md 5b 章)。R6 の全体 (4,070 万) が R5 (6,290 万) より小さいのは、作業が小さかったからではない。R6 は 5 アプリと共通部品と Spinel を扱った大きな段で、手の画面の写しが少なかったからである。
- **単価の揺れ**: 1 回の呼び出しの費用は、その時点の文脈の大きさで決まる (段の初めは安く、終わりは高い)。写し 1 枚あたりは、段の初めの 20 万 (R6 の最初の試み) から、文脈の大きい R6 の 56 万まで動く。見積もりは R4a〜R5 の 31〜36 万を中心にして、幅で示した。
- **分け方の規則による誤差**: 確認の台本を書いた呼び出しなどは「その他」に入るので、確認の割合は少なめに出ている (5.1)。1 回の API 呼び出しで実装と確認を同時に呼んだときは等分した。
- **R6 の時点の道具**: R6 のときにあったのは RG1 (描画の記録) と RG3b (サイズ・VM プール) だけで、RG2 (画面)・RG3 (相手)・RG4 (実機)・RG6 (calibrate) はまだ無かった。R6 で写しを 19 枚手で撮ったのはそのためである。全部の道具を使った段の記録は、まだ 1 つも無い。
- **確かめたいこと**: 次のリファクタリングで同じ集計 (確認の呼び出しの数と単価、確認の割合) を取れば、5.5 の見込みを確かめられる。

## 7. 残件 (各報告から集めた)

**入口・運用**

- `doc/README.md` の索引の更新 (`rake docs:index`)。doc/regression の文書をコミットするときに親が行う。

**場面・相手を足す**

- 描画の記録: 全 mruby の構成のデスクトップ (確認の画面・ファイル選択・ランチャー)、麻雀の記録を同じ形の基準に入れるか、高解像度 (640x360) で描く mruby のアプリ、押せる範囲 (HitAreas) を記録に出すか。
- 画面: MIDI APU の SMF の行 (`..` の字形)、ブラウザ版の MML の行のクリック、Spinel のデスクトップの構成、全画面の高解像度のアプリ。ブラウザ版はアプリを閉じる口が無く、ページを読み直す (1 回 35 秒)。ランチャーの絵はアプリを足すと変わる (場面と `web_index` を見直す)。
- 相手: ホストの SIGSTOP/SIGCONT (「答えない」)、状態を消して戻す、別の参加者 (CRuby で join して手や線を送る)、zenohd の停止と再開、HTTP の偽の相手 (天気のアプリに向け先を変える口が要る)。麻雀で /home に名前が無いときの枝は流れていない。道具を kill したときにゲームホストとモニタが残る。

**数えられないもの・比べていないもの**

- sim で周期ダンプが出ない (status_led のタスクのスレッドが無い。原因は追っていない)。直れば sim の控えに IRAM free を足せる。
- 閉じた直後のカーネルの使用量 (GC を待つか促す口が要る)。sim の台本にエディタ (Spinel) を入れていない。ブラウザ版の VM プールの表は無い。
- 実機の起動: P4-Nano 以外の 4 端末の基準 (つないだときに calibrate で取る)。起動の秒数と VM プールは比べていない。
- calibrate: sim の gc_used の案は割合の部分を考えない。IRAM free の幅は、RG6 の後に 2 KB に広げた (e9103501)。

**道具の外で気づいたこと (直していない)**

- P4-Nano でも起動ログに `Running on ESP32-P4 (M5Stack Tab5)` と出る (main/boot/boot.c)。
- Retro のエディタの窓の位置が、標準構成 (x=5) と全 mruby (x=107) で違う。原因も、不具合かどうかも見ていない。
- 128x128 で step_sensor の下の行が画面の左にはみ出す。動画の再生・MML・NSF/SMF プレイヤ・PicoRabbit+・midi_apu の状態行が窓の幅を超える (RG1 の記録で気づいた。FmrbUI の部品の分は R6 で詰めた)。
- MCP の sim_up でも、種類を切り替えた直後に sim が「上がらない」ことがありうる (道具の側は起こし直しで受けている)。MCP の flash は端末とポートを選べない。
