# 3.1.0 の前の直し その 3 の結果 (転送のアプリを本体に焼き込む)

> 2026-11-27。指示は instruction_r3.md。本体の checkout (ブランチ app-uart) と sim (Retro・Modern)、ネイティブ版、
> ブラウザ版で確認した。ESP32 のビルド・実機・シリアルは触っていない。

## 1. まとめ方

転送のアプリは `default/transfer` という名前の、本体に焼き込んだアプリになった。シェル・エディタと同じく、ビルドが部品を
1 つにまとめてバイトコードにし (`transfer_irep`)、起動のときは何も `require` しない。

| 物 | 置き場 | 中身 |
|---|---|---|
| `transfer.app.rb` | `main/ruby/default_app/` (flash/usr/share/transfer から移した) | アプリ本体。頭に `# combine:` の行 |
| `app_package.rb`・`rshell.rb`・`transfer_inbox.rb` | `main/ruby/default_app/transfer/` (同上、移した) | 転送のアプリだけが使う部品 (サブフォルダの仕組み) |
| Asterism::Transfer (`transfer.rb`) | `flash/usr/share/asterism/transfer/` のまま (rake setup の写し) | `# combine:` で前に置く |
| `receive_conf.rb` | `flash/usr/share/transfer/` のまま | `# combine:` で前に置く (ほかの使い手も storage から読む) |

まとめる順は「`# combine:` の物 → サブフォルダの物 (名前の順) → 本体 → autostart」。`TransferInbox` が
`Asterism::Transfer::Inbox` を継ぐので、共有の部品を先にした。

- **`# combine:` を CMake でも読むようにした** (`compile_ruby_to_bytecode.cmake`)。前はブラウザ版・ネイティブ版の
  `hosted_regen_mrb!` だけが読んでいた。名前の物が無ければ構成の時点で止まる (rake setup の写しが無いとき)。
  `hosted.rake` も同じ順 (共有の部品をサブフォルダの物より前) に揃えた。前から使っていた `system_desktop_keys` には
  サブフォルダが無いので順は変わらない。
- **アプリの属性は C の表に移した** (`fmrb_app_spawner.c` の `default/transfer`)。headless・`large_memory`・
  `single_instance`・`movable`、名前 `Transfer`、スタック 16 KB・優先度・flags は普通のアプリと同じ。`.app.toml` は消した。
  `launcher_visible = false` は、焼き込んだアプリがランチャーに出ないので要らない。
- **焼き込んだアプリにパスの名前を持たせた**。`fmrb_spawn_attr_t` に `builtin_path` を足し、BYTECODE のアプリでも
  `ctx->filepath` に入れる。`single_instance` の比べ (`launch_claim`)、カーネルの `_get_app_info` の `path`
  (Spinel の `fmrb_spx_app_info_snapshot` と mruby の `kernel.c` の両方)、`FmrbApp.script_path` がこれを返す。
  カーネルの `adopt_transfer` はこれで外から起こされた転送のアプリを引き取る。ほかの焼き込んだアプリは前のまま空。
- **Asterism の無い S3 の構成** (`FMRB_ASTERISM=0`。ボードの名前の無い S3) では、バイトコードも表の行も入れない
  (`FMRB_NO_TRANSFER_APP`)。S3 の 3 ボードと P4・sim には入る。
- **リモートシェル**: `RShell` のモジュールとクラスは常に定義されるが、`Door` は `rshell_enabled` のときだけ作り、
  そのときだけ `<node>/transfer/rshell` を公開する (`@rshell ||= ::RShell::Door.new(self)`)。切のときは何も作らず、
  公開もしない。切の増分は 3 章。

## 2. ほかの使い手の扱い

使い手を洗い出した結果。

| 使い手 | 読む物 | 扱い |
|---|---|---|
| カーネル (`TRANSFER_APP`) | 起こす名前・引き取りの比べ | `"default/transfer"` に |
| `FmrbReceiveConf.tell_transfer` (`receive_conf.rb`) | 起こす名前 | `"default/transfer"` に。走っているかは前どおり名前 `Transfer` で見る |
| `FmrbTransfer` (`fmrb_transfer.rb`、シェルの asend・試験の xfer_probe) | 起こす名前 | `"default/transfer"` に |
| シェル (`asend`・`areceive`・`amove`) | `fmrb_transfer.rb`・`receive_conf.rb` を `require` | storage に残す (変えない) |
| 受け取りのアプリ (`/app/tool/receiving.app.rb`) | `receive_conf.rb` を `require` | storage に残す (変えない) |
| `install_ask.app.rb` | 何も読まない (転送のアプリがパスで起こす) | storage に残す |
| 試験のアプリ `xfer_probe` | Asterism::Transfer・`fmrb_transfer.rb` を `require` | `flash/` に残る (sim・ネイティブ版・開発のブラウザ版) |
| `regress:run` の場面・`checkpoint_board.rb` | 起こすパス | `default/transfer` に。board の道具は転送のアプリを端末へ送らなくなった |
| 試験 `test/rshell`・`test/app_package` | ソースのパス | 新しい置き場に。64 KB の台本の上限の見張りは、もう読み込まないので外した |

`receive_conf.rb` は storage にも残し、同じファイルをビルドがバイトコードにも入れる (写しは作らない)。シェルを同じ形に
するのは見送った (シェルは `asend` などのときだけ読むので、焼き込むとシェルのプールが常に増える)。

storage から外した物: 移した 4 ファイルと `.app.toml` は `flash/` から無くなったので像に入らない。Asterism::Transfer の
`transfer.rb` は `config/storage_exclude_common.txt` で外した (`xfer_probe` のため flash/ には残す)。
`sha256.rb` は残した: Asterism::Transfer は `Digest::SHA256` も `MbedTLS::Digest` も無いビルドでだけ実行時にこれを
読むので、焼き込むと誰も使わない物を常に持つことになる。

## 3. 測った数

### 3.1 sim (Retro、手で起こして測った。プールは sim の large プール 3 MB)

山はアプリを閉じるときのプールの記録 (一時的に足したログで取り、外した)、落ち着いた後は GC の後の ps の値。

| | 前 (storage から require) | 後 (焼き込み) |
|---|---|---|
| 切: 山 | 1,444,024 | **774,128** (-669,896) |
| 切: 落ち着いた後 | 977,808 | **752,896** (-224,912) |
| on: 山 | 2,038,536 | **774,048** (-1,264,488) |
| on: 落ち着いた後 | 1,119,752 | **756,696** (-363,056) |
| on のときの増分 (落ち着いた後) | +141,944 | **+3,800** |
| 起動の直後 (アプリのログ `transfer: start`) | 989,144 | 746,136 |

- 前の on の山 (約 2.0 MB) は、実機の large プール (2 MB) の際だった。
- **切のときの増分**: リモートシェルの部品だけを抜いたビルドを一時的に作って比べた。抜いたとき 700,160 (山 735,728)、
  入れたとき 752,896 (山 774,128)。**切でも約 52.7 KB 増える** (前は +1.4 KB)。`RShell` のバイトコード (約 48 KB) を
  VM が読み込むとき、mruby は全部の irep をプールに展開するため。クラスの定義だけで、インスタンス・公開は無い。
  それでも全体は前より約 225 KB 少ない。
- スタック: sim の値は前も後も 13,071〜13,077 で変わらない。sim では山を作る所が実機と違い、**スタックの仮説
  (`require` の仕組みが山を作る) は sim では確かめられなかった**。実機での測りを親に頼む (7 章)。

### 3.2 `rake regress:run ONLY=modern` の `running_transfer`

| | 前 | 後 |
|---|---|---|
| Transfer (落ち着いた後) | 977,888 | **752,880** (-225,008) |
| Transfer の compile の行 (コンパイルの直後、used / peak) | 674,928 / 1,158,256 | (無い。コンパイルしない) |

ほかのアプリの数は前と後で同じ。基準 (`test/regress/sim_baseline.json`) とは、変更の前の木で流した時点で既に 25 件違って
いた (カーネル +4.6 KB、デスクトップ +6.6 KB、StackChan Remote +42 KB など。この変更より前の変化)。基準の更新はしていない。

### 3.3 storage から減る量

中身 177,107 バイト + `.app.toml` 622 バイト。littlefs の 4 KB のブロックで数えて約 184 KB (46 ブロック)。
P4・NARYA v3・StickS3・AtomS3R のどれも同じだけ減る。

## 4. S3 のファームの見積もり

焼き込むバイトコードは 150,318 バイト (`-g` の行番号の表を含む。無しなら 132,607)。ほかに表の 1 行・C の数十バイト。

| 機種 | 空き (doc/reference/flash_layout.md 3.1、11-26) | 後の見込み |
|---|---|---|
| NARYA v3 | 257,744 B (4%) | **約 107 KB (1.7%)** |
| StickS3・AtomS3R | 521,040 B (9%) / 535,808 B | 約 370 KB (6.4%) / 約 385 KB |
| P4-Nano・Tab5 | 約 1.33〜1.36 MB (16%) | 約 1.18〜1.21 MB (14%) |

11-26 の数は UART の前なので、NARYA v3 の実際の空きはこれより少し小さい。入らない見込みは高くないが、空きは 2% を切る。
内蔵 RAM の静的な増分は無い (バイトコードと表は const で Flash に置かれる。足したのは const の表のポインタ 1 つと、
スタックに作る `fmrb_spawn_attr_t` の 4 バイト)。

## 5. 確かめた事

| 項目 | 結果 |
|---|---|
| `rake regress` (ホストの試験 40 本、`test/rshell`・`test/receive_conf`・`test/app_package` を含む) | 通る |
| `rake regress:transfer:quick` (ネイティブ版。シェルの `areceive on/off` を含む) | 通る |
| `rake regress:transfer:quick WEB=1` (ブラウザ版。シェルの `asend` を含む) | 通る |
| `rake regress:transfer:install` | 7 件のうち `auto` だけ落ちる (下) |
| sim (Retro、`rake clean` → `rake build:linux`): 起動・接続・カーネルの引き取り | `Transfer app adopted` `connected as <node>` |
| sim: 2 つ目の `default/transfer` | `single_instance` で断られる |
| sim: リモートシェル on → PC の asterism CLI (`rshell_uncertified`、`--node console`) | `open`・`exec_read` (`ls /home`・`ps`・`free`)・鍵の場所の `cat` の断り・`close` が通る |
| sim: 受け取りの設定で切 → on (再確認の 10 秒) | 切で `no_object`、on で公開し直して `open` が通る |
| sim: checkpoint の受け取り側の `check` | `{"ok" => true, "missing" => ["no_such_method_zz"]}`。基準の名前の数・digest は前と同じ (4537、71f5fd7e) |
| ネイティブ版・ブラウザ版のビルド | 通る (`rake native:core`、`rake wasm:web`) |
| Spinel のカーネル (sim・hosted の生成 C) | `cst_TRANSFER_APP` が `"default/transfer"`、`info[:path]` との比べは `sp_str_eq` |

`regress:transfer:install` の `auto`: 受け取り・確認の画面・置く所・デスクトップへの知らせまでは通り、その後の
「メニューの (30,5)→(30,19) をクリックしてランチャーを開く」でランチャーの読み直しがログに出ない。転送のアプリより後の、
デスクトップのクリックの段で、この変更が触っていない所。変更前の木では流していないので、前からかは確かめていない。

## 6. 見立てと違った点

- **カーネルは焼き込んだアプリのパスを知らなかった**。`_get_app_info` の `path` は FILE のアプリだけが持つので、
  最初の形では転送のアプリの `transfer_ready` をカーネルが引き取れず「接続した」が出なかった。`builtin_path` を
  BYTECODE のアプリにも出すようにして直した。
- **切のときの増分は 0 にならない** (約 53 KB)。クラスを定義するだけでも、まとめたバイトコードの irep は全部が
  読み込みのときにプールへ展開される。0 にするには、リモートシェルを別のバイトコードにして on のときだけ C から
  読む仕組みが要る (新しい C の入口と、走っている VM の中での読み込み)。今回は入れていない (8 章)。
- `.mrb` の試し (TODO.md) では山 937 KB だったが、焼き込みでは 774 KB (sim) まで下がった。Asterism::Transfer も
  コンパイルしなくなり、`require` ごとの task も無くなった分。

## 7. 親に実機で確かめてほしい事

1. **スタックの余り** (P4-Nano): 周期ダンプの `fmrb_task: Transfer ... 16384 <余り>`。前は 644。`require` が
   原因なら数 KB に戻るはず。
2. **VM のプール** (P4-Nano・Tab5、2 MB の large プール): 周期ダンプの `Transfer` の Used / Peak。切と on
   (受け取りのアプリでリモートシェル on) の両方。
3. ファームの大きさ (`rake regress:size`、とくに NARYA v3 の空き)。
4. 受け取りのアプリ・シェルの `asend`・`areceive`、リモートシェル (console から) が実機で通ること。
5. app_sync で上げる端末: 古い `/usr/share/transfer/{transfer.app.rb,.toml,transfer_inbox.rb,rshell.rb,app_package.rb}`
   は像に無いので `PRUNE=1` で消える。`/usr/share/asterism/transfer/transfer.rb` は storage_exclude に載せたので
   PRUNE でも消えない (手で消すか、残しても害は無い)。

## 8. 残り

- 切のときの約 53 KB を 0 にするか (リモートシェルを別のバイトコードにして on のときだけ読む)。ユーザの判断。
- `regress:run` の基準の更新 (この変更より前からずれている。人が確かめてから)。
- `regress:transfer:install` の `auto` のクリックの段 (5 章)。
- ネイティブ版のパッケージ (`native:root`) とブラウザ版の束は、Asterism::Transfer の `transfer.rb` を前どおり写す
  (試験のアプリ用。公開の物では使わない)。
