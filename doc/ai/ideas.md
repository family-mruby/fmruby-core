# OpenAI API 活用の構想メモ

状態: 構想 (未着手)。2026-08-25 の検討の書き出し。
前段: doc/user_extension/voice (V2b でクラウド TTS が実機で動いた) と
doc/user_extension/services (常駐サービスの器)。

## 使える部品 (実績あり)

- HTTPS クライアント: tts_http (chunked / Bearer / タイムアウトつき)。
  esp_crt_bundle で CA 焼き込み不要。TLS 1 接続 約 6KB の内蔵 RAM。
- 鍵: ~/.openai_key をビルド時に /etc/services.toml へ注入 (dev ビルドのみ)。
- Services ホスト: 常駐・定時発火 (wake_in)・購読。失敗は 1 行ログで黙る流儀。
- publish/subscribe: どのアプリからも使える。**1 メッセージ 8KB 上限** (msgpack zone)。
- 入出力: TTS 読み上げ (実機で動作中)、マイク (ES7210、FFT 計測で実績)、
  APU/MML 演奏、efontJA_12 の日本語表示、かな入力 (shell/editor)。
- OpenAI 側: chat completions (文章生成)、Whisper (音声認識)、TTS (済)。
  画像 API は base64 応答なので使わない方針 (V2b で決めた線)。

## 共通の設計方針

- **汎用の「ai サービス」を 1 本立てる** (chat completions の口)。用途ごとに
  サービスを増やさず、topic (例 ai/req → ai/res) で相乗りする。
- コードやファイルは**パスで渡す** (8KB 上限のため。同一 FS なので成立)。
- 失敗系は tts と同じ: タイムアウト + 1 行ログで沈黙、再試行なし。
- 応答は数秒〜十数秒。**「考え中」表示を共通部品にする** (画面か音)。
- system prompt に**この機械の Ruby の制約**を数行で渡す (Regexp なし /
  Array#pack なし / ブロック呼び出し 0.4ms/回 / Spinel の proc 制約など)。
  汎用 Ruby ではなく「この機械で動く Ruby」を答えさせるのが価値の核。
- 費用: gpt-4o-mini 系で 1 回 1 円未満。

## アイデア一覧

### すぐ作れる (tts_http 流用 + 1 サービス/コマンド)

1. **ai コマンド (shell)** — `ai "質問"` で chat に投げて表示、`-v` で読み上げ。
   最小の一歩。経路 (ai サービス) をここで固める。
2. **朝のブリーフィングサービス** — 定時に天気などを取り「3 文に要約」させて
   tts/say。services の wake_in がそのまま器。
3. **お話マシン** — お題から短い物語を作って読み上げ。寝る前用。
   ファミリー機の性格に合う見せ場。

### この機械ならでは (デモ映え)

4. **作曲 → APU 演奏** — MML (か音符の JSON) を書かせて既存経路で鳴らす。
   答えが文章でなく音で返る。
5. **音声アシスタント (PC なし)** — マイク録音 → Whisper (multipart POST を
   1 つ足す) → chat → TTS。押して話す「トランシーバー式」なら realtime API
   不要。発表・コンテスト向きの本命。
6. **RPG の NPC 会話を動的生成** — 応答遅延は「考えてる」演出で吸収。

### エディタ・入力系 (実用性)

7. **コードレビュー (エディタ統合)** — 下に構成案。
8. **エラー説明** — 実行時例外 + コードを投げて日本語で解説。学習機として強い。
9. **クラウドかな漢字変換** — エディタで一度落とした漢字変換を、文単位で
   LLM に変換させる形で安く拾い直す道。
10. **ドット絵生成 (文字経由)** — 16x16 の RGB332 配列を JSON で書かせて
    スプライトへ。画像 API を使わずに済む。品質は運。

## コードレビューの構成案 (7 の詳細)

```
エディタ (Spinel)                    Services ホスト (mruby)
  メニュー「Review」/ ショートカット      ai サービス
    保存 → publish("ai/review",     →    パスのファイルを読み chat へ
      {"path": ...})                     (tts_http 流用)
    ステータス行「review中...」     ←    publish に結果を返す
    結果をヘルプ画面 (F1 の器) で表示
```

- **エディタ自身に HTTP をやらせない**。理由は 3 つ:
  (1) エディタは Spinel で、SSLSocket をそこから呼ぶのは未検証。TLS は
  実績のある mruby の Services ホストへ寄せる。
  (2) 待つのはサービス側なので、十数秒かかっても編集が固まらない。
  (3) 8KB 上限があるのでどのみちパス渡しになり、読むのはサービス側が自然。
- 結果は「L12: ...」の行番号つきで返させる。表示はヘルプ画面の読み取り専用
  ビューがそのまま器。将来は行ジャンプ連動。
- 型は picoruby-ti が既に見ている。AI 側は論理・設計・「その API はこの機械に
  ない」系を受け持つ分担。
- 対象ファイルは数十 KB まで (トークンと VM メモリの両面)。
