# fmruby-core アーキテクチャ設計評価

## 現状の構成概要

```
Boot → Kernel(C) → Kernel(Ruby VM) → system_desktop(Ruby VM) → User Apps(Ruby VM×N)
         |
       Host Task(C) ── Graphics/Audio/HID
```

- **Kernel**: PID=0。C層がVM管理・HIDルーティング、Ruby層が60Hzイベントループ・ウィンドウ管理・アプリライフサイクル
- **Host**: PID=1。グラフィクス/オーディオ/入力デバイスのハードウェア抽象層
- **system_desktop**: PID=2。メニューバー・ランチャー・ファイルセレクタ等のUI
- **User Apps**: PID=3〜15。FmrbAppを継承し、独立VMで動作

## 良い点

### 1. レイヤー分離が明確

Kernel(C) → Kernel(Ruby) → Apps という階層が自然で、責務の境界がはっきりしている。Cでやるべきこと（VM管理、メモリプール、タスク生成）とRubyでやるべきこと（ウィンドウ管理、入力ルーティングのロジック）の分け方が合理的。

### 2. メッセージパッシングによるIPC

アプリ間がメッセージキューで疎結合。PUB/SUBもある。VM間で直接参照がないため、アプリのクラッシュが他に波及しにくい。組み込みOSとして堅実な設計。

### 3. アプリのライフサイクル管理

FREE→INIT→RUNNING⇔SUSPENDED→STOPPING→FREEの状態遷移が明確。フルスクリーン時の他アプリsuspend/resumeも整合している。

### 4. system_desktopがKernelから分離されている

デスクトップUIが独立アプリとして動いているのは良い設計判断。Kernelが肥大化せず、デスクトップの変更がKernelに影響しない。

## 懸念点・改善の余地

### 1. Kernelの責務過多（Ruby側）

`fmrb_kernel.rb` が869行あり、以下をすべて担っている：

- ウィンドウ管理（ヒットテスト、z-order、ドラッグ/リサイズ）
- HID入力のルーティングと座標変換
- アプリのspawn/exit制御
- PUB/SUBブローカー
- ファイルセレクト要求の中継
- フルスクリーン管理
- デスクトップオーバーレイ状態の追跡

ウィンドウマネージャの機能（ドラッグ、リサイズ、ヒットテスト、z-order）だけでもかなりの量。将来機能が増えるなら、ウィンドウ管理をモジュールに分離することで見通しが良くなる。

### 2. Kernel ↔ Desktop間の暗黙的な結合

形式上は別プロセスだが、実際にはKernelがdesktopの内部状態（オーバーレイ矩形、ドロップダウン状態）を知っている。`overlay_state`メッセージでdesktopがKernelにUI矩形を通知し、Kernelがそれをヒットテストに使う構造は、desktopのUIレイアウト変更がKernelに影響する結合を生んでいる。

理想的には、ヒットテストの責任をどちらか一方に寄せるか、ウィンドウシステムとしてより汎用的なプロトコル（各アプリがクリッカブル領域を登録する仕組みなど）にすると結合が減る。

### 3. system_desktopの二重役割

system_desktopは「デスクトップの壁紙・メモリ表示」と「ファイルセレクタ・ランチャー・エラーダイアログ等のシステムUI」を兼任している。後者はどのアプリからも呼ばれるシステムサービスであり、前者とは性質が異なる。

現状ではMixinで機能分離されているが、概念的には：

- **Desktop**: 壁紙、タスクバー、メニュー
- **System UI Service**: ファイルセレクタ、ダイアログなどの共有UI部品

を分けるとより明確になる。ただし、ESP32のメモリ制約でVM数を増やせないのであれば現状の統合は妥当なトレードオフ。

### 4. メッセージペイロードの160バイト制限

現状の用途では十分だが、アプリ間で構造化データをやりとりしたい場合にボトルネックになりうる。ファイルパスが長い場合等、限界に近い場面がないか注意が必要。

### 5. PIDの固定割当て

Kernel=0, Host=1, Desktop=2は固定で、3〜15がユーザアプリ。全体で16プロセスの上限は組み込みとしては十分だが、将来ヘッドレスサービス系アプリ（通信、ストレージ管理等）を増やすなら、システムアプリ用の予約枠があると管理しやすい。

## 総合評価

組み込み環境でのマルチタスクGUIシステムとして、よく整理された設計。特にメッセージパッシングによる疎結合、C/Ruby間の責務分担、アプリライフサイクル管理は堅実。

最大の改善ポイントは **Kernel Ruby層の責務分割**（特にウィンドウ管理の分離）と **Kernel-Desktop間の結合度の低減**。ただしこれらは組み込みのメモリ制約とのバランスで、現状が意図的なトレードオフであれば許容範囲。
