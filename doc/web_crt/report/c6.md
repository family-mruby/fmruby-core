# 報告 C6: NTSC の色のにじみ、時間で動く効果、既定の強さ (ブラウザ版の C2 と共通)

> 状態: 強め直した 3 つの効果をユーザに見てもらう所で止めた | 更新: 2026-11-08 | 共通のシェーダーに NTSC の色のにじみ・ちらつき・ノイズを足し、ブラウザ版とネイティブ版の全部の口 (機種の定義・--set・[crt]・comp crt・設定の Window・ページの欄) に通した。新しい効果が 0 ならブラウザ版の絵はバイトまで同じ。既定はユーザが決めた (今の 5 つのまま、新しい 3 つは 0)。最初の 3 つの効果は GPD で弱すぎたので強め直し、見比べの組を入れ直した

指示書は [../instruction_c6.md](../instruction_c6.md)、計画は [../plan.md](../plan.md)。
ブラウザ版の C2 (NTSC の色のにじみ・時間で動く効果・既定の強さの詰め) もここで扱う。

## 効果の作り (hosted/crt/crt.frag)

3 つとも、ほかの効果と同じく強さ 0 なら計算しない (uniform の分岐)。

| 効果 | 鍵 | 中身 |
|---|---|---|
| NTSC の色のにじみ | `ntsc` | その画素の明るさ (YIQ の Y) はそのまま、色 (I・Q) を行に沿ったガウス (σ 3 Family mruby 画素、左右 7 画素まで、遠い所は 1 つおき) から取り、強さの平方根で混ぜる。色は右へ尾を引く (左の画素を最大 6 割多く取る、復調器の遅れ)。明るさの段差には、副搬送波の位相 (1 画素 0.6 周、1 行で半周) で色相の回る偽色の縁を付ける |
| ちらつき | `flicker` | 画面全体の明るさがコマごとに上下 (100 で ±12%) と、幅の広い暗い帯 (100 で最大 3 割暗い) が 4 秒で 1 回上から下へ流れる (電源のうなり) |
| ノイズ | `noise` | Family mruby の 1 画素ごとの粒。コマごとに変わる (100 で ±25%) |

- 色の変換は YIQ。にじみの幅は、WROVER の NTSC 出力 (横 320 画素を約 52 µs に描く、
  画素の速さ約 6 MHz) と、色の帯域 (I 約 1.3 MHz) の比から 2〜4 画素ほどと見て決めた。
- 時間で動く効果は「コマの番号」(`u_frame`) を受ける。番号は時計から 1 秒に 30
  (`CRT_TIME_FPS`、crt.js の `TIME_FPS`)。描く速さ (動画の間は 60) によらず、粒と
  ちらつきは 1 秒に 30 回変わる。
- 粒の乱数は整数のハッシュ (pcg3d)。GLSL ES 3.00 の uint で、WebGL2 と GLES 3 の両方で同じ。

### 捨てた案

- **最初の強さ** (σ 1.6・左右 3 画素、ちらつき ±5%・帯 6%、粒 ±8%): GPD の 7 インチ
  1080p (Family mruby の 1 画素 = 出力 3 画素) で、NTSC 0・50・80 の違いがユーザに見えず
  (画面写しの平均の差 1〜2/255)、帯も粒 20 も気づかれなかった。下の「強さの作り直し」。
- **ドットの這い (dot crawl、時間で動く偽色)**: 偽色の縁は入れたが、コマごとに位相を
  ずらすと NTSC だけで毎コマ描くことになる。動かさない。
- **ちらつきを wlroots の `wlr_output_schedule_frame` で描かせる**: 最初はこう組んだが、
  この関数は出力を「描く必要あり」にするので、シーン (wlroots の合成) が毎回描き直していた
  (GPD で `time_frames` が 0 のまま、1 コマの CPU 2 ms)。直した形は下の「描く回数」。

## 強さの作り直し (ユーザが GPD で見た後)

ユーザの判断 (2026-11-08): 既定は今の 5 つのまま (now の組)、新しい 3 つは 0。デモには
strong の組が映える。新しい 3 つは 50 ではっきり見え、100 で強い所まで強める。

- 色のにじみ: ガウスを σ 3 (左右 7 画素まで) に広げ、混ぜ方を強さの平方根に (50 で 7 割)、
  右へ尾を引くずれと、明るさの段差の偽色の縁を足した。明るさはくっきりのまま。
- ちらつき: 明るさのゆれ ±5% → ±12%、帯 6% (細い) → 30% (広い)。
- ノイズ: ±8% → ±25%。
- 画面写しの平均の差 (今の既定に足した、GPD の headless のデスクトップ): NTSC 50 で
  2.1/255、100 で 3.6/255 (前は 80 で 1〜2)。差の大半は色の付いた細い所と文字の縁。
- 新しい効果が 0 のときのブラウザ版の 12 枚は、作り直しの後もバイトまで同じ。
- GPU の重さ (headless、flicker 50 で 1 秒 30 コマ): NTSC 0 で 6.4 ms、50 で 7.5 ms、
  100 で 8.3〜8.7 ms (この時は GPU の周波数が前の計測より高め)。noise 50 は 7〜8 ms。
  1 秒 30 コマ、0 に戻すと 10 秒に 10 コマ (変わったときだけ) を確かめた。

## 描く回数

- **ブラウザ版**: `flush()` は今までどおり変わったときだけ描く。ちらつきかノイズが 0 より
  大きい間だけ、コマの番号が進んだ rAF でも描く (1 秒に 30 回)。
- **ネイティブ版**: シーンが変わったときだけ描くのは今までどおり。ちらつきかノイズが
  0 より大きい間は、描いたコマの 1/30 秒後に 1 回だけ鳴るタイマーを仕掛け、鳴ったとき
  シーンに新しい物が無ければ、前のコマのシーンの buffer (この間だけ lock して持つ) を
  もう一度シェーダーに通して出力に commit する。シーンに新しい物があればそのコマが
  来るので何もしない。ページの切り替え (page flip) がまだ終わっていなければ 2 ms 後に
  やり直す。0 に戻すと、次のコマでタイマーを止めて buffer を放す。
  `comp crt` の `time_frames` がタイマーで描いたコマの数。

  曲がりの往復、C と JS の一致)、描画の記録 213/213。`native:test` の機種の定義は 560 項目

- `rake regress:wl`: standard・mruby とも通過 (pixman なので CRT は出ない。既定 sharp で

- `rake regress:screens`: 33/33 (retro 9、modern 11、web 6、native 3、native-keys 4)。
  基準の更新なし。
- ブラウザ版のバイト比較: headless の Chromium (SwiftShader) で、変更前 (3e727102) と後の
  crt.js に同じ絵を描かせ、3 つの大きさ (426x240→1278x720、640x360→1280x720、
  426x240→852x480) × 4 つの設定 (既定、全部 0、全部 100、混ぜたもの) の **12 枚の PNG が
  バイトまで同じ**。新しい効果を入れた絵も描けること (にじみで赤い縁が青に滲む、粒が
  出る) を見た。

### GPD (headless の 2 つ目のコンポジタ、ユーザの画面には出していない)

C4 と同じく .deb を `/tmp/fmx` に展開し、1080x1920・rotate 270・scale 3 で動かした。

- 起動の 1 行 `look=crt(55,30,30,15,40,0,0,0)`。
- 「画面」のページ: 8 つの stepper が 2 列に並び、CRT を押して「色のにじみ」の「>」を 2 回
  押すと `comp crt` が `ntsc=10` を返し、1 秒後に `[crt]` が 8 つの鍵で書かれた。
  そのまま `--set display.look=sharp` で起動し直すと、`[crt]` が勝って
  `look=crt(55,30,30,0,40,10,0,0)` で始まった。
- grim で撮った絵で、にじみ (アイコンの緑・青の縁が柔らかくなる) と粒が見えた。

計測 (何も触らないデスクトップ、20 秒ずつ。GPU の周波数は 300〜450 MHz のまま):

| 設定 (既定の 5 つ + 下の値) | 20 秒に描いたコマ | うちタイマー | CRT の描画 (GPU) | 1 コマの CPU |
|---|---|---|---|---|
| 新しい効果 0 | 20 (時計の 1 秒 1 回) | 0 | 7.8 ms | 2.0〜2.4 ms |
| flicker 25 | 605 | 585 | 7.6〜8.4 ms | 0.44〜0.50 ms |
| ntsc 50・flicker 25 | 606 | 586 | 10.6〜11.8 ms | 0.44 ms |
| ntsc 50・flicker 25・noise 20 | 605 | 585 | 9.6〜11.6 ms | 0.48 ms |
| ntsc 50 だけ | 20 | 0 | 11.2 ms | 2.0 ms |
| 新しい効果 0 に戻す | 20 | 0 | 7.8 ms | 2.4〜2.8 ms |

- **0 に戻すと「変わったときだけ」に戻る** (20 秒に 20 コマ、タイマー 0)。
- 時間で動く効果は 1 秒に 30 コマ (狙いどおり)。タイマーのコマはシーンを描かないので
  CPU は 0.45 ms 前後。
- NTSC のにじみは GPU で約 +3.5 ms (隣 6 画素を読む。GPU が 300 MHz のまま、C4 と同じく
  軽い負荷では周波数が上がらない)。ノイズ・ちらつきの足し分は計れないほど小さい。
- ちらつき・ノイズを入れると、何もしない間も GPU が 1 秒に 30 回、約 8〜12 ms 動く
  (300 MHz で GPU の 25〜35%)。電池で使う時間には効く。既定 0 の理由どおり。

## 見立てと違った点

- `wlr_output_schedule_frame` は「次のコマを出して」だけでなく出力を「描く必要あり」にする
  (`wlr_output_update_needs_frame` を呼ぶ)。シーンはそれを見て毎回描き直すので、タイマーで
  コマを頼むと、シーンの描画 (CPU 2 ms) まで 1 秒に 30 回走った。タイマーから直接
  commit する形に直した (上の「描く回数」)。
- GPU の周波数は、1 秒に 30 回 8〜12 ms 動かしても 300〜450 MHz のまま上がらなかった。

## 残件

- 強め直した 3 つの効果の目視 (ユーザ)。デモ用に strong へ切り替える口 (親がユーザに聞く)。
- ブラウザ版の時間で動く効果の重さは、実のブラウザ (GPU のある Chrome) で測っていない
  (headless の SwiftShader は CPU で描くので参考にならない)。
- ちらつき・ノイズの間は GPU が止まらないので、電池の持ちを見るならユーザの手元で。
