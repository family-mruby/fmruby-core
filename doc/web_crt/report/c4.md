# 報告 C4: ネイティブ版のコンポジタの CRT の下回り

> 状態: 完了 | 更新: 2026-11-07 | wlroots 0.19 の公開の口だけで、シーンを自前の swapchain に描かせ、ブラウザ版と共通のシェーダーで出力に描く。GPD の画面で、動画が滑らか・文字が読める・画面ロックにもかかることをユーザが確認した。曲がりの上の押下はユーザの返事待ち (headless では確認済)

指示書は [../instruction_c4.md](../instruction_c4.md)、計画は [../plan.md](../plan.md)。

## 組み方 (実装の前に調べたこと)

wlroots 0.19.2 (GPD・ビルドの image と同じ版) のヘッダと実装を読んで、公開の口
(`include/wlr/` に出ているもの) だけで組めるかを確かめた。結論: **組める**。
wlroots の内部 (`include/render/` など) には手を入れない。

### 1 コマの流れ

今の `output_frame()` は `wlr_scene_output_commit()` 1 つで済ませている。CRT が入の
ときは、これを次の 3 つに分ける。

1. **シーンを画面外に描かせる**: `wlr_scene_output_build_state()` に
   `struct wlr_scene_output_state_options` の `swapchain` (公開、「別の swapchain に
   描かせる」ための口) で**自前の swapchain** を渡す。シーンはそこから 1 枚取り、
   damage の所だけ描き直して、その buffer を `state.buffer` に入れて返す。
   damage の管理 (buffer の年齢) はシーンの `damage_ring` が buffer ごとに持つので、
   自前の swapchain でもそのまま効く。
   - swapchain は `wlr_swapchain_create()` (公開、`wlr/render/swapchain.h`)。大きさは
     出力の buffer (回転前、GPD は 1080x1920)、形式は出力の swapchain の形式
     (`output->swapchain->format`、公開の欄) と、描画器が texture にできる形式
     (`wlr_renderer_get_texture_formats()`) の modifier の重なり。
   - シーンの state から使うのは buffer だけ。シーンが付ける待ちの timeline
     (explicit sync) は捨てる (出力へ commit するのは別の state)。同じ GL の文脈の
     中で順に描くので、シーンの描画が CRT の描画より後になることはない。
2. **CRT のシェーダーで出力に描く**: 出力の swapchain (`wlr_output_configure_primary_swapchain()`、
   公開) から 1 枚取り、`wlr_renderer_begin_buffer_pass()` で描画を始める。
   GLES2 の描画器の begin は、文脈を current にし、その buffer の FBO を bind し、
   viewport を合わせ、scissor を切る (`render/gles2/pass.c` を読んで確かめた)。
   **submit までの間は wlroots の文脈がそのまま使える**ので、そこで自前の GL の命令
   (program・uniform・texture・draw) を出し、`wlr_render_pass_submit()` で閉じる。
   - シーンの buffer は `wlr_texture_from_buffer()` で texture にし、
     `wlr_gles2_texture_get_attribs()` (公開、`wlr/render/gles2.h`) で GL の texture の
     名前と target を得る。dmabuf の texture は wlroots が buffer ごとに覚えているので、
     毎コマ作る wlr_texture は包みだけ (使ったら壊す)。target が
     `GL_TEXTURE_EXTERNAL_OES` (texture にしかできない形式) なら CRT は出さない。
   - GL の状態: wlroots の pass は描くたびに program・blend・texture を自分で設定し、
     頂点は client 側の配列で毎回 enable/disable する。自前の描画もそれに合わせる
     (VBO を使わない、blend を切る、texture を bind し戻す)。
   - シェーダーは GLSL ES 3.00 (WebGL2 と同じ言葉)。wlroots は ES 2 の文脈を
     頼むが、Mesa は後方互換の一番上の版 (3.x) を返す。`GL_VERSION` が 3 未満か
     compile に失敗したら、理由を 1 行ログに出して CRT を出さない (今の見た目で続く)。
   - GL の関数は libGLESv2 (glvnd) を直接リンクする (wlroots と同じ文脈に dispatch される)。
3. **出力に commit**: 自前の state に出力の buffer を入れ、damage は全面 (曲がり・
   にじみは周りの画素を読むので、描き直しは全面)、`wlr_output_commit_state()`。

### damage のときだけ描く

- `wlr_scene_output_needs_frame()` (公開) が偽で、設定も変わっていなければ何も
  しない (今と同じ)。シーンが変わったコマだけ、1 回シェーダーを通す。
- 設定が変わったとき (今は内部の関数、C5 で UI から) は `wlr_output_schedule_frame()`
  で次のコマを頼み、直前のシーンの buffer を持ったままにしておいて (lock 1 つ)
  それを描き直す。
- 切に戻すとき: 出力の swapchain の buffer には CRT の絵が描いてあり、シーンの
  damage_ring はそれを知らないので、`wlr_damage_ring_add_whole(&scene_output->damage_ring)`
  (`damage_ring` は公開の欄) で全面を描き直させる。

### direct scanout とカーソル

- シーンは、画面に buffer が 1 つだけのとき (全画面の動画など) direct scanout を
  試み、そのとき buffer を自前の swapchain に描かずに client の buffer をそのまま
  state に入れる。CRT が入の間は `wlr_output_lock_attach_render(output, true)` (公開)
  で direct scanout を止める (切で lock を外す)。
- カーソル: ハードウェアのカーソルは出力の別の plane なので、CRT の絵の上に平らに
  乗る (決定事項のとおり)。ハードウェアのカーソルが使えない出力 (入れ子の Window、
  一部の GPU) では、シーンがソフトウェアのカーソルを画面外の絵に
  描くので、そのときはカーソルも曲がる (残件に記す)。

### 座標

- 出力の buffer の座標 (回転前) と論理の座標 (回転後、1920x1080) の対応は、
  wlroots の `wlr_box_transform()` (公開、シーンが使うのと同じ関数) に 1 画素の箱を
  3 つ通して、アフィン変換 (行列) として求める。シェーダーには「buffer の画素 →
  表示の位置 (0..1)」と「論理の画素 → シーンの buffer の texel」の 2 つの行列を渡す。
  回転の向きの式を自分で書かないので、wlroots と食い違わない。
- wlroots の FBO では buffer の y=0 (上) が GL の y=0 になる (GLES2 の pass は
  `WL_OUTPUT_TRANSFORM_FLIPPED_180` の射影で描く)。dmabuf の texture も 1 行目が上。
  なので buffer の座標はどちらも y が下向き (ブラウザ版の既定の framebuffer とは
  上下が逆。シェーダーでは行列が吸収する)。
- ポインタ: `wlr_cursor` の位置 (論理の座標) を、表示の位置として曲がりの式
  (`warpToSource` と同じ式) に通し、絵の位置にしてから、今までの当たり判定・
  Window への座標・Family mruby への座標に使う。絵の外の押下は捨てる。

### 捨てた案

- **シーンの描画にシェーダーを差し込む**: wlroots 0.19 のシーンにも GLES2 の
  pass にも、自前のシェーダーを渡す口が無い。
- **`wlr_renderer` を包んで自前の描画器にする**: 公開の `wlr_renderer_impl` で
  包むことはできるが、texture の import・buffer の FBO などを全部委譲する必要が
  あり、量が多いうえに wlroots の版ごとに壊れやすい。
- **自前の EGL の文脈を作る**: `wlr_egl_get_display()`・`wlr_egl_get_context()` は
  公開だが、current にする関数 (`wlr_egl_make_current`) は内部。begin_buffer_pass の
  中で描けば要らない。
- **シーンの出力を 2 つ作る (画面外の出力)**: headless の出力を足す形は、
  カーソル・damage・screencopy が 2 つに分かれて複雑になる。swapchain の口で足りる。

### 動いている間の切り替え (C5 の口)

`crt_set(look, strengths, ...)` が内部の関数。今は制御のソケットの要求でも呼べる:
`comp crt` (状態と計測)、`comp crt look=crt|sharp scanline=N mask=N glow=N curve=N vignette=N`
(どれか)。切り替えるとすぐ全面を描き直す。入→切では、出力の buffer に残った CRT の
絵を消すため、シーンの damage_ring 全体を傷にして描き直させる。

### シェーダーの共通化で変えたこと

- ブラウザ版のシェーダーの文字列は、コメントと `#ifdef` が増えただけで、前処理の後は
  今までと同じ式 (`px(ip)` は `px(ip + (ivec2(0, 0)))` になった)。**headless の Chromium
  (SwiftShader) で、変更前 (a77edda5) と後の crt.js に同じ絵を描かせ、3 つの大きさ ×
  4 つの設定の 12 通りで PNG がバイトまで同じ**だった。
- コンポジタ用の差: 絵の画素を読むときに Family mruby の画素へ丸めない。読むのは
  出力の実の画素 (Konsole の文字はそのままの細かさ) で、にじみの隣は「1 Family mruby
  画素 = 3 出力画素」離れた所。走査線と格子は Family mruby の画素の単位。倍率による
  弱めはブラウザ版と同じ式で、倍率 = `display.scale` (GPD は 3 なので全量)。
- 曲がりの C 版と JS の差は最大 2.2e-16 (`hypot` と `Math.hypot` の丸めの差)。

### GPD の GPU で headless (ユーザの画面には出していない)

GPD は SSH で入れて、利用者 kishima は render node (`/dev/dri/renderD128`) を ACL で
使える。そこで、.deb を `/tmp/fmx` に展開だけして (入れずに)、
`WLR_BACKENDS=headless WLR_RENDERER=gles2`、出力 1080x1920 を `display.rotate=270`、
`display.scale=3` (GPD と同じ形) で動かし、ビルドの image の grim を持って行って
画面を撮った。動いているセッション (ユーザの画面) には触っていない。

- `CRT look on OpenGL ES 3.2 Mesa 26.0.8-1ubuntu0.3 (Mesa Intel(R) Graphics (ADL-N))`。
  シーンの buffer は 1080x1920、出力の 6 つの modifier が全部 texture にもできた。
- 回転 270 で、CRT の絵が正しい向き (上下・左右が sharp の撮影と同じ) に出た。
  走査線・格子・にじみ・曲がり・四隅の暗さが見える。
- **曲がり 100 で座標**: 曲がった絵の上で見えている Editor のアイコンの位置を
  2 回押すとエディタが開き、Family mruby のカーソル (絵の中に描かれる) が押した所に
  描かれた。Konsole のアイコンで Konsole (Linux の Window) が開き、曲がった絵の上で
  見えている Konsole のメニューの釦の位置を押すと、そのメニューが開いた。
  表示の左上 (5,5)・右下 (1915,1075) の押下は絵の外として捨てた (`dropped=2`)。
- **pixman** (`WLR_RENDERER=pixman`) で `look=crt`: `CRT look unavailable: the renderer
  is pixman (it needs GLES); the output stays sharp` の 1 行で、そのまま動く。
  動いている間に `comp crt look=crt curve=50` を送っても描かず、角の押下も捨てない。
- **damage のときだけ描く**: 何も触らないデスクトップでは CRT の描画は 1 秒に 1 回
  (時計) だけ (10 秒に 10 コマ、sharp の出力の commit と同じ間隔)。

### 計測 (GPD、1920x1080 の出力 1 枚、headless)

ログに 10 秒ごとに出す (`CRT look: N frames in ...`)。`comp crt` でも直近の値が見える。

| 効果 | CRT の描画だけ (GPU、時間の問い合わせ) | 描画の始めから GPU が終えるまで (シーンの描画を含む) |
|---|---|---|
| 全部 0 (写すだけ) | 2.6 ms | 5.2 ms |
| にじみ 30 だけ | 6.9〜7.5 ms | 9.6 ms |
| 既定 (55・30・30・15・40) | 7.7〜8.1 ms | 10〜13 ms |

- 1 コマの CPU の時間 (シーンを描かせる所から commit まで): 平均 2 ms 前後。
- **この計測の間、GPU の周波数は 300 MHz (最大 1250 MHz) のまま**だった
  (`gt_cur_freq_mhz`)。1 秒に数コマ〜20 コマの軽い負荷では i915 が周波数を上げない。
  動画のように毎コマ描く間は上がるはずなので、実際の 1 コマはこれより軽い見込み
  (未確認。GPD の画面で動画を流したときのログで確かめる)。
- 重いのはにじみ (隣 10 画素を読む)。写すだけでも 2.6 ms かかっているのは、周波数の
  低さが大きいと見ている。コマが落ちるようなら、にじみを縮小した絵から取る形に
  変えるのを C6 で考える (見た目がブラウザ版と少し変わる)。

### GPD の画面 (ユーザの目視、2026-11-07)

.deb (3.0.0+git7.5601bfc9) を入れ、`/etc/default/family-mruby-session` を
`FMRB_ARGS="--set display.scale=3 --set display.look=crt"` にしてログインし直した。

- Chrome の全画面の動画が滑らか (カクつかない)。
- Family mruby と Konsole の文字が読める。
- 画面ロックにも CRT がかかる。
- 曲がりの上で押した所に届くか: ユーザの返事待ち (headless の GPD の GPU では、曲がり
  100 で Family mruby のアイコンと Konsole のメニューに届くことを確認済、上の節)。

動画の間のセッションのログ (親が読んだ値):

| 項目 | 値 |
|---|---|
| 描いたコマ | 10 秒に 280〜479 |
| CRT の描画だけ (GPU) | 平均 5.9〜6.9 ms、最大 8.1 ms |
| 描画の始めから GPU が終えるまで | 平均 6.9〜8.6 ms、最大 19.1 ms |
| 1 コマの CPU | 約 1 ms |
| CPU の使用率 | family-mruby 約 9%、Chrome 約 45% |

headless の測定 (7.7〜8.1 ms、GPU 300 MHz のまま) より、動画の間は軽かった。毎コマ
描く負荷では周波数が上がるという見立てと合う (何もしないときは 300 MHz)。

## 見立てと違った点

- wlroots の描画の時計 (`wlr_render_timer`) は「その描画の始めから GPU が終えるまで」で、
  前に積んだシーンの描画も入る。CRT の描画だけの重さを見るため、GL の時間の問い合わせ
  (`GL_EXT_disjoint_timer_query`、GLES 3 の関数) を別に足した。どちらもログに出す。
- 最初、wlroots の時計を次のコマの描画を始めた後で読んでいて 0 になった (begin が
  時計を始め直す)。begin の前に読むように直した。
- シーンの state を commit しないので、シーンの「まだ出していない傷」が消えないの
  ではと心配したが、出力への commit (buffer 入り、damage なし) の通知でシーンが
  自分で消す (`scene_output_handle_commit`)。何もしないと毎コマ描く、とはならなかった。
- GPD は SSH で GPU が使えるので、ユーザの手を借りる前に、実機の GPU で headless に
  絵と座標まで確かめられた (指示書の見立てでは目視まで全部ユーザだった)。

## ユーザに確かめてほしいこと (GPD の画面)

.deb (`3.0.0+git7.5601bfc9`) は GPD の `/tmp/fm.deb` に置いた。入れて、
`/etc/default/family-mruby-session` の FMRB_ARGS に `--set display.look=crt` を足し、
ログインし直す。

1. 走査線と格子が見えるか。Family mruby の 640x360 の文字 (メニューバー・アイコンの
   名前・エディタ) と、Konsole の文字が読めるか。
2. 曲がり (既定 15) の上で、タッチパッド・マウスで押した所が見えている所に届くか
   (Family mruby の釦と、Konsole・Firefox などの Linux の Window の釦・メニューの両方)。
   画面の四隅の黒い所の押下は何も起きない (捨てる)。
3. マウスのカーソルが平らなまま曲がった絵の上を動くか (矢印の先に届く)。
4. カクつかないか: Window を動かす、文字を打つ、動画 (Firefox で YouTube など) を
   全画面で流す。そのときのログ (`~/.local/state/family-mruby/session.log` の
   `CRT look: N frames ...`) は SSH で親が読む。
5. 画面ロック (電源のメニューの Lock) も CRT の絵になるか。
6. 気になった効果の強さ (C6 で詰める)。

強さは、動いている間に SSH から変えられる (再起動なし):
`python3 /tmp/fmx/ctl.py` に `FMRB_CTL=/tmp/fmrb-native-1000/ctl` を付けて
`comp crt curve=0 glow=50` など。`comp crt look=sharp` で切れる。

## 残件

- 見た目の判断と強さの詰め (C6)。にじみの重さ (上の計測)。
- タッチ: コンポジタは今タッチを扱っていない (wlroots のタッチの事象を受けていない) ので、
  曲がりの逆変換もタッチには無い。GPD のタッチパネルを使うようになったら同じ
  `crt_pointer` を通す。
- ハードウェアのカーソルが使えない出力では、シーンがソフトウェアのカーソルを画面外の
  絵に描くので、カーソルも曲がる。
- grim・画面の共有 (screencopy、ext-image-copy-capture) は出力の buffer を読むので、
  CRT をかけた絵になる (画面に見えている物と同じ)。`native_screenshot` と回帰の
  道具は Family mruby の絵 (CRT の前) を読むので変わらない。
- 全画面のアプリ (426x240 を大きい倍率で出す間) も、画素の単位は `display.scale`
  のまま (決定事項どおり)。
- 設定の UI・覚える所・「既定に戻す」は C5。
