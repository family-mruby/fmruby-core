# RBS で型情報を言語と端末の間で共有する 構想

> 状態: 構想 | 更新: 2026-11-14 | RBS の型定義を、端末の中の言語の間 (境界のバイト列)、端末の間 (Asterism の型の宣言)、ROS 2 の型に共通の元にする。整数と小数の幅の別名は決定済み。最初の試作 (RBS の記録型から Asterism の宣言、C の解析器) が通った。次の段は未定

## 目的

- **言語をまたいだ通信で、型の情報を共有する** (2026-11-14 ユーザ。最終的な興味はここにある)。
- 型の定義を 1 つ書けば、端末の中のアプリと本体の間、端末と端末の間、ROS 2 との間で、同じ
  意味で使えるようにする。
- RBS を、Ruby のコードの説明だけでなく、言語と端末をまたぐインタフェースの定義として使う。

まずは小さなところから進める (ユーザ)。

## なぜ RBS か (2026-11-14 ユーザ)

**RBS を IDL (インタフェース定義言語) として扱う。** 理由はプロジェクトの名前のとおり: Family
**mruby** は Ruby が中心の企画なので、言語をまたぐ定義も Ruby の型定義で書く。専用の IDL の
ほうが技術的に楽な所でも採らない。ほかの言語は、Ruby の定義を通じてこの環境に加わる。

IDL に求められることと、RBS での対応:

| IDL に求められること | RBS での対応 |
|---|---|
| 関数の名前・引数・戻り値を定義する | メソッドの定義 |
| データの構造を定義する | 記録型 |
| 選択肢を定義する | リテラルの型 |
| 説明を付ける | コメント (日本語と英語) |
| 各言語のコードを生成する | 生成の道具 (doc/wasm_apps の W4) |
| 通信の形を決める | 端末の中は固定の並びのバイト列、端末の間は MessagePack |

RBS は IDL として設計された言語ではないので、足りない所は決まりで補う: 整数の幅は型の別名、
どのメソッドを外に出すかは印 (RBS の注釈の文法)、通信の形は型から導く規則、版は型定義の
内容から生成の道具が決める。

普通の IDL に無い利点: 定義がそのまま Ruby の型定義で、エディタの補完とヘルプに使われる
(Ruby の側では生成したコードを使うのではなく、定義がそのまま働く)。Ruby の利用者が読める・
書ける。エディタのために既に書いてあった。

**決まりを足すときの軸**: Ruby が中心であること。RBS として自然に読めること。独自の記法を
増やさないこと。IDL としての都合を優先して RBS らしさを損なわない。

## 関係する計画

- doc/wasm_apps: 型定義 (`sig/*.rbs`) から、端末の中の全言語のつなぎを生成する (W4)。境界の
  記録型は固定の並びのバイト列になる。
- doc/hw_resources: HW の機能も同じ型定義に書く。
- Asterism (別のリポジトリ、独立した OSS): 型の宣言を実行時に配る仕組みを持つ
  (`define_type(名前, [[フィールド, 型], ...], 説明)`)。ROS 2 の型の橋も持つ。

## 決定 (2026-11-14 ユーザ)

### 整数と小数の幅の別名

RBS には幅の区別が無いので、型の別名で表す。**名前は ROS 2 と同じにする。**

```rbs
type int8    = Integer
type uint8   = Integer
type int16   = Integer
type uint16  = Integer
type int32   = Integer
type uint32  = Integer
type int64   = Integer
type uint64  = Integer
type float32 = Float
type float64 = Float
type bin     = String
```

- **幅を書かない `Integer` は int32、`Float` は float64** として扱う (幅の要る場面 = 境界の
  バイト列と ROS 2)。32 ビットに収まらない値は `int64` と明示する。
- 範囲の外の値は、バイト列に詰めるときにエラーにする (黙って切り捨てない)。
- `uint64` の 2 の 63 乗以上は端末では扱えない、と資料に書く (本体の整数は全部のビルドで
  64 ビットの符号つき)。
- ROS 2 の `byte` と `char` は、取り込むときに `uint8` に読み替える。
- 別名の定義は 1 つの rbs のファイルにまとめる。Family mruby は `sig/` の中、Asterism は gem の
  中に同じ内容を持つ。
- 道具は別名を名前で見分ける (どのファイルで定義されたかは見ない)。アプリが自分の rbs に同じ
  別名を書いても動く。

3 つの場面での対応:

| RBS | 端末の中の境界 (固定の並びのバイト列) | ROS 2 | Asterism の型 |
|---|---|---|---|
| `int8`〜`int64`・`uint8`〜`uint64` | その幅の整数 (リトルエンディアン) | 同じ名前の型 | `int` |
| `Integer` (幅なし) | 32 ビットの符号つき整数 | `int32` | `int` |
| `float32` | 32 ビットの小数 | `float32` | `float` |
| `float64`・`Float` (幅なし) | 64 ビットの小数 | `float64` | `float` |
| `bin` | ポインタと長さ | `uint8` の配列 | `bin` |
| `String` | ポインタと長さ | `string` | `str` |
| `bool` | 1 バイト | `bool` | `bool` |
| `untyped` | (境界には載せない) | (表せない) | `any` |
| `Array[T]` | ポインタと個数 | 可変長の配列 | `T[]` |

### 端末で RBS を解析する部品

- **上流の `rbs` の gem に入っている C の解析器を使う。** Ruby に依存せず、メモリの確保は
  まとめて取って終わったら全部返す作り。自作はしない。
- **UTF-8 だけにする** (上流のビルドの指定 `RBS_ENCODING_EXCLUDE_FULL`)。
- **識別子 (型・フィールド・メソッド・クラスの名前) は ASCII に限る** (ASCII 以外を使う予定は
  無い)。コメントと文字列の中の日本語は通す。
- 大きさの見込みは約 85 KB (下の「試作」)。端末に載せて測ってから、改めて判断する。

## 試作 (2026-11-14、`tools/rbs_asterism_poc/`)

PC の上のプログラム。上流の C の解析器で RBS の記録型の別名を読み、Asterism の `define_type` に
渡す形を出す。ファームウェアには組み込んでいない。

- 卓のゲームが公開している型 5 つを RBS の記録型で書くと、実際に網に流れている宣言と、

  | 構成 | 解析器の分 |
  |---|---|

  | UTF-8 だけ | 約 102 KB |

## RBS と ROS 2 のメッセージの定義 (調べた結果)

Asterism には ROS 2 の橋が既にある (`.msg`・`.srv` から Ruby の型のファイルを生成して同梱、
通信の形式の読み書きは幅・上限つきの文字列・固定長と可変長の配列に対応)。

| ROS 2 の `.msg` | RBS で書けるか |
|---|---|
| フィールドの名前と並び | 書ける (並びは書いた順とする決まりが要る) |
| `bool`・`string`・`float64` | 書ける |
| `float32`・`int8`〜`uint64` | 上の別名で書ける |
| 入れ子の型、可変長の配列、コメント | 書ける |
| サービス (要求と応答) | 書ける (メソッドの引数と戻り値が合う) |
| 固定長の配列 | 組で書けるが読みにくい |
| 上限つきの配列と文字列、既定値 | 書けない (注釈で補う) |
| アクション | 対応する形が無い |

逆に、RBS の省略できるフィールド・値が無い場合・複数の型のどれか・`untyped` は、ROS 2 で
表せない。ROS 2 に出したい型は、使える書き方を絞る必要がある。

見立て: 全部を RBS に一本化せず、RBS を中心に置いて ROS 2 とは変換でつなぐ (ROS 2 が元の
型は今の道具のまま、必要なら RBS も出力する)。

## 使い道の候補 (小さい順、どれも未着手)

| 番号 | 内容 | 置き場所 |
|---|---|---|
| 1 | PC の上の Ruby のプログラム (卓のゲームなど) で、RBS から型を宣言する補助 | Asterism の gem |
| 2 | 本体が決める記録型 (イベント・センサなど) を、doc/wasm_apps の W4 の生成で Asterism の宣言にも出す | Family mruby |
| 3 | wasm・Lua のアプリから、型つきのトピックを流す | Family mruby |
| 4 | 公開するオブジェクトのメソッドも RBS で書き、各言語の型つきの呼び出しを生成する | Family mruby と Asterism |
| 5 | 端末の上で RBS を解析し、端末のエディタで書いた型をその場で宣言する | Family mruby |

- 同じ記録型から、端末の中は固定の並びのバイト列、端末の間は MessagePack と宣言、の 2 つの
  形が出る。
- Asterism は独立した OSS なので、Family mruby の生成の道具に依存させない。

## 別の端末のオブジェクトを、他の言語から型つきで呼ぶ (使い道の 4、2026-11-14 に検討)

公開するオブジェクトを RBS のクラスとして書けば、そこから Rust や Python 用の呼び出しの関数を
生成できる。アプリを書く人から見ると、別の端末にある Ruby のオブジェクトが、自分の言語の
普通のメソッドとして呼べる。

型定義の例:

```rbs
# A shared drawing board (640x360).
class Board
  # Joins the board as name. Returns the token every later call brings.
  def join: (String name) -> { token: String, owner: bool }

  # Starts a stroke: colour c 0-15, width step w 0-3, pts [x, y, ...].
  def line: (String token, uint8 c, uint8 w, Array[int16] pts) -> { id: int32 }
end
```

生成されるコードの例 (Rust):

```rust
pub struct Board { /* the place of the object: node/app/object */ }

impl Board {
    pub fn join(&self, name: &str) -> Result<JoinResult, CallError> { ... }
    pub fn line(&self, token: &str, c: u8, w: u8, pts: &[i16]) -> Result<LineResult, CallError> { ... }
}
```

生成される関数の中身は定型: 引数を MessagePack に詰め、Asterism の呼び出しを送り、返ってきた
値を構造体に戻す。

- **RBS が足すのは、引数と戻り値の型。** 今の Asterism でも、オブジェクトはメソッドの名前・
  引数の数・引数の名前・説明を公開している (MCP が一覧からツールを作れるのはそのため)。動的な
  言語ならそれだけで呼べる。型が要るのは、Rust のような型の厳しい言語で関数と構造体を作る
  ときと、間違った引数をコンパイルのときに見つけたいとき。特に戻り値は、今は説明文に書いて
  あるだけなので、記録型として書くと受ける側が構造体として扱える。
- **逆向きもできる。** 同じ定義から、呼ばれる側の骨組み (届いた引数を構造体に戻して、アプリが
  書いた関数に渡す) も生成できる。Rust で書いたアプリがオブジェクトを公開し、Ruby のアプリから
  呼ぶ向き。
- **呼び出しの送り方は、アプリが動く場所で違う。**

  | 場所 | 送り方 |
  |---|---|
  | 端末の上の wasm・Lua・MicroPython のアプリ | 本体が通信を受け持つ。「相手の場所・メソッドの名前・引数のバイト列を渡すと、結果のバイト列が返る」境界の関数を 1 つ用意し、生成される関数はそれを呼ぶ。各言語が Zenoh を持つ必要は無い |
  | PC の上の Rust・Python のプログラム | 自分で Zenoh につなぐ。Zenoh の上に、Asterism の呼び出しの決まりを実装する小さな層が言語ごとに要る |

- **端末の中の生成と同じ道具で作れる。** doc/wasm_apps の W4 は「RBS のクラスとメソッドの定義
  から、各言語の呼び出しのコードを作る」。違いは、呼び出しの届け先が本体の C の関数か、
  Asterism の網か、だけ。RBS が端末の中の言語の間と、端末の間の両方をつなぐ。
- 気を付ける点:
  - 定義と実物のずれ。生成したコードはビルドした時点の RBS に基づく。接続のときに、相手が
    公開している情報 (メソッドの名前と引数の数) と照合して、ずれていたら知らせる仕組みが要る。
  - 型の決まらない値。今の卓のゲームは、戻り値に中身の決まらない配列をよく使う。そこは他の
    言語でも動的な値として扱うことになる。型をつけたい所は記録型として書き直す。
  - エラーの扱い。Asterism のエラーの種類 (相手が例外を投げた、公開されていない、引数が違う、
    応答が無い) を、各言語のエラーの型に対応させる決まりが要る。
  - Asterism の呼び出しの仕組みの細部は、まだ読んでいない。ここまでは、一覧で見える情報と
    型の宣言の仕組みからの見立て。進めるときは、プロトコルの文書を読んでから設計する。
