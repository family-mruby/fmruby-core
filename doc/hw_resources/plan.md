# HW の資源をアプリに開放する (GPIO・I2C・ADC・PWM・UART) 計画

> 状態: 計画済 | 更新: 2026-11-14 | ピンとバスの持ち主の管理を本体の C の 1 か所に作り直し、GPIO・I2C・ADC・PWM・UART を、PicoRuby の上流と同じ書き方のクラスで Ruby から使えるようにする。端子は基板ごとの TOML で名前を付ける。型定義からの生成 (doc/wasm_apps の W4a) の後に全言語へ出す。H0 (調べ) 済、実装はアプリの API の整理 (doc/codebase_tidy) の後

## 目的

- アプリから、基板の端子につないだ部品 (センサ、LED、サーボ、シリアルのモジュールなど) を
  使えるようにする。
- 複数のアプリが同じピンやバスを使おうとしたときに、本体が調停する。アプリの約束に頼らない。
- アプリの言語によらず同じ管理を通す。Ruby のほか、wasm (Rust・TinyGo・Zig)・Lua・MicroPython の
  アプリからも同じ機能を使えるようにする (doc/wasm_apps の境界の方針に乗せる)。

経緯: 管理が中途半端なままだったのは、多言語対応の方針がまだ決まっていなかったため。
境界の方針 (定義は `sig/*.rbs` の 1 か所、境界の関数は単純な形、Ruby は薄い包み) が決まった
ので、その上で作り直す (2026-11-14 ユーザ)。

## 方針 (2026-11-14 ユーザ)

- **標準化する機能は GPIO・I2C・ADC・PWM・UART。**
- **SPI は対象外。** 高速の通信を Ruby から実行するのは適さない。
- **HW のクラスは自前で持ち、API は上流の PicoRuby に合わせる。** 上流の gem をそのまま使うと
  HAL への適合の調整が要り、型定義も上流の gem の中になる。自前なら、境界の関数・型定義からの
  生成・Ruby の包みにそのまま乗る。PicoRuby を使う人が自然に書けるクラスを保つ。
  - 今は上流の gem に自作の下の層を付けた形で動いている GPIO と I2C も、同じ形に揃える。
  - 互換の範囲:

    | 範囲 | 扱い |
    |---|---|
    | クラス名、生成のしかた、主なメソッドと引数の形 | 上流と同じにする |
    | ピンを名前で受ける、使用中のときのエラー、閉じる処理 | 自前の拡張として足す。上流のコードの動きは変えない |
    | 特定のマイコンに固有の機能 (ピンの機能の切り替えなど) | 対象外。違いを資料に書く |

  - 上流の I2C のクラスを使う Ruby のドライバ (`picoruby-rx8130`・`picoruby-rx8900`・
    `picoruby-bmi270`) が、直さずに動くこと。
  - 互換は、上流の gem に付いている試験と使用例を、sim の偽物の上で流して確かめる。
- **I2C のバスは共有にする。** バスは本体が持ち、アプリは使う機器の番地を申告する。番地ごとに
  持ち主を管理し、同じ番地を 2 つ目のアプリが使おうとしたら断る。操作は代理のタスクが 1 つずつ
  実行するので、通信は混ざらない。本体の機器 (IMU・音のコーデック・電源の管理など) の番地は
  システムのものとして登録し、アプリから触れないようにする。
- **ピンとバスは名前で指定するのを基本にし、番号でも指定できる。** 番号は基板ごとに違い、
  Linux では意味も違う。番号での指定は、PicoRuby 向けの既存のコードのために残す。
- **名前の見せ方の定義は、編集しやすくする。** 見せ方は基板に完全に依存するため。
  - C のヘッダに埋めず、TOML のファイルにして起動時に読む。`config/hw_<基板>.toml` を元に
    端末の `/etc/hw.toml` を作り、利用者は `/home/hw.toml` で上書きできる (`associations.toml` と
    同じ流儀)。自作の拡張基板をつないだ人が、ビルドし直さずに名前を足せる。
  - システム専用のピン (USB・PSRAM・SD・表示・描画側との通信など) とシステムの I2C の番地は、
    今までどおり本体のコードで守る。TOML に書いてあっても開放しない。
  - 書き間違い (知らない番号、システム専用のピン、名前の重複) は起動時にログに出す。
- **最初の対象の基板は、ヘッドレスの S3 (AtomS3R・StickS3)、Modern (Tab5・NARYA v4)、Retro
  (NARYA v3)。**
- **将来は Cardputer Zero (Linux のネイティブ版) の HW も使えるようにする。** 最初の対象には
  入れないが、作りを ESP-IDF に縛らない: 資源の管理は `fmrb_hal` の上の共通の層に置き、HW を
  動かす部分だけを環境ごとに差し替える。基板ごとの定義は、機種の定義 (`config/machines/`) と
  同じ考え方で書けるようにする。
- **試験用の偽物は sim にだけ置く。ブラウザ版には置かない** (一般の利用者も使うので、混乱させ
  ない)。ブラウザ版では HW の関数は「この環境では使えない」というエラーを返し、アプリが起動の
  前に確かめられる問い合わせの関数を用意する。
- **資源の管理は境界の下 (本体の C の 1 か所) に置く。** 持ち主はタスクではなくアプリの単位に
  する。アプリが終わったときの片付けは、言語に関係なく本体が行う。
- IMU・時計・電池・マイクなどは、バスではなく機器の機能として見せる (今ある専用の API)。
  アプリに I2C の番地で直接触らせない。
- パルスの出力 (RMT。LED テープ・赤外線) は、今の機能を新しい管理の下に入れるところまで。
  機能を広げるのは将来。

## 設計の骨格

- アプリには、開くと返る番号つきの口を渡す。以後の読み書きはその番号で行う。ファイルと同じ
  形で、型定義の規則 (レシーバは第 1 引数の番号) に乗る。
- Ruby の側は、上流のクラスの形 (`GPIO.new(...)`・`I2C.new(...)`・`ADC.new(...)`・
  `PWM.new(...)`・`UART.new(...)`) を包みとして持つ。名前を受けたときは、包みが名前を番号に直す。
- 基板ごとの差は、資源の表 (TOML) に閉じ込める。
- 「この端末で何が使えるか」を見せる: 使える端子の名前・用途・今の持ち主を返す問い合わせの
  関数、GPIO の一覧のアプリ (`gpio_viewer`) の拡張、Shell のコマンド。

TOML の書式の例 (番号は説明用):

```toml
[[port]]
name = "grove"          # アプリが指定する名前
label = "Grove"         # 画面に出す名前

  [port.i2c]            # この端子を I2C として使うとき
  sda = 2
  scl = 1

  [[port.pin]]          # この端子を 1 本ずつ使うとき
  name = "grove.1"
  gpio = 1
  can = ["gpio", "adc", "pwm"]

  [[port.pin]]
  name = "grove.2"
  gpio = 2
  can = ["gpio", "adc", "pwm"]

[default]               # 名前を省いたときに使うもの
i2c = "grove"
```

アプリは `I2C.new("grove")`・`GPIO.new("grove.1")` のように書ける。`GPIO.new(1)` も残す。

## 受け入れ条件

- 対象の基板で、GPIO・I2C・ADC・PWM・UART がアプリから使える。
- 2 つのアプリが同じピン、または同じ I2C の番地を使おうとしたとき、2 つ目が理由つきで断られる。
  別の番地の機器なら、同じバスを 2 つのアプリで同時に使える。
- システム専用のピンとシステムの I2C の番地は、TOML をどう書いてもアプリから使えない。
- アプリが終わると、そのアプリが持っていたピンとバスが返される。異常終了でも同じ。
- 上流の PicoRuby 向けに書かれた I2C のドライバ (RTC・IMU) が、直さずに動く。上流の gem に
  付いている試験が、対象外と決めた項目を除いて通る。
- 名前の定義を `/home/hw.toml` で足すと、ビルドし直さずにその名前で開ける。
- sim で、取得・解放・競合の判定が回帰の道具で確認できる。ブラウザ版では HW の関数が
  「使えない」を返し、アプリが事前に確かめられる。
- 内蔵 RAM が増えない (`rake regress:size`)。
