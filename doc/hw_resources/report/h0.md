# H0: 今の作りと基板ごとの空きを調べる (2026-11-14)

コードを読んだだけで、何も変えていない。端末では確かめていない。

## 1. 今ある土台

- **ピンの台帳** (`components/fmrb_hal/fmrb_hal_pin_manager.h`、実装は ESP32 用と POSIX 用)。
  ピンごとに使い方の種類と持ち主 (タスク) を持つ。取得・解放・持ち主ごとの一括解放・
  空いているかの問い合わせがある。使い方の種類には、GPIO・I2C・RMT のほかに、SPI・PWM・UART も
  定義済み (実装は無い)。
- **システムのピンの登録**。起動時 (`main/boot/boot.c`) に台帳を初期化し、起動用・USB・PSRAM・
  SD・描画側との通信などのピンを「システム専用」として登録する。元はピンの割り当ての定義
  (`components/fmrb_common/include/fmrb_pin_assign.h`)。
- **代理のタスク** (`main/drivers/hw_proxy/`)。GPIO・I2C・RMT・ファイルの操作を、1 つのタスクが
  1 つずつ実行する。呼ぶ側はミューテックスで順番を待つので、同時に 2 つの操作が走らない。
- **終了時の片付け** (`hw_proxy_release_resources`)。タスクが終わると、そのタスクが持っていた
  I2C・RMT・ピンを返す。
- **Ruby の側**。上流の PicoRuby の gem (`picoruby-gpio`・`picoruby-i2c`) を使い、下の層だけを
  自作している (`lib/add/picoruby-gpio-proxy`・`picoruby-i2c-proxy`・`picoruby-rmt-proxy`)。
  I2C の gem には、閉じる処理を足す修正を当てている (`lib/patch/picoruby-i2c`)。
- **端子が用途を兼ねる扱い**。Tab5 と NARYA v3 の Grove 端子は、I2C のバスとしても、シリアルの
  MIDI 出力としても使える。開くときに台帳が調停する。

## 2. 穴

| 場所 | 今の動き | 問題 |
|---|---|---|
| I2C の初期化 (`hw_proxy_i2c.c`) | ピンの取得を呼ぶが、結果を見ていない | システム専用のピンや、他のアプリが使っているピンを指定しても通る |
| GPIO (`hw_proxy_gpio.c`) | 取得するのは `reset` の操作だけ。設定・読み・書き・プルでは持ち主を確認しない | 他のアプリが取得したピンを、別のアプリが書き換えられる |
| I2C のバス | バス (2 本まで) ごとに持ち主が 1 つ。別のタスクの初期化は「使用中」で断る | 同じバスの別の機器を、2 つのアプリで使い分けられない |
| I2C のバスの寿命 | ESP-IDF の不具合を避けるため、一度作ったバスは解放後も持ち続け、次の持ち主が引き継ぐ | 共有にするときは、この作りを前提にできる (バスは本体が持つ) |
| RMT | チャネルが全体で 1 つ、持ち主が 1 つ | 2 つのアプリが同時に使えない |
| 持ち主 | タスクのハンドル | アプリの単位ではない。1 つのタスクに複数のサービスが同居する場合の区別が無い |
| ADC・PWM・UART | 無い | 上流の gem はあるが、ビルドの設定でコメントアウトされている (`lib/add/family_mruby_esp32.rb`) |

## 3. 基板ごとの、開放の候補

ピンの割り当ての定義から読んだもの。

| 基板 | アプリに開放する候補 | システムが使っている主なもの |
|---|---|---|
| AtomS3R | Grove 端子 (G1・G2、プルアップ無し)、底のヘッダ (G5〜G8、G38、G39) | 内部の I2C (G45・G0: バックライトの制御、IMU)、LCD、赤外線の送信 (G47)、ボタン (G41) |
| StickS3 | Grove 端子 (G9・G10、プルアップ無し)、Hat2 のヘッダ (G1〜G8、G43、G44) | 内部の I2C (G47・G48: 電源の管理、IMU、音のコーデック)、LCD、音、赤外線 (G46・G42)、ボタン (G11・G12) |
| Tab5 | Grove 端子 (G53・G54。シリアルの MIDI 出力と兼用) | 内部の I2C (G31・G32: タッチほか。表示の I2C の処理を仲介する扱いが入っている)、キーボード (G0・G1)、SD、USB |

分からなかった点:

- Tab5 の背面の拡張ヘッダに、開放できるピンがあるか。
- NARYA v3 に、I2C の 2 本以外で空いているピンがあるか。
- NARYA v4 (今は開発用の基板で確認中) のピンヘッダのうち、開放してよいもの。

## 4. 内部の I2C に載っている本体の機器

どの基板も、本体が使う機器が I2C のバスにつながっている (IMU、音のコーデック、電源の管理、
バックライトの制御、タッチなど)。I2C を共有にするなら、これらの番地をシステムのものとして
登録する必要がある。AtomS3R では、アプリが内部の I2C を開けるように、起動用のピンを兼ねる
2 本をシステム専用にしていない、という判断が既に入っている。

## 5. 上流の PicoRuby のクラスの形

上流には gpio・i2c・adc・pwm・uart・spi の gem がある。型定義から読んだ主な形:

| クラス | 生成 | 主なメソッド |
|---|---|---|
| GPIO | ピンと設定の旗 | `read`・`write`・`high?`・`low?`・`setmode`・`set_dir`・`set_pull`、クラスメソッドの `read_at`・`write_at` |
| I2C | バスの番号・ピン・周波数 (キーワード引数) | `read`・`write`・`scan` |
| ADC | ピン | `read`・`read_voltage`・`read_raw` |
| PWM | ピン、周波数とデューティ (キーワード引数) | `frequency`・`duty`・`period_us`・`pulse_width_us` |
| UART | バスの番号・ピン・速さ (キーワード引数) | `read`・`readpartial`・`getbyte`・`bytes_available`・`gets`・`puts`・`write`・`set_format`・`set_flow_control` |

- 上流のクラスはピンを整数で受ける。名前での指定は上流に無い拡張になる。包みで名前を番号に
  直せば、上流と同じ書き方のコードはそのまま動く。
- 上流の gem には、それぞれ試験が付いている (I2C と SPI は使用例)。互換の確認に使える。

## 6. 見立て

- 管理は無いのではなく、土台があって穴が空いている。作り直しの中心は、持ち主の確認を全部の
  操作に通すことと、I2C を番地ごとの持ち主に変えること。
- 端子が用途を兼ねる扱いが既にあるので、TOML の「端子ごとに使える用途の一覧」はその延長になる。
- ADC・PWM・UART は、Ruby のクラスの形は上流に合わせ、下の層を代理のタスクの上に新しく書く。
