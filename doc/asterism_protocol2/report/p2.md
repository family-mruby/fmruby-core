# P2 report: Asterism 本体に protocol 2 を入れた

> 状態: 済 (確認待ちの点あり) | 更新: 2026-11-13 | asterism に `Asterism.publish` / `Asterism.subscribe` / `define_type` / `pubs_of` / `types_of`、アプリの自己紹介 `@profile` の queryable、`@pubs` の put、通し番号と送り手の時刻の attachment を入れ、`docs/protocol.md` と適合の試験を protocol 2 に書き換えた (asterism eaff7b9・71a43ed)。部品 (picoruby-asterism-zenoh) の不具合は見つからず、触っていない。**pose の要素の並びと「組み込みの型の配列」の書き方は design.md に無く、決めずに残した** (下の「止まった点」)

## 1. 足した API

### 送る側・受ける側 (CRuby と端末で同じ `mrblib/topic.rb`)

| API | CRuby | 端末 (mruby / PicoRuby) | 中身 |
|---|---|---|---|
| `Asterism.publish(name, type:, unit:, desc:, ts:, encoding:)` → `Asterism::Topic` | ○ | ○ | 部品の `session.publisher` で `asterism/<node>/<app>/<name>` を宣言。`name` は `/` を含んでよい (各区切りは名前の決まり)。同じ名前で呼ぶと置き換え (番号は 0 から、`@pubs` の並びは保つ) |
| `topic.put(value)` | ○ (どのスレッドからも、LOCK を取る) | ○ | encoding なし: `Codec.pack` して encoding を付けずに送る。encoding あり: String をそのまま送る (String 以外は ArgumentError)。attachment は `[seq]` か `[seq, ms]` |
| `topic.close` / `Asterism.unpublish(topic か名前)` / `Asterism.published` | ○ | ○ | 取り下げると `@pubs` を put し直す |
| `topic.seq` / `topic.declaration` / `topic.ts?` / `topic.closed?` | ○ | ○ | 次に送る番号、宣言の map |
| `Asterism.define_type(name, fields, desc: nil)` | ○ | ○ | `{"f" => [[名前, 型], ...], "d" => 説明}`。型は組み込みの番号 (`:vector3` も可)・基本の型名・ほかの独自の型名、末尾 `[]` で配列。状態と同じく接続をまたいで残る |
| `Asterism::Types` | ○ | ○ | `NUMBER`=1 〜 `TEXT`=7 の定数、`Types.number(:vector3)`、受け取った定義の掃除 `Types.check` |
| `Asterism::Pubs` | ○ | ○ | `Pubs.encoding_id("image/jpeg")` (=17、Zenoh の決まった番号 0〜52 の表)、受け取った宣言の掃除 `Pubs.check`、`@pubs` の put を読む `Pubs.parse` |
| `Asterism.subscribe(path, depth: nil) { \|v, info\| }` → `Asterism::Subscription` | ○ | ○ | `Asterism.poll` の中からだけブロックを呼ぶ (待っている呼び出しの中では呼ばない)。`\|v\|` だけのブロックも動く (CRuby・mruby の両方で試験した) |
| `info` (`Asterism::SampleInfo`) | ○ | ○ | `key`・`node`・`app`・`name`・`path`・`seq`・`time` (送り手の ms、無ければ nil)・`encoding` (無ければ `"msgpack"`)・`timestamp` (ルータの、部品の `Timestamp`、無ければ nil)・`lost`・`restarted?`・`to_h` |
| `sub.close` / `closed?` / `received` / `malformed` / `dropped` | ○ | ○ | `malformed`: encoding が無いのに MessagePack 1 つでない値 (ブロックに渡さず数える) |
| `Asterism.status_of(node, app)` | ○ | ○ | `@profile?status` に問い合わせるように変えた (形は今どおり) |
| `Asterism.pubs_of(node, app)` / `Asterism.types_of(node, app)` | ○ | ○ | 答えたが無い → `{}`、答えが無い → nil。自分のアプリの分は網を使わない |

### CRuby だけ (lib/asterism/cruby/objects.rb)

- 新しい入口 (`publish`・`unpublish`・`published`・`topic_put`・`define_type`・`subscribe`・`unsubscribe`・`app_profile_async`) を `Asterism::LOCK` の下に入れた。
- `net.publish` / `net.subscribe` (ブロックは受信スレッドで動き、raise は `on_error` に `"subscribe"` で届く) / `net.pubs_of` / `net.types_of` / `net.define_type` / `net.unpublish` / `net.published`。
- CLI の `Survey#statuses` (`asterism status get` など) を `@profile?status` に変えた (変えないと asterism 自身の試験が落ちるため。CLI の表示に宣言を出すのは P3)。

### 名前の決め方

- `pubs_of` は指示書の例 `pubs_of("<node>/<app>")` ではなく、`status_of(node, app)` の流儀に合わせて引数 2 つにした (指示書の「今の流儀に合わせる」を優先)。
- 包みのクラスは `Asterism::SampleInfo`、購読は `Asterism::Subscription`、宣言したトピックは `Asterism::Topic`。CRuby の `::Data` と `::Encoding` を隠さないよう、`Asterism::Data`・`Asterism::Encoding` は使っていない。
- 指示書・design.md に無く、足したもの (既定の動きは変えない): `subscribe` の `depth:` (部品の購読の深さ、省略で部品の既定 16)、`Asterism.unpublish` / `published` (`unexpose` / `exposed` と対)、`SampleInfo#restarted?` (折り返しとつなぎ直しを区別した結果を見せる)。
- 受け付ける長さの上限 (design.md に無いので既存の流儀から): `unit` 64 バイト、`desc` 2048 バイト (メタの doc と同じ `DOC_MAX`)、型の名前・フィールドの名前 128 バイト、フィールド 64 個まで。

## 2. `@profile` の queryable の立て方: 「伝えるものができたときに立てる」

- **今の「状態があるときだけ」を広げて、状態・トピック・独自の型のどれかが初めてできたときに立てる** (`Asterism.app_queryable`、一度立てたら close まで残す)。
  状態だけのアプリ・何も無いアプリの queryable の数は今と同じ (`**` と、あれば `@profile`)。
- 理由 (RAM): P1 の実測で queryable 1 つは zenoh-pico 側 650 B (PSRAM) と VM のプール 64 + depth 4 × 8 = 96 B。Family mruby の
  アプリの多くは状態もトピックも持たないので、常に立てるとアプリごとにこれが増える。立てる時機を 1 か所 (`app_queryable`) に
  まとめたので作りも複雑にならない (呼ぶのは `tell_status`・`publish`・`define_type`、接続時に型があるとき)。
- 読む側の違い: 何も無いアプリは答えない (`status_of` などは nil)。答えて部分が無いときは `{}` (キーごと省く)。
- 引数の読み方: `;` で区切り、`=` の前を名前とし、`status`・`pubs`・`types` だけを数える。どれも無ければ既定 (状態とトピック)。
  `status;types` のように 2 つ書けば 2 つ返す (design.md 9 の素直な延長。実装の呼び出しは 1 つずつしか書かない)。
- `@status` の put は今どおり。`@status` への問い合わせには誰も答えなくなった (試験で確認)。

## 5. 1 値あたりに送るバイト数 (実測)

測り方: 受け手 (CRuby、peer で listen) と送り手の間に TCP の中継を挟み、送り手 → 受け手のバイト数を数えた (Zenoh の枠を含む、キー以外も全部)。
500 個を 2 ms おきに送った平均。値は `[0.5, -1, 3]` (MessagePack 12 バイト) など。スクリプトは scratchpad (コミットしていない)。

### CRuby の送り手 (zenoh-c 1.10.1、msgpack-ruby = 最短の形)

| 送り方 | 線の上 (B/値) | payload | attachment |
|---|---|---|---|
| **`topic.put` (publisher、`[seq]`)** | **33.2** | 12 | 4 (`[499]`) |
| `topic.put`、`ts: true` (`[seq, ms]`) | 43.2 | 12 | 13 |
| 参考: 今の素の `session.put` (attachment なし) | 28.0 | 12 | 0 |
| 参考: 部品の publisher、attachment なし | 31.0 | 12 | 0 |
| 参考: `session.put` + `[seq]` | 34.2 | 12 | 4 |
| `topic.put(1)` (整数 1 つ) | 20.2 | 1 | 4 |
| 100 バイトの JPEG (`image/jpeg`、生) | 122.2 | 100 | 4 |
| 同じ 100 バイトを MessagePack の bin で | 123.2 | 102 | 4 |
| seq が 65535 を超えたとき (`topic.put(1)`) | 25.0 | 1 | 6 |

### 端末の送り手 (mruby + zenoh-pico 1.10.1。ただし試験用の MessagePack は長い形で書く)

| 送り方 | 線の上 (B/値) | payload | attachment |
|---|---|---|---|
| **`topic.put` (publisher、`[seq]`)** | **34.9** | 14 | 12 |
| `topic.put`、`ts: true` | 44.0 | 14 | 21 |
| 参考: 今の素の `session.put` (キーを毎回送る) | 45.2 | 14 | 0 |
| 参考: 部品の publisher、attachment なし | 23.0 | 14 | 0 |
| 参考: `session.put` + attachment | 58.2 | 14 | 12 |
| 100 バイトの JPEG | 122.0 | 100 | 12 |

- host_test の MessagePack (host_test/msgpack.rb) は array16・int64 の長い形で書くので、`[499]` が 12 バイトになる。端末の msgpack-c は最短の形
  (CRuby と同じ 4 バイト、payload 12 バイト) なので、**端末では `topic.put` 1 値あたり約 25 バイト (attachment を除く枠 約 21 + attachment 約 4)、
  今の素の put の約 43 バイトより 18 バイトほど軽い**と見積もる (差し引きの見積もりで、実機では測っていない)。
- 値ごとに payload の外に増えるのは attachment だけ: `[seq]` は seq < 128 で 2 バイト、65535 まで 4、それより上で 6、`ts` は +9 (ms が 2^32 を超えるので uint64)。
  encoding は MessagePack で 0、`image/jpeg` でも線の上の差は 1 バイト未満 (bin の頭 2 バイトがなくなる分と相殺)。

## 6. 見立てと違った点

- **zenoh-c (CRuby) では publisher にしても線の上は軽くならない**: 素の `session.put` 28.0 B に対し、attachment なしの publisher で 31.0 B。
  zenoh-c は素の put でもキーを毎回丸ごとは送っていない (peer の直結で 16 バイトの枠に収まる)。キーが軽くなるのは zenoh-pico の側
  (45.2 → 23.0 B) で、design.md 2 章の「キーも短くなる」は端末の送り手について正しい。
- **attachment の大きさは「1〜5 バイト」でなく 2〜6 バイト**: design.md 2 章の表は通し番号の整数の大きさで、配列の頭 1 バイト (`0x91`) が加わる。
- **アプリは自分の流した値を自分の購読で受け取らない** (CRuby・mruby とも、手元の peer で確認)。protocol.md には「当てにしない」と書いた。
- **ベースラインで `rake test` が 1 つ落ちていた**: `test_cli.rb` の `test_usage` (router 無しの `asterism nodes` が 2 を返すはず)。
  この WSL の環境変数 `ASTERISM_CREDENTIALS` が設定されていて、CLI がそれを読んで本物の網へつないだため (変更前から。試験の環境依存)。
  以後は `env -u ASTERISM_CREDENTIALS` で流した。試験側で環境変数を外すかは触っていない。
- 同じ名前でもう一度 `publish` したとき、表から消して入れ直すと `@pubs` の並びが変わり、同じ中身でも put が出た。置き換えをその場にして
  並びを保つようにした (同じ宣言なら put しない)。

## 7. 撤回した仮説

- 「通し番号の読みは "上限近くから 0" だけを折り返しと見ればよい」: 上限近くの幅を決める必要があり恣意的になるので、
  RFC 1982 と同じ「前方への距離が範囲の半分 (2^30) 未満なら前進、それ以外はつなぎ直し」にした。上限 → 0 は距離 1 で折り返しになる。
  試験で、半分を超える前方への飛び (5 → 2^31-1) がつなぎ直しと読まれることも確かめた (人工的な場合)。
- 「部品の API を足す必要が出るかもしれない」: 出なかった (P1 の `publisher`・`each_sample`・`Sample#encoding`/`attachment`/`timestamp` で足りた)。
  picoruby-asterism-zenoh・asterism-zenoh とも変更なし。

## 8. 止まった点・確認してほしい点 (自分では決めていない)

1. **pose (組み込みの型 3) の要素の並び**: design.md は「位置と向き」「配列の流儀」とだけある。protocol.md には
   「並びは未確定。案は `[x, y, z, qx, qy, qz, qw]` (向きは四元数)」と書いた。候補: (a) その案 (ROS の Pose と同じ並び)、
   (b) 2 次元の `[x, y, θ]` も別の番号で足す、(c) `[[x, y, z], [qx, qy, qz, qw]]` の入れ子。コードは形を検査しないので、どれでも実装は変わらない。
2. **独自の型のフィールドで「組み込みの型の配列」の書き方**: design.md 10 は「型は組み込みの番号 … 末尾の `[]` で配列」で、番号に `[]` を
   付けた形が決まっていない。今は `define_type` が ArgumentError で断る (`"vector3[]"` など)。候補: (a) 文字列 `"2[]"`、
   (b) 組み込みの型を名前で書く `"vector3[]"` (番号と名前の 2 つの書き方になる)、(c) 配列 `[2]`。
3. 通し番号の読みの細部 (受け手の API の既定の動き): 最初の値は `lost` 0、つなぎ直しは `restarted?` true で `lost` は新しい回の番号 (= その前に来なかった数)、
   同じ番号の繰り返しもつなぎ直し。design.md 2 章・12 の読み方から決めたが、`lost` の数え方を変えたいならここ (`Subscription#unwrap`)。
4. MessagePack でない値 (encoding なしで解けない) はブロックに渡さず `malformed` に数える。nil として渡す形にはしていない (3.1「読めないものを nil にしない」に合わせた)。

## 9. 残件 (P3 で使う側を入れ替えるときの注意)

- **入れ替えは一斉に**: protocol 2 の `status_of` は `@profile?status` に聞くので、protocol 1 のアプリ (今の asterism-games・console・fmruby-core の
  アプリ) の状態は読めない。逆に protocol 1 の読み手は protocol 2 のアプリの状態を `@status` への問い合わせで読めない (put は届く)。
- console・CLI の ACL: 読み手は `asterism/*/*/@profile` の query と `asterism/*/*/@status`・`@pubs` の subscription、アプリは
  `asterism/<node>/*/@profile` の queryable と reply、`@status`・`@pubs` の put が要る。今の `@status` の queryable の規則は要らなくなる。
- `asterism mcp` の `asterism_values` は `asterism/**` の put を MessagePack として覚えるだけで、encoding・attachment を見ない
  (JPEG のトピックは読めない値になる)。CLI の `asterism status echo` は `@status` の put を購読するので今のままで動く。宣言の表示は未対応。
- アプリ側の書き換え: 今 `session.put("asterism/<node>/<app>/...")` で流しているもの (卓の状態、お絵かきの strokes、ログ) は `Asterism.publish` に。
  トピックは接続ごと (Asterism.close・つなぎ直しの `connect` で消える) なので、`connect` のあとに宣言し直す。型・状態は残る。
- zenoh-pico の publisher は購読者を知る前の最初の数回の put を送らないことがある (P1)。受け手の最初の値の番号は 0 とは限らない (`lost` は数えない)。
- 端末の `Topic#put` は値ごとに attachment の String を 1 つ作る (`MessagePack.pack([seq])`)。毎フレーム流すアプリで GC が気になれば、
  その時に測る。publisher 1 つ約 0.7 KB (PSRAM、P1) なので、トピックは使い回す (毎回 `publish` しない)。
- 送り手の時刻は `Time.now` (端末は mruby-time、MRB_INT64 なので ms がそのまま整数に入る)。端末の時計が合っていないと 1970 年近くの値になる (12 章のとおり)。
- `rake regress:size` / `regress:live` と esp32・wasm のビルドは P1 から引き続き未実施 (Docker が見えない)。P2 は mrblib (Ruby) だけの変更なので
  内蔵 RAM の静的な増分は無い見込みだが、VM が mrblib を読む量は増える (topic.rb 約 600 行、エンコーディング表は 1 本の String)。
