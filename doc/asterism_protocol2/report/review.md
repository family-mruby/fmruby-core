# 設計レビューの結果と実装への提案

> 状態: 提案 (未反映) | 更新: 2026-11-13 | protocol 2 の設計 (design.md の決定 1〜28) と実装の方向を、別のセッションでレビューした結果。ユーザが決めた 4 点 (決定 29〜32 の案) と、実装・文書の直し、P4 の危険をまとめる。このレビューではコード・既存の文書を書き換えていない。反映は実装の側で行う

## 読んだ範囲

design.md、plan.md、asterism の `docs/protocol.md` 全文、`mrblib/topic.rb` 全文、report の p2b・p2c。
p1・p2・p3a・p3b の report、`mrblib/asterism.rb` の大半、asterism-games・asterism-console のコードは grep で当たっただけ。
「要確認」と書いた項目は、コードを最後まで追っていない。

## 総評

骨組み (身元・呼び出し・データの 3 層、共有の置き場 `@shared`、接続のオブジェクト) に矛盾は無い。
verbatim の区切り、publisher の宣言、「キーは共有の名前、宣言は送り手ごと」は Zenoh・rmw_zenoh の流儀に合っている。
端末は接続 1 本なら成り立つ。直すべき所は、読み手の側の記憶の扱いに集まっている。

## 1. ユーザが決めたこと (2026-11-13、design.md の決定の表に足す)

| # | 問い | 答え |

| 29 | つなぎ直しの見分け方 | 読み手は、アプリの生存の印の leave で、そのアプリの通し番号の記憶を捨てる (次の値は最初の値として `lost` 0)。通し番号は**接続ごと**で、同じ接続で宣言し直しても 0 に戻さない。ワイヤは変えない |

決めなかったこと (今の決まりのまま):

- 独自の型の値は map のまま (フィールド名なしで並べる配列の形は入れない)。値ごとの大きさは、フィールド名を
  1〜2 文字にする作法で抑える。この作法を protocol.md 11.2 に書く。
- 共有の置き場の送り手は attachment のまま (キーには置かない)。
- 宣言・`@profile` の答えの全体の上限は、P3c の実測の後に決める (3 章の 3)。

## 2. 決定に伴う直し

### 決定 29 (つなぎ直し)

なぜ要るか: 今の判定は番号の距離だけを見る (`topic.rb:566-578`)。送り手が再起動した後、読み手が最初に受けた番号が
前回より大きいと前進と読む。例: 最後が 3、再起動、新しい回の 10 を最初に受けると `lost` 6・`restarted?` false。
再起動の直後は取りこぼしが起きやすい時なので、記録の欠けの数が一番知りたい場面で信用できない。

- asterism: 接続が生存の印の leave を受けたとき、その接続の全部の購読から、そのアプリ (`<node>/<app>`) の番号の記憶
  (`Subscription` の `@last`) を消す。共有の置き場の値は、送り手 (`from`) がそのアプリのものを消す。
- asterism: `publish` で同じ名前を置き換えるとき (`topic.rb:687-700`)、前のトピックの番号を引き継ぐ。
  `unpublish` の後に同じ名前を宣言し直す場合の扱い (引き継ぐか) は、接続ごとの番号の表を持てば自然に引き継げる。
- protocol.md 9.3・9.4、design.md の決定 12・16: 「宣言し直すと 0 から」を「接続ごとに 0 から」に直す。
- 残る限界を 9.4 に書く: 読み手が leave を見る前に送り手が戻った場合は、今と同じ読み違えが起こりうる。
- 適合の見本: 宣言し直しの後の番号、leave の後の最初の値の `lost` を足す。

**同じ仕組みで片づくもの**: 読み手の決まりとして「アプリの leave で、そのアプリの宣言・型・番号の記憶を全部捨てる」を
protocol.md の 1 か所に書くと、次の 3 つも同時に直る。

- 落ちた送り手の宣言 (`@pubs` の最後の put) が残る件 (console に頼んである対応と同じもの)。
- 3 章の 1 (番号の記憶が減らない)。
- 3 章の 2 (型の問い合わせを覚えておく場合の、捨てる合図)。

### 決定 30 (時刻)

- protocol.md 3.3 の「an int of nanoseconds」を ms に、11.1 の log 型の `time` を「ms since 1970, an int」に直す。
- log 型を流す所・読む所 (asterism の CLI、games、console の表示と記録、fmruby-core) を探して合わせる
  (このレビューでは探していない)。適合の見本に log 型の値があれば直す。

### 決定 31 (今の値)

- protocol.md 9 章に「遅れて購読した読み手と、欠けに気づいた読み手は、次の値まで今の値を持たない。今の値が要る
  トピックは、アプリがオブジェクトの呼び出しで答える」と書く。
- games: 卓の状態・観戦の読み手が `info.lost > 0` か `info.restarted?` のときに取り直す。games の lib には今
  `info.lost`・`restarted?` を見ている所が無い (grep で 0 件)。
- 背景: publisher は既定の設定のまま (`picoruby-asterism-zenoh/src/zenoh.c:1777`)、端末の購読の輪は深さ 16 で
  古い順に捨てる (`zenoh.c:95`)。欠けは数えられるが、取り戻す手段は決まりに無い。

### 決定 32 (フィールドの型は名前だけ)

- asterism: `Types.field_type!` (`topic.rb:99-109`) が Integer を通しているのをやめる (ArgumentError)。
  読み手の `Types.check` (`topic.rb:135-151`) は、フィールドの型が空でない str のものだけを残す。
- protocol.md 11.2: `f` の表から「an int (a built-in type's number)」を外し、例の `["at", 2]` を `["at", "vector3"]` に。
- design.md の決定 10・15・17 の「番号でも書ける」の文言を合わせる。適合の見本に番号のフィールドがあれば直す。
- games・console の `define_type` で番号を書いている所があれば名前に直す。

## 3. 実装・文書の直し (決定は要らない)

重大度の順。

1. **購読の番号の記憶が減らない (中)**: `@last` はキーと送り手の組ごとに増えるだけ (`topic.rb:578`)。
   `*/@shared/spectate/**` を端末・ブラウザ版で長く購読すると、VM プールを食い続ける。決定 29 の leave で捨てる。
2. **`type_of`・`declaration_of` が呼ぶたびに網へ問い合わせる (中)**: 覚えておく仕組みが無い (`topic.rb:891-927`)。
   購読のブロックの中で値ごとに呼ぶと、値ごとに get と待ちが入る。送り手ごとに覚え、その送り手の `@pubs` の put か
   leave で捨てる。
3. **`@pubs`・`@profile` の答えに全体の上限が無い (中、要確認)**: status は 1024 B までだが、宣言は `d` が 1 件 2048 B まで、
   件数は無制限。zenoh-pico の分割の上限を上書きしている設定は見当たらなかった。卓の多いホストの宣言を端末・
   ブラウザ版が読めるかを P3c で実測する。結果を見て、全体の上限 (たとえば 4 KB) を決まりに置くかをユーザに聞く。
4. **共有の置き場の送り手の照合 (中)**: ノードごとの置き場の値で、`from` のノードがキーのノードと違っても
   そのまま信じている (`topic.rb:557-561`)。違えば送り手なしとして扱う。宣言の側 (`Pubs.check`) は照合している。
5. **接続のときのロック (低)**: CRuby で 2 本目を開くと、網の重複の確認 (`asterism.rb:601-615`、最長 1.5 秒) の間、
   全体のロックでほかの接続が止まる。プログラム内の重複を見た後、網の確認の間はロックを外す。
6. **console の記録の欠け (要確認)**: `lib/bridge/runner.rb:1000` の `lost` は購読の `dropped` の合計に見える。
   通し番号の欠け (網の途中で落ちた分) が入っていないなら足す。
7. **文書**:
   - protocol.md 13 章の「boards have no TLS」が古い。
   - plan.md の P2c の状態が「未着手」のまま。
   - encoding の後ろの schema (`;charset=...`) は宣言の `e` に入らない。その旨を 10.1 に一言。
   - design.md の本文への溶かし込みは、P3c の指示書を書く前に行う (サブが古い本文を読むため)。

## 4. 端末で確かめること (P3c)

- esp32・wasm のビルドと `rake regress:size` (内蔵 RAM の増分 0)。P1 以降通していない。
- 3 章の 3 の実測 (受け取れる宣言の大きさ)。
- NARYAv3: p2b の report に「TLS 1.3 が無く tls のルータにつながらない見込み」とある。P4 の受け入れに S3 を
  入れるなら先に確認する。
- 端末の 1 値あたりの大きさ (見積もり 25 B) の実測。

## 5. P4 (一斉の入れ替え) の危険と順序

1. **半分動く混在**: 呼び出しの形は protocol 1 と 2 で同じ。古いブラウザ版 (キャッシュ) や古いファームが新しい
   ホストにつなぐと、呼び出しは通り、状態と観戦だけ来ない。接続のときに相手の `protocol` を見て断るか、
   少なくともログに出す。ブラウザ版はキャッシュの版を確実に切り替える。
2. **台帳の自動の直しは一方通行**: 決定 18 で Ask の `@status` を `@profile` に置き換える。VPS の更新の前に DB の
   写しを取り、旧版の console に戻す手順を書く。
3. **ルームのアプリ名とロール**: `room01` などが増えるので、アプリ名で縛るロールはパターン (`room$*` など) が要る。
   同じ証明書で複数の接続を張れるか、zenohd の接続数の上限とあわせて、本番と同じ ACL を生成した手元の zenohd に
   全員 (ホスト・ルーム・console・ブラウザ版・ネイティブ版) をつないで通す。
4. **順序**: gem の公開は戻せない (同じ番号は使えない)。VPS を git 参照で通し、通しの確認の後に gem、
   最後にブラウザ版の配置。
5. **P3c が先**: 4 章が通るまで P4 の準備に入らない。
