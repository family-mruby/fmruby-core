# P1 report: 部品に encoding と publisher の Ruby の API を足した

> 状態: 一部未了 | 更新: 2026-11-13 | picoruby-asterism-zenoh に encoding (put の指定、受け取った値の読み出し)、publisher の宣言、受け取った値のタイムスタンプを足した。asterism-zenoh は触っていない。`rake regress` は通った。**`rake regress:size` と `rake regress:live` は docker が使えず流せていない** (下の「残件」)

## 1. 調べた結果

### asterism-zenoh (CRuby) の今の形

| 何を | 形 |
|---|---|
| put の encoding | `session.put(key, payload, attachment:, encoding:, ...)`。encoding は文字列 (`"image/jpeg"`) |
| publisher | `session.publisher(key, encoding:, priority:, ...)` → `Publisher`。`put(payload, attachment:, encoding:, timestamp:)`、`delete`、`matching?`、`matching_listener`、`close` / `closed?`。**`declare_publisher` / `undeclare` という名前は無い** |
| 受け取った値 | `each_pending` / `each_reply` は今どおり `[key, payload, attachment]`。encoding などは別の取り出し `sub.each_sample` (`Sample`) と `get.each_result` (`Reply`) で読む。どちらも同じ列から取る |
| Sample の中身 | `Data.define(:key, :payload, :attachment, :kind, :encoding, :timestamp, :priority, ...)`。位置引数でも作れる |
| encoding を付けなかった値 | **`"zenoh/bytes"`** (nil ではない)。実測: 付けない put を受けると `sm.encoding == "zenoh/bytes"`。nil になるのは `Query#encoding` で、問い合わせに中身が無いときだけ |
| Timestamp | `ntp64`、`id` (ZID の hex)、`to_time`、比較 (Comparable)、`to_s` |

### zenoh-pico 1.10.1 で使えるもの

- `z_declare_publisher` (`z_publisher_options_t.encoding`)、`z_publisher_put` (`z_publisher_put_options_t` の encoding・attachment・timestamp)、
  `z_put_options_t.encoding`、`z_sample_encoding`、`z_encoding_to_string` / `z_encoding_from_str`、`z_sample_timestamp`
  (`_z_timestamp_check` で有効なときだけ非 NULL)、`z_timestamp_ntp64_time` / `z_timestamp_id`。すべて今の設定のまま使える。
- 要る機能: `Z_FEATURE_PUBLICATION`・`Z_FEATURE_SUBSCRIPTION`・`Z_FEATURE_QUERY`・`Z_FEATURE_ENCODING_VALUES` (いずれも
  include/zenoh_generic_config.h の既定で 1)。fmruby-core の esp32・esp32p4・linux・native・wasm の構成 (lib/add/family_mruby_*.rb) は
  これらを上書きしていない (wasm が変えるのは TCP・WS・UNICAST_PEER、native は TLS だけ)。**sdkconfig と zenoh-pico の設定の変更は要らない**。
- publisher の宣言は、キーの宣言 (`_z_declared_keyexpr_declare`) と書き込みの絞り (write filter: 購読者の interest) を作る。
  どちらも宣言の控え (`_declaration_cache`) に入るので、つなぎ直しのあと zenoh-pico が宣言し直す。
  write filter は合う購読者がいない put を送らない (下の「見立てと違った点」)。
- タイムスタンプ: zenoh-pico は受け取った push の timestamp をそのまま sample に載せる。zenoh-c のルータ (router モードの既定で
  timestamping が on) を通した値には付く。peer の直結 (ルータなし) では付かない。get の答えには、ルータを通しても付かなかった。

## 2. 足した API (CRuby と並べて)

| | CRuby (asterism-zenoh、変更なし) | 端末・ブラウザ版 (picoruby-asterism-zenoh) |
|---|---|---|
| put の encoding | `session.put(key, payload, attachment:, encoding:, ...)` | `session.put(key, payload, attachment: nil, encoding: nil)`。nil・省略は今と同じ (何も送らない) |
| publisher の宣言 | `session.publisher(key, encoding:, priority:, ...)` | `session.publisher(key, encoding: nil)` |
| publisher の put | `pub.put(payload, attachment:, encoding:, timestamp:)` | `pub.put(payload, attachment: nil, encoding: nil)`。encoding nil は publisher の encoding |
| 取り下げ | `pub.close` / `pub.closed?` | 同じ。セッションを閉じると残った publisher も取り下げる (subscriber・queryable・token と同じ扱い) |
| 受け取った値 (購読) | `sub.each_sample` → `Sample` | 同じ。`Sample` は `key, payload, attachment, kind, encoding, timestamp` (CRuby の先頭 6 つと同じ順)、`put?`・`delete?`・`text`・`to_h`・`deconstruct_keys`・`==`・`to_s` |
| 受け取った値 (get) | `get.each_result` → `Reply` (エラーの答えも含む) | `get.each_result` → `Reply` (Sample と同じ項目、`ok?` は常に true。zenoh-pico のエラーの答えは今どおり `errors` に数えるだけ) |
| 既定の encoding | `"zenoh/bytes"` | `"zenoh/bytes"` (CRuby に合わせた) |
| タイムスタンプ | `Timestamp` (`ntp64`, `id`, `to_time`, Comparable) | `Timestamp` (`ntp64`, `id`, `to_time`, Comparable, `to_s` は `"<ntp64>/<id>"`) |
| 今の取り出し | `each_pending` / `each_reply` は `[key, payload, attachment]` | **変えていない** |

- 呼び手 (asterism の mrblib) を壊さないため、`each_pending` の形はそのままにし、encoding は CRuby と同じく別の取り出し (`each_sample` /
  `each_result`) で読む形にした。同じ列から取るので、片方で取った値はもう片方に出ない。
- 端末だけの違い: `Sample` は位置引数でだけ作れる (`Sample.new(key, payload, attachment)` は両方で動く)。CRuby だけの項目
  (`priority`・`congestion_control`・`express`・`reliability`・`source_zid`、`Reply#replier_zid`) は無い。`Query#encoding`・`q.reply(encoding:)`・
  `pub.delete`・`matching?` は足していない (P1 の範囲外。design.md 1 章の決まりで答えに encoding は付けない)。
- C の中: 受け取った値の列 (ring) の 1 項目に `has_ts` (bool) と `enc_len` (uint16) を足した。32 ビットの端末では前の詰め物に収まり、
  1 項目 20 バイトのまま。既定の encoding は複写の buffer にも場所を取らない。encoding 以外の名前とタイムスタンプ (24 バイト) は
  値ごとの buffer (z_malloc、ESP-IDF では PSRAM) の後ろに付く。

## 3. 試験

- `rake test` (picoruby-asterism-zenoh、2 つの mruby プロセスの peer): 130 → **167 checks, 0 failed** (4 回流して揺れなし)。
  足したもの: encoding を付けた put・付けない put・schema つきの encoding の往復、attachment つき、`each_sample` (配列と block)、
  `each_pending` の形が変わらないこと、encoding の型の誤り、未知のキーワード、listener 側の宣言した publisher からの値
  (publisher の encoding・put ごとの encoding・attachment)、publisher の close と閉じた後の put、セッションの close で残った publisher が
  取り下げられること、`each_result`、Timestamp の部品と比較と `to_time`。
- `rake test_cruby` (新設、zenoh-c のルータとクライアント ↔ zenoh-pico のクライアント): **通った**。zenoh-c → pico で `image/jpeg`・
  attachment・既定の `zenoh/bytes`・ルータのタイムスタンプ (時刻が今、2 つの値で同じ ID)、pico → zenoh-c で publisher の `image/png`・
  put ごとの `text/csv`・`session.put` の `application/cdr`・既定、答えの `text/plain`。
- fmruby-core `PICORUBY_ASTERISM_ZENOH_DIR=<手元の checkout> rake regress`: **host 26 suites 0 failed、regress 229 runs 0 failed**。
  ただしこの道具は網を偽物にするので、gem の C は通らない (P1 の変更で落ちないことの確認にとどまる)。

## 4. RAM

### publisher・queryable 1 つあたり (ホスト、32 ビット)

i386 (`-m32`、`MRB_INT64`) で mruby を作り、zenoh-pico の `z_malloc` / `z_realloc` / `z_free` に生きている量を数える一時的な計装を
入れて (vendor の写しを scratchpad で直した。コミットしていない、消した)、zenoh-c のルータへクライアントでつないで測った。
数は宣言の前後の差 (宣言して poll を 0.6 秒回した後)。

| 宣言 | zenoh-pico (z_malloc。ESP-IDF では PSRAM) | gem の構造体 (mrb_malloc、VM のプール) |
|---|---|---|
| publisher (合う購読者あり) | 680 B (19 塊) | `zrb_pub` 100 B (うち `z_owned_publisher_t` 88 B) + Ruby のオブジェクトとキーの文字列 |
| publisher (購読者なし、encoding つき) | 643 B (16 塊) | 同上 |
| publisher 5 つ | 3,405 B (1 つ 681 B) | |
| queryable (depth 16 でも 1 でも) | 650 B (13 塊) | `zrb_qable` 64 B + depth × 8 B (16 なら 128 B) |
| 参考: subscriber depth 16 | 635 B | `zrb_sub` + depth × 20 B |

- 内訳は宣言したキー (番号との対応)・write filter・宣言の控え (つなぎ直し用)。publisher の put は後に何も残さない (+0)。
- 全部を閉じると、最初の宣言の前より 40 B 多いまま止まる (2 回目以降は増えない。キーの表の 1 項目と見ている)。漏れではない。
- 内蔵 RAM の動的な確保には載らない: ESP-IDF の z_malloc は PSRAM だけ (ports/esp32/zp_system_esp32.c)。

### 静的な増分 (regress:size は未実施)

- **`rake regress:size` は流せていない**: この WSL に docker が無い (Docker Desktop の WSL 連携が切れている。`/usr/bin/docker` の
  先 `/mnt/wsl/docker-desktop` が無い)。ファームのビルドは ESP-IDF のイメージで動くので、esp32・linux のビルドもできない。
- 代わりに、変更前後の `src/zenoh.c` を 32 ビットで翻訳して節を比べた: `.data` 0 → 0、`.bss` 0 → 0。増えたのは `.text` (+5.6 KB、-Os)、
  文字列 (`.rodata.str1.1` +375 B)、`mrb_data_type` 1 つ (`.data.rel.ro` +8 B。PIC の再配置のための節で、ESP32 では .rodata = flash)。
  **書き換わる静的な領域は増えていない**ので、内蔵 RAM の静的な増分は 0 の見込み。ファームの大きさは数 KB 増える見込み。
  確定の数字は docker が戻ってから `rake regress:size` で取る。

## 5. 見立てと違った点

- **CRuby の既定の encoding は nil ではなく `"zenoh/bytes"`**。指示書は「既定の encoding のときは nil (asterism-zenoh と同じ形に)」だったが、
  CRuby の今の形は `"zenoh/bytes"` なので、「asterism-zenoh に合わせる」を優先して端末も `"zenoh/bytes"` にした (asterism-zenoh は変えていない)。
  P2 の受け手は「`zenoh/bytes` なら MessagePack」と読めばよい (Zenoh は既定の encoding を送らないので、送り手が `"zenoh/bytes"` を明示しても
  付けなくても線の上は同じ)。nil にそろえたいなら CRuby の戻り値を変えることになり、利用者に見える変更なので決めていない。
- **名前は `declare_publisher` / `undeclare` ではなく `publisher` / `close`** (CRuby の名前)。指示書のとおり CRuby に合わせた。
- **write filter**: zenoh-pico の publisher は、合う購読者を知る (interest の答えが来る) までの put と、合う購読者がいない put を送らない。
  宣言した直後の数回の put は落ちうる。P2 の通し番号は「受け手がいるときに数える」ものなので害は無いが、受け手は最初の番号が 0 とは
  限らないと読むこと。
- **答え (get の reply) にはルータのタイムスタンプが付かない** (zenoh-c のルータを通しても nil)。design.md 4 章の「ルータのタイムスタンプ」は
  put の値だけに当てにできる。
- **mruby の `Integer#<=>` は大きな整数を Float で比べる**: NTP64 の時刻で 1 違う 2 つが `<=>` で 0 になった (`<` と `==` は正しい)。
  Timestamp の比較は `<` / `>` で書いた。Asterism で NTP64 をそのまま `<=>` / `sort` にかけないこと。
- NTP64 は 2038 年を過ぎると int64 の正の範囲を超える (上位 32 ビットが秒)。端末では超えたら Float で返す (CRuby は Bignum)。

## 6. 撤回した仮説

- 「encoding を足すには今の取り出し `[key, payload, attachment]` を 4 要素にする必要がある」: 要らなかった。CRuby が既に別の取り出し
  (`each_sample` / `each_result`) を持っていたので、それに合わせれば呼び手は無傷。
- 「asterism-zenoh に足りないものがある」: 無かった。触っていない。

## 7. 残件 (P2 で気にすること)

- **`rake regress:size` (内蔵 RAM の静的な増分 0 の確定) と `rake regress:live` (ネイティブ版の Asterism 接続) は未実施**。docker を
  使える状態にしてもらってから、`PICORUBY_ASTERISM_ZENOH_DIR=../picoruby-asterism-zenoh rake regress:size` と `rake regress:live` を流す。
  fmruby-core の build/ には触っていない (今も Linux の x86-64 のまま)。
- ブラウザ版 (wasm、emscripten) と esp32 のコンパイルも同じ理由で通していない。使う API は機能の切り替えの無い部分だけなので、
  通らない見込みは低い。
- 受け手が MessagePack かを見るときは `encoding == "zenoh/bytes"` (CRuby・端末で同じ)。nil にそろえるかは P2 の受け手の API を決めるときに
  ユーザに選択肢で聞く。
- publisher 1 つ約 0.7 KB (PSRAM)。アプリごとのトピック数が多いと効くので、P2 の `Asterism.publish` は宣言を使い回すこと。
- `Reply` に CRuby のエラーの答えは入らない (端末だけの違い)。Asterism の呼び出しの答えは中身の `{"error"}` で返すので影響は無い。

## 8. 追記: regress:size で内蔵 RAM が増えた件と直し (2026-11-13)

- **見つかったこと** (親が docker を戻して `rake regress:size` を流した): 最初の 2 コミット (c4d9e3a・829969e) で NARYAv3 の DIRAM が
  正味 +152 B。files の差は 1 つだけで、`libmruby.a:encoding.o` の `.dram0.data` +212 B。原因は zenoh-pico の
  `src/api/encoding.c` の `const char *ENCODING_VALUES_ID_TO_STR[]`。ポインタそのものが書き換え可能な配列 (53 個 × 4 B) なので
  `.data` に置かれる。前は誰も使わず gc で消えていたが、gem が `z_encoding_from_str` / `z_encoding_to_string` を呼んだので
  リンクされるようになった。4 章の「静的な増分 0 の見込み」は外れた (gem の .o だけを見て、zenoh-pico の側を見ていなかった)。
- **直し** (picoruby-asterism-zenoh b0717f8、vendor/zenoh-pico は直していない): 名前と番号の変換を gem の
  `static const char *const` の表 (flash) で行い、encoding は `_z_encoding_make` で作り、`->id`・`->schema` を直接読む
  (固定している zenoh-pico 1.10.1 の内部。コメントに書いた)。gem から `z_encoding_from_str`・`z_encoding_from_substr`・
  `z_encoding_to_string`・`z_encoding_equals`・`z_encoding_loan_default` への参照は無くなった。
- **振る舞いは同じ**: 14 個の名前 (`image/jpeg`・`image/jpeg;x`・`foo`・`foo;bar`・`image/jp`・`""`・`zenoh/bytes;s`・`;x`・
  `application/msgpack`・`a;` ほか) で、zenoh-pico の変換と番号・schema・印字の文字列がすべて一致した。zenoh-pico の癖もそのまま
  (`;` の前の名前が番号つきの名前の先頭と一致すれば、その番号になる: `image/jp` は `image/jpeg`、`a;` は `application/octet-stream`。
  知らない名前は既定の番号の schema になり、`zenoh/bytes;foo` と印字される)。`rake test` 167 checks 0 failed、`rake test_cruby` ok。
- **測り直し**: `PICORUBY_ASTERISM_ZENOH_DIR=<手元> ONLY=NARYAv3 rake regress:size` → `libmruby.a internal +0`
  (flash +22,341)、`encoding.o` は DIRAM 0・差 0。要約は `ok` (DIRAM 125,403 -56、IRAM +0、ほかの内蔵 +0。-56 は libfmrb_mem・libmain の
  基準との差で、この変更とは別)。終わった後の build/ は linux sim (retro)、`build/fmruby-core.elf` は x86-64。
- 教訓: zenoh-pico の API を新しく呼ぶときは、その関数が書き換え可能な表を引き込まないかを regress:size の files の差で見る。
