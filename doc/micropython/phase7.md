# Phase 7: アプリ間通信の実証 (Python 版 RoboPilot)

## 目的

**この第二段階で一番試したいのがこれ**。別々のアプリが topic を介して
やりとりする仕組みの上に、Python のアプリを載せる。

題材は既にある `flash/app/game/robo_explorer/` の 2 本組。迷路の世界を持つ
`robo_explorer` (Ruby) と、それを操縦する `robo_pilot` (Ruby) が
`robo/cmd` / `robo/state` / `robo/result` の 3 つの topic でやりとりしている。

**世界側 (Ruby) はそのまま、操縦側だけを Python で書き直す。**
そうすると Ruby のアプリと Python のアプリが同じ topic で会話することになり、
「言語をまたいでアプリがつながる」ことがそのまま見本になる。世界側に
手を入れないので、Python 側が正しく喋れているかどうかも紛れなく分かる。

## なぜこれが試金石になるか

流れるものが小さくない。世界側が毎ターン流す状態は 12 個の項目を持ち、
そのうち `view` (正面の廊下の見え方) は**配列の中に配列**が入る。
`[左が壁, 右が壁, そこにある物]` が手前から最大 5 個並ぶ。

- **受け取り**: 入れ子の配列を含む地図データを Python の値に開けること。
- **送り出し**: 命令 (`{"op": "move"}` など) を組み立てて流せること。
  phase5 で配列を書けるようにした部分が、ここで実際に要る。
- **応答の速さ**: Ruby 版は命令を出してから結果が返るまでの時間を記録に
  出している。Python 版でも同じものを出し、**Ruby 版と数字を並べる**。
  これが「Python でもアプリ間通信が実用になるか」の答えになる。

## 「脳」を別ファイルにする

Ruby 版は、遊ぶ人が書き換える部分 (`my_pilot.rb`) だけを別ファイルにし、
操縦アプリがそれを取り込んでいる。

**phase5 で import を入れたので、普通に `import my_pilot` で書けた**
(`sys.path` がアプリ自身のディレクトリを指しているので経路も要らない)。
検討していた `read_file` + `exec` の案は使わずに済んだ。

```python
import my_pilot
brain = my_pilot.MyPilot()
```

注意する点:

- 脳の中で例外が起きても操縦アプリごと落ちてはいけない。Ruby 版と同じく
  例外を捕まえて画面と記録に出し、世界は動かし続ける。書き直した脳を
  起動し直せば同じ回を続けられる、という体験を守る。
- 読み込みに失敗したとき (ファイルが無い・構文が誤り) の出方を決める。
  何も言わずに動かないのが最悪なので、画面に理由を出す。
- 脳を作り直す条件は Ruby 版と同じにする (世界が最初に戻ったら新しい脳)。

## やること

1. `flash/app/game/robo_explorer/robo_pilot_py.app.py` を書く。画面の作りと
   日本語の言い回しは Ruby 版に合わせる (見比べられるようにするため)。
2. `flash/app/game/robo_explorer/my_pilot.py` を書く。中身は Ruby 版と同じ
   右手法。**説明の書き方も Ruby 版に合わせる** (これは遊ぶ人が読む文書
   でもある)。
3. `robo_pilot_py.app.toml` を用意し、Ruby 版と並べて起動できるようにする。
   ウィンドウの初期位置は Ruby 版とぶつからないようにする。
4. 命令から結果までの時間を記録に出し、Ruby 版と比べた表を report に残す。

## 確かめること

- Ruby の世界 + Python の操縦で、迷路を最後まで自動で歩けること。
- Ruby の操縦と Python の操縦を**同時に起動**したときの振る舞い。
  同じ topic に 2 人が命令を流すことになるので、世界がどう見えるかを
  確かめて、分かったことを書く (仕組みの穴が見つかるかもしれない)。
- 世界側を再起動したとき、Python 側が取り残されないこと。
- 脳のファイルを壊した状態で起動し、操縦アプリが落ちずに理由を出すこと。

## やらないこと

- 世界側 (robo_explorer) の Python 版。同じものを 2 つ作る意味が薄い。
- topic の仕組み自体の拡張。今ある形で足りるかを見るのがこのフェーズ。
- 音。次のフェーズで扱う。

## 確定した事項 (実装で決めた結果)

- 頭脳は `import` で読む。取り込み自体の失敗 (構文の誤り・ファイルが無い) は
  アプリの外側で起きるので、**取り込みを try で囲んで理由を画面に出す**。
  実行時の例外は Ruby 版と同じく呼び出し側で受ける。
- 応答時間は Ruby 版と差が無かった (平均 3.2ms / 3.5ms)。入れ子の配列を
  毎ターン受け取っても問題にならない。
- 操縦アプリが 2 つ同時に命令を流しても壊れないが、**譲り合いもしない**。
  topic に持ち主の考えは無い。仕組みは足さない。

## 完了条件

1. Ruby の世界を Python の操縦アプリが動かし、自動で迷路を踏破する
   (シミュレーションで画面を撮って確認)。
2. 命令から結果までの時間が測ってあり、Ruby 版と並べてある。
3. 脳 (`my_pilot.py`) を書き換えると振る舞いが変わり、壊しても
   操縦アプリが落ちない。
4. Tab5 実機でも同じことができる (遠隔操作で確認)。
