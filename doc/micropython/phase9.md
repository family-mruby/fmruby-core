# Phase 9: 見本のゲーム (ブロック崩し) と文書の締め

## 目的

phase5〜8 で足した機能を**全部使う 1 本のゲーム**を Python で書き、
「Family mruby の上で Python でも遊べるものが作れる」ことを見せる。
同時に、ここまでで解消した制限を文書から落とす。

題材はブロック崩しにした。理由:

- 迷路を歩く探検ものは Ruby の見本が既にある。同じものを言語だけ変えて
  並べても、見る側に伝わるものが少ない。
- 動くものが少なく (板・球・落ちてくる道具)、**Python の実行速度への
  依存が小さい**。速度を理由に見栄えを削る必要が出にくい。
- それでいて、スプライト・日本語・BGM・効果音・タイマ・停止と再開が
  どれも自然に登場する。

## 遊びの中身

- 下の板 (パドル) で球を打ち返し、上に並んだブロックを全部消す。
- 球を落とすと残機が減る。残機ゼロで終わり。
- ブロックを壊すと、たまに道具が落ちてくる。拾うと効果が出る。
  - 板が広がる (一定時間)
  - 球が遅くなる (一定時間)
  - 残機が 1 増える
- 面をクリアすると次の面。面が進むと球が速くなり、並びが変わる。
- 得点と残機、面数を上部に表示。日本語で「ステージクリア」「ゲームオーバー」
  「はじめる」などを出す。

道具の効果に時間制限を付けるのは、**タイマ (phase5) を見せるため**である。

## 作りの方針 (性能の使い方)

phase5-0 と phase6 の計測結果に従うが、初期案は次のとおり。

| 要素 | 描き方 | 理由 |
|---|---|---|
| 板・球・落ちてくる道具 | スプライト | 位置替えの費用が「1 命令 + 提示」で済む。合成は描画側が行う |
| ブロック | 最初に一度描き、壊れた 1 個だけを消す | 毎フレーム描き直す必要がない |
| 得点・残機・面数 | 値が変わったときだけ描き直す | 文字描画は 1 本ずつ命令になる |
| 背景 | 一度だけ | 同上 |

つまり**毎フレームの Python の仕事は「球の座標計算・当たり判定・
スプライトの移動・提示」だけ**になる。目標は 30 フレーム/秒。
届かない場合は、まず提示の回数を減らし、それでも駄目なら球の速度と
更新間隔の関係を見直す (球を速くするのに更新を速める必要はない)。

当たり判定は矩形どうしの単純なもの。ブロックは格子なので、球の座標から
添字を計算して 1 個だけ調べる (全ブロックを走査しない)。

## 素材

素材を作る道具は Ruby で書く (この企画の周辺道具の決まり)。既にある
`flash/app/game/rpg_demo/generate_*.rb` が手本になる。

- `generate_sprites.rb` — 板・球・道具の画像。小さいので手で置ける大きさ
- `generate_bgm.rb` — 譜面データ。既存の曲を流用してもよいが、
  短い専用の曲があるほうが見本として良い
- 効果音は素材ファイルではなく、音符の直接指定でその場で作る

## 置き場所と設定

- `flash/app/game/breakout/breakout.app.py` (素材も同じディレクトリ)
- `flash/app/game/breakout/breakout.app.toml` — 画面上の名前 (日本語名も)、
  ウィンドウの大きさと位置。**Retro の 320x240 に収まること**を前提に
  決める。Modern (426x240) では横に余白が出る置き方にする
- ランチャーの絵は `usr/share/icon/` に置く。無ければ既定の文字表示になる

## 検証

- シミュレーションで、入力注入により一通り遊べることを確認する
  (板を動かす、球を打ち返す、面をクリアする、失敗する)。画面は撮って残す。
- 音は波形の計測で、BGM と効果音が同時に出ていることを数値で確認する。
- S3 実機と Tab5 実機の両方で動かす。Tab5 は遠隔操作で自律的に確認できる。
- 1 フレームの時間と、GC で止まった時間の最大値を記録する。

## 文書の締め

- `known_limitations.md` から、解消した項目を落とす (日本語表示・
  スプライト・画像・音・タイマ・pub/sub・停止と再開・画面の大きさ変更)。
  残る制限 (同時 1 本のみ、extmod のモジュール、対話実行、スレッド、
  ファイルからの取り込み) は残す。
- `README.md` の将来課題を書き直す。
- Python アプリの書き方を 1 枚にまとめる。Ruby 版との差分が分かる形にする。

## やらないこと

- 得点の保存。ファイルの書き込みが要るので、必要なら phase5 に最小限を
  足してから考える。
- 二人対戦、通信対戦。
- 面のデータを外部ファイルにすること。並びはコードの中の表で足りる。

## 確定した事項 (実装で決めた結果)

- 道具の出現は `random` で決める。**extmod の random を取り込んだ**
  (extmods/micropython.mk + port/Makefile + mpconfigport.h)。種は時計から。
- 窓の題字は共通層が既定フォントで描く (日本語フォントのままだと帯から
  はみ出す)。`FmrbGfx.current_font` を見て戻す。
- バーの移動は押下で旗を立てて**毎フレーム動かす**。1 フレーム 6 画素、
  1 押し 3 画素。キーボードの自動繰り返しは当てにしない。
- 玉の向きは 16 分の 1 画素の単位ベクトル。**バーの 7 区画のどこで受けたかで
  反射角が決まる** (真ん中はほぼ真上、端は浅く横へ)。整数だけで書く。
- `on_suspend` / `on_resume` は書いてあるが、隠されたときには呼ばれない
  (カーネルがタスクごと止める。phase5 の報告を参照)。
- 得点の保存は入れない (ファイルへの書き込みが無い)。
- 1 フレームの Python の取り分は**最悪 1 ms / 予算 33 ms** (シミュレーション)。

## 完了条件

1. シミュレーションと実機 (S3 / Tab5) の両方で、始めから終わりまで遊べる。
2. BGM と効果音が鳴り、他のアプリが前に出たときに止まり、戻ると再開する。
3. 1 フレームの時間と GC の停止時間が測ってあり、目標に対する余裕が
   数字で書いてある。
4. 日本語の表示が崩れていない (画面を撮って確認)。
5. `known_limitations.md` と `README.md` が現状に合っている。
