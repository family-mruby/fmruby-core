## 分かったこと

### 1. import で「脳だけ別ファイル」がそのまま書けた

phase5 で入れた import が、ここでちょうど使われた。Ruby 版の
`require "/app/game/robo_explorer/my_pilot"` に対応するのは `import my_pilot`
だけで、`sys.path` がアプリ自身のディレクトリを指しているので経路も書かない。
`read_file` + `exec` の案は要らなかった。

### 2. 脳から共通層が見えないのは、この用途ではむしろ良かった

`my_pilot.py` の中では `FmrbApp` も `Log` も見えない。頭脳が触れるのは
渡された state と、返す命令の辞書だけになる。**「ロボットについて知れるのは
state だけ」という Ruby 版の説明が、Python では仕組みとして保証される**。

### 3. 壊れた脳の受け止め方は 2 段構えが要る

- **実行時の例外** (think の中で落ちる) は Ruby 版と同じく呼び出しを包めば済む。
- **import 自体の失敗** (構文が誤り・ファイルが無い) は、それより前に起きる。
  モジュールの取り込みは実行の一番外側なので、アプリの下に書いた try では
  間に合わない。取り込み自体を try で囲み、失敗したら理由を画面に出す形にした。

実際に構文を壊して起動すると「頭脳が読めない / invalid syntax /
my_pilot.py を直して再起動」と出て、アプリは生きたままだった。
**何も言わずに動かない、が一番困る**ので、ここは作り込む価値があった。

### 4. 操縦が 2 つ同時でも壊れない (が、譲り合いはしない)

Ruby の操縦と Python の操縦を両方自動運転にすると、ロボットは 2 つの頭脳の
命令を交互に受けて、行ったり来たりする。**エラーにはならず、世界も操縦側も
落ちない**。topic には持ち主の考えが無いので当然の結果で、必要なら
アプリ同士で決める話になる。

一方で、片方を自動運転にして、もう片方を切ったままにすると、
**Python 側は Ruby の世界を眺める窓として正しく働く** (状態が届くたびに
線画と数字が更新される)。見せ方としてはこちらのほうが分かりやすい。

### 5. 入れ子の配列は phase5 で通してあったとおり動いた

世界が毎ターン流す `view` (最大 5 個の `[左が壁, 右が壁, 物]`) を、
そのまま線画に使えている。phase5 で msgpack に配列を足していなければ、
ここで詰まっていた。

## 次への申し送り

- 実機 (Tab5) での確認が残っている。遠隔操作で同じ手順が踏めるので、
  ESP32 の計測をするときに一緒に行う。
- 操縦アプリのウィンドウは Retro (320x240) に収まる大きさにした
  (160x210)。Ruby 版は 172x220 で、Modern を前提に置かれているため
  Retro では右端がはみ出す。並べて見るときは Python 版のほうが収まりが良い。
- 頭脳を書き換えたら、アプリを起動し直す必要がある (import したモジュールは
  その VM の中に残るため)。Ruby 版の require と同じ制約。
