## 2. 受け口と動作の流れ

### 受け口と機種の定義

| 場所 | 中身 |
|---|---|
| `native/wlr/output_wlr.c` | 出力の受け口 `wlroots` (`native_output_t`)。tinywl (0.19) を出発点に、要るものだけにした。描画は wlr_scene、出力 1 つ、xdg-shell の窓と popup、seat、wlr-screencopy と xdg-output |
| `native/wlr/comp_route.{h,c}` | wlroots を使わない決め事: 絵の置き場所、窓の置き場所、点の下にあるもの、キーボードの持ち主、L9 向けの窓の通知の入れ物。host 試験の対象 |
| `native/backend/native_backends.c` | 表に `wlroots` を足した。`input.backend = "wlroots"` は `display.backend = "wlroots"` とだけ組める (どちらか片方だと理由つきで断る) |
| `config/machines/linux_pc_wl.toml` | 新しい機種。`display.backend`・`input.backend` が `wlroots`、音は SDL、`[compositor] autostart` (既定は空) |
| `native/machine/native_machine.{h,c}` | `[compositor] autostart` を足した (`--set compositor.autostart=foot`) |

上の層 (main/・kernel・デスクトップ) には何も足していない。`#ifdef` は
`native_backends.c` の表 (DRM・ALSA と同じ並び) だけ。`linux_pc` (cage) と
`linux_pc_drm` はそのまま。

### 動作の流れの受け渡し

- **wlroots はプログラムの主スレッドで回す**。主スレッドは FreeRTOS のタスクではなく
  (L1 からの作り)、今までも SDL の窓・DRM・制御の口を持っていた。出力の `pump()` が
  `wl_event_loop_dispatch()` で、ここだけが wlroots を呼ぶ。協調のスレッド群
  (FreeRTOS のタスク) は wlroots を一切呼ばない。新しいスレッドは足していない。
- 受け渡しは 2 つだけ:
  - **(a) 絵: 表示タスク → コンポジタ**。今までの `native_frame` (錠 1 つ、丸ごとの写し)
    に、起こす口を 1 つ足した (`native_frame_set_wake_fd()`)。表示タスクは絵を写して
    錠を放したあと eventfd に 1 を書く。主スレッドはその eventfd を `wl_event_loop` に
    入れてあるので、待ちから直ちに戻り、錠の中で最新の絵を写し取り、XRGB8888 の
    wlr_buffer にして wlr_scene に渡す。錠を持つのは写す間だけで、wlroots の中で
    錠を持つことは無い。待ちの上限は今までの主ループと同じ 5 ms (制御の口のため)。
  - **(b) 入力: コンポジタ → Family mruby**。SDL の窓と同じ、主スレッドが書き手 1 つの
    環 (`native_input_push()`、原子操作だけで錠なし、256 個) に入れ、Family mruby の
    入力タスクが 10 ms ごとに汲む。L9 で使う窓の通知 (出た・大きさが変わった・消えた・
    キーボードが移った) は `comp_route` の中の 64 個の環に積み、錠 1 つで別のスレッドから
    取れる形にした (L8 では取り手は試験だけ)。
- 絵が欠けないこと: 写すのは常に錠の中の 1 枚まるごと。host 試験で、書き手のスレッドが
  300 枚を書く間に読み手が eventfd で起きて写すと、248 回写して 1 枚も混ざらず、
  順番も戻らなかった (新しいものが勝つ)。

## 3. 描画と入力の行き先

### 描画

- wlr_scene に下から: 出力全体の黒 → Family mruby の絵 (wlr_scene_buffer、
  `wlr_scene_buffer_set_dest_size()` で整数倍、`WLR_SCALE_FILTER_NEAREST`) → Linux の窓。
  置き場所は L2 の共通の部品 (`fmrb_present_place`) で決める: 最大の整数倍、真ん中、余りは黒。
  1280x720 の出力で `frame 426x240 at 3x, 1278x720 at (1,0)`。
- 拡大はレンダラに任せている。pixman でも、grim の画面と「Family mruby の絵を 3 倍して
  置いたもの」が窓の外で 1 画素も違わない (下の 5)。
- 窓は本来の大きさで、出力の真ん中 (試作の固定)。xdg の窓の木は、窓の geometry
  (foot なら題の帯を含む枠) を木の原点に置く (wlroots の scene がそうする)。
- カーソル: Family mruby の絵の上では wlroots のカーソルを消す (Family mruby が
  自分のカーソルを描く)。窓の上では窓が頼んだもの。

### 入力の行き先 (comp_route)

- 点の下にあるもの: 上の窓から順に見て、入っていればその窓 (窓の中の座標)。どれにも
  入らなければ Family mruby (絵の中なら絵の座標、黒い縁なら絵の端に寄せた座標。SDL の
  窓と同じ)。窓の中の細かい面 (subsurface・popup) は wlr_scene に聞く。
- ボタンを押したとき: 窓の上ならその窓がキーボードを持ち、一番上に上がる。絵か縁の上なら
  Family mruby に戻る。キーボードを持つ窓が消えても Family mruby に戻る。既定は Family mruby。
- ボタンを押している間のポインタは、押した所の物に送り続ける (枠の外へ引きずっても)。
- キーは wlroots の xkb を通る Linux のキーコードで受け、Family mruby 行きは L2 の表
  (`fmrb_linux_key_to_hid()`・`fmrb_linux_key_mod_bit()`) で HID の番号と修飾にする。
  窓行きは `wlr_seat_keyboard_notify_key()`。キーは**押した所に離す**
  (押している間に持ち主が変わっても、離す側だけ別に行くことはない)。
- 車輪: Family mruby 行きは向きを直して刻みに (Wayland の + は手前、Family mruby の + は奥)。

### 外の窓を起こす口と終わり

- `compositor.autostart` を `/bin/sh -c` で 1 つ起こす。新しいセッション (setsid) にし、
  `WAYLAND_DISPLAY` は自分の口。プログラム自身の環境の `WAYLAND_DISPLAY` も、親
  (WSLg) につないだあとで自分の口に書き換えるので、L10 の Shell の `!` から起こした
  プログラムも自分の上に出る (`!foot` で foot の窓が出るのを確かめた。
  `tmp/wl_check/shell_bang_foot.png`)。
- Family mruby が終わると、起こしたもののセッションに SIGTERM、0.5 秒で終わらなければ
  SIGKILL。ログに `native: compositor: "foot ..." stopped with the program`。
  Shell の `!` で起こしたものは今までどおり L10 の仕組みで終わる。
- 入れ子の窓を閉じる (出力が消える) と、プログラムも終わる。

### 合成後の画面の撮り方

- コンポジタは wlr-screencopy と xdg-output を出しているので、grim で撮れる。
  コンテナの中で、コンポジタの口を指して:

  ```
  docker exec -e XDG_RUNTIME_DIR=/run/fmrb/xdg -e WAYLAND_DISPLAY=wayland-0 <container> grim /run/fmrb/screen.png
  ```

  `/run/fmrb` は手元の run dir (`wl_check.rb --run` なら `/tmp/fmrb-wl-run-<uid>`)。
  口の名前は起動のログ (`native: compositor: wlroots 0.19.2 on WAYLAND_DISPLAY=wayland-0`)
  と `comp info` にある。
- `tools/fmrb_native.rb shot` は今までどおり Family mruby の絵だけ (426x240) を撮る。
  比べるときはこの 2 つを使う (下の 5 の 2)。

### 制御の口の言葉 (道具のため)

制御の口 (`<run dir>/ctl`) に、出力が自分の言葉を持てるようにした
(`native_ctl_set_output_handler()`、他の出力は無し)。コンポジタの言葉は `comp ...`:

| 言葉 | 中身 |
|---|---|
| `comp info` | 出力の大きさ、絵の大きさ・倍率・位置、キーボードの持ち主、窓 (`id:WxH+X+Y`)、口の名前、使っているレンダラ |
| `comp stats [reset]` | 絵の数と間隔 (平均・最長)、出力の commit の数、窓へ送ったキーと、そのキーから窓の次の commit までの時間 |
| `comp key CODE 1\|0` / `move X Y` / `button B 1\|0` / `click X Y` / `wheel N` | 道具のためのキーボードとポインタ (wlroots の中に作った 1 組)。本物の機器と同じ処理を通るので、行き先の決め方ごと確かめられる |

## 4. 試験

- **host 試験** (`rake native:test` の 5 つ目、`test/native/comp.c`、wlroots 無し): 43 項目。
  絵の置き場所 (1280x720・1920x1080・高解像度の絵・出力が小さいとき)、点の下の物
  (窓の角、窓の外すぐ、縁)、2 つの窓の重なり、大きさの変化と出力の変化で真ん中に
  置き直すこと、押したときのキーボードの移り方と窓の上がり方、窓が消えたとき、
  別のスレッドから通知を順に取れることと溢れたとき、絵の受け渡し (eventfd で起きる・
  混ざらない・新しいものが勝つ)。`test/native/main.c` には `linux_pc_wl` の定義の読み込みと
  `--set compositor.autostart` を足した (490 項目)。
- **コンテナの中の確かめ** (`rake native:wl_check`、`test/native/wl/wl_check.rb`):
  Ubuntu 26.04 のイメージで `--machine linux_pc_wl`、foot に `cat > typed` を走らせて起こす。
  レンダラごとに 9 項目: 起動、grim と絵の比較、foot へのキー、Family mruby へのキー
  (エディタの 1 打鍵を native の基準 `editor_type.png` と比べる)、3 つの負荷での時間、
  foot が全部のキーを受けたこと、終わり。既定は headless (`WLR_BACKENDS=headless`、
  1280x720)、`NESTED=1` で WSLg に入れ子 (確かめの間だけ窓が出て、終われば閉じる)。
  1 回 (2 つのレンダラ) で 75 秒。debugd の口でアプリを起こすので、手元の python3 に
  msgpack が要る (`tools/fmrb_native.rb app` と同じ)。結果と画面は `tmp/wl_check/<形>-<レンダラ>/`。
- **回帰の道具に載せる提案**: headless の `rake native:wl_check` を `regress:full` の 1 つに
  するのがよいと考える。基準の絵を持たない (grim の画面を、その場で撮った Family mruby の
  絵から作った期待と比べる。foot の中身は比べず「絵ではない」ことだけ見る) ので、foot の
  版や字体が変わっても揺れない。エディタの 1 打鍵は native の基準をそのまま使う。
  Docker と Ubuntu 26.04 のイメージ (約 1 GB) が要るのが重さ。載せるかは親が決める。

### 測定 (受け入れ 5)

`wl_check.rb` の 5 番。foot がキーボードを持つ状態で、6 秒の間に 30 個のキーを foot へ送る。
CPU は program 全体 (wlroots の主スレッド + Family mruby の全タスク) の 1 コアに対する割合
(`/proc/<pid>/stat`)。「キー → commit」は、窓へキーを送ってから foot が次に絵を出すまで。

| 形 / レンダラ | 負荷 | CPU (1 コア比) | 絵の数 (約 6.6 秒) | 絵の間隔 平均 / 最長 | 出力の commit | キー → foot の commit 平均 / 最長 |
|---|---|---|---|---|---|---|
| 入れ子 (WSLg) / 自動 (pixman) | 何もしない | 3.2% | 7 | 1001.5 / 1003 ms | 78 | 1.6 / 3 ms |
| 入れ子 / 自動 | shooter | 6.4% | 126 | 51.8 / 55 ms | 301 | 1.5 / 2 ms |
| 入れ子 / 自動 | spin_hog | 100.9% | 0 | - | 62 | 1.2 / 2 ms |
| 入れ子 / pixman | 何もしない | 3.4% | 6 | 1002.4 / 1003 ms | 77 | 1.5 / 3 ms |
| 入れ子 / pixman | shooter | 7.0% | 126 | 51.9 / 55 ms | 300 | 1.5 / 2 ms |
| 入れ子 / pixman | spin_hog | 100.6% | 0 | - | 62 | 1.3 / 2 ms |
| headless / pixman | 何もしない | 3.3% | 6 | 1001.8 / 1004 ms | 75 | 1.5 / 2 ms |
| headless / pixman | shooter | 6.0% | 129 | 51.7 / 55 ms | 305 | 1.4 / 2 ms |
| headless / pixman | spin_hog | 98.9% | 0 | - | 62 | 1.2 / 2 ms |

- 何もしていないとき、Family mruby の絵は 1 秒に 1 枚 (時計) で、コンポジタはその都度だけ描く。
- shooter (1 秒に約 20 枚描くアプリ) のとき、絵の間隔は平均 52 ms・最長 55 ms で、
  絵は止まらず欠けない (受け渡しは丸ごとの写し)。CPU は 7% 前後。
- spin_hog (20 秒の間、譲らずに CPU を握るアプリ) のとき、program は 1 コアを使い切り、
  Family mruby の絵は 6.5 秒の間 1 枚も来ない。これはコンポジタの外の話で、SDL の
  native (手元のビルド) でも同じ (spin_hog の間、絵の番号が 6 秒で 34 → 34)。協調の
  スレッド群の中で 1 つのタスクが譲らないと、表示タスクも回らない (今までの作り)。
  その間もコンポジタは別のスレッドで回り、foot へのキーは平均 1.3 ms・最長 2 ms で
  届き、foot は 30 個とも受けた。**Family mruby が忙しくても foot の打鍵は遅れない**。

## 6. 確かめの手順 (WSLg で人が触る)

```
cd fmruby-core
rake native:wl                 # 初回はイメージ (Ubuntu 26.04) とビルドを作る
rake native:wl_run             # WSLg に窓が出て、Family mruby の上に foot が出る
```

- foot を押すと foot に打てる。Family mruby の絵を押すと Family mruby に戻る。
- 終わりは Family mruby の電源のメニューの「Exit」か、窓を閉じる (foot も一緒に終わる)。
- 合成後の画面は、動かしている間に別の端末で
  `docker exec -e XDG_RUNTIME_DIR=/run/fmrb/xdg -e WAYLAND_DISPLAY=wayland-0 fmrb-wl-run grim /run/fmrb/screen.png`
  (`/tmp/fmrb-wl-run-<uid>/screen.png` に出る)。
- 別の起こし方: `rake native:wl_run ARGS="--set compositor.autostart=foot"` の ARGS で
  program の引数を渡す。確かめの一式は `rake native:wl_check` (headless) と
  `rake native:wl_check NESTED=1` (WSLg に一時的に窓が出る)。
- 音は WSLg の PulseServer へ出す (`--run` のときだけ)。

## 7. L9 に向けた見立て・撤回した仮説・罠・残件

### L9 に向けた見立て

- **窓の通知を kernel に入れる形**: `comp_route` の通知の環 (出た・大きさ・消えた・
  キーボード) を、kernel 側のタスクが汲む形がそのまま使える。汲む口は入力の環と同じく
  主スレッドを待たせない (錠は通知 1 つを写す間だけ)。逆向き (kernel の window manager が
  決めた置き場所・前後・フォーカス) は、主スレッドへの 3 つ目の受け渡しになる。
  `native_frame` と同じ「錠 + eventfd で起こす」形がよい。置き場所は Family mruby の座標で
  受け、コンポジタが倍率と絵の位置で写す (`comp_route` の中央置きを置き換える)。
- **前後の関係**: 今は Linux の窓が常に絵の上にある。Family mruby の窓が Linux の窓の上に
  来る場合は、Linux の窓を「見えている所」だけ描く必要がある。wlr_scene の切り抜き
  (subsurface の木の clip) か、Linux の窓を kernel が決めた可視の矩形で切る形を考える。
- **Xwayland**: `wlr_xwayland_create()` で足せる (wlroots 0.19 の xwayland は
  `libwlroots-0.19` に入っている)。Depends に `xwayland` が加わる。X11 の窓は xdg と
  別の木になるので、`comp_route` には窓の種類を問わない id で入れる。
- **キーボードの配列**: 窓へは xkb の既定 (us、`XKB_DEFAULT_*` で変わる)。Family mruby の
  `keyboard_layout` と揃える口は L9 で。
- **出力が複数**: 今は最初の 1 つだけ使う (2 つ目はログに出して使わない)。

### 見立てと違った点・撤回した仮説・罠

- **GLES は WSL2 のコンテナで動かせなかった**。WSL2 の `/dev/dri` は vgem (描く力の無い
  仮の機器) で、Mesa の d3d12 は `/dev/dxg` を使わず、GLES は Mesa のソフトウェアの描き手
  になる。wlroots はそれを既定では断り (`Software rendering detected`)、
  `WLR_RENDERER_ALLOW_SOFTWARE=1` で始めても `gbm_bo_create failed: Permission denied`
  で出力の buffer が作れない。よって WSL2 では wlroots の自動の選択も pixman になる
  (入れ子でも headless でも)。GLES の描画 (最近傍の拡大を含む) は GPU のある Linux PC
  でユーザが確かめる。`wl_check.rb --renderer gles2` は render node を渡す形を残してある。
- **xdg の窓の木の位置**: tinywl に倣って「窓の位置 - geometry の左上」に置いたら、
  foot の題の帯の分 (27 画素) 下にずれた。wlroots 0.19 の scene の xdg の木は、もう
  geometry を原点に合わせている。grim の比較で見つけた (窓の下 26 行が絵と違った)。
- **測定の負荷**: 最初に選んだ raycaster と flappy は、キーを押すまで絵を描き変えない
  (SDL の native でも絵の番号が止まる)。止まって見えたのは忙しさではなかった。
  描き続ける shooter と、CPU を握る spin_hog にした。
- Docker Desktop の `--network host` では、コンテナの debugd に手元から届かなかった。
  `-p 127.0.0.1:15565:5565` で出した (手元の native の 5565 と重ならない)。
- `--set` の値に `'` を含むとき、Ruby の `gsub` の置き換え文字列の `\'` が「後ろの文字列」
  の意味になり、コンテナの命令が壊れた (ブロックの形にした)。
- `native_docker` に `arch:` のキーワードを足したら、環境変数のハッシュを `{}` 無しで渡して
  いた所がキーワード扱いになって落ちた (`{}` で包んだ)。
- trixie の `Dockerfile` の説明は「amd64 もここで作る」のまま。直すと hash が変わって
  arm64 のイメージが作り直しになり、trixie の新しいパッケージを拾ってしまうので触っていない。
  次に arm64 のイメージを作り直すときに一緒に直す。

### 残件

- GLES での確認 (GPU のある Linux PC で `rake native:wl_run`、または .deb を入れて
  `family-mruby --machine linux_pc_wl --set compositor.autostart=foot`)。
- 実際の手のキーボードとマウスでの操作 (WSLg の入れ子で、ユーザが触る)。道具の
  キーボードとポインタは本物の機器と同じ処理を通るが、手の操作はまだ見ていない。
- 窓を閉じたときに終わる (出力が消える) 道は、コードを読んだだけで、自動では見ていない。
- 窓の移動・大きさの変更の頼み (xdg の move・resize)、最大化・全画面、クリップボードの
  中身の受け渡しの先 (Family mruby との間) は無い。popup は出るだけ。
- `linux_pc_wl` の電源のメニューの logind は、コンテナには logind が無いので見ていない。
- session (ログイン画面の入口) は今も cage と `linux_pc`。コンポジタに切り替えるのは
  L9 の後。
- `comp_route` の通知の取り手 (kernel) は L9。
