## 1. kernel のクリップボード

### 形

| 項目 | 決めたこと |
|---|---|
| 場所 | `main/kernel/fmrb_clipboard.{h,c}`。端末・sim・ネイティブ版・ブラウザ版のどれでも同じファイル |
| 中身 | UTF-8 の文字列 1 つ。改行は `"\n"` |
| 上限 | **64 KB (65,536 バイト)** (`FMRB_CLIPBOARD_MAX`)。超える `set` は断り (`FMRB_ERR_INVALID_PARAM`)、クリップボードはそのまま |
| 置き場所 | 固定の 1 つの塊 (文字の 64 KB + 1、錠の静的なブロック、世代、長さ、外のクリップボードの表)。端末では `FMRB_EXT_RAM_BSS_ATTR` で **PSRAM** (`.ext_ram.bss` 65,644 バイト)。sim・ネイティブ版・ブラウザ版では属性が空になり、普通のメモリ (`.bss`) |
| 世代 | `uint32_t`。変わるたび (アプリの `set`、外から取り込んだとき) に 1 増える。起動時は 0 |
| 錠 | FreeRTOS の mutex 1 つ。`xSemaphoreCreateMutexStatic` で、そのブロックも同じ PSRAM の塊の中 (内蔵 RAM を使わない)。`fmrb_rtos.h` に `fmrb_static_semaphore_t` と `fmrb_semaphore_create_mutex_static` を足した。kernel の起動 (`fmrb_kernel_start`、ファイル同期の錠の次) で作る |
| 待ち | 錠のほかは何も待たない。外のクリップボードの口も待たないことを決まりにした |

- 指示書の「native・ブラウザ版は普通のヒープ」との違い: 静的な塊にした。上限が決まっているので確保に失敗せず、断片化せず、タスクから malloc を呼ばない (hosted の FreeRTOS は合図でタスクを止めるので、glibc の内部の錠を持ったまま止まる形を避ける)。ネイティブ版では普通のプロセスのメモリで、場所の違いは無い。
- C の口: `fmrb_clipboard_set`、`fmrb_clipboard_read(off, buf, cap, &gen)` (途中から少しずつ読める)、`fmrb_clipboard_length`、`fmrb_clipboard_generation`、`fmrb_clipboard_lock` / `unlock` (大きな読み手がその場で借りる。エディタの貼り付け)。

### 外のクリップボードとのつなぎ方 (共通)

- 機種が表 (`fmrb_clipboard_host_t`) を kernel の起動の前に入れる: `publish` (アプリが `set` したとき、そのタスクから錠の中で呼ぶ。外は写して後で自分の側へ渡す) と `take` (外に新しい文字があれば写して返す)。
- `take` は、アプリがクリップボードを読むたび (文字・長さ・世代を問うたび) に錠の中で聞く。Linux でコピーした文字は、次にアプリが読んだときに入る (取り込むのは読まれたときだけ)。
- 外から来た文字は `"\r\n"` と `"\r"` を `"\n"` に、NUL を除く。64 KB を超えるものは**断り、クリップボードを空にする** (古い文字が貼られるより、何も貼られない方がよいため)。ログに 1 行。
- `set` の前にも `take` を聞くので、外のまだ取り込んでいない文字より、後のアプリの `set` が勝つ。
- 外から取り込んだ文字は外へは送り返さない (行き来の繰り返しにならない)。

### Ruby の口 (FmrbApp)

| 口 | 答え |
|---|---|
| `FmrbApp.clipboard(limit = 0)` | 文字 (空なら `""`)。`limit > 0` ならそのバイト数まで、文字の途中では切らない |
| `FmrbApp.set_clipboard(str)` | true。64 KB を超えると false で、クリップボードはそのまま |
| `FmrbApp.clipboard_gen` | 世代 (変わった回数) |

- mruby は `lib/add/picoruby-fmrb-app/ports/esp32/app.c`。世代を前後で見て、読む間に変わったら読み直す。
- Spinel は `fmrb_app_base_spinel.rb` に同じ名前。FFI (`fmrb_spx_app_clipboard_chunk(off, limit)`) が 4 KB ずつ返す (静的な PSRAM の 4 KB の中継)。世代を前後で見て読み直す。標準の形で Spinel で動くのは kernel とエディタだけで、どちらもこの口を呼ばない (エディタは EditorCore の C)。Spinel 側はビルドが通ることと生成された C に入ることまでを確かめ、動かしてはいない。
- `sig/fmrb_app.rbs` に 3 つを足した (要約は 112 バイト以内)。型の db はビルドで作り直される (regress の各ビルドは clean から)。

## 2. エディタと Shell

### エディタ

- EditorCore (C) の文書ごとのクリップボード (`ed_doc_t.clip`) を消し、kernel のものにした。`copy_range` は選択を文書の領域に一度組み立てて `fmrb_clipboard_set` に渡す。`paste_at` は kernel のクリップボードを借りてその場で差し込む。`clipboard_length` は kernel の長さ。Spinel のエディタも mruby のエディタも EditorCore を通るので、両方が同じになる。Ruby の変更はメッセージだけ。
- 64 KB を超える選択のコピーは何もしないで、状態の行に「大きすぎます」(既にある `b_too_large`) を出す (`EC_ERR_TOOBIG`)。
- 切り取り (Edit メニュー) は、コピーできたときだけ選択を消すようにした (前は文書の領域が足りずにコピーできなくても消していた)。
- **Ctrl+X は今どおり「終了」**: 指示書の「エディタの Ctrl+C/X/V」の X は、このエディタでは切り取りでなく終了 (未保存なら確かめる) に割り当てられている。キーの割り当ては変えず、切り取りは Edit メニューのまま。共通のクリップボードを使うのは Ctrl+C、Ctrl+V、Edit メニューの切り取り・コピー・貼り付け。
- 前はエディタを閉じるとそのクリップボードも消えた。今は残り、閉じてから開いたエディタにも貼れる。

### Shell

- 貼り付けのキー: **Ctrl+V** (エディタと同じ) と **Ctrl+Shift+V** (Linux の端末と同じ)。今の Shell で Ctrl+V は何もしていなかった (印字できない文字として捨てていた)。
- プロンプト (irb、キーボードを読むスクリプトの入力も同じ) では、文字をキーで打ったのと同じ経路 (入力の列) に入れる:
  - **改行とタブは空白にする**。ほかの制御文字は除く。末尾の改行 (コピーした 1 行に付く) の分の空白は落とす。
  - 行に入る分 (100 文字) だけ。読むのも 1 KB まで。
  - **Enter を押すまで何も実行しない** (複数行を貼っても 1 行にまとまる。実行は人が確かめてから)。
- `!` で Linux のプログラムが動いている間:
  - **Ctrl+Shift+V** で、その入力へ文字をそのまま送る。改行は端末と同じく CR (`"\r"`)。前に打ったキーとの順は保つ (入力の列に印を置く)。pty が一度に受け取らなかった分は持っておき、次の回に送る。
  - **Ctrl+V はそのプログラムの ^V (0x16) のまま** (vim の矩形選択などを壊さない。foot・Konsole と同じ)。
  - 括弧付きの貼り付け (bracketed paste) はしない (端末の読み手がその設定を見ていないため)。
- `help` に 2 行足した (`Ctrl+V - Paste the clipboard into the line`、Linux のある機種では `Ctrl+Shift+V - Paste into the Linux command running`)。

## 3. PC・ブラウザ版とのつなぎ方

### 共通の受け渡し (ネイティブ版、`native/backend/native_clip.{h,c}`)

- kernel の表を入れる側。出る方 (Family mruby → Linux) は `publish` が静的な 64 KB の箱に写し、主スレッドを起こす。入る方 (Linux → Family mruby) は主スレッドが `native_clip_offer` で静的な 64 KB の箱に写し、kernel の `take` が持っていく。どちらも pthread の錠を写す間だけ持つ。タスクは malloc を呼ばない。
- 制御の口の `clip` が数を答える (`OK joined=1 out=.. in=.. in_big=.. taken=..`)。

### コンポジタ (Wayland の選択、`native/wlr/wl_clip.c`)

- Family mruby でコピー → 起こされた主スレッドがその文字でコンポジタ自身のデータの源を作り、席の選択 (`wlr_seat_set_selection`) にする。出す種類は `text/plain;charset=utf-8`、`text/plain`、`UTF8_STRING`、`TEXT`、`STRING`。
- Linux のアプリが貼る → 源の `send` が、そのアプリの pipe に、pipe が受け取るだけ書く (書けるようになったら続きを書く出来事を event loop に置く。同時に 8 本まで)。アプリが途中で閉じても止まらないよう、書く間だけ SIGPIPE を止めて残った合図を捨てる (SIGPIPE を無視にすると、ここから起こす全部のプログラムに受け継がれるため)。
- Linux のアプリが選択を出す → `set_selection` の合図で、文字の種類 (`text/plain;charset=utf-8`、`UTF8_STRING`、`text/plain`、`TEXT` の順に探す) を持っていれば pipe を渡して読む。読むのは event loop の読める出来事で、主スレッドは待たない。64 KB を超えたら読むのをやめ、大きすぎたことを渡す (kernel が断る)。5 秒で終わらなければやめる。次の選択が来たら前の読みはやめる。
- **持ち主が終わっても残す**: 選択の持ち主のアプリが終わって選択が空になったら、最後の文字でコンポジタが持ち直す (event loop の次の回で)。foot でコピーして foot を閉じても貼れる。
- **Xwayland の X11 のアプリ**: wlroots の Xwayland の橋渡しで、X11 の CLIPBOARD と Wayland の選択が両方向につながることを試験で確かめた。ただし wlroots の決まりで、**X11 のアプリがクリップボードを読めるのは X11 の窓にキーボードがあるとき**だけ (貼るときは普通そうなっている)。
- **primary selection (中ボタンの貼り付け) は扱わない**。primary selection の管理を作っていないので、アプリは自分の中だけで持つ。
- 制御の口の `comp clip` が、選択の持ち主 (`fmrb` / `linux` / `none`) と数を答える。

### SDL の窓 (`sdl` の機種、`native/output/output_sdl.c`)

- アプリのコピーは主スレッドで `SDL_SetClipboardText` (SDL のクリップボードは C の文字列なので、NUL があればそこまで)。
- デスクトップの文字は、`SDL_CLIPBOARDUPDATE` と、窓がフォーカスを得たときに読み、最後の文字 (どちら向きでも) と違えば渡す。手元の SDL 2.0.20 の X11 は、自分が持っていたクリップボードを他に取られたときにしか変化を知らせない。ほかのアプリで続けてコピーしたあとは、Family mruby の窓をクリックした (フォーカスを得た) ときに入る。Kubuntu 26.04 の SDL2 (SDL3 の上の sdl2-compat) は変化をいつも知らせるはず (未確認)。
- X11 では読むのに持ち主の返事を少し待つことがある。読むのはその 2 つの出来事のときだけ。
- `cage` の形 (`linux_pc`) も SDL の窓なので同じ。fbdev・DRM の機種 (Cardputer Zero) はつながず、Family mruby の中だけ。

### ブラウザ版 (`wasm/backend/clip_wasm.c`、`wasm/web/main.js`)

- 共有メモリに出る箱と入る箱 (各 64 KB) と、長さ、書いている間は奇数になる番号 (seqlock)。
- 出る方: ページが描くたび (requestAnimationFrame) に番号を見て、変わっていたら文字を写して `navigator.clipboard.writeText`。コピーのキーの数 ms 後なので、利用者の操作の内として扱われる見込み。
- 入る方: Ctrl+V (と Cmd+V) は、ブラウザの `paste` の出来事 (許可を求めずに文字をもらえる) を待つために、そのキーを最大 300 ms 止めておき、`paste` で文字を入る箱に入れてからキーを渡す (アプリが読む前に文字が入る)。
- **ページの決まりで読めない・書けないとき**: `paste` が来なければ 300 ms 後にキーを渡し、Family mruby は自分のクリップボードを貼る。`writeText` が断られても Family mruby の中では使える。どちらもコンソールに 1 行。
- 古い wasm で新しい口が無ければ、ページは何もしない (描画は止めない)。

### sim (Linux の docker)

- つながない。Family mruby の中だけ。

## 5. 判断したこと

- **上限 64 KB、超える Linux の文字は断ってクリップボードを空に** (1 章)。
- **静的な塊** (1 章、指示書の「普通のヒープ」との違い)。
- **Ctrl+X は終了のまま** (2 章)。
- **Shell の貼り付けは Ctrl+V と Ctrl+Shift+V、改行は空白、Enter まで実行しない。Linux のプログラムには Ctrl+Shift+V だけで、Ctrl+V は ^V のまま** (2 章)。
- **選択の持ち主が終わってもコンポジタが持ち直す** (3 章)。指示書に無い動きで、ほかの Wayland の机 (クリップボードの管理のあるもの) と同じ。止めるなら `wl_clip.c` の `set_selection` の 1 行。
- **標準の形でエディタを 2 つ開く決まりは変えない**: Spinel のエディタを 2 つ動かせないのは今の決まり (同じ Spinel のプログラムは 1 つずつ。メモリの台帳がプログラムごとに 1 つのため) で、クリップボードとは別の話。受け入れ 1 は全部 mruby の形で 2 つ、標準の形ではエディタと Shell、閉じて開き直したエディタで確かめた。2 つ開けるようにするかはユーザの判断。

## 6. VirtualBox の Kubuntu 26.04 で人が確かめる手順

1. 開発機で `.deb` を作る: `cd fmruby-core && rake native:deb ARCH=amd64` → `native/build-deb/family-mruby_<版>_amd64.deb`。VM へ写す (`C:\share_data\vm_mnt` に `fm.deb` で置くなど)。
2. VM の中で入れる: `sudo apt install ./fm.deb`。ログイン画面で「Family mruby」を選んでログイン (黒いときは L9b の手順の `WLR_RENDERER=pixman`)。
3. Family mruby の中で確かめること (コンポジタの形):
   - メニューの Editor で何か打ち (日本語はかな入力で)、Ctrl+A・Ctrl+C。Linux の区分から Konsole か Kate を開き、Ctrl+Shift+V (Konsole) か Ctrl+V (Kate) で貼れる。
   - Kate か Konsole で文字を選んでコピー (Kate は Ctrl+C、Konsole は Ctrl+Shift+C) し、Family mruby のエディタで Ctrl+V。
   - Family mruby の Shell で Ctrl+V: 1 行に入り、Enter まで実行されない。複数行をコピーして貼ると空白でつながる。
   - Shell で `!` (Linux のシェル) を開き、Ctrl+Shift+V で貼れる。改行のある文字はその行が実行される。`exit` で戻る。
   - X11 のアプリ (Linux の区分の xterm や Firefox の X11 版があれば) とも同じ。X11 のアプリへは、その窓をクリックしてから貼る。
   - Konsole でコピーしてから Konsole を閉じ、Family mruby のエディタや Kate で貼れる (選択が残る)。
   - 中ボタンの貼り付け (選んだだけの文字) は Family mruby とはつながらない (Linux のアプリ同士も、このコンポジタの上ではつながらない)。
4. ログ (`~/.local/share/sddm/wayland-session.log`): `native: clipboard: took N bytes from a Linux program (text/plain;charset=utf-8)`、`clipboard: set N bytes (generation G)`、`clipboard: took N bytes from the host`。
5. 余力があれば SDL の窓の形 (Plasma の中で端末から `family-mruby --machine sdl`): Plasma のアプリでコピー → Family mruby の窓をクリック → エディタで Ctrl+V。エディタでコピー → Plasma のアプリで貼る。

## 7. 撤回した見立て・踏んだ罠

- X11 のアプリがクリップボードを読もうとすると「none」が返った。wlroots の Xwayland の橋渡しは、X11 の窓にキーボードが無いと読みを断る。試験で X11 の窓をクリックしてから読むようにした (作りの不具合ではない)。
- 手元の SDL 2.0.20 の X11 は、ほかのアプリ同士のコピーの変化を知らせない。フォーカスを得たときにも読むようにした。
- ホストの試験の「欠けた読み」の数え方で、受け渡しを始める前の文字を数えていた (試験の誤り)。
- 一時の HOME で `fmrb_native.rb app spawn` を呼ぶと、Python の debug の口が利用者の場所の msgpack を見つけられない。道具の呼び出しには HOME を渡さないようにした。
