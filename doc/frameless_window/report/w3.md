# W3: 透けている所のクリックを後ろの Window へ回す

> 状態: 報告 | 更新: 2026-11-11 | (a) 画素を読む方を入れた。押下が枠なしの Window に当たったときだけ、カーネルがその canvas の 1 画素を描画側に問い (既にある GET_PIXEL)、透ける色なら次の Window へ回す。費用は押下 1 回につき約 10 ms (ネイティブ版・sim の Retro で実測。中身はホストのタスクの待ちで、画素を読む時間ではない)、内蔵 RAM の増分は 0。graphics-audio は変えていない。途中で Modern の GET_PIXEL が色を取り違えていたのを見つけて直した。ネイティブ版 (標準と mruby のカーネル)・ブラウザ版・sim の Retro で確かめ、回帰の道具 (regress・screens・checkpoint・spinel・size) は全部通った

指示書は `doc/frameless_window/instruction_w3.md`、計画は `plan.md`、前段は `report/w1_w2.md`。

## 1. 比べたもの

### 1.1 (a) 描画側の画素を読む

調べると、口は既にあった。アプリの `@gfx.get_pixel(x, y)` が使う同期の命令 `GFX_CMD_GET_PIXEL` (link では `FMRB_LINK_GFX_GET_PIXEL = 0x55`) が、display_local (Tab5・ネイティブ版・ブラウザ版) と graphics-audio (WROVER・sim) の**両方に実装済み**で、どちらも答えを返す。経路は ホストのタスクの列 → link → 描画側 → 応答 → ホストのタスクが待ち手の semaphore を上げる、で、途中にある描画の命令の後ろに並ぶ (直前まで描いた所が読める)。カーネルはこれを `fmrb_gfx_submit_unmetered` (アプリの持ち分の枠を取らない、canvas の解放と同じ口) で出せばよい。

| 項目 | 測った値・見立て |
|---|---|
| 押下 1 回の時間 (ネイティブ版) | 9.4〜10.9 ms (10 回)。1 回だけ 0.09 ms (ホストのタスクがちょうど起きていたとき) |
| 同 (sim の Retro、graphics-audio はソケットの先) | 9.7〜10.0 ms (5 回) |
| 同 (ブラウザ版) | 画面とふるまいで確かめた (ログを出す口が無いので時間は測っていない)。体感で遅れは分からない |
| 内訳 | ほぼ全部がホストのタスクの待ち。主ループは `fmrb_msg_receive(PROC_ID_HOST, .., 10)` で最大 10 ms 寝てから `fmrb_transport_process()` で応答を拾うので、描画側がすぐ答えても次の周回まで拾われない。画素を読む時間は 0.1 ms 未満 |
| いつ払うか | 押下 (mouse_down) のときだけ、しかも**その点の一番上が枠なしの Window のときだけ**。枠つきの Window・デスクトップ・メニューバーの押下は今までと同じ (比べる式が 1 つ増えるだけ)。move・up・キーは払わない (押下で決まった相手に送られる)。2 枚の枠なしが重なって両方透けていれば 2 回 (約 20 ms) |
| 内蔵 RAM | 増分 0。新しい static は無い。待ちの semaphore は呼ぶたびに作って消す (アプリの get_pixel と同じ)。カーネルのタスクの stack の峰は `gfx_cmd_t` 1 個ぶんほど深くなる (下の 5 章) |
| 押している間の待ち | カーネルのタスクがその間止まる (他の入力は列で待つ)。上限は transport の 5 s (描画側が止まったときだけ。そのときは画面ごと止まっている) |
| Retro (S3) での見立て | graphics-audio を変えずにそのまま動く (sim で確かめた)。実機は UART 921600 bps の往復が加わる: 命令と応答はそれぞれ 20 バイトほどで 0.2 ms ずつ、WROVER が先に積まれた描画を片付ける時間がこれに乗る。10〜20 ms ほどと見る (実機では測っていない) |

### 1.2 (b) アプリが当たりの形を申告する

基底に口 (例 `set_hit_regions([[x, y, w, h], ...])` か 1 bit のマスク) を足し、カーネルはそれだけを見る形。

| 項目 | 見立て |
|---|---|
| 押下 1 回の時間 | 往復なし (矩形の数だけ比べる)。Retro でも同じ |
| 置き場所 | ctx (PSRAM) に Window ごと。矩形 8 個で 64 バイト × 7、64x64 のマスクなら 512 バイト × 7 |
| アプリの負担 | 絵と申告を自分で揃え続ける。アバターの 16x16 の絵でも矩形は行ごとに 14 個ほど。絵が動く・変わるたびに申告し直し、忘れると見た目と当たりがずれる (見えない所が当たる・見える所が抜ける) |
| 足すもの | 基底 2 つ (mruby・Spinel、Spinel は ivar の並びの罠がある)、C の口、カーネルの読み口、チェックポイントで移るときの申告の持ち運び |

### 1.3 選んだもの

(a)。理由:

- 費用は押下 1 回あたり約 10 ms で、指示書の「体感で分からない」に収まる (クリックの遅れとして感じるのは数十 ms から上)。しかも払うのは枠なしの Window を押したときだけ。
- 内蔵 RAM は増えない。
- 判定が画面と必ず一致する (描いたものがそのまま当たり)。アプリは何も書かなくてよい。
- 口が両方の描画側に既にあったので、Retro も graphics-audio を変えずに同じコードで動く。(b) の「Retro でも使える」という利点が (a) にもあった。

(b) は入れていない。(a) で足りない場面 (下の 4 章の sprite) が実際に困ると分かってから、足すかを決めればよい。

## 3. 途中で分かったこと: Modern の GET_PIXEL が色を取り違えていた

最初に試すと、アバターの赤 (0xE0) が 0x1C と返り、透ける色 0x01 は 0x00 と返った (どこも「当たり」になる)。display_local の canvas は RGB565 (バイトを入れ替えない並び) なのに、`readPixel()` の答え (RGB565) を `rgb888_t` に入れて RGB332 に直していたため、色の成分を取り違えていた (canvas の置き場の注釈も「8bpp (RGB332)」と古かったので直した)。`readPixelValue()` で格納値を取り、`rgb565_t` → `rgb332_t` で直すようにした。graphics-audio 側は前から `readPixelValue()` で正しかった。

この直しで、Modern (Tab5・ネイティブ版・ブラウザ版) のアプリの `get_pixel` も正しい色を返すようになる (例: `flash/app/demo/picoruby.app.rb` の get_pixel の頁)。画面の回帰 (`regress:screens`) にこの頁は入っていない。

## 5. 取り下げた見込み・仮決め

- 見込み「display_local に 1 画素を問う口を足す」→ 既にあった (アプリの get_pixel の口)。足したのはカーネルからの呼び口だけ。
- 見込み「Retro は子マイコンの側を変えないと無理かもしれない」→ graphics-audio の GET_PIXEL がそのまま使えた。
- 見込み「押下の費用は画素を読む時間」→ 読む時間はわずかで、約 10 ms はホストのタスクの主ループの待ち (応答を拾うのが次の周回)。アプリの get_pixel も同じだけ待っている。
- 仮決め: 読むのは描きかけの方の buffer (display_local の `sprite`、graphics-audio の `draw_buffer`)。命令の列の順に読むので、アプリが clear の後・描く前に押されると、絵のある所も透けて見えて抜けうる。present 済みの方 (display_local の `render_sprite`) を読めば画面と一致するが、命令の形 (両方の描画側で共有) を変えることになるので今は変えていない。
- 仮決め: 時間切れや失敗は「当たり」(今どおりの四角)。

## 6. 残件

- **sprite は当たりにならない**: 判定は canvas の画素だけを見る。`SpriteInstance` で絵を出し canvas を透けたままにしたアプリは、絵の上を押しても後ろへ抜ける。spec.md 3.4 と skill に書いた。困るアプリが出たら、(b) の申告か、描画側で sprite も見る問いを考える。
- **約 10 ms はホストの主ループの待ち**: 同期の命令を出した直後に `fmrb_transport_process()` を回すなど、ホストのタスク側で縮められる見込みがある。アプリの get_pixel・sync_file など同期の命令全部に効くので、この段では触っていない。
- **実機 (Tab5・S3) で測っていない**。S3 の UART の往復と WROVER の待ちを含めた時間、カーネルのタスクの stack の峰 (呼び口が `gfx_cmd_t` ほか 0.5 KB ほど深い。canvas の解放の経路と同じ深さ。周期ダンプの `fmrb_task:` の Free で見る) は実機をつないだときに見る。
- `tool/spinel_poc/harness_input_router.rb` は CRuby で全 700 件が `NoMethodError` になる。今回の変更の前から同じ (stash して同数)。直していない。
