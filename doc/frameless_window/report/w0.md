# W0: 今の口だけで枠なしの Window を試作して確かめる

> 状態: 報告 | 更新: 2026-11-10 | 枠を描かず Window 全体を透ける区画にした試作 (64x64、ドット絵) は、ネイティブ版・ブラウザ版・sim の Retro のどこでも後ろが透けた。仮決めは成り立つ。上 11 行はカーネルのドラッグと読み直しを起こす。アプリ自身のドラッグは事象こそ途切れないが、カーネルが送る相対座標の基準が途中で黙って変わるため、絵が戻ったり止まったりする。W2 のドラッグはカーネルが持つしかない

指示書は `doc/frameless_window/instruction_w0.md`、計画は `plan.md`。リポジトリのコードは直していない。

## 1. 試作

リポジトリの外に置いた (`/tmp/claude-1000/-home-kishima-fmrb-family-mruby/d865add5-d638-40f7-89da-40dce8f29b87/scratchpad/w0/app/w0_avatar.app.rb` と `.app.toml`)。

- `.app.toml`: 64x64、`(120, 60)`、`movable = true`、`launcher_visible = false`。
- `on_create`: `self.closable = false`。`@gfx.clear(TRANSPARENT_COLOR)` で全体を透ける色にし、16x16 の文字列のドット絵を 4 倍で `fill_rect` (行ごとの連長) で描き、`set_composite_regions([{0,0,w,h, transparent: true}])` を掛けて `present`。`clear_user_area` と `draw_window_frame` は呼ばない (呼ぶと枠が出る)。
- `on_event`: 左の押下で掴んだ点を覚え、`mouse_move` で `set_window_position` で自分を動かし、離しで終える。各事象をログに出す。`r` キーで「`on_restore` で透けを掛け直すか」を切り替える (インスタンス変数なのでイメージに入って運ばれる)。
- `on_restore`: 掛け直す設定なら全部描き直す (上と同じ `paint`)。

ネイティブ版は利用者の場所を scratchpad に分けて 2 つ動かした (`ruby tools/fmrb_native.rb --run-dir /tmp/fmrb-w0-a up --user-dir <scratchpad>/w0/homeA --debug-port 5571`、B は `-b`・`homeB`・5572)。MCP の native_* は既定の利用者の場所 (~/.local/share/family-mruby-dev) を使うので、W0 では CLI だけを使った。sim は `flash/home/w0/` に置き (sim の /home は flash/home)、終わってから消した。ブラウザ版は web_fs で `/flash/home` に置き、Shell の `run` で起動し、終わってから消した。

## 2. 確かめたこと

画面は `/tmp/claude-1000/-home-kishima-fmrb-family-mruby/d865add5-d638-40f7-89da-40dce8f29b87/scratchpad/w0/` に置いた (以下、ファイル名だけ書く)。

### 2.1 透けるか

| 構成 | 結果 | 画面 |
|---|---|---|
| ネイティブ版 (Modern の表示の経路、426x240) | デスクトップの壁紙の上、別の Window (Kamon) の上のどちらでも、絵の外と足の間が透けた | n1_spawn.png、n2_over_window.png |
| ブラウザ版 (426x240) | Shell の Window の上で透けた。自分のドラッグでも透けたまま動いた | w1_web_over_shell.png、w2_web_selfdrag.png |
| sim の Retro (NARYAv3、320x240) | 壁紙の上・Kamon の上で透けた | s1_retro_spawn.png、s2_retro_over_window.png、s3_retro_selfdrag.png |
| sim の Modern | 確かめていない (下) | - |

sim の Modern は確かめていない。今の build/ は Retro (NARYAv3) の Linux ビルドで、Modern にするには両リポジトリの `clean_all` と作り直しが要る。sim の合成は Retro・Modern とも graphics-audio の `graphics_handler.cpp` の同じ `composite_region` (機種での分岐は無い) で、Modern の表示の経路 (display_local) はネイティブ版とブラウザ版で確かめたので、足りない所は無いと見た。

最初の 1 枚から枠は出ない。基底の `initialize` は枠の GfxBlock を作り角の丸みの区画を掛けるが、描くのは `clear_user_area` / `draw_window_frame` を呼んだときだけなので、アプリが `@gfx.clear` と区画の掛け直しをすれば枠の無い絵だけになる。

### 2.2 上の 11 行

- 左の押下で**カーネルのドラッグが始まる** (`spx: Start drag: PID 4, offset=(30,3)`)。透ける画素 (絵の無い所) を押しても始まる。押下はアプリにも届くので、試作のアプリのドラッグも同時に動く。カーネルは `_update_window_position`、アプリは `set_window_position` で同じ値を書き、この試験では一致したので見た目は壊れなかった (n6_titlerows_drag.png)。たまたま一致しただけで、アプリの式が違えば取り合いになる。
- **右クリックで読み直しの問い** (`Reload W0 Avatar?`) が出た (n7_title_rclick.png)。基底の `_frame_event` の `ev[:y] < 11` による。右の押下でもカーネルのドラッグが始まる (ボタンを見ていない)。
- 閉じるボタンの当たり判定は `closable = false` で消えた (右上を押しても何も起きない)。カーネル側の mouse_up の閉じる判定は mruby 以外の VM のアプリだけが対象で、mruby のアプリには効かない。

### 2.3 アプリ自身のドラッグ

**事象は途切れない**。カーネルは mouse_move を、ドラッグ中でなければ「焦点のある Window」(`@hid_target_pid`) に送り、ポインタがどこにあるかを見ない。押下で焦点が移るので、カーソルが Window の外へ出ても事象は届き続ける。離しも押した Window に届く (`@mouse_down_pid`)。速く動かした試験 (30 ms ごとに 120 px 飛ぶ) でも 3 回の move と離しが全部届いた。

ただし 2 つの落とし穴がある。

1. **負の座標が 16 bit の符号なしで届く**。Window の左・上へ出ると `ev[:x]` は 65446 のような値になる (`fmrb_hid_event_t` の x・y は `uint16_t`)。アプリが `v > 32767 ? v - 65536 : v` で直す必要がある。
2. **相対座標の基準が途中で黙って変わる**。カーネルは相対座標を自分の Window の一覧 (`@window_list`) の位置から作るが、アプリの `set_window_position` は一覧を古くしない (dirty の印を付けない)。一覧が読み直されるのは押下のとき (強制) と、押下で付いた印 (焦点を移した `mark_window_list_dirty`) を、周期の `check_terminated_apps` が拾ったとき 1 回だけ。だから基準は「押下から最初の周期の点検までの間にあった位置」で、アプリには分からない。
   - 「今の位置 + (rel − 掴んだ点)」で動かすと、基準が押下時のまま残るので動きが加速する (カーソルが 50 px 動いて Window は 150 px)。
   - 「押下時の位置 + (rel − 掴んだ点)」で動かすと、途中で基準が今の位置に変わった所で絵が後ろへ跳ぶ。30 Hz で 1 秒、(30,40) → (230,140) へ動かした試験では、6 回目で 13 px 戻り、終わりの位置は (167,83) (正しくは (200,100)) で 33 px 遅れた (n5_selfdrag_30hz.png の記録)。sim の Retro では、読み直しが最初の move の直後に来て、その後の move の rel が変わらず Window が止まった。
   - 確実に動くのは「離したときに 1 回だけ動かす」形だけ (ドラッグ中に動かさなければ基準の位置は変わらない)。ついてくるドラッグは今の口では書けない。
3. 30 回送った move のうち届いたのは 25 回 (カーネルは move を詰まらせず最新だけ残す)。位置は絶対なので害は無い。

注入でどこまで再現できるか: `fmrb_input.rb` (sim_input / native_input と同じ語彙) の `down`・`move`・`up` と `sleep` で、押したまま動かす・外へ出す・負の座標までは再現できた。実際のマウスとの違いは間隔の揺れだけで、上の基準の問題は周期の点検の時刻で決まるので、手で動かしても同じことが起きるはずである (手では確かめていない)。

### 2.4 透けている所のクリック

透ける画素 (絵の外、rel (2,40)) を押すと、押下・離しとも**試作のアプリに届いた**。後ろの Kamon には届かない。当たり判定は `find_window_at` の Window の四角だけで、画素を見ない。見込みのとおり。

Window を (0,0) まで動かすと、絵はメニューバーの上に重なって描かれる。y < 13 の押下はデスクトップへ行くので、その部分は掴めない (n4_selfdrag_fast.png)。

### 2.5 閉じ方

| 口 | 結果 |
|---|---|
| Ctrl+Q (焦点がある状態) | 閉じた。カーネルが `quit request to built-in pid=4` を送り、基底の `on_quit_request` が `stop` (ネイティブ版・ブラウザ版) |
| Shell の `kill 4` | 閉じた (n11_shell_kill.png) |

キーボードがあれば今の口で閉じられる。キーボードの無い構成 (Tab5 をタッチだけで使うとき) では、今の口は遠隔 (tab5_app の kill) しか無い。仮決めの「どれも効かない形が見つかったら右クリックの口を足す」に当たるかは、W2 で決める材料として書いておく。

### 2.6 `amove` の後

ネイティブ版 A → B (`app move 4 --to /tmp/fmrb-w0-b`、29825 バイト、1.6 秒で moved)。

- `on_restore` で描き直して区画を掛け直すと、**透けたまま着いた** (n8_amove_reapply.png)。基底は `_checkpoint_restored` の中で枠を作り直し、角の丸みの区画を掛け、`clear_user_area` で枠を描くが、`present` は `on_restore` の後の 1 回だけなので、枠が一瞬見えることも無い。
- 掛け直さない設定 (`r` で切り替えてから B → A) では、**枠とタイトルバーと閉じるボタンの丸が出て、絵は消えた** (n9_amove_noreapply.png)。plan の見込みどおり。`closable = false` はインスタンス変数なので運ばれ、丸は描かれても押しても閉じない。
- 移す間の「moving...」の札は C (fmrb_app_checkpoint.c の `mark_show`) が Window の左上に出す (狭い Window の扱い)。枠なしでも出る場所はある。

### 2.7 合成の速さ (Retro)

- sim の Retro の graphics-audio は 5 秒ごとに `graphics_task: loop: fps=.. render_avg=..us` を出す (render は合成の 1 回分)。試作が止まっているとき 31-32 us、30 Hz で 5 秒ドラッグし続けたとき (present 20 回/秒) 41-42 us、max 476 us。fps は 30.2-30.3 のまま、late=0。
- sim は x86 なので値はそのまま実機にならない。合成のコードは WROVER と同じ `composite_region` で、透ける区画は 1 画素ずつの比較 (`if (px != key) dp[x] = px`)、透けない区画は行ごとの memcpy。64x64 の Window 全体を透けさせると比べる画素は 4096 (角の丸みだけなら 4x4x4 = 64)。毎回の合成は壁紙の 320x240 = 76800 バイトの写しから始まるので、増える分はその 5% ほどの量になる。200x150 の大きな絵でも 30000 画素で、壁紙の写しより少ない。**使えないほど遅くなる見込みは無い** (推定。WROVER の実機では測っていない)。
- 費用は「透けさせる区画の面積」に比例する。絵の外接矩形だけを透ける区画にし、残りを区画から外せば (区画を持つキャンバスは区画の外を合成しない) さらに減らせる。

### 2.8 そのほか

- plan の「動かすたびに INFO のログが 2 行」は、今の develop では既に DEBUG に下がっている (16825033、2026-11-10)。W0 のログにも出なかった。
- アプリの `@pos_x` / `@pos_y` は `set_window_position` と起動・復元のときだけ更新される。カーネルのドラッグで動いた後は古いまま。アプリが自分の位置を元に何かするなら (自分のドラッグを含む) ずれる。

## 3. 取り下げた見込み

- 「アプリが自分でドラッグを作ると、速く動かしてカーソルが Window の外へ出たときに事象が届かなくなるおそれ」(plan) は**外れ**。焦点のある Window に送られ続けるので途切れない。代わりに、上の基準の問題 (2.3 の 2) と負の座標 (2.3 の 1) がある。
- 試作の最初の式 (今の位置 + 差分) は、カーネルが毎回今の位置を基準にすると思い込んだもの。基準は押下時のままで加速した。次の式 (押下時の位置 + 差分) は基準が途中で 1 回変わることで崩れた。どちらも取り下げた。

## 4. W1・W2 の作りの見立て

### 4.1 W1: `window_frame = "none"` と上 11 行

フラグの道筋は `resizable` と同じ所を通す。

- C: `fmrb_app_spawner.c` で toml を読む (`resizable` の隣、~827 行)、`attr` → `ctx` (`fmrb_app.c` ~2097)、Window の一覧 (`fmrb_app_get_window_list`、`fmrb_window_info_t` に 1 bit)、Spinel のカーネルへ渡す印 (`fmrb_spx_kernel.c` の `FMRB_SPX_WIN_FLAG_*`)、Spinel のアプリの初期化の並び (`fmrb_spx_app.c` の buf)、mruby のアプリの `_init` (`app.c`。`@_frameless` のような ivar)、checkpoint のイメージの toml (`fmrb_app_checkpoint.c` ~402。移った先でも枠なしになるため)。
- 基底 (`fmrb-app.rb`): 枠なしなら `initialize` で枠の GfxBlock を作らず、キャンバスを透ける色で塗り、Window 全体を透ける区画にする。`_layout_user_area` は Window 全体を user area にする (`(0,0)-(w,h)`)。`draw_window_frame` は何もしない、`clear_user_area` の既定の色は透ける色、`_apply_rounded_corner_regions` の代わりに全体の区画を掛ける (大きさで控える今の仕組みをそのまま使えば resize と復元でも掛け直る)、`_frame_event` は閉じるボタンと右クリックの読み直しを見ない、スプライトの範囲は Window 全体。`_checkpoint_restored` は今の `_build_frame_block unless @_fullscreen` と区画の掛け直しを枠なしの分岐にする。これで `on_restore` で掛け直さなくても透けたまま着く (受け入れ条件)。
- Spinel の基底 (`main/prebuild_scripts/spinel/fmrb_app_base_spinel.rb`) にも同じ分岐が要る。**危険: 基底に ivar を足すと Spinel の ivar の並びが親子で食い違った前例がある** (doc/spinel_aot/reports/editor_ivar_layout_bug.md)。標準構成の sim 検証にエディタの 1 打鍵を必ず入れる。
- カーネル (`input_router.rb` の mouse_down): `elsif ... relative_y < 11 ...` のドラッグ開始に「枠なしでない」を足す。mouse_up の閉じるボタンの判定 (mruby 以外の VM 向け) も同じ。`find_window_at` は変えない。
- 回帰: 枠つきのアプリは分岐の外なので画面の基準は変わらない見込み。`rake regress:screens` で確かめる。内蔵 RAM は ctx に 1 bit (既存のバイトの空きに入れれば 0)。

### 4.2 W2: `window_drag = "anywhere"` とクリックとドラッグの見分け

- カーネルが持つ。2.3 のとおり、アプリのドラッグは基準の問題で今の口では正しく書けない。カーネルのドラッグは絶対座標 (`x - @drag_offset_x`) で動かし、毎回 dirty の印を付けるので、この問題が無い。
- mouse_down: `window_drag = "anywhere"` の Window なら、すぐにはドラッグを始めず「押下保留」(`@capture_mode = :press`、押した点と offset、Window) にし、**押下をアプリへまだ送らない**。
- mouse_move: 保留中に押した点から一定の距離 (仮に 4 px。Retro のタッチやマウスの揺れを見て決める) を超えたら `:drag` に移り、以後は今のドラッグと同じ。アプリには押下も move も送らない。
- mouse_up: 保留のまま離れたら、押下と離しを続けてアプリへ送る (クリックとして届く)。ドラッグだったら何も送らない。右ボタンは保留しない (今の右クリックをアプリに渡す)。
- 費用と危険: クリックの押下がアプリに届くのが離しの時まで遅れる (押している間の見た目の反応が無い)。長押しを使いたいアプリは `window_drag = "none"` にして自分で扱う。押下を即座に送り、ドラッグに移った時点で取り消しを送る形もあるが、アプリ側に取り消しの事象が要るので W2 では採らない見立て。
- 付けて直すとよいもの: (a) アプリが `set_window_position` で動いたときもカーネルの一覧を古くする (C の位置の変更に世代の数を持たせ、`update_window_list` が比べる、など)。`window_drag = "none"` で自分で動かすアプリと、2.3 の基準の問題のため。(b) アプリの `@pos_x` / `@pos_y` をカーネルのドラッグの後も正しくする (読むときに ctx から取る口)。
- 閉じる口: キーボードがあれば今の口 (Ctrl+Q・Shell の kill) で足りる。タッチだけの構成で閉じる口が無いことを W2 で決める (仮決めの範囲で、基底の右クリックかタッチの長押しを足すか)。

### 4.3 W3 (透けている所のクリックを後ろへ) への材料

当たり判定は Window の四角だけ。画素を見るには、カーネルが合成側の画素を読む口が要る (Retro では WROVER の側にあり、SPI を往復する)。Modern (display_local と同じプロセス) なら読めそうだが、W0 では費用を測っていない。
