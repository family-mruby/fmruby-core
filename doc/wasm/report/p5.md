## T1: 解像度選択と表示倍率

### 決めたこと

- 選択肢は **426x240 (既定・実機一致) / 640x360 / 852x480 の 3 つとも採用**。
  レイアウト破綻は見つからなかった (下の検証を参照)。
- **`default_user_app_width/height` は比例させる**。出荷値 386x180 は 426x240 の
  0.906 / 0.75 なので、その比を保つ (640x360 → 580x270、852x480 → 772x360)。
  固定にすると広い画面の隅に小さな窓が出るだけで、画面を広げた意味がない。
- 倍率は 1x / 2x / 3x / フィットで既定はフィット。canvas の CSS サイズだけを
  変えるのでリロードしない。フィットは整数倍に丸めない — 窓が狭いときに
  1x へ落ちるより、`image-rendering: pixelated` のまま端数で入る方がよい。
- **全画面**も入れた (implementation_plan の P5 節にあり、指示書 T1-T4 では
  タスク化されていなかった分)。screen-box を requestFullscreen し、全画面中は
  フィット固定。Esc はブラウザが全画面解除に使うので、Keyboard Lock がある
  環境 (Chrome) では Esc/Ctrl+W を奪い返し、無い環境向けにはページに注記した。

### 配線

解像度はテーマと同じ preRun 経路で `/flash/etc/system_conf.toml` を書き換える
(main.js `applyResolutionSetting`)。**core 側は無改修**で、指示書の見込みどおり
conf 駆動のまま追従した。URL クエリ `?w=&h=` は選択肢に一致するときだけ採用し、
localStorage へ書き写す (ブックマークから開いた後、クエリ無しのリロードでも
同じ画面になる)。セレクタを操作したときは `location.replace` でクエリを落とす —
古い `?w=` が新しい選択に勝ってしまうため。

### 検証 (headless、node + conf 差し替え)

3 解像度それぞれで デスクトップ / メニュー / ランチャー / エディタ起動+打鍵 /
PicoRabbit デッキメニュー を撮った。

| | 426x240 | 640x360 | 852x480 |
|---|---|---|---|
| デスクトップ・メニューバー | OK | OK | OK |
| ドロップダウンメニュー | OK | OK | OK |
| ランチャー (4x3 グリッド) | OK | OK | OK |
| エディタ起動 + 打鍵 | OK | OK | OK |
| PicoRabbit デッキメニュー (全画面) | OK | OK | OK |

窓は自分のサイズを保ったまま広い画面の中に置かれ、はみ出し・重なりは無い。
PicoRabbit のような全画面アプリは画面サイズに追従して端まで正しく並ぶ。

**唯一の見た目の欠け: 壁紙が 426x240 のまま**で、広い解像度では残りが
デスクトップ色 (cyberpunk では黒) になる。直すのは P5 の範囲外なので、
選択肢は落とさずページの説明文に一段書いた。直すなら 2 手あり、どちらも
小さくはない: (a) 解像度ごとの壁紙を bundle に足す、(b) `DRAW_IMAGE` に
拡大を実装する — **Modern/wasm の `DRAW_IMAGE` は scale を見ておらず
`pushSprite` するだけ**なので、Ruby 側で `draw_image(scale_x:)` を渡しても
効かない (display_p4_task.cpp)。

## T2: 同時起動アプリ数 (max_apps)

### 天井の持ち方を変えた

`FMRB_MAX_APPS` とそこから導く数を **`components/fmrb_common/include/fmrb_limits.h`
へ切り出した**。理由は `fmrb_mem_config.h` (アプリ 1 枠につきプールが 1 つ) が
同じ数から寸法を取る必要があるのに、`fmrb_task_config.h` を include すると
`fmrb_rtos.h` 経由で FreeRTOS ヘッダまで付いてくるため。切り出しで
**ノブは `FMRB_MAX_APPS` 1 つ**に保てた (プール数もプロセス id の上限も派生)。

- `PROC_ID_MAX = FMRB_MAX_APPS` (以前は最後の enum 要素の自動値)。名前付きの
  `PROC_ID_USER_APP0..4` は残す — picoruby-fmrb-const が Ruby へ公開している。
- `POOL_ID_USER_APP_LARGE = POOL_ID_USER_APP0 + FMRB_USER_APP_COUNT` として、
  ユーザアプリのプールを「名前のある両端を持つ連続領域」にした。
  `fmrb_mempool.c` の size / name 引きは case 列挙をやめて範囲判定にしてある。
- 静的確保は従来どおり先頭 3 つだけ。残りは `fmrb_mempool_reserve` が
  初回使用時に取る (32 枠でも .bss は増えない)。
- `main/app/fmrb_app.c` の `_Static_assert` に
  `PROC_ID_USER_APP0 == FMRB_SYSTEM_PROC_COUNT` を追加した。fmrb_limits.h が
  この位置を仮定してユーザ枠数を引くので、ずれたらビルドで落ちる。

wasm だけ **`FMRB_MAX_APPS=32`**。wasm/CMakeLists.txt と
lib/add/family_mruby_wasm.rb の**両方**に入れた (mrbgem の port が同じ定数で
配列を切るため。MRB_* と同じ規律)。

### system_conf の max_apps

`max_apps` を新設した。既定は天井、上を超えたら警告付きで clamp、
ユーザアプリ 1 枠を切ったら引き上げ。**照合は spawner ではなく
`fmrb_app.c` の `alloc_ctx_index()` に置いた** — 枠を配る唯一の場所なので、
どの spawn 経路も迂回できない (spawner に置くと launcher/shell/debugd の
経路ごとに書くことになる)。sim で `max_apps = 99` を入れて clamp を実測:

```
W kernel: max_apps=99 exceeds the build ceiling 9; clamped
I kernel: Max Apps: 9 (build ceiling 9)
```

### kernel Ruby への渡し方 (指示書の確認項目)

**Ruby 側に `FMRB_MAX_APPS` で回るループは無かった**。input_router.rb:55 の
`FMRB_MAX_APPS=7` はコメントで、窓一覧は C が数えて返したものをそのまま
配列で受けている (`_get_window_list`)。実体は `@max_app_num` 1 つで、
ログに出るだけ。ただし 2 つとも古い値を持っていた:

- mruby 版 kernel.c はビルド天井 (`FMRB_MAX_APPS`) を渡していた → **conf 値**に。
- Spinel 版 (fmrb_kernel_base_spinel.rb) は **`@max_app_num = 7` のリテラル**で、
  当時の 9 にも追随していなかった → FFI `fmrb_spx_max_apps` を足して C から取る。
  theme_color と同じ理由・同じ置き場所 (fmrb_spx_common.c): 生成時に焼くと腐る。

wasm 実測: `spx: Max App Number = 32`。

### 表示側の天井が先に効いた (最大の発見)

12 本起動したところ **11 本目から `Canvas pool full (max 8)`** で、12 本目の
MIDI APU は `define_prog: pool full` を受けて例外死した。窓 1 つにつき
canvas 1 枚なので、**`DISPLAY_P4_MAX_CANVAS` が実際の同時起動数を決めていて、
`FMRB_MAX_APPS` を上げても絵に描いた餅になる**。8 は PSRAM の予算 (1 枚
あたりフレームバッファ 2 枚ぶん、426x240 で約 200KB) であって設計上の
限界ではないので、両方を `#ifndef` で上書き可能にし、wasm だけ
`DISPLAY_P4_MAX_CANVAS=34` / `DISPLAY_P4_VM_MAX_PROGS=64` にした。
既定値は変えていないので実機・sim には影響しない。

### 多数起動の実測 (wasm/node、drive.js でランチャー連打)

| | 上げる前 | 上げた後 |
|---|---|---|
| spawn した数 | 15 (kernel/desktop/services + 12 アプリ) | 15 |
| 途中で死んだ数 | 2 (BASIC demo は自然終了、MIDI APU は canvas 枯渇) | 1 (BASIC demo の自然終了のみ) |
| `Canvas pool full` | 5 回 | 0 回 |

使われた枠は最大 idx=15 (mempool_id=15)。crash マーカーは 0 件。
Shell / Editor / BASIC / MicroPython / Lua / mruby アプリが同時に生きている。

pthread pool は 40 → **56** (32 枠 + 常設タスク)。node では枯渇しても代償が
無いが、ブラウザではプールが空の pthread_create がメインスレッドの番待ちに
なるため、先に温めておく方針は P1 のまま。

`build/dist/` に 8 ファイル、合計 6.19 MB。


**staging のゲートとは別に、リンカが実際に詰めた結果を読み返す**。
core_web.js のローダ metadata からファイル一覧を取り、

1. staging と packed の差 (どちらか片方にしかないもの)
2. git 追跡でも既知の生成物でもないファイル
3. .data のバイト列に、このマシンの実際の資格情報 (`~/.openai_key`、

   現れないこと。加えて `sk-` 形式と PEM 秘密鍵の形も見る

書いた直後に照合そのものの粗を 1 件直した: 最初の版は wifi.toml /
services.toml の `k = "v"` を全部拾っていて、サービス名 (`tts.rb`、

**NSF について**: 指示書の受け入れ条件は「.data に NSF 0 件」だったので

(`flash/usr/share/sounds/nsf/lost_in_hyperspace.nsf` と `test.nsf`) は

### 素の静的サーバでの動作 (受け入れの核心)

`python3 -m http.server` で dist/ を配信 (ヘッダは一切足していない。
`curl -I` で COOP/COEP が付いていないことを確認済み) し、Windows の
Chrome (headless) から読ませた:

```
1 回目: crossOriginIsolated=false secure=true sw=false   sab=undefined
2 回目: crossOriginIsolated=true  secure=true sw=true    sab=function
3 回目: crossOriginIsolated=true  secure=true sw=true    sab=function
```

**coi-serviceworker が仕事をしている** = GitHub Pages 相当の素のホストで
成立する、の証明。index.html でも status 行が `ready` になり、canvas の
CSS サイズがフィット計算 (628x354) で入っていることまで DOM で確認した。

**初回訪問は 1 回リロードが挟まる** (Service Worker の登録 → 制御開始)。
その間ページは動けないので、`crossOriginIsolated` が false のときに status 行が
そう言うようにした。これが無いと、モジュールの instantiate が
SharedArrayBuffer 由来の分かりにくいエラーで落ちるだけになる。

### 同梱サンプルの音: NSF が wasm で鳴っていなかった (直した)

NSF を同梱すると決めたので web 版で実際に鳴るか確かめたところ、
`NSF play: failed to load /flash/cache/nsf_player/lost_in_hyperspace.nsf`
で落ちていた。原因は **audio_p4 が fopen に生の `"/flash%s"` を渡していた**
こと。プレイヤが `FILE*` を欲しがるので fmrb ファイル HAL を通さず、
デバイスの VFS マウント点を直書きしていた。wasm の storage は POSIX HAL の
cwd 相対 `flash` なので、絶対パス `/flash` は存在しない。

`AUDIO_P4_FLASH_BASE` を audio_p4_internal.h に置いて 3 箇所を通した
(host_file_local.c の `LOCAL_BASE_PATH` と同じ形・同じ理由)。ESP32 側の
文字列は `/flash` のままなので実機は無影響 (TAB5 ビルドで確認)。

同じ根で **Breakout の BGM も鳴っていなかった** — 12 本起動の検証中に出た
`load_fmsq_file: cannot open /flash/cache/app/breakout/bgm.fmsq` がそれで、
当時は無関係なノイズだと思って流していた。3 箇所とも直っている。

修正後、drive.js の `rec` で NSF の再生を録って確認:

```
drive: audio 2800ms rms=2845 freq~110Hz
drive: audio 2900ms rms=2930 freq~135Hz
drive: audio 3100ms rms=3325 freq~535Hz
```

無音窓なしで音高が動いている = 曲が流れている。
**audio_p4 は Linux sim ではコンパイルされない** (sim の音は graphics-audio 側)
ため、この穴は wasm を通して初めて見えた。

## 追補 (2026-08-30): 設定がブラウザで効かない — 根本原因と作り替え

ユーザの実ブラウザ確認で「テーマ切替が変わらない」「解像度が内部解像度に
見えない」が出た。headless Chrome で両方再現し、根本原因を特定:

> **PROXY_TO_PTHREAD では、ページ (ブラウザのメインスレッド) の MEMFS と
> main() が走るスレッドの MEMFS は別のファイルシステム**である。preRun での
> FS.writeFile はページ側 FS に落ち、機械は自分側 FS (packed .data 由来) を
> 読む。console には ENOENT が出ていた (テーマは焼き込みなので既定だけ動く)。

作り替え: **ページは argv で渡すだけ、適用は機械が自分でやる**。

- main.js は `--fmrb-res=WxH` / `--fmrb-theme=classic` を Module.arguments に
  積むだけになった。FS export も廃止。
- wasm/backend/page_settings_wasm.c (新規) が、main() のスレッド上・機械側
  FS で system_conf.toml を書き換え、classic では壁紙も戻す。
  同じフラグが node でも効く (`node core --fmrb-res=852x480`)。
- resume() の罠も 1 つ: 信頼されないクリック (autostart 等) では
  `AudioContext.resume()` が永遠に解決しない。タイムアウト競争にした。

### headless 検証を可能にした道具 (常設)

「ブラウザ JS 経路が headless で試せない」ことがこの見逃しの根だったので、
道具を足した:

- `?autostart=1` — ページ自身が電源クリックを押す (音は黙って諦める)。
- `?holdload=N` + 開発サーバの `probe-hold` (N ms 遅れて返る画像) —
  load イベントを起動完了まで引き延ばし、headless Chrome の --screenshot
  (load 時に発火) が「起動後の画面」を撮れるようにする。
- 手順: `rake wasm:serve` +
  `chrome --headless=new --screenshot=... '<page>?autostart=1&holdload=30000&w=852&h=480'`

この道具で 3 態 (既定 / 852x480 / classic) のスクリーンショットを取り、
