## T0: 基準画像 (完了)

### 比較手段が指示書の想定より強い

指示書は `tools/fmrb_pngdiff.rb` での比較としており、同ツールの説明は実機の
JPEG フレームには `--tol 24` を勧めている。実測すると**その必要が無い**:
リモートデスクトップの経路は決定的で、静止画面を 2 回撮ると
**バイト単位で一致**する。つまり PPA と CPU は **tol 0 で厳密比較できる**。

ただし 2 つ罠がある (どちらも実測で確定):

- **JPEG は 8x8 ブロック**なので、メニューバーの時計と空きメモリ表示が
  **y=8..23 の行すべてを汚染する**。バー自体は y<13 なので、従来の
  「y>=13 で切る」では足りない。tol 0 で 167 px、tol 8 でも 37 px 残る。
- JPEG は幅 **432** に padding される (426 の 16 切り上げ)。x=426..431 は
  比較対象外。

そこで矩形を 2 枚使う。合わせて、比較しようのない右上以外を全部覆う。

| | 矩形 | 静止画面 2 回撮りの差 |
|---|---|---|
| L | `0 13 224 227` | 0 px |
| B | `0 24 426 216` | 0 px |

| 基準 | 画面 | 矩形 |
|---|---|---|
| desktop | デスクトップ単独 | L + B |
| editor | FM-Editor 空バッファ | L + B |
| tiles | draw_tile_test をエディタに重ねる。**カラーキー (透過) の検証** | L + B |
| rabbit_list | PicoRabbit デッキ一覧 (全画面) | L + B |
| rabbit_slide | スライド 1/11。フォント + スプライト | `0 0 426 208` |

rabbit_slide だけ別矩形なのは、左下のマスコットが animate するため
(1 秒差の 2 枚で y=223 に 20 px 以上の差)。y<208 は完全一致。

カーソルは撮影前に `move 410 200` で退避する (フレームに焼き込まれるため)。

### display_backend_t の確定形

```c
typedef struct {
    const char *name;
    void (*init)(int fb_w, int fb_h);
    void (*first_frame)(void);
    void (*blend_block)(const display_blend_req_t *req);
    void (*present)(LGFX_Sprite *fb, size_t fb_size);
    void (*present_patch)(const uint16_t *block, int x0, int y0,
                          int w, int h, int fb_w, int fb_h);
    void (*shutdown)(void);
} display_backend_t;
```

`blend_block` の引数は構造体 1 個 (`display_blend_req_t`)。**クリップと
ビューポートのトーラス分割は呼び出し側 (display_p4_task.cpp) に残した**ので、
バックエンドは「もう切り終わったブロックを 1 枚置く」だけを知っていればよい。
セマンティクスが 1 箇所に集まり、2 実装の間で食い違いようがない。

### 移設対応表

| 元 (display_p4_task.cpp) | 先 |
|---|---|
| INIT_DISPLAY の PPA client 登録 + `g_lcd.getFrameBuffer()` | `ppa_init` |
| `render_frame` の `g_first_render` ブロック | `ppa_first_frame` |
| `blend_canvas_block` の PPA 部分 (msync + `ppa_do_blend` + 失敗時 CPU コピー) | `ppa_blend_block` |
| `render_frame` の SRM 3x+回転 と `pushRotateZoom` 代替 | `ppa_present` |
| `cursor_patch` の DSI 直書き部分と LGFX 代替 | `ppa_present_patch` |
| `g_ppa_srm` / `g_ppa_blend` / `g_dsi_fb` / `DSI_FB_W/H` | PPA バックエンドの static |

残したもの: 受信ループ、コマンド解釈、canvas/sprite/image ストア、z 順、
ビューポート分割、sprite clip、capture、カーソルの合成と bake/restore、
`ppa_alloc_buffer`、`ppa_verification_test`。

### 指示書の在庫と食い違った点

- **`cursor_patch` は `g_dsi_fb` へ直接書く** (指示書のとおり)。SRM の回転
  (`nx = iy, ny = margin + imgH - 1 - ix`) を手で再現し、書いた行だけ C2M で
  書き戻している。カーソル移動が 1.8MB でなく 4.6KB で済むのはこの経路。
  よって `present_patch` として I/F に入れた。**合成 (どの画素にカーソルを
  乗せるか) は呼び出し側に残し**、バックエンドは出来上がったブロックを
  拡大して置くだけにした。これで合成ロジックが 2 経路に重複しない。
- **`ppa_verification_test` は移設不要**だった。自前で
  `ppa_register_client` するのでグローバルを消しても壊れない (呼び出しは
  `#ifdef PPA_VERIFICATION_TEST` で既定オフ)。CPU バックエンドでは呼ばれない
  という要件は、この `#ifdef` で既に満たされている。

### 指示書から意図的に外した 2 つ

- **`alloc_fb` を I/F に入れなかった**。`ppa_alloc_buffer` はキャッシュライン
  整列の PSRAM を取るだけで PPA 固有ではなく、canvas も同じものを使う。
  両バックエンドで共有する。
- **パネル起動 / I2C service / ヘッドホン検出を PPA 側へ移さなかった**。
  指示書はこれらを PPA バックエンドへ、としているが、**CPU バックエンドも
  同じパネルを点けないと描けない**。これは PPA のハードウェアではなく Tab5 の
  ハードウェアなので `display_p4_task.cpp` に残し、バックエンドからは
  `display_p4_lcd()` と `display_p4_panel_framebuffer()` で触る形にした。
  (後者を分けたのは、`getFrameBuffer()` が `LGFX_Tab5` にしか無く、
  `display_backend.h` に Tab5 パネル定義を持ち込みたくないため。)

### サイズ (受け入れ条件 3)

`idf.py size-components` の libmain.a、同一ツリーで分割前後をそれぞれビルド。

| | Total | .bss | .data | fmruby-core.bin |
|---|---|---|---|---|
| 分割前 | 1548219 | 35141 | 5831 | 0x58ed10 |
| 分割後 | 1549207 | 35653 | 5831 | 0x58ef00 |
| 差 | +988 | **+512** | 0 | +496 B |

`.bss` の +512 は `cursor_patch` に足した `static uint16_t block[16*16]`。
カーソルを合成したブロックを作ってからバックエンドへ渡す形にした費用で、
合成ロジックを 2 経路に重複させない代わり。消すなら `render_frame` の
`s_cursor_save` (同サイズ、使う時間帯が重ならない) と共有できるが、静的変数を
2 関数で共有する形になるので分けている。**+512B を受け入れ、共有はしない
(ユーザ判断確定、2026-08-29)**。

## T2: CPU バックエンド (完了、実機検証済)

2026-08-29、448cd705 として develop にコミット。

- `display_blend_cpu.c`: 合成核。ESP-IDF を include しない素の C
  (wasm がそのまま使うファイル)。矩形ブリット + カラーキー、fg 不透明で
  上書き。キャッシュ操作は無し (全部 CPU アクセスなので不要)。
- `display_backend_cpu.cpp`: 出力は pushRotateZoom (PPA バックエンドの
  SRM 不在時フォールバックと同じ経路)。present_patch も同フォールバックの
  LGFX pushImage 経路をそのまま使う。
- 選択配線も実装済み: `FMRB_DISPLAY_BACKEND=cpu rake build:esp32` →
  Rakefile が container env へ → main/CMakeLists.txt が
  `FMRB_DISPLAY_BACKEND_CPU` を define。**env を変えただけでは ninja は
  reconfigure しない**ので、切替時は main/CMakeLists.txt を touch し、
  ブートログ (`CPU display backend` vs `PPA Blend initialized`) で
  どちらが動いているか確認する。

### カラーキーの決着 (最大の争点だったもの)

差は**出なかった**。呼び出し側が帯を 565 色から
`[c<<k, (c<<k)|mask]` (下限=ゼロ埋め、上限=下位ビット全立て、両端含む) で
作るため、この帯に対しては「FG 画素の 8bit 展開が帯に入る」=「565 成分が
キーと等しい」となり、展開がゼロ埋めでもビット複製でも判定は同一になる。
CPU 実装はゼロ埋め展開 + 両端含む比較で、tiles 基準 (カラーキー透過) を
含む全画面が PPA と一致した。wasm への申し送り: **帯をこの生成規則で
作る限り、展開方式の差は現れない**。

### 実機検証 (受け入れ条件 2)

CPU 強制ビルド (bin 0x58da70) を app_only で焼き、T0 の 5 基準すべてに
対して **tol 0・0 px 一致** (撮影 2 回の安定性も全画面 0 px)。つまり
CPU 合成は PPA と画素単位で等価。capture 経路は SRM 前の合成済み
426x240 を取るので、これは blend 結果の直接比較になっている。

### render_ms (性能記録)

PicoRabbit スライド 1/11 表示中 (マスコットが animate、5 frames/5s)、
`display_p4: render` の周期ログで実測:

| バックエンド | avg | max |
|---|---|---|
| PPA | 17ms | 18ms |
| CPU | 262-269ms | 284ms |

約 15 倍遅。P4 の撤退線判断の材料 (指示書どおり数字のみ、最適化しない)。
デスクトップ単独では PPA 20ms 前後。

### サイズ

既定 (PPA) ビルドは T1 と**完全に同一** (libmain.a Total 1549207 /
.bss 35653 / bin 0x58ef00)。CPU バックエンドのオブジェクトは未参照で
リンカ GC が全部落とすため。CPU 選択ビルドは bin 0x58da70 (PPA 経路が
逆に落ちて 5.3KB 小さい)。

## 音の関数表化 (8aeeb90d)

**やったこと**: init / ready / write / set_volume の 4 点を
`audio_backend_t` (main/drivers/audio_p4/audio_backend.h) に集めた。
write は従来どおり `apuif_set_output_writer(audio_backend()->write)` で
APU に渡す。audio_p4_hw.c の 4 関数は static 化し、呼び出し 4 箇所
(display_p4_task.cpp の init、audio_p4_task.c の ready/write、
audio_p4_handler.c の set_volume) を全部表経由にした。

**やらなかったこと**: ビルド時の選択機構 (実装が 1 つしか無いので不要。
wasm が来たときに表を差し替える)。マイク (ES7210) は表に入れない —
Tab5 ハードウェア固有の公開 API で、出力経路ではない。実機での官能確認は
ユーザが実施し、発音を確認済み (2026-08-29。ブートログの codec init 成功 +
APU タスク起動と合わせて、表経由化の回帰なし)。

## wasm への申し送り

- 合成核は `main/drivers/display_p4/display_blend_cpu.c` をそのまま
  コンパイルする (ESP-IDF 非依存、display_backend.h の C 部分だけ見る)。
- カラーキーは「帯の生成規則」ごと持ち込むこと (canvas 作成時の
  `[c<<k, (c<<k)|mask]`)。この規則の帯なら 8bit 展開方式の差は現れない。
- 音は audio_backend_t の 4 点を WebAudio で埋めれば audio_p4_task.c は
  そのまま動く。
- CPU 出力 (pushRotateZoom) は P4 で約 15 倍遅い。wasm では present が
  Canvas 転送に変わるので数字はそのまま持ち込まれないが、P4 の CPU
  ビルドを常用する案の撤退線判断にはこの数字を使う。
