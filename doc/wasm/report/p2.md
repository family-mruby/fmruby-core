# P2 報告: task_hal の自己プリエンプション化

2026-08-29 実施。指示書は instruction_p2.md。

結論: **通った**。`FMRB_TASK_SELF_TICK=1` で mruby_tick タスク無しの構成が成立し、
タイムスライスは従来と同じ 50ms、`sleep_ms` の精度も従来と同じ。既定ビルドは
従来どおり (追加コードは 1 行もコンパイルされない)。

ただし**指示書の設計だけでは動かなかった**。VM のバイトコード境界に hook を
足すのは必要条件であって十分条件ではなく、穴が 2 つあった (どちらも原因まで
追い切って修正し、それぞれ専用の検査項目を残した)。Tab5 実機の回帰も
2026-08-29 に完了し、受け入れ条件は 4/4 (下記セクション 4)。

## 指示書との相違 (先に読むところ)

### 1. タイムスライスは 12ms ではなく 50ms

指示書は「4ms x 3 tick = 12ms を正とする」としているが、この木では
`MRB_TICK_UNIT=5` / `MRB_TIMESLICE_TICK_COUNT=10` が
`lib/add/family_mruby_*.rb` と `mruby_abi_defines.cmake` で上書きされており、
**実効値は 5ms x 10 = 50ms**。12ms は task_hal.h のフォールバック既定値。

実測でも従来ビルドが 50ms だったので、コードは値を直書きせず
`MRB_TICK_UNIT` / `MRB_TIMESLICE_TICK_COUNT` から導き、
**両モードが同じ `vm_apply_ticks()` を通る**ようにした。定数が変わっても
自動的に同値になる。

### 2. hook だけでは足りない: 穴が 2 つ

指示書は「vm.c の境界で自給する」だけを求めているが、それだけでは
**アプリがまったく動かない**。

#### 穴 A: アイドル中の VM は tick を作れない

自給の tick 源は VM の実行そのものなので、全タスクが眠っている VM は
バイトコードを 1 つも実行せず、tick を作れない。結果、`sleep_ms` したタスクが
**二度と起きない**。

わざと修正を外したビルドで再現確認済み: `task_sleep` が 45 秒待っても
round 1 すら出ない。

対処: スケジューラ側 (`task.c` `task_run_body` のループ先頭と、
`mrb_hal_task_idle_cpu` の待機後) からも tick を供給する。
どちらも同じ実時間換算を通るので二重計上にはならない。

#### 穴 B: 起こされたタスクが 1 巡遅れる

穴 A を塞いだ直後、`sleep_ms(100)` x10 が **1000ms のはずが 1500ms** になった。
`_spin` の待ち時間を 5ms にすると 105ms/回になったので、遅れは
**アプリのメインループ 1 周分**と分かった。

両ビルドの**同じ地点** (`mrb_hal_task_take_pending_ticks`) にトレースを入れて
比べたところ、既定ビルドにはスケジューラのパスが 1 周期あたり 1 回多い。
原因は:

> **`mrb->task.switching` は「そのタスクが走っている最中」に書かないと意味が
> ない。** `execute_task()` (task.c:435) がタスクに CPU を渡すたびに
> `switching_ = FALSE` で消すため、スケジューラ側から書いた要求は
> 100% 捨てられる。

従来方式はこの条件を「別スレッドの top-half が走行中に非同期で書く」ことで
満たしていた。自給方式で同じにするには、**要求を立てる**のと**配達する**のを
分ける必要がある。

対処:

- `vm_apply_ticks()` はタイムスライスが尽きたら `vm->switch_pending` を立てるだけ。
- `vm_deliver_switch()` が `mrb->task.switching` に書く。呼ばれるのは
  **VM のスレッドでタスクが走っている文脈だけ** (top-half / vm.c の hook)。
- vm.c 側の間引き計数は **mrb_vm_exec に入った直後の 1 命令目で必ず 1 回
  発火する** ようにした (`TASK_SELF_TICK_DECL` の初期値が 1、発火後は
  interval で再装填)。タスクが再開した最初の境界が、top-half の非同期書き込みと
  等価な瞬間になる。

これで `sleep_ms(100)` x10 = **999ms**、従来ビルドと同じ。

## 実装

### hook 地点

- `lib/patch/picoruby-mruby/lib/mruby/src/vm.c` (mruby f56d44ec の全文コピー、
  **加筆のみ 4 箇所**、すべて `fmrb: self-supplied timeslice` の目印つき):
  1. `RETURN_IF_TASK_STOPPED` の直前にマクロ群 (vm.c:1665 付近)
  2. `RETURN_IF_TASK_STOPPED` の本体に `TASK_SELF_TICK(mrb);` を 1 行
  3. `mrb_vm_exec` の局所変数に間引き計数
  4. `RETRY_TRY_BLOCK:` の直後で計数を再初期化 (MRB_CATCH の longjmp 後に
     不定値を読まないため。catch 経路はここへ戻る 1 本だけ)

  未定義時は**全部が空に展開され、局所変数も宣言されない**。

- `lib/patch/.../mruby-task/ports/freertos/task_hal.c`: 自給の本体、
  top-half の条件コンパイル、`switch_pending` の追加。
- `lib/patch/.../mruby-task/src/task.c`: スケジューラのループ先頭で
  `mrb_hal_task_account_ticks()`。

`task_hal.c` は `fmrb_hal_time.h` を include できた (この component は
`fmrb_hal` を PRIV_REQUIRES しており、include path の追加は不要だった)。

### 上流提案の余地

vm.c の差分は実質 1 行 (`RETURN_IF_TASK_STOPPED` の先頭にマクロを 1 つ) で、
残りはそのマクロの定義と局所変数。**上流に「バイトコード境界フック」を
マクロ 1 個で差せる形**にして提案する余地はある。前例 (tick 破損修正が
mruby 本体に入っている) もあるので、wasm が形になった段階で
`MRB_VM_OP_HOOK(mrb)` のような名前で持ち込むのが自然。

### フラグ

`FMRB_TASK_SELF_TICK=1` の環境変数 1 個。既定は未設定 = 従来どおり。

- Rakefile の `ENGINE_ENV_OPTS` でコンテナへ渡す (FMRB_GC_PROFILE と同じ形)。
- rake 側 (vm.c を焼く): `lib/add/family_mruby_{linux,esp32,esp32p4}.rb`
- CMake 側 (task_hal.c を焼く): `components/picoruby-esp32/CMakeLists.txt`

ABI 定義ではない (構造体は変わらない) ので `mruby_abi_defines.cmake` には
入れていないが、**両側が一致していないと壊れる**のは同じ。片肺の壊れ方は
非対称で、vm.c 側だけ無ければ tick が誰も作らない (無言)、task_hal.c 側だけ
無ければ `mrb_hal_task_self_tick` 未定義でリンクが落ちる (騒がしい)。
両方が同じ環境変数を読むので、実際には食い違わない。

**`lib/` を触るので、切り替え時は必ず `rake clean`**。CMake の
`add_custom_command(OUTPUT libmruby.a)` はソースに依存していないため、
clean しないと ninja が picoruby の rake を再実行せず、vm.c の変更が
**黙って反映されない** (実際に一度踏んだ: vm.c は新しいのに vm.o が古いまま
ビルドが成功した)。

## 間引き計数の値と根拠

`MRB_TASK_SELF_TICK_INTERVAL = 65536` (vm.c 内、`#ifndef` で上書き可)。

Linux sim で 1000 万回の Ruby ループ (`acc = acc + i; i = i + 1`、約 6000 万
バイトコード) を 15 回測り、中央値で比較した。sim は素の x86 なので VM が速く
(約 3 億バイトコード/秒)、hook のコストが最も厳しく出る条件。

| 構成 | 中央値 | 最小 | 既定比 |
|---|---|---|---|
| 既定 (top-half) | 215ms | 201ms | — |
| 自給 N=65536 | 224ms | 207ms | **+4%** |
| 自給 N=8192 | 262ms | 241ms | +22% |
| 自給 N=1048576 (hook がほぼ発火しない) | 188ms | 185ms | **-13%** |
| 自給 N=1 (バグ。全命令で HAL 呼び出し) | 約 48000ms | — | 約 220 倍 |

読み取れること:

- **1 命令ごとの計数 (デクリメント + 分岐) はほぼタダ**。N を極大にした
  188ms が既定の 215ms より**速い**。5ms 周期で起きる mruby_tick タスク
  そのものの費用 (コンテキストスイッチ 200 回/秒) が消えるほうが大きい。
- **コストは HAL 呼び出しの頻度で決まる**。N=8192 と N=1048576 の差は
  約 7300 回の呼び出しで 75ms、すなわち **1 回あたり約 10 マイクロ秒**。
  中身は `fmrb_hal_time_get_us()` (数十ナノ秒) ではなく
  `xSemaphoreTake/Give`。Linux の FreeRTOS POSIX port は critical section が
  `pthread_sigmask` (システムコール) なので、無競合でも高い。
- したがって **N を下げるより、HAL 呼び出しを安くするほうが効く**。
  自給モードでは 1 つの VM のエントリに触るのはその VM 自身のスレッドだけ
  (top-half が居ない) なので、原理的には mutex を外せる。今回はやっていない
  (P2 の範囲を超える) が、ESP32 で自給に一本化するなら先にこれをやるべき。

N=65536 の検出遅れ (= CPU を握ったタスクが剥がされるまでの上限):

| | バイトコード/秒 (概算) | 65536 命令 = |
|---|---|---|
| Linux sim (x86) | 3 億 | 0.22ms |
| wasm (推定) | 数千万 | 1〜2ms |
| ESP32 | 数百万 | 15〜30ms |

50ms のタイムスライスに対して sim と wasm は誤差、**ESP32 だけは粗い**。
ESP32 は当面 top-half のままなので実害は無いが、一本化するなら
上記の mutex 除去とセットで N を下げること。

**選び方を間違えても tick は失われない**。HAL は実時間の経過を換算し、
余りを繰り越すので、遅れて呼ばれた分はまとめて計上される。影響するのは
「剥がすのがどれだけ遅れるか」だけ。

## タイムスライス実測 (両モード)

`flash/app/test/slice_probe.app.rb`: 同一 VM 内の CPU 占有 Task 2 本が、
自分の連続実行が途切れた幅を 30 回測る。中央値がタイムスライス。

| 構成 | A | B |
|---|---|---|
| 既定 (top-half) | min=50 med=100 max=100 | min=3 med=100 max=100 |
| 自給 (N=65536) | min=49 med=99 max=199 | min=49 med=50 max=51 |

med が 100 になるのは「相手 + アプリ本体のメインループ」の 2 枠を待った回で、
50 が 1 枠。**両モードとも 1 枠 = 50ms** で、指示書の受け入れ条件
「従来と同等」を満たす。自給側のほうがばらつきが小さい (tick を実時間から
直接読むため、別タスクのスケジューリング揺れが乗らない)。

すべて Linux sim、**標準構成** (`.env` のとおり Spinel カーネル + Spinel

### 1. 既定ビルドの回帰

- ブート、デスクトップ描画、エディタ起動、打鍵 (`default ok` を入力) 正常。
- `task_sleep` = 10 x 100ms が **999ms**。
- crash マーカー (`Guru|abort|assert`) **0 件**。

### 2. 自給ビルド + busy-loop アプリ

`flash/app/test/spin_hog.app.rb` (20 秒間 `on_update` から戻らない) を起動した

### 4. ESP32 実機 (Tab5) — 実施済み (2026-08-29、主セッションが実施)

既定ビルドであることを ELF で確認してから焼いた (`mruby_tick_task` シンボル
あり / self_tick 系シンボル無し / compile_commands.json に
MRB_TASK_SELF_TICK 無し)。

- flash 成功、ブート完走。crash マーカー (Guru / abort) **0 件**。rst は
  `0x17 CHIP_USB_UART_RESET` (ポートを開いた際の既知のリブート) のみ。
- `M1|` スナップショットと `fmrb_task:` 周期ダンプは従来どおり
  (system_desktop の stack 残 6.7KB、IRAM free 136KB)。
- デスクトップ表示、エディタの遠隔起動 (`default/editor`) と打鍵
  (`p2 ok` が入力され Ln 1, Col 6)、アプリのパス起動を確認。
- `task_sleep` を実機で実行: 10 x 100ms = **1050ms**。エディタ起動が
  重なった 1 巡だけ +143ms で、残りはすべて +100〜101ms。穴 A (起きない) /
  穴 B (毎回 +50ms) の兆候なし。

#### 回帰とは別に、遠隔 kill でハングを 1 回踏んだ (P2 起因ではない)

検証後にエディタを `/app/kill` で終了させたところ、
`Exited on request, reaping` → `STOPPING -> FREE` の**直後に**シリアル出力と
WiFi が完全に停止した (10 秒周期ダンプが 90 秒以上沈黙)。ポート開き直しの
リセットで復旧。再起動後に同じ操作 (default/editor 起動 → 遠隔 kill) を
繰り返すと正常に完走し、**再現しない**。

- 焼いた既定ビルドに P2 のコードは 1 行も入っていない (上記のシンボル確認 +
  task.c の追加が `#ifdef MRB_TASK_TICK_SELF_SUPPLY` 内であることを diff で
  確認) ので、P2 の回帰ではない。
- 1 回目に固有だった条件: Task Sleep アプリが並走、エディタに未保存バッファ、
  kill 要求のタイムアウト後再送の可能性 (要求から stop 配達まで約 20 秒)。
  既知の kill 経路の問題 (doc/archive/app_kill_fix) と同族の race とみられる。
  アプリ自体は正当に exit しているので、reap 後の killer/リーパ側で何かを
  保持したまま止まった形。

ESP32 の**ビルドが通ること**は別途確認した: `rake clean_all` → `rake build:esp32`
(FMRB_HW_TARGET=TAB5 = esp32p4、Spinel カーネル + Spinel エディタ) が成功し、
RISC-V の ELF と `fmruby-core.bin` 0x58ed10 バイト (app 区画の 7% 空き) が
出ている。**ツリーは esp32 ビルドの状態のままにしてある** (P3 が Tab5 実機の
リファクタなので、そのまま使えるほうがよいというユーザの判断)。sim 作業を
先にやるときだけ `rake clean_all` → `rake build:linux`。

## ESP32 で自給に一本化できそうか (implementation_plan の宿題)

**現状のままでは薦めない。2 つ直してから。**

1. **HAL 呼び出しが高い** (上記)。ESP32 の FreeRTOS mutex は Linux port より
   安いはずだが、VM が遅いぶん N を下げる必要があり、頻度は上がる。
   自給モードでは 1 VM のエントリに触るのはその VM のスレッドだけなので、
   mutex を外す (またはスレッドローカルにエントリを持つ) のが先。
2. **検出遅れが粗い** (N=65536 で 15〜30ms)。1 と合わせて N を下げれば解決する。

一方で**一本化の利点は実測で確認できた**: 5ms 周期のタスクが 1 本消えるので、
VM 速度は素の状態で 13% 速い (188ms vs 215ms)。ESP32 は単核/双核の事情が
あるので、実機で `fmrb_task:` と入力遅延 (`spx: hid_lat`) を測ってから判断する。

## 気づき (P2 の範囲外)

- **`bind()` に EINTR リトライが無い**
  (`main/drivers/debug/fmrb_debug_transport_tcp.c:56`)。sim の起動で 1 回
  `bind(:5555) failed: Interrupted system call` を踏み、debugd が上がらなかった
  (再起動で復旧)。同じファイルの accept (:115) には EINTR 処理があるので、
  抜けているだけに見える。SIGALRM に依存する Linux port 固有の症状で、
  wasm port では消える種類の問題。1 行で直せる。
- **`fmrb_app_kill` の強制経路**。壊れた中間ビルド (VM が 90 倍遅かった版) で
  spin_hog を kill したとき「No response in 1000ms, forcing termination」に入り、
  そのあと debugd が応答しなくなった。**最終版では同じ操作が正常に完了する**
  ので P2 の回帰ではないが、「1000ms 以内に応答できないアプリ」を kill すると
  debugd ごと巻き込む経路が実在することの再確認にはなる
  (doc/archive/app_kill_fix と同根)。
- **Spinel プログラムには自給が効かない**。標準構成のカーネルとエディタは
  Spinel AOT で、mruby の dispatch loop を通らないので
  `RETURN_IF_TASK_STOPPED` が無い。スケジューラ側の
  `mrb_hal_task_account_ticks()` で**時計は進む**が、CPU を握った Spinel
  プログラムを**剥がす手段は無い**。しかも wasm では `SP_NO_MMAN` で
  `sp_fiber.c` / `sp_sched.c` を外す計画 (plan.md) なので、Spinel 側の
  ファイバスケジューラも無くなる。**P4a で確認すべき穴**。
