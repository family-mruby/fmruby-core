### vendor に何を入れたか

指示書は「tasks.c / queue.c / list.c / stream_buffer.c + include」だったが、
それだけでは**タスクを 1 本も作れない**。IDF はカーネルを改造していて、
`xTaskCreate` / `xTaskCreatePinnedToCore` / `xTaskCreateStatic*` と
`vTaskSetThreadLocalStoragePointerAndDelCallback` の実体が tasks.c ではなく
esp_additions/freertos_tasks_c_additions.h にあり、tasks.c が
`configINCLUDE_FREERTOS_TASK_C_ADDITIONS_H` 経由で取り込む形になっている。
そこで以下も vendor した (いずれも改変なし)。

- freertos_tasks_c_additions.h
- include/freertos/idf_additions.h
- include/esp_private/freertos_idf_additions_priv.h
- include/esp_private/freertos_debug.h

timers.c と event_groups.c は削った (plan.md の棚卸しどおり使用ゼロ)。
ヘッダは event_groups.h / timers.h だけ残してある (FreeRTOS.h からの参照用)。

## tick をいつ誰が進めるか (確定設計)

**追いつき方式。`prvCatchUpTicks()` が 1 箇所にまとまっていて、呼ぶのは 2 箇所だけ。**

- 基準は起動時刻 (`dTickBaseMs = emscripten_get_now()`)。
  「今までに何 tick 供給したか」(`ullTicksFed`) と「実時間から見て何 tick 経って
  いるべきか」の差を、**1 tick ずつ `xTaskIncrementTick()` を呼んで**埋める。
  カーネルの遅延リストは 1 tick ずつしか進められないので、飛ばすことはしない。
  基準が実時間なので、長い CPU 占有の後もまとめて追いつき、**恒久的なずれには
  ならない**。
- 呼ぶ場所:
  1. `vPortYield()` の入口 (critical section に入る前)。ブロックしようとしている
     タスクが最新の tick を見られる。
  2. **アイドルフック** (`esp_vApplicationIdleHook`)。1ms 寝てから追いつく。
     全タスクがブロック中のとき tick を進めるのはここだけ。
     `xTaskIncrementTick()` が切替を要求したらフックの中から `taskYIELD()` する。
- `uxCriticalNesting != 0` のときは何もしない。実機で「割り込み禁止中に tick 割り込みは
  来ない」のと同じ規則にした。

実測: 10 秒間の tick と実時間のずれは **0.2〜1.2ms** (5 回とも)。
1 回の追いつきで進めた最大 tick 数は **150〜151** (テスト 8 の 150ms 空回しの直後)。

### 捨てた案

- **configUSE_IDLE_HOOK=1 を使う**: IDF の tasks.c は `configUSE_IDLE_HOOK` と
  無関係に `esp_vApplicationIdleHook()` を必ず呼ぶ。両方定義するとフックが 2 個に
  なるので、`configUSE_IDLE_HOOK=0` にして IDF 側のフックだけを実装した。
- **`traceTASK_DELAY()` で `vTaskDelay` の直前に追いつく**: この trace は
  `vTaskSuspendAll()` の内側にあり、そこで `xTaskIncrementTick()` を呼んでも
  `xPendedTicks` に積まれるだけ。`xTaskResumeAll()` で適用されるのは遅延リストに
  入った**後**なので、精度は 1mm も上がらない。採らなかった。
- **configUSE_TICKLESS_IDLE**: 複雑化するだけなので使っていない (指示どおり)。

## vPortCancelThread (他殺) — 指示から変えた点

**指示は「ログ + no-op」だったが、正しく実装できたので実装した。**
pthread_cancel は使っていない。

このポートでは**走っていないタスクのスレッドは必ず `prvSuspendSelf()` の
`event_wait()` で寝ている**。そこを利用して、`vPortCleanUpTCB()` が

1. TLS 削除コールバックを回し、
2. 相手の `xDying` を立てて event を signal し、
3. `pthread_join()` で回収する

という手順を踏む。起こされたスレッドは `event_wait()` から戻った直後に `xDying` を
見て `pthread_exit()` するだけで、カーネルの状態には一切触れない。join を
`prvDeleteTCB()` がスタックを解放する前に完了させるので、スタック上に置いた
Thread_t と event を踏まない。

自殺 (`vTaskDelete(NULL)`) の場合は従来どおり `prvSwitchThread()` 内で
`pthread_exit()` するので、上の join は取りこぼしの回収になる。

新設経路なので PoC に専用の項目 (`delete_other_task`) を入れてある。
永久ブロック中のタスクを外から消し、タスク数が減ること・削除コールバックが
1 回だけ走ること・**消した側が join で固まらないこと**を見る。

これは `fmrb_app_kill` の最後の手段 (doc/archive/app_kill_fix) が wasm でも
使える見込みが立った、ということでもある。ただし P2 の自己プリエンプションが
無いと「消したい相手が CPU を握ったまま」の状態には手が出せないので、
P2 が不要になったわけではない。

## タスクスタックの扱い (P4a に効く)

タスクは**カーネルが確保したスタックでは動かない**。Emscripten の pthread が
自前で確保したスタックで動く。カーネルのブロックは、POSIX port と同じく
このポートの per-task 構造体 (Thread_t) を置く場所としてしか使っていない。

- `pthread_attr_setstacksize()` に渡す値は `xTaskCreate` の指定値。ただし
  **下限 64KB** (`portWASM_MIN_TASK_STACK_BYTES`) を入れた。実機のスタック値は
  Xtensa/RISC-V のフレーム前提で 2KB (mruby_tick) まで下がるものがあり、
  同じ C コードを wasm にすると足りない。Emscripten の既定も 64KB。
- `portSTACK_TYPE` は **uint8_t** にした (IDF と同じ)。つまりスタック指定はバイト。
  上流 POSIX port は `unsigned long` で、Linux sim では指定値が黙って 8 倍に
  なっている。その癖は持ち込まない。
- 副作用: `uxTaskGetStackHighWaterMark()` は**意味を持たない** (誰も書かない
  ブロックを見るので常に「未使用」を返す)。`configCHECK_FOR_STACK_OVERFLOW` も
  同じ理由で 0。実機ログの `fmrb_task:` の Free 列は wasm では読めない。
  本当のスタック溢れは Emscripten 側 (`-sSTACK_OVERFLOW_CHECK`) で捕まえる。
- カーネルのスタックブロックは丸ごと無駄になる。P4a の 25 本 x 8-16KB で
  300KB 程度。ブラウザなら許容範囲だが、気になれば wasm 専用の生成経路で
  縮められる。

## pthread pool 枯渇の実測

`-sPTHREAD_POOL_SIZE=32` に対して**40 本**のタスクを作り、1 本ごとの
`xTaskCreate` の所要時間を測った。

- pool 32: 40 本すべて成功。最遅の 1 本で **0.6〜1.3ms**。
- pool **4**: 同じく 40 本すべて成功。最遅 **0.8ms**。

つまり **node では pool を使い切っても目立った代償が無い**。Worker はその場で
作られ、作成側が待たされることは実質なかった。`-sPROXY_TO_PTHREAD` で main が
Worker 側にいるため、Worker 生成を捌くブラウザ/node のメインスレッドが常に空いて
いるのが効いていると思われる。

**注意**: これは node での実測。ブラウザでの挙動は P4b で確認するまで未知とする。
pool サイズは CMake のキャッシュ変数 `WASM_PTHREAD_POOL_SIZE` にしてあるので、
`-DWASM_PTHREAD_POOL_SIZE=4` で追試できる。

## vTaskDelay の精度 (実測)

| 項目 | 実測 (5 回) | 判定幅 |
|---|---|---|
| `vTaskDelay(100ms)` 1 回 | 99.1〜100.4ms | 95〜115 |
| `vTaskDelay(20ms)` 10 回 | 198.8〜200.0ms | 195〜230 |
| キュー受信タイムアウト 50ms | 49.1〜49.3ms | 45〜70 |
| notify タイムアウト 60ms | 59.8〜60.6ms | 55〜80 |
| ブロック解除 (キュー満杯 / セマフォ / MessageBuffer) | 38.7〜40.1ms (相手は 40ms 待ち) | 35〜70 |
| notify give → 相手が起きるまで | 0.1ms | <10 |

指示の「±10ms 程度」より一桁良い。誤差が積み上がらないのは、tick が実時間基準の
追いつきで、ブロック直前に必ず最新化されるため。

## 協調の限界 (仕様として明記)

PoC の `cooperative_holdoff` / `cooperative_release` が、この port の性格を
そのまま検査項目にしてある。

- 低優先度タスクが 150ms 空回ししている間、**上位タスクの 20ms の
  `vTaskDelay` は 150.1〜150.2ms かかる**。tick が進まないので当然。
- その空回しタスクが `taskYIELD()` した瞬間、上位は **0.1ms** で走る。

これが P2 (task_hal の自己プリエンプション化) が必須である理由の実測値。

## stub したもの一覧 (P4a の stub/ 設計の入力)

wasm/stub/include/ に置いた最小ヘッダ:

| ファイル | 中身 |
|---|---|
| `sdkconfig.h` | カーネルと esp_additions が読む CONFIG_* だけ (13 個) |
| `esp_assert.h` | `ESP_STATIC_ASSERT` |
| `esp_compiler.h` | `likely` / `unlikely` / `ESP_STATIC_ANALYZER_CHECK` |
| `esp_heap_caps.h` | `MALLOC_CAP_*` と heap_caps_malloc/calloc/free/get_free_size |

実装は wasm/stub/heap_wasm.c 1 本 (pvPortMalloc / vPortFree / pvPortCalloc /
xPortGetFreeHeapSize / xPortGetMinimumEverFreeHeapSize と heap_caps_*)。
wasm の線形メモリは 1 つなので capability は全部同じ malloc に落ちる。
"free" は 64MB の予算からの残りという建前の数字 (M1| 相当のログを P4a で出す
ときに比較可能な値が要るため)。

portmacro.h 側で潰した IDF マクロ: `portMUX_TYPE` (int)、`portGET_CORE_ID`、
`xPortInIsrContext` / `portCHECK_IF_IN_ISR` / `portASSERT_IF_IN_ISR`、
`portVALID_{LIST,TCB,STACK}_MEM`。

**sdkconfig.h の罠**: IDF のソースには `#ifdef CONFIG_FREERTOS_SMP` で分岐する
箇所がある。無効な設定を `#define ... 0` と書くと**有効扱いになる**。
無効なものは定義しない、が正しい。最初これで SMP 分岐を踏んで
コンパイルエラーになった。

## 指示から変えた点 (まとめ)

1. **vendor の範囲**: esp_additions の 4 ファイルを追加 (上記「vendor に何を入れたか」)。
2. **vPortCancelThread**: no-op ではなく実装した (上記)。
3. **`configUSE_IDLE_HOOK`**: 1 ではなく 0。IDF 側のフックを使う (上記)。
4. **mutex の所有者テスト**: 指示は「非所有者の give が失敗する」だったが、
   IDF の `configCHECK_MUTEX_GIVEN_BY_OWNER` は**失敗を返さず assert で落とす**
   (IDF 自身のテストが「panic して再起動すること」を確認している)。
   PoC でそれをやると process ごと死ぬので、代わりに所有者記録そのものを見る
   3 項目にした: `xSemaphoreGetMutexHolder` が所有者を返すこと、非所有者の take が
   タイムアウトすること、**優先度継承が起きて give で戻ること** (11 → 継承 → 10)。
5. **`vTaskDelete(other)` の項目を追加** (2 の裏取り)。

## P4a に向けた懸念

- **`fmrb_task:` の周期ダンプが片肺になる**。スタック high-water が測れない
  (上記)。wasm では別の指標 (pthread スタックサイズと Emscripten の
  STACK_OVERFLOW_CHECK) に置き換えるか、この行を出さない判断が要る。
- **スタック下限 64KB は仮の値**。mruby VM / Spinel / prism を載せると
  実測が要る。特に prism は再帰が深く、rakelib/ti.rake が既に 1MB を積んでいる。
  P4a では `.app.toml` の `task_stack_kb` を wasm 向けに読み替える仕組みが要るかも
  しれない。
- **fmrb_midi_sched.c の critical section が無意味になる**。このポートの
  `portMUX_TYPE` は何も守らない (守るものが無い) が、MIDI の 1ms 精度は
  そもそも初期スコープ外なので P4a では問題にならない見込み。
- **`*FromISR` 系が素通り**。ISR が無いので実害は無いはずだが、
  「ISR から呼んだつもり」のコードが混ざったときに黙って通る。
  plan.md の棚卸しでは使用ゼロなので、P4a で新たに現れたら疑う。
- **ブラウザ未確認**。P1 は node のみ (`-sENVIRONMENT=node`)。
  pool 枯渇・`emscripten_thread_sleep` の 1ms 精度・`pthread_cond_wait` の挙動は
  いずれもブラウザで測り直す (P4b)。
- **アイドルの 1ms sleep が常時回る**。node では実測で 10 秒あたり
  約 2 万回の追いつき呼び出し。ブラウザでの電力・CPU 負荷は P4b で見る。
