# 報告: ページ側のテーマ選択を外した

> 状態: 完了 | 更新: 2026-09-03 | 色は Config だけが決める。壁紙の staging も
> 一緒に消した (デスクトップが同じ仕事をもっと正しくやっていた)

ユーザ報告 (2026-09-03):「WASM の HTML からのテーマ選択、設定しても反映して
ない。OS の Config から設定できるのでそれでいい」。

## なぜ効かなかったか

**選んだ直後に、自分で捨てた設定を自分で書き戻していた。**

セレクタの手順はこうだった。

1. 選んだ preset を localStorage に保存
2. **Config が保存した [theme] の 9 色を捨てる** (残すと起動時に preset の上へ
   乗って何も起きないため。コードにそう書いてあった)
3. `location.reload()`

3 の reload が **`pagehide` を起こす**。そこに繋がっている
`captureConfSettings()` が、**まだ動いている機械の system_conf.toml から
9 色を読み直して保存し直す**。2 で捨てた物が同じ瞬間に戻ってくるので、
次の起動でまた preset の上に乗る。**見た目は「何も起きない」**。

Erase で踏んだのと同じ穴で、あちらは `erasing` フラグで塞いであった
(report/storage_t3_t4.md)。テーマ側には入れていなかった。

## 直さずに外した

塞ぐのは 1 行だが、外す方を選んだ。

- **Config の方が能力が上**。light / dark / cyberpunk の 3 つに対し、ページは
  light / cyberpunk の 2 つで **dark が選べない**。
- **1 つの設定に入口が 2 つあると、優先順位の規則が要る**。その規則を説明する
  ために About を 1 項目使っていた。今回の穴もその規則の実装から出た。
- ページ側にしかできないことが無い。「起動前に選べる」は利点だが、一度選べば
  済む話である。

外したもの: `<select>`、`?theme=`、`--fmrb-theme=light`、`LIGHT_THEME` の表、
`s_light`、tar の設定に載せていた `theme`、About の説明。

## 壁紙の staging も消えた

`s_light` を追ったら、**同じ仕事が 2 か所にあった**ことが分かった。

`page_settings_wasm.c` は起動時に、テーマと解像度から
`bg_[cyber_]WxH.png` を選んで `/flash/data/` へ写していた。ところが
`system_desktop.app.rb` の `theme_wallpaper` + `resolve_wallpaper` が、
**起動直後に同じ選び方で同じ場所へ写す**。

デスクトップ側の方が正確である。

| | C 側 (消した) | デスクトップ側 (残る) |
|---|---|---|
| テーマ | ページで light を選んだか | **実際の色から判定** (`cfg_current_preset`) |
| 大きさ | 引数の値 | **実際の窓の寸法** |
| Config で変えたとき | 追随しない | 追随する |

しかも `sync_file` は中身が同じなら転送しないので、二重にやっても無駄が乗る
だけだった。**C 側は、数百 ms 後に上書きされる物を先に置いていた**。

`copy_file` の使い手が居なくなったので一緒に消え、
page_settings_wasm.c は 207 行から 140 行になった。

## 確かめたこと

- `gcc -fsyntax-only -Wall -Wextra` で警告ゼロ (未使用の残骸が無いこと)。
- ブラウザ版を焼き直して起動。**Config でテーマを light → cyberpunk に変えて
  保存 → リロードで、色も壁紙もネオン版に変わった**。C 側の staging 無しで
  デスクトップが正しい壁紙を置いていることの実証。
- テーマは**起動時に読む**ので、Config の保存はその場では見た目が変わらない
  (wasm の Config に再起動ボタンは無い)。ページを読み込み直して反映される。
- **最初の 1 フレームで梱包の既定壁紙が見えるか**は、1 コマ単位で撮って
  いないので確言できない。撮った範囲では見えていない。
