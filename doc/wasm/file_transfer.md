# wasm へのファイルの持ち込み (設計と段取り)

> 状態: 実装済 (確認待ち) | 更新: 2026-09-03 | 任意のファイルを /home に置く道を作る。
> 素の入口 (放り込み) を土台にし、Chromium ではフォルダを結び付けて
> 「PC で編集 → ブラウザで実行」の輪を回す

タブの中の機械に、PC にあるファイルを渡したい。今は tar に包む以外の道が無い。

方式選びの前に押さえるべき事実が 1 つある。**OPFS は保存先であって取り込み口
ではない**。どの保存方式を採っても、PC のファイルを持ち込む口は別に要る
(次章)。したがってこの文書は、保存方式ではなく**入口**の設計である。

## 今できること・できないこと

実装を読んで確かめた (2026-09-03)。

| | 状態 |
|---|---|
| 持続する場所 | **`/flash/home` と `/flash/app/usr` の 2 つだけ**。IDBFS が載っている (main.js の `STORES`) |
| それ以外のパス | MEMFS。書けるがリロードで消える。**持ち込み先にしてはいけない** |
| ページの取り込み | `.tar` のみ (`index.html` の `accept=".tar"`)。1 個のファイルを渡す道が無い |
| ページの書き出し | 2 つの store を丸ごと tar にして download |
| 任意ファイルの書き込み | **既にある**。`?drive=1` の relay の `fs put` (main.js)。`mkdirTree` → `writeFile` → `flushHome()` の 4 行。動作実績あり |

つまり**書き込みの仕組みは完成していて、普通の訪問者から呼ぶ道が無いだけ**。
新しく作るのは入口であって、下回りではない。

## OPFS を採らない

Origin Private File System は IndexedDB の代わりに置ける保存先で、確かに
速くて大きなファイルに強い。ただし**この件は 1 ミリも進まない**。PC の
ファイルを origin の中へ運ぶには、結局ファイル選択かフォルダ結び付けか
放り込みが要る。OPFS はその先の置き場所の話である。

代償は小さくない。Emscripten で OPFS を使うには **WASMFS (`-sWASMFS`) への
切り替え**が要り、OPFS の同期アクセスは専用のワーカーからしか触れないので、
今の proxy 構成に手が入る。

**採るとしたら別の理由 (IDBFS の syncfs が実測で遅い) が出てから**。
入口を作る話とは切り離す。

## File System Access API で実際に何ができるか

対応ブラウザを絞ってよいなら、これがこの企画の中心になる。

### 入口は 3 つ

| 呼び出し | 返るもの | 用途 |
|---|---|---|
| `showOpenFilePicker({multiple:true})` | ファイルの handle の配列 | 選んで取り込む |
| `showSaveFilePicker({suggestedName})` | ファイルの handle | 名前を付けて書き出す。**同じファイルに上書きし続けられる** |
| `showDirectoryPicker({mode:'readwrite'})` | フォルダの handle | **本命。フォルダごと読み書きする** |

いずれも **HTTPS 必須**で、**利用者の操作 (クリック) の中からしか呼べない**。
公開先は https なので前者は満たしている。

### handle で何ができるか

- 読む: `await handle.getFile()` で `File` が返る。`arrayBuffer()` で中身、
  **`lastModified` が更新の唯一の手がかり**
- 書く: `await handle.createWritable()` → `write()` → `close()`。
  **一時ファイルに書いて close で入れ替わる**ので、途中で失敗しても
  元のファイルが壊れない
- フォルダを歩く: `for await (const [name, h] of dir.entries())`。
  `getFileHandle(name, {create:true})` で作り、`removeEntry(name, {recursive})` で消す

### 覚えていられる

**handle は構造化複製できるので IndexedDB に保存できる。** これが効く。
次に来たとき、フォルダを選び直させずに済む。ただし許可は残らないので
`queryPermission()` は `prompt` を返し、`requestPermission()` を
**クリックの中から**呼ぶ必要がある。**選び直しではなくクリック 1 回**、
という差になる。

(ページを PWA として入れた場合だけ許可が残る仕組みが Chrome にある。
この 1 回すら消せる可能性があるが、未検証。**F4 で確かめる**。)

### 見張れない

**変更を知らせる仕組みが無い。** 監視の口が無いので、`getFile()` して
`lastModified` を見比べる形になる。数十個のファイルを 1-2 秒おきに見る程度なら
問題にならないが、**フォルダ全体を無条件に歩くのは避ける** (深さと数の上限を
決める)。

### どのブラウザか

**デスクトップの Chromium 系だけ** (Chrome / Edge)。Firefox と Safari は
入口 3 つとも未実装で、スマホの Chrome も対応しない。Safari は OPFS には
対応しているが、それは前章のとおり別の話。

**だから F1 (放り込み) を土台に置く。** 全ブラウザで最低限が成立した上に、
Chromium だけ F2 以降が乗る形にする。

## 設計

### F1: 放り込みと選択 (全ブラウザ)

- 画面にファイルを落としたら `/flash/home/<名前>` に置く。
  `accept` を外した `<input type="file" multiple>` のボタンも並べる
- 中身は relay の `fs put` と同じ (`writeFile` + `flushHome()`)
- **`.tar` だけは今までどおり復元として扱う**。それ以外は素のコピー。
  拡張子で分ければ利用者は意識しなくてよい
- 名前は tar 取り込みと同じ規則で組み立て直す (**2 つの store の外に出さない**)

**行き先は推測せず選ばせる。** 前提として**持続する場所は 2 つしかない**ので、
選択肢は小さい。

```
Add files: [Choose files...]  to  [/home/inbox |v]   (drop them anywhere on the page)
```

既定は **`/home/inbox`**。外から来て、まだ仕分けていないものが入る場所である。
`/home` 直下の実績 (`backgrounds`, `services`) にならって**中身を名指しする
名詞**にした。どう来たか (放り込み・選択・作業場) を名前で縛らないので、
F2/F3 で写したものが混じっても嘘にならない。

**中身を見て行き先を変えることはしない** — 単発のファイルは種類を問わず
ここへ入り、別の場所にしたいときは利用者が選ぶ。

**とくに .png を壁紙の置き場所へ自動で送らない** (2026-09-03 決定)。
落としただけで設定の候補に現れるのは、利用者が指示していない移動である。
壁紙にしたければ行き先で `/home/backgrounds` を選ぶか、あとで file manager
で移す。**選択肢に `/home` 直下の既存フォルダを並べる**ので、
`/home/backgrounds` は作ってあれば出る。

拡張子で黙って振り分ける案は採らない。1 つ賢くすると全部に規則が要り、
利用者は自分のファイルがどこへ行ったか読めなくなる。

**フォルダごと落とせる。** `webkitGetAsEntry()` と
`<input webkitdirectory>` は**どのブラウザでも構造ごと読める** (Chromium 限定
ではない)。`mygame/` を丸ごと落とせば、選択も推測もなしに素材ごと
`/app/usr/mygame/` に入る。**「アプリと絵を一式渡す」という一番多い形が、
F1 だけで全ブラウザで成立する**。

**アプリかどうかは `*.app.toml` で見る。** 投げたフォルダかその直下の子に
あれば `/app/usr/<名前>/`、無ければ `/home/<名前>/`。

ランチャー自身の判定は `.toml` で終わりだが (launcher.rb の `S_TOML`)、
**ここは同じ緩さにしてはいけない**。あちらは既に `/app` の中を歩いていて、
そこにあるものは構造上すべてアプリである。放り込みには文脈が無く、
利用者の PC のどのフォルダが来るか分からないので、設定やデータの `.toml` を
拾って素材の束をアプリ扱いしてしまう。梱包の実績も **`.app.toml` が 71 本に
対し例外は `flappy.toml` の 1 本だけ**で、規約は十分に固い。

外したときの傷も非対称である。`.app.toml` を要求して外すとアプリが `/home` に
入って**ランチャーに出ない** — 見えるので気づく。`.toml` で拾って外すと
**素材が `/app/usr` に紛れ込む** — 気づきにくく、以後ランチャーがそれを
走査する。判定は写す前に見せて押し戻せるようにするが、既定は前者に倒す。

### 持ち込むのはアプリだけではない

**むしろ素材の方が多い**。画像 (スプライト、タイル、壁紙)、音 (.nsf .fmsq
.mid)、地図 (.map.bin)、手本の .rb。設計に効く違いが 4 つある。

**1. 平らに置いてはいけない。** アプリは素材を**隣に置く**前提で書かれている
(梱包の `app/game/rpg_demo/` は .bmp と .rb が同じ場所にある)。作業場の
`mygame/` の中身は `/app/usr/mygame/` へ**構造ごと**写す。名前だけ見て
振り分けると、動くアプリの素材が迷子になる。

**2. 壁紙の置き場所は決まっている。** `cfg_scan_wallpapers` は
`/usr/share/backgrounds` と **`/home/backgrounds`** を走査して `.png` を拾う
(config_dialog.rb。2026-09-03 まではここが `/home` 直下だった)。
**そこへ入れれば Config の Wallpaper に並ぶ**ので、この用途は F1 だけで
完結する。ただし**送り込むのは利用者が行き先に選んだときだけ**で、
.png だから自動で、ということはしない。

**3. 素材に再走査は要らない。** ランチャーが見ているのは `.app.rb` /
`.app.toml` の名前だけ。素材を差し替えて**アプリを起動し直せば新しい絵が出る**。

**4. 大きさが 2 桁違う。** .rb は数 KB、画像は数十 KB から。追随で毎回
写さないよう `lastModified` の比較は必須で、**syncfs の実測が
「あとで測る」ではなく最初の関門になる** (末尾の未確定事項)。

なお BMP はパレットを見ずに画素を RGB332 として読む。**写真をそのまま
置いても意図した色にはならない**。持ち込みの不具合と紛らわしいので、
案内に一言要る。

### F2: フォルダを結び付ける (Chromium)

`showDirectoryPicker` で選んだフォルダを「作業場」とし、handle を
IndexedDB に覚える。次の訪問はクリック 1 回で戻る。

**行き先を選ぶ UI は要らない。置いた場所で決まる。** 作業場の直下は
tar と同じ 2 つの名前にする。

```
fmrb-apps/
  home/            -> /flash/home
  app-usr/
    mygame/        -> /flash/app/usr/mygame/
      mygame.app.rb
      mygame.app.toml
      player.bmp
```

`importTarget()` が既にこの前置きを解釈しているので、**同じ規則を使い回す**。
副産物として、**書き出した tar を展開すればそのまま作業場になる**。

### F3: PC → 機械の追随

作業場のファイルを 1-2 秒おきに見て、`lastModified` が進んでいたら
機械側へ写す。**これで「PC のエディタで直す → ブラウザで動かす」の輪が
閉じる** — 実機の `put → launch` と同じ形をブラウザに持ち込むことになる。

**画面に足すのは設定の帯の 1 行だけ。**

```
Your files (/home): persistent   [Download them] [Restore from a file] [Erase]
Work folder: fmrb-apps -- watching 12 files   [Stop] [Send my work back]
```

**輪を回している間、ページのボタンは 1 つも押さない。** 見えるのは
キャンバス上の状態行が一瞬変わることだけ。

```
copied hello.app.rb -> /app/usr
copied player.bmp -> /app/usr/mygame
copied newgame.app.rb -> /app/usr -- right-click in the launcher to see it
```

1 周は「**PC で保存する → ブラウザでランチャーの項目を押す**」の 2 動作。
中身が変わっただけなら**再走査は要らない** (項目は名前で並び、起動時に
その場でファイルを読むため)。3 番目の文言が出るのは**名前が新しいときだけ**で、
編集の輪では出ない。

**ページのボタンを 1 周ごとに押させてはいけない。** 設定の帯を押すと
キャンバスからキーボードの焦点が外れ、毎回クリックして戻す羽目になる。
F3 を全自動にしたのはこれが理由で、**UI としては何も足さないのが正解**。

既に動いているアプリは差し替わらない。Ctrl+Q で閉じてから起動し直す
(実機と同じ。ページ側から他殺するのは危ない)。

### F4: 機械 → PC の書き出し

機械が書いた `/home` を作業場へ写す。**こちらは自動にしない。**

**向きで扱いを変えるのは意図的**である。取り込みは失っても困らない
(元が PC にある) が、書き出しは**利用者の PC のファイルを上書きする**。
黙ってやってよい操作ではない。両方向を自動にすると、どちらが新しいかの
判定を誤ったときに元が消える。

副産物として、**作業がブラウザの中だけに閉じ込められなくなる**。今は Erase
やブラウザの掃除で全部消え、備えは手動の tar だけである。

## 段取り

| | 内容 | 受け入れ |
|---|---|---|
| F1 | 放り込み + ファイル選択で `/home` へ。tar は従来どおり。**素材の syncfs も測る** | **完了・受け入れ済 2026-09-03** (9b4b6f4c)。行き先の規則 9 件を実ソースから取り出して試験、全部通過 |
| F2 | `showDirectoryPicker`、handle の保存と許可の復帰 | **実装済・確認待ち** (94856c8b) |
| F3 | PC → 機械の追随 | **実装済・確認待ち** (94856c8b) |
| F4 | 機械 → PC の書き出し (明示操作) | **実装済・確認待ち** (94856c8b)。PWA の許可が残るかは未確認 |

**F2-F4 は Claude には動かせない。** `showDirectoryPicker` も許可の付与も
利用者の操作からしか呼べず、注入はキャンバスの入力に入る経路なのでページの
DOM に起こせない。確認できたのは「ページが例外なく起動する」ところまで。
放り込みと選択 (F1) も同じ理由で操作自体は確認できず、受け入れはユーザによる。

実装で追加した判断 (計画に無かったもの):

- **取った時刻の表を handle と一緒に IndexedDB へ残す**。handle だけだと
  再訪のたびに素材を全部読み直す。表があれば 1 ファイル 1 stat で済む。
- **書き出した直後にその時刻を表へ書く**。読み戻すと同じ中身を全部
  写し直すことになる。
- 再接続用に横取りした click は**名前付きにして外せるようにする**。
  無名の包みだとボタンがその訪問の間ずっと乗っ取られたままになる。

F1 は F2 以降の前提 (書き込みの実体を共有する)。

## 未確定事項

- 追随の間隔と、歩く範囲の上限 (深さ・個数)。実測してから決める
- 同じファイルを両側で直したときの規則。F4 を明示操作にすることで
  当面は避けているが、書き出し時に**相手の方が新しい**場合の扱いが要る
- **大きなファイルを置いたときの syncfs の実測 (F1 で測る)**。素材が主用途
  である以上、ここは後回しにできない。遅ければ OPFS を考え直す材料になる。
  IndexedDB の割り当て上限に当たったときの見せ方も要る

## スコープ外

- OPFS / WASMFS への移行 (前章の理由)
- サーバ側への保存・同期。ブラウザの中で完結させる方針は変えない
- `/etc` の持ち込み (設定はページ側が正)
- Firefox / Safari 向けの代替でフォルダ結び付けを真似ること。
  F1 で止める
