# wasm のストレージ永続化 (設計と段取り)

> 状態: 進行中 | 更新: 2026-08-31 | T0-T4 完了 (/home は IndexedDB に残り、tar で持ち出せる)。実操作もブラウザ駆動で確認済。残るは T5 と実機側の確認

ブラウザ版でユーザが作ったものをタブを閉じても残す。P5 (配信) までは
すべて揮発で、リロードすると書いたプログラムが消える。

実装の分割は末尾の段取り。ここで一番効くのは方式選びではなく、
**/home に配布物が混じっている問題** (次章) の始末である。

## 前提として確かめた事実

### ファイルの実体は 1 つで、ブラウザの main スレッドにある

生成された `wasm/build/core_web.js` を読むと、ファイル系のシステムコールは
すべて `if (ENVIRONMENT_IS_PTHREAD) return proxyToMainThread(...)` で始まる
(`openat` / `mkdirat` / `unlinkat` / `renameat` / `getdents64` / `stat64` /
`fd_read` / `fd_write` ほか)。機械 (main() を走らせている作業スレッド) の
読み書きは main スレッドへ転送され、そこにある 1 つの MEMFS を触っている。

つまり**ページ側から機械のファイルを触る道は塞がっていない**。IDBFS を
割り当て、`FS.syncfs` を呼ぶのは main スレッドの仕事にできる。

**T0 で実測して決着した (report/storage_t0.md)**。ページは機械が書いた
`display_width` を読み返せ、機械しか作らない `/flash/home` も見える。
report/p5.md の付記「ページの MEMFS と機械の MEMFS は別物」は誤りで、
正体は順番だった: 梱包を展開する `runWithFS` は
`Module["preRun"].push(...)` で**後ろに足され**、しかも実ファイルの書き込みは
全部の preRun が終わった後 (run dependency 待ち) に走る。ページが preRun で
書いたものは errno 44 で失敗するか、後から上書きされる。

設定を argv で運ぶ現行の作りはそのまま残す — ページから書けると分かった
だけで、機械が自分の読む直前に焼き込む方が順番の事故が無い。

### /home は梱包に無いので、ページが起動前に触れる

T0 で確かめた: `/home` は梱包に 1 ファイルも入っていない (T1 の成果) ため、
ページが preRun で `/flash/home` を作って中身を置くと、展開後も機械の起動時
mkdir の後も残る。**IDBFS の割り当て先としてそのまま使える**。

### C 側から IndexedDB を同期で触ることはできない

`emscripten_idb_load` / `_store` の同期版は ASYNCIFY 必須で、非同期版の
コールバックは呼び出したスレッドのイベントループが回らないと届かない。
機械のスレッドは main() から戻らないので、どちらも使えない。
**永続化の駆動役はページ (main スレッド) 側**になる。

### 実機と違って「焼き直しの瞬間」が無い

実機は `rake flash` で /home ごと入れ替わり、残したいときはユーザが
`app_only` を選ぶ。更新の意思決定を人が下している。ブラウザは配布物を
差し替えてリロードするだけで、ユーザは何も選ばない。**版が上がったときの
規則をコードに書ききる必要がある**。

## 中心の問題: /home に配布物が混じっている

### 現状

git 追跡分の /home は次の 6 ファイル (32KB)。全部が配布物であり、同時に
全部がユーザの持ち物として置かれている。

| ファイル | 性格 |
|---|---|
| `README.md` / `README_ja.md` | 純粋な配布文書。ユーザは編集しない |
| `services.toml` | 配布の手本 (60 行の解説つき) かつユーザの設定ファイル |
| `services/heartbeat.rb` | 手本。サービスの書き方の説明を兼ねる |
| `services/hourly_chime.rb` | 手本 |
| `services/broken.rb` | 手本 (壊れたサービスの見本) |

実行時に /home へ増えるのはユーザの作りもの (エディタで書いた .rb 等) と
`services_state.toml` (enable/disable の記憶。ホストが書き、ユーザの物として
二度と書き換えない、と自分で宣言している)。

### 何が壊れるか

/home をまるごと永続化し、次の版を配ったときに何が起きるか。

1. **手本が古いまま凍る**。`services.toml` は「この機械が何を常駐させるか」の
   書き方そのものを説明している文書でもある。次の版で新しい書き方 (たとえば
   app エントリの新しいフィールド) を足しても、永続化された古い写しが勝ち
   続ける。ユーザは「案内に無い機能」「動かない例」に出会う。README も同じで、
   /usr/share/samples の場所が変わっても古い案内を読み続ける。
2. **上書き規則にするとユーザの編集が飛ぶ**。`services.toml` は
   `enable = false` を書く場所として編集されることが前提のファイルなので、
   配布側を常に勝たせる規則にはできない。手本と設定を 1 つのファイルが
   兼ねている以上、「配布物だから上書きしてよい」も「ユーザの物だから
   触らない」もどちらも間違う場面がある。
3. **「消した」が表現できない**。`broken.rb` は壊れたサービスの見本なので、
   一度見たら消したくなる。「無いものは足す」規則だと版が上がるたびに
   復活する。かといって「一度入れたら二度と足さない」規則にすると、新しい
   手本が既存のユーザに永久に届かない。
4. **書き出しに配布物が混ざる**。tar で持ち出す機能を付けたとき、ユーザの
   データだけを取り出したいのに手本 3 本と README 2 本が必ず付いてくる。
   取り込む側でも「どれが自分の物か」が判別できず、別の版の手本が
   紛れ込む。

### 根っこ

**あるファイルが配布物なのかユーザの物なのかを、後から見分けられない**。
名前と場所だけでは区別がつかない。区別するには「配布時にどういう内容で
置いたか」の記録が要る。

### これは実機にもある問題

`app_only` で焼くと /home が残るので、同じことが起きる。今は
「ユーザが app_only を選んだのだから古い /home が残って当然」で通っているが、
配布の手本が古いまま残る点は変わらない。**ブラウザ版が問題を先に踏むだけで、
直し方は両方に効く**。

## 方針: 出せるものは /home から出す

### A. 構造で解く (主)

配布物を /home の外へ移し、**/home を 100% ユーザの物にする**。永続化・
書き出し・取り込み・初期化の規則が全部「/home を丸ごと」で書けるようになる。

**実施済 (2026-08-31)**。移した先は次のとおり。

| 今の場所 | 移した先 | 備考 |
|---|---|---|
| `/home/README.md` `/home/README_ja.md` | `/usr/share/doc/home.md` `home_ja.md` | 新しい配置を説明する内容に書き直した |
| `/home/services/hourly_chime.rb` | `/usr/share/services/` | **システムサービスに格上げ** (下記) |
| `/home/services/heartbeat.rb` `broken.rb` | `/usr/share/samples/services/` | 写して使う見本。既定では走らない |
| `/home/services.toml` | `/usr/share/samples/services/services.toml.example` | 手本としての役割はこちらへ |

### 手本 3 本の行き先 (ユーザ判断 2026-08-31)

3 本は手本であると同時に、初めて起動した機械で services 機能が動いて見える
唯一の実物だった。**hourly_chime だけ機能として残す**を選んだ:

- `hourly_chime` は `config/services.toml` に `enable = true` で載せ、本体を
  `/usr/share/services/` へ置く (= システムサービス扱い)。正時に鳴る既定の
  体験は変わらず、しかも更新で新しい版に入れ替わる。止めたい人は
  `svc disable hourly_chime`、あるいは自分の `/home/services.toml` に
  `enable = false` を書く。
- `heartbeat` と `broken` は見本として `/usr/share/samples/services/` へ。
  既定では 1 本も走らない。

副作用が 2 つある。**Retro ではサービスホストが起動しなくなる** (Retro には
`/etc/services.toml` が無く、`/home/services.toml` の存在だけでホストが
上がっていた。サービスは Modern 専用という設計どおりの状態に戻る)。
**ブラウザ版は独自の一覧が要る** — bundle は追跡分しか束ねず
`flash/etc/services.toml` は生成物なので、`config/services_wasm.toml`
(clock + hourly_chime だけ。網を使う net/timesync/tts は除く) を
`rake wasm:webflash` が `/etc/services.toml` として置く。

`/home/services.toml` が無いのは異常ではない (services.app.rb の `read_file`
は欠落を正常として扱い、システム側の `/etc/services.toml` だけで動く)。
**/home は空で出荷する**。ユーザが自分のサービスを持ちたくなったら手本を
複製する、という手順になる (複製の導線は未確定事項を参照)。

web の staging だけで移すのではなく、**実機の flash 構成ごと変えた** — 実機に
同じ問題があり、web だけレイアウトを分岐させると「配布物 = git 追跡分」の
不変条件の読み替えが 1 つ増えるため。

### /home は誰が作るか

git は空ディレクトリを追跡できず、web の梱包もファイルの無いディレクトリを
作らない。よって**起動時にファイル HAL が `/home` を作る**
(posix と esp32 の `fmrb_hal_file_init`)。ユーザが消しても次の起動で戻り、
古い storage の上に app_only で焼いたときも埋まる。

### T1 の検証 (2026-08-31)

wasm の node ビルド (Modern 構成、NODERAWFS で実の flash/ を読む) で、
`flash/home` をディレクトリごと消してから起動した:

- `/home` が起動時に作り直された。
- `services: no /home/services.toml` が info として出て、異常にならない。
- `clock started (sys, /usr/share/services/clock)` と
  `hourly_chime started (sys, /usr/share/services/hourly_chime)`、
  `2 running, 0 disabled`。エラーは 0 件。

未確認: 実機 (esp32 側の `fmrb_hal_file_init` の変更はまだコンパイルして
いない)、Retro でサービスホストが上がらなくなること、ブラウザでの通し。
また **`rake wasm:webflash` は git の index を読む** ので、移動を stage
するまで staging が古いパスを探して失敗する。

### B. 指紋で解く (A で出しきれなかった分の保険)

どうしても /home に配布物を置き続ける必要が出た場合の規則。種を入れた
ときにパスごとに (配布版, crc32) を記録しておき、版が上がったら 3 分岐する。

| 現在の状態 | 判定 | 動作 |
|---|---|---|
| ファイルが無い | ユーザが消した | 足さない |
| crc32 が記録と一致 | 未編集 | 新しい配布物で置き換える |
| crc32 が違う | ユーザが編集した | 触らない。必要なら隣に `.new` を置いて知らせる |

crc32 は `main/kernel/host/host_file_local.c` の `local_file_crc32` がある。
記録は IndexedDB のメタ (下記) に持つ。設定ファイルを配る側が昔からやって
いる三分岐と同じ形で、**A を済ませてあれば対象は 0 件か 1 件で済む**。

## 何を残すか

| 区分 | 対象 | 判断 |
|---|---|---|
| 残す | `/home` | 主役。A の整理後は全部ユーザの物 |
| 残す (次点) | `/app/usr` | ユーザが置いたアプリ。今は空 |
| 残さない | `/tmp` | 仕様として揮発。RAM 記憶域のまま |
| 残さない | `/app` `/usr` `/cache` `/bin` `/etc` | 配布物。版が上がったら入れ替わるべき |
| 残さない | `/etc/system_conf.toml` | 解像度と配色はページの localStorage + argv が正。永続化すると正が二重になり、リロードで直る逃げ道も消える |
| 任意 | `/var/cache/launcher_index` | 再読込のたびの走査を省ける。梱包の版が変わったら捨てる鍵が要る |

## 方式

**IDBFS を /home に割り当てる**を採る。

- 読み込みは preRun で `FS.syncfs(populate: true)` を `addRunDependency` と
  組にして、機械が起動する前に終わらせる。
- 書き込みは `autoPersist` (書き込みのたびに自動で溜め込む) に任せ、
  取りこぼしを `visibilitychange` / `pagehide` で拾う。`beforeunload` は
  非同期処理が間に合わないことがあるので当てにしない。
- 割り当て先と梱包内容の衝突は、A の整理 (/home を空にする) で消える。

検討して落とした案:

- **自前スナップショット (tar を 1 キーで IndexedDB へ)**: microtar が木の中に
  あるので書けるが、C 側から同期で IndexedDB を触れない以上、結局ページ側で
  FS を触ることになり土台は同じ。**tar は書き出し / 取り込み機能として使う**
  (下記) ので、実装は無駄にならない。
- **WasmFS + OPFS**: `-sWASMFS` への全面切替が要り、preload-file と
  転送前提の作りが崩れる。得るものに対して危険が大きい。
- **File System Access (PC の実フォルダを直に)**: 同期のファイル呼び出しと
  非同期 API が噛み合わない。恒久保存の主役にはせず、書き出し先として使う。

## 消える前提で設計する

ブラウザの記憶域は消える。**書き出しと取り込みは付属品ではなく必須**である。

- 追跡防止の仕組みにより、数日触らないと script が書いた記憶域が捨てられる
  場合がある。プライベート窓では最初から残らない。
- `navigator.storage.persist()` で恒久化を要求し、`estimate()` で使用量を
  見せる。要求が通ったかどうかもページに出す。
- 書き出しは /home の tar をダウンロード。取り込みは同じ tar を戻す。
  取り込みは「PC のファイルを /home に入れる」導線と兼ねられる (今は無い
  機能で、あるとブラウザ版が道具として成立する)。
- 初期化 (記憶域を捨てて出荷状態へ戻す) も同じ画面に置く。

## 多タブ

同じ IndexedDB を 2 台の機械が触ると後勝ちで壊れる。Web Locks で最初の
タブだけが書き手になり、2 枚目は読み取り専用か、警告を出して永続化を
切る。
