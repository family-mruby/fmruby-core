# Phase B4 指示書: 周辺・体験 (互換レベル L4)

前提: Phase B3 + B3.5 完了 (ターゲット作品が linux sim で動き、
エディタの RUN で .bas を起動・置き換え再実行できる)。B4 は互換の
すそ野 (POKE/PEEK、ON ERROR、ファイル) と「Family BASIC らしい体験」
(直接モードコンソール)、および B3.5 report sec 9 の申し送り
(T4-7〜T4-9、方針は裁可済み) を扱うフェーズ。**冒頭のユーザ判断で
内容が変わる**ため、T4-1 を最初に行うこと。ただし T4-7〜T4-9 は
T4-1 の判断と独立なので、先に片付けてよい (T4-7 は RUN の体験の穴を
塞ぐものなので早いほどよい)。

## タスク

### T4-1: 直接モードコンソールの要否判断 (ユーザ判断)

- 判断材料を整理してユーザに提示する:
  - fm-editor で .bas を編集 -> 実行、で足りているか (B3 までの運用実感)
  - 直接モード実装のコスト見積り (画面エディタ、LIST/AUTO/RENUM/DELETE/
    FIND、CONT の対話利用、エディタとインタプリタの状態共有)
- 「やる」となった場合のみ T4-6 を実施。「やらない」場合は行エディット
  系コマンド (B1 でトークンのみ定義済み) を「直接モード専用エラー」の
  文言に整えて終了。

### T4-2: 仮想 POKE / PEEK

- B0 T0-5 の棚卸しで判明した頻出アドレスを対象に、仮想メモリマップを
  実装する (compat_plan sec 5.6)。メモリマップの枠は core_spec sec 14 /
  v3_spec のマップに従い、エミュレート対象は代表領域 (画面 RAM、
  スプライト属性、乱数シード等、棚卸し結果で確定) のみ。
- 未対応アドレス: PEEK = 0、POKE = 無視。いずれも警告ログ (fmrb_log
  経由。BASIC 画面には出さない) を 1 アドレス 1 回に抑制して出す。
- 対応表 (アドレス範囲 -> 挙動) は report と doc 化する (ユーザが作品の
  非互換を判断する材料になる)。

### T4-3: ON ERROR / RESUME / ERROR

- ON ERROR GOTO / RESUME [行番号] / ERROR n (v3_spec の書式)。
  B1 で保持しているエラー種別・発生行を ERL / ERR 関数として公開し、
  捕捉 -> 復帰の制御フローを実行エンジンに足す。
- エラー処理中の再エラー、RESUME なしでの END 等の縁の挙動は spec に
  従い、不明点は疑義リストへ。

### T4-4: LOAD / SAVE / LOAD?

- littlefs (/home 以下) への読み書きに読み替える (compat_plan sec 5.7)。
  LOAD"名前" / SAVE"名前" のファイル名規則 (拡張子 .bas 補完、パスの
  扱い) を決めて report に記録。LOAD? はファイル内容比較。
- 実行中プログラムの置き換え (LOAD がプログラムを差し替えて停止する
  挙動) とアプリタスクのライフサイクルの整合に注意。

### T4-5: 残りの画面系 (BGGET / BGPUT / BACKUP / SCREEN / VIEW / FILTER)

- シャドウバッファ (B2) の退避・復元として実装する。書式・退避領域の
  個数は spec に従う。TRON / TROFF (トレース出力) もここで実装。

### T4-6: 直接モードコンソール (T4-1 で実施決定の場合のみ)

- BASIC コンソールアプリ: 起動するとタイトル + プロンプトの
  Family BASIC 画面になり、行入力 (行番号付き = プログラム編集、
  なし = 即時実行)、画面上のカーソル移動編集、LIST / AUTO / RENUM /
  DELETE / FIND、RUN / STOP / CONT、LOAD / SAVE を提供する。
- 実装は .bas アプリの一形態 (フルスクリーン) とし、インタプリタ状態を
  対話セッションとして保持する。
- キー入力 (カナモード含む) は B2 T2-3 の機構を使う。

### T4-7: 予約キー Ctrl-Q でアプリを閉じる (裁可済み)

背景: fullscreen の .bas 実行中はキーが全部アプリに行き、キーボードから
抜ける手段が無い (B3.5 report sec 6)。**予約キーは Ctrl-Q に決定済み**。

- kernel の HID ルーティング層 (アプリへ配送する前) で Ctrl-Q を
  横取りし、現在の HID target アプリへ APP_CONTROL `{"cmd":"stop"}` を
  送る。アプリには Ctrl-Q 自体を配送しない (= アプリからは見えない
  予約キー。BASIC 側の対応は不要で、B3.5 で直した stop 受信経路が
  そのまま効く)。
- 判定は scancode + Ctrl 修飾で行う (keycode は環境で値が変わる)。
- 対象は run/停止と同じ基準 (`run_path_allowed?` 相当 = /app /home 配下
  から起動したアプリ) に限る。デスクトップと組み込みアプリ (エディタ等)
  には送らない: エディタは未保存確認 (Ctrl-X のダイアログ) を持って
  おり、無条件 stop で潰してはいけない。
- 停止後のフォーカスは B3.5 の返却機構 (@run_parent -> desktop) に
  任せる。RUN -> Ctrl-Q -> 編集継続 -> F5、がクリックなしで回ることが
  ゴール。
- 検証は headless で可能: fmrb_input.py の `key ctrl+q` で fullscreen
  .bas が終了し、エディタへフォーカスが戻ることをログ + スクリーン
  ショットで確認する。

### T4-8: キーボード配列を言語設定に追従させる (裁可済み)

背景: B3.5 report sec 9 #26。scancode -> 文字の変換が経路ごとに独立して
おり、sim の `keyboard_layout = "jp"` と食い違う層では記号が化ける
(`"` -> `*` 等)。**方針は決定済み: キーボードは言語設定
(system_conf の keyboard_layout) に合わせて変更する**。

- まず現状調査: どの層に scancode -> 文字テーブルがあるか
  (BASIC の入力、fm-editor、desktop、tools/fmrb_input.py) を洗い出して
  report に表で残す。
- 端末側の全経路を keyboard_layout 設定 (us / jp) に追従させる。
  変換テーブルを 1 箇所に集約できるならして、各層はそれを引く。
- tools/fmrb_input.py の `text` も layout を指定 (または system_conf を
  読んで自動判別) して逆変換する。これで記号入りプログラムの注入検証が
  できるようになる。
- system_conf.toml は生成物なので、設定の追加・変更は config/ 側で行う。
- カナ入力は現行の TAB トグル + ローマ字 2 打を維持。JIS カナ配列
  (かな刻印どおりの直接入力) を足すかは、このタスクの調査結果
  (テーブル集約後のコスト) を材料にユーザ判断を仰ぐ。
- 検証: jp 設定で `"` `=` `:` を含む .bas を fmrb_input.py で注入して
  そのまま動くこと。us 設定でも golden が green のこと。

### T4-9: .keys ゴールデンの決定化 (入力待ち通知)

背景: B3.5 report sec 5。起動から最初の INKEY$ までが 10ms 台で、
ホストからの注入が間に合わず .keys ゴールデンが決定的に回らない。

- BASIC ランタイムが「入力待ちに入った」ことを fmrb_log マーカー
  (画面ダンプ同様の固有プレフィクス) で 1 回出す。対象は INKEY$ 系・
  INPUT。連発しないようエッジ (待ち非待ちの遷移) でのみ出す。
- ハーネス (basic_screen_check.py または .keys ランナー) はマーカーを
  待ってからキーを注入する。
- B2 でスキップした `.keys` ケース (208_screen_inkey 等) を有効化して
  green にする。
