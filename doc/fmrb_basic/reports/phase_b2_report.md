## 1. T2-1: シャドウバッファと画面プリミティブ

- コアが `28x24` の**文字コード配列 + カラー属性配列**を per-task プールに
  持つ。これが正であり、描画・SCR$・スクロール・ダンプはすべてここから
  答える (compat_plan sec 5.1)。
- カーソル (`cursor_x_` / `cursor_y_`) はコアが持つ。PRINT のゾーン計算は
  B1 から引き続きこの桁を使う。最下行での改行はスクロール
  (文字と属性を 1 行分シフトし、最下行をクリア)。
- 実装した命令・関数:

  | 要素 | 挙動 |
  |---|---|
  | CLS [面] | 全消去 + カーソル原点。V3 の面指定は評価するが B4 まで無視 |
  | LOCATE X,Y | 0-27 / 0-23。範囲外は IL |
  | COLOR X,Y,n | (X,Y) を含む **2x2 エリア**の属性を n (0-3) に設定 |
  | PALET [B|S] n,C1..C4 | BG 側を実装。C1 は配色番号 0 のときのみバックドロップ。S (スプライト) は受理して B3 へ持ち越し |
  | POS(x) / CSRLIN | カーソル桁 / 行 |
  | SCR$(X,Y[,Sw]) | 画面の文字コード。Sw=1 で配色番号 |
  | INKEY$ / INKEY$(0) | キューから 1 文字 / キー待ち |
  | KEY n,"文字列" / KEYLIST | ファンクションキー 8 本 x 15 文字 |
  | CLICK ON/OFF | フラグ保持 (音は B3) |

- ホスト出力コールバック (`put_char`) は**残してある**。コアは
  「シャドウバッファへの書き込み」と「文字ストリームのミラー」を両方行い、
  ゴールデンランナーは後者を、実機は前者を使う。実機側では PRINT 行が
  ログにも残る (ハーネスがこれを読む)。

## 2. T2-2: フォントと描画経路

### 2.1 フォントアセットの形式と作り方

- **原本は `tools/gen_basic_font.py`** の中のグリフ絵柄。1 グリフ =
  8 文字 x 8 行を空白区切りで並べた 1 行の文字列で、`#` が点灯、`.` が消灯:

  ```python
  0x41: "..###... .##.##.. ##...##. ##...##. #######. ##...##. ##...##. ........",  # A
  ```

- 生成: `python3 tools/gen_basic_font.py` ->
  `components/basic/assets/basic_font8.c` (256 x 8 バイトの const 配列)。
  ヘッダは `assets/basic_font8.h`。**生成物もコミットする** (ビルドに
  Python を要求しないため)。絵柄を直したいときはスクリプトを編集して
  再生成する。
- 収録範囲:

  | コード | 内容 | 作り方 |
  |---|---|---|
  | 32-95 | ASCII (大文字のみ) | 手描き 64 字 |
  | 96-150 | カナ (清音・小書き) | 手描き 55 字 |
  | 151-175 | 濁音・半濁音 | **基底カナから自動生成** (右上 2 列に濁点/半濁点を合成) |
  | 176-183 | 記号 | 手描き 8 字 |
  | 184-255 | BG パターン | 手続き生成のプレースホルダ (縞・枠・市松など 8 種の巡回) |
  | 0-31 | BG グラフィックグループ (システム用) | 空白 (B3 でタイルセットと一緒に決める) |

- 絵柄はすべて自作。Family BASIC の CG は任天堂の著作物なので、
  **コード配置だけが spec 準拠**で絵柄は独自 (compat_plan sec 5.2)。
  品質はプレースホルダ相当 (清書はユーザ判断、00_common の未決事項 2)。

### 2.2 描画経路

- レンダラ (`extension/fmrb_basic_gfx.c`) はコアからのセル更新通知を受け、
  **1 セルを「背景の矩形 1 個 + グリフの水平ラン数個」**として
  fmrb_gfx canvas に描く。フォントシートを graphics 側へ転送する経路
  (BMP + `LOAD_SPRITE_IMAGE_BMP` + `DRAW_TILE`) を使わなかった理由:
  - シートを送るにはファイル転送経路が要り、Retro/linux では音源・画像と
    同じ転送を BASIC 起動ごとに行うことになる。
  - 属性色 (COLOR/PALET) ごとにシートを複製する必要がある
    (4 属性 x 256 字 = 64KB)。ラン描画なら色は描画時に決まる。
  - 変更セルだけ描くので、通常のテキスト出力では 1 行あたり数百コマンド。
- present は**セルごとに行わず**、tick とプログラム終了時にまとめる
  (T2-1 の指示どおり)。ダーティ範囲は矩形 1 個に畳んでいる。
- 画面は 224x192 の canvas。フルスクリーン時はフレームバッファ中央
  (320x240 なら (48,24))、ウィンドウ実行時はウィンドウ位置に置く。
- **色**: 色コード 0-60 -> RGB332 の変換表をレンダラに持つ
  (core_spec sec 7 が「PPU パレットと同一構造」と言うので、広く使われる
  実測 RGB を RGB332 へ落とした 64 エントリ表)。テキストは
  「配色グループの 3 色目を文字色、バックドロップを背景」として描く。
  残り 2 色は多色タイル用で B3 で使う。
- 旧 basic_console のウィンドウ枠・行バッファ・文字描画は撤去した。

### 2.3 既知のコスト

全画面書き換え (CLS、スクロール、PALET 変更) は 672 セルの再描画となり、
空白セルでも 1 コマンド、文字セルで 10 前後のコマンドを送る。linux sim
では実用速度だが、**スクロールを多用するプログラムでは律速になりうる**。
改善案 (B3 以降の候補): (a) canvas viewport を 1 行分ずらして
最下行だけ描く ring 方式、(b) グリフをシート化して `DRAW_TILE` 1 発に
する。どちらも B3 のスプライト実装と同時に評価するのが妥当。

## 3. T2-3: キー入力

- HID キーイベントはアダプタ (`fmrb_basic.cpp`) の `on_tick` で
  自タスクのメッセージキューから取り出し、コアのキューへ積む
  (`interpreter::push_key`)。プログラム実行中でも 32 ステートメントごとに
  取り込まれる。
- INKEY$ は 1 文字ポップ、INKEY$(0) はキー待ち。**時計制御を持たない
  ホスト (テストランナー) では待たずに空文字を返す**ようにしてあり、
  ゴールデンテストが固まらない。
- **カナ入力方式 (簡略方式、要記録)**: `TAB` (0x09) がカナモードの
  トグル。モード中は**ローマ字 2 打**でカナを作る (K+A -> カ、
  N+N -> ン、J/F は ZI/HU の別綴りとして受理)。カナのコード表は行ごとに
  連続しているので、変換表は「子音 -> 行頭コード」の 13 エントリで済む。
  実装はコア側なので、ゴールデンテストからも同じ経路を叩ける
  (`test/golden/212_kana_input`)。
  **JIS カナ配列 (キー刻印どおりの直接入力) は未実装**。ベーマガ作品の
  実行には不要 (プログラム中の文字列は .bas ソース側で解決する) なので、
  必要になった時点で B4 の入力周りとまとめて判断する。

## 4. T2-4: テキストダンプ検証 (次フェーズの主検証手段)

### 4.1 使い方

**ホスト (速い、docker 不要)**: `.bas` に `_SCRDUMP` を書き、
`rake basic:test` で他のゴールデンと一緒に比較する。

```basic
100 _SCRDUMP 1      ' タグ 1 で T 行 + A 行
110 _SCRDUMP 1,1    ' 第 2 引数 bit0 で配色 (C 行) も出す
```

**linux sim (実機と同じ経路)**:

```
# 端末 1: family-mruby ルートでスタックを起動したまま
tools/dev_run_check.sh --keep /tmp/boot.png
# 端末 2: fmruby-core で
python3 tools/basic_screen_check.py            # 2xx ケース全部
python3 tools/basic_screen_check.py 202_screen_scroll
python3 tools/basic_screen_check.py --list
```

スクリプトは対象 `.bas` を `flash/app/demo/_screencheck.app.bas` に
コピーし、**debugd (TCP 5555) の spawn コマンドでアプリを起動**して
(ランチャをクリックする必要がない)、`docker logs` から `SCRD|` 行を
拾って `.expected` 内の `SCRD|` 行と比較する。終了時に一時ファイルは
消す。キー入力を要するケース (`.keys` を持つケース) は sim では
決定的に再現できないためスキップし、ホスト側だけで検証する。

### 4.2 形式 (B0 sec 3.3 からの変更点)

```
SCRD|1|BEGIN 28x24 bg=0
SCRD|1|T00 20 20 46 41 ... (28 バイトを 16 進、これが比較の正)
SCRD|1|A00 |  FAMILY BASIC             |
SCRD|1|C00 0000111122223333...   (第 2 引数指定時のみ)
SCRD|1|END 48
```

- **A 行の透過表記を 0x20-0x5F に狭めた**。B0 では 32-126 をそのまま
  出す設計だったが、カナは 0x60 以降にあり、そのままだと小文字英字に
  見えてしまう (この文字セットに小文字は無い)。0x60 以上は `.` にする。
- `END` は本文行数。行フィルタ方式では欠落を検出できないため。
- ダンプは実機/linux ではログ (`FMRB_LOGI`)、ホストランナーでは stdout に
  出る。同じ文字列なので `.expected` を 1 つで共用できる。

## 5. T2-5: .bas アプリのフルスクリーン既定化

- `fmrb_app_spawner.c`: `.bas` を検出したら `fullscreen = true` を既定に
  し、`.app.toml` の `default_window_mode` が明示されていればそちらを
  優先する (`window` / `fullwindow` 指定時はウィンドウ実行)。
- デモの `basic.app.toml` から `default_window_mode = "window"` を外し、
  既定のフルスクリーンで動くようにした。

## 8. 仕様の疑義リスト (spec は変更していない)

B0 sec 8.1 の 3 件と B1 sec 9 の 8 件は未決のまま。B2 で新たに判明:

| # | 内容 | 採用した挙動 | 影響 |
|---|---|---|---|
| 14 | `SCR$(X,Y,1)` は配色番号を返すが、SCR$ の戻り値は文字列。数値をどう包むか spec に記述なし | コード値 0-3 を持つ 1 文字の文字列 (`ASC(SCR$(X,Y,1))` で読む) | 配色を読むプログラム |
| 15 | スクロール時の配色属性の扱い。属性は 2x2 エリア単位なので 1 行スクロールでは半エリアずれる | 文字と一緒に 1 行ずらす | 色付き画面をスクロールする作品 |
| 16 | 起動時の配色 (core_spec sec 16 は「BG 用パレットコード 1」とだけ書き、色コードを列挙していない) | 白・赤・緑・青のプレースホルダ配色 | 見た目のみ。実機映像が手に入れば表を差し替える |
| 17 | LOCATE の範囲外はどのエラーか (spec に記述なし) | IL (Illegal function call) | エラー分岐する作品 |
| 18 | カナ入力方式 (実機は JIS カナ配列のキーボード) | TAB トグル + ローマ字 2 打 | 直接モード実装時 (B4) に再検討 |

## 9. Phase B3 への引き継ぎ

- **スプライト面はまだ無い**。SPRITE / DEF SPRITE / DEF MOVE / PLAY /
  BEEP は現在 `ext_statement` に落ちて IL になる
  (`test/golden/151_unsupported_statement` がこれを固定している)。
  B3 はコア側にハンドラを足して置き換える。
- **パレットの受け皿はできている**: `PALET S` は構文解析まで通って
  無視されるだけなので、B3 はスプライト用パレットの保存と通知を足す。
  色コード -> RGB332 の変換表はレンダラにある。
- **タイル絵柄**: フォント生成スクリプトの仕組み (絵柄 -> C 配列) は
  そのままアニメキャラクタ (テーブル A) にも使える。コード 0-31 の
  BG グラフィックグループと 184-255 の背景パターンはプレースホルダの
  ままなので、B3 で絵柄を決める。
- **描画コスト**: sec 2.3 の全画面書き換えコストは、スプライトが毎フレーム
  動く B3 でより効いてくる。viewport スクロールかタイルシート化の
  どちらかを B3 の早い段階で判断するとよい。
- **入力**: STICK / STRIG は B3 でゲームパッド HID を取り込む。キー取り込みの
  骨格 (`on_tick` でメッセージキューを空にする) はそのまま使える。
- **PLAY**: B0 の裁可どおり MML -> FMSQ + チャンク転送コマンド追加。
  fmruby-graphics-audio 側の変更が必要なので、着手時に調整すること。
