# M1 report: ESP-Hosted の mempool を切って測る

> 状態: 完了 (親の検収とユーザの判断待ち) | 更新: 2026-10-06 | P4-Nano で mempool あり / なしを同じコミット・同じ手順・同じ計装で比べた。**なしでは 1664 B の塊が溜まらず、負荷の後の内蔵 RAM は 2 回目の負荷でも同じ値に戻る (起動直後から -7.9 KB は 1 回目だけの確保)。ありでは塊が 10-11 個残り、一番大きく取れる空きが約 45 KB 小さくなる**。速さ (転送・MJPEG・H.264) に差は見えない。BLE は両方とも起動する。**別件: 64 KB の put / get の直後に core 0 が落ちることがある (mempool の有無によらない)**

指示書: ../instruction_m1.md / 計画: ../plan.md / 前提: ../../ruby_asterism/report/z3.md 12 章 (feature/asterism-z3 の上にある)

## 1. 要約

- 変更は `config/sdkconfig.defaults.p4` と `config/sdkconfig.defaults.naryav4` に `CONFIG_ESP_HOSTED_USE_MEMPOOL=n` を足しただけ (コミット 9c326e6b)。ほかの sdkconfig の項目は変えていない。生成された sdkconfig は `# CONFIG_ESP_HOSTED_USE_MEMPOOL is not set` (旧名の `CONFIG_ESP_USE_MEMPOOL` も連動して not set)。
- 受け入れ条件との対応:
  1. 内蔵 RAM の戻り: なしでは 1664 B の塊は起動直後の 1 個のまま増えない。負荷の後 3 分の値は起動直後より 7.9 KB 少ないが、2 回目の負荷の後もまったく同じ値 (200836) に戻ったので、これは最初の 1 回だけの確保 (2 章の分解を参照)。ありは 1 回目で塊が 4 -> 10-11 個、内蔵 RAM -12.7 から -15.8 KB。
  2. 速さ: 転送・MJPEG・H.264 とも差は誤差の範囲 (3 章)。
  3. 細切れ: 負荷の後の一番大きく取れる空きは、なし 143-156 KB、あり 110-115 KB。どちらもアプリ 1 本 (24 KB) には足り、負荷の後にアプリ (Kamon) を起動して落ちなかった。**細切れはむしろ mempool ありの方が悪い** (溜め置きの塊がヒープの途中に散らばって残るため)。
  4. 起動時の内蔵 RAM は増えない (むしろ減る分が小さい: M1|wifi_rd で +3,580 B、静的な分で +252 B)。BLE は両方とも `BLE initialized` / `ble_on_sync: synced=1` / `BLE advertising started` まで出た。
- 別件の不具合 (4 章): 64 KB の put と get を続けると、core 0 のタスクがフラッシュ上の命令やデータへのアクセスで落ちて再起動することがある。mempool ありで 3 回の起動のうち 3 回、なしで 3 回のうち 1 回。どちらでも起きるので mempool とは関係が無い。`CONFIG_SPI_FLASH_AUTO_SUSPEND` との組み合わせを疑っている (cpu_usage.md 5 章の注意と同じ形)。調べてはいない。

## 2. 内蔵 RAM

### 2.1 起動時 (M1| とブート直後)

| 項目 | mempool あり | mempool なし (計装あり) | なし (計装なし、最終版) |
|---|---|---|---|
| `M1\|boot_start` internal | 504,560 | 504,812 | 504,812 |
| `M1\|ble_ready` internal | 227,864 | 231,456 | 231,036 |
| `M1\|wifi_rd` internal / largest | 209,092 / 172,032 | 212,672 / 172,032 | 212,252 / 172,032 |
| 落ち着いた後の `IRAM free:` | 203,420 | 208,716 | 208,276 |
| 落ち着いた後の largest | 159,744 | 163,840 | (計装なしでは出ない) |
| 落ち着いた後の 1664 B の塊 | 4 | 1 | - |

- 「落ち着いた後」は WiFi がつながって 2-3 分、何もしていない状態の 10 秒ごとのダンプ。ありは 2 回の起動とも 203,400-203,468、なしは 2 回とも 208,664-208,716。
- 起動の途中でも ESP-Hosted は塊を溜める (ありでは起動直後から 4 個)。なしでは常に 1 個 (使用中のもの)。

### 2.2 負荷の後 3 分

手順は 5 章。値は負荷を止めてから 3 分後の 10 秒ごとのダンプ (この間は一定)。

| 実行 | 内蔵 RAM の空き | 起動直後との差 | largest | 1664 B の塊 | 備考 |
|---|---|---|---|---|---|
| あり 1 回目 (A1) | 188,128 | -15,292 | 112,640 | 10 | 転送の途中で落ちて再起動 (4 章) |
| あり 1 回目 (A2) | 187,576 | -15,844 | 110,592 | 10 | 同上 |
| あり 1 回目 (A3) | 190,676 | -12,772 | 114,688 | 11 | 同上 |
| あり 2 回目 (A3 に続けて) | 187,604 | -15,844 | 114,688 | 10 | 落ちていない |
| なし 1 回目 (B1) | 200,836 | -7,880 | 155,648 | 1 | 落ちていない |
| なし 2 回目 (B1 に続けて) | 200,836 | -7,880 | 155,648 | 1 | 1 回目と同じ値 |
| なし 段階別 (B3) | 204,008 | (下記) | 143,360 | 1 | 転送の途中で落ちて再起動 |

- 「起動直後との差」は 2.1 の落ち着いた後の値 (あり 203,420、なし 208,716) との差。落ちて再起動した実行は、再起動の後に残りの負荷を受けている (再起動直後の M1 はふだんの起動と同じ値なので、同じ起点として扱った)。
- ありの -12.7 から -15.8 KB のうち、塊の増分 (6-7 個、10-11.6 KB) が大半。
- **なしの -7,880 B は 1 回目だけで、2 回目では増えない**。段階別の実行 (B3) では、再起動の後の転送 (put 1 回 + get 1 回) の直後に 204,176 になり、その後のアプリ単独・MJPEG・H.264 のどの段階の後も 204,0xx-204,2xx から動かなかった。最初の通信 (HTTP サーバのソケットや lwIP の初回の確保と見られる) の分で、mempool とは関係が無い。あり側の差にも同じ分が含まれていると見る (確保済みの塊の数は、ありでは塊以外に +3 個、なしでも +3 個)。
- 負荷の最中 (H.264 の配信中) の最小: あり 113,620-114,868 (min_ever)、largest は 65,536 まで下がった回がある。なし 119,940-126,176、largest 92,160-98,304。

### 2.3 アプリの起動 (負荷の後 3 分おいてから)

`/app/demo/kamon.app.rb` を起動し、25 秒後に一覧で RUNNING を確かめてから終了した。全 7 回 (あり 4、なし 3) で落ちなかった。起動中の内蔵 RAM は約 17.6 KB 減り、終了で元に戻った (あり 187,604 -> 169,988 -> 187,604 など)。

## 3. 速さ

| 項目 | mempool あり | mempool なし |
|---|---|---|
| 64 KB の put (平均 / 中央値 / 範囲、落ちた回を除く) | 1.115 / 1.069 / 0.943-1.738 s (17 回) | 1.056 / 1.060 / 0.958-1.299 s (14 回) |
| 64 KB の get (平均 / 中央値) | 0.298 / 0.295 s (20 回) | 0.298 / 0.229 s (15 回) |
| MJPEG `/stream` 30 秒の fps | 9.45 / 9.22 / 9.60 / 9.23 | 9.30 / 9.41 / 9.39 |
| MJPEG の受信量 | 202-211 KB/s | 204-206 KB/s |
| H.264 `/ws_video` 30 秒の fps | 15.16 / 15.20 / 15.37 / 15.33 | 15.10 / 15.26 / 15.32 |

- 差は実行ごとの揺れより小さい。mempool を切ったことによる確保と解放の増加は、この負荷では速さに出ない。
- fps は画面の変化で決まる (変化が無いと配信は 500 ms ごとの再送だけになる)。両方とも Breakout.py を動かした (操作なし) 同じ場面で測った。H.264 の受信量は 7.8 KB/s で、Breakout の画面の変化が小さいため。
- put の 25-32 秒の外れ値 (あり 3 回、なし 1 回) は、落ちて再起動するまで待った時間なので除いた (4 章)。

## 4. 別件: 64 KB の put / get の直後に core 0 が落ちる

- 起きたこと: `/fs/put` (/home へ 64 KB) と `/fs/get` を繰り返すと、get のログの直後に core 0 で Guru Meditation になり再起動する。

| ビルド | 起動 | 何回目の put / get で | 種類 | 落ちた場所 (addr2line) |
|---|---|---|---|---|
| あり | A1 | 1 回目の get の直後 | Store access fault (MTVAL は s_stereo_buf の中) | `audio_p4_hw_write` (audio_p4 タスク) |
| あり | A2 | 1 回目の get の直後 | Instruction access fault (フラッシュ上の命令) | `i2s_channel_write` (audio_p4 タスク) |
| あり | A3 | 4 回目の get の直後 | Instruction access fault | `fmrb_transport_process` (fmrb_host タスク) |
| なし | B1, B2 | 10 回 (2 周) 落ちず | - | - |
| なし | B3 | 4 回目の get の直後 | Instruction access fault | `fmrb_wav_stream_mix` (audio_p4 タスク) |

- どれも core 0 のタスクが、IRAM ではない場所 (フラッシュ上のコード、または内蔵 RAM の .bss) にアクセスした瞬間に落ちている。止まっている場所はタスクごとにばらばらで、そのタスクのコードの誤りではなく、フラッシュの書き込みの最中か直後のアクセスそのものが失敗していると見る。
- 再起動の後に続けた put / get (あわせて 15 回以上) は落ちなかった。起動して落ち着いた後の最初の数回で起きやすい。
- mempool の有無によらず起きるので、M1 の判断には関係しない。cpu_usage.md 5 章にある「計測版で 352 KB の put で core 0 が Instruction access fault」と同じ形で、`CONFIG_SPI_FLASH_AUTO_SUSPEND=y` (flash_write_flicker で採用) との組み合わせを疑っている。f1 の検証 (Guru 0 件) の put は 2 KB で、64 KB の put / get は含まれていない。原因は調べていない (sdkconfig と IDF の範囲)。
- 今回の計装 (5 章) は 10 秒ごとのダンプでだけ動き、落ちた時刻はダンプと重なっていない。計装の無い develop で起きるかは確かめていない (Z3 の調査のときの 64 KB の get / put では落ちていない)。

## 5. 比べ方

- コミット: feature/hosted-mempool の 9c326e6b (develop 6c278977 + defaults の 1 項目)。「あり」は同じコミットで `config/sdkconfig.defaults.naryav4` の追加した 1 行だけを作業ツリーで一時的に無効にして作った。どちらも `rake clean_all` の後に `FMRB_HW_TARGET=NARYAv4 rake build:esp32` (`.env` は TAB5 のまま触っていない)。app の大きさは あり 0x619bf0、なし 0x6199a0 (計装あり)、最終版 0x6197a0 (計装なし)。ブートローダは同じ大きさ。
- 焼き方は MCP の `flash` の `app_only` (全体の書き込みは不要だった)。機体は P4-Nano (192.168.10.15)、ミュートを確かめてから測った。
- 一時的な計装 (コミットしていない): `components/fmrb_common/src/fmrb_task.c` の 10 秒ごとのダンプに 1 行足し、`heap_caps_get_info(MALLOC_CAP_INTERNAL)` の空き・最大の塊・最小・確保済みと空きの塊の数と、`heap_caps_walk` で使用中の 1536-1700 B の塊の数を出した。両方のビルドに同じものを入れた。最終版の焼き直しと Linux のビルドの前に外した。
- 負荷の手順 (各実行で同じ。手元のスクリプトで時刻つきで回した):
  1. WiFi がつながって 2-3 分置いた後の値を起点にする。
  2. (a) 64 KB (乱数、固定の種) を `/home/m1_test.bin` へ put して get し、中身を照合する。これを 5 回。最後に消す。
  3. `/app/game/breakout/breakout.app.py` を起動し 5 秒待つ。(b) `/stream` を 30 秒受けて部分の数を数える (X-Seq で新しい画面であることも確認。全部新しい画面だった)。(c) `/ws_video` に WebSocket でつなぎ 30 秒受け、種別 0x01 のフレームを数える。Breakout を終了する。
  4. 3 分待って値を記録する。アプリ (Kamon) を起動して落ちないことを確かめ、終了する。
- `tab5_screenshot` の連続ではなく、それと同じ MJPEG の経路 (`/stream`) を 30 秒受け続けて fps を測った (cpu_usage.md 5 章の e1 と同じ)。

## 6. 見立てと違った点・踏んだ罠

- 見立てでは細切れは mempool を切ると悪くなるかもしれなかったが、逆だった。ありでは溜め置きの塊 (1664 B) が H.264 の配信などで大きな確保が出入りした後のヒープの途中に残り、一番大きく取れる空きを約 45-49 KB 削る。なしでは負荷の後の largest は起動直後から -8 KB (1 回目だけの確保の分) にとどまる。
- 起動直後の時点でも、ありは塊を 3 個多く持っている (起動中の通信の山の分)。そのため、起動時の値もなしの方が約 3.6-5.3 KB 多い。
- 負荷の手順に転送を入れると、4 章の不具合で再起動が入り、ありの 1 回目は 3 回とも途中で再起動した。比べる値は「再起動の後に残りの負荷を受けた状態」になったが、塊の溜まり方は Z3 の 12 章と同じ (4 -> 10 個) で、2 回目の負荷 (落ちていない) でも同じ値に収まった。
- `app_only` の書き込みは 115200 bps で 1 回 5.5 分かかる。再起動の手段がほかに無い (遠隔の再起動の口は無い) ので、起動し直すたびに同じファームを焼き直した。

## 7. Tab5 で確かめること

- 同じ defaults の項目が `sdkconfig.defaults.p4` に入っている。Tab5 では焼いていない。起動・WiFi・BLE (C6 経由) と、同じ負荷の後の内蔵 RAM (1664 B の塊が増えないこと) を確かめる。
- 4 章の put / get の後に落ちる件が Tab5 でも起きるか (`sdkconfig.defaults.p4` には `CONFIG_SPI_FLASH_AUTO_SUSPEND` が入っていない。Tab5 で起きなければ、自動中断を疑う材料になる)。
