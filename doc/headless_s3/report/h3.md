# H2b・H3 報告: 落ちたアプリを画面に出し、画面を取り込み、AtomS3R を Asterism の網に入れる

> 状態: 完了 (検収待ち) | 更新: 2026-10-12 | instruction_h2b_h3.md の記録。単一アプリの端末で遠隔に起動したアプリが落ちると、止まったときの画面にアプリと理由が出て、次のアプリが立つと消える。devctl に画面の取り込み口 `/fb` (128x128 の RGB565 をそのまま) を足し、MCP の tab5_screenshot が PNG にして返す。新しいビルドの選択肢 `FMRB_ASTERISM` で S3 に Asterism を入れ (AtomS3R の既定は 1、Retro は 0)、AtomS3R の `asterism_demo` が asterism-console の図に ▣ で出て、console と PC から呼べた。往復は約 146 ms (中央値)。WiFi と zenoh がつながった状態の内蔵 RAM の空きは 135,280 B で、zenoh による減りは 1 KB 未満

## 1. 結果の要約

- **落ちたアプリ (H2b)**: `boot_mode = "app"` の端末で、`/app/launch` で起動したアプリが例外で終わると、止まったときの画面 (暗い赤、`STOPPED`) にそのアプリのパスとエラーが出る。起動し直しはしない。次に起動したアプリが自分の画面を作った時点で、止まったときの画面は消える。kill (頼まれた停止) では出ない。`boot_mode = "desktop"` では何もしない (今までどおりデスクトップのエラーの窓)。
- **画面の取り込み**: 作った。devctl の自前のサーバ (S3) に `GET /fb` を足し、`/status` に `"fb":true` を載せた。MCP の tab5_screenshot は `"mode":"none"` で `"fb":true` の端末なら `/fb` を読んで PNG (128x128) にして返す。1 枚 0.15-0.34 秒。取り込みの場所は PSRAM で、内蔵 RAM は使わない。Tab5 の振る舞いは変えていない。
- **H3 のビルド**: `FMRB_ASTERISM=1` で S3 のビルドに picoruby-asterism-zenoh と picoruby-asterism が入る。ATOMS3R は端末の既定で 1。Retro は既定で 0 のままで、zenoh の記号は ELF に無い。
- **flash**: AtomS3R のファーム 0x3E2DA0 (4,074,912 B)、5M の区画の残り 0x11D260 (1,167,968 B、22%)。H2 から +149,424 B。
- **内蔵 RAM**: `asterism_demo` を startup_app にして WiFi と zenoh がつながった定常で `IRAM free: 135,280 B`。H2 の定常 (試しのアプリ、WiFi あり) 135,748 B との差は 468 B。zenoh-pico の確保は PSRAM だけで、zenoh のタスクは無い。
- **網**: console の図に `▣ fmruby-XXXXXX` とアプリ demo、オブジェクト screen・apu・info が入れ子で出た。console から `screen.say` を呼ぶと 127 ms で返り、端末の画面に出た。PC の CRuby (asterism gem) から `info.echo` を 30 回呼んで、最小 99 ms・中央値 146 ms・最大 185 ms。
- **網に入るまで**: app_main から IP の取得まで 2.40 秒、つながるまで 2.80 秒。リセットから app_main までの約 1.42 秒 (H1) を足して、**リセットから網に入るまで約 4.2 秒**。
- **回帰**: Retro と Tab5 のビルドが通り、静的な内蔵 RAM (D/IRAM) は H2 と同じ (126,259 B / 130,186 B)。ファームは両方とも約 +3.2 KB (H2b のカーネルの変更、共通の部分)。sim の標準構成、`rake test` は 6 章。

## 2. H2b: 落ちたアプリの扱い

### 2.1 作ったもの

| 場所 | 変更 |
|---|---|
| `fmrb_kernel.c` / `.h` | 止まったときの canvas の handle を覚える (外部 RAM の 2 B)。2 回目の `fmrb_kernel_show_halt` は同じ canvas を描き直す (重ねない)。`fmrb_kernel_clear_halt()` を足した: canvas を消し、画面の合成を促す present を 1 回送る (canvas を消すだけでは、アプリが次に present するまで画面に残るため) |
| mruby の binding (`picoruby-fmrb-kernel` の kernel.c) と Spinel の FFI | `_clear_halt` を両方に足した (H1 の `_show_halt` と同じ形) |
| `fmrb_kernel.rb` | `@boot_app_mode` (`boot_mode = "app"` で起動したとき真)、最後のエラーとその pid を覚える。`note_launched_app_death`: 単一アプリの端末で、startup_app とサービスの host 以外のアプリが頼まれずに終わったら、`STOPPED` / アプリのパス / エラー / `Launch an app to go on.` を出す。`clear_halt_for`: アプリが立った (`on_app_started`) ときに消す |
| `app_lifecycle.rb` | 終わったアプリのパスを読み、`note_launched_app_death` を呼ぶ (サービスの host と単一アプリの扱いより先。それらが pid を忘れるため) |

- どの起動の経路 (devctl・アプリの run 要求) かは区別しない。単一アプリの端末で startup_app 以外に起動されるのは、事実上 `/app/launch` で起動したものだけ。
- startup_app を 4 回落とした後の give-up の画面も、次に起動したアプリが立てば消える (H2 の申し送りの 2)。
- 消すのは「次のアプリが自分の canvas を作った」時点。起動に失敗したアプリ (コンパイルの失敗など) は canvas を作らずに終わるので、止まったときの画面はその失敗の理由に描き直される。

### 2.2 確かめたこと (AtomS3R、Spinel のカーネル)

1. `/app/launch?path=/app/test/crash_soon.app.rb` → 2 秒後に例外。ログ `Single-app boot: /app/test/crash_soon.app.rb died: crash_soon: failing on purpose (RuntimeError) ...`。tab5_screenshot (`/fb`) の画面は暗い赤の地に `STOPPED`、パス、エラー、backtrace の先頭。
2. `/app/launch?path=/app/test/atoms3r_hello.app.rb` → ログ `halt screen cleared for pid=5`、画面は試しのアプリの絵 (枠・色の帯) に戻った。
3. そのアプリを `/app/kill` → `Cleaning up terminated app` だけで、止まったときの画面は出ない。

- 128x128 では、エラーと backtrace で行が尽き、最後の `Launch an app to go on.` は画面の外に落ちる (シリアルのログには全文がある)。何をすれば消えるかは開発の流れで分かるので、このままにした。理由を 1 行目だけにするかは文言の選択なので変えていない。
- mruby のカーネル (`FMRB_KERNEL_ENGINE=mruby`) の経路は、binding を足しただけで端末では動かしていない (今の端末の構成はどれも Spinel のカーネル)。
- `boot_mode = "desktop"` の振る舞いは、`@boot_app_mode` が偽のままなので変わらない。sim の標準構成で確かめた (6 章)。

## 3. 画面の取り込み口 `/fb`

### 3.1 端末の側

- `devctl_task.c` (Retro・AtomS3R の自前のサーバ) に、`FMRB_HAS_LOCAL_DISPLAY` のときだけ `GET /fb` を登録する。Retro には入らない (画面は子マイコンにある)。Tab5 は rd_http.c のサーバに devctl を載せる形で、`devctl_task.c` を使わないので変わらない。
- 応答: 本文は画素そのもの (RGB565、framebuffer の並びのまま 16 bit の little endian、行の順)。大きさは `X-Width` / `X-Height`、形は `X-Format: rgb565le`。128x128 で 32,768 B。
- 遠隔の画面の取り込み (`display_p4_capture_*`) をその 1 回だけ有効にし、描き直しを促して、できた 1 枚を送ってから無効に戻す。送りは取り込みの場所から直接 socket へ (内蔵 RAM の一時の場所は無い)。
- 取り込みの場所 (2 枚) は PSRAM に最初の `/fb` で取り、以後持ち続ける。今までは高解像度 (640x360) の大きさで取っていたが、PPA の無い端末 (`FMRB_HAS_PPA` が無い) では画面の大きさ (AtomS3R は 32 KB x 2) にした。高解像度の絵が入らないときは、切り詰めずにその回の取り込みを飛ばす (読む側は記録した大きさを信じるため)。P4 は今までどおりの大きさなので、必ず入り、振る舞いは同じ。
- 登録の数: devctl 12 + `/status` + `/fb` = 14 で、今の `max_uri_handlers = 14` に収まる (Retro は 13 のまま)。

### 3.2 PC の側 (tools/mcp)

- `tools/mcp/lib/tab5.rb`: `screenshot` は、`/status` が `"mode":"none"` なら、`"fb":true` のとき `/fb` を読み、Ruby の zlib だけで PNG にする (Tab5 の JPEG の経路はそのまま)。`"fb"` が無い端末 (Retro) は、取れない理由をエラーで返す。
- `fmrb_mcp_server.rb`: 画像の mimeType を結果から選ぶ (PNG / JPEG)。description に AtomS3R の場合を書いた。
- MCP のサーバは起動し直すまで古いコードのまま動くので、この作業ではライブラリ (`FmrbMcp::Tab5#screenshot`) を Ruby から直接呼んで確かめた。tab5_screenshot として使うには MCP のサーバの起動し直しが要る。

## 4. H3: Asterism を S3 のビルドに入れる

### 4.1 入れ方

| 場所 | 変更 |
|---|---|
| `Rakefile` | 新しいビルドの選択肢 `FMRB_ASTERISM` (既定 0)。container に渡す (`ENGINE_ENV_OPTS`)。`BOARD_BUILD_DEFAULTS` の ATOMS3R に `FMRB_ASTERISM=1` |
| `lib/add/family_mruby_esp32.rb` | `FMRB_ASTERISM=1` のとき `picoruby-asterism-zenoh` と `picoruby-asterism` を足す (P4 の構成と同じ 2 行) |
| `components/picoruby-esp32/CMakeLists.txt` | zenoh の ESP-IDF の port のソース 3 本を、P4 に加えて「esp32s3 かつ `FMRB_ASTERISM=1`」でもコンパイルする |

- P4 のビルドは今までどおり常に入る (変えていない)。S3 は全端末でこの選択肢が使える (Retro で `FMRB_ASTERISM=1` を付ければ入る。試していない)。
- rake の側 (gem の一覧) と CMake の側 (port のソース) は、container の同じ環境変数を読むので食い違わない。切り替えるときは libmruby を作り直すため `rake clean` が要る。
- gem・zenoh-pico・Xtensa の向けの直しは要らなかった。gem はビルド名 `esp32` から zenoh-pico の ESP-IDF の platform を選び、PSRAM だけから確保する `zp_system_esp32.c` がそのまま S3 で動く。公開済みの gem は変えていない。

### 4.2 大きさ

| | ファーム | 5M の区画の残り |
|---|---|---|
| AtomS3R (H2) | 0x3BE5F0 (3,925,488 B) | 1,317,392 B (25%) |
| **AtomS3R (H3)** | **0x3E2DA0 (4,074,912 B)** | **1,167,968 B (22%)** |

- 増分 +149,424 B の内訳 (ELF の記号): zenoh-pico と gem の C (`z_*`・`_z_*`・`zp_*`・`zrb_*`) が 69,779 B、Asterism の Ruby のバイトコード (`gem_mrblib_picoruby_asterism*`) が 52,710 B。残りは文字列・記号の表など。H2b と `/fb` の分は数 KB。
- 静的な内蔵 RAM (esp_idf_size の D/IRAM): 111,279 B (H1 は 111,255 B、+24 B: `.dram0.data` +16、`.dram0.bss` +8)。gem の一覧の表が 2 つ伸びた分と見ている (Z2 の P4 と同じ種類)。
- storage は変えていない (`usr/share/asterism` は H1 の除外の一覧から外してある)。

### 4.3 内蔵 RAM (WiFi + zenoh、`IRAM free:` の定常)

| 状態 | IRAM free | PSRAM free |
|---|---|---|
| H2: 試しのアプリだけ、WiFi・devctl あり | 135,748 | 1,388,552 |
| H3: 試しのアプリだけ (このファーム) | 135,708 | 1,388,352 |
| 試しのアプリ + `/app/launch` で 2 本目の試しのアプリ (zenoh なし) | 117,796 | 1,245,200 |
| 試しのアプリ + `asterism_demo` (つながった状態) | 117,564 | 1,124,716 |
| `asterism_demo` を kill した後 | 135,412 | 1,322,776 |
| **`asterism_demo` を startup_app にして起動し、つながった定常** | **135,280** | 1,267,924 |

- アプリ 1 本 (stack 16 KB ほか) で約 18 KB 減るのは zenoh を使わないアプリと同じ。zenoh の接続による内蔵 RAM の減りは 232 B (2 本目が zenoh なしのアプリのときとの差)。P4 で測った 2.4 KB (lwIP の socket) より小さい。
- kill の後の 296 B の差は、閉じた TCP の TIME_WAIT の分と見ている (P4 では約 2 分で戻った。今回は戻るまで待っていない)。
- zenoh のタスクは無い (zenoh-pico は単一のスレッドで、アプリの `poll` から回す)。よって zenoh のタスクの stack は内蔵 RAM に無い。
- `asterism_demo` のタスクの stack の残りは 6,312-6,460 / 16,384 B。VM プールは 512 KB のうち 346 KB を使う (周期のダンプの Used)。
- **H4 に回せる量**: 定常の空き 135 KB、最大の塊は WiFi の後で 96-114 KB。アプリを spawn するときの余裕 (`app_spawn_margin_kb = 30`) を引くと、アプリ (16 KB の stack) をもう 2-3 本、または system オブジェクトの小さいタスクを置く余地がある。

### 4.4 網に入るまで (asterism_demo を startup_app にした起動)

| 時点 | app_main から |
|---|---|
| app_main | 0 |
| カーネルが単一アプリを起動 (`Single-app boot`) | 0.45 s |
| WiFi の起動 (`M1|wifi_ready`) | 0.63 s |
| IP を得る | 2.40 s |
| zenohd につながる (`connected ..., 383 ms`) | 2.80 s |

- リセットから app_main まで約 1.42 秒 (H1 の実測) なので、リセットから網に入るまで約 4.2 秒。
- 最初は、アプリが WiFi の IP より先に接続を試して失敗した (`cannot open a session ... (-102)`、1 回だけ試す作り)。試しのアプリの側で、`FmrbApp.wifi_info` が未接続の間は最大 20 秒待ってからつなぐようにした (WiFi の無い sim・ブラウザ版は `wifi_info` が nil で、すぐつなぐ)。
- 起動直後の接続は 383 ms、起動の後で開き直すと 69 ms。

### 4.5 網と呼び出し

- ルータは親の compose の zenohd (`docker-compose.zenoh-lan.yml` を重ねて 7447 を LAN に開く)。端末の `/home/zenoh_echo.txt` に `tcp/<PC の LAN の IP>:7447`。ノード名は mDNS の名前 `fmruby-XXXXXX` (H2 と同じ決まり)。
- asterism-console (`bin/rails server` + `bin/bridge`) の図: `▣ fmruby-XXXXXX` の下にアプリ demo、オブジェクト screen・apu・info。ルータに client でつながる線。
- console からの呼び出し: Call permissions に node `fmruby-*` / app `demo` / object `info`・`screen` / method `*` を足し、図の screen を選んで `say(["hi from console"])` → `=> 15`、127 ms。端末の画面の `said` に出た。
- PC から (`tools/fmrb_zenoh.rb`、REST 経由): `info.status` → `{"name":"fmruby-XXXXXX","board":"atoms3r","iram_free":117564,...}` (161 ms)、`screen.say "hello from pc"` → 13、`info.boom` → `RuntimeError: boom on ...`、`meta` で公開した 3 つのオブジェクトとメソッドが出る。
- 往復 (PC の CRuby の asterism gem からルータ経由で `info.echo(i)` を 30 回): 最小 98.9 ms、中央値 145.9 ms、最大 184.9 ms。端末の側は `on_update` の周期 (50 ms) と 1 回の描き直し (約 10 ms) の中で答えるので、それが往復の大半を占める。P4 の A1 (35-240 ms) と同じ範囲。

### 4.6 128x128 での表示

- そのままでは読めない (窓 340x130、1 行 52 桁の作り)。試しのアプリの側で、`system_conf.toml` の `display_width` が 320 未満なら、全画面を求め (`request_fullscreen(true)`)、1 行に 1 項目 (ノード名、状態、ノードの数、peer、said) と、ログの行を画面の幅 (21 桁) で折り返して新しいものから詰める形にした。
- 画面 (`/fb` で確かめた): `fmruby-XXXXXX` / `connected` / `nodes 2 +1 -0` / `peer -` / `said hi from console` / ログ (`fmruby-XXXXXX connect` `ed (tcp/...:7447, 69 ms)` `joined: console`)。6x8 の字で読める。
- 320 以上の画面 (Tab5・sim・ブラウザ版) の表示は今までと同じ。

## 7. 気づいたこと・H4 への申し送り

- **MCP のサーバの起動し直し**: tab5_screenshot で AtomS3R の画面を見るには、`tools/mcp` の変更を読み込ませるため MCP のサーバを起動し直す必要がある。ip を渡して使う (`fmruby.local` は Tab5・P4-Nano と取り違える)。
- **試しのアプリの VM プール**: `asterism_demo` は 512 KB のうち 346 KB (68%) を使う。7 割を超えると回収が空回りして止まる既知の性質がある (VM プールの余裕の件)。H4 で system オブジェクトをアプリに載せるなら、プールの大きさか使い方を先に見る。
- **起動直後の接続**: Asterism の gem は 1 回つなぐだけで再接続しない (Z1 の決定)。startup_app として網に入るアプリは、WiFi を待つ処理を自分で持つ必要がある (4.4)。H4 の system オブジェクトを全端末の機能にするなら、WiFi の準備を待つ口 (または gem の側の待ち) を決める必要がある。
- **止まったときの画面の文言**: 128x128 では backtrace で行が尽きる (2.2)。エラーの 1 行目だけにするかはユーザが決める。
- console の DB に Call permissions を 2 行 (node `fmruby-*`、app `demo`、object `info`・`screen`、note `H3 AtomS3R`) 足したまま残した。
