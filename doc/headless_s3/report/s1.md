# S1 報告: StickS3 の 6 軸センサで一歩を検知し、Asterism に流す

> 状態: 完了 (検収待ち、歩いて・振っての確認はユーザ) | 更新: 2026-10-24 | instruction_s1.md の記録。BMI270 の gem を S3 のビルド (StickS3 のみ) に入れ、FIFO を足した。一歩は Ruby で加速度の大きさの立ち上がりを拾い、その場で Asterism のキーに出す。合成の波形では、足の衝撃の山の 16 ms 前 (中央値) に検知し、端末で 4〜7 ms で put、PC に届くまでは put の後 1.5 ms (中央値)。置いたままでは数えない (合成 300 s、実機 30 分以上)。アプリは StickS3 の startup_app にした

## 1. 結果の要約

- **取り込み**: BMI270 の gem (picoruby-bmi270) は develop にすでに入っていた (Tab5 のビルドだけ)。S3 のビルドには新しい選択肢 `FMRB_IMU` で入れ、StickS3 の既定を 1 にした。I2C は Tab5 と同じく画面の側の直列化した窓口 (unit 1) を通るので、C の変更は要らなかった。gem に FIFO を読む口を足した。
- **検知**: Ruby で 3 軸の大きさの山の立ち上がりを拾う方式 (3 章)。BMI270 の歩数計・一歩の検知の機能は使わない。
- **合成の波形** (CRuby、`rake imu:test`): 歩行 677 歩を取りこぼし 0・余分 0、静止 300 s で 0 歩。遅れは衝撃の山に対して中央値 -16 ms (山より前)、90% 点 +6 ms、最大 +125 ms (150 ms の止まりを 20 回の読みごとに入れた場合。止まりなしの最大は +55 ms)。
- **網での値**: `asterism/<端末>/step/pedometer/step` に MessagePack の map (4 章)。一歩ごとと 3 秒ごと。生の加速度は別のキー `.../pedometer/accel` に 20 Hz (切り替えられる、既定 on)。
- **PC に届くまで**: 端末で FIFO を読んでから put まで 4〜7 ms。put から PC まで中央値 1.5 ms、90% 点 8 ms、最大 51 ms (5 章)。合わせて、足の衝撃の山から PC までの見込みは 0〜60 ms 程度で、目標 (100 ms) に入る。
- **PC から**: `reset` を呼べる (往復 61 ms)。`asterism object get` と `tool/imu/step_watch.rb` で値が見える。asterism-console の Plots で生の加速度の線が描けた。
- **内蔵 RAM**: 定常 `IRAM free: 132,208〜132,296 B` (M3s の asterism_demo の定常 132,064 B)。静的な D/IRAM は M3s と同じ 114,863 B。
- **回帰**: `rake test` が通る。Tab5・NARYAv3・AtomS3R のビルドが通り、静的な D/IRAM は変わらない。NARYAv3・AtomS3R はファームも 1 B も違わない (9.3)。
- **画面**: ユーザの指示で字を 2 倍にし、出す物を絞った (6 章)。

## 3. 検知の方式と選んだ理由

### 3.1 方式

`StepDetector` (アプリの中の 1 クラス。CRuby の試験はアプリのファイルからこの部分を切り出して読む):

1. 3 軸の大きさ m = |a| (向きによらず、置いていれば 1 g)。
2. m を軽くならす (時定数 12 ms)。
3. ゆっくりした平均 (時定数 1 s、重力) を引いた dyn = m - 平均。平均は dyn がしきい値より下のときだけ動かす (歩き始めに平均が山に引っぱられて次の山が小さく見えるのを防ぐ)。
4. **dyn がしきい値 rise (150 mg) を上に越えた標本で一歩**。山の頂ではなく立ち上がりで出すので、山を待たない。
5. 次の一歩は、dyn が一度平均より下 (0 未満) に戻り、かつ前の一歩から 250 ms たってから。

- 歩調 (歩/分) は直近 4 つの間隔の平均。2 秒以上空いたら 0 (歩くのをやめた) とし、間隔の記録も捨てる。
- 標本は BMI270 の FIFO から (100 Hz)。アプリは 10 ms ごとにたまった分をすべて読み、最新の標本を「今」、それより前を 10 ms ずつ前として時刻を付ける。描き直しや put で更新が遅れても標本は失われない。
- しきい値と最小間隔は `tune(rise_mg, min_gap_ms)` で網から変えられる (再起動で戻る)。残したいときは `/home/step_sensor.toml` に `rise_mg = 150`、`min_gap_ms = 250` を書く。

### 3.2 BMI270 の一歩の検知を使わなかった理由

- **遅れ**: BMI270 の歩数の機能 (step counter / step detector) は、歩数計として誤検知を減らすために数歩の規則性を見てから数える作りで、最初の数歩はまとめて出る (指示書のとおり)。一歩ごとの出力 (step detector の割り込みの状態) も、山を見終えてから立つので、立ち上がりで出す Ruby の方式より遅い。
- **読み方**: 割り込みの線は S3 に来ていない (M5PM1 の G4) ので、どちらにしても状態のレジスタを周期的に読みに行くことになり、遅れの下限は読む周期で決まる。Ruby で生の値を読んでも I2C の回数はほとんど変わらない (FIFO の長さと中身の 2 回)。
- **設定**: 一歩の検知を使うには機能のページ (feature page) の設定と割り込みの割り当てを足す必要があり、今の設定データ (M5Unified の配列) で何が使えるかの確認もいる。Ruby の方式はしきい値をその場で変えられる (来週の用事の場で調整できる)。
- **誤検知**: 指示書の条件は「止まっているときに数えない」で、振る・叩くは許す。大きさのしきい値はこの条件に合う (3.3、7 章)。

### 3.3 合成の波形での数と遅れ

`ruby tool/imu/test/step_detector_test.rb` (`rake imu:test`、`rake test` に入れた)。重力 1 g を無作為の向きに固定し、その向きに沿って一歩ごとの衝撃 (ガウスの山、幅 25 ms、0.35 g ± 20%) と体の上下 (歩調の正弦、0.12 g)、横に揺れ (0.05 g)、白い雑音。間隔は ± 8% ゆらす。アプリの読み (10〜16 ms ごと、40 回ごとに 60 ms 止まる) を FIFO として再現する。遅れは衝撃の山の時刻から、一歩を出した読みの時刻まで (衝撃は山の約 50 ms 前から立ち上がる)。

| 場合 | 真の歩数 | 検知 | 取りこぼし | 余分 | 遅れ ms (最小 / 中央 / 90% / 最大) |
|---|---|---|---|---|---|
| 歩行 1.5 歩/秒 | 60 | 60 | 0 | 0 | -34 / -22 / -4 / 46 |
| 歩行 2.0 歩/秒 | 79 | 79 | 0 | 0 | -32 / -20 / -10 / 39 |
| 歩行 2.5 歩/秒 | 100 | 100 | 0 | 0 | -30 / -18 / -10 / 42 |
| 歩行 2.0、弱い (衝撃 0.22 g) | 80 | 80 | 0 | 0 | -16 / -5 / 1 / 48 |
| 歩行 2.0、雑音 0.03 g | 80 | 80 | 0 | 0 | -35 / -20 / 5 / 40 |
| 歩行 2.0、読みが遅い (20〜30 ms ごと) | 80 | 80 | 0 | 0 | -31 / -16 / -4 / 20 |
| 歩行 2.0、鋭い衝撃 (幅 12 ms) | 80 | 80 | 0 | 0 | -13 / -3 / 6 / 55 |
| 歩行 2.0、20 回の読みごとに 150 ms 止まる | 80 | 80 | 0 | 0 | -31 / -17 / 81 / 125 |
| 歩く 10 秒、止まる 5 秒、歩く 10 秒 | 38 | 38 | 0 | 0 | -27 / -20 / 33 / 46 |
| 静止 120 s (雑音 0.004 g) | 0 | 0 | — | 0 | — |
| 静止 120 s (雑音 0.03 g) | 0 | 0 | — | 0 | — |
| 静止 60 s、ゆっくり 90 度傾ける | 0 | 0 | — | 0 | — |

- 歩調: 2.0 歩/秒の規則的な歩行で 120 歩/分、最後の一歩の 3 秒後は 0。
- 遅れが負なのは、山の手前の立ち上がりで出すため。最大の側は、山の手前で読みが止まった場合 (止まりの間にたまった標本は、次の読みでまとめて検知される)。
- 最初の版は FIFO を使わず、最新の値だけを読んでいた。鋭い衝撃が 1〜2 標本しかしきい値を越えず、読みの抜けでその一歩を取りこぼした (40 秒に 3 歩)。FIFO に替えて 0 になった。
- 模型は単純なので、実物の歩き方 (手に持つ、ポケット、首から下げる) で山の大きさと形は変わる。7 章の確認で、しきい値が合うかを見てほしい。

## 4. 網での値の形

アプリ名 `step`、オブジェクト `pedometer`。ノード名は M3s と同じ (mDNS の名前 `fmruby-XXXXXX`)。

### 4.1 一歩の値 (`asterism/<端末>/step/pedometer/step`)

MessagePack の map (`asterism_values` と `asterism object get` で読める形):

| キー | 中身 |
|---|---|
| `steps` | 通算の歩数 (reset で 0) |
| `t_ms` | その一歩の時刻 (端末の時計、起動からの ms。まだ無ければ nil) |
| `interval_ms` | 前の一歩からの間隔 (2 秒を超えたら 0) |
| `cadence` | 歩調 (歩/分、直近 4 間隔。止まって 2 秒で 0) |
| `ago_ms` | put した時点で、最後の一歩から何 ms たったか |
| `sent_ms` | put した時刻 (端末の時計) |
| `event` | `"step"` (一歩)、`"repeat"` (3 秒ごとの同じ値)、`"reset"`、`"state"` (接続した直後) |
| `sensor` | `"ok"` かセンサの不具合の理由 |
| `raw` | 生の加速度を出しているか |

- 受け側は `steps` の変化か `event == "step"` で一歩を知る。繋いだ直後は 3 秒以内に `repeat` で今の値が来る。
- 端末の時計と PC の時計の関係は `pedometer.clock` で取れる (4.3)。

### 4.2 生の加速度 (`asterism/<端末>/step/pedometer/accel`)

20 Hz (5 標本に 1 回)、MessagePack の map、**すべて mg の整数**: `x`・`y`・`z` (その時の標本)、`m` (その大きさ)、`m_peak` (前の put からの大きさの最大。間引いても衝撃が見える)、`dyn` (平均からの差、検知がしきい値と比べる量)、`rise` (しきい値)、`steps`。一歩の put の後に出す (一歩を待たせない)。`pedometer.raw(true / false)` で切り替え、既定は on (5 章のとおり、on の方が往復が速い)。

### 4.3 メソッド (`<端末>/step/pedometer`)

| メソッド | 返り |
|---|---|
| `reset` | 歩数を 0 にし、reset の後の状態 (4.1 の map)。`event: "reset"` の値も出す |
| `state` | 今の状態 (4.1 の map) |
| `clock` | 端末の時計 (ms) |
| `tune(rise_mg, min_gap_ms)` | 検知の設定を変え、その値 (rise は 30 mg 以上、間隔は 100 ms 以上に丸める) |
| `raw(on)` | 生の加速度を出すか。返りは新しい値 |

## 5. PC に届くまでの時間

| 区間 | 値 | 測り方 |
|---|---|---|
| 衝撃の山 → 検知 | 中央値 -16 ms、90% 点 +6 ms (3.3) | 合成の波形 |
| 標本 → 読む | 0〜10 ms + BMI270 の中のならし | 読みの周期 10 ms |
| 読む → put の後 | 4〜7 ms | 端末のログ (`ms to put`) |
| put → PC | raw on: 中央値 1.5、90% 点 8.0、最大 50.7 ms (40 回)。raw off: 1.4 / 5.7 / 13.4 ms (41 回) | 下の通り |

- **put → PC の測り方**: 端末が put の直後にシリアルにその `sent_ms` を書く版を一時的に置き (コミットしていない)、PC の同じ時計で、シリアルの行が届いた時刻と Asterism の値が届いた時刻を比べた。シリアル (USB) の遅れは数 ms 以下なので、値は「put の後、シリアルの行より何 ms 遅れて網から届いたか」になる。PC と端末の時計を合わせる必要がない。
- **時計を合わせる方法は WSL2 では使えなかった**: PC の `CLOCK_MONOTONIC` は端末の時計に対して 1% 遅れて進み (端末の 61.2 秒が 60.6 秒)、壁の時計は 20 秒ほどごとに最大 300 ms 戻される (のこぎりの形)。`clock` の往復 (最短 20〜30 ms) で直線を当てはめても、届くまでの時間の推定に ± 100 ms のゆれが残った。`step_watch.rb` の delay の欄はこの方法なので目安 (7 章)。
- **呼び出しの往復** (PC → 端末 → PC、`asterism ping --call state` 40〜60 回): raw on は平均 37〜41 ms (最小 20〜25 ms)、raw off は平均 74〜94 ms (最小 27〜40 ms)。交互に 4 回測って同じ傾向。端末の WiFi の省電力 (待ちの間に受信を溜める) で、端末に向かう向きが遅れると見ている。生の加速度を流していると無線が起きたままになる。一歩の値は端末から出る向きなので、この差は小さい (上の表の put → PC)。
- PC からの `reset` は 61 ms で返った。
- 端末のアプリの忙しさ (`update busy`、10 秒のうち on_update の中にいた時間): raw on 5.1〜5.4 秒、raw off 4.5 秒。1 回の on_update の最大は通常 22〜40 ms。

## 7. ユーザに確認してほしいこと (歩く・振る)

前提: 親の compose の zenohd を zenoh-lan を重ねて起動したまま (今も動いている)、StickS3 の `/home/asterism/config.toml` に手元の zenohd (書いてある)。StickS3 は電源を入れると step_sensor が起動し、画面の上の行が `WiFi ok` と `AST ok` になる。

1. **PC で値を見る**: fmruby-core で `ruby tool/imu/step_watch.rb fmruby-XXXXXX --reset` (ノード名は `asterism node list --router tcp/127.0.0.1:7447`)。一歩ごとに `step N cadence ... delay ...` の行が出る。
2. **歩く**: StickS3 を手に持って (またはポケット・首から下げて、来週の持ち方で) 20 歩、数えながら歩く。**合格**: 画面と PC の歩数が実際の歩数 ± 1〜2、足が着くのと画面・PC の行がほぼ同時 (体感で遅れない)、歩調が 100〜130 歩/分くらい。
   - delay の欄は WSL2 の時計のため ± 100 ms ほどゆれる目安 (5 章)。体感の遅れの方を見てほしい。
3. **止まる**: 机に置いて 1 分。**合格**: 数が増えない。PC にも step の行が出ない (3 秒ごとの repeat は出る)。置く瞬間の 1 歩は許す (叩くと同じ)。
4. **振る**: 手で振る・机を叩くと数える (仕様どおり)。
5. **reset**: KEY1 を押すと 0 になる。PC から `asterism call fmruby-XXXXXX/step/pedometer reset --router tcp/127.0.0.1:7447` でも 0 になる。
6. **合わないとき**: 歩いても取りこぼすならしきい値を下げる (`asterism call fmruby-XXXXXX/step/pedometer tune 100 250 --router ...`)。1 歩を 2 回数えるなら最小間隔を上げる (`tune 150 350`)。決まった値は `/home/step_sensor.toml` に `rise_mg = ...`、`min_gap_ms = ...` で残せる。歩いたときの生の値は `step_watch.rb ... --accel` か console の Plots で見られる (`dyn` が一歩ごとに `rise` を越えているか)。
7. **画面**: 2 倍の字と 7 セグメントの数字が読めるか、明るさ。
8. **抜き差し**: 電源ボタン (1 回押し) で起動し直し、30 秒以内に `AST ok` に戻るか (前の自分が網に残っていると「already on the network」で 3 秒待って繋ぎ直す。実機で 1 回確認済み)。

この作業中、シリアルを開いて端末をリセットした約 17 秒後 (PC の時計で 15:31 ごろ) に、6 秒間で 12 歩が記録された。直前の dyn は -300 mg ほどの沈み込みのあと +330〜1,548 mg の山で、歩調 94〜180。手で持って動かしたときの形なので、**この時刻に端末に触ったかを教えてほしい** (触っていなければ、勝手に数えた例として調べる)。

## 9. 内蔵 RAM・安定性・回帰

### 9.1 内蔵 RAM と VM プール

| | StickS3 (今回、step_sensor) | M3s (asterism_demo) |
|---|---|---|
| 静的な D/IRAM | 114,863 B | 114,863 B |
| 定常 `IRAM free:` (WiFi + zenoh、startup_app で起動) | 132,208〜132,296 B | 132,064 B |
| `M1|debugd` | 133,804 B | 133,772 B |
| アプリのタスクの stack の残り | 6,452 / 16,384 B | — |

| VM プールの Peak | 468〜491 KB (起動の直後、BMI270 の初期化と接続) | — |

- 内蔵 RAM は増えていない (gem はバイトコードで flash、FIFO の読みは VM プール)。
- **VM プールは 7 割に近い** (`project_vm_pool_headroom` の注意の域)。大半は Asterism の gem で、asterism_demo と同じ程度。起動の直後の Peak 96% は初期化 (8 KB の設定データと 128 B の塊の配列) のごみ。定常で 30 分以上、プールで死ぬことも、目立つ止まり (update の最大 40 ms 程度) も無かった。

### 9.2 安定性

- `Guru|abort` 0 (この作業のシリアルのログ全体、flash の後の約 1 時間)。
- devctl の kill と launch を 10 回以上: 端末は落ちず、次の起動でまた繋がる。`on_destroy` で Asterism を閉じる。
- 起動直後の「already on the network」(前の自分がルータに残る) → 3 秒後に繋がった (実機)。
- 置いたままの時間 (約 30 分、7 章の 12 歩の前後を除く) に勝手な一歩は無かった。ただし最初の版 (FIFO・記録の前) の 30 分ほどの間に 1 回だけ、置いたままのはずの時刻に 1 歩が記録された (09:26)。原因は分かっていない (机の揺れか、人が触れたか)。今の版は一歩ごとに直前 8 標本の dyn をログに出すので、次に起きれば区別できる。

## 10. 残件

- 7 章の歩く・振る確認 (ユーザ)。しきい値 150 mg・最小間隔 250 ms は合成の波形で決めた値。
- 9.2 の置いたままの 1 歩の原因。
- `step_watch.rb` の delay の欄は WSL2 の時計のため目安。正確に測るなら 5 章のシリアルと比べる方法 (put の後にシリアルに書く版が要る)。
- VM プールの余裕 (7 割)。Asterism を使うアプリ共通の話で、プールの大きさを変えるならファームの側。
- BMI270 の FIFO が溢れた (3 秒以上読まなかった) ときは古い標本が捨てられる。アプリが 3 秒止まることは今は無い。
- 受け側 (ブラウザ版で歩くキャラ) は次の段。値の形は 4 章。
- 端末の時計 (`t_ms`) は起動からの ms。S3 は NTP で時刻を合わせていないので、壁の時計の時刻は値に入れていない。
