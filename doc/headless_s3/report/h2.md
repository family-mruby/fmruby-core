# H1e・H2 報告: 5 MB に余裕を作り、WiFi で開発の流れを回す

> 状態: 完了 (検収待ち、sim の標準構成の確かめは保留中) | 更新: 2026-10-12 | instruction_h1e_h2.md の記録。端末ごとのビルドの既定 (`BOARD_BUILD_DEFAULTS`) と、日本語のフォントを外す一般の選択肢 `FMRB_FONT_JA` を足した。AtomS3R はコマンドラインの追加なしでビルドでき、ファームは 3.74 MB、5M の区画の残りは 1.26 MB (25%)。WiFi につながり、mDNS の名前で見つかり、PC からアプリを置く・起動する・書き換えて起動し直す流れが再 flash なしで回る。遠隔の画面の取り込みは S3 では使えない (stream が無い)。WiFi を使った状態の内蔵 RAM の空きは 135,748 B

## 1. 結果の要約

- **ビルド**: `FMRB_HW_TARGET=ATOMS3R rake build:esp32` だけで、エディタは mruby、Spinel の FFT なし、日本語のフォントなしになる。どれもシェルの環境変数で上書きできる。
- **flash**: ファーム 0x3BE5F0 (3,925,488 B)、5M の区画の残り 0x141A10 (1,317,392 B、25%)。H1 (エディタ mruby・FFT なし) から 1,083,104 B 減った。ほぼ日本語のフォント 3 つの分 (1,083,758 B)。
- **`FMRB_FONT_JA=0`**: 端末で `set_font(:ja, 16)` が `[:ja, 8]` を返し、例外にならない (`:ja_bold, 12` も `[:ja, 8]`)。sim (Spinel のカーネルとエディタ、`FMRB_FONT_JA=0`) で、デスクトップ・エディタ (かなの入力を含む)・F1 のヘルプ・シェルが例外なく動く。
- **他の端末**: 既定 (`FMRB_FONT_JA=1`) で、Retro はファーム +688 B、Tab5 は +560 B。静的な内蔵 RAM は両方とも H1 と同じ (DIRAM 126,259 B / 130,186 B)。`rake test` は通る。
- **WiFi**: 起動からつながり、mDNS の名前 `fmruby-XXXXXX.local` は Windows の名前解決で端末の IP に引ける。
- **開発の流れ**: MCP の tab5_fs / tab5_app に ip を渡して、置く → kill → 起動 → 書き換えて置き直す → kill → 起動、が回る。そのために devctl の自前のサーバに `/status` を足した (4.1)。**画面の取り込み (tab5_screenshot) は S3 では使えない**。
- **内蔵 RAM**: WiFi・mDNS・devctl を足した定常の空きは 135,748 B (WiFi なしの H1 は 213,824 B、差 78,076 B)。開発の流れを何度か回した後も 135,708 B で、減り続けない。

## 2. H1e: 作ったもの

### 2.1 端末ごとのビルドの既定 (A)

- `Rakefile` に `BOARD_BUILD_DEFAULTS` (端末の名前 → 環境変数と値) を置いた。ATOMS3R は `FMRB_APP_ENGINE_EDITOR=mruby`、`FMRB_FFT_SPINEL=0`、`FMRB_FONT_JA=0`。
- 優先の順は **シェル > 端末の既定 > `.env`**。`.env` は開発者の手元の普段の選択 (たいてい別の端末向け。今の手元は Spinel のエディタ) なので、端末の既定がそれに勝つ。シェルで渡したものは端末の既定に勝つ (`FMRB_HW_TARGET=ATOMS3R FMRB_FONT_JA=1 rake build:esp32` で日本語のフォントを入れられる)。
- 区別のため、`.env` の読み込みは自分が入れた変数の名前を覚える (`DOTENV_KEYS`)。
- ビルドの記録で確かめた: ATOMS3R のビルドの docker の行は `-e FMRB_APP_ENGINE_EDITOR=mruby -e FMRB_FFT_SPINEL=0 -e FMRB_FONT_JA=0` (`.env` は editor=spinel)。Retro・Tab5 のビルドは `FMRB_FONT_JA=1` のまま。

### 2.2 `FMRB_FONT_JA` (B)

既定 1。0 のときの流れ:

| 場所 | 0 のときの振る舞い |
|---|---|
| `Rakefile` | `FMRB_FONT_JA` を container に渡す (ほかのエンジンの選択と同じ `ENGINE_ENV_OPTS`) |
| `fmrb_hw_defines.cmake` | `FMRB_NO_FONT_JA` を定義する (全端末、Linux も)。否定の名前にしたのは、定義の無い経路 (wasm など) が今までどおり「フォントあり」になるため |
| `display_p4_task.cpp` | `SET_FONT` の JA と JA 太字は大きさを問わず misaki 8。efontJA を一つも名指ししないので、リンカが落とす |
| `const.c` / Spinel の定数の生成 | `FmrbConst::FONT_JA` (真偽値) を両方のエンジンに置く |
| `FmrbGfx.resolve_font` (mruby) | 使えるフォントの表を `[[:default], [:ja, 8]]` にする。`:ja` と `:ja_bold` は大きさを問わず `[:ja, 8]` を返す |
| Spinel の `set_font` と C の shim | 大きさを 8 にする |
| エディタ (`font.rb`) | 編集の欄の升目を misaki の大きさ (半角 4、行 8) にする。どの大きさを選んでも同じ |
| シェル | 升目を misaki の大きさにする (半角 4、行 8) |

- 端末の中で描く端末 (AtomS3R・P4) ではフォントの実体がファームから消える。描画を子マイコンに出す端末 (Retro) では、フォントは子マイコンのファームにあるので、変わるのは選択だけ (子マイコンの側は触っていない)。
- ELF の記号で確かめた: AtomS3R の像に `efontJA_*` は無く、`misaki_8` (117,554 B) だけが残る。
- `set_font` が `[:ja, 8]` を返すので、アプリは置き換わったことが分かる。エラーにはしない。
- エディタとシェルの升目の切替は、外したときの見た目を合わせるための最小の追従。日本語のフォントを前提にしたほかの所 (ヘルプ、PicoRabbit など) は `set_font` の返り値か描画の側の置き換えに任せ、手を入れていない。

### 2.3 外した構成で確かめたこと (sim、`FMRB_FONT_JA=0`)

sim の標準のエンジン (Spinel のカーネル、Spinel のエディタ、mruby のデスクトップ、Modern の 426x240) に `FMRB_FONT_JA=0` を付けてビルドした。

| 対象 | 結果 |
|---|---|
| デスクトップ | 起動して壁紙・メニューバーが出る |
| エディタ (Spinel) | 起動し、`puts 1` と、かなの入力 (Ctrl+Space で「にほんご」) が入る。字は misaki 8 で、升目が字に合う |
| エディタの F1 のヘルプ | `puts` のヘルプが開く (misaki 8) |
| シェル | 起動して `ls` が動く。字は misaki 8 の升目 |
| core のログ | error / exception / Guru / abort は 0 件 |

- Spinel のエディタで `FmrbConst::FONT_JA` を読む経路 (生成した定数は `FONT_JA = false`) と、mruby のシェル・デスクトップの経路の両方を通った。
- 端末 (AtomS3R) では、試しのアプリで `set_font(:ja, 16)` → `[:ja, 8]`、`set_font(:ja_bold, 12)` → `[:ja, 8]`、`font_height` → 8 をログで確かめた。

## 4. H2: WiFi と開発の流れ

### 4.1 作ったもの

- `config/system_conf_atoms3r.toml`: `wifi_auto_start = true`。WiFi の設定は `config/wifi.toml` (手元にあるもの) を、S3 の今の流儀どおりビルドが storage の像の `etc/wifi.toml` に入れる。像を作るときに「WiFi の認証情報を含むので配らない」と注意が出る (既存の仕組み)。
- **devctl の `/status`**: 遠隔の画面の無い端末 (Retro・AtomS3R) は devctl が自前の小さい HTTP サーバを立てて `/app/*`・`/fs/*` を出しているが、`/status` が無かった。MCP の tab5_* は最初に `/status` を見て Family mruby の端末かを確かめるので、404 で断られた。自前のサーバに限り、rd_http.c と同じ形の `{"ip":…,"mode":"none","streaming":false}` を返すようにした。遠隔の画面のある Tab5 は rd_http.c の `/status` のままで、変わらない。

### 4.2 起動と WiFi (端末で実測)

- WiFi の起動はカーネルの ready とアプリの spawn の後 (`M1|` の順)。WiFi はアプリの最初の絵を遅らせない。
- アプリの起動 (`spawn:` の行) から約 3.3 秒で IP を得る (AP との接続は約 0.05 秒、DHCP が残り)。
- ログ: `wifi: mDNS hostname: fmruby-XXXXXX.local`、`Connected, ip=… (http://fmruby-XXXXXX.local/, also http://fmruby.local/)`。
- mDNS: WSL2 の `getent` は mDNS を引かない (手元の環境の性質)。Windows の名前解決 (`Resolve-DnsName fmruby-XXXXXX.local`) は端末の IP を返した。MCP の tab5_ip の自動の解決も、この Windows の経路を使う。今回は IP を渡して使った (手元に Tab5 と P4-Nano もあり、共有の名前 `fmruby.local` は取り違えるため)。

### 4.3 開発の流れ (再 flash なし)

MCP のツールに ip を渡して次を回した:

1. `tab5_ip` → `{"mode":"none","streaming":false}` を返す。
2. `tab5_fs push` で `devloop.app.rb` と `.app.toml` (`default_window_mode = "fullscreen"`) を `/app/dev/` に置く。
3. `tab5_app ps` → kernel (pid 0) と起動のアプリ (pid 4)。`kill 4` → `launch /app/dev/devloop.app.rb` → pid 4 で起動し、128x128 の全画面になる。
4. 版の文字を書き換え、`tab5_fs put` で置き直し → `kill` → `launch`。ログに新しい版が出る (kill から新しい版のログまで約 1.2 秒)。
5. 後片付け (ファイルを消して、起動のアプリを `launch` し直した)。

| 操作 | 時間 |
|---|---|
| `/fs/put` 256 KB | 2.17 s / 2.23 s (約 118 KB/s) |
| `/fs/get` 256 KB | 0.91 s / 0.45 s (約 290-580 KB/s)。読み戻した中身は一致 |
| `/fs/put` 小さいアプリ (838 B) | 約 0.1 s |
| `/app/list` | 約 17 ms |
| kill → launch → アプリの `on_create` | 約 0.6 s |

- **遠隔の画面の取り込みは使えない**。tab5_screenshot は rd_http.c の `/stream` (MJPEG) から 1 枚取るが、S3 には遠隔の画面 (rd_*) が入っていない (`/stream` は 404)。S3 には JPEG のハードウェアの符号器が無いのが入れていない理由。画面の確かめは、今は sim で同じアプリを動かすか、ユーザの目で行う。128x128 なら RGB565 で 32 KB なので、生の画素を返す小さい経路 (例: `/fb` で 1 枚) を devctl に足せば取り込めるはず (案。作っていない)。
- `.app.toml` の無いアプリを `launch` すると、窓の既定の大きさ 100x100 の canvas で起動する (デスクトップが無いので枠も無い)。全画面にするには `.app.toml` に `default_window_mode = "fullscreen"` を書く。

| spawn:Small Screen Test | 224,852 | 184,320 |
| wifi_ready | 155,972 | 114,688 |
| devctl | 144,396 | 104,448 |
| debugd | 136,928 | 96,256 |

- 内訳: WiFi (driver・lwIP・mDNS の task) 約 68.9 KB、devctl (httpd の task と socket) 約 11.6 KB。H1 の WiFi なしの定常 213,824 B から 78,076 B 減。
- task の stack の残り (定常): fmrb_kernel 6,008 / 16,384、アプリ 6,304 / 16,384、fmrb_host 10,520 / 24,576、debugd 3,068 / 6,144、status_led 1,428-1,988 / 4,096 (WiFi の後に下がる)。
- PSRAM の空きは 1,388,552 B (WiFi なしは 1,455,180 B)。

### 4.5 H3 (zenoh) に回せる量の見込み

- 今の空きは 135.7 KB、最大の塊は 96 KB。
- P4 の Z2 の実測では、zenoh-pico の確保は PSRAM だけで、内蔵 RAM の減りは接続中の socket 1 本分 (約 2.4 KB、lwIP) だった。Asterism のアプリの VM と stack は今の試しのアプリと同じ枠 (stack 16 KB は内蔵) に収まる見込み。
- 見込み: zenoh と Asterism を足しても内蔵 RAM の減りは 5-10 KB 程度、空きは 125 KB 前後。アプリを spawn するときの余裕 (`app_spawn_margin_kb = 30`) を引いても、アプリ 1 本の stack を 2-3 本分増やせる程度の余地がある。zenoh-pico の task (受信・lease) の stack を内蔵に取るなら 1 本 4-8 KB を足す。
- flash は 1.26 MB 空いており、P4 で +100 KB 前後だった zenoh と Asterism は十分に入る。

## 5. 単一アプリの扱いと開発の流れ

H1 の申し送りの 2 点を端末で確かめた。

1. **kill の後に `/app/launch` したアプリは単一アプリとして扱われない**: 確かめた。`crash_soon.app.rb` を `launch` すると、例外の後は起動し直さず、`/app/list` は kernel だけになる。画面は最後の絵のまま。
   - 開発の流れでは、**起動し直さないこと自体は困らない** (落ちたものを繰り返し起動されるより、止まってくれる方が直しやすい)。
   - **困るのは、落ちた理由が WiFi の側から見えないこと**。理由はシリアルのログにしか出ず、`/app/list` からは消えるだけ。USB を挿さずに WiFi だけで開発する形では、落ちたことにも気づきにくい。
2. **止まったときの画面 (z=255) が、後から起動したアプリを隠す**: カーネルの作り (`give_up_single_app` が z=255 の canvas を作り、消す所が無い) から、今もそうなる。startup_app を 4 回落とした後に開発の流れに入ると、起動したアプリが見えない。端末では画面を取り込めないので、目では確かめていない。

直し方の案 (仕様の選択なので作っていない):

- **案 1 (おすすめ)**: `boot_mode = "app"` のとき、`/app/launch` などで起動したアプリが例外で終わったら、起動し直しはせず、止まったときの画面にその理由を出す (`STOPPED`・理由・「Reset to try again.」は今のまま)。あわせて、アプリを起動するときに止まったときの画面が残っていれば消す。開発の流れでは、落ちたら画面に理由が出て、次の launch で消える。
- **案 2**: 案 1 に加え、`/app/list` (または `/status`) に最後に落ちたアプリのパスとエラーの 1 行目を載せる。画面の取り込みが無い S3 では、PC から理由を読めるのはこれだけになる。
- **案 3**: `/app/launch` に「単一アプリとして起動し直す」を付ける (例: `?single=1`、または `startup_app` のパスと同じなら単一アプリとして扱う)。差し替えた startup_app を、起動し直しの回数を数え直して起動する。運用の形 (落ちても起動し直してほしい) を開発中にも試したいときに使う。

## 7. 気づいたこと

- **flash の後にシリアルの capture が止まる**: H1 の書き込みの手順 (ビルドの docker の esptool で `/dev/ttyACM1` に直接書く) を capture を開いたまま使うと、書き込みのリセットで capture が `device reports readiness to read but returned no data` で落ちる。`serial_log` は落ちた後も古い行を見せ続ける (`running: true` のまま) ので、気づきにくい。書き込みの後は `serial_stop` → `serial_start` (port は `/dev/ttyACM1`) で開き直す。
- **`rake clean_all` は wasm の libmruby を消す**: この作業で `rake clean_all` を 3 回使った (端末の切替)。wasm の libmruby は作り直していない (ブラウザ版の操作中は wasm に触らない指示のため)。ブラウザ版をビルドし直す前に `rake wasm:mruby` が要る。
- **Spinel の定数の生成**: `gen_app_combined.rb` は生成済みの定数のファイルがあると作り直さない。カーネルが Spinel の構成では、カーネルの生成が先に作り直すので問題は無い。カーネルを mruby、エディタを Spinel にして `FMRB_FONT_JA` だけを変えると古い値が残りうる (今の構成の組み合わせでは起きない)。

## 8. 端末の状態

- AtomS3R (`/dev/ttyACM1`): H1e・H2 の最後のファーム (feature/headless-h1、`boot_mode = "app"`、試しのアプリ、WiFi あり、devctl の `/status` あり)。WiFi につながっている。`/app/dev/` の試しのファイルは消した。
- P4-Nano (`/dev/ttyACM0`) には触っていない。
- `build/` は Linux の標準の構成 (x86-64、`FMRB_FONT_JA=1`)。sim は `FMRB_FONT_JA=0` の像で上がったまま (下ろす指示待ち)。
