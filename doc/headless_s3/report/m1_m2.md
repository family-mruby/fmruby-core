> 状態: 完了 (検収待ち) | 更新: 2026-10-12 | instruction_m1_m2_m4.md の記録。`display_p4` を `display_local` に名前だけ変え (M1)、端末ごとの違いを「端末の画面の口」(`board/board_display.h`) の実装 4 つに追い出して描画の部品から端末名の分岐を 0 にし (M2)、CI に `build-esp32 (ATOMS3R)` を足した (M4)。全構成で静的な内蔵 RAM は develop と同じ。AtomS3R は焼いて、画面の取り込みが develop の像と画素単位で一致した。Tab5・NARYAv4 は実機で見ていない (7 章)

### 2.2 M2: 端末の画面の口

ヘッダ `main/drivers/display_local/board/board_display.h` に口を書いた。描画の部品 (`display_local_task.cpp`、出力の backend) は、端末ごとの違いをこれだけで扱う。

| 関数 | 中身 |
|---|---|
| `board_display_lcd()` | 端末の LovyanGFX の device (端末の型の静的な object) |
| `board_display_configure()` | 電源・識別・panel の取り付け (背光と touch を含む)。どの端末を立ち上げるかのログもここ。false なら init しない |
| `board_display_after_init()` | init の後の向き (Tab5 の `setRotation(3)`) |
| `board_display_after_audio()` | codec が立った直後、touch の task が読み始める前の 1 回だけの読み取り (Tab5 のヘッドホンの初期状態) |
| `board_display_panel_framebuffer()` | panel 自身の frame buffer (PPA が直接書く。SPI の panel と panel なしは NULL) |
| `board_display_i2c_write` / `_read` / `_write_reg8` | `display_local_i2c_*` の中身。引数の確かめと lock は描画の側 (`display_local_task.cpp`) が済ませてから呼ぶ |
| `board_display_poll_headphone()` | 共有のバスの周期の仕事 (touch の task の loop から)。必要なら自分で lock を取る (`display_local_i2c_lock/unlock`) |

コンパイル時の事実は端末ごとの `board_display_conf.h`:

| マクロ | 意味 | tab5 | naryav4 | atoms3r | none |
|---|---|---|---|---|---|
| `BOARD_DISPLAY_NO_PANEL` | panel が無い | 0 | 0 | 0 | 1 |
| `BOARD_DISPLAY_OWNS_I2C` | I2C のバスの持ち主が描画の側 | 1 | 1 | 1 | 0 |
| `BOARD_DISPLAY_FB_W/H/BPP/ROTATED` | PPA が書く frame buffer | 720x1280、2、回す | 1280x720、3、回さない | なし | なし |

- **背光の明るさ**: 口に関数を置かなかった。どの端末も背光 (Tab5 の PWM、AtomS3R の LP5562) を `configure` の中で LovyanGFX の device に付けるので、明るさは `board_display_lcd()->setBrightness()` でどの端末でも同じに変えられる。今は誰も実行時に変えていない (H4 で背光をオブジェクトにするときは、描画の側にこれを呼ぶ関数を 1 つ足せば、端末ごとの作業は要らない)。
- **I2C のポートの持ち主**: `BOARD_DISPLAY_OWNS_I2C`。持たない端末 (ブラウザ版) では `display_local_i2c_*` が「できない」(`FMRB_ERR_NOT_SUPPORTED`) を返す。今までと同じ。
- **小さい画面の振る舞い**: 端末の事実にしていない。起動の画面の小さい版は今までどおり panel の幅 (320 未満) で選ぶ。止まったときの画面の 1 行の扱いもカーネルの側で画面の幅のまま。

**実装** (`main/drivers/display_local/board/<名前>/`):

| 実装 | 中身 | 出どころ |
|---|---|---|
| `tab5/` | PI4IO の電源の手順、touch で panel の種類を判別、`LGFX_Tab5`、回転、lgfx の I2C (port 1)、ヘッドホンの検出と speaker の切り替え | `display_local_task.cpp` からそのまま移した。`lgfx_tab5.hpp` もここへ |
| `naryav4/` | `LGFX_Naryav4` の `configure` が作るバスを持ち、i2c_master で読み書き | 同上。`lgfx_naryav4.hpp` |
| `atoms3r/` | SPI の panel の判別 (`LGFX_AtomS3R`)、lgfx の I2C (port 1、LP5562 と BMI270 のバス) | 同上。`lgfx_atoms3r.hpp` |
| `none/` | panel の無い `LGFX_Device` (sprite の親だけ) | ブラウザ版 |

- **どれを入れるか**: CMake の `fmrb_hw_board_display()` (`components/fmrb_common/fmrb_hw_defines.cmake`) が端末から選ぶ (P4 は NARYAv4 なら naryav4、ほかは tab5。S3 は ATOMS3R なら atoms3r。それ以外は無し)。`main/CMakeLists.txt` がその `.cpp` と道 (`board/` と `board/<名前>/`) を足す。ブラウザ版は `wasm/CMakeLists.txt` が none を指す。
- Linux の sim は display_local を使わない (描画は graphics-audio)。口の実装も要らない。
- `dpi_fb_align.hpp` は Tab5 と NARYAv4 が共有するので `display_local/` に残した。

**PPA の backend**: Tab5 と NARYAv4 で送り出しの道が違う (回して RGB565 / 回さず RGB888)。`FMRB_HW_NARYAV4` で分けていたのを、frame buffer の事実 (`BOARD_DISPLAY_FB_BPP`・`_ROTATED`) で分けるようにした。道は今の 2 つのまま。それ以外の組み合わせは `#error` で止まる (新しい P4 の端末を足すときに気づくため)。

- `main/CMakeLists.txt`: どのソースを入れるか (P4 の一式、ATOMS3R の一式、NARYAv4 では touch と Tab5 のキーボードを入れない)。指示書の「CMake で端末から選ぶ」の部分。

## 3. 大きさ (同じ日に同じ手順で作った develop のビルドと比べた)

ESP32 (`esp_idf_size`、エンジンは .env の既定、AtomS3R は端末の既定)。ファームは「Total image size」、静的な内蔵 RAM は D/IRAM。

| 構成 | develop ファーム | M1 | M2 | develop D/IRAM | M1 | M2 |
|---|---|---|---|---|---|---|
| AtomS3R | 4,084,547 | +16 | +164 | 111,279 | 同じ | 同じ |
| Retro (NARYAv3) | 4,469,903 | 0 | 0 | 126,259 | 同じ | 同じ |

## 4. 振る舞いの読み合わせ (Tab5・NARYAv4)

実機で見られないので、移した道を前と並べて読んだ。

- Tab5 の起動: `Tab5 display: power on` のログ → `tab5_power_on()` (中身は一字も変えていない) → `configure(variant)` → VM と cursor の init → `init()` → `setRotation(3)` → `LGFX init OK` → 起動の画面 → codec の init → 「Waiting for kernel...」→ ヘッドホンの初期状態の読み取り → ready。順も前と同じ。
- NARYAv4 の起動: `NARYAv4 display: I2C + DSI bus` → `configure()` → バスの handle を覚える → 以下同じ。回転なし。
- I2C の窓口: 引数の確かめ → lock → 端末の primitive → unlock。NARYAv4 の読み (`i2c_master_receive`、バスが無ければ `INVALID_STATE`) と、Tab5・AtomS3R の lgfx の 3 つの呼び出しは、前の式をそのまま primitive に移した。
- ヘッドホンの周期の読み取り: lock を取る場所・失敗のときの返し方・2 回続けて同じなら切り替える数えは同じ。数えの型を int から uint8_t にした (2 までしか数えない)。
- PPA の送り出し: 定数 (frame buffer の大きさ・画素の byte 数・横向きの大きさ) とどちらの道を選ぶかが、前の `#if` の結果と同じになることを、両方の端末の設定で確かめた。ビルドの差が数十 B なのも、道が変わっていない裏づけ。

## 6. M4: CI

`.github/workflows/build.yml` の `build-esp32` の matrix に `ATOMS3R` を足した (`[NARYAv3, TAB5, ATOMS3R]`)。手順は今のジョブと同じで、端末の既定 (`BOARD_BUILD_DEFAULTS`) が .env の値に勝つので、mruby のエディタ・Spinel の FFT なし・日本語のフォントなし・Asterism あり、でビルドされる。CI は push のときに回る。

## 7. ユーザに確かめてほしいこと (Tab5・NARYAv4 の実機)

どちらも M2 の像を焼いて:

1. **Tab5**: 起動の画面が出て (1280x720、横向き)、デスクトップが今までどおりの向き・位置で出る。シリアルのログに `Tab5 display: power on`、`panel probe: ...`、`LGFX init OK (1280x720)`。
2. **Tab5 の touch**: タップでカーソルが動く (touch は lgfx の I2C を lock して読む道。移していないが、同じバスの他の使い手が移った)。
3. **Tab5 のヘッドホン**: 挿したまま起動すると起動の音が speaker から出ない。抜き差しで `Headphone plugged/removed` のログが出て、speaker が切り替わる。
4. **Tab5 の音量**: 音量を変えると効く (ES8388 への書き込みが I2C の窓口を通る)。
5. **NARYAv4**: HDMI に 1280x720 で起動の画面とデスクトップが出る。ログに `NARYAv4 display: I2C + DSI bus`。音 (ES8311) の初期化が通る (`Audio: codec ready`)。
6. どちらも: 全画面の高解像度 (エディタ) への切り替えと戻り、カーソルの速さ (`display_local: cursor:` のログ) が今までと同じ。

## 8. 端末の状態

- AtomS3R (`/dev/ttyACM1`): M2 の像 (`feature/display-local` の f33fcbd1 相当、app の区画だけ書いた)。storage は H3 のまま (startup_app は試しのアプリ)。確かめのために起動した試しのアプリ・IMU のデモは kill した (止まった後の画面のまま。リセットで試しのアプリに戻る)。シリアルの capture は開いたまま。
- P4-Nano (`/dev/ttyACM0`) には触っていない。
- `build/` は Linux の標準の構成 (x86-64、`file` で確かめた)。ブラウザ版は libmruby から作り直し、`wasm:web` の bundle まである。sim とブラウザ版の server・browser は止めた。
