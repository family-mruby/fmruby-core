# W2 報告 (後半): 遠隔デスクトップにホイールを通す

> 状態: 完了 | 更新: 2026-09-01 | **NARYA v4 実機で確認済** (Tab5 ではなく、繋がっていたのがこちらだったため)

W2 の前半 (ブラウザ = wasm) は W1 と一緒に済ませた (report/w1.md)。
残っていた後半、**Tab5 の遠隔デスクトップ** (WiFi 越しの画面 + 操作) に
ホイールを足した。

## 足した 4 か所

| 場所 | 中身 |
|---|---|
| `main/drivers/remote_desktop/rd_input.h` | メッセージ型 `0x06 mouse_wheel { i16 x, i16 y, i8 notches }` |
| `main/drivers/remote_desktop/rd_input.c` | その型を `fmrb_host_send_mouse_wheel()` へ渡す |
| `tool/web/remote/remote.js` | 閲覧ページの `wheel` イベント → ノッチに直して送る |
| `tools/fmrb_rd_input.rb` + MCP `tab5_input` | `wheel N` コマンド |

**中核 (host_task から下) は 1 バイトも触っていない**。W1 で通した口に
新しい入力源を 1 つ繋いだだけ。

## 決めたこと

- **型は 0x06**。0x05 は ping が使っている。既存の型は動かさない。
- **クリックと違って move を先に送らない**。button の処理は座標合わせの
  ために `fmrb_host_send_mouse_move()` を先に呼ぶが、ホイールは
  **フォーカス窓に配る**ので不要で、しかも閲覧者がボタンを押したままの
  ときに勝手なドラッグになる。
- **ノッチ換算はページの中でやる** (px / 行 / ページの差と符号の反転)。
  wasm ページと**同じ規則を意図的にそのまま持ってきた** (100px = 1 ノッチ、
  端数は溜める)。ホイールの意味が閲覧経路ごとに違うのは避けたい。
- **`wheel N` に座標を持たせない**。直前の `move X Y` の位置で起きたことに
  する — `tools/fmrb_input.rb` (sim) と同じ約束にして、道具が変わっても
  手癖が変わらないようにした。ついでに click / drag も最後の位置を
  更新するようにしてある。
- i8 なので ±127 で頭打ちにする (ページ側で clamp)。

## W1 の教訓を先に適用した

W1 では**中継が型のホワイトリストで、知らない型を黙って捨てていた**。
同じ形の穴が無いか、**先に受け口を読んでから**書いた。

`rd_http.c` の WebSocket 受けは、keyframe 要求だけを横取りして
**残りは全部 `rd_input_handle()` に渡している** (型で振り分けていない)。
足す場所は無い。読んで確かめた上で書いた、というのがここでの成果。

## 確かめたこと

- **TAB5 (ESP32-P4) のビルドが通る**。`fmruby-core.bin` 0x5a13a0 バイト、
  app 区画の残り 6%。
- 閲覧ページはファームに焼き込まれている (`EMBED_FILES`)。**新しい
  `.bin` の中に `sendMouseWheel` の文字列があること**を確認した
  (ページだけ直して焼き忘れる、が起きない形)。
- `remote.js` は `node --check` を通した。

## 実機で確かめた (NARYA v4、2026-09-01)

Tab5 ではなく **NARYA v4** (P4-Nano + Olimex + HDMI) で確認した。遠隔
デスクトップは Modern 共通なので、確認したい経路はこちらでも同じ。

| 見たもの | 結果 |
|---|---|
| Log Viewer `wheel 3` | 9 行ぶん戻る (3 ノッチ x wheel_lines=3)。AUTO も降りる |
| Log Viewer `wheel -2` | 6 行ぶん進む |
| ランチャー `wheel -1` | **アイコン 1 行**ぶん進む (文字行ではなくノッチ単位) |
| 未知の型 0x07 を撃つ | `rd_input: unknown input msg type 0x07 (len=6)` が出る |

**最後の 1 行が効いた**。0x06 を撃っても警告が出ないことだけでは
「受理された」と「そもそも届いていない」の区別がつかない。**同じ形で型
だけ変えた 0x07 を並べて撃つ**と、警告が出る = 経路は生きている、0x06 は
出ない = 受理されている、と 1 回で分かる。W1 の sim で「型で落とす中継」を
踏んだときと同じ切り分けが、そのまま逆向きの証明に使える。

### 引っかかったこと: ホイールはフォーカス窓にしか行かない

**窓の外をクリックするとフォーカスがデスクトップに移り、以後のホイールは
何も起こさない**。426x240 のうち Log Viewer の右端は x=310 あたりで、
そこより右はデスクトップだった。「効かない」と思ったら、まず窓の中を
クリックしてから回す。

Log Viewer を開いた直後に撃った 1 回だけは効かなかった (窓の中の座標で、
spawn から 6 秒後)。その後は全部効いており、ランチャーでは spawn 直後の
1 発目から効いた。**再現していないので原因は詰めていない**。フォーカスが
移り切る前だった、が今のところの見立て。

### ついでに見えたもの

遠隔デスクトップを繋いでいる間、シリアルに
`E lcd.dsi: can't fetch data from external memory fast enough, underrun
happens` が定期的に出る。P4 で記録済みのアンダーラン
(naryav4/report/p4.md) で、**画面の転送が乗ると増える**。帯域を減らす側の
計画は naryav4/instruction_p6.md。
