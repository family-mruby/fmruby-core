# R1 報告: 繋がり続ける口 FmrbAsterism::Link と 3 アプリの載せ替え

> 状態: 途中で止まった (StickS3 の確認が残る) | 更新: 2026-10-25 | instruction_r1.md の記録。fmrb-asterism に `FmrbAsterism::Link` を作り、step_sensor・walk_scroller・asterism_demo を載せ替えた。ホストの試験・sim・ブラウザ版の確認と RAM の比較は済んだ。StickS3 の実機の確認は、端末が網に見えないことと、端末のファームに Link が無い (gem に入れたので焼き直しが要る) ことの 2 つで止まった

## 1. 結果の要約

- **口**: `lib/add/picoruby-fmrb-asterism/mrblib/link.rb` (230 行) に `FmrbAsterism::Link`。アプリは `link_up(link)` (繋がるたびに流れる) と、任意で `link_down(link)` を書き、`on_update` で `@link.update` を 1 回呼ぶ。asterism の gem 本体は変えていない。
- **載せ替え**: 振る舞い (画面・網に出す値・操作) は変えていない。小さな違いは 4 章。

| アプリ | 前 | 後 | 差 |
|---|---|---|---|
| step_sensor | 723 | 667 | -56 |
| walk_scroller | 1,513 | 1,476 | -37 |
| asterism_demo | 436 | 417 | -19 |

- **試験**: `test/asterism/link_run.rb` (偽の Asterism・時計・WiFi) を足し、`rake test` に入れた (`asterism:link_test`)。`rake test` は全部通る。合成の波形の試験 (step_detector_test) も通る。
- **RAM**: 静的な内蔵 RAM (idf.py size の DIRAM) は Tab5・Retro・StickS3 とも前後で同じ。ファームは Tab5 +4,088 B、StickS3 +3,984 B、Retro は gem が入らないので 0。
- **StickS3**: 未確認 (5 章)。端末には触れていない (ファイルも置いていない) ので、作業の前の状態のまま。

## 3. 口の設計

- 置き場: fmrb-asterism (端末側) の別ファイル `link.rb`。`FmrbAsterism.settings` を読み、node・router・credentials・設定の誤りをそのまま使う。CRuby の gem には入れていない (plan の未確定事項 1 は「端末側」で決めた形)。
- 作り方: `FmrbAsterism::Link.new(owner, app, tag:, retry_ms: 3000, wifi_wait_ms: 20000, screen_wait_ms: nil, settings: nil)`。
- アプリへの知らせは、保存したブロックではなく名前で呼ぶメソッド (`link_up`・`link_down`)。外側の局所変数を捕まえる必要が無く、Spinel の制約にも当たらない。`link_up` が例外を出したら接続の失敗として扱い、開きかけの接続を閉じる。
- 状態 (`state`、Symbol 1 つ):

| 状態 | 意味 |
|---|---|
| :waiting_wifi | WiFi に address が無い (wifi_wait_ms まで。WiFi の無い端末は待たない) |
| :waiting_screen | screen_wait_ms を渡し、screen_ready がまだ (screen_wait_ms まで) |
| :connecting | 次の更新で繋ぐ。接続は止まる (TLS の握手で 10〜20 s) ので、この状態にした更新はいったん返り、アプリがその間に「接続中」を描ける |
| :connected | 繋がっている |
| :reconnecting | 繋がっているが、Zenoh が自分で開き直している (Asterism.reconnecting?) |
| :retrying | 接続に失敗。retry_ms 後にまた |
| :still_there | 前の自分がまだ網にいて断られた。retry_ms 後にまた |
| :lost | 切れた (閉じた)。retry_ms 後にまた |
| :failed | 失敗して retry_ms が nil (もう試さない) |
| :closed | close した |

- `reason` は繋がっていない理由 (接続の誤り、または `asterism: <lost_reason>`)。`connected?` は :connected か :reconnecting、`up?` は :connected だけ。`update` は `connected?` を返す。
- アプリ側の網の処理 (each_pending など) で例外が出たら、アプリが `@link.lost(why)` を呼ぶ (walk_scroller の形)。
- ログは `"<tag>: <node>/<app> connected (<router>, N ms)"`・`"<tag>: connect: <理由>"`・`"<tag>: lost: <理由>"`。

## 4. 載せ替えで変わったところ (小さなもの)

- 接続が 1 更新遅れる (:connecting を 1 回挟むため。step_sensor は 10 ms、ほかは 20〜50 ms)。step_sensor の "AST .." は前と同じく接続の前に描かれる。
- step_sensor: poll が例外を出したら切れた扱いになった (前はログに出して続けた)。walk_scroller・オセロと同じ扱いにそろえた。exposed のメソッドの例外は Asterism が RemoteError にして返すので、poll から出るのは内部の誤りだけ。
- asterism_demo: 切れたときに close する (前は閉じずに置いた。画面は同じ)。Asterism::Error 以外の例外も失敗として拾う。
- walk_scroller: Asterism::Error 以外の接続の誤りは、理由の文字にクラス名が付く (調整の画面の `offline: ...`)。WiFi は前と同じく待たない (`wifi_wait_ms: 0`)。
- ログの文字: step_sensor の 10 s ごとの行の `net` が状態の Symbol (`connected`・`retrying` など) になった。切れたときの行に `asterism: ` が付く。walk_scroller の接続の行は Link の形になった。
- listen / peer の locator は 3 アプリとも peer の接続になる (前は asterism_demo だけ。ほかの 2 つでは誤った設定として失敗していた)。

## 5. 確認

### 5.1 ホスト

- `ruby test/asterism/link_run.rb`: WiFi の待ちと諦め、画面の待ち、失敗と 3 s 後の再試行、already on the network、Asterism 以外の例外、設定の誤り (connect を呼ばない)、link_up の例外、切断と繋ぎ直しで link_up がもう一度流れること、poll の例外、reconnecting、アプリからの lost、再試行なし、listen / peer、link_down の無い owner、close。全部通る。
- `rake test`: 全部通る。`ruby test/asterism/run.rb` (設定の試験、rake setup の写し) も通る。

### 5.2 sim (asterism_demo、step_sensor)

- `rake clean` → `rake build:linux` (x86-64 を確認)。sim_up は 426x240 (TAB5)。
- asterism_demo: `linux connected (tcp/zenohd:7447, 5 ms)`。PC から `info.status`・`screen.say` が返り、画面の said に出た。CLI のノードを出し入れして `joined:`・`left:` が出た (on_join・on_leave は link_up で登録)。zenohd を止めると `disconnected: the connection was lost` が画面に出て、繋ぎ直さない (前と同じ)。zenohd を止めたまま起動すると `linux failed: cannot open a session to tcp/zenohd:7447 (-128) (..., 3958 ms)` (前と同じ文)。
- step_sensor (sim、センサ無し): 繋がり (`AST ok`)、PC から `state` が読めた。zenohd を止めると `lost: asterism: the connection was lost` → `AST --`、3 s ごとに試し、zenohd を戻すと `linux/step connected` で繋がり直した。ブラウザ版の調整の画面から `tune` が届いた (140 にして 0 で 150 に戻した。save は sim の /home に書くので押していない)。
- 標準構成の確認: エディタを開いて `a` を打ち、`Ln 1, Col 2 *`。

### 5.3 ブラウザ版 (walk_scroller)

- `rake wasm:mruby` → `wasm:mrb` → `wasm:web`。zenohd は runbook の 1 章 (lan と ws を重ねた compose)。`?app=/app/demo/walk_scroller.app.rb&res=426x240`。
- `tool/imu/step_send.rb --count 10 --cadence 110 --measure`: 10 歩歩いた。put から画面まで中央値 21 ms (最小 13 / 最大 35)。右下は緑の `pc-stepsend 10`。
- zenohd を止めると右下が赤の `reconnecting 10`、戻すと繋がり直し、続きの 3 歩が届いた (中央値 8 ms)。
- T の調整の画面: 相手が pedometer を持たないときは `no answer: sensor gone or not allowed`、sim の step_sensor が相手のときは `rise 140 mg gap 250 ms`・`not saved`・`tuned (S to save)` と出た (前と同じ表示)。

### 5.4 StickS3 (止まった)

- 端末の address に ping も HTTP も届かず (No route to host)、VPS のルータのノードの一覧にも出ていなかった (作業中の約 30 分)。電源が切れているか、別の網にいると見ている。
- もう 1 つの問題: Link は gem (ファームの中) に入れたので、焼いていない StickS3 のファームには `FmrbAsterism::Link` が無い。新しい step_sensor をそのまま置くと `uninitialized constant` で起動しない。指示 (焼かない) と、終わりの状態 (新しい step_sensor で VPS に繋がっている) は、このままでは両立しない。
- 選択肢 (ユーザが決める):
  1. StickS3 を焼き直す (flash は /home を消すので、wifi.toml・config.toml・証明書の tar・step_sensor.toml (130 / 250) の置き直しが要る)。
  2. 確認だけを仮の形で: `link.rb` を端末の一時の場所に置き、先頭で require する step_sensor の写しで確認し、終わったら元の step_sensor に戻す。
  3. Link を gem ではなく、アプリが require するストレージの Ruby ファイルにする (アプリの置き換えだけで端末に届く。各 VM に常に読み込まれる gem と違い、使うアプリだけが払う)。plan の置き場の決定を変えることになる。
- 端末には何もしていない。保存してあるしきい値 130 mg / 250 ms は触っていないので、そのまま。

## 6. RAM

`idf.py size` の DIRAM (静的な内蔵 RAM)。前 = link.rb を外したビルド、後 = 入れたビルド。同じ作業ツリーで、`rake clean` を挟んで作った。

| 端末 | DIRAM 前 | DIRAM 後 | 像の大きさ 前 → 後 |
|---|---|---|---|
| Tab5 (P4) | 129,698 | 129,698 | 6,667,436 → 6,671,524 (+4,088) |
| Retro (NARYAv3) | 126,035 | 126,035 | 4,502,895 → 4,502,895 (gem が入らない) |
| StickS3 | 114,863 | 114,863 | 4,508,999 → 4,512,983 (+3,984) |

- mrblib の Ruby はファームの flash に bytecode として入るだけで、静的な内蔵 RAM は増えない。各 VM の起動時にクラスが定義される分は VM のヒープ (アプリのプール) に乗る。
- 作業の後、build/ は Linux (TAB5、x86-64) に戻した。

## 7. R4 (卓のアプリ) で口をどう使うか

- オセロ・ボード・麻雀の `network_ready?`・`connect`・`lost`・`reconnecting?`・`exchange` は、そのまま Link に置き換えられる形にしてある: `connect` の中身 (on_join・on_leave の登録、`@rescan_until`、`subscribe_states`) は `link_up` へ、`lost` の後始末 (`@sub`・`@join_f`・`@cmd_f`・`@view_f` を nil) は `link_down` へ。`reconnecting?` は `@link.state == :reconnecting`。
- オセロは esp32 以外で WiFi を待たない (`PLATFORM != "esp32"`)。sim は wifi_info を返すので、そろえるなら `wifi_wait_ms` を端末で分けるか、Link に同じ条件を足すかを R4 で決める。
- `RECONNECT_MS` が 3 s でなければ `retry_ms:` に渡す。
- 卓の一覧・入る・出る・席の札・view の間隔は Link の上に乗る別の部品 (R4 の本題)。
