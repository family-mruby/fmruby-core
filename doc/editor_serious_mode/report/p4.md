# P4 実施報告: editor-core gem (文書モデルの C 化)

指示書: ../instruction_p4.md / 前段: report/p1.md - p3.md

## 何を作ったか

- **専用プール `POOL_ID_EDITOR_DOC` (1MB, PSRAM)** を新設
  (fmrb_mem_config.h + fmrb_mempool.c の 2 ファイル同期)。`ps` の一覧にも出る。
- **`lib/add/picoruby-fmrb-editor-core`**: 文書モデルの native mrbgem。
  - `src/` は gem フック、実体は `ports/esp32/editor_core.c`
    (picoruby-esp32 の CMake が fmrb_mem / fmrb_hal_file を見える形でビルド。
    picoruby-fmrb-debug と同じ構成)。gembox / Rakefile の setup コピー /
    CMake の PICORUBY_SRCS glob を配線済み。
  - 確保は `fmrb_mem_create_handle(POOL_ID_EDITOR_DOC)` + `fmrb_malloc`。
    `mrb_malloc` も `fmrb_sys_malloc` も使っていない。
- **picoruby-syntax-highlight に C レベルの入口を 1 本追加**:
  `fmrb_syntax_highlight_line(src, len, out_map)`。既存の mruby バインディングは
  これを呼ぶ形に整理した (機能は同一)。
- **editor.app.rb から `@lines` と `@clipboard` を全廃**。UI 状態
  (カーソル・選択・スクロール・検索 UI・デバッガ) はアプリ側のまま。

## 内部表現とその選択理由

行ポインタ配列 + 行ごとの可変バッファ:

```c
typedef struct { char *buf; int32_t len, cap; uint8_t *hl; int32_t hl_chars; } ed_line_t;
```

- **列は UTF-8 文字インデックス** (現行踏襲)。境界で必ずバイト位置に変換する。
- **ハイライトは行単位キャッシュ** (`hl`)。行が変わった時だけ捨てる。
  P3 で残した「行単位キャッシュ」の実装位置がここ。
- **文書は mrb_state ごと**: `doc_of(mrb)` がスロットを引くので、エディタが
  2 つ起動しても互いの文書を壊さない (API にハンドルは出さない)。上限
  `ED_MAX_DOCS = 3` (ユーザアプリ枠と同数)、超えたら負エラー。

### 指示書の API との差分 (2 点)

1. **`render_row` を `render_text` + `render_hl` の 2 本に分けた**。
   1 レコードに畳む案は、mruby の `String#[]` が**文字単位**スライスであるため
   Ruby 側でヘッダとテキストをバイト境界で切り出せない (多バイト文字を含む
   レコードで壊れる)。呼び出し回数は旧実装 (行アクセス + tokenize) と同じ 2 回。
2. **`char_at` は Integer ではなく 1 文字の String** を返す。呼び出し側
   (draw_cursor) が必要なのは文字列で、Integer からの復元は
   `Integer#chr` がバイト単位なので多バイトで壊れる。

その他は指示書どおり (`find` は 9 バイトの packed [found, y, x]、
`insert_multiline` / `paste_at` は 8 バイトの packed [y, x])。

## 受け入れ条件の実測 (Linux sim 320x240 / 全画面 / Spinel カーネル)

### 1. 大きいファイルが開ける

`edit_doc:` を load 直後に 1 行出すようにした (sim と実機で同じ行が取れる)。

| ファイル | 行数 | 結果 | arena | VM プール |
|---|---|---|---|---|
| 20.7KB | 1349 | OK | 83,496 B | 67% |
| **53.4KB** | 3419 | **OK** (P1 では VM 消滅) | 207,928 B | 67% |
| **200KB** | 12590 | **OK** | 761,672 B | 67% |
| 400KB | - | **エラー表示のみ** (`Load failed (document arena full)` / ステータスに "Too large")。エディタも firmware も生存 | - | - |

- arena が文書サイズの約 3.8 倍になるのは**行ごとに 1 確保している**ため
  (行構造体 32B + TLSF のブロックヘッダ + 32B 粒度)。実測で確認したのは
  「無駄の主因は容量の切り上げではなく確保回数」で、load 後に行バッファを
  実寸へ縮める処理を入れても 761,672 → 761,640 B しか動かなかったので外した。
  32bit の実機では行構造体が 20B 台になるぶん軽くなる見込み。
  **さらに詰めるなら「1 本のテキスト arena + 行オフセット表」**だが、
  200KB 要件は満たせているので今回はここまで。

### 2. VM プール (mruby ヒープ) から文書が消えたか

同一 VM・同一プール (500KB) で新旧を測る使い捨てアプリ
(`flash/app/test/doc_mem.app.rb`) で比較した。20.7KB のファイル:

| モデル | pool_usage | 備考 |
|---|---|---|
| 何も持たない状態 (基準) | 61% | |
| **EditorCore (新)** | **61%** | 文書は arena に 83KB。**プールの消費は増えない** |
| Array of String (旧: `File.read` + `split`) | **77%** | +16 ポイント = 約 80KB がプールに乗る |

文書サイズに比例する消費が mruby プールから**完全に消えた** (0 ポイント増)。
エディタ実測でも 20.7KB / 53.4KB / 200KB のいずれでも pool は 67% で一定。

### 3. 全画面エディタ + 14KB 窓アプリ (tetris) の NoMemoryError — **原因が別だった**

**達成できていない。ただし p2.md の見立て (エディタとの同時使用が原因) が
誤りだった**ことを確認した:

- **tetris を単体で `run` しても同じ `Out of memory` で落ちる** (エディタ非起動)。
  落ちているのは tetris 自身の VM で、ログは
  `[Tetris] Script size: 14240 bytes` の直後。**14KB の Ruby を実行時
  コンパイルするのに 500KB のアプリプールが足りない**という別問題。
- P4 が担う側 (エディタの消費) は解決している証拠として、
  **200KB の文書を開いたエディタ + 他アプリ 2 本が同時に生存**することを確認
  (`ps`: FM-Shell run / FM-Editor suspend(park) / NSF Player run、OOM なし)。
- この 500KB 制約は **64bit の sim で厳しく出る**性質 (同じ理由で
  `FMRB_MEM_POOL_SIZE_SYSTEM_APP` は Linux だけ 1536KB にしてある)。実機 32bit
  では通っている可能性が高い。対処は「アプリプールを広げる」か
  「大きいアプリはバイトコード化する」で、**editor-core の範囲外**。

## 性能の考察 (境界越え)

- 1 行描くのに `render_text` + `render_hl` の 2 回。全画面 27 行で 54 回/全面
  再描画。実測 draw_mean は 1.6-1.7ms で、P1-T4 (2.2-2.5ms) より速い。
  **境界越えの回数より、ハイライトを毎回計算していたことの方が重かった**。
- したがって指示書が用意していた退避策 (`render_rows` で一括返し) は不要だった。
  可視行数が 45 行に増える段階 5 (640x360) で再測すればよい。

## 段階 6 (Spinel 版エディタ) への引継ぎ

- 境界 API は**スカラーと String だけ**で閉じてあるので、Spinel FFI
  (`:int` / `:str`) にそのまま乗る。packed record は binstr のまま読める。
- ただし現在の実体は **mruby バインディング (mrb_get_args / mrb_str_new)** に
  直結している。Spinel から使うには、C の内部関数 (`doc_*` / `ec_*` の中身) を
  mruby 非依存の層に切り出し、その上に mruby 版と Spinel 版の 2 つの薄い
  バインディングを置く形が素直。内部はすでに mrb_state を「文書スロットの鍵」
  としてしか使っていないので、鍵を差し替えれば済む。
- undo/redo は範囲外のままだが、**編集操作が全部 gem を通る**ので、
  gem 内ジャーナルで後から足せる (アプリが行を直接書き換える裏口は無い)。
