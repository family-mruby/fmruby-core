# P1 実施報告: エディタ本気モード (全画面 + 計測 + 差分描画 + sim 解像度連動)

指示書: ../instruction_p1.md / 計画: ../plan.md

## T1: エディタ全画面「本気モード」

### 実施内容

- spawner に組み込みエントリ `default/editor_fs` を追加
  (main/app/fmrb_app_spawner.c)。irep は `default/editor` と同じ
  editor_irep。属性は fullscreen = true / fullscreen_switchable = true /
  rounded_corners = false (全画面は枠を描かないので不透明 canvas にして
  合成を軽くする) / large_memory なし。
  アプリ名は窓版と同じ `FM-Editor` にした。shell と desktop の
  「エディタを名前で探してファイルパスを渡す」中継がそのまま効くため。
- 全画面組み込みエントリの窓サイズは spawn_builtin_app で display 設定から
  埋める。**指示書の想定 (fmrb_app.c:1512-1516 が display サイズを入れる)
  は SYSTEM_APP の分岐**で、USER_APP は attr の値が 0 だと
  default_user_app_width にフォールバックしてしまう。そのため toml 経路
  (同ファイルの fullscreen 分岐) と同じ計算をここでも行う。
- 入り口: shell の `edit` に `-f` を追加 (`edit [-f] <file>`)。
- エディタに `on_resume` を追加し、park 復帰時に全面再描画する。

### 想定外だった点: ファイルパスの中継が全画面では成立しない

指示書は「既存の shell → editor 中継 (tick_pending_edit) をそのまま使う」
としていたが、**全画面ではこの経路は原理的に動かない**:

1. shell が kernel に spawn 要求を出す。
2. kernel が spawn 直後に `enter_fullscreen` で **shell を suspend** する。
3. shell の tick_pending_edit (3 tick 後にパスを送る) は永久に来ない。

そこで kernel の spawn 要求に任意フィールド `open_path` を足し、
**kernel 自身**が新しい pid に `file_selected` を送る形にした
(kernel は suspend されない)。窓モードは従来の中継のまま (退行なし)。

さらに、spawn 直後の送信は落ちる:

```
W fmrb_msg: msg_send DROPPED: dest=5 queue not registered
```

アプリのメッセージキューは**アプリ自身のタスクが起動時に登録**するため、
spawn 直後にはまだ無い。よって kernel の tick_process で
`_try_send_raw_message` を成功するまで再試行する (上限 60 tick)。
実装は fmrb_kernel/app_lifecycle.rb の `flush_open_path`。

### 副次的にわかったこと

- 全画面エディタを Ctrl+X で閉じると HID フォーカスは**デスクトップ**に
  戻る (shell ではない)。デスクトップにフォーカスがある状態で `e` を押すと
  system_conf の shortcuts で editor が起動するので、続けて文字を打つと
  「新しいエディタに打ち込まれる」ことになる。既存挙動。
- 実行時の窓 ⇔ 全画面トグルは指示書どおり未実施 (P4 の canvas が spawn 時
  サイズ固定)。Retro 側の可否は plan.md 3 章の記述のまま (未実測)。

### T1 で見つけて直したバグ: 全画面アプリの上端 13px にクリックが届かない

全画面エディタのメニューバー (File/Edit/...) をクリックしても何も起きない。
原因は kernel の入力経路 2 箇所が、**画面上端 13px (デスクトップの
メニューバー行) を無条件でデスクトップへ回していた**こと:

- input_router.rb: `if @fullscreen_pid && y >= $menu_bar_height` — 全画面でも
  上端だけは除外していた (コメントに明示されていた設計)。
- window_manager.rb `find_window_at`: `y < $menu_bar_height` なら
  デスクトップの窓を返す。

全画面中はデスクトップは suspend されメニューバーも画面に出ていないので、
上端もそのアプリのものにした (park 中は @fullscreen_pid が nil なので
デスクトップにメニューバーが戻る)。修正後、全画面でも Hilight / File
メニューのクリックが効くことを確認。

## T2: 計測の整備

### 何を測れるようにしたか

1. **打鍵 → present (エディタ Ruby 側)**: editor.app.rb に常時オンの計測を
   追加。キー到着で `Machine.uptime_us` を 1 回、redraw 前後で 1 回ずつ。
   累積は整数のみ、100 サンプルごとに 1 行だけログを出す:

   ```
   edit_lat: n=100 mean=29051us max=68397us p99<=55ms over25ms=49
             draw_mean=2509us draw_max=7082us hist5ms=4,8,13,... rows=27 hl=1
   ```

   - サンプルは「まだ画面に出ていない最古のキー → present」。連続打鍵で
     甘い値が出ないようにこちら側に寄せてある。
   - p99 は 5ms 刻みのヒストグラムからの上限見積り (サンプルを保存しない)。
   - `draw_*` は redraw_all の所要時間。**present は非同期** (gfx コマンドを
     host_task のキューに積むだけ) なので、これは「Ruby が描画コマンドを
     作り終えるまで」であって画面に出るまでではない。画面側は下の 2。
   - 修飾キー単独 (keycode 224-231) は計測開始にしない。

2. **1 フレームの描画コスト (画面側)**:
   - Retro / sim: graphics-audio の graphics_task に既にあった
     `loop: fps=... render_avg=...` を**マイクロ秒化**した。従来は
     FreeRTOS tick (Linux ビルドは 10ms) で割っていたため render_avg=0ms
     しか出ず使えなかった。合成 (render) とパネル/SHM への転送 (disp) を
     分けて出す:

     ```
     loop: fps=30.3 render_avg=35us render_max=100us disp_avg=17us disp_max=90us late=0
     ```

     同じコードが WROVER (Retro の映像側) でも動くので S3 構成でも取れる。
   - Modern (P4): display_p4_task に既に
     `render: N frames/5s avg=..ms max=..ms` があるので追加なし。

### T1 時点の基準値 (Linux sim 320x240, kernel=spinel, 差分描画なし)

打鍵は 70ms 間隔で 110 文字 (実際の打鍵速度相当) を注入。100 サンプルの集計。

| 条件 | 行数 | HL | mean | max | p99 | 25ms 超 | draw mean | draw max |
|---|---|---|---|---|---|---|---|---|
| A 全画面 / 小 (384B) | 27 | on | 29.1ms | 68.4ms | <=55ms | 49/100 | 2.51ms | 7.1ms |
| B 全画面 / 大 (10.9KB) | 27 | 自動 off | 28.4ms | 66.0ms | <=55ms | 53/100 | 2.37ms | 7.7ms |
| D 窓 / 小 (384B) | 21 | on | 29.0ms | 67.1ms | <=55ms | 54/100 | 2.03ms | 7.2ms |
| E 窓 / 大 (10.9KB) | 21 | 自動 off | 29.2ms | 69.8ms | <=55ms | 52/100 | 2.71ms | 8.2ms |

画面側 (GA): 待機時 render_avg 25-57us、打鍵中 34-35us、max 0.5ms 程度。
sim では画面合成は遅延要因になっていない。

### この数字が示していること (T4 の方針に直結)

**遅延の主因は描画ではなくポーリング 2 段**である。全面再描画のコストは
2.0-2.7ms しかないのに、打鍵→present は平均 29ms、最大 68ms:

1. キーは on_event で `@input_buffer` に積まれるだけ。
2. `@editor_task` (Task.new) が `getch` で `sleep_ms 33` しているので、
   最悪 33ms 待ってから handle_key が走り `@need_redraw` が立つ。
3. 実際の描画は次の `on_update` (これも 33ms 周期) で行われる。

33ms x 2 = 最悪 66ms。実測 max 68ms とほぼ一致する。よって
**dirty-line 差分描画だけでは T4 の目標 (p99 < 33ms、25ms 超ゼロ) には
到達しない**。T4 では入力経路も直す (キーを on_event で直接処理し、
その場で差分描画する)。副作用として Task.new + sleep_ms が消えるので、
plan.md 6 章の Spinel 化の障害 1 も同時に解消する。

窓 vs 全画面の差は sim ではほぼ無い (CPU が余っているので suspend の効果が
出ない)。全画面の方が行数が多い分 draw が僅かに重い。実機 (特に S3) での
比較は**ユーザ確認待ち**。

### 併せて見つかった既存バグ: 10KB ファイルでハイライトを ON にすると固まる

10.9KB / 719 行のファイルを開き、Hilight を ON にすると**エディタが停止する**
(窓モード / 全画面モードの両方で再現。present が一切出なくなり、以後キー
イベントはアプリのキューが埋まって捨てられる)。gdb で見ると当該 VM の
スレッドは `mrb_hal_task_idle_cpu` で待っており、**mruby-task に実行可能な
タスクが 1 つも無い**状態。picoruby の既知の落とし穴 (`sleep_ms` は
`_spin` の外では tick が進まず止まる) と同じ症状。

- HL_AUTO_LIMIT_BYTES = 1024 があるため既定では踏まない (手で ON に
  した時だけ)。T1 の変更とは無関係 (窓モードでも起きる)。
- 引き金は「全文 join + 全画面分の色分割 draw_text」の重い redraw。
  T4 (行単位の増分ハイライト + 差分描画 + 入力経路の直し) で引き金が
  無くなる見込み。**T4 後に同じ手順で再確認する**。
