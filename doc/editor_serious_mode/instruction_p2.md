# 実装指示書 P2: 全画面モードの GUI 統合 (起動・トグル・復帰バグ)

対象: 実装担当セッション (Opus)。作業リポジトリ: fmruby-core。
前提: P1 完了済み (report/p1.md)。plan.md と report/p1.md を先に読むこと。

## 背景

P1 で全画面エディタ (default/editor_fs) は動くが、入口が shell の
`edit -f` しかない。GUI からの起動と、窓 ⇔ 全画面の行き来を実現する。
併せて、全画面の入れ子 (全画面エディタから全画面アプリを起動して戻る) で
見つかったバグを直す。

## 進め方の約束

P1 と同じ (instruction_p1.md 冒頭参照)。report は
doc/editor_serious_mode/report/p2.md へ。タスクごとにコミット。
検証は Linux sim 基本、実機確認が要るものは「ユーザ確認待ち」と明記。
今回は 3 タスクとも kernel の共有部分に触るため、**既存アプリ
(raycaster / rpg_demo 等の全画面アプリ、窓アプリ、Ctrl+Tab park) の
退行確認を各タスクの受け入れ条件に含める**。

**Spinel カーネルに関する注意 (重要)**: .env は FMRB_KERNEL_ENGINE=spinel
であり、今回触る kernel Ruby (fmrb_kernel.rb / app_lifecycle.rb /
input_router.rb / window_manager.rb) は **Spinel で AOT コンパイルされて
動く**。したがって:

- Spinel の書き方制約に従うこと (doc/spinel_aot/ruby_writing_constraints.md。
  特に「後で呼ばれるブロックは外側のローカル変数を捕捉できない」。
  ivar / 定数 / 同期ブロックは可)。
- **両エンジンで検証すること**: 既定の Spinel カーネルに加えて、
  FMRB_KERNEL_ENGINE を外した mruby カーネルでも sim でひととおり
  動かす (片方の構成でしか通らない経路は無言の穴になる)。
- カーネルの C API を増やす場合は mruby 版バインディングと Spinel の
  packed record 定義の**両方**が必要 (doc/focus_switch/report/p1.md の
  経験則)。

なお**エディタ本体の Spinel 化は P2 の範囲外** (plan.md 段階 4/6)。
P2 は「Spinel カーネル上で正しく動く kernel 改修」までが責務。

## T3 を最初にやる: 全画面まわりの 3 症状の修正

先にバグを直すのは、T2 (トグル) が同じ状態管理の上に乗るため。
3 症状は独立に見えて、いずれも「全画面状態の管理が単一スロットで、
全画面中の spawn / 終了の意味論が未定義」に根がある可能性が高い。

### 症状 1: 全画面入れ子からの復帰でタスクバーが出る

全画面エディタから F5 で RPG (全画面アプリ) を RUN → Ctrl+Q で RPG を
終了して戻ると、**エディタは表示されるがデスクトップのタスクバーが
画面に出てしまう**。

### 症状 2: 全画面中に窓アプリを RUN すると壊れる

全画面エディタから RUN で**窓モードのアプリ**を起動すると、エディタ画面の
上に窓が重なって表示され、窓をクリックすると消える。

期待動作 (仕様として実装する): **全画面中のアプリから窓アプリが spawn
されたら、全画面アプリを park (suspend + canvas 非表示) してデスクトップを
復帰させ、窓アプリを通常のデスクトップ上に表示する**。窓アプリの終了時は
@run_parent (= エディタ) に HID が戻る流れで**エディタを unpark して全画面に
復帰する** (F5 で試して閉じたらエディタに戻る、という編集ループを成立
させる)。Ctrl+Tab でも park 中のエディタに到達できること。

推定原因: カーネルはこのケースの意味論を持っておらず、デスクトップ
suspend のまま・入力ルーティングは全画面のまま (@fullscreen_pid が
エディタを指し続け、クリックは窓ではなくエディタに配られる)・z-order
だけ窓が上、という中途半端な状態になっている。「クリックで窓が消える」は
全画面 canvas の bring_to_front か再描画が窓の上に被る動きと推定。
原因確定の上で直すこと。

### 症状 3: 全画面エディタで Ctrl+Q が効かない

全画面エディタで Ctrl+Q (アプリ終了のグローバルホットキー) を押しても
何も起きない。

推定原因: P1 でキー入力を on_event の直接処理に変えた際、フレームワーク
既定のホットキー処理 (fmrb-app.rb 側の Ctrl+Q → destroy 経路) より先に
エディタがイベントを消費している。エディタの on_event でフレームワークの
既定処理へ回すべきキーを素通しにするか、ホットキー判定を先に行う形に
直す。窓モードのエディタと他アプリの Ctrl+Q が退行しないことも確認。
(修飾キー判定が scancode 系で正しいかも併せて確認。
sim では keycode ではなく scancode を見る必要がある。)

### 症状 1 の見立て (要検証)

カーネルの全画面状態は @fullscreen_pid の**単一スロット**で、入れ子を
知らない。RPG が enter_fullscreen した時点でスロットは RPG に置き換わり、
RPG 終了時の cleanup_terminated_app は「全画面解除」しかしない
(app_lifecycle.rb の cleanup 系)。結果:

- デスクトップが suspend から復帰してタスクバー等を描く
- エディタ自身は resume されて全画面サイズの canvas を持ったままだが、
  カーネル側は「全画面中」ではなくなるので、window_manager の
  メニューバー分岐 (P1 で入れた !@fullscreen_pid 条件) もデスクトップ側に
  倒れ、z-order/入力の整合も崩れる

### 修正方針

- 全画面状態を**スタック (または「前の全画面 pid」の 1 段記憶)** にする。
  enter_fullscreen 時に現在の @fullscreen_pid を積み、全画面アプリの
  終了時 (cleanup) に前の全画面アプリへ復元する:
  復元先がまだ生きていれば suspend 解除 + canvas 可視化 + HID を返し、
  @fullscreen_pid を戻す。デスクトップは suspend のまま。
- 1 段で足りるか (エディタ → RPG の 2 段まで) はスタックにするかを
  実装時に判断して report に理由を書く。@run_parent (request_run の
  親子記録) との整合も確認する。
- Ctrl+Tab の park/unpark (@parked_fullscreen_pid) との相互作用に注意。
  park 中に別の全画面アプリが立つ・終わるケースを一通り洗うこと。

### 受け入れ条件

- 症状 1: 再現手順で、RPG 終了後に**エディタが全画面のまま**でタスクバーが
  出ないこと。HID もエディタに戻ること。
- 症状 2: 全画面エディタ → RUN で窓アプリ → デスクトップ + 窓が表示され、
  エディタは見えない。窓の操作が普通に効く。窓アプリ終了でエディタが
  全画面に復帰する。Ctrl+Tab でも park 中エディタに到達できる。
- 症状 3: 全画面/窓モードどちらのエディタでも Ctrl+Q で終了できる。
  他アプリの Ctrl+Q・エディタ内の通常キー入力に退行が無いこと。
- 窓モードエディタから F5 → RPG → Ctrl+Q の従来ケースが退行しないこと
  (デスクトップに戻る)。
- デスクトップから直接全画面アプリを起動 → 終了、の従来ケースが
  退行しないこと。
- Ctrl+Tab park → 復帰が全画面入れ子と組み合わさっても破綻しないこと
  (代表ケースをスクリーンショットで report に)。

## T2: 窓 ⇔ 全画面の実行時トグル

### 方針: 再 spawn ではなく同一 VM のまま切り替える

再 spawn 方式は未保存バッファの引き渡し問題を抱えるので採らない。
同一 VM のまま切り替えれば、バッファ・カーソル・undo 履歴が全部残る。

必要な部品は 3 つ:

1. **P4 の canvas 確保方針を Retro に合わせる**: display_p4_task の
   canvas 確保 (canvas_alloc) を「窓サイズ」ではなく**画面サイズで確保**に
   変更する (Retro 側 graphics-audio は最初からそうしている:
   graphics_handler.cpp の "Always allocate at display screen size")。
   メモリ増は canvas 1 枚あたり 426x240x2 = 200KB (PSRAM)。
   MAX_CANVAS 8 枚で最悪 1.6MB、Tab5 の PSRAM 32MB に対して許容。
   これで P4 でも実行時の窓サイズ拡大が効くようになる
   (P1 report の「P4 は spawn 時サイズ固定」制約の解消)。
2. **カーネルに実行時の enter/exit fullscreen 経路を作る**:
   既存の enter_fullscreen は after_spawn (spawn 時) からしか呼ばれない。
   実行中アプリからの {"cmd"=>"enter_fullscreen"} / {"cmd"=>"exit_fullscreen"}
   要求を受け、他アプリの suspend/resume、窓サイズ変更
   (fmrb_app_update_window_size 系)、アプリへの resize 通知、
   T3 で入れた全画面状態管理への積み下ろし、を行う。
   exit 時は元の窓ジオメトリ (位置・サイズ) に戻すこと (enter 時に保存)。
3. **エディタ側のトグル UI**: キーは F11 (fmrb_keymap にあるか確認、
   無ければ追加)。メニューにも項目を足す (View → Fullscreen 等)。
   レイアウトは on_resize → recompute_layout が既に追随するので、
   エディタ側は要求を送って resize を受けるだけのはず。

### 補足

- これが入ると editor_fs エントリと edit -f は「最初から全画面で開く
  ショートカット」として残る (廃止しない)。
- 汎用機構なので、エディタ以外のアプリ (resizable な窓アプリ) でも
  使えるのが望ましいが、v1 の動作確認はエディタで良い。
- 多重 VM 計画 (doc/multivm_app/plan.md 2.3 ギャップ 5「窓モードの
  後から変更 API が無い」) への答えにもなる。plan 側への反映は
  レビュー側でやるので report に一言書けば良い。

### 受け入れ条件

- 窓エディタで F11 → 全画面 (70x27) → F11 → 元の窓位置・サイズに復帰。
  編集中バッファ・カーソル・スクロール位置が保持されること。
- 全画面中の他アプリ suspend / 復帰時の resume が正しいこと。
- edit -f 起動 → F11 で窓化、も動くこと。
- Retro (.env NARYAv3 の sim、320x240) でも同じトグルが動くこと。
- P4 の canvas 確保変更で既存アプリの表示が退行しないこと
  (窓アプリ数枚 + 全画面アプリ + リサイズ操作をスクリーンショット確認)。
- esp32 (S3/P4) 両ビルド通過。実機の見え方はユーザ確認待ち。

## T1: GUI からの起動

### 要件

マウス/タッチだけで全画面エディタに到達できるようにする。

### 実装方針 (小さく)

- デスクトップのメニュー (またはタスクバー) に「Editor」項目を足し、
  spawn 要求 {"cmd"=>"spawn", "app_name"=>"default/editor"} を送る。
  T2 が入れば**窓で開いて F11 で全画面**が基本動線になるため、
  メニューは通常版エディタで良い (editor_fs を並べる必要はない)。
- ランチャーは /app スキャン由来なので組み込みアプリは出ない。
  ランチャー側の改修はやらない (メニューで足りる)。
- 新規ファイル (パス無し) で開いたときのエディタの挙動を確認し、
  保存時に名前を付ける動線が無ければ最低限の対処 (固定の
  /home/untitled.rb に保存する等) を入れ、report に記す。

### 受け入れ条件

- sim でマウスだけで: メニュー → Editor 起動 → F11 全画面 → 編集 →
  保存 → 終了、が完結すること。
