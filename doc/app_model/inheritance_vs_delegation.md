# FmrbApp は継承でよいか (検討)

> 状態: 結論あり (現状維持) | 更新: 2026-09-06 | 「継承より移譲」を当てて
> みた記録。**移譲には移らない**。ただし `on_event` の契約だけは消す価値がある

ユーザ提起 (2026-09-06):「今の FmrbApp は OOP 継承をつかっているが、設計として
よいものか。継承より移譲、という話を思い出して考えていた」。

数えられるものは数えた。**懸念として挙げたものの多くは、実際には起きていない**。

## 今の形

`FmrbApp` は基底クラスで、`main_loop` を持ち、アプリを呼ぶ。アプリは
`class MyApp < FmrbApp` と書いて hook を上書きする。**制御は反転している** —
基底のメソッドを借りるために継承しているのではない。

継承しているファイルは **76 本**。

## 原則が狙う病理を当ててみる

### 1. 「再利用のための継承」 — 当てはまらない

これが本来の標的である。ここは制御の反転で、Arduino の `setup`/`loop`、
Android の Activity、Godot の Node と同じ形。**枠組みが呼ぶ側のときは
継承が定石**。

### 2. 「壊れやすい基底クラス」 — 理屈は本当、実害はゼロ

基底は **ivar を 30 個**持ち、名前空間はアプリと共有である。危険は本物。

**ただし 76 本を通して衝突は 1 件も無い** (2026-09-06 実測)。
疑ったものは 2 つとも空振りだった。

- `@scroll` に代入しているアプリが 5 本あるが、**基底の `@scroll` は
  コメントの中にしか無い**。衝突していない。
- `services.app.rb` の `@name = entry.name` は**別クラス `SvcCtx` の中**。

### 3. 「継承は 1 軸しか使えない」 — 既に mixin で解けている

普通はこれが一番強い論拠になる。ところがこの設計は**横断的な機能を module で
分けている** (`SystemDesktopApp` は Launcher / FileSelector / ConfigDialog など
8 個を include する)。**枠組みとの関係だけを継承にして、機能の束は mixin**。
1 軸問題が起きる形になっていない。

### 4. 「super を呼び忘れる」 — これだけが本物

実測 (2026-09-06):

| hook | 上書き | `super` を呼ぶ | 基底の中身 |
|---|---|---|---|
| `on_create` | 76 | **0** | ログ 1 行 |
| `on_update` | 75 | **0** | `330` を返すだけ |
| **`on_event`** | 43 | **41** | **閉じるボタンの処理** |
| `on_destroy` | 40 | **0** | ログ 1 行 |
| `on_control` | 18 | 0 | **基底に無い** |
| `on_resize` | 7 | 0 | 空 |
| `on_resume` | 6 | 1 | ログ 1 行 |
| `on_suspend` | 3 | 0 | ログ 1 行 |

**契約は `on_event` ただ 1 つ**である。基底に実体があるのがそこだけだから。
呼んでいない 2 本 (picorabbit, system_desktop) は**どちらも閉じるボタンを
持たない全画面アプリ**で、破っているのが正しい。

つまり **41/43 で守られている**。規則としてはよく機能している。

## 移譲にすると何が変わるか

```ruby
class MyGame
  def initialize(app)
    @app = app
    @gfx = app.gfx        # 書かないと以降ずっと @app.gfx
  end
  def on_update; ...; end
end
```

**コールバックの形は変わらない。** `def on_update` を書いて枠組みが呼ぶ。
変わるのは*誰の上に定義するか*だけで、費用もほぼ同じ (今は self への仮想
呼び出し、移譲では `@handler` への呼び出し — ivar を 1 回読む差)。

**「移譲だから block になる」わけではない。** ここは混ざりやすい。block は
コールバックの一形式にすぎず、しかも**この機械では毎フレームの経路に使えない**
(block 呼び出しは 1 回 0.4ms。`set_timer` が block なのは秒単位で 1 回だから)。

hook の有無は `respond_to?` を**起動時に 1 回**調べて真偽値に畳む。毎フレーム
問い合わせてはいけない。

| | 継承 (今) | 移譲 |
|---|---|---|
| アプリが書くもの | `def on_update` | `def on_update` (同じ) |
| 呼び出しの費用 | 仮想呼び出し | ほぼ同じ |
| ivar | 基底と共有 (30) | **完全に自分のもの** |
| 枠組みへの参照 | `@gfx` 直接 | `@app.gfx` か初期化時に写す |
| `super` | `on_event` だけ規則が要る | 規則が消える |

## 結論: 現状維持

**ゼロから作るとしても継承を選ぶ。** 移植の手間という論拠を外しても、判断は
**利用者から見た形**で決まるため。

この機械は「Ruby を書いて遊ぶ」のが主題で、`initialize(app)` と `@app` は
枠組みの都合である。最初の 1 本を書く人にとって、`class MyApp < FmrbApp` と
`def on_update` と `@gfx` は削れるだけ削った形になっている。

## ゼロから作るなら変える 2 点

**1. `on_event` を上書きさせない。**

```ruby
def on_event(ev)            # 基底が持つ。アプリは触らない
  return if handle_close_button(ev)
  handle_event(ev)          # アプリが書くのはこちら
end
```

**「super を呼ぶ」という規則が存在しなくなる。** 守れる規則より、要らない
規則の方が良い。既存を直すなら `on_event` を持つ 43 本の改名で、
**閉じるボタンを持たない 2 本は `handle_event` にするだけで挙動が変わらない**。

**2. 基底の ivar に最初から接頭辞を付ける。**

公開するのは `@gfx` `@name` 程度にして、残り 27 個は `@_` を付ける
(今は 30 個中 3 個)。**移譲の本当の利点である名前空間の分離は、これでほぼ
手に入る**。

`@gfx` すらメソッドにすれば予約語はゼロにできるが、**描画の輪で効く**
(メソッド呼び出しは素の操作の帯、数 µs。100 個描けば無視できない)。
局所変数に写せば済むが、初心者に「まず `g = gfx` と書け」と言うことになる。
割に合わない。

## この結論が崩れる条件

**継承を選ぶ判断は「1 プログラム 1 アプリ」に依存している。** 次のどれかが
起きたら見直す価値がある。

- **1 つの VM に複数のアプリを載せる** (doc/multivm の構想)。自分が誰かが
  曖昧になり、移譲の方が素直になる。**一番効く条件**。
- 機械の外で hook だけ単体試験したくなったとき。
- 枠組みの軸が 2 本になったとき (「窓を持つ」と「常駐する」が独立に
  組み合わさる、など)。
