# G1・G2 報告: リリースのビルドで書く場所を絞り、端末で許可した PC だけを通す

> 開始 2026-11-16 19:20 (JST) / 終了 2026-11-16 20:05 | 計画: ../plan.md (G1・G2、未確定事項 1-4 は決定済)

## 1. 変えた所

### 仕組みの中心 (純粋な C)

- `main/kernel/fmrb_remote_guard.{h,c}` (新規): スイッチ (閉じる・開く)、番号 (6 桁)、トークン (16 バイト、
  16 進 32 文字) を最大 4 台ぶん、取り消し、書いてよい場所 (`/home`・`/app`) の決まり。保存・乱数・ロックは
  呼び出し側が渡す (`fmrb_rguard_ops_t`)。**誰も arm しなければ何でも通す** (開発のビルド、sim・ネイティブ版・
  ブラウザ版)。全ターゲットに入れた (main/CMakeLists.txt、hosted/hosted.cmake): FmrbSystem がどこでも同じ答えを
  返すように。状態は 96 B で、ESP32 では PSRAM の .bss (`FMRB_EXT_RAM_BSS_ATTR`)。
- 試験: `test/remote_guard/main.c`、`rake remote_guard:test` (`rake test` に入れた)。97 個の確認: 閉じている
  とき・番号違い・番号の 1 回使い切り・5 回違いで停止と OFF→ON での復帰・再起動 (保存から読み直し) で閉じて
  トークンは残る・4 台を超えると最古を押し出す・全部取り消し (保存にも)・大文字の 16 進・`/home` `/app` の
  境界 (`/homework`・`/apps` は不可)。

### ESP32 (devctl とリモートデスクトップ)

- `main/drivers/devctl/devctl_http.c`
  - **全経路を guard に通す**: 登録を `guarded_handler` 経由にした (user_ctx に元の経路)。トークンは
    `X-Fmrb-Token` ヘッダか `token=` クエリ (ブラウザの `<img>`・WebSocket のため)。断るときは
    `401 {"ok":false,"guard":"closed|no_token|bad_token","err":"<何をすればよいか>"}`。
  - **`POST /pair?code=NNNNNN`** → `{"ok":true,"token":"..."}`。閉じていれば 403 `closed`、違えば 403 `wrong`
    (残り回数)、5 回違えば 403 `locked`。開発のビルドは `{"ok":true,"guard":"free","token":""}`。
  - **`GET /auth`**: このリクエストが通るかを 200/401 で答える (WebSocket は握手の後でしか断れないので、
    道具と viewer はこれを先に聞く)。
  - **G1**: `fs_req_path` に「書く」を足し、制限のあるビルドでは put・del・mkdir を `/home`・`/app` の下だけに
    (ほかは 403 と理由)。読むのは今までどおり 4 つの根、鍵は読まない。
  - トークンの保存: NVS の名前空間 `fmrb_rguard`、キー `tokens` (80 B の blob)。ロックは FreeRTOS の mutex
    (arm のときに作る。ハンドルは PSRAM の .bss)。乱数は `esp_fill_random` (WiFi が上がっているので RF の雑音)。
  - `/status` の ident に `"guard":"free|closed|open"` を足した。
  - S3 の 4 KB の転送バッファ: `.bss` から、サーバを始めるとき (`devctl_http_register`) の内蔵ヒープへ。
    リリースのビルドにも devctl が入るので、WiFi を上げない端末に 4 KB を払わせないため。
- `main/drivers/remote_desktop/rd_http.c`: devctl を**いつも**登録 (リリースにも)、しかも viewer の経路より先に
  (guard の arm より前に `/stream`・`/ws` が受け付ける隙をなくす)。`/stream` は 401、`/ws` は
  `{"t":"denied",...}` を 1 枚送って閉じる、`/ws_video` は閉じる。`/`・`remote.js`・`keymap.js`・`/status` は
  開いたまま (登録の画面と端末の見分けのため)。`/status` の ident はリリースでも出す。
  `max_uri_handlers` 28 → 30。
- `main/drivers/devctl/devctl_task.c` (Retro): `/fb` を guard に、`/status` の buffer を広げた、
  `max_uri_handlers` 18/21 → 20/23。
- `main/boot/boot.c`・`main/CMakeLists.txt`: devctl を WiFi のある端末のどのビルドにも入れる。
  `FMRB_DEV_REMOTE_CTL` は「開発のビルド (自由)」か「リリース (guard)」かを分けるだけになった。
- `rakelib/build.rake`: `rake build:esp32` は **`FMRB_RELEASE=1` なら `-DFMRB_DEV_REMOTE_CTL=OFF`、ほかは
  `=ON` を毎回渡す** (CMake のキャッシュにリリースが残らないように。`CMAKE_OPTS` が後に来て勝つ)。

### Config (端末の画面)

- `config_dialog.rb`: リリースのビルドで、WiFi が上がってサーバがあるときだけ (`FmrbSystem.remote_access >= 0`)
  **「遠隔操作 (Remote control)」の 1 行**を足す。矢印で OFF → **ON 123456** (登録の番号) → **登録取消 N PC**
  → OFF。ON・OFF はすぐ効く (ファイルには書かない、再起動で OFF)。登録取消は Save を押したときに実行
  (誤って通り過ぎても何も起きない)。5 回違いの後は「ON (停止中)」。PC が登録すると番号が替わるので、
  周期の tick で番号が変われば描き直す。
  - 行を 2 つにしなかった理由: 今の 13 行で 240 ラインの画面をちょうど使い切っている (224 + メニューバー 15)。
    1 行足すと 238 で、メニューバーの上にかぶせて画面に収める (`@cfg_y` を画面の下端から決める)。
  - 高さは `@cfg_rows`・`@cfg_h` (desktop の重なりの計算も)。開発のビルド・sim では今と同じ。
- FmrbSystem に 5 つ: `remote_access` (-1/0/1)、`remote_access_code`、`set_remote_access(on)`、
  `remote_access_paired`、`revoke_remote_access`。mruby (app.c)・Spinel (ffi・fmrb_spx_app.c)・
  `sig/fmrb_system.rbs`。`rake system:check` 通過。
- i18n: `remote_access` 遠隔操作 / Remote control、`remote_forget` 登録取消 / Forget、
  `remote_revoked` 登録取消済 / PCs forgotten、`remote_locked` 停止中 / locked。

### ブラウザの viewer (`tools/web/remote/remote.js`、端末に埋め込み)

- 最初に `/auth`。閉じていれば「Config > Remote control を ON に」と出して 3 秒ごとに待つ。登録が要れば番号を
  `prompt` で聞いて `/pair`、トークンを localStorage に置き、`/stream`・`/ws`・`/ws_video` に `token=` で付ける。
  切れたら `/auth` からやり直す。開発のビルド (`free`) と古いファーム (404) では何も出ない。

### 道具 (family-mruby tools/)

- `tools/fmrb_rd_token.rb` (新規): `~/.config/fmrb/remote_tokens.json` (ディレクトリ 0700、ファイル 0600、
  `FMRB_CONFIG_DIR` で移せる)。端末の mDNS 名 (`/status` の host) で引き、最後に答えた IP も持つ。

  閉じている (`closed`) ときは「登録済みの PC は ON にするだけ」と言い分ける。
- `fmrb_rd_fs.rb`: 全リクエストにトークン (FmrbFs#with_token)、**`pair <番号>`・`unpair`** を足した。

- MCP (`tools/mcp/`): tab5_* は全部トークン付き。401 は「到達できない」ではなく理由つきの Error にした

- 試験: `tools/fmrb_rd_token_test.rb` (minitest、偽の端末、11 件)、MCP の selftest 8 番に「リリースのビルド」の

  12 番でトークンの試験を呼ぶ。

## 3. 仮に決めたこと (親・ユーザに見てほしい)

1. **5 回違いで止める**: 番号は 100 万通りなので、止めないと ON の間に総当たりで 10 数時間で当たる。5 回違えば
   番号を消し、Config で OFF → ON するまで登録できない (LAN の誰かに邪魔はされうるが、入られはしない)。
2. **番号は 1 回で替わる**: 2 台目の PC は新しい番号を読む。
3. **5 台目はいちばん古い登録を押し出す** (断るより回る方を取った)。
4. **OFF にしても張ったままの画面・入力の接続は切らない** (新しい接続を断るだけ)。切るなら rd_http の
   WS の登録簿と MJPEG の task に「閉じた」を伝える手間が要る。
5. **トークンは NVS に素のまま** (ハッシュにしない)。読むには基板から flash を読むことになり、そのとき /home の
   鍵も同じく読める。
6. **リリースの判定は `FMRB_RELEASE=1`**: `.github/workflows/release-installer.yml` は前から `FMRB_RELEASE: "1"`
   を設定しているが、ファームの `FMRB_DEV_REMOTE_CTL` は ON のままだった。**つまり 3.0.0 を含む今までの
   リリースのファームは開発のビルドと同じ devctl を持っていた** (G0 以後のビルドなら鍵まで読める。3.0.0 は G0 より
   前なので鍵は読めないが、/app・/fs・/audio は無認証で開いている)。この変更で次のリリースから guard が掛かる。
7. 書けるのは `/home`・`/app` だけで、`/mnt/sd` も断る (計画どおり)。`/home` の鍵のファイルへの put は今までどおり
   通す (登録済みの PC は信頼する)。
8. `/sys/reboot`・`/sys/gc`・`/fs/md5`・`/audio/*` はリリースにも残し、guard の下に置いた。

## 5. regress:size

基準 4e7e7e61 との比べ (内蔵 RAM が増えれば落ちる)。S3 と P4 を 1 台ずつ (`ONLY=` で分けて流した)、
S3 はリリースでもう 1 回。

| 端末・ビルド | DIRAM | ほか | 判定 |
|---|---|---|---|
| NARYAv3 (S3) 開発 | 121,339 (**-4,120**) | IRAM 16,384 +0、other 104 +0 | ok |
| NARYAv3 (S3) リリース (`FMRB_RELEASE=1`) | 121,339 (-4,120) | 同じ | ok (`FMRB_DEV_REMOTE_CTL=OFF` を build log で確認) |
| TAB5 (P4) 開発 | 129,338 (-360) | other 948 +0 | ok |

- S3 の -4,120 は 4 KB の転送バッファを `.bss` から WiFi を上げたときの内蔵ヒープへ移した分 (`libmain.a`
  -4,099)。WiFi を上げると実行時に 4 KB を取る (devctl の httpd task の 8 KB と同じく)。
- S3 のリリースは開発と同じ DIRAM。基準 (開発のビルド、devctl 入り) より小さいので、devctl が入っていなかった
  前のリリースと比べても増えていない (前のリリースは基準から devctl の 4 KB を引いた値で、今のリリースと同程度)。
- TAB5 の -360、ほかの部品の動きはこの段より前の変更 (基準 4e7e7e61 から後のコミット)。
- 基準は更新していない。

## 6. 親が P4-Nano で流すこと

焼くのはリリースのビルド。`build/` に残したのは**開発のビルド** (NARYAv4、`FMRB_DEV_REMOTE_CTL=ON`、
6,607,600 B) なので、リリースを作り直す (ターゲットは環境変数で。`.env` は NARYAv3 のまま。どちらも
`rake build:esp32` のたびに ON/OFF を渡すので、`clean_all` は要らない。差分のビルドで 2 分ほど):

```
cd /home/kishima/fmrb/family-mruby/fmruby-core
FMRB_RELEASE=1 FMRB_HW_TARGET=NARYAv4 rake build:esp32     # cmake の出力に "FMRB_DEV_REMOTE_CTL=OFF: release build"
file build/fmruby-core.elf                                  # RISC-V
(MCP) flash   # または serial_stop の後 FMRB_HW_TARGET=NARYAv4 rake flash
```

注意: リリースのビルドは鍵を読まないので **keep_home (WiFi の退避) は使えない**。/home を残すなら G0 の
`rake flash:keep_home_serial`、あるいは先に開発のビルドのうちに `ruby tools/fmrb_rd_fs.rb <IP> backup`。

1. 起動ログに `remote control is closed until Config > Remote control is turned on (0 PCs paired)`。
   `curl -s http://<IP>/status` に `"guard":"closed"`。
2. 閉じていること:
   ```
   curl -s -X POST "http://<IP>/app/launch?path=/app/demo/spinel_hello.app.rb"   # 401 guard closed
   ruby tools/fmrb_rd_fs.rb <IP> ls /app                                         # error: 401 ... の手順
   (MCP) tab5_screenshot                                                         # 401 の Error
   ブラウザで http://<IP>/                                                       # 「Config > Remote control を ON に」
   ```
3. 端末で Config を開く → いちばん下の「遠隔操作」の右矢印 → `ON 123456` (6 桁) が出る。ダイアログが
   メニューバーにかぶって画面に収まっていること (目視)。
4. 登録: `ruby tools/fmrb_rd_fs.rb <IP> pair <番号>` → `paired with fmruby-xxxxxx`。Config の番号が別の番号に
   替わること。`ls -l ~/.config/fmrb/remote_tokens.json` が 600。
   MCP なら `tab5_ip(pair_code: "<番号>")`。
5. 使える: `tab5_app ps`・`tab5_screenshot`・`tab5_input`・`tab5_fs ls /app`、put → launch の流れ。
6. G1: `ruby tools/fmrb_rd_fs.rb <IP> put x.txt /etc/x.txt` → 403 (/home と /app だけ)、`/home/x.txt` は通る。
   `ruby tools/fmrb_rd_fs.rb <IP> get /home/wifi.toml` → 403 (鍵は読まない)。
7. ブラウザの viewer: 番号を聞かれる → 入れると画面と入力が使える (別の番号が要る: 4 の後に替わっている)。
8. 番号違い 5 回 (`pair 000000` を 5 回) → `locked`、Config の行が「ON (停止中)」。OFF → ON で新しい番号。
9. 再起動 (`ruby tools/fmrb_rd_fs.rb <IP> reboot` はこの時点で通る) → 閉じている (401 closed、道具は
   「登録済みの PC は ON にするだけ」) → Config で ON → 再登録なしで使える (NVS に残っている)。
10. 取り消し: Config の行を「登録取消 N PC」まで進めて Save → 「登録取消済」→ PC から 401 bad_token と
    「pair し直す」。
11. 終わったら開発のビルドに戻す (`FMRB_HW_TARGET=NARYAv4 rake build:esp32` で ON に戻る)。

## 7. 残り・気づいたこと

- 実機での 6 章 (Config の行の見た目、番号の替わり、NVS の残り、ブラウザの viewer)。
- **SDK の手順書** (family-mruby-sdk の docs/getting_started の「実機に送る」節) は、この段の指示で触らないことに
  なっているので**直していない**。リリースのファームに送る手順 (Config > 遠隔操作 を ON、`pair <番号>`) を足す必要
  がある (受け入れ条件)。

  開発のビルドの流れ)。`sync` (app_sync) も `/etc`・`/usr` に書くので同じ。
- Retro (S3) のリリースのビルドは regress:size の S3 の開発のビルドで devctl のコードがコンパイルされることだけを
  確かめた (5 章)。Retro の Config の行・登録は実機が要る (S3 は遠隔の画面が無いので、ユーザの操作と serial)。
- 古いリリース (3.0.0) の端末を「壊れた」と言わないよう、404 の説明を「2026-11-16 より前のリリース」に直した。
