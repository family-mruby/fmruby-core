# K2 実施報告: Spinel の File と Lua の io を file HAL 経由に

> 状態: 完了 (親の検収待ち) | 更新: 2026-09-29 | Spinel は File.open / Dir.open / exist? 系だけが入出力の差し替え口を通り、**File.read・write・size・delete・rename、Dir.mkdir・rmdir・entries など約 40 か所が VFS を直接呼んでいた**。フォーク (fmrb-ext daef484b、push なし) で差し替え口に 4 つの口を足して全部を通し、口で表せない操作 (リンク・権限・時刻など) は NotImplementedError にした。Lua は本体を変えず、**Lua の核のソースに見出しを強制で読み込ませて fopen / freopen / remove / rename / tmpfile / tmpnam を HAL 経由の実装に置き換えた** (io・os・loadfile・dofile・require がまとめて通る)。確認の途中で、強制 kill の後の lua_close が死んだタスクのファイルをもう一度閉じて sim で二重解放になることが分かり、強制経路では lua_close を呼ばないようにした。P4-Nano で**直す前は 1 回目で停止、直した後は 2 回とも止まらない**。静的な D/IRAM は 3 機種とも develop と同じ

## 2. 洗い出し: HAL を通っていなかった操作

### 2.1 Spinel (components/fmrb_spinel_rt、フォーク kishima/spinel fmrb-ext)

Spinel の実行時ライブラリは、SP_MULTI_CTX のとき実体ごとの入出力の差し替え口 (sp_instance_config の io_*) を持ち、
fmruby は fmrb_spinel_host.c でそれを HAL につないでいる。差し替え口を通っていたのは一部だけだった。

| 操作 (Ruby) | 実行時の関数 | 直す前 | 直した後 |
|---|---|---|---|
| File.open (モード文字列・フラグの両形) | sp_File_open_perm / _flags_perm | 口 (io_open、fopencookie で stdio に包む) | 同じ |
| File#read / write / gets / seek / close など、開いたファイルへの操作 | stdio → クッキー | 口 (io_read / write / seek / close) | 同じ |
| File.exist? / file? / directory? | sp_file_exist 他 | 口 (io_stat) | 同じ |
| Dir.open / Dir#read / close | sp_Dir_new 他 | 口 (io_opendir 他) | 同じ |
| File.read / binread / readlines / write / write (モード付き・位置付き) / IO.copy_stream / IO#reopen(path) / ARGF | sp_file_read 他 9 関数 | **VFS 直 (fopen / open)** | 口 (sp_vfs_fopen) |
| File.size / size? / zero? / ftype / stat / lstat と File::Stat の型・大きさ・権限の問い合わせ、owned? など | sp_file_size 他 約 20 関数 | **VFS 直 (stat / lstat)** | 口 (sp_vfs_stat: io_stat から型と大きさを作る) |

生成プログラムが実際に使っている File / Dir (gen/ の C と Ruby から数えた):

| プログラム | 使っているもの | 直す前 |
|---|---|---|
| カーネル | File.exist? 2 | 口を通る |
| エディタ | File.open 6 (read / write)、Dir.open 1 | 口を通る |

Spinel 構成のデスクトップの 3 つは、VFS 直のうえ仮想の道 (/etc/..., /home/...) を解決しないので、実機では**そもそも失敗していた**
(設定の保存が「書いて改名」で改名に失敗する、ファイル管理の大きさが 0、削除できない)。今回で HAL を通り、解決もされる。
標準構成のカーネルとエディタは直す前から全部口を通っていたので、K1 の守りが既に効いていた。

| 操作 | Lua の核の中 | 直す前 | 直した後 |

/flash/... も HAL の別名として引き続き開ける。

## 3. 直した内容

### 3.1 Spinel (フォーク daef484b + スナップショットの取り直し)

- `sp_ctx.h` / `sp_ctx.c`: sp_instance_config と sp_ctx に `io_remove` / `io_rename` / `io_mkdir` / `io_rmdir` を足した。
  NULL なら libc の既定 (`sp_io_posix_*`) になるので、口を設定しない実体の動きは変わらない。
- `sp_io.c` / `sp_io.h`: `sp_vfs_stat` (io_stat から stat 構造体を作る。リンクは無いので lstat も兼ねる)、`sp_vfs_remove` 他、
  `sp_vfs_unsupported` (NotImplementedError) を足し、削除・改名・stat による問い合わせ・IO#reopen(path) をそれらへ。
- `sp_cold.c`: 道を開く・stat する・一覧する所を `SP_PATH_FOPEN` / `SP_PATH_STAT` / `SP_PATH_LSTAT` / `sp_pdir_*` に揃えた。
  既定の構成 (SP_MULTI_CTX なし) では従来の libc 呼び出しそのもの。
- フォークの試験 `test/multi_ctx/io_backend.sh` を足し、`make test-multi-ctx` に入れた。読み書き・追記・一覧・stat・改名・削除・
  mkdir / rmdir をする Ruby を、口を数える実体で動かし、既定の構成 (-E) と出力が同じで、全部の口が呼ばれることを見る。
  symlink / chmod / mtime / truncate / chdir が NotImplementedError になることも見る。
- 変更の大きさ: フォークで 5 ファイル +280 / -72 行 (大半は `#ifdef SP_MULTI_CTX` の差し替え)。構成の変更ではなく、
  既にある口の考え方を残りの関数に広げただけなので、止めずに進めた。
- fmruby 側: `fmrb_spinel_host.c` で新しい 4 つの口を HAL の remove / rename / mkdir / rmdir につないだ。
  あわせて fopen のモードから HAL のフラグへの変換で `r+` / `w+` を読み書き両用にした (従来は読むだけ / 書くだけになっていた。
  `a+` は HAL に読み書き追記の開き方が無いので、書くだけの追記のまま)。
- `import_from_fork.rb` でスナップショットを取り直した。**IMPORT_INFO は daef484b、SPINEL_PIN は 4faa22b4 のまま**
  (更新は親の判断)。コンパイラ側 (src/) は変えていないので、生成される C は同じ。`rake spinel:gen` は食い違いの警告を出す。

### 3.2 Lua (本体は変えない)

- `components/lua/fmrb_lua_hal_stdio.h`: Lua の核のソースだけに `-include` で読み込ませる見出し。lprefix.h と <stdio.h> を先に
  読み込んでから、`fopen` / `freopen` / `remove` / `rename` / `tmpfile` / `tmpnam` を HAL 経由の関数に置き換える。
  標準の `io` を別に書き直すのではなく、Lua の核が使う C の関数の入口だけを差し替えたので、書式つきの読み (`"n"` `"l"` `"a"`)、
  lines、seek、setvbuf、エラーの返し方は liolib.c のまま変わらない。
- `components/lua/fmrb_lua_hal_stdio.c`: HAL のハンドルを fopencookie で FILE に包む。クッキーは HAL のハンドルそのもの
  (割り当て無し)。tmpfile だけ名前を覚える小さな構造 (fmrb_sys_malloc) を持つ。一時の名前は時計から作る (静的な数え上げを持たない)。
  失敗で errno が残らない HAL の呼び出しには ENOENT などを入れ、Lua のエラーの文言 (strerror) が出るようにした。
- `components/lua/CMakeLists.txt` と `wasm/CMakeLists.txt`: 核のソースに `-include` を付け、新しい .c を足した。fmrb_hal を REQUIRES に。

### 3.3 強制 kill の後の lua_close をやめた (main/app/fmrb_app.c)

sim の繰り返しの 6 回目で core が `free(): double free detected` で落ちた。順番は、強制経路が HAL の錠の中で
死んだタスクのファイルを閉じる (K1) → その後の資源の後始末で `lua_close` → `__gc` がそのファイルの FILE を fclose →
クッキーが**もう閉じた HAL のハンドル**を閉じる、だった。posix の HAL は close でハンドルを確かめないので二重解放になる
(ESP32 の HAL は枠を確かめるので落ちないが、その間に枠が別のタスクに使われていれば、他人のファイルを閉じうる)。
もう一つ、`f:write` の途中で消されたタスクは FILE の錠を持ったままでありうるので、殺した側で fclose すると
その錠で永久に待ちうる。

`destroy_vm` に「強制か」を渡し、**強制経路では lua_close を呼ばない**ようにした。Lua の使う記憶域はアプリの
メモリプールにあり、直後にプールごと捨てるので、lua_close でしか解放できないものは無い。スクリプトの `__gc` (Lua のコード)
を殺した側のタスクで走らせることも無くなる。協調終了 (アプリ自身の後始末) では従来どおり lua_close してから、
残ったハンドルを閉じる。

Spinel は実体を壊すとき後始末 (finalizer) を走らせない作りなので、同じ問題は起きない。mruby は File を後始末しない。

## 4. 確認

### 4.1 sim

一時アプリ (コミットしない。scratchpad/k2_apps):

- `fsk2_lua_writer`: 1 回の `f:write(table.unpack(parts))` で大量に書く。Lua の停止要求は VM の命令の合間でしか読まれないので、
  C の関数の中に 1 秒より長くいれば強制経路に落ちる。sim はホストのファイルが速いので 1 回 4 GB (512 KB × 8000)、実機は 320 KB (16 KB × 20)。
- `fsk2_lua_io`: 2.2 の表の操作を 24 項目確かめる。
- K1 の `fskill_writer` (mruby) / `fskill_check` (書いて読み戻す) をそのまま使った。

## 6. 残ること・気づいたこと

- **強制 kill で置き去りになる FILE**: Lua と Spinel のファイルは C の FILE (fopencookie) で包んでいる。強制 kill では
  それを閉じない (3.3) ので、C ライブラリの FILE の表に 1 つ残る (FILE の構造と stdio の緩衝、ESP32 では内蔵 RAM から
  数百バイト)。強制 kill 1 回で開いていたファイルの数だけ。直す前の Lua (fopen) でも同じだけ残っていたので、増えてはいない。
  その FILE のクッキーは閉じたハンドルを指したままなので、全部の FILE を掃く `fflush(NULL)` を誰かが呼ぶと危ない。
  ファームの中で呼んでいるのは Spinel のプロセス関係 (組み込みでは通らない) だけ。
- **HAL のハンドルの枠 (10 個) を Lua も使う**ようになった。直す前の Lua は VFS の記述子を直に使っていて、この枠に数えられて
  いなかった。多くのファイルを同時に開く Lua のスクリプトは、ほかの言語と合わせて 10 個までになる。
- posix の HAL の close / read / write はハンドルを確かめない (ESP32 の HAL は確かめる)。3.3 で今回の経路は塞いだが、
  閉じたハンドルを使う誤りがあれば sim では二重解放、実機では空振りと、振る舞いが違う。
- Spinel 構成のデスクトップの設定の保存・ファイル管理の大きさ・削除は、今回で動くはずになったが、その構成の sim は回していない
  (フォークの io_backend の試験で改名・削除・大きさの口が呼ばれることと、fmruby 側の口が HAL を呼ぶ 1 行であることまで)。

## 7. 判断してほしい点

1. **SPINEL_PIN の更新**: フォーク fmrb-ext に daef484b をコミットした (push していない)。スナップショット (IMPORT_INFO) は
   daef484b、SPINEL_PIN は 4faa22b4 のまま。push と PIN の更新をするか。コンパイラ (src/) は変えていないので、PIN を上げても
   生成される C は変わらない。
2. **口で表せない操作を NotImplementedError にしたこと** (2.1 の表の該当行): 直す前は VFS 直で、実機では仮想の道が解決されずに
   失敗、sim ではコンテナの中の別のファイルに答えていた。黙って違うファイルに答えるより例外の方がよいと判断した。
   File.mtime など時刻は、HAL の stat に mtime はあるが、口の約束を広げるほどの使い道が今は無いので外した。
3. **強制 kill で lua_close を呼ばない** (3.3): スクリプトの `__gc` は強制 kill では走らなくなる (協調終了では走る)。
4. 上流への PR (U-系の台帳) に載せるか。`SP_MULTI_CTX` の口の約束を広げる変更で、上流の関心で書くなら
   「差し替え口を設定した実体の道の操作が、口を迂回して libc に行っていた」不具合として出せる。
