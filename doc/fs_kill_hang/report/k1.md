## 2. 再現と特定 (T1)

### 2.1 再現の手順

一時アプリ 2 本 (コミットしない。scratchpad に退避):

- `fskill_writer`: `on_update` の中で 2 MB のファイルを 16 KB ずつ `File#write` し続け、`on_update` から戻らない
  (r2 の実機試験と同じ 16 KB 単位)。停止要求は `on_update` の合間でしか読まれないので、kill は必ず強制経路に落ちる。
- `fskill_check`: `/home` に小さく書いて読み戻し、各段階をログに出す。

手順: writer を起動 → 1-2 秒後に kill → check を起動。

**T1.3 の切り分け**: 毎回 `No response in 1000ms, forcing termination` が出ており、**強制経路 (fmrb_task_delete) を通った**。
協調終了 (should_exit) では止まっていない。mruby のアプリは VM の途中で should_exit を見ないので、
`on_update` の中で長く回る処理は必ず強制経路に落ちる (Lua / BASIC / Python は VM の命令ごとに見るので協調終了する)。

### 2.2 sim (gdb の証拠)

Linux の file HAL (`fmrb_hal_file_posix.c`) も `s_file_mutex` で全操作を直列化し、無期限に待つ作り (ESP32 と同じ)。
kill の後の check の起動 (debugd の spawn) が応答しなくなった。再起動の前に gdb を当てた。

止まっていたスレッド (debugd):

```
#9  xQueueSemaphoreTake (xQueue=0x7a5f04000db0, xTicksToWait=18446744073709551615) at queue.c:1901
#10 fmrb_hal_file_open (path="/app/test/fskill_check.app.rb", flags=1, ...) at fmrb_hal_file_posix.c:189
#11 spawn_user_app (...) at fmrb_app_spawner.c:617
#13 handle_spawn (...) at fmrb_debugd.c:291
```

待っている錠 `s_file_mutex` (= 0x7a5f04000db0) の中身:

```
xMutexHolder = 0x7a5ef4021410, uxMessagesWaiting = 0 (取られている), xTasksWaitingToReceive = 1 (debugd)
持ち主の TCB: pcTaskName = "FsKillWriter", uxMutexesHeld = 1, uxPriority = 3 (debugd から継承), uxBasePriority = 2,
             xStateListItem.pxContainer = 0x0 (どの状態リストにも居ない = 削除済み)
g_ctx_pool[5]: app_name = "FsKillWriter", state = PROC_STATE_FREE, task = 0x0
```

**錠は `s_file_mutex`、持ち主は強制 kill で消された FsKillWriter**。スロットは既に FREE に戻っている。
kill 自体は `ok` を返しており、止まるのはその後のファイル操作 (アプリの起動もスクリプトを HAL で読むので止まる)。

### 2.3 実機 (P4-Nano、修正前のファームウェア 0f021d6f = develop のコード)

flash への書き込みを増やさないため、焼き直さずに r2 のファームウェアのまま 1 回だけ試した。

1. writer を起動し、約 9 秒後に `/app/kill` → `forcing termination` → `Killed by force`、kill は ok。
2. `/app/list` (ファイルに触らない) → **応答する**。
3. `/fs/list /home` → **タイムアウト**。
4. 以後 `/app/list` も応答しない (httpd は 1 本のタスクなので、3 で止まったまま)。
5. シリアルからのリセットで戻した。書きかけの `/home/fskill_big.bin` は **0 バイト**だった。

3 が決め手になる。devctl の `/fs/list` は file HAL を通らず `opendir` を直接呼ぶ (devctl_http.c)。
`opendir` → VFS → `vfs_littlefs_opendir` の経路で取る錠は **LittleFS の錠 (esp_littlefs の `efs->lock`、再帰 mutex)** だけで、
`s_file_mutex` は取らない。消えた writer は `fwrite` → `vfs_littlefs_write` の途中 (= `efs->lock` を持った状態) で消されたので、
実機では **HAL の錠と LittleFS の錠の両方**が失われている。r2 の「遠隔の要求がすべて応答しなくなった」はこれで説明がつく
(sim の書き込み先はホストのファイルなので、LittleFS の錠は sim には無い)。

実機に一時的なログは入れなかった。sim で錠と持ち主が確定し、実機は HAL を通らない経路で止まることが
LittleFS の錠を指しているため、計測用の焼き直し (約 6 MB) を省いた。

### 2.4 原因のまとめ

- 強制 kill の経路 (`fmrb_app_kill` → `fmrb_task_delete`) は、registry と MicroPython の錠には障壁を置いていたが
  (archive/app_kill_fix 3b)、**ファイル操作の錠には何も置いていなかった**。
- ファイル操作は短い窓ではない。16 KB の書き込み 1 回が実機で 130-190 ms、`File#write` 1 回で数十秒もありうる。
  書き続けるアプリは時間のほとんどを錠の中で過ごすので、猶予 1 秒の後に消すと高い確率で錠の中に当たる
  (sim で 2 / 2、実機で 1 / 1)。
- FreeRTOS の mutex は持ち主にしか返せないので、消した後に返す手は無い。

## 3. 修正 (T2)

### 3.1 候補の比較

| 案 | 内容 | 判断 |
|---|---|---|
| A. 強制経路でファイル操作中は消さない | kill 側が HAL の錠を取り、持ったまま消し、消してから返す | **採用**。錠を取れた = 相手はファイル操作の外か、この錠を待っている (どちらも消して安全)。LittleFS の錠は HAL の錠の内側でしか取られないので、同時に守れる。平常時の費用はゼロ |
| B. ファイル操作を消されない専用タスクに任せる | hw_proxy のような代理 | 採らない。全ファイル操作が 1 往復ぶん遅くなり、タスクのスタック (内蔵 RAM) が要る。A で足りる |
| C. 錠の持ち主を覚えて消した後に始末 | | 採らない。mutex は持ち主にしか返せない。LittleFS の中途の状態も戻せない |
| (参考) mruby の VM で should_exit を見る | 協調終了にできれば強制経路が要らない | 今回は採らない。submodule の mruby-task に手が入り、長い 1 回の `File#write` の最中は結局 C の中にいるので A は別に要る |

A の障壁は、3b の「取ってすぐ返す」では足りない。ファイル操作は次々に続くので、返した直後にアプリが次の書き込みに入る。
そのため**持ったまま消す**形にした。

### 3.2 変更点

- `components/fmrb_hal/fmrb_hal_file.h` (API 追加、ESP32 と posix の両方に実装)
  - `fmrb_hal_file_lock(timeout_ms)` / `fmrb_hal_file_unlock()`: HAL の直列化の錠を外から取る。
  - `fmrb_hal_file_close_owned_locked(owner)`: 指定したタスクが開いたファイルとディレクトリを全部閉じる (錠を持って呼ぶ)。
- `main/app/fmrb_app.c`
  - 強制経路: 錠を取る (取れるまで待つ。5 秒ごとに「待っている」と警告) → 既存の registry / MicroPython の障壁 → 削除 →
    そのタスクが開いていたファイルを閉じる → 錠を返す。閉じたら数をログに出す。
  - アプリ自身の後始末 (`app_task_main` の cleanup): VM を閉じた後に、そのタスクが開いたままのファイルを閉じる。
- `components/fmrb_hal/platform/esp32/fmrb_hal_file_esp32.c`
  - ファイル・ディレクトリの枠に開いたタスク (`owner`) を持たせた (枠は PSRAM にある)。
  - 錠の外で VFS を呼んでいた 3 か所を錠の中に入れた: `readdir` の後の `stat`、`statfs` (`esp_littlefs_info` が LittleFS の錠を取る)、
    `mkfs`。A は「LittleFS の錠は HAL の錠の内側でしか取られない」ことに依っているため。
- `components/fmrb_hal/platform/posix/fmrb_hal_file_posix.c` (sim と wasm が使う): 開いている handle を一覧に持ち、
  `owner` で閉じられるようにした。
- `lib/add/hal-esp32-dir/dir_hal.c` (Ruby の `Dir`、ESP32): HAL を通さず VFS を直接呼んでいた
  `opendir` / `readdir` / `closedir` / `rewinddir` / `mkdir` / `rmdir` / `chdir` / `stat` を HAL の錠の中に入れた。

### 3.3 待ちの上限を置かなかった理由

3d (同期 I/O) は 30 秒で打ち切って消すが、ファイル操作で同じことをすると、打ち切った時点で錠を持っているのは相手なので、
消せば確実に全ファイル操作が止まる。ファイル操作は、ファイルシステム自体が壊れていない限り必ず終わる。
壊れているなら消しても何も救えない。よって上限なしで待ち、5 秒ごとに警告を出す。
kill を呼んだタスク (httpd / debugd) は、相手の書き込み 1 回ぶん (実機で 160-190 ms、最悪は 1 回の `File#write` の長さ) 待つことになる。

### 3.4 書きかけのファイルの扱い

**kill までに書けた分で閉じる (途中まで残る)**。LittleFS は close で内容を確定するので、ファイルシステムは壊れない。
実機で 114,688 B と 163,840 B (どちらも 16 KB の倍数 = 書き込みの区切り) が残ることを確かめた。

- 修正前は、閉じられずに残るので書いた分は確定せず (実機で 0 バイト)、HAL の枠 (10 個) と VFS の記述子と
  LittleFS の開いたファイルの状態が漏れていた。10 回の強制 kill で HAL の枠が尽きる。
- 途中まで残るのが困るアプリは、一時名に書いて rename する (遠隔の put と同じ作り)。消す案は、アプリが何を
  意図していたか分からないので採らなかった。

アプリ自身の後始末でも閉じるようにしたのは、Python / BASIC の停止要求は VM の途中で巻き戻すので、スクリプトの close を
通らないことがあるため (mruby もこの経路では File を後始末しない)。閉じた数は警告に出る。

## 4. 同じ種類の穴 (ESP32 / Linux / wasm の HAL)

| 経路 | 状況 |
|---|---|
| file HAL (ESP32 / posix) を通る操作: mruby の File、エディタの保存、アプリの起動、toml、MicroPython の bridge、BASIC の資産 | **今回で塞いだ** |
| mruby の Dir (ESP32 の dir_hal.c) | **今回で塞いだ** (HAL の錠の中へ) |
| HAL 内で錠の外にあった VFS 呼び出し (`readdir` 後の `stat`、`statfs`、`mkfs`) | **今回で塞いだ** |
| Lua の `io` (liolib.c、submodule) | 残る。`fopen` / `fwrite` を直接呼ぶので HAL の錠に入らない。Lua は VM の命令ごとに停止要求を見るので、ループで書く限り協調終了する。1 回の `f:write` が猶予 1 秒を超える (r2 の速さからの見積もりで、実機で約 100 KB を超える 1 回の書き込み) と強制経路に落ち、同じ停止が起こりうる。submodule を変えずに塞ぐなら、`fmrb_lua` で `io` を HAL 経由の実装に差し替える案がある |
| Spinel の実行時ライブラリの File (sp_io.c、外部の部品) | 残る。VFS を直接呼ぶ。Spinel で動く窓アプリ (エディタ) の保存は `fmrb_spinel_host.c` 経由で HAL を通るので、今回の経路は塞がっている |
| devctl (httpd) の遠隔のファイル転送 | 殺されるタスクではないので問題ない (錠を持って消されることが無い) |
| hw_proxy 経由の操作 (PSRAM スタックのタスクだけ) | 殺される側が `hw_proxy_call` の中 (hw_proxy の `s_mutex` を持ち、応答が自分のスタックに書かれる) で消されると同じ種類の穴になる。いまアプリのスタックは内蔵 RAM で、この経路を通らない (fmrb_task_config.h)。PSRAM スタックを戻すときは要対策 |
| posix (sim / wasm) | ホストのファイル / emscripten のファイルシステムなので LittleFS の錠は無い。HAL の錠は同じ作りで、今回の修正がそのまま効く (sim で確認、wasm はビルドと node での起動まで) |

既存の registry / MicroPython の障壁 (3b) は「取ってすぐ返してから消す」ので、返してから消すまでの間に相手が錠に入る隙がある
(P4 は 2 コアで、相手は別のコアで動ける)。どちらも錠の中は数命令なので当たりにくいが、今回と同じく持ったまま消す形に
揃えるとより確実になる。今回は範囲外として触っていない。

## 6. 判断の結果 (親経由、ユーザ)

「推奨どおり」:

1. 錠を待つ時間に上限は置かない。5 秒ごとの警告は残す。
2. 書きかけのファイルは途中まで残す。
3. アプリの通常の終了でも、開きっぱなしのファイルを閉じる (このまま)。
4. Lua の `io` と Spinel の File の穴は記録して別段階にする (plan.md の「残り」)。
5. registry と MicroPython の錠も「持ったまま消す」形に揃える → 7 章で実装した。

## 7. registry と MicroPython の錠を持ったまま消す

### 7.1 変更

- 3b の障壁 (`fmrb_msg_registry_lock_barrier` / `fmrb_mp_lock_barrier`: 取ってすぐ返し、それから消す) は、返してから消すまでの間に
  相手が錠に入る隙があった (P4 は 2 コアで、相手は別のコアで動ける)。これを取る関数と返す関数の組
  (`fmrb_msg_registry_lock` / `_unlock`、`fmrb_mp_lock` / `_unlock`) に置き換え、削除をはさんで持つようにした。
  障壁の関数は消した (呼んでいたのは fmrb_app.c の 1 か所だけ)。
- 強制経路の並び: ファイルの錠を取る → registry → MicroPython → 削除 → MicroPython を返す → registry を返す →
  開いていたファイルを閉じる → ファイルの錠を返す。

### 7.2 順番とデッドロックしないこと

取る順番は **ファイル → registry → MicroPython**、返すのは逆順。3 つを重ねて持つのは強制経路だけで、ほかの経路は
どれか 1 つを持っている間にほかの 2 つを取らない。

| 錠 | 持っている間にすること | ほかの 2 つを取るか |
|---|---|---|
| ファイル (`s_file_mutex`) | VFS の呼び出し (LittleFS の錠を内側で取る)、ログ | 取らない (HAL の中で送信も Python にも触らない) |
| registry (`g_registry_lock`) | 登録表の読み書き、キューの確保と解放 | 取らない (ファイルにも Python にも触らない。送受信そのものは錠の外) |
| MicroPython (`s_lock`) | `s_owner` の読み書きだけ (acquire の中) | 取らない |

逆向きに重ねる経路が無いので、強制経路どうし (httpd と debugd が同時に kill しても順番は同じ) を含めて循環は起きない。
registry と MicroPython の錠の中は数命令で止まらないので、kill 側が待つのはファイル操作の終わりだけ。

ファイルの錠とは別の組み合わせで、1 か所見つけて直した: 1 本目の修正で Ruby の `Dir` (dir_hal.c) は、hw_proxy へ回す経路でも
呼ぶ側がファイルの錠を持ったまま `hw_proxy_call` に入っていた。hw_proxy へ回るファイル操作は「hw_proxy の錠 → (代理のタスクが)
ファイルの錠」の順なので、逆順になっていた (PSRAM スタックのタスクが 2 本同時に使うとデッドロックしうる。いまアプリの
スタックは内蔵 RAM なので、この経路は通らない)。hw_proxy へ回すときは、代理のタスクがファイルの錠を取る形
(hw_proxy_file.c) に改め、順番を「hw_proxy → ファイル」に揃えた。

### 7.3 確認

| 構成 | 内容 | 結果 |

## 8. 残り (別段階)

- Lua の `io` (liolib.c、submodule): HAL を通らず VFS を直接呼ぶ。1 回の `f:write` が猶予 1 秒を超えると強制経路に落ち、
  同じ停止が起こりうる。塞ぐなら `fmrb_lua` で `io` を HAL 経由の実装に差し替える。
- Spinel の実行時ライブラリの File (sp_io.c、外部の部品): 同じく VFS を直接呼ぶ。
- hw_proxy の途中で消される穴: PSRAM スタックのタスクを戻すときに要対策 (4 章)。
