## 0. 要約

- スプライトの BMP 90 枚をパレットの PNG に、壁紙 8 枚を同じ色のパレットの PNG に作り直し、BASIC の 2 枚を 1 bpp・4 bpp の BMP にした。
  起動画面 (`boot.png`) はそのまま。**PicoRabbit の 8 枚は BMP のまま残した** (端末のスプライトエディタで直す前提の絵で、エディタは
  BMP しか開けない。5 章の決めること 1)。
- 読む所は 2 か所 (fmruby-core の display_local、graphics-audio) で、`LOAD_SPRITE_IMAGE_BMP` が先頭の 8 バイトで PNG と BMP を
  見分ける。P4 の側は 8 bit (RGB332) の仮のスプライトに `drawPng` してから、BMP と同じ `drawPixel` の輪で RGB565 へ入れる。
  `load_bmp` の名前と線の形は変えていない。
- git の画像は 2,038,266 B → 148,551 B。storage の像は **P4 (Tab5・NARYAv4) 659 → 547 区画 (-112、-0.44 MB)、
  NARYAv3 463 → 406 区画 (-57、-0.22 MB)**。
- 回帰: `rake regress` (基準の更新は walk_scroller の 5 つ、ファイル名だけ)、`regress:screens` 33/33 (基準の変化なし)、
  `regress:run`・`regress:live` 16/16・`regress:size` (内蔵 RAM の増加なし) が通った。
- 別件の調べ 2 つ (P4 の `/cache` の複製、pngle の 44 KB) は 6 章。どちらもコードは変えていない。

## 5. 決めること (ユーザ)

1. **PicoRabbit の 8 枚と、スプライトエディタ**: 端末のスプライトエディタ (`sprite_editor.app.rb`、`BMP332.load`) は BMP しか開けない。
   PicoRabbit の絵は「エディタで直したファイルが正」と道具に書いてあるので、BMP のまま残した (8 区画)。ほかの PNG にした絵
   (shooter など) も、エディタで開くことはできなくなった (道具で作り直す絵なので実害は小さい見込み)。選択肢: (a) このまま
   (エディタで直したい絵は BMP)、(b) エディタに PNG の読み込みを足す (core 側で inflate が要る。P4 は LovyanGFX の pngle が使える
   が Retro の core には無い)、(c) PicoRabbit も PNG にしてエディタの対象から外す。family-mruby 直下の `tools/fm_asset_editor`
   (ホストの絵の道具) も BMP を書く。読む所が両方受けるので、出来た BMP はそのまま使える。
2. 6 章の 2 つ (`/cache` の複製をやめるか、pngle を PSRAM へ移すか)。

## 6. 別件の調べ (コードは変えていない)

### 6.1 P4 の `sync_file` が同じ FS に複製を作る件

- 経路: `FmrbGfx#sync_file` → `fmrb_kernel_sync_file` (元の大きさと CRC を読み、写しの状態を聞く) → 違えば元を全部読んで
  `FILE_CMD_TRANSFER` → host_task の `file_transfer_start` が Modern (`FMRB_HAS_LOCAL_DISPLAY`・`FMRB_PLATFORM_HOSTED`) では
  `host_file_local_write` で **同じ littlefs の `/cache/...` に書く**。状態の答え (`host_file_local_status`) も写しを全部読んで CRC を出す。
- かかるもの: (1) storage に元と写しの 2 つ。(2) 呼ぶたびに元と写しを全部読む (CRC)。(3) 最初の 1 回は書き込み (32 KB で 353 ms の
  実測、voice/report/v2.md)。
- **PNG にしたので (1)・(3) はほぼ消えた**: P4 の麻雀の写しは 222 KB → 10 KB、アイコンは 16 × 1.6 KB → 16 × 約 110 B (inline)。
  残るのは (2) の読み (P4 の麻雀の開始で 15 KB) と、写しのファイルの数。
- やめるなら: `fmrb_kernel_sync_file` (または `FmrbGfx#sync_file`) で Modern のときは何もせず成功を返し、アプリが `dest:` に書いた
  `/cache/...` を読む所 (display_local の `resolve_vfs_path`) で元のパスへ置き換える必要がある。アプリは元ではなく `dest` のパスを
  `load_bmp` に渡しているので、「元のパスを返す」だけでは足りない (アプリを直すか、写しのパスと元の対応を表に持つ)。ネイティブ版の
  写しは `~/.cache/family-mruby-dev/cache` にあり、元の `/app` は読み取り専用の木なので、同じ扱いができるかも確かめが要る。
  効果は PNG の後では小さい (数十 KB・数区画と、読みの数十 ms) ので、急ぐ理由は弱い。

### 6.2 pngle の作業領域 (44 KB) が内蔵 RAM にあるか

- `sizeof(pngle_t)` = **44,408 B** (ホストで測った。読みの緩衝 512 B + inflate の状態 約 11 KB + 32 KB の辞書)。
  `LGFXBase::draw_png` が static の 1 つを `lgfx_pngle_new()` (`PNGLE_MALLOC` = 素の `malloc`) で一度だけ作り、解放しない。
- core の P4 (`sdkconfig.defaults.tab5`・`naryav4`) も Retro の S3 (`naryav3`) も `CONFIG_SPIRAM_USE_CAPS_ALLOC=y`・
  `CONFIG_SPIRAM_USE_MALLOC` 無しなので、**素の malloc は内蔵 RAM**。P4 では最初の `drawPng` (起動画面 `boot.png`、
  system_desktop の `create_image`) で 44 KB が内蔵 RAM に取られ、ずっと残る見込み。graphics-audio (WROVER) も同じ設定。
- ほかに `drawPng` のたびに: 行の緩衝 (`scanline_buf`、幅 × ビット数、次の PNG まで残る。**壁紙を RGB からパレットにしたので
  1280 幅で 7.7 KB → 約 0.3 KB に下がった**)、パレット (色数 × 4 B)、LGFX の行の緩衝 (幅 × 4 B、`heap_alloc_dma`、描き終わりで解放)。
  スプライトの PNG は増える方向の一時の山を作らない (BMP の 1/20 のファイル)。
- **M1| の行は sim・ネイティブ版では出ない** (ESP32 だけ) ので確かめられていない。起動画面は M1 の区切りの間 (アプリの `spawn:`
  の行の後) で描かれるので、実機では デスクトップの `M1|spawn:<名前>` の行と、その後の 10 秒周期の `IRAM free:` の差、または
  `boot_splash = false` で焼いた時との差で見る (7 章)。
- 移すなら: LovyanGFX (m5gfx の managed component と hosted/vendor) の `lgfx_pngle_new` の malloc を `heap_caps_malloc(...,
  MALLOC_CAP_SPIRAM)` にする差し込み (lib/upstream の patch) か、起動画面の後に `releasePngMemory()` を呼んで次の PNG で作り直す形。
  32 KB の辞書を PSRAM に置くと inflate の速さが落ちる見込みなので、実機で壁紙・起動画面の時間を測ってから決める。
