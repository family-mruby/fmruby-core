# F3 報告: 声の WAV を IMA-ADPCM にする

> 開始 2026-11-16 10:15 (JST) / 終了 2026-11-16 11:20 | 親: ../plan.md の F3 (未確定事項 3 の決定: IMA-ADPCM)

## 0. 要約

- 麻雀の声 6 本 (`flash/usr/share/sounds/voice/mahjong/default/`) を 4 bit の IMA-ADPCM (WAV の形式 0x11、16 kHz・モノラルのまま)
  にした。**133,544 B → 37,224 B** (約 28%)。P4 の storage で **40 → 16 区画 (-24 区画、-96 KB)**。Retro の像は前から声を外している。
- 復号は共有の `fmrb_wav.c` (fmruby-core の `components/fmrb_audio` と、graphics-audio の `main/common` の写し) に足した。
  鳴らす所はこの 2 つしかなく、P4・ネイティブ版・ブラウザ版は `audio_p4_task.c`、sim は graphics-audio の `audio_task.c` が使う。
  鳴りながら 1 標本ずつ復号する (全体を PCM に戻した領域は作らない)。PCM の WAV は今までどおり鳴る。
- **内蔵 RAM の静的な増分 0**: 再生の状態 (`fmrb_wav_stream_t`) は 32 bit で 20 B のまま (前も 20 B)。復号器の状態は、読み込んだ
  ファイルの領域 (P4 は PSRAM) のヘッダの上に置く。表 (89 の step) は const で flash に入る。
- 変換の道具は **`tools/ima_adpcm.rb`** (標準ライブラリだけ)。出す標本のバイトは `ffmpeg -i in.wav -c:a adpcm_ima_wav out.wav`
  (ffmpeg 4.4) と 6 本とも同じ。`tools/mahjong_voice_default.rb` も最後にこれで符号化するので、作り直しても同じファイルになる。
- ついでに見つけた既存の不具合 2 つを直した (4 章): 65,536 標本 (16 kHz で約 4 秒) を越える WAV が先頭に戻って鳴り続ける、
  補間の掛け算が全振幅の段差で int32 を溢れる。
- 確認: `rake regress` (ホスト 29 組・描画の記録 229)、新しい live の場面 `wav_voice` (PCM の前と ADPCM の後で振幅・長さが同じ)、
  regress:live 17/17・screens 33/33・run (流し直しで通過)・size (内蔵 RAM の増加なし)。

## 1. WAV を鳴らす所 (調べた結果)

| 端末 | 鳴らす所 | 備考 |

| Retro (S3 + WROVER) | 鳴らさない (`fmrb_bnd_audio_play_wav` が Retro では送らずに false)。WROVER の graphics-audio にも同じコードは入る | sim の Retro 構成も同じ |

- `flash/` の WAV: 麻雀の声 6 本と、F1 で像から外した試験の音 2 本 (`sine440_*.wav`、ホストの試験が読む) だけ。効果音は
  APU・FMSQ で、WAV ではない。

  ゲームの中はずんだもん (PCM) が鳴る**。変換はしていない (6 章の決めること 1)。
- asterism-games の commentate の音はブラウザ・PC 側の別リポジトリで、この段の外。

## 2. 復号の作り

- 形式: `fmt ` の形式 0x11、モノラル、4 bit、block_align (ffmpeg は 1024 B = 2,041 標本)。ブロックは 4 B の頭 (最初の標本の値・
  step の番号・0) と、残りの標本の 4 bit (下位が先)。`fmt ` の拡張の samples per block が block_align と食い違う・4 bit でない・
  ステレオは断る (今までどおり 1 行のログ)。`fact` があれば、その標本数で止める (最後のブロックの埋め草を鳴らさない)。
  途中で切れたブロックは、あるだけ鳴らす。
- 1 標本の式は ffmpeg の復号器と同じ `((2n + 1) * step) >> 3`。ffmpeg の符号化器が予測に使う式と同じなので、ブロックの中で
  ずれない (教科書どおりの「step/8・/4・/2 を足す」式は切り捨てが違い、最大 66 ずれる)。`tools/ima_adpcm.rb` の復号と ffmpeg の
  復号 (`-f s16le`) が全標本で一致することを確かめ、ファームの復号はホストの試験でその Ruby の復号と全標本を比べる。
- 補間 (16 kHz → APU の 15,720 Hz) は今までどおり 2 点の直線。復号器は「今の標本」と「次の標本」を持ち、読み位置が進んだ分
  だけ前へ復号する (戻らない)。1 出力標本あたり最大 4 標本 (48 kHz のとき)。
- 置き場: `fmrb_wav_stream_start_file(st, buf, info, out_rate)` を足し、両方の読み手はファイル全体を読んで parse したあとこれを
  呼ぶだけにした (前は読み手ごとに memmove していた)。PCM は今までどおり標本を領域の先頭へ寄せ、ADPCM は標本をそのままにして
  ヘッダ (48 B 以上。復号器は 64 bit で 40 B) の上に復号器を置く。ヘッダが短すぎる WAV は断る (変換器が出すものには無い)。
- 「全体のバッファを持たない」について: 圧縮したファイルは今までどおり丸ごと読む (読み手のタスクを増やさない今の作り。
  `audio_p4_task.c` の注釈のとおり)。PCM に戻した全体 (4 倍の大きさ) は作らない。声 1 本あたり PSRAM は 19〜26 KB → 5〜7 KB。

## 3. 変換と大きさ

```
ruby tools/ima_adpcm.rb flash/usr/share/sounds/voice/mahjong/default/*.wav   # PCM のファイルだけその場で変換
ruby tools/ima_adpcm.rb --out DIR FILE.wav...                                   # 別の所へ
ruby tools/ima_adpcm.rb --check FILE.wav...                                     # 形式・長さ・大きさ
ffmpeg -i in.wav -c:a adpcm_ima_wav out.wav                                     # 同じ標本のバイト (fact と LIST だけ違う)
```

- ffmpeg との違いは 2 つで、どちらも再生には効かない: `fact` は本当の標本数 (ffmpeg は最後のブロックの埋め草を含めた数を
  書き、それで止めると最大 0.13 秒長くなる)、エンコーダ名の `LIST` を書かない。
- `rake voice:mahjong_default` (`tools/mahjong_voice_default.rb`) は正規化のあとに `ImaAdpcm.convert` を通す。CREDITS.md の
  「Generated, not edited」の行に符号化を足した。

| 声 | 長さ | PCM | IMA-ADPCM |
|---|---|---|---|
| riichi | 0.80 s | 25,644 B | 7,228 B |
| pon | 0.62 s | 19,724 B | 5,180 B |
| chi | 0.68 s | 21,804 B | 6,204 B |
| kan | 0.66 s | 21,004 B | 6,204 B |
| tsumo | 0.82 s | 26,124 B | 7,228 B |
| ron | 0.60 s | 19,244 B | 5,180 B |
| 計 | | 133,544 B | **37,224 B** |

- littlefs (`littlefs-python 0.13.3`、block_size 4096) に 6 本だけ書いた使用区画: 40 → 16 (ディレクトリの分を含む)。
- 復号した音と元の PCM の差 (RMS) は 320〜930。これは ffmpeg が作るものと同じ (ユーザが聴き比べで良しとしたもの)。
  頭の正規化 (-1 dBFS = 29,205) は復号後も 1 割以内 (試験で確かめる)。

## 4. ついでに直したもの

- **長い WAV が先頭に戻る**: 読み位置が 16.16 の 1 語 (`pos_q16`) で、65,536 標本で溢れて 0 に戻っていた。16 kHz で 4.1 秒、
  24 kHz で 2.7 秒を越える WAV (tts のキャッシュの声など) は、終わらずに頭から鳴り直し続けていたはず (実機・sim では確かめて
  いない、コードを読んだ結果)。標本の番号と 16 bit の端数に分けた (構造体の大きさは同じ)。試験 `test_long_clip_does_not_wrap`。
- **補間の溢れ**: `(b - a) * frac` が全振幅の段差 (65,535 × 65,535) で int32 を越えていた。端数を 1 bit 落として掛ける。

## 6. P4 (NARYAv4) のビルド

本体の checkout の `build/` に残した (焼くのは親)。`rake clean_all` → docker で
`idf.py -DSDKCONFIG_DEFAULTS=config/sdkconfig.defaults.naryav4 set-target esp32p4` → `~/toolchains/cache/littlefs_py_venv` を
`build/` へ写す → `FMRB_HW_TARGET=NARYAv4 rake build:esp32` (doc/wasm_apps/report/w1b_2.md 7 章の順)。

| 項目 | 値 |
|---|---|
| `file build/fmruby-core.elf` | ELF 32-bit RISC-V |
| DIRAM (内蔵 RAM の静的な使用) | **124,876 B** (F2・W1b と同じ。増分 0) |
| `fmruby-core.bin` | 7,636,432 B (app の区画の空き 8%) |
| storage の像の声 | `default/` の 6 本は ADPCM (37 KB)。その上の `usr/share/sounds/voice/mahjong/` に flash_local のずんだもん 6 本 (PCM) |

- 実機で聴くもの: (1) 麻雀でゲームの中の宣言は、この像では flash_local のずんだもん (PCM、変わっていない) が鳴る。
  (2) ADPCM の既定の声 (Open JTalk の Mei) は、試験のアプリを送って鳴らす:
  `ruby tools/fmrb_rd_fs.rb <IP> tests push wav_voice` → `/app/test/wav_voice.app.rb` を起動 → キー 1〜6 (リーチ・ポン・チー・
  カン・ツモ・ロン)。ログに `play_wav: /flash/usr/share/sounds/voice/mahjong/default/riichi.wav (12800 frames @ 16000 Hz, IMA-ADPCM)`。
  聴くこと: 声が 1 回ずつ最後まで、雑音・プツ音なく、PCM の頃と同じ高さ・長さで鳴るか。
