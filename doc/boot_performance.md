# ブート時間の実測とコストモデル

デスクトップの起動が遅い件を、推測ではなく実測で分解した記録。
**結論として原因は 3 つに分かれ、それぞれ効く範囲が違う**。ランチャーの
スキャンだけの話ではないので、Ruby でホットループを書くとき全般の指針として
残す。

対象: ESP32-S3 (NARYA v3, 16MB flash / 8MB PSRAM) / mruby エンジン /
`FMRB_APP_ENGINE_DESKTOP=mruby`。計測日 2026-07-29。

## 起動時間の内訳

`system_desktop` の `on_create` からブート完了まで、着手時点で約 20 秒。

| 区間 | 着手時 | 現在 | 中身 |
|---|---:|---:|---|
| `scan_apps` | 12.9 s | **7.8 s** | `/app` 走査、35 アプリ検出 |
| `ensure_icon_sprites` | 4.0 s | 4.0 s | SpriteImage 5 枚 |
| 壁紙 `create_image_from_file` ×2 | 3.3 s | 3.3 s | GA 側デコード |
| **合計** | **20.4 s** | **14.9 s** | |

スキャンの現在値は 1 ファイルあたり 182 ms (着手時 300 ms)。まだ高い。
内訳の見積りは strip/index/slice が 15 行ぶんで約 13 ms、`split("\n")` が
約 2 ms、Ruby 経由の File open+read+close が 26 ms で、合計しても 40 ms 程度に
しかならない。**差分の 140 ms は、マイクロプロファイルの単体計測では捉え切れて
いないアロケーション量に比例する GC コストとみている**。原因 3 を潰さない限り
ここから先は削れない。

## 計測方法

推測を 2 回外したので、以降は必ず測ってから直した。道具は 2 つ。

**`main/conn_check/fs_bench.c`** — FS の 1 オペレーション単価。VM 生成前、
マウント直後に走るので**インタプリタも GC も混ざらない**。エンジン非依存で、
mruby / Spinel / ストレージ設定を跨いで同じ指標が取れる。
`FMRB_FS_BENCH_ENABLED` を 1 にして焼く。フェーズごとに 400 ms の上限が
あるので、どれだけ遅くてもブートは最悪 1.2 秒しか伸びない。

**ランチャー内のマイクロプロファイル** — `launcher.rb` の
`profile_scan_primitives`。新しい API を足さずに済ませるため、`Log.info` の
タイムスタンプ差を物差しにしている。`SCAN_PROFILE` を true にして焼く。

Ruby から使える us 単位のクロックは無い。足すと Spinel 側の FFI も要るので、
ログのタイムスタンプ (1 ms 分解能) で足りる粒度に測定を寄せている。

## 原因 1: 読み出しが 1 バイトずつ VFS を叩いていた (修正済み)

`fmrb_hal_file_open` が全ハンドルに `setvbuf(_IONBF)` していた。newlib は
unbuffered ストリームを **1 バイトずつ**リフィルするので、`fread` 1 回が
バイト数ぶんの VFS 往復になっていた。

`_IONBF` が必要なのは**書き込みだけ**である。newlib の FILE バッファが
PSRAM に確保されると SPI フラッシュへの書き込みが黙って失敗するため、
書き込みは VFS へ直接届ける必要がある。読み出しにはこの制約は無い。

書き込み可能な open に限定する修正で:

| | 修正前 | 修正後 |
|---|---:|---:|
| read スループット | 20.4 us/B | **0.34 us/B** |
| `tetris.app.rb` (14240 B) の読み出し | 290 ms | 約 11 ms |
| `stackchan.app.rb` (17348 B) | 354 ms | 10.5 ms (実測) |

**アプリ起動が遅い体感の実体はこれだった**。C 層の問題なので Spinel でも
消えない。

### LittleFS の単価 (修正後)

| 項目 | 実測 |
|---|---:|
| open 失敗 (パス解決のみ) | 2.2 ms |
| open 成功 + close の固定費 | 6.6 ms |
| readdir 1 エントリ | 7.4 ms |
| read | 0.34 us/B |

readdir が高いのは `fmrb_hal_file_readdir` が size/mtime を埋めるために
**エントリごとに stat() している**ため。ランチャーの `Dir.read` は別経路
(mruby の dir HAL) なのでこれは払っていないが、ファイルマネージャや BLE LS は
払っている。

読み出しは `esp_partition_read` 経由で、これは呼ぶたびにフラッシュキャッシュを
止めて他コアを待たせる。`CONFIG_LITTLEFS_MMAP_PARTITION=y` にすると memcpy に
なるが、効果は残り 1 秒未満なので優先度は低い。有効化するなら書き込み後の
コヒーレンシ確認が要る。

## 原因 2: スキャンは FS 律速ではなかった

上の単価をランチャーの呼び出し回数に当てると **FS は約 1.2 秒**。12.9 秒の
1 割に満たない。

これは実験でも裏が取れている。拡張子プローブ (open 59 回) と Dir.open プローブ
(失敗 opendir 42 回 + 例外 58 回) を除去しても、**スキャン時間は 12.98 → 13.21
秒で動かなかった**。実測単価で 400 ms 相当の仕事を消しても wall time が変わらない、
という結果自体が「FS ではない」の証明になっている。

## 原因 3: アロケーション 1 回に GC が ~135 us 付いてくる

ランチャー内マイクロプロファイルの結果 (1 呼び出しあたり):

| | GC 有効 | GC 無効 | 比 |
|---|---:|---:|---:|
| `String#strip` | 0.29 ms | 0.015 ms | **19x** |
| `String#split` | 2.26 ms | 0.04 ms | **56x** |
| `String#gsub` | 14.7 ms | 20.3 ms | 効かない |

同時に取った参考値:

| | |
|---|---:|
| 空ループ (アロケーション無し) | 2.6 us/iter |
| 例外 raise + rescue | 4.6 ms/回 |
| Ruby 経由の File open+read+close | 25.9 ms/回 (C 実測 6.6 ms) |
| `GC.stat` | live=1590, malloc_threshold=0, generational=true |

**VM のバイトコード実行そのものは健全** (2.6 us/iter)。`MRB_USE_DEBUG_HOOK` も
実害は無い (フックは attach 時のみ設置される)。

問題は**アロケーションに付いてくる GC**で、live がわずか 1590 オブジェクトしか
無いのに 1 アロケーションあたり ~135 us を収集に使っている。この比率は Ruby を
書く限りどこにでも付いて回るので、**アイコン構築の 4 秒も、アプリ起動時の
Ruby 実行も、同じ根を持つ**とみてよい。

### `gsub` は別枠

picoruby の `String#gsub` は mrblib の Ruby 実装で、呼び出しごとに splat 展開・
`(1..2).include?` の Range 生成・`byteindex`/`byteslice` ループ・`join` を回す。
GC を切っても速くならない (むしろ悪化する) のはそのため。

`parse_app_toml` は **TOML の 1 行ごとに `gsub('"', '')` を呼んでいた**。
43 ファイル × 約 10 行 = 430 回 × 15 ms ≒ 6.5 秒で、12.9 秒の半分がこれだった。

## この計測から得られる指針

ホットループを Ruby で書くときは、この機体では以下が効く。

- **`gsub` を使わない**。前後のクォート除去のような用途はスライスで書く。
  文字列置換が本当に要るなら C 側に寄せる。
- **アロケーションを減らす**。判定は値を作る前に行う。`parse_app_toml` では
  関心のあるキーかどうかを先に見て、それ以外の行は値に触れずに `next` する
  だけで大きく減った。
- **例外を制御フローに使わない**。1 回 4.6 ms。「開いてみて失敗したらそうでは
  ない」という判定は、事前に列挙した情報で代替する。
- **すでに読んだ情報を再取得しない**。ディレクトリ一覧を持っているなら、
  ファイルの存在確認に open を使わない。

## 現状と残件

修正済み:

- `setvbuf` を書き込み時のみに限定 (原因 1)。
- ランチャーの拡張子プローブと Dir.open プローブを除去。時間には効かなかったが、
  FS 呼び出し 100 回超と例外 58 回が消え、コードの入れ子も浅くなった。
  等価性は実ツリー 43 ファイルで確認済み。
- `parse_app_toml` から `gsub` を除去し、キー判定を値の生成より前に移動。
  43 ファイル全部で新旧の解析結果が一致することを確認済み。
  **実機で 12.98 → 7.82 秒 (-40%)**。予測は 2 秒前後だったので、外した分が
  そのまま「アロケーションに比例する GC コスト」の大きさを示している。

未着手:

- **GC の設定調査**。`step_ratio` / `interval_ratio` / `step_limit` の実効値と、
  このフォーク固有の `sched_driven` / `auto_step` の状態を確認する。1590
  オブジェクトの heap にこの費用を払う理由が説明できていない。**ここが本丸で、
  効けばプロジェクト全体が速くなる**。
- アイコン構築 4 秒。1 ピクセルずつ GFX コマンドを送っている。
  `SpriteImage#load_bmp` (GA 側デコード) に寄せるのが筋。

  必要かどうか判断する。
