# ブート時間の実測とコストモデル

デスクトップの起動が遅い件を、推測ではなく実測で分解した記録。
**結論として原因は 3 つに分かれ、それぞれ効く範囲が違う**。ランチャーの
スキャンだけの話ではないので、Ruby でホットループを書くとき全般の指針として
残す。

対象: ESP32-S3 (NARYA v3, 16MB flash / 8MB PSRAM) / mruby エンジン /
`FMRB_APP_ENGINE_DESKTOP=mruby`。計測日 2026-07-29。

## 起動時間の内訳

`system_desktop` の `on_create` からブート完了まで、着手時点で約 20 秒。

| 区間 | 着手時 | 現在 | 効いた変更 |
|---|---:|---:|---|
| `scan_apps` | 12.9 s | **0.29 s** | gsub 除去 -> リテラル定数化 -> インデックスキャッシュ |
| `ensure_icon_sprites` | 4.0 s | **1.33 s** | リテラル定数化 -> BMP + load_bmp |
| ブートロゴ + アニメ + 壁紙 | 3.3 s | 4.4 s | 未着手 (GA 側のデコード) |
| **`on_create` → Boot complete** | **20.4 s** | **6.03 s** | |

file sync も毎ブート 240 ms の転送をしていたが、GA 側が status 応答の CRC を
常に 0 で返していたため core 側の一致判定が必ず外れていた。GA 側で CRC32 を
計算するようにして `up-to-date` になった (fmruby-graphics-audio 43fb541)。

途中経過の内訳 (キャッシュ導入前、計測用の仕込みあり、43 ファイル):

| | |
|---|---:|
| parse (行ループ) | 2967 ms |
| read (File open+read+close) | 1004 ms |
| dirlist (Dir 列挙) | 685 ms |
| 上記いずれにも属さない | 2372 ms |

## 計測方法

推測を 2 回外したので、以降は必ず測ってから直した。道具は 2 つ。

**`main/conn_check/fs_bench.c`** — FS の 1 オペレーション単価。VM 生成前、
マウント直後に走るので**インタプリタも GC も混ざらない**。エンジン非依存で、
mruby / Spinel / ストレージ設定を跨いで同じ指標が取れる。
`FMRB_FS_BENCH_ENABLED` を 1 にして焼く。フェーズごとに 400 ms の上限が
あるので、どれだけ遅くてもブートは最悪 1.2 秒しか伸びない。

**ランチャー内のマイクロプロファイル** — `launcher.rb` の
`profile_scan_primitives`。新しい API を足さずに済ませるため、`Log.info` の
タイムスタンプ差を物差しにしている。`SCAN_PROFILE` を true にして焼く。

Ruby から使える us 単位のクロックは無い。足すと Spinel 側の FFI も要るので、
ログのタイムスタンプ (1 ms 分解能) で足りる粒度に測定を寄せている。

## 原因 1: 読み出しが 1 バイトずつ VFS を叩いていた (修正済み)

`fmrb_hal_file_open` が全ハンドルに `setvbuf(_IONBF)` していた。newlib は
unbuffered ストリームを **1 バイトずつ**リフィルするので、`fread` 1 回が
バイト数ぶんの VFS 往復になっていた。

`_IONBF` が必要なのは**書き込みだけ**である。newlib の FILE バッファが
PSRAM に確保されると SPI フラッシュへの書き込みが黙って失敗するため、
書き込みは VFS へ直接届ける必要がある。読み出しにはこの制約は無い。

書き込み可能な open に限定する修正で:

| | 修正前 | 修正後 |
|---|---:|---:|
| read スループット | 20.4 us/B | **0.34 us/B** |
| `tetris.app.rb` (14240 B) の読み出し | 290 ms | 約 11 ms |
| `stackchan.app.rb` (17348 B) | 354 ms | 10.5 ms (実測) |

**アプリ起動が遅い体感の実体はこれだった**。C 層の問題なので Spinel でも
消えない。

### LittleFS の単価 (修正後)

| 項目 | 実測 |
|---|---:|
| open 失敗 (パス解決のみ) | 2.2 ms |
| open 成功 + close の固定費 | 6.6 ms |
| readdir 1 エントリ | 7.4 ms |
| read | 0.34 us/B |

readdir が高いのは `fmrb_hal_file_readdir` が size/mtime を埋めるために
**エントリごとに stat() している**ため。ランチャーの `Dir.read` は別経路
(mruby の dir HAL) なのでこれは払っていないが、ファイルマネージャや BLE LS は
払っている。

読み出しは `esp_partition_read` 経由で、これは呼ぶたびにフラッシュキャッシュを
止めて他コアを待たせる。`CONFIG_LITTLEFS_MMAP_PARTITION=y` にすると memcpy に
なるが、効果は残り 1 秒未満なので優先度は低い。有効化するなら書き込み後の
コヒーレンシ確認が要る。

## 原因 2: スキャンは FS 律速ではなかった

上の単価をランチャーの呼び出し回数に当てると **FS は約 1.2 秒**。12.9 秒の
1 割に満たない。

これは実験でも裏が取れている。拡張子プローブ (open 59 回) と Dir.open プローブ
(失敗 opendir 42 回 + 例外 58 回) を除去しても、**スキャン時間は 12.98 → 13.21
秒で動かなかった**。実測単価で 400 ms 相当の仕事を消しても wall time が変わらない、
という結果自体が「FS ではない」の証明になっている。

## 原因 3: Ruby 側のコスト。ただし GC が主犯ではなかった

ここは調査が二転三転した。**結論から書くと、犯人は 2 つで、どちらも
「アロケーションを伴うメソッド呼び出しが高い」ことに帰着する**。

### (a) `String#gsub` が Ruby 実装

picoruby の `String#gsub` は mrblib の Ruby 実装で、呼び出しごとに splat 展開・
`(1..2).include?` の Range 生成・`byteindex`/`byteslice` ループ・`join` を回す。
GC を切っても速くならない。

`parse_app_toml` は **TOML の 1 行ごとに `gsub('"', '')` を呼んでいた**。
除去して **スキャン 13.0 → 7.8 秒**。前後のクォート除去はスライスで足りる。

### (b) メソッド引数の文字列リテラル

`key == "literal"` は `key == CONSTANT` の **約 40 倍**かかる。この比は 2 回の
ブートで再現した。ホットパスのリテラルをすべて定数に括り出した結果、同じ
43 ファイルに対する **parse フェーズが 5.0 秒 → 3.0 秒**。

同じ規則がアイコン構築にも刺さっていた。24x24 の展開ループが
`if row[ix] == '1'` を **2880 回**回していた (576 px × 5 アイコン)。

機構は特定できていない。リテラル生成単体は安く、定数との比較も安いのに、
両者を組み合わせた瞬間に高くなる。GC アリーナと一時オブジェクトの相互作用が
疑わしいが、未確認。**規則は再現しており対策も効いているので、機構の特定は
保留にしてある。**

### 撤回した仮説

同じ轍を踏まないよう、外した筋を残す。

- **「GC がアロケーションごとに ~135 us」— 誤り。** `strip` を 200 回回す
  ループで 0.29 ms/回という値を得たが、これは**初回実行 (cold) の値**で、
  定常状態では 0.09〜0.12 ms。`GC.stat` を見ると `gc_debt` は常に -1400 前後に
  沈んでおり、アロケーションごとのステップは起きていない。フルサイクルも
  `GC.start` で 10 ms。live は 1590 前後で単調増加もしない。
- **「desktop タスクが CPU を奪われている」— 誤り。** ログのタイムスタンプで
  区間を測ったところ、固定の C 処理 (File open+read+close) が 15 ms のときと
  154 ms のときがあり、実行機会を奪われていると判断した。**これは計測
  アーティファクト**で、マーカーの `Log.info` が 1 行あたり UART を 8 ms
  ブロックする分が区間に混入していた。us クロックで測り直すと同じ処理は
  14.4 ms/回で一定。カーネルタスク (prio 9, 同 core) も `_poll_message(33)` で
  正しくブロックしており、33.3 ms 周期で回っていることを確認済み。
- **「リテラル生成そのものが高い」— 誤り。** 生成単体は安い。高いのは
  メソッドに渡したときだけ。

### 計測手法の教訓

- **ログのタイムスタンプで短い区間を測ってはいけない。** 1 ms 分解能に加えて、
  1 行が UART を数 ms ブロックするので、観測が対象を乱す。
- **先に us クロックを用意する。** `FmrbApp.uptime_us` を足したのは調査の
  終盤だったが、これを最初に入れていれば誤った結論を 2 つ出さずに済んだ。
- **短いマイクロループの値を信用しない。** 100 回ループの値は、GC サイクルが
  どこに落ちるかで **100 倍**振れることを確認した。同じコードの 2 回の実行で
  `literal only` が 1060us と 223888us になった。**判断は必ず、実処理を
  数百回以上集計した値で行う。**

## この計測から得られる指針

ホットループを Ruby で書くときは、この機体では以下が効く。

- **`gsub` を使わない**。前後のクォート除去のような用途はスライスで書く。
  文字列置換が本当に要るなら C 側に寄せる。
- **メソッドに文字列リテラルを直接渡さない**。ループの外で定数に括り出す。
  `end_with?(".toml")` `include?(".")` `== "false"` `row[ix] == '1'` のような
  何気ない記述が、1 行ごと・1 ピクセルごとに効いてくる。
- **アロケーションを減らす**。判定は値を作る前に行う。`parse_app_toml` では
  関心のあるキーかどうかを先に見て、それ以外の行は値に触れずに `next` する
  だけで大きく減った。
- **例外を制御フローに使わない**。「開いてみて失敗したらそうではない」という
  判定は、事前に列挙した情報で代替する。
- **すでに読んだ情報を再取得しない**。ディレクトリ一覧を持っているなら、
  ファイルの存在確認に open を使わない。

## 現状と残件

修正済み:

- `setvbuf` を書き込み時のみに限定 (原因 1)。
- ランチャーの拡張子プローブと Dir.open プローブを除去。時間には効かなかったが、
  FS 呼び出し 100 回超と例外 58 回が消え、コードの入れ子も浅くなった。
  等価性は実ツリー 43 ファイルで確認済み。
- `parse_app_toml` から `gsub` を除去し、キー判定を値の生成より前に移動。
  43 ファイル全部で新旧の解析結果が一致することを確認済み。
  **実機で 12.98 → 7.82 秒 (-40%)**。
- ホットパスの文字列リテラルをすべて定数に括り出した (パースループ、スキャン
  ループ、アイコン展開の per-pixel ループ)。ロジックは変えていない純粋な置換で、
  等価性は実ツリー 43 ファイルで再確認済み。**parse フェーズ 5.0 → 3.0 秒**。
- `FmrbApp.uptime_us` を追加 (`lib/add/picoruby-fmrb-app/ports/esp32/app.c`)。
  Ruby から us 単位で計測するための API。Spinel 側には対応する FFI が無いので、
  共有 Ruby から使うときは注意。
- **アイコンを BMP 化して `SpriteImage#load_bmp` に** (`tool/gen_icon_bmp.rb`,
  `rake icons`)。`.icon` の per-pixel GFX コマンド送信をやめ、graphics-audio に
  デコードさせる。BMP は GA 側に 1 度転送してキャッシュ。**4.0 秒 → 1.33 秒**。
  `load_icon` / `@icon_cache` / `_force_gc` は役目を終えたので削除
  (`_force_gc` は per-pixel の churn 対策だったので、churn ごと消えた)。
- **GA 側の file STATUS が CRC32 を返すように** (fmruby-graphics-audio 43fb541)。
  毎ブートの再転送 240 ms が消えた。
- **アプリ一覧のインデックスキャッシュ** (`/data/launcher_index`)。起動時は
  キャッシュを無条件に信じ、増減の反映は右クリック rescan のみ。検証しないのは、
  検証にはディレクトリを歩く必要があり (dirlist だけで 685 ms)、キャッシュの
  目的の大半が失われるため。形式はタブ区切りで、ヘッダにバージョンと言語を持つ
  (ラベルは言語ごとに解決されるので、言語変更で無効化される)。**スキャン
  12.9 秒 → 0.29 秒**。

未着手:

- **画像デコード 4.4 秒**。残った最大項目で、いま全体の 7 割。318x224 を 2 枚
  (ブートロゴと壁紙) デコードしている。うち約 1 秒は意図的なブートアニメーション
  なので削る対象ではない。core からはパスを送っているだけなので、調査は
  fmruby-graphics-audio 側。
- アイコン 1.33 秒。スプライト 1 枚あたり約 160 ms で、`file_status` /
  `_create_sprite_image` / `_load_sprite_image_bmp` の 3 往復。詰めるなら
  往復を減らす。
- TOML パースを C 側 (`components/fmrb_toml`) に寄せる案。キャッシュが効いた
  ので急がないが、初回起動と rescan は今もフルスキャン (約 6 秒) である。
- 「リテラルをメソッドに渡すと 40 倍」の機構特定。対策は効いているので急がない
  が、分かれば他の書き方の指針が増える。
