# 実装指示書 Ff: 基準の表をファームを作るときに作り、flash に置く

`doc/checkpoint/flash_table.md` (この段の計画と決まったこと)、`plan.md` (F0〜F5 の決まったこと)、`report/f1b.md`
(基準の表の内訳と平らな表への作り直し)、`report/f4.md` (`SND0`・`requires`・`mrb_checkpoint_has_method`)、
`report/f5.md` (止める前の問い合わせ)、`movable_apps.md`、mruby-checkpoint の `doc/plan.md` (D12) と `doc/format_v1.md` を
先に読む。

## 目的

申告したアプリの VM が払う基準の常駐の費用 (今は 64 bit のネイティブ版で約 356 KB、32 bit の見積もりで約 336 KB) を、
**32 bit で数十 KB** に下げる。ビルドで決まる部分 (名前・メソッドの一覧・クラスの写し・irep → 名前) を、ファームを
作るときに C のソースとして作ってリンクし (ESP32 なら flash の rodata)、VM ごとには番号 → ポインタの小さな表だけを持つ。
F6 (実機) でこの形を使う。

## 決まっていること (2026-11-04、ユーザが選んだ)

- **案 A (ホストで作る)**: その構成と同じ gem の組み合わせで、ホストの mruby を作って名前を集め、C のソースにして
  ファームにリンクする。端末で最初に起動したときに作る形 (案 B) は使わない。
- ESP32 にしか無い gem (ハードウェアの port) の扱いは、この段で決める (名前だけを持つ代わりのもので足りるか、など)。
- 範囲は名前を flash に出すだけでなく、**生かしておく表 (`keep`) と ivar の写しも番号の形にする**。
- **メソッドの一覧もこの表で持つ**。`mrb_checkpoint_has_method` (F5 の止める前の問い合わせと、着いた側の `SND0`・
  `requires` の確認) は、VM の中のクラスをたどらずにこの表を引く。
- 各ビルドは自分の表だけを持つ。ほかの構成の表は埋め込まない。
- 表とファームが食い違うと名前の引き当てを誤る。イメージに表の版の印を入れ、違えば理由つきで断る。
- 内蔵 RAM +0。

## やること

1. **今の内訳を 32 bit で測る**: ブラウザ版の測るための別のビルド (`FMRB_WASM_CHECKPOINT=1`、wasm32) か、ホストの
   32 bit のビルドで、基準の表の中身ごとの量を出す (F1b §1.1 の形)。flash に移せる分と VM ごとに残る分を分ける。
2. **表の作り方を決める**: C の関数を番地 (関数への参照) で書くか、ほかのもの (クラスとメソッドの名前で VM の起動の
   後に引く、など) で結ぶか。mruby・picoruby の C のメソッドの多くは `static` の関数で、生成した C のソースから名前で
   参照できないことに注意する。リンクの後にファームを書き換える形は取らない。決めた形と理由を report に書く。
3. **作る道具**: 構成ごと (ネイティブ版・sim・ブラウザ版・P4・S3) に、その構成の gem の組み合わせで名前を集め、C の
   ソース (と版の印) を書き出す rake の task。ビルドの中で自動で作り直す (gem の組み合わせや mrblib が変われば
   作り直される)。ESP32 にしか無い gem の扱いをここで決める。生成物はコミットしない (ビルドの生成物)。
4. **gem の入口**: mruby-checkpoint に「外から渡された固定の表」と「VM ごとの番号 → ポインタ」に分けて読む入口を
   足す。固定の表が無いビルド (mruby-checkpoint 単体の試験など) は今の形のまま動く。`keep` と ivar の写しの番号化。
   `mrb_checkpoint_has_method` が表を引く。
5. **版の印**: イメージに表の版の印を入れる (形式の任意のセクションか、既存の欄か。形式の版を上げる必要があるかを
   判断して report に書く)。食い違いは理由つきで断る。
6. **Family mruby に入れる**: ネイティブ版・sim・ブラウザ版の別のビルド (`FMRB_WASM_CHECKPOINT=1`) で表を作って
   リンクし、使う。P4・S3 の構成の表も道具で作れて、ホストでコンパイルが通るところまで (ファームに入れるのは F6)。
7. **測る**: 申告したアプリ 1 つの VM の基準の常駐の費用を、ネイティブ版 (64 bit) と 32 bit (ブラウザ版の別のビルド)
   で、前後を表にする。基準を作る間の一時的な量 (F1b §1.2 の 64 bit で 200 KB ほど) も測る。
8. 標準のアプリに `movable = true` を付けるのは「Ff の後」と決まっているが、**この段では付けない**。付ける候補と理由を
   report に挙げる (親がユーザに諮る)。

## 確かめること

- mruby-checkpoint: `rake test`・`test:asan`・`test:stress`。試料のイメージが前の gem と同じバイト列か (版の印を足した
  分の違いは除いて説明する)。
- fmruby-core: `rake regress:checkpoint` (既定と `SIM=1`、ブラウザ版の `WEB=1` も)、`rake regress`、`rake regress:run`、
  `rake regress:size` (内蔵 RAM +0、ESP32 は gem をまだ持たないので変わらないはず)、
  `rake regress:screens ONLY=retro,modern,native,native-keys`。
- 表の版の印が違うイメージを、理由つきで断ること (試験に足す)。
- 普段の速さ: VM の命令数 (valgrind) が F0 の基準と 1% 以内 (触ったのが基準を作る所と読み書きだけなら省略してよい、
  省略した理由を書く)。

## 触ってよい範囲・止まる条件・守ること

- fmruby-core は本体の checkout の `feature/linux-native` にコミット (push しない)。mruby-checkpoint は
  worktree (`wt/mruby-checkpoint-ff` (worktree の決まった置き場所)、ブランチ `wt/ff`) を作ってコミット (push しない。開発中は
  `MRUBY_CHECKPOINT_DIR`、固定点は親が合わせる)。family-mruby のリポジトリ直下 (`tools/`) も触ってよい (コミットまで)。
  ただし直下の `tools/fmrb_web.rb` にある、コミットされていない変更 (別の作業のもの) には触らない・コミットに混ぜない。
- 止まる条件: 利用者から見た動きが変わる直し方、D1〜D16 や上の決まっていることと食い違う事実、案 A では作れないと
  分かったとき、内蔵 RAM が増える、submodule・sdkconfig を直接直す必要。
- 人が開いているブラウザ (ポート 8016) に触らない。ブラウザ版の確認は自分のポートのヘッドレスで。
- 文書は常体、定着したカタカナ語を使う。コミットする文書にローカルの絶対パスや実在の IP・端末の ID を書かない
  (コミットの前に、差分を検索して確かめる)。
- 終わったら worktree の build を残さない。
