# F5: Asterism でイメージを送り、受け取った側で起動する

> 状態: 実装済・検収待ち | 更新: 2026-11-05 | 2 つの Family mruby の間で、申告済みのアプリを Asterism (Zenoh) の上で移せるようにした。受け口は転送のアプリ (`/usr/share/transfer/transfer.app.rb`、mruby の VM の headless なアプリ) で、`<ノード>/transfer/inbox` に `check` / `begin` / `chunk` / `commit` / `status` / `cancel` を出し、`caller:` で呼び手のノード ID を受け、`/home/asterism/receive.toml` に書いた相手だけを受ける。段取りはカーネル (Ruby、両方の構成) が持ち、「相手に聞く → 止める (移動中の印) → 運ぶ → 相手で起動 → 返事 → 閉じる (または続ける)」を進める。止める前に、運ぶコードが呼ぶメソッドの名前と `requires` を相手に送り、`requires` が足りなければ止めずに断る。頼み方は道具 (`fmrb_native.rb app move PID --node ノードID`、MCP の `native_app`)、Shell (`move <pid> <ノード ID>`)、アプリの API (`FmrbApp.move`・`FmrbApp#move_to`)。ネイティブ版 ⇔ ネイティブ版で 23 KB を 22〜35 ms で運び、止めている時間は 56〜66 ms (F2 のデバッグサーバの道は 1.2 秒・1.3 秒)。`rake regress:checkpoint` に Asterism の場面を足した (既定で 6 つ、`SIM=1` で sim と 2 つ)。2026-11-05: 時計を直したブラウザ版とネイティブ版の間を両向きとも移せた (運ぶ 26〜38 ms、止めている時間 60〜79 ms)。`WEB=1` でブラウザ版の場面 4 つ (12 章)

計画は `doc/checkpoint/plan.md`、指示は `doc/checkpoint/instruction_f5.md`。F4 は `report/f4.md`。
mruby-checkpoint の gem にも、Asterism の gem (ruby-asterism) にも手を入れていない。

## 1. 受け口の置き場所

| 候補 | 見立て |
|---|---|
| カーネル | 標準の構成ではカーネルは Spinel のプログラムで、Asterism (picoruby-asterism は mruby の上の純 Ruby、Zenoh は picoruby-asterism-zenoh の C) を持てない。全部 mruby の構成だけ持てる形は、D14 の「両方の構成で同じ」に合わない |
| C | Asterism の層 (呼び出しの形、`caller:`、meta、liveliness) は Ruby にしか無い。C で書き直すのは Asterism の gem を変えるのと同じ |
| サービスホスト | Modern だけ (Retro は起動しない)、一覧の file があるときだけ起動する。サービスは 1 つの VM の中で順に呼ばれるので、TLS のつなぎ (10〜20 秒止まる、`FmrbAsterism::Link` の説明) がほかのサービスを止める |
| **自前の headless のアプリ (採用)** | mruby の VM で動く普通のアプリ。`FmrbAsterism::Link` でつなぎ直しの面倒を見られる。カーネルとはアプリの制御のメッセージで話す。Retro・Modern・sim・ネイティブ版・ブラウザ版のどれでも同じ |

- 転送のアプリは `/usr/share/transfer/transfer.app.rb` (と `.app.toml`)。ファームの bytecode に入れず、storage の file にした (ESP32 の flash の app の領域を使わない。起動は file の compile の分だけ遅い)。
- カーネルは 2 つの時に起動する: 起動のときに `/home/asterism/receive.toml` があれば (受け取る端末は待っていないといけない)、移す頼みが来た時に動いていなければ。起動したら動き続ける。
- 受け口が使う C のメソッド (`FmrbApp._checkpoint_has_method`・`_checkpoint_restore`・`_checkpoint_restore_poll`) は、checkpoint の用意をした VM (movable なアプリ、復元する VM) にだけ、基準を取る前に定義する。ほかのアプリの VM は持たない (最初は全部の VM に定義していて、`regress:run` で 1 つのアプリが 672 B 増えた。8 章)。
- `.app.toml` に `movable = true` を書いた。動かすためでなく、VM を開いたときに基準 (このビルドの組み込みのクラス・メソッドの名前の表) を取らせるため。相手の `check` に答えるのはこの表 (`mrb_checkpoint_has_method`)。転送のアプリ自身を移す頼みは、Zenoh のセッションを運べないので gem が断る。費用は基準の分 (ネイティブ版 64 bit で 355,976 B、ブラウザ版 32 bit で 322,064 B、VM のプールから)。Ff (表を flash に置く) の後は表を引くだけになる。

## 2. 受け口の作り (`<ノード>/transfer/inbox`)

| メソッド | 引数 | 答え |
|---|---|---|
| `check(kind, meta)` | `"checkpoint"`、`{"names" => [...], "requires" => [...]}` | `{"ok" => true, "missing" => [このビルドに無い名前]}` か `{"ok" => false, "reason"}` (`requires` の名前が無い) |
| `begin(kind, meta)` | `{"name", "size", "toml" (イメージの横の属性の中身)}` | `{"id", "piece" (1 回の大きさ)}` |
| `chunk(id, pos, bytes)` | 順に | 次の pos |
| `commit(id)` | | 種類ごとの処理に渡す。`"checkpoint"` は `/tmp/<name>.ckpt` と `.toml` に置き、カーネルに起動を頼む → `{"status" => "pending"}` |
| `status(id)` | | `pending` / `{"status" => "restored", "pid", "missing"}` / `{"status" => "refused", "reason"}` |
| `cancel(id)` | | 途中のものを捨てる。起動したものは止める (返事が遅れたとき、5 章) |

- 呼び手: すべてのメソッドを `caller: :from` で出す (Asterism が呼び手のノード ID を `from:` に入れ、呼び手は偽れない)。受けてよい相手は `/home/asterism/receive.toml` の `from = ["ノード ID", ...]` (`"*"` は網に入れる全員)。file が無ければ誰からも受けない。毎回読む (書き換えればすぐ効く)。ノード ID の確かさは Asterism の決まりのまま: `tls/` のルータと console の証明書なら、ルータのアクセス制御が証明書と名前を結ぶ。
- 1 回の呼び出しは 4 KB まで (zenoh-pico の `Z_FRAG_MAX_SIZE`) なので、1 片は 3,072 B。`check` の名前の一覧も 2 KB ずつに分ける (`requires` は最初の 1 回だけ)。
- 同時に 1 つ。別の相手の `begin` は、受けている途中なら `busy` で断る。同じ相手の `begin` は前のものを捨てる。10 秒片が来なければ捨てる。大きさは 1 MiB まで。名前は英数字と `_`・`-` だけ (`/tmp` の外に出られない)。
- 受けている途中は `/tmp/<name>.checkpoint.part` に書き、`commit` で大きさを確かめてから名前を付け替える。半端な file は起動されない。
- 種類は表 (`KINDS`) で、今は `"checkpoint"` だけ。ブラウザ版のアプリのインストール (W5) は、ここに `.app.wasm` の種類を足し、`commit` の処理を書く形。
- 受け口は、呼ばれた後 2 秒は 2 ms ごとに、そうでなければ 50 ms ごとに Asterism を見る (受け口はポーリングなので、着いた呼び出しに気づくのは次に見たとき)。

## 3. 移す段取り (カーネル、`fmrb_kernel.rb` の `start_move`)

```
頼み (道具: デバッグサーバの move / Shell・アプリ: FmrbApp.move) → C (fmrb_app_checkpoint.c ask_move:
  動いている mruby のアプリで movable か) → カーネル "move" {pid, to, hold, from}
1. 転送のアプリが動いていなければ起動し、"transfer_ready" を待つ              (30 秒)
2. アプリへ "checkpoint_calls" → アプリの _spin が /tmp/<名前>.calls を書く      (5 秒)
   (requires と、mrb_checkpoint_sent_names。イメージは書かない)
3. 転送のアプリへ "move_check" → 相手の check → "move_checked" {ok, reason | missing}  (15 秒)
   断られた・相手がいない → アプリへ "checkpoint_untaken" {reason}。アプリは止まっていない
   missing は警告としてログと答えに残し、続ける
4. F2 の start_checkpoint (hold) → アプリが書いて止まる (移動中の印) → "checkpoint_held" (8 秒)
5. 転送のアプリへ "move_send" → begin / chunk ... / commit / status → "move_sent" {ok, pid | reason}
   (hold が上限。既定 10 秒)
6. 起動できた → アプリへ checkpoint_finish {close: true, reason: "moved to <ノード> as PID n; it lacks: ..."}
   断られた → checkpoint_finish {close: false} → 止めた所から続ける
```

- 期限と失敗のときの扱いは F2 にそろえた: 止めておく `hold` は既定 10 秒、アプリ自身は `hold` + 2 秒で自分で続ける。止める前 (1〜3) の失敗では、アプリは何も気づかずに動き続ける。
- 返事が遅れたとき (hold が切れて続けた後に相手で起動した): カーネルが転送のアプリに "move_cancel" を送り、相手の `cancel` がその写しを止める。転送のアプリ自身が `status` を待ちきれなかったときも、`commit` の後なら `cancel` を送る。どちらも 2 つにしないため。
- 頼んだ側への答え: アプリには `checkpoint_result` {pid, ok, to, there (相手での PID), missing | reason} (自分を移すアプリは、移れば閉じるので答えは無く、断られたら `on_checkpoint_refused`)。道具 (デバッグサーバ) には、アプリの答えの表 (`fmrb_app_checkpoint_poll`) に、閉じた (`detail`: どこで起動したか) か断られた・続けた (理由) が入る。
- カーネルは同時に 1 つの移動だけを持つ (F2 の `@ckpt_*` と共に)。
- カーネルからアプリへのメッセージは 176 B なので、理由と名前の一覧は切って送る (`clip`)。全部はログにある。

## 4. 頼み方

| 入口 | 使い方 |
|---|---|
| 道具 | `ruby tools/fmrb_native.rb app move PID --node ノードID [--hold MS] [--max MS]` → `{status: moved, pid, detail, missing?, took_ms}` / `{status: stayed, reason, here: "not stopped" \| "went on"}`。F2 の `--to RUN_DIR\|PORT` (デバッグサーバの道) はそのまま |
| MCP | `native_app` の `action: "move"` に `node` (description に書いた。selftest に 1 つ足した) |
| Shell | `move <pid> <ノード ID>` → `move: PID 6 moved to rg-ckpt-b (PID 6 there)` / `move: PID 6 stayed (...)` |
| アプリ | `FmrbApp.move(pid, to, hold: 0)` (答えは `on_control` に `checkpoint_result`)、自分は `move_to(to)` (`sig/fmrb_app.rbs` に両方)。`move` は `FmrbUI`・スプライトの `move` と重なるので、インスタンスのメソッドは `move_to` にした |

- 名前は Asterism の端末の名前 (ノード ID) にそろえた。`config.toml` の `node`、なければ mDNS の名前・ブラウザ版の `wasm-XXXXXX` など、`FmrbAsterism.settings` が決めるもの。

## 6. 計測 (ネイティブ版 ⇔ ネイティブ版、同じ PC のルータ、標準と全部 mruby)

| 何を | Asterism (F5) | デバッグサーバ (F2) |
|---|---|---|
| 相手に聞く (名前 8 個、1 回の呼び出し) | 3〜45 ms | — |
| 運ぶ (23,083 B、begin + 8 片 + commit) | 21〜35 ms | 1.15〜1.2 s |
| 書いてから相手で起動して閉じるまで (止めている時間) | 55〜66 ms | 1.3〜1.38 s |
| 頼んでから閉じるまで (カーネルのログ) | 69〜119 ms | 1.4 s |
| 呼び出しの数 | 11 (begin・chunk 8・commit・status) | 22 |
| 断られる (requires・許していない・相手がいない) | 1〜3 ms (カーネル)、道具から 110〜150 ms | — |

- F2 で運ぶのに 1 秒かかっていたのは、デバッグサーバの往復ごとに最大 50 ms 眠るため。Asterism では呼び出しを 1 つずつ投げて (`async`)、答えが来たら次を投げる。送る側はその間メッセージ待ちに戻る。
- 最初の形 (1 回の `on_update` の中で全部の呼び出しを待つ) では、ネイティブ版の協調のスケジューラでほかのタスクが 260 ms 止まり (`stats` の `burst_ms`)、カーネルの hold の期限も効かなかった。1 回の呼び出しごとに戻る形に直した。
- 受け口の待ち (50 ms) が最初の呼び出しの遅れになる (3〜45 ms のばらつき)。

## 7. ブラウザ版 (F4 の別ビルド `FMRB_WASM_CHECKPOINT=1`)

自分の port の開発サーバ (`FMRB_WASM_CHECKPOINT=1 DIST=1 PORT=8047 rake wasm:serve`) とヘッドレスの Chromium (Playwright) で動かし、`fmrb_web.rb --port 8047` で操作した。ルータは PC の zenohd の `ws/` (ページの `?zenoh=`)。人が開いている 8016 のページには触っていない。

| 何を | 結果 |
|---|---|
| 大きさ (`wasm:dist`、今のコミット) | `core_web.wasm` 6,370,874 B、`core_web.data` 4,230,227 B、dist 全体 10.43 MB。転送のアプリ (storage の file 19,858 B) が `.data` に入る |
| 起動 (load からデスクトップの `Boot complete`) | 4.8 秒 (F4 と同じ) |
| 転送のアプリ | ブラウザ版でも起動して `ws/` でつながる (6.7〜10.6 秒)。基準は 3,577 個の名前で 322,064 B |
| 止める前の確認 | ブラウザ版 → ネイティブ版: 名前 8 個、足りない名前 0。ネイティブ版 → ブラウザ版: `ckpt_calls` の `linux_settings` がブラウザ版に無いと答え、警告として移す側へ (`Move: wasm-... lacks methods PID 6 calls: linux_settings (it is moved all the same)`) |
| 受けてよい相手 | 両向きに断る (`f5-a takes nothing from wasm-...`、`wasm-... takes nothing from f5-a`) |
| ブラウザ版 → ネイティブ版 | イメージ (23,083 B) が運ばれ、ネイティブ版で復元できた (32 bit → 64 bit、452〜541 µs)。ただし運ぶのに 47 秒かかり、ブラウザ版の側の待ち (`status` の 5 秒) が先に切れて、ブラウザ版で続け、ネイティブ版の写しは `cancel` で止まった (2 つにならない) |
| ネイティブ版 → ブラウザ版 | 確認は通ったが、ブラウザ版が `begin` に 5 秒以内に答えず、ネイティブ版で続けた |

- 動きは通る (確認・許可・運ぶ・32 bit → 64 bit の復元・遅れた写しを止める) が、**この PC のヘッドレスの Chromium では、ブラウザ版の時間の待ちが 17〜34 倍に伸びていて** (`task_sleep` の 100 ms の待ちが 1.7〜3.4 秒、`ckpt_counter` の 250 ms の 1 歩が 3.4 秒)、Asterism の 1 回の呼び出しに 3〜5 秒かかった。今のビルド (F5 の変更の無い `wasm/build`) を自分の port で開いても同じだったので、F5 の変更でなく、このセッションのヘッドレスのブラウザの性質 (F4 では「ときどき数秒止まる」程度だった)。最後まで移せた数字 (運ぶ時間・止めている時間) は取れていない。人の開いているブラウザ (Window が見えているもの) で確かめてもらう必要がある。
  (2026-11-04 追記: ヘッドレスのせいではなく、port の時計が Worker ごとにずれていたため。直した。doc/wasm/report/worker_clock.md)
- そのため、呼び出しの待ちを 5 秒から 10 秒に延ばした (仮決め 6)。延ばした後のブラウザ版との通しは、ページのセッションが切れて試せていない。
- ほかに気づいたこと: このヘッドレスのページでは、`fmrb_web.rb put` で `/home` に置いた file を端末 (Shell の `cat`) が読めず、ページを読み直すと `/home` が空に戻った。設定は Shell の `irb` で端末の中から書いた。F4 では `put` した file を端末が読めていたので、ページの保存の作り (今の `wasm/web/main.js`) と道具の間で何かが変わったかもしれない (F5 の範囲外として記録だけ)。 (2026-11-04 追記: 道具の path はページの MEMFS の path で、端末の `/home` は `/flash/home` にある。doc/wasm/report/worker_clock.md 6 章)
- ブラウザ版の場面は `regress:checkpoint` に入れていない (2026-11-05 追記: 時計を直した後に両向きとも通り、`WEB=1` のときだけ流す場面を足した。12 章)。入れるなら、上の遅さが人のブラウザで出ないことを確かめ、公開のビルドに gem を入れると決まってから (`regress:screens` の web の道具の上に、Shell の `move` と別の端末の受け口で場面を足す)。

## 8. 気づき

- 受け口がポーリングなので、受ける側の速さはそのアプリが Asterism を見る間隔で決まる。呼ばれた後しばらくは細かく見る形にした。
- `fmrb_native.rb` の `--node` の答えは、アプリの答えの表に入る文字列 (`moved to X as PID n; it lacks: ...`) から PID と名前を読む。構造のある答えにするなら、デバッグサーバの `move` が移動の表を持つ形になる。
- 運ぶ道の両端 (`commit` の後の失敗、hold が切れた後の起動) で写しを止める処理を入れたので、どの失敗でも「2 つ動く」にはならない。ただし相手が `cancel` を受ける前に落ちたときは、相手に写しが残りうる (相手は普通に動くアプリとして持つ)。

- ネイティブ版の `fmrb_hal_time_get_us` は `gettimeofday` (壁の時計) で、ログの時刻 (単調な時計) と違って跳ぶことがある。F2 の「止めていた時間」の数え方 (アプリ側) がこれで 1 回だけ 1.7 秒ずれた。止める・続ける自体はカーネルの `Machine.board_millis` で正しく動いている。単調な時計に替えるかは F5 の範囲外として記録だけ。

## 9. サブの仮決め (ユーザが見直す)

1. 受け口は自前の headless のアプリ (転送のアプリ) で、storage の `/usr/share/transfer/` に置く。ファームの bytecode にはしない。
2. 転送のアプリは、`receive.toml` があれば起動のときに、無ければ最初の移す頼みのときに起動し、その後は動き続ける。
3. 転送のアプリの `.app.toml` に `movable = true` を書き、基準の表を持たせる (相手の `check` に答えるため)。Ff の後は flash の表を引く形に替える。
4. 受けてよい相手は `/home/asterism/receive.toml` の `from = [...]`。無ければ誰からも受けない。`"*"` で全員。
5. 受け口は同時に 1 つ。別の相手は `busy` で断る。10 秒片が来なければ捨てる。大きさは 1 MiB まで。
6. 呼び出しの待ちは 10 秒 (ブラウザ版の受け口が遅い場合に合わせた。相手がいなければ Asterism はすぐ「nobody answers」を返す)。`status` は `commit` から 9 秒待つ。
7. 1 片は 3,072 B、`check` の名前は 2 KB ずつ。
8. 止める前の確認で `requires` が足りないときは、アプリに知らせずに続ける (止めていないので)。頼んだアプリが自分なら `on_checkpoint_refused`。
9. 道具の頼み方は `app move PID --node ノードID` (F2 の `--to` と並べた)。
10. インスタンスのメソッドは `move_to` (`move` は他のクラスと重なる)。
11. 試験の「requires で断る」は、どのビルドにも無い名前を `requires` に書いたアプリ (`ckpt_requires_absent`) で作った。警告の場面は同じビルドどうしでは作れないので、`SIM=1` の sim の場面に置いた。
12. sim の場面では、作業の木の `flash/home/asterism` に流すあいだだけ設定を書き、終わったら元に戻す。

## 10. 決めてほしいこと (ユーザ)

1. **ブラウザ版の公開のビルドに gem を入れるか** (F4 から持ち越し、7 章の結果を見て)。
2. 受け口の既定 (仮決め 4・5): `receive.toml` が無い端末は何も受け取らない、でよいか。console の許可の表 (asterism-console) と結ぶか。
3. 転送のアプリを Retro (S3) に入れるか (F6 の話。storage の file なので flash の app の領域は使わないが、VM 1 つと基準の表が要る)。
4. ESP32 の flash の増え方 (S3 +27 KB、P4 +30 KB。ほとんどがカーネルの移す段取りの Ruby を Spinel にした C)。ESP32 では移すことができない (gem が無い) 間もカーネルに入っている。`FMRB_HAVE_CHECKPOINT` の無いビルドで段取りを外す形 (カーネルの Ruby を分ける) にするか。
5. mDNS の部品の版 (5 章の注): `^1.8.0` が 1.15.0 に解決されて ESP32 のビルドが落ちる。版を留めるか。

## 11. F6 と W5 に要るもの

- F6 (実機): 転送のアプリは VM 1 つとタスク 1 本 (内蔵 RAM のスタック) を使う。受け取る端末は常に、移す端末は頼んだときから。基準の表は Ff で flash に置いてから。Tab5 の TLS のつなぎは 10〜20 秒なので、移す頼みの最初の 1 回は待つ (カーネルの期限は 30 秒)。
- W5: 種類の表に `.app.wasm` を足し、`commit` で `/app/usr` などへ置いてランチャーの一覧に足す。`begin` の `meta` に `.app.toml` の中身を入れる形はそのまま使える。

## 12. ブラウザ版との通し (時計を直した後、2026-11-05)

7 章で最後まで通らなかったブラウザ版との移動を、port の時計を直したビルド (3397f633、doc/wasm/report/worker_clock.md) で流し直した。両向きとも最後まで移せた。

### 12.1 やり方

- ブラウザ版は今のコミット (5f8f46e0) で作り直した gem 入りの別ビルド (`source ~/emsdk/emsdk_env.sh`、`rake spinel:gen`、`FMRB_WASM_CHECKPOINT=1 rake wasm:mruby wasm:dist`。`wasm/build-ckpt`)。自分の port の開発サーバ (`FMRB_WASM_CHECKPOINT=1 DIST=1 PORT=8057 rake wasm:serve`) と、Playwright の Linux の Chromium (ヘッドレス) で開き、`fmrb_web.rb --port 8057` で動かした。人の開いている 8016 のページには触っていない。
- ルータは自前の zenohd (`eclipse/zenoh:1.10.1`、tcp と ws/ を別の port)。ネイティブ版 (標準の構成) はノード `f5-a`、ブラウザ版は `f5-web`。互いに相手からだけ受け取る (`receive.toml`)。
- ブラウザ版の設定は `fmrb_web.rb put` で `/flash/home/asterism/config.toml`・`receive.toml` に置き (ページの filesystem の `/flash/home` が端末の `/home`)、ページを読み直した。カーネルが起動のときに転送のアプリを動かす。7 章の「`put` した file を端末が読めない」は置き場所の取り違えで、これで読めた。
- ネイティブ版 → ブラウザ版は `fmrb_native.rb app move PID --node f5-web`、ブラウザ版 → ネイティブ版はブラウザ版の Shell で `move PID f5-a`。カウンタ (`ckpt_counter`) を 5 往復させた。

### 12.2 結果

### 12.4 `rake regress:checkpoint WEB=1`

公開のビルドに gem を入れるかは決まっていないが、gem 入りの別ビルドを自分のサーバとブラウザで開けば、人のページ (8016、`fmrb_web.rb` の状態の file) に触らずに流せることが分かったので、場面を足した (`tools/regress/checkpoint_web.rb`、`WEB=1` のときだけ。既定と `regress:full` には入れない)。

- ブラウザは `fmrb_web.rb up` を使わず、自分で Linux の Chromium を起こす (`--headless=new`、プロファイルは `tmp/regress/checkpoint/web_profile`、ページのログは `--enable-logging=stderr` で file へ)。`fmrb_web.rb` の `up`・`down` は状態の file (`wasm/build/drive_browser.pid`) が 1 つしかなく、人のページと取り合うため。Chromium は `FMRB_CHROME`、`/usr/bin` のもの、Playwright のもの (`~/.cache/ms-playwright`) の順に探す。Windows の Chrome は使わない (プロファイルを Windows の側に作ることになり、ログも取れない)。
- 開発サーバは port 8067。ページは `?autostart=1&drive=1&app=default/shell&zenoh=ws/127.0.0.1:17459` (Shell を開いておく)。設定を `put` して `reload` し、転送のアプリがつながるのを待つ。
- 場面は 4 つ: web move (A → ブラウザ版 → Shell の `move` で A へ。両向きの続き方を F2 と同じ `continuity_of` で見る)、web calls、web requires、web late。
- 結果: 通る。`ONLY=standard NO_BUILD=1` で 2.1 分、作るところからの `rake regress:checkpoint WEB=1` (標準・全部 mruby・ブラウザ版) で 5.4 分 (ブラウザ版の分は 44 秒)。出力 (前者):

```
web (standard): ok (web move: in a 5->6, main 5->6, t step 487 ms, carried 27 ms, held 76 ms, 23083 B; back a 20->21, main 21->22, t step 293 ms, carried 30 ms, held 67 ms, 23107 B; web calls: moved, missing linux_settings (217 ms); web requires: refused before it stopped; web late: went on here (a 5->6, main 5->6), the copy in the browser stopped; 44s)
```

### 12.5 気づき

- ブラウザ版のログの時刻 (`I (2804916107) ...` の括弧の中) は、まだタスクごとにずれている (同じ瞬間の行で 400〜560 ms)。ログの時刻は `esp_log_timestamp()` (`fmrb_log_port_hosted.c`) の `clock_gettime(CLOCK_MONOTONIC)` で、ブラウザ版では Worker ごとの時計 (`emscripten_get_now()`) になるため。動きには関係しない (tick と待ちは直した時計) が、ブラウザ版のログを時刻で並べると前後する。ページの console の到着の順は正しい。直すなら `port_clock` の時計に揃える (今回は触っていない)。
- 公開のビルドに gem を入れるか (10 章の 1) は、この結果を見て決めてもらう。費用は f4.md の 4.2 (wasm +128 KB、gzip +47 KB) と、movable なアプリと転送のアプリの基準の表 (1 つあたり 322 KB、VM のプールから)。
