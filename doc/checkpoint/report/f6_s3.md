# F6 (S3): ESP32-S3 の構成 (NARYAv3・StickS3・AtomS3R) に入れる

> 状態: 実装済・検収待ち (実機は未確認) | 更新: 2026-11-07 | S3 の構成の libmruby に mruby-checkpoint を入れ、基準の表を flash に、hook を `mrb_state` に置いた (P4 と同じ形)。内蔵 RAM は 3 構成とも +0、ファームは NARYAv3 +330 KB、StickS3 +382 KB、AtomS3R +380 KB。S3 のアプリのプール (500 KB) のため、mruby-checkpoint の側で基準を作る間の一時的な量を減らした (S3 の gem の組み合わせ、ホストの 64 bit で 271,744 → 23,272 B、残る量 104,232 → 82,472 B)。32 bit の見積もりで、VM を開くときに要る量は約 263 KB → 約 70〜90 KB になり、プールの割り当てを変えなくても movable のアプリが動く見込み。実機には焼いていない

計画は `doc/checkpoint/plan.md`、P4 は `report/f6.md` (この報告はその 7 章「S3 の見込み」の続き)。
mruby-checkpoint の側は worktree のブランチ `wt/s3` (`main` 48aa39e の上に 2 コミット、`doc/report/s3_baseline.md`)。

## 4. VM を開くときの量を減らした (mruby-checkpoint の側)

f6.md の 7 章の見込み: 32 bit で基準の常駐 約 90〜116 KB に、作る間の一時的な量 約 175 KB が重なり、VM を開くときに約 263 KB 要る。P4 の実機で `112328 bytes of the pool (179648 more while it was made)`。

一時的な量の大半は、作る間だけ持つ「ポインタ → 名前の番号」のハッシュ表 (オブジェクト用と C の関数用、1 枠 8 B を半分まで埋める 2 の冪の大きさ、伸ばすときは新旧が重なる)、irep の表、名前ごとの snapshot の番号表、名前で中身をたどる待ち行列の名前の写しだった。さらに、訪ねたクラスごとに `mrb_class_path` が作る String のごみが、プールにヒープのページを 1 枚増やしていた (残る量に数えられていた)。

入れた工夫 (詳しくは mruby-checkpoint の `doc/report/s3_baseline.md`):

1. ハッシュ表は名前 (irep) の番号だけを持ち、ポインタは残す名前の表から引く。16 bit の枠、3/4 まで、固定の表があれば表の数で最初から大きさを決める。オブジェクトと C の関数で 1 つ。
2. irep はポインタだけ持ち、表のハッシュとは見つけた順に比べる。違ったときは表の同じハッシュの項の番号 (2 B) で結ぶ (前は全部 16 B。P4 の実機は表と irep が違っていて 27,600 B 持っていた)。
3. 待ち行列は名前の番号。表の snapshot は二分探索。表と違って見える snapshot は組の並び (前は snapshot の数ぶんの配列、P4 で 3,460 B)。
4. 残す 3 つの索引 (`obj_idx`・`func_idx`・`irep_idx`) を 16 bit の項にし、その場で並べる。
5. クラスの名前を String を作らずに読む。集めたメソッドと ivar はその場で並べる。
6. C の関数の番地を表に入れる形 (Ff の 2 章の (a)) は入れなかった。S3 で減るのは約 1,000 関数 × 6 B = 約 6 KB で、各 gem の `static` の関数に手を入れる量に見合わない。

数字 (同じ表、同じ gem の組み合わせ。`tools/ckpt_table` の `--measure`、ホストの 64 bit、estalloc のプール):

| gem の組み合わせ | 名前 | 残る量 前 → 後 | 作る間の一時的な量 前 → 後 |
|---|---:|---:|---:|
| NARYAv3 | 3,403 | 104,232 → 82,472 | 271,744 → 23,272 |
| NARYAv3 + Asterism (`FMRB_ASTERISM=1`) | 4,163 | | → 28,512 |
| StickS3 | 4,187 | | → 28,544 |
| AtomS3R | 4,163 | | → 28,512 |
| ネイティブ版 (`regress:checkpoint` のログ。前は Ff の報告の値で、gem の版が違う参考) | 4,111 | (110,768) → 97,544 | (276,896) → 47,832〜56,144 |

mruby-checkpoint の既定の gembox (1,719 名前) の 32 bit のドライバ (表あり) では、残る量 45,836 → 20,429、一時的な量 65,995 → 9,830。

## 5. S3 のプールでの見積もり (32 bit)

実機では測っていない。部分ごとの大きさは数で決まる (ポインタ 4 B、索引 2 B、値の場所 9 B) ので、ホストの数から 32 bit の量を出した。

| | NARYAv3 (3,403 名前) | StickS3 (4,187 名前) |
|---|---:|---:|
| 部分の合計 (ptrs・索引・keep・irep・値の場所ほか) | 49,906 | 62,788 |
| 実機で表と irep が違うとき (P4 と同じなら) の irep の項 | +2,556 | +3,430 |
| 表に無い名前と snapshot (P4 の実機で約 1.3 KB) | +約 1,300 | +約 1,300 |
| gem の準備 (`Checkpoint` モジュール、データの型、受ける側のメソッド) と割り当ての頭 | +約 3,000〜6,000 | +約 3,000〜6,000 |
| **基準の常駐** | **約 57〜60 KB** | **約 71〜74 KB** |
| 作る間の一時的な量 (64 bit の値 × 既定の gembox の 32 bit / 64 bit の比 0.65) | 約 15 KB | 約 19 KB |
| **VM を開くときに要る量** | **約 72〜75 KB** | **約 90〜93 KB** |
| 前の見積もり | 約 263 KB | 約 263 KB 以上 |

- アプリが使える残り: 500 KB − 基準の常駐 = NARYAv3 で約 440 KB、StickS3・AtomS3R で約 426 KB (gem を使わないアプリの 85〜88%)。VM を開いた直後の一時的な量は、アプリの読み込みより前に返るので、アプリと重ならない。
- P4 の実機の比 (常駐 112,328 B / 部分の合計 約 94 KB) の残り 約 18 KB の大半は、クラスの名前のごみのヒープのページだった (4 章の 5 で無くなった) と見ている。実機の `VM set up for checkpoints` の行で確かめる (8 章)。
- 書く・戻すときの作業の領域 (イメージのバッファ、表) は今までどおりプールの外 (`fmrb_sys_realloc`、SYSTEM のプール)。

### 親に返す選択肢 (プールの割り当て)

プールの大きさはアプリから見える仕様なので、サブでは決めない。

1. **(推奨) 変えない (500 KB のまま)**。movable のアプリは約 85% を使える。大きいアプリは今までどおり `large_memory = true` (1 MB、同時に 1 つ) を自分で付けられる。
2. movable のアプリは自動で大きいプール (`POOL_ID_USER_APP_LARGE`、1 MB) を使う。同時に動く movable のアプリが 1 つに限られ、転送で着くアプリも大きいプールを取るので、そのプールを使う別のアプリと取り合う。
3. S3 のアプリのプールを、基準の常駐の分 (約 70 KB) だけ増やす。PSRAM の空き (約 3.2 MB) から、静的に取る 3 つで約 210 KB。

## 6. 転送のアプリ (Asterism の受け口) を S3 に入れるか

- 転送のアプリ (`/usr/share/transfer/`、`.app.rb` と `.app.toml` で 24,778 B) は、3 つの板の storage に既に入っている (除外の一覧に無い)。
- 動くのに Asterism (`picoruby-asterism-zenoh`・`picoruby-asterism`・`picoruby-fmrb-asterism`) が要る。StickS3・AtomS3R は既定で `FMRB_ASTERISM=1` なので、gem を入れたこの段のファームで受け口になれる。
- **NARYAv3 (Retro) は既定で `FMRB_ASTERISM=0`**。そのままでは転送のアプリが動かず、移す相手にも移す元にもなれない (同じ端末で止めて続けるのはできる)。`FMRB_ASTERISM=1` で組んで測った (gem 入り、同じ木):

| NARYAv3 | DIRAM | ファーム | 基準の名前 |
|---|---|---|---|
| `FMRB_ASTERISM=0` (この段) | 125,699 | 4,954,896 | 3,403 |
| `FMRB_ASTERISM=1` | 126,395 (**+696**) | 5,213,872 (+258,976) | 4,163 |

- Asterism を入れると内蔵 RAM の静的な領域が +696 B 増える (checkpoint の分ではない)。中身は mbedTLS の PSA の核の `.bss` (`psa_crypto.c` 508 B と `psa_crypto_slot_management.c` 184 B) で、Zenoh の TLS の経路が連れてくる。zenoh-pico と Asterism の gem 自身の静的な領域は内蔵 RAM に無い (2026-11-07 に直した。初めは「zenoh-pico と Asterism の gem の分」と書いていた。report/s3_next.md の 1.2)。
  → 2026-11-07: NARYAv3 は既定で入れることになった (report/s3_next.md)。D4 の「内蔵 RAM は +0」に当たるので、この段のサブでは入れていない。同じ日に、PSA の核と `ssl_ciphersuites.c` の `.bss` を PSRAM へ移す fragment の条件を緩め、NARYAv3 の DIRAM は Asterism なしより少なくなった (report/s3_next.md の 5 章)。flash の空きは足りる (区画 6 MB の 17%)。
- WiFi: NARYAv3 は ESP32-S3 の WiFi STA (`wifi_task.c`、mDNS) を持つ。BLE とは実行時に排他 (wifi_task.c の決まり)。転送のアプリが動いている間は WiFi の側。WiFi・lwIP・zenoh-pico のセッションが実行時に内蔵の heap から取る量は、実機でないと測れない (StickS3 の Asterism の実績があるので、そちらのログで見られる)。
- 親に返す選択肢:
  1. **(推奨) NARYAv3 の既定は `FMRB_ASTERISM=0` のまま**。Retro は同じ端末で止めて続けるところまで。移したい人は `FMRB_ASTERISM=1` で組む (+696 B の内蔵 RAM と +259 KB の flash を了解のうえで)。リリースの前の実機の確認は StickS3・AtomS3R で移す場面を、NARYAv3 は同じ端末の場面を見る。
  2. NARYAv3 の既定を `FMRB_ASTERISM=1` にする。内蔵 RAM の +696 B を何かで相殺する必要がある (この段では見つけていない)。

## 8. 実機で確かめる手順 (この段では行っていない)

焼き方は `doc/regression/usage.md` と CLAUDE.md の「実機の検証」。共通:

1. この木で `MRUBY_CHECKPOINT_DIR=/home/kishima/fmrb/wt/mruby-checkpoint-s3` (または pin を進めた後は不要) を付けて `FMRB_HW_TARGET=<板> rake clean_all build:esp32`。表は自動で作る (`tmp/ckpt_table/<板>/measure.txt` にホストの 64 bit の費用)。
2. storage も焼く (区画表は変えていない。ただし app だけ焼いてきた板は storage が古く、`/usr/share/transfer/` と試験のアプリ `app/test/ckpt_*` が無いことがある。`/home` を退避してから)。flash は MCP の `serial_start` → `flash`。
3. 起動: `rake regress:boot BOARD=<板>` (`narya_v3` / `sticks3` / `atoms3r`)。crash の印 0 件、`IRAM free:` が前と同じこと。
4. VM を開く量: movable のアプリ (`/app/test/ckpt_counter.app.rb`) を起こし、シリアルの `VM set up for checkpoints: the baseline (N names ...) took X bytes of the pool (Y more while it was made); table: ...` と `baseline by part` の行を読む。X が 5 章の見積もり (NARYAv3 約 57〜60 KB、StickS3 約 71〜74 KB)、Y が約 15〜19 KB に近いか。`M1|spawn:` の内蔵 RAM が gem なしのときと同じか。
5. 実機の場面: `rake regress:checkpoint BOARD=<板>` (`targets.rb` は変えなくてよい。`checkpoint_board.rb` は firmware を持つどの板でも選べる)。StickS3・AtomS3R は Asterism が入っているので全部の場面。NARYAv3 は `FMRB_ASTERISM=1` で組んだときだけ移す場面が流せる (既定のファームでは board self だけが意味を持つ)。開発の遠隔操作 (`FMRB_DEV_REMOTE_CTL`、既定 ON) の HTTP と WiFi が要る (S3 は BLE と排他なので WiFi の側で起動する)。
6. 注意: AtomS3R は画面が 128x128 で、board window の試験の Window (160x90) が入らない見込み。落ちたら場面を外すか Window を小さくする。

## 10. P4 の構成

TAB5・NARYAv4 は同じ変更 (gem の新しい版、`build.rake` の表の作り方の共通化) の上で `rake regress:size ONLY=tab5,naryav4` を流した。通る。

| 端末 | DIRAM | ほかの内蔵 RAM | ファーム | app の領域の空き |
|---|---|---|---|---|
| TAB5 | 129,330 (f6.md の後と同じ) | 948 (+0) | 7,213,888 | 1,109,184 (13%) |
