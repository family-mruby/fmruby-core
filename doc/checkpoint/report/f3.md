# F3: 窓のあるアプリを運ぶ

> 状態: 実装済・検収待ち | 更新: 2026-11-04 | 申告した mruby のアプリの窓を、F1 (同じプロセスで起動し直す) と F2 (2 つのネイティブ版の間で移す) の両方で運べるようにした。`FmrbGfx` の C のデータは「どの画面に描いていたか (役)」だけをイメージに書き (gem の C のデータの表に、checkpoint を開いた VM だけが登録する。D7)、着いた側では基底クラス `FmrbApp` が窓の画面を文脈から作り直し、`FmrbGfx` を新しい画面に結び直し、`GfxBlock` を定義し直し、枠・角丸・スプライトの範囲・フォント・知らせの購読を戻してから `on_restore` を呼ぶ (D8)。描いた絵はイメージに入れず、アプリが `on_restore` で描き直す (案 (b))。`rake regress:checkpoint` に窓の場面を 2 つ (起動し直す・移す) 足し、窓の範囲が画素で同じこと、移った後にクリックとキーが届くことを、両方の構成で確かめた

計画は `doc/checkpoint/plan.md`、指示は `doc/checkpoint/instruction_f3.md`。F1 は `report/f1.md`、F1b は `report/f1b.md`、F2 は `report/f2.md`。
mruby-checkpoint の gem には手を入れていない (C のデータの表 `mrb_checkpoint_register_data` がそのまま使えた)。

## 1. 道筋

```
書く側 (A)
  セーフポイント → gem がオブジェクトを書く
    FmrbGfx (C のデータ) → gfx.c の gfx_ckpt_dump: 版、役 (窓 / 壁紙 / 追加の画面 / 無し)、
                           追加の画面なら作り方 (幅・高さ・z・透過・色キー)
  → .ckpt と .toml (窓の今の位置・大きさ・種類、角丸、全画面の切替、高解像度、最小の大きさ)
着いた側 (同じプロセス、または B)
  spawner: .toml を読んで文脈を作る (窓の位置・大きさ・z は普通の起動と同じ道。フォーカスはカーネルの after_spawn)
  mrb_checkpoint_restore → gfx_ckpt_restore: 役だけを持った FmrbGfx (何にも描かない)
  fmrb_app_checkpoint_resume → FmrbApp#_checkpoint_restored (Ruby、基底クラス)
    _checkpoint_canvases (C): 文脈から窓 (と壁紙) の画面を作る、@_canvas・@pos_x などを今の値に
    ObjectSpace の FmrbGfx を全部 _checkpoint_rebind (C): 役の画面に結ぶ (追加の画面は作り直す)、フォントと文字の大きさを戻す
    ObjectSpace の GfxBlock を全部 _checkpoint_redefine: 表示側にプログラムを定義し直す (次の draw で全部のレジスタを送る)
    ObjectSpace の SpriteImage / SpriteInstance の id を忘れる
    角丸の合成の範囲、スプライトの範囲、clear_user_area (枠を描く)
    @_topics を subscribe し直す
    アプリの on_restore (描き直す)
    present
  → mrb_checkpoint_continue (止まった所から)
```

## 3. 描いた中身の戻し方

| 案 | 中身 | 大きさ | 判断 |
|---|---|---|---|
| (a) 画素をイメージに入れる | 書くときに画面の画素を読み、着いた側で書き戻す | RGB332 (1 画素 1 バイト) で、Retro の全画面 320x240 が 76,800 B、Modern 426x240 が 102,240 B、高解像度の全画面 640x360 が 230,400 B。この試験の窓 160x90 でも 14,400 B (イメージ 29,672 B の半分)。追加の画面・壁紙・スプライトの画像はさらに別 | 採らない |
| (b) 基底クラスが窓を作り直し、アプリが描き直す | 基底クラスが空の窓 (枠と利用の範囲の背景) を作り、`on_restore` でアプリが描く | イメージは増えない | **採った** |
| (c) 両方 | | (a) と同じ | 採らない |

理由:

- **画素を読む口が無い**。コアから表示側の画面を読むのは `get_pixel` (1 画素ずつの同期の往復) と、表示側のファイルへの書き出し (`export_frame`) だけ。Retro では画面は WROVER の上にあり、読み戻すには SPI の上に大きな読みの命令を足すことになる。これは描画の経路 (graphics-audio との境) の作りを変えることで、指示書の止まる条件にあたる。
- **イメージが数倍になる**。窓のないアプリのイメージは 23 KB、窓のアプリで 30 KB。画面を入れると全画面のアプリで 100〜230 KB 増え、F5 で Asterism に送る量と、端末 (F6) の PSRAM の作業の領域にそのまま効く。
- Retro と Modern で画面の大きさが違う (F4)。画素を運んでも、大きさの違う端末では描き直しが要る。アプリの状態から描き直す形なら、F4 でも同じ道で済む。
- 描き直しは、`on_update` で毎回全部描くアプリ (多くのゲーム・時計) には何も要らない。何かあったときだけ描くアプリ (pub/sub の見本、この試験のアプリ) は `on_restore` に描く関数を 1 行書けばよい (§6)。

基底クラスが `on_restore` の前にすること: 窓の画面を作り、利用の範囲を `THEME_WINDOW_BG` で消して枠を描き (`clear_user_area`)、`FmrbUI` の部品に描き直しの印を付ける。`on_restore` の後に `present`。何も描かないアプリでも、空の窓が出る。

## 4. 基底クラスとアプリの線

- 基底クラス (`FmrbApp`) が戻す: 窓 (位置・大きさ・種類・角丸・タイトル・枠)、窓・壁紙・追加の画面と、それを指す全部の `FmrbGfx`、フォントと文字の大きさ、`GfxBlock`、合成の範囲・スプライトの範囲、`subscribe` した知らせ、止まっていた印 (`@_suspended`)。フォーカスと重なりはカーネルが普通の起動と同じに決める。タイマ・Task・インスタンス変数はイメージの中にある (gem)。
- アプリが `on_restore` で直す: 描いた絵、スプライト・画像・マスク・動画、生の HID の転送、マイク、つなぎ直し (ソケット、Asterism)。
- 書けないもの (断られる): 開いたファイル、ソケット、Asterism のセッションなど、登録の無い C のデータを持っているとき。
- `sig/fmrb_app.rbs` の `on_restore` と、`fmrb-app.rb` の `on_restore` のコメントに書いた。

## 5. 試験

### 5.1 試験のアプリ

- `/app/test/ckpt_window.app.rb` (窓 160x90、`movable = true`、ランチャーに出さない): クリックで緑の点、キーで文字を描き (何かあったときだけ描く)、日本語のフォント (`:ja, 12`)、自前の `GfxBlock` (最後の点の赤い枠)、スプライト (右下の 6x6)、Task が 300 ms ごとにログに数え、知らせ `ckpt_window` を `subscribe` する。`on_restore` でスプライトを作り直して全部描く。
- `/app/test/ckpt_file.app.rb` (窓なし、`movable = true`): `/tmp` のファイルを開いたまま数える。断りの場面に使う (前の「窓が断られる」場面の代わり)。

### 5.2 `rake regress:checkpoint` の場面

| 場面 | 確かめること |
|---|---|
| refuse file | 開いた `File` を持つアプリは「C data of class File (type 'IO') has no entry in the checkpoint data table」で断られ、動き続ける |
| window (F1 の形) | クリック 2 つとキー 2 つで描かせ、`--restart`。窓の範囲 `[60, 50, 160, 90]` が書く前と画素ですべて同じ。Task が次の 1 歩から続く。カーネルのログに新しい pid の `subscribed to 'ckpt_window'`。起動し直した後のクリックとキーがアプリに届く |
| window move (F2 の形) | 同じことを B へ移して。B の窓が A の書く前と画素で同じ、B で Task が続き購読し直す、B でクリックとキーが届く、A の窓は閉じて A はイメージの後に 1 歩も数えない |

- 画面の比べ方は `regress:screens` の `Regress::Screens::Image#diff` (画素がすべて一致、揺れの幅なし) に窓の範囲を渡す。撮る前にマウスの指す先を窓の外 (400, 200) へ動かし、2 回続けて同じになるまで撮り直す (描いたばかりの絵が表示に届くのを待つ)。違ったら `tmp/regress/checkpoint/window.png` と `.diff.png` を残す。
- 窓の外 (デスクトップ・時計) は比べない (B は別のプログラムで、時計も違う)。

## 6. 既存のアプリで試す

`/app/demo/sub_demo.app.rb` と `pub_demo.app.rb` (知らせを出す側と受ける側、どちらも窓 160x80) に `movable = true` を付けて、ネイティブ版 (全部 mruby) で試した。

| 何を | 結果 |
|---|---|
| 書けるか | 書ける。どちらもイメージに書け (`/tmp/sub_demo.ckpt` など)、起動し直せた |
| 数の続き | Publish を 2 回押してから両方を起動し直し、もう 1 回押すと「Sent: 3」「Received: 3」。インスタンス変数は続く |
| 購読 | 起動し直した SubDemo に届く (基底クラスが `subscribe` し直した。カーネルのログに `PID 5 subscribed to 'demo'`) |
| 足りなかったもの | 起動し直した直後、**どちらの窓も枠だけで中が空**。どちらも何かあったとき (`on_create`・クリック・知らせ) だけ描くので、次に何か起きるまで描かれない。直し: 両方に `on_restore` で `draw_screen` を呼ぶ 3 行を足し、`.app.toml` に `movable = true` を付けた (このまま出す) |

- 2 つのプログラムの間では、Pub と Sub が別のプログラムに分かれると知らせは届かない (カーネルの購読は 1 つのプログラムの中)。これは F5 (Asterism) の話。
- `movable = true` を付けたアプリは、gem を持つビルド (ネイティブ版・sim) で基準の分 (64 bit で約 356 KB) をプールに使う。どちらも小さいアプリで、ネイティブ版のプール (1.5 MB) に収まる。ESP32 の構成では gem が無いので何も変わらない。

## 9. 気づき

- 表示側の `GfxBlock` のプログラムとスプライトの ID は、表示側に**全体で 1 つの表**で持たれている。復元したアプリが古い ID をそのまま使うと、着いた側でたまたま同じ ID を持つ**ほかのアプリの**プログラムやスプライトを動かしうる。プログラムは定義し直し、スプライトは忘れる (例外になる) ようにした。画像・マスク・動画の ID はアプリがただの整数で持つので、基底クラスからは見つけられない (アプリが `on_restore` で作り直す約束にした)。
- 窓の枠の `GfxBlock` は、表示側でプログラムが画面ごとに消される (`DELETE_PROG (by canvas)`) ので、書いた側を閉じたときに漏れない。
- 書いた側 (F1) を閉じると、窓の画面と枠のプログラムは普段の後片付け (`fmrb_app_canvas_release_all`) で消える。`on_destroy` を呼ばない閉じ方でも残らない。
- F2 で止めている間 (1.4 s ほど)、A の窓は書いたときの絵のまま残る。何も印は出していない (F2 §10 の宿題。サブの仮決め 6)。
- 作ったばかりの画面の中身は、アプリが描くまで決まっていない。基底クラスが利用の範囲を消して枠を描くので、`on_restore` が何も描かなくても、普通に起動した直後のアプリと同じ見た目 (空の窓) になる。

## 10. サブの仮決め (ユーザが見直す)

1. 描いた中身は (b): イメージに入れず、アプリが `on_restore` で描き直す。基底クラスは空の窓 (枠つき) を用意し、`on_restore` の後に `present` する。
2. `FmrbGfx` は「役」を書く形 (窓・壁紙・追加・無し)。ID は書かない。着いた側の結び直しは、基底クラスが `ObjectSpace.each_object(FmrbGfx)` で全部を探して頼む (アプリが持つ `FmrbGfx` を基底クラスが知らなくてよい)。`GfxBlock`・スプライトも同じく `ObjectSpace` で探す。
3. 窓の画面は、gem の C のデータの戻し (イメージを読んでいる途中) ではなく、復元が済んでから基底クラスが作る。復元が断られたとき (F2 の move refused) に B に窓が一瞬出ないように。
4. 購読の控えは基底クラスの `@_topics` (最初に `subscribe` したときに作る。使わないアプリは費用 0)。
5. スプライトの古い ID は基底クラスが忘れる。作り直しはアプリ。画像・マスク・動画の ID は手を出さない。
6. F2 で止めている間の A の窓には何も出さない (書いたときの絵のまま)。
7. `GfxBlock` のバイト列の控えは、gem を持つビルドの運べるアプリだけ (`_checkpoint_keep?`)。最初はビルドだけで見分けたが、sim のすべての窓のアプリが枠の 2 つの分 (約 500 B) を払い、`regress:run` の Kamon が幅を超えた (§7)。ESP32 では今までどおり持たない。
8. 横の `.toml` に足したのは、角丸・全画面の切替・高解像度・最小の大きさ。全画面に切り替えていたアプリは全画面として起動する (窓に戻したときの大きさは運ばない)。
9. 断りの場面は、窓のアプリの代わりに「開いたファイルを持つアプリ」(`ckpt_file`) にした。
10. pub/sub の見本 2 つに `movable = true` と `on_restore` を付けたまま出す (§6)。
11. 着いた側で窓の大きさが書いた側と違う (端末の画面が違う) ときの扱い (`on_resize` を呼ぶなど) は入れていない。同じビルドの間では起きない。F4。

## 11. 決めてほしいこと (ユーザ)

1. 描いた中身の戻し方: (b) (アプリが描き直す) でよいか。画素を運ぶ (a) は、表示側から画面を読み戻す命令を graphics-audio との境に足す必要があり (Retro では SPI の上の大きな読み)、イメージも全画面で 100〜230 KB 増える。
2. F2 で止めている間、A の窓に「移動中」の印を出すか (今は何も出さない)。
3. 移せるアプリを増やすときの方針: 標準のアプリに `movable = true` を付けていくか (gem を持つビルドで基準の約 356 KB をプールに使う)。今は pub/sub の見本 2 つだけ。

## 12. F4 に要るもの

- 画面の大きさ・形の違う端末の間 (Retro 320x240 ⇔ Modern 426x240): `.toml` の窓の位置・大きさが着いた側の画面に収まらないとき、spawner が直した大きさと、イメージの中の `@window_width` などが食い違う。基底クラスで比べて `on_resize` を呼ぶ形が素直 (`_checkpoint_canvases` が位置は今の値に書き換えている)。
- フォントの有無 (`FONT_AVAILABLE` は端末の系列ごと): 着いた側に無いフォントは近いものになる。`@current_font` は着いた側で選び直した値に揃える。
- ファイル: 開いたファイルの登録 (パスと位置と開き方、調査 §5.3 の (a))。今は断る。
- 画像・マスク・動画の ID を基底クラスが知る形 (今はアプリが整数で持つ)。
