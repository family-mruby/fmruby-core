# F0: patch と gem を Family mruby に入れる (ネイティブ版と sim)

> 状態: 実装済・検収待ち | 更新: 2026-11-03 | mruby-checkpoint の gem を固定点で取り込み、sim とネイティブ版にだけ入れた。VM の patch (セーフポイントの hook・切り替えの要求の数) は全ビルドの `lib/patch` に混ぜた。gem から 1 プロセス 1 VM の前提を外した。普段の命令数は減り (−1.3〜−11.1%)、ESP32 の内蔵 RAM は増えない

計画は `doc/checkpoint/plan.md`。段と決定 D1-D16 は mruby-checkpoint の `doc/plan.md`、
隔たりの調査は同 `doc/survey_family_mruby.md` (以下「調査」)。

### 1.3 gem の直し (mruby-checkpoint の f0 ブランチ)

調査 §2.5 の 1 プロセス 1 VM の前提を外した。

| 前 | 後 |
|---|---|
| `static checkpoint_state *states[8]` を線形に探す | 状態は VM のアロケータ (`mrb_calloc`) で取り、ポインタは VM のグローバル変数 `_checkpoint_state_` (Ruby からは綴れない名前) に C のポインタの値で持つ。即値なので permanent にもイメージにも入らない |
| `made_funcs[64]` (名前 96 バイト × 64、6 KB) と遅延の初期化 (`nmade_funcs = -1`) | 状態の中の可変長の表。VM ごとに最初の基準で 1 回探す |
| `static mrb_state *sort_mrb` + `qsort` | `mrb_state` を渡せるマージソート (安定。キーは表の中で重ならないので並びは同じ) |
| 素の `malloc` / `realloc` / `free` (状態・別表・関数の名前の表・パス、P6 のソースの表) | すべて `mrb_malloc` 系 |

- 静的なものは 1 つだけ残した: **要求を待っている状態の数** (`npending`、4 バイト、原子的に増減)。
  hook はどの VM の切り替えのたびにも呼ばれ、状態を引く (シンボルとグローバル変数の表) と
  1 回数百命令かかった (Task のベンチマークで、gem なしの後に比べ +11.7%)。数が 0 なら引かずに戻る。
  VM がいくつあっても正しい (数でしかない)。
- `settle_switch` (要求のあとで旗を元に戻す所): 下ろした直後に数を見直し、セーフポイントで
  読んだときから動いていれば旗を立て直す。別のスレッド (case-D の tick) でスライスが終わった
  要求を、下ろした旗で消さないため。
- `mrbgem.rake`: 駆動の道具 (`tools/checkpoint`) が無ければ実行ファイルを宣言しない。
  Family mruby の写しには `tools/` が無いので、`bin/checkpoint` を作ろうとしない。
- mruby-checkpoint の `patches/0001` にも §3.1 の直しを入れ、`patches/0002` も数を 2 つに分けた
  (§3.3)。Family mruby の写しと同じ形に保ち、原理検証の試験一式で意味が変わらないことを確かめるため。

## 3. 気づき

### 3.1 ルートのコンテキストで旗が立ちっぱなしになる (直した)

最初の形 (0001 をそのまま混ぜたもの) で、自前の時分割ありのベンチマークが 12 倍遅くなった
(bm_mandel_term 2.6G 命令、bm_so_mandelbrot 186G)。

- Family mruby の HAL は、タイムスライスの間隔で `switching` を立てる。走っている Task が
  あるかどうかを見ない (case-D の別のタスクも、自前の時分割も)。上流の HAL (POSIX など) は
  走っている Task のスライスが終わったときだけ立てる。
- ルートのコンテキスト (Task の外) では、立った旗を下ろす者がいない (下ろすのはスケジューラが
  Task を走らせるとき)。前の判定は `switching && c != root_c && ...` を命令ごとに行っていたので
  安かった。0001 の速い側は `switching || STOPPED` だけを見るので、そこから先の命令が全部
  遅い側 (と hook) を通る。
- 直し: 遅い側で、ルートのコンテキストなら旗を下ろす。下ろしてよい理由は、スケジューラが
  Task を走らせる前に必ず下ろす (`execute_task`) ことと、ルートの sleep も下ろしている
  (`sleep_us_impl`) こと。ルートで立った旗は今も捨てられている。
- Family mruby でルートのコンテキストが命令を走らせるのは、gem の mrblib の初期化など短い所。
  ベンチマーク (トップレベルのプログラム) で目立ったが、アプリでも sim の tick のタスクが
  起動の間に旗を立てれば同じことが起きていた。
- mruby-checkpoint の 0001 にも入れ、原理検証の試験一式で意味が変わらないことを確かめた (§2.1)。

### 3.2 hook の費用は「状態を引く」所にあった

hook は要求が無くても切り替えのたびに呼ばれる。原理検証の `states[8]` の線形探索は安かったが、
VM の中に状態を持たせると、引くのにシンボルの表とグローバル変数の表を通る (1 回約 600 命令、
内訳はシンボルの引き当てが 3/4)。要求の数を先に見る形にした。presym にして引く案もあるが、
それでも 1 回 100 命令ほど残る。

### 3.3 要求の数の進め方 (別のスレッドから)

case-D では、tick のタスク (別のスレッド) と VM のスレッドの両方が切り替えを頼む。最初は 1 つの数を
tick 側だけ原子的に (`__atomic_add_fetch`) 進めた。VM 側の素の加算で tick 側の 1 回が消えても、
そのとき書く値は控えた値より先に進んでいるので、「動いたか」は正しく分かる。ところが
**ESP32-S3 では原子的な加算がライブラリの呼び出しになり、newlib の内蔵 RAM が 95 バイト増えた**
(`regress:size` で DIRAM +96、P4 は RISC-V の命令になり +0)。

数を 2 つに分けた: VM のスレッドが進める `switch_requests` と、tick が進める
`switch_requests_async`。書き手が 1 つずつなので、どちらも素の加算でよい。読む側は和を見る
(`task_switch_requests()`)。どちらも増えるだけなので、和はどちらが動いても動く。tick 側は数を先に
進め、release の fence を挟んで旗を立てる (旗を見た者は数の動きも見る)。fence は S3 では `memw`、
P4 では `fence` の 1 命令で、呼び出しにならない。自前の時分割では `vm_deliver_switch` も VM の
スレッドで動くが、そのビルドでは `switch_requests_async` を書くのはそこだけなので、書き手は 1 つの
まま。mruby-checkpoint の 0002 と gem も同じ形にした。

## 4. サブの仮決め (ユーザが見直す)

1. hook の関数ポインタは `MRB_VM_SAFEPOINT_HOOK` のときだけ置く (sim・ネイティブ版)。ESP32 の
   `vm.c` は速い側・遅い側の形だけが変わり、静的な領域は増えない。F6 で端末に入れるときに、
   4 バイトの .bss を置くか、`mrb_state` (プール) に持つ形にするかを決める。
2. ルートのコンテキストで旗を下ろす直し (§3.1) を Family mruby と mruby-checkpoint の両方の
   0001 に入れた。上流 (mruby) に出すかは、U1〜U5 と一緒にユーザが決める。
3. gem の唯一の静的なもの `npending` (4 バイト)。端末に入れるときは内蔵 RAM の 4 バイトになる
   (F6 で、PSRAM の属性を付けるか `mrb_state` に寄せるかを決める)。
4. 状態のポインタを VM のグローバル変数に持つ。`global_variables` に `_checkpoint_state_` が
   出る (Ruby からは `$` で始まらないので読み書きできない)。mruby の `_gc_root_` と同じ扱い。
5. `rake setup` はどのビルドでも gem を写す (取りに行く)。ESP32 だけ作る人も mruby-checkpoint を
   取ることになる (Asterism と同じ)。

## 5. F1 が要るもの

- **タイムスライスの残り (D10)**: Family mruby で次の横取りを決めるのは HAL の `tick_countdown`
  (と `switch_pending`・`pending_ticks`)。イメージは mruby-task の `t->timeslice` を運ぶが、HAL の
  数は運ばない。HAL に VM ごとの読み書きの入口 (例 `mrb_hal_task_slice_get/set`) を足し、gem は
  埋め込む側の callback (書くときに読む・続けるときに書く) で受ける形が要る。gem は HAL を
  直接知らないので、callback の登録の口を gem に足す。
- **作業の領域をプールの外へ (D11)**: いま書き出しのバッファ・番号の表・基準はそのアプリの VM
  プールから取る (`mrb_malloc`)。gem にアロケータの口 (例 `mrb_checkpoint_set_allocator`) を
  足し、Family mruby は `fmrb_sys_malloc` の PSRAM を渡す。状態の構造体そのものはプールでよい。
- **止める合図 (D5)**: `_spin` を起こす `APP_CONTROL` の `cmd = "checkpoint"`、アプリのタスクの中で
  `mrb_checkpoint_request`。要求は同じスレッドから出す (§3.3 の数の扱いもその前提)。
- **基準を取る VM (D12)**: `.app.toml` の印 (D6) のあるアプリの `create_vm_mruby` でだけ
  `mrb_checkpoint_baseline` を呼ぶ。gem は全 VM に入っているが、基準を取らない VM の費用は
  状態の構造体 (`mrb_calloc` 1 つ) と `Checkpoint` の定義だけ。`regress:run` の VM プールで確かめる。
- **ソースの登録**: mruby-checkpoint の P6 で、イメージに表示用のソース (任意のセクション `SRC0`) を
  入れられるようになった。埋め込む側がコンパイルするファイルごとに `mrb_checkpoint_add_source()` で
  ソースを登録する決まりなので、Family mruby のアプリの読み込み (`execute_mruby_script` のソースの
  コンパイル。flash のバイトコードは対象外) で登録する。登録した分は状態の構造体の中、VM のプールに
  載る (大きいアプリでは D11 の置き場所と一緒に考える)。F0 では実装していない。
- **復元の起動の形**: `.ckpt` を見分ける読み方、`mrc_create_task` の Task と
  `mrb_checkpoint_set_host_task` / `mrb_checkpoint_host_task`、書き出し側の終わり方 (suspend で
  プロセスを終えず、アプリを閉じる。`mrb_checkpoint_set_handler`)。
- ルートのコンテキストで書き出すときの旗 (§3.1): 書き出しのあとは旗が下りる。続ける側
  (`mrb_checkpoint_continue`) の `switch_pending` も、ルートなら次の境目で下りる。アプリは Task で
  動くので F1 では当たらない見込み。

## 6. 親が流すもの

worktree では sim の画面と回帰の道具を流せない (docker compose のマウント先が本体のため)。
取り込んだあと、本体 checkout で:

```
cd fmruby-core
MRUBY_CHECKPOINT_DIR=<mruby-checkpoint の f0 を取り込んだチェックアウト> rake clean   # lib/ を変えたので
MRUBY_CHECKPOINT_DIR=... rake build:linux && file build/fmruby-core.elf
rake regress                 # ホストの試験 + 描画の記録
rake regress:run             # sim のアプリごとの VM プール (gem の分の増え方を見る)
rake regress:screens         # 標準構成の sim (エディタの 1 打鍵を含む) とブラウザ版
MRUBY_CHECKPOINT_DIR=... rake native:core && rake regress:wl   # ネイティブ版 (要るなら)
```

pin を push 済みの commit に直したあとは `MRUBY_CHECKPOINT_DIR` は要らない
(`rake checkpoint:setup` が `vendor/mruby-checkpoint` に取る)。
