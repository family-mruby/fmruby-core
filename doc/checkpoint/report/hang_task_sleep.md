# task_sleep が起きない (ネイティブ版、自給の tick)

> 状態: 解決 | 更新: 2026-11-04 | `rake regress:checkpoint` の mruby 構成が時々「task_sleep の round 1 が 15 秒出ない」で落ちた。原因は F0 ではなく、自給の tick (FMRB_TASK_SELF_TICK、2026-08 から) の作り: スケジューラがタスクの合間に数えて尽きたタイムスライスを、次に走るタスクの 1 命令目で配っていた。メインループの 1 回の番がスライスより長いと、その後ろに並んだ Task が毎回 1 命令も実行せずに戻され、永久に走らない。スライスは走っているタスクにだけ配るようにし、起こしたタスクを先に並べる処理はスケジューラ側に移した

## 1. 症状

- `rake regress:checkpoint` の mruby 構成 (全部 mruby) が時々
  `FAILED no task_sleep running in the log within 15s` で落ちた。
  `flash/app/test/task_sleep.app.rb` は `task_sleep: start` を出したあと、
  `sleep_ms(100)` を繰り返す Task の `round 1` を出さない。
- 同じ回の標準構成は通っていた。手元で 10 回流して 2 回、続けて 2 回と
  3 回のうちに 1 回ずつ落ちた (合わせて 15 回中 4 回、約 27%)。
- 起動直後に `task_sleep` だけを 30 回起動しても落ちない。

## 2. 調べたこと

### 2.1 止まっている所 (gdb)

止まった状態のネイティブ版に gdb を当てた (`ptrace_scope` が 1 なので、
起動の前に `prctl(PR_SET_PTRACER)` してから exec する包みを挟んだ)。
アプリの VM のスレッドは `mrb_task_run` → `execute_task` → `_spin` の
`fmrb_msg_receive` で待っていて、VM のスケジューラの状態はこうだった。

- 実行待ちの列: メインループのタスク (RUNNING、`_spin` の中) と、
  その後ろに `sleeper` Task (READY、文脈は CREATED のまま = 1 命令も
  走っていない)。待ちの列は空。
- `mrb->exc` は無し、`gc.iterating` は偽、メインループの呼び出しの段に
  C の境目も無い。切り替えの要求の数は増え続け、`tick` も進んでいる。

つまりスケジューラは回っていて、Task は順番が来ているのに走らない。

### 2.2 一時的な計装

`task_run_body` に「タスクを実行したのに pc も ci も動かずに READY で
戻った」回を数える計装を入れた (コミットしていない)。止まった回では、
task_sleep の VM で同じ Task が 1,000 回以上続けて「進まずに戻り」、
毎回ちょうど 1 回だけ切り替えの要求が増えていた。

### 2.3 仕組み

自給の tick では、ティックを数えるのは (1) スケジューラのループの先頭と
待機、(2) VM の命令ごとの検査 (65536 命令に 1 回) の 2 か所だった。
(1) で尽きたスライスは `switch_pending` に立てるだけで、配るのは (2)。
(2) の間引きの数は `mrb_vm_exec` に入った直後だけ 1 から始まり、
**次に走るタスクの 1 命令目で、それまでに立った要求を必ず配る**作りだった
(doc/wasm/report/p2.md の「穴 B」の対処)。

メインループの番は `on_update` → `Task.pass` で終わり、次の番は
`_spin(50)` から始まる。ネイティブ版のスライスは 5 ms x 10 = 50 ms なので、
メインループの 1 回の番は必ずスライスを 1 つ以上使い切る。それを
ループの先頭が数えて要求を立て、次に走るタスクの 1 命令目で配る。

- ふだんは Task は眠っていて、起こされるとメインループの後ろに並ぶ。
  先に走るメインループが 1 命令目で要求を受けてすぐ戻るので、Task は
  要求の無い状態で走れる (「穴 B」の対処が効いているのはここ)。
- ところが Task が**実行待ちのまま**メインループの前に来ることがある。
  `Task.new` は (同じ優先度なので) 切り替えを求めず、メインループは
  `on_create` の残りと `on_update` を走って、最初の `Task.pass` で初めて
  後ろへ回る。この最初の番 (`_init`、窓と描画の往復、`on_create`) が
  スライスの境目にかかっていると、まだ 1 命令も走っていない Task が
  1 命令目で要求を受けて戻る。以後は毎回「メインループが `_spin(50)` を
  含む長い番を走る → 先頭で要求が立つ → Task が 1 命令目で受けて戻る」の
  繰り返しで、抜けられない。

入るかどうかは最初の番がスライスの境目にかかるかどうかで決まるので、
落ちたり落ちなかったりした。checkpoint の前の回を流した後のほうが
入りやすかった理由 (最初の番の長さの違い) までは詰めていない。

### 2.4 必ず再現するアプリ

`flash/app/test/task_turns.app.rb`: メインループは `on_update` で 120 ms を
返し (`_spin` で待つ番がスライスより長い)、`passer` Task は 1 歩ごとに
`Task.pass` する (いつも実行待ちにいる)。直す前は 1 歩目のあと止まる。

| ビルド | 構成 | 止まった回 |
|---|---|---|
| 9c68b5a9 (直す前) | mruby | 5 / 5 |
| 9c68b5a9 (直す前) | 標準 | 3 / 3 |
| a06bb89b (F0 の前) | mruby | 3 / 3 |

F0 の前から同じに止まる。**F0 (checkpoint の safe point、ルート文脈での
`switching` の消去) は原因ではない**。ルート文脈はこのアプリでは
バイトコードを実行しておらず (スケジューラは C)、進まないのは Task の
文脈だった。task_sleep が回帰の通しに入ったのが F1 なので、F1 で
見え始めた。原因は 2026-08 の自給の tick (8e391c41) から入っている。

Linux sim (top-half の tick) と実機は、別スレッドの tick が走っている
タスクに直接書くので、この作りを通らない (自給の tick の部分は
`MRB_TASK_TICK_SELF_SUPPLY` の中だけ)。影響があるのはネイティブ版と
ブラウザ版 (どちらも自給の tick)。

## 3. 直し方

スライスは、尽きたときに走っているタスクにだけ配る。

- `vm.c`: 間引きの数を 1 からでなく間隔いっぱいから始める (1 命令目で
  配らない)。
- `task_hal.c`: スケジューラ側で数えたとき (`mrb_hal_task_account_ticks`)
  に立った要求は捨てる。走っているタスクが無いので、それは直前に
  CPU を離れたタスクのスライスで、次のタスクのものではない
  (`execute_task()` が `switching` を消すのと同じ理由)。
- `task.c`: 「穴 B」の対処をスケジューラ側に移した。タスクの番が
  終わったら、**そのタスクを列の後ろへ回す前に**ティックを数えて適用する。
  その番の間に起こされたタスクは、番を終えたタスクより前に並ぶ。別スレッドの
  tick が番の最中に起こしたときと同じ並びになる。

どれも `MRB_TASK_TICK_SELF_SUPPLY` の中だけで、実機 (ESP32) のコードは
変わらない。

## 4. 確認

| 確認 | 直す前 | 直した後 |
|---|---|---|
| `task_turns` (mruby / 標準) | 5/5・3/3 止まる | 0/10・0/5 (10 歩 1,200 ms = メインループ 1 番に 1 歩) |
| `task_sleep` を 10 回起動 | - | 0/10、10 x 100 ms が 1,001-1,018 ms (直す前の通った回と同程度。穴 B は戻っていない) |
| `checkpoint.rb --only mruby` を繰り返す | 15 回中 4 回落ちる | 15 回とも ok |

- `rake regress:checkpoint`: 両構成 ok。最初の回に `turns` を足した
  (`task_turns` の 10 歩を 10 秒以内に求める。回帰の見張り)。
- `rake regress`: ok。`rake regress:run`: ok (sim 2 系統)。
  `rake regress:screens ONLY=retro,modern,native,native-keys`: 27/27。
  `rake regress:size`: ok、内蔵 RAM +0 (NARYAv3・TAB5。実機の tick は
  top-half なので、変わった行は実機のビルドに入らない)。

## 5. メモ

- 強制終了 (`Dropping mruby VM (forced kill)`) が checkpoint の通しで毎回
  出ているのは別件 (`ckpt_counter` の Task が stop の後も回り続ける)。
  今回の止まりとは関係しない (強制終了だけを前に挟んでも止まらない)。
- ブラウザ版の libmruby (`rake wasm:mruby`) は作り直していない。
