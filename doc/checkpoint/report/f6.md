## 1. P4 の構成の段の失敗 (やること 0)

- 症状: `rake regress:size` の TAB5 が IDF の構成の段で `Missing required kconfig option after retry` で止まる (esp_hosted の manifest の Kconfig の警告の後)。
- 原因: 部品の管理 (component manager) の「新しい版があるか」の確認が、構成のたびに依存をレジストリに対して解き直す。解く道具は範囲が許すすべての版の manifest を読む。`esp_wifi_remote` 0.8.5 が `esp_hosted >=0.0.6` を求めるので、2026-11-05 にレジストリに出た esp_hosted 3.1.0 の manifest も読み、その任意の USB の依存が、持っている esp_hosted (1.4.0、版を固定済み) に無い Kconfig の名前を挙げる。部品の管理は CMake にもう一度構成させ、その 2 回目も同じ所で落ちる。コミットに依らず、レジストリにその版がある間はすべての P4 のビルドで起きる (前のサブの調べ)。
- 版の固定では直らない (esp_hosted は既に固定。3.1.0 を引き込む範囲は esp_wifi_remote のもの)。確認を切ると直る: ロックの無い (または別のチップの) 本当の解き直しでも 3.1.0 は読むが、2 回目を頼む前にロックを書き、2 回目はロックを使う。
- 直し: 最上位の `CMakeLists.txt` で `IDF_COMPONENT_CHECK_NEW_VERSION=0` (`f17c8ee3`、前のサブのコミット。理由はコメントに書いた)。sdkconfig は変えていない。
- 確かめ: 同じコミット (`74a1f83c`) の NARYAv4 (gem なし、別の worktree)、この段の変更の上の TAB5・NARYAv4 (gem あり) が、どちらも `clean_all` からの構成と組み立てを通った (`rake regress:size`)。

## 3. hook と要求の数を `mrb_state` に

決まっていること: hook の関数ポインタと切り替えの要求の数は、実機では `mrb_state` の中に置く。

- **両方のビルドで同じ形にした** (実機だけ変えない)。`mrb_state` に `safepoint_hook`・`gc_root_hook` (どちらも `MRB_VM_SAFEPOINT_HOOK` のときだけ)。今までのグローバル変数 `mrb_vm_safepoint_hook`・`mrb_gc_root_hook` は無くした。mruby-checkpoint の `patches/0001`・`0004` も同じ形に (`wt/f6` の `834dc71`)。理由: 2 つの形を持つと、gem の C が 2 通りになり、試験も 2 通り要る。フィールドなら VM ごとに別で、ほかの VM の費用にならない。
- **要求の数**: gem は「要求を持つ VM の数」を静的な変数 (`npending`) で数え、hook はまずそれを見て早く戻っていた (F0 の 1.3。状態を毎回引くと Task のベンチマークで +11.7%)。hook が VM ごとになったので、**その VM に要求がある間だけ hook を置く** 形にし、数を無くした。要求の無い VM は切り替えで何も呼ばない (F0 の形より 1 回の呼び出しぶん少ない)。scheduler の切り替えの要求の数 (`patches/0002` の `switch_requests`・`switch_requests_async`) は元から `mrb_state` の `task` の中にある。
- GC の root の hook は、gem を使う VM (`checkpoint_new`) にだけ置き、VM が gem を手放すときに外す。
- gem の静的な変数はこれで 0 (もう 1 つ、送るメソッドの名前を並べる `qsort` の比較に状態を渡す静的なポインタがあった。複数の VM が同時に並べると取り違える。状態を渡す挿入の並べ替えにした、`eb0576e`)。
- ABI: フィールドなので `MRB_VM_SAFEPOINT_HOOK` は ABI の定義になった。rake の側 (各構成の `family_mruby_*.rb`) と CMake の側 (`mruby_abi_defines.cmake`、`hosted.cmake`) の両方に置く。

## 5. 実機の場面の試験 (`rake regress:checkpoint BOARD=`)

`tools/regress/checkpoint_board.rb` (前のサブが書き始めたもの)。`regress:boot` と同じく opt-in で、既定にも `regress:full` にも入らない (`REGRESS_BUILD_CACHE` がある、つまり `regress:full` の中では `BOARD` を見ない)。使い方は `doc/regression/usage.md` の 12 章。

- 実機のログは MCP の serial の capture の file から読む (ポートを開かないので実機をリセットしない)。
- 実機は開発の遠隔操作 (HTTP) で動かす。止める頼みは 2 章の `/app/checkpoint`・`/app/move`。
- 自前の Zenoh のルータを PC の全部のインターフェースで起こし (WSL2 は mirrored なので LAN から届く見込み)、実機の `/home/asterism` の `config.toml`・`receive.toml` を流すあいだだけ書き換え、終わったら元に戻して転送のアプリを起こし直す。
- 場面: board self (同じ端末で `restart: true`)、board in・out (ネイティブ版 ⇔ 実機)、board window (Window のアプリを実機へ移して戻す)、board calls (`missing` に `linux_settings`)、board requires (止める前に断る)、board no answer (誰もいないノード、実機で数え続ける)。
- 2026-11-06 に P4-Nano で全部通った (8 章)。最初に流したときに見つかって直したもの:
  1. `NODE_A` が解決できない (`BoardRounds` のメソッドから、`Runner` が include する `AsterismRounds` の定数は見えない。Ruby の定数は字句の範囲と自分の祖先で探す)。`AsterismRounds::NODE_A` を自分の定数に写した。
  2. `board_http(:get, path, path: x)` の `path:` がキーワード引数と取られる (`unknown keyword: :path`)。問い合わせの Hash を `{ }` で包んだ。
  3. `/app/launch` は path の `%2F` を戻さない (`/fs/*` は戻す)。`URI.encode_www_form` が `/` を `%2F` にするので起動できなかった。`/` をそのまま送る組み立てにした (英数字と `/._~-` だけの path は、戻すときも戻さないときも同じ)。
  4. 自前のルータの port 17461 に実機から届かない。WSL2 の mirrored は Hyper-V のファイアウォールが受けを port ごとに通し、この PC は Zenoh の 7447 だけを通してある。決まりの port を 7447 にし (`BOARD_ROUTER_PORT=` で変えられる)、7447 がふさがっている (sim の zenohd) ときは断って止まり、実機の転送のアプリが `cannot open a session` を出したら「ルータに届かない (ファイアウォール?)」と言って止まるようにした。
  5. app だけ焼いた実機は storage が古く、試験のアプリ (`ckpt_*`) と転送のアプリ (`/usr/share/transfer/`) が無かった。場面が実機で起こすアプリ 6 つ (`.toml` 込みで 12 file) を、実機のものが無いか違うときだけこの木の `flash/` から置き、終わったら戻す (無かったものは消し、作ったディレクトリも消す) ようにした。
  6. 開発の遠隔操作で起こした転送のアプリを、カーネルが自分のものと知らない (カーネルは自分で起こした PID しか見ない)。受ける側は動く (`restore` は PID を見ない) が、実機から送る (out) ときにカーネルが転送のアプリを起こそうとし、`single_instance` なので起こせず、移せない。下の「カーネルの直し」。
- カーネルの直し (`fmrb_kernel.rb` の `adopt_transfer`): 転送のアプリから `transfer_ready` が来て、カーネルが転送のアプリを持っていない (`@xfer_pid < 0`) とき、送り主の path が `/usr/share/transfer/transfer.app.rb` なら自分の転送のアプリとして引き取る (`Transfer app adopted (pid=n, started outside the kernel)`)。デバッグサーバや Shell から起こした場合も同じで、引き取らないと、その転送のアプリが動いているあいだ、その端末からの移動がすべて「転送のアプリを起こせない」で失敗する。プロトコルとアプリから見える動きは変わらない。
- 道具の口を 2 つ足した: `BOARD_ONLY=1` (`--board-only`、実機の場面だけ。ネイティブ版は相手として起こす) と `FMRB_ROOT=` (fmruby-core の worktree で流すとき、直下の道具を置いたディレクトリ。`tools/fmrb_native.rb` は自分の隣の `fmruby-core` を使うので、その `fmruby-core` がこの木であること。`screens/image.rb` の `fmrb_png` もここから読む)。

## 7. S3 の見込み (この段では作らない)

- flash: 表 約 210 KB (Ff の NARYAv3 の表) + gem 約 69 KB + 文言 約 14 KB + glue 約 22 KB で約 315 KB。NARYAv3 の app の領域の空きは約 1.67 MB なので収まる。
- 内蔵 RAM: P4 と同じ形なら +0 (gem の静的な変数は 0、`prebuilt_gems` は既に flash へ。S3 の DIRAM は今回の patch でむしろ減る、6 章の `regress:size`)。glue の静的な領域は PSRAM (S3 の PSRAM の空きは約 3.2 MB)。
- VM: S3 のアプリのプールは 500 KB。基準の常駐 90 KB に、作る間の一時的な量 約 173 KB (Ff の 32 bit の値) が重なり、VM を開くときに約 263 KB が要る。アプリが使える残りは約 237 KB に減る。大きいアプリは movable にできない見込み。一時的な量を減らす (名前の番号のハッシュ表を表の索引で置き換える) か、`movable` のアプリだけ大きいプールにする、のどちらかが要る見込み。
- P4 の実機の値 (8 章) を見てから改めて見積もる。

## 8. 実機で見たこと

- 起動する時間 (実機): 復元そのものは 54 ms (同じ端末、self)、88〜220 ms (ネイティブ版から来たもの。`restored ... in N us`)。ファイルを受けてから復元が済むまでは約 1.6 秒 (VM を開く約 1 秒が大半)。

## 10. サブの仮決め (ユーザが見直す)

1. hook のフィールドは実機だけでなく全ビルドで同じ形 (3 章)。
2. 要求の数は数えず、要求のある VM にだけ hook を置く (3 章)。
3. `prebuilt_gems` を const にして gem 1 つぶんの内蔵 RAM を相殺した (4 章)。picoruby-require の 2 つのファイルの丸ごとの写しなので、picoruby の submodule を動かしたら写し直す (`rakelib/setup.rake` のコメント)。
4. 実機で止める頼みの入口は開発の遠隔操作の HTTP (`FMRB_DEV_REMOTE_CTL`、無認証、リリースでは無い)。
5. 実機の場面は、実機の `/home/asterism` を流すあいだだけ書き換えて戻す。
6. カーネルは、外から起こされた転送のアプリを `transfer_ready` の時点で引き取る (5 章)。path で見分ける。引き取らずに「起こせない」と断る道もあるが、`single_instance` のアプリが 1 つ動いているのに移せない、を残すことになるので引き取る方にした。
7. 実機の場面のルータの port は 7447 (Zenoh の決まり。この PC のファイアウォールが通している port)。sim の zenohd と同時には流せない (断って止まる)。
8. 実機に無い・違う試験のアプリと転送のアプリは、流すあいだだけこの木の `flash/` から置いて戻す。storage を焼き直す (実機の `/home` が消える) よりこちらにした。
9. `/app/launch` が path の `%xx` を戻さないのは、ファームを直さず道具の側で合わせた (`/fs/*` とそろえるならファームの `launch_handler`・`move_handler` で `fs_url_decode` を通す。11 章)。

## 11. 残件・ユーザに頼むこと

- 実機の場面は通った (8 章)。`rake regress:boot BOARD=naryav4` は流していない (このファームを焼いた起動の crash の印 0 件・IRAM の空きは見た)。
- 実機の storage が古い (app だけ焼いてきたので、`/usr/share/transfer/` も試験のアプリも無い。`desktop.toml` ほかも違う)。転送のアプリが無いので、今の実機は Asterism でアプリを受けられない。`/home` を退避して storage を焼き直すか、要るものを置くかはユーザが決める。
- 基準の表と実機の VM の違い (`V:Asterism@@profile_icon` ほか 5 つ、8 章)。運ぶのには障らないが、表を作るときの VM に Asterism のクラス変数が無い理由は見ていない。
- `/app/launch`・`/app/move` の問い合わせの値は `%xx` を戻さない (10 章の 9)。
- 実機の画面 (HDMI) の目視: Window のアプリを実機へ移したときの Window と「移動中」の印 (`ckpt_window`。遠隔の画面の道具で撮れればそれで代える)。
- P4 の app の領域の空きが約 170 KB (2%)。表をさらに小さくする (C の関数の番地を表に、irep を名前の番号で) か、領域の割り当てを見直すかは、ユーザが決める。
- `lib/add/MRUBY_CHECKPOINT_PIN` は前のまま (`04a04d3`、Ff の前)。P4 のビルドはこの段の gem (`wt/f6`) でないと組めない (lib/patch の hook がフィールドになったので)。`wt/f6` を mruby-checkpoint の main に入れて pin を進めるまでは `MRUBY_CHECKPOINT_DIR` が要る。
- 標準のアプリに `movable = true` を付けるか (Ff の決まったこと: 実機の移動を確かめた後に決める)。
