# F2: ネイティブ版の 2 つのプロセスの間で、Window のないアプリを移す

> 状態: 検収済 | 更新: 2026-11-04 | 同じビルドのネイティブ版を 2 つ (A・B) 並べ、A のアプリを「書いて止めたまま (hold)」にし、イメージと横の `.toml` をデバッグサーバで分けて取り出し・分けて入れ (`file_get`、`file_begin` / `file_chunk` / `file_commit`)、B のカーネルが起動して「起動できた」を返してから A のカーネルがアプリを閉じる (D15)。B が断ったとき・返事が来ないときは A が止めた所から続ける。道具は `fmrb_native.rb app move PID --to <B の run dir>` と MCP の `native_app` の `move`。あわせて、Task が回り続けるアプリを閉じると毎回強制終了になっていた件を直した (アプリの終わりで Task も終える)。`rake regress:checkpoint` に移す場面を 3 つ足し、両方の構成で通る

計画は `doc/checkpoint/plan.md`、指示は `doc/checkpoint/instruction_f2.md`。F1 は `report/f1.md`、F1b は `report/f1b.md`。

## 1. 道筋

```
道具 (fmrb_native.rb app move PID --to <B>)
  A のデバッグサーバ: checkpoint {pid, hold: 10000}
    → A のカーネル: start_checkpoint。アプリへ {"cmd" => "checkpoint", "hold" => ms}
    → アプリの _spin → セーフポイントで書く (F1 のまま) → ckpt_written
       /tmp/<名前>.ckpt と .toml を書く → on_checkpoint → カーネルへ checkpoint_held {path}
       → hold_until_told: セーフポイントの中で止まったまま、カーネルの答えを待つ
    → A のカーネル: note_checkpoint_held。期限 (今 + hold) を覚える
    → 答え {status: held, path, size}
  A のデバッグサーバ: file_get {path, pos} を 3 KB ずつ (.ckpt と .toml)
  B のデバッグサーバ: file_begin {path, size} → file_chunk {id, pos, data} … → file_commit {id} (.toml、.ckpt の順)
  B のデバッグサーバ: restore {path}
    → B のカーネル: restore_checkpoint → _spawn_app_req(path) (.ckpt の起動は F1 のまま)
    → B のアプリのタスク: 復元できたら (続ける前に) 答えの表に DONE、できなければ REFUSED と理由
    → 答え {status: restored, pid} | {status: refused, reason} | {status: timeout}
  A のデバッグサーバ: checkpoint_finish {pid, close: B で起動できたか, reason}
    → A のカーネル: finish_checkpoint → アプリへ {"cmd" => "checkpoint_finish", "close", "reason"}
    → アプリ: close なら F1 と同じに閉じる (Task を全部終え、VM を普段どおり閉じて exit)
              続けるなら預かったメッセージを戻し、止めた所から続ける → カーネルへ checkpoint_continued
    → 答え {status: closed} | {status: continued, reason}
```

## 2. 移す段取り (D14・D15)

### 2.1 止めたままにする

- 止めるのは `ckpt_written` の中、つまりセーフポイントの中。アプリのタスク (OS のスレッド) がここで待つので、VM の Task もメインループも 1 歩も進まない。A で動き続けた分と B で続く分が食い違わない。
- 待ちはアプリのメッセージのキューを 50 ms ずつ読む。`checkpoint_finish` 以外のメッセージは 16 個まで預かり、続けるときに自分のキューへ送り直す (閉じるときは捨てる)。17 個目からは捨ててログに出す。
- 止めている間に kill が来たら (`should_exit`)、閉じる側に倒す。kill の待ち (1 秒) の間に普段どおり閉じる。
- 続けると、止めていた間の tick は自給の tick の勘定 (実時間) がまとめて数えるので、眠っていた Task は起きる時刻を過ぎていれば次の番で起きる。

### 2.2 返事と期限

| 誰が | 期限 | 過ぎたら |
|---|---|---|
| 道具 → A の `checkpoint` | `max` 8 秒 (書けるまで) | `timeout`。A は止めてもいない (のちに書けて止まったら、カーネルの期限で続ける) |
| A のカーネル | `hold` ms (既定 10 秒)。止まったと聞いた時から | アプリに `checkpoint_finish {close: false, reason: "no answer in N ms"}` |
| A のアプリ自身 | `hold` + 2 秒 | カーネルが答えないとき、自分で続ける (`the kernel did not answer`) |
| 道具 → B の `restore` | `max` 8 秒 (復元できるまで) | `timeout` → A に続けさせる |
| 道具 → A の `checkpoint_finish` | `max` 5 秒 | `timeout` (表の今の状態を答える) |

### 2.3 失敗のとき

- B が断った (復元できない、起動できない) / B に届かない / 運ぶ途中で道具が誤りを受けた: 道具は A に `close: false` と理由 (`not taken there: ...`) を送り、A は止めた所から続ける。答えは `{status: stayed, reason, here: continued}`。
- B では起動できたのに、A がもう期限で続けていた: 2 つ動いてしまうので、道具は B のアプリを kill し、`stayed` と理由を返す。
- 道具が途中で死んだ: A のカーネルの期限で A が続ける。B にイメージだけ残ることはある (`file_commit` の前なら `.part` のまま、名前には出ない)。
- A のカーネルは同時に 1 つの移動だけを持つ (F1 のまま)。

### 2.4 イメージをプロセスの外へ出す道

- デバッグサーバの命令にした (`file_get`、`file_begin` / `file_chunk` / `file_commit`)。ネイティブ版の `/tmp` はプロセスの中の tmpfs なので、外から触れるのはプロセスの中のコードだけ。
- 1 つのフレームは 4 KB までなので、データは 3 KB ずつ。受け口は `<path>.part` に書き、`file_commit` で大きさを確かめてから名前を付け替える。半端なファイルは起動されない。F5 ではこの 3 段 (`begin` / `chunk` / `commit`) を Asterism のサービスの裏に置き、wasm のアプリのインストールと共用にする (`fmrb_app.h` の受け口を呼ぶ)。
- 道は `/tmp/` の直下だけ (`..` と `/` を断る)。デバッグサーバは Linux では 127.0.0.1 だけで待つ。

### 2.5 着いた側の「起動できた」

- B の起動はカーネルがする (D14)。デバッグサーバ → カーネルに `restore {path}` → `_spawn_app_req`。答えはプロセスに 1 つの表 (`s_restore`) で、アプリのタスクが `mrb_checkpoint_restore` の後、続ける前に DONE を書く。読めない・復元できない・VM の準備ができないときは REFUSED と理由。spawner が起動できなかったとき (`fmrb_app_spawn_app` の誤り) も同じ表に書く。
- 道具の `app restore` もこの命令にした (前は spawn)。答えが `{status: restored, pid}` / `{status: refused, reason}` になる。

## 3. 強制終了の原因と直し (ユーザが足した項目)

- 症状: どの checkpoint の通しでも、`ckpt_counter` を止めると `No response in 1000ms, forcing termination` → `Dropping mruby VM (forced kill)` になっていた。最初は「復元したアプリだけ」に見えたが (F1 の通しで止めていたのが全部復元したものだった)、普通に起動した `ckpt_counter` を kill しても同じだった。
- 原因: mruby-task のスケジューラ (`mrb_task_run`) は、VM の Task が全部終わるまで戻らない。`FmrbApp#stop` → `main_loop` が戻る → `destroy` (exit の知らせ、`on_destroy`、`_cleanup`) まで進んでも、`Task.new` で作った無限ループの Task (`count_a`・`count_b`) は眠っては起きて回り続け、アプリのタスクは VM から出てこない。kill はアプリの片付けを 1 秒待ってから強制で落とす。`task_sleep` や `ckpt_self_refused` が普通に閉じていたのは、Task が自分で終わるか Task を持たないため。
- 直し: `FmrbApp#_cleanup` (C、`destroy` の最後) で、走っている Task (`destroy` を呼んだプログラム) 以外の Task を全部 `mrb_terminate_task` で終える。アプリはもう終わっていて (キューもキャンバスも消した後)、残った Task は動き続けても何もできない。終えれば `mrb_task_run` が戻り、普段の終わり方 (VM を `mrb_close`、片付け、exit) になる。`FmrbApp` を使わない素のスクリプト (Task だけを残して終わるもの) は `_cleanup` を通らないので、今までどおり Task が終わるまで動く。
- 確かめ: 直す前は `ckpt_counter` の kill が毎回強制終了 (直す前の F1b の通しのログで 1 構成 4 回)。直した後は `Task exiting normally` → `Exited on request` で、`rake regress:checkpoint` の両構成・A と B の両方のログで強制終了が 0 件 (道具が最後に数え、1 件でもあれば落ちる)。D15 の「普段の終わり方で閉じる」もこの形 (§2.1 の閉じ方は F1 の Task を全部終える形で、こちらも強制終了にならない)。
- 影響: ESP32 にも入る (`app.c` は全構成)。コードだけで静的な RAM は使わない (§5)。

## 4. 道具

```
# B を A の横に起こす (run dir・debug の port・利用者の場所を分ける)
ruby tools/fmrb_native.rb --run-dir /tmp/fmrb-native-b up --debug-port 5566 --user-dir <B の home>
# A のアプリ PID 5 を B へ
ruby tools/fmrb_native.rb app move 5 --to /tmp/fmrb-native-b [--hold MS]
#  → {"from_pid":5,"image":"/tmp/ckpt_counter.ckpt","held_ms":126,"bytes":23039,"carried_ms":1278,"done_ms":1395,"status":"moved","pid":5}
# 書いて止めるだけ / 止めたものを閉じる・続ける
ruby tools/fmrb_native.rb app checkpoint 5 --hold 3000
ruby tools/fmrb_native.rb app finish 5 close|continue [理由]
# /tmp/ のファイルを PC へ / PC から
ruby tools/fmrb_native.rb file get /tmp/ckpt_counter.ckpt out.ckpt
ruby tools/fmrb_native.rb file put out.ckpt /tmp/ckpt_counter.ckpt
```

- 2 つ並べるのに、プログラムの側は今の `--run-dir` (ソケット・pid・ログ) と `FMRB_DEBUG_TCP_PORT` で足りた。足りなかったのは道具の側: `app` などの命令がどの port を使うかを run dir ごとに覚えていなかった。`up --debug-port N` が run dir に `debug_port` を書き、ほかの命令と `move --to` がそれを読む (環境変数が先)。利用者の場所 (`/home`・`/etc`) は既定だと 2 つで同じ所になるので、B には `--user-dir` を渡す。
- 移す操作は 1 つの接続で何度も頼むので、Python の debug client の命令行ではなく、`fmrb_native.rb` に Ruby の小さな client (`DebugLink`、msgpack は `tools/fmrb_msgpack.rb`) を足した。ほかの `app` の命令は今までどおり Python の client。
- MCP: `native_app` に `action: "move"` (`pid`・`to`・`hold`) と、`checkpoint` に `hold`。description に B の起こし方を書いた。B は MCP の `native_up` では起こさない (shell の 1 行)。`selftest_native.rb` に引数の受け渡しを 2 つ足した。

`regress:checkpoint` の出力 (標準、移す場面のところ):

```
move: a 5->6, b 3->4, main 5->6, t step 403 ms, tick 200, 4046 names alike, carried in 1180 ms, held 1381 ms;
move refused: cannot restore /tmp/ckpt_counter.ckpt: restore failed: secti...; went on here: a 5->6, main 5->6;
move no answer: held 1517 ms, went on: a 5->6, main 5->6; 41s
```

- move: A の最後の 1 歩の次から B で続く (a・b・main)。A はイメージの後に 1 歩も数えていない。A は `Task exiting normally` で閉じる。A の書いたときの task tick と B の復元した task tick が同じ (200)。B の基準の名前が A と同じ 4,046 個で、名前と種類の digest も同じ (`32b7af76`)。
- move refused: `--damage` でイメージの最後の 16 バイトを落として運ぶ (道具の試験用の印)。B の gem が「section EMB0: 53 bytes of contents, only 41 left」で復元を断り、A は止めた所から続く (a・main がイメージの次の 1 歩から)。B にカウンタは残らない。
- move no answer: `app checkpoint --hold 1500` のあと誰も答えない。A のカーネルが 1,517 ms で続けさせ、止めていた間は 1 歩も数えず、次の 1 歩から続く。
- 強制終了: 両構成とも、A・B のログに 0 件。

## 6. 計測

| 何を | 値 |
|---|---|
| イメージ | 23,039 B (F1 と同じ) と `.toml` 164 B |
| 止めてから「止まった」の答えまで | 126〜128 ms (道具から見て。要求からイメージの書き終わりは 1 ms 前後) |
| 運ぶ (取り出し + 入れる + B の起動の答え) | 1.15〜1.2 s |
| 止めていた時間 (A のログ) | 1,309〜1,311 ms |
| B の復元 | 341 µs |
| `t=` の段差 (a の 1 歩をまたいで) | 402〜403 ms (1 歩は 200 ms の sleep が本体の 250 ms の待ちの後ろに並ぶ分。F1 の restart と同じ程度) |
| 基準の常駐の費用 | 355,200 B (名前 4,046 個)。F1b の 355,216 B から動いていない (16 B の差は割り当ての端数) |

- 運ぶ時間の大半はデバッグサーバの往復の数 (取り出し 9 回、入れる 13 回)。ネイティブ版は協調のスケジューラなので、デバッグサーバは socket を待たずに見て、無ければ 50 ms 眠る。1 回の往復が最大 50 ms 待つ。1 回に 3 KB しか運べない (フレームが 4 KB) ことと合わせて 1 秒ほどになる。F5 では Asterism の道に変わるので、ここは詰めていない。
- D9 (別のプロセスでの `board_millis`): ネイティブ版の端末の時計はホストの単調な時計で、2 つのプロセスで同じ値になる。B のずれは移るのにかかった時間 (−1,218 ms など) で、`t=` は書いたときから続く。違う時計の端末どうしでも、`EMB0` が書いたときの値を運ぶので同じに効く (F1 の wait で 2 秒の空きを確かめてある)。
- mruby-task の tick: gem が運ぶ値が B でそのまま続く (書いたとき 200、復元後 200)。ログに出すようにした (`image at task tick N`、`restored ... task tick N`)。

## 7. 気づき

- 強制終了は checkpoint と関係なく、Task を回し続けるアプリならどれでも起きていた (§3)。今までの試験のアプリは Task が自分で終わる形だったので、見えていなかった。
- B が復元を断ったとき、B では普通のアプリの起動の失敗と同じに、カーネルへ例外が報告される (デスクトップに出る形)。断りとしては分かりやすいが、移す側の都合の失敗を B の利用者に見せるかは F5 で考える。
- `checkpoint_finish` の理由は、カーネルからアプリへのメッセージ (176 B) に収まる長さで切れる。ログには切れた形で出る。

## 8. サブの仮決め (ユーザが見直す)

1. 止めたままにする場所は `ckpt_written` (セーフポイント) の中で、アプリのタスクごと待つ形。止めている間に来たメッセージは 16 個まで預かって、続けるときに戻す。
2. 期限は、カーネルが `hold` (既定 10 秒、道具の `--hold`)、アプリ自身が `hold` + 2 秒。B の `restore` を待つのは 8 秒。
3. 止めている間の kill は「閉じる」に倒す。
4. 閉じ方は F1 と同じ (Task を全部終えて VM を普段どおり閉じる)。`on_destroy` は呼ばない (F1 の仮決め 3 のまま。アプリは壊れたのでなく移ったので)。
5. B では起動できたのに A が期限で続けていたときは、道具が B のアプリを kill する (2 つにしない)。
6. イメージを出し入れする道はデバッグサーバの命令 (`file_get`、`file_begin` / `file_chunk` / `file_commit`) にした。道は `/tmp/` の直下だけ。受け口 (`fmrb_app_transfer_*`) は F5 の Asterism のサービスから呼べるように `fmrb_app.h` に置いた。今は gem を持つビルドだけ。
7. 運ぶのは `.ckpt` と横の `.toml` の 2 つ (`.toml` が先)。B のイメージの名前は A と同じ `/tmp/<名前>.ckpt`。
8. B の起動は B のカーネルが (`restore` の命令 → `_spawn_app_req`)。「起動できた」は復元が済んで続ける前 (`on_restore` の前)。
9. 道具の `app restore` を、spawn から新しい `restore` の命令に替えた (答えが `{status, pid | reason}` になる)。
10. B が断る場面の試験は、道具の印 `--damage` (イメージを短く切って運ぶ) で作った。
11. 強制終了の直しは `FmrbApp#_cleanup` で残った Task を終える形。`FmrbApp` を使わない素のスクリプトは今のまま。
12. 名前が同じに引けることは、復元が通ることに加えて、基準の名前の数と digest (FNV-1a) をログに出して比べる形にした。

## 9. 決めてほしいこと (ユーザ)

1. 止めた側を閉じるときに `on_destroy` を呼ぶか (今は F1 と同じく呼ばない。D15 の「普段の終わり方」を、強制終了でない普段の VM の閉じ方と読んだ)。呼ぶなら、`on_destroy` が A の側で何かを消す・保存するアプリで、B に移った状態と食い違わないかを考える必要がある。
2. B が復元を断ったとき、B のデスクトップに失敗を出すか (今は出る)。
3. 移す既定の `hold` (10 秒) と、運ぶ速さ (今は 23 KB に 1.2 秒。F5 で Asterism に替わるまでこのままでよいか)。

## 10. F3 に要るもの

- Window のあるアプリは、今はセーフポイントで `FmrbGfx` を運べずに断られる (F1 のまま)。C のデータの書き出し・戻しを gem ごとに登録する口 (D7) と、キャンバスを開き直す情報 (D8) が要る。
- 移す場面の試験は、A・B の 2 つのプログラムを並べる形がそのまま使える (`regress:checkpoint` の B)。Window のあるアプリなら、B の画面の確かめ (`fmrb_native.rb shot`) を足す。
- 止めたままにしている間、A の Window は描かれないまま残る。閉じるまで A の画面に何を出すか (止まった印など) を決める。
