# F4: ビルドの違う端末の間で運ぶ (sim ⇔ ネイティブ版、ブラウザ版 ⇔ ネイティブ版)

> 状態: 実装済・検収待ち | 更新: 2026-11-04 | F4a: sim (ESP-IDF の Linux ビルド、tick は別のタスク) とネイティブ版 (tick は VM が自分で) の間で、窓のないアプリ・窓のあるアプリを両向きに移せるようにした。道は F2 のデバッグサーバの命令そのまま (sim の debug サーバは 5555、道具は `app move --to 5555`)。画面の大きさが違うとき (Retro 320 幅 ⇔ Modern 426 幅) は spawner が窓を画面に収め、基底クラスが利用の範囲を作り直して `on_restore` の前に `on_resize` を呼ぶ。`rake regress:checkpoint` に sim の場面を 8 つ (Retro・Modern、標準と全部 mruby) 足した。F4b: ブラウザ版に gem を入れる形を「測るための別のビルド」(`FMRB_WASM_CHECKPOINT=1`) として作り、wasm が +128 KB (+2.1%)、起動の時間は差なしを測った。32 bit ⇔ 64 bit で両向きに移せた。公開のビルドに入れるかは止まってユーザに聞く

計画は `doc/checkpoint/plan.md`、指示は `doc/checkpoint/instruction_f4.md`。F3 は `report/f3.md`。
mruby-checkpoint の gem には手を入れていない。

## 1. permanent の名前の差

3 つのビルドで、`movable` なアプリ (`ckpt_counter`) の VM が基準を取った直後の名前を全部書き出して比べた。
書き出しは開発用の印で行う: `/tmp/ckpt_names` があると、checkpoint を開いた VM が `/tmp/<アプリ>.names` に
名前を 1 行ずつ書く (`fmrb_app_checkpoint.c` の `dump_names`。gem を持つビルドだけ、印が無ければ開くのに
失敗する 1 回だけ)。

| ビルド | 名前の数 | 片方にしか無いもの |
|---|---|---|
| ネイティブ版 (64 bit) | 4,056 | sim に対して: `FmrbApp` の特異メソッド 6 つ (`linux_keyboard`・`linux_settings`・`settings_page`・`wl_close`・`wl_key`・`wl_window`。ネイティブ版だけの C の関数) |
| sim (64 bit) | 4,050 | なし (ネイティブ版の部分集合) |
| ブラウザ版 (gem 入り、32 bit) | 3,563 | ネイティブ版に対して: `FmrbNet#_fetch_*` 6 つ (ブラウザの fetch) |
| ネイティブ版にあってブラウザ版に無い | 499 | `Net` (290)、`MbedTLS` (63)、`SSLSocket`・`UDPSocket`・`TCPSocket`・`BasicSocket`・`TCPServer`・`SSLContext`・`SocketError`、`URI`、`Base64`、`EOFError`、`Array#pack`・`String#unpack`/`unpack1`、`FmrbApp` の 6 つ |

(F3 の時点の 4,054 からネイティブ版が 2 つ増えたのは、この段で足した `FmrbApp#_layout_user_area` と `FmrbGfx#_canvas_size`。)

- 差のもと: sim とネイティブ版は gem の並びが同じ (`family_mruby_linux.rb` と `family_mruby_native.rb`)。違いはネイティブ版だけの C の関数 (Linux の窓・設定)。ブラウザ版は通信の gem (`picoruby-socket`・`net-http`・`net-websocket`) を持たず、それが引き込む `mbedtls`・`base64`・`pack`・`mruby-pack` も無い。
- 名前の引き当ては、イメージが**参照している** permanent のものだけを引く (gem の形式 §8)。試験のアプリと標準の小さなアプリ (カウンタ・窓・pub/sub の見本) はどれも差の中の名前を参照しないので、どの組み合わせでも移せた (§4・§5)。
- 参照していれば、着いた側の gem が理由つきで断る (黙って違うものに結ばない)。確かめた: `@k = TCPSocket` を持つアプリをネイティブ版からブラウザ版へ → `restore failed: permanent object 'TCPSocket' not found in this build` で起動しない。
- **名前の表では捕まえられない差がある**。メソッドの呼び出しはシンボルで、イメージに名前としては入らない。`[65].pack("C")` を毎回呼ぶアプリをネイティブ版からブラウザ版へ移すと、復元は通り、次の `on_update` で `undefined method 'pack' for Array (NoMethodError)` でアプリが終わった。名前の表は「持っているオブジェクト」の差を見るだけで、「呼ぶメソッド」の差は見ない。

根本から直す方法の比較 (決めてほしいこと 2):

| 案 | 中身 | 費用 | 見立て |
|---|---|---|---|
| (a) gem の並びを揃える | ブラウザ版に `mruby-pack`・`picoruby-base64` などソケットに依らないものを入れる | wasm が少し増える。ソケットはブラウザに無いので揃えられない | 足りないものは減るが、残る (通信の gem)。ほかの端末 (S3 の gembox) でも同じ問題が出る |
| (b) 書く側が「呼んだメソッド名」を書き、着いた側が確かめる | gem がアプリの irep の送り先のシンボル (`OP_SEND` など) のうち、書いた側で permanent のメソッドだったものを並べてイメージに入れ、着いた側にどのクラスにもその名前のメソッドが無ければ理由つきで断る | gem の変更 (新しいセクション)。イメージが数百 B 増える。動的な `send` は捕まらない | 一番根本に近い。誤り (名前が同じで別のクラスのメソッド) はあるが、断るべきものの大半を捕まえる |
| (c) 今のまま | 走ってから `NoMethodError` | なし | 端末の機能の違いと同じ扱い。黙って違うものに結ぶことはない (例外になる) |

## 2. sim に入れる (F4a)

### 2.1 時分割

- sim は tick を別の FreeRTOS のタスクが進める (`task_hal.c` の上半分)。F0 でこの道の切り替えの要求も数えるようにしてある (`vm_deliver_switch` が `switch_requests_async` を進めてから `switching` を立てる)。sim の上で F1 (起動し直し)・F2 (止めたまま、誰も答えないと続く)・F3 (窓の起動し直し) の場面を流し、どれも通った (§6)。直しは要らなかった。
- 運ぶ tick の状態 (D10、`EMB0`) は、sim では「別のタスクが数えたがまだ VM に渡していない tick」(`pending`) が大きいことがある (メインループが `_spin` の中で待っている間に溜まる。測ったときは 38)。ネイティブ版はそれを着いた最初のスケジューラの回で数える。どちらの側でも、書いたときの `task tick` から続く (sim → ネイティブ版、ネイティブ版 → sim の両方で書いたときと復元したときの task tick が同じ)。
- `board_millis` (D9): sim とネイティブ版は同じホストの単調な時計を読むので、ずれは運んだ時間だけ (−934 ms など)。ブラウザ版は時計が違い、ずれは ±1.79e12 ms になったが、`t=` は書いたときから続いた (§5)。

### 2.2 イメージの出し入れの道

- sim のデバッグサーバ (TCP 5555、`docker-compose.yml` で外に出してある) は F2 の命令 (`checkpoint`・`checkpoint_finish`・`restore`・`file_get`・`file_begin` / `file_chunk` / `file_commit`) をそのまま持つ (`FMRB_HAVE_CHECKPOINT` は sim も持つ)。sim の `/tmp` もプロセスの中の tmpfs で、外からはこの命令で触る。
- 道具は `tools/fmrb_native.rb app move PID --to RUN_DIR|PORT` にした。`--to` に数だけを渡すとその port のデバッグサーバ (sim は 5555) へ移す。sim から移すときは `FMRB_DEBUG_TCP_PORT=5555 ruby tools/fmrb_native.rb app move PID --to <ネイティブ版の run dir>`。MCP の `native_app` の `to` も port を受ける (description に書いた)。
- 運ぶ時間 (道具から見て、取り出し + 入れる + 起動の答え): sim → ネイティブ版 0.8〜1.0 s、ネイティブ版 → sim 1.1〜1.2 s (23 KB)。F2 と同じく往復の数で決まる。

## 3. 画面の違い

### 3.1 窓の大きさ

| 場合 | 着いた側 | 扱い |
|---|---|---|
| 窓が着いた側の画面に収まる (Retro ⇔ Modern の `ckpt_window` 160x90) | 同じ位置・大きさ | 何もしない (F3 のまま) |
| 窓が着いた側の画面より大きい・はみ出す (Modern の 380 幅の窓 → Retro 320 幅) | spawner が画面に収める: 幅・高さを全画面の大きさまで縮め、はみ出す分を左上へ寄せる (最小の大きさも画面に合わせる) | 基底クラスが新しい大きさで利用の範囲を作り直し、`on_resize` を呼んでから `on_restore` |
| 全画面のアプリ (Retro 320x240 ⇔ Modern 426x240) | spawner が着いた側の全画面の大きさで作る (普通の起動と同じ) | 同じ |

- 収める処理は spawner の `.ckpt` の起動のときだけ (`FMRB_HAVE_CHECKPOINT` の中)。普通の起動の窓の扱いは変えていない。ログに `The image's window 380x100 at 30,60 is made to fit this screen (320x240): 320x100 at 0,60` と出る。
- 基底クラス (`FmrbApp#_checkpoint_restored`): `_checkpoint_canvases` (C) が文脈の大きさ・全画面かを `@window_width` / `@window_height` / `@_fullscreen` に書き、イメージの中の値と比べる。違えば `_layout_user_area` (初期化と同じ分け方。`initialize` もこれを使うようにした) で利用の範囲を作り直し、窓と壁紙の `FmrbGfx` の大きさ (`:center` が測るもの) を `_canvas_size` で直し、枠・角丸・スプライトの範囲は新しい大きさで (F3 のまま) 作り、`on_resize(w, h)` → `on_restore` → `present`。
- `on_resize` を先にしたのは、窓の大きさを変えたとき (カーネルの `resize`) と同じ順にするため。アプリは `on_resize` で配置を計算し直し、`on_restore` で描く。`sig/fmrb_app.rbs` の `on_restore` に書いた。
- 試験: `ckpt_wide` (窓 380x100) をネイティブ版から Retro の sim へ → `window=320x100 user=1,11,318x88 at 0,60`、`on_resize 320x100` が 1 回、利用の範囲の四隅の赤い四角が新しい位置にある。Modern の sim へは大きさが変わらず `on_resize` は来ない。`ckpt_full` を Retro の sim からネイティブ版へ → 320x240 から 426x240、`on_resize` が 1 回。

### 3.2 フォント

- `FmrbGfx#set_font` はもともと着いた側の表 (`FONT_AVAILABLE`、`FmrbConst::HW_FAMILY` と `FONT_JA`) で選び直し、選んだ値を `@current_font` に入れる。基底クラスは結び直した後に `set_font(*current_font)` を送り直すので、`@current_font` は着いた側で選び直した値に揃う (F3 のまま、直しは要らなかった)。
- sim (Retro・Modern)・ネイティブ版・ブラウザ版はどれも `FONT_JA=1` で、Retro と Modern の表も同じ。この 3 つの間ではフォントは変わらない。違いが出るのは `FONT_JA=0` の端末 (AtomS3R・StickS3、misaki 8 だけ) で、F6 の話。そこへ移ると `[:ja, 12]` が `[:ja, 8]` になり、戻しても 12 には戻らない (頼んだ値を覚えていない)。サブの仮決め 6。

## 4. ブラウザ版 (F4b)

### 4.1 入れ方 (公開のビルドには入れていない)

- `FMRB_WASM_CHECKPOINT=1 rake wasm:mruby wasm:web` (または `wasm:dist`) で、gem 入りの別のビルドを作れるようにした。libmruby は別の名前 (`family-mruby-wasm-ckpt`)、ファームは `wasm/build-ckpt/` に作るので、`wasm/build/` (人が開いているページが読むもの) と公開の `wasm:dist` / `wasm:site` / `wasm:deploy` は変わらない。`wasm:site` と `wasm:deploy` はこの印があると断る。
- 中身はネイティブ版と同じ: `MRB_VM_SAFEPOINT_HOOK` と `FMRB_HAVE_CHECKPOINT` (gem より前に、build 全体へ)、gem、CMake の側で `fmrb_app_checkpoint.c` の define と gem のヘッダ (`wasm/CMakeLists.txt` の `FMRB_WASM_CHECKPOINT`)。
- 比べるための同じコミットのビルドは `FMRB_WASM_BUILD_DIR=wasm/build-f4base` で作った (この変数も足した。ファームの build の場所を移すだけ)。

### 4.2 計測 (同じコミット、Release、`wasm:dist`)

| 何を | 今のビルド | gem 入り | 差 |
|---|---|---|---|
| `core_web.wasm` | 6,170,958 B | 6,299,037 B | +128,079 B (+2.1%) |
| 同 gzip -9 | 2,609,571 B | 2,656,705 B | +47,134 B (+1.8%) |
| `core_web.js` | 178,045 B | 178,484 B | +439 B |
| `core_web.data` | 4,219,043 B | 4,219,043 B | 0 |
| dist 全体 | 10.21 MB | 10.33 MB | +0.12 MB |
| 起動 (ヘッドレスの Chromium、localhost、`?autostart=1`、load からデスクトップの `Boot complete` まで、3 回ずつ交互) | 4,818 / 5,560 / 4,791 ms | 4,759 / 4,772 / 4,796 ms | 差なし (揺れの中) |
| movable なアプリの基準 (32 bit、1 VM) | — | 321,184 B (名前 3,563 個) | ネイティブ版 64 bit は 355,960 B |

- 起動の時間は localhost なので、ネットワークの分 (gzip で +47 KB) は入っていない。遅い回線ではその分だけ伸びる。
- 普段 (movable でないアプリ) の費用はセーフポイントの hook の判定だけで、gem の基準は movable なアプリと復元する VM だけが取る (D12)。

### 4.3 止める・続ける・出し入れ (手で確かめた)

ブラウザ版は自分の port のヘッドレスの Chromium (Playwright) と、自分の port の開発サーバ (`FMRB_WASM_CHECKPOINT=1 DIST=1 PORT=8037 rake wasm:serve`) で動かし、`tools/fmrb_web.rb --port 8037` の命令 (入力・`get`・`put`) で操作した。人が開いている 8016 のページと、その道具の状態ファイル (`wasm/build/drive_browser.pid`) には触っていない。

| 向き | 段取り | 結果 |
|---|---|---|
| ネイティブ版 → ブラウザ版 | ネイティブ版で `app checkpoint` (閉じる) → `file get` で `.ckpt`・`.toml` → ブラウザ版の `/home` に `put` → Shell で `run /home/ckpt_counter.ckpt` | 32 bit で復元できた (3,000 µs)。main 13→14、a 13→14、`t=` 3196→3197 から続く |
| ブラウザ版 → ネイティブ版 | Shell で `run /app/test/ckpt_counter.app.rb`、`checkpoint <pid>` → `cp /tmp/ckpt_counter.ckpt /home/` (と `.toml`) → `get` → ネイティブ版に `file put` → `app restore` | 64 bit で復元できた (326 µs)。main 3→4、a 2→3、`t=` 3804→4054 |
| 名前の差で断る | `@k = TCPSocket` を持つアプリをネイティブ版からブラウザ版へ | `permanent object 'TCPSocket' not found in this build` で起動しない (頼んだ者がいない起動なので、F2 の決まりどおり失敗の窓が出る) |

- イメージの大きさは 32 bit と 64 bit で同じ (カウンタ 23,039 B)。形式がポインタの幅に依らない (gem の形式 §1)。
- 出し入れの道: ブラウザ版にはデバッグサーバが無い。ページの `fs` の命令 (`fmrb_web.rb get/put`) が触れるのは Emscripten の MEMFS (`/flash/home` など) で、端末の `/tmp` はファームの中の tmpfs (`fmrb_tmpfs`) なので外から見えない。今回は Shell の `cp` で `/home` を経由した。本当の道は F5 (Asterism の `begin` / `chunk` / `commit`、D13) で、ブラウザ版のアプリのインストールと共用にする受け口がそのまま `/tmp` に書く。
- ブラウザ版の時分割 (VM が自分で tick を進める) はネイティブ版と同じ道 (`MRB_TASK_TICK_SELF_SUPPLY`) なので、止める・続けるに違いは無かった。
- ヘッドレスの Chromium で、ときどき機械全体が数秒止まる (`task_sleep` の 100 ms の待ちが 1.9 s になる)。gem の有無に関係なく、同じ手順で今のビルドにも gem 入りにも出た (出る回と出ない回がある)。checkpoint とは関係しないので、記録だけする。

### 4.4 試験に入れていないもの

ブラウザ版 ⇔ ネイティブ版の場面は `rake regress:checkpoint` に入れていない。公開のビルドに gem を入れるかがユーザの判断待ちで (止まる条件)、入れない間は場面が `FMRB_WASM_CHECKPOINT=1` の別のビルドを作ること (emsdk、10 分ほど) になる。入れると決まったら、`regress:screens` の web の道具 (自分の port の開発サーバとヘッドレスのブラウザ) の上に、Shell の `run` / `checkpoint` と `fs` の道で場面を足す。

## 5. 試験

### 5.1 `rake regress:checkpoint` の sim の場面

`tools/regress/checkpoint_sim.rb` (checkpoint.rb の Runner に入る)。usage.md 12 章。

| 場面 | 確かめること |
|---|---|
| sim restart | sim の中で F1: カウンタが書いたときの次の 1 歩から続く |
| sim hold | sim の中で F2 の止めたまま誰も答えない形: 止めている間は数えず、1.5 秒で続く |
| sim window | sim の中で F3: 窓が画素で同じ |
| to native / to sim | カウンタを両向きに。数が続き、task tick が同じ。元の側は普段どおり閉じる |
| window | `ckpt_window` を sim からネイティブ版へ。窓が RGB332 で同じ (角の 4 画素を除く)、クリックとキーが届く |
| wide | `ckpt_wide` をネイティブ版から sim へ。Retro で収まり `on_resize`、Modern でそのまま |
| full | `ckpt_full` を sim からネイティブ版へ。Retro からは `on_resize`、Modern からはそのまま |

- 画面の比べ方: sim (`fmrb_screenshot.py`) とネイティブ版 (`fmrb_native.rb shot`) では RGB332 から 24 bit への広げ方が違う (例: 218,36,85 と 222,36,82)。どちらも元は RGB332 なので、上位のビット (R 3・G 3・B 2) に戻して比べる。違いが残ったのは窓の四隅の 2 画素ずつ (角丸の外に見える壁紙) だけだったので、角の 3x3 を除いた。
- sim は 3 つのコンテナを使う。始める前に sim が動いていたら (人のもの) 作る前に断り、build/ は `build_tree.rb` で借りて返す (`regress:run` と同じ)。`regress:full` の中では順に流れるので、`regress:run`・`regress:screens` と重ならない。

## 7. 気づき

- sim とネイティブ版は gem の並びが同じなので、名前の差はネイティブ版だけの C の関数 6 つ。どちらの向きにも、試験のアプリは何もせずに移せた。違うのは時分割・画面・時計で、どれも F1〜F3 の作り (EMB0 の tick の状態、`.toml`、`board_millis` のずれ) で吸収できた。
- 窓の大きさの違いは、窓の大きさを変えたとき (`resize`) と同じ形 (`on_resize`) にすると、アプリ側に新しい約束が要らない。`on_update` で毎回描くアプリは何もしなくてよく、何かあったときだけ描くアプリも `on_resize` と `on_restore` で足りる。
- ブラウザ版の 32 bit ⇔ ネイティブ版の 64 bit は、gem の原理検証どおり、Family mruby の上でも何もせずに通った。
- 名前の表の確かめは「持っているもの」の差だけを見る。呼ぶメソッドの差は走ってから `NoMethodError` になる (§1)。端末が増えるほど (S3・ブラウザ版の gembox の違い) 効いてくる。

## 8. サブの仮決め (ユーザが見直す)

1. 名前の書き出しは開発用の印 (`/tmp/ckpt_names` があるときだけ `/tmp/<アプリ>.names`)。gem を持つビルドだけ。
2. 画面に収まらない窓は spawner が `.ckpt` の起動のときだけ収める (大きさを先に縮め、次に位置を寄せる)。普通の起動は変えない。
3. 大きさが変わったら `on_resize` → `on_restore` の順。変わらなければ `on_resize` は呼ばない。
4. sim との間の道具は `app move --to PORT` (sim へ) と `FMRB_DEBUG_TCP_PORT=5555` (sim から)。新しい道具は作らず、`fmrb_native.rb` を広げた。
5. `regress:checkpoint` は既定で sim の場面も流す (構成 2 つ × 系列 2 つ、sim を 4 回作る)。`SIM=none` で外せる。
6. フォントは頼んだ値を覚えない (着いた側で選び直した値を `@current_font` に持つだけ)。`FONT_JA=0` の端末を通ると戻らない。F6 で要るなら `FmrbGfx` に頼んだ値を持たせる。
7. ブラウザ版の gem は公開のビルドに入れず、`FMRB_WASM_CHECKPOINT=1` の別のビルド (別の libmruby の名前・別の build の場所、公開の道具は断る) にした。
8. ブラウザ版 ⇔ ネイティブ版の場面は、公開のビルドの判断が出るまで `regress:checkpoint` に入れない。

## 9. 決めてほしいこと (ユーザ)

1. **ブラウザ版の公開のビルドに gem を入れるか** (止まった点)。wasm +128 KB (+2.1%、gzip で +47 KB)、起動の時間は localhost で差なし。入れると F5 でブラウザ版 ⇔ ネイティブ版を Asterism で運べる。入れなければ、ブラウザ版は運ぶ相手にならない (`FMRB_WASM_CHECKPOINT=1` の別のビルドは残る)。
2. **呼ぶメソッドの差** (§1): (a) ブラウザ版の gem の並びを揃える (ソケットに依らないもの)、(b) gem がイメージに「呼んだ permanent のメソッド名」を入れ、着いた側が確かめて断る、(c) 今のまま (走ってから `NoMethodError`)。
3. `regress:checkpoint` に sim の場面を既定で入れてよいか (ネイティブ版だけなら 2 分ほど (作り終えていれば) → sim を含めて 12.1 分。`regress:full` も 10 分ほど延びる)。`SIM=none` で外せる。

## 10. F5 に要るもの

- ブラウザ版の出し入れの道が無い (デバッグサーバが無く、ページの `fs` は `/tmp` に届かない)。F5 の受け口 (`begin` / `chunk` / `commit`) がそのまま道になる。ブラウザ版から送り出す側 (止めたままにして送る) も Asterism の上に要る。
- ビルドの違う相手へ送る前に、相手の名前の表と合うかを聞けると、送ってから断られるより早い (名前の数と digest を交換する、§1 の (b) をするなら呼ぶメソッドも)。
- 時計が違う端末どうし (ブラウザ版とネイティブ版で ±1.79e12 ms) でも `board_millis` は続いた。F5 でも EMB0 のままでよい。
