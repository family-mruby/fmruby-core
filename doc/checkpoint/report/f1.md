# F1: ネイティブ版の 1 プロセスの中で、Window のないアプリを止めて同じ所で続ける

> 状態: 検収済 | 更新: 2026-11-03 | 申告したアプリ (`movable = true`) だけ VM に checkpoint を開いて基準を取り、デバッグサーバ → カーネル → アプリの `_spin` の順に頼んで、`_spin` の外のセーフポイントで `/tmp/<名前>.ckpt` に書き出して閉じ、カーネルがイメージから起動し直して続ける。`board_millis` のずれ (D9) と HAL のタイムスライスの数 (D10) は gem の埋め込む側のセクション (`EMB0`) で運び、書き出しの作業の領域はプールの外 (D11)。標準 (Spinel のカーネル) と全部 mruby の両方のネイティブ版で `rake regress:checkpoint` が通る。基準の常駐の費用が 1 VM あたり約 1 MB (64 bit) と大きいことが分かった

計画は `doc/checkpoint/plan.md`、指示は `doc/checkpoint/instruction_f1.md`。段と決定 D1-D16 は mruby-checkpoint の
`doc/plan.md`、隔たりの調査は同 `doc/survey_family_mruby.md` (以下「調査」)。

## 1. 作ったもの

### 1.1 道筋

```
道具 (デバッグサーバの checkpoint {pid, restart})
  → fmrb_app_checkpoint_ask: カーネルへ APP_CONTROL {"cmd" => "checkpoint", "pid", "restart"}
  → カーネル (Ruby): request_checkpoint。アプリへ {"cmd" => "checkpoint"}
  → アプリの _spin (C): fmrb_app_checkpoint_request → mrb_checkpoint_request、@_spin_break で待ちを抜ける
  → _spin が main_loop に戻った直後の命令の境目 (セーフポイント) で gem がイメージを作る
  → ckpt_written: /tmp/<名前>.ckpt と /tmp/<名前>.toml を書く → on_checkpoint → VM の Task を全部終える
    → カーネルへ checkpoint_done {path}。アプリのタスクは普段どおり VM を閉じ、exit を送る
  → カーネル: exit で restart_from_checkpoint。restart なら _spawn_app_req("/tmp/<名前>.ckpt")
  → spawner: .ckpt を見分けて FMRB_LOAD_MODE_CHECKPOINT。横の .toml を普段どおり読む
  → アプリのタスク: VM を開く → checkpoint を開き基準を取る → イメージを読んで mrb_checkpoint_restore
    → EMB0 で時計と HAL の数を戻す → on_restore → mrb_checkpoint_continue (止まった所から)
```

### 1.2 申告と準備 (D6・D12)

- 印は `.app.toml` の `movable = true` (`1` でもよい。`single_instance` と同じ書き方)。spawner が読み、mruby のアプリだけ文脈の `movable` を立てる。
- `create_vm_mruby` の直後、プログラムを読む前に、申告したアプリと `.ckpt` の起動だけ: `mrb_checkpoint_open`、作業の領域のアロケータ、`EMB0`、handler、断りの handler、最後に `mrb_checkpoint_baseline`。印の無い VM は何もしない (費用は F0 のまま 16 バイト)。
- ソース (P6): 申告したアプリのソースは、コンパイルの前に `mrb_checkpoint_add_source` で登録する (ファイル名はコンパイラに渡す名前と同じ `ctx->filepath`)。flash のバイトコードは対象外。復元した側は gem が登録し直す。イメージにソースを入れるかの既定 (`mrb_checkpoint_set_include_source`) は gem の既定 (入れない) のまま。

### 1.3 止める (D5)

- 入口はデバッグサーバの命令 `checkpoint`。ネイティブ版なら `python3 tool/debug/fmrb_dbg_client.py --json localhost:5565 checkpoint pid=<pid> restart=1`。デバッグサーバはカーネルに頼み (`fmrb_app_checkpoint_ask`)、アプリの答え (C の表) を最大 `max` ms (既定 5 秒) 待って返す。Spinel など mruby 以外のアプリは、頼む前に断る (D16)。
- カーネル (Ruby) は頼みを受けて、アプリに `checkpoint` を送る。同時には 1 つ。
- アプリの `_spin` は、印が無ければ断る (理由を返して動き続ける)。印があれば、アプリのオブジェクトを VM のグローバル変数 (`_fmrb_checkpoint_app_`、Ruby からは綴れない名前) に置いて `mrb_checkpoint_request` を呼び、待ちを抜ける (`@_spin_break`)。グローバル変数はイメージに入るので、復元した側もアプリのオブジェクトを見つけられる。
- イメージが書かれるのは、`_spin` が戻った直後の命令の境目。`_spin` の後の Ruby (`_run_timers` など) は書き出し側では動かない。要求の時点で C の境目の中 (C から呼ばれたブロックの中で `_spin` している) なら gem が断り、その理由を返す。書き出しの時点で運べない値 (C のデータの登録の無い型) があれば、gem の断りの handler が理由を返し、アプリは動き続ける (Window のあるアプリの `FmrbGfx` で確かめた。§2.1)。
- 書けたら (`ckpt_written`、セーフポイントの中):
  - `/tmp/<名前>.ckpt` と、起動の属性の `/tmp/<名前>.toml` (`app_screen_name`・`movable = true`・`large_memory`・Window の形。文脈から作る) を書く。書けなければ断って続ける。`<名前>` は最初にコンパイルした `.rb` のファイル名の最初の `.` まで。
  - アプリの `on_checkpoint` (あれば。例外は記録して捨てる)。
  - `expected_stop` を立て、VM の Task を全部終える (`mrb_terminate_task`)。走っている Task はセーフポイントの終わりで止まり、スケジューラが空になって `mrb_task_run` が戻る。あとはアプリのタスクが普段どおり VM を閉じ、カーネルに `exit` を送る。
  - カーネルに `checkpoint_done {path}`。

### 1.4 続ける

- spawner は拡張子 `.ckpt` を mruby の `FMRB_LOAD_MODE_CHECKPOINT` にする。属性は横の `.toml` を普段どおり読む (`.ckpt` の最後の拡張子を `.toml` に替えた名前)。
- アプリのタスクは VM を開いて準備し (§1.2)、イメージを `fmrb_sys_malloc` に読み、`mrb_checkpoint_restore`。gem の `EMB0` の handler が時計と HAL の数を戻す。読みのバッファはすぐ放す。
- `mrb_checkpoint_host_task` でプログラムの Task を引き (終わり方の報告に使う)、`_fmrb_checkpoint_app_` からアプリのオブジェクトを引いて変数を消す。`fmrb_app_notify_started` (新しく起動したアプリでは `_init` のキャンバスが送るもの)、ルートのコンテキストで `on_restore` (あれば)、`mrb_checkpoint_continue`。続きは `mrb_task_run` の残り (C から `mrb_task_run` を呼んだ形の続き、gem の P4 の形)。終わり方は普段の起動と同じ `report_mruby_result`。
- 復元した側の `ctx->filepath` は `.ckpt` のまま。最初の `.rb` のパスは `EMB0` で運び、次のイメージの名前に使う。

### 1.5 時間 (D9・D10) と作業の領域 (D11)

- `EMB0` の中身 (版 1): `u8` 版、`i64` 書いたときの `board_millis`、`u32` HAL の次の横取りまでの tick (`tick_countdown`)、`u32` 数えたがまだ当てていない tick (`pending_ticks`)、`u8` 立ったがまだ VM に渡していない横取りの要求 (`switch_pending`)、`u32` 今の tick の中で過ぎた µs (自前の時分割のとき)、`u16` + バイト列 最初の `.rb` のパス。
- D9: `Machine.board_millis` は「端末の時計 + VM のずれ」。ずれは書いたアプリでは 0 (復元したアプリならそのずれ)、復元した側では「書いたときの値 − 今の端末の時計」。アプリのタイマ (`@_timers` の `:at`) と、アプリが ivar に持つ時刻はそのまま続く。ずれは app id の表に持ち、`mrb_s_board_millis` が `fmrb_app_checkpoint_millis_offset(mrb)` で引く (表の VM と違えば 0)。
- D10: HAL に VM ごとの読み書きの口 (`mrb_hal_task_slice_get/set`、`FMRB_HAVE_CHECKPOINT` のときだけ) を足した。書くときに `EMB0` の dump が読み、続けるときに restore が書く。mruby-task の `t->timeslice` と `mrb->task.tick` は gem が運ぶ (P4b のまま)。
- D11: gem にアロケータの口 (`mrb_checkpoint_set_allocator`) を足し、Family mruby は `fmrb_sys_realloc` / `fmrb_sys_free` を渡す。対象は書き出しと復元の間だけ生きる作業の領域 (イメージのバッファ、番号の表、読みの表、生きているレジスタの解析)。基準・状態の構造体・復元したオブジェクトはプール。イメージのファイルは `/tmp` (tmpfs)。

### 1.6 gem の直し (mruby-checkpoint の `f1` ブランチ)

`f1` の commit `080700d50c5d` (push していない)。`lib/add/MRUBY_CHECKPOINT_PIN` は push 済みの `8a2a3ec` のまま
なので、この段のコードは `MRUBY_CHECKPOINT_DIR=<f1 のチェックアウト>` で作る。push した後に固定点をこの commit に直す。

| 口 | 中身 |
|---|---|
| `mrb_checkpoint_set_allocator(mrb, fn, ud)` | realloc の形の関数 (p NULL で取る、大きさ 0 で放す)。書き出し・復元の間 (`g->work`) に作る作業の領域が使う。`gbuf` と `pmap` は作ったときのアロケータを覚えるので、書き出しの後まで生きるイメージ (handler に渡すもの) も正しく放せる。`g->work` は数でなく旗 (例外で抜けても残らない) |
| `mrb_checkpoint_set_embedder(mrb, dump, restore, ud)` | 埋め込む側のセクション `EMB0`。`END0` の直前に 1 つ。restore は復元が誤りなく済んだあと、`mrb_checkpoint_continue` の前に 1 回。dump が 0 以外を返すと書き出しを断る |

- 形式 (`doc/format_v1.md` §13) に `EMB0` を足した (任意のセクションなので版は 1 のまま)。インスペクタは `embedder: true` の要素として出す (`doc/inspect_json.md`)。
- 駆動の道具 (`checkpoint`) は全部の試験で両方を使う: 数えるアロケータ (状態を閉じたとき、借りた作業の領域が全部戻っていなければ落ちる) と、決まった印を入れる `EMB0` (復元ごとに 1 回、同じ印が戻らなければ落ちる)。
- 「開いた VM だけが登録する」C のデータの一覧 (F0 §5 の D7・F3) は F1 では要らなかったので足していない (Window のないアプリは C のデータを持たない)。

### 1.7 試験のアプリ

## 2. 確認

### 2.1 rake regress:checkpoint (新)

`tools/regress/checkpoint.rb`。ネイティブ版を標準 (Spinel のカーネル) と全部 mruby の 2 つで作り、自分の置き場
(run dir `/tmp/fmrb-native-ckpt-<uid>`、port 5585) でヘッドレスに起こし、場面を 4 つ流す (usage.md 12 章)。

| 構成 | restart | wait (2 秒待ってから手で起動) | 断り |
|---|---|---|---|
| standard | a 5→6、b 3→4、main 5→6、`t=` の段差 401 ms、イメージ 23,039 B | `t=` の段差 402 ms | 印の無いアプリ: 「movable = true が無い」。Window のアプリ: 「C data of class FmrbGfx (type 'Graphics') has no entry in the checkpoint data table」。どちらも動き続ける |
| mruby | a 5→6、b 3→4、main 5→6、`t=` の段差 400 ms | `t=` の段差 402 ms | 同じ |

(最後の通し、作るところから: 1.5 分。標準の `t=` の段差は 397 ms・401 ms、全部 mruby は 401 ms・401 ms。)

- `t=` の段差は a の 1 歩 (200 ms の sleep が本体の 250 ms の待ちの後ろに並ぶ) と、止める・起動するのにかかった時間。2 秒待った wait でも同じなので、`board_millis` が書いたときの値から続いている (D9)。D9 が無ければ 2.4 秒ほどになる。
- ログの例 (標準): 要求から書き終わりまで 1 ms 前後 (ログの時刻)、ファイルの書き込み 117〜125 µs、イメージ 23,039 B、復元 345〜379 µs、`restored clock: board_millis goes on from ... (offset -2615), slice countdown 10, pending ticks 0`。
- D10 の「往復なしと一致」は、Family mruby では実時間の時計なので、横取りの位置を往復なしと比べることはしていない (同じ実行は二度起きない)。運んでいることはログ (`slice countdown 1`・`9`・`10` などの値) で見た。gem の側の一致は原理検証の仮想の時計で確かめてある (P4b)。

## 3. 気づき

### 3.1 基準の常駐の費用が 1 VM あたり約 1 MB (D12)

ネイティブ版 (64 bit) で、申告したアプリの VM プール (1.5 MB) の使用量は、コンパイル直後で 1,423,992 B。
印を外した同じアプリは 403,576 B。差のほぼ全部が基準 (`mrb_checkpoint_baseline`) で、ログの計測で 1,018,640 B
(permanent の名前 4,041 個)。調査 §6.3 の見積もり (数十〜100 KB) より一桁大きい。

一時的に gem に数えを入れて内訳を見た (コミットしていない):

| もの | 量 | 大きさの見当 |
|---|---|---|
| 名前の文字列 | 4,041 個、98,200 B | + 割り当て 1 つずつの管理の分 (estalloc) |
| 名前の表 (`names`・`ptrs`・`is_func`) | 容量 4,096 | 約 70 KB |
| 生きているオブジェクトの表 (`heap`) | 3,453 個、容量 8,192 | 約 98 KB |
| 名前を引く表 (`obj2name`・`func2name`・`irep2idx`) | 容量 8,192・4,096・4,096 | 約 196 KB |
| クラスの写し (`snaps`) | 850 個 (容量 1,024)、メソッド 3,140、ivar 1,498 | 約 150 KB |
| permanent の irep | 1,641 個 (容量 2,048) | 約 32 KB |
| 生かしておく Array (`__checkpoint_keep__`) | 3,453 個 × 16 B | 約 55 KB |

足して約 0.8 MB。残りは割り当て 1 つずつの管理の分と、表を倍にしたときの空き。64 bit の値の表現 (`MRB_NO_BOXING`
で 16 B) と、ハッシュの表を半分空けて持つ作りが効いている。32 bit の端末ではおよそ半分の見込みだが、S3 の
500 KB のプールには重い。決めてほしいこと 1。

### 3.2 Task のブロックの self はアプリでない

最初の試験のアプリは Task のブロックから `@t0` を読み、Task が何も出さずに死んでいた (`nil - Integer`。Task の
例外は Task の値になるだけで、表に出ない)。mruby-task の Task は、作ったところの self ではなくトップレベルの
self で動く。試験のアプリは局所変数で渡すように直した。チェックポイントとは関係しない。

### 3.3 同じ枠で起動し直すと、道具への答えが消えていた

カーネルの起動し直しは同じ app id を使う (前のアプリの枠が空くので)。最初は VM の準備で表を丸ごと消していて、
デバッグサーバが答えを読む前に「書けた」が消え、`timeout` と答えた。答え (状態と、パスか理由) は準備で消さない
ようにした。

### 3.4 /tmp はホストから見えない

ネイティブ版の `/tmp` は RAM の tmpfs (8 MB) で、ホストのファイルではない。F1 は同じプロセスの中なので困らないが、
F2 (2 プロセスの間) ではイメージを外へ出す道 (デバッグサーバか遠隔制御のファイルの出し入れ、またはホストの
ディレクトリ) が要る。

## 4. サブの仮決め (ユーザが見直す)

1. 止める入口はデバッグサーバの命令 `checkpoint {pid, restart?, max?}` だけにした。シェルのコマンドや `FmrbApp` の API (アプリが自分で頼む) は作っていない。`tools/fmrb_native.rb` (と MCP の `native_app`) に `checkpoint` を足すのは親のリポジトリなので、触っていない。道具は `tool/debug/fmrb_dbg_client.py` を直接呼ぶ。
2. 印の名前は `movable`。`true` か `1`。mruby 以外のアプリでは無視する。
3. hook の名前は `on_checkpoint` (書けた直後、セーフポイントの中。イメージにはもう影響しない) と `on_restore` (復元の後、続ける前、ルートのコンテキスト)。書いた側では `on_destroy` も `FmrbApp#destroy` も呼ばない (アプリは壊れたのでなく移ったので)。VM の外の後片付け (メッセージのキュー、キャンバス、開いたファイル) は C の普段の終わり方がする。
4. 書いた側の閉じ方は、セーフポイントで VM の Task を全部終える形 (`mrb_terminate_task`)。`_spin` の後の Ruby は書いた側では 1 命令も動かない。
5. イメージの名前は `/tmp/<最初の .rb のファイル名の最初の . まで>.ckpt` で、同じアプリは上書き。横の `.toml` は元の `.app.toml` を写さず、文脈から作る (コメントの toml のアプリでも同じに起動できるように)。`task_stack_kb` など文脈に無いものは運ばない。
6. 作業の領域のアロケータが受け持つのは、書き出しと復元の間だけ生きるもの。基準はプールに残した (強制の kill では `mrb_close` が動かず、プールの外に取ると漏れるため)。クラスの写しを取る小さな配列 (`checkpoint_collect_iv`/`_mt`) もプールのまま。書き出しの最中に強制の kill が来ると、作業の領域 (システムのプール) は漏れる。
7. イメージにソースを入れる既定は gem の既定 (入れない) のまま。
8. カーネルが同時に扱う移動は 1 つ。起動し直しは、アプリの `exit` (C の終わり方が送るもの) を受けてから。
9. `FMRB_HAVE_CHECKPOINT` は sim とネイティブ版の両方に入れた (gem を持つビルド)。sim では `mruby_abi_defines.cmake` の Linux の枝に置いた (ABI の定義ではないが、同じ 2 つの部品に届かせるため。コメントに書いた)。sim での動きは確かめていない (ネイティブ版だけ)。
10. 試験のアプリは `flash/app/test/` に置き、ランチャーに出さない。
11. `rake regress:checkpoint` は `regress:full` に入れていない (ネイティブ版を 2 つ作るので 5 分ほど足される)。

## 5. 決めてほしいこと (ユーザ)

1. **基準の費用 (§3.1)**: 申告したアプリは 64 bit で 1 MB ほどプールを使う。
   - (a) gem の表を小さくする (名前の文字列を 1 つの塊に、表の空きを減らす、生かしておく Array を表と兼ねる など)。半分程度までは見込める **← おすすめ (F2 の前に)**
   - (b) D12 の (c): 名前の表をファームごとに作って flash に置き、VM ごとには番地の表だけを持つ。端末 (F6) にはこれが要る見込み。作りの変更が大きい
   - (c) このまま (ネイティブ版はプールが大きいので F2・F3 は進められる)。F6 の前に決め直す
2. `rake regress:checkpoint` を `regress:full` に入れるか。
3. 止める入口を増やすか (シェルのコマンド、アプリが自分で頼む API。後者は調査 §3.2 の「`on_event` から呼べるように同じ道に乗せる」)。

## 6. F2 に要るもの

- イメージをプロセスの外へ出す道 (§3.4)。
- 移動元を、着いた側の返事まで止めておく形 (D15)。F1 では書いたらすぐ閉じる。今の作りでは、書いた後に Task を終えずに止めておき、返事で閉じるか続けるかを決める形が素直 (`ckpt_written` で `end_all_tasks` を遅らせる)。
- 別のプロセスでの `board_millis` (D9 はそのまま効く。起動からの時間が違っても書いたときの値から続く) と、mruby-task の tick (gem が運ぶ)。
- 同じビルドの 2 つのプロセスで permanent の名前が同じに引けること (4,041 個)。
- 基準の費用 (§3.1) を減らすなら F2 の前。
