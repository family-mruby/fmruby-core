# Spinel: 同じプログラムを 2 つ同時に動かせるようにする

> 状態: 進行中 (C・G1-G4 を実施、A2 は保留) | 更新: 2026-10-04 | 同じ Spinel プログラムの 2 つ目は断る (C)。gem は持ち主以外が遅い版 (G1)、FFT アプリと spinel_hello は .app.toml で同時起動禁止 (G2)、断られた後のキー入力の行き先を戻す (G3・G4)。根本の A2 は計画だけ保留

## 目的

エディタ (Spinel) を 2 つ同時に開いても、互いの状態を壊さないようにする。同じ仕組みで、Spinel の gem を
複数の mruby アプリから同時に呼んでも壊れないようにする。

## 分かっていること (doc/app_exit/report/e1.md の E2)

- Spinel の生成プログラムは、状態を生成 C のファイル単位の変数に持つ。同じプログラムの 2 つのインスタンスは
  これを共有する。
  - 例外・catch・break のスタック (`jmp_buf`、深さ、最大値、飛んでいる最中の例外) はインスタンスの開始で
    戻されない。片方の raise がもう片方のスタックの `jmp_buf` に飛ぶことがあり、深さが負になる。
  - クラスの ivar・定数・オブジェクトのプールは、インスタンスの開始で `sp_reset_tu_statics` が戻す。
    後から起動した方が、動いている方の値を消す。
- 1 プログラムあたり約 800 個のファイル単位の変数がある (E2 の見積もり)。
- Spinel の文書 (docs/internals/multi-instance.md) は「1 つの生成プログラムにつきインスタンスは 1 つ
  (約束事で守る)」としている。`SP_MULTI_CTX` は**別々のプログラム**を同居させる仕組み。
- Spinel の gem (raycast、spinel_hello、fft) は本体に 1 組だけで、2 つの mruby アプリから同時に呼ばれると同じ
  共有が起きうる (未試験)。
- 今の Family mruby には同時起動の制限は無い (E3 で外した。ユーザ決定 2026-10-03)。2 つ同時に動かすと、
  まれに落ちる・状態が混ざる。

## 方針 (案。段階を決める前にユーザと相談)

- 生成 C のファイル単位の変数を、インスタンスごとの文脈 (`SP_MULTI_CTX` の ctx、または新しい「プログラムの
  インスタンス」の構造体) に移す。生成器 (codegen.c) と実行時 (spinel_rt) の変更で、フォーク (fmrb-ext) で行う。
- 上流の方針 (1 プログラム 1 インスタンス) と食い違うので、上流に出すかは別に考える。
- 速さ (変数への参照が 1 段間接になる) と、内蔵 RAM (インスタンスごとの領域は PSRAM に置ける) を測る。
- 最初の段階は調査: 変数の種類ごとの数と参照の回数、間接化の費用の見積もり、段階の分け方
  (例外まわりだけを先に、など)。

## ユーザの決定 (2026-10-03)

根本対策が難しい、またはトレードオフ (速さ・内蔵 RAM・上流との乖離・保守) が大きすぎるなら、同時起動の制約を
課すことを検討する。調査の段階で見積もりを示し、「根本対策」「一部だけ直す (例外まわりなど)」「制約」を
選択肢として並べて、ユーザが選ぶ。

## I1 の結果 (report/i1.md)

| 案 | 中身 | 使う人から見て | 代償 |
|---|---|---|---|
| A | 書き換わる変数を一覧にして構造体へ移す | エディタを何個でも同時に | 変換器と実行時 500-800 行、3-5 日、上流と乖離。移し忘れが黙って共有される危険 |
| B | 例外まわりだけ起動ごとに | 開けるが、まだ混ざる・落ちる (16 組中 1) | 1-2 日。単独では隠すだけ |

内蔵 RAM はどの案も 0。

## A2 (保留中の根本対策、2026-10-03 ユーザの提案)

**考え方**: 変換器が、書き換わる状態をファイル単位に**一切置かない**作りにする。状態はすべてインスタンスの領域
(ヒープ、PSRAM) に置く。A (今ある変数を移す) と違い、新しい機能を変換器に足しても移し忘れが起きず、アプリや gem
ごとの事情を気にしなくてよい。ファイル単位に残してよいのは書き換えない表 (凍結文字列、シンボル表など、今も flash) だけ。

**きれいに作れそうな根拠 (親がコードを読んで確かめた、2026-10-03)**:

- 変換器 (fork の src/codegen.c、約 1.3 万行) の `static` を出す約 140 か所はほとんど関数の定義。書き換わる状態
  (cst_、civ_、プール、動的シンボル、FFI の受け皿) の宣言は十数か所に集まっている。
- 実行時ライブラリの状態は、上流が SP_MULTI_CTX で既に `sp_ctx` に移している。残りは spinel_rt.h の 1 ファイル
  ごとの状態 (約 40 個) で、`sp_reset_tu_statics` に対象が揃っている (上流の docs/internals/multi-instance.md は
  「同じプログラムを 2 つ動かさない前提でここは変えていない」と明記)。
- 状態を構造体にまとめ、`#define cst_X (今のインスタンスの構造体->cst_X)` のように**名前を残して中身を差し替える**
  形なら、何千とある参照の箇所に手を入れずに済む。変更は宣言を出す所だけ。
- 「生成 C の書き換わる static 領域が 0 バイト」をビルドのたびに機械的に検査できる (nm / map)。I1 で外から機械的に
  書き換えたエディタは、実機の 2 つ同時の試験で 16 組中 0 組の失敗。

**未確認の点 (再開時の試作で見極める)**:

- 今のインスタンスの取り出し: 上流は関数呼び出し (`sp_ctx_current()`) で遅い。FreeRTOS のタスクごとの変数
  (`__thread`、このファームで使えることは確認済) で直接読む形にする。ただし TLS をすべてのタスクに持たせる形は内蔵 RAM に
  入らない (I1 5.5) ので、TLS に置くのはポインタ 1 つだけにする。
- 他のタスクから状態を読む所 (デスクトップの `ps` が他のアプリの例外の深さを読む) は ctx を渡す形に直す。
- 手で書いた C (fmrb_spx_*.c、fmrb_spinel_host.c、gem の native、raycast の `s_open` など) の static の洗い出し。
- 上流との差は `#ifdef` の内側に閉じ込める。上流に「再入可能性」として提案できるかは別に考える。

**再開するときの段取り (案)**:

1. 試作 (1-2 日): 変換器に構造体と名前の差し替えの出力を `#ifdef` の内側で入れ、エディタで書き換わる static を 0 に。
   実機でエディタ 2 つの試験と、同じビルドの中での速さの比較。
   見極めの基準: 変換器の変更が宣言の所に収まるか / 取り出しが速さを落とさないか / 手で書いた C の修正が数か所で済むか。
   満たさなければ C のまま。
2. 検査をビルドに組み込む (生成 C の書き換わる static の量)。
3. 種類ごとに移す (例外まわり → プール → 定数・クラスの変数 → FFI の受け皿)、段ごとに検査の値と 2 つ同時の試験。
4. gem も同じ規則に乗せ、0 になったら C の制約を外す。

## C で対応 (ユーザ決定 2026-10-03)

今は C: 同じ Spinel のプログラムの 2 つ目の起動を断る (「すでに起動しています」)。エディタは同時に 1 つ
(`default/editor` と全画面の `editor_fs` で 1 つ)。カーネル・ほかのプログラム・mruby などのアプリとは同時に動く。
E2 で書いた形 (a1b2ee50 の claim) を戻す。E3 で直した文書の枠の扱いは、そのまま正しく動く。

案に関係なく見つかったもの (i1.md 6 章) のうち、まだ決めていないもの:

- Spinel の gem (raycast、fft、spinel_hello) は、2 つ目の mruby アプリから呼ぶと黙って壊れうる。**ユーザ決定 (2026-10-03):
  案 b** = 持ち主でないタスクからは、その gem の遅い版 (Spinel でない版) で計算させる (G1)。
- `sp_brk_stack` と `sp_fstr_tab` が、同じプログラムを 1 つずつ開き直したときに消えたメモリを指す (今の生成 C では未使用)。
  直し方は小さい (リセットに足す) が、フォークの変更と SPINEL_PIN の更新が要る。
