# 報告 C1: 同じ Spinel プログラムの 2 つ目の起動を断る

> 状態: C1 完了 (2026-10-03 検収)、C2 は親の検収待ち | 更新: 2026-10-03 | コミット: C1 のコード d29663a3、C2 はコードと報告が同じコミット | C1 は E2 (a1b2ee50) の claim を戻した。
> C2 はエディタの文書の枠の回収を E2 の 1 変数の形に戻した (下の「C2」)。C2 は実機 P4-Nano・sim (標準構成)・`rake test`・NARYAv4 のビルドを通した。
> 静的な D/IRAM は NARYAv4 で 125,612 B (C1・develop と同じ)

## 結論

- 同じ Spinel プログラムが動いているとき、2 つ目の起動は「This app is already running. / Only one copy of it can run
  at a time.」の窓で断る。実機では遠隔の `/app/launch` (`default/editor` と `default/editor_fs`)・メニューの Editor・
  ランチャーのダブルクリックの 4 経路で断られ、1 つ目はその後も打鍵が入った。
- 閉じた後も kill の後も次のエディタが開ける。エディタの起動は計 34 回 (うち断り 13 回、開いたのは 21 回)、
  「Doc full」は 0 回。
- E3 の文書の枠の扱い (アプリの枠ごとの欄、`EditorCore.slot` を毎回 C に聞く、開始前と終了後の返却) は変えていない。

## 戻したもの (d29663a3)

e43bcf02 のうち claim を外した部分の逆を、今の develop (230e0685) に当てた。E3 以降、この 3 ファイルは変わっていない
ので、差分はそのまま当たった。

- `fmrb_app_spinel_claim` / `fmrb_app_spinel_release` (fmrb_app.c、宣言と説明は fmrb_app.h)。印は `Init_<program>` の
  関数の番地。`g_ctx_lock` の中で全スロットを見て、ほかの生きているアプリが同じ印を持っていれば `FMRB_ERR_BUSY` と
  エラーの窓。
- コンテキストの欄 `spinel_program` (`g_ctx_pool` は PSRAM)。
- `fmrb_app_run_spinel_vm`: インスタンスを作る前に claim、作れなかったときと終了後 (`after` の後) に release。
- `destroy_vm` の NATIVE の枝で印を消す (強制終了は release まで来ないため)。
- `after` の説明は a1b2ee50 の文 (「claim を持っている間に呼ぶ。断られたときは呼ばない」) に戻した。

a1b2ee50 と違うところ (動きは同じ):

- spawner の `after` の前のコメントを「`after` が返すのはプログラムの全インスタンスで共有の物」から「claim を
  持っている間なので、2 つ目はまだ始まっていない」に変えた。E3 で枠はアプリの枠ごとの欄になり、共有ではなく
  なったため。
- a1b2ee50 は claim の 2 関数を `fmrb_current_compile_mrb` の説明コメントとその関数の間に挟んでいた。説明コメントの
  上へ移した。

戻さなかったもの:

- `spinel_editor_native` のコメントと、開始前の `fmrb_spx_ec_release_slot()` (E3 の形のまま)。断られたエディタも
  開始前の返却は通るが、触るのは自分のアプリの枠の欄だけで、そこにあるのは前に同じ枠で強制終了されたエディタの
  残りだけなので、動いている 1 つ目の枠には触らない。

## 構造体の欄を足したことの影響

`spinel_program` は `mrc_cc` の後ろに入るので、後ろの欄の位置が 4 B ずれる。picoruby のビルド済みライブラリ
(libmruby.a、今回は作り直していない) に入る gem の `src/` は、`fmrb_app.h` を読んでもコンテキストの欄を使わない
(使うのは `ports/esp32/` で、これは ESP-IDF 側で毎回コンパイルされ、今回も作り直されたことを確かめた)。
そのため `rake clean` なしで食い違いは起きない。

## 止まった所

- TAB5 のビルドのために `rake clean_all` を実行しようとしたところ、実行の許可 (自動の判定) で止められた
  (build/ を消す操作として)。指示にある「ターゲットを切り替えるときは先に clean_all」を守れないので、TAB5・S3・
  Linux のビルドと、Linux を前提にする sim (標準・互換) はやっていない。回り道 (別の場所で作るなど) もしていない。
  親かユーザが許可するか、親の側で実行してほしい。
- 互換構成 (エディタも mruby) ではエディタは Spinel のプログラムではないので、claim はかからず 2 つ開ける
  (E2 と同じ。互換構成の sim は上の理由で今回は確かめていない)。instruction の「エディタは同時に 1 つ」は標準構成の話と
  読んだ。互換構成でも 1 つにするなら別の変更になるので、入れていない。
- 強制終了されたエディタの枠は、同じアプリの枠で次のエディタが起動するまで残る (E3 の残り)。同時に 1 つになったので、
  E2 の形 (次のエディタが開くときに記録済みの枠を回収する) に戻せば残りは出なくなるが、「E3 の枠の扱いはそのまま」の
  指示に従って変えていない。枠の表は ED_MAX_DOCS (ユーザアプリの数) あり、5 つの異なるアプリの枠で強制終了が
  重ならない限り「Doc full」にはならない。

## C2: エディタの文書の枠の回収を E2 の形に戻す

instruction_c2.md (ユーザの決定) の作業。C1 で同じ Spinel プログラムは同時に 1 つになったので、E3 のアプリの枠ごとの表を
やめ、E2 の 1 変数に戻した。

### 変えたもの

- `main/app/fmrb_spx_editor.c`: `s_slot_plus1` を `FMRB_MAX_APPS` 要素の表から 1 変数 (PSRAM) に戻した。`fmrb_current()` で
  app_id を引く `slot_entry()` と、そのための include (`fmrb_app.h`・`fmrb_limits.h`) を消した。
  - `fmrb_spx_ec_open_slot`: 記録があればそれを返し、なければ開いて覚える。E3 と同じく `EditorCore.slot` は毎回 C に聞く
    (`fmrb_editor_ffi.rb` はそのまま) ので、E2 のように「開くたびに前の枠を返す」形にはできない (2 回目の呼び出しで自分の
    文書を閉じてしまう)。回収は下の開始前の返却が受け持つ。
  - `fmrb_spx_ec_release_slot`: 記録した枠を閉じて忘れる (E2・E3 と同じ)。
  - `fmrb_spx_ec_close_slot`: 閉じた枠が記録と同じなら忘れる (E3 の形を 1 変数にしたもの。Ruby 側からは今は呼ばれない)。
- `main/app/fmrb_app_spawner.c`: 開始前の返却を claim の内側へ移した。`spinel_editor_init` (`fmrb_spx_ec_release_slot()` の
  後に `Init_editor()` を呼ぶだけ) を作り、`fmrb_app_run_spinel_vm` にはこれを渡す。終了後の返却 (`after`) は従来どおり。
  - 理由: E3 の形 (タスクの入口で、claim より前に返却) のままだと、断られた 2 つ目のエディタが、動いている 1 つ目の枠を
    閉じてしまう (記録は 1 つしかないので、それは 1 つ目の枠)。claim を取った後なら、記録に残っている枠は強制終了された
    エディタの残りしかありえない。
  - claim の印は `Init_editor` の番地から `spinel_editor_init` の番地に変わる。どちらもエディタのプログラムに 1 つの関数
    なので、断る・通すの判定は変わらない。`fmrb_app.h` の説明 (印は「Init_<program>」) をそれに合わせた (コメントのみ)。
- `main/prebuild_scripts/spinel/fmrb_editor_ffi.rb`: コメントだけ直した (「アプリの枠ごと」→「動いているエディタの枠」)。
  コードは E3 のまま。

利用者から見える動きは変えていない (強制終了の後に別のアプリの枠でエディタを開いても枠が残らない、という差だけ)。
互換構成 (エディタも mruby) は `FMRB_APP_ENGINE_EDITOR_SPINEL` の外なので触っていない。
