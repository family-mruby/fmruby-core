# 報告 H1: 開き直したときに消えたメモリを指す 2 つの領域 (sp_brk_stack / sp_fstr_tab)

> 状態: 実装・検証済み、親の検収待ち | 更新: 2026-10-05 | フォーク fmrb-ext `0bba87dc` (push していない)、fmruby-core は実行時のスナップショットの取り込みと、この報告 |
> 新しいインスタンスの開始で、遅れて確保する 2 つの領域を空に戻す (インスタンスごとに 1 回)。sim と実機 P4-Nano で、直す前は 2 回目の開き直しで落ち、
> 直した後は 30 回とも正しい。静的な D/IRAM は NARYAv4 で 125,612 B (develop と同じ)

## 結論

- 見立てどおりだった。`sp_brk_stack` (と仲間の配列) と `sp_fstr_tab` は、初めて使うときにそのときのインスタンスの領域から確保され、
  インスタンスの開始で戻されない。同じプログラムを閉じて開き直すだけで、2 回目は消えた領域を指す。
- 直し方は「戻す」を選んだ。`sp_ctx` には移していない。戻すのは `sp_tu_ctx_init` (実行時のヘッダの側、インスタンスの開始で必ず通る) で、
  インスタンスごとに 1 回だけ。そのための印を `sp_ctx` に 1 つ足した (`tu_lazy_inited`)。変換器 (codegen.c) は変えていない。
- 利用者から見た動きは変わらない。フォークの変更は実行時のヘッダ 2 つ・文書・試験 1 本で、止まる条件には当たらなかった。
- 上流 (matz/spinel の master) には `SP_MULTI_CTX` (インスタンスを作り直す仕組み) が無いので、この不具合は起きない。PR 候補は
  「記録」として下に書いた (台帳の決まりにより台帳は直接編集していない)。

## T1: 再現

### フォークの試験 (`test/multi_ctx/lazy_slots.sh`、新規)

ext のプログラム 1 本 (ブロックからの `break` と `-"tag#{i}"`) を、作る → init → 呼ぶ → 消す、を 2 つのプールを交互に使って
くり返す。消したプールは 0xA5 で埋め、ASan の版では毒を塗る (読み書きすると報告される)。

| | 直す前 (654c9fd5) | 直した後 (0bba87dc) |
|---|---|---|
| 20 回の開き直し (埋めたプール) | 2 回目で SIGSEGV (0/20 正しい) | 20/20 が CRuby と同じ |
| ASan、`break` だけ | `use-after-poison` WRITE、`sp_brk_push` (spinel_rt.h 11131) | 報告なし |
| ASan、`-"str"` だけ | `use-after-poison` READ、`sp_fstr_lookup` (spinel_rt.h 1126) | 報告なし |
| `--no-main` を 1 つのインスタンスで 40 回 | プールの増加 9,424 B | 同じ 9,424 B |

最後の行は直し方の確認: 戻しを毎回の入口で行うと、呼ぶたびに break の配列を確保し直して 596,448 B 増える (試しにそう書き換えて
確かめ、FAIL になることを見た)。インスタンスごとに 1 回なので増えない。

### sim と実機 (一時的な改造で再現。コミットしていない)

- spinel_hello の Spinel 側 (`spinel_hello_kernel.rb`) の `greet` に、ブロックからの `break` と `-"k#{k}"` を足した (結果が正しければ
  返す文字列は今までどおり "Hello world!")。
- 試しのアプリ `h1_reopen.app.rb`: `Fmrb::SpinelHello.new` → `greet` → `close` を 30 回。1 回ごとに新しいインスタンスと新しいプール
  (fmrb_sys_malloc の 128 KB) になる。
- 埋めない場合、sim では 30 回とも正しく見えた (消えたプールの中身がまだ残っていて、たまたま通る)。プールの次の持ち主が上書きした
  状態を作るため、`spinel_hello_end` で解放の前にプールを 0xA5 で埋める 1 行も一時的に足した。

| | 直す前 | 直した後 |
|---|---|---|
| sim (Linux、標準構成) | 2 回目の `greet` で core が Segmentation fault (exit 139) | 30/30 "Hello world!" |
| 実機 P4-Nano | 2 回目で Guru Meditation (Load access fault、MTVAL 0xa5a5a5a5)。addr2line: `strcmp` ← `sp_str_eq` ← `sp_fstr_lookup` ← `sp_str_dedup` | 30/30、画面に「round 30 bad 0」、Guru 0 件 |

検証の後、改造 2 つと試しのアプリは元に戻した (端末の /app/debug からも消した)。

## T2: 直し方とその理由

### 変えたこと (フォーク `0bba87dc`)

- `lib/sp_ctx.h`: `sp_ctx` に `int tu_lazy_inited` を足す。`sp_instance_create` が構造体を 0 で埋めるので、新しいインスタンスでは 0。
- `lib/spinel_rt.h`:
  - `sp_tu_lazy_reset()` (SP_MULTI_CTX のときだけ): `sp_brk_stack` / `sp_brk_val` / `sp_brk_serial` / `sp_brk_exc_top` /
    `sp_brk_recur_mark` を NULL、`sp_brk_top` を 0、`sp_fstr_tab` を NULL、`sp_fstr_cap` / `sp_fstr_len` を 0 にする。解放はしない
    (前のインスタンスの領域なので、今のインスタンスの free に渡せない)。
  - `sp_tu_ctx_init()` の最後で、`tu_lazy_inited` が 0 のときだけ上を呼び、1 にする。
  - break の配列のポインタ 5 つと、凍結文字列の表の 3 つに `SP_TU_BSS` を付けた (理由は下の「静的な領域」)。
- 遅れて確保する形はそのまま。`break` を使わないプログラムが実行時に払うものは無い。

### 戻す / sp_ctx に移す の比べ

上流の作り (docs/internals/multi-instance.md) は、状態を 2 つに分けている。ライブラリ (lib/*.c) の状態は `sp_ctx` に移し、生成プログラムの
ファイル単位の状態 (実行時のヘッダの static を含む) は TU に残して、インスタンスの開始で戻す。break のスタックと凍結文字列の表は後者
(文書の表でも「TU (no change)」の行に `sp_brk_*` と `sp_fstr_cap/len` がある)。例外のスタックや catch のスタックと同じ扱いになる。

- **戻す (選んだ)**: 上の分け方に沿う。変更は実行時のヘッダの中に閉じる。使う側の速さは変わらない。
- **sp_ctx に移す**: 寿命はちょうど合うが、`SP_CTX()` は関数呼び出し (`sp_ctx_current()`) なので、`sp_brk_push` の中の 5 つの配列への
  読み書きがそれぞれ呼び出しになる。TU の状態をここだけ lib の側へ移すと分け方も崩れる。採らなかった。

「戻す」場所は 2 つ考えた。

- 生成される `sp_reset_tu_statics` に足す: 変換器の変更になるうえ、これは `--no-main` の入口では**呼ぶたびに**走る (1 回の呼び出しが
  プログラムの 1 回の実行という作り)。そこで戻すと、同じインスタンスで確保した配列を捨てて毎回確保し直し、インスタンスが終わるまで
  漏れる (上の 596,448 B)。
- `sp_tu_ctx_init` で、インスタンスごとに 1 回 (選んだ): `--persistent-statics` の `statics_inited` と同じ形 (印は `sp_ctx` の中にあり、
  `sp_instance_create` が 0 にする)。インスタンスの番地で見分ける形は、消したインスタンスと同じ番地に次のインスタンスが作られうるので
  使えない。印は 1 インスタンスに 1 つなので、1 つのインスタンスを 1 つの生成プログラムが持つ前提になる (`statics_inited` と同じ前提)。

`sp_brk_top` も一緒に 0 に戻す。普通に終わったインスタンスでは 0 のはずだが、break の範囲の中で外から片付けられたインスタンスの後では
0 でない。配列だけ NULL にすると、GC の `sp_mark_brk_vals` が `sp_brk_val[0..top)` を読みにいって NULL を踏む。

### 静的な領域

戻しの書き込みがあると、break を使わないプログラムでも break の配列のポインタが消されずに残る (ホストの x86-64 で、break の無い
プログラムの .o に `sp_brk_stack` ほか 4 つが新しく現れた。`sp_brk_top` は前から居る)。ESP32 では内蔵 RAM の .bss/.sbss に載るので、
`SP_TU_BSS` を付けて fmruby では PSRAM に置いた (654c9fd5 で生成プログラムの 0 始まりの枠に付けたのと同じ扱い)。NARYAv4 の ELF で
`sp_brk_stack` / `sp_brk_val` は 0x48xx_xxxx・0x491x_xxxx (`.ext_ram.bss`) にあり、`sp_fstr_tab` は今の生成プログラムでは消えている。
`SP_TU_BSS` が空の既定の構成では、初期化子を外しただけで中身は同じ。

## 同じ形の領域の洗い出し

実行時のヘッダ (spinel_rt.h) の TU の static で、インスタンスのヒープを指しうるものを、GC の根の印付け (`sp_re_mark_globals` が呼ぶ
もの) と `malloc` の呼び出し箇所から洗った。

| 領域 | 遅れて確保 | インスタンスの開始で | 判定 |
|---|---|---|---|
| `sp_brk_*` (配列 5 つと深さ) | する | 戻さなかった | **直した** |
| `sp_fstr_tab` / `_cap` / `_len` | する (表) | 戻さなかった | **直した**。表の中の文字列も前のインスタンスのヒープにある |
| `sp_at_exit_hooks` / `_count` | しない (固定の配列) | 戻さない | 普通に終われば init / 入口の終わりで空になる (ext の init は最後に `sp_at_exit_run(0)`)。外から片付けられたときだけ残る |
| 例外・catch のスタック、`sp_proc_ret_head`、`sp_pending_*` / `*_cause` | しない | 戻さない | 実行中だけ使う。外から片付けられたインスタンスの後だけ値が残る。例外のスタックは、ホストが `_try` の中で init を呼ぶ形では入口で 0 に戻せない (そのフレームが積まれている) ので、今回は触っていない |
| `sp_program_name` | しない | 入口で毎回入れ直す (`$0` を使うとき) | 問題なし |
| `sp_bt_buf` | しない | - | 戻り番地だけでヒープを指さない |

生成 C の側 (変換器が出す枠) は、GC の印付けの対象 (`sp_mark_user_globals`) と `sp_reset_tu_statics` の戻しが同じ所で組み立てられていて
(codegen.c の `mk` / `rs`)、動的なシンボルの表 (`sp_ndyn`)・大きな整数のリテラル (`sp_bigl`)・クラスの変数などは全部戻されている。
正規表現のリテラル (`sp_re_pat_N`) は `sp_tu_init` が入口で毎回コンパイルし直すので、遅れて確保する形ではない。ライブラリ (lib/*.c) の
状態は上流の作りで `sp_ctx` に入っている (`make check-mc-globals` が分類を検査する)。

遅れて確保して戻さない形は、この 2 つだけだった。外から片付けられたインスタンスの後に残る値 (表の 3・4 行目) は別の種類の話で、
I1 の案 B (例外まわりをインスタンスごとに) に近い。今回の指示の範囲の外として残した。
