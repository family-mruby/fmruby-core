# 報告 G1: Spinel の gem を 2 つ目のアプリが使うときは遅い版に切り替える

> 状態: G1 検収済み、G2 は実装・検証済みで親の検収待ち (末尾の「G2」) | 更新: 2026-10-03 | コミット: G1 のコード aca894ac、G2 は e6c2f47f (sim のメモリ切れ) と 0c5651d2 (宣言と表示)、報告はこのコミット |
> 3 つの gem (raycast、fft、spinel_hello) が持ち主のタスクを覚え、ほかのアプリは Spinel でない版で動く。実機 P4-Nano・sim・ブラウザ版 (起動のみ)・`rake test`・
> TAB5/S3/NARYAv4/Linux/wasm のビルドを通した。静的な D/IRAM は NARYAv4 で 125,612 B (develop と同じ)

## 結論

- gem のインスタンスは、最初に開いたアプリのタスクが持ち主になる。ほかのタスクの `begin` は「使用中」(各 gem の `*_BUSY`、
  -5) を返し、gem の Ruby はそのアプリを遅い版で動かす。止めない・断らない。
  - raycast: `:spinel` → `:ruby`。
  - FFT: `:spinel` → `:ruby`、`:spinel_q15` → `:ruby_q15` (理由は下の「FFT の切り替え先」。指示の「C の版があればそれ」から外した)。
  - spinel_hello: `SpinelHelloCore` (mrblib にあり mruby でも動く) で挨拶を作る。`:ruby`。
- アプリが読める `backend` は実際に動いている版を返す (`Fmrb::Raycast#backend`、`Fmrb::Fft#backend`、`Fmrb::Fft.bench` の
  `:backend`、新しく足した `Fmrb::SpinelHello#backend`)。切り替えたときは受け皿がログに 1 行出す:
  `raycast: [G1 ray] the Spinel raycast instance belongs to G1 ray (pid 5); this app runs on the ruby backend instead`
  (どのアプリが・持ち主はどれか・どの版で動くか。タグが gem 名)。
- 遅い版に切り替わったアプリは最後まで遅い版のまま。持ち主が閉じると、次に開いたアプリが新しい持ち主になる。
- 持ち主でないアプリが閉じても、持ち主のインスタンスは消えない (下の「直した既存の穴」)。
- 強制終了された持ち主のインスタンスとプールは fmrb_app の後始末で解放され、持ち主の記録も消える (実機と sim で確認)。

## 作り

### 持ち主の記録 (fmrb_spinel_host)

- `fmrb_spinel_gem_t` (`components/fmrb_spinel_rt/include/fmrb_spinel_host.h`) に、持ち主のタスク・プール・est・持ち主の
  pid と名前 (ログ用) を持たせる。gem ごとに受け皿のファイル単位の変数 1 つ (PSRAM に置く。BSS なので名前と解放関数は
  `begin` で入れる)。
- `fmrb_spinel_gem_claim`: 持ち主を NULL から自分へ比較交換で取る。結果は「取った」「もう自分の物」「使用中」の 3 つ。
  2 つのアプリが同時に `begin` しても片方だけが取る。
- `fmrb_spinel_gem_is_open_on`: entry の呼び出しと `end` の前に、呼んだタスクが持ち主かを確かめる。
- `fmrb_spinel_gem_release`: 持ち主が片付けた後に記録を消す (最後に持ち主を NULL に戻す)。
- `fmrb_spinel_gem_task_ended`: 終わったタスクが持っていた gem を全部落とす。初めて持たれた gem は一覧 (PSRAM のポインタ
  1 つ) につながり、これをたどる。インスタンスは「今のインスタンス」にせず落とす (呼ぶのはカーネルのタスクのことがあり、
  `fmrb_spinel_instance_end` だとカーネル自身のインスタンスを壊す)。インスタンスの物は全部プールの中なので、
  `fmrb_spinel_instance_exc_hw` の表から外し、est を片付け、プールを返せば済む (強制終了の mruby VM を落とすのと同じ考え)。

### 後始末 (fmrb_app.c)

- `release_spinel_gems` を通常終了 (`destroy_vm` の後) と強制終了 (`force_release_resources` の `destroy_vm` の後) の両方で
  呼ぶ。何か落としたときだけ `Released N Spinel gem instance(s) it still owned` を出す。
- 通常終了では gem の final (mrb_close) が先に持ち主として片付けるので、これは網。強制終了では VM を mrb_close せずに
  落とすので final が走らず、これが唯一の解放になる。

### 受け皿と binding

- 3 つの受け皿 (`native/*.c`) の `s_open`/`s_pool`/`s_est` を `fmrb_spinel_gem_t` に置き換えた。`begin` の失敗の経路でも
  記録を戻す。
- binding に `note_fallback(backend)` (FFT は `spinel_note_fallback`) と定数 `BUSY` (FFT は `SPINEL_BUSY`) を足した。
- FFT の final は今まで Spinel のインスタンスを終えていなかった (`fmrb_fft_release` だけ)。ほかの 2 つと同じく
  `fmrb_fft_spinel_end` を呼ぶようにした (持ち主のときだけ効く)。

### Ruby 側

- `Fmrb::Raycast.open` / `Fmrb::Fft.spinel_open` / `Fmrb::SpinelHello.open` は、持てたら true、使用中なら false を返す
  (ほかの失敗は今までどおり raise)。`new` は false のとき版を切り替え、`note_fallback` を呼ぶ。参照の数は持てたときだけ
  増えるので、`close` は実際の版が Spinel のときだけ参照を減らす。
- `Fmrb::Fft::SPINEL_FALLBACK = { spinel: :ruby, spinel_q15: :ruby_q15 }`。

### FFT の切り替え先

`:ruby` / `:ruby_q15` にした。指示の「C の版」(`:c` / `:c_q15`) にしなかった理由:

- C の版 (`fmrb_fft_bench.c`) は作業用の配列 (s_re、s_im、q_re など) をファイル単位の変数に持ち、全タスクで共有している。
  鍵も無い。2 つのアプリが同時に C の版を使うと、互いの計算を上書きする。
- さらに、どの mruby アプリが閉じても gem の final が `fmrb_fft_release` を呼び、この配列を解放する。C の版で計算中の
  アプリがいると、解放されたメモリを使う。切り替えが起きるのは「2 つのアプリが同時に FFT を使う」ときなので、
  ちょうどこの危ない状況に送り込むことになる。
- `:ruby` / `:ruby_q15` は Spinel の版と同じ Ruby (`fft_core.rb` / `fft_core_q15.rb`) をアプリ自身の VM で動かすので、
  共有が無く、結果も Spinel の版と同じ数になる (実機の fft_bench で dev=0 / 12 は Spinel の版と同じ)。代わりに遅い
  (512 点で 1 回 0.25 秒前後)。
- C の版を安全にすれば (下の「止まった所 3」)、切り替え先を C に変えるのは `SPINEL_FALLBACK` の 1 行で済む。

### 直した既存の穴

- **どのアプリが閉じても gem のインスタンスが消えていた**。raycast と spinel_hello の final は無条件に `*_end()` を呼んで
  いた。gem は全部の mruby VM に入っているので、raycast を使っていないアプリが閉じても、持ち主のインスタンスのプールを
  解放していた (しかも呼んだタスクの「今のインスタンス」を壊す形で)。今は持ち主のときだけ終える。
- **強制終了された持ち主のインスタンスが残っていた**。`s_open` が 1 のまま、プール (128-192 KB の PSRAM) と
  `fmrb_spinel_host` の表の 1 枠が残り、次に開いたアプリは今のインスタンスが無いタスクから死んだインスタンスを使った。
  今は上の後始末で解放され、次のアプリが持ち主になれる。

## 止まった所 (案を返す)

1. **アプリの画面が、頼んだ版を出している (Raycaster、mic_spectrum)**。どちらも画面の版の名前を `Fmrb::*#backend` で
   なく自分の `BACKENDS[@backend_idx]` から出している。切り替わると「[B]spinel cast:14988us」のように Spinel と出しながら
   Ruby で動く (実機の画面で確認)。案: 表示を `@caster.backend` / `@fft.backend` に変える (各 1 行)。Raycaster のログの
   `Raycaster engine:` も同じ。画面の表示を変えるので手を付けていない。
2. **fft_bench の画面が実際の版の名前になった**。`Fmrb::Fft.bench` の `:backend` を実際の版にした (指示の「読める口は
   実際の版」) ので、切り替わったときは spinel の行が「ruby」、spinel_q15 の行が「ruby_q15」と出る (同じ名前の行が 2 つ
   並ぶ。実機の画面で確認)。切り替えが無いときは今までと同じ。アプリ側のログは自分の頼んだ名前で出し、spinel の行の
   `entry=... around=...` は持ち主の値を読むので負の数になる。案: (a) このままにする、(b) bench の `:backend` は頼んだ版に
   戻し、別のキー (`:ran_on` など) で実際の版を返し、fft_bench の画面はたとえば「spinel>ruby」と出す。どちらにするか
   決めてほしい。
3. **FFT の C の版 (`:c`、`:c64`、`:c_q15`、`:dsp`) が全タスクで作業用の配列を共有している** (上の「FFT の切り替え先」)。
   G1 とは別に、今でも 2 つのアプリが C の版を同時に使うと結果が混ざり、どの mruby アプリが閉じても配列が解放されて、
   C の版で計算中のアプリが解放済みのメモリを使う。案: C の版を鍵で直列にし、`fmrb_fft_release` を「使っているタスクが
   いなければ」にする (または gem の final から外す)。直したら FFT の切り替え先を C にできる。

## 見つけたこと (G1 の範囲外、直していない)

- **sim で spinel_hello のインスタンスが約 70 回の挨拶でプールを使い切って落ちる** (`unhandled exception: out of memory`、
  core ごと終了)。この版の sim で、1 つだけ開いて 100 ms ごとに挨拶して再現する。実機 (G1 より前の版) では 600 回まで
  落ちなかったので、64 ビットの sim で 128 KB のプールが足りないか、挨拶ごとのごみが回収されていないかのどちらか。
  G1 で持ち主の側の経路は変えていないが、develop の sim では確かめていない。公式の spinel_hello アプリは 1 回しか挨拶
  しないので表には出ない。試験アプリは挨拶を 2 秒に 1 回に減らして避けた。
- **1 つのタスクが 2 つの gem を Spinel で同時に開くと壊れる**。インスタンスの「今」はタスクに 1 つで、後から開いた gem の
  インスタンスが今になる。先に開いた gem の entry はほかの gem のインスタンスで走り、`end` は今のインスタンス
  (= ほかの gem の物) を壊す。今その使い方をするアプリは無い。直すなら entry の前後で今のインスタンスを切り替える
  口を host に足す。
- 強制終了がインスタンスの entry の途中で起きると、生成プログラムのファイル単位の例外まわりの状態 (深さなど) は戻らない
  (i1.md 6 章と同じ種類)。次のインスタンスの init はそれ以外を戻す。G1 の試験では問題は出ていない。

## G2: 仕上げ (表示・同時起動の禁止・spinel_hello のメモリ切れ)

> コミット: e6c2f47f (sim のメモリ切れ)、0c5651d2 (`.app.toml` の宣言と表示) | 指示: instruction_g2.md |
> 静的な D/IRAM は NARYAv4 で 125,612 B (G1・develop と同じ)

### 結論

- **spinel_hello のメモリ切れは develop (e6b313c2) の sim でも起きる** (G1 の退行ではない)。原因は GC の作業用の
  一覧 (mark stack) の大きさが「ポインタの個数」で決めてあり、64 ビットの sim では実機の倍の 64 KB を最初の回収で
  一度に頼むこと。128 KB のプールに 83 KB の起動分が載っていると取れず、`sp_oom_die` で core ごと終わる。
  sim では個数を半分 (4096) にして、実機と同じ 32 KB にした。直した後は 5000 回の挨拶まで落ちない。
- `.app.toml` に 2 つの鍵を足した。`single_instance = true` は同じファイルの 2 つ目を断り、`exclusive_group = "fft"` は
  同じ値を書いたアプリが動いている間の起動を断る (自分の 2 つ目も)。fft_bench と mic_spectrum に `exclusive_group = "fft"`、
  spinel_hello に `single_instance = true` を書いた。書いていないアプリは調べないので、今までと同じ。
- Raycaster の画面は動いている版 (`@caster.backend`) を出す。fft_bench は切り替わった行を「spinel>ruby」と出し、
  `Fmrb::Fft.bench` は `:backend` (選んだ版) と `:ran_on` (動いた版) の両方を返す。

### spinel_hello のメモリ切れ

同じ試験アプリ (Spinel Hello を開いたまま 100 ms ごとに挨拶し、10 回ごとにログ) を、develop と G1 の sim (`rake clean_all` の
後の Linux ビルド) で動かした。

| ビルド | 結果 |
|---|---|
| develop e6b313c2 | 60 回目のログの後に `unhandled exception: out of memory`、core が終わる |
| G1 a56cbe46 | 同じ (60 回目の後) |
| G1 + 直し | 5000 回まで落ちない |

develop の確かめ方: 作業ツリーがきれいなことを確かめて、元の checkout を `git checkout --detach e6b313c2` にして sim を
作り、終わってからブランチに戻した (docker が元の checkout の build/ を使うため、worktree は使わなかった)。

原因を追った手順 (一時的な計測。コミットしていない):

- 挨拶ごとにプールの使用量を見ると、インスタンスを作った直後が 82,976 B 使用・47,376 B 空き。挨拶 1 回で 152 B 増え、
  60 回目で 92,096 B 使用・38,256 B 空き。**空きが 38 KB あるのに** メモリ切れで落ちた。
- 落とすのは `sp_gc.c` の `sp_gc_mark_par_run` で、最初の回収のときに作業用の一覧を `SP_GC_MARK_STACK_MAX` 個の
  ポインタ分、プールから一度に取る。この値は fmrb_spinel_rt の CMakeLists で 8192 (実機の 32 ビットで 32 KB)。
  64 ビットの sim では 64 KB になり、38 KB の空きでは取れない。回収が走るのは使用量がしきい値 (プールの 1/32) を
  超えたときで、ちょうど 60 回あたり。
- 実機は 32 KB を頼むうえ、起動分も小さい (ポインタが半分) ので落ちない (G1 より前に 600 回まで確かめた記録と合う)。
- 直し (e6c2f47f): ポインタが 8 バイトのとき (`CMAKE_SIZEOF_VOID_P` が 8) の既定値を 4096 にした。実機・ブラウザ版
  (wasm は別に 8192 を指定、32 ビット) は変わらない。足りなければ一覧は伸びるか、走査の再帰に落ちるだけで、正しさは
  変わらない。Spinel の実行時やフォークは変えていない。
- 直した後の使用量は、最初の回収で一覧の 32 KB が乗って約 120 KB になり、その後は 120-126 KB の間を行き来する。
  200 回ごとに約 350 B ずつ底が上がるが、約 1900 回目で一度 120,400 B まで戻る (古い世代の回収と見られる) ので、
  増え続けはしない。5000 回の時点で 122,248 B。
- 注意 1: sim では 128 KB のうち空きが最も少ないとき 4-5 KB しかない。spinel_hello の挨拶はこれで足りるが、gem に
  大きな処理を足すと sim で先に足りなくなる。
- 注意 2: 値は CMake のキャッシュに入るので、前に作った build/ では `rake clean_all` するまで 8192 のまま。
  sim と実機の切り替えでは毎回 `rake clean_all` するので、普段は気にしなくてよい。

### 同時起動の禁止 (`.app.toml` の宣言)

| 鍵 | 値 | 意味 |
|---|---|---|
| `single_instance` | `true` か `1` (既定 false) | 同じファイル (起動したパス) のアプリが動いていれば断る |
| `exclusive_group` | 文字列 (既定なし、15 バイトまで比べる) | 同じ値を書いたアプリが動いていれば断る。自分の 2 つ目も断る |

作り:

- spawner (`fmrb_app_spawner.c`) が 2 つの鍵を読み、起動の属性 (`fmrb_spawn_attr_t`) からアプリの枠
  (`fmrb_app_task_context_t`、PSRAM) に写す。`exclusive_group` が 15 バイトを超えたら警告を出し、先頭 15 バイトで比べる。
- 判定はアプリ自身のタスクの最初、VM を作る前 (`launch_claim`、fmrb_app.c)。`g_ctx_lock` の中で、ほかの生きている枠のうち
  「判定を通った印」(`launch_claimed`) を持つものだけを見る。同時に 2 つ起動しても片方だけが通る。
- 印は VM を片付けるとき (`destroy_vm`、通常終了と強制終了の両方が通る) に消すので、刈り取りを待っている枠が次の起動を
  断ることはない。枠を割り当てるときにも消す。
- 断るときは Python の 2 つ目・Spinel のプログラムの 2 つ目と同じく、エラーの窓に出す (`set_last_error` +
  `notify_error_to_kernel`)。文言は既存に合わせた。
  - 同じファイル: 「This app is already running. / Only one copy of it can run at a time.」(C1 と同じ)
  - 同じ組: 「FFT Bench is already running. / Only one "fft" app can run at a time.」(Python の断りと同じ形)
- 説明は `doc/app-distribution/spec.md` の 3.1 節 (端末が読む鍵の一覧) と、fmrb-app-new の手順
  (`.claude/skills/fmrb-app-new/SKILL.md`。親のリポジトリでは gitignore されているのでファイルを直しただけ) に足した。

## G3: 起動中に終わったアプリの後、キー入力の行き先を元に戻す

> コミット: 2919ba1b (カーネル)、9768c860 (互換構成のビルド切れ) | 指示: instruction_g3.md |
> 静的な D/IRAM は NARYAv4 で 125,612 B (develop・G2 と同じ)

### 結論

- 起動のときに、それまでのキー入力の行き先を覚える (`@launch_prev_hid`、pid → 行き先)。アプリが窓を出す前に終わったら、
  覚えた行き先がまだ生きていてフォーカスできれば、そこへ戻す。そうでなければ今までの規則 (起動した親 → デスクトップ)。
- 窓を出した後に閉じたときは変えていない (起動した親かデスクトップ)。実機と sim で確かめた。
- 実機で Mic Spectrum の 2 つ目・fft_bench・エディタの 2 つ目・spinel_hello の 2 つ目を断らせた後、**何もクリックせずに**
  打った E (や x) は元のアプリに届いた。
- ただし**断りの窓を窓の中でクリックして閉じると、キー入力はデスクトップへ移る** (下の「止まった所」)。ユーザが報告した
  手順はおそらくこれで、G3 の直しだけではこの手順の症状は消えない。

### 「窓を出した」の判定

`on_app_started` (アプリの `app_started` 通知) を選んだ。

- この通知は共有の canvas 作成の手助け (`fmrb_app_notify_started`) から出る。どの実行系 (mruby・Spinel・MicroPython・
  Lua・BASIC) も、スクリプトを読み込んで main の canvas を作った後にだけここを通る。つまり「窓が画面に出られる状態に
  なった」最初の時点で、全実行系に共通している。
- G2 の断り (`launch_claim`) は VM を作る前、コンパイルエラーは canvas を作る前なので、どちらもこの通知の前に終わる。
- 起動の表示の終わり (`clear_starting`) は使わなかった。`app_error` (起動後の実行時例外も含む) と 20 秒の時間切れでも
  消えるので、「窓が出た」とは言えない。
- 窓の一覧 (`@window_list`) は非同期に更新されるので、終わった時点で見ても当てにならない。
- 覚えた値は `on_app_started` で消し、`cleanup_terminated_app` でも消す (pid は枠の番号で使い回されるため)。
  画面の無いアプリ (headless) は今までどおりキー入力を渡さないので、覚えもしない。

### 全画面・F5 の扱い

- 起動前の行き先は、全画面のアプリを脇へ寄せる (park) より前に読む。寄せるとキー入力がデスクトップへ移るため。
- **覚えた行き先が寄せられた全画面のアプリなら使わない** (今までの規則に任せる)。最初は使っていたが、sim で全画面の
  エディタから窓のアプリ (compile_err) を起動すると、エラーで終わった後にエディタが全画面に戻り、デスクトップの
  エラーの窓が停止中のデスクトップの裏に隠れた (利用者から見た動きの変化)。今までの規則では、この場合はデスクトップに
  戻ってエラーの窓が見え、エディタは寄せられたまま。直した後はそのとおりに戻ることを sim と実機で確かめた。
- F5 は `@run_parent` の規則がそのまま効く (起動した親 = 起動前の行き先なので結果は同じ)。全画面のエディタからの F5 で
  コンパイルエラーになったときは、今までどおりエディタが全画面に戻る。

### 互換構成のビルド切れ (G1 の退行、直した)

- カーネルとデスクトップを mruby にした構成 (`FMRB_KERNEL_ENGINE=mruby FMRB_APP_ENGINE_EDITOR=mruby`) の Linux ビルドが、
  `fmrb_app.c` の `fmrb_spinel_gem_task_ended` が宣言されていないというエラーで止まった。G1 (aca894ac) で足した呼び出しが、
  Spinel のカーネルかデスクトップのときだけ読むヘッダにあったため。G1・G2 は標準構成だけで確かめていた。
- Spinel の実行時の部品は今はどの構成にも入っている (見本の gem が常に使う) ので、ヘッダはいつも読むようにした。
  例外スタックの統計 (`FMRB_HAVE_SPINEL_HOST`) は今までどおり条件つき。

### 止まった所 (案を返す)

断りの窓 (デスクトップのエラーの窓) を**窓の中で**クリックして閉じると、キー入力はデスクトップへ移る。カーネルは
クリックされた窓にフォーカスを渡す (input_router)。エラーの窓はデスクトップの前景に描かれた重ね表示なので、クリックは
デスクトップへ届き、デスクトップがキー入力を取る。G3 で戻した行き先が、閉じるクリックで上書きされる。窓の外を
クリックした場合は、閉じる処理とは別にクリックした窓へフォーカスが移るので問題は出ない。

これを直すと「デスクトップの窓をクリックするとデスクトップにフォーカスが移る」という今の動きが変わるので、指示の
止まる条件に当たる。直さずに案を出す。

- 案 1: エラーの窓の中のクリックでは、カーネルがフォーカスを動かさない (デスクトップが重ね表示のうち「キー入力の要らない
  窓」を知らせる)。エラーの窓はクリックで閉じるだけで、キー入力を受けないので、取る理由がない。
- 案 2: デスクトップがエラーの窓を閉じたときに、カーネルへ「元に戻して」と頼む。カーネルは窓を開いたときの行き先を覚えて
  おき、それが生きていれば戻す。開くきっかけが G3 の場面に限らない (実行中の例外) ので、こちらの方が範囲が広い。

どちらも小さい。案 1 の方が今のフォーカスの規則 (クリックした所に渡す) からの例外が 1 つで済む。
