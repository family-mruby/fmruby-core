# 窓の転送 (Remote Window): アプリの窓を別の機体のデスクトップに出す

記録: 2026-08-31。状態: 構想 (実装未着手)。
関連: node_variants.md (ヘッドレス機の価値 3.7、使い方 3.5 の 1 を
アプリ単位に置き換える)、usecases.md 10、pet_design.md (V0 として使える)、
doc/remote_desktop/design.md (capture 経路の土台)、
doc/dev_remote_ctl/plan.md (機体間の HTTP 口)。

## 何か

機体 A で動いているアプリの**窓 1 枚だけ**を、機体 B のデスクトップに
普通の窓 (枠・フォーカス・移動つき) として出し、B での操作を A のその
アプリに返す。アプリは無改修で、いつもどおり自分のキャンバスに描くだけ。

Asterism の資源としては `/machines/<機体>/apps/<pid>/window`。

```ruby
box = Asterism["/machines/stamp1"]
box.apps.find { |a| a.name == "thermo" }.window.show_on(self)
```

芯は「**アプリはハードのある場所で動き、顔は人のいる場所に出る**」。
pub/sub で値を送って画面ごとに UI を書き直すのではなく、顔そのものが
移動する。ヘッドレス機 (node_variants.md 3 章) の価値のうち「画面は
あとから着く」を実体化する、**Asterism でユーザが最初に目にする機能**
として位置づける。

## なぜ筋がよいか

- Modern の描画は**アプリごとに独立したキャンバス**を合成する構造
  (display_p4、DISPLAY_P4_MAX_CANVAS)。デスクトップ全体より 1 枚を
  取り出す方が素直で、remote desktop の capture 経路 (バイト一致の
  決定的なもの) と同じ土台に乗る。
- 受け側は「画像を貼って入力を返す代理アプリ」1 本。枠・フォーカス・
  移動・重なりは受け側のデスクトップが普通の窓として面倒を見る。
  デスクトップ丸ごとの入れ子 (node_variants.md 3.5 の 1) より合成が
  自然なので、**あちらはこの案に置き換える**。
- **非対称が用途に合う**: 送り側になれるのは Modern 系 (ヘッドレス・
  Tab5・NARYA v4・wasm)。Retro はキャンバスが子チップ (WROVER) 側に
  あるので送り側は難しいが、**受け側にはなれる** (代理アプリは画像を
  描くだけ)。

## 制約 (先に言っておくもの)

- **音は送り側で鳴る**。ゲームを Retro の APU で鳴らしたいなら Retro で
  走らせるべきで、転送の出番ではない。
- Retro に出すときは RGB565 → RGB332 の減色が入る。逆方向は問題なし。
- **入力の帰属**: マウス・キーボード配列・かなモードは受け側の機体のもの。
  送り側は「特定 pid に注入する口」が新たに要る (今はフォーカス中の
  アプリ宛だけ)。
- 遅延は LAN で数十 ms + `_spin` の周期。操作する窓としては十分、
  ゲームには向かない。
- 認証は遠隔画面と同じ枠 (doc/softap_remote/plan.md 段階 B の token)。

## ユーザに刺さる使い方

- **家の見える化パネル**: 温度・玄関・洗濯の残り時間・植木の水。センサが
  繋がったヘッドレス機で 1 回だけアプリを書き、その顔が居間の Retro
  (テレビ)・机の NARYA v4・出先のブラウザに窓として出る。
- **Retro に「Retro には無い機能」の窓が出る**: S3 は WiFi と BLE
  キーボードが排他なので、天気・時報・AI など網が要るアプリは Retro で
  走らせにくい。ヘッドレス機で走らせて窓だけテレビに出せば、Retro は
  BLE キーボードのまま。
- **作業の続きを別の画面で**: エディタや長時間走る BASIC・MIDI
  シーケンサ・FFT 表示をヘッドレス機に置き、朝は机の Modern から、夜は
  ブラウザから同じ窓を開く。GUI 版の tmux。「画面が来ては去り、作業は
  箱に残る」。開発者に一番刺さる形。
- **教室**: 先生機のデスクトップに、生徒 1 人 1 人の実行中アプリの窓が
  並ぶ。アプリは生徒の機体で動いたまま。
- **ロボットの頭の中**: 車台のヘッドレス機で走る振る舞いアプリの窓が、
  操縦席のデスクトップに出る (node_variants.md 3.5 の 4)。
- **ペットの V0**: 引っ越し (状態の移動、pet_design.md V1) を実装する前に、
  家の箱で 1 匹走らせて窓をどの画面にも出せば「どこにでも居る」を
  見せられる。契約を詰める前のデモとして安い。

## 実装の順番 (案)

ヘッドレス機の実物を待たず、**Tab5 → NARYA v4 の間で試せる**。

1. 送り側: display_p4 にキャンバス 1 枚の capture 経路 (全画面 capture の
   隣に、pid → キャンバスの取り出し)。差分矩形か丸ごと RGB565 を LAN に
   流す。H.264 はチップに 1 本なので使わず、まず生の矩形で。
2. 受け側: 代理アプリ (`remote_window.app.rb`)。画像を自分のキャンバスに
   貼り、窓の大きさを送り側のキャンバスに合わせる。マウス・キーを送り側
   へ返す (/ws の入力規約と同形、宛先 pid つき)。
3. 送り側: 特定 pid への入力注入 (フォーカス中のアプリ宛ではなく)。
   `_set_hid_target` の隣に pid 指定の口。
4. 発見: 送り側のアプリ一覧 (dev_remote_ctl の /app/list) を受け側の
   ランチャーか「隣の機体」窓に出し、そこから窓を開く。Asterism の
   liveliness に載せ替えるのは zenoh 導入後。
5. Retro を受け側にする (RGB332 減色、UART 越しの帯域を実測)。
