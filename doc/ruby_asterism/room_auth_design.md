# 部屋の入り方の設計 (署名つきの鍵と席の証明書) の整理

> 状態: 参照 | 更新: 2026-10-19 | ブラウザ版が部屋のリンクで Asterism の網に入るしくみ (G2・0.3.0 の席・0.3.9 の入り直し) を、よくある方式と比べて整理した。部品はどれも定番。zenohd の ACL を動きながら変えられない前提では、席の証明書を貸し出す形が妥当 (2026-10-19 ユーザ)

関連: `game_rooms_comparison.md` (作る前に定番の部屋の仕組みと比べた記録)、asterism-console の `docs/rooms.md` (部屋・鍵・席・門の仕様)、`lib/relay/room_door.rb` (門の実装)、`lib/relay/room_token.rb` (鍵の形)。

## 1. しくみの要約

1. console が、部屋の ID・枠 (`01`〜`08`)・期限・人数の上限を書いた鍵を作り、signer が Ed25519 で署名する。鍵はリンクのフラグメント (`#room=<鍵>`) で配る。フラグメントはサーバに送られない。
2. ブラウザ版は、部屋ごとの秘密を作ってブラウザに記憶し、`POST /room/seat` の本文で鍵と秘密を門に送る。門は `部屋:秘密` の SHA-256 で席の表を引き、席 (例 `wasm-0103`) を返す。同じ秘密には同じ席を返す。
3. ブラウザ版は `wss://<router>/room?t=<鍵>` を開き、最初のメッセージで秘密を送る。門は鍵を公開鍵だけで確かめ、席が決まってから、**その席の証明書で zenohd の mTLS の待ち受けにつなぐ**。WebSocket と TLS の形式を変換して、両方向に流す。
4. zenohd の ACL は、席の証明書の名前 (ノード ID) ごとに、その枠のキーの範囲 (`room/<slot>/**`) に書き込みを絞る。
5. 門は、鍵の期限・部屋が閉じられたとき・枠が別の部屋に渡ったときに切る。同じ秘密の席の要求が来たら、席に残る古い接続を切る (入り直し、0.3.9)。

鍵・秘密・そのハッシュは、URL にもログにも出さない。

## 2. 部品はどれもよくある形

| 部品 | 似ている例 |
|---|---|
| 期限つきのリンクで入る (リンクを持つ人だけが入れる) | 会議ツールの会議リンク、共有ドキュメントの「リンクを知っている人」、オブジェクトストレージの期限つき URL |
| 署名つきの鍵を、発行元に問い合わせずに公開鍵だけで確かめる | JWT (EdDSA)、PASETO。CDN やゲートウェイがその場で検証する形 |
| 範囲と期限を書いた鍵で、サーバの設定を変えずに人を足す | NATS の利用者の鍵 (JWT)。これに倣った (`game_rooms_comparison.md` 3 章) |
| 入口で鍵を確かめてから、中の網には別の身元でつなぐ | API ゲートウェイ、入口の代理 (Envoy など)、IoT クラウドのカスタム認可 (WebSocket で来た鍵を中のポリシーに読み替える) |
| ブラウザに秘密を持たせ、切れても同じ席に戻る | オンラインゲームのロビーの再接続トークン |
| 部屋ごとに名前空間を分ける | チャットの部屋、MQTT のトピックの区切り |

## 3. 珍しいところ: 席の証明書を前もって作り、貸し出す

- zenohd のルータの ACL は、証明書の身元 (ノード ID) で権限を決める。証明書を持てないブラウザを同じ ACL に乗せるため、枠ごとに 16 席ぶんの証明書を前もって作り、門が「秘密 → 席」の表で貸し出す。
- 一般的には、その都度短命の証明書を発行する (SPIFFE、step-ca の短命証明書など) か、ブローカーの認証の拡張で鍵をそのまま権限に読み替えることが多い。証明書を貸し出す形はあまり見かけない。

## 4. なぜこの形か: zenohd は ACL を起動時に 1 回だけ読む

- zenohd 1.10.1 は ACL を起動時に読むだけで、動きながら足せない。部屋を作るたびに、その部屋の ACL を足すことができない。
- そこで、部屋の枠 (`room/<slot>/**`) と各枠の席の証明書、その ACL を前もって入れておく。部屋の開け閉めは console と門だけで完結し、zenohd を起こし直さない。
- 動的に ACL を変えられない前提では、妥当な設計と判断した (2026-10-19 ユーザ)。

### 利点

- ルータの設定を、部屋のたびに変えなくて済む。
- 証明書の身元がノード ID に結び付くので、「誰が書いたか」をルータの側で偽れない。
- 門は公開鍵だけで鍵を確かめるので、console が止まっていても部屋に入れる。

### 弱点

- 席の数が上限になる (枠あたり 16、枠は 8)。
- 席の再利用 (30 分つながっていない席を別の人に渡す) の扱いが要り、ゲームホストの側にも「同じ席の番号でも別の人かもしれない」という配慮が要る (`seat_reuse_ms`)。

## 5. ほかにありうる方法 (今の制約の外)

| 案 | 良い点 | 今使わない理由 |
|---|---|---|
| zenohd が ACL を動きながら変えられるようになったら、部屋ごとに ACL を足す | 枠や席の上限が無くなる | zenohd 1.10.1 にその機能が無い。上流の対応待ち |
| zenohd の認証・認可を、自前の拡張 (Rust のプラグイン) で差し替える | 鍵をそのまま権限に読み替えられる | Rust で拡張を書き、版の追従も続ける重さ |
| 門が Zenoh のメッセージの中身まで見て、権限を確かめる | zenohd に手を入れずに細かく絞れる | 門が Zenoh の取り決めを深く理解する必要があり、複雑で壊れやすい |
| 部屋ごとに zenohd を立てる | 部屋が完全に分かれる | VPS のメモリ (空き約 370 MB、2026-10-19) では数が出せない |

**見直しの合図**: zenohd が ACL を動的に変えられるようになったら、1 つ目の案を検討する。

## 6. 記録の位置づけ

- 鍵の形 (署名つき・範囲と期限つき) は、作る前に定番と比べて選んだ (`game_rooms_comparison.md`)。
- 席の証明書は、zenohd の制約から来た形で、ほかの案と網羅的に比べて一番と決めた記録は無い。この文書の 5 章が、その後の整理。
