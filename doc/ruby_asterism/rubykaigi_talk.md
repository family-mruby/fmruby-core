## 2. 切り口 (推奨順)

1. **本命: 「Ruby のオブジェクトモデルを網に広げると、何が言語の問題として出てくるか」**
   - dRuby の後継として、CRuby・mruby・PicoRuby・ブラウザ (wasm) にまたがる「1 つのオブジェクトの網」を作った。そこで突き当たった言語の問題を示す。
     - 何がまたげて、何がまたげないか: 値は MessagePack、例外はクラス名とメッセージ、ブロックや参照は渡らない。
     - `method_missing` / `respond_to_missing?` で、相手のメソッドの一覧 (meta) からどこまで Ruby らしく振る舞えるか。
     - 別の機体にある同じ ID のオブジェクトの同一性 (`equal?`) をどう定義するか。
   - Ruby::Box と JRuby の基調講演の流れ (隔離と、新しい場所) の次の一歩。前回の発表 (1 台の機械に複数の VM) から、
     「複数の機械を 1 つの VM のように」へつなぐ。
2. **「処理系をまたぐ Ruby の共通の部分集合」**
   - 共有の層 (`mrblib`) を CRuby と PicoRuby のコンパイラ + mruby VM の両方で動かして分かった違いを、実測で示す。
     - mruby に `Data` も `Struct` も無い。
     - `case/in` は動くが、ハッシュの型のパターンとブロックの中の束縛は動かない。
     - Regexp や `defined?` が無い。
     - 文字列リテラルの凍結 (Ruby 4)。
     - C に戻る呼び出しごとにスタックが深くなる。
   - これを「Ruby のプロファイル」(どの機能をどの処理系が持つか) として、表と試験の仕組みにまとめる。PicoRuby の不具合は上流に直しを出す。
3. **「Ruby が ROS 2 の正式な一員になる」**
   - ROS 2 に公式の Ruby は無い。rmw_zenoh の形を純 Ruby で話し、マイコンの Ruby も CRuby も `ros2 node list` に出る普通のノードにした。
   - 型の変換器 (`.msg` から純 Ruby、型のハッシュを PC で計算) も成果として見せる。
4. **AI とつなぐ**
   - 公開しているメソッドの一覧 (meta) を MCP の道具の一覧に変え、LLM のエージェントが実物の機体のメソッドを呼べるようにする (usecases.md 8)。
   - 主題にするより、締めのデモにする方が強い。

## 2.1 dRuby との比べ (本命の切り口の中心、2026-10-12)

考え方は dRuby に近い (別の場所の Ruby のオブジェクトを、手元の代理を通して呼ぶ)。違いは、「いろいろな機械が混ざる網に載せる」ために何を捨てて何を得たか。ここが本命の切り口の中心になる。

| 点 | dRuby | Asterism |
|---|---|---|
| 呼び方 | 代理 (`DRbObject`) にメソッドを呼ぶと相手に届く | 代理 (`net["node/app/obj"]`) に呼ぶと相手に届く |
| 相手で起きた例外 | 呼んだ側で例外 | 呼んだ側で例外 (`RemoteError`、クラス名とメッセージ) |
| つながり | 相手の `druby://ホスト:ポート` へ直接 TCP | Zenoh のルータ (か peer) を通る。ルータの中継でインターネットも越える |
| 相手の見つけ方 | URI を知っている (Rinda を足せば探せる) | 生存の監視 (on_join / on_leave) で出入りが分かる |
| 中身の形 | Marshal (Ruby のオブジェクトをほぼそのまま) | MessagePack (数・文字列・配列・Hash など、値だけ) |
| 参照とブロック | 渡せる (`DRbUndumped` で参照、ブロックは相手から呼び返す) | **渡さない**。値だけ。相手のオブジェクトの参照を返さず、ブロックも渡さない |
| 呼べるメソッド | 公開したオブジェクトのメソッドは基本的に何でも | `methods:` で挙げたものだけ |
| 守り | 自分で用意する (Marshal は信頼できない相手には危ない) | TLS・証明書・ACL をルータで。呼べるメソッドも絞る |
| 動く場所 | CRuby | CRuby、mruby / PicoRuby のマイコン、ブラウザ版 (wasm) |
| 呼び出しの形 | 同期 (返るまで待つ。スレッドで並べる) | 端末では非同期 + 見回り (`poll`)、CRuby ではブロックと受け取りのスレッドも |
| ほかに | Rinda (タプルスペース) | 送り合い (put / subscribe)、ROS 2 のノード、プロフィール (名前・アイコン) |

- **捨てたもの**: 参照渡しとブロック (網の向こうのオブジェクトの寿命と GC を、マイコンや知らない相手とは共有できない)、Marshal (処理系ごとに形が違い、信頼できない相手には危ない)、同期の呼び出し (マイコンで止まると画面も入力も止まる。C から Ruby へ戻る呼び出しのスタックの深さ)。
- **得たもの**: マイコン・ブラウザ・ROS 2 と同じ網で話せる、相手の出入りが分かる、インターネットを越える、守り (証明書・ACL・呼べるメソッドの限定)、網の様子を console で見て記録し巻き戻せる。
- 話の流れの案: 「dRuby は 20 年前に Ruby のオブジェクトを網に広げた。同じことをマイコンとブラウザと ROS 2 が混ざる網でやると、何を捨てる必要があったか」。聴き手の多くが dRuby を知っているので、入口として分かりやすい。

## 2.2 Rinda (+ dRuby) との比べ (2026-10-12)

dRuby の上の Rinda は、タプルスペース (`Rinda::TupleSpace`: write / take / read / notify) と、相手を見つける仕組み (`Rinda::RingServer` / `RingFinger`: UDP の同報で TupleSpace を探す) を持つ。Asterism (Zenoh) の送り合いと生存の監視は、役割が近い。

| 点 | Rinda (dRuby の上) | Asterism (Zenoh の上) |
|---|---|---|
| 置き場 | 1 つの TupleSpace (1 つのプロセスの中) に全員が書き、全員が読む | 置き場は無い。送り手が `put` すると、その時点の購読者に届く (残すなら Zenoh の storage を足す) |
| 書く | `write(tuple, 期限)`。期限が切れると消える | `Asterism.session.put(key, value)` (キーごと) |
| 探す・待つ | `read` / `take(pattern)`。合うものが来るまで止まって待つ | `subscribe(キーの式)` で、届いたら知らされる (見回りで受け取る)。止まって待つ形ではない |
| 取り出す (他の人に渡さない) | `take` は 1 つの tuple を 1 人だけが取る (原子的) | **無い**。届いたものは購読者全員に届く。1 人だけに渡すには、呼び出し (オブジェクト) で受け持つ |
| 条件の書き方 | tuple のパターン (nil は何でも、クラス・正規表現・範囲で `===`) | キーの式 (`*`・`**`) で、どのキーかを選ぶ。値の中身での絞り込みは受け取った側で |
| 変化を知る | `notify(event, pattern)` (write / take / delete) | `subscribe` (put / delete)、生存の監視 (on_join / on_leave) |
| 相手を見つける | RingServer に UDP の同報で問い合わせ (同じ網の中) | 生存の印 (liveliness)。ルータを通るので網の外 (インターネット越し) も同じ |
| 期限・生存 | tuple の期限と更新役 (renewer) | 生存の印は、つないでいる間だけある (切れると消える) |
| 一番の弱み | TupleSpace のあるプロセスが止まると全部止まる。守り (認証・暗号) は自分で | 1 人だけに取り出す仕組みが無い。順番の保証はキーごと |
| 守り | 自分で用意 | TLS・証明書・ACL |

- **言えること**: Rinda は「共有の黒板 (1 か所) に書いて取る」、Asterism (Zenoh) は「網に流して、欲しい人が受ける」。Asterism には置き場と `take` が無いので、「仕事を 1 人に配る」(作業の列) は、Rinda なら `take` 1 行、Asterism では受け持ちのオブジェクトを 1 つ置いて呼び出しで配る。
- **発表で使える問い**: 「Rinda の `take` を、マイコンとブラウザが混ざる網でやると何が要るか」(原子的に 1 人へ渡すには、置き場の持ち主が要る = 中央が要る)。dRuby との比べ (2.1) と合わせて、「何を捨てて何を得たか」の 2 枚目にできる。
- 作れそうなもの: Asterism の上に「小さな TupleSpace のオブジェクト」(write / take / read を公開する) を 1 つ置けば、Rinda の書き味を網で再現できる。置き場はそのオブジェクトの持ち主 (1 か所) になる。

## 3. 構成の案 (1 を主題にする場合)

1. **つかみ**: asterism-console のグラフに、会場の機体・ROS 2・PC の Ruby が並ぶ。ブラウザのボタンで Tab5 がしゃべる。
2. **問い**: 「Ruby のオブジェクトを網の向こうに置くと、言語の何が壊れるか」。
3. **本体**: 言語の論点を、実装の判断と実測の数字で示す。
   - ポーリングで受け取る形に統一した理由: C から Ruby へ戻る呼び出しのスタック、GVL。
   - 処理系ごとの違いの表。
4. **持ち帰るもの**: 共通の部分集合の表と試験、PicoRuby への上流の直し、gem (asterism)。
5. **締め**: AI のエージェントが網の機体を呼ぶ。

## 4. 発表までに用意するもの
