## 2. 切り口 (推奨順)

1. **本命: 「Ruby のオブジェクトモデルを網に広げると、何が言語の問題として出てくるか」**
   - dRuby の後継として、CRuby・mruby・PicoRuby・ブラウザ (wasm) にまたがる「1 つのオブジェクトの網」を作った。そこで突き当たった言語の問題を示す。
     - 何がまたげて、何がまたげないか: 値は MessagePack、例外はクラス名とメッセージ、ブロックや参照は渡らない。
     - `method_missing` / `respond_to_missing?` で、相手のメソッドの一覧 (meta) からどこまで Ruby らしく振る舞えるか。
     - 別の機体にある同じ ID のオブジェクトの同一性 (`equal?`) をどう定義するか。
   - Ruby::Box と JRuby の基調講演の流れ (隔離と、新しい場所) の次の一歩。前回の発表 (1 台の機械に複数の VM) から、
     「複数の機械を 1 つの VM のように」へつなぐ。
2. **「処理系をまたぐ Ruby の共通の部分集合」**
   - 共有の層 (`mrblib`) を CRuby と PicoRuby のコンパイラ + mruby VM の両方で動かして分かった違いを、実測で示す。
     - mruby に `Data` も `Struct` も無い。
     - `case/in` は動くが、ハッシュの型のパターンとブロックの中の束縛は動かない。
     - Regexp や `defined?` が無い。
     - 文字列リテラルの凍結 (Ruby 4)。
     - C に戻る呼び出しごとにスタックが深くなる。
   - これを「Ruby のプロファイル」(どの機能をどの処理系が持つか) として、表と試験の仕組みにまとめる。PicoRuby の不具合は上流に直しを出す。
3. **「Ruby が ROS 2 の正式な一員になる」**
   - ROS 2 に公式の Ruby は無い。rmw_zenoh の形を純 Ruby で話し、マイコンの Ruby も CRuby も `ros2 node list` に出る普通のノードにした。
   - 型の変換器 (`.msg` から純 Ruby、型のハッシュを PC で計算) も成果として見せる。
4. **AI とつなぐ**
   - 公開しているメソッドの一覧 (meta) を MCP の道具の一覧に変え、LLM のエージェントが実物の機体のメソッドを呼べるようにする (usecases.md 8)。
   - 主題にするより、締めのデモにする方が強い。

## 3. 構成の案 (1 を主題にする場合)

1. **つかみ**: asterism-console のグラフに、会場の機体・ROS 2・PC の Ruby が並ぶ。ブラウザのボタンで Tab5 がしゃべる。
2. **問い**: 「Ruby のオブジェクトを網の向こうに置くと、言語の何が壊れるか」。
3. **本体**: 言語の論点を、実装の判断と実測の数字で示す。
   - ポーリングで受け取る形に統一した理由: C から Ruby へ戻る呼び出しのスタック、GVL。
   - 処理系ごとの違いの表。
4. **持ち帰るもの**: 共通の部分集合の表と試験、PicoRuby への上流の直し、gem (asterism)。
5. **締め**: AI のエージェントが網の機体を呼ぶ。

## 4. 発表までに用意するもの

- 処理系の違いの表を、文書と試験の形でまとめる (今は report に散らばっている)。
- PicoRuby のコンパイラの `case/in` の不具合 (ハッシュの型のパターン、ブロックの中の束縛) を上流に報告して直す。
- 性能の数字 (往復の時間、送受信の速さ)。plan.md の「gem の課題」7。
- 英語の文書 (同じく 2)。CFP の審査で読まれる。
- meta → MCP の最小の橋 (締めのデモ用)。
