# 部屋と NAT 越えの仕組みの比較 (ゲーム向けの定番と Asterism)

> 状態: 参照 | 更新: 2026-10-14 | G2 の「部屋」を作る前に、ほかの言語の定番の仕組みと比べた記録。入り方・NAT の越え方・状態の同期の 3 点で比べ、G2 に取り込む点を決める

## 1. Ruby の中

Ruby で「部屋を作り、NAT を越えて対戦する」専用の仕組みは、ほとんど無い。

- dRuby・Rinda (Ruby の標準): 遠くの Ruby オブジェクトを呼ぶ・共有の場所に書いて読む。相手の URI を知って直接繋ぐ。部屋や期限つきの入場は無い (asterism の `docs/comparison.md`)。
- Action Cable・AnyCable (Rails): WebSocket のチャネルで人を分けて配る。ゲーム専用ではなく、部屋・入場・対戦相手探しはアプリが書く。
- Rubame (WebSocket の小さなゲームサーバ、2013 年で止まっている)、GS2 の Ruby の部品 (外部のサービスの客の部品、2016 年) は、今使える選択肢ではない。
- Zenoh の Ruby の部品は、Asterism の gem 以外に見つからない。

## 2. ほかの言語の定番

| | Colyseus | Nakama | Photon (Realtime・Fusion) | Unity Lobby + Relay | WebRTC + TURN (PeerJS・geckos.io・coturn) | NATS | Asterism (G2 の部屋) |
|---|---|---|---|---|---|---|---|
| 言語 | Node.js (TypeScript) | Go (サーバの中のロジックは Lua・TypeScript・Go) | C# 中心 (Unity) | Unity (C#) | ブラウザの JavaScript ほか | Go のサーバ、客の部品は各言語 (Ruby もある) | Ruby (CRuby・mruby・PicoRuby)、下は Zenoh |
| 置き場所 | 自分のサーバ、有料のクラウドもある | 自分のサーバ、有料のクラウドもある | 外部のクラウドが基本 | Unity のクラウドだけ | 自分のサーバ (TURN) | 自分のサーバ | 自分のサーバ (O1) |
| ライセンス・料金 | MIT | Apache 2.0 | 同時接続数で課金 (100 人まで無料、500 人で月 125 ドル、2026 年の公表値) | 使った量で課金 | 部品は自由、TURN の中継の通信料は自分持ち | Apache 2.0 | MIT |
| 部屋 | 1 つの部屋の型から部屋を何個でも作る。条件で振り分ける対戦相手探し | 部屋 (マッチ)・対戦相手探し・チャット・ランキング・アカウント・保存まで全部入り | 部屋・ロビー・対戦相手探し | Lobby (部屋の一覧と参加) と Relay (中継) が別のサービス | 無い (自分で作る) | 名前空間 (アカウント) と送ってよい宛先の範囲 | 期限つきの名前空間 (G2) |
| 入り方 | アプリが書く | アカウント (匿名・端末 ID・外部の ID) | アプリの ID と認証 | 匿名の認証のあと、ホストが出す参加コードを共有して入る | 合図の役のサーバを自分で用意 | 範囲と期限つきの署名された鍵 (JWT) を配る。サーバの設定を変えずに人を足せる | 範囲と期限つきの署名された鍵をリンクで配る (下の 3) |
| NAT の越え方 | サーバに中継させる (WebSocket) | サーバに中継させる | 中継のサーバ | Relay が中継する | P2P で直接、だめなら TURN で中継 (1-2 割は TURN が要るという業者の見積もり) | サーバに中継させる | サーバに中継させる (全員が VPS に外向きに繋ぐ) |
| 状態の同期 | サーバの状態を差分で自動配信 | サーバの中のゲームの処理 (権威を持つ方式) | 予測と巻き戻しなど速い対戦向け | 無い (上に乗せる Netcode の仕事) | 無い | 無い (配信の土台) | オブジェクトの呼び出しと配信 (状態の同期は無い。下の 4) |
| マイコン | 無い | 無い | 無い | 無い | 無い | 客の部品に小さいものはある | ESP32 (P4・S3) で動く、TLS も |
| 向く遊び | ブラウザの対戦、部屋の多いカジュアル | アカウントや経済のあるゲーム全般 | 速い実時間の対戦 | Unity で友だちと遊ぶ | 遅れを小さくしたい P2P | ゲームに限らない配信と権限 | ターン制や遅れを許す遊び、機械と人が混ざる網 |

読み取れること:

- 入り方は、Unity の参加コードや NATS の範囲と期限つきの鍵が、G2 の部屋の案と同じ考え方。定番の方向に沿っている。
- NAT は、ほとんどがサーバに中継させて越えている。P2P は遅れが小さいが、1-2 割は TURN の中継が要り、作りが複雑。Asterism が中継で済ませるのは普通の選び方。
- Asterism に無いもの: 状態の自動の同期 (Colyseus)、速い対戦の予測 (Photon)、アカウント・ランキング・経済 (Nakama)。遅れを許す遊びまでの範囲では無くても成り立つ。
- Asterism だけにあるもの: マイコン・ブラウザ・CRuby・ROS 2 が同じ網に入る、Ruby のオブジェクトを呼ぶ形、自分のサーバで全部持てる。

## 3. G2 に取り込む点

- **部屋のパスワードを「範囲と期限が書かれた署名つきの鍵」にする** (2026-10-14 ユーザ、良さそうとの判断): console が、部屋 (名前空間)・期限・上限 (人数など) を書いた鍵に署名して配る。入口 (door) は console の公開鍵で署名を確かめるので、毎回 console に問い合わせなくてよい。部屋を早く閉じるための取り消しの一覧 (または部屋の削除) は別に持つ。鍵はリンクのフラグメントで渡し、推測できない長さにする。NATS の利用者の鍵 (JWT) と同じ考え方。console にハッシュだけを持つ案との比較は G2 のステップ 1 で行う。
- **鍵に部屋の中の役割は書かない** (2026-10-14 ユーザ): 鍵は「部屋に入れる」ことだけを表す。役割は部屋に入ってから決める (下の 4)。
- 口で伝えられる短い参加コード (Unity の参加コード) は、総当たりに弱いので入れない (パスワードは UUID くらいの長さの乱数とする 2026-10-14 の決定と合わない)。

## 4. 将来: 状態の同期と麻雀の部屋

- やりたいこと (2026-10-14 ユーザ): 簡単な麻雀の部屋。雀魂の友人戦のように、**部屋に入ってから、卓に座る (プレイヤー) か観戦に回るかを選ぶ**。
- **鍵は部屋への入場だけ**。ACL が守るのは「その部屋の中だけ」まで。役割は部屋の中の仕組みが決める。
- **部屋の係** (状態を持つオブジェクト、VPS の CRuby か誰か 1 台): 座る・立つ・観戦の受付と席の数 (4 人) の管理、対局の進行 (手番・点数)、見せる範囲の制御 (場は全員に配り、手牌はその席の人にだけ渡す)。Colyseus の「サーバの状態を配る」に当たる。
- **手牌の守り方**: 部屋の中は全員が同じ鍵なので、ACL では人ごとに分けられない。席に座ったとき、部屋の係がその席だけの乱数 (席の合言葉) を返し、手牌を見る・打牌するときはそれを添えて呼ぶ。知らない観戦者や他のプレイヤーには手牌を渡さない。
- **観戦**: 場の配信だけを流す。数手遅らせて流すかは部屋の係で決められる。
- G2 の部屋 (鍵と ACL) は「部屋に入れる」ところだけに集中し、麻雀はその上に乗る部屋の係のアプリとして作る (オセロの「誘う・受ける」を、席と観戦に広げる形)。
- **麻雀の処理は riichi_engine を使う候補** (2026-10-14 ユーザ): rubygems の `riichi_engine` (0.1.0、2026 年、MIT、Ruby 3.2 以上、頼る gem は zeitwerk だけ、Ruby で約 3,700 行)。純 Ruby のリーチ麻雀のエンジンで、局の進行 (山・配牌・自摸・打牌・鳴き・リーチ)、和了と役の判定、点数と順位、CPU の打ち手 (Easy・Normal・Hard) を持つ。入口は `RiichiEngine::API` の 1 つで、安定を約束する範囲が文書で決まっている。保存・配信・ユーザは使う側が持つ作り (Adapter 契約)。
  - 計画の作りとの合い方: 局の状態 (`RoundState`) を JSON に書き出し・読み戻しできる (ゲームホストの「起動し直しても続けられる」に使える)。席ごとの「今できる操作の一覧」(`available_round_actions`) と、操作を当てて次の状態を返す関数 (`apply_round_action`) があり、プレイヤーから来た操作は一覧にあるものだけ受ければよい。4 人そろわないときは CPU の打ち手で席を埋められる。
  - 気をつけること: 出たばかりの 0.1.0 で作者は 1 人。使う版を固定し、ゲームホストの側に局を一通り回す試験を持つ。見える範囲 (自分の手牌と場、観戦者は場だけ・遅らせる) はエンジンに無いので部屋の係が作る。端末 (mruby・PicoRuby) では動かない (CRuby の前提) が、ゲームホストは VPS の CRuby なので問題ない。卓の画面は別に作る (ブラウザ版か Tab5・P4 のアプリ)。

## 5. ゲームホスト (部屋の係) は常に起きていて安定している必要がある (2026-10-14 ユーザ)

部屋の係が落ちたり眠ったりすると、その部屋の対局が丸ごと止まる。そこで次の形にする:

- **置き場所は VPS の CRuby のプロセス**。console の一式と同じく docker と systemd の下で動かし、落ちたら自動で起動し直し、VPS の再起動でも戻る。誰かの端末やブラウザ版に置く形は、抜けた・電池が切れた時点で止まるので、家の LAN で遊ぶときの手軽な形としてだけ残す。
- 1 つのプロセスで部屋をいくつも持つ。VPS はメモリ 2 GB なので、部屋の数と人数に上限を置く。
- **起動し直しても続けられる**: 部屋の状態 (席・手番・点数・山など) を変わるたびにファイルに書き、落ちて起動し直してもそこから再開する。console の毎日のバックアップ (0.1.3) にも入れる。
- **ルータの起動し直しに耐える**: Apply で zenohd が起動し直しても、G1.5b のつなぎ直しで数秒で戻る (同じ gem を使う)。
- **プレイヤーの途切れに耐える**: 数秒〜数十秒の途切れは席を空けずに待つ (オセロの 60 秒待ちと同じ考え)。長く戻らないときの扱い (自動で打つ・抜けた扱い) はゲームごとに決める。
- **見張り**: ゲームホストも console の図に出し、死活と部屋の数を管理者の画面から見られるようにする。
- **更新**: console と同じく image にして update.sh の流れで更新する。対局の途中の更新は避けられるようにする (「誰もいないときに反映」と同じ考え)。
- 麻雀の部屋が最初の利用者。

## 6. オンライン麻雀を作る見込みと Step (2026-10-14)

知り合いどうしで遊べるオンライン麻雀は、今の Asterism の上に作れる見込み。ターン制なので、VPS を通る 0.1-0.2 秒の遅れは遊びに影響しない。

- **揃っているもの**: VPS の zenohd に全員が外向きに繋ぐ形 (NAT を越える)、G2 の部屋 (署名つきの鍵・期限・16 人・部屋どうしは見えない)、G1.5b のつなぎ直し、Asterism の呼び出し (手を送る) と配信 (場を配る)、riichi_engine (局の進行・役・点数・CPU の打ち手・状態の書き出し)、console の図の部屋の表示。
- **作るもの**: (1) 卓の画面 (手牌・河・鳴き・点数・ポン/チー/カン/ロン/ツモ/リーチの操作。牌は最初から画像で出す。素材は自由に使える牌の画像を使い、配ってよいか (再配布・改変・クレジットの要否) を確かめてから取り込む。卓は 640x360 を基準にする。P4 (P4-Nano の HDMI・Tab5) は 1280x720 を 2 倍に拡大して使っており、アプリが使える最大は 640x360 (全画面のエディタと同じ)。ブラウザ版も設定で 640x360 にできるので、同じ画面がどちらでも動く)。(2) ゲームホスト (riichi_engine を包み、席と観戦、席ごとの見え方、手番の待ち時間と時間切れの自動の打牌、状態の書き出し、空いた席の CPU)。(3) 鳴きの割り込み (捨て牌の直後にほかの 3 人がポン・ロンなどを選ぶ短い時間と優先順位。riichi_engine の `resolve_pending_action` を使い、待ち時間と途切れた人の扱いはゲームホストが持つ)。
- **気をつけること**: 山と乱数はゲームホストだけが持ち、手牌は席の合言葉でその人にだけ渡す (知り合いどうしならこれで十分)。riichi_engine は 0.1.0 なので局を回す試験をこちらで持ち、誤りは作者に報告する。卓 2-3 つなら VPS (2 GB) に余裕がある。

| Step | 内容 | 目安 |
|---|---|---|
| Step 1 | ゲームホスト: CPU 3 人と自分 1 人で局が回る。卓は牌の画像で出す (640x360、まずブラウザ版で) | 2-3 週間 |
| Step 2 | 4 人の人間、鳴きの割り込み、観戦、つなぎ直し | 1-2 週間 |
| Step 3 | 卓の画面の仕上げ (鳴き・点数・局の結果の表示、P4・Tab5 で動かす) | 1-2 週間 |

Step 1 で「CPU 相手に自分が打てる」ところまで行けば、作りに無理がないかが早めに分かる。
