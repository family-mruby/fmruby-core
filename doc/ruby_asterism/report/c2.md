# C2 報告: ruby-asterism への分割

> 状態: 完了 (検収待ち) | 更新: 2026-10-08 | instruction_c2.md の実装と確認の記録。Asterism を 3 つのローカルのリポジトリ (asterism / asterism-zenoh / picoruby-asterism-zenoh) に分け、Ruby だけで書いた層の正を asterism に移した。fmruby-core は PIN ファイルで 2 つを取り込み、同梱の型は rake setup が storage の木に写す。受け入れ条件 1-5 を満たした。止まる条件には当たらなかった。zenoh-pico の peer どうしの liveliness_get が終わらない件を新しい試験で見つけた (8 章)

## 1. 結果の要約

- 3 つのリポジトリを `family-mruby/` の下に作り、それぞれ `main` にコミットした。remote は付けていない。
  - `asterism/` (C1 のリポジトリを作り直した): 純 Ruby の層の正。`mrblib/` 1 つが mrbgem `picoruby-asterism` と CRuby の gem
    `asterism` の両方になる (写しは無い)。同梱の型、型の変換器、型の試験もここ。
  - `asterism-zenoh/` (新規): CRuby の C 拡張 (zenoh-c)。C1 の `asterism/asterism-zenoh/` を根に移した。
  - `picoruby-asterism-zenoh/` (新規): mruby / PicoRuby の zenoh-pico の mrbgem。fmruby-core の `lib/add/` から移した。
    zenoh-pico の PIN もこちらに移した。
- fmruby-core: `lib/add/picoruby-asterism/`、`lib/add/picoruby-asterism-zenoh/`、`lib/add/ZENOH_PICO_PIN`、
  `test/asterism_msgs/`、`flash/usr/share/asterism/msgs/` を git から外し、`lib/add/ASTERISM_PIN` と
  `lib/add/PICORUBY_ASTERISM_ZENOH_PIN` で取り込む形にした。
- 親リポジトリ: `.gitignore` に 2 行、`tools/fmrb_ros2_types.rb` は asterism の `tools/ros2_types.rb` を呼ぶだけにした。
- ファームに入るコードは変わっていない (mrblib は 1 バイトも同じ、C はヘッダの注釈だけ)。P4 (NARYAv4) の
  fmruby-core.bin は R3 と同じ 0x62cc90 バイト。

```
  mrblib/           asterism.rb cdr.rb future.rb proxy.rb ros.rb  (正)
  asterism.gemspec  CRuby の gem asterism
  lib/asterism.rb   msgpack、asterism/zenoh、../mrblib/*.rb、asterism/cruby.rb の順に読む
  lib/asterism/cruby.rb, version.rb
  data/msgs/        同梱の 62 の型 + NOTICE + LICENSE-Apache-2.0.txt
```

- コミット: `0ad30b0` (C1) の上に `3e69d93` (この段)。C1 の履歴を残したので、最初のコミットには asterism-zenoh の
  C 拡張が入っている (どちらも MIT、同じ作者)。
- `rake test:msgs` は CRuby だけで回る (Zenoh も docker も要らない)。`rake test:objects` は asterism-zenoh を
  `ASTERISM_ZENOH_DIR`、隣の `../asterism-zenoh` (rake compile 済み)、入れた gem の順に探し、無ければ理由を出して止まる。
- `tools/ros2_types.rb` は `--image` (または `ASTERISM_ROS2_IMAGE`) で渡した ROS 2 Jazzy の像から型を作り直す。
  data/msgs の NOTICE と許諾の文は消さない (パッケージのディレクトリだけ作り直す)。親の像
  `fmruby-ros2-jazzy-zenoh:local` で作り直した結果、data/msgs と ros2_jazzy の定義は 1 バイトも変わらなかった
  (type_hashes.txt の「誰が書いたか」の 1 行だけが変わった)。

```
picoruby-asterism-zenoh/

  host_test/MRUBY_PIN, build_config.rb, listener.rb, test_zenoh.rb
```

- コミット: `7308ccf` (1 つ)。gem の中身は fmruby-core `0eecb74d` の `lib/add/picoruby-asterism-zenoh/` と同じで、
  変えたのは注釈 (PIN の場所、許諾のヘッダ) と README。
- 単独の検査 (`rake`): ZENOH_PICO_PIN の zenoh-pico と、host_test/MRUBY_PIN の mruby (PicoRuby の submodule が

  39 項目すべて通る。ESP-IDF の port はここでは compile しない。

## 3. fmruby-core の取り込み方

| 物 | PIN | 取得先 (gitignore) | 上書きの環境変数 |
|---|---|---|---|
| asterism | `lib/add/ASTERISM_PIN` (`git@github.com:ruby-asterism/asterism.git`、main、3e69d93) | `vendor/asterism` | `ASTERISM_DIR` |
| picoruby-asterism-zenoh | `lib/add/PICORUBY_ASTERISM_ZENOH_PIN` (`git@github.com:ruby-asterism/picoruby-asterism-zenoh.git`、main、7308ccf) | `vendor/picoruby-asterism-zenoh` | `PICORUBY_ASTERISM_ZENOH_DIR` |
| zenoh-pico | picoruby-asterism-zenoh の `ZENOH_PICO_PIN` (1.10.1、e1ab223a) | `vendor/zenoh-pico` | `ZENOH_PICO_DIR` (従来どおり) |

- `rake asterism:setup` が 2 つを ssh で clone し、PIN のコミットに合わせる (浅い clone。先が進んでいればコミットを
  直接 fetch)。`rake setup` (どのビルドからも呼ばれる) は必要なら自分でこれを呼ぶ。PICORUBY_TI_PIN と同じ形。
- 上書きの環境変数があれば取得はせず、その checkout をそのまま使う。HEAD が PIN と違うか未コミットの変更があると、
  `rake` がその旨を出す (ビルドは止めない)。作業中はすべて `ASTERISM_DIR=../asterism
  PICORUBY_ASTERISM_ZENOH_DIR=../picoruby-asterism-zenoh` でビルドした (HEAD は PIN と同じ)。
- ZENOH_PICO_PIN は picoruby-asterism-zenoh に移した。gem が zenoh-pico の内側 (セッションの transport、TCP の link)
  に手を入れているので、版は gem と一緒に動くべきもの。`rake zenoh:setup` は gem の checkout から読む。
- `rake setup` が写すもの:
  - picoruby の mrbgems へ: picoruby-asterism-zenoh の `mrbgem.rake include src ports README.md LICENSE`
    (+ 従来どおり zenoh-pico の src/include ほか)、asterism の `mrbgem.rake mrblib README.md LICENSE`。
    .git、host の試験、Rakefile、vendor は写さない。
  - storage の木へ: asterism の `data/msgs` を `flash/usr/share/asterism/msgs` に (下の 4 章)。
- `rake asterism:test`: 使っている asterism の checkout で型の試験 (`test/msgs/run.rb`) を回す。`rake test` からは
  外した (CI が非公開のリポジトリを取れないため)。
- 取得の経路は、PIN の repo を手元の `file://` に置き換えた写しの木で `rake asterism:setup zenoh:setup` と
  `rake asterism:test` を回して確かめた (2 つの PIN のコミットに着地し、zenoh-pico の PIN を gem の checkout から
  読み、型の試験が通った)。`git ls-remote` で 3 つの GitHub のリポジトリに ssh で届くこと (空であること) も確かめた。

## 4. 同梱の型が storage に届く道

- 決めたこと: **写しを追跡しない**。`rake setup` が asterism の `data/msgs` を `flash/usr/share/asterism/msgs` に写し、
  そのディレクトリは gitignore にした。`flash/help/` (sig/ から作る) と同じ扱い。
- これで「flash/ の追跡分 = 配布してよいもの」は崩れない (型は追跡されないが、生成物としていつも木にある)。
  - sim は flash/ をそのまま読むので、ビルドのたびに新しい型が見える。
  - 機体の storage の像は flash/ を写した作りかけの木から作るので、full flash で型が入る。
  - NOTICE と Apache-2.0 の文が型と一緒に `/usr/share/asterism/msgs/` に入る (littlefs で 4 ブロック増える見込み)。
- 変わる点: ブラウザ版 (wasm) の bundle は追跡分だけを束ねるので、型は入らなくなった。wasm は Asterism を
  リンクしていないので、使い道は元から無かった。
- app_only の焼き直しでは storage は変わらない。P4-Nano には tab5_fs の push で NOTICE と許諾の文を足した
  (62 の型は R3 で置いたものと同じ大きさで、push は飛ばした。中身も同じもの)。

## 5. ライセンスの扱い

- 各リポジトリに MIT の LICENSE (Copyright (c) 2026 Katsuhiko Kageyama)。これまでのコードは全部この作者のコミットで、
  mrbgem.rake も MIT と書いていた。fmruby-core 自体は GPL-3.0 だが、移したのは同じ作者のもので、ユーザの決定
  (MIT) どおりにした。
- zenoh-pico から作ったファイル: 元の条件 (EPL-2.0 OR Apache-2.0、Copyright ZettaScale Technology) を確かめ、
  先頭に元の著作権・SPDX・「このリポジトリの MIT ではない」を書いた。
  - `src/zp_tcp_posix.c` (元 tcp_posix.c、2026)、`src/zp_network_posix.c` (元 unix/network.c、2022)、
    `ports/esp32/zp_tcp_esp32.c` (元 tcp_esp32.c、2026)、`include/zenoh_espidf_platform.h` (元 espidf.h の型の並び、2022)。
  - `ports/esp32/zp_system_esp32.c` は上流のファイルを `#include` して割り当ての 3 関数だけ差し替える自前のコードなので
    MIT のまま。`include/zenoh_generic_config.h` は zenoh-pico の設定の名前に値を入れた自前の設定で、文や構造を
    写していないので MIT のまま (境目に近いのはこの 1 つ)。
- zenoh-c (CRuby) の C 拡張は自前のコード (MIT)。zenoh-c はリポジトリに含めず `rake zenoh_c:fetch` で取る。
- ROS 2 の型: 元のパッケージ (std_msgs、geometry_msgs、sensor_msgs、builtin_interfaces、service_msgs、
  example_interfaces) は、像の package.xml で全部 Apache License 2.0 と確かめた。asterism の NOTICE に出所と
  対象 (tools/ros2_jazzy、data/msgs、test/msgs の照合用の値) を書き、data/msgs に NOTICE と Apache-2.0 の全文を置いた。
  生成したファイルの先頭には元から「どの定義から作ったか」が書いてある (改変の表示)。
- gemspec の `license` は MIT のままにし、data/msgs が Apache-2.0 であることは注釈と同梱の NOTICE で示した
  (gem の公開の形は後で決めるため)。
- fmruby-core の THIRD_PARTY_LICENSES.md に 3 つ (Asterism、zenoh-pico、ROS 2 の定義) を足した。zenoh-pico は
  Z1 からファームに入っていたのに載っていなかった。
- 判断を親に返す点 (止まるほどではない): fmruby-core (GPL-3.0) は zenoh-pico を EPL-2.0 OR Apache-2.0 のどちらで
  使うか。GPL-3.0 と組めるのは Apache-2.0 の側なので、そちらを選ぶのが自然だが、THIRD_PARTY_LICENSES.md には
  選択を書かず、両方の名前だけ書いた。Z1 からの話で、C2 で新しく生じたものではない。

## 6. CI への影響

CI の設定は変えていない。`.github/workflows/build.yml` の 4 つの仕事への影響:

| 仕事 | 影響 |
|---|---|
| test-host (`rake test`) | 通る。型の試験を `rake test` から外したので、Asterism のリポジトリを取りに行かない (手元で、上書きの環境変数なしで `rake test` が exit 0) |
| spinel-gen (`rake spinel:gen`) | 通る。setup を通らない |
| build-esp32 (`rake build:esp32`、.env の NARYAv3 = S3) | **落ちる**。`rake setup` が非公開のリポジトリを ssh で clone しようとして失敗する (S3 は Asterism をリンクしないが、setup は全部の gem を写す) |
| build-linux (mruby / spinel) | **落ちる**。同じ理由。Linux は Asterism をリンクする |

直し方の候補 (どれも利用者から見た動きの選択を含むので、親とユーザが決める):
1. リポジトリを公開して、PIN の repo を https にする (CI はそのまま通る)。
2. CI に読み取り用の鍵 (deploy key) を置く (CI の設定の変更)。
3. `rake setup` に Asterism を外す道を作り、Linux / P4 のビルド設定から gem を外す (CI のビルドは Asterism 抜きになる)。

## 8. 見立てと違った点・見つけたこと

- **zenoh-pico の peer どうしの `liveliness_get` が終わらない**。picoruby-asterism-zenoh の新しい host の試験で、
  待ち受け側がトークンを持っていても答えが来ず、時間制限 (1000 ms) を過ぎても `done?` が 6 秒以上 false のままだった。
  `liveliness_watch` は同じトークンを報告する。Z3 で確かめたのはルータ経由。C2 の範囲 (分割) の外なので直して
  いない。試験からは外し、README に既知の件として書いた。
- **mruby の host のビルドには mruby-io が要る**。今の mruby では `puts` が core に無い。
- **1 つの mruby のプロセスに zenoh-pico の peer を 2 つ置けない** (2 章)。試験を 2 プロセスにした。
- C1 の README と Rakefile にあった `rake sync` / `SYNCED_FROM` / 写しの試験は、正が asterism に移ったので消した。
- 古い記述が 2 か所残っている (範囲の外なので直していない): fmruby-core `lib/add/family_mruby_linux.rb` の注釈と、
  親の `docker-compose.yml` の注釈が `lib/add/ZENOH_PICO_PIN` を指している。

## 9. 親が push する順番

PIN の取得が通るには、PIN が指すコミットが GitHub にあればよい。順番は次のとおり。

1. `asterism/` の main を `git@github.com:ruby-asterism/asterism.git` へ (3e69d93、C1 の 0ad30b0 を含む)。
2. `picoruby-asterism-zenoh/` の main を `git@github.com:ruby-asterism/picoruby-asterism-zenoh.git` へ (7308ccf)。
3. `asterism-zenoh/` の main を `git@github.com:ruby-asterism/asterism-zenoh.git` へ (08d64a2。PIN からは参照されない
   ので順番は自由)。
4. その後で fmruby-core と親の `feature/asterism-c2` (develop への merge と push は親の判断)。

1 と 2 の前に fmruby-core を push すると、上書きの環境変数なしのビルドが clone で落ちる。push の後、
`vendor/asterism` などを消して上書きなしで `rake setup` を 1 度回すと、本当の経路を確かめられる (今回は file:// で
代わりに確かめた)。
