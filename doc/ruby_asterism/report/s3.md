# S3 報告: 機体で台車を操縦し、カメラの画像を機体の画面に出す

> 状態: 完了 (検収待ち) | 更新: 2026-10-10 | instruction_s3.md の実装と確認の記録。S1 の ROS 2 の台車 (MuJoCo、カメラつき) を P4-Nano から矢印キーで操縦し、台車のカメラの JPEG (160x120、5 Hz) と odom を機体の画面に出した。JPEG は今ある公開の API (`create_image` が P4 では JPEG を SoC の復号器に渡す) と RAM の上の `/tmp` で出せたので、新しい API は要らなかった。画像は毎秒 4.9-5.0 枚、1 枚の描画 9-12 ms、内蔵 RAM は S1 のアプリと同じ水準。odom の誤差は 0.18-0.20 %・0.27 度。asterism-console で操縦中のグラフ・画像・odom の線グラフを同時に見て、MCAP に記録して巻き戻した。手順書は親リポジトリの `docker/mujoco/README.md` に足した。止まる条件には当たらなかった

## 1. 結果の要約

- 試しのアプリ: `flash/app/test/rover_cam.app.rb` / `.app.toml` (S1 の `ros2_drive.app.rb` を土台にした)。
  - 矢印キーで `/cmd_vel` を送る。**動かしている間だけ** 10 Hz で送り、止めたら 1 回だけ止めを送って黙る (操縦者は一度に 1 つ)。
  - `/odom` の位置・向き・速さ (S1 の軽い型に stamp を足したもの)。
  - カメラの最新の 1 枚を左に 160x120 で出す。右に画像の頻度 (受けた数・描いた数)、遅れ、1 枚の描画の時間、更新の 1 周の時間。
- JPEG の経路: 受けた JPEG を `/tmp/rover_cam.jpg` (PSRAM の上の RAM のファイル) に書き、`@gfx.create_image` →
  `draw_image` → `delete_image`。P4 の表示の側は CREATE_IMAGE_FROM_FILE で JPEG を見分けて SoC の復号器にかける (2 章)。
- sim: 表示の側 (graphics-audio) が PNG しか読まないので、画像の欄に JPEG の大きさ・バイト数・枚数を出す (3 章)。
- asterism-console: コードの変更なし。グラフ・Watch の画像・Plots の線グラフ・記録・時間の帯・網の巻き戻しが S3 の走りでそのまま動いた。
- 手順書: 親リポジトリ `docker/mujoco/README.md` の「The demo: drive from a board, watch on the console (S3)」。
  台車の起動から片付けまでを上から打って、そのとおりに再現できることを確かめた (5.5 節)。

## 2. JPEG を機体の画面に出す経路の調べ

### 2.1 今ある経路

| 経路 | 入口 | 中身 | S3 に使えるか |
|---|---|---|---|
| 動画の再生 (`video_open`、`display_p4_video.cpp`、`video_play.app.rb`) | ファイル (JPEG を並べた MJPEG) | 専用のタスクがファイルを自分の時計 (fps) で読み、復号して表示のタスクに渡す。開くときに最初の 1 枚の大きさを読む。終わりまで行くと止まるか先頭に戻る | 合わない。流れてくる 1 枚ずつではなく、決まったファイルを自分の速さで読む作り。毎回開き直すと再生のタスクと読み込みの区画を毎回作り直すことになる |
| `create_image` / `draw_image` / `delete_image` (と、それをまとめた `load_image`) | ファイルのパス | P4 の CREATE_IMAGE_FROM_FILE (`display_p4_task.cpp`) は**先頭が FF D8 FF なら SoC の JPEG 復号器にかけ**、PNG なら LovyanGFX で読む。結果は PSRAM の sprite。`display_p4_video.h` に「静止画にも使う」と書いてある | **使える**。指示書の前提 (PNG だけ) は P4 では古かった |
| 遠隔画面の JPEG (`rd_encoder_jpeg.c`) | 画面 | 符号化 (画面を JPEG にして送る側) | 向きが逆。使わない |

`load_image` は `sync_file` と `present` までまとめて行うので、画面を出す時機を自分で決めたいこのアプリでは、下の 3 つを直接呼んだ。

### 2.2 試した経路と実測

- 1 枚ごとに: `File.open("/tmp/rover_cam.jpg", "w")` で書く → `create_image` (同期。復号が終わって番号が返る) →
  `draw_image` → `delete_image` → 文字を描き直して `present`。flash には書かない。
- `/tmp` は P4 では PSRAM の上の RAM のファイルシステム (`fmrb_tmpfs`、容量 8 MB)。`fmrb_hal_file_resolve_path` が
  `/tmp` を flash に畳まずにそのまま渡すので、表示の側の `fopen` もそのファイルを読む。
- 実測 (P4-Nano、アプリの 2 秒ごとの記録、走りを含む約 3 分):

| 項目 | 値 |
|---|---|
| 1 枚の描画 (書き込み + 復号 + 描画 + 解放、アプリから見た時間) | ふだん 9-12 ms、最大 64 ms |
| 画像の頻度 | 受けた数・描いた数とも 2 秒ごとに 4.4-5.5 Hz (平均 約 4.95 Hz)。PC の側の記録は 41 s に 205 枚 (5.0 Hz)。1 回だけ 2 秒の間 1.5 Hz に落ちた (WiFi のつまり。PC の側は落ちていない) |
| 描けなかった枚数 | 0 (`create_image` が nil を返した回数) |
| 間引き | 描く前に次の 1 枚が来たら古い方を捨てる。受けた数と描いた数はほぼ同じで、間引きはほとんど起きていない |

- 単体の確かめ (試しのアプリを別に作って機体で動かし、確かめたあと消した): 同じ JPEG を 100 回 `create_image` /
  `draw_image` / `delete_image` すると 2.72 s (1 回 27 ms)。アプリの 10 ms より長いのは、表示の側が 1 枚ごとに 2 行
  (CREATE_IMAGE_FROM_FILE と Image store free) を INFO でシリアルに出し、間を置かずに回すとその出力に詰まるため。
  5 Hz なら効かない。
- 選んだ経路: `create_image` (今ある公開の API)。**新しい API は要らなかった**ので、止まる条件には当たらない。

### 2.3 記憶

| 状態 | 内蔵 RAM の空き (10 秒ごとのダンプ) | PSRAM の空き |
|---|---|---|
| アプリなし | 201,792 B | 9,258,064 B |
| S1 のアプリ (`ros2_drive`) | 179,912-181,472 B | 8,829,072 B |
| S3 のアプリ (`rover_cam`、画像を描いている) | 175,956-183,060 B (ふだん 180-182 KB) | 8,785,640-8,824,572 B |
| S3 のアプリを止めたあと (初回) | 201,568 B (-224 B) | 9,254,624 B (-3,440 B) |

- 動いている間の内蔵 RAM は S1 のアプリと同じ幅で、画像で増えていない。アプリの記憶 (VM 1 MB) と sprite・復号の出力・
  `/tmp` のファイルは PSRAM。
- 初回だけ内蔵 224 B・PSRAM 3.4 KB が残る。復号器の engine (`jpeg_new_decoder_engine`) を最初の 1 枚で作り、作ったまま
  持つ作りのため (動画の再生や JPEG の背景と共有。2 回目からは増えない)。
- 6 回動かして止めたうち 2 回、止めたあとの内蔵 RAM がさらに 512 B 減った (201,568 → 201,056 → 200,544)。
  `/tmp` の書き込みだけ (100 回)、画像だけ (100 回)、網だけ (画像を描かない版) の 3 つを別に動かすと、どれも減らなかった。
  あとの 3 回 (console の記録つきの通しを含む) も減らなかった。減った 2 回はどちらも、動いている間に台車のコンテナの
  起こし直しか、網の参加者の出入りがあった。原因は突き止めていない (6 章)。

## 3. sim との差

- sim の表示の側 (graphics-audio の Linux 版) の CREATE_IMAGE_FROM_FILE は PNG だけを読み、パスも自分の `flash/` の下で
  解く。core の `/tmp` (ホストのディレクトリ) は見えない。よって sim では画像を描かず、黒い欄に
  「JPEG 160x120 2807 B / no JPEG decoder here / frame N」を出す (大きさは Ruby で JPEG の SOF を読む)。
- 判定は `FmrbConst::PLATFORM == "esp32"` かつ `FmrbConst::HW_FAMILY == "modern"`。Retro の実機は `create_image` が
  JPEG を読めないので、sim と同じ表示になる。
- sim の数字: 画像 4.95-4.97 Hz (描いた数も同じ)、描画 0-1 ms、poll 0 ms、更新の 1 周 50 ms (戻り値どおり)、
  `/cmd_vel` は動いている間 10.4 Hz。

### 4.1 操縦とオドメトリ

毎回、台車を起こし直して原点から始め、終わったあとに `/odom` と `/ground_truth/odom` を rclpy で同時に読んで比べた。
動かし方は S1 と同じ (上を 4 回 = 0.2 m/s、約 5 s、空白。左を 2 回 = 0.6 rad/s、約 2.6 s、空白)。

| 送り手 | `/odom` | 真の位置 | 差 |
|---|---|---|---|
| P4-Nano (tab5_input の注入、1 回目) | 1.1488 m、100.74 度 | 1.1467 m、100.47 度 | +0.18 %、+0.27 度 |
| P4-Nano (2 回目、console で記録しながら) | 1.1469 m、102.65 度 | 1.1447 m、102.38 度 | +0.19 %、+0.27 度 |
| P4-Nano (手順書の通し) | 1.1274 m、103.51 度 | 1.1252 m、103.24 度 | +0.20 %、+0.27 度 |
| sim (sim_input の注入) | 1.0184 m、89.60 度 | 1.0166 m、89.37 度 | +0.18 %、+0.23 度 |

- 機体で 1 m・90 度より多く動いたのは S1 と同じく注入の間隔のため (動いている時間で量が決まる)。今回は 1 キーが
  0.1-0.4 s で届き、S1 (約 0.5 s) より速かった。
- PC の側で `/cmd_vel` を数えると (rclpy)、機体の 1 回の走りで 75-76 通。前進 6.06 s と旋回 3.21 s の間だけ届き、
  止めは 2 回 (各 1 通)、そのあとは 1 通も来ない。動いている間は約 8.2 Hz (sim は 10.4 Hz)。

### 4.2 画像の遅れと更新の 1 周 (P4-Nano)

| 項目 | 値 | 測り方 |
|---|---|---|
| 遅れ (送り手が出してから機体が描き終わるまで) | 2 秒ごとの平均 44-170 ms (ふだん 約 100 ms)、2 秒ごとの最大 92-370 ms (WiFi のつまりと台車の起こし直しの 3 回は 480-670 ms) | 下の注 |
| age (描いた 1 枚の撮影時刻が、最新の odom より何 ms 古いか。シミュレータの時計) | 0-170 ms (odom 20 Hz・画像 5 Hz の刻みで飛ぶ) | header.stamp どうしの差。台車の側の描画と JPEG への圧縮を含む |
| 更新の 1 周 (on_update の間隔) | 2 秒ごとの平均 95-136 ms、最大 278 ms | アプリが 50 ms を返し、その上に仕事が約 60 ms 乗る |
| poll (受信と読み解き) | 止まっているとき 17-20 ms、走っているとき 31-43 ms、最大 87-173 ms | S1 (21 ms、最大 32-59 ms) と同じ程度 |
| 1 枚の描画 | 9-12 ms、最大 64 ms | 2.2 節 |

- **遅れの測り方**: rmw_zenoh の添付 (attachment) にある送り手の時刻 (送り手の壁の時計) と、描き終えたときの機体の時計の差。
  機体の時計は PC と約 0.4-0.57 s ずれていた (しかも 2 秒で数十 ms 動く)。そこで、直前の 2 秒に受けた `/odom` の
  (受けた時刻 - 送り手の時刻) の最小を時計のずれとみなして引いた。つまり「いちばん速く届いた odom に比べて、画像が
  どれだけ遅れて描かれたか」で、精度は更新の 1 周 (約 110 ms) ほど。sim は時計が同じなので、ずれを引く前の値が
  そのまま遅れで、25-50 ms だった。
- 1 周の大半は poll (約 20 ms)、画像 (約 10 ms)、右の文字 10 行と present。画像の頻度 (5 Hz = 200 ms) には足りている。

### 4.3 asterism-console (操縦しながら)

host の Ruby で `bin/rails server` と `bin/bridge` を動かし、ヘッドレスの Chromium (Playwright の像) で 2 つのタブ
(グラフの画面と Plots) を開いたまま、機体を操縦して 3 秒ごとに両方を撮った。console のコードは変えていない。

| 項目 | 結果 |
|---|---|
| グラフ | ROS 2 のノード 13 (台車の 9 と機体の `/fmruby_cam_fmruby_aaaaaa` ほか) と話題 29。機体のノードの詳細に「Publishes `/cmd_vel` to /twist_stamper」「Subscribes `/camera/image/compressed` from /camera_jpeg、`/odom` from /diff_drive_controller」。グラフの上でも機体のノードへ 2 本・機体から 1 本の矢印 |
| 画像 | Watch に `0/camera/image/compressed/**` を足すと、走りに合わせて景色 (赤い柱が近づく、旋回で緑の柱と紫の箱) が変わった |
| 線グラフ | Plots で `/odom` の `pose.pose.position.x`・`.y`。x が 0 から 1.15 へ動いて止まった (429 通、すべて描いた) |
| 記録 | `/cmd_vel`・`/odom`・`/ground_truth/odom`・カメラ・網の構造を 41 s。5,204 通、4.4 MB、カメラ 205 枚 (5.0 Hz)、`/cmd_vel` 75 通 (機体の送った数と同じ)、失ったもの 0 |

| 網の巻き戻し | 「Network at the cursor」で記録した間の 5 つの変化 (確かめ用のノードの出入り) をたどれ、機体のノードと矢印が記録の時刻のまま出た |

### 4.4 手順書の通し

`docker/mujoco/README.md` の S3 の節を、上から次のとおりに打って確かめた (アドレスは本当のものに置き換えて)。

1. `compose ... down` → `up -d zenohd mujoco` (zenoh-lan つき) → `list_controllers` で 3 つ active。
2. console は動かしたまま (利用者を作る段は済み)。
3. `fmrb_rd_fs.rb put` で app と toml を送り、`fmrb_rd_launch.rb` で起動。
4. Recordings の画面の form で 4 つの話題と網の構造に印を付け、上限 41 秒で開始 (Playwright で form を操作した)。
5. 機体で同じ走り (4.1 節の 3 行目)。グラフ・Watch の画像・Plots が同時に動いた。
6. 記録 (5,206 通、カメラ 205 枚、失ったもの 0) を開き、`/odom` の行を選んで 2 つの欄を Plot、カメラの行をクリックして
   カーソルを動かし、Next で 1 枚進め、Play で再生、Network at the cursor で巻き戻し。
7. `fmrb_rd_ps.rb` と `fmrb_rd_kill.rb` で機体のアプリを止め、`compose down`。

## 5. 見立てと違った点

- **`create_image` は P4 では JPEG も読む**。指示書 (と plan) は「PNG だけ」という前提で、新しい API の案を書く見込みも
  あったが、P4 の表示の側はすでに JPEG を SoC の復号器にかける分岐を持っていた (動画の再生と同じ復号器の包み)。
  公開の API の説明 (`fmrb-gfx.rb` の `create_image` のコメント) にはその旨が無い。
- **機体の時計は PC と 0.4-0.57 s ずれ、2 秒で数十 ms 動く**。添付の時刻をそのまま引くと遅れが負になった。
  時計を合わせる仕組み (net/timesync) がこの機体では効いていないか、合わせても揺れる。遅れは odom で補正した値で示した。
- **更新の 1 周は約 110 ms** (アプリの返す 50 ms + 仕事)。S1 のアプリも同じ形で、`/cmd_vel` が 10 Hz に届かず
  約 8.2-8.7 Hz になるのはこのため。sim は仕事がほぼ 0 なので 50 ms・10.4 Hz。
- **`docker exec fmruby_mujoco ros2 ...` は動かない**。exec では ROS 2 の setup が読まれず `ros2` が見つからない。
  `docker exec fmruby_mujoco /ros_entrypoint.sh ros2 ...` なら動く。S1 で書いた README の既存の 3 か所
  (Start and stop の `list_controllers`、Drive it の `topic pub` と `topic echo`) はこの形になっていない。指示書が
  `docker/mujoco/` は足すだけとしているので既存の行は直さず、S3 の節では動く形で書いた。
- **表示の側が 1 枚ごとに 2 行のログを出す** (CREATE_IMAGE_FROM_FILE と Image store free、INFO)。5 Hz で毎秒 10 行。
  動きには効かないが、シリアルのログが読みにくくなり、間を置かずに回すとその出力が律速になる (2.2 節)。
- 台車と console の側は S1 のまま動き、console のコードの変更は要らなかった。

## 6. 残った課題

- **止めたあとの内蔵 RAM の 512 B** (2.3 節): 6 回のうち 2 回。画像・`/tmp`・網だけの単体では起きず、再現の条件を
  つかめていない。動いている間の台車の起こし直しか網の参加者の出入りとの関わりを疑っている (zenoh-pico・lwIP の側の
  可能性)。何度も起動と停止をくり返す試しで確かめたい。
- **JPEG を描く公開の API の文書**: `create_image` が Modern では JPEG を受けることを `fmrb-gfx.rb` のコメントと
  エディタの型の説明 (sig) に書くとよい (ファームの C は変えない、文書だけの直し。今回の範囲の外)。
- **表示の側の 1 枚 2 行のログ**: CREATE_IMAGE_FROM_FILE と Image store free を DEBUG に下げる案 (ファームの C の
  直しなので今回はしていない)。
- **機体の時計**: 添付の時刻で遅れを測るには、機体の時計が PC と数 ms で合っている必要がある。今は odom で補正している。
- **更新の 1 周を縮める**: 文字の行を変わったものだけ描き直す、返す待ち時間を 50 ms より短くする、で `/cmd_vel` を 10 Hz に
  近づけられる見込み (見せ場には今のままで足りている)。
- **Tab5 での確かめ**: P4-Nano だけで確かめた。Tab5 での確かめはユーザが行う。
- **viewer (WSLg) を並べた見せ場**: 手順書は S1 の手順への参照で足した。画面付きでの通しは目で見る確かめになるので、
  ユーザが行う。
