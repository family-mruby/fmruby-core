# S4 報告: 端末 2 台 (P4-Nano が台車の頭脳、ブラウザ版が操縦機)

> 状態: 完了 (検収待ち) | 更新: 2026-10-12 | instruction_s4.md の実装と確認の記録。P4-Nano のアプリ `rover_brain` が `/cmd_vel` を出す唯一の者になり、Asterism のオブジェクト `<端末>/brain/rover` (drive・go・turn・stop・state) を公開した。ブラウザ版のアプリ `rover_pilot` が生存の監視で頭脳を見つけ、キーで呼び、台車のカメラを ROS 2 から直接受けて出した。`go(1.0)` と `turn(90)` の誤差は真の位置に対して -10 mm から +4 mm、-1.9 度から +0.2 度。仕事の途中の stop・新しい仕事による取り消し・0.5 s の見張りが効いた。console の記録で、ブラウザ版から頭脳への呼び出し (呼んだ相手つき) と頭脳の `/cmd_vel`・`/odom` が同じ時間の帯に並び、巻き戻せた。P4-Nano の内蔵 RAM は S3 のアプリより増えていない。手順書は親の `docker/mujoco/README.md` の S4 の節。止まる条件には当たらなかった (1 点、オブジェクトの形に任意のキーワードを足した。6 章)

## 2. 頭脳の作り

### 2.1 網とのつながり

- セッションを 2 本開く: `Asterism.connect` (オブジェクトの公開) と `Asterism::Zenoh::Session.open` (ROS 2 のノードと
  ログの put)。`Asterism.connect` のセッションは公開の API からは取れない (`Asterism.session!` は `@api private`) ので、
  公開の API だけで書ける 2 本の形にした。内蔵 RAM は増えていない (5.5 節)。
- 毎回の更新で `Asterism.poll` (来た呼び出しに答える) → `node.poll` (`/odom` を受ける) → 制御の 1 歩、の順。
  更新は 20 ms を返し、P4-Nano の 1 周は 33-53 ms (仕事 1-24 ms、文字の描き直しは 200 ms ごと)。

### 2.2 オブジェクト

| 呼び出し | 動き | 返す値 |
|---|---|---|
| `drive(v, w)` | 速さを直接 (上限 1.0 m/s・3.0 rad/s で切る)。今の仕事は「canceled by drive」。最後の呼び出しから 0.5 s で止める | `[v, w]` (切ったあとの値) |
| `go(m)` | 仕事。始めた向きに沿って m メートル (負なら後ろ) | 仕事の番号 |
| `turn(deg)` | 仕事。deg 度 (正なら左) | 仕事の番号 |
| `stop` | 仕事 (「stopped」) も速さも止め、0 を 1 回送る | `true` |
| `state` | 位置・向き (度)・速さ (`/odom`)、送っている命令、今していること (idle / drive / go / turn)、仕事 (番号・種類・目標・済んだ量・進み具合・状態・終わったか・かかった時間)、最後に呼んだ相手と呼び出し、呼ばれた数、`/odom` の古さ、1 周の時間、内蔵 RAM の空き | Hash |

- 新しいものが勝つ: 仕事か `drive` が来たら今の仕事を取り消す (状態に「canceled by go」などを残す)。
- `/odom` がまだ無いときの仕事は「aborted: no odom」ですぐ終わる。仕事の途中で `/odom` が 0.5 s 来なければ止めて
  「aborted: no odom」。

### 2.3 制御の輪 (go と turn)

- 測り方: go は始めたときの位置と向きを覚え、`/odom` の位置の変化を始めの向きに射影した量 (横へのずれは入れない)。
  turn は `/odom` の向きの変化を 1 通ごとに足し合わせる (±180 度をまたいでも、180 度を超えても数えられる)。
- 速さ: 残り r に対して `sqrt(2 * a * r)`。上限は巡航 (0.3 m/s・1.0 rad/s)、下限は這う速さ (0.02 m/s・0.08 rad/s)。
  a はゆるめ (0.2 m/s^2・0.8 rad/s^2) にして、着く前に十分遅くなるようにした。go の間は向きを保つ
  (向きのずれ × 2、上限 0.3 rad/s)。
- 先読み: 残りから「今送る命令が効くまでに台車が進む量」を引く。速さ × (odom の遅れ 30 ms + 手元の最新の `/odom` の
  古さ + 1 周の時間 (平滑した実測) + 車輪が命令に追いつく 50 ms)。これが 3 mm (turn は 0.23 度) を切ったら終わり。
  0 を 1 回送る。
- 上限: 命令の変化は 1 歩ごとに制御器と同じ加速 (0.5 m/s^2・2 rad/s^2、S1・S2 の値) まで。速さは制御器の上限
  (1.0 m/s・3.0 rad/s) まで。
- 送り方: 何かしている間は 1 歩ごとに `/cmd_vel` (P4-Nano で約 20 Hz。PC の側で 1 m の間に 84 通)。終わったら 0 を 1 回送って黙る (S3 と同じ。
  別の操縦者が後を取れる)。止まった後に diff_drive_controller が「Velocity command timed out. Braking.」を出すのは
  このため (害は無い)。

調整の経過 (P4-Nano、PC から 1 m と 90 度を交互に):

| 版 | go の誤差 (mm) | turn の誤差 (度) | 見立て |
|---|---|---|---|
| 先読み 60 ms 固定、a = 0.4・1.6 | +13.6、+18.3 | +2.0、+3.8 | sim (-4.6 mm、-0.7 度) では足りたが、P4-Nano では遅れが大きく行き過ぎた |
| 先読みに 1 周の時間と、止めた後の制動 (v^2 / 2a) を足した | -10.7、-21.5 | -1.6、-2.9 | 制動の分を二重に見て手前で止まった |
| 制動を外し、車輪の遅れ 100 ms | -13.4 から +4.3 | -2.8 から +0.2 | ばらつきが大きい |
| `/odom` の古さを足した | -22.8 から -11.8 | -4.1 から 0.0 | 止めたときの速さが 0.09-0.17 m/s・0.2-0.65 rad/s と高く、遅れの見積もりの揺れがそのまま誤差になった |
| a を半分 (0.2・0.8) | -3.5 から -8.6 | -1.2 から -2.0 | 止めるときの速さが 0.05-0.09 m/s に下がった。少し手前 |
| 車輪の遅れ 50 ms (今の版) | -10.2 から +0.1 | -1.9 から +0.2 | 5.2 節 |

- 効いたのは「着く前に遅くする」こと。先読みの見積もりより、止めるときの速さの方が誤差を決める。
- `/odom` の古さを足したのは、WiFi のつまりで `/odom` がまとめて届くとき、古い位置のまま判定して行き過ぎるのを防ぐため。
  記録の通し (5.6 節) で 1 回、古さ込みの遅れが 299 ms になり、`/odom` の上では 81 度で止めたが、真の角度は 89.6 度だった
  (先読みが当たった例)。

### 2.4 画面

状態) と進み具合の棒、最後に呼んだ相手と呼び出しと何秒前か、呼ばれた数・送った `/cmd_vel` の数・受けた `/odom` の数、

## 3. 操縦機の作り

### 3.1 頭脳の見つけ方

- `Asterism.each("*/brain/rover")` で、生きているオブジェクトから頭脳を探す。`Asterism.on_join` / `on_leave` が来たときと、
  2 s ごとに探し直す。今の頭脳が生きている間は替えない。いなければ最初のものを取る。
- 見つからない間は「looking for */brain/rover」、いなくなったら「brain gone: <名前>」を出す。頭脳を止めると 2 s 以内に
  そう出て、別の頭脳 (sim の `linux`) を起こすとそちらを見つけた (5.1 節)。

### 3.2 キーの形

S3 と同じ「押すと段で変わる」形にした。

| キー | |
|---|---|
| 上 / 下 | 速さ ±0.05 m/s (±0.5 まで) |
| 左 / 右 | 回り ±0.3 rad/s (±1.5 まで) |
| `g` | `go(1.0)` |
| `t` | `turn(90)` |
| Space (と `s`) | `stop` |

- 速さが 0 でない間、`drive(v, w)` を 200 ms ごとに送る (5 Hz。頭脳の 0.5 s の見張りに 300 ms の余裕)。段を下げて 0 に
  なったら `drive(0, 0)` を 1 回。
- `g`・`t`・Space は、先に手元の速さを 0 にする (続けて `drive` が出て仕事を取り消さないように)。
- 押している間だけ送る形にしなかった理由: ブラウザのキーの繰り返しは当てにならず (OS とブラウザの設定次第)、
  離したことを取りこぼすと止まらない側に倒れる。段の形なら押した回数だけで決まり、遠隔の注入 (web_input・tab5_input は
  押しっぱなしにできない) でも同じように試せる。止める手段は Space と、操縦機を閉じれば 0.5 s で止まること。
- 呼び出しはすべて async。返事は次の更新以降で見る (同時に 4 つまで。超えた分は数えて捨てる)。どの呼び出しにも
  `from: <ID>` を付ける。
- `state` を 300 ms ごとに呼ぶ。前の返事が来るまで次は出さない。
- 呼び出しはキーの処理 (on_event) ではなく on_update から出す (asterism_demo と同じ。P4 の 16 KB のスタックで、
  on_event は 1 段深い)。

### 3.3 画面

左にカメラ (160x120、rover_cam と同じ描き方。ブラウザ版と Modern の実機は JPEG を描き、sim は大きさと枚数を出す)。
右に `<ID> -> brain <頭脳>`、送っている速さ、頭脳の `state` (位置・向き・速さ・していること・仕事と進み具合)、
呼び出しの往復時間 (最後 / 2 s の平均 / 2 s の最大)、カメラの頻度と遅れ、最後の返事、キーの説明。

## 5. 実測

### 5.1 見つけ方と console

- ブラウザ版の操縦機は開いてすぐ `wasm -> brain fmruby-aaaaaa` を出した。頭脳を止めると「brain gone」と
  「looking for */brain/rover」、sim で頭脳を起こすと `brain linux` に替わった。
- console の図 (ヘッドレスで撮った): Asterism のノード 3 つ (console・端末・`wasm`)、端末の中にアプリ `brain` と
  オブジェクト `rover`。ROS 2 のノード `/fmruby_brain_fmruby_aaaaaa` から台車へ `/cmd_vel`、台車から `/odom`。
  `/fmruby_pilot_wasm` へ `/camera/image/compressed` と `/odom`。
- Call permissions に node `fmruby-*`・app `brain`・object `rover`・method `state` を足し、オブジェクトの詳細から
  `state` を呼ぶと 87.2 ms で Hash が返った (`last_caller` は `wasm`)。
- Logs の画面に頭脳の行が出た: `go(1.0) from wasm -> job 14 running`、`job 14 go 1.0 done at 0.991 (4521 ms, v 0.061 lag 134 ms)`、
  `drive(0.2, 0.3) from wasm`、`stop from wasm` など。同じ画面に diff_drive_controller の WARN も並ぶ。

### 5.2 go と turn の誤差 (今の版)

真の値は `/ground_truth/odom`。終わってから 1.5 s 待って比べた (止めた後の惰走を含む)。台車は毎回原点からではない
(続けて走らせた)。

| 頭脳 | 呼んだ側 | go(1.0) の真の距離 | turn(90) の真の角度 |
|---|---|---|---|
| P4-Nano | PC (CRuby、4 往復) | 0.9918、0.9919、0.9898、0.9964 m | 89.25、88.59、89.03、90.21 度 |
| P4-Nano | PC (CRuby) | 1.0001 m | 89.77 度 |
| P4-Nano | ブラウザ版 (`g`・`t`) | 0.9957 m | 88.10 度 |
| P4-Nano | ブラウザ版 (手順書の通し、記録から) | 0.9939 m | 89.56 度 |
| sim | PC (CRuby、台車を起こし直して原点から 2 往復) | 0.9931、0.9928 m | 89.03、89.14 度 |
| sim | sim の操縦機 (`g`・`t`) | (5.3 節の確かめと同じ走り、画面で 0.992 m) | |

- 誤差は go -10.2 から +0.1 mm、turn -1.9 から +0.2 度 (P4-Nano)。sim は -7 mm、-1.0 度前後。いずれも目安の内。
- `/odom` そのものの誤差は S1-S3 と同じ (前進 +0.2 %、旋回で `/odom` が真より 0.23 度多い)。頭脳は `/odom` で止めるので、
  旋回はこの分だけ手前になる。
- 1 m は約 4.3-4.6 s、90 度は約 2.4-2.7 s。

### 5.3 stop・取り消し・見張り (P4-Nano)

| 試し | 結果 |
|---|---|
| `go(1.0)` の 1.5 s 後に `stop` | 仕事は「stopped」(0.353 m)。止めの後の惰走は 0.3 m/s から制御器の減速 (0.5 m/s^2) で約 9 cm (測った 91 mm は stop の往復を含む) |
| `turn(180)` の 1 s 後に `go(0.3)` | 旋回は「canceled by go」(40.4 度で)。`state` は新しい仕事 11 が running |
| `drive(0.2, 0)` を 1 回だけ呼んで黙る | 呼んでから 486 ms で 0 の `/cmd_vel` (PC の側で受けた時刻)。sim の頭脳は 502 ms |
| ブラウザ版で走らせたまま操縦機を閉じる (Ctrl+Q) | キーを送ってから 650 ms で 0 の `/cmd_vel` (キーが届くまでに 293 ms、最後の `drive` は閉じる前の最大 200 ms 前)。ログに「drive: no call for 500 ms, stopped」 |

| 項目 | 値 |
|---|---|
| `state` の往復: PC (CRuby) → P4-Nano | 40-50 回で中央値 70.9 / 91.7 ms、90 % 100-117 ms、最大 152 ms (最小 14.6-18.7 ms) |

| カメラ (ブラウザ版の操縦機) | 4.5-5.0 Hz、遅れ 2 s の平均 175-201 ms・最大 223-245 ms |

  操縦機の作りによるものではない。P4-Nano の rover_cam も同じ日は 200-287 ms (S3 では約 100 ms)。原因は追っていない
  (6 章)。

### 5.5 内蔵 RAM (P4-Nano)

シリアルは使わない決まりなので、`FmrbApp.heap_info[:iram_free]` (周期のダンプの「IRAM free」と同じ
`heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`) で測った。

| 状態 | 内蔵 RAM の空き |
|---|---|
| 頭脳だけ (頭脳の `state` と画面、走りを含む) | 176,680-179,912 B (ふだん 179-180 KB) |
| S3 の rover_cam (report/s3.md、周期のダンプ) | 175,956-183,060 B (ふだん 180-182 KB) |
| S1 の ros2_drive (report/s3.md) | 179,912-181,472 B |

同じ日に、同じ測りのアプリ (内蔵 RAM の空きの今・最小・最大を出すだけの一時のアプリ。測ったあと消した) を並べて比べた:

| 並べたもの | 今 | 最小 |
|---|---|---|
| 測りのアプリだけ | 181,428 B | 181,428 B |
| 頭脳 + 測り (PC と操縦機から go・turn・drive) | 162,196 B | 150,632 B |
| rover_cam + 測り (矢印で走らせ、画像を描いている) | 159,800-161,756 B | 144,152 B |

- 頭脳はセッションを 2 本持つが、カメラを描かない分、S3 のアプリより内蔵 RAM を使わない (最小で 6.5 KB 多く空いている)。
  増えていない。
- 測りのアプリ 1 つで約 18 KB 減る (アプリ 1 つ分のタスクのスタックなど)。上の 2 表は別の条件なので混ぜて比べない。

### 5.6 手順書の通し

`docker/mujoco/README.md` の S4 の節を、上から次のとおりに打った (アドレスは本当のものに置き換えて)。

1. compose を down してから、zenoh-lan と zenoh-ws と mujoco を重ねて `up -d zenohd mujoco`。制御器 3 つが active、
   zenohd の待ち受けに `tcp/[::]:7447` と `ws/[::]:7449`。
2. console の server と bridge を起動 (利用者と Call permissions の行は済み)。
3. `fmrb_rd_fs.rb put` で `/home/zenoh_echo.txt` と app と toml、`fmrb_rd_launch.rb` で頭脳を起動。
4. ブラウザ版 (`rake wasm:web` で束を作り直したもの) を `?app=/app/test/rover_pilot.app.rb` で開く (web_up が
   `rake wasm:serve` と同じ開発用のサーバを立てる)。開いてすぐ頭脳を見つけた。

## 6. 見立てと違った点・決めたこと

- **呼び出しの送り手は gem からは分からない**。Asterism の呼び出しの中身は `[method, args, kwargs]` だけで、答える側は
  誰が呼んだかを知らない (zenoh-pico の query にも送り手の情報は無い)。そこで、5 つのメソッドすべてに**任意の
  キーワード `from:`** (呼んだ側のノード名) を足し、操縦機は必ず付けるようにした。付けない呼び出し (console や
  `fmrb_zenoh.rb`) も通り、相手は「?」になる。1 章の形 (位置引数) は変えていない。gem の側で送り手を渡す案
  (呼び出しの添付に送り手のノード名を載せ、答える側の `Asterism` が今の呼び出しの送り手を見せる) は gem の本体の
  直しになるので、していない。
- **console の図には「誰が誰を呼んだか」の矢印が無い**。console は Asterism の呼び出しを見られない (query は
  subscribe では見えず、呼び出しの記録 (Call log) は console 自身の呼び出しだけ)。今回は、頭脳が
  `asterism/<ID>/brain/log` (console の v3 の提案の形) に呼び出しを書き、Logs の画面と記録で「ブラウザ版 → 頭脳」を
  見せた。図に矢印を描くなら、(a) 上の送り手の添付を gem に入れ、答える側が呼び出しの記録を put する、(b) console が
  その記録から「calls」の辺を描く、の 2 つが要る。図の既定の見え方を変える選択なので、していない。
- **端末の ROS 2 のノードは図で端末の枠の外に出る**。頭脳のセッションが 2 本で、ROS 2 のノードは Asterism のノードと
  別の zid になるため。`Asterism.session!` (private) で 1 本にまとめれば同じ zid になる。公開の API で 1 本にする
  手段 (例: `Asterism.session` を公開する) は gem の判断。
- **`docker restart fmruby_mujoco` のあと、zenohd が新しいセッションと REST に答えなくなった** (1 回)。そのとき網には
  P4-Nano のセッション 2 本、ブラウザ版 2 本、sim 2 本、console、確かめのスクリプトがいた。zenohd の CPU は 0.1 % で、
  TCP の接続は受けるが握手が時間切れになる。zenohd を起こし直して戻った (操縦機は TimeoutError を出して止まり、
  頭脳への往復が 1,007 ms を示していた)。S3 では同じ起こし直しを何度もして起きていない。再現は試していない。
- **後ろへの go は `/odom` と真の位置が大きくずれる**。`go(-0.5)` で `/odom` は -0.494 m、真の位置は -0.416 m
  (8 cm)。後ろへ進むと台車が滑る (補助輪の側が前になる) ためと見ている。頭脳は `/odom` どおりに止めている。
  受け入れ条件は前への 1 m なので、この先で台車のモデルを見直すなら確かめる。
- **カメラの遅れが B1・S3 の日より大きい** (5.4 節)。同じ日の rover_cam と同じなので、操縦機・頭脳の作りではなく、
  その日の環境 (台車のコンテナが 1 コアの 95 % を使っていた等) と見ている。追っていない。
- **記録の中に、台車の話題が 1-2 s まとめて途切れる所が 2 か所あった** (`/odom`・`/ground_truth/odom`・カメラが同時に)。
  失ったもの 0 なので、台車の側 (シミュレータ) の止まりと見ている。走りには効いていない。
- 頭脳の VM は sim で約 500 KB (1.5 MB のうち)。ROS 2 の型と 2 本のセッションの分。

## 7. 残った課題

- 呼び出しの送り手を gem で渡すこと、console に呼び出しの矢印を描くこと (6 章の (a)(b))。決めるのはユーザ。
- セッションを 1 本にするか (図で ROS 2 のノードを端末の枠に入れる)。gem に公開の手段が要る。
- zenohd が答えなくなった件の再現と切り分け。
- 頭脳の `/cmd_vel` は、何かしている間は 1 周ごと (約 20 Hz) に出る。制御器は 100 Hz で読むので害は無いが、WiFi の
  送り数を減らすなら 10 Hz に間引ける。
- turn は `/odom` の旋回の誤差 (0.23 度) の分だけ手前で止まる。真の角度に合わせたいなら、IMU で回った角度を測る形に
  替えられる (`/imu` は 50 Hz で出ている)。
- HDMI の大きな画面に頭脳の画面とカメラを出すこと (plan の S4 の表)。今は窓 1 枚。
- 見せ場の画面つきの通し (MuJoCo の viewer を並べる) は目で見る確かめなので、ユーザが行う。
