## 2. 守りの作り (W2a)

### 2.1 ログイン

- `bin/rails generate authentication` (Rails 8.1) を基にした。パスワードは `has_secure_password` (bcrypt)。
  生成物のうち、パスワードの再設定 (メールを使う) は外した。メールの仕組みを持たないため。
- すべての controller が `require_authentication` を通る。外すのはログインの画面 (`sessions#new` `create`
  `otp` `verify_otp`) と `rails/health` だけ。HTML はログインの画面へ送り、JSON などは 401 を返す。
  **ログインを外す設定は作っていない** (環境変数でも外せない)。
- Action Cable: `ApplicationCable::Connection` が同じ署名つきの cookie を確かめ、無ければ接続を断る
  (`reject_unauthorized_connection`)。グラフの差分、呼び出しの答え、眺めるキーの値はログインした画面にしか届かない。
  実際に cookie なしで `/cable` に WebSocket を張ると `{"type":"disconnect","reason":"unauthorized"}` が返った。
- セッションは 12 時間で切れる (`Session.live`)。cookie は httponly・SameSite=Lax、HTTPS のときは secure。
  ログインの試行は 3 分に 10 回まで (Rails の rate_limit)。ログインの度に Rails のセッションを作り直す。
- 最初の管理者: `bin/rails console:user EMAIL=... ADMIN=1`。パスワードは端末から (表示しない) か `CONSOLE_PASSWORD`
  から受け取り、コマンドの引数では受け取らない。端末が無く環境変数も無ければ止まる。12 文字以上。
  ほかに `console:users` (一覧) と `console:otp_off` (端末をなくした人の多要素を外す)。
- **多要素 (TOTP)**: gem `rotp` 1 つ (依存なし) で入れた。人ごとに任意。アカウントの画面で「Turn on」-> 秘密の値と
  `otpauth://` の URI を出す (確かめるまでのあいだだけ) -> 認証アプリの 6 桁で確かめると有効になる。以後のログインは
  パスワードの後に 6 桁を求める。同じ 6 桁は 2 度通らない (最後に使った時間の区切りを覚える)。QR コードは出していない
  (もう 1 つ gem が要るため)。
- 役割は 2 つ: 管理者 (許可の表と台帳を変えられる、反映できる) と、ふつうの人 (見る、許されたものを呼ぶ)。

### 2.2 呼べるメソッドの制限

- 表 `CallPermission`: ノード・アプリ・オブジェクト・メソッドのそれぞれに型 (`*` はその区切りの中の任意の文字の並び。
  `/` はまたがない)。例: `fmruby-*` / `demo` / `screen` / `say`。
- **既定は空 = 何も呼べない**。オブジェクトのメソッドの一覧 (meta) も、そのオブジェクトにかかる行が 1 つも無ければ
  読まない。
- 確かめは 2 か所: Rails (`POST /bridge_requests`) が先に断り、bridge も呼ぶ直前にもう一度確かめる (行が後から消された
  場合や、DB に直接書かれた頼みごと)。
- 断ったものは `denied` として残し (403)、bridge には渡らない。
- 画面: 許されていないメソッドは灰色にして「not permitted」と書き、押せない。「Another method」の欄からは送れるが、
  `denied` が返る。
- 許可の表の画面は、ログインした人は誰でも見られ、行を足す・消すのは管理者だけ。

### 2.3 呼び出しの記録

- 頼みごとの行 (`BridgeRequest`) に頼んだ人 (`user_id`) を足し、それを記録にした: 誰が、いつ、どのパス・メソッド・
  引数、答え (`ok` と戻り値、`remote_error`、`timeout`、`denied` など)、かかった ms。
- 「Call log」で新しい順に 200 件。既定は呼び出しだけで、meta も出す切り替えがある。JSON でも取れる。

### 2.4 待ち受け

- `config/boot.rb` で `BINDING` の既定を `CONSOLE_BIND` か `127.0.0.1` にした。Rails の既定は production で
  0.0.0.0 なので、**どの環境でも既定は 127.0.0.1** になった。`config/puma.rb` も同じ住所に bind する
  (puma を直接起動したとき)。
- 外で待ち受ける (`CONSOLE_BIND=0.0.0.0` か `-b`) と、`config/initializers/exposure.rb` が利用者がいるかを確かめ、
  いなければ起動しない。いればログに「sign-in is required. Put TLS in front」と出す。
- 確かめ: `CONSOLE_BIND=0.0.0.0` で起動し、LAN 側の住所から `/` が `302 -> /session/new`、`/graph` (JSON) が 401。
- 素の HTTP ではパスワードと cookie が平文で流れるので、外に出すなら TLS の中継を前に置く (README の守りの前提)。

## 3. 署名の分け方と台帳 (W2b)

### 3.1 全体

```
 ブラウザ --> Rails (台帳、発行の記録、反映) --HTTP 127.0.0.1 + 合言葉--> bin/signer (CA の秘密鍵)
                 |  storage/relay/generated/cloud.json5 を書く
                 +--> docker compose restart zenohd-cloud (/generated/cloud.json5 を読む)
```

### 3.2 bin/signer

- 素の Ruby (標準ライブラリと `lib/relay/cert_authority.rb`)。Rails を読まない。CA の秘密鍵を持つのはこのプロセスだけ。
- `init` (新しい CA)、`import` (今の CA を標準入力から取り込む)、`serve` (待ち受け)。
- 待ち受けは HTTP で、`GET /ca` (CA の証明書) と `POST /sign` (名前・証明書の要求 (CSR)・DNS 名・IP・日数) の 2 つだけ。
  `Authorization: Bearer <合言葉>` が合わなければ 401。合言葉は `storage/relay/signer.token` (0600) で、Rails も同じ
  ファイルを読む。
- 署名の前に確かめること: 名前の形 (`[A-Za-z0-9][A-Za-z0-9._-]{0,62}`、`ca` は不可)、日数 (1-825)、CSR の署名が
  CSR の鍵と合うか (すり替えた CSR は断る)。証明書の CN は頼まれた名前にし、CSR の subject は使わない。
- 署名の度に `issued.log` (JSON 1 行) に書く。Rails の台帳とは別の、署名役自身の記録。
- 動かし方は 2 通り。手元では `script/signer_docker` で、**CA を docker の名前つきの volume (`asterism_signer_ca`) に
  置き**、`ruby:3.3-alpine` の中で動かす。待ち受けは `127.0.0.1:7450` にだけ出す。
  ```
  script/signer_docker import storage/relay/certs/ca.pem storage/relay/certs/ca.key
  rm storage/relay/certs/ca.key
  script/signer_docker up
  ```
- W1 で作った CA はこの手順で volume に移し、`storage/relay/certs/ca.key` は消した。W1 の証明書 (家・クラウドの
  ルータ、console、cruby、ros2-cloud) はそのまま使える。`script/relay_certs` は、`ca.pem` があって `ca.key` が無い
  所では動かずに止まる (CA を作り直して上書きする事故を防ぐ)。

### 3.3 発行の流れ

1. 管理者が台帳の相手の画面で「Issue a certificate」を押す。
2. Rails が鍵 (ECDSA P-256) と CSR を作り、signer に署名を頼む。
3. 返った証明書を確かめる (CN が名前と同じか、作った鍵と対か、signer の CA で検証できるか)。
4. 台帳 (`RelayCertificate`) に、証明書 (公開の情報)・通し番号・期限・指紋 (SHA-256)・発行した人を書く。
5. 答えはそのままダウンロード (`<名前>-<番号>.tar`、`Cache-Control: no-store`)。中身は鍵 (0600)、証明書、CA、
   設定の例 (`zenoh.json5`)、使い方 (`README.txt`。`examples/node.rb` の起動の行つき)。
   **鍵はこのダウンロードにしか無い**。DB にも、ファイルにも残さない (試験で DB の全行に鍵の文字列が無いことを確かめた)。
- 失効: 台帳に印を付ける (`revoked_at`、誰が)。その名前に有効な証明書が残らなければ、次の反映で ACL から外れる。
- W1 で `script/relay_certs` が作った証明書は `bin/rails relay:import` で台帳に入れた (`source: imported`)。

### 3.4 台帳 (`RelayPeer`)

| 項目 | 意味 |
|---|---|
| 名前 | 証明書の CN = ACL の subject = Asterism のノードの ID (クライアント) / ルータの `metadata/name` (ルータ) |
| 種類 | router / client |
| 説明 | |
| 読み書きするキー | 1 行に 1 つ。ACL で全 9 種・両方向 |
| 読むだけのキー | 1 行に 1 つ。相手から (ingress) は購読・問い合わせ・生存の問い合わせ・生存の購読だけ、相手へ (egress) は全部 |
| 管理用の空間 | クライアントなら読める (`@/**` の query・reply)。ルータなら、そのルータの管理用の空間をクラウド越しに読ませる (W1 の home と同じ規則) |
| 有効・無効 | |
| 証明書の日数 | 発行するときの期限 (既定 90 日、最大 825 日) |
| DNS 名・IP | 待ち受けるルータの証明書に足す名前 |

- 証明書の期限は台帳の発行の記録から出す (有効なものの中で最も遅い期限)。
- 「読むだけ」でも問い合わせはできる。Asterism の呼び出しは問い合わせなので、`asterism/**` を読むだけにしても
  メソッドは呼べる。画面の注意書きに書いた。

### 3.5 設定の生成 (`lib/relay/cloud_config.rb`)

- 台帳からクラウドの zenohd の設定を丸ごと作る。TLS・待ち受け・scouting・管理用の空間の部分は W1 の `cloud.json5` と
  同じ値。ACL は `default_permission: "deny"` で、相手ごとに subject 1 つ・policy 1 つ・規則 1-3 つ。
- ACL に入れるのは「有効」かつ「有効な証明書が台帳にある」相手だけ。クラウド自身の名前 (zenohd-cloud) は入れない。
  何も許していない相手も入れない。
- ファイルの先頭 3 行は注釈で、「GENERATED by asterism-console from its relay registry (the database is the source).
  Do not edit by hand」、作った時刻と人、中身の要約 (digest)。中身は JSON (JSON5 として読める)。
- 1.10.1 がこの設定を読むことは、実際に起動して確かめた (`Initial conf` に ACL がそのまま出た)。
- `bin/rails relay:show` (表示) と `relay:generate` (書くだけ、起動し直さない) もある。

### 3.6 反映

- 画面の「Apply」は、まず予定を出す:
  - ACL に入る名前、今回加わる名前、外れる名前 (前回書いたファイルとの比較)。
  - **起動し直しで切れるもの**: グラフで今クラウドのルータにつながっているセッションと、ルータどうしのつながり
    (何を運んでいるかつき)。
  - 起動し直しの後に起きること (家のルータと bridge は自分でつなぎ直す、クラウドにつないだ Asterism のノードは
    つなぎ直さない、ROS 2 の peer は値は流れるが生存のしるしが戻らない、の 5 行)。
  - 書く設定の全文。
- 押すと (確かめのダイアログの後)、`storage/relay/generated/cloud.json5` を書き (一時ファイル + rename、0644)、
  親のディレクトリで `docker compose -f docker-compose.yml -f docker-compose.relay.yml restart zenohd-cloud` を走らせる
  (`ASTERISM_RELAY_GENERATED_DIR`・`ASTERISM_RELAY_COMPOSE_DIR`・`ASTERISM_RELAY_RESTART` で変えられる)。
  別のスレッドで動き、画面は 2 秒ごとに読み直して追う。
- 後で、bridge のグラフに新しいクラウドのルータ (起動し直すと zid が変わるので、それで古いグラフと見分ける) が現れてから
  6 秒待ち、そのときクラウドにつながっているものを記録し、前と比べて「戻った」「戻らない」を出す。
- 反映の記録 (`RelayApply`): 誰が、いつ、書いた設定の全文、予定、起動し直しのコマンドの出力、後の様子、結果。
- 同時に 2 つは走らせない。管理者だけ。
- 親の compose の変更: `zenohd-cloud` の起動の引数を `${ASTERISM_RELAY_CLOUD_CONFIG:-/relay/cloud.json5}` に、
  volume に `${ASTERISM_RELAY_GENERATED:-./docker/zenoh-relay}:/generated:ro` を足した。環境変数を置かなければ
  今までと同じ (手で書いた `cloud.json5` を読む)。生成を使うときは 2 つを置いて `up` する。
  ```
  ASTERISM_RELAY_GENERATED=./asterism-console/storage/relay/generated \
  ASTERISM_RELAY_CLOUD_CONFIG=/generated/cloud.json5 \
    docker compose -f docker-compose.yml -f docker-compose.ros2.yml -f docker-compose.relay.yml \
    up -d zenohd zenohd-cloud ros2 ros2-cloud
  ```

### 3.7 グラフへの重ね合わせ

- bridge が 2 秒ごとに台帳を読み (`RelayPeer.registry`)、グラフを作るときに名前で照らし合わせる
  (`Bridge::Graph#add_registry`)。照らし合わせの鍵は「Asterism のノードの ID」と「ルータの `metadata/name`」。
- 印 (点の data の `registry`)。
  - `registered`: 登録済みで、ここにいる。緑の輪。
  - `disabled`: ここにいるが、台帳では無効。橙の輪 (無効にしてから反映するまでの間に出る)。
  - `unregistered`: ここにいるが、台帳に無い。赤の輪。
  - `absent`: 登録済みで、ここにいない。灰色の点線の四角を別に置く。
- 点の詳細に「Registry」(状態、種類、ACL に入っているか、証明書の期限) と、Asterism のノードなら「Through」
  (どのルータ経由か) を出す。層の切り替えに「Relay registry」を足した。
- 照らし合わせられないもの: ROS 2 の peer の証明書の名前 (`ros2-cloud`) は、ノードの ID でもルータの名前でもないので、
  いつも「ここにいない」と出る。W1 のとおり、遠くの管理用の空間からはセッションの証明書の名前が取れないため。

## 5. W1 で残ったこと: クラウドを起動し直すと ROS 2 の生存のしるしが消える件

再現して少し調べた。**原因は zenohd と rmw_zenoh (の中の zenoh) の側にある。記録だけにした**。

- クラウドの ROS 2 のコンテナで `listener` を 2 つ動かした。1 つは既定 (rmw_zenoh は peer の形でルータにつなぐ)、
  もう 1 つは `ZENOH_CONFIG_OVERRIDE` に `mode="client"` を足したもの (`/listener_client`)。
- クラウドを起動し直した後: どちらも `I heard: [Hello World: ...]` を受け続けた (値は流れる)。グラフには
  `/listener_client` だけが戻り、peer の `/listener` は戻らなかった。
- そのときクラウドのログに、peer のセッション (`south:0:peer/...`) から
  `Received token with interest id from south-bound face. This message should only flow downstream` が 12 行。
  つなぎ直した peer が自分の生存のしるしを「問い合わせ (interest) への答え」の形で出し直し、1.10.1 のルータは
  それを下流からは来ないはずのものとして捨てている。
- rmw_zenoh 0.2.11 の中の zenoh-c は 1.8.0 (ルータは 1.10.1)。版の違いによる食い違いと見ている (1.8.0 のルータで
  同じことが起きるかは試していない)。
- 回避: クラウド側の ROS 2 を client の形でつなぐ。`docker-compose.relay.yml` の ros2-cloud を変えることになるので、
  今回は変えていない (W2 の範囲は生成の置き場の都合の変更だけ)。反映の画面の注意書きに書いた。
- 起動し直しで切れるもののほかの様子 (同じ確かめの中で見た): 家のルータは数秒でつなぎ直す。bridge は 3 秒後に
  つなぎ直す (新しい zid)。CRuby の Asterism のノードは `disconnected: the connection was lost` で終わる
  (Z2 からの決まりのとおり)。

## 6. 見立てと違った点・踏んだ罠

- **`bin/rails server` は puma.rb の bind を上書きする**。開発の環境では `localhost` を、production では `0.0.0.0`
  を渡すため、`CONSOLE_BIND` を puma.rb に書いただけでは効かなかった (`ss` で 127.0.0.1 と ::1 のまま)。
  `config/boot.rb` で `BINDING` を埋める形にし、外で待ち受けるかの判定も `-b` と `BINDING` を見る。
- **反映の後の様子が、起動し直しの前のグラフのままだった**。反映を Rails の executor の中のスレッドで回したため、
  ActiveRecord の問い合わせの写しが効き、同じ `GraphState` を返し続けた。`uncached` で読むようにした。
  さらに、起動し直す前のグラフの版が上がることもあるので、クラウドのルータの zid が変わったことで新しいグラフと
  見分ける。
- **起動し直すと bridge のセッションの zid が変わる**。前と後のセッションを zid で比べると「戻らない」に見える。
  運んでいるもの (Asterism のノード名、ROS 2 のノード名) と、bridge 自身のものはまとめて比べる。ただし運んでいる
  ものの線はルータのトークンの表から引くので、時に線が無く、セッションの名前 (zid) で比べて「戻らない」と出る
  ことがある (表示の上のことで、つながりは戻っている)。
- **Chromium の `pattern` 属性は `v` の正規表現**として読む。`[A-Za-z0-9._-]` の `-` を `\-` にしないと型が無効になる
  (コンソールに出た)。
- **`docker compose restart` は、作ったときの `-f` の組を全部要さない**。`docker-compose.yml` と
  `docker-compose.relay.yml` だけで、ROS 2 の重ね合わせを含めて作った zenohd-cloud を起動し直せた (作り直しはしない
  ので、作ったときの環境変数 (`ASTERISM_RELAY_CLOUD_CONFIG`) もそのまま)。
- **TLS は通るが ACL で何もできない**、という状態がそのまま「無効」になる。1.10.1 に失効の一覧 (CRL) は無いので、
  無効にしても TLS のリンクは期限まで張れる。同じ名前の別の証明書は見分けられない (ACL は名前で照らす)。
  画面と README に書いた。

## 7. 残った課題

- **多要素**: TOTP は入れたが、QR コードは出さない (秘密の値と URI を写す)。予備の使い捨ての番号 (なくしたとき用) も
  無い (管理者が `console:otp_off` で外す)。管理者にだけ多要素を必須にする設定も無い。
- **動かしたままの反映**: 今は設定を書いて zenohd-cloud を起動し直すので、クラウドにつながる全員が数秒切れ、
  CRuby のノードは起動し直しが要る。1.10.1 の管理用の空間から ACL を書き換えられるかは試していない
  (`adminspace/permissions/write` を開ける必要があり、開けると網から書けてしまうので、別の守りが要る)。
- **ROS 2 の生存のしるし**: 5 章。クラウド側の ROS 2 を client の形にする (compose の変更) か、zenoh の版をそろえる。
- **反映の権限**: Rails が docker を動かす (`docker compose restart`)。この手元では Rails の利用者が docker を
  使えるので、その気になれば signer の volume にも届く。サーバに置くなら、Rails を docker の権限の無い利用者で動かし、
  起動し直しは 1 つのコマンドだけを許す仕組み (sudo の規則など) に任せる。README に書いた。
- **照らし合わせ**: ROS 2 の peer の証明書の名前とグラフの点はつなげない (3.7)。クラウドのルータの中から
  セッションの証明書の名前を読む仕組み (W1 6 章の (1)) が要る。
- **眺めるキー**: ログインしていれば誰でも、どのキーでも眺められる (呼び出しのような許可の表は無い)。
- **反映の後の比較**: 6 章のとおり、運んでいるものの線が無いセッションは zid で比べるので「戻らない」に見えることが
  ある。
