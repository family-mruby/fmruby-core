# R1 報告: ROS 2 (rmw_zenoh) との最小の疎通

> 状態: 完了 (検収待ち) | 更新: 2026-10-07 | instruction_r1.md の実装と確認の記録。ROS 2 Jazzy (rmw_zenoh_cpp 0.2.11、Zenoh 1.8.0) を docker で立て、既存の zenohd 1.10.1 につないだ。Zenoh の gem に attachment と Session#zid を足し、純 Ruby の Asterism::CDR / Asterism::ROS を書いた。P4-Nano と sim の ros2_talker が ROS 2 の `ros2 topic echo` / `ros2 topic pub` / `ros2 node list` / `ros2 topic list` と通じ、受け入れ条件 1-6 を満たした。版の不一致は無く、止まる条件には当たらなかった

## 1. 結果の要約

- PC 側: ROS 2 **Jazzy**、**rmw_zenoh_cpp 0.2.11** (`ros-jazzy-rmw-zenoh-cpp 0.2.11-1noble.20260915`)、その中の
  **zenoh-c / zenoh-cpp 1.8.0** (`ros-jazzy-zenoh-cpp-vendor 0.2.11`、libzenohc.so の版の文字列 `v1.8.0-2687c513...`)。
  ルータは既存の **zenohd 1.10.1** (docker-compose.yml の zenohd) をそのまま使い、rmw_zenohd は使わなかった。
  機体側は zenoh-pico 1.10.1 (固定のまま)。1.8.0 (ROS 2) - 1.10.1 (ルータ) - 1.10.1 (zenoh-pico) の組で問題なく通じた。
- 環境: 親リポジトリの `docker-compose.ros2.yml` (新規)。`ros:jazzy-ros-base` に `ros-jazzy-rmw-zenoh-cpp` を入れた
  イメージをその場で作る (`dockerfile_inline`)。ホストへのパッケージの導入・sudo は無し。ホストへのポートの公開も無し。
- gem (`picoruby-asterism-zenoh`): `put(key, payload, attachment: bytes)`、購読の `each_pending` の 3 つ目の値
  (attachment、無ければ nil)、`Session#zid` を足した。zenoh-pico の設定は変えていない (attachment は常に
  組み込まれている)。
- 純 Ruby (`picoruby-asterism` の mrblib に cdr.rb・ros.rb): `Asterism::CDR` (Writer / Reader) と `Asterism::ROS`
  (Node / Publisher / Subscription / Attachment / StdMsgs::String)。使うのは `Asterism::Zenoh::Session` だけで、
  Family mruby にも A1 のオブジェクトの層 (MessagePack) にも依存しない。
- 試しのアプリ `flash/app/test/ros2_talker.app.rb` (+ .app.toml)。
- P4 (NARYAv4) のファームは develop から **+12,272 B** (区画の残り 882,384 B、12%)。静的な内蔵 RAM の区画は同じ大きさ、
  起動時の `M1|` は全段で同じ (非同期の段の揺れ +4-8 B のみ)。**起動時の内蔵 RAM の増分 0**。

## 2. 観察したワイヤの形 (rmw_zenoh_cpp 0.2.11)

観察の方法: docker の中で `ros2 topic pub` を走らせ、別のコンテナの zenoh-python (eclipse-zenoh 1.10.1、使い捨ての
イメージ) からルータの購読と liveliness の取得で生のバイトを見た。仕様は rmw_zenoh の jazzy の枝の docs/design.md と
`attachment_helpers.cpp`・`liveliness_utils.cpp`・`rmw_subscription_data.cpp` で確かめた。

| 項目 | 観察した形 | 例 (std_msgs/String、ドメイン 0、/chatter) |
|---|---|---|
| データのキー | `<ドメイン>/<トピック名 (先頭と末尾の / を除く)>/<DDS の型名>/<型のハッシュ>` | `0/chatter/std_msgs::msg::dds_::String_/RIHS01_df668c740482bbd48fb39d76a70dfd4bd59db1288021743503259e948f6b1a18` |
| 型名 | DDS の名前 (`<パッケージ>::msg::dds_::<型>_`) | `std_msgs::msg::dds_::String_` |
| 型のハッシュ | `RIHS01_` + SHA-256 の 64 桁 (型の記述から計算する。std_msgs/String は定数で持った) | `RIHS01_df668c74...6b1a18` |
| CDR | 先頭 4 バイト `00 01 00 00` (リトルエンディアンの CDR)。文字列は uint32 の長さ (終端の NUL を含む) + 中身 + NUL。揃えはヘッダの直後から数える。末尾の詰め物は無い | `"hello"` -> `00 01 00 00  06 00 00 00  68 65 6c 6c 6f 00` |
| attachment | int64 の通し番号 + int64 の送った時刻 (UNIX 時刻の ns)、いずれもリトルエンディアン、GID の長さ 1 バイト (16)、GID 16 バイト。計 33 バイト | `ed01000000000000 ba98fe2ff830dc18 10 b434de9e...dcbb74` |
| attachment の要否 | **必須**。rmw_zenoh の購読は attachment の無い標本を捨てる (`Unable to obtain attachment for topic ...` を出して捨てる)。REST から attachment なしで put して実際に捨てられることを見た | - |
| 符号化 (encoding) | `zenoh/bytes` (既定のまま。見ていない) | - |
| ノードのトークン | `@ros2_lv/<ドメイン>/<zid>/<nid>/<nid>/NN/<enclave>/<名前空間>/<ノード名>` | `@ros2_lv/0/e05b88ef...bbec/0/0/NN/%/%/_ros2cli_28` |
| トピックのトークン | `@ros2_lv/<ドメイン>/<zid>/<nid>/<id>/MP` (出す側) または `MS` (受ける側) `/<enclave>/<名前空間>/<ノード名>/<トピック名>/<型名>/<型のハッシュ>/<QoS>` | `@ros2_lv/0/e05b88ef...bbec/0/4/MP/%/%/_ros2cli_28/%chatter/std_msgs::msg::dds_::String_/RIHS01_df66.../::,10:,:,:,,` |
| 名前の書き方 | トークンの中では `/` を `%` にする。根の名前空間と enclave は `%`。トピック `/chatter` は `%chatter` | - |
| QoS | 既定の値と同じ欄は空。既定の形 (reliable、volatile、keep last 10) は `::,10:,:,:,,` | - |
| zid | Zenoh のセッションの ID の 16 進 (rmw_zenoh は文字列として扱うだけで、形を確かめない) | - |

- `<nid>` はセッションの中のノードの番号、`<id>` はそのノードの中の実体の番号。rmw_zenoh は 0 から振る (ノードは
  `0/0`、出す側・受ける側は `0/1` から)。
- GID は rmw_zenoh ではトークンのキーの XXH3 128 ビット。受ける側は出す側を見分けるのに使うだけなので、Asterism::ROS
  はトークンのキーから作る 16 バイト (32 ビットの FNV-1a を 4 本) にした。`ros2 topic info -v` には GID として出る。
- サービス (`SS` / `SC`) は今回作っていない (6 章)。

## 3. 作ったもの

### 3.1 Asterism::Zenoh (足しただけ)

| 呼び出し | 内容 |
|---|---|
| `session.put(key, payload, attachment: nil)` | attachment は String (nil で無し)。zenoh-pico の `z_put_options_t.attachment` に写す |
| `sub.each_pending { \|key, payload, attachment\| }` | 3 つ目は String、無いか空なら nil。ブロック無しなら `[[key, payload, attachment], ...]` |
| `session.zid` | セッションの Zenoh の ID の 16 進の文字列 |

- 受け取った attachment は、キーと payload と同じ 1 つのバッファ (zenoh-pico の割り当て、P4 では PSRAM) の後ろに置く。
  輪の 1 枠は `size_t` 1 つ分 (Linux 8 バイト、P4 4 バイト) 大きくなるが、枠は `mrb_malloc` (アプリの VM プール、PSRAM)。
- liveliness の監視と get の答えは今までどおり 2 つの値。既存の呼び出し (asterism.rb・zenoh_* のアプリ) は 2 つの値で
  受けているので変更は要らなかった。
- zenoh-pico 1.10.1 は attachment を機能の切り替え無しで常に組み込んでいる。`zenoh_generic_config.h` は変えていない。

### 3.2 Asterism::CDR と Asterism::ROS (純 Ruby)

API は picoruby-asterism の README の「ROS 2」の節。要点:

```ruby
s = Asterism::Zenoh::Session.open("tcp/192.0.2.2:7447")
node = Asterism::ROS::Node.new(s, "fmruby_talker")
pub = node.publisher("/chatter", Asterism::ROS::StdMsgs::String)
sub = node.subscription("/chatter_back", Asterism::ROS::StdMsgs::String)
s.poll; pub.publish("hello"); sub.each_pending { |msg, info| ... }
node.close
```

- `Asterism::CDR::Writer` / `Reader`: uint8 / bool / (u)int16 / (u)int32 / (u)int64 / string。書くのはリトルエンディアン、
  読むのは両方。PicoRuby に `Array#pack` が無いので 1 バイトずつ組み立てる。64 ビットの読みは上の符号付きのバイトから
  積み上げて、Integer のあふれを避けた。
- 時刻: `Time.now` があれば ns、無ければ 0。
- ノードを作るとノードのトークン、publisher / subscription を作るとトピックのトークンを出す。`close` で引っ込める。
  close しなくても、セッションが閉じる (アプリの VM が閉じる) とトークンは消える。

### 3.3 ros2_talker

- ロケータは zenoh_echo と同じ (`/home/zenoh_echo.txt` の 1 行目、無ければ `tcp/zenohd:7447`)。ID は asterism_demo と
  同じ (`/home/asterism_node.txt`、無ければ mDNS 名、無ければ `linux`)。
- ROS のノード名は `fmruby_talker_<ID>` (`-` を `_` に。ROS の名前は英数字と `_` だけ)。
- 1 秒ごとに `/chatter` へ `"hello from <ID> N"`。`/chatter_back` に来た文字列を画面とログに出す (通し番号つき)。
- `on_destroy` でノードとセッションを閉じる。

## 5. 見立てと違った点・踏んだ罠

- **版の心配は要らなかった**。Jazzy の rmw_zenoh は Zenoh 1.8.0。ルータを rmw_zenohd に替えずに、zenoh-pico と同じ
  zenohd 1.10.1 を使えた。ROS 2 側は rmw_zenoh の既定のセッションの設定 (peer、マルチキャストの発見は切ってある) の
  まま、`ZENOH_CONFIG_OVERRIDE='connect/endpoints=["tcp/zenohd:7447"]'` で接続先だけを変えた。
- **attachment は「トピックの受信では無視してよい」ではなかった** (design.md 5 章の見立ての訂正)。rmw_zenoh_cpp 0.2.x
  の購読は attachment の無い標本を捨てる。トピックでも必須。
- **zid の形は確かめられない**。rmw_zenoh はトークンの zid を文字列として扱うだけなので、何でも通る。ただ、自分の
  セッションの本当の ID を使うのが正しいので `Session#zid` を足した (ほかの機体の同じ名前のノードとも区別できる)。
- **`ros2 topic pub` は相手の購読を待つ**。待つ相手は liveliness の MS のトークンで判定される。機体の購読のトークンが
  正しい形でないと pub が始まらない。これが通ったことで、MS のトークンの形も確かめられた。
- **PicoRuby の制約に合わせた書き方**: `Array#pack` 無し (1 バイトずつ)、`each_char` を避けて `byteslice` の
  ループ、64 ビットの掛け算のあふれを避けて GID は 32 ビットの FNV-1a、bare の `String` を避けて `::String`
  (`StdMsgs::String` という名前の中で混ざらないように)。
- **観察用の zenoh-python**: python:3.12-slim に `eclipse-zenoh==1.8.0` は wheel が無く入らなかった (ソースから
  作ろうとして失敗)。`>=1.8,<1.11` で 1.10.1 の wheel が入った。また `liveliness().get()` を回すのに `timeout` を
  付けないと終わらずに固まった (最初の観察のコンテナが 2 つ残っていたので、最後に消した)。
- **sim_down は ROS 2 のコンテナの分だけネットワークを消せない** (`Resource is still in use`)。ROS 2 のコンテナを
  止めた後に `docker network rm family-mruby_default` で消した。

撤回した仮説: なし (版を合わせるために rmw_zenohd を使う案は、試す前に zenohd で通ったので不要になった)。

## 6. 大きさと内蔵 RAM (P4-Nano、NARYAv4)

### 6.1 flash と静的な領域

同じ手順 (`FMRB_HW_TARGET=NARYAv4 rake build:esp32`。develop は `rake clean_all` の後、R1 は `rake clean` の後) で、
develop (6d1f6957) と R1 (c9b0cdc7) を比べた。

| | fmruby-core.bin | 区画 (0x700000) の残り | .iram0.text | .dram0.data | .dram0.bss | .flash.text | .flash.rodata |
|---|---|---|---|---|---|---|---|
| develop | 0x625940 | 0xda6c0 (12%) | 85,300 | 14,916 | 25,396 | 3,599,578 | 2,741,664 |
| R1 | 0x628930 (+12,272 B) | 0xd76d0 (882,384 B、12%) | 85,300 | 14,916 | 25,396 | 3,600,506 (+928) | 2,753,008 (+11,344) |

増分のほとんどは cdr.rb・ros.rb のバイトコード (.rodata)。C の増分 (attachment と zid) は .text の +928 B。

### 6.2 起動時

develop と R1 をそれぞれ `flash` (app_only) で焼いた直後の `M1|` 24 行を比べた。`boot_start` から `spawn:Services` まで
すべて同じ値。BLE と WiFi の段だけ R1 が +4-8 B (`ble_ready` 231016 / 231024、`wifi_rd` 212248 / 212252)、
`ble_nimble_port` の `largest` が 204800 / 200704 (非同期の段の揺れ、A1 と同じ種類)。周期ダンプの IRAM free は develop
208256-208280、R1 208224 (焼いた直後、遠隔の操作の前)。**起動時の内蔵 RAM の増分は 0**。

### 6.3 動かしている間と閉じた後 (R1)

| 状態 | IRAM free | 備考 |
|---|---|---|
| アプリの起動前 | 205664 | 焼いた後に tab5_fs で 2 つ put した後 |
| ros2_talker を動かしている間 (1 回目) | 187056 | アプリのタスク (スタック 16 KB) と接続 1 本 |
| 閉じた後 (1 回目) | 205348 (-316) | |
| 動かしている間 (2 回目) | 186880 | |
| 閉じた後 (2 回目) | 205176 (-172) | |
| 動かしている間 (3 回目) | 186680 | |
| 閉じた後 (3 回目) | 205176 (0) | |

- 3 回目は閉じた後に同じ値に戻ったので、回ごとの漏れではない。最初の数回に一度だけ取られるもの (A1 の 6.3、Z3 の
  12 章と同じ種類) と見ている。
- アプリのスタック: 16 KB のうち残り 9,168 B (使ったのは約 7.2 KB)。A1 の待つ呼び出し (10.7 KB) より浅い。
- アプリの VM プール: 296,712 B 使用 (1 MB のうち)。

## 7. PC 側の確かめ方

親リポジトリで:

```
# sim と確かめるとき (sim_up の後。zenohd は sim と一緒に上がる)
docker compose -f docker-compose.yml -f docker-compose.ros2.yml up -d zenohd ros2

# 機体と確かめるとき (zenohd を LAN に開く)
docker compose -f docker-compose.yml -f docker-compose.zenoh-lan.yml \
  -f docker-compose.ros2.yml up -d zenohd ros2

# 機体または sim で /app/test/ros2_talker.app.rb を起動してから
docker exec -it fmruby_ros2 ros2 topic echo /chatter std_msgs/msg/String
docker exec -it fmruby_ros2 ros2 topic pub -t 3 /chatter_back std_msgs/msg/String "{data: 'hello'}"
docker exec -it fmruby_ros2 ros2 node list
docker exec -it fmruby_ros2 ros2 topic list -t
docker exec -it fmruby_ros2 ros2 topic info -v /chatter

# 片付け
docker compose -f docker-compose.yml -f docker-compose.ros2.yml stop ros2 zenohd
```

- 初回はイメージ (ros:jazzy-ros-base + rmw_zenoh) を作るので数分かかる。
- 機体の `/home/zenoh_echo.txt` に PC の LAN のアドレス (`tcp/192.0.2.2:7447` など) を書いておく。
- WSL2 では Windows 側の TCP 7447 の受け入れの規則が要る (Z2 と同じ)。

## 10. 申し送り

- **asterism-cdr / asterism-msgs / asterism-ros に育てるとき** (design.md 2 章):
  - 今の `Asterism::CDR` はそのまま asterism-cdr の芯になる。足すもの: float32/float64 (PicoRuby の Float と、
    バイト列から浮動小数への変換の手段を確かめる)、配列 (uint32 の個数 + 要素)、固定長の配列、入れ子の構造体、
    XCDR2 (Kilted 以降で使うかは確かめる)。
  - 型のハッシュ (RIHS01) は、型の記述 (type description) を決まった形の JSON にして SHA-256 を取る。asterism-msgs では
    `.msg` から型の記述を作り、ハッシュを計算するか、ROS 2 の環境で `ros2 interface` などから取り出した値を同梱する。
    PicoRuby に SHA-256 があるかは要確認 (無ければ生成時に計算して定数で持つ)。
  - 型名は `std_msgs::msg::dds_::String_` の形。`.msg` の名前から機械的に作れる。
  - std_msgs/String の型のハッシュは Jazzy と Kilted / Rolling で同じはずだが、ディストリビューションごとに確かめる。
- **サービス**: rmw_zenoh は queryable (サーバ) と get (クライアント) に載せる。トークンは `SS` / `SC`。要求にも
  attachment (通し番号、時刻、GID) が要り、答えの attachment で要求と組にする。get の target は `ALL_COMPLETE`、
  queryable は complete で宣言する。今の gem の get / queryable は attachment を渡せない (put と購読だけに足した) ので、
  サービスでは `get(..., attachment:)`・`q.attachment`・`q.reply(..., attachment:)` を足す必要がある。get の target と
  queryable の complete の指定も今は無い。
- **QoS**: 今は既定 (reliable、volatile、keep last 10) の形をトークンに書くだけ。transient local は rmw_zenoh が
  Zenoh の advanced publisher (公開の控え) と advanced subscriber (履歴の問い合わせ) で作っているので、zenoh-pico の
  `Z_FEATURE_ADVANCED_PUBLICATION` / `SUBSCRIPTION` を有効にする必要があり、内蔵 RAM とバッファの量を測ってから決める。
  best effort は送る側の reliability の指定 (put のオプション) で作れる見込み。
- **liveliness のトークン**: rmw_zenoh のほかのノードは `@ros2_lv/**` を監視している。機体のトークンは 3 つ
  (ノード 1 + トピック 2) で、ROS 2 の側の `ros2 node list` の速さに問題は見えなかった。
- **ドメイン ID と名前空間**: Node に `domain:` と `namespace:` を渡せるが、0 と `/` 以外は確かめていない。
- **ノード名**: `fmruby_talker_<ID>` は機体ごとに違うので、同じ PC の ROS 2 から複数の機体が見分けられる。同じ機体で
  2 つ動かすと同じ名前のノードが 2 つになる (ROS 2 は警告を出すだけ)。
- **design.md 5 章の訂正**: 「attachment はトピックの受信では無視してよい」は誤り (2 章)。設計の文書の直しは
  親のセッションに任せる (触ってよい範囲の外)。
