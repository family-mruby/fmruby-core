## 2. 仕様の文書の構成 (docs/protocol.md)

1. Model: ノード・アプリ・オブジェクト、アプリごとに Zenoh のセッション 1 本、サーバ無し。
2. Names and keys: 名前の決まり (1 つの塊、`/ * $ ? #` 無し、`@` で始まらない、長さの制限は無い)、キーの表、`@profile` は verbatim の塊で `asterism/**` に入らないこと。
3. Values: MessagePack の使う型、Symbol は str、入れ子 16 段 (呼び出しの配列から数える)、各実装が書くバイトの形、移植性の無い入力の表、str に任意のバイトが乗ること。
4. Calls: get の形 (target ALL・consolidation NONE・parameters 無し・attachment 無し)、`[method, args, kwargs]`、答える側の手順 10 段、答えの形と、決まりそのものが出す例外のクラス名と文言、呼ぶ側 (最初の答えを取る・Zenoh の error reply は無視・「だれも答えない」)、入れ子の上限 4。
5. Meta: `{"methods" => [[name, arity]]}`、arity の意味 (-1 は調べない)、`*` で全オブジェクト、無いオブジェクトには答えない。
6. Liveliness: ノードの印とオブジェクトの印、消え方、`asterism/**` の監視の読み方、接続のときの二重起動の確かめ。
7. Profiles: 問い合わせの parameters (`icon=0|no|false`)、項目と上限、PNG の受け入れの条件と `icon_hash` の計算 (塊の CRC の並びの Adler-32)、読む側の掃除 (要約は受けたアイコンから計算し直す)。
8. 使う Zenoh の機能の最低限と版 (zenoh-c・zenoh-pico・zenohd とも 1.10.1)、使っていないもの。
9. 実装どうしの違いの表。
10. 適合の試験 (見本の形、driver、試される側の実装が何をするか)。
11. 捕まえた中身の例 (sim の端末のバイト列)。

## 3. 捕まえた中身との突き合わせ

構成: 親の compose の zenohd (1.10.1) と、CRuby の素の Zenoh だけで書いた記録用のノード (scratchpad の `cap.rb`。Asterism のオブジェクトの層を使わない)。相手は次の 3 つ。

| 相手 | 中身 |
|---|---|
| CRuby (asterism 0.6.0 + zenoh-c) | 作業ツリーの gem で `asterism_demo` と同じ形の info を公開したノード |
| mruby (`rake test:mruby` のビルド + zenoh-pico) | 同じスクリプトを mruby で |
| Family mruby のファーム | sim (Linux の標準構成、Tab5 相当 426x240) で `/app/test/asterism_demo.app.rb` を起動。端末の MessagePack (msgpack-c) が使われる |

やったこと:

- 記録ノードが偽のノード `cap` (アプリ `demo`、`screen` と `info` の印) になり、来た問い合わせのキー・parameters・payload・encoding・attachment を全部記録した。CRuby・mruby・端末から `cap` への呼び出し (`status`、Symbol と kwargs、入れ子、meta、`profile_of`) と、端末のキー操作 (`s` で screen.say、`r` で meta) を捕まえた。
- 逆に、記録ノードから 3 つの相手へ手で作った get を 31 種送り、答えのキー・payload・encoding を記録した (正しい呼び出し、kwargs、知らないキーワード、公開していないメソッド、引数の数違い、例外、無いオブジェクト、壊れた payload 6 種、ワイルドカード、meta、`*` の meta、プロフィールと parameters 4 種、`**`)。
- 生存の印の出方 (接続・終了の順) と、プロフィールの put (接続のとき・変えたとき) を記録した。

分かったこと (仕様に書いた):

- 呼ぶ側の payload のバイト列は 3 つで同じ (`93 a6 status 90 80`)。encoding は既定 (`zenoh/bytes`)、attachment は無し、meta とプロフィールの問い合わせは payload も parameters も無し (プロフィールは `icon=0` か空)。
- 答えのバイト列の違いは、32-255 バイトの文字列の形だけ: CRuby は str16 (互換モードに str8 が無い)、端末は str8。整数・小数・配列・map は同じバイト。試験用の mruby の MessagePack は array16・map16・int64 で書く (正しい形だが別のバイト)。よって適合はバイトではなく値で見る。
- 決まりが作る例外の文言は 3 つで同じ。言語の出す文言は違う (CRuby `unknown keyword: :nope`、mruby `unknown keyword: nope`)。
- 端末だけの振る舞い: bin を nil で読む (エラーにならない)、2^64-1 を -1 で読む、payload の後ろの余分なバイトを無視する、メソッド名が bin だと malformed。CRuby は bin を String で読み、余分なバイトは malformed。
- `@profile` は `asterism/**` の購読にも get にも入らない。`asterism/*/@profile` には入る。
- 終了のときは、オブジェクトの印が先に消え、ノードの印が後。
- ついでに分かった CRuby の小さな不具合: Integer が 64 bit を超えると、送る前に `EncodeError` ではなく `RangeError` が出る (README と違う)。直していない (案 R-4)。

記録の生データは scratchpad の `x0/` (`cap_*.jsonl`、`probe_*.jsonl`) にある。終わりに sim を下ろし、zenohd も止めた。

## 4. Ruby に寄った形の一覧と案 (要約、docs/protocol_review.md)

| 項目 | 今の形 | ほかの言語で困ること | おすすめ |
|---|---|---|---|
| R-1 引数 | `[method, args, kwargs]` (kwargs は空でも必ず) | TS・C にキーワード引数が無い | 3 つ組のまま。protocol 1 の受け手は `[method, args]` も受ける |
| R-2 Symbol | str になり、戻りは String | ほかの言語に Symbol が無い | そのまま、文書にする |
| R-3 Hash のキー | 何でも | Python は既定で str・bytes 以外を拒む (`strict_map_key`)、JS の object は文字列だけ | 移植できるのは str と int |
| R-4 整数 | CRuby は uint64 も送る、端末は int64 | JS は 2^53 まで | 符号つき 64 bit だけ。CRuby は範囲外を `EncodeError` に |
| R-5 小数と整数 | 1.0 は小数のまま | JS は区別できない | そのまま、受け手が変換する旨を書く |
| R-6 時刻 | 型が無い | | 慣習: エポックからの int ナノ秒。ext は後で |
| R-7 バイト列 | 全部 str (アイコンも) | **Python の既定はアイコンつきのプロフィールで UnicodeDecodeError、JS は壊れる。Python の bytes は端末で nil になる** | protocol 1 で bin。まず全部の受け手が bin を読む (端末の MessagePack の直し)、その後に送り手 |
| R-8 nil と省略 | 省略した kwargs と nil は別 | | そのまま、書く |
| R-9 例外 | Ruby のクラス名と文言 | 種類が分からない | 4 つ目の要素 `{"kind" => ...}` を足す (0.6.0 の呼ぶ側は無視するので互換) |
| R-10 メソッド名 | `?` `!` `=` も | Python などで書けない | 名前は不透明な文字列のまま、移植用の名前の目安と汎用の呼び出し口 |
| R-11 arity | 数か -1 | 省略可能な引数を表せない | 今はそのまま |
| R-13 決まりの版 | 無い | | プロフィールに `protocol` (無ければ 0) |
| R-14 呼び手 | 分からない (アプリが手で `from` を渡す) | | 下の 4.1 |
| R-15 壊れた入力 | 端末と CRuby で違う | | 余分なバイトと読めない型は malformed。端末の MessagePack を直す |
| R-16 ノードの印 | アプリどうしで同じキー | | アプリの印 `asterism/<node>/<app>` を足す (互換) |
| R-17 Zenoh の error reply | 使わない、呼ぶ側は無視 | | そのまま、書く |

互換の要点 (ソースで確かめた): 0.6.0 の受け手は呼び出しが**ちょうど 3 要素**でないと malformed にするので、呼び出しに要素は足せない。答えの配列の後ろの要素・meta のキー・プロフィールの項目・query の attachment・5 塊でないキーは 0.6.0 が無視するので、足しても壊れない。

### 4.1 呼び手 (R-14、2026-10-12 にユーザが案 C を選んだ件)

- Zenoh 1.10.1 には、get に送り手の情報 (source info: ZID と entity id) を付ける口があり、受け手は `z_query_source_info()` で読める。zenoh-c は unstable の API として持つ (配布物に入っている)。zenoh-pico は付ける側が `Z_FEATURE_UNSTABLE_API` を要し、picoruby-asterism-zenoh はこれを切ってビルドしている。既定では付かない (CRuby で確かめた: put の `source_zid` は nil)。asterism-zenoh が出しているのは `Sample#source_zid` と `Reply#replier_zid` だけで、`Query#source_zid` と `get(source_info:)` は無い。
- **source info は送り手が自分で書く** (`z_source_info_new` は任意の ZID を取る)。ルータが送り手のセッションと突き合わせる仕組みは API にも設定にも無い。生存の印にも宣言した ZID は付かない。よって Zenoh だけでは「名乗りと ZID が整合している」までで、本物かどうかは確かめられない。
- 案 C の組み方: (1) 呼ぶ側の gem が query の attachment に `{"from" => ノード ID}` を付ける (0.6.0 は attachment を無視するので互換)、(2) 各アプリが `asterism/<node>/@zid/<zid>` の印を出す (verbatim なので古い監視に入らない)、(3) source info に自分の ZID を付け、受ける側の gem が名乗り・ZID・印を突き合わせる。結果は「不明 (名乗り無し)」「名乗りだけ」「整合」「食い違い (呼び出しを断る)」。
- 本当に確かめるにはルータが要る: zenohd の ACL は、証明書の CN (W1 の mTLS) ごとに、どのキーに query してよいかを決められる。名乗りをキーに入れ (`.../call/<呼び手>`)、呼び手ごとの規則を W2 の台帳から作れば、ルータが保証する。キーが 6 塊になるので protocol 1 (R-13) が要る。
- 家のルータを経るとき: source info は要求の中身なので転送される (設計上。束ねが出していないので網では試していない)。どちらにしても送り手が書いた値のまま。端末は TLS が無いので、つながる LAN のルータを信じる範囲。ブラウザ版は `wss://` の中継の後ろで、クライアントの証明書が無く、zenoh-pico 1.10.1 は user/password の鍵を定義だけして使っていないので、常に「名乗りだけ」。
- API の案: a `Asterism.caller` (短いが `Kernel#caller` を隠す)、b `Asterism.current_call` (`from`・`verified`・`object`・`method`、呼び出しの外では nil)、c `expose(..., caller: :from)` で `from:` を gem が入れる (rover_brain の今の形に合う)。おすすめは b と、移行用に c。段取りは (1) 名乗りと API → (2) ZID の照合 (CRuby から、端末は unstable の API のビルドの大きさを測ってから) → (3) ルータが保証する形 (protocol 1)。(3) が無い間は「`from` は取り違え防ぎで、許可の仕組みではない (許可はルータの ACL)」と文書に書く。
- 足りないもの: asterism-zenoh に `get(source_info:)` と `Query#source_zid`、picoruby-asterism-zenoh に unstable の API でのビルドと同じ 2 つ、Zenoh 自体に「送り手が選べない送り手の ZID」(1.10.1 には無い)。

## 5. ユーザが決めること

docs/protocol_review.md の「Decisions」に番号つきで並べた (かっこ内はおすすめ):

1. R-1 3 つ組のまま、protocol 1 の受け手は 2 要素も受ける (はい)
2. R-2 Symbol は文字列として行き来する (はい、文書にする)
3. R-3 移植できるキーは str と int (A)
4. R-4 符号つき 64 bit だけ、CRuby は範囲外を `EncodeError` (はい)
5. R-5 JS から整数で来る小数は文書だけ (はい)
6. R-6 時刻はエポックからの int ナノ秒の慣習 (A)
7. R-7 protocol 1 で bin、受け手から先に (B)
8. R-8 nil と省略の違いを書く (はい)
9. R-9 例外に 4 つ目の要素 `kind` (はい)
10. R-10 メソッド名は不透明、目安と汎用の呼び出し口 (はい)
11. R-11 arity は今のまま (はい)
12. R-13 プロフィールに `protocol`、無ければ 0 (はい)
13. R-14 `Asterism.current_call` と `caller: :from`、段取り 1-3、食い違いは断る
14. R-15 余分なバイトと読めない型は malformed、端末の MessagePack を直す (はい)
15. R-16 アプリの印を足す (はい)

決まりの版の扱い (R-13 の案): 0.6.0 が無視する追加は版を上げない。0.6.0 が読み違える変更 (bin、呼び出しの形、5 塊の新しいキー) だけが protocol 1 で、相手のプロフィールが `protocol >= 1` のときだけ送る。protocol 1 のノードも当面は protocol 0 の呼び出しに答える (やめるのは 2.0 で決める)。

## 7. 気づいたこと

- 端末の MessagePack (fmruby-core `lib/add/picoruby-fmrb-msgpack`) が、読めない型 (bin・ext) を**黙って nil** にし、後ろの余分なバイトを見ない。Python など bin を普通に送る言語が入ると、端末への引数が知らないうちに nil になる。直すのは fmruby-core の C (3 行程度) で、網の形は変わらない (R-15・R-7 の第 1 段)。この段では触っていない。
- mruby の Proxy は、`Kernel` の private メソッドと同じ名前 (`fail` など) のメソッドを遠隔に送らず、手元で NoMethodError にする (CRuby は method_missing に回るので送る)。適合のノードを書いていて当たった。`Object` の公開メソッドの名前 (`display`・`hash`・`class`) はどちらでも送れない。網の決まりではなく Ruby の API の話として R-10 に書き、汎用の呼び出し口を案にした。
- CRuby の 64 bit を超える Integer は `RangeError` (README は `EncodeError`)。R-4 で直す案。
- 端末の答えは 50 ms ほどかかる (アプリの更新の周期で poll するため)。CRuby・mruby は 2-4 ms。決まりの外だが、ほかの言語の実装の時間切れの目安になる。
- docs/protocol.md と protocol_review.md は gem のファイルに入らない (gemspec の files の外。api_review.md と同じ)。
