## 2. 構成

```
[home]    sim (asterism_demo, ros2_talker)  --+
          P4-Nano (asterism_demo, WiFi)    --+-- tcp/7447 (plain) -- zenohd (home router, zenohd-home)
          ROS 2 (fmruby_ros2: talker)      --+                         |
                                                                       | tls/zenohd-cloud:7448 (mTLS, home dials out)
                                                                       v
[outside] CRuby (examples/node.rb)     -- tls/localhost:7448 --+-- zenohd-cloud (cloud router)
          the console's bridge         -- tls/localhost:7448 --+     TLS only, checks the peer's certificate,
          ROS 2 (fmruby_ros2_cloud)    -- tls (own network)  --+     ACL by certificate name
```

- **重ね合わせ**: `docker-compose.relay.yml` は、親の `zenohd` の起動の引数に `-c /relay/home.json5` を足し
  (REST・ストレージの引数は今までと同じ)、`zenohd-cloud` と `ros2-cloud` を足す。重ねなければ今までどおり。
  起動は次のとおり (sim_up は zenohd を素の docker-compose.yml で作り直すので、sim_up の後にやり直す)。

  ```
  docker compose -f docker-compose.yml -f docker-compose.zenoh-lan.yml \
    -f docker-compose.ros2.yml -f docker-compose.relay.yml up -d zenohd zenohd-cloud ros2 ros2-cloud
  ```

- **ポート**: 家は今までどおり 7447 (LAN 用の重ね合わせで LAN に出す)、REST 8000 は loopback。クラウドの 7448 は
  loopback にだけ出す (ホストの CRuby と bridge が `tls/localhost:7448` でつなぐ)。
- **ros2-cloud は別の網** (`relay_cloud`) に置き、その網には zenohd-cloud だけが入る。家の側からは名前も引けない
  (`getent hosts zenohd` が失敗する)。ROS 2 の値がルータ 2 台を通るしかない形にした。
- **bridge はクラウドのルータにつないだ**。クラウドから `@/*/router` を問うと家のルータも答えるので (4 章)、
  1 本で両方が見える。家につなぐと、クラウドの管理用の空間は ACL で見えない。

### 2.2 証明書の作り方

- 置き場所: asterism-console (`script/relay_certs` と `lib/relay/cert_authority.rb`)。W2 で画面から発行するとき、
  Rails からそのまま `Relay::CertAuthority` を使えるようにするため。Rails に依存しない素の Ruby (標準の OpenSSL) で、
  単体の試験もある。
- 出力: `asterism-console/storage/relay/certs/` (gitignore の中)。重ね合わせはここを `/certs` に読み取り専用で
  つなぐ (`ASTERISM_RELAY_CERTS` で別の場所にできる)。
- 中身: CA (`ca.pem`・`ca.key`、10 年) と、名前ごとの `<名前>.pem`・`<名前>.key` (825 日)。鍵は ECDSA P-256 の
  PKCS#8 (権限 0600)。証明書は v3 で、subjectAltName (名前そのものと追加の DNS 名・IP)、keyUsage、
  extendedKeyUsage (serverAuth と clientAuth の両方。ルータは待ち受けにもつなぐ側にも同じ証明書を使える)。
  subject の CN が ACL の `cert_common_names` に当たる。
- 使い方: `script/relay_certs` で CA と既定の 5 つ (zenohd-cloud、zenohd-home、console、cruby、ros2-cloud) を作る。
  CA と、すでにある名前は作り直さない (`--force` で作り直す)。`script/relay_certs mybot` で 1 つ足せる。
  `--rogue` で別の CA と、それが署名した zenohd-home の証明書を `rogue/` に作る (断られることを確かめる用)。
- 今は CA の鍵が発行した証明書と同じ所にある。W2 では分ける (6 章)。

### 2.3 asterism-console の変更

- bridge の 2 つのセッション (読むためのものと Asterism のもの) に、同じ zenoh の設定を渡す。環境変数
  `ASTERISM_TLS_CA`・`ASTERISM_TLS_CERT`・`ASTERISM_TLS_KEY` (mTLS)、または `ASTERISM_ZENOH_CONFIG` (JSON5 の
  ファイル)。
- グラフ: ルータどうしの線 `router_link` は、両側のルータがそれぞれ相手を挙げるので、組ごとに 1 本にまとめた
  (前は向きの違う 2 本になるところだった)。線にリンクの種類 (`tls`) を書く。ルータの名前は `metadata/name`
  (`router zenohd-cloud`)。
- 点の詳細: ルータは「Router links」(相手のルータ、種類、両端の住所) と、bridge がつないでいるルータなら
  「Certificate」(bridge 自身のリンクの `auth_identifier`)。セッションは「Link」(tcp / tls) と、tls なら
  「Certificate」(bridge 自身のセッションは自分の証明書の名前、ほかは「(the router does not show it)」)。
- 試験は 29 件 194 項目 (V1 の 26 件に、ルータ 2 台のグラフ、設定の読み方、証明書の 3 件を足した)。

### 3.1 往復の時間

すべて同じ PC の docker の中なので、中継の段が 1 つ増える分 (コンテナの間の TLS 1 本) は小さい。インターネット越し
なら、その往復がそのまま足される。

| 呼ぶ側 -> 相手 | 直接 (CRuby が家に tcp) | 中継 (CRuby がクラウドに tls) |
|---|---|---|
| CRuby -> P4-Nano `info.status` (100 回) | 最小 43.1 / 中央 150.8 / 最大 327.8 ms | 最小 22.6 / 中央 148.3 / 最大 313.3 ms |
| CRuby -> sim `info.status` (100 回) | 最小 1.3 / 中央 51.9 / 最大 55.9 ms | 最小 1.8 / 中央 52.9 / 最大 56.2 ms |
| CRuby -> CRuby (家の側、300 回、2 回ずつ) | 中央 2.15・2.17 ms、90% 4.25・4.22 ms | 中央 2.20・2.14 ms、90% 4.20・4.20 ms |

- P4-Nano と sim は、相手のアプリの刻み (sim は約 50 ms ごとに poll) と WiFi の揺れが大きく、中継の差は揺れの中に
  埋もれた。
- CRuby どうしでは、どちらも約 2.1 ms が下限 (受け取りのスレッドが何も来ないと 2 ms 眠る作り。gem の課題 7)。
  中継の差は 0.1 ms より小さかった。

## 4. 中継の先の管理用の空間の扱い

- **遠いルータは答える**。クラウドにつないだ bridge が `@/*/router`、`@/*/router/linkstate/**`、
  `@/*/router/token/**` を問うと、家のルータの分も返る。家のルータの管理用の空間の queryable がルータどうしの
  経路に乗って届くため。クラウドの ACL で、家からの `declare_queryable`・`reply` (`@/**`) と、家へ出す `query` を
  許した (許さないと家の分は返らない)。V1 の bridge の読み方を変えずに 2 台が見えたので、「ルータごとに bridge」
  「ルータごとの要約」は作らなかった。
- linkstate は家の側では `1 -- 0` の形 (V1 の正規表現で読める)。どちらのルータも相手を router のセッションとして
  挙げるので、線は組ごとに 1 本にまとめた。
- **リンクの証明書の名前は遠くから読めない**。zenohd はリンクごとの `auth_identifier` (証明書の CN)・
  `interfaces`・`mtu` などを `@/<zid>/session/transport/unicast/<相手>/link/<id>` に持つが、この部分はルータの中の
  セッション (REST のプラグインなど) からの問い合わせにしか答えない。クラウドの console から `@/<zid>/session/**`
  を問うと、zid を名指ししても 0 件だった。家の REST からは家の分が読めた。`@/<zid>/router` の sessions の links は
  `src` と `dst` だけ。そこで画面は、リンクの種類 (ロケータの頭) は全部に、証明書の名前は分かるものだけに出す
  (bridge が自分のリンクから知るクラウドの証明書の名前と、自分の証明書の名前)。
- **守り**: 管理用の空間はクラウドでは console の証明書にだけ読ませる。ほかの証明書と、家の側 (家のルータ経由) からは
  読めない (3.2)。家のルータの管理用の空間は、クラウドから見ると console だけが読める。

## 5. 見立てと違った点・踏んだ罠

- **ACL は広い宣言をそのまま断る**。`**` の購読 (`declare_subscriber`) は、許したキー (`demo/cruby/**` など) を
  含んでいても、宣言そのものが断られ、何も届かない (狭めて通すのではない)。最初の ACL の確かめはこれで全部
  「届かない」と出た。キーごとに購読して確かめ直した。console の値を眺める欄も、クラウドにつないでいる間は
  許したキーの範囲でしか値が来ない。
- **断った宣言の取り下げで ERROR が出る**。`Unknown subscriber id=3` (`hat::broker::pubsub`) など。上の広い購読を
  閉じたとき。害は無いがログは赤くなる。
- **クラウドを起動し直すと、ROS 2 の peer の生存のしるしが console のグラフから消えた**。値 (`I heard: ...`) は
  届き続けていた。クラウドのログには起動直後に `Received token with interest id from south-bound face. This
  message should only flow downstream` が ROS 2 の peer から多数。listener を起動し直すと点が戻った。原因は
  確かめていない (rmw_zenoh の peer がつなぎ直したときのしるしの出し直しと、ルータの扱いの食い違いと見ている)。
- **asterism の `Asterism.connect` が zenoh の設定を受け取れなかった**。`Asterism::Zenoh.open` と
  `Asterism::ROS.connect` は `config:` を受けるのに、オブジェクトの網だけ locator・mode・listen しか渡せず、
  CRuby のノードと bridge が TLS でつなげなかった。`config:` を足した (渡したときだけ `Session.open` に渡すので、
  機体の呼び方は変わらない)。zenoh が受け付けない設定は、`Session.open` と同じく `ArgumentError`。
- **ポートの公開で住所がまとまる**。ホストの CRuby と bridge のセッションの住所は、どれもコンテナの網の出口
  (`198.51.100.1` 相当) に見える。P4-Nano (LAN) も家のルータでは同じ出口から入ってくる。V1 の申し送りどおり zid と
  トークンの表で見分けている。
- **gossip**: クラウドで切った。ros2-cloud の住所は別の網にあるので、もし家に伝わってもつながらないが、
  中継の確かめに紛れが入らないようにした。

## 6. W2 (管理画面) への申し送り

- **証明書の名前とセッションの突き合わせ**: 遠くの管理用の空間からは証明書の名前が取れない (4 章)。台帳 (証明書の
  名前) とグラフの点 (zid) をつなぐには、(1) クラウドのルータと同じ所でルータの中から読む仕組み (REST の
  プラグインを loopback だけで開き、管理の仕組みだけが読む。REST は ACL を通らずに書けるので、外には出さない)、
  (2) 証明書の名前をノードの側が名乗る (Asterism のノードの ID と証明書の CN をそろえる決まりにし、ACL の
  subject と台帳を同じ名前で持つ)、のどちらかが要る。(2) が軽い。今回の既定の名前もそうしてある
  (`console`・`cruby`)。
- **CA の鍵**: 今は `storage/relay/certs/ca.key` が発行した証明書と同じ所にある。W2 で画面から発行するなら、
  `Relay::CertAuthority` の署名の部分を別のプロセス (または別の所の鍵) に分け、Rails の DB と同じ所に CA の鍵を
  置かない。発行の記録 (名前、通し番号、期限) を台帳に持つ。失効は zenohd 1.10.1 の設定に CRL の項目が無いので、
  当面は ACL から名前を外す + `close_link_on_expiration` と短い期限で受ける。
- **ACL の反映**: 設定ファイルを作り直してクラウドを起動し直す形で試した。起動し直すと家のルータは数秒で
  つなぎ直す (`connect` の既定の再試行)。CRuby・bridge は bridge だけがつなぎ直し、Asterism の CRuby ノードは
  つなぎ直さない (Z2 からの決まり)。ROS 2 の peer は値は戻るが生存のしるしが戻らないことがあった (5 章)。
  動かしたまま ACL を書き換えられるかは、`adminspace/permissions/write` を開けて確かめる必要がある (今回は閉じた)。
- **ACL の書き方の注意**: 宣言 (購読・問い合わせの先・生存のしるし) は、許したキーより広いと丸ごと断られる。
  画面で編集させるなら「このキーを許す」と「この形の購読を許す」が同じ規則で決まることを見せる。`@` で始まる
  キーは `**` に入らないので別に書く。
- **ACL の断りはログに trace でしか出ない**。画面で「断られた」を見せるには、ルータのログを trace で集めるか、
  別の手が要る。
- **ルータ 1 台につき 1 つの名前**: グラフのルータの名前は `metadata/name` から取る。W2 で作る設定ファイルにも必ず
  入れる。
- **往復の時間**: 段が増えると延びる。A1 の時間制限の既定 (2 秒) は、今回の構成では十分だった (最大 0.33 秒)。
  インターネット越しで延ばせるようにする話は plan どおり残る。
