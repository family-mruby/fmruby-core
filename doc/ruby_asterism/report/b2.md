# B2 報告: https で配るブラウザ版から網に入る

> 状態: 完了 (検収待ち) | 更新: 2026-10-12 | instruction_b2.md の実装と確認の記録。公開の版と同じ作り (rake wasm:dist) を手元で https で配り、Asterism の網に入れた。https のページからは、ループバックのルータへは ws:// のまま (Chrome・Firefox とも混在の例外)、それ以外へは wss:// を選ぶ。wss:// は親リポジトリの docker-compose.zenoh-wss.yml (Caddy が TLS を終えて zenohd の ws/ に流す)。ルータはページの Network の枠で設定し、CONF_KEYS の店に保存して次の起動に渡す。ノードの ID はページが最初の訪問で作る `wasm-<16 進 6 桁>` で、2 つ目のタブは保存しない使い捨ての ID。asterism-console は `wasm-<16 進 6 桁>` を端末 (▣) とみなすよう直した。公開済みの gem の直しは要らなかった。止まる条件には当たらなかった

手順書は ../browser.md。

## 1. 結果の要約

- https のページ (自前の CA の証明書) から、Windows の Chrome 154・Chromium 141・Firefox 142 のどれでも、
  手元のルータ `ws/localhost:7449` に TLS なしでつながった。ループバック以外への `ws://` はどれも SecurityError。
- 中継 `wss://<名前>:7450` 越しに、Chrome と Firefox の機械がつながり、互いに呼び合えた。S4 の操縦機
  (`rover_pilot`) も中継越しに台車を操縦し、カメラが 4.4-4.9 Hz で出た。
- ルータの設定は保存されて次の起動で使われ、`?zenoh=` はその回だけ効き、保存された値を書き換えない。
- 2 つのブラウザ (別のプロファイル) が別の ID で同時に入り、console に ▣ で並んだ。同じブラウザの 2 つ目のタブは
  `(this tab only)` の ID で入った。
- 既存の動き (起動、エディタ、保存、Config の設定の持ち越し、http の版) は壊れていない。
- 大きさ: core_web.wasm は変わらず (5,925,597 B)、core_web.js +277 B、core_web.data +1,495 B (設定の注釈とアプリ)。

## 2. ループバックの混在の例外の調べ

### 2.1 調べ方

https で配った小さなページ (Caddy、自前の CA) から `new WebSocket(...)` を作り、開いたか・投げたかを見た。
ページのオリジンは `https://localhost:8443` と、ループバックでない名前 `https://fmrb.test:8443` (ブラウザの名前解決で
127.0.0.1 に向けた) の 2 通り。Chromium と Firefox は Playwright の container (ループバックの口を host に転送)、
Chrome は Windows の本物を headless で。

### 2.2 結果

| ブラウザ | `ws://localhost` | `ws://127.0.0.1` | `ws://[::1]` | ループバック以外の `ws://` |
|---|---|---|---|---|
| Chrome 154 (Windows) | 開く | 開く | 失敗 (注) | SecurityError (作るところで投げる) |
| Chromium 141 | 開く | 開く | 開く | SecurityError |
| Firefox 142 | 開く | 開く | 開く | SecurityError ("The operation is insecure.") |

- オリジンが localhost でも fmrb.test でも同じ。どのブラウザも、https のページからループバックへの `ws://` を許す。
  よって手元のルータには TLS なしでつながる。
- 注: Chrome の `[::1]` の失敗は、docker が 7449 を 127.0.0.1 にだけ公開しているため (SecurityError ではなく
  つながらないだけ)。
- 投げる形: ループバック以外への `ws://` は WebSocket の作るところで例外になる (Chrome はコンソールに
  「Mixed Content ... must be available over WSS」)。リンクはこれを open の失敗として返す (前からある try/catch)。

### 2.3 公開の版 (インターネットのオリジン) では別の関門がある

Chrome 154 で、ページの置き場を「公開の網」とみなさせる (`--ip-address-space-overrides=127.0.0.1:8443=public`) と、
ループバックへの `ws://` はつながらなかった (エラー)。`--disable-features=LocalNetworkAccessChecks` を足すと開いた。
つまり混在の例外は効いているが、Chrome の Local Network Access (公開のサイトから手元・LAN への接続に許可を求める)
が止めている。headless では許可を出せないので、実物で出る許可の画面は確かめていない。公開の版から手元・LAN の
ルータ (中継も LAN の IP なら同じ) につなぐときは、使う人が許可する必要がある見込み。Firefox はこの形では試していない。

## 3. wss:// の作り

### 3.1 リンク

- zenoh-pico のロケータは `ws/<host>:<port>` のまま。`_z_ws_endpoint_init` は今までどおり `ws://host:port/` を
  組み立て、主スレッドで WebSocket を作る直前 (zp_ws_js_open) に scheme を決める:
  ページが https で、相手がループバック (`localhost`・`*.localhost`・`127.x.x.x`・`[::1]`) でなければ `wss://`。
  http のページは常に `ws://`。
- 指示書の案 (`_z_ws_endpoint_init` で選ぶ) ではなく主スレッドで選んだのは、ページの https/http を確かに知って
  いるのが主スレッドだから (呼び出しも増えない)。
- ロケータで wss を明示する形は作らなかった。zenoh-pico の端点の設定 (`#...`) はリンクの層まで渡らず、gem を
  直さずに通す道が無い。規則だけで足りる (ループバック以外は https なら wss しか開けず、ループバックは ws で開ける)。
  できないのは「http のページから wss の中継」と「ループバックの名前で中継」だけ (browser.md 9 章)。

### 3.2 中継 (親リポジトリ docker-compose.zenoh-wss.yml)

- Caddy (caddy:2-alpine) が `https://${ZENOH_WSS_HOST}:7450` で TLS を終え、WebSocket の要求だけを
  `${ZENOH_WSS_UPSTREAM:-zenohd:7449}` に流す。それ以外の要求には「証明書を許した」旨の 1 行を返す (ブラウザは
  WebSocket の証明書の警告を出さないので、使う人はまずこの URL を開いて許す)。
- 証明書は Caddy の自前の CA (`tls internal`)。CA は volume に残る。設定 (Caddyfile) は compose の `configs.content`
  に書き、ファイルを増やさなかった。
- `ZENOH_WSS_HOST` は必須にした (ループバックの名前を既定にすると、ページが ws:// を選んで中継を通らないため)。
  公開の範囲は `ZENOH_WSS_BIND` (既定 127.0.0.1)。
- zenoh-ws.yml の後に重ねる。既存のファイルは変えていない。
- 確かめ: 中継の中で 7450 (ブラウザ側) と zenohd:7449 への接続が張られていること、TLS だけの 7450 につながったこと
  (平文の ws:// では開かない口) で、wss で通ったと判じた。

## 4. ルータの設定 (決めたこと)

- ページの下に枠 Network を足した (Display・Your files と同じ枠と `.field` の行)。中身は Router の 1 行と注記。
  入力欄は既存の select と同じ見た目にした。新しい作りの画面は起こしていない。
- 値は `ws/<host>:<port>` (`?zenoh=` と同じ文字の決まり)。Enter か欄を離れたときに保存し、注記が
  「saved; used from the next start ...」に変わる。空なら束の既定に戻す。形が違えば「not saved」。
- 保存先は CONF_KEYS の店 (`fmrb_web_conf`)。`zenoh_router` を CONF_KEYS に足したので、機械の中で
  system_conf.toml を直した値も持ち越す。
- 取り込み (ページを離れるときに system_conf.toml を読んで店に書く) の例外を 2 つ足した:
  - その回が `?zenoh=` で開かれたとき (ファイルの値は URL のもの。startup_app と `?app=` の扱いと同じ)。
  - その回に Network の枠で Router を変えたとき (ファイルの値は古い)。
  どちらも店の Router をそのまま残す。
- 機械に渡す順は、店の値 → `?zenoh=` (後が勝つ)。
- 設定は「次の起動から」。動いている機械のつなぎ先は変えない (Config の Save と同じ扱い)。
- page_settings_wasm.c の受け取りの数を 24 → 28 にした (CONF_KEYS 20 + startup_app + zenoh_router + asterism_node と余り)。

## 5. ノードの ID (決めたこと)

- 形: `wasm-<16 進 6 桁>` (crypto.getRandomValues で 3 バイト)。端末の `fmruby-<16 進 6 桁>` に揃えた。
- 置き場: localStorage の `fmrb_web_node`。版で消える CONF_KEYS の店とは別にした (ID が出し直しのたびに変わると
  console の許可や記録の名前が切れるため)。Erase では消さず、バックアップにも入れない。
- 渡し方: 起動のときに `--fmrb-conf=asterism_node="wasm-xxxxxx"`。config/system_conf_wasm.toml に
  `asterism_node = ""` を足した (page_settings_wasm.c は在る行しか書き換えない)。
- 使い方: 試しのアプリ 4 本 (asterism_demo・rover_cam・rover_pilot・rover_brain) の ID の決め方を
  `/home/asterism_node.txt` → mDNS の名前 → 設定 `asterism_node` → `FmrbConst::BOARD` にした
  (設定を読む関数を `conf_router` から鍵を取る `conf_value(key)` にした)。sim・端末は設定が無いので変わらない。
- 2 つ目のタブ: /home の Web Locks (`fmrb-home`) を取れなかったタブは、保存しない新しい ID で網に入る。
  2 つ目のタブは既に「/home を保存しない使い捨ての機械」なので、ID もそれに揃えた (つながない案より、2 つ目のタブで
  何かを試す人に分かりやすい)。枠の見出しに `node wasm-xxxxxx (this tab only)` と出る。
- ロックの判定を待ってから ID を決めるため、起動 (Click to start) の処理で `lockDecided` を待ってから引数を足す。
- drive の status に `node` と `node_kept` を足した。

asterism-console (main、lib/bridge/marks.rb): 端末の名前の規則に `wasm-[0-9a-f]{6}` を足した。

```diff
-    BOARD_NAME = /\A(fmruby-[0-9a-f]{6}|linux|wasm)\z/
+    BOARD_NAME = /\A(fmruby-[0-9a-f]{6}|wasm-[0-9a-f]{6}|linux|wasm)\z/
```

試験 (marks_test.rb) と docs/v2_2.md も合わせた。

## 7. 気づいたこと

- sim_up は zenohd を docker-compose.yml だけで作り直す (ws/ の待ち受けが消える)。sim を上げた後に ws の重ね合わせで
  zenohd を起こし直した。browser.md に書いた。
- 同じ ID で閉じてすぐ開き直したとき、1 回だけつながるまで 3.9 s かかった (ほかは 21-56 ms)。前のセッションの後始末を
  ルータが待った可能性があるが、追っていない。
- Playwright の `context.close()` では pagehide が来ず、設定の取り込みが走らない。測りではページを離れる (別の URL へ
  移る) 形で確かめた。実物のタブを閉じるときは pagehide が来る。
- 親の docker/mujoco/README.md の S4 の節は「the node is `wasm`」と書いてある。今は `wasm-<16 進 6 桁>` (親の
  リポジトリの直しは今回の範囲外なので残した)。

## 8. 公開の版へ出すときに要ること (残った課題)

- **Local Network Access**: 公開のサイトから手元・LAN のルータへつなぐと、Chrome は許可を求める (2.3)。許可の画面の
  出方と、断ったときにページが何と言うかは実物で確かめていない。ページに案内を足すかを決める。
- **インターネットの向こうのルータ**: 公開の版から使うなら、本物の証明書を持つ wss の口が要る (自前の CA の証明書は
  使う人ごとに許してもらう必要がある)。ルータに認証が無いので、公開するなら W の中継 (mTLS・ACL) の手前に置く形を考える。
- **GitHub Pages / coi-serviceworker**: 確かめはサーバが COOP/COEP を返す形 (wasm:serve)。公開の版は coi-serviceworker
  で隔離を作る (初回に 1 回読み直す)。WebSocket はこれに関係しないはずだが、Pages の上では確かめていない。
- **設定の持ち越し**: Router は CONF_KEYS の決まりで束の版に結び付くので、公開の版を出し直すと既定に戻る。ID は戻らない。
- **自動の確かめ**: fmrb_web.rb は http の開発サーバに話す。https の版を操作するには、今回のように https の proxy を
  開発サーバの前に置く (drive の中継はそのまま通る)。
- **ID の重複の検査**: design.md 9 章の「起動のときに liveliness で同じ ID の重複を確かめる」は入れていない。
