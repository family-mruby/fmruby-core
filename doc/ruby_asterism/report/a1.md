# A1 報告: 遠くのオブジェクトの代理

> 状態: 完了 (検収待ち) | 更新: 2026-10-07 | instruction_a1.md の実装と確認の記録。Zenoh の gem を Asterism::Zenoh (picoruby-asterism-zenoh) に改名し、peer の上限を 3 にし、その上に純 Ruby の picoruby-asterism を作った。sim と Tab5 がルータ経由で互いの APU・画面・情報のオブジェクトを代理で呼び合い、受け入れ条件 1-9 を満たした。途中で Tab5 のアプリのスタックが溢れたので、gem の待ちの作りを軽くした (5 章)

## 1. 結果の要約

- 改名: モジュールは `Asterism::Zenoh`、例外は `Asterism::Zenoh::Error`、gem は `lib/add/picoruby-asterism-zenoh/`。
  最上位の `Zenoh` はコードのどこにも無い。改名だけのコミットにした。
- peer の上限: zenoh-pico の `Z_LISTEN_MAX_CONNECTION_NB` を、gem の mrbgem.rake が作る config.h の中で 3 にした
  (vendor/ は書き換えていない)。sim で 4 つ目の peer が断られた。
- picoruby-asterism: mrblib だけの gem (asterism.rb / future.rb / proxy.rb)。使うのは `Asterism::Zenoh` と
  `MessagePack.pack` / `unpack`、それに PicoRuby の `Machine` (あれば。時計と待ちの間の短い休み)。Family mruby の
  API は使っていない。Linux と P4 のビルドだけに入れた。
- 試しのアプリ `flash/app/test/asterism_demo.app.rb`: `apu` (MML)・`screen` (窓に文字)・`info` (状態など) を公開し、
  相手のものをキーで呼ぶ。
- PC 側: `tools/fmrb_zenoh.rb` に `call` と `meta`、純 Ruby の MessagePack の部分集合 `tools/fmrb_msgpack.rb`。
- 往復の時間 (ルータ経由): sim と Tab5 の間で 1 回 35-236 ms (ほとんど 100-200 ms)。PC から Tab5 へ 73-184 ms。
- Tab5 のファームは develop から +18,688 B (区画の残り 12%)。起動時の内蔵 RAM の増分は 0。

## 2. API

### 2.1 Asterism::Zenoh (改名と追加だけ)

Z3 までの API はそのまま (名前の前に `Asterism::` が付く)。足したのは定数 `Asterism::Zenoh::MAX_PEERS` (3)。
上限はビルドの時の環境変数 `PICORUBY_ZENOH_MAX_PEERS` (1..10) で変えられる。

### 2.2 Asterism

| 呼び出し | 戻り値 | 例外・時間切れ・注意 |
|---|---|---|
| `Asterism.connect(locator, node:, app:, mode: nil, listen: nil)` | `Asterism` | `locator` / `mode:` / `listen:` は `Asterism::Zenoh::Session.open` に渡す。`node:` は機体の ID、`app:` はアプリの名前 (キーの 1 区切り。`/ * $ ? #` を含まず `@` で始まらない。違えば `ArgumentError`)。つながらなければ `Disconnected`。同じ `<ID>/<アプリ>` のオブジェクトがもう生きていれば `Error` (同じアプリの 2 つ目)。接続済みでも `Error` |
| `Asterism.expose(name, obj, methods:)` | `"<ID>/<アプリ>/<name>"` | `methods:` は名前の配列か、`名前 => 引数の数` の Hash (呼ぶ前に数を確かめる。配列の形と -1 は確かめない)。`obj` に無い公開メソッドは `ArgumentError`。同じ名前は置き換え |
| `Asterism.unexpose(name)` | true / false | |
| `Asterism.poll` | true / false | アプリの更新ごとに呼ぶ。Zenoh の poll、届いた呼び出しへの応答、生存の追跡。切れていれば false |
| `Asterism[path, timeout_ms = 2000]` | `Proxy` | `path` は `<ID>/<アプリ>/<オブジェクト>` (ワイルドカードは不可)。作っただけでは何も送らない |
| `proxy.メソッド(*args, **kw)` | 相手の戻り値 | 答えを待つ (既定 2 秒)。相手で例外・公開していない (`NoMethodError`)・引数の数が違う (`ArgumentError`)・そのオブジェクトが無い (`NameError`) は `RemoteError`。答えが来ないと `Timeout` (誰も答えないキーは、ルータがすぐ終わりを返すので即座に)。切れていると `Disconnected`。送れない値は送る前に `EncodeError`。ブロックは渡せない (`ArgumentError`) |
| `proxy.async.メソッド(...)` | `Future` | 送ってすぐ戻る |
| `future.done?` / `future.value` / `future.took_ms` | | `done?` は待たない (`Asterism.poll` で進む)。`value` は終わるまで待ち、待つ形と同じ例外を出す |
| `proxy.respond_to?(name)` / `proxy.methods` | true / false、Symbol の配列 | meta から (1 回だけ取る。`asterism_refresh` で取り直す)。相手が答えないと `respond_to?` は false、`methods` は例外 |
| `proxy.asterism_meta` / `proxy.asterism_path` | Hash、String | |
| `Asterism.each(pattern = "**") { \|proxy\| }` | 件数 (ブロック無しなら配列) | 今生きている公開中のオブジェクトのうち `<ID>/<アプリ>/<オブジェクト>` が合うもの (自分のアプリのものを含む)。`*` は 1 区切り、`**` は任意の数 |
| `Asterism.nodes` | ID の配列 | 今生きているノード。自分が先頭 |
| `Asterism.connected?` / `node_id` / `app` / `exposed` / `lost_reason` | | |
| `Asterism.close` | nil | 公開を全部引っ込める。何度呼んでもよい |

例外: `Asterism::Error` (基底、`StandardError`)、`EncodeError`、`RemoteError` (`remote_class`・`remote_message`)、
`Timeout`、`Disconnected`。

**切断の扱い (指示書で選ぶように言われた点)**: `Asterism::Zenoh::Error` は Asterism の外へは出さず、必ず
`Asterism::Disconnected` に包む (文言は元のまま)。理由は、使う側が `rescue Asterism::Error` 一つで Asterism の
失敗を全部受けられるようにするため。切れた後の動きは Z2 の決定のまま (自動でつなぎ直さない、`poll` が false、
アプリが `connect` と `expose` をやり直す)。README に書いた。

### 2.3 キーと符号 (実際)

| キー | Zenoh | payload (MessagePack) |
|---|---|---|
| `asterism/<ID>/<アプリ>/<オブジェクト>/call` | get / queryable | 問い: `[メソッド名, [引数...], {キーワード}]`。答え: `["ok", 戻り値]` か `["error", 例外のクラス名, メッセージ]` |
| `asterism/<ID>/<アプリ>/<オブジェクト>/meta` | get / queryable | 答え: `{"methods" => [[名前, 引数の数], ...]}` (数を宣言しなければ -1)。オブジェクトを `*` にすると公開中のもの全部が 1 件ずつ答える |
| `asterism/<ID>` | liveliness | ノードがつながっている |
| `asterism/<ID>/<アプリ>/<オブジェクト>` | liveliness | オブジェクトを公開中 |

- queryable はアプリごとに 1 つ (`asterism/<ID>/<アプリ>/**`)。答えのキーは自分の具体的なキーにする (問いの ID や
  アプリがワイルドカードでも答えられる)。
- キーワードは文字列のキーで送り、公開する側で Symbol に戻して `public_send(name, *args, **kw)` する。
- 自分のアプリのオブジェクトを呼ぶと、ネットワークに出さずにその場で同じ符号・同じ確かめで実行する (Zenoh の
  セッションは自分の queryable を見ないため)。

### 2.4 値

nil・真偽・整数 (64 ビット)・浮動小数・文字列・配列・Hash。Symbol は文字列になる。それ以外は送る前に
`EncodeError` (戻り値の場合は呼んだ側に `RemoteError` の `Asterism::EncodeError`)。入れ子は 16 段まで。

`info.echo` (受け取ったものを返す) で PC から確かめた: null / true / false / -5 / -200 / 70000 / 2^40 / -2^40 /
2^63-1 / 1.5 / -0.25 / "日本語" / 入れ子の配列 / 入れ子の Hash / "" / [] / {} がすべてそのまま戻った。
キーワード `tag:` も届き、知らないキーワードは `ArgumentError: unknown keyword: nope`。picoruby-fmrb-msgpack は
直さずに使えた (止まる条件に当たらない)。

## 5. 見立てと違った点・踏んだ罠

### 5.1 Tab5 でアプリのスタックが溢れた

最初の版で、Tab5 のアプリから相手の `respond_to?` と `methods` を試す操作 (キー `r`) をすると
`Stack protection fault` (タスク `Asterism Demo`、16 KB) で再起動した。sim では起きない (Linux のスタックは大きい)。

- mruby は Ruby から Ruby への呼び出しでは C のスタックを使わないが、C の関数が Ruby を呼び返す (ブロックを
  呼ぶ、`respond_to?` が `respond_to_missing?` を呼ぶ、イベントを C から渡す) たびにインタプリタが入れ子になる。
- 最初の版は、待ちの中で zenoh の答えを `each_reply { }` (C からブロック) で受け、meta の取得は
  `respond_to_missing?` の中 (C の `respond_to?` から呼ばれる) から始まり、デモは呼び出しを `on_event` (C から
  `_dispatch_event` 経由) の中で行っていた。その上で zenoh-pico の poll が回る。
- 直したこと: gem は答え・生存の出来事・問い合わせを配列の形 (ブロック無し) で受け、`Proxy#respond_to?` を Ruby で
  定義した。デモはキーを `on_event` で覚えるだけにして、`on_update` で呼ぶ。
- 測った値 (16 KB のうち使った量、周期ダンプの Free から): 待っていないとき 8.1 KB。直した後、`on_event` の中で
  1 回待つと 12.4 KB、`on_update` の中なら 10.7 KB。`on_update` の形では、入れ子の呼び合い (relay) を含めて全部の
  操作で 10.7 KB を超えなかった (残り 5.6-5.8 KB)。README に「待つ呼び出しは更新の中から、または async で」と書いた。
- 待ちの入れ子の上限 (`MAX_NESTING` = 4) は残したが、P4 の 16 KB で 4 段まで足りるかは測っていない (デモで出るのは
  2 段)。

### 5.2 その他

- **mruby に `nil.to_i` が無い**。デモの `@says.to_i` で落ちた (sim の互換構成で見つけた)。gem にも `@depth.to_i` が
  あったので `(@depth || 0)` にした。
- **zenohd の REST の GET は本文を問いの payload として渡す**。そのため PC の `call` は REST だけで書けた
  (MessagePack を本文に入れ、答えは base64 で返る)。
- **誰も答えないキーへの get は、時間を待たずに終わる**。相手のアプリが閉じると queryable が無くなり、ルータが
  すぐ終わりを返す。`Timeout` は 3 ms で出る。文言を「nobody answers」と「within N ms」で分けた。
- **sim_up は zenohd を LAN 向けの重ね合わせなしで作り直す**。そのたびに Tab5 の接続が切れたので、
  `docker compose -f docker-compose.yml -f docker-compose.zenoh-lan.yml up -d zenohd` をやり直した。
- **ID の重複**: 設計 (design.md 4 章) の「同じ ID がいないか確かめる」は、ノードの単位ではなく `<ID>/<アプリ>` の単位で
  した。ノードのトークン `asterism/<ID>` は同じ機体のアプリが皆出すので、ノードの単位で断ると 1 台で 2 つの
  Asterism のアプリが動かせない。確かめは `liveliness_get` で、ルータ経由なら答えはすぐ来る (最長 1.5 秒待つ)。
- **Method#arity が無い** (mruby-method の gem が入っていない)。meta の引数の数は、`expose` の `methods:` を Hash で
  書いたときだけ入る (配列なら -1)。

## 6. 大きさと内蔵 RAM / PSRAM (Tab5)

### 6.1 flash と静的な内蔵 RAM

同じ手順 (`rake clean_all` の後 `rake build:esp32`、.env のまま TAB5) で、develop (6d465862) と A1 を比べた。

| | fmruby-core.bin | 区画 (0x700000) の残り | .dram0.data | .dram0.bss |
|---|---|---|---|---|
| develop | 0x626710 | 0xd98f0 (12%) | 0x3ac4 | 0x74f4 |
| A1 | 0x62b010 (+18,688 B) | 0xd4ff0 (873,456 B、12%) | 0x3ac4 | 0x74f4 |

増分のほとんどは picoruby-asterism の mrblib のバイトコード (flash の .rodata)。NARYAv4 は A1 で 0x625940
(残り 12%)。NARYAv4 の develop は焼かないので作っていない。

### 6.2 起動時

develop と A1 のファームをそれぞれ `flash` (app_only) で焼いた直後の起動の `M1|` 行 (24 行) を比べた。値は
すべて同じか、非同期の段 (debugd と desktop の順の入れ替わり、BLE / WiFi) の揺れの範囲 (例: `wifi_rd` が
201884 と 201872)。周期ダンプの IRAM free は develop 197220、A1 197212-197244 (焼いた直後、遠隔の操作の前)、
PSRAM free は両方 10277652。**起動時の内蔵 RAM の増分は 0**。gem は純 Ruby なので、静的な領域も起動の処理も
増やしていない (デスクトップの VM が gem のバイトコードを読む分は PSRAM の VM プールの中)。

### 6.3 動かしている間と閉じた後 (最終のファーム)

| 状態 | IRAM free | PSRAM free |
|---|---|---|
| アプリの起動前 | 194652 | 10277652 |
| asterism_demo、接続して呼び合っている間 | 175808-175896 | 9847432 |
| 閉じて 3 分 (1 回目) | 194328 | 9356044 |
| 開き直して動かしている間 (2 回目) | 175816-175820 | 8925864 |
| 閉じて 3 分 (2 回目) | 194328 | 9356044 |

- 動かしている間の減り (約 18.8 KB) は、アプリのタスク (スタック 16 KB ほか) と接続 1 本 (lwIP) の分で、Z3 の
  zenoh_nodes (197200 -> 176200-178684) と同じ程度。アプリのスタックの残りは最小 5,736 B。
- アプリの VM プールは 314-320 KB (zenoh_nodes の 274-290 KB より約 30 KB 多い。gem のバイトコードとオブジェクト)。
- 1 回目に閉じた後の 324 B の差は 3 分たっても戻らなかったが、2 回目は閉じた後に同じ 194328 に戻った。回ごとに
  減るもの (漏れ) ではなく、最初の回に一度だけ取られるもの (Z2 の「最初の接続で一度だけ」、Z3 の 12 章の
  ESP-Hosted の溜め置きと同じ種類) と見ている。
- PSRAM はアプリで約 430 KB 減り (ほとんどが VM プール)、閉じると戻る。表の 921,608 B の段差は 1 回目の途中の
  tab5_screenshot (13:17:23) の直後に現れ、閉じた後も残るので、遠隔の画面の取得の側のバッファと見ている (アプリの開閉では動かない)。
- 起動前の 194652 が焼いた直後の 197212 より低いのは、その間の遠隔のファイルの転送 (tab5_fs put) の分
  (Z3 の 12 章と同じ現象)。

## 7. 呼び出しの往復の時間

ルータは PC の zenohd (Docker Desktop の中)。sim は同じ PC、Tab5 は WiFi。時間はアプリが呼んでから答えを
受け取るまで (デモの表示とログ)。

| 向き | 呼び出し | 時間 |
|---|---|---|
| sim -> Tab5 | say / play / secret / boom / meta (待つ形) | 86-205 ms (多くは 100-200 ms) |
| Tab5 -> sim | 同じ | 35-236 ms (多くは 50-150 ms) |
| どちらも | async の status (`took_ms`、done? を見る更新の周期を含む) | 104-370 ms |
| どちらも | relay x10 (1 回 = 往復 2 回の入れ子) | 0.9-1.6 秒 (1 回あたり 90-160 ms) |
| PC -> Tab5 | REST 経由の call / meta | 65-184 ms |
| PC -> sim | REST 経由の call | 4-51 ms |

公開する側は `Asterism.poll` (アプリの更新、デモは 50 ms ごと) でしか答えないので、往復には相手の更新の周期が
最大 1 回分乗る。待っている側は 2 ms ごとに poll する。

## 10. A2 と ROS への申し送り

- **参照の受け渡し・イベント (A2)**: 今の符号は値の写しだけ。参照を返すなら、戻り値の位置に「代理の印」
  (例: `{"$ref" => "<ID>/<アプリ>/<名前>"}`) を置き、公開する側で一時の名前を付けて expose する形が今の
  キー空間のまま作れる。その場合、一時の公開をいつ引っ込めるか (呼んだ側の GC を知る手段が無い) が要点になる。
  イベントは put / subscribe (`asterism/<ID>/<アプリ>/<オブジェクト>/event/<名前>`) に載せるのが素直。
- **スタック**: 待つ呼び出しは C のスタックを食う (5.1)。A2 でブロックを渡す・コールバックを呼ぶ形にすると
  入れ子が増えるので、P4 の 16 KB で必ず測る。アプリの `.app.toml` の `task_stack_kb` で増やせるが、内蔵 RAM を
  使う。
- **ノードのトークンの共有**: 同じ機体の 2 つのアプリが同じ `asterism/<ID>` を出すと、片方が閉じたとき監視する側に
  「ノードが消えた」が届く (Z3 の重複の件と同じ)。`Asterism.nodes` はオブジェクトのトークンからも ID を拾うので
  一覧からは消えにくいが、正しく数えるには VM ごとのキー (`<ID>/<VM>`、design.md 4 章) か、トークンの数え上げが要る。
- **ROS の最小の疎通**: 下の `Asterism::Zenoh` は put / subscribe・get / queryable・liveliness が揃っているので、
  rmw_zenoh のキーと attachment を組み立てる純 Ruby の層 (asterism-ros) を同じ形で上に置ける。CDR の符号化は
  MessagePack と別に要る。
- **時間切れの刻み**: 待つ側の時間切れは Ruby で見ている (2 ms ごと) ので、zenoh-pico の 1 秒刻みの影響は受けない
  (2,006 ms で出た)。
