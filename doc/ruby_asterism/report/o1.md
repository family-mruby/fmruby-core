## 4. image の workflow (`.github/workflows/image.yml`)

- `v*` のタグで、`deploy/vps/Dockerfile` を linux/amd64 と linux/arm64 (QEMU) で作り、`ghcr.io/ruby-asterism/asterism-console:<版>`・`:<major>.<minor>`・`:latest` に push する。タグと `VERSION` が違えば失敗する。手で走らせたとき (workflow_dispatch) は作るだけで push しない。GHA のキャッシュを使う。
- compose は `${CONSOLE_IMAGE:-ghcr.io/ruby-asterism/asterism-console}:${CONSOLE_VERSION:-0.1.0}` を引く。手元で作る道は `docker-compose.build.yml` を重ねる。
- `VERSION` (0.1.0)、`CHANGELOG.md`。版はアカウントの画面と `bin/asterism version` に出る。image に OCI のラベル (版・出どころ・ライセンス)。
- actionlint 1.7.7 (shellcheck 込み、docker の公式 image) で 0 件。
- 手元で amd64 を作れた: キャッシュなしで 50 s、image は 316 MB。arm64 も手元の QEMU で作れた (11 分、340 MB、起動して asterism-zenoh が読めた)。

## 5. 最初の設定 (`bin/asterism setup`)

`docker compose run --rm console bin/asterism setup`。console のコンテナの中で、まだのことだけをする (何度走らせても、そろっているものは変えない):

1. `.env` の確かめ (秘密の値、名前、`example.org` が残っていないか)
2. `db:prepare`
3. CA: signer は CA が無くても起動し、`POST /init` で 1 度だけ CA を作る (2 回目は 409)。鍵は signer の volume のまま。指紋を出し、控えを促す。手持ちの CA は今までどおり `bin/signer import` (setup の前)
4. 役割の例「match」(役割が 1 つも無いとき)
5. 最初の管理者 (`ADMIN_EMAIL`・`CONSOLE_PASSWORD`、無ければ端末で聞く)
6. サーバ自身の証明書 (ルータ: 公開の名前と `zenohd`・`ASTERISM_RELAY_EXTRA_DNS`、bridge: `console`)。無い・別の CA・30 日以内に切れる・公開の名前を含まない、のときだけ発行し直す (`Relay::LocalIdentity`、`relay:issue_local` も同じものを使う)
7. 台帳からルータの設定を書く

運用の形は `ASTERISM_ENROLLMENT` (`.env`)。今は `admin` (管理者が登録し招待する) だけ。`approval`・`self` は「将来」とし、置くと console は起動しない (docs/o1.md)。

## 6. tar と `credentials:`

**tar (console)**: 発行の画面に「Save all (.tar)」を足した (今の Copy と Save to file 3 つ + 設定の例は残した)。tar はブラウザの中で作る (`app/javascript/lib/credentials_tar.js`、POSIX ustar、圧縮なし、依存なし)。中身は `<名前>/` の下にまとめた (展開しても別の相手の `ca.pem` や鍵と混ざらないため):

| ファイル | 権限 | 中身 |
|---|---|---|
| `<名前>/` | 0755 | |
| `<名前>.key` | 0600 | 秘密鍵 (PKCS#8) |
| `<名前>.pem` | 0644 | 証明書 |
| `ca.pem` | 0644 | CA |
| `zenoh.json5` | 0644 | router: 家のルータの設定まるごと (LAN に `tcp/[::]:7447`、クラウドのルータへ mTLS、相対パス、`metadata/name`)。展開した場所で `zenohd -c zenoh.json5` でそのまま動く。client: zenoh の client の接続の例 |
| `asterism.json` | 0644 | `format`・`name`・`kind`・`router` (`ASTERISM_RELAY_PUBLIC_ENDPOINT`)・`serial`・`not_after`・`fingerprint`・`console` (console の URL)・`issued_at`。秘密は無い |

`asterism.json` は console が作り (発行の答えの `info`)、ブラウザが tar に入れる。

**`credentials:` (asterism gem)**: `Asterism.connect`・`Asterism::Zenoh.open`・`Asterism::ROS.connect` が tar のパスを受ける。`Asterism::Credentials` が `Gem::Package::TarReader` でメモリの上で読み (一時ファイルなし)、鍵と証明書の組を確かめ、zenoh の設定の `transport/link/tls/root_ca_certificate_base64`・`connect_certificate_base64`・`connect_private_key_base64` と `enable_mtls` に入れる。宛先と `node:` は `asterism.json` から (渡せば上書き)、`config:` (Hash) はその上に重なる (String とは組めない)。tar がグループかほかの人に読めると、ssh のように警告する (`chmod 600 <file>`)。ブラウザが保存した tar は普通 0644 なので、install.md と画面に `chmod 600` を書いた。gem の版は上げていない (CHANGELOG の Unreleased)。

- 作った tar が 8192 バイト (5 つのファイルと directory の header とブロックの詰め)。数 KB の見込みどおり。
- Web Crypto の鍵 (Chromium) と console の発行で作った tar を、zenohd 1.10.1 も zenoh-c (CRuby) もそのまま読んだ (G0 と同じ)。base64 の 3 項目は zenoh-c の設定でそのまま効いた。
- install.md の「更新」の手順で、更新後に setup を走らせても何も発行し直さない (証明書がそろっている) ことを確かめた。
- Caddy の `rewrite` はクエリを落とさない、`uri` は `forward_auth` より先に走る (7.1)。

## 10. 残った課題・決めてほしいこと

1. **最初の版の番号**: 0.1.0 を提案 (VERSION・CHANGELOG・compose の既定に入れた)。
2. **ユーザがすること**:
   - asterism-console と asterism の main を push する。
   - asterism-console に `v0.1.0` のタグを打って push → workflow が ghcr に公開する。**最初に公開した package は非公開になるので、GitHub の Packages の設定で公開 (public) にする** (org の設定によっては repository と結び付ける)。arm64 は QEMU の作りなので時間がかかる。
   - asterism gem の `credentials:` を含む版を出す (版の番号を決めて上げ、rubygems へ)。それまでは install.md の CRuby の例と `check_node.rb --credentials` は手元の checkout でしか動かない (install.md には「asterism with credentials:, after 0.7.0」と書き、3 つのファイルの道も残した)。console の image は asterism 0.7.0 のままで困らない。
   - 作者の VPS の入れ直し (11 章)。
3. **arm64**: 手元の QEMU で作れ、起動して gem が読めた (この章の最後)。
4. **決めてほしいこと**:
   - tar の中身を `<名前>/` の下に置く形 (展開すると directory ができる)。gem はどちらの形も読む。
   - `zenoh.json5` の違い: router は家のルータの設定まるごと (LAN の 7447 を平文で listen)、client は接続の例。
   - ブラウザのノード ID の既定の接頭辞 `wasm-` を残した (WebAssembly のページの名前として一般的と見た)。
   - `ASTERISM_STUDIO_URL` は「読まない」にした (別名として残さない)。
   - ルータ名の既定を `zenohd-cloud` にした (VPS は `.env` で `zenohd-vps` を持てば変わらない)。
   - 運用の形の設定の場所は `.env` の `ASTERISM_ENROLLMENT` (値 `admin`。`approval`・`self` は将来)。
   - 開発の Gemfile は今までどおり隣の checkout の gem を既定にしている (image は rubygems)。OSS として「clone して bundle install」で動くよう既定を rubygems にするかは別に決めたい (Gemfile.lock が変わる)。
   - Apply の既定が `bin/relay_restart_request` になったので、作者の手元の開発 (family-mruby の `docker-compose.relay.yml` の zenohd-cloud を console が起動し直す形) では、console を起動するときに `ASTERISM_RELAY_RESTART="docker compose -f docker-compose.yml -f docker-compose.relay.yml restart zenohd-cloud" ASTERISM_RELAY_COMPOSE_DIR=..` を付ける必要がある。

6. 手元に残した image: 稽古で使った `alpine:3` (volume の大きさを見るのに使った。前から有ったかは判別できなかったので消していない)。

arm64 の結果: 手元の Docker Desktop の QEMU で `docker build --platform linux/arm64` が通った (11 分、image 340 MB)。その image を arm64 で起動し、`require "asterism"` (asterism-zenoh の C 拡張と aarch64 の zenoh-c) が読めることを確かめた (`aarch64-linux`、0.7.0)。GitHub の runner でも同じ QEMU の作りになる。
