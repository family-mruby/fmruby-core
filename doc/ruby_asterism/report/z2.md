# Z2 報告: P4 実機で Zenoh

> 状態: 完了 (検収待ち) | 更新: 2026-10-06 | picoruby-zenoh を ESP32-P4 のファームに入れ、P4-Nano (NARYAv4) と PC の zenohd が WiFi 越しに put / subscribe で往復した。受け入れ条件 1-9 を NARYAv4 で満たした (ユーザ決定により Z2 は NARYAv4 で完了とし、Tab5 の確認は後日の実機確認の一覧へ)。内蔵 RAM の増加は静的・起動時とも 0、接続中はソケット 1 本分 約 2.4 KB (lwIP)。その後ユーザが選んだ切断の案 1・2 (相手が閉じたら閉じる、送信に 3 秒の時間制限) を入れた (12 章)

## 1. 結果の要約

- picoruby-zenoh を `lib/add/family_mruby_esp32p4.rb` に足した。S3 と wasm の構成には入れていない。
- zenoh-pico の本体 (コア) と gem の C は、これまでどおり mruby のビルド (rake、RISC-V の素のコンパイラ) で
  コンパイルする。ESP-IDF のヘッダが要る 3 本 (system 層、TCP 層、ソケットの補助) だけを
  `components/picoruby-esp32/CMakeLists.txt` の P4 の分岐でコンパイルする。
- そのために、ESP-IDF のヘッダを含まない型だけの platform ヘッダ (`include/zenoh_espidf_platform.h`) を
  gem に置き、zenoh-pico の `ZP_SYSTEM_PLATFORM_HEADER` で差し込んだ。vendor/ は書き換えていない。
- `z_malloc` は PSRAM だけから取る (`MALLOC_CAP_SPIRAM`)。静的な内蔵 RAM (.dram0.data / .dram0.bss) は
  バイト単位で増えていない。起動の `M1|` 行は gem を入れる前とすべて同じ値だった。
- ESP-IDF の TCP 層 (tcp_esp32.c) は Z1 の POSIX 版より悪く、読み取りに時間制限が全く無い。gem 側の
  実装 (`ports/esp32/zp_tcp_esp32.c`) に差し替えた。
- zenoh-pico はタスクを立てない (`xTaskCreate` / pthread の参照なし)。
- 実機 (NARYAv4) のアプリが PC の zenohd (LAN に開いたもの) につながり、`fmrb/test/out` の連番を PC で
  読め、PC から put した値が画面に出た。開き直し 5 回でも同じ。接続は 39-137 ms。
- 経過: 最初の作業では 2 つの止まる条件で止まった。(1) zenohd を LAN に開く重ね合わせの compose
  ファイルの作成が、このセッションの権限の判定で拒否された。(2) Tab5 が PC に USB でつながって
  いなかった (つながっていたのは P4-Nano だけ)。その後ユーザが決めた: Z2 は P4-Nano (NARYAv4) で
  完了とする、Tab5 は後日の実機確認の一覧へ回す、zenohd を LAN に開くことを認める。ユーザが Windows の
  Hyper-V のファイアウォールに TCP 7447 の受信の規則を足し、親 (検収側) が
  `docker-compose.zenoh-lan.yml` を書いて zenohd を起動した。その上で条件 3-6 と切断の実測を行った。

## 2. ESP-IDF のポートで差し替えたもの

### 2.1 ビルドの分け方

zenoh-pico の ESP-IDF の platform ヘッダ (`zenoh-pico/system/platform/espidf.h`) は FreeRTOS と UART の
ドライバのヘッダを読む。zenoh-pico のほぼ全部のファイルがこのヘッダを経由するので、そのままだと
zenoh-pico 全体を ESP-IDF のコンポーネントでコンパイルすることになり、定義と include の道を CMake 側に
130 本分そろえる必要がある。

代わりに、zenoh-pico が用意している差し込み口 `ZP_SYSTEM_PLATFORM_HEADER` を使った。gem の
`zenoh_generic_config.h` が `ZENOH_ESPIDF` のときにこれを `zenoh_espidf_platform.h` に向ける。この
ヘッダは espidf.h と同じ型 (時刻は `struct timespec` / `struct timeval`、ソケットは lwIP の fd、
端点は `struct addrinfo *`) を ESP-IDF のヘッダなしで定義する。シングルスレッドとソケットの
リンク以外の構成では `#error` にした (型がずれるのを防ぐ)。

| 何を | どこで | 備考 |
|---|---|---|
| zenoh-pico のコア (128 本) と gem の zenoh.c | rake (mruby のビルド、`riscv32-esp-elf-gcc`) | `ZENOH_ESPIDF`。system/unix は外す |
| `ports/esp32/zp_system_esp32.c` | CMake (P4 の分岐) | 上流の `src/system/espidf/system.c` を include し、確保の 3 関数だけ差し替え |
| `ports/esp32/zp_tcp_esp32.c` | CMake | 上流の tcp_esp32.c の代わり |
| `vendor/zenoh-pico/src/system/socket/esp32.c` | CMake | 上流のまま |

platform の選択は mrbgem.rake の `ZENOH_PICO_PLATFORM` (環境変数) を広げた。指定が無いとき、ビルド名が
`esp32` で始まれば `ZENOH_ESPIDF`、それ以外は `ZENOH_LINUX`。ESP-IDF 側でコンパイルするファイルと
その定義・include の道は gem の README.md (Building) に書いた。gem は Family mruby の関数を呼んでいない
(`fmrb_` の参照なし)。

CMake の `set_source_files_properties` は `idf_component_register` より後に置く必要があった
(依存関係を調べる段階でスクリプトとして読まれ、`not scriptable` で止まる)。

### 2.2 TCP 層 (tcp_esp32.c) を読んで分かったこと

Z1 で POSIX の TCP 層を差し替えた理由が、ESP-IDF の版にもすべてあった。しかも時間制限の点では悪い。

1. **読み取りが止まる。** `_z_tcp_esp32_read` はフラグなしの `recv` で、受信の時間切れ (SO_RCVTIMEO) も
   設定していない。クライアントの接続はブロッキングのままなので、データの無い `poll` はルータが何か
   送るまで (keep-alive の周期まで) アプリを止める。差し替えでは `MSG_DONTWAIT` で即座に返す。
2. **connect に上限が無い。** 応答の無い相手には lwIP の SYN 再送が尽きるまで止まる。差し替えでは
   非ブロッキングの connect + select で 3 秒。
3. **ハンドシェイクの read_exact に上限が無い。** 差し替えでは Z1 と同じく、1 バイト目まではソケットの
   時間切れ (100 ms) ごとに返し、来始めたら最大 5 秒待つ。
4. 上流は lwIP に SO_LINGER があると接続ごとに lease の時間 (10 秒) の linger を付ける。閉じるときに
   止まりうるので付けていない (Z1 の POSIX 版と同じ)。

送信 (`send`) はブロッキングのまま (上流・Z1 と同じ)。EINTR は ESP-IDF では起きないが、POSIX 版と形を
そろえて再試行にした。listen / accept は client だけの構成なので失敗を返す。

### 2.3 確保先

上流の `z_malloc` は `heap_caps_malloc(size, MALLOC_CAP_8BIT)` で、ESP-IDF は内蔵 RAM から先に出す。
gem の `zp_system_esp32.c` は上流の system.c を `#include` し、その前に `z_malloc` / `z_realloc` /
`z_free` を別名に置き換えて上流の 3 関数を使われない名前にし、gem の版 (`MALLOC_CAP_SPIRAM |
MALLOC_CAP_8BIT`) を定義した。内蔵 RAM へのフォールバックはしない (取れなければ zenoh-pico が
メモリ不足として返す)。乱数・時計・sleep は上流のまま使うので、zenoh-pico の更新に追従する。
上流の system.c が espidf.h 経由で得ていた FreeRTOS のヘッダ (`vTaskDelay`) は wrapper で読む。

内蔵 RAM から取られうるものとして残るのは lwIP の側 (ソケット、PCB、送受信の pbuf、getaddrinfo の
結果)。これは ESP-IDF の lwIP の設定 (sdkconfig) で決まり、gem からは選べない。

### 2.4 タスクを立てないこと

`Z_FEATURE_MULTI_THREAD=0` で、上流の system.c のタスク・mutex・condvar の部分はコンパイルされない。
zenoh-pico と ports のオブジェクトの未定義シンボルを nm で見て、`xTaskCreate` / `pthread_*` が無い
ことを確かめた。名前に task を含むもの (`_zp_unicast_read_task_fn` など) は zenoh-pico の中の
協調型の仕事 (zp_spin_once から呼ばれる) で、OS のタスクではない。FreeRTOS の関数で参照があるのは
`vTaskDelay` (z_sleep_*) だけ。

### 4.3 アプリを動かしている間 (接続の前後)

同じ起動の中で、アプリの起動前、接続に失敗した状態 (zenohd を LAN に開く前)、接続した状態を比べた。
値は 10 秒ごとの周期ダンプの行。

| 状態 | IRAM free | PSRAM free |
|---|---|---|
| アプリの起動前 (それまでのアプリを閉じた後) | 197092 | 8209484 |
| zenoh_echo、接続に失敗した状態 (5 回) | 179328 / 179308 | 7788480 |
| zenoh_echo、接続した状態 (最初の 1 回、3 回続けて同じ値) | 176916 | 7782240 |
| 比べ: timer_test (zenoh を使わないアプリ) | 179720 | - |

- アプリ 1 つ分 (タスクのスタック 16 KB ほか、`need=24576`) が減るのは zenoh を使わないアプリと同じ。
- **接続していることによる内蔵 RAM の減りは約 2.4 KB** (179328 -> 176916)。zenoh-pico の確保は
  PSRAM だけなので (2.3)、これは lwIP の側 (ソケット、TCP の PCB、受信の pbuf など) の分である。
  PSRAM は接続で 6,240 B 減る (zenoh-pico のセッション、送受信のバッファ、購読)。
- アプリのタスクのスタックの残りは、接続に失敗した状態で 9272 B、接続した状態で 8296 B
  (16 KB のスタックで、接続中の呼び出しが約 1 KB 深い)。
- アプリの VM プールは接続中 264-276 KB (アプリ自身のログで `pool_used=266-275 KB`、
  `sys_used=3824` で一定)。

閉じた後の戻り方:

- 閉じた直後は前の値に戻らず、約 2 分かけて段階的に戻る (192664 -> 192884 -> 193096 -> 193312 ->
  193524 -> 193756、1 段 約 216 B)。こちらから接続を閉じた側の TCP は TIME_WAIT (lwIP の 2MSL、
  120 秒) の間 PCB を持つため。続けて開き直すと、前の回の TIME_WAIT の PCB の分だけ接続中の値も
  下がって見える (176916 -> 176684 -> 176492 -> 176268 -> 174392)。
- 2 分たった後の値は 193756 で、最初の接続の前 (197092) より **3,336 B 少ない**。そのあと 2 回
  開き直しても、2 分後には同じ 193756 に戻った。回ごとに減るもの (漏れ) ではなく、最初の TCP の接続で
  一度だけ取られるもの (lwIP / WiFi の経路のどこか) と見ている。中身は特定していない。接続に失敗した
  開き直しでは、この減りは起きていない (197092 のまま)。

| 2 | 73 ms | 176492 | 7782240 | 275688 / 275744 |
| 3 | 72 ms | 176268 / 174600 | 7782240 | 274464 / 271504 |
| 4 | 137 ms | 174392 | 7782240 | 274272 / 271392 |

### 5.1 接続の失敗で止まる時間 (条件 7)

zenohd を LAN に開く前に測った。接続先は `/home/zenoh_echo.txt` の `tcp/192.168.10.2:7447`。SYN に答えが
無く (RST も来ない。後で分かったが Windows の Hyper-V のファイアウォールが捨てていた)、gem の connect の
上限 3 秒で失敗した。

- アプリのログ: `zenoh_echo: failed: cannot open a session to tcp/192.168.10.2:7447 (-102)
  (tcp/192.168.10.2:7447, 3005 ms)`。8 回の試行で 3,005-3,033 ms。
- この間、ほかは止まらない。接続の待ちの最中にマウスの移動とクリックを遠隔で入れたところ、
  `host: Cursor made visible on first mouse event` が接続の待ちの途中 (起動の 0.6 秒後) に出て、
  直後の 5 秒の統計は `cursor: n=5 wait avg=1ms max=2ms`、描画は `32 frames/5s avg=28ms`。
  アプリのタスクは lwIP の select で眠っているので CPU を取らない。止まるのはそのアプリの窓
  (画面は `connecting` のまま 3 秒) だけ。
- 名前の解決が要る接続先 (既定の `tcp/zenohd:7447` など) は、lwIP の DNS の時間切れまで同じように
  そのアプリだけが止まる見込み。/home のファイルの消去 (書き込み) を増やさないために測っていない。

## 6. 切断の実測 (4 章)

この章は案 1・2 を入れる前 (コミット 592e9d13 の時点) の実測。入れた後の動きは 12 章。

この時点では動きは変えていない (Z1 のまま: 自動の再接続なし、lease 10 秒、client の読み取りは相手が閉じても
「読むものが無い」と扱う)。試しのアプリに、状態が変わったときと、put が 200 ms 以上かかったときの
ログを足して測った (`zenoh_echo: error: ... (last put N)`、`put N took M ms`)。

時間は PC で操作をした時刻から、アプリが失敗に気づいた行が serial のログに出るまで。

| 起こしたこと | 方法 | 気づくまで | 気づき方 |
|---|---|---|---|
| zenohd が止まる | `docker compose ... stop zenohd` | 3.0 / 1.9 / 2.7 秒 | 次の put が `put failed (-100)` |
| zenohd が黙る (プロセスは止まるが TCP は生きている) | `docker pause fmruby_zenohd` | 12.7 / 12.4 / 12.6 秒 | put が `put failed (-100)` (lease 10 秒の満了) |
| WiFi が切れる | (測れていない、下) | - | - |

- どの試行でも `poll` は true のままで、気づくのは put の失敗だった。put が 200 ms 以上かかった回は
  無い (送信で止まらなかった)。画面は `error: put failed (-100)` になる。
- PC 側の zenohd は Docker Desktop の中にあり、機体の TCP は PC の上の Docker Desktop の転送口で
  終わっている。zenohd を止めると転送口が接続を切るので、機体はすぐ (次の put で) 気づく。zenohd を
  pause すると転送口は TCP を受け続けるので、機体は zenoh の lease (10 秒) の満了で気づく。後者は
  「ルータが黙った (応答の無い)」状態の近似で、Z1 の sim の約 20 秒より早い。
- **WiFi が切れたときは測れていない。** 機体の WiFi を遠隔で切る口が無く (遠隔の操作そのものが WiFi に
  乗っている)、PC 側でパケットを捨てる方法も、TCP が Docker Desktop の転送口で終わるので「ACK が
  返らない」状態を作れない (コンテナの側で捨てても転送口が ACK を返す)。アクセスポイントを切る・
  電波の届かない所へ動かすなど、手の作業が要る。コードから見た見込み: 受信が途絶えるので lease の
  満了 (10-13 秒) で put が失敗する。ただし ACK が返らないので送ったデータは lwIP の送信バッファに
  溜まる。このアプリの量 (1 秒に 1 回、数十バイト) なら lease の満了までに溜まるのは 1 KB 未満で、
  送信のバッファ (数 KB) は埋まらない見込み。大きな値を速く送るアプリでは、バッファが埋まった時点で
  `send` が止まり、lwIP の再送が尽きるまで (分の単位) アプリが止まりうる。

### 変える案 (ユーザは 1 と 2 を選んだ。12 章で実装)

1. **相手が閉じたら閉じる**: 読み取りで `recv` が 0 (相手が接続を閉じた) を返したら、gem の側で
   セッションを閉じたことにする。zenohd が止まった場合に、put を待たずに次の `poll` が false になる
   (Z1 からの残件と同じ案)。費用は小さい。
2. **送信に時間制限**: ソケットに `SO_SNDTIMEO` (例: 1 秒) を付ける。WiFi が切れて送信のバッファが
   埋まったときに、put が止まらずに失敗する。
3. **lease を短く**: `Z_TRANSPORT_LEASE` を 10 秒から短くする (例: 4 秒)。黙ったルータ・WiFi の
   切断に早く気づくが、keep-alive の送信が増え、無線の一時的な途切れでも切れやすくなる。
4. **TCP の keepalive を短く**: `TCP_KEEPIDLE` などで lwIP の keepalive を秒の単位にする。zenoh の
   lease が先に働くので、3 と比べて得は少ない。

1 と 2 は既定の動きを大きく変えずに入れられる。自動の再接続は入れない (Z1 の後の決定) ので、
どの案でも「切れたことに気づいたらアプリが開き直す」は同じ。

## 12. 切断の気づき方の変更 (案 1・2、ユーザ決定)

ユーザが 6 章の案 1 (相手が閉じたら閉じる) と案 2 (送信に時間制限) を選んだ。lease (案 3)、keepalive
(案 4)、自動の再接続なし、その他の API は変えていない。

### 12.1 作り

- zenoh-pico の client の読み取りは「相手が閉じた」を「読むものが無い」と区別しないので、zenoh-pico の
  中ではなく gem の TCP 層とセッションの側で扱った。vendor/ は書き換えていない。
- TCP 層 (POSIX 版と ESP-IDF 版の両方) の約束を `include/picoruby_zenoh_link.h` にまとめた:
  - `zp_tcp_socket_closed(sock)`: `recv(MSG_PEEK | MSG_DONTWAIT)` で 1 バイト覗き、0 (相手が閉じた・
    こちらで shutdown した) か、EAGAIN 以外の失敗なら true。止まらない。状態はソケット自身が持つので、
    gem の側に記憶 (静的な領域) を足していない。
  - 送信 (`_z_tcp_write`) は `MSG_DONTWAIT` で送り、送り切れない分は送信の余地を待つ。待ちは 1 回の
    送信 (メッセージ 1 つ) の合計で `PICORUBY_ZENOH_SEND_TIMEOUT_MS` (3000) まで。超えたら
    `shutdown(SHUT_RDWR)` して失敗を返す (途中まで送ったメッセージで流れが壊れるので、続けない)。
    `SO_SNDTIMEO` は使っていない (lwIP の設定に左右されず、POSIX と同じ書き方にできるため)。
  - 時間の定数 (接続 3000、送信 3000、ハンドシェイクの読み取り 5000) はこのヘッダ 1 か所に置いた。
    Ruby からは `Zenoh::CONNECT_TIMEOUT_MS` と `Zenoh::SEND_TIMEOUT_MS` で読める。
- gem (zenoh.c) は `poll` の後、`put` の前と後、`closed?` で、セッションのリンクのソケットを
  `zp_tcp_socket_closed` に聞き、true ならセッションを閉じる (`z_close`)。リンクのソケットは
  zenoh-pico のセッションの中 (`_tp._transport._unicast._common._link`) から取っている。固定した版
  (1.10.1) の構造に依存するので、zenoh-pico を上げるときに確かめる箇所になる。
- 結果として、接続が失われたら: `poll` が false、`closed?` が true、`put` が `Zenoh::Error`
  (`session is closed`。その put の最中に分かったときは `put failed: the connection to the router
  is lost`)。自動の再接続はしない。アプリが `Zenoh::Session.open` で開き直す。gem の README に
  「When the router is lost」として書いた。
- 試しのアプリ: zenoh_echo は失ったときに `closed?` と、もう一度 put したときの例外をログに出す。
  送信の時間制限を試すために `flash/app/test/zenoh_burst.app.rb` (4 KB の値を 1 回の更新ごとに
  200 ms の間送り続ける) を足した。

### 12.4 気づいた点 (変えていない)

- **lease の満了では `closed?` が false のまま。** zenohd が黙った (pause) とき、zenoh-pico は lease の
  満了でトランスポートを閉じるが、セッションの「閉じた」の印 (`z_session_is_closed`) は立てず、
  ソケットも生きている。そのため `put` は `Zenoh::Error` (`put failed (-100)`) になるが、`poll` は
  true、`closed?` は false のまま。今回の範囲 (相手が閉じた・ソケットの失敗・送信の時間切れ) の外なので
  変えていない。揃えるなら、gem でトランスポートの状態 (`_common._state == CLOSED`) も「閉じた」と
  みなす (費用は小さい)。選ぶのはユーザ。
- WiFi の切断 (ACK が返らない) は、これまでどおり手の作業が要り、測っていない。今は lease (10-13 秒)
  か送信の時間制限 (送信のバッファが埋まってから 3 秒) の早い方で put が失敗する見込み。

## 13. 追記 (親): リース切れも閉じた扱いにそろえた

ユーザ決定 (2026-10-06) で、ルータが応答しないまま TCP が生きている場合 (リース切れ) も、`poll` が false、
`closed?` が true になるようにした。zenoh-pico はリース切れでトランスポートを片付け (種類が NONE、リンクは
解放) るが、セッションに閉じた印を付けない。gem はこの NONE を見てセッションを閉じる。リンクを読む前に
種類を見るので、解放済みのリンクには触らない。

- sim (標準構成): `docker pause` で zenohd を止めると、リース切れのあとに `poll` が false
  (`closed?=true put raises Zenoh::Error: session is closed`)。開き直すと接続し、PC からの値が画面に出る。
  `E (` / Guru / abort は 0。
- WiFi が切れる場合の実機での測定は行わない (ユーザ決定 2026-10-06)。アプリから見ると相手からの応答が
  途絶えるだけで、zenohd が固まった場合 (リース切れ) と同じ経路で閉じる。
