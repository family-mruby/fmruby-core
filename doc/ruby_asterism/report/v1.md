## 2. 構成

### 2.1 bridge と Rails の分け方

```
 ブラウザ <-- Action Cable (solid_cable) -- bin/bridge <-- Zenoh --> zenohd
    |                                         |   ^
    +-- HTTP: 画面・頼みごと・眺めるキー --> Puma  |  (SQLite: グラフ、頼みごと、
                                         +----+---+   眺めるキー、cable の通信)
```

- 網とつながるのは `bin/bridge` (lib/bridge/runner.rb) の 1 つだけ。Rails の環境を読むが、Puma とは別のプロセス。
  Puma が何本動いても網には 1 つのノードしか出ない。2 つ目の bridge は同じ `console/console` で接続しようとして
  Asterism に断られる (A1 の「同じアプリの 2 つ目」の確かめ)。
- bridge は Zenoh のセッションを 2 本持つ。
  1. 読むためのセッション (`Asterism::Zenoh.open`、Ruby らしい層): 管理用の空間の get、生存のしるしの監視
     (`liveliness_watch`)、眺めるキーの購読。受け取りのスレッドで動く。
  2. オブジェクトの網 (`Asterism.connect(node: "console", app: "console")`): meta と呼び出し。
     `Asterism.net.start` で受け取りのスレッドを回し、頼みごとは別のスレッド (最大 4 本) で `Asterism.meta` /
     `Asterism.call` を呼ぶ (C5 の錠と待ちの作りがそのまま効く)。
- ルータが落ちると bridge は 3 秒ごとにつなぎ直す (zenohd を `docker restart` して 3 秒後に戻ったのを見た)。
- 環境変数: `ASTERISM_ROUTER` (既定 `tcp/127.0.0.1:7447`)、`ASTERISM_CONSOLE_NODE` (既定 `console`)。
  Rails は既定どおり 127.0.0.1 で待ち受ける。

### 2.2 配り方

- Action Cable の配り手を開発の環境でも solid_cable にした (config/cable.yml。Rails の既定の `async` は同じ
  プロセスの中にしか届かない)。cable 用の SQLite (`storage/development_cable.sqlite3`) を開発の環境の
  database.yml に足した。bridge が `ActionCable.server.broadcast` すると表に 1 行入り、Puma が 0.1 秒ごとに
  拾ってブラウザへ送る。
- 流れは 1 本 (`ConsoleChannel`、`console`)。種類は次のとおり。
  - `graph_diff`: グラフの差分 (足した点・線、消えた点・線、中身の変わった点)。版の番号つき。画面は番号が飛んだら
    `GET /graph` で全体を取り直す。
  - `bridge`: 3 秒ごとの生存の知らせ (つないでいるルータ、ノードの名前)。10 秒来なければ画面は「止まっている」と出す。
  - `request`: 頼みごとの答え。`sample`: 眺めるキーの値。`watch` / `unwatch`: 眺めるキーの増減。
- グラフの全体は `GraphState` (1 行) に置く。画面の最初の表示はそこから作り、後は差分で直す。
- bridge の受け取りのスレッドは DB に触らない。眺めるキーの値はいったん Queue に入れ、主のスレッドが 0.1 秒ごとに
  配る (cable の配り手が DB を使うため)。

### 2.3 グラフのまとめ方 (lib/bridge/graph.rb)

純 Ruby で、網に触らない (試験は手で入力を作る)。入力は管理用の空間 (ルータごとの `router`・`linkstate`・
`token` の表)、`asterism/**` と `@ros2_lv/**` の生きているキー。出力は種類つきの点と線 (id で並べるので、同じ
網からは同じグラフが出て、差分が安定する)。

| 点 | id | 出どころ |
|---|---|---|
| ルータ | `router:<zid>` | `@/<zid>/router`。相手が router のセッションと linkstate の辺もルータとして足す |
| セッション | `session:<zid>` | `@/<zid>/router` の `sessions` (client / peer)。住所はリンクの `dst` |
| Asterism のノード・アプリ・オブジェクト | `a_node:<ID>`、`a_app:<ID>/<アプリ>`、`a_object:<ID>/<アプリ>/<名前>` | 生存のしるし `asterism/<ID>` と `asterism/<ID>/<アプリ>/<名前>` |
| ROS 2 のノード・トピック・サービス | `r_node:<zid>/<nid>`、`r_topic:<ドメイン><名前>`、`r_service:<ドメイン><名前>` | `@ros2_lv/...` の NN / MP / MS / SS / SC (形は r1.md・r2.md) |

| 線 | 意味 |
|---|---|
| `session` / `router_link` | ルータとセッション、ルータどうし |
| `carries` (層をまたぐ) | セッション → その上の Asterism のノード / ROS 2 のノード |
| `has_app` / `exposes` | Asterism のノード → アプリ → オブジェクト |
| `publishes` / `subscribes` | ROS 2 のノード → トピック (送り手)、トピック → ノード (受け手) |
| `calls` / `serves` | クライアント → サービス、サービス → サーバ |

- **どのセッションが何を運んでいるか**: Asterism はルータのトークンの表 (`@/<zid>/router/token/asterism/<ID>` の
  `clients` / `peers`) から、ROS 2 はトークンのキーの中の zid から引く。
- zid の書き方: zenohd は先頭の 0 を落として出す (例: 31 桁の `720abcd7...e0080`)。比べるときは両方の先頭の 0 を
  落とす。
- bridge 自身 (ノード `console` と 2 本のセッション) は消さずに点線の枠で印を付ける。

### 2.4 画面からの操作

- 頼みごとは DB を通す: 画面が `POST /bridge_requests` で `BridgeRequest` (kind は meta か call、パス、メソッドの
  名前、引数の JSON、時間制限 0-30 秒、既定 2 秒) を作る → bridge が 0.1 秒ごとに見て拾い、状態を running にして
  実行 → 答え (`ok` と戻り値、`remote_error` と相手の例外のクラス・文言、`timeout`、`error`、かかった ms) を書き戻し、
  `request` で知らせる。cable の知らせが来ない場合に備えて、画面は時間制限の 1 秒後から `GET` で問い直す。
  30 秒拾われなかった頼みごとは `expired` にする。
- Rails の側で断るもの: パスが `<ノード>/<アプリ>/<名前>` でない (ワイルドカード・`@` で始まる・区切りの数が違う)、
  メソッドの名前が Ruby の名前の形でない、引数が JSON の配列でない、時間制限が 30 秒を超える。
- **公開していないメソッドは、オブジェクトを持つ側が断る** (A1 の `NoMethodError ... (not exposed)`)。画面は meta
  の一覧だけをボタンにするが、「Another method」の欄から一覧に無い名前も送れるようにして、相手が断ることを
  見られるようにした。
- 眺めるキー: `Watch` の行を bridge が 0.5 秒ごとに突き合わせ、増えたキーを購読し、消えたキーを取り下げる。
  1 つのキーにつき 1 秒 10 件まで配る (超えた分は数だけ出す)。値の見せ方は、表示できる UTF-8 なら文字、
  MessagePack として読めれば JSON、先頭が CDR のヘッダなら文字列のメッセージとして読む (読めなければ 16 進)、
  それ以外は 16 進。

## 3. 管理用の空間から取れたもの (zenohd 1.10.1)

zenohd の設定は今のまま (docker-compose.yml の zenohd + LAN 用の重ね合わせ) で `@/**` に答えた。設定は足していない。
キーの一覧 (プラグインの状態を除く):

```
@/<router zid>/router                       # ルータの要約 (JSON)
@/<router zid>/router/linkstate/north       # ルータどうしの経路 (Graphviz の dot)
@/<router zid>/router/linkstate/south:0:peer
@/<router zid>/router/token/<トークンのキー>  # 生存のしるしごとに、誰が出しているか
@/<router zid>/router/subscriber/<キー>      # 購読ごとに同じ形
@/<router zid>/router/queryable/<キー>
@/<router zid>/router/metrics               # OpenMetrics (gzip)
@/<router zid>/router/plugins/...、status/plugins/...
```

`@/<zid>/router` の例 (zid は短くし、住所は置き換えた):

```json
{"locators":["tcp/198.51.100.2:7447"],"metadata":null,
 "plugins":{"rest":{...},"storage_manager":{...}},
 "sessions":[
   {"links":[{"dst":"tcp/[::ffff:192.0.2.10]:52368","src":"tcp/[::ffff:198.51.100.2]:7447"}],
    "peer":"55955650...508e","region":"south:0:client","shm":false,"weight":null,"whatami":"client"},
   {"links":[{"dst":"tcp/[::ffff:198.51.100.6]:50914","src":"..."}],
    "peer":"a085c6bf...d7b3","region":"south:0:peer","whatami":"peer"}],
 "version":"v1.10.1-1211779c... built with rustc 1.97.1","zid":"c1df5ae4...0c51"}
```

トークンの表の例 (`@/<zid>/router/token/asterism/probe-node`):

```json
{"routers":["c1df5ae4...0c51"],"peers":[],"clients":["55955650...508e"]}
```

linkstate の例 (ルータ 1 台のとき):

```
graph {
    0 [ label = "c1df5ae4...0c51" ]
}
```

- 取れたもの: ルータの zid・版・待ち受けの住所・プラグイン、つながっているセッション (相手の zid、client / peer /
  router の種類、リンクの両端の住所)、ルータどうしの経路 (ルータ 1 台なので辺は無い)、トークン・購読・問い合わせの
  先ごとに出しているセッション。
- 読み方: `@/*/router`、`@/*/router/linkstate/**`、`@/*/router/token/**` の 3 つを 2 秒ごとに get。1 回あたり
  数 ms で返る。
- `whatami` は Asterism の CRuby・機体 (zenoh-pico)・sim がすべて `client`、ROS 2 (rmw_zenoh) は `peer`
  (rmw_zenoh の既定のまま zenohd につないでいる)。

## 6. 見立てと違った点・踏んだ罠

- **管理用の空間は設定なしで読めた**。zenohd 1.10.1 の既定で `@/**` に答える (REST からも、セッションからも)。
  止まる条件 (設定の意味を変える) には当たらなかった。外のルータでは W1 で ACL で隠す。
- **Docker Desktop の中を通るので、LAN の機体もセッションの住所が `198.51.100.1` (コンテナの網の出口。報告では 198.51.100.x に置き換えた) に見える**。
  PC の上の CRuby (`127.0.0.1` から入る) と同じ住所になり、住所では機体と PC を見分けられない。zid とトークンの
  表で見分けている。W1 で家役・クラウド役のルータを分けるときも、住所を頼りにしないこと。
- **sim_up は zenohd を LAN 用の重ね合わせなしで作り直す** (A1 と同じ)。sim_up の後に
  `docker compose -f docker-compose.yml -f docker-compose.zenoh-lan.yml -f docker-compose.ros2.yml up -d zenohd ros2`
  をやり直した。作り直すとルータの zid が変わる。bridge はつなぎ直して古いルータの点を消し、新しいルータの点を出した。
- **ルータを再起動すると、Asterism の機体・sim・CRuby はつなぎ直さない** (Z2 の決定のまま)。ROS 2 の peer も
  3 秒後の時点では戻っていなかった (その後は見ていない)。bridge だけが戻る。画面は「ルータと bridge のセッションだけ」になる。
- **P4-Nano のアプリの 2 回目の起動が約 110 秒かかった** (kill の直後の launch)。3 回目は 1.2 秒。シリアルは
  見ていない (親の capture のため)。前の回の後始末が終わるのを待っていた可能性があるが、確かめていない。
- **bridge 自身も Asterism のノードとして網に出る**。`Asterism.connect` は node と app を必ず取るため。機体の
  asterism_demo の画面にも `joined: console` と出る。グラフでは点線の枠で印を付けた。
- **Rails 8.1 の minitest は 6.0 で、`minitest/mock` が無い**。bridge の試験は、オブジェクトの網の代わりを
  `Bridge::Runner.new(objects:)` で差し込む形にした。
- **Action Cable の受け入れる Origin**: 開発の環境の既定は `localhost` だけなので、`127.0.0.1` で開いたページの
  WebSocket がはじかれる。両方を許した。
- ROS 2 の talker は parameter のサービスを 7 つ出すので、ROS 2 の層の点の半分がそれになる。隠す選択は付けていない。

## 8. 次の段階 (W1・W2) への申し送り

- **W1 (ルータの中継)**: 今のグラフは「ルータごとに `@/<zid>/router` を読む」形なので、ルータが 2 台以上になれば
  点は増え、相手が router のセッションと linkstate の辺から `router_link` の線が引ける (試験では作ったが、本物の
  2 台では見ていない)。ただし bridge がつながるルータの外の管理用の空間が見えるかは、中継のつなぎ方 (router どうしの
  ゴシップ・ACL) 次第。W1 で `@/*/router` に遠いルータが答えるかを確かめる。答えないなら、ルータごとに bridge を
  つなぐか、遠いルータのセッションを要約して流す形が要る。
- **管理用の空間の守り**: 今は誰でも `@/**` を読める (LAN の中だけの前提)。W1 で ACL で一般のクライアントから隠すと、
  bridge も読めなくなる。bridge にだけ読む権利を与える (証明書の名前で ACL を分ける) 形にする。
- **W2 (管理)**: 台帳・証明書・ACL を同じ画面に重ねるなら、点の id はそのまま使える (`router:<zid>`、
  `session:<zid>`、`a_node:<ID>`)。「登録済みでつながっている / 来ていない / 未登録」の色分けは、台帳の行と
  グラフの点を zid または ID で突き合わせて、点の data に印を足すだけで出せる (`Bridge::Graph#node` は data を
  足し合わせる)。台帳は Rails の DB に置き、bridge が読む。
- **認証**: 画面にも bridge への頼みごとにも認証が無い。W2 で管理画面を足す前に、少なくともログイン
  (できれば多要素) と、呼んでよいメソッドの絞り込み (今は網で公開されたもの全部) を入れる。
- **頼みごとの経路**: DB を 0.1 秒ごとに見る形は単純だが、往復に最大 0.2 秒ほど足される。頼みごとが増えるなら、
  bridge が solid_cable の流れを購読する形 (逆向きの Action Cable) に替えられる。
- **住所**: Docker Desktop の中を通すと住所が出口の 1 つにまとまる (6 章)。W1 の家役・クラウド役の zenohd を
  docker で立てるときは、ホストの網 (`network_mode: host` が使える環境) か、zid で見分ける前提で作る。
