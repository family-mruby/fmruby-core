# V2.4 報告: 開いた機械を囲む枠と、出入口の IP の扱い

> 状態: 完了 (検収待ち) | 更新: 2026-10-11 | instruction_v2_4.md の実装と確認の記録。asterism-console の網の図で、開いた ROS 2 の機械のメンバーを、名前つきの四角 (枠) で囲む。枠は配置の計算に入らない飾りのノードで、メンバーが動くたびに描き直す。開いた直後と「Lay out again」ではメンバーを先にまとめて配置し、ほかのノードを枠の外に置く。あわせて、docker の公開ポートの出入口の IP から来た ROS 2 のノードを畳まないようにした。出入口の IP は、bridge 自身の接続の手元の端と、ルータから見えた bridge の IP が食い違うことから見分ける。MuJoCo の台車・P4-Nano の ROS 2 のアプリ・CRuby の ROS 2 の例 (LAN 側の 7447 から)・sim の asterism_demo と、V2.4 より前の記録で確かめた。止まる条件には当たらなかった。asterism-console は main に push 済 (9c70329)

## 1. 枠の描き方

- **入れ子の箱にしない**。枠は独立したノード (class `frame`、kind `frame`、ID `frame:<塊の ID>`) で、位置と大きさをページが計算して与える。配置 (fcose)・数の表示・画面合わせが使う `visible()` から外したので、配置の計算には一切入らない。描く順は `z-compound-depth: bottom` で一番下 (線よりも下)。選択もつかみもできない。
- 大きさ: 見えているメンバーそれぞれの形・ラベル・数の印 (バッジ) を合わせた範囲に 14 px の余白。バッジの `bounds-expansion` (40 px、描画の都合の値) は数えない。そのまま `boundingBox()` を使うと枠がこの分ふくらむので、自前で計算した (`frameBounds`)。
- 見出し: 枠の左上の外側に「mujoco (10 ROS 2 nodes)」(名前が無ければ IP)。紫 (ROS 2 の色) の細い線、背景はごく薄い紫。
- **描き直す時**: メンバー (data `group` を持つノード) の `position` の出来事ごと (ドラッグ・配置・新しいノードの置き場所)。ドラッグ中は何度も来るので、ブラウザの描画 1 回に 1 度にまとめる (`queueFrames`、requestAnimationFrame)。ほかに `applyView` の終わりごと (開閉、層の切り替え、差分の反映でメンバーが増減したとき)。畳んだ・消えた・メンバーが 1 つも見えない機械の枠は消す。
- **クリック**: 枠と見出し (`text-events: yes`) のクリックで機械を選び、V2.3 の詳細 (「Fold」つき) を出す。選んだ機械の枠は選択の琥珀色の線になる。メンバーは枠より上に描くので、メンバーのクリックは今までどおりメンバーに届く。
- メンバーは自由に動かせ、枠が付いてくる。ほかのノードを枠の中へドラッグすることは止めない。

## 2. まとめて置く条件

- **「Lay out again」と最初の図** (`layoutAll`):
  1. 開いた機械ごとに、メンバーとメンバーどうしの線だけで先に配置する (輪に並べてから fcose、理想の辺の長さを少し短く)。これで機械の形と大きさが決まる。
  2. その機械を一時的に畳み、塊のノードの大きさを 1. の大きさにして (style の上書き)、全体を配置する。fcose はノードの大きさを避けるので、ほかのノードはその場所に入らない。
  3. 塊のあった場所に、1. の形のままメンバーを置き、畳んだ状態を元に戻す。
- **初めて開いたとき** (`openGroup`): メンバーを上の 1. と同じく配置し、畳んだ塊のあった場所に置く。ほかのノードは置いた場所を保つが、枠 (と 24 px の余白) にかかるものだけ、枠の中心から近い方の辺の外へ動かし、ほかと重ならなくなるまでその向きに進める (`clearFrame`)。Asterism のノードはアプリ・オブジェクトごと動く。
- **後から来たノード** (差分、巻き戻しの次の変化): 今までどおり隣のノードのそばに置き、それが開いた機械の枠の中で、その機械のメンバーでなければ、同じ手で枠の外へ出す。
- 入り込みを完全には防がない (ドラッグで入れる、新しいノードが枠のすぐ外に置かれて重なる、など)。

## 3. 出入口の IP の見分け方

- **グラフから見分ける (detected)**。bridge は自分のルータへの接続の手元の端を知っている (`Session#links` の `src`、例 `tcp/127.0.0.1:38722`)。これをルータのノードの data `bridge_link.local` に入れた。ルータの管理用の空間は bridge の Session がどこから来たか (`address`、例 `tcp/[::ffff:172.20.0.1]:42320`) を出す。2 つの IP が違えば、間で送り元の IP が書き換えられている。そのときルータから見えた IP を、**そのルータでの**出入口とする (`Bridge::Gateways.detect`)。この console は LAN の機器と同じ公開ポートを通ってルータに入るので、設定なしで今の構成の出入口 (`172.20.0.1`) が分かる。`bridge_link.local` はルータの data なので記録にも残り、巻き戻しも同じ手で見分ける。
- **設定で与える (given)**: `ASTERISM_GATEWAY_IPS` (カンマか空白で区切る)。どのルータでも効く。bridge が機器と同じ出入口を通らない構成 (bridge を docker の網の中のコンテナで動かす、別のホストで動かす、bridge の通らない NAT の向こうのルータ) のため。
- **V2.4 より前の記録**には `bridge_link.local` が無い。その巻き戻しは、設定のものと、今の生きた図で見分けた出入口を使う (V2.3 の名前を今の DB から取るのと同じ考え)。
- **決められない環境**: 書き換えが無く設定も無いときは、出入口は無いものとし、V2.3 と同じく IP で畳む。書き換えの無い構成 (zenohd を host の網で動かす、Linux の docker で LAN からの送り元が保たれる) では、機器は自分の IP で来るので、そもそも見分ける必要が無い。
- ほかの案を採らなかった理由: zenohd の管理用の空間は自分の locator (`tcp/[::]:7447`) と相手の見えた IP しか出さず、どれが出入口かは分からない。docker に網の出入口を問う方法は、console を docker の CLI とそのソケットに縛り、docker 以外の経路でルータに入る bridge では間違う。
- 畳み方: ROS 2 のノードの最初の Session の (IP, ルータ) が見分けた出入口、または IP が設定の出入口なら、塊に入れず 1 つずつ出す。ノードの data に `gateway: { "ip", "how" => "detected" | "given" }` を付け、詳細の「Machine」の行に「not known: 172.20.0.1 is a gateway」と、どう分かったか・なぜ畳まないかを出す。

## 5. 残った課題

- 枠の大きさはメンバーの配置で決まる。台車のように線の多い機械では、まとめて置いても枠は図の半分ほどを占める (600 x 500 px 前後)。理想の辺の長さを短くしたが、これ以上縮めるとトピックの線のラベルが重なる。
- 枠の外へ出したノードが画面の外に出ることがある (後から来たノードを枠から出したとき。画面合わせは動かさない決まりなので見えなくなる)。
- 出入口の見分けは bridge 自身の接続 1 本に頼る。bridge が機器と違う経路でルータに入る構成では `ASTERISM_GATEWAY_IPS` が要る。出入口の向こうの機械を見分けるには、ルータを host の網で動かすか、機体が自分の IP を名乗る仕組み (gem の範囲) が要る (V2.3 の課題のまま)。
- 確かめのために CRuby の `ros2_talker.rb` を LAN 側から動かした (`/cmd_vel` も出すので台車に届く)。終わりに止めた。写しを撮るため rails を一時的に `0.0.0.0` で上げ直し、終わりに 127.0.0.1:3000 に戻した。bridge は `bridge_link.local` を出すために新しいコードで起動し直した。
