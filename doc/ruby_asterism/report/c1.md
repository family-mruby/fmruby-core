## 3. API

`Asterism::Zenoh` (mruby 版と同じ。詳しくは asterism-zenoh/README.md):

| 呼び出し | 内容 |
|---|---|
| `Session.open(locator = nil, mode: :client, listen: nil)` | client、または `mode: :peer` で接続 / 待ち受け。`CONNECT_TIMEOUT_MS` で答えが無ければ `Error` |
| `session.put(key, payload, attachment: nil)` | |
| `session.subscribe(key, depth = 16)` | `each_pending { \|key, payload, attachment\| }` (ブロック無しなら配列)、`pending` / `received` / `dropped`、`close` / `closed?` |
| `session.get(key, timeout_ms = 2000, params = nil, payload = nil, attachment:, target:, consolidation:)` | `each_reply { \|key, payload, attachment\| }`、`done?`、`pending` / `received` / `dropped` / `errors` |
| `session.queryable(key, depth = 16, complete: false)` | `each_pending { \|q\| }` (ブロックの後に終える) または `Query` の配列 |
| `q.key` / `params` / `payload` / `attachment`、`q.reply([key,] payload, attachment:)`、`q.finish` / `finished?` | |
| `session.liveliness(key)`、`liveliness_watch(key, depth = 16)`、`liveliness_get(key, timeout_ms = 2000)` | |
| `session.poll(steps = 8)` / `closed?` / `close` / `zid` / `peers` | |
| `Asterism::Zenoh::Error`、`CONNECT_TIMEOUT_MS` / `SEND_TIMEOUT_MS` (3000)、`PEER`、`MAX_PEERS`、`C_VERSION` | |

mruby 版との違い (README に書いた):

- `PICO_VERSION` の代わりに `C_VERSION` ("1.10.1")。
- `MAX_PEERS` は zenoh-c の `transport/unicast/max_sessions` の既定値 (1000)。gem で 3 に絞ってはいない
  (指示の「zenoh-c の設定に合わせる」)。
- get の時間切れは zenoh-c が正確に見る (zenoh-pico のような 1 秒刻みではない)。
- liveliness の監視が、同じセッションのトークンも知らせる (zenoh-pico は知らせない)。Asterism の層は重複を
  除いているので影響は無い。
- 受け取ったキーは UTF-8、payload と attachment はバイナリ (ASCII-8BIT) の String。

`Asterism` / `Asterism::ROS` / `Asterism::CDR` の API は写しそのもの (picoruby-asterism の README)。

## 4. 受信の仕組みと GVL

- zenoh-c は自分のスレッドで通信し、そのスレッドからコールバックを呼ぶ。subscriber・liveliness の監視・
  queryable・get はそれぞれ zenoh-c の FIFO のチャネルを 1 つ持ち、その前に gem の C のコールバックを置く。
  gem のコールバックは Ruby に触らない (GVL も Ruby のオブジェクトも Ruby のメモリの関数も使わない)。
- zenoh-c の FIFO は満杯になると送る側 (zenoh のスレッド) を止める。mruby 版は「満杯なら一番古いものを捨てて
  数える」なので、gem のコールバックが満杯のときに一番古いものを取り出して捨て (`dropped` に数え)、それから
  FIFO に入れる。数 (`pending` / `received` / `dropped` / `errors`) は gem が数える。満杯で捨てた問い合わせは
  終える (相手に最後の答えが届く)。
- アプリは自分のスレッドから `each_pending` / `each_reply` で取り出す (FIFO の try_recv)。取り出しとコールバックは
  チャネルごとの mutex で直列にする (どちらも短く、待たない)。
- チャネルは Ruby のオブジェクトと zenoh-c のクロージャが共に持ち、最後に手放した側が解放する (参照の数え上げ)。
  get が終わる前に Ruby のオブジェクトが回収されても安全。
- GVL を手放すのは、待つかもしれない呼び出し: `Session.open` (接続)、`put`、`get`、`liveliness_get`、`close`。
  これらはセッションごとの mutex で close と直列にする。
- `poll` は受信には要らない (zenoh-c が裏で受ける)。mruby 版と同じく、接続が切れていないかを見るだけ。
- 切断の扱いは mruby 版と同じ決まり: client はルータが 0 になったら、接続だけの peer は相手が 0 になったら
  セッションを閉じる。待ち受けている peer は開いたまま。以後 `poll` が false、`closed?` が true、`put` が `Error`。
  つなぎ直しはしない。
- 設定も zenoh-pico の gem に寄せた: マルチキャストと gossip の発見は切る、接続だけの peer は待ち受けない、
  接続は 3 秒で諦める (`exit_on_failure`)、自分の put を自分の subscriber に、自分の get を自分の queryable に届けない
  (`Z_LOCALITY_REMOTE`)。

## 5. 写しの仕組み

- `rake sync` が fmruby-core から 3 つを写す (mrblib → `asterism/lib/asterism/shared`、`flash/usr/share/asterism/msgs` →
  `asterism/data/msgs`、`tools/asterism_msggen.rb` → `asterism/tools/`)。写した元のコミットを `SYNCED_FROM` に残す。
  fmruby-core の場所は `FMRUBY_CORE` で変えられる (既定は隣の `../fmruby-core`)。
- `rake sync:check` と試験 `test_sync.rb` が、写しと元が 1 バイトも違わないことを確かめる (fmruby-core が無ければ
  飛ばす)。今の写しの元は e901fb28。
- CRuby だけで要る違いは `cruby.rb` で吸収した (写しは書き換えない):
  1. `Asterism::ROS::TYPE_PATH` を gem の `data/msgs` にする。
  2. MessagePack はすべての String を str の型で送る (`compatibility_mode: true`)。CRuby の msgpack はバイナリの
     String (zenoh から受けた payload など) を bin の型で書くが、機体の MessagePack (picoruby-fmrb-msgpack) は bin を
     読めない。`Asterism::Codec.pack` と `Asterism.error_reply` を差し替えた。機体が送るのも str の型なので、機体から
     見た動きは変わらない。
- それ以外は写しがそのまま CRuby で動いた (CDR の文字コードは R3 で、型の読み込み (`require`) は R3 の
  `load_type_file` で、すでに CRuby に対応していた)。

| 向き | 呼び出し | 回数 | 時間 |

| P4-Nano → CRuby | `info.status` (async、`took_ms`) | 数回 | 126 ms 前後 (機体の更新の周期 50 ms を含む) |

## 8. 見立てと違った点・撤回した仮説・踏んだ罠

- **zenoh-c の FIFO は満杯で止まる**。指示の「FIFO のハンドラに溜める」をそのまま使うと、アプリが取り出さない
  購読が 1 つあるだけで zenoh の受信のスレッドが止まり、リースが切れうる。mruby 版の「一番古いものを捨てて
  数える」に合わせるため、FIFO の前に gem のコールバックを置いた (4 章)。FIFO 自体は使っている。
- **CRuby の msgpack はバイナリの String を bin の型で書く**。機体の MessagePack は bin を読まない
  (`MSGPACK_OBJECT_BIN` の分岐が無い) ので、`cruby.rb` で str の型にそろえた (5 章)。
- **zenoh-c (Rust) は自分の put を自分の subscriber に届ける**。zenoh-pico は届けない。そのままだと ROS の
  `node.call` を自分のサービスに向けたときなどに動きが変わるので、subscriber・queryable・get を `Z_LOCALITY_REMOTE`
  にした。liveliness の監視には同じ設定が無く、自分のトークンも届く (3 章の違い)。
- **zenoh-c の client は切れても裏でつなぎ直そうとする**。gem はルータの数が 0 になった時点で閉じるので、
  mruby 版と同じ「切れたら閉じる」になる。ただし `poll` の間隔より速くルータが戻った場合は気づかない (zenohd の
  再起動は数秒かかるので、実際には起きにくい)。
- **P4-Nano の zenoh_echo が古かった**。`/app/test/zenoh_echo.app.rb` が A1 の改名の前の版で
  (`uninitialized constant ZenohEchoApp::Zenoh`)、asterism_demo は置かれていなかった。今の fmruby-core の版を
  tab5_fs で置いた (ファームは焼いていない)。
- **sim_up は zenohd を LAN 向けの重ね合わせなしで作り直す** (A1 と同じ)。機体の確認を先に済ませてから sim に移った。
  ROS 2 のコンテナは zenohd が作り直された後も、つなぎ直して動いた。
- **`sim_down` は ROS 2 のコンテナの分だけネットワークを消せない** (R1 と同じ)。3 つの compose を重ねた `down` で
  消した。

撤回した仮説: 「zenoh-c の FIFO をそのまま使えば mruby 版と同じ溜め方になる」(上記)。

## 9. ユーザがあとで決めること

1. **配布の形**: 今は手元でビルドするだけ (`libzenohc.so` を拡張の隣に写す)。rubygems に出すなら、機種ごとの
   ビルド済みの gem (x86_64 / aarch64 の Linux、macOS。zenoh-c の公式のビルド済みのものを同梱) にするか、
   インストール時に zenoh-c を取りに行くか。Rust の zenoh を rb-sys + Magnus で包む版に切り替えるか
   (zenoh-c の版に縛られず、cross-gem の仕組みがそろっている)。
2. **純 Ruby の層の正をどちらに置くか**: 今は fmruby-core が正で、asterism は写し (`rake sync`)。asterism を正にして
   fmruby-core が写す形 (mrblib は gem から生成) に移すか。
3. **CRuby らしいブロックの API**: 受信をスレッドで回して `subscribe { |s| ... }` を呼ぶ形、`Asterism.connect` に
   ブロックを渡す形、`node.spin` など (design.md 3 章・6 章)。C1 では作っていない。作るなら、コールバックは
   Ruby のスレッドから呼ぶ (zenoh のスレッドからは呼ばない) 形が今の作りに合う。
4. **mruby 版との小さな違いをそろえるか**: `PICO_VERSION` / `C_VERSION` の名前 (共通の `IMPLEMENTATION_VERSION` を
   両方に置くなど)、`MAX_PEERS` (CRuby でも 3 に絞るか)、自分のトークンを liveliness の監視に出すか。
5. **gem の版**: 今は `0.1.0.pre`。`asterism` の名前は 0.0.0 で確保したまま (push はしていない)。
