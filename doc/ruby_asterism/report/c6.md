## 2. どちらの層に何を入れたか

### 2.1 共有の層 (`mrblib/`、機体と CRuby の両方)

| 入れたもの | 中身 |
|---|---|
| `Asterism.on_join { \|node\| }` / `Asterism.on_leave { \|node\| }` | `Asterism.poll` の中で、今いるノード (自分を除く) と前に知らせたノードを比べ、差の分だけブロックを呼ぶ。接続の直後は、すでにいるノードが最初の poll で現れる。接続が切れたら、知っていたノードが次の poll で全部去る。待つ呼び出しの中の poll (`wait_until` の `pump`) からは呼ばない。ブロックの例外は `Asterism.poll` から出る。`Asterism.close` で忘れる (切れただけなら残る) |
| `node.subscribe(topic, type) { \|msg, info\| }` | `node.subscription` を作り、届いたものを `node.poll` の中でブロックに渡す。`sub.close` で終わる。ブロック無しは `ArgumentError` (`subscription` を使う) |
| `node.every(秒) { }` | `Timer` (`cancel`・`fired`・`period`)。`node.poll` の中で期限の来たものを呼ぶ。最初は 1 周期後。周期を保ち、長く止まった後は取りこぼしをまとめて撃たず今から数え直す (C5 の CRuby と同じ決まり)。時計は `Asterism.now_ms` |
| `node.poll` と `node.pump` | `node.poll` = セッションの poll + サービスの応答 (`pump`) + subscribe のブロック + タイマー。サービスの呼び出しが答えを待つ間 (`Client#wait_for`) は `pump` だけを回し、subscribe と every のブロックは呼ばない |
| `Message#deconstruct_keys` / `Attachment#deconstruct_keys` | C5 で CRuby 専用だったものを移した (2.3) |
| 番号を一度だけ読む | `Client#call_async` と `Publisher#publish` は `@sequence` をローカルに読んでから使う |
| 答えの取り方の順 | `Future#collect`、`ROS::Call#collect`、`already_there?` は `done?` を先に読んでから答えを取り出す (4 章) |

ブロックを呼ぶところは `while` で回している (`each` のブロックの中から使う人のブロックを呼ばない)。使う人のブロックと更新の間に、ほかの入れ子を挟まないため。

### 2.2 CRuby の層 (`lib/asterism/cruby/`)

- `net.on_join` / `net.on_leave` は `Asterism.on_join` / `on_leave` をそのまま呼ぶ形にした。自分で持っていたノードの一覧と差の計算は消した (同じ名前の仕組みは 1 つだけ)。受け取りのスレッドの tick は `Asterism.poll` だけになった。ブロックの例外は、共有の層の `tell` を上書きして `on_error` に回す (where は今どおり `"on_join"` / `"on_leave"`)。
- ROS は、受け取りのスレッドの tick が `node.poll` を呼ぶだけになった。CRuby の層の Timer と、購読ごとの task は消した。`handle` / `fire` を上書きして、subscribe と every のブロックの例外を `on_error` に回す。サービスのブロックの例外の扱い (`ServiceFailed`) は `pump` の上書きに移した (待つ呼び出しも同じ道を通るため)。
- `every` と `cancel_timer` は接続の錠を取る。ブロック無しの `subscribe` (Enumerator) と `topic` は今どおり CRuby だけ。
- `Client#call_async` を包んでいた Mutex は外した (4 章)。
- `Asterism.now_ms` を CRuby では単調な時計にした (期限とタイマーが壁の時計の飛びで狂わないように)。
- 接続が切れた後に `Asterism.connect` し直したとき、古い Net を捨てるようにした (切れただけでは close が呼ばれず、前の Net が残るため)。

使う人から見た CRuby の動きは変えていない (C5 の試験は書き換えずに全部通る)。

### 2.3 case/in はアプリの VM で使える (2 つの形を除く)

sim (標準構成と互換構成の両方) のアプリの VM で、試しのアプリを走らせて確かめた。どちらの構成も結果は同じ。

| 形 | 結果 |
|---|---|
| `deconstruct_keys` を持つオブジェクトに `in {x:, y:}`、`in {x: 3}`、式の `obj in {x: 7}` | 動く |
| 入れ子のハッシュ `in {linear: {x:}, angular: {z:}}`、`in {a: v}`、`**rest`、ガード (`if`)、`1 \| 3`、範囲、`^pin`、配列 `[a, b]`・`[Integer => a, String]`、最上位の `Integer => a`、合わないときの `NoMatchingPatternError` | 動く |
| ハッシュの値にクラス: `in {x: Integer}` / `in {x: Integer => a}` (Hash でもオブジェクトでも) | **合わない** (`NoMatchingPatternError`) |
| ブロックの中で、外のメソッドの変数に束縛する: `pre = nil; [h].each { \|m\| case m in {a: pre} ... }` | **束縛されない** (nil のまま) |

ブロックの中でも、ブロックの中だけの新しい名前なら束縛される。使えないのは上の 2 つの形だけなので、`deconstruct_keys` は共有の層に移した。2 つの形は PicoRuby のコンパイラ (Prism からの生成) の問題で、範囲の外なので直していない。README の Limits に書き、例では case をメソッドに分けた。P4-Nano でも ros2_talker の `case msg in {linear: {x:}, angular: {z:}}` が動いた (5.3)。

## 3. 呼び合い (キー m) が CRuby に届かない件

### 3.1 原因

**呼び出しは CRuby に届いていて、答えも返っていた。CRuby の例 `examples/node.rb` が relay を受けても何も表示しなかった** のが原因。どの層の不具合でもない (試しのアプリ、共有の層、CRuby の層のどれも正しく動いていた)。

- `Info#relay` は呼んだ側の `info.status` を呼び返してから答える。CRuby の側で表示するのは `Info#status` だけで、relay の中の呼び返しは**機体の** status なので CRuby には何も出ない。
- C5 の時のファームとアプリのまま再現した: 機体のキー m で、機体のログに `relay x10: 10 ok (918 ms)`。CRuby の画面には `info.status` (3 秒ごとの async) しか出ない。C5 の作業中の機体のログにも、同じ形の `relay x10: 10 ok (906 ms)` が残っていた。
- C5 の作業中には、キー m の行が機体のログに 1 つも無い回もあった (`relay x10` も `relay: no peer` も無い)。その間も 3 秒ごとの status は続いていたので、アプリは止まっていない。キーがアプリまで届いていない。C6 の互換構成の sim で、別のアプリの窓が前にあるとキー m がアプリに届かないのを見た (窓をクリックしてから押すと届く)。キーの届け先 (窓のフォーカス) の問題で、Asterism の側ではない。

### 3.2 直したこと

- `examples/node.rb`: relay を受けるたびに `info.relay from <ID> #n (called <ID> back: 2.2 ms)` を表示する。
- `examples/node.rb --relay`: 答える間 (受け取りのスレッドが答える)、主スレッドが相手の `info.relay` を 10 回ずつ繰り返し呼ぶ (`relay x10 to <ID>: 10 ok (... ms)`)。CRuby 側にはキーが無いので、これで「両方から同時に m」を作る。
- 機体の asterism_demo: 来た relay をログに `relay from <ID> #n` と出す。

### 3.3 同時に押しても詰まらない

| 組み合わせ | CRuby (`--relay`) | 機体 / sim (キー m) |
|---|---|---|
| P4-Nano ⇔ CRuby (新しいファーム) | 70 秒で `relay x10` 34 回、全部 `10 ok` (1 回 1.0-2.7 秒)。機体からの relay を 80 回受けた | 3 秒ごとに 8 回、全部 `relay x10: 10 ok (1097-1451 ms)`。CRuby から来た relay は 340 回 |
| sim (標準構成) ⇔ CRuby | 40 秒で 59 回、全部 `10 ok` | 5 回、全部 `10 ok (69-91 ms)` |
| sim (互換構成) ⇔ CRuby | 25 秒で 37 回、全部 `10 ok` | 3 回、全部 `10 ok (66-80 ms)` |
| 参考: P4-Nano (C5 の時のファーム) ⇔ CRuby | 50 秒で 28 回、全部 `10 ok` | 6 回、全部 `10 ok (980-1252 ms)` |

時刻が重なっていることはログで見た (例: 機体の `relay x10: 10 ok (1097 ms)` は 21:34:38.8 から 39.9 まで。その間 CRuby は 21:34:37.5 から 39.4 までと 39.6 から 40.9 までの 2 回の `relay x10 to` を回していた)。CRuby の 1 回が 1-2 秒かかるのは、機体が相手の呼び出しに答えるのが更新 (50 ms ごと) の中だけだから (A1 の 7 章と同じ)。

## 4. 見つけた競合: 答えが来ていたのに「nobody serves it」

### 4.1 何が起きていたか

C5 は「`@sequence` を読む間にスレッドが切り替わり、2 本が同じ番号を付ける」ことが原因と見て、`call_async` を Mutex で包んだ。C6 で番号を一度だけ読む形に直し、Mutex を外したところ、`test:api` が 1 回だけ `nobody serves it` で落ちた。そこで、8 本のスレッドから同時にサービスを呼ぶ試しを 1,000 回回して調べた。

- 番号はどの回も重なっていなかった。それでも 1,000 回のうち 12 回落ちた。
- C5 の Mutex を戻しても 10 回落ちた。**Mutex は原因を消していなかった** (落ちる率を下げていただけ)。

原因は、答えの取り出しと `done?` を読む順だった。前の形は「答えを取り出す → `done?` を読む」。zenoh-c では答えと get の終わりが別のスレッドから届くので、2 つの読みの間に「答え」と「終わり」の両方が届くことがある。すると、答えがまだ待ち行列に残っているのに `done?` が true で、答え無しで終わったと判断していた (誰も答えない、に見える)。機体 (zenoh-pico) は `poll` の中でしか届かないので起きない。

### 4.2 直し方

`Future#collect`、`ROS::Call#collect`、`Asterism.already_there?` で、`done?` を先に読み、それから答えを取り出すようにした。`done?` が true なら、終わりより前に届いた答えはすでに行列にある。直した後、8 本 x 1,000 回を 2 度回して落ちたのは 0 回。番号を一度だけ読む直しも残した (番号は重ならないが、読み直す理由も無い)。

## 6. スタックと内蔵 RAM

### 6.1 アプリのスタックの余り (P4-Nano、16 KB、周期ダンプの Free の最後の値)

同じ P4-Nano で、C5 の時のファームとアプリ (A1 から変わっていない mrblib) と、C6 のファームとアプリを、同じ操作で比べた。

| アプリと操作 | C5 の時 | C6 | 差 |
|---|---|---|---|
| asterism_demo、両方から同時に relay (機体のキー m と CRuby の `--relay`) | 5,840 B | 5,800 B | -40 B |
| ros2_talker、/chatter の発行と /chatter_back の受け取り | 6,884 B | 6,260 B | -624 B |
| 同じ、ただし /cmd_vel_in の購読 (Twist の型の読み込み) を外した版 | (6,884 B) | 6,884 B | 0 B |
| ros2_types (変えていない) | 4,084 B | 4,084 B | 0 B |

- on_join / on_leave、every、ブロックつきの subscribe そのものは、スタックをほとんど増やさない (-40 B と 0 B)。
- ros2_talker の -624 B は、足した `/cmd_vel_in` のために起動時に `geometry_msgs/msg/Twist` を読む分 (`require_type` は型のファイルを呼んだ所のスタックでコンパイルし、Twist は中で Vector3 を読むので 2 段になる)。その購読を外した版は C5 の時と同じ 6,884 B だった。
- いちばん少ないのは ros2_types の 4,084 B (C5 以前から同じ)。止まる条件 (スタックが足りない) には当たらない。

### 6.2 起動時の内蔵 RAM (P4-Nano、NARYAv4)

- ファーム: `fmruby-core.bin` 0x62dd50 (区画 0x700000 の残り 0xd22b0、12%)。変えたのは mrblib の Ruby だけで、増えるのはバイトコード (flash) だけ。
- 起動の `M1|` を C5 の時のファームの起動と比べた。`boot_start` から `file_sync` までの同期の段は全部同じ値。その後の段は USB・音声・BLE・WiFi の非同期の初期化と重なり、差は -20 B から +444 B の揺れ (C6 の方が多いか同じ段がほとんど)。最後の `wifi_rd` は 212252 → 212696。
- 周期ダンプの IRAM free (起動直後、アプリを開く前): 218772 → 219216。
- **起動時の内蔵 RAM の増分は 0**。

足した試験 (`test/test_asterism.rb`、受け取りのスレッドを使わない、機体と同じポーリングの形):

- on_join / on_leave: 子のプロセスが現れたら `Asterism.poll` で 1 回だけ `on_join`。子が去る (ルータ) か接続が切れる (peer) と 1 回だけ `on_leave`、その後の poll では何も来ない。

- パターンマッチ: Twist と Attachment が共有の層だけで `case/in` に合う。
