# R3 報告: メッセージ型の変換器

> 状態: 完了 (検収待ち) | 更新: 2026-10-08 | instruction_r3.md の実装と確認の記録。`.msg` / `.srv` から純 Ruby の型を作る変換器 (CRuby、標準ライブラリだけ) を作り、型のハッシュ (RIHS01) を変換器で計算して Jazzy の型の記述の JSON と全部一致させた。62 の型を storage に同梱し、アプリが使う型だけを `Asterism::ROS.require_type` で読む。手書きの std_msgs/String と AddTwoInts は作った型に置き換えた。P4-Nano と sim で受け入れ条件 1-5 を満たした。止まる条件には当たらなかった

## 1. 結果の要約

- 変換器: `lib/add/picoruby-asterism/tools/asterism_msggen.rb`。入力は `.msg` / `.srv` (ROS 2 の `share` と同じ並びの
  ディレクトリ、または手元のファイル)。参照する型もたどって、型ごとに 1 つの Ruby のファイルを作る。
- 型のハッシュ: 変換器が計算する。同梱の型とその参照先の 66 個が Jazzy の JSON と一致した。ほかに、Jazzy の 6 つの
  パッケージ (std_msgs、builtin_interfaces、geometry_msgs、sensor_msgs、example_interfaces、service_msgs) の
  全部の `.msg` / `.srv` (JSON 125 個、ハッシュ 335 個) でも一致した。上限つきの文字列・列、wstring、既定値、
  サービスを含む試験用の型 13 個も、像の中の rosidl が計算した値と一致した。
- 値の形: 普通のクラス (基底は `Asterism::ROS::Message`)。アプリの VM に `Data` も `Struct` も無かった。
- 読み込み: storage の `/usr/share/asterism/msgs/<pkg>/<msg|srv>/<Name>.rb` に置き、`require_type` が読んだ
  ときだけアプリの VM に入る。ファームには変換器の作った型は 1 つも入っていない。
- P4 (NARYAv4) のファームは develop から **+8,384 B** (区画の残り 865,136 B、12%)。`.iram0.text` /
  `.dram0.data` / `.dram0.bss` は同じ大きさで、起動時の `M1|` の同期の段は全部同じ。**起動時の内蔵 RAM の増分 0**。
- 試しのアプリ `flash/app/test/ros2_types.app.rb` (+ .app.toml)。ros2_talker と ros2_service は作った型に
  書き換えた。
- host のテスト `rake asterism:test` (`rake test` に入れた) は 2,396 項目すべて通る。

## 2. 変換器の使い方

```
# ROS 2 の環境の型 (と、それが使う型)
ruby tools/asterism_msggen.rb -I /opt/ros/jazzy/share -o out geometry_msgs/msg/Twist
# 自分のパッケージ (my_pkg/msg/Foo.msg。参照先のパッケージは -I で)
ruby tools/asterism_msggen.rb -I /opt/ros/jazzy/share -o out path/to/my_pkg/msg/Foo.msg
# ハッシュだけ出す
ruby tools/asterism_msggen.rb -I share --hash example_interfaces/srv/AddTwoInts
# ROS 2 が入れた型の記述の JSON とハッシュを比べる
ruby tools/asterism_msggen.rb -I /opt/ros/jazzy/share --check-json /opt/ros/jazzy/share sensor_msgs/msg/Imu
```

- 出力は `<out>/<pkg>/<msg|srv>/<Name>.rb`。機体では `/usr/share/asterism/msgs` か、`Asterism::ROS::TYPE_PATH` に
  足したディレクトリに置く。CRuby では出力のディレクトリを `TYPE_PATH` に入れる。
- サービスのハッシュには `service_msgs/msg/ServiceEventInfo` と `builtin_interfaces/msg/Time` の定義が要る
  (ROS 2 の `share` には必ずある)。
- Family mruby には依存しない (標準ライブラリの digest・json・optparse・fileutils だけ)。
- 同梱の型を作り直すのは親リポジトリの `tools/fmrb_ros2_types.rb`。ROS 2 の像から定義と JSON を取り出し、全部の
  ハッシュを JSON と比べ (違えば止まる)、定義と JSON のハッシュを `tools/ros2_jazzy/` に写し、
  `flash/usr/share/asterism/msgs` を作り直す。`--check` は比べるだけ、`--fixtures` は試験の照合用のデータ
  (試験用の型の rosidl のハッシュと、rclpy が作った CDR) を作り直す。

できるファイルの例 (geometry_msgs/Twist):

```ruby
::Asterism::ROS.require_type("geometry_msgs/msg/Vector3")

module ::Asterism::ROS::GeometryMsgs
end

class ::Asterism::ROS::GeometryMsgs::Twist < ::Asterism::ROS::Message
  ROS_NAME = "geometry_msgs/msg/Twist"
  TYPE_NAME = "geometry_msgs::msg::dds_::Twist_"
  TYPE_HASH = "RIHS01_9c45bf16..."
  FIELDS = [:linear, :angular]
  attr_accessor :linear, :angular
  def initialize(linear: nil, angular: nil) ... end   # 既定値はここ
  def self.write(w, m) ... end                         # CDR へ
  def self.read(r) ... end                             # CDR から
end
```

サービスは `module ...::AddTwoInts` (サービスの `ROS_NAME`・`TYPE_NAME`・`TYPE_HASH`) と、その下の
`Request` / `Response` のクラス (それぞれ自分の型名とハッシュも持つ)。

## 3. 型のハッシュの計算の仕方

Jazzy の `rosidl_generator_type_description` (像の中の版 4.6.9) と同じ手順にした。

1. 型ごとの記述: `{"type_name": "pkg/msg/Name", "fields": [{"name", "type": {"type_id", "capacity",
   "string_capacity", "nested_type_name"}}]}`。既定値の欄 (`default_value`) は除く。定数は入らない。
2. `type_id` は基本の型ごとの番号 (int8=2 ... double=11、bool=15、byte=16、string=17、wstring=18、
   上限つきの文字列 21 / 22、入れ子=1) に、固定長の配列なら +48、上限つきの列なら +96、上限なしの列なら +144。
   `.msg` の `char` は IDL では uint8 なので 3、`byte` は 16。`capacity` は配列の長さか列の上限、
   `string_capacity` は文字列の上限。
3. 中身の無い型には `structure_needs_at_least_one_member` (uint8) を 1 つ置く。
4. サービス `pkg/srv/X` の記述は `request_message`・`response_message`・`event_message` の 3 つの入れ子。
   `X_Event` は `info` (service_msgs/msg/ServiceEventInfo)、`request` と `response` (上限 1 の列)。
5. 全体: `{"type_description": その型, "referenced_type_descriptions": 参照する型の全部 (たどった先も含む)
   を名前で並べたもの}` を、Python の `json.dumps(..., ensure_ascii=True, separators=(", ", ": "))` と同じ形の
   文字列にして SHA-256。先頭に `RIHS01_`。

照合の結果:

| 照合の相手 | 数 | 結果 |
|---|---|---|
| 同梱の型と参照先 (host のテスト、`ros2_jazzy/type_hashes.txt` = 像の JSON の値) | 66 | 全部一致 |
| 像の JSON (同梱の型を作るたびに `fmrb_ros2_types.rb` が比べる。JSON の `type_hashes` の欄ごと) | 153 | 全部一致 |
| 像の 6 パッケージの全部の `.msg` / `.srv` (作業中に 1 回) | 335 | 全部一致 |
| 試験用の型 asterism_test_msgs (上限・wstring・既定値・サービス) と、像の rosidl が計算した値 | 13 | 全部一致 |
| R1 の std_msgs/String の定数、R2 の AddTwoInts の定数 | 2 | 一致 |

## 4. CDR の扱う範囲

`Asterism::CDR` (XCDR1、先頭 4 バイトの印、揃えは印の後から数える) に足した。

| 種類 | 書く | 読む | 備考 |
|---|---|---|---|
| bool、byte、char、int8-64、uint8-64 | 済 | 済 | 範囲の確かめはしない (はみ出すと下のビットだけ書く)。uint64 の 2**63 以上は読むと負 (R1 と同じ) |
| float32、float64 | 済 | 済 | `Array#pack` / `String#unpack` があれば使う (P4・sim の mruby には mruby-pack が入っていた)。無ければ計算で組み立てる (非正規化数・無限大・NaN・-0.0 まで、host のテストで pack と全部のビットを照合) |
| string、string<=N | 済 | 済 | 上限を超えると書くときに `ArgumentError` |
| 固定長の配列 T[N] | 済 | 済 | 長さが違うと `ArgumentError` |
| 列 T[]、T[<=N] | 済 | 済 | 個数 (uint32) + 要素。上限を超えると `ArgumentError`。要素が 0 個なら要素の揃えの詰め物は入れない (Fast-CDR と同じ。rclpy の bytes で確かめた) |
| byte / uint8 / char の配列と列 | 済 | 済 | Ruby では 1 つのバイナリの String (Integer の Array も受ける) |
| 入れ子の型、その配列と列 | 済 | 済 | 入れ子そのものには揃えは無く、最初の要素で揃う |
| wstring | 例外 | 例外 | `NotImplementedError` (型は作れる。ハッシュも正しい) |
| ビッグエンディアン | - | 済 | 読むだけ (R1 と同じ) |

CDR の正しさは、像の中の rclpy (`serialize_message`、rmw_zenoh_cpp と Fast-CDR) が作った 38 の
メッセージのバイト列と照合した (`test/asterism_msgs/golden_cdr.tsv`)。照合は「自分が書くバイトのうち、
詰め物以外が全部同じ」と「読んだ値が同じ」で見る (7 章の罠)。

## 5. 値の形

- アプリの VM (mruby、picoruby-mruby) で調べた: `Data` は無い、`Struct` も無い。よって普通のクラスにした。
  CRuby でも同じコードが動く (host のテストは CRuby で回している)。
- 共通の部分は `Asterism::ROS::Message` (firmware の ros.rb):
  - `from(v)`: nil なら全部既定値、Hash (Symbol か String のキー。足りない欄は既定値、知らない欄は
    `ArgumentError`)、その型の値ならそのまま。入れ子の Hash も入れ子の型になる。
  - `to_h` (入れ子も Hash に)、`encode(msg_or_hash)`、`decode(bytes)`、`==`、`inspect`。
- 型ごとのファイルにあるのは: 定数、`FIELDS`、accessor、既定値つきの `initialize(**fields)`、`write` / `read`。
- `pub << { linear: { x: 0.1 } }` が使える (`Publisher#<<` を足した)。publisher などに型の名前の文字列も渡せる
  (`node.subscription("/cmd_vel", "geometry_msgs/msg/Twist")`。中で `require_type` する)。

## 6. 型の読み込み方とメモリの量

### 6.1 決めた形

- 置き場所: storage の `/usr/share/asterism/msgs/<pkg>/<msg|srv>/<Name>.rb` (flash/ に同梱。/home ではない)。
- `Asterism::ROS.require_type("geometry_msgs/msg/Twist")` が、型の定数が無ければ `TYPE_PATH` からファイルを
  探し、**mruby では中身を読んで `eval` する** (CRuby では `require`)。ファイルの先頭の `require_type` で、
  使う型が先に入る。2 回目からはファイルを読まずに定数を返す。
- 型のファイルは入れ子のモジュールにせず、完全な名前 (`class ::Asterism::ROS::GeometryMsgs::Twist`) で書く。

picoruby の `require` / `load` を先に調べた結果、使わないことにした:

- picoruby-require の `require` は、ファイルごとに `Sandbox` (mruby-task の別の task) を作ってコンパイル・実行し、
  終わるのを `sleep_ms 5` を挟んで待つ。定数はアプリの VM に入るので、読み込み自体はできる (入れ子の require も
  通った)。
- ただし Sandbox の task は VM が閉じるまで残る (doc/multivm_app/plan.md 2.1 のとおり)。sim では初回の require
  が 44.8 KB、2 つ目以降の空のファイルでも 1 つあたり約 3.4 KB を取った。P4 でも Vector3 1 つの `load_file` が
  14,088 B (eval なら 8,648 B)。
- `Kernel#eval` (picoruby-eval、両方の構成に入っている) は同じ VM の中でコンパイルするだけで、task を作らない。
  実行は呼び出した側の文脈になるので、ファイルの中の名前は `::` から書く。

### 6.2 量

flash (ファーム、NARYAv4。同じ日に develop (3828be23) を `rake clean_all` の後、R3 を `rake clean` の後に作った):

| | fmruby-core.bin | 区画 (0x700000) の残り | .iram0.text | .dram0.data | .dram0.bss | .flash.text | .flash.rodata |
|---|---|---|---|---|---|---|---|
| develop | 0x62abd0 | 0xd5430 (873,520 B) | 85,300 | 14,916 | 25,396 | 3,601,690 | 2,760,680 |
| R3 | 0x62cc90 (+8,384 B) | 0xd3370 (865,136 B、12%) | 85,300 | 14,916 | 25,396 | 3,601,690 | 2,769,064 (+8,384) |

増分は cdr.rb (浮動小数・配列・列) と ros.rb (`Message`・`require_type`) のバイトコードだけ。C は変えていない。
手書きの 2 つの型はファームから消えた。

storage (同梱の型 62 ファイル):

- ファイルの中身の合計 67,635 B (1 ファイル 521-4,271 B)。
- littlefs (ブロック 4 KB) に置くと 85 ブロック = 348,160 B (区画 8 MB の 4.2%)。像を作る littlefs-python で
  このディレクトリだけの像を作り、使ったブロック数を数えた。小さいファイルでも 1 つ 1 ブロック取る。

アプリの VM (P4-Nano、プール 1 MB、`GC.start` の後の `FmrbApp.pool_used` の差。ros2_types が起動時に計る):

| 読んだ型 | 実際に入ったファイル | 増分 | 時間 |
|---|---|---|---|
| geometry_msgs/msg/Twist | Vector3、Twist | 15,336 B | 55 ms |
| sensor_msgs/msg/Imu | Quaternion、Time、Header、Imu (Vector3 は読み込み済み) | 32,768 B | 136 ms |
| std_msgs/msg/Float32MultiArray | MultiArrayDimension、MultiArrayLayout、Float32MultiArray | 19,992 B | 110 ms |
| 計 | 9 ファイル | 68,096 B | 340 ms |

- ファイル 1 つあたり約 7.6 KB。ros2_types の VM は読み込んだ後 369,752 B、動いている間 390-414 KB。
- sim (64 ビット) では同じ 3 つで 68,312 B、1 ms。

型 1 つの読み方の比較 (P4、geometry_msgs/Vector3 を 1 つ、試しのアプリで計測。スタックは 16 KB のうちの残り):

| 読み方 | VM の増分 | スタックの残り |
|---|---|---|
| 何も読まない (アプリの基準) | - | 9,392 B |
| `eval("1 + 1")` | 1,008 B | 9,332 B |
| `require` (Sandbox) で std_msgs/String | 9,120 B | 4,752 B |
| `Sandbox#load_file` で Vector3 | 14,088 B | 4,752 B |
| `eval`、モジュールを 3 段入れ子にした形 (最初の版) | 8,648 B | 4,724 B |
| `eval`、完全な名前で書いた形 (採用) | 5,920 B | 6,876 B |

- 入れ子のモジュールは、本体ごとにコンパイル結果が増え、コンパイルも深くなる。完全な名前にしたことで、
  ros2_types の 3 つの型は 94,048 B から 68,096 B に、ros2_types のスタックの残りは 1,924 B から 4,084 B に
  なった。
- 欄の表 (配列) だけを持たせて変換は共通のコードに任せる形も試したが、同じ Vector3 で約 5.5 KB (最初の eval の
  分を引いた見積もり) と大きくは減らなかった。速さも落ちるので採らなかった。

### 6.3 内蔵 RAM とスタック

- 起動時: develop と同じコードの R2 のファーム (焼く前の最後の起動) と、R3 を `flash` (app_only) で焼いた直後の
  `M1|` 24 行を比べた。`boot_start` から `spawn:Services` までの 19 行は全部同じ値。BLE と WiFi の非同期の段だけ
  R3 が 432-436 B 多く空いていた (揺れ)。**起動時の内蔵 RAM の増分 0**。
- ros2_types を 3 回起動して閉じた: 動いている間の IRAM free 184,588-184,908、閉じた後 203,188 / 203,188 /
  202,976 (R1・R2 と同じ、最初の数回に一度だけ取られる種類)。
- アプリのスタック (16 KB) の残り: ros2_types 4,084 B、ros2_talker 6,884 B (R1 は 9,168 B)、ros2_service
  5,840 B (R2 は 5,736 B)。型を読むときの eval のコンパイルが、更新の中より約 2.5 KB 深い。型は `on_create` で
  読むのがよい (README に書いた)。

host のテスト (`test/asterism_msgs/run.rb`、CRuby、docker 不要) の中身:

- ハッシュ: 同梱の 66 個 (Jazzy の JSON)、試験用の 13 個 (rosidl)、R1・R2 の定数。
- 同梱のファイルが変換器の出力と 1 バイトも違わないこと (手で直したら落ちる)。
- 読み込み: 62 の型を `require_type`、2 回目、知らない型 (`UnknownType`)、型の名前の誤り。
- 値: Hash から (欠け・String のキー・知らない欄)、`to_h`、既定値 (Quaternion の w = 1、配列・文字列・バイト列の
  既定値)、定数 (数・文字列・浮動小数)。
- CDR: rclpy の 38 のメッセージとの照合、62 の型の乱数の値での往復 (189 個)。
- 境界: 全部の上限ちょうど、上限を 1 超えたとき (文字列・配列の中の文字列・列・バイト列・型の列・固定長の
  長さ違い)、空の列、空の float64 の列の後の揃え、入れ子の揃え (uint8 の後の float64 が 8 に揃う、入れ子の型が
  最初の要素で揃う)、wstring、切れたデータ、データより長い列の個数、ビッグエンディアン、利用者のサービス。
- 浮動小数を pack 無しで組み立てる経路: 222 個の値で pack とビットまで一致 (Math.ldexp / frexp がある場合と
  無い場合の両方)。

## 8. 見立てと違った点・撤回した仮説・踏んだ罠

- **`Data.define` は使えなかった** (design.md 6 章の案)。アプリの VM に `Data` も `Struct` も無い。普通のクラスに
  した。design.md の直しは親のセッションに任せる。
- **`require` は Sandbox の task を残す**。読めはするが、ファイルごとに VM のメモリを取り続ける (6.1)。`eval` に
  した。撤回した仮説: 「型のファイルは picoruby の `require` で読めば足りる」。
- **入れ子のモジュールは高い** (6.2)。最初の版は `module Asterism / module ROS / module <Pkg>` で包んでいて、
  ros2_types のスタックの残りが 1,924 B まで減った。完全な名前で書く形に直した。
- **CDR の先頭の定数を書き換えていた**。`Writer` の最初の版は、CRuby の文字コードのために足した `binary` が mruby
  では同じ String を返すので、`HEADER_LE` の定数そのものに追記していた。最初の 1 通だけ正しく、2 通目から壊れた
  (sim で `/array` が読めず、Imu は 1 通目だけ読めた)。毎回新しい String を作るように直し、定数は freeze した
  (mruby でも書き換えると例外になる)。host のテストは CRuby なのでこの経路を通らない。
- **rclpy の CDR の詰め物は 0 ではない**。Fast-CDR は揃えのための詰め物を書かず、バッファにあったものがそのまま
  出る (`2020`、`fast` などの文字が入る)。またバッファの長さがメッセージより長いことがある (末尾に 4-8 バイト)。
  照合は詰め物以外のバイトで行い、受け手は末尾の余りを無視してよいことも確かめた。こちらの `Writer` は詰め物を 0 に
  し、末尾には何も足さない。`--fixtures` で作り直すたびに golden_cdr.tsv の詰め物の部分は変わる。
- **空の列の後に揃えの詰め物は入らない** (JointState で確かめた)。要素ごとに揃えるこちらの書き方と同じ。
- **CRuby では文字列の文字コードが要る**。バッファは BINARY、読んだ文字列は UTF-8 にする (mruby では何もしない)。
- **`require_type` の中の `eval` は、呼んだメソッドの文脈で動く**。型のファイルの中の名前は `::` から書く。
- **storage は小さいファイルでも 1 ブロック取る**。67.6 KB の型が littlefs では 340 KB になる。
- ROS 2 の `ros2 topic pub` は相手の購読のトークンを待ってから出すので、機体の購読のトークンの形 (型名・ハッシュ)
  が作った型でも正しいことが、`/cmd_vel` と `/array_in` が届いたことで確かめられた。

## 11. 申し送り

- **使う側の書き方が変わった** (R1・R2 から): `Asterism::ROS::StdMsgs::String` は `require_type` してから使い、
  `publish` には Hash か型の値を渡し、受け取りは `msg.data`。ros2_talker / ros2_service はそう直した。
- **判断してほしい点**: byte / uint8 / char の配列と列を Ruby ではバイナリの String にした (画像などの大きな
  データで要素ごとの Integer を作らないため。rclpy は uint8[] を整数の列、byte[] を bytes の列にする)。Array で
  受けたいなら変換器の `byte_kind?` と Reader の `bytes` を変える。
- **知らない型の受け取り**: 今は型を読み込んでいない購読はできない。Jazzy の型の記述の問い合わせ
  (`type_description` サービス) で機体に無い型の欄を受け取り、汎用の Reader で読む形が考えられる。型のハッシュ
  の計算は機体ではしない (SHA-256 が無い) ので、問い合わせで得た記述をそのまま信じることになる。
- **QoS**: 型とは関係なく、R1・R2 のまま既定の形だけ。
- **CRuby 版での使い方**: cdr.rb・ros.rb はそのまま CRuby で読め、`TYPE_PATH` に変換器の出力を入れれば
  `require_type` も `require` で動く (host のテストがこの形)。Zenoh の CRuby 版のバインディングは無いので、
  通信までは確かめていない。
- **同じパッケージに同じ名前の msg と srv があると** Ruby の定数がぶつかる (今の同梱の型には無い)。必要になったら
  名前の付け方を決める。
- **整数の範囲を確かめない**。int8 に 300 を入れると下の 8 ビットだけが出る。rclpy は例外にする。要るなら
  `Writer` で確かめる (少し遅くなる)。
- **メモリをさらに減らすなら**: (1) 型のファイルを PC で .mrb にして読む (コンパイルが要らないのでスタックも浅い。
  ただし今の picoruby で .mrb を同じ VM に読む口は Sandbox だけで、task が残る)。(2) 型の定義を 1 つのファイルに
  まとめて storage のブロックを減らす (使わない型まで読むことになる)。
- **他のディストリビューション**: ハッシュの決まりは Jazzy で確かめた。Kilted / Rolling では `--check-json` で
  確かめてから使う。
- design.md 6 章 (値の形) と plan.md の R3 の節の更新は親のセッションに任せる。
