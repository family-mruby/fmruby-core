# S2 報告: Ruby で MuJoCo を回し、台車を Asterism のオブジェクトとして公開する

> 状態: 完了 (検収待ち) | 更新: 2026-10-10 | instruction_s2.md の実装と確認の記録。CRuby から標準の Fiddle で MuJoCo 3.15.0 の C の API を直接呼び、S1 の台車を実時間 (毎秒 500 歩、1 コアの約 4 %) で回した。台車はノード `mujoco`・アプリ `rover` の `drive`・`state`・`world` として網に出し、CRuby・sim・P4-Nano・asterism-console から操縦できた。前進 1 m と 90 度の旋回で、車輪から計算した位置は本当の位置と 0.2-0.3 %・0.3 度で合った。ROS 2 は使っていない。止まる条件には当たらなかった

## 1. 結果の要約

- MuJoCo の皮: asterism の `examples/mujoco/lib/mujoco.rb` (Fiddle)。構造体の中の位置は、固定した版のヘッダを C で
  コンパイルして `offsetof()` で求めた表 (`lib/mujoco/layout_3_15_0.rb`、生成物) から読む。版が違う libmujoco は開かない。
- libmujoco の取り方: 公式のリリース (Linux x86_64 の tar) を、版と sha256 を `MUJOCO_PIN` に書いて**手元で**取る
  (`fetch.rb`、置き場は gitignore の `examples/mujoco/vendor/`)。docker の像には入れない (2.3 節)。
- 物理を回すプロセス: `examples/mujoco/rover.rb`。S1 の `rover.xml`・`scene.xml` (写しを `examples/mujoco/model/` に置いた)
  を読み、2 ms の刻みを実時間に合わせて回す。加速の上限は Ruby の側 (直進 0.5 m/s^2、旋回 2 rad/s^2)。
- 公開するオブジェクト: `drive` (cmd・stop)、`state` (pose・odom・imu・speed・all)、`world` (reset・objects・info)。
  状態は 10 Hz で `asterism/mujoco/rover/state` にも put する。
- 複数の操縦者: **最後の命令が勝つ**。暇な操縦者は何も送らない (止めるときに stop を 1 回だけ送る) 決まりにした (4 章)。
- 操縦する側: CRuby の `examples/mujoco/drive.rb` (試走とキーボード)、Family mruby の
  `flash/app/test/asterism_rover.app.rb` (矢印キー、portable API の非同期の呼び出し)。sim と P4-Nano で動いた。
- asterism-console: コードの変更なしで、グラフの入れ子・画面からの `drive.cmd`・状態のキーの線グラフ・記録と見返しができた。
  許可表に 2 行足した (console の docs/s2.md)。

## 2. FFI の包み方

### 2.1 呼ぶ関数

`Fiddle.dlopen` で libmujoco を開き、使う関数ごとに `Fiddle::Function` を作る。使うのは `mj_version`、
`mj_versionString`、`mj_loadXML`、`mj_makeData`、`mj_step`、`mj_forward`、`mj_resetData`、`mj_name2id`、
`mj_deleteData`、`mj_deleteModel` の 10 個。引数と戻り値は int とポインタだけなので、Fiddle の型の指定で足りる。

### 2.2 構造体の読み方

`mjModel` (5,656 B) と `mjData` (162,104 B) の形を Fiddle に教えることはしない。先頭の番地からの距離 (オフセット) で、
要る欄だけを読む。

| 構造体 | 読む欄 | 型 |
|---|---|---|
| mjModel | `nq` `nv` `nu` `nbody` `njnt` `ngeom` `nsite` `nsensor` `nsensordata` | mjtSize (int64) |
| mjModel | `opt.timestep` | mjtNum (double) |
| mjModel | `jnt_type` `jnt_qposadr` `jnt_dofadr` `geom_type` `sensor_dim` `sensor_adr` | int* |
| mjModel | `geom_size` | mjtNum* |
| mjData | `time` | mjtNum |
| mjData | `qpos` `qvel` `ctrl` `sensordata` `xpos` `xquat` `geom_xpos` `geom_xmat` | mjtNum* |

- オフセットの例 (3.15.0): `nq` 0、`opt.timestep` 784、`jnt_qposadr` 2104、`sensor_adr` 5080、`mjData.time` 160648、
  `qpos` 160688、`ctrl` 160736、`xquat` 160848。mjData は先頭に統計の固定長の配列を持つので、配列の指す先は 16 万バイトの先にある。
- 求め方: `layout_gen.rb` が、固定した版のヘッダ (`vendor/mujoco-3.15.0/include`) を読む小さな C を作ってコンパイルし、
  各欄の `offsetof()` を出させて Ruby の表に書く。同時に、各欄の C の型が表の型と同じかを `_Static_assert` と
  `__builtin_types_compatible_p` でコンパイラに確かめさせる (版を上げたときに型の変わった欄があればコンパイルで止まる)。
  `mjtNum` が double、int が 32 bit、64 bit の構成であることも確かめる。数え上げは手でしていない。
- 配列の値は `Fiddle::Pointer` でバイトを写し、`unpack("E*")` (double) と `unpack("l<*")` (int) で読む。書くのは `ctrl` だけ。
  配列を指すポインタは一度読んだら覚えておく (MuJoCo は作ったあと動かさない)。

### 2.3 版の検査

- `MuJoCo::Lib.open` は、`mj_version()` が表を作ったヘッダの `mjVERSION_HEADER` (3015000) と同じで、
  `mj_versionString()` が "3.15.0" のときだけ通す。違えば `MuJoCo::VersionMismatch` で止まる。
- 実際に効くか確かめた: 3.14.0 のリリースを取って `MUJOCO_LIB` に渡すと、物理を始める前に
  「3.14.0 (3014000) is ... for 3.15.0 (3015000)」で止まった。
- 版の違いは実害になる: 3.14.0 と 3.15.0 のヘッダを比べると、mjModel は 5,696 B から 5,656 B に縮み
  (flex の欄が 1 つ消えた)、`sensor_adr` は 5120 から 5080 に、`geom_size` は 2528 から 2520 に動いた。mjData も
  162,080 B から 162,104 B に変わった。小さい版の差でも位置は動くので、版を固定して検査するのは要る。
- 版の検査を抜けたあとの確かめ: 読んだ大きさが 0 から 100 万の間で、timestep が 0 より大きく 1 秒より小さいこと。
  `mj_forward` のあと、時刻が 0 で、世界の物体 (body 0) が原点・回転なしであること。外れたら `MuJoCo::Error`。

### 2.4 libmujoco の取り方 (手元か像か)

手元で取ることにした。理由:

- 物理を回すのが host の CRuby (利用者の rbenv の Ruby) なので、像に入れても使えない。
- 取るのは tar を 1 つ (33 MB) で、ビルドも system への導入も無い。`fetch.rb` は標準のライブラリだけで、
  ダウンロード・sha256 の照合・展開をする。sha256 は GitHub のリリースの digest と一致した。
- S1 の像の中の MuJoCo (mujoco_vendor の 3.12.0) は版が違い、ROS 2 の部品と一緒に固定されている。S2 の台車とは別の世界なので、
  合わせる理由が無い。

glibc 2.35 (Ubuntu 22.04、WSL2) で確かめた。macOS と aarch64 は固定していない。描画はしないので GPU も画面も要らない。

### 2.5 Python の mujoco を挟む案との比べ

止まる条件 (FFI で安全に呼べない) には当たらなかったので、案としてだけ残す。FFI は「ヘッダから求めた位置 + 版の検査」で
安全に呼べた。Python を挟むと構造体の心配は無くなるが、プロセスが 2 つになり、Ruby から 1 歩ごとに呼べない。
今の作りで十分速い (5.1 節) ので、Python は要らない。

## 3. 物理を回すプロセスと公開するオブジェクト

### 3.1 回し方

- 1 回の制御で物理を 5 歩 (10 ms、100 Hz)。制御のたびに、加速の上限をかけた (v, w) から 2 輪の目標の速さ
  (左 (v - w L/2)/r、右 (v + w L/2)/r、r = 0.05 m、L = 0.24 m) を `ctrl` に書き、物理を進め、車輪の角度の差から
  位置を足し込む (diff_drive_controller と同じ、中点の向きで足す)。
- 実時間に合わせる: 進めた歩数 x 2 ms を壁の時計と比べ、遅れていれば追いつくまで進め、進んでいれば待つ。待つ間も
  2 ms ごとに `Asterism.poll` して呼び出しに答える。0.1 s より遅れたら追いつくのをあきらめる (止まったあとに暴走しない)。
  時計に `data.time` を使わないのは、`world.reset` で時刻が 0 に戻るため (最初の版はこれで時計が狂った)。
- すべて 1 本のスレッドで回す。portable API (`Asterism.poll`) なので、オブジェクトは物理の歩と歩の間に呼ばれ、
  鍵が要らない。状態の put は別の Zenoh のセッションで出す (オブジェクトの層のセッションは内部のもので、外から使う口が無い)。

### 3.2 オブジェクト

| 呼び出し | 返すもの |
|---|---|
| `drive.cmd(v, w, by: nil)` | 並進 v (m/s、上限 1.0) と回転 w (rad/s、左が正、上限 3.0)。受け取った値 `{"v", "w"}`。`by:` は送り手の名前 (state.speed に出る) |
| `drive.stop(by: nil)` | true。加速の上限をかけて止まる |
| `state.pose` | 本当の位置 (free joint の qpos): `{"x", "y", "z", "yaw", "yaw_deg"}` |
| `state.odom` | 車輪から計算した位置: `{"x", "y", "yaw", "yaw_deg"}` |
| `state.imu` | `{"quat" [w,x,y,z], "gyro" [x,y,z], "accel" [x,y,z]}` (S1 の IMU の 3 つのセンサ) |
| `state.speed` | 計算した `v`・`w`、頼まれた `cmd_v`・`cmd_w`、上限をかけた後の `out_v`・`out_w`、`wheels` [左, 右]、`driver`、`age` (最後の命令からの秒) |
| `state.all` | `{"t", "pose", "odom", "speed", "imu"}`。状態のキーに put するのと同じ Hash (MessagePack で 381-393 B) |
| `world.reset` | 始めの位置へ戻す (`mj_resetData`)。計算した位置も 0 から |
| `world.objects` | 柱 4 本と箱 2 つ: `[{"name", "type", "pos", "size", "yaw_deg"}]` |
| `world.info` | MuJoCo の版、timestep、直近の毎秒の歩数・CPU |

- 値はすべて Hash / Array / 数 / 文字列 / nil。
- `state.all` と `world.info` は指示書に無いものを足した。機体からの呼び出しを 1 回にまとめるためと、測った値を網から見るため。
- `by:` は省いてよい。console の画面は引数を JSON の配列で渡すのでキーワードを付けられず、送り手は `?` と出る。

## 4. 命令が途絶えたときと、2 つの側から来たとき

- **途絶え**: 最後の命令から 0.5 s で目標を 0 にする。CRuby から `drive.cmd(0.3, 0)` を 1 回だけ送って 0.1 s ごとに
  `state.speed` を読むと、0.45 s まで目標 0.30、0.56 s で 0 になり、減速の上限で 1.00 s に止まった。
- **2 つの側から**: 最後の命令が勝つ (送り手は問わない) を選んだ。ROS 2 の `/cmd_vel` と同じ振る舞いで、台車の側に
  選び手を置かずに済む。その代わり、操縦する側に決まりを 1 つ置く: **動かしたいときだけ送り続け、止めるときは stop を
  1 回送って黙る**。S1 の機体のアプリは 0 を 10 Hz で送り続けたので、もう 1 つの送り手と交互に届いて台車がすべった。
  S2 の機体のアプリと `drive.rb` は止まっている間は何も送らない。
  - 確かめ: sim のアプリを止めたまま開いておき、CRuby の試走をすると、sim のアプリが無いときと同じ結果
    (前進 +0.32 %、旋回 +0.30 度。小数 4 桁まで同じ) になった。
  - 2 つが同時に動かすと: CRuby の試走 (直進を 20 Hz) の最中に sim で左の旋回 (0.3 rad/s を 5 Hz) を 3 s 入れると、
    送り手が 35 回入れ替わり、台車は向きを変えながら進み、計算した位置は前進で +2.03 % (本当は 0.980 m)、向きは
    本当 8.87 度に対し計算 3.07 度とずれた。ROS 2 で 2 つの送り手があったときと同じ種類の崩れ方。
- **残した案** (使う人の振る舞いが変わる選択なので、選ばずに書いておく):
  1. 握っている側だけ: `drive.acquire(by:)` で握り、握った側の命令だけ通す。一定時間命令が来なければ放す。
  2. 優先度: 送り手ごとに順位 (例えば console > CRuby > 機体) を付け、上の送り手が命令している間は下を無視する
     (ROS 2 の twist_mux の形)。
  3. 今の形のまま、交代を state に出すだけ (今は `driver` と log に出している)。

### 5.1 速さと負荷 (PC、論理 24 コア)

| 状態 | 毎秒の歩数 | CPU (1 コアに対して) |
|---|---|---|
| `rover.rb --bench 5` (網なし、待たずに `mj_step` を回す。台車は止まっている) | 171,758 (実時間の 344 倍) | 101 % |
| 実時間、制御のたびに poll (毎秒 100 回) | 500.0 (1.0000 倍、10 s ごとの記録 37 回で追いつき 0) | 2.3-4.5 % |
| 実時間、待つ間も 2 ms ごとに poll (毎秒 600 回。今の形) | 500.0 | 3.5-4.6 % |

- `Asterism.poll` 1 回は平均 0.02-0.06 ms。ps で見た RSS は 51 MB。
- 呼び出しの往復 (CRuby、同じ PC、`state.pose` 100 回): poll を毎秒 100 回にしていたときは中央値 10.5 ms (待つ間の
  10 ms に答えが入れない)。待つ間も poll するようにして中央値 2.2 ms、最大 4.8 ms になった。CPU の増え方は 1 % ほど。
- 走っている間と止まっている間で CPU はほぼ変わらない。物理の 1 歩は 6 us 弱 (bench から) で、Fiddle の呼び出しと
  配列の読み書き (1 回の制御で 10 回ほど) を足しても、実時間の 500 歩は 1 コアの数 % に収まる。

### 5.2 操縦とオドメトリ

毎回 `world.reset` から始め、終わったあとに `state.all` を CRuby で読んで比べた。距離は原点からの距離 (その場の旋回は
車軸の中心で回るので距離を変えない)、向きは reset からの角度。

| 送り手 | 動かし方 | 計算した位置 | 本当の位置 | 差 |
|---|---|---|---|---|
| CRuby (`drive.rb`) | 前進 1 m を odom で止める、左に 90 度 | 1.0002 m、90.05 度 | 0.9980 m、89.75 度 | +0.21 %、+0.30 度 |
| CRuby (poll 100 Hz の版) | 同じ | 1.0001 m、90.07 度 | 0.9969 m、89.77 度 | +0.32 %、+0.30 度 |
| sim (`asterism_rover`、sim_input の注入) | 上を 4 回 (0.2 m/s) 5 s、空白。左 2 回 (0.6 rad/s) 2.6 s、空白 | 1.0825 m、94.94 度 | 1.0801 m、94.70 度 | +0.22 %、+0.25 度 |
| sim (1 回目) | 同じ | 1.0760 m、94.42 度 | 1.0739 m、94.17 度 | +0.20 %、+0.25 度 |
| P4-Nano (`asterism_rover`、tab5_input の注入) | 同じ | 1.2524 m、111.80 度 | 1.2497 m、111.51 度 | +0.22 %、+0.29 度 |
| P4-Nano (1 回目) | 同じ | 1.2518 m、112.28 度 | 1.2490 m、111.99 度 | +0.22 %、+0.30 度 |

- 誤差は S1 (ROS 2 の diff_drive_controller、+0.20 %、+0.30 度) と同じ大きさ。加速の上限を Ruby で同じ値にかけたので、
  車輪のすべり方も同じになった。
- CRuby の 2 行の差は、呼び出しが速くなって odom で止める判定が細かくなったぶん (1 回の呼び出し 10 ms から 2 ms)。
- sim と機体はキーの注入の間隔で動かす量が決まる。P4-Nano で多く動いたのは、S1 と同じく tab5_input の 1 キーが
  約 0.5 s かかるため (S1 の報告 3.1 節)。
- 機体のアプリの数字: 1 回目の走りで `drive.cmd` を 46 回 (動いている約 9 s に 200 ms ごと)、`state.all` の答えは
  毎回 55 ms 前後、最大 286 ms。sim では 49-51 ms (更新の周期 50 ms に揃う。答えはすぐ来ていて、次の更新で拾う)。
- 柱の位置 (`world.objects`) は scene.xml のとおり (赤 (2, 0, 0.5)、紫の箱 (1.5, 1.2, 0.2) で 20 度ほか)。IMU は止まって
  いるとき加速度 z が 9.81。

## 6. 見立てと違った点・踏んだ罠

- **構造体の位置は小さい版の差でも動く** (2.3 節)。最初から版を固定して検査する作りにしたので実害は出なかった。
- **mjData の配列の先頭は 16 万バイトの先にある**。mjData は警告・時間・解法の統計を固定長の配列で先頭に持つ。手で数えたら
  まず外す位置で、ヘッダから機械で求めたのは正しかった。
- **`world.reset` で時計が狂った**。最初は MuJoCo の `data.time` で実時間に合わせていたので、reset で時刻が 0 に戻ると
  追いつく処理が働き、その 10 s の報告で「実時間の -4.1 倍」と出た。進めた歩数で時計を持つようにした。
- **待つ間に poll しないと呼び出しが 10 ms かかる**。最初の版は 10 ms の制御のあとにまとめて眠っていたので、往復の
  中央値が 10.5 ms だった。眠る間も 2 ms ごとに poll して 2.2 ms。
- **sim のアプリの最初の 1 回だけ TimeoutError** (「no answer from mujoco/rover/...」がすぐ返る)。つないだ直後の 1 回目の
  呼び出しで起きた。2 回目からは答えが来る。台車のプロセスを起こし直した間 (約 10 s) は、P4-Nano のアプリで 30 回の
  TimeoutError になり、台車が戻るとアプリを起こし直さずに続いた (呼び出し先が居ないときはすぐ失敗し、居れば答える)。
- **console の画面からキーワードを渡せない** (3.2 節)。`by:` を省ける作りにしておいて正解だった。

## 9. S3 への申し送り

- **台車は 2 つある**: S1 の ROS 2 の台車 (docker、カメラあり) と S2 の Ruby の台車 (host、カメラなし)。別々の世界なので、
  S3 で「Tab5 で操縦しながらカメラを見る」なら、どちらか 1 つにそろえる必要がある。案:
  1. S1 の台車を使い、ROS 2 の話題で操縦とカメラ (S1 のとおり。Asterism のオブジェクトは使わない)。
  2. S2 の台車にカメラを足す: MuJoCo の描画 (`mjr_*`、EGL の文脈) を Fiddle で呼ぶ。描画の構造体 (`mjvScene`・`mjrContext`)
     は大きく版への依存も強いので、今の「要る欄だけ読む」形が通じるか調べてからになる。
  3. S2 の台車の状態を S1 の像の中の MuJoCo の Python の部品で描く: 体の位置 (`xpos`・`xquat`) を送って描かせる。
  どれにするかは S3 の指示で決めてほしい。
- **複数の操縦者の決まり** (4 章) が見せ場で効く。Tab5・CRuby・console の再生が同時に動かすなら、握っている側だけ・
  優先度のどちらかが要る。今の形 (最後の命令が勝つ) のままなら、見せる手順で「1 つずつ」を守る。
- **機体の更新の周期で答えを拾う**: P4-Nano の `state.all` は 55 ms 前後 (最大 286-420 ms)。画面に出す値の更新は
  4 Hz で足りている。カメラの画像を同じ呼び出しで運ぶのは重いので、画像はキー (put) にして、機体は最新だけを受ける形がよい。
- **記録は今のままでよい**: 状態のキーは 10 Hz・1 通 400 B ほど。画像を足しても S1 のカメラ (1 枚 2.8 KB、5 Hz) と同じ量。
- **libmujoco の版を上げるとき**は README の「Updating MuJoCo」の 3 手順。表を作り直さずに版だけ上げると開かずに止まる。
