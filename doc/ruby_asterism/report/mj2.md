## 2. ゲームホスト (asterism-games)

### 2.1 待ち合わせの呼び出しと配信

| メソッド | 引数 | 返す値 |
|---|---|---|
| `join` | 名前 | `{"token", "seat" (-1 は席なし), "owner"}` か `{"error" => "full"}` (16 人まで) |
| `mine` | なし | 入っている端末には `join` と同じもの、ほかは nil (何も作らない) |
| `sit` | 合言葉, 席 | `"ok"` か理由。席 -1 は空いた席のどれか。待ち合わせの間だけ。座っている人は移る |
| `stand` | 合言葉 | `"ok"` か理由 (待ち合わせの間だけ) |
| `cpu` | 合言葉, 席, 入れるか | 卓の主だけ。空いた席に CPU を入れる・外す。席 -1 で空いた席を全部埋める |
| `start` | 合言葉 | 卓の主だけ。4 席がそろい 1 人以上が人間のとき。席をくじで並べ替えて (起家を決めて) 始める |
| `view` | 合言葉 | その人の見え方 (座っていない人は手牌なし) |
| `act` | 合言葉, sv, 種類, 牌 | Step 1 と同じ。座っていない人は `"not seated"` |
| `table` | なし | 全員に見せてよい見え方 |
| `leave` | 合言葉 | 待ち合わせでは席が空く、対局中は席が CPU になる |

- 卓に入る (`join`) と合言葉が返る。合言葉は人ごとで、座る・立つ・席を移る間も同じ。手牌は座っている人の合言葉でだけ返る。
- 卓の主は最初に座った人。主が立つか出ると、座っている人のうち最初に座った人に移る。
- 全員に見せてよい見え方 (put と `table`) に、席の種類 `sk` (空き・人・CPU)、途切れている席 `aw`、主の席 `ow`、入っている人の一覧 `mb` (名前・席・途切れ・主) を足した。待ち合わせの画面はこれだけで描ける。put は Step 1 と同じく変わるたびと 5 秒ごと。
- 終局すると、卓の主の「次へ」か `over_seconds` (既定 60 秒) で待ち合わせに戻る。席はそのまま (対局中に出た人の席は CPU のまま) なので、主がもう一度「始める」で次の半荘になる。
- 起動し直し: 入っている人・席・主も `var/state/<卓>.json` に書く (版 2)。待ち合わせの途中でも対局の途中でも続く。起動し直した直後は全員を「今見た」として数える。
- 長く来ない観戦の人 (`away_seconds` の 6 倍) は一覧から消す。座っている人は消さない。

### 2.2 鳴きの割り込みの調停

1. 打牌 (か加槓) でエンジンが `naki_wait` になったら、選べる席 (エンジンの `pending_actions`) の全員から 1 回ずつ答えを集める。CPU はその場でエンジンの打ち手が答える。
2. 人間の席には同じ締め切り (`call_seconds`、既定 8 秒、打牌から数える) を付け、見え方の `dl` に「待っている席のビット・残り ms」を出す。答えた人はビットから外れる。答えは取り消せない (答えたあとの一覧は空)。
3. 締め切りまでに答えなかった人はパス。
4. 全員がそろったら、エンジンの `resolve_pending_action(..., from_seat: 打った席, rule:)` で決める。ロン > ポン・明槓 > チー、同じ優先は打った人の下家から順。ロンが 2 人ならダブロン、3 人なら三家和で流局 (ルールの既定。2.4)。選ばれなかった席はパスとしてエンジンに当てる。
5. 人間が誰も鳴かなかったときは Step 1 と同じく CPU の間 (`cpu_ms`) を置いてから進める。

- 人間に見せる選択肢はエンジンの一覧 (`available_round_actions`) のまま。人間が 2 人以上選べる場面はログに `calls: humans [..] may call` と出し、数を `multi_human_calls` に数える。
- `dl` は Step 1 では `[席, ms]` だったのを `[席のビット, ms]` に変えた (自分の手番も同じ形)。

### 2.3 途切れた人の扱い

- 入っている人がゲームホストを呼ぶたび (`view` など、合言葉がその端末のものであるとき) に「見た」時刻を更新する。卓の画面は 3 秒ごとに `view` を呼ぶので、`away_seconds` (既定 10 秒) 呼ばなければ途切れとみなす。見え方の `aw` と `mb` に印が付き、ログに `away seats [..]` が出る。
- 途切れた席は、戻るまで普通の時間切れで打つ (打牌は `turn_seconds` で自摸切り、鳴きは `call_seconds` でパス)。数を `away_turns`・`away_calls` に数える。
- 戻った端末は `view` を呼んだ時点で印が消え、見え方を取り直して続ける。ページを閉じて開き直した (アプリが起動し直した) 端末は、卓の一覧を出す前に各卓へ `mine` を聞き、入っていた卓に戻る。
- 長く戻らない席を CPU に替える機能は入れていない (11.1 に案)。

### 2.4 ルールの既定 (雀魂に合わせる)

- 既定はゲームホストの `Engine::RULE_DEFAULTS` に置き、卓の設定 `rule:` で上書きできる。riichi_engine の Fork の PR ブランチでは上流の既定値を変えていない (選べる設定を足しただけ)。上流の既定と雀魂が違うものはゲームホストが明示して渡す。
- 項目ごとの表 (雀魂の既定、riichi_engine のどの設定か、選べるか、ゲームホストの既定) は asterism-games の README "Rules" に置いた。要点:

| 項目 | 雀魂の既定 | ゲームホストの既定 | 選べるか |
|---|---|---|---|
| ダブロン | あり | あり (`double_ron: true`) | 選べる (Fork で直した) |
| 三家和 (3 人のロン) | 3 人とも和了 (流局にならない) | **流局** (`triple_ron_draw: true`。ユーザの 2026-10-15 の決定。雀魂と違う) | 選べる (Fork で直した) |
| ダブロンの積み棒・供託 | 放銃者の下家から見て最初の和了者 | 同じ | ゲームホストの点数計算 |
| ダブロンの親 | 和了者に親がいれば連荘 | 同じ (エンジンの `winners`) | エンジンのまま |
| 途中流局 | 九種九牌・四風連打・四開槓・四家立直、親の連荘 | 九種九牌だけ | 他の 3 つはエンジンに無い (MJ-E) |
| 役満の重なり | 重ねる | 重ねる (`multiple_yakuman: true`) | 選べる (Fork に足した) |
| ダブル役満 (四暗刻単騎など) | 2 倍 | 1 倍 | エンジンに無い (`double_yakuman` は使われていない、MJ-E) |
| トビ | あり、0 点は続行 | 同じ | エンジンのまま (0 点未満で終わる) |
| 西入 | 30,000 点未満なら西入、サドンデス、西 4 局で終わり | 同じ (`nishi_iri: true`、30,000) | 選べる。エンジンは西 4 局のあとも西を続けるので、ゲームホストが西 4 局で終える |
| アガリ止め・テンパイ止め | 両方 (ラス親がトップのとき) | エンジンのアガリ止めだけ (テンパイ止めは無い) | 選べない (MJ-E) |
| ウマ | 友人戦は 5-15 (確かでない) | +15/+5/-5/-15 | 選べる |
| 持ち時間 | 1 手 5 秒 + 20 秒の持ち時間 (友人戦) | 1 手 20 秒、鳴き 8 秒 (持ち時間の貯金は無い) | ゲームホストのタイマー |

- 調べた結果に自信の無い項目 (槓ドラの乗る時機、包の範囲、アガリ止めの点の条件、友人戦のウマ) は README の表に「確かでない」と書いた。
- **ユーザの 2 つの決定が食い違う点**: 「三家和は流局」(2026-10-15) と「既定は原則として雀魂に合わせる」。雀魂は 3 人とも和了 (流局にしない) なので、どちらかを選ぶ必要がある。今は個別の決定 (流局) に従い、`rule: { triple_ron_draw: false }` 1 行で雀魂の形になる。決めてほしい (11.3)。

### 2.5 そのほか

- 既定の設定を 2 卓 (`mahjong1`・`mahjong2`) にした。卓ごとに状態のファイルと時間を持ち、互いに関わらない。
- `bin/mahjong-bots`: 画面の無い参加者を N プロセス (1 プロセス 1 接続) で卓に入れ、画面と同じ呼び出し (`join`・`sit`・`view`・`act`) で打つ。2 卓目の確認と負荷の測りに使った。
- 止めるときに、それまでの 1 通の最大をログに出す (`games: largest message N B`)。

## 3. 卓の画面 (flash/app/game/mahjong/mahjong.app.rb)

- 画面は 4 つ: つなぎ中、卓の一覧、待ち合わせ、卓 (対局・観戦)。
- **卓の一覧**: 1 つの購読 `asterism/*/games/*/state` で全部の卓の put を受け、卓ごとに「待ち合わせ / 対局中 / 終局、人・CPU・空きの数、卓にいる人数」を出す。上下と Enter かクリックで入る。開いたときと、一覧を出している間 15 秒ごとに各卓へ `mine` を聞き、入っている卓があればそこへ戻る (アプリの起動し直し・ページの開き直し)。
- **待ち合わせ**: 4 席の行 (席の番号、名前か「空き」、卓の主、途切れ) と、席ごとのボタン (座る n・立つ S、主には CPU・空ける)、観戦している人の一覧、主には「CPU で埋める C」「始める Enter」、全員に「卓を出る Esc」。キーは 1-4 で座る、s で立つ、c で埋める (主)、Enter で始める (主)、Esc で出る。
- **卓**: Step 1 の配置のまま。途切れた席の名前に「(途切れ)」を橙で出す (赤は卓の緑の上で読めなかったので 0xF4)。席の名前は、点数と印が収まるように長い名前を詰める (左と対面の名前は同じ行に並ぶため)。鳴きの場面で自分が答えたあと (か、自分には選択肢が無いとき) に「ほかの人の答えを待っています」。自分の残り秒は `dl` のビットに自分が入っているときだけ出す。
- **観戦**: 座っていない人は卓を見るだけ (手牌なし、ボタンは「卓を出る Esc」だけ)。席 0 を下に置いた向き。
- **局の結果**: ダブロンは和了者ごとに 1 区画 (和了者・放銃者・手牌と和了牌・役・符と翻と点) を打った人の下家から順に並べ、箱を縦に広げる (640x360 で 270 px)。三家和は「三家和で流局」。終局の箱に「次へ: 卓の主が待ち合わせに戻す」。
- 小さい画面 (sim の 426x240) の一覧・待ち合わせは同じ部品を詰めて並べる。
- picoruby で踏んだもの: `Integer#zero?` が無い (卓の一覧で Enter を押すとアプリが落ちた)。`n == 0` に直した。

## 4. riichi_engine の Fork

ユーザの決定 (2026-10-15): ダブロンを既定で有効に、三家和は流局、役満の重なりは設定で選べるように。Step 1 と同じ形 (上流の main から機能ごとにブランチ 1 本・コミット 1 つ、spec と PR の下書き、`fmrb` に merge) にした。

| ブランチ | 中身 | spec |
|---|---|---|
| `fix/multiple-ron` | `double_ron`・`triple_ron_draw` が効いていなかった。`resolve_pending_action` (と `ActionResolver.resolve`) に任意の `rule:` を足し、渡したときにロンが 2 人以上なら、3 人で `triple_ron_draw` なら `{type: :sanchahou, seats:}`、そうでなく `double_ron` なら `{type: :ron_agari, seat:, seats:}` を返す。`apply_round_action` は両方を受け (`winners` は打った人の下家から順、和了ごとにイベント 1 つ)、`:sanchahou` は途中流局で `GameFlow` が親の連荘・本場 1 つ増し。文書にダブロンの点数の求め方 (積み棒・供託は先頭の和了者だけ) を書いた | 14 (resolver 5、round_flow 6、game_flow 3) |
| `feat/multiple-yakuman` | 新しいキー `multiple_yakuman` (既定 `false` で 0.1.0 のまま)。真なら役満の数だけ基本点を倍にし、段階の表示は「2倍役満」。数え役満には効かない。既存の `double_yakuman` (四暗刻単騎などの 2 倍を指すとも読める、使われていない) とは別にした | 5 (新しい spec 2、score_calculator 2、rule_config 1) |

- 名前: 上流のキーは英語 (`double_ron`・`triple_ron_draw`・`kiriage_mangan`) とローマ字 (`kuitan`・`nishi_iri`) が混ざる。英語の並びに合わせて `multiple_yakuman` にした。
- `fmrb` (`0.1.1.fmrb2`): 2 本を merge。`fix/ron-turn-order` と同じ `resolve` を触るので、引数を両方持たせ (`from_seat:, rule:`)、ロンの席を打った人の下家から順に並べた。spec は 362 件すべて通る。
- Python の `mahjong` との突き合わせを `multiple_yakuman: true` で回すようにした: 乱数 10,000 x seed 1-3 と代表 61 で、食い違い 0、決まりの違い 0 (Step 1 では役満の重なりが決まりの違いとして 3-4 件ずつ残っていた)。`MULTIPLE_YAKUMAN=0` で既定の値でも回せる。
- PR の下書きは日本語 (`pr_drafts/fix-multiple-ron.md`・`pr_drafts/feat-multiple-yakuman.md`)。上流のコミットのメッセージは英語なので、コミットは英語にした。索引 (`pr_drafts/README.md`) に、既存の 15 本の英語の下書きは送る前に日本語に書き直すと書いた。
- 遊ぶ流れを止める誤りは、このステップでは見つからなかった (直したのはユーザの決定による 2 本だけ)。

### 5.1 ブラウザ版 4 つでの半荘

- 構成: 親リポジトリの `docker compose -f docker-compose.yml -f docker/asterism/docker-compose.zenoh-ws.yml up -d zenohd`、ゲームホスト (`config/example.yml`、`MAHJONG_TURN_SECONDS=15`・`MAHJONG_CALL_SECONDS=6`・`MAHJONG_CPU_MS=300`・`MAHJONG_RESULT_SECONDS=5`)、`rake wasm:serve` のブラウザ版。
- ブラウザ 4 つは Playwright の container (G2 Step 2 と同じ image) の中の Chromium で、ページごとに別の context (別のノード ID)。MCP の `web_*` と `tools/fmrb_web.rb` は 1 ページを駆る作りなので使わなかった。Docker Desktop の container からはページの `localhost` が WSL に届かないため、container の中で `localhost:8006` (開発サーバ) と `localhost:7449` (zenohd の ws) を中継する小さな node のスクリプトを置いた (ページから見るとループバックのままなので、isolation と `ws://` の扱いは手元のブラウザと同じ)。スクリプトは公開しない (作業用の場所に置いた)。
- 操作はキーだけ (画面と同じ口)。どのページのキーを押すかは、ゲームホストが書き出した状態のファイルから「手番の席・鳴きを選べる席」を読んで決めた。打牌は Enter (自摸切り) の前に t (ツモ) と、3 割で r (リーチ)。鳴きは 1.5 秒待ってから t (ロン)、45% で p、30% で c、最後に Esc (パス)。
- 流れ: 4 つのページが一覧から `mahjong1` に入り、1-4 で座る (1 つ目が卓の主)、主が Enter で始める。半荘は東 1 局から西 4 局まで 12 局 (全部流局、うち 2 局は聴牌料の移動あり、本場は 11 まで積んだ)。誰も 30,000 点に届かないので西入し、西 4 局で終わった (2.4)。終局の画面は順位・点・ポイント、主の Enter で待ち合わせに戻り、4 人とも席に残っていた。所要 26 分。
- 自摸切りだけの打ち方では和了が出ない。和了の画面は Step 1 で見ており、今回はダブロン・三家和の場面を作って見た (5.2)。
- 操作から画面まで (卓の画面が出す「応答」): 1,078 回、中央値 60 ms、95% 366 ms、最大 582 ms。4 つの wasm を 1 台の PC の container で同時に動かしているので、Step 1 (62-78 ms) より裾が長い。

### 5.2 鳴きの割り込み

- 半荘の中で、2 人以上の人間が同時に選べる場面は 4 回 (ゲームホストのログ)。たとえば西 2 局では、下家にチー (5s6s)、対面にポンが同時に出て、2 人の画面に同じ残り秒 (5 秒) が出た (`s2_web_calls_pon_and_chi_four_screens.png`、4 人の画面を並べたもの)。どの場面も 2 人の答え (か締め切り) のあとで決まった。半荘の中でチーとポンが実際に成立している (鳴いた牌が卓の右下と各席に出ている)。
- ダブロン: 4 つのページを卓に座らせたあと、ゲームホストを止めて状態のファイルを書き換え (ある席の自摸が 8s、ほかの 2 席が 8s で和了れる手)、起動し直して打った。2 人に「ロン T」が出て、1 人目が答えると「ほかの人の答えを待っています」、2 人目が答えると両方の和了 (平和・断么九、30 符 2 翻 2000 点 x 2、放銃者 -4000) が 1 つの箱に並んだ。
- 三家和: 同じ形で 3 人がロンし、「三家和で流局」(点の移動なし)。
- ダブロンの点数・積み棒と供託・親の連荘・ルールを切ったときの頭はねと 3 人の和了は試験で確かめた (5.5)。

### 5.4 2 卓の同時と、ゲームホストの CPU とメモリ

- 5.1 の半荘の間ずっと、`mahjong2` で `bin/mahjong-bots` の 4 人が半荘を 3 回打った (思考 800 ms)。2 卓は互いに関わらず進んだ。
- その間のゲームホスト (CRuby 3.2、1 プロセス): CPU は 1 コアの 1-2% (10 秒ごとの値)、RSS は 56 MB から 59 MB。
- 負荷を上げた測り: 2 卓ともボット 4 人 (思考 300 ms、CPU の間 300 ms) で半荘を同時に打った (約 4 分で 2 卓とも終局)。

| 状態 | CPU (1 コアに対する割合、30 秒ごと) | RSS |
|---|---|---|
| 誰もいない 2 卓 | 1.1% | 54.8 MB |
| 2 卓とも 4 人が打っている | 3.6-8.1% (8 回の平均 6.6%) | 58.5-59.2 MB (最大 59.2 MB) |

- CPU の大半はエンジン (手の一覧と和了の判定) と MessagePack。VPS (2 GB) で卓 2-3 つという見込み (game_rooms_comparison.md 6 章) に対して、メモリは卓の数ではほとんど増えない (1 プロセス約 60 MB)。

### 5.5 大きさ・見せる範囲・断ること・起動し直し (試験)

- 1 通の最大: CPU 4 人の半荘 20 回で 566 B、人間 4 人の半荘で 509 B (どちらも呼び出しの答えとキー)。手で作った最悪の場合 (河 24 枚 x 4、加槓 4 組 x 4、32 バイトの名前で 16 人の一覧、3 人の和了に役 14 個ずつ、終局の順位) で 1,926 B。どれも試験の上限 3,800 B の下。実際に動かしたゲームホストのログの最大は 510 B。
- 他人の手牌が入らない: 人間 4 人の半荘 (画面と同じく `act` で打つ。和了はもらう、時々鳴く、時々一覧にない操作を送る) で、毎回の手のあとに 4 席の見え方を調べ、自分の手牌だけがあり他の席の手牌のキーが無いことを確かめた (23,331 回の確かめ)。観戦の人の見え方に手牌が無いことも試験にした。
- 一覧にない操作: 上の半荘で一覧にないロンを 51 回送り、すべて `"not offered"`。座っていない人の `act` は `"not seated"`、合言葉の誤りは Step 1 と同じく断る。
- 起動し直し: 局の途中と待ち合わせの途中で書き出して読み戻し、同じ見え方・同じ主・同じ合言葉で続くことを試験で確かめた。実際にもダブロンの確かめでゲームホストを 3 回止めて起動し直し、4 つのページが卓に戻った。

## 10. ローカル役満などの設定の口 (見立て)

- 役の判定は riichi_engine の `YakuJudge` の `YAKUMAN_CHECKERS`・`REGULAR_CHECKERS` (役ごとのモジュールの並び) で、各役は `check(ctx)` を持つ。ローカル役満は、この並びにモジュールを足し、`RuleConfig` のキー (例 `local_yaku: ["daisharin", ...]`) で有効なものだけを並びに入れる形が上流の作りに沿う。`YakuContext` に `rule` が入っているので、役の側でルールを見ることもできる。
- 点数の段階 (ダブル役満の 2 倍など) は `ScoreCalculator` の `yakuman_count` (今回足した) を役ごとの倍率の和に広げると入る (`YakuEntry` の `han: -1` を `-2` で 2 倍、のような印)。`double_yakuman` をその意味で実装するのが自然。
- ゲームホストの側は、卓の `rule:` (と Step 3 の設定の画面) から `RuleConfig` に渡すだけで、変える所は無い。

## 11. 残件と決めてほしいこと

### 11.1 案: 長く戻らない席を CPU に替えるか

- 案 B: 途切れが N 分続いたら CPU が打つ (席は人のまま、戻れば人に戻る)。
- 案 C: 何もしない (今のまま)。遊び方の選択なので決めてほしい。勧めるなら A (作りが小さく、戻ったときの扱いが今と同じ)。
