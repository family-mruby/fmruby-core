## 2. extconf の動き

zenoh-c をどこから持ってくるかは次の順に決まる。

1. `ZENOH_C_DIR` (または `gem install asterism-zenoh -- --with-zenoh-c-dir=DIR`) があれば、その `include/` と `lib/` を使う。何も取らない。
2. 無ければ、`ZENOH_C_PIN` からその機械の zip の名前と sha256 を引き、`<repo>/releases/download/<tag>/<asset>` から取る。
3. 取れないとき、対応しない機械のときは、何をすればよいかを書いて止まる。

取得と確認は `ext/asterism_zenoh/zenoh_c.rb` にまとめた。extconf と Rakefile の `zenoh_c:fetch` が同じものを使う。

- 機械の見分け: `RbConfig::CONFIG` の `host_cpu` と `host_os` から `x86_64-linux`、`aarch64-linux`、`x86_64-linux-musl`、`aarch64-linux-musl`、`x86_64-darwin`、`aarch64-darwin` のどれかを決める (`arm64` も `aarch64` に寄せる)。
- 取得: net/http。リダイレクトは 10 回まで追う (GitHub のリリースは別のホストへ飛ばす)。プロキシは `http_proxy` などの普通の環境変数が効く (net/http の既定)。
- 取る先の差し替え: `ASTERISM_ZENOH_C_MIRROR=<base>` で `<base>/<tag>/<asset>` を取る。http(s)、`file://`、手元のディレクトリのどれでもよい。ネットに出られない機械にも使える。
- 確認: 取った zip 全体の sha256 を `ZENOH_C_PIN` の値と比べる。違えば使わずに止まる。展開のときは各ファイルの CRC-32 と大きさも見る。
- 展開: Ruby の zlib で zip の中央ディレクトリを読み、`include/` と共有ライブラリ (`lib/libzenohc.so` か `.dylib`) だけを出す。静的ライブラリ (`libzenohc.a`、40 MB 前後) は出さない。unzip、curl、git は使わない。
- 置き場所: `make install` が拡張の隣 (入った gem の `lib/asterism/`) に共有ライブラリを置き、`lib/asterism/zenoh-c/` に Apache License 2.0 の本文、zenoh-c の NOTICE.md、`SOURCE` (どの zip を、どの sha256 で取ったか) を置く。拡張は rpath (Linux は `$ORIGIN`、macOS は `@loader_path`) で共有ライブラリを見つける。
- 後片付け: RubyGems は `make clean` を 2 回呼ぶ (ビルドの前と、入れた後)。取ってきた zenoh-c を 2 回目でだけ消すように、入れたときに印のファイルを作り、`clean` はその印があるときだけ消す。zip は一時ディレクトリに置くので残らない。`ZENOH_C_DIR` で渡したものには触らない。
- macOS: 公式の dylib は自分の名前 (install name) をビルドした CI の絶対パス (`/Users/runner/work/...`) で持っている。そのままつなぐと拡張がそのパスを探しに行くので、つないだ直後に `install_name_tool -change` で `@rpath/libzenohc.dylib` に書き換え、`codesign --force --sign -` で署名し直す。zenoh-c の dylib そのものは書き換えない (sha256 で確かめたものをそのまま置く)。

止まるときの表示 (実際に出たもの):

```
asterism-zenoh: cannot download https://github.com/eclipse-zenoh/zenoh-c/releases/download/1.10.1/zenoh-c-1.10.1-x86_64-unknown-linux-gnu-standalone.zip: Failed to open TCP connection to github.com:443 (getaddrinfo: Temporary failure in name resolution) (Socket::ResolutionError)
Point the build at a zenoh-c of your own (its include/ and lib/, release 1.10.1):
  ZENOH_C_DIR=/path/to/zenoh-c gem install asterism-zenoh
  (or: gem install asterism-zenoh -- --with-zenoh-c-dir=/path/to/zenoh-c)
Prebuilt zenoh-c releases: https://github.com/eclipse-zenoh/zenoh-c/releases/tag/1.10.1
To download from a mirror instead: ASTERISM_ZENOH_C_MIRROR=<base> (fetches <base>/1.10.1/<asset>).
```

対応しない機械では 1 行目が `no prebuilt zenoh-c is pinned for this machine (arm-linux-eabihf); pinned: x86_64-linux, aarch64-linux, x86_64-linux-musl, aarch64-linux-musl, x86_64-darwin, aarch64-darwin.` になり、sha256 が違うときは `sha256 mismatch for <asset>: got ..., pinned ... (ZENOH_C_PIN). Not using it.` になる。続く案内は同じ。

## 3. zenoh-c の配り方 (想定どおりだった)

- zenoh-c 1.10.1 のリリースには機種ごとの `zenoh-c-1.10.1-<triple>-standalone.zip` がある (Linux は gnu と musl の x86_64 / aarch64 / arm / armv7、macOS は x86_64 / aarch64、Windows は gnu と msvc)。ほかに Debian の包み (`libzenohc-...-debian.zip`) がある。
- 6 つの zip を取って sha256 を自分で計算し、GitHub の API が出す各資産の digest と一致することを確かめてから `ZENOH_C_PIN` に書いた。
- どの zip も中身は `include/` と `lib/` (共有ライブラリ、静的ライブラリ、cmake、pkgconfig) だけで、LICENSE も NOTICE.md も入っていない (C3 で x86_64 の zip について見たのと同じ)。だから gem に `licenses/zenoh-c/LICENSE-APACHE` (Apache License 2.0 の全文。C3 の picoruby-asterism-zenoh の LICENSE-APACHE と同じもの、sha256 `cfc7749b...`) と `licenses/zenoh-c/NOTICE.md` (zenoh-c のタグ 1.10.1 の NOTICE.md をそのまま) を入れた。
- Linux の gnu 版の `libzenohc.so` は glibc 2.34 以上を要る (x86_64 で確かめた)。Debian 12 の Ruby の像 (glibc 2.36) は満たす。古い glibc の機械では読み込みで落ちる。
- 32 ビットの arm (armv7 など) と Windows は zip があるが、確かめる手が無いので今回は載せなかった。

## 8. 見立てと違った点・踏んだ罠

- **macOS の dylib の install name**: 公式の dylib は CI の絶対パスを自分の名前に持つ。rpath を足すだけでは足りない (2 章で書き換えた)。確かめていないので、ここが macOS で最初に疑う所になる。
- **RubyGems は `make clean` をビルドの前にも呼ぶ**: 取ってきた zenoh-c を `clean` で消すだけにすると、ビルドの前に消えてつなげなくなる。印のファイルで 2 回目だけ消すようにした。
- **拡張は 2 か所に入る**: RubyGems の既定で `lib` と `extensions` の両方に写るので、共有ライブラリ (17 MB) も 2 つになる。gem の側で避ける手は無い。
- **`docker run --platform` は手元の像の名前を付け替える**: arm64 や armv7 の像を取ると `ruby:3.3` がそちらを指すので、終わりに amd64 の像を取り直した。
- 確かめるための仕掛け (docker の中で zenoh-c が前もって無いかを見る `find`) が、作業用に置いた手元の zenoh-c を拾って止まったことがある。仕掛けの側の誤りで、gem の問題ではない。

## 9. 公開の前に親とユーザが決めること

1. **版**: 2 つとも 0.1.0 にした (`.pre` なし)。最初の公開を `0.1.0` にするか、`0.1.0.pre1` などで試してから `0.1.0` にするか。rubygems.org は同じ版を出し直せない (yank しても同じ版の番号は二度と使えない) ので、macOS が未確認のまま `0.1.0` を出すと、直しは `0.1.1` になる。
2. **公開の順番**: `asterism` は `asterism-zenoh = 0.1.0` に依存するので、**先に asterism-zenoh、次に asterism**。その前にリポジトリの push (asterism-zenoh `db3c4a9`、asterism `b6d1776`) を済ませ、gemspec の `source_code_uri` の先が見える状態にしておく。gem のファイルは push したコミットから `rake gem` で作り直す。
3. **名前**: `asterism` は 0.0.0 で確保してある (C1 の 9 章)。`asterism-zenoh` は確保していない。公開の前に空いているか見る。
4. **yank の方針**: 壊れた版を出したとき yank するか、次の版で直すだけにするか。依存の形 (`= 0.1.0` の固定) なので、asterism-zenoh だけを yank すると asterism の同じ版が入らなくなる。直すなら 2 つをそろえて次の版を出すのが素直。
5. **依存の固定の幅**: 今は `asterism-zenoh = 版` (同じ版だけ)。片方だけ直すたびに両方の版を上げることになる。`~> 0.1.0` に緩めるかどうか。
6. **macOS の確認**: 出す前に macOS (arm64 が先) で一度入れてもらうか、未確認と README に書いて出すか。
7. **MFA**: gemspec に `rubygems_mfa_required = "true"` を入れた。公開する側のアカウントで MFA が有効である必要がある。
8. **プラットフォームごとのビルド済み gem**: 今回は「入れるときに C をコンパイルする」形だけ。C コンパイラの無い利用者向けに機種ごとの gem を出すなら、zenoh-c を同梱することになり、README の「配布の注意」のとおり Rust の crate の表示の一覧が要る。
9. **glibc の下限**: Linux の gnu 版は glibc 2.34 以上 (Debian 12、Ubuntu 22.04 以降)。それより古い機械を README で断るかどうか (今は書いていない)。
