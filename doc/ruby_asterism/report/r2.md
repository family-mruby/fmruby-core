## 2. 観察したワイヤの形 (rmw_zenoh_cpp 0.2.11)

観察の方法: docker の中で `add_two_ints_server` と `ros2 service call` を走らせ、別のコンテナの zenoh-python
(R1 と同じ使い捨ての像 `zenoh-py-obs:local`、eclipse-zenoh 1.10.1) から、(1) liveliness の取得でトークンを、
(2) クライアントになって `add_two_ints_server` に get を送って答えを、(3) サーバになって (SS のトークンと
queryable を出して) `ros2 service call` の問い合わせを、それぞれ生のバイトで見た。get の設定は rmw_zenoh 0.2.11 の
`rmw_client_data.cpp`・`rmw_service_data.cpp` で確かめた。

| 項目 | 観察した形 | 例 (AddTwoInts、ドメイン 0、/add_two_ints) |
|---|---|---|
| サービスのキー | `<ドメイン>/<サービス名 (先頭と末尾の / を除く)>/<DDS の型名>/<型のハッシュ>` (トピックと同じ形) | `0/add_two_ints/example_interfaces::srv::dds_::AddTwoInts_/RIHS01_e118de6b...` |
| 型名 | サービスの型名 (`<パッケージ>::srv::dds_::<型>_`)。Request_ / Response_ の接尾辞は付かない (rmw_zenoh が Response_ を削っている) | `example_interfaces::srv::dds_::AddTwoInts_` |
| 型のハッシュ | **サービスの型のハッシュ** (要求・応答の型のハッシュではない)。`share/example_interfaces/srv/AddTwoInts.json` の最初の `RIHS01_` と同じ | `RIHS01_e118de6bf5eeb66a2491b5bda11202e7b68f198d6f67922cf30364858239c81a` |
| 要求の CDR | ヘッダ `00 01 00 00` + int64 a + int64 b (リトルエンディアン) | `{a: 40, b: 2}` -> `00010000 2800000000000000 0200000000000000` |
| 応答の CDR | ヘッダ + int64 sum | `sum=5` -> `00010000 0500000000000000` |
| 問い合わせの attachment | トピックと同じ 33 バイト: int64 通し番号 + int64 時刻 (ns) + GID の長さ 1 バイト (16) + GID 16 バイト。通し番号はクライアントごとに **1 から** | `0100000000000000 e971e66e4d33dc18 10 c461bed6...391ec024` |
| 答えの attachment | 同じ 33 バイト。**通し番号と GID は要求のもの (クライアントのもの) をそのまま返す**。時刻はサーバが答えた時刻 | 要求 `07.. 6047ca03.. 10 000102..0f` -> 答え `07.. 0da8d603.. 10 000102..0f` |
| 組み合わせ | クライアントは答えの通し番号で要求と組にする。サーバは (GID, 通し番号) で問い合わせを覚えておいて答える | - |
| 答えのキー | サーバのサービスのキー (問い合わせのキーと同じ) | - |
| get の設定 | target は `ALL_COMPLETE`、consolidation は `NONE`、時間制限は既定 (10 秒。アクションの get_result だけ無制限)。parameters は空。rmw_zenoh は get を querier で出す (ワイヤでは同じ問い合わせ) | - |
| queryable | `complete = true` で宣言する | - |
| 符号化 | `zenoh/bytes` (既定のまま) | - |
| サーバのトークン | `@ros2_lv/<ドメイン>/<zid>/<nid>/<id>/SS/<enclave>/<名前空間>/<ノード名>/<サービス名>/<型名>/<型のハッシュ>/<QoS>` | `@ros2_lv/0/8681e335.../0/11/SS/%/%/add_two_ints_server/%add_two_ints/example_interfaces::srv::dds_::AddTwoInts_/RIHS01_e118.../::,10:,:,:,,` |
| クライアントのトークン | 同じ形で `SC` | `@ros2_lv/0/e4077712.../0/10/SC/%/%/_ros2cli_requester_example_interfaces_AddTwoInts/%add_two_ints_obs/...` |
| QoS | サービスの既定は `::,10:,:,:,,` (トピックの既定と同じ)。パラメータのサービスは `::,1000:,:,:,,` | - |

- **complete でない queryable には ALL_COMPLETE の問い合わせが届かない**。zenoh-python で `complete=False` の
  queryable と SS のトークンを出すと、`ros2 service call` は問い合わせを 1 件も届けられずに待ち続けた (8 秒で打ち
  切った)。`complete=True` では届いて答えられた。gem に `complete:` を足したのはこのため。
- `ros2 service call` は SS のトークンでサービスがあることを確かめてから呼ぶ (R1 の `ros2 topic pub` と同じ)。
- `ros2 service list` はクライアントしかいない名前も出す (機体のクライアントの `/add_two_ints` が、PC のサーバを
  止めた後も機体が動いている間は出る)。

## 3. 作ったもの

### 3.1 Asterism::Zenoh (足しただけ)

| 呼び出し | 内容 |
|---|---|
| `session.get(key, timeout_ms = 2000, params = nil, payload = nil, attachment: nil, target: :all, consolidation: :none)` | `target:` は `:all` (既定、今までどおり)・`:all_complete`・`:best_matching`。`consolidation:` は `:none` (既定)・`:latest`・`:monotonic`・`:auto` |
| `get.each_reply { \|key, payload, attachment\| }` | 3 つ目は答えの attachment (無ければ nil)。ブロック無しなら `[[key, payload, attachment], ...]` |
| `session.queryable(key, depth = 16, complete: false)` | `complete: true` で ALL_COMPLETE の問い合わせを受ける |
| `q.attachment` | 問い合わせの attachment (無いか空なら nil) |
| `q.reply(payload, attachment: nil)` / `q.reply(key, payload, attachment: nil)` | 答えに attachment を付ける |

- 答えの attachment は、R1 の購読と同じく、キーと payload と同じ 1 つのバッファ (z_malloc、P4 では PSRAM) の後ろに
  置く。輪の枠は R1 で既に大きくしてあったので、構造体は変えていない。
- `each_reply` が 3 つの値を返すようになったが、既存の呼び出し (asterism.rb の `Future`、zenoh_nodes) は 2 つで
  受けるか `[i][1]` で取るので、変更は要らなかった。
- 既定の動き (target ALL、consolidation なし、complete でない queryable) は変えていない。

### 3.2 Asterism::ROS (純 Ruby、ros.rb に足した)

API は picoruby-asterism の README の「ROS 2」の節。要点:

```ruby
add = Asterism::ROS::ExampleInterfaces::AddTwoInts
node.service("/fmruby/add_two_ints", add) { |req| { sum: req.a + req.b } }
cli = node.client("/add_two_ints", add)
node.poll                         # session.poll + サービスへの要求に答える
cli.call(a: 2, b: 3).sum          # 待つ (時間切れは Asterism::ROS::Timeout)
c = cli.call_async(a: 2, b: 3)    # 待たない。c.done? / c.value / c.took_ms
node.call("/add_two_ints", add, a: 1, b: 2)   # 名前ごとにクライアントを作って使い回す
```

| 呼び出し | 内容 |
|---|---|
| `node.service(name, type, qos:, depth: 8) { \|req\| ... }` | complete な queryable と SS のトークン。ブロックは `type::Request` を受け、`type::Response` か Hash を返す。ブロックが走るのは `node.poll` (または `service.handle_pending`) の中だけ |
| `node.poll(steps = 8)` | `session.poll` の後、届いた要求に答える。`session.poll` の値を返す |
| `node.client(name, type, qos:)` | SC のトークン |
| `client.call(request = nil, timeout_ms: 2000, **fields)` | 要求は `type::Request`、Hash、またはキーワード。答えまで `node.poll` を回して待つ (待っている間も自分のサービスは答える)。時間切れは `Asterism::ROS::Timeout`、相手がいないときはすぐに `Timeout` (理由に "nobody serves it")、セッションが閉じたら `Asterism::Zenoh::Error` |
| `client.call_async(...)` | `Call` を返す。`done?` は待たない (`node.poll` が進める)、`value` は待って答えを返すか `call` と同じく例外、`response`・`took_ms`・`sequence` |
| `node.call(name, type, request = nil, timeout_ms:, **fields)` | design.md 6 章の案。型は明示 (liveliness からの型の判定はしない) |
| `ExampleInterfaces::AddTwoInts` | `TYPE_NAME`・`TYPE_HASH` (定数) と `Request` (`a`, `b`) / `Response` (`sum`)。それぞれ `new(**fields)`・`encode`・`decode`・`to_h` |

- サーバの決まり: attachment の無い要求と、CDR として読めない要求は答えずに終える (`service.errors` に数える)。
  rmw_zenoh のサーバと同じく、attachment の無い要求は相手にしない。ブロックが例外を出したら、その要求は答えずに
  終え、例外を `node.poll` から出す (黙って捨てない)。同じ回に届いた残りの要求も、答えずに終える。
- クライアントの決まり: 通し番号は 1 から。答えは attachment の通し番号が自分の要求と同じものだけを取る (サーバが
  複数いて余計な答えが来ても混ざらない)。GID は R1 と同じく、トークンのキーから作る 16 バイト。
- 待つ形は A1 の `Asterism.wait_until` と同じ作り (2 ms 休みながら `node.poll`)。答えはブロックではなく配列で
  受け取り、C から Ruby のブロックを呼ぶ段を増やさない (スタックのため)。時計と休みは `Asterism.now_ms` /
  `Asterism.pause` を使う (オブジェクトの層の接続には依存しない)。
- 「相手がいない」の見分け: get が時間制限の前に終わり、答えが無かったとき。ルータが問い合わせの行き先が無いことを
  すぐに返すので、相手がいないときは数十 ms で `Timeout` になる。

### 3.3 ros2_service

- 接続と ID は ros2_talker と同じ (`/home/zenoh_echo.txt`、`/home/asterism_node.txt`、mDNS 名、`linux`)。
  ノード名は `fmruby_service_<ID>`。
- `/fmruby_service_<ID>/add_two_ints` を提供し、届いた要求と答えを画面とログに出す。
- キー c: PC の `/add_two_ints` を `a = N, b = 10N` で呼んで待つ。キー a: `a = N, b = 100` で待たずに呼び、後の更新で
  答えを拾う。キー n: `node.call` で `a = N, b = -1`。いずれも和と往復の時間を出す。
- キーは on_event で覚えておくだけにし、呼び出しは on_update でする (asterism_demo と同じ。待つ呼び出しのスタック)。

## 5. 呼び出しの往復の時間

| 向き | 構成 | 回数 | 時間 |
|---|---|---|---|
| 機体 -> PC (`client.call`、待つ形) | P4-Nano (WiFi) -> zenohd -> `add_two_ints_server` | 13 | 18-216 ms、中央値 49 ms (18, 20, 21, 36, 38, 42, 49, 52, 53, 65, 66, 79, 216 ms)。`node.call` の 2 回は 51 ms と 37 ms |
| 機体 -> PC (`call_async`) | 同上 | 3 | 89-90 ms (答えを拾うのは次の更新 = 50 ms ごと) |
| 機体 -> PC (`client.call`) | sim -> zenohd (同じ PC の中) | 2 | 3 ms |
| PC -> 機体 | zenoh-python から機体のサービスへ get (rmw_zenoh と同じ attachment と設定) | 20 | P4-Nano: 中央値 99.7 ms (41.8-166.5)。sim: 中央値 51.5 ms (50.7-52.8) |

- PC -> 機体は、要求が届いてから次の更新 (アプリは 50 ms ごとに `node.poll`) まで待つので、sim でもほぼ 50 ms に
  なる。ポーリングの設計どおりの値で、早く答えたいアプリは更新の間隔を縮めるか、`node.poll` を更新の中で何度か
  呼ぶ。P4-Nano はこれに WiFi の往復 (数十 ms、ばらつきあり) が足される。
- 機体 -> PC の待つ形は、待っている間 2 ms ごとに poll するので、更新の間隔の影響を受けない。
- 計り方: 機体 -> PC はアプリの `Machine.board_millis` の差 (ログと画面)。PC -> 機体は zenoh-python の get の
  前後の時刻 (`ros2 service call` は起動の時間が混ざるので使わなかった)。どちらの答えも和、通し番号、GID が正しい
  ことを確かめた。

## 6. 見立てと違った点・撤回した仮説・踏んだ罠

- **zenoh-pico 1.10.1 で足りた**。instruction の止まる条件 (版を上げる必要) には当たらなかった。
- **型のハッシュはサービスの型のもの**。要求・応答の型のハッシュではない。`AddTwoInts.json` には 6 つの `RIHS01_` が
  あり、最初のもの (サービス) がキーとトークンに使われる。
- **complete の指定が要る** (2 章)。get の target を ALL_COMPLETE にしたクライアントは、complete でない queryable を
  無視する。gem の既定 (complete でない) のままではサービスにならない。
- **答えの GID はクライアントのもの**。答えの attachment の GID をサーバの GID だと見立てていたが、rmw_zenoh は要求の
  GID (クライアントのもの) をそのまま返す。通し番号も要求のもの。
- **観察用のコンテナが終わらない**: zenoh-python で問い合わせを抱えたまま (答えずに) 持っていると、`time.sleep` の
  後の終了で固まって残った (R1 の liveliness_get の件と同じ種類)。`docker rm -f` で消した。2 回目の答えないサーバの
  確かめで、残っていた 1 回目のものが新しいルータにつなぎ直していたのに気づいた (そのときの結果は「答えない
  サーバがいる」ときのものとして扱った。PC のサーバと答えないサーバが両方いるときも、機体は正しい答えを取れた)。
- **`ros2 service call` は相手が答えないと終わらない**。`timeout` で囲んでも止まらないことがあった (`pkill` で止めた)。
- **`ros2 service list` はクライアントだけの名前も出す** (2 章)。条件 3 の「消える」は、機体のサービスとクライアント
  の名前の両方が消えることで確かめた。

撤回した仮説: 答えの attachment の GID はサーバのもの (上記)。

## 7. 大きさと内蔵 RAM (P4-Nano、NARYAv4)

### 7.1 flash と静的な領域

同じ日の同じ手順 (`FMRB_HW_TARGET=NARYAv4 rake build:esp32`。develop (ace208f9) は `rake clean_all` の後、R2 は
`rake clean` の後) で比べた。develop の値は R1 の報告の R1 (c9b0cdc7) と一致した (コードは同じ)。

| | fmruby-core.bin | 区画 (0x700000) の残り | .iram0.text | .dram0.data | .dram0.bss | .flash.text | .flash.rodata |
|---|---|---|---|---|---|---|---|
| develop | 0x628930 | 0xd76d0 (882,384 B、12%) | 85,300 | 14,916 | 25,396 | 3,600,506 | 2,753,008 |
| R2 | 0x62abd0 (+8,864 B) | 0xd5430 (873,520 B、12%) | 85,300 | 14,916 | 25,396 | 3,601,690 (+1,184) | 2,760,680 (+7,672) |

増分のほとんどは ros.rb のバイトコード (.rodata)。C の増分 (attachment・target・complete) は .text の +1,184 B。

### 7.2 起動時

P4-Nano に入っていた R1 のファーム (コードは develop と同じ) の起動と、R2 を `flash` (app_only) で焼いた直後の起動の
`M1|` 24 行を比べた。

- `boot_start` から `spawn:Services` までの 19 行はすべて同じ値。
- BLE の段 (`ble_nimble_port`・`ble_ready`・`ble`) の internal は同じ (`largest` だけ 204800 / 200704、
  192512 / 188416 の揺れ)。
- WiFi の段だけ R2 が -28 B (`wifi_ready` 216704 -> 216676、`wifi_rd` 212248 -> 212220)。同じ R1 のファームの
  過去の起動でも `wifi_rd` は 212248-212260 と揺れており、R2 の値はその幅から 28 B 外れた。R2 で変えたのは
  flash 上のコードとバイトコードだけで、起動時に動くものは無い (gem の初期化は定数とメソッドの登録だけで、
  増えたメソッドは 1 つ) ので、WiFi の接続の段の揺れと見ている。遠隔から再起動する手段が無く、焼き直しは
  flash を傷めるので、R2 の起動は 1 回しか見ていない。
- 起動の後の周期ダンプの IRAM free は 208716 (R1 の報告の焼いた直後 208224、develop 208256-208280 より多い)。

以上から **起動時の内蔵 RAM の増分は 0** と判断した (静的な区画と同期の段が同じ、非同期の段の揺れのみ)。
念のため、次に別の理由で焼き直すときに `wifi_rd` の値をもう一度見るとよい。

### 7.3 動かしている間と閉じた後 (R2)

| 状態 | IRAM free | 備考 |
|---|---|---|
| アプリの起動前 | 205644 | 焼いた後に tab5_fs で 2 つ put した後 |
| ros2_service を動かしている間 (1 回目) | 186392-187116 | アプリのタスク (スタック 16 KB) と接続 1 本。呼び出しの最中も同じ幅 |
| 閉じた後 1 回目 / 2 回目 / 3 回目 / 4 回目 | 205344 / 205108 / 204900 / 204688 | 最初の数回は 200-300 B ずつ減った |
| ros2_talker を 3 回起動して閉じた後 | 204476 / 204476 / 204476 | talker も 1 回目だけ -212 B、その後は同じ |
| ros2_service を 3 回起動して閉じた後 | 204476 / 204476 / 204476 | 同じ値に止まった |

- 最初の数回に一度だけ取られるもの (R1 の 6.3、A1 の 6.3 と同じ種類) で、回ごとの漏れではない。ros2_service と
  ros2_talker のどちらを使っても同じ値 (204476) に落ち着いた。

  (10.7 KB) と同じくらい。

## 11. 申し送り

- **ほかの型の作り方** (README の「Adding a type」): メッセージは `TYPE_NAME`・`TYPE_HASH`・`encode`・`decode` を
  持つモジュール、サービスはサービスの `TYPE_NAME`・`TYPE_HASH` と `Request` / `Response` のクラス。型のハッシュは
  ROS 2 の環境の `share/<パッケージ>/<msg|srv>/<型>.json` の最初の `RIHS01_`、または liveliness のトークンから取る。
  CDR の揃え (int64 は 8 バイト揃え、ヘッダの後から数える) は `Asterism::CDR::Writer` が面倒を見る。
- **asterism-msgs への育て方** (R3 の型の生成): AddTwoInts の Request / Response は手書きだが、形は機械的
  (フィールドごとの accessor、`new(**fields)`、Hash も受ける `encode`、`decode`、`to_h`)。`.msg` / `.srv` から
  この形を生成し、型のハッシュは生成時に ROS 2 の JSON から拾って定数にするのが近道 (PicoRuby で SHA-256 を
  計算しなくて済む)。サービスの型は要求・応答の 2 つのクラスと、サービスの型名・ハッシュの組で表す。
  アクションはサービス 3 つ (`_action/send_goal` など) とトピック 2 つに分かれるので、この組み合わせで作れる
  見込み (get_result は時間制限を長くする必要がある。2 章)。
- **応答の速さ**: サーバ側の応答は更新の間隔 (50 ms) に縛られる (5 章)。速さが要るアプリは更新の中で
  `node.poll` を回すか間隔を縮める。ポーリングの設計は変えていない。
- **サービスのブロックの中で待つ呼び出し**をすると `node.poll` が入れ子になる。深さの制限は付けていない (A1 の
  `MAX_NESTING` に当たるもの)。スタックの余りは 5.7 KB なので、入れ子にするなら確かめてから。
- **答えないサーバ**がいるとき、その get は時間制限まで生きている (zenoh-pico の中の get が 1 つ残る、PSRAM)。
  答えが来た時点で `Call` は終わるが、zenoh-pico の get が片付くのは制限の後。呼び出しを短い間隔で大量に出す
  アプリでは、時間制限を短めにする。
- **QoS とサービス**: サービスの QoS は既定の形をトークンに書くだけ。
- **design.md 6 章の案との違い**: `node.call` は型を明示する (liveliness からの型の判定はしない)。`res.sum` の形は
  `Response` の accessor で満たした。`Data.define` は使っていない (PicoRuby で使えるかは未確認)。
