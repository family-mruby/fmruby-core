# V2.2 報告: 網の図の色と、台帳の見え方

> 状態: 完了 (検収待ち) | 更新: 2026-10-11 | instruction_v2_2.md の実装と確認の記録。asterism-console の網の図で、色を「何の仲間か」だけに使い (青=ルータ、紫=ROS 2、橙=トピック、青緑=Asterism)、Asterism の 3 段 (ノード・アプリ・オブジェクト) を形で分けた。ノードの名前の前に何で動いているかの印 (機体・CRuby・console) を付けた。台帳 (Relay registry) の表示は既定でオフにしてブラウザに覚えさせ、オンのときは今つながっているものに角の印、つながっていない登録は「Not connected (registry)」の枠 1 つにまとめ、台帳からつながり先が分かるものはそのルータへ破線を引く。巻き戻しの図も同じ。sim・P4-Nano の ROS 2 のアプリ・CRuby・ROS 2 の台車で確かめた。止まる条件には当たらなかった。asterism-console は main に push 済 (f0d0fde、テストの機体名を仮の名前にした bf0ba0c)

## 1. 色と形の割り当て

| 仲間 | 色 | 形 |
|---|---|---|
| ルータ | 青 | ひし形。ルータどうしは太い青の線 |
| ROS 2 | 紫 | ノードは紫の角丸の四角 (バッジは前のまま) |
| トピック | 橙 | 出す側から受ける側への線 (「Topics as nodes」では札形) |
| Asterism | 青緑 (`#00897b`)。図の中の緑系はこれ 1 つ | ノード: 中が白、青緑の実線の枠、名前は太字で前に印。アプリ: 灰色の破線の枠、塗りなし。オブジェクト: 青緑の小さな丸 |
| その他 | 灰色 | その他の接続、Session の点 (「Sessions as points」)、台帳の枠 |

名前の前の印 (Unicode の Geometric Shapes の文字。絵文字は使わない。この文書では符号位置で書く):

| 印 | 形 | 何で動いているか |
|---|---|---|
| U+25A3 | 中に小さな黒い四角のある四角 (チップに見立てる) | 機体 (Family mruby の機体、Linux の sim、ブラウザ版) |
| U+25C8 | 中に小さな黒いひし形のある白いひし形 (宝石に見立てる) | CRuby (それ以外の Ruby のプロセス) |
| U+25CE | 二重丸 | この console |

- 網は Asterism のノードが何で動いているかを教えない。ノードは名前だけの liveliness token で、それ以上の情報が乗っていない (gem の `asterism/<node>`)。そこで名前の決まりで見分ける: 機体は mDNS の名前 `fmruby-<16 進 6 桁>` を名乗り、sim とブラウザ版は `linux` に落ちる (fmruby-core の asterism_demo)。それ以外は CRuby の印 (U+25C8)。ノードのファイルで別の名前を付けた機体も CRuby の印になる。詳細には「told by its name」と書いた。console は bridge 自身のノードなので、console の印は確かである。
- 印の文字は、12px の太字で読めるかを headless の Chromium で比べて選んだ。console の初めの案 (U+25C9、黒丸の入った丸) は小さな点にしか見えなかったので、二重丸 (U+25CE) に替えた。
- console 自身に付けていた黒い破線の枠はやめた (破線はアプリの意味になった)。印と「(this console)」で分かる。
- 組み立ては bridge の側 (`lib/bridge/marks.rb` の `Bridge::Marks.apply`)。`Bridge::Graph#to_h` の最後 (`Bridge::Connections` の後) と、巻き戻しの `RecordingsController#graph` で呼ぶ。足したものを外してから足すので何度かけても同じで、V2.2 より前の記録も同じ見え方になる。ページはどれを見せるかだけを選ぶ。

## 2. 台帳の見え方

- 「Relay registry」は既定でオフ。`localStorage` に覚える (「Sessions as points」と同じ)。巻き戻しの画面にも同じ切り替えを足し、設定を共有する。
- オンのとき:
  - **角の印**: 台帳と照らし合わせた Asterism のノードとルータの右上に、濃い灰色の小さな丸。中がチェック (登録済み)、横棒 (台帳で無効)、疑問符 (台帳に無い)。前の緑・橙・赤の輪をやめた。凡例に 3 つの意味を書いた。
  - **「Not connected (registry)」の枠**: つながっていない登録を 1 つの枠にまとめる。ルータの登録は小さなひし形、クライアントは小さな角丸の四角 (どちらも灰色)。
  - **破線**: 台帳からつながり先が分かるものは、そのルータへ破線 (矢印つき) を引く。詳細の「Expected at」に理由を出す。
- 生きた図の差分で、登録の名前がつながると枠から出てノードに印が付き、切れると枠に入る (ページで親を付け替える)。

## 3. 台帳から分かるつながり先の範囲

台帳は cloud ルータの名簿である。`Relay::CloudConfig` は台帳から cloud ルータの ACL を作り、有効で有効な証明書を持つルータとクライアント (`in_acl`) を 1 つずつ subject にする。そこから言えることだけを線にした。

| 登録 | つながるはずのルータ |
|---|---|
| ACL に入るクライアント (cloud ルータ用の証明書を持つ機体・プロセス) | cloud ルータ |
| ACL に入るルータ (中継の相手。例: 家のルータ) | cloud ルータ |
| cloud ルータ自身の登録 (サーバの証明書のため) | なし (それ自体がルータ) |
| ACL から外れる登録 (無効、有効な証明書が無い) | なし (cloud ルータは拒む。台帳はそれ以外を知らない) |

- cloud ルータの名前は `Relay::Settings.cloud_name` (`ASTERISM_RELAY_CLOUD_NAME`、既定 `zenohd-cloud`)。線は cloud ルータが網にいればそこへ、いなくて台帳に登録があれば枠の中のその登録へ、どちらも無ければ引かない。
- 分からないもの: 家にいるクライアントがどの LAN のルータを使うか (LAN では家のルータに平文の TCP でつながり、台帳の外)、クライアントが家のルータの中継を通るか cloud へ直接行くか、ROS 2 の peer (証明書の名前がノードの名前と一致しないので、そもそもノードに結び付かない)。これらは枠に置くだけ。
- 今つながっているものには、つながるはずのルータの線は引かない (実際の線が出ている)。

## 5. 残った課題

- 何で動いているかは名前の決まりで推している。確かにするには、gem がノードの token に種類を載せる (例: `asterism/<node>` の付帯情報) 必要がある。gem は今回の範囲外なので触っていない。
- 台帳から分かるつながり先は cloud ルータだけである。台帳がルータの組み合わせ (どの家のルータの中継か) を持てば、家の側の線も引ける。
- 台帳の枠は fcose が置く場所に出る。網にいる cloud ルータへ線が出ると、枠がそのそばへ寄る。枠の位置を決め打ちにはしていない。
- 巻き戻しで、V2.2 より前の記録の登録には「expect」が無いので、今の `cloud_name` で計算し直す。記録した時と cloud の名前が違うと線がずれる。
- 確認のために fixture の DB (`storage/fixture.sqlite3`) を migrate し、確認用のユーザを 1 人作った (リポジトリの外)。CRuby のノードは確認のために起こし、終わりに止めた。台車のコンテナは、ROS 2 のノードが図から消えていた (zenohd の作り直しで peer の token が戻らない、W2 の README の既知の挙動) ので再起動した。
