# Z3 報告: 問い合わせと応答、生存の監視、機体どうしの直接の接続

> 状態: 完了 (検収待ち) | 更新: 2026-10-06 | picoruby-zenoh に get / queryable と liveliness、ルータなしの peer を足した。sim と P4-Nano (NARYAv4) が zenohd 経由でも直接でも問い合わせ合い、受け入れ条件 1-10 を満たした。peer はシングルスレッドのポーリングだけで成り立った。10 本の peer の試験の後に内蔵 RAM が約 38 KB 戻らなかった件は、原因が ESP-Hosted (C6 との SDIO の通信) の送受信のバッファの溜め置きで、zenoh の漏れではないと分かった (12 章)。直すには sdkconfig の変更が要るので、止まって提案する

## 1. 結果の要約

- zenoh-pico の QUERY / QUERYABLE / LIVELINESS / UNICAST_PEER を有効にした。タスクもスレッドも足していない。
- Ruby の API は指示書の目安のまま (`get` / `each_reply` / `done?`、`queryable` / `each_pending` / `q.reply`、
  `liveliness` / `liveliness_watch`)。足したのは `liveliness_get`、`Query#finish`、`Session#peers` と、
  `Session.open` の `mode:` / `listen:` キーワード引数。
- コールバックの中で VM を触らない作りは Z1 のまま。問い合わせは `z_query_clone` でリングに置き、
  `each_pending` のブロックが終わった時点で片付ける (最後の参照が消えると zenoh-pico が終わりの返事を送る)。
- sim と NARYAv4 が zenohd 経由で互いを「生きている」と表示し、相手の info を問い合わせて表示した。
  アプリを閉じると相手の画面から 1 秒ほどで消え、開き直すと戻る (NARYAv4 側 10 回、sim 側 6 回)。
- zenohd を止めて、NARYAv4 が待ち受け、sim がつなぐ形で put / subscribe と get / queryable と liveliness が
  通った。待ち受けを閉じて開き直すと、つなぐ側を開き直せばまた通る (3 回)。
- peer の待ち受けの内蔵 RAM は待ち受けだけで 1 KB 弱。peer の数の上限は 10 (zenoh-pico の固定値) で、
  実機で 10 本つながり 11 本目は断られた。
- ファームは +30,896 B (区画の残り 12%)。起動時の内蔵 RAM の増分は 0。

## 2. 有効にした zenoh-pico の機能とビルドの変更

`include/zenoh_generic_config.h` で次を 1 にした。ほかは Z2 のまま。

| 機能 | 用途 |
|---|---|
| `Z_FEATURE_QUERY` | get、liveliness の get |
| `Z_FEATURE_QUERYABLE` | queryable |
| `Z_FEATURE_LIVELINESS` | liveliness のトークンと監視 |
| `Z_FEATURE_UNICAST_PEER` | peer (Z3b) |

peer をポーリングだけで回すために変えたもの (vendor/ は書き換えていない):

1. **待ち受けと受け付け (listen / accept)。** gem の TCP 層 (POSIX 版と ESP-IDF 版) は client だけの作りで
   listen / accept が失敗を返していた。zenoh-pico は待ち受けのソケットを非ブロッキングにして、協調型の
   仕事 (accept の仕事) から 1 秒ごとに accept を呼ぶ。待っている相手がいないのが普通の場合なので、
   gem の accept はそのとき何も記録せずに失敗を返す (上流はそのたびにエラーを出す)。待ち受けのソケットが
   閉じていれば `_Z_ERR_INVALID` を返して仕事を終わらせる。
2. **peer の読み取りの待ち。** peer の読み取りは全部の peer のソケットを `select` で待ち、その時間は
   `Z_CONFIG_SOCKET_TIMEOUT` (100 ms)。`poll` は最大 8 回まわるので、データが無いと 1 回の `poll` が
   数百 ms 止まる。`transport/unicast/read.c` の 1 本だけを `-DZ_CONFIG_SOCKET_TIMEOUT=0` でコンパイルし
   (mrbgem.rake のファイルごとの定義)、待ちを「読めるか見るだけ」にした。ハンドシェイクの待ち (TCP 層の
   read_exact) は 100 ms のまま。生成されたオブジェクトで引数が 0 になっていることを逆アセンブルで確かめた。
3. **EINTR。** 上流の POSIX の `select` は EINTR を失敗として返し、peer の読み取りの仕事はそこで終わる
   (セッションは開いたまま、二度と読まない)。sim は SIGALRM で刻むので起こりうる。POSIX では
   `system/unix/network.c` を gem の `src/zp_network_posix.c` に置き換え、EINTR を再試行する。
   ESP-IDF では EINTR は起きないので上流の `socket/esp32.c` のまま (CMakeLists.txt は変えていない)。

`Z_LISTEN_MAX_CONNECTION_NB` (10) は config.h.in に `#ifndef` なしで書かれていて、変えられない。

## 3. API の一覧

Z2 までのもの (put / subscribe / poll / closed? / close / 定数) は変わらない。

| 呼び出し | 戻り値 | 例外・時間切れ・注意 |
|---|---|---|
| `Asterism::Zenoh::Session.open(locator)` | `Session` | client (Z1 のまま) |
| `Asterism::Zenoh::Session.open(locator, mode: :peer)` | `Session` | peer として相手につなぐ。つながらなければ `Asterism::Zenoh::Error` |
| `Asterism::Zenoh::Session.open(nil, mode: :peer, listen: "tcp/0.0.0.0:7447")` | `Session` | peer として待ち受ける (`locator` を同時に渡してもよい)。`mode:` は `:client` / `:peer` 以外で `ArgumentError`。client で `listen:` も `ArgumentError` |
| `session.peers` | Integer | つながっている peer の数 (client はルータの 1)。閉じたら 0 |
| `session.get(key, timeout_ms = 2000, params = nil, payload = nil)` | `Get` | すぐ戻る。当てはまる queryable 全部に問い合わせ (target ALL)、答えをまとめない (consolidation NONE)。`timeout_ms` は 1..600000、範囲外は `ArgumentError`。閉じたセッションは `Asterism::Zenoh::Error` |
| `get.each_reply { \|key, payload\| }` | Integer | 届いた答えを古い順に。ブロック無しなら `[[key, payload], ...]`。エラーの答えは渡さず `errors` で数える |
| `get.done?` | true / false | 全員が終わりの返事を送った、時間切れ、セッションが閉じた、のいずれかで true。時間切れの判定は `poll` の中で 1 秒ごとなので、最大で約 1 秒遅れる |
| `get.pending` / `received` / `dropped` / `errors` | Integer | 答えは 16 件まで溜める。溢れたら古いものを捨てて数える |
| `session.queryable(key, depth = 16)` | `Queryable` | 溜めておける未回答は `depth` 件。溢れたら一番古いものを答えずに終わらせ (問い合わせ側は答えなしで終わる)、`dropped` で数える |
| `qa.each_pending { \|q\| }` | Integer | 溜まった問い合わせを渡す。ブロックが終わったら (例外のときも) その問い合わせを終わらせる。ブロック無しなら `Query` の配列で、各々は `q.finish` か GC まで開いたまま |
| `qa.pending` / `received` / `dropped` / `close` / `closed?` | | |
| `q.key` / `q.params` / `q.payload` | String | 問い合わせのキー (ワイルドカードを含みうる)、パラメータ (`a=1;b=2`)、ペイロード (無ければ `""`)。終わった後は `Asterism::Zenoh::Error` |
| `q.reply(payload)` / `q.reply(key, payload)` | nil | キーの既定は問い合わせのキー。問い合わせのキーに当てはまらないキーは `Asterism::Zenoh::Error`。何度でも呼べる |
| `q.finish` / `q.finished?` | | 終わりの返事を送る。何度呼んでもよい |
| `session.liveliness(key)` | `LivelinessToken` | `close` / GC / セッションを閉じるまで「生きている」 |
| `token.close` / `token.closed?` | | |
| `session.liveliness_watch(key, depth = 16)` | `LivelinessWatch` | `each_pending { \|key, alive\| }`。始めた時点で生きているものが先に `alive=true` で来る。同じセッションのトークンは来ない (zenoh-pico の作り)。`pending` / `received` / `dropped` / `close` / `closed?` |
| `session.liveliness_get(key, timeout_ms = 2000)` | `Get` | 今生きているトークンを答え (ペイロードは空) として返す |
| `Asterism::Zenoh::PEER` | true / false | peer が組み込まれているか |

中の作り:

- `Get` の状態 (答えのリングと終わりの印) は `z_malloc` で取る。zenoh-pico の答えのクロージャの drop が
  Ruby のオブジェクトより後に呼ばれうる (VM ごと消えた後もありうる) ので、Ruby 側と zenoh-pico 側の
  どちらか後に手を離した方が解放する。`z_get` が失敗したときは zenoh-pico が先に drop を呼ぶ。
- セッションを閉じるときは、queryable の未回答を先に終わらせ (終わりの返事がまだ送れるうちに)、次に
  トークン、購読、最後に `z_close` (ここで進行中の get が drop される)。
- 例外のときもブロックの後で問い合わせを終わらせるのに、mruby 本体の `mrb_protect_error` を使った
  (`mrb_ensure` は mruby-error の gem にあり、gem の独立を崩すため使わない)。
- peer の「閉じた」の判定: 待ち受けているセッションは peer の出入りでは閉じない。つなぐだけのセッションは
  peer が 0 になったら閉じる (client と同じ扱い: `poll` が false、`closed?` が true、`put` が例外)。
  zenoh-pico は相手が閉じた・失敗した・リースが切れた peer を自分で外すので、その結果の数を見ている。
  これは Z2 で決めた切断の扱いを peer に当てはめたもので、新しい選択は足していない。

## 5. 大きさと内蔵 RAM / PSRAM (NARYAv4)

### 5.1 flash

| | fmruby-core.bin | 区画 (0x700000) の残り |
|---|---|---|
| Z2 (report/z2.md 12.3) | 0x6199d0 | 0xe6630 (13%) |
| Z3a (get / queryable / liveliness) | 0x6200b0 (+26,336 B) | 0xdff50 (12%) |
| Z3b (+ peer) | 0x621280 (+4,560 B) | 0xded80 (912,768 B、12%) |

### 5.2 静的な内蔵 RAM

Z3a と Z3b のどちらも `.dram0.data` 0x3a44 / `.dram0.bss` 0x6334 で同じ。リンクのマップの `.dram0.data` から
`.dram0.heap_start` までに zenoh-pico と gem のオブジェクト (zenoh / zp_tcp / zp_system) は 1 つも無い。
gem は Z2 からあるので、`prebuilt_gems` の表も大きさが変わらない。Z2 の NARYAv4 の同じ節の値は取って
いない (Z2 は TAB5 で比べた)。

### 5.3 起動時

起動の `M1|` 行は、Z3b の起動で `wifi_ready|internal=213540`、`wifi_rd|internal=209084` など、
report/z2.md 4.1 の値と同じだった。周期ダンプの IRAM free は 203364 (Z2 は 203412、develop は 203376)。

Z3a の最初の起動は `ble_ready|internal=227424`、IRAM free 202984 で、約 2 KB 低かった。これは BLE の
初期化の揺れで、同じ capture のログに Z2 以前のファームでも 2 つの値の起動が混ざっている (例:
`ble_ready` が 227440 / 229532、IRAM free が 202988 / 203412)。zenoh のコードは起動時には動かない
(gem の初期化はアプリの VM ごとのクラスの定義だけ)。

### 5.4 動かしている間 (ルータ経由、Z3a)

| 状態 | IRAM free | PSRAM free |
|---|---|---|
| アプリの起動前 (前のアプリを閉じた後) | 197200 | 10306644 |
| zenoh_nodes、接続中、相手 1 台 | 176200-178684 | 9878260 |
| 比べ: Z2 の zenoh_echo (起動前 197092 -> 接続中) | 176916 | -427 KB |

zenoh_nodes の内蔵 RAM の減りはアプリ 1 つ分 (タスクのスタック 16 KB ほか) と接続 1 本 (lwIP 約 2.4 KB) で、
Z2 の zenoh_echo と同じ程度。PSRAM の減り (約 428 KB) も同じで、ほとんどはアプリの VM プール。
アプリの VM のプールの使用は 274-290 KB (アプリのログ `pool_used`)。

## 6. peer (Z3b)

### 6.1 可否

**シングルスレッドのポーリングだけで成り立った。** 読み取りのタスク・accept のタスクとも要らない。
zenoh-pico の peer の accept はもともと協調型の仕事 (`_zp_unicast_accept_task_fn`) で、`zp_spin_once` から
呼ばれる。足りなかったのは 2 章の 3 点 (accept の実装、待ちの 0 化、EINTR) だけだった。

- 接続にかかる時間: つなぐ側から見て 859-1042 ms。待ち受け側の accept が 1 秒ごとなので、最大 1 秒待つ。
- `poll` の止まる時間: 30 ms 以上かかった `poll` をアプリでログに出した。待ち受け側 (NARYAv4) で出たのは
  peer の受け付け (ハンドシェイク) と切断のときだけで、33-67 ms、zenohd の peer 6 本が同時につないだときに
  137 ms が 1 回。データの無い `poll` で 30 ms を超えたことは無い。つなぐ側 (sim) は 0 回。
- get の時間切れの判定も 1 秒ごとなので、1.5 秒の制限の get が 1.9-2.3 秒で終わる。

### 6.2 待ち受けのコストと上限

同じ起動の中で、10 秒ごとの周期ダンプの値。

| 状態 | IRAM free | PSRAM free |
|---|---|---|
| 何も動かしていない (前の接続から 2 分以上) | 196616 | 10306644 |
| 比べ: timer_test (zenoh を使わないアプリ) | 179000 | 9885640 |
| zenoh_nodes が待ち受け、peer なし | 178028-178256 | 9878788 |
| peer 1 本 (sim) | 176028-177600 | 9877516-9877752 |
| peer 4 本 (sim のアプリ 4 つ) | 165132-173076 | 9875776-9876312 |
| peer 10 本 (sim 4 + PC の zenohd を peer で 6) | 114200-157312 | 9873444-9874412 |

- **待ち受けだけの内蔵 RAM は 1 KB 弱** (timer_test との差 744-972 B。待ち受けのソケットと PCB)。
- peer 1 本あたりは 1.5-3 KB、通信の量で上下する (lwIP の受信と送信の pbuf)。10 本では 20-60 KB 減り、
  一時的に 114 KB まで下がった。PSRAM はほとんど動かない (zenoh-pico の peer ごとの状態は小さい)。
- **上限は 10 本。** zenoh-pico の `Z_LISTEN_MAX_CONNECTION_NB` (10、変えられない) で、11 本目の zenohd は
  accept の後に断られ (`peers=10` のまま)、つなぎ直しを繰り返した。NARYAv4 の lwIP のソケットの数
  (`CONFIG_LWIP_MAX_SOCKETS=16`、sdkconfig.defaults.naryav4) には届かなかった。sim のユーザアプリの枠が
  5 つ (4 つ目まで起動でき、5 つ目は -9) なので、残りは PC の zenohd を `mode:"peer"` で 6 つ起動して数えた。
- zenoh-pico の peer は中継をしない。NARYAv4 に 4 つの sim のアプリがつないでも、sim のアプリどうしは
  互いを見ない (どれも名前が linux なので画面の上では区別できなかったが、仕組みとしてそうなる)。

## 7. 10 本の peer の試験の後、内蔵 RAM が約 38 KB 戻らない (最初の見立て。原因は 12 章)

zenohd の peer 6 本を `docker stop` で止め、sim の peer 4 本を kill し、NARYAv4 のアプリを閉じた後、
IRAM free は 158024 で止まり、試験の前の 196616 に戻らなかった (約 38.6 KB)。PSRAM は 10306644 で元に
戻った。zenohd の peer を止めてから 21 分以上 (14:57 から 15:19 まで)、値は 1 バイトも動いていない
(Z2 の TIME_WAIT のように段階的に戻る動きが無い)。
最大の空きの塊も小さくなり、次にアプリを開いたとき `largest=36864` だった (アプリ 1 つに 24576 要る)。

分かっていること:

- 減ったのは zenohd の peer 6 本の段階 (peer 4 本のときは 169-171 KB で、zenohd の peer を止めて peer が
  4 本に戻った後は 138 KB)。それまでの sim との peer の試験 (条件 8・9、待ち受けの開き直し 4 回) の後の
  何も動かしていない値は 196616 で、焼いた直後の 202948 より 6.3 KB 低かった。こちらは段階的に戻る
  途中の値か、Z2 で見た最初の接続で一度だけ減る分 (3.3 KB) と同じ種類のものかを切り分けていない。
- zenoh-pico は peer を外すときにソケットを閉じている (`_owns_socket` が true の peer は
  `_z_transport_peer_unicast_clear` で close。accept した peer はすべて true)。断った 11 本目も close している。
- 見立て 1 (弱まった): zenohd の peer は PC の Docker Desktop の NAT の向こうにあり、コンテナを止めると
  NAT の状態が消える。こちらが閉じた接続の FIN や未送のデータに ACK が返らず、lwIP が PCB と pbuf を
  持ったまま再送を続けている (LAST_ACK / FIN_WAIT)。ただし再送が尽きれば戻るはずで、21 分たっても
  1 バイトも戻らないのは合わない。
- 見立て 2: どこかの経路でソケットか lwIP の資源が解放されていない (漏れ)。zenohd の peer は sim の
  peer と違い、つないだ直後に多くの宣言や問い合わせを流し、11 本目は断られては 1 秒ごとにつなぎ直して
  いた。accept の後に断る経路、ハンドシェイクの失敗の経路、上流の `_zp_unicast_process_peer_event` の
  「処理に失敗した peer を外す」経路のどれかが疑わしいが、読んだ範囲ではどれも close している。
- 確かめる手: lwIP の統計 (`LWIP_STATS` の MEMP / PBUF) か PCB の一覧 (`tcp_active_pcbs` /
  `tcp_tw_pcbs`) を周期ダンプに出す (main/ と sdkconfig に触るので Z3 の範囲の外)、zenohd の peer の数を
  1 本ずつ増やして減り方を見る、11 本目を起こさずに 10 本で止める、NAT を通らない相手で行う。
  どれもこのセッションでは行っていない。

利用の上では、peer を多く受ける機体で内蔵 RAM が数十 KB 単位で減ること自体が、内蔵 RAM を増やさない方針と
ぶつかる。peer の数をアプリ側で制限する口 (zenoh-pico の 10 より小さく) を足すかは、A1 の前に決めたい。

## 8. 見立てと違った点・踏んだ罠

- **ワイルドカードの問い合わせ。** `fmrb/node/*/info` の問い合わせは queryable の側に `q.key` が
  `fmrb/node/*/info` のまま届く。最初の試しのアプリは自分のキーと完全一致を比べていて答えなかった。
  末尾の部分を見て、自分の具体的なキーで答える形にした (答えのキーは問い合わせのキーに当てはまれば
  よい)。
- **自分のトークンは自分の監視に来ない。** zenoh-pico の liveliness の「今いる人」は相手のトークンだけで、
  ローカルのトークンには対応していない (上流の TODO)。試しのアプリは自分を `self` として別に出した。
- **REST の問い合わせは 10 秒で切れる。** `query fmrb/node/linux/silent` (答えずに 10 秒持つ) は zenohd の
  既定の時間切れで、エラーの答え `Timeout` が 1 件返る (10,003 ms)。
- **同じ名前の 2 つ目。** NARYAv4 で閉じるクリックが窓の出る前に届き、同じアプリが 2 つ動いた
  (同じ名前のトークンが 2 つ)。1 つを閉じると相手の画面から名前が消えた (もう 1 つは生きているのに)。
  名前の重複は試しのアプリの前提の外。A1 で機体の名前を決めるときの注意になる。
- **get の時間切れは 1 秒刻み。** zenoh-pico の時間切れの判定は 1 秒ごとの仕事なので、制限より最大 1 秒
  遅れて `done?` になる。
- 上流の accept はソケットが空のたびに `_Z_ERROR_RETURN` でエラーを出す。ポーリングで 1 秒ごとに呼ぶと
  ログが埋まるので、gem の accept は記録しない。
- zenohd 1.10.1 の CLI に `--mode` は無い (`--cfg 'mode:"peer"'` で渡す)。

## 11. A1 と Z4 への申し送り

- **A1 (遠くのオブジェクトの代理)**: `get` + `queryable` の往復は 1 回 40-160 ms (PC の REST 経由の実測)。
  呼び出しを get に載せるなら、引数は `params` か `payload`、戻り値は答えの payload。`each_pending` の
  ブロックで答えて終わらせる形がそのまま使える。答えない相手は `done?` で分かるが、時間切れは 1 秒刻み。
  機体の名前の決め方 (重複の扱い) と、自分のトークンが自分に見えないことに注意。
- ルータなしでも同じ API で動くので、A1 はルータの有無を意識しない作りにできる。ただし peer は中継を
  しないので、3 台以上を網にするならルータ (zenohd) を使う。
- **Z4 (S3)**: 増分の目安は Z2 の約 59 KB + Z3 の約 31 KB。S3 は区画の残りが少ない。peer が要らなければ
  `Z_FEATURE_UNICAST_PEER=0` で約 4.5 KB 減らせる (gem は `Asterism::Zenoh::PEER` で分かる)。S3 の CMake の分岐で
  ESP-IDF 側の 3 本 (system、TCP、socket/esp32.c) をコンパイルするのは Z2 と同じ。内蔵 RAM は 7 章の
  peer の件があるので、S3 では peer を切るのが無難。

## 12. 内蔵 RAM が戻らない件の原因 (追加の調査)

### 12.1 結論

**ESP-Hosted のホスト側のドライバが、C6 と SDIO でやり取りするバッファ (1 個 1536 B、ヒープ上で
1664 B、DMA が使える内蔵 RAM) を、使い終わっても解放せずに自前の空きリストに溜める**
(`CONFIG_ESP_HOSTED_USE_MEMPOOL=y`、`managed_components/espressif__esp_hosted/host/drivers/mempool/mempool.c`)。
空きリストに上限は無く、ヒープに返す経路も無い。そのため内蔵 RAM の減りは「それまでに同時に使われた
バッファの数の最大値」で決まり、一度増えたら再起動まで戻らない。通信が一時に集中すると増える。

- zenoh-pico と gem の漏れではない。ソケット・TCP の PCB・zenoh-pico の確保 (PSRAM) はすべて元に戻る。
- 1 回ごとに減る漏れでもない。同じ負荷をもう一度かけても増えない (上の値で頭打ち)。
- zenoh を使わない HTTP の転送 (`tab5_fs` の 64 KB の get と put) でも同じように増える。
- 上限の見積もり: 溜まる数は送受信のキュー (`CONFIG_ESP_HOSTED_SDIO_TX_Q_SIZE=20`、`RX_Q_SIZE=20`、
  それぞれ優先度ごとに 3 本) に入りうる数まで。理屈の上の最大は約 120 個 (約 200 KB) だが、観測した
  最大は Z3 の試験の 23 個ほど (約 38 KB)。

これは「範囲の外 (ESP-Hosted / sdkconfig)」なので、指示どおり直さずに止まる。案は 12.5。

### 12.2 調べ方 (一時的な計装。コミットしていない)

`components/fmrb_common/src/fmrb_task.c` の 10 秒ごとのダンプから、gem の `ports/esp32/zp_tcp_esp32.c` に
一時的に足した関数を弱い参照で呼び、次を出した。sdkconfig は変えていない。

- `heap_caps_get_info(MALLOC_CAP_INTERNAL)`: 空きの合計、最大の塊、確保済みと空きの塊の数。
- 開いている lwIP のソケット (`LWIP_SOCKET_OFFSET` から 16 個を `fcntl` で調べ、種類とポート)。
- TCP の PCB の一覧 (`tcp_active_pcbs` / `tcp_tw_pcbs` / 待ち受け。`tcpip_callback` で lwIP のスレッドから
  読む): 状態、ポート、送信待ちの数、受信の窓。
- `heap_caps_walk` で内蔵 RAM の使用中の塊のうち 1536-1700 B のものを数え、各塊の番地と先頭の 4 バイト
  (空きリストの「次」へのポインタになる) を出す。

計装の差分は 156 行で、調査の後に `git checkout` で戻した (作業ツリーにも残っていない)。実機には計装を
外した Z3b のファーム (0x621280、前と同じ大きさ) を焼き直した。

### 12.3 段階ごとの再現 (焼いた直後から、各段階の後 3 分以上待って記録)

値は 10 秒ごとのダンプの内蔵 RAM の空き。特に書いていなければアプリは閉じた状態。「1664 B の塊」は
内蔵 RAM の使用中の 1536-1700 B の塊の数。計装を 3 回入れ直したので、起動は 3 回に分かれる:
(b)-(e) と (f) の 2 回目は 1 回目の起動 (塊を数える前の計装)、(f) の 1 回目は 3 回目の起動、
焼いた直後・timer_test・(a)・HTTP は 4 回目の起動 (いずれも app_only の焼き直しで再起動した直後から)。

| 段階 | 空き (前 -> 後) | 差 | 1664 B の塊 | ソケット / PCB |
|---|---|---|---|---|
| 焼いた直後 | 202732 | | 4 | 3 / 待ち受け 80 番のみ |
| zenoh を使わないアプリ (timer_test) を開いて閉じる | 202732 -> 202756 | 0 | 4 | 同じ |
| (a) zenohd への client の開閉 5 回 | 202756 -> 202560 | -196 | 4 | 同じ (TIME_WAIT は 3 分で消えた) |
| (b) 待ち受けだけ (peer なし)、2 回 | 200868 -> 199200 -> 199200 | 1 回目 -1668、2 回目 0 | (この段階は塊を数える前の計装) | 7447 のソケットと PCB は閉じると消えた |
| (c) PC の peer 1 本がつないで止まる | 179820 (待ち受け中) -> 179820 | 0 | | peer のソケットと PCB はすぐ消えた (相手が先に閉じるので TIME_WAIT も無い) |
| (d) peer がつながったまま待ち受けを閉じる | 198176 -> 198176 | 0 | | TIME_WAIT 1 個が 2 分で消えた |
| (e) 10 本の上限で 11 本目が断られる | (10 本の間) 165784 -> 164116 | -1668 | | 11 本目のソケットと PCB は残らない |
| (f) 10 本を同時に止める | 184436 (待ち受けのみ) -> 174428 | -10008 | 4 -> 10 | ソケット 4 (待ち受けと系のもの)、PCB は待ち受けだけ |
| (f) をもう一度 | 168152 -> 168152 | 0 | 増えない | 同じ |
| HTTP (zenoh なし) の 64 KB の get と put | 202560 -> 196664 | -5896 | 4 -> 7 | 同じ (3 分後も同じ値) |

(b)・(e) の -1668 と (f) の -10008 (= 6 個 x 1664 + 24) は、どれも 1664 B の塊の増分そのもの。
1664 = `MEMPOOL_ALIGNED(1536)` を 64 B 揃えで確保した大きさ。

### 12.4 塊が ESP-Hosted の空きリストであることの確かめ

(f) の後の 10 個の塊の先頭の 4 バイトをたどると、2 本の単方向リストになった (ESP-Hosted は
`buf_mp_g` (SDIO のバッファ) と通信路ごとの `memp` の 2 つの溜め置きを持つ):

```
0x4ff98040 -> 0x4ff99f80 -> 0x4ff55b40 -> NULL
0x4ff9e400 -> 0x4ff9dd40 -> 0x4ff7cf00 -> 0x4ff9ca80 -> 0x4ff998c0 -> 0x4ff7c600 -> NULL
(0x4ff68ebc は先頭が 0x0000000c で、使用中の別のもの)
```

`mempool_free()` は解放されたバッファの先頭に `SLIST_INSERT_HEAD` でつなぐだけで、`_h_free` を呼ばない
(`H_USE_MEMPOOL` のとき)。確保は `MEM_ALLOC` = `esp_dma_capable_malloc` (内蔵 RAM)。

### 12.5 小さい差と Z2 の 3.3 KB

- Z2 の「最初の接続で一度だけ減る 3,336 B」は 2 個分 (2 x 1664 = 3,328)。
- 焼いた直後の 202948 と、sim との peer の試験の後の 196616 の差 (6,332 B) も、ほとんどがこの溜め置きの
  増分 (4 個で 6,656、残りは数百 B の小さい確保の揺れ)。遠隔の操作 (画面の取得、ファイルの転送) も同じ経路を
  通るので、zenoh を使わなくても増える。
- 最初の調査のときに見えた「最初のアプリで 1,636 B 減る」も 1 個分で、焼き直した後の同じ手順では減らなかった
  (その前の通信の量で決まる)。

### 12.6 直す案 (選ぶのはユーザ。sdkconfig と ESP-Hosted は範囲の外)

1. **`CONFIG_ESP_HOSTED_USE_MEMPOOL=n`** (sdkconfig.defaults.naryav4 と p4)。バッファを毎回ヒープに返す。
   溜め置きの分の内蔵 RAM は通信が終われば戻る。代わりにパケットごとに確保と解放をする (速さと断片化への
   影響は測っていない)。Tab5 も ESP-Hosted (C6) なので同じ。
2. 溜め置きに上限を付ける ESP-Hosted への手当て (例: 空きリストが N 個を超えたら解放)。managed_components の
   中の変更になるので、lib/patch のような上書きの仕組みか、上流への提案が要る。
3. そのままにして、「通信の山の分だけ内蔵 RAM を予約する」と扱う。最大の見積もりは 12.1 のとおり。

gem の側でできることは無い (zenoh の通信量を減らしても、ほかの通信で同じことが起きる)。peer の数を
10 より小さく制限する口は、この件とは別の理由 (接続中の lwIP の消費、6 章) でなら意味がある。

### 12.7 まだ行っていないこと

原因が範囲の外にあるため、直した後の (a)-(f) の再試験と、受け入れ条件 2・4・8 と sim の zenoh_echo の
再試験は行っていない (gem のコードは 12 章の調査で何も変えていない)。
