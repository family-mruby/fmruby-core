# G1.5b 報告 (P4-Nano): 端末がつなぎ直さなかった原因と直し、内蔵 RAM の同じコミットでの比べ

> 状態: 完了 | 更新: 2026-10-13 | report/g1_5b.md の 9 章「P4-Nano での確かめ」の続き。G1.5b のファームを P4-Nano に焼いたところ、家のルータを起動し直した後に端末が戻らなかった。原因は gem の ESP-IDF 用 TCP の口 (`ports/esp32/zp_tcp_esp32.c`) の握手の読みで、リセットされた接続を待ち続けて `poll` の中から戻らなくなっていた。直した後は 6 回の起動し直しで 1.2-2.4 s で戻った。内蔵 RAM は、同じコミットで `Z_FEATURE_AUTO_RECONNECT` を 0 と 1 にしたビルドどうしで、静的にも動いている間にも差が無い

## 1. 結果の要約

| リポジトリ | ブランチ | 中身 |
|---|---|---|
| picoruby-asterism-zenoh | main (53e7535) | 握手の読み (`_z_tcp_read_exact`) が、失敗したソケット (リセット) を閉じた接続と同じに扱って終わる。ESP-IDF と POSIX の両方の口。CHANGELOG |
| fmruby-core | fix/asterism-reconnect-p4 | `lib/add/PICORUBY_ASTERISM_ZENOH_PIN` を 53e7535 に上げる、この報告 |

asterism は直していない (b384547 のまま)。版は上げていない。push していない。ピンが指すコミットは push するまで取れないので、それまでのビルドは `PICORUBY_ASTERISM_ZENOH_DIR=../picoruby-asterism-zenoh` を付ける。

## 2. 起きていたこと

- 症状: オセロがつながった状態で家のルータを `docker restart` すると、アプリは「the line dropped, connecting again」を出したまま 3.5 分以上戻らず、ルータからも見えなかった。シリアルに zenoh の誤りの行は無かった。画面と他のタスクは動いていた。
- ルータの側で見た: ルータのコンテナの網と、docker の host の網で `tcpdump` (port 7447) を取った。止まっている間、端末からの接続は 1 つも来ていなかった (sim と同じ機械の mruby の client は同じ宛先で 1 s で戻った)。
- 端末の側で見た: zenoh-pico (scratch の写し) と gem に一時の `printf` を入れたファームで、失敗の道・つなぎ直しの task・TCP の open・poll の状態を出した。

```
ZDBG failed_result enter state=2
ZDBG failed_result spawned reopen id=6
othello: the line dropped, connecting again
ZDBG reopen try
ZDBG tcp_open connected fd=51 56ms
(ここから先、reopen の結果も poll の行も出ない)
```

つなぎ直しの task は spawn され、1 回目の `_z_open` で TCP はつながったが、`_z_open` から戻らなかった。poll の行もそれきり出ないので、オセロの task は `poll` の中で止まっていた (画面の更新は別のタスク)。

- 握手の読みに errno を出す行を足して焼き直すと、5 回中 5 回、つなぎ直しの 1 回目で次が出た。

```
ZDBG tcp_open connected fd=51 3ms
ZDBG read_exact failed errno=104 n=0
ZDBG reopen ret=-99
ZDBG reopen try
ZDBG tcp_open connected fd=51 11ms
ZDBG reopen ret=0
ZDBG reconnected
```

## 3. 原因

- ルータは docker のポートの公開 (Docker Desktop、host の 7447) の奥にある。ルータのコンテナが起動し直している間も、公開の口は接続を受け、奥につなげずにリセットする。端末の 1 回目の試しはこの「つながってすぐリセット」に当たる (errno 104 = ECONNRESET)。
- gem の `_z_tcp_read_exact` は、最初の 1 バイトの前は「select で読めると出る → recv」を回し、recv が失敗すると `continue` していた。期限を見るのは 1 バイト目が来てからだった。
- lwIP は、リセットされたソケットの recv に**毎回** ECONNRESET を返す (select も毎回すぐ「読める」と返す)。そのため 1 バイトも来ないまま回り続け、関数から戻らなかった。Linux は ECONNRESET を 1 回返した後は 0 (閉じた) を返すので、ホストの試験では起きなかった。
- zenoh-pico のつなぎ直し (`_z_client_reopen_task_fn`) は poll の中で `_z_open` を呼ぶので、止まったのはアプリの task ごと。誤りの行は出ない (止まっているだけ)。

前のファーム (アプリがセッションを開き直す形) は 3 s ごとに試していたので、たまたま公開の口がリセットする間を外れていた。同じ読みを通るので、同じ穴は前からあった。

## 4. 直し

picoruby-asterism-zenoh 53e7535:

- `zp_recv_now` が「ソケット自体が失敗した (would block 以外の誤り)」を返せるようにした。
- `_z_tcp_read_exact` は、失敗したソケットでは 0 (閉じた接続と同じ) を返して終わる。呼び手 (`_z_link_recv_t_msg`) は `_Z_ERR_TRANSPORT_RX_FAILED` を返し、zenoh-pico はつなぎ直しを 1 s 後に試し直す (retryable)。上の 2 行目の `reopen ret=-99` がそれ。
- POSIX の口も同じ形にした (Linux では今は害が無いが、決まりを揃える)。
- `rake test` (77 項目) と `rake test_reconnect` (docker、約 1 s で戻る) が通る。

内蔵 RAM・flash への影響は無い (分岐 1 つ)。sdkconfig とファームの C は触っていない。

## 5. 端末で測ったつなぎ直し (直した後、P4-Nano、家のルータを `docker restart`)

アプリの記録の「the line dropped」から「connected again」まで (端末の時計):

| 回 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 途切れ | 1.23 s | 2.24 s | 2.36 s | 2.24 s | 1.20 s | 2.34 s |

- 表は直した最終のファーム (一時の printf なし)。1.2 s の回は 1 回目の試しが拒まれ (まだ公開の口が無い)、2.2-2.4 s の回は 1 回目がリセットに当たって、どちらも 1 s 後の 2 回目で通った (一時の printf 入りのファームでの 6 回で、1 回が前者・5 回が後者だった)。
- 戻った後、家のルータの生存の印に `asterism/fmruby-aaaaaa/game/othello` と `asterism/fmruby-aaaaaa/game` が戻っていた (probe で確かめた)。
- 参考: 同じコミットで `Z_FEATURE_AUTO_RECONNECT=0` (アプリが開き直す形) は 3 回とも 3.1 s。

## 6. 内蔵 RAM (同じコミット、`Z_FEATURE_AUTO_RECONNECT` だけ 0 と 1)

ビルド: fmruby-core develop (c1685c2b) + picoruby-asterism-zenoh 53e7535 (0 の方は `include/zenoh_generic_config.h` の 1 行だけを手元で 0 にした)、asterism b384547、`FMRB_HW_TARGET=NARYAv4`、それぞれ `rake clean` の後に `rake build:esp32`、アプリの区画だけを焼いた。値は周期のダンプの `IRAM free:` (10 s ごと)。

| | 0 (アプリが開き直す) | 1 (zenoh-pico がつなぎ直す) | 差 |
|---|---|---|---|
| DIRAM 合計 (`idf.py size`) | 125612 | 125612 | 0 |
| DIRAM .bss / .data / .text | 25396 / 14916 / 85300 | 25396 / 14916 / 85300 | 0 |
| Flash 合計 | 6419710 | 6422278 | +2568 |
| fmruby-core.bin | 6523072 | 6525648 | +2576 |
| 起動後、アプリなし (落ち着いた値) | 208232 | 208232 | 0 |
| オセロがつながった状態 (6 回) | 189752-189772 | 189708-189752 | ほぼ 0 (揺れ 20-40 B の範囲) |
| ルータの起動し直し 3 回 / 6 回の後 | 189768 | 189756 | 0 |
| オセロの task のスタック Free | 4560 前後 | 4560 前後 | 0 |

- 動いている間に増えるもの (宣言の控え、つなぎ直しの task) は PSRAM の割り当てから取られ、内蔵 RAM には出なかった。起動し直しを繰り返しても減っていかない (漏れていない)。
- はじめの報告の「つながった状態で 4 KB 少ない」(旧 189,764、新 185,680) は、つなぎ直しが止まっていた状態の値と同じ並び (止まっていた間は 185,912) で、比べる状態がそろっていなかったと見る。止まっている間は、リセットされた TCP の接続 (lwIP の制御ブロックとバッファ、内蔵 RAM) が開いたまま残っていた。正常なつながりどうしで比べると差は無い。

## 7. 残った課題

- **つなぎ直しの試しが poll を止める** (g1_5b.md 9 章と同じ): `_z_open` は poll の中で走る。ルータの PC ごと居なくなって SYN が返らないときは、試すたびに `PICORUBY_ZENOH_CONNECT_TIMEOUT_MS` (3 s) まで止まる。拒まれる・リセットされる場合はすぐ返る (今回の測りは全部こちら)。端末の画面が 1 s おきに 3 s 固まる形になりうる。必要なら gem で試しの間隔を空ける。
- 握手の読みの、1 バイト目が来た後に止まる道は、`PICORUBY_ZENOH_READ_EXACT_TIMEOUT_MS` で上限がある (今回の直しの外)。
- ピンは push 前のコミットを指す。push の後でこのブランチのピンがそのまま使える。
- 一時の printf を入れた zenoh-pico の写しと試しの台本はスクラッチパッドに置いた (コミットしていない)。

## 8. 端末の今

- P4-Nano は最終のファーム (`Z_FEATURE_AUTO_RECONNECT=1` + 53e7535、printf なし) で動いている。焼き方はアプリの区画だけ (/home は残る)。
- 立ち上げたオセロは止めた。家のルータのコンテナは動いたまま。
