## 3. Step 1: 鳴きの秘匿

### 3.1 何が漏れていたか

| 経路 | 今まで | 直し |
|---|---|---|
| `dl` のビット | 鳴ける (まだ答えていない) 人の席のビットを全員と公の見え方に出していた | 席の見え方だけに出す。答える前の候補の席は自分のビット 1 つ、ほかの席 (候補でない席、答えた席) は「自分以外の 3 席」のビット (誰でも同じ値)。公の見え方 (put・`table`・観戦者) には鳴きの窓の間 `dl` を出さない |
| 版 `v` | 答えるたびに `changed` で全員の版が上がり、put も出ていた。ビットが減るたびにも上がった | 答えは答えた席の見え方だけを変える (その席の `v` が卓の版 + 1、ボタンが消える)。卓の版は上げず、put しない (`Table#unsaved?`、`Host#step` は保存だけ)。窓の始まりの `set_deadline` も版を上げない (人の入った窓が CPU だけの窓より版が 1 つ多く進むのを止めた)。窓が決まったときに版を 2 つ進め、答えた席の見えていた版を必ず越える |
| `ev` | 全員がパスしたとき、最後のパスの席 (候補だった席) が `[10, 席]` で残ることがあった (河底のパスで流局したとき) | 決まったあとのパスは `[10, -1]` |

- 残るもの (ユーザの決定どおり): 鳴きの窓があること (`r[7]` が鳴き) と、人が入った窓は長い (最大 `call_seconds`) こと。「ほかの人の答えを待っています」は誰とは言わない。

### 3.2 古いアプリと新しいホスト、その逆

- 古いアプリ (develop) と新しいホスト: 古いアプリは `bits & ~mine != 0 && bits & mine == 0` で待ちの表示を出す。候補でない席・答えた席には「3 席のビット」が来るので今までどおり「待っています」が出る。候補の席は自分のビットなので出ない。答えた席の `v` が 1 つ進むので、古いアプリでもボタンが消える (古いアプリは `v` が変わったときだけ描き直す)。
- 新しいアプリと古いホスト: 新しいアプリは「鳴きの窓で自分に答えるものが無い」(自分のビットが無い) なら待ちの表示を出す。古いホストのビットからも同じ判断になり、誰かは出さない。CPU だけの窓 (約 0.7 秒) でも出る (人の窓と見分けにくくした)。

### 3.3 試験 (`test/test_mahjong_call_privacy.rb`、新規 5 件)

- 各席の選択肢は自分のものだけ。`dl` の値 (候補は自分のビット、ほかは 3 席)、公の見え方・観戦者に `dl` なし。
- **2 つの卓を比べる**: 席 3 がポンできる卓とできない卓 (ほかは同じ) で、席 0・1・2・観戦者・put・公の見え方を、席の並びと自分の手牌と観戦者の手牌を除いて **キーごとに一致** を確かめる。席 3 がポンと答えたあとも同じく一致し、`dirty?` (put) は false、`unsaved?` は true、席 3 の `v` だけが 1 進む。
- 窓が決まると全員の版が答えた席の見た版を越える。全員パスのとき `ev` は席を名指ししない。
- 人 4 人の半荘を最後まで (鳴きはときどき): 鳴きの窓の毎ステップで、各席の `dl` が「自分のビット」か「3 席」以外にならないこと、観戦者・put・公の見え方に `dl` と選択肢が無いこと (窓 10 回以上)。

## 7. Step 5・6: 小さい項目と 1 通の大きさ

### 7.1 `?w=640&h=360` の黒い画面

- 原因: 表示の合成 (`main/drivers/display_local/display_local_task.cpp`) は、基本の画面のときに **640x360 の canvas を飛ばす** (全画面の高解像度に入る直前・出た直後のアプリの canvas を 426x240 に描かないため)。ページを 640x360 で開くと、基本の画面そのものが 640x360 で、デスクトップも壁紙も 640x360 の canvas なので、全部が飛ばされて黒くなっていた (機械の起動・描画の命令は正常: ブラウザの console のログで確かめた)。
- 直し: 飛ばすのは基本の画面が 640x360 でないときだけ。Tab5 (基本 426x240) の動きは変わらない。直したあと 640x360 のページでデスクトップと卓のアプリが出た。

### 7.2 `tools/mahjong_local.rb up` の「not up after 60 s」

- 原因: ログの読み始めを `File.size` (バイト) で取り、`File.read(log)[start..]` (文字の位置) で切っていた。ログに日本語の名前が入ると文字数がバイト数より少なくなり、切り出しが空になって「up」を見つけられなかった (手元のログで 12,495 バイト・12,047 文字)。
- 直し: バイトで読む (`seek` して `read`)。

## 9. 追加: 部屋の中のブラウザの名乗り (案 A)

### 9.1 作り

- ブラウザ版 (`wasm/web/main.js`): 部屋のリンクで開いたとき、部屋ごとに一度 16 バイトの秘密を `crypto.getRandomValues` で作り、localStorage (`fmrb_room_secret_<部屋の ID>`) に残す。ノード ID は `wasm-` と SHA-256(`<部屋の ID>:<秘密>`) の先頭 6 桁 (今までと同じ形なので ACL・console・正規表現はそのまま)。読み直しても同じ ID、別の部屋では別の ID。2 つ目のタブは残さない秘密を別に作る (前の「2 つ目のタブは別の ID」と同じ)。SHA-256 はページの中で同期で計算する (`crypto.subtle` は非同期で、安全な文脈の外に無いため)。
- 秘密は機械に起動前のファイル (`/flash/etc/asterism_room_secret`、アプリからは `/etc/asterism_room_secret`) で渡す。設定の引数 (`--fmrb-conf`) はログに出て設定のファイルに残るので使わない。/flash/etc は毎回の訪問で束から作り直される。卓のアプリは秘密を画面にもログにも出さない。
- 卓のアプリ: 秘密があるとき (部屋の中) だけ `join(name, secret)`・`mine(secret)` (無ければ今までどおり 1 引数・0 引数)。断られたら「この部屋での名乗りが合わない (部屋のリンクを開き直す)」。
- ゲームホスト: 監督が部屋のホストに部屋の ID (`room_id`、rooms.json の room。部屋の鍵の room と同じ) を渡し、ホストが卓に渡す。卓は `room_id` があるとき、`join`・`mine` で、呼んだノード (`Asterism.current_call.from`) が秘密から計算した ID と違えば `{"error" => "identity"}`。メンバーは秘密の SHA-256 を持ち (保存もこれだけ、秘密そのものは保存しない)、同じ 6 桁になる別の秘密は `"taken"`。部屋の外 (家の LAN、常設の卓) は何も確かめない。`Remote::METHODS` の `join`・`mine` は可変 (-1)。`bin/mahjong-bots --room <部屋の ID>` はボットごとに秘密と ID を作る。

### 9.2 確かめたこと

- 試験 (`test/test_mahjong_room_identity.rb`、8 件): ID の形と、部屋・秘密で変わること / ほかのメンバーの ID での `join`・`mine` は秘密なし・別の秘密・形の違う秘密のどれでも断られ、自分の ID では別のメンバーになり席は取れない / 読み直しで同じ秘密から同じトークンと席 / 保存のファイルに秘密が無く、読み戻したあとも確かめる / 同じ 6 桁の 2 つの秘密 (強制) は `"taken"` / 部屋の外は確かめない / 呼び出しの引数の有無 / ホストの卓に `room_id` が届く。監督の試験に `room_id` を足した。
- ネットワークを通して: 手元の zenohd に `room_id` つきのホストを 1 つ起こし、秘密から作った ID の CRuby で `join` (秘密なし → identity、秘密あり → トークン)、`mine` (正しい秘密 → トークン、違う秘密 → identity) を確かめた。
- ページの SHA-256 は "abc" と 100 文字で標準の値と一致。

### 9.3 残る弱さ (直していない)

部屋の中では全員が同じ枠の証明書でつなぐので、メンバーがホストのキー (`room/<slot>/asterism/games/...`) に queryable や state の put を出して、ほかのページが `join` に付けて送る秘密を集められる。直すなら、枠ごとにホスト用の証明書を別に作り、games のキーの queryable と put をホストだけに許す ACL にする (親が計画する)。asterism-games README "Who joins" にも書いた。

### 14.1 牌の角の丸め (`tools/mahjong_tilegen.rb`)

- 描き終わったセルに後からかける処理にした (「rounded corners」の節)。シートを手で直したあとでも、もう一度かければ角が戻る。
  - `--round DIR`: `DIR/tiles_hand.bmp`・`tiles_river.bmp` だけを丸める (その場で書き換える。変わらなければ書かない)。
  - `--layout-sheets SRC DST`: 最初に元の 2 枚を丸め、そのあと拡大 → その大きさで丸め直し → 回転、の順で large/ のシートを作る。側面 (`tiles_side.bmp`) も回す前に丸める。
  - `--sheets`: 描いたあとに丸める。
- やり方: セルを正立の向き (厚みが下) で見て、4 つの角それぞれで、半径 r の四分円の外の画素を透過 (0xE3) にし、透過からの距離が t 以内 (t は縁の太さ: 1 倍で 1、2 倍で 2) の画素を縁の色 (セルの上辺の真ん中の色) にする。縁の内側で透過か縁の色が残っている画素 (拡大した角の名残) は、その行の角の外の色 (面・厚み・影) にする。角の正方形 (r + t + 1) の外は触らない。2 回かけても変わらない (確認)。下の角は厚みと影の行がそのまま丸い縁で終わる。
- 半径 (`CORNER_R`、シートごと):

| シート | セル | r |
|---|---|---|
| `tiles_hand.bmp` | 42x56 | 3 |
| `tiles_river.bmp` | 24x32 | 2 |
| `tiles_hand2_a/b.bmp` | 84x112 | 5 |
| `tiles_river2_r0/r90/r180/r270.bmp` | 48x64 (64x48) | 4 |
| `tiles_river_r90/r180/r270.bmp` | 32x24 (24x32) | 2 |
| `tiles_side.bmp` | 32x20 / 20x32 | 2 |

- 絵柄は変えていない: 変わった画素は全部角の正方形の中 (`tiles_hand.bmp` 1,064 画素、`tiles_river.bmp` 456、`tiles_hand2_a.bmp` 880、`tiles_river2_r90.bmp` 1,064、`tiles_side.bmp` 36。角の外は 0)。前の丸め (1 画素) は描画の `body` に残っている (PNG の出力用)。
- 大きさ: セルの並びもファイルの大きさも同じ (非圧縮の BMP)。`tiles_hand.bmp` 95,158 B、`tiles_river.bmp` 31,798 B、`tiles_hand2_a/b.bmp` 189,238 B、`tiles_river2_*.bmp` 123,958 B、`tiles_river_r*.bmp` 31,798 B、`tiles_side.bmp` 3,382 B。前後で 0 B の差。
