## 4. 見立てと違った点

### 4.1 ハッシュのパターンのリテラルは「動く」のではなく「何にでも合う」

C6 の報告 (2.3) は `in {x: 3}` を「動く」としていたが、**値が 4 でも合う** (`case {x: 4} in {x: 3}` がその枝に入る、`{x: 7} in {x: 8}` が true)。C6 は合う側しか試していなかった。原因はクラスが合わないのと同じ 1 つの不具合で、パターンの値を生成するときに比べる相手の値を上書きしている (5 章)。asterism の README の Limits は「範囲も使える」とも書いていたが、ハッシュの値の位置では範囲も合わない。両方を README で直した。

### 4.2 記録と合わなかった古い注意

- `defined?` はアプリの VM で動いた (定数・無い定数・インスタンス変数の 3 つとも CRuby と同じ答え)。「picoruby に defined? が無い」は今の版には当てはまらない。
- `Array#pack` / `String#unpack` もある (R3 の記録どおり。mruby-pack が入っている)。「picoruby に pack が無い」は古い。
- クラスのメソッドからトップレベルや組み込みの定数を裸で引く形、包むモジュールの定数を引く形は、どれも動いた。取り込んだクラスの定数をモジュールのメソッドから裸で引く形は、**CRuby でも NameError** で、PicoRuby だけの穴ではなかった (`self.class::CONST` が全部の Ruby で正しい書き方)。

### 4.3 新しく見つけたもの (どれも PicoRuby master では直っている)

- `protected` のメソッドを同じクラスの別のインスタンスから呼ぶと NoMethodError (試しの eval を通さない、直のコンパイルでも同じ)。
- rescue 修飾子の中で `$!` が nil。
- `Module#name` が無い (`to_s` はある)。
- **eval の罠**: アプリのファイルのトップレベルにあるローカル変数と同じ名前の新しいローカルを、eval した文字列の中で代入すると SyntaxError (コード生成の「Can't find local variables」)。試しのアプリの末尾の `rescue => e` のせいで、`e` を使う試しが全部落ちた。PicoRuby `c932f70b` の host ビルドでも再現し、master では直っている。試しのアプリはトップレベルのローカルを `rprof_top_error` 1 つにして避けた。

### 4.4 測定

- 再帰の深さの上限: アプリの VM 501、mruby / PicoRuby master 506、CRuby 約 10,000。
- ブロックつきの呼び出しはメソッド呼び出しの 2.1-2.6 倍 (CRuby は 1.2-1.4 倍)。sim (x86-64) の値なので、機体の絶対値ではない。比を見る。
- C のスタックの深さ (C から Ruby へ戻る呼び出しごとの消費) は sim では測れない。A1 の 5.1 の実測 (16 KB のうち 8.1 KB / 10.7 KB / 12.4 KB) を文書に引いた。

## 5. case/in の上流報告

- 下書き: `doc/ruby_asterism/upstream/picoruby_case_in.md` (英語)。再現: `case_in_repro.rb` (CRuby・mruby・PicoRuby で走る)、`flash/app/test/case_in_repro.app.rb` (同じ内容を、eval を通さずアプリとしてコンパイル)。
- 宛先: PicoRuby のコンパイラは submodule `mrbgems/mruby-compiler` = `picoruby/mruby-compiler2` で、これは `mruby/mruby` の `mrbgems/mruby-compiler` の写し (README が「直しは mruby/mruby へ」と書いている)。よって宛先は mruby/mruby。
- 上流の状態: 両方とも直っている。
  - ハッシュの値: `0e6bac0e5a7e` (PR #7507、2026-09-05)。
  - ブロックの中の束縛: `680084ac1275` (PR #7562、2026-09-08)。
  - `picoruby/mruby-compiler2` `a2c72afb` (2026-10-02) に同期済みで、PicoRuby master `a90afd12` がそれを指している。同じ issue は無い (`gh search issues` で 3 つのリポジトリを見た。直しは issue 無しの PR で入っていた)。
- 原因 (コンパイラの `codegen_pattern`):
  1. ハッシュのパターンの値の位置だけ、比べる相手の値のレジスタが `cursp()` と同じ位置に残っていて、値のパターンを生成するとそこに上書きする。
  2. 束縛は今のスコープの `lv_idx` しか見ず、外のスコープの変数だと何もしない (Prism が持っている depth を使っていない)。
- 直しの候補: `picoruby_case_in.patch`。上流の 2 つのコミットを `10408c3` に移したもの (1 か所だけ手で合わせた)。PicoRuby `c932f70b` の host ビルドに当てて、再現の 4 本が NG から ok になることを確かめた。Family mruby の木には当てていない。
- 判断: 上流で直っているので issue は出さない方がよい。Family mruby がすべきことは、vendored の PicoRuby を `mruby-compiler2` `a2c72afb` 以降を指す版へ進めること (case/in の他の差、`protected`、`$!`、eval の罠も一緒に直る)。大きすぎるなら、上の patch を lib/patch の仕組みで当てる手がある。どちらもこの作業の範囲外なので、やっていない。
- 気になった点: 手元の docker image `kishima/mruby:4.1.0-rc2` (中のソースは直しを含む `3375f17`) の mruby は、2 つとも NG のままだった。中の binary が別の時点のソースから作られたものかもしれないが、確かめていない。上の判断には使っていない (master を自分でビルドして確かめた)。
