# Z1 報告: sim で Zenoh の最小の疎通

> 状態: 完了 (検収待ち) | 更新: 2026-10-06 | instruction_z1.md の実装と確認の記録。sim の mruby アプリと親リポジトリの zenohd が put / subscribe で往復した。標準構成と互換構成の両方で受け入れ条件 1-9 を満たした

## 1. 結果の要約

- zenoh-pico 1.10.1 を PIN ファイルで固定し、`rake zenoh:setup` で vendor/zenoh-pico に取得する形にした。
- picoruby-zenoh gem (`Zenoh`) を lib/add/picoruby-asterism-zenoh/ に作り、Linux のビルド構成にだけ入れた。
  Family mruby の API は一つも使っていない。
- zenohd 1.10.1 を親リポジトリの docker-compose.yml に足した。PC からの確かめは tools/fmrb_zenoh.rb。
- **読み取りのタスクは要らなかった。** zenoh-pico のシングルスレッドの構成と `zp_spin_once` を
  アプリの `_spin` (on_update) から回すだけで、受信・keep-alive・lease が回る。
- ただし zenoh-pico 本体の POSIX の TCP の層 (tcp_posix.c) はそのままでは使えなかった (4 章)。
  gem が自前の TCP の層 (src/zp_tcp_posix.c) を持ち、vendor/ の中は書き換えていない。

## 3. API の一覧

| 呼び出し | 戻り値 | 例外・注意 |
|---|---|---|
| `Asterism::Zenoh::Session.open(locator)` | `Asterism::Zenoh::Session` | mode は client 固定。接続できないと `Asterism::Zenoh::Error` (`cannot open a session to <locator> (<code>)`)。接続の間は止まる (connect の上限 3 秒 + 名前の解決) |
| `session.put(key, payload)` | `nil` | payload は String (そのままのバイト列)。key が不正なら `ArgumentError`、閉じたセッションや送信の失敗は `Asterism::Zenoh::Error` |
| `session.subscribe(key, depth = 16)` | `Asterism::Zenoh::Subscriber` | key は key expression (`fmrb/**` も可)。depth は 1..1024、溜めておける件数 |
| `session.poll(steps = 8)` | `true` / `false` | `zp_spin_once` を最大 steps 回。止まらない。セッションが閉じていたら `false` |
| `session.closed?` | `true` / `false` | |
| `session.close` | `nil` | 購読も閉じる。何度呼んでもよい。呼ばなくてもよい |
| `sub.each_pending { \|key, payload\| }` | 取り出した件数 | 呼んだ時点で溜まっている分だけを古い順に。ブロック無しなら `[[key, payload], ...]` |
| `sub.pending` / `sub.received` / `sub.dropped` | Integer | 溜まっている数 / 受けた総数 / 溢れて捨てた数 (古いものから捨てる) |
| `sub.close` / `sub.closed?` | | close の後も溜まった分は取り出せる |
| `Asterism::Zenoh::PICO_VERSION` | String | `"1.10.1"` |

指示書の目安からの変更点: `subscribe` に省略できる `depth` を足した、`poll` に省略できる `steps` を足して
真偽を返すようにした、`each_pending` をブロック無しで呼ぶと配列を返す。いずれも目安の呼び方はそのまま動く。

中の作り:

- 受信のコールバック (`zp_spin_once` の中から呼ばれる) は VM を触らない。key と payload を
  `z_malloc` で確保した 1 本のバッファに写して、購読ごとのリング (`depth` 件、`mrb_malloc`) に入れる。
  満杯なら最古を捨てて `dropped` を数える。`each_pending` が Ruby の String を作り、バッファを返す。
- Session と Subscriber はどちらの順で解放されても安全にした。セッションは生きている購読の一覧を持ち、
  閉じる前に購読を外して切り離す。購読はセッションを指す Ruby の参照 (`@session`) も持つ。
  VM の終了 (mrb_close) はオブジェクトを順不同で解放するため。
- 確保は gem の構造体が `mrb_malloc`、zenoh-pico と受信値が zenoh-pico の `z_malloc` (Linux では malloc)。
  fmrb_mem は使わない (README に理由を書いた)。

## 4. 見立てと違った点・踏んだ罠

### 4.1 zenoh-pico の POSIX の TCP の層が、ポーリングにも sim にも合わない

`tcp_posix.c` を読んで分かったことが 3 つあり、gem の `src/zp_tcp_posix.c` に置き換えた
(関数の名前と役割は同じ。元のファイルは EPL-2.0 OR Apache-2.0 で、出所を見出しに書いた)。

1. **読み取りが待つ。** client の読み取りのタスクは `zp_spin_once` のたびに `recv` を呼び、ソケットの
   受信の時間切れ (SO_RCVTIMEO、既定 100 ms) まで待つ。データの無い poll のたびにアプリが 100 ms 止まる。
   置き換えでは `MSG_DONTWAIT` で即座に返す。「まだ無い」は SIZE_MAX で、読み取りのタスクは元から
   それを「読むものが無い」として扱う。ハンドシェイクの `read_exact` だけは待つ (下)。
2. **EINTR を失敗として扱う。** sim の FreeRTOS の POSIX ポートは SIGALRM (SA_RESTART なし) で刻むので、
   待っている系統呼び出しはしょっちゅう EINTR で戻る (doc/sim_boot_eintr と同じ現象)。元の実装は
   `recv` / `send` / `connect` の EINTR をリンクの失敗にして、セッションを落とす。置き換えではすべて
   再試行する (`connect` は EINTR の後も裏で続いているので、EINPROGRESS と同じく完了を待つ)。
3. **connect に上限が無い。** 届かない相手だとカーネルの既定 (分の単位) まで止まる。置き換えでは
   非ブロッキングの connect + poll で 3 秒 (`PICORUBY_ZENOH_CONNECT_TIMEOUT_MS`)。

`read_exact` (ハンドシェイク) は、1 バイト目までは 1 回あたりソケットの時間切れ (100 ms) まで待って
時間切れを返し (呼ぶ側が締め切りまで繰り返す)、1 バイト目が来た後は途中で切らずに最大 5 秒待つ。元の
実装は途中まで読んだところで時間切れになると読んだ分を捨てる。

listen / accept は client だけの構成なので、失敗を返すだけにした。

### 4.2 REST の GET は保存が無いと空

zenohd の REST の GET は Zenoh の問い合わせ (get) なので、put しただけの値は返らない (`[]`)。
zenohd にメモリの保存 (storage_manager、`fmrb/**`) を設定し、最新の値を答えさせた。そのため
`tools/fmrb_zenoh.rb get` が読めるのは `fmrb/**` の下だけ。REST は既定の符号化 (zenoh/bytes) の値を
base64 で返すので、ツールの側で戻す。

### 4.3 sim には VM プールの周期ダンプが無い

instruction は「VM プールの値」を求めているが、`fmrb_app_dump_vm_pools()` を呼ぶ周期ダンプは
status_led のタスクの中にあり、Linux の sim では status_led のタスクが起動されない
(boot.c の Linux 版の init_hardware に status_led_start が無い。gdb で全スレッドを見ても居ない)。
そこで次の 3 つで代えた。いずれも既存の仕組みで、コードの外側の変更はしていない。

- debugd の `ps` (sim_app の ps と同じ) が返す、各 VM の `mem_used` (estalloc のプールの使用量)。
- 試しのアプリが 5 秒ごとにログに出す `FmrbApp.pool_used` (自分の VM のプール)、
  `FmrbApp.sys_pool_info[:used]` (共有の system プール)、`GC.stat[:live]`。
- core のプロセスのソケットの数と VmRSS (/proc)。

### 4.4 撤回した仮説

- 「zenohd を止めたときの接続の失敗は即座に返る」: core のコンテナから `zenohd` の名前の解決に失敗する
  まで約 3.9 秒かかった (docker の内蔵 DNS が外へ問い合わせるため)。その間もほかのタスクは動いていた
  (host の GFX STATS、transport のログが途切れない)。アプリの画面は接続の間 "connecting" のまま。
- 「最初の 5 回の開閉で core の RSS が少しずつ増える (11008 → 11264 kB) のはリーク」: 別のアプリ
  (net_probe) を挟んだ後に zenoh_echo を 8 回開閉すると RSS は 15652 kB で 1 kB も動かなかった。
  初回の確保によるページの増え方だった。ホストで zenoh-pico 単体の開閉 5 回を AddressSanitizer
  (LeakSanitizer) で回してもリークの報告は無い。

## 6. 大きさ

Linux (x86-64、mruby のビルドの既定の -O3 -g) のオブジェクトの合計:

| | text | data | bss |
|---|---|---|---|
| zenoh-pico (128 本) | 198,284 | 440 | 0 |
| gem の C (zenoh.c + zp_tcp_posix.c) | 7,264 | 32 | 0 |

x86-64 の -O3 なので ESP32 (-Os、RISC-V / Xtensa) の見積もりには使えない。公表値は基本構成で
flash 約 80 KB / RAM 約 12 KB。Z2 で実測する。実行時の確保は 1 セッションで受信のバッファ
(BATCH_UNICAST_SIZE 2 KB と断片の組み立て 4 KB まで) + 送信のバッファ + 購読ごとのリング
(16 件 x 24 バイト + 受けた値)。

## 7. 残件と、Z2 (ESP32) で気をつけること

- **TCP の層は POSIX 用だけ。** ESP32 では zenoh-pico の ESP-IDF の層 (tcp_esp32.c / lwIP) を使うことになるが、
  4.1 の 1 (読み取りが SO_RCVTIMEO まで待つ) は同じ形のはずで、そのままでは poll のたびにアプリが止まる。
  ESP32 用にも同じ置き換えを作るか、Z_CONFIG_SOCKET_TIMEOUT を小さくするかを Z2 で決める。EINTR は
  ESP-IDF では起きない見込み。
- **ルータが消えたことに気付くのが遅い。** client の読み取りは `recv` が 0 (相手が閉じた) を返しても
  「読むものが無い」と扱うので (zenoh-pico 本来の作り)、検出は lease (10 秒) か送信の失敗まで待つ。
  今回は約 20 秒。早く知りたいなら gem の読み取りで 0 を検出してセッションを閉じる形にできるが、
  利用者から見た動き (いつ false になるか) の選択なので、ここでは変えていない。
- **自動の再接続は切ってある。** 切れたらアプリが開き直す。入れるかどうかは利用者から見た動きの選択。
- **接続は止まる。** `Session.open` は名前の解決と connect の間、アプリを止める (sim では最長約 4 秒、
  ほかのタスクは動く)。実機で優先度の高いタスクから呼ぶと周りを止める。非同期の open にするかは
  後で決める。
- **sim の周期ダンプが無い** (4.3)。VM プールの値を Linux でも見たいなら、status_led か別のタスクで
  `fmrb_app_dump_vm_pools()` を呼ぶ必要がある (Z1 の範囲の外なので触っていない)。
- **溢れて捨てる経路を sim で通せていない。** 確かめるなら `subscribe(key, 2)` のアプリで送る。
- **`rake setup` が毎回 zenoh-pico を確かめる。** ESP32 のビルドでも `rake setup` が gem と zenoh-pico を
  picoruby の木にコピーする (ti と同じ扱い)。ESP32 の構成は gem を参照しないのでビルドの中身は
  変わらないが、新しい checkout では最初の `rake setup` で zenoh-pico の取得 (ネットワーク) が要る。
- zenoh-pico 本体の警告 (session.c の未使用の変数など 5 件) はビルドに出るが、上流のもので害は無い。
- 画面の失敗の文言は窓の幅 (46 文字) で切っている。
