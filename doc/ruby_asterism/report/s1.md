# S1 報告: MuJoCo の 2 輪の台車を ROS 2 経由で動かす

> 状態: 完了 (検収待ち) | 更新: 2026-10-09 | instruction_s1.md の実装と確認の記録。mujoco_ros2_control (Jazzy、0.1.2、MuJoCo 3.12) で自作の 2 輪の台車を docker の中で動かし、diff_drive_controller・joint_state_broadcaster・imu_sensor_broadcaster が active になった。カメラは 160x120 の JPEG を 5.00 Hz (1 枚 約 2.8 KB)。CRuby・sim・P4-Nano から `/cmd_vel` で操縦し、車輪のオドメトリは真の位置と 0.2 %・0.3 度で合った。asterism-console は CompressedImage を画像として出し、走りを MCAP に記録して時間の帯で画像と線グラフを見返せる。止まる条件には当たらなかった

## 1. 結果の要約

- 像: `fmruby-mujoco-jazzy:local` (2.32 GB)。`ros:jazzy-ros-base` に rmw_zenoh と mujoco_ros2_control ほかを apt で入れた
  (`docker/mujoco/Dockerfile`)。重ね合わせは `docker-compose.mujoco.yml` (新規) と、WSLg の viewer 用の
  `docker-compose.mujoco-wslg.yml` (新規)。既存の compose のファイルは変えていない。
- 台車: 自作の MJCF (`docker/mujoco/model/rover.xml`、`scene.xml`) と URDF (`rover.urdf.xacro`、ros2_control の記述つき)。
  箱の車体、2 輪 (半径 0.05 m、間隔 0.24 m、速度の servo)、後ろの補助輪、IMU、前向きのカメラ。床・照明・色の柱 4 本・箱 2 つ。
- 制御器: diff_drive_controller (`/cmd_vel` から `/odom`)、joint_state_broadcaster、imu_sensor_broadcaster。3 つとも active。
- カメラ: mujoco_ros2_control のカメラの部品 (CameraPlugin) が 160x120 の生の画像を 5 Hz で出し、image_transport の
  republish が JPEG にして `/camera/image/compressed` に出す。描画は画面の無い EGL (Mesa、CPU)。実測 5.00 Hz、1 枚 2,757-2,807 B。
- Asterism の側: CRuby の例 `asterism/examples/ros2_rover.rb` (前進 1 m・左に 90 度を odom で止め、真の位置と比べる。
  キーボードでも操縦できる)。Family mruby の試しのアプリ `flash/app/test/ros2_drive.app.rb` (矢印キーで操縦、odom の
  位置・向き・速さを出す)。sim と P4-Nano で動いた。
- asterism-console: CompressedImage (JPEG / PNG) を、値を眺める欄・トピックの詳細・記録の時間の帯で画像として出す。
- CPU: 画面なしの台車のコンテナ全体で 1 コアの約 58 %。WSLg の viewer を出すと、GPU を渡せば約 90 %、渡さないと約 13 コア。

### 2.2 台車のモデル

| 項目 | 値 |
|---|---|
| 車体 | 箱 0.30 x 0.20 x 0.08 m、2.0 kg。重心は車軸より 3 cm 後ろ (後ろの補助輪に載る) |
| 車輪 | 半径 0.05 m、幅 0.025 m、0.2 kg、間隔 0.24 m。平たい楕円体。`<velocity kv="5">`、力の上限 2 Nm |
| 補助輪 | 後ろに摩擦なしの球 (condim 1)。前に 5 mm 浮かせた球 (急に止まったときに前へ倒れないための当て) |
| IMU | 車体の上の site に framequat・gyro・accelerometer (mujoco_ros2_control の決まりの名前 `imu_sensor_quat` など) |
| カメラ | 前向き、高さ 0.14 m、fovy 60 度、`resolution="160 120"` |
| 真の位置 | 車体の free joint を `odom_free_joint_name` に指定し、`/ground_truth/odom` に出す (オドメトリの確かめ用) |
| 物理 | timestep 2 ms、implicitfast、elliptic の摩擦の円錐、impratio 10 |

車輪の半径と間隔は `rover.xml`・`rover.urdf.xacro`・`controllers.yaml` の 3 か所に書いてある (README に明記)。

### 2.3 制御器と話題

| 話題 | 型 | 頻度 |
|---|---|---|
| `/cmd_vel` (入力) | geometry_msgs/Twist | 送る側しだい。0.5 s 来ないと止まる |
| `/odom` | nav_msgs/Odometry | 20 Hz |
| `/ground_truth/odom` | nav_msgs/Odometry | 100 Hz |
| `/imu` | sensor_msgs/Imu | 50 Hz |
| `/joint_states` | sensor_msgs/JointState | 50 Hz |
| `/camera/image/compressed` | sensor_msgs/CompressedImage | 5 Hz、160x120 JPEG (品質 80) |

- Jazzy の diff_drive_controller は TwistStamped しか受けない (`use_stamped_vel` は無くなっていた)。twist_stamper で
  `/cmd_vel` (Twist) を `/cmd_vel_stamped` にして渡す。時刻は sim の時計 (use_sim_time) で付ける。
- 制御器の話題の名前の付け替えは、spawner の `--controller-ros-args` で行う (ros2_control_node に付け替えを渡す書き方は
  非推奨の警告が出た)。
- 加速の上限: 直進 0.5 m/s^2、旋回 2 rad/s^2 (4 章の理由)。

### 2.4 カメラの流れ

```
MuJoCo の camera "camera" (160x120)
  -> CameraPlugin (5 Hz、EGL の surfaceless、Mesa llvmpipe)  /camera/image_raw (sensor_msgs/Image、57.6 KB)
  -> image_transport republish (raw -> compressed、JPEG 品質 80)  /camera/image/compressed (約 2.8 KB)
  -> camera_watch.py (ROS の購読者。republish を起こしておく、30 s ごとに頻度を記録)
```

- 画面が無いと CameraPlugin は GLFW の初期化に失敗して EGL に切り替える (ログに `EGL: Vendor: Mesa Project`)。GPU を
  docker に渡さなくても Mesa が CPU で描くので、osmesa は要らなかった。
- republish は ROS の購読者がいるときだけ圧縮する (5 章)。console の購読は ROS の購読者に数えられないので、
  `camera_watch.py` を常に購読させている。

### 3.1 操縦とオドメトリ

オドメトリの確かめは、毎回 `/odom` と `/ground_truth/odom` (MuJoCo の free joint の真の位置) を同時に読んで比べた。

| 送り手 | 動かし方 | `/odom` | 真の位置 | 差 |
|---|---|---|---|---|
| CRuby (`ros2_rover.rb`) | 前進 1 m を odom で止める、左に 90 度 | 1.0003 m、90.28 度 | 0.9984 m、89.98 度 | +0.20 %、+0.30 度 |
| CRuby | 前進 1.5 m、90 度 | 1.5002 m、90.09 度 | 1.4974 m、89.79 度 | +0.19 %、+0.30 度 |
| CRuby | 前進 0.8 m、90 度 | - | - | +0.21 %、+0.30 度 |
| sim (`ros2_drive`、矢印キーの注入) | 上を 4 回 (0.2 m/s) 5 s、空白で止める。左 2 回 (0.6 rad/s) 2.6 s | 1.0725 m、93.41 度 | 1.0704 m、93.17 度 | +0.20 %、+0.24 度 |
| P4-Nano (`ros2_drive`、tab5_input の注入) | 同じ | 1.2606 m、114.53 度 | 1.2580 m、114.22 度 | +0.21 %、+0.31 度 |

- CRuby は odom を見て止めるので、ちょうど 1 m・90 度で止まる。sim と機体はキーの注入の間隔で動かす量が決まる。
- 機体で 1 m・90 度より多く動いたのは、注入したキーが機体に届く間隔が延びたため。PC の側で `/cmd_vel` の変わり目の
  時刻を取ると、0.1 s おきに注入した 4 回の「上」が 2.03・2.46・3.02・3.53 s に届き (1 回あたり約 0.5 s)、止める空白は
  8.82 s。0.2 m/s が 5.3 s 続いた。旋回も 0.6 rad/s が 2.95 s 続いた。アプリは押されたとおりに送っている。
- 機体のアプリは `/cmd_vel` を 25 s に 217 回 (8.7 Hz) 送った (目標は 10 Hz)。
- 台車が柱にぶつかると、車輪は回り続けるので odom は進むが、真の位置は止まる (P4-Nano の 2 回目の走りで赤い柱に当たり、
  odom 2.02 m に対し真の位置 1.78 m)。真の位置を出しておく意味が分かる例になった。

### 3.2 asterism-console

host の Ruby で `bin/rails server` と `bin/bridge` を動かし、ヘッドレスの Chromium (console の `script/headless/run`) で
画面を撮った。

| 項目 | 結果 |
|---|---|
| グラフ | ROS 2 のノード 11 (`/mujoco_ros2_control_node`、`/controller_manager`、3 つの制御器、`/robot_state_publisher`、`/twist_stamper`、`/camera_jpeg`、`/camera_watch`、`/mujocosystem`、機体の `/fmruby_drive_fmruby_aaaaaa`) と 29 の話題。機体のノードから `/twist_stamper` への `/cmd_vel`、`/diff_drive_controller` から機体への `/odom` が矢印で出た |
| カメラの画像 | トピックの詳細に 4.87 Hz、14.0 KB/s、最後の 1 枚 2.9 KB と画像。値を眺める欄 (`0/camera/image/compressed/**`) にも画像 |
| 線グラフ | Plots の画面で `/odom` の `pose.pose.position.x`・`.y`。0.8 m の走りで y が 1.0 から 0.2 へ動いた |
| 記録 | `/cmd_vel`・`/odom`・`/ground_truth/odom`・`/imu`・`/joint_states`・カメラ・網の構造を 25 s。5,903 通、3.3 MB、カメラは 125 枚 (5.0 Hz)、失ったもの 0 |
| 時間の帯 | カーソルの位置のカメラの画像 (右の欄と「At the cursor」の縮小画像) と、`/odom` x・y の線グラフを同時に見られた |

console の変更 (asterism-console の docs/s1.md):

- `Bridge::Payload.image`: CompressedImage の CDR から画像の部分を取り出し、`{mime, data (base64), bytes, width, height}`
  にする。JPEG か PNG かは中身の先頭 (magic number) で見る (format の文字列は "rgb8; jpeg compressed bgr8" のように
  決まった形でない)。大きさは JPEG の SOF・PNG の IHDR から。256 KB を超える画像は出さない。
- 話題の頻度の欄は最後の 1 通の先頭 4 KB だけを持っていたので、画像の話題では 1 通をまるごと (256 KB まで) 持つ。
- 時間の帯: 画像を出し、値の表示の `data` (バイト列) は「(2323 bytes, image/jpeg)」に置き換える。
- 試験: 本物の 160x120 の 1 枚を fixture にして 5 件。console の試験は全部で 192 件、失敗 0、rubocop の指摘 0。

## 4. 見立てと違った点・踏んだ罠

- **mujoco_ros2_control はそのまま入って動いた**。apt の 0.1.2 の文書と例 (`mujoco_ros2_control_demos` の
  mobile_base と test_robot) の形で、最初の起動から 3 つの制御器が active になった。カメラと LiDAR は 0.1 系で
  本体から plugin に移っていた (`mujoco_plugins` の YAML で CameraPlugin を指定する。指定しないと自動で登録され、
  非推奨の警告が出る)。
- **EGL は CPU でも動く**。CameraPlugin の EGL は Mesa の surfaceless を使うので、GPU を渡さなくても llvmpipe で描けた。
  osmesa は要らなかった。160x120 を 5 Hz なら負担は小さい。
- **車輪のすべり**。最初のモデル (円柱の車輪、kv 0.5) では odom が真の位置より 2.9 % 長く、旋回は 7.3 度多かった。
  試した順と結果:

  | 変えたこと | 前進の差 | 旋回の差 |
  |---|---|---|
  | 最初 (円柱、kv 0.5、pyramidal の摩擦) | +2.90 % | +7.26 度 |
  | elliptic の摩擦、impratio 10 | +0.91 % | +7.13 度 (旋回に 35 s。servo が弱く、こすれに負けた) |
  | kv 5、力の上限 2 Nm | +4.11 % | +11.31 度 |
  | 車輪を平たい楕円体に | +2.28 % | +5.42 度 |
  | 車輪の接触を硬く (solref 0.004) | +3.13 % | +3.31 度 |
  | **diff_drive_controller に加速の上限** | **+0.20 %** | **+0.30 度** |

  効いたのは最後の加速の上限だった。速さの指令が段で変わると servo が車輪を一気に回し、床の上で空回りする。
  前の変更 (楕円体の車輪、硬い接触、elliptic) は残している (外して確かめてはいない)。
- **送り手が 2 つあると台車がすべる**。機体のアプリ (0 を 10 Hz で送り続ける) を動かしたまま CRuby の例を走らせると、
  2 つの指令が交互に届き、odom の差が +5.5 % になった。機体のアプリを止めると +0.20 % に戻った。README に「送り手は
  1 つ」と書いた。
- **P4 では Odometry の解読が重い**。生成した型で `/odom` (20 Hz) を全部解読すると、機体のアプリの更新の 1 回が長くなり、
  `/cmd_vel` は約 3.3 Hz しか出ず、止める指令が遅れた。受信の輪を 2 にして最新だけを解読しても、poll (受信と解読) は
  1 回 91 ms (最大 122 ms)。Odometry は共分散の行列 2 つ (float64 が 72 個) を持ち、生成した型はそれを 1 つずつ読む。
  アプリに位置・向き・速さだけを読む軽い型 (`Ros2DriveOdom`、共分散を飛ばす) を置くと 21 ms (最大 32-59 ms) になり、
  送信は 8.7 Hz になった。sim では 0-1 ms。String#unpack が無い構成では生成した型に戻す。
- **republish は購読者がいるときだけ動く**。image_transport の republish は ROS の購読者が合ったときだけ生の画像を
  購読して圧縮する。rmw_zenoh は購読者を liveliness のトークンで数える。console の bridge の購読はトークンを出さない
  素の Zenoh の購読なので、console だけが見ていると画像は 1 枚も流れなかった (rclpy で測ったときは流れていた)。
  台車の側に常に購読する小さなノード (`camera_watch.py`) を置いた。Asterism::ROS の購読 (機体・CRuby) はトークンを
  出すので、それだけでも republish は動く。
- **機体の型のファイルが古かった**。P4-Nano の `/usr/share/asterism/msgs` には nav_msgs が無かった (焼いたファームが
  asterism 0.4.1 より前)。tab5_fs で `flash/usr/share/asterism/msgs/nav_msgs` と `geometry_msgs` を送った。
- **tab5_input のキーは 1 回あたり約 0.5 s かかる** (3.1 節)。時間で動かす量を決める試しには向かない。
- **`ros2 topic hz` がコンテナの中で終わらなかった** (`timeout` でも止まらず、後で kill)。頻度は rclpy の小さな
  スクリプトで測った。
- **diff_drive_controller の警告**: 指令が無い間、`Velocity command timed out. Braking.` が 1 秒に 1 回ログに出る。
  動きには関係ない。
- 撤回した仮説: 「すべりは MuJoCo の柔らかい接触の性質 (creep) で、接触の設定で直す」。接触を変えても 2-4 % 残り、
  原因は指令の段の変わり方だった。

## 5. 実測

### 5.1 CPU とメモリ (PC、論理 24 コア)

## 8. S2・S3 への申し送り

- **S2 (Asterism で直接)**:
  - MuJoCo の C のライブラリは像の中の mujoco_vendor にある (3.12.0)。CRuby から FFI で呼ぶならこれか、pip の mujoco
    (3.x、Python の部品と一緒に libmujoco が入る) を使う。pip の mujoco は同じ像で `pip install --break-system-packages`
    で入り、EGL で窓なしに描けた (README の「Offscreen pictures」)。
  - 物理の設定はこの台車で決めたもの (timestep 2 ms、implicitfast、elliptic、impratio 10、平たい楕円体の車輪、kv 5) を
    そのまま使える。ただし ros2_control の外で車輪を回すなら、加速の上限を自分で入れること (段で指令すると空回りする)。
  - 真の位置 (free joint の qpos) は S2 では直接読める。オドメトリの誤差の見せ場に使える。
- **S3 (Tab5 で操縦・画像)**:
  - 画像は 1 枚 約 2.8 KB、毎秒 約 14 KB。機体で受けるときは輪を 1-2 にして最新だけを扱う。生成した
    `sensor_msgs/CompressedImage` の解読はヘッダ・format・data の String だけなので Odometry より軽いはずだが、
    data の取り出しを測ってから決める。
  - Asterism::ROS の購読は liveliness のトークンを出すので、機体が購読すれば republish も動く。camera_watch.py は
    console のために残す。
  - **P4 で大きな型を毎回解読すると、更新の周期が延びて指令が遅れる**。gem の側で「要る欄だけ読む」「列を読まずに
    飛ばす」仕組みがあると、Odometry や CompressedImage が楽になる (gem の課題に足す候補)。今はアプリに軽い型を置いた。
  - 操縦する機体・CRuby・console の再生は同時に 1 つだけにする (2 つあると交互に届いてすべる)。複数を許すなら
    twist_mux のような選び手を台車の側に置く。
  - console の bridge が ROS 2 の話題を記録・監視するとき、購読者のトークンを出すようにすると、republish のような
    「購読者がいるときだけ出す」相手もそのまま記録できる (今は出さない。console の docs/s1.md)。
