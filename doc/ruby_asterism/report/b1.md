# B1 報告: ブラウザ版の Family mruby を網に入れる (手元の http の版)

## 2. Emscripten の層の調べ: 非同期の WebSocket と同期の zenoh-pico

### 2.1 上流の層 (zenoh-pico 1.10.1) の作り

- `src/link/transport/upper/ws_emscripten.c`: POSIX のソケットの関数 (socket / connect / recv / send) を呼ぶ。
  Emscripten はこれを SOCKFS (ソケットの模倣) で受け、connect でブラウザの WebSocket を作る
  (`ws://<host>:<port>/`)。SOCKFS は決して待たない: connect はすぐ戻り、recv は届いた分が無ければ EAGAIN。
- 待ちは上流の層が自分で作る: 読み書きを「1 ms 眠って試す」を時間切れ (ソケットの時間切れ、gem の設定では 100 ms)
  まで繰り返す。connect の後は WebSocket が開くのを待たずに 100 ms 眠るだけ。
- 眠りは `emscripten_sleep` (system.c)。これは ASYNCIFY を要る: wasm のスタックをほどいてブラウザのイベントループに
  一度戻り、その間に WebSocket の受信のイベントが処理される。つまり上流の合わせ方は「ASYNCIFY で同期の呼び出しの
  途中にイベントループを回す」。
- 気づいた上流の不具合: (1) platform/emscripten.h が `<stddef.h>` を読まないので、platform.h を最初に読む
  `src/system/common/platform.c` がコンパイルできない。(2) `z_random_fill` がバッファの先頭 1 バイトにだけ書く。
  (3) recv が 0 (閉じた) と「まだ無い」の区別を付けず、リンクが閉じても lease まで気付かない。

### 2.2 Family mruby の wasm 版とのかみ合わせ

wasm 版は ASYNCIFY を使っていない。FreeRTOS のタスクはそれぞれ Web Worker (pthread) で動き、main() も Worker の中
(PROXY_TO_PTHREAD)。ページの主スレッドは wasm を走らせず、画面・入力・音の橋渡しだけをする (doc/wasm/guide_overview.md)。
このため:

- 待つ間にイベントループを回す必要が無い。WebSocket は主スレッドにあり、主スレッドは機械と無関係に動き続けるので、
  届いたものはいつでも受け取れる。Worker の側は「待つ間、協調スケジューラの CPU を手放す」だけでよい
  (FreeRTOS の待ち = vTaskDelay。待たずに回るタスクが 1 本あると全員止まる、という wasm 版の生存条件)。
- SOCKFS は pthread のビルドでは主スレッドの持ち物で、ソケットの系統呼び出しはすべて主スレッドへ同期で代行
  (proxy) される。ASYNCIFY なしでも SOCKFS は動く。

### 2.3 一つ目の版 (SOCKFS + vTaskDelay) と、その問題

最初は上流の層を SOCKFS のまま書き直した (眠りを vTaskDelay に、見回りの読み取りは待たない、connect は poll で
開くまで待つ、閉じたことを覚える)。最小の試しも asterism_demo もこれで通った。ただし:

- `WEBSOCKET_SUBPROTOCOL` を `null` にする必要があった。SOCKFS は既定で `Sec-WebSocket-Protocol: binary` を求め、
  zenohd は何も返さないので Chrome が握手を拒む (curl で zenohd の応答に subprotocol が無いことを確かめた)。
- 1 回の見回り (zp_spin_once 8 回) が平均 0.47 ms、最大 2.8 ms (最小の試し、主スレッドが暇なとき)。読むたびに
  recv と poll が主スレッドへの往復になる。
- **主スレッドが忙しいと機械全体が止まる。** 代行の呼び出しは主スレッドが空くまで返らず、その間、呼んだタスクは
  協調スケジューラの CPU を持ったまま。遅れの測定のために主スレッドで MessageChannel の短い往復を回し続けたところ、
  rover_cam の 1 回の見回りが 6.3 s・8.4 s・13.5 s かかり (その間 5 秒ごとのログも途切れた = 全タスクが止まった)、
  3 回目で lease が切れてセッションが閉じた。同じ測定を Zenoh なしで回しても機械は止まらない。

ファイルの読み書きも同じ代行だが、ファイルはたまにしか触らない。Zenoh は毎回の見回りで代行するので、主スレッドの
重い処理にいつもさらされる。

### 2.4 採った形: 主スレッドの WebSocket と共有メモリのリング 2 本

wasm/zenoh/zp_ws_emscripten.c。SOCKFS を使わず、JavaScript (EM_ASM) で WebSocket を自分で作る。

| 向き | 主スレッド (JavaScript) | Worker (C、zenoh-pico から呼ばれる) |
|---|---|---|
| 受信 | `onmessage` が `[長さ 4 バイト][中身]` を受信のリングに足し、書いた量を Atomics で進める | 見回りの読み取りはリングを読むだけ。代行も待ちも無い。無ければ「まだ無い」(SIZE_MAX) |
| 送信 | 頼まれたら送信のリングを全部 `WebSocket.send` で送り、読んだ量を進める | リングに書いて、主スレッドに非同期で頼む (MAIN_THREAD_ASYNC_EM_ASM、返事を待たない)。満杯なら譲りながら最大 3 s 待つ |
| 状態 | `onopen` / `onclose` / `onerror` が開いた・閉じたを書く | open は開くまで譲りながら待つ (最大 3 s)。`zp_tcp_socket_closed` はこの値を読むだけ |

- 主スレッドへの同期の呼び出しは開くと閉じるだけ。見回りの経路から代行が消えた。
- 1 回の見回りは平均 0.014 ms・最大 0.93 ms になった (最小の試し、同じ条件で SOCKFS の版は 0.47 ms・2.8 ms)。
- WebSocket は自分で作るので subprotocol の問題も消え、リンクの設定 (`WEBSOCKET_SUBPROTOCOL`) も要らなくなった。
  端点は addrinfo ではなく URL (`ws://host:port/`) で持つ。そのため platform の型を自前のヘッダ
  (wasm/zenoh/zp_emscripten_platform.h、`ZP_SYSTEM_PLATFORM_HEADER` で差し込む) で定義した。上流のヘッダの
  `size_t` の問題もこれで避けている。
- リンクは zenoh-pico から見て datagram (WebSocket の 1 メッセージ = 1 バッチ)。zenohd の ws/ も同じ。
- リングは受信 256 KB・送信 64 KB を 4 本 (セッション 4 つ分) 静的に持つ (計 1.25 MB、BSS なので wasm の大きさには
  効かない)。受信のリングが溢れたら閉じた扱いにする (取りこぼすとセッションは壊れるので)。
- 眠り (z_sleep_*) は wasm 版では vTaskDelay、最小の試しでは usleep (wasm/zenoh/zp_emscripten_wait.h)。
- system 層 (wasm/zenoh/zp_system_emscripten.c) は上流の system.c から、眠りと `z_random_fill` を直したもの。
- gem の約束 (include/picoruby_zenoh_link.h) に合わせた: 見回りの読み取りは待たない、握手の読み取りは最大 5 s、
  送信の時間制限 3 s、閉じたことを `zp_tcp_socket_closed` で返す (gem はすぐセッションを閉じる)。
- 上流のファイルは EPL-2.0 OR Apache-2.0。gem と同じく Apache-2.0 を選び、出所と変更を見出しに書いた。
  ws_emscripten.c は関数の名前と形だけを残して書き直した。

## 6. 打鍵と描画の遅れ (受け入れ条件 5)

測り方: ページに drive の命令 `latency` を足した。入力をリングに入れてから、機械が出した最後のフレームの決めた
四角 (打鍵ならエディタの状態行 `Ln 1, Col N`、マウスなら移動先のカーソルの位置) が変わるまでの時間を、主スレッドで
setTimeout ごとに見る (粒はおよそ 4 ms)。各条件 40 回 x 2。エディタを開いて `a` を打つ。マウスは何も無い所を
行き来する。headless の Chrome (Windows)、同じ PC。

| 条件 | 打鍵 中央値 (ms) | 打鍵 90 % | マウス 中央値 | フレーム/5 s |
|---|---|---|---|---|
| develop (Asterism なし)、エディタだけ | 16.2 / 16.4 | 19.6 / 20.4 | 16.5 / 16.1 | 5 |
| B1、エディタだけ | 16.1 / 15.8 | 19.4 / 18.6 | 15.5 / 16.4 | 5 |
| B1、asterism_demo がつながっている | 31.0 / 24.9 | 35.2 / 47.2 | 16.2 / 16.2 | 85 |
| B1、asterism_demo がつながらない (`?zenoh=ws/localhost:7999`) | 28.7 / 23.6 | 46.6 / 33.2 | 16.5 / 15.6 | 86 |
| B1、rover_cam (カメラ 5 Hz・odom 20 Hz を受けて描く) | 36.8 / 41.9 | 49.7 / 50.1 | 16.0 / 15.9 | 79 |

読み方:

- gem を入れただけでは何も変わらない (1 行目と 2 行目)。
- asterism_demo は、つながっていてもいなくても同じだけ打鍵を遅らせる (3 行目と 4 行目)。差は Zenoh ではなく、
  このアプリが 50 ms ごとに窓を描き直すこと (フレームが 5 秒で 85 枚)。見回りの分は測りの揺れに埋もれる。
- rover_cam の増分も描画が主: アプリ自身の計測で、1 回の更新 (約 67 ms ごと) の見回りと受信の解読が 1 ms (最大 3 ms)、
  JPEG の復号と描画が 1 枚 14-17 ms (5 Hz)。
- マウス (カーソル) はどの条件でも同じ。機械全体が止まることは無かった。SOCKFS の版で起きた秒の単位の停止 (2.3) は、
  リングの版では見回りの経路から代行が消えたので起きない (rover_cam の見回りの最大は 3 ms のまま)。

測りについての注意: 最初の測り方 (主スレッドで MessageChannel を回して待つ) はファイルの代行を飢えさせ、2.3 の停止を
起こした張本人でもあった。setTimeout に変えたので粒が 4 ms になり、2 つの表の値はそのまま比べられない
(最初の測り方での develop の値は打鍵 中央値 2.1-2.5 ms)。上の表はすべて同じ測り方。

## 7. カメラの扱い

- ブラウザ版の表示の側 (display_p4_task の CREATE_IMAGE_FROM_FILE) は、P4 と同じく先頭が FF D8 FF なら JPEG として
  復号に回し、wasm 版ではそれが LovyanGFX の TJpgDec (wasm/backend/display_video_wasm.c、動画の再生と共有) になる。
  新しい API は要らなかった。
- rover_cam は「JPEG を描くのは Modern の実機だけ」としていた判定に `FmrbConst::BOARD == "wasm"` を足しただけ。
  受けた JPEG を `/tmp/rover_cam.jpg` に書いて `create_image` → `draw_image` (P4 と同じ経路)。
- 実測: 受け取り 4.9-5.0 Hz・表示 4.9-5.0 Hz、1 枚の描画 14-17 ms (最大 19 ms)、配信から描画までの遅れ 平均 20-62 ms
  (odom で時計のずれを補正した値)。
- 表示の側が 1 枚ごとに INFO のログを 4 行出す (CREATE_IMAGE_FROM_FILE ほか)。ブラウザではページの console に流れる。

## 8. 見立てと違った点

- 上流の Emscripten の層は ASYNCIFY が前提だった。wasm 版は ASYNCIFY を使っていないので、層は差し替えが要った。
  ただし pthread のビルドでは SOCKFS が ASYNCIFY なしで動くので、一つ目の版はすぐ動いた。問題は動いた後の
  「主スレッドに人質を取られる」性質で、これは測るまで見えなかった (2.3)。
- 図の印: console は「ノード名が `fmruby-xxxxxx` か `linux` なら機体」と決めていて (asterism-console
  lib/bridge/marks.rb、コメントに「sim とブラウザ版は linux に落ちる」とある)、`wasm` は ◈ (CRuby) で描かれる。
  console の手元の作業ツリーで規則に `wasm` を足し、bridge を起動し直すと ▣ wasm と ▣ linux が並んだ。確かめた後で
  元に戻した (console はコミットしていない)。要る直し:

```diff
-    BOARD_NAME = /\A(fmruby-[0-9a-f]{6}|linux)\z/
+    BOARD_NAME = /\A(fmruby-[0-9a-f]{6}|linux|wasm)\z/
```

  ノード名を `linux` に戻せば console は直さずに済むが、sim と同時につなぐと名前がぶつかる。どちらにするかは
  仕様の選択 (ブラウザの ID は design.md 9 章でランダムな ID の案がある)。
- console の bridge と rails はこの作業の中で起動し直した。rails は headless の撮影のために
  `CONSOLE_EXTRA_HOST=host.docker.internal` を付けて起動した (付けないと host の検査で撮影の container が弾かれる)。

## 9. gem について

- picoruby-asterism-zenoh・asterism とも直しは要らなかった (差分なし)。
- 提案 (急がない): Emscripten の platform の層 (wasm/zenoh/ の 3 本) は gem の ports/emscripten/ に移せる形で

## 10. B2 への申し送り

- **wss://**: リンクは URL を自分で組み立てている (`ws://host:port/`、zp_ws_emscripten.c の `_z_ws_endpoint_init`)。
  https のページから使うには、ここで `wss://` を選べるようにする (例: ページが https なら wss、またはロケータの
  設定から)。zenoh-pico のロケータは `ws/` のままでよい (wss は zenoh-pico には無い名前)。リバースプロキシが
  TLS を終えてルータの ws/7449 に流す。
- **ルータの設定の画面**: 今は `?zenoh=` と system_conf の `zenoh_router` だけ。Config に入れるなら、page の
  CONF_KEYS (保存して次回に渡す鍵) に `zenoh_router` を足すかどうかも決める (今は URL の値を保存しない)。
- **ノードの ID**: ブラウザは `wasm` 固定 (/home/asterism_node.txt で変えられる)。複数のブラウザ・公開の版では
  design.md 9 章の案 (最初の起動でランダムな ID、localStorage、Web Locks で 1 つだけ起動) が要る。console の
  機体の判定 (8 章) と合わせて決める。
- **主スレッドの重さ**: Zenoh の見回りは主スレッドを待たなくなったが、ファイルの読み書きは今も代行で、主スレッドが
  忙しいと止まる (rover_cam は 1 枚ごとに /tmp に書く)。ページに重い JavaScript を足すときは気をつける。
- **受信のリング 256 KB**: 見回りの間に届く量がこれを超えると閉じる。大きい画像を高い頻度で受けるなら大きくするか、
  溢れたら古いものを捨てる (今はセッションが壊れるので閉じる)。
- **peer モード**は使えない (ページは listen できない)。ルータ必須。
- **zenohd の ws/** は手元の 127.0.0.1 だけ。別の PC からページを開くなら公開の範囲を決める。
- drive の `latency` / `frames` は残してある (wasm/web/main.js)。主スレッドで回る測りなので粒は約 4 ms。
