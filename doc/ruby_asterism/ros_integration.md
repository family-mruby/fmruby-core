# Asterism の ROS 2 連携の仕様 (案)

> 状態: 案 | 更新: 2026-10-14 | ROS 2 の通信を rmw_zenoh のまま Asterism の網に流し、ロボットごとに ROS のドメインを分けて見分ける。Asterism のキーの形・端末の名前・証明書の仕組みは今の実装 (protocol 1、console 0.1.4、G2 の部屋の計画) に合わせ、ROS を区別できることを要点にする

## 1. 目的と基本方針

- ROS 2 の通信は rmw_zenoh のまま Asterism の網に流し、ロボットごとに ROS のドメインを分けて見分ける。ROS のトピックを Asterism のオブジェクトに包まず、Zenoh でそのまま繋ぐことを優先する (今の `Asterism::ROS` も rmw_zenoh の形 (キー・CDR) で直接話している。R1-R3)。
- 対象は rmw_zenoh を使う ROS 2 のノード。DDS を使う ROS 2 は 8 章の未確定事項。
- 制御に要る速い通信はロボットの中に閉じる。Asterism の網は、指示・監視・記録を受け持つ。
- ドメインで分ける理由: tf・`/clock` など ROS の設計が「1 ドメインに 1 台」を前提にしているため。名前空間で分けると、絶対名のトピックのリマップやフレーム名の前置きが要る。

## 2. キー空間の区分

キーの先頭の塊で、そのキーが何に属するかを機械的に決める。rmw_zenoh のキーはドメイン ID (数字) で始まるので、Asterism のキーと重ならない。Asterism のキーの形は今のまま変えない。

| 先頭 | 属するもの | 例 |
|---|---|---|
| 数字 | ROS 2 (先頭はドメイン ID) | `12/cmd_vel/geometry_msgs::msg::dds_::Twist_/RIHS01_…` |
| `asterism` | Asterism のオブジェクトの網 (今の protocol 1) | `asterism/fmruby-aaaaaa/game/othello` |
| `room` | G2 の部屋 (前置きの下は上の 2 つと同じ形) | `room/03/asterism/wasm-aaaaaa/game/othello` |
| `@` | 生存の印・管理用 (Zenoh と ROS が使う) | `@ros2_lv/12/…`、`@/<zid>/router` |

- ROS のキーの形は rmw_zenoh が決めるもので、Asterism の側では変えない。例の後半 (型名と型のハッシュ) は版によって違うことがある。今の構成 (rmw_zenoh 0.2.11) で確かめた形はドメイン 0 のものだけ (8 章)。
- Asterism は先頭の段では `@` を使わない。アプリの生存の印は `asterism/<ノード>/<アプリ>` (オブジェクトごとに `asterism/<ノード>/<アプリ>/<オブジェクト>`)、プロフィールは `asterism/<ノード>/@profile` で、どれも `asterism` の下 (protocol 1)。
- 区分は ACL の書き方にそのまま使う: ROS は `<ドメイン>/**` と `@ros2_lv/<ドメイン>/**`、Asterism は `asterism/**`、部屋は `room/<枠>/**`。

## 3. 名前の規則

今の名前の付け方を変えない。ROS の名前 (ノード名・名前空間) に入る場合だけ、ROS で使える形に直して使う。

- **Asterism の端末 ID**: 今のまま。Family mruby の端末は mDNS の名前 `fmruby-<MAC の一部>` (焼き直しても変わらない)、ブラウザ版は console のハンドルから `wasm-<ハンドル>`、CRuby は渡した名前。証明書の名前 (CN) と同じにする (今の作り)。
- **拠点の名前**: console の Registry の登録の名前 (証明書の名前、例 `home-kishima`) は今のまま。ハイフンを含んでよい。
- **ロボットの名前**: 拠点の登録に足す「この拠点が持つロボット」の名前。ROS の名前空間 (5 章の群れの例外) や Asterism のノード ID (7 章) に使うので、英小文字で始め、英小文字・数字・アンダースコアだけにする (ROS の名前にはハイフンが使えず、`__` は予約されている)。console は、拠点の登録に足すロボットの名前にだけ、この規則を確かめる。
- 一度決めた ID は変えない。表示名はプロフィール (`Asterism.profile(name:)`) で別に持つ (今の作り)。

## 4. ROS ドメインの割り当て

ロボット 1 台に ROS のドメインを 1 つ割り当て、その対応は console が管理する。ロボットの側の設定は `ROS_DOMAIN_ID` だけでよく、名前空間やリマップは要らない。

- **ドメインの持ち主は拠点の登録**。ロボットは拠点の出入口のルータに繋がるだけで、クラウドへ証明書で繋ぐのは出入口 (例 `home-kishima`) なので、ACL が見分けられる単位は拠点の証明書になる。そこで G1.5 の「代わりに話すノード ID の一覧」と同じ形にそろえる: Registry の拠点の登録はそのままに、その登録に「この拠点が持つロボットとドメインの一覧」(例: `go2_lab` = 12) を持たせる。
- 表示は「拠点 / ロボット」(例: `home-kishima / go2_lab`) の形にし、番号だけで出さない。
- **ドメイン 0 は「拠点の中だけ」として予約**し、境界を越えさせない (設定を忘れたロボットが外に漏れるのを防ぐ)。今の台車の試し (MuJoCo、ドメイン 0) は、拠点の外に出すときはドメイン 1 以上に移す。
- 番号は 1-101 の範囲で、重ならないように console が割り当てる (rmw_zenoh では上限は関係ないが、DDS の ROS と混ぜる場合の制約に合わせる)。
- 割り当ては console の今の役割 (ひな形から ACL を作る仕組み) の上に作る。ひな形に `${domain}` を書けるようにし、拠点の登録が持つドメインの一覧で広げる (`${node}` をノード ID の一覧で広げるのと同じ)。

## 5. 群れの例外

ROS のトピックで直接協調させるロボットだけは、同じドメインにまとめて名前空間で分ける。この場合は、ROS の「1 ドメイン 1 台」の前提に逆らう手間を受け入れる。

- 名前空間は `/<ロボットの名前>` (例: `/go2_lab`)。持ち主はドメインで分かれているので入れない。
- `/tf`・`/tf_static` は相対名へリマップする (`/tf:=tf`)。
- フレーム名にもロボットの名前の前置きを付ける (`robot_state_publisher` の `frame_prefix` など)。
- 名前空間とリマップは launch で付ける (`PushRosNamespace`、`--ros-args -r __ns:=/go2_lab`)。Asterism はそのための launch の雛形を用意する。

ドメインを分けたまま一部のトピックだけを繋ぎたい場合は、`domain_bridge` ではなく Asterism のオブジェクトを使う (7 章)。

## 6. 境界の ACL

拠点の出入口のルータとクラウドのルータの境界では、ドメインを持つ拠点の証明書で繋いだルータから来た ROS のキーだけを通す。Zenoh のキーには持ち主が無いので、この ACL が「ドメインの持ち主」を作る。

| 対象 | 通す条件 |
|---|---|
| `12/**` | ドメイン 12 を持つ拠点 (例 `home-kishima`) の証明書で繋いだルータからだけ (書き込み・公開) |
| `@ros2_lv/12/**` | 同上 (ROS の生存の印) |
| `0/**`、`@ros2_lv/0/**` | 常に通さない |
| 割り当てのないドメイン | 通さない |
| 他人のドメインの読み取り | 共有の設定で許したものだけ |

- ACL は console の画面での選択から作り、使う人には「誰に・どのロボットを・見るだけか操作もか」だけを見せる。
- **ドメインで持ち主を決めたうえで、W5 のトピックの絞り込みと頻度の上限で、さらに絞れる (任意)**。ドメインごと通すだけだと、クラウドの側で誰かがカメラを購読すれば、その帯域がそのまま VPS を通る。拠点の外に出すトピックを選ぶ (例: カメラは出さない、`/odom` は毎秒 10 回まで) のは、W5 の計画のとおり出入口のルータとクラウドのルータで書く。
- 今の ACL の作りの注意: `**` は `@adv` を含むキーに当たらない (G2 のステップ 1 で見つかった)。ROS の transient local など高度な配信を通すなら、`@adv` の分も並べる。

## 7. ドメインをまたぐ連携と表示

ドメインをまたいだロボットどうしの連携は、tf やトピックを繋ぐのではなく、各ロボットが公開する Asterism のオブジェクトで行う。ROS の中の細かい座標の関係はドメインの中に閉じ、外には結果だけを出す。

```ruby
robot = net["go2_lab/nav/robot"]   # asterism/<ノード>/<アプリ>/<オブジェクト>
robot.pose      # 共通の地図の座標系での位置
robot.status
robot.go_to("kitchen")
```

- オブジェクトのキーは今の Asterism の形 (`asterism/<ノード>/<アプリ>/<オブジェクト>`)。ノード ID はロボットの名前 (ROS の側と同じもの) にする。
- console の図では、ドメインの ROS のノードと、同じ名前の Asterism のノードを 1 つのまとまりとして描く (今は同じ Zenoh のセッションの ROS のノードを Asterism のノードの枠に入れている (G1b)。別のセッションでも、ドメインの割り当てから同じまとまりにする)。
- ドメインの割り当てで ROS のノードを束ねられるので、V2.3・V2.4 の「接続元の IP で畳む」方式の穴 (docker の出入口の IP の向こうにある複数の機械が 1 つに畳まれる) も塞がる。ドメイン方式を採る理由の 1 つ。
- console は ROS のトピックと Asterism の値を同じ MCAP に記録し、同じ時間軸で巻き戻す (今の V4 の記録を広げる)。
