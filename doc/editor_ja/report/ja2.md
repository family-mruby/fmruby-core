## T1: 行の折り返し

### editor-core の API

`ec_wrap_segments` が返り値にリストを持つ形ではなく、**int を渡して int を
返す 2 本**にした:

```c
int ec_wrap_count(int slot, int y, int view_cells);
int ec_wrap_start(int slot, int y, int view_cells, int seg);
```

- `ec_wrap_start(seg)` は `seg >= count` のとき行長を返す。よって
  区分 k のスライスは `[start(k), start(k+1))` で、終端を別に問い合わせる
  必要がない。
- レコード形式を作らずに済むので、**mruby / Spinel どちらのバインディングも
  バイナリ解析なし**で書ける (JA1 の render_width が binstr なのと対照的)。
  1 画面行あたり 2 回の呼び出しで、18 行でも 36 回。

境界の決め方: セル幅マップの接頭和で、**入らない全角は次の区分へ送る**
(区分の途中で 2 セル文字を割らない)。窓より広い 1 文字は、単独の区分に置く
(無限ループ回避を兼ねる)。

### キャッシュの持ち方

- **固定 24 エントリのファイルスコープキャッシュ** (行ごとに `ed_line_t` を
  太らせるのはやめた)。1 エントリは
  `{slot, y, cells, stamp, count, cached, starts[32]}` で約 80 バイト、
  合計 2KB 弱。画面 18 行 + 余裕。
- 無効化は **`g_wrap_stamp` 1 個**。`line_drop_hl` (行内容の変更点)、
  `lines_insert` / `lines_remove` (行の増減で添字がずれる) で加算する。
  1 個の counter で全エントリが失効する保守的な作りだが、編集は
  どのみちその周辺を再描画する。
- `starts[]` は 32 区分まで。70 セル窓なら約 2200 文字ぶんで、実在の行は
  ほぼ収まる。それを超える行は count だけ正しく持ち、`ec_wrap_start` が
  末尾側だけ歩く。
- **全行の一括計算はどこにもない**。描画はアンカーから画面行数ぶん区分を
  消費するだけなので、触るのは可視行だけ。

### アンカー基準スクロール

- 画面先頭は `@scroll_y` (論理行) + `@anchor_seg` (区分番号)。
  折り返し OFF では `@anchor_seg` は常に 0 で、JA1 の経路と同一になる。
- `row_of(y, seg)` / `move_anchor(delta)` が中核。どちらも画面行数で
  打ち切るので、**文書の総画面行数は一度も数えない**。
- 上下移動は区分単位。桁は `cursor_cell_column` (現在の区分内のセル位置) を
  覚えて `char_at_cell` で目標区分の同じセルに落とす — 見た目どおり
  まっすぐ下りる。PageUp/Down は `move_cursor_rows(±@edit_rows)`。
- 行番号ガター: **現状のエディタに行番号表示は無い** (ガターはデバッガの
  ブレークポイント用の点のみ)。よって「先頭区分にのみ行番号」は該当なし。
  ブレークポイントの点は論理行の**先頭区分の行**に出る。

### 区分数が変わったときの追随

`mark_edited` が `line_segments(@cy)` を `@cur_line_segs` と比べ、
**変わっていればその行以下を再描画** (`mark_dirty_from`)、変わっていなければ
従来どおりその行だけ。`@cur_line_segs` の基準値は
`ensure_cursor_visible` (カーソルが落ち着くたびに呼ばれる) で更新する。
整数 1 個の比較なので、打鍵ごとに窓全体を塗り直す実装にはなっていない。

### 折り返し ON/OFF

メニューバーに `折返し(W)` を追加 (既定 ON、`*` で状態表示)。Alt-W も割当て。
OFF で JA1 の横スクロールに完全に戻る (右端の半端セル仕様も維持)。
永続化はしない (色分けトグルと同じ、バッファ単位)。
トグル時はカーソル行を画面先頭に置き直してから `ensure_cursor_visible` に
任せるので、視点が飛ばない。

## T2: クリックでカーソル移動

`place_cursor_at(mx, my)`:

1. `row = (my - @edit_y) / LINE_H` で画面行。
2. アンカーから row 回だけ区分を進めて (論理行, 区分) を得る — 描画と同じ walk。
3. `want = (mx - text_x0) / CELL_W` でセル位置。区分のセル幅マップを前から
   足していき、`want < cells + w` になった文字で止める。
   → **全角の右半分を突いてもその文字**になる (次の文字に行かない)。

判定範囲は編集領域の矩形 (ガター右端から、`@dbg_pane_y` まで)。メニューバーは
先に判定して return するので食われない。ステータス行・デバッガペインは範囲外。
折り返し OFF でも同じ経路 (区分 0 と `@scroll_x` になるだけ)。

選択のドラッグ開始は範囲外。**将来やる場合のメモ**: mouse_move は毎フレーム
飛んでくるので、move ごとに再描画すると打鍵より重くなる。
`redraw_if_dirty` は既に「キュー処理後に 1 回だけ描く」形になっているので、
ドラッグ中は選択端の更新だけ行い描画は既存の合流点に任せるのが素直。

## 途中で踏んだ既存バグ: エディタを 2 回目に開くと SEGV

### 症状

JA2 の作業中、**エディタを開いて閉じてもう一度開くと Spinel ビルドが
segfault** するようになった。JA1 の状態 (stash して再ビルド) では再現せず、
一見 JA2 の回帰に見えた。

### 原因 (gdb でバックトレースを取得)

```
sp_FmrbI18n_s_add (editor_combined.rb:1933)
 → sp_poly_each_elem → sp_PolyArray_new → sp_gc_alloc
 → sp_gc_collect → sp_gc_mark_all → SIGSEGV (0x1 を mark)
```

**生成された Spinel プログラムは定数をプロセスグローバルな C の static に
持つ**。エントリ (`editor_entry`) はそれをソース順に再代入するが、
**GC の globals-mark フックはその最初の再代入より前に登録される**
(`sp_re_init()` がエントリ冒頭)。したがってエントリ実行中に GC が走ると、
**まだ再代入されていない定数** — つまり**前のインスタンスが残したポインタ**を
mark する。そのポインタは同じプールを指しており、プールは既に新しいヒープに
渡っているので落ちる。

JA1 で落ちなかったのは運で、`m_wrap` を 1 キー足したことで
`FmrbI18n.add` の途中で閾値を超え、GC がその窓の中に入っただけ。
**JA2 が作ったバグではなく、Spinel プログラムを 2 回目に起動する経路の
潜在バグ**。エディタは繰り返し起動される唯一の Spinel プログラムなので、
ここでしか出ない。

### 採った対処と、捨てた対処

最初に「最初の GC をエントリの外に追い出す」ため
`fmrb_spinel_instance_begin` の閾値を pool/32 → pool/4 に上げた。
起動は直ったが、**200KB ファイルで打鍵すると `unhandled exception: out of
memory` になった** (同じ値が文字列ヒープの閾値にもなるため、512KB プールに
対して取り過ぎ)。**この対処は捨てた**。

採ったのは **エントリの最大の割り当てをエントリの外へ出す**方法:

- `editor/i18n.rb` の `FmrbI18n.add({...})` を `EditorStrings.install` という
  メソッドに包み、**`EditorApp#on_create` から呼ぶ**。
- on_create の時点でエントリは完了しており、全定数がこのインスタンスの
  ポインタを持っている。そこでの GC は安全。
- 閾値は pool/32 のまま (メモリ挙動は JA1 と同一)。

計測: 閾値 pool/32 (16KB) はエントリ中に GC が走って落ち、pool/16 (32KB) では
落ちなかった。つまりエントリの割り当ては 16〜32KB の間。i18n テーブルを
外に出した後は、その 16KB 閾値のままで 5 回連続の開閉が通る。

### 本来の直し方 → **解決済み** (2026-08-11)

生成器側で修正した。`doc/spinel_aot/report/stale_statics.md` を参照
(fork `c7de66c`: エントリ冒頭で `sp_reset_tu_statics()` を呼び、mark 対象の
全スロットと `SP_POOL_DEFINE` のフリーリストを 0 クリアする)。
**アプリ側の回避 (`EditorStrings.install` を on_create から呼ぶ) は撤去し**、
`FmrbI18n.add` はエントリに戻した。以下は当時の見立て:

**生成器 (Spinel) 側で、インスタンス生成時に TU の定数 static を 0 クリア
するべき**。`sp_tu_ctx_init()` が per-instance のフック登録をしている場所が
そのまま入れどころに見える。fork へ起票する価値がある。

それまでは「**Spinel プログラムのエントリで大きな割り当てをしない**」が
アプリ側の制約になる。`doc/spinel_aot/ruby_writing_constraints.md` に
追記すべき事項 (B: fork 修正で消えるべきもの)。

## 既知の制限

- 折り返しは**文字単位**。単語境界・禁則処理なし (指示書どおり範囲外)。
- 折り返し設定は保存されない (バッファ単位)。
- 行番号ガターは元から無いので、継続区分の表現も無い。
- ドラッグでの選択は未実装 (設計メモのみ)。
- スクロールバー等の「全体に対する比率」表示は無いので、論理行ベースの
  近似も今回は不要だった。
