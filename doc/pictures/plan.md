# 絵の扱いの汎用化 (読む・書き直す・拡大して描く・置き場の管理)

> 状態: 進行中 | 更新: 2026-11-21 | P0 (調査と API の案) 済、選択待ち (report/p0.md 7.3)。アプリごとに書かれている絵の処理 (読み直して PNG に書き直す、読む前の足切り、整数倍の拡大、一時ファイル経由の表示、限られた絵の置き場の使い回し、透明の市松) を、描画側・絵の gem・FmrbGfx の 3 つの層の汎用の部品に移す。チャットのスタンプ (doc/asterism_chat C3) が通った後に着手

## 1. 目的

絵を出すアプリ (チャットのスタンプ、画像ビューワー、スプライトエディタ、App Store) が、同じ処理をそれぞれ自前で持っている。
新しいアプリが絵を出すたびに実装が増えないよう、汎用の API にまとめる (2026-11-21 ユーザ: 「機能を共通化してアプリ毎の実装は
増えないような工夫は必要」「FmrbApp や Gfx の API や既存の機能の拡張で汎用化」)。

## 2. 今アプリごとに書かれているもの (2026-11-21 の調べ)

| 処理 | 書いているアプリ |
|---|---|
| 絵を読み直して小さい PNG に書き直す (`BMP332.parse` → `encode_png`) | チャット (`chat/stamps.rb`) |
| PNG の先頭だけ見て大きさを知る (読む前の足切り) | チャット |
| 整数倍の拡大 (Ruby で 1 点ずつ) と、拡大した絵を一時ファイルに書いて読み直す | チャット |
| 限られた絵の置き場 (スプライトの絵 64 枚・`create_image` 8 枚、どちらも機械全体) の使い回し | チャット、App Store (別々の実装) |
| 透明の所を市松で出す、大きすぎる絵の足切り (65,536 点) | ビューワー、スプライトエディタ (別々の実装) |
| 描画側が PNG の透明を捨てて黒く出す (アプリが読み直して避ける) | doc/asterism_chat/report/c3b.md の Q1 |

API の穴: 手元の画素からスプライトの絵を直接作れない (ファイルからだけ)。拡大して描けない (等倍だけ)。

## 3. 決めたこと (2026-11-21 ユーザ)

入れる範囲 (4 つとも):

1. **描画側**: PNG の透明 (α・tRNS) を透明色 `0x01` にする (`png332.c` と同じ決まり。α < 128 は透明)。
   **描くときに整数倍の拡大を指定できる**。sim・Retro は graphics-audio、P4・ブラウザ版・ネイティブ版は
   `display_local_task.cpp` の両方。
2. **絵の gem (`BMP332`)**: `info` (読み込まずに大きさと形式) と `to_png` (読み直して小さいパレットの PNG に。上限つき。
   C の中で済ませ、画素を VM に持たない)。
3. **`FmrbGfx` (アプリの基底の側)**: 絵の置き場の管理。`picture(パス)` で絵を取り、`draw_picture(絵, x, y, scale:)` で描く。
   枚数の上限と使い回し (最近使った順) は中で面倒を見る。透明の市松もここに。
4. **画素から直接スプライトの絵を作る**: RGB332 のバイト列から、ファイルを経ずに作る。

順番: **チャットのスタンプ (C3) を通してから**、汎用の部品を作り、チャット・ビューワー・スプライトエディタ・App Store の側を削る。
「移す前と後で同じに動く」を確認の基準にする。チャットを VPS に置く (C4) のは、この汎用化の後。

## 4. 方針

- API の名前と引数は P0 で、今の `sig/` の流儀に合わせて決める (上の名前は見立て)。sig の doc コメント (1 行目 112 バイトまで)、
  端末のヘルプ (`flash/help/`)、アプリの書き方の skill にも載せる。
- **内蔵 RAM を増やさない**。`FmrbGfx` に足す分は全アプリに載るので、絵を使わないアプリの VM プールが増えない形
  (使ったときだけ確保) にする。増分は `regress:size`・`regress:run` で測る。
- 描画側の直しは 2 か所 (graphics-audio と端末の中の描画) に同じ決まりを入れる。線の形 (リンクのプロトコル) に拡大の引数を
  足すなら、ヘッダは `components/fmrb_wire/include` の 1 か所、`rake wire:check` を通す。プロトコルの版の扱いを P0 で決める。
- Retro でも同じ API が使える。mruby のアプリと Spinel の基底の両方 (ビューワーの前例: `request_file_select` の `dir:`)。

## 5. 段取りと受け入れ条件

| 段 | 中身 | 受け入れ条件 |
|---|---|---|
| P0 | 調べて決める: API の形 (sig の案)、描画側の 2 か所の今の読み方と拡大の入れ方、線の形と版、メモリの見積り、移す先と削る所の一覧 | report に sig の案と、利用者に見える所の選択肢 |
| P1 | 描画側: 透明を `0x01` に、拡大して描く (graphics-audio と端末の中の描画) | α つきの PNG を `SpriteImage#load_bmp`・`create_image` で直に読んで透明が抜ける (sim・ブラウザ版・ネイティブ版)。拡大が 2 か所で同じに出る。今ある絵の見た目が変わらない |
| P2 | `BMP332.info`・`to_png`、画素から直接スプライトの絵 | ホストの試験。VM プールの使用量が、今のアプリの書き方より減る |
| P3 | `FmrbGfx` の絵の置き場の管理 | 絵を使わないアプリの VM プールが増えない。上限を超えて絵を出しても落ちず、古いものから離れる |
| P4 | アプリを移す: チャットのスタンプ、ビューワー、スプライトエディタ、App Store | 移す前と後で同じ画面。アプリの行数が減る (前後を report に)。`rake regress`・`regress:screens`・`regress:run` |
