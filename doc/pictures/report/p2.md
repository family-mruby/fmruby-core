# P2 報告: 絵の gem の `BMP332.info`・`to_png` と、境界の `picture_info`

> 状態: 完了 (検収待ち) | 更新: 2026-11-21 | `BMP332.info` (先頭だけ読んで大きさと形式)・`BMP332.to_png` (C の中で読み直して小さいパレットの PNG に。断り方は Hash)・境界 `FmrbGfx#picture_info` (同じ C)・`module BMP332` の sig。`to_png` のバイト列は今の `parse` → `encode_png` と同じ (flash/ の絵全部と α・tRNS の絵で試験)。48x48 の RGBA の絵で VM プールに残るものが 10,200 B → 680 B。指示書は instruction_p2_p3.md

## 0. 要点

- **`BMP332.info(path)` / `BMP332.info(data: bytes)`** → `{width:, height:, format: :png | :bmp, bytes:}` か nil。PNG は IHDR、BMP は見出し (54 B) だけを読む。大きすぎて解けない絵も大きさを答える (呼ぶ側が「大きすぎ w x h」と言えるように)。
- **`BMP332.to_png(path または data:, max_width:, max_height:, max_bytes:, max_file_bytes: 65536)`** → `{png:, width:, height:}`。断るときは例外でなく Hash: `{error: :too_big, width:, height:}`・`{error: :too_heavy, bytes:}`・`{error: :file_too_large, bytes:}`・`{error: :unreadable}`・`{error: :no_memory}`。引数の間違い (パスも data: も無い、など) だけが例外。
- **バイト列は今の `parse` → `encode_png` と同じ** (同じ C の `fmrb_png332_decode`・`fmrb_bmp332_parse`・`fmrb_png332_encode` をつなぐだけ)。ホストの試験で flash/ の PNG 110 枚・BMP 2 枚・α と tRNS の 5 枚・作った BMP 2 枚の全部で 1 バイトも違わないことを確かめた。sim の上でも 10 枚 (チャットのスタンプに近い 16〜64 px の RGBA・パレット・BMP と flash/ の絵) で `to_png(path)`・`to_png(data:)` とも同じ。**チャットの sha256 は変わらない**。
- **境界 `FmrbGfx#picture_info(path)`** → 記録 `{width: uint16, height: uint16, format: uint8, bytes: uint32, mtime: uint32}` か nil (C は 0)。format は 1 が PNG、2 が BMP。p0 の案に `bytes` と `mtime` を足した (P3 の置き場が「ファイルが書き換わったら読み直す」を 1 回の呼び出しで知るため。4 章)。Spinel の基底にも包みを足した。
- **VM プール**: 48x48 の RGBA の PNG (6,912 B) で、今の書き方 (`File` で読む → `parse` → `encode_png`) が GC までに残すもの 10,200 B に対し、`to_png` は 680 B (PNG の String と Hash)。一時領域の山 (解く・書く作業領域) は同じ C なので同じ。
- 内蔵 RAM・静的領域は足していない (状態を持たない C。作業領域はどれも渡したアロケータ = アプリの VM プールから)。大きさは P3 と合わせて `rake regress:size` で測った (p3.md)。

使い方 (アプリを書く人から):

```ruby
info = BMP332.info("/home/stamps/a.png")       # {width: 16, height: 16, format: :png, bytes: 112} / nil
r = BMP332.to_png(path, max_width: 48, max_height: 48, max_bytes: 8192)
if r[:error]
  # :too_big (r[:width], r[:height]) / :too_heavy (r[:bytes]) / :file_too_large (r[:bytes]) / :unreadable / :no_memory
else
  FmrbFile.write(out, r[:png])                  # r[:width], r[:height]
end
BMP332.to_png(data: bytes, max_width: 48, max_height: 48)   # 受けたバイト列から
gfx.picture_info(path)                          # {width:, height:, format: 1|2, bytes:, mtime:} / nil
```

Lua・MicroPython・C・wasm のアプリからは境界の `picture_info` (C の名前 `fmrb_gfx_picture_info`、import 名 `gfx_picture_info`)。

## 2. 受け入れ条件の結果

### 2.1 ホストの試験 (条件 1)

`rake png332:test` に足したもの (`test/png332/main.c` の `check_picture`):

- 絵ごとに、解き手の答え (PNG は `fmrb_png332_decode`、BMP は `fmrb_bmp332_parse`) と `fmrb_picture332_head` の幅・高さ・形式が同じ。
- `fmrb_picture332_to_png` の結果が `fmrb_png332_encode(解き手の画素)` と 1 バイトも違わない。
- 上限ちょうど (幅・高さ・`max_bytes` = 書いた PNG の大きさ) は通り、1 つ小さいと `TOO_BIG` (幅と高さつき)・`TOO_HEAVY` (書いた大きさつき)。
- BMP332 が読まない BMP (1・4 ビット。flash/ の 2 枚がそう) は、`head` も `to_png` も断る。24 ビットの BMP・GIF の先頭も断る。
- アロケータで取ったものが全部返る (今までの試験の確かめに乗る)。

対象: flash/ の PNG 110 枚、α・tRNS の 5 枚、flash/ の BMP 2 枚 (どちらも 1・4 ビットで読めない側)、作った 8 ビット BMP 2 枚 (下から・上からの行順、幅 5 で詰め物あり)。結果 `png332: 119 pictures: BMP332.info's head and BMP332.to_png's bytes as parse + encode_png`。`rake test` 一式も通った。

### 2.2 sim (Retro) の上で

スクラッチの試しのアプリ (`p2test.app.rb`。sim の `flash/home/pictest` に置き、終わってから消した) で 81 項目すべて通った:

- 10 枚 (16x16 の RGBA の円、48x48 の RGBA (中に α 0 の穴)、64x64 のパレット (透明の穴)、20x10 の 8 ビット BMP、16x16 のパレット、flash/ の `ball.png`・`tiles_hand.png` (420x224)・`image_viewer.png`・`world.png`・`asterism_demo.png` (RGBA)) で `to_png(path)`・`to_png(data:)` が `encode_png(parse(...))` と同じバイト列、大きさも同じ。`info(path)`・`info(data:)`・`gfx.picture_info` が同じ大きさと形式とバイト数。
- 断り方: `max_width: 32` で `{error: :too_big, width: 48, height: 48}`、`max_bytes: 100` で `:too_heavy`、137,507 B の PNG で `{error: :file_too_large, bytes: 137507}` (`max_file_bytes: 200000` なら通る)、無いファイル・GIF のバイト列で `{error: :unreadable}`、無いファイル・ディレクトリの `info` は nil、300x300 の `info` は大きさを答える、引数なしの `info` は ArgumentError。

### 2.3 VM プール (条件 3 の to_png の分)

同じアプリの中で、GC の後から測った (`FmrbApp.pool_used` の差、GC の前):

| 48x48 の RGBA の PNG (6,912 B) | GC までに残るもの |
|---|---|
| 今の書き方: `File` で読む → `BMP332.parse` → `BMP332.encode_png` | 10,200 B |
| `BMP332.to_png(path)` | 680 B |

- 残るものは、今の書き方がファイルの String・画素の String・Hash・PNG の String、`to_png` が PNG の String と Hash だけ。
- 作業領域の山 (解く間の IDAT と展開した行、書く間の deflate の表) は同じ C を同じ順で通るので、今と同じ (ファイルの写しが String から C の一時領域に変わるだけ)。
- チャットの今の `prepare` は、この後にさらに拡大した画素を Ruby で作って PNG をもう 1 度書く。それが無くなる分は P4 で数える (p0 5.2 の見立ては 1 枚 12〜13 KB → 0.3 KB)。

## 3. 内蔵 RAM・大きさ (条件 4)

P2 だけを分けては測っていない。P3 と合わせた `rake regress:size` の結果は p3.md の 3 章。静的な領域は足していない (`picture332.c`・`picture332_file.c` は状態を持たず、スタックは 600 B 前後: 境界の関数のパスの写し 256 B とファイルの情報の構造体)。

## 4. p0 の案から変えた所

- **入力はパスかバイト列** (p0 は推奨「パスだけ」、親の仮決め Q5a の (b) どおり)。`info(data:)`・`to_png(data:)`。
- **`to_png` の上限の名前**: p0 の `max:` を、指示書どおり `max_width:`・`max_height:` に分けた。元のファイルの足切りは `max_file_bytes:` (既定 65,536、チャットの `SOURCE_MAX` と同じ) で変えられるようにした。`data:` にも同じ足切りが効く。
- **断る理由に `:no_memory` を足した** (VM プールが足りないとき。今のチャットは例外を rescue して `[:bad]` にしている。区別できるほうがよいと見た)。
- **境界の記録 `picture_info` に `bytes`・`mtime` を足した** (p0 は `width`・`height`・`format`)。置き場が「同じパスのファイルが書き換わったら読み直す」を、ファイルの先頭を読むのと同じ 1 回の呼び出しで知れる。`mtime` は秒で、時刻を持たないファイルシステムでは 0 (そのときは大きさだけで気づく)。
- **`info` は 8 ビット・無圧縮の BMP だけを絵とみなす** (BMP332 が読める物だけ)。PNG は署名と IHDR があれば絵とみなし、インターレース・16 ビットなど BMP332 が解かない PNG でも大きさを答える (描画側の pngle は読めるので、置き場には置ける。`to_png` は `:unreadable` で断る)。
- **Ruby の包みを足していない**: `info`・`to_png` のキーワードは C で受けた (`mrb_kwargs`)。mrblib に Ruby のメソッドを足すと、絵を使わないアプリの VM プールにも proc が載るため。

- 境界の関数の C (`fmrb_boundary_gfx.c`) から gem のヘッダ (`fmrb_picture332.h`) を読む形にした。`fmrb_png332_pngle.h` を display_local が読むのと同じ道 (picoruby-esp32 の include)。ネイティブ版・ブラウザ版も `hosted.cmake` がこの include を持つ。
