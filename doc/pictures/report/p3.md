# P3 報告: FmrbGfx の絵の置き場 (パスを渡すだけの API)

> 状態: 完了 (検収待ち) | 更新: 2026-11-21 | `draw_picture(path, x, y, scale:, checker:, clip:)`・`picture_size`・`put_picture`・`release_picture(s)`・`picture_limit=`・`picture_error`・`draw_checker`。スプライトの絵に寄せ、描き手ごとに既定 8 枚、最近使っていないものから離す。機械全体が一杯なら自分の古いものを離して作り直す。Ruby 1 ファイルを mruby と Spinel で共有。絵を使わない mruby のアプリの VM プール +488 B (メソッドの登録の分)、内蔵 RAM +0。sim の Modern・Retro・ブラウザ版・ネイティブ版で確認。指示書は instruction_p2_p3.md

## 0. 要点

- **利用者から見た形** (plan 7 章 Q6・p0 6.2 のとおり。名前と引数は 1 章):

  ```ruby
  @gfx.draw_picture("/home/stamps/a.png", 10, 20, scale: 2)   # 描く。置き場に無ければ読む。描けなければ false
  @gfx.draw_picture(path, x, y, scale: -2, checker: true, clip: [cx, cy, cw, ch])
  w, h = @gfx.picture_size(path)                               # 読まずに (picture_info)。絵でなければ nil
  @gfx.put_picture("mine", w, h, pixels)                       # 手元の画素を名前で
  @gfx.draw_picture("mine", 10, 20, scale: 4)
  @gfx.release_picture(path)  /  @gfx.release_pictures         # 閉じるときは要らない
  @gfx.picture_limit = 16                                      # 既定 8
  @gfx.picture_error          # 直前の失敗の理由: :unreadable / :too_big / :file_too_large / :no_room / :not_sent
  @gfx.draw_checker(x, y, w, h, cell: 4, clip: nil)            # 透明の下の市松だけ
  ```

- **置き場はスプライトの絵** (透明色 0x01)。初めての絵は `picture_info` (先頭だけ) → `create_sprite_image(w, h, 0x01, true)` → `sync_file` → `load_sprite_image`、描くのは `draw_tile_raw` (等倍・切り抜きなし) か `draw_tile_scaled_raw`。描画側の命令・線の形・版は変えていない。
- **上限と追い出し**: 描き手 (FmrbGfx) ごとに `picture_limit` 枚 (既定 8)、最近描いていないものから離す。描画側が「もう作れない」と答えたら (枚数か GA の 256 KB の置き場)、自分の一番古いものを離して作り直し、自分のものが無くなっても作れなければ描かずに false (`:no_room`)。落ちない。
- **書き換わったファイル**: 置き場にある絵は、描くときに 1 秒に 1 回まで `picture_info` で大きさ・バイト数・時刻を見て、違えば読み直す (同じ幅と高さなら同じスプライトの絵に読み直し、違えば作り直し)。
- **大きい絵**: 65,536 点か 65,536 バイトを超える絵は置かない (`:too_big`・`:file_too_large`)。置ける絵は `scale: -2〜-32` で縮小して描ける。**ビューワーの「縮小して出したい大きい絵」は、置ける範囲 (65,536 点・64 KB) なら置いてから縮小で足りる。超える絵のために読むときに間引く命令は足さない** (描画側の命令が要るので止まる条件。4 章、選択肢 Q3)。
- **アプリが終わるとき**: スプライトの絵は canvas と一緒に描画側が回収する。Ruby の側は何もしない (後片付けの口を足していない)。チェックポイントから戻ったアプリだけ、基底 (`_checkpoint_restored`) が置き場の番号を忘れさせる (1 行)。
- **mruby と Spinel**: `lib/gems/picoruby-fmrb-app/mrblib/fmrb-picture.rb` の 1 ファイル。Spinel のプログラムには `gen_app_combined.rb` が基底の直後に差し込む (呼ばれないメソッドは生成されない)。状態は最初の絵まで作らない平行の配列 (Spinel が型を 1 つに絞れるように)。
- **VM プール**: 絵を使わない mruby のアプリで **+488 B** (同じ HEAD で P3 のファイルを外して作ったビルドと比べた。コンパイル直後 5 本とも +488 B ちょうど、動いている時 +440〜584 B)。中身は 15 メソッドと 2 定数の登録 (1 つ 30 B 前後)。KB 単位ではないが、`regress:run` のアプリの幅 (512 B) に近い (2 章)。
- **内蔵 RAM +0** (`rake regress:size`、3 章)。

### 1.1 中の作り

- 状態 (どれも最初に使うまで nil): `@_pk` 鍵 (パスか名前) の配列 (古い順)、`@_pn` 鍵 1 つにつき 6 つの整数 (スプライトの絵の番号、幅、高さ、ファイルのバイト数、時刻 (`put_picture` は -1)、最後に見た時刻)、`@_pl` 上限、`@_pe` 直前の失敗の理由、`@_pc` 市松の帯 `[番号, 升, 幅]`。Hash を使わず平行の配列にしたのは、Spinel が 1 つの配列に 1 つの型を求めるため (生成した C で `@_pn` が整数の配列、引数が `sp_int` になることを確かめた)。
- 最近使った順は配列の並びで持ち、描いた絵を末尾へ動かす (最大 8 前後なので線形で足りる)。ブロックは使っていない (picoruby のブロックは重い)。
- `draw_picture` の `scale:` は 1〜32 と -2〜-32 (0 と -1 は 1)。範囲の外は ArgumentError (P1 の境界の ERR_ARG と同じ扱いを Ruby で先に)。`clip:` の幅か高さが 0 以下なら何も描かずに true。`checker: true` は描く大きさ (縮小なら切り上げ) の矩形に `draw_checker` を先に押す。
- `draw_checker`: 白 (0xFF) と薄い灰 (0xB6) の升 (ビューワーと同じ並び)。升の 2 倍の高さの帯を描画側に 1 枚作り (幅は要った最大、升の 2 倍に切り上げ)、行ごとに `draw_tile` で押す。帯は置き場の枚数に数えない (`release_pictures` で一緒に離す)。
- mruby では作る命令が失敗すると例外、Spinel では負の数が返るので、`create_sprite_image` は begin/rescue で包んで両方を 0 として扱う。

### 1.2 p0 の案から変えた所

- **`picture_error` を足した** (指示書「上限を超える絵は false を返し、理由を取れる形に」)。p0 の sig の案には無い。理由は `:unreadable`・`:too_big`・`:file_too_large`・`:no_room`・`:not_sent` (描画側へ送れない)。成功すると nil に戻る。
- **`draw_checker` に `cell:` と `clip:`** (p0 8.3 の見立て。`clip:` は `draw_picture(..., checker: true, clip:)` が使う)。
- **上限は 65,536 点と 65,536 バイト** (p0 は点の数だけ)。Retro の描画側がスプライトの絵に読む PNG のファイルの上限が 65,536 B (`GH_SPRITE_BMP_MAX_FILE`) で、超えると黙って読まないため。sim・P4 系はもっと読めるが、「ある端末で出る絵はどの端末でも出る」にそろえた。
- **書き換わりを見るのは 1 秒に 1 回まで** (指示書は「大きさか mtime」とだけ)。毎回見るとファイルの `stat` と先頭の読みが絵の数だけ毎フレーム走るため。時刻は秒なので、同じ秒の中で同じバイト数に書き換えると気づかない。
- `release_picture` (1 枚) も入れた (p0 の sig の案にある。指示書の例には無い)。`picture_limit` の読み取りは入れていない (メソッドを増やさないため)。

- 絵を使うアプリの状態は、最初の絵から `@_pk`・`@_pn` (8 枚で 60 項前後の配列 2 本) と市松の帯の配列。

### 2.4 Spinel

- 基底に差し込んだ部品で、デスクトップ・エディタの Spinel のプログラムが今までどおり生成・ビルドできた (呼ぶ物が無いので、置き場のメソッドは生成されない)。
- スクラッチで、エディタの結合したソースに置き場の全部のメソッドを呼ぶ関数を足して Spinel にかけ、C が生成されることを確かめた。`.to_i` を挟んで `picture_info` の Hash の値を整数に絞ると、`draw_picture`・`draw_checker`・`_pic_make`・`_pic_add` の引数と `@_pn` は整数の型 (`sp_int`・`sp_IntArray`) になった。**Spinel で書いたアプリから動かしてはいない** (今 Spinel のアプリはデスクトップとエディタだけで、どちらも絵を出さない)。

## 4. 大きい絵 (ビューワー) の扱いの結論

- 置き場に置ける大きさは **65,536 点かつ 65,536 バイトまで**。この範囲の絵は、置いてから `scale: -k` で縮小して描けば足りる (描画側の縮小は升の左上の 1 点を取る。今のビューワーの「k 点ごとに 1 点」と同じ間引き方)。描画側の置き場の大きさは、GA (sim・Retro) で 1 枚最大 64 KB (機械全体 256 KB の 1/4)、P4 系で 128 KB (RGB565、PSRAM)。
- 今のビューワーも 65,536 点を超える絵は断っている (`MAX_PIXELS`) ので、**P4 でビューワーを移しても、出せる絵の範囲は今と同じ** (ただし Retro では PNG のファイルが 64 KB を超えると今は出せた絵 (VM で読む) が出なくなる。sim・P4 系の描画側は 256 KB まで読むが、置き場は全端末で 64 KB にそろえた。選択肢 Q3)。
- **読むときに間引いて置く命令は足していない** (描画側の命令が要る = 止まる条件)。要るなら、次に線の形を変えるときに `LOAD_SPRITE_IMAGE` に縮小の引数を足す (描画側の pngle の受け口で k 行・k 点ごとに書く) のが小さい。アプリの側で済ませるなら、`BMP332.load` で読んで間引いた画素を `put_picture` で置く (VM に画素を持つ。今のビューワーと同じ重さ)。

## 5. アプリの書き方の skill に足す文の案

直下の `.claude/skills/fmrb-app-new/SKILL.md` の「## 描画」の後に足す案 (直していない):

````markdown
## 絵 (PNG・BMP) を出す

**パスを渡すだけ**。スプライトの絵の番号・`sync_file`・最近使った順の管理はアプリに書かない。

```ruby
@gfx.draw_picture("/home/stamps/a.png", 10, 20, scale: 2)  # 初めてなら読む。描けなければ false
@gfx.draw_picture(path, x, y, scale: -2, checker: true)    # 1/2 に、透明の所に市松
@gfx.draw_picture(path, x, y, clip: [0, 30, 200, 100])     # その矩形の中だけ
w, h = @gfx.picture_size(path)                              # 読まずに大きさ (nil なら絵でない)
@gfx.put_picture("mine", 16, 16, pixels)                    # 手元の画素 (RGB332、0x01 が透明) を名前で
@gfx.draw_picture("mine", 0, 0, scale: 4)
```

- `scale:` は 1〜32 (拡大) と -2〜-32 (1/k に縮小)。透明は 0x01 (PNG の α・tRNS もそうなる)。
- 描き手ごとに 8 枚まで持ち、古いものから離す (`@gfx.picture_limit = 16` で変える)。毎フレーム描いてよい (2 回目からは読まない。ファイルを書き換えたら次に描くとき読み直す)。
- 閉じるときの後片付けは要らない (canvas と一緒に離れる)。部屋を変えたときなどは `@gfx.release_pictures`。
- false のときの理由は `@gfx.picture_error` (`:too_big` = 65,536 点超、`:file_too_large` = 64 KB 超、`:unreadable`、`:no_room`)。
- 送る・保存するために小さい PNG にしたいときは `BMP332.to_png(path, max_width:, max_height:, max_bytes:)` (画素を VM に持たない。断るときは `{error: ...}` の Hash)。大きさだけなら `BMP332.info(path)`。
- 画素を自分で読む `BMP332.load` は、編集する (スプライトエディタ) ときだけ。出すだけなら使わない (VM プールを食う)。
````
