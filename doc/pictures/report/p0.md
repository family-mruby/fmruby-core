# P0 報告: 絵の扱いの汎用化の調査と API の案

> 状態: 完了 (選択待ち) | 更新: 2026-11-21 | 絵がファイルから画面に出るまでの道 (機械ごと)、描画側 2 か所の PNG の読み方の違い、透明の直しの形、整数倍の拡大と画素から直接スプライトの絵を作る命令 (線の形・版・Retro の子マイコン)、`BMP332.info`・`to_png`、`FmrbGfx` の絵の置き場、sig の案、4 つのアプリの移す先と削る所、段取りと見積りを調べた。コードは書いていない。利用者に見える名前と引数は 7 章の選択肢 (推奨つき) にした。指示書は instruction_p0.md

## 0. 要点

- **描画側の 2 か所は作りが違う** (確かめた事実)。graphics-audio (sim・Retro) は絵 (スプライトの絵も canvas も) を RGB332 で持ち、`create_image` は PNG のバイト列のまま持って描くたびに `drawPng` で解く (canvas の上に α を混ぜて描く)。display_local (P4・ブラウザ版・ネイティブ版) はスプライトの絵も canvas も RGB565 で持ち、`create_image` は作るときに白で埋めた RGB565 の絵へ解く (α は白と混ざる)。スプライトの絵の上限は graphics-audio 64 枚 (256 KB の置き場を機械全体で共有)、display_local 160 枚 (PSRAM、置き場の上限なし)。`create_image` はどちらも 8 枚で、**どちらもアプリの終わりに回収されない** (canvas に結び付いていない)。
- **透明の直しは「LovyanGFX の PNG の解き手に自前の受け口を渡し、α < 128 を 0x01 にする」形を推奨** (2 か所とも同じ `lgfx_pngle`。メモリは今と同じ、行ごとに流す)。決まり (α・tRNS → 0x01、色は上位ビット) は `fmrb_png332.h` の inline 関数 1 つに置き、png332.c と 2 つの描画側がそれを使う。大きさは片側 40〜60 行。
- **拡大は新しい命令 `DRAW_TILE_SCALED` (0x8E) を推奨**。今の `DRAW_TILE` と境界の `draw_tile_raw` は変えない (C・wasm の SDK の形が変わらない)。Ruby の包み `draw_tile` に `scale:` を足す。`draw_image` は線の形にもう倍率 (8.8 固定小数) があり、両方の描画側で効いている (足す物は無い)。
- **画素から直接スプライトの絵を作る命令 `SPRITE_IMAGE_DATA` は、型ぬきの形 (`CREATE_MASK`・`MASK_DATA`) と同じ分け方**で送る (1 回 222 バイトまで、答えを待たない)。Retro の UART (実効 90 KB/s 前後) で 48x48 は 2.3 KB・約 26 ms (推定)。
- **線の形の変更は P1 にまとめ、版を 1 回だけ上げる** (link 6 → 7、GA 3.1.0 → 3.2.0)。core は版を厳密に照らし、合わなければ起動を止める (`fmrb_kernel.rb` が raise) ので、**Retro は S3 と WROVER (子マイコン) の両方の焼き直しが要る**。P2〜P4 は描画側に触らない (焼き直しは 1 回)。
- **`BMP332.info`・`to_png` は C の中で済ませると、VM に残るゴミ (読んだファイル・画素の文字列・Hash・拡大した画素) が 1 枚あたり数 KB → 数百 B になる** (推定)。一時領域の山 (PNG を書く deflate の表、最大で数十 KB) は今と同じで、プールから出てすぐ返る。チャットは拡大した絵を Ruby で作り PNG に書き直してファイルに貯める処理が丸ごと無くなる。
- **`FmrbGfx` の絵の置き場はスプライトの絵に寄せる**のを推奨 (アプリの終わりに回収される・透明色が使える・Retro でも使える・枚数が多い)。Ruby で書き、mruby の gem と Spinel の基底で同じファイルを使う (`fmrb-sprite.rb` と同じ作り)。絵を使わないアプリの VM プールの増分は、メソッドの登録の分だけ (数百 B〜1 KB と推定、P3 で `regress:run` で測る)。
- **画像ビューワーは VM に画素を持たなくなる** (200x150 の絵で今 +147 KB の VM プールの山。スプライトの絵に読み、拡大して押すだけになる)。スプライトエディタは編集に画素が要るので `BMP332.load` が残り、移すのは小さい絵 (一覧・実寸) の描き方まで。
- 段取りは **「画素から直接スプライトの絵」を P2 から P1 へ移す** (線の形の変更を 1 回にまとめるため) のを推奨。P1〜P4 の大きさは合わせて 1,300〜1,600 行の変更、サブの作業で 4〜5 回分 (推定)。

## 1. 今の経路 (機械ごと)

### 1.1 アプリの側 (どの端末も同じ)

```
アプリ (mruby の VM)
  BMP332.load(path) / BMP332.parse(bytes)  ... png332.c・fmrb_bmp332.c。VM プールで解き、画素 (RGB332) を String で返す
  BMP332.encode_png(w, h, pixels)          ... 同じく VM プールで書く
  @gfx.sync_file(path)                     ... 描画側のファイルシステムへ写す (中身が同じなら送らない)
  @gfx.create_image(path) / draw_image     ... 描画側で PNG を解く (8 枚の置き場)
  SpriteImage.new + load_bmp(path)         ... 描画側で PNG・BMP をスプライトの絵に読む
  @gfx.draw_tile(id, sx, sy, w, h, dst_x:, dst_y:)  ... スプライトの絵の一部を等倍で押す
```

命令の道は全端末で同じ: アプリ → 境界の C (`main/app/fmrb_boundary_gfx.c`) → `components/fmrb_gfx` の命令の列 → `main/kernel/host/host_task.c` が線の形 (`fmrb_link_protocol.h` の構造体を msgpack に包む) に → transport → 描画側。答えを待つ命令 (`create_image`・`create_sprite_image`・`create_mask`) は host の列を通らず transport で直接やり取りする。

- **スプライトの絵はアプリの終わりに回収される**: canvas を消すと `sprite_manager_delete_all_for_canvas` (graphics-audio `graphics_handler.cpp:1617`) / `display_local_sprite_delete_all_for_canvas` (`display_local_task.cpp:655`) が、その canvas の絵と置いた絵を全部離す。

- `CREATE_IMAGE_FROM_MEM` (0x06) と `DRAW_BITMAP` (0x41) は線の形にあるが、どちらの描画側も実装していない (display_local は ACK だけ、graphics-audio は無い)。

## 2. 描画側の透明

### 2.1 今の読み方 (確かめた事実)

- どちらも LovyanGFX の `drawPng` (中は `lgfx_pngle.c`)。pngle は tRNS を読む (パレットの α、灰色・RGB の透明の値)。
- `drawPng` の受け口 (`LGFXBase.cpp` の `png_draw_alpha_callback`): α 0 の点は飛ばし、0 < α < 255 は下にある画素を読み (`readRect`) 混ぜて書く。よって 0 で埋まったスプライトの絵に読むと、外は 0x00 (黒)、縁は黒と混ざった色になる (c3b 2.3 の実物と合う)。
- 色は RGB888 の上位 3/3/2 ビット (png332.c の `to332` と同じ)。

### 2.2 直しの形 (選択肢 Q10)

- **(推奨) A: 自前の受け口で pngle を回す**。`lgfx_pngle_new` → `lgfx_pngle_set_draw_callback(受け口)` → ファイルのバイト列を流す。受け口は 1 行分の argb を受け、点ごとに `fmrb_png332_from_argb(a, r, g, b)` (α < 128 なら 0x01、それ以外は上位ビット) をスプライトの絵に書く。
  - 決まりは `lib/gems/picoruby-fmrb-bmp332/include/fmrb_png332.h` に `static inline` で 1 つ置き、png332.c (アプリの側の読み手) もそれを使うように変える。graphics-audio は CMake で隣の fmruby-core のこのヘッダの場所を include に足す (fmrb_wire と同じ読み方。写しは作らない)。
  - メモリ: 今の `drawPng` と同じ (pngle の作業領域だけ。行ごとに流れる)。WROVER の PSRAM・P4 の系のプールの使い方は変わらない。
  - 大きさ: graphics-audio 40〜50 行、display_local 40〜50 行 (P4 の側は RGB332 の下書きが要らなくなり、直接 RGB565 に書ける)、png332.c の直し 5 行、ヘッダ 15 行。
  - 気をつける所: pngle の内部の関数名 (`lgfx_pngle_*`) は LovyanGFX の内部の API。graphics-audio は `components/LovyanGFX`、fmruby-core は `managed_components/m5stack__m5gfx` の写しで、版が違えば名前がずれる (P1 で確かめる)。
- B: 描画側でも png332.c の `fmrb_png332_decode` を使う。決まりがコードごと 1 つになるが、ファイル全体と展開した全部の行 (RGBA なら 4 x 幅 x 高さ) を一度に持つ。640x360 の RGBA は 900 KB を超え、P4 の系のプール (500 KB) に入らない。WROVER の PSRAM の空きは確かめていない。
- C: 直さない (c3b Q1 の C)。

### 2.3 BMP

8 ビットの BMP は RGB332 の値そのままで α が無い。変わらない。graphics-audio の BMP の読み手が core と別の写しである件は 8 章。

### 2.4 今ある絵で変わるもの

`git ls-files "flash/*.png"` は 110 枚 (c3b の後に 1 枚増えた)。α か tRNS を持つのは c3b 4 章と同じ RGBA の 3 枚だけ (`flash/app/test/asterism_demo.png`・`flash/usr/share/asterism/icon.png`・`icon_browser.png`)。3 枚とも端末の上で `load_bmp`・`create_image` に渡す道は無い (`asterism_demo.app.rb` はパスを網へ送るだけ)。**直しで画面が変わる追跡中の絵は無い**。

気をつける所 (推定): スプライトの絵の多くは透明色を 0 (黒) にしている (`transparent_color: 0` が 12 か所。ランチャーのアイコンもそう、`launcher.rb:277`)。今、α を持つ PNG をそれらに読むと α 0 の点が 0x00 になり**たまたま透明に見える**。直した後は 0x01 になり、透明色 0 のスプライトでは紺 (0,0,85) が見える。追跡中の絵には当たらないが、App Store で入れたアプリのアイコンが α つきの PNG だとランチャーの見た目が変わる。案: ランチャーのアイコンは透明色 0x01 も抜けるよう、読む前の下地を 0 にしたまま「0x01 → 0」に置き換える受け口の引数 (読むときの透明色) を `LOAD_SPRITE_IMAGE` に持たせる…までは要らないと見ている (アイコンは `tools/gen_icon_png.rb` が作るパレットの PNG で α が無い)。P1 の受け入れ条件に「ランチャーのアイコンが変わらない」を入れる。

## 3. 拡大して描く

### 3.1 今あるもの

- `draw_image` (`create_image` の絵): 線の形に `scale_x_fp8`・`scale_y_fp8` (8.8 固定小数) がある。graphics-audio は `drawPng(..., scale_x, scale_y)`、display_local は `pushRotateZoom` (ff34804d で直った)。**整数倍も小さくするのも、今のまま効く**。
- `draw_tile` (スプライトの絵): 等倍だけ。
- スプライトを置いた絵 (`SpriteInstance`): 等倍だけ。合成は両方の描画側で別の作り (P4 は PPA を使う所がある)。

### 3.2 案 (選択肢 Q1・Q2・Q9)

**(推奨) 新しい命令 `FMRB_LINK_GFX_DRAW_TILE_SCALED = 0x8E`** (0x80〜0x8F のうち空いている 1 つ):

```c
// DRAW_TILE_SCALED: DRAW_TILE with each source pixel drawn scale x scale.
// The destination is clipped to (clip_x, clip_y, clip_w, clip_h) on the
// canvas as well as to the canvas; clip_w == 0 means no clip of its own.
typedef struct __attribute__((packed)) {
    uint16_t canvas_id;
    uint16_t image_id;
    int16_t  src_x, src_y;
    uint16_t w, h;            // source rect (pixels of the sprite image)
    int16_t  dst_x, dst_y;
    uint8_t  scale;           // 1..FMRB_LINK_TILE_SCALE_MAX
    uint8_t  flags;           // reserved, 0
    int16_t  clip_x, clip_y;
    uint16_t clip_w, clip_h;
} fmrb_link_graphics_draw_tile_scaled_t;   // 26 bytes
```

- 切り抜き (`clip_*`) を持たせるのは、チャットが会話の欄の上の端で絵の一部 (13 px の帯) だけを出すため。今は等倍の `draw_tile` の元の矩形で切っているが、2 倍で出すと帯の境が元の画素の半分に当たる。描画側は `setClipRect` で切れる (両方とも LGFX_Sprite)。
- 描き方 (描画側の時間): **行ごとに同じ色の連なりを 1 回の `fillRect(n*k, k)` にし、透明色の連なりは飛ばす**。点の絵 (色が続く) は命令あたりの書き込み回数が大きく減る。最悪 (毎点色が変わる) は元の画素数ぶんの `fillRect(k, k)` で、今の等倍の 1 点ずつと同じ桁。WROVER (240 MHz) での実時間は測っていない。
- 足す場所: `fmrb_link_protocol.h` (構造体と番号)、`components/fmrb_gfx/fmrb_gfx_cmd.c`・`.h` (`GFX_CMD_DRAW_TILE_SCALED`)、`main/kernel/host/host_task.c` (線の形へ)、`main/app/fmrb_boundary_gfx.c` (`fmrb_bnd_gfx_draw_tile_scaled_raw`)、`sig/fmrb_gfx.rbs` (境界に載る `draw_tile_scaled_raw`、7 章)、mrblib `fmrb-gfx.rb` と Spinel の基底の `draw_tile` の包み (`scale:`)、graphics-audio `graphics_handler.cpp`、display_local `display_local_task.cpp`、`tools/regress/recorder.rb` (記録の 1 行)、生成物 (MicroPython の qstr の表をコミット、`rake micropython:gen`)、`fmrb_link_version.h` と `fmrb_ga_version.h`・`fmrb.h` の版。
- 境界の `draw_tile_raw` の形は変えない。C の SDK (`sdk/c/fmrb_boundary.h`) と wasm のアプリの import が今のまま使える。

ほかの形:

- B: `DRAW_TILE` の構造体の後ろに `scale` を足す (番号は同じ)。古い描画側は長い分を読み捨てて等倍で描く (落ちないが黙って違う絵)。新しい描画側は短い (古い core の) 命令を受けるために `size >= sizeof` の確かめを変える必要がある。境界の `draw_tile_raw` の引数が増えると C・wasm の SDK が壊れるので、境界は結局別の名前になる。
- C: 拡大は `draw_picture` (5 章) の中だけにし、`draw_tile` には足さない。境界と線の形は A と同じものが要る。

### 3.3 スプライトを置いた絵 (`SpriteInstance`) の拡大

足さないのを推奨 (P1 の範囲の外)。合成の道が 2 つの描画側で違い (P4 は PPA)、4 つのアプリは使っていない。要るアプリは拡大した絵をスプライトの絵として作れば足りる (`DRAW_TILE_SCALED` でスプライトの絵に描く: 描く先をスプライトの絵にした状態でも `DRAW_TILE` は効くかは確かめていない。8 章)。

### 3.4 版と古い子マイコン (確かめた事実と推定)

- core は起動のときに link の版 (`FMRB_LINK_VERSION`、今 6) と GA の版の文字列 (`FMRB_GA_VERSION`、今 "3.1.0") を**両方とも厳密に**照らし、合わなければ `fmrb_kernel.rb:1408-1431` が赤い LED を点けて raise する (起動しない)。display_local は同じ版を自分で答える (同じビルドなので必ず合う)。
- よって版を上げると、Retro は **S3 だけ焼き直しても起動しない**。WROVER も焼き直す (今までの link 5・6 と同じ扱い)。sim は graphics-audio を `rake build:linux` し直す (sim_up が古いビルドを断るので気づける)。
- 版を上げずに新しい命令を送ると、古い graphics-audio は知らない命令として捨てる (`default` で -1、答えを待たない命令なので core は気づかない)。絵が出ないだけで落ちない。
- 版を上げない別の道: `INIT_DISPLAY` の答えの能力のビット (`FMRB_LINK_DISPLAY_CAP_*`、`SET_SCREEN_MODE` の前例) で「拡大できる」を知らせ、できない描画側には等倍で描く。ただし GA の版の文字列も照らしているので、graphics-audio を直す以上どのみち GA の版は上げる (上げないと、直した GA と直していない GA が区別できない)。**選択肢 Q9 の推奨は「link 7・GA 3.2.0 に上げ、線の形の変更は P1 に全部まとめて 1 回で焼き直す」**。

## 4. 画素から直接スプライトの絵を作る

### 4.1 今できること・できないこと (確かめた事実)

- `SpriteImage.new(width:, height:)` + `set_target` + `fill_rect` などで描ける。1 点ずつなら `set_pixel` / 1x1 の `fill_rect` が 1 命令。スプライトエディタの 256 色の升目・市松の帯はこの形 (数十〜数百の命令で済む絵)。
- 画素の文字列 (RGB332) をそのまま渡す命令は無い。48x48 の絵を点で送ると最悪 2,304 命令 (色の連なりで減る)。Retro の UART では 1 命令 20 B 前後なので 2,304 命令は 50 KB 前後・0.5 秒 (推定)。
- ファイルを経れば速い (チャットが今している: `encode_png` → ファイル → `sync_file` → `load_bmp`)。ただし VM で PNG を書く時間と一時領域、ファイルの書き込み (flash の摩耗) がかかる。

### 4.2 案 (選択肢 Q4)

**(推奨) 新しい命令 `FMRB_LINK_GFX_SPRITE_IMAGE_DATA`** (番号は 0x42、「Image/bitmap drawing」の空き。0x80 台は 0x8E を 3 章に使うと埋まる):

```c
// SPRITE_IMAGE_DATA: RGB332 pixels written into a sprite image's
// (x, y, w, h). w * h bytes follow, row by row. Asynchronous, like
// MASK_DATA: the sender splits a large rect so each message fits a frame.
typedef struct __attribute__((packed)) {
    uint16_t image_id;
    int16_t  x, y;
    uint16_t w, h;
    // Followed by w * h bytes of RGB332 pixels.
} fmrb_link_graphics_sprite_image_data_t;   // 10 bytes
```

- 1 回の大きさ: フレームのデータ 248 B から、見出し 10 B と msgpack・COBS の余裕 18 B (`MASK_CHUNK_OVERHEAD` と同じ) を引いた **220 B**。境界の C (`fmrb_bnd_gfx_write_sprite_image`) が矩形を行のまとまりに分けて送る (幅が 220 を超える行は横にも分ける)。graphics-audio は組み立て直した分けた命令の受け皿が 256 B なので (`fmrb_link_protocol.h` の `CREATE_MASK` の注)、1 フレームに収める分け方が要る。
- 答えを待たない。送り方は `create_mask` と同じく transport へ直接。**気をつける所**: host の列 (描画の命令) を追い越すので、同じ絵を描いている途中で書き換えると、列に残っている前の `draw_tile` が新しい画素で描かれうる。作ったばかりの絵に書くのは問題ない。書き換えに使うなら host の列を通す形にする (P1 で決める。推奨は列を通す: 順序が保たれ、`present` までに描かれる)。
- 上限: 1 回の呼び出しで 65,536 点 (スプライトエディタ・ビューワーの上限と同じ)。スプライトの絵の大きさを超える所は描画側で切る。
- 時間 (推定): Retro の UART で 48x48 = 2,304 B・11 回の送り、約 26 ms。32x32 で約 12 ms。P4 は同じチップの中なので無視できる。
- display_local は RGB565 の絵なので、受けて点ごとに 332 → 565 に直して書く (`drawPixel` と同じ変換。透明色の比べ方 (565 の値) と食い違わない)。
- 足す場所は 3.2 と同じ並び (構造体、cmd、host_task、境界、sig、包み、2 つの描画側、recorder、qstr)。包みは `SpriteImage#write_pixels` (7 章 Q4)。

## 5. `BMP332.info`・`to_png`

### 5.1 形 (選択肢 Q5)

C の中 (`png332.c` に `fmrb_png332_info` と、解いて書く 2 つをつなぐ所、`bmp332.c` に mruby の結び) で済ませ、画素を VM の String にしない。

- `BMP332.info(path)` → `{width:, height:, format: :png | :bmp, bytes:}` か nil (読めない・形が違う)。PNG は先頭 33 B (印と IHDR)、BMP は先頭 54 B だけ読む。ファイルの大きさは `bytes`。
- `BMP332.to_png(path, max: 2048, max_bytes: 65536)` → `{png: String, width:, height:}`。断るときは例外ではなく `{error: :too_big, width:, height:}` / `{error: :too_heavy, bytes:}` (書いた PNG が `max_bytes` を超えた) / `{error: :file_too_large, bytes:}` (元のファイルが 65,536 B を超えた。読まない) / `{error: :unreadable}`。
  - チャットの `[:big, w, h]`・`[:heavy, bytes]`・`[:bad]` と同じ 3 つの理由 + 元のファイルの足切り。例外にしないのは、一覧の 1 枚ずつで begin/rescue を回さないため (チャットは今 rescue で `[:bad]` にしている)。
  - 読み込み: C でファイルを開き、大きさ (`bytes`) が上限を超えれば読まない → 先頭で大きさ (`max`) を見て、超えれば解かない → 解く → 書く → 結果の String だけを VM に作る。一時領域はどれも VM プール (`mrb_malloc_simple`、今の png332.c と同じ) から取り、終わったら返す。
- 入力をバイト列でも受けるか (`data:`): 推奨は**受けない** (Q5a)。チャットの受けた絵は sha を照らした後にファイルに書くので、パスで足りる。

### 5.2 VM プールの見積り (推定、P2 で測る)

48x48 の RGBA の PNG (8 KB) 1 枚を、今のチャットの書き方 (`prepare`) と比べる。

| | 今 (Ruby) | `to_png` (C) |
|---|---|---|
| 解く間の山 (一時) | 読んだファイル 8 KB (String) + IDAT 8 KB + 展開 9.3 KB + 作業 1.6 KB + 画素 2.3 KB | 同じ (ファイルは C の一時領域) |
| 書く間の山 (一時) | deflate の作業 8.7 KB + ハッシュの表 16 KB + prev 4.7 KB + tok 9.4 KB + 出力 2.5 KB ほか ≈ 43 KB | 同じ |
| 残るゴミ (GC まで) | ファイルの String 8 KB + 画素の String 2.3 KB + Hash + PNG + 拡大した画素 (32x32 なら 1 KB、行ごとの `byteslice` の String が 16 本) + 拡大した絵の PNG ≈ 12〜13 KB | PNG の String と Hash ≈ 0.3 KB |
| 拡大した絵をもう 1 度書く | もう 1 回 `encode_png` (上の書く山が再び) とファイルの書き込み | 無い (拡大は描画側) |

- 一覧に 12 枚あるタブを開いたとき、GC までに積もるゴミは今 150 KB 前後、C なら 4 KB 前後 (推定)。山そのもの (1 枚の書く間の 43 KB) は変わらない。
- チャットのコード (c3 の +47 KB の多くはスタンプのコード) は、4 章の削る分 (8 章) で 1 割前後 (8〜10 KB) 減ると見ている (行数の比で見積もった。推定)。
- ホストの試験: `test/png332/` の C の試験に `info`・`to_png` を足す (`rake png332:test`、`rake regress` の中)。

## 6. `FmrbGfx` の絵の置き場

### 6.1 寄せる先 (選択肢 Q8)

**(推奨) スプライトの絵に寄せる**。

| | スプライトの絵 | `create_image` |
|---|---|---|
| アプリの終わり | 回収される (canvas と一緒に) | **回収されない** (1.2) |
| 枚数 | 64 (GA) / 160 (P4)、機械全体 | 8、機械全体 |
| 透明 | 透明色で抜ける (P1 の後は α の PNG も) | GA は α で混ぜる、P4 は白 (食い違い) |
| 色 | RGB332 | GA は RGB332 (canvas が 332)、P4 は RGB565 |
| 一部を描く | `draw_tile` | できない |
| Retro | 使える (アイコン・ゲームが使っている) | App Store は出さないことにしている |

- 失うもの: P4 の `create_image` の 16 ビットの色。App Store の店の絵 (32x24) が P4 で 332 の色になる (sim・Retro は今も 332)。壁紙 (デスクトップ、JPEG を含む) は今のまま `create_image` を使う (置き場の対象にしない)。
- 別案 B: App Store は `create_image` のまま残し、置き場は 2 種類を持つ (`full_color: true` で `create_image`)。置き場の中の分岐と、`create_image` の回収されない問題を置き場が肩代わりする (`stop` で離す) 分だけ大きくなる。

### 6.2 API の形 (選択肢 Q6・Q7)

**(推奨) パスを鍵にする形**。アプリは番号も物も持たない。

```ruby
@gfx.draw_picture("/home/stamps/a.png", 10, 20, scale: 2)          # 無ければ読み込んでから描く
@gfx.draw_picture(path, x, y, scale: 2, checker: true)             # 透明の所を市松で
@gfx.draw_picture(path, x, y, scale: 2, clip: [cx, cy, cw, ch])    # 欄の中だけ
w, h = @gfx.picture_size(path)                                    # 読まずに大きさ (nil なら読めない)
@gfx.put_picture("chat:#{sha}", 16, 16, pixels)                    # 画素から (パスの代わりの名前)
@gfx.release_picture(path)
@gfx.release_pictures
@gfx.draw_checker(x, y, w, h)                                     # 市松だけ (エディタ・ビューワーの下地)
@gfx.picture_limit = 16                                           # この描き手が持つ枚数 (既定 8)
```

- 中の作り: `{鍵 => [sprite_id, w, h]}` と最近使った順の配列。`draw_picture` で無ければ `picture_size` → `create_sprite_image(w, h, 0x01, true)` → `sync_file` → `load_sprite_image`。`picture_limit` を超えたら一番古いものを `delete_sprite_image`。
- **機械全体の上限に当たったとき** (作る命令が 0 を返す: 枚数か、GA の 256 KB の置き場が一杯): 自分の古いものを 1 枚ずつ離して作り直しを試み、自分のものが無くなっても作れなければ描かずに false を返す (落ちない)。ほかのアプリの絵には触れない (触れる道が無い)。ログは同じ鍵で 1 回だけ。
- 透明の市松: 色 0xFF・0xB6、升 4 px (ビューワーと同じ)。1 枚の帯 (幅は使った最大、高さ 8) を初めて要るときに作って持つ。`checker: true` は絵の矩形に帯を押してから絵を押す。
- アプリが終わるとき: スプライトの絵は canvas と一緒に回収されるので、何もしなくてよい (App Store の `stop` のような後始末は要らない)。
- 描き手ごと (`FmrbGfx` の物ごと) に置き場を持つ。`window_gfx` など 2 つ目の描き手は別の置き場 (スプライトの絵は canvas ごとのものなので、混ぜられない)。
- 別案 (B): 計画の見立てどおり絵の物を返す形 (`pic = @gfx.picture(path)` → `@gfx.draw_picture(pic, x, y, scale:)`)。物を持ったまま置き場から追い出されると、物の中の番号が無効になる (描くときに作り直す仕掛けが物の側にも要る)。パスを鍵にする形は、追い出されても次の `draw_picture` が黙って読み直すだけで済む。

### 6.3 mruby と Spinel の両方に載せる・絵を使わないアプリを太らせない

- **(推奨) Ruby で書いた 1 つのファイル** (`lib/gems/picoruby-fmrb-app/mrblib/fmrb-picture.rb`、案) を、mruby の gem の mrblib と、Spinel のプログラム (`tools/spinel/gen_app_combined.rb` が `fmrb-sprite.rb` と同じく差し込む) の両方で使う。sig では `%a{fmrb.internal}` (Ruby で書いたメソッド。境界には載せない)。Lua・Python・wasm のアプリには置き場は無く、下の境界の関数 (`draw_tile_scaled_raw`・`write_sprite_image`・`picture_info`) を直接使う。
- 状態は使ったときだけ作る (`@_pics` は最初の `draw_picture` まで nil)。絵を使わないアプリの増分はメソッドの登録の分だけ。mrblib の irep は flash の const (internal_ram_budget.md の R1) なので、VM プールに乗るのはメソッド表の項と proc (推定、1 メソッド 50〜100 B、8 メソッドで 1 KB 未満)。c3b のデスクトップの +2 KB はアプリのバイトコードのメソッド (irep ごと VM プール) で、mrblib とは載り方が違う。**P3 で `rake regress:run` の kamon・mml・flappy・デスクトップを変更の前と比べる**。
- 増分を 0 にしたいなら別案: メソッドは `draw_picture` 1 つだけ置き、初めて呼ばれたときに `require "/usr/lib/fmrb/picture.rb"` (案) で残りを読む (スプライトエディタの `require` と同じ道)。Spinel は実行中に読めないので Spinel の側は差し込みのまま。2 つの道を保つ分の手間がある。
- `picture_size` は**境界の関数 `picture_info(path)` を C で** (`main/app/fmrb_boundary_gfx.c`、記録 `{width:, height:, format:}`)。中は `fmrb_png332_info` (5 章) と同じ関数。Ruby でファイルの先頭を読む形は Spinel で File のバイナリの読みが通るかを確かめていない (8 章) ので避ける。
- 内蔵 RAM: 増えない見込み。置き場の状態は VM プール、描画側の絵は PSRAM・スプライトの置き場、境界の C は静的領域なし。`rake regress:size` で確かめる。

### 7.3 親 (ユーザ) に決めてほしいこと (利用者に見える所)
