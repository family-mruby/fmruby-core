# 報告 S2: mruby の割り当て経路の回収条件 (中断)

> 状態: 中断 (親の指示で途中で止めた) | 更新: 2026-10-01 | gc.c の回収条件は入れていない。測ってみると、GC の遅さの主因は
> 回収条件ではなく、estalloc のデバッグ用の検査 (`est_free` が解放のたびにプールの先頭から全ブロックをたどる) だった。
> 検査を外した試験ビルドでは、全体 GC 1 回が約 200 ms → 約 13 ms、負荷時の Shell の打鍵で 50 ms 以上が 98% → 9% になる。
> gc.c の変更だけを入れると逆に悪化する (1 回 1.7 秒)。指示書の止まる条件 (gc.c 以外に手を入れる必要) に当たる

## 分かったこと

### 1. P4 の `MRB_HEAP_PAGE_SIZE` は 128 (S1 の 256 は誤り)

- gc.c は picoruby-mruby の gem として compile され、その `mrbgem.rake` (lib/patch/picoruby-mruby/mrbgem.rake) が
  posix/wasm 以外では `MRB_HEAP_PAGE_SIZE=128` を gem の cc に足す (o1heap のときだけ別計算)。mrbconf.h の
  `MRB_CONSTRAINED_BASELINE_PROFILE` の既定 256 は使われていない。
- 確かめ方: P4 の gc.o を逆アセンブルし、`mrb_obj_alloc_core` の容量の足し込みが `addi a5,a5,128`、余白の判定が
  `addi a4,a4,64`、`add_heap` の確保が 2,576 B (= 16 + 128 × 20。RVALUE は 20 B) であることを見た。
- よって余白は 64 スロット (容量 3,072 の約 2%)。Shell の容量 3,072 は 24 ページ。1 ページは約 2.5 KB。
- **S3 も 128 のはず** (同じ mrbgem.rake の同じ分岐。S3 の gc.o は手元に無く、逆アセンブルでは未確認)。
  Linux と wasm は posix 扱いで `MRB_BASELINE_PROFILE`、ページの大きさは gc.c の既定 1024。

### 2. GC が遅い主因は estalloc の `est_free` のデバッグ検査

- `lib/patch/picoruby-mruby/mrbgem.rake` が、プールの統計 (`est_take_statistics`、VM Pools の表と `FmrbApp.pool_usage`)
  のために **`ESTALLOC_DEBUG=1` を常に入れている**。estalloc.c の `est_free` は `ESTALLOC_DEBUG` のとき、解放する
  ブロックをプールの先頭から物理順にたどって探す (二重解放・範囲外の検査)。1 回の解放がプールのブロック数に比例し、
  ブロックの頭は PSRAM に散らばっている。`est_malloc` / `est_free` は中身の 0xaa / 0xff 埋めもする。
- GC の掃除 (sweep) は死んだオブジェクトの中身 (文字列・配列・Hash の本体) を `mrb_free` で 1 個ずつ返すので、
  全体 GC 1 回の時間はほぼ「解放の数 × プールのブロック数」で決まっていた。印の付け (mark) は小さい。
- 試験: `est_free` の検査ブロックだけを外し (`#if defined(ESTALLOC_DEBUG) && defined(<未定義>)`)、統計と埋めは残した
  ビルドで測った。全体 GC 1 回が 200 ms 前後 → 13 ms 前後になった (下の表)。

### 3. gc.c の回収条件だけを変えると悪化する

- 試した条件: 「前回の生存数 + 容量の 1/4 < 容量」のときだけ回収する (既存の「+ ページの半分」も残す)。
  差分は scratchpad の `s2/gc_reclaim_quarter.diff`。ヒープは生存数の約 4/3 まで育ち、回収 1 回で空く数が
  約 60 → 約 500 になる。
- 検査が残ったままだと、回収の回数は約 1/8 になるが、1 回で解放する数が増えるので **1 回が 1.5-1.7 秒**になった
  (Shell だけ、irb の `GC.start` で 0.5-1.1 秒)。GC の総時間はむしろ増え、打鍵の最大は 370 ms → 1.7 秒。
  検査を外さずにこの変更を入れることはできない。

## 判断の材料と次の手

1. **本命は estalloc の検査を外すこと** (構成 4)。gc.c は触らずに、打鍵の 50 ms 以上が (a) 58% → 3%、
   (b) 98% → 9%、全 VM の GC の総時間が 1/7-1/20 になる。統計 (`est_take_statistics`) は残せる。
   - 当て方の案: estalloc の `ESTALLOC_DEBUG` を「統計」と「重い検査 (解放時の全走査・埋め)」に分ける。
     estalloc は picoruby-mruby の中の submodule なので、lib/patch で当てるか上流 (estalloc) に出すか。
     上流向けの説明は「`ESTALLOC_DEBUG` は統計と検査を一緒に入れるが、検査は解放ごとにプール全体を走査するので、
     統計だけが欲しい利用者は O(n) の解放を払うことになる。分けたい」。
   - 確かめること: 二重解放などの検出を失ってよいか (develop で検査が何かを見つけた記録があるか)。
     Linux (`family_mruby_linux.rb`) と wasm (`family_mruby_wasm.rb`) も ESTALLOC_DEBUG を入れているので、同じ遅さが
     sim とブラウザ版にもあるはず。S3 も同じ。
   - これは指示書の範囲 (gc.c だけ) の外なので、親とユーザの判断が要る。
2. gc.c の回収条件は、1 の後なら効く (構成 3 と 4 の比較)。GC の回数は約 1/8 (Shell 55 → 7 回、Monitor 380 → 51 回 /
   5 分)、総時間は Shell で 0.69 → 0.11 秒、Monitor で 3.6 → 0.72 秒。ただし 1 の後では打鍵の遅れの数字はほぼ同じ
   (3-9%) で、プールを 30-60 KB 余分に使う。**1 の後に入れる価値があるかは改めて判断する** (S3 のプールでは不利)。
   上流向けの説明の下書きは「回収で空くのが半ページ分しかない状態でも全体 GC を回すので、生存数が容量のすぐ下に
   いる作業集合では数十割り当てごとに全体 GC になり、ヒープも育たない。全体 GC の手間はヒープ全体に比例するので、
   空く見込みは容量の一定割合で見るべき。そうすれば割り当てあたりの手間に上限ができ、ヒープは最大の生存数の
   約 4/3 で止まる」。
3. 残りの測定 (再開時): 1 を当てた構成で sim (標準・互換、Retro の解像度)・wasm・S3 のビルドと回帰、S3 の gc.o での
   ページの大きさの確認、FM-Editor の互換構成 (mruby) の影響、`hid_lat` が出るまでの長めの操作。

## 見立てと違った点

- S1 も S2 の指示書も「全体 GC の回数が多い」を主因と見ていたが、1 回の重さのほうが主で、その重さは GC ではなく
  アロケータのデバッグ検査だった。回数を減らす変更は、1 回の重さが解放の数に比例するので、検査が残っていると
  逆効果になる。
- P4 のページの大きさは 256 ではなく 128。
