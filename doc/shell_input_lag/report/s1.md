# 報告 S1: Shell の打鍵の遅れの計測と修正

> 状態: 計測済・一部修正 (止まる条件で停止) | 更新: 2026-10-01 | 遅れの主因は見立ての待ち方ではなく、Shell の VM の GC だった。
> 約 120 回の割り当てごとに同期の全体 GC (1 回 40-390 ms) が走り、アプリ 3 本の負荷で core 1 が埋まると 1 回が数秒に伸びる。
> 待ち方の修正 (`935ed6f6`) でアプリ 0 個の打鍵は約 32 ms → 約 16-26 ms になったが、負荷時の数秒は GC の側を直さないと消えない。
> GC の手当ては候補に無く VM 全体に効く変更なので、案を出して止める

## 結論

- **見立てのうち当たっていたもの**: getch が 33 ms ごとに眠って見に行く作りと、`_spin` が 33 ms 待ち切ってから
  `on_update` に戻る作りで、打鍵 1 回あたり平均 15 ms 前後の待ちがあった。打鍵で `_spin` を抜け、getch を
  1 tick で起こし、続く `on_update` を 5 ms 後に回す形に直した (`935ed6f6`)。
- **見立てと違ったもの (主因)**: Shell の mruby VM が、ほぼ常に**約 120 回の割り当てごとに同期の全体 GC** を
  している。打鍵 1 回で約 20 オブジェクト割り当てるので、5-6 打鍵に 1 回、40-390 ms 止まる。アプリ 0 個でも
  打鍵の 45-70% が 50 ms を超えていたのはこれ。
- **負荷時の数秒**: Breakout.py が動くと core 1 の描画タスク (display_p4、優先度 5) が core 1 の約 85-90% を使い、
  優先度 2 の Shell はほとんど CPU をもらえない。その状態で上の全体 GC が走ると 1 回が数秒に伸び、打鍵から
  表示まで **2.5-6 秒**になる。待ち方の修正はここには効かない (直す前後とも数秒)。
- GC の直し方は plan.md の候補に無く、VM (mruby の割り当て経路) を変えるか、表示タスクの配置を変えるかで、
  どちらも Shell の外の範囲が大きい変更なので、指示書の止まる条件に従って案 (「案」の節) を出して止める。
  Shell だけでできる GC の手当て (`idle_gc`) は試して悪化を確かめ、入れていない。

## 計測の方法

一時的な計装 (コミットしていない。差分は作業中の scratchpad に置いた) で、打鍵 1 回ごとに次の時刻 (µs) を取った。

| 時刻 | 取る場所 |
|---|---|
| t_in | `fmrb_host_send_key_down` が host の列に積むとき (`host_send_key`。USB キーボードと遠隔入力が通る共通の入口) |
| t_host | host タスクが focused app の列に送る直前 |
| t_disp | app.c の `dispatch_hid_event_to_ruby` (C) が KEY_DOWN を Ruby の Hash にするとき |
| t_evt | Shell の `on_event` が `@input_buffer` に積むとき |
| t_get | shell_task の getch がその文字を拾ったとき |
| t_r0 / t_r1 | 拾った文字を含む描き直しの `on_update` の始まり / `present` を送り終えたとき |

- t_in と t_host は host_task.c の小さな環 (PSRAM、64 件) に積み、app.c が KEY_DOWN を Ruby に渡すときに
  一番古いものを取り出して `ev[:t_in]` などとして渡した (同じチップの時計なのでそのまま引ける)。
- 区間: **host** = t_host − t_in、**queue** = t_evt − t_host (app の列で待った時間)、**getch** = t_get − t_evt、
  **todraw** = t_r0 − t_get、**draw** = t_r1 − t_r0 (描き直しと present の送出)、**total** = t_r1 − t_in。
- 5 秒ごとに `FM-Shell: SHLAT` 行を出した。区間ごとに「50 ms 未満の平均 / 最大 / 50 ms 以上の件数」。
  平均を 50 ms 未満で切ったのは、GC の止まりが平均を壊して待ち方の変化が見えなくなるため。
- 表示側 (present 後の描画) は既存の `display_p4: render:` 行で見た。区間 4 (表示との突き合わせ) は、
  描画 1 枚が 30-42 ms であることの確認にとどめた。
- **打鍵**: tab5_input と同じ遠隔の入力 (`/ws` の WebSocket) を使う小さな Ruby の台本 (scratchpad) で、100 ms ごとに
  `a`〜`h` と Backspace 8 回を 12 回くり返した (192 打鍵、約 20 秒)。遠隔のキーは `rd_input.c` →
  `fmrb_host_send_key_down` で USB キーボードと同じ host の経路を通ることをコードで確かめた。
- **Shell の起動**: devctl の `/app/launch?path=default/shell` (組み込み app の名前で起動できる)。
- **条件**: (a) デスクトップと Services と Shell だけ。(b) Shell + MML (`/app/demo/mml.app.rb`)・Breakout.py
  (`/app/game/breakout/breakout.app.py`)・Monitor (`default/monitor`)。**FM-Editor は足せなかった**: ユーザ app の枠は
  Services を含めて 5 で、Shell を入れると 4 本目は `No free context slots` (-9) で起動しない。ユーザの報告の
  「4 本 + Shell」は今のファームでは同時に動かない組み合わせで、(b) は 3 本で測った。
- GC の回数と停止時間は、計測用ビルド (`FMRB_GC_PROFILE=1`、`rake clean_all` から) の `GC.stat` で数えた。

## 何が起きていたか

### 1. GC が 5-6 打鍵に 1 回、同期で全体を回る

- 計測用ビルドで (a) を測ると、48 打鍵 (5 秒) あたり GC が 9 回、**すべて major (全体)**、1 回平均約 130 ms、
  最大 224 ms (`gc n=29→38 minor=0 major=29→38 pause tot=908→2069ms max=224ms`)。
- 割り当ての数 (GC を止めて `:live` の差で数えた): 打鍵なしで約 24 個/秒、打鍵 1 回で約 20 個。
- **機序**: 割り当てを 50 個ずつ進めて `GC.stat` を見ると、`:live` が 3,072 (= ヒープの全スロット) に届くたびに
  約 50 個減り、そのたびに `:debt` が約 −2,760 に戻る。負債 (debt) は大きく負のままなので負債による GC ではなく、
  **空きスロットが尽きた割り当てで全体 GC を回している**。
  - mruby の `mrb_obj_alloc_core` は、空きが尽きたとき「前回の GC 直後の生存数 + ページの半分 < 容量」なら
    ページを足さずに `mrb_full_gc` で回収する (`gc.c`、"reclaim before growing")。
  - P4 は `MRB_CONSTRAINED_BASELINE_PROFILE` で `MRB_HEAP_PAGE_SIZE` = **256**。Shell の生存数は約 2,800-2,950
    (うち 1,691 がメソッドの Proc)、容量は 12 ページ = 3,072。2,950 + 128 < 3,072 が成り立つ間はページを足さず、
    回収しても空きは約 120 しか戻らない。だから約 120 割り当てごとに全体 GC になり、ヒープは永遠に育たない。
- 全体 GC 1 回の重さ: 起動直後の `GC.start` で 40-43 ms、打鍵を続けた後で 60-99 ms (一度 455 ms)。打鍵中の山は
  これに描画の横取りが重なって 150-390 ms。
- 注意: `ObjectSpace.count_objects` は数える前に全体 GC を回すので、GC の観察に使うと自分で GC を起こす
  (最初の試みでこれを踏み、`:debt` が動かない誤った表を得た)。

### 2. 負荷時は core 1 が埋まっている

- Shell (優先度 2) は MML・Breakout.py・Monitor と同じ core 1 で、そこに display_p4 (優先度 5) と kernel (9)、
  デスクトップ (3) もいる。Breakout.py が動くと display_p4 だけで core 1 の約 85-90% を使う。
- Shell の Ruby の計算 1.5 ms の区間が最大 900 ms かかった。上の全体 GC (無負荷 40-130 ms) は同じ比率で
  数秒に伸び、その間に来た打鍵は app の列で待つ (queue 最大 2.5-5.8 秒)。

### 3. 待ち方 (見立てどおり)

- shell_task は main_loop が `Task.pass` で譲ったときしか動けない (main が `_spin` の C の中で待つ間は VM ごと止まる)。
  直す前は、打鍵 → `_spin` の残り (最大 33 ms) → `on_update` (まだ描くものが無い) → `Task.pass` (getch の 33 ms の眠りが
  明けていなければ素通り) → `_spin` 33 ms → `on_update` で描く、の順で、getch で平均 15 ms、描くまでにもう 7-12 ms。

## 直した内容と理由 (`935ed6f6`)

候補 1 (打鍵が来たら起こす) と候補 3 (描き直しを軽くする) から選んだ。待ち方は T2 の数値 (getch 15 ms、todraw 7-12 ms)
で待っている区間がはっきりしていて、Shell の中で閉じて直せる。

- `on_event` は打鍵を `@input_buffer` に積んだら `request_early_update` で `_spin` を抜ける (`queue_key`)。
- getch は 33 ms ではなく 1 tick (5 ms) 眠る。shell_task は main が譲ったときしか走らないので、眠りの長さは
  「次に譲られたとき起きているか」だけを決める。待っていない間に CPU を使う量は変わらない。
- `on_update` は、getch が待っていて打鍵が積まれているとき、33 ms ではなく 5 ms で戻る (`KEY_FOLLOWUP_MS`)。
  shell_task がコマンドを実行中なら従来どおり 33 ms (打ち込みの先行を空回りで追わない)。
- 打鍵の経路の割り当てを減らした: 行末への追加は String 1 個 (従来 4 個)、ASCII の打鍵ごとの `utf8_reset` の
  空文字列をやめた、ASCII 行のカーソル位置を 1 文字ずつの String を作らずに計算、`redraw_input_line` で入力行の
  文字列を 1 回だけ作る。**ただし実機の 1 打鍵あたりの割り当ては約 20 個のまま変わらなかった** (残りは C が作る
  イベントの Hash 2 個 (key_down/key_up) とその中身、描画の呼び出しの引数など)。GC の回数を減らす手当てにはなっていない。
- `@current_line` に `<<` を使わないのは、履歴を呼び出したとき `@current_line` が `@cmd_history` の String そのものに
  なるため (書き換えると履歴が壊れる)。

## 撤回した仮説・試して入れなかったもの

- **`idle_gc` (Shell だけで GC を暇な時間に回す)**: `self.idle_gc = true` にすると (b) の打鍵は平均 33 ms・最大 250 ms 程度に
  なった (5 秒窓 3 つ)。しかしヒープが打鍵 1 回あたり数 KB 育ち続け (30 秒の連続打鍵でプール 36% → 98%)、天井で
  緊急の全体 GC になった。`_spin` の 33 ms の窓では idle のステップが見積もりに収まらず歩けない
  (`doc/midi/report/p7.md` 1.6 の「狭い窓では病的」と同じ)。デスクトップと同じ形の歯止め (静かなときに時間を区切って
  `GC.step`、65% で `GC.start`) を足して測ると、(a) で一度 3.9 秒、(b) で 7-14 秒の停止になった。数秒の止まりを
  まとめて後払いにするだけなので入れなかった。Retro は Shell の基準の使用量だけでプールの約 75% を使うので、
  そもそも育てる余地が無い。
- **`GC.generational_mode = false` + `GC.step_limit = 512`**: 止まりは 270-430 ms でむしろ長かった。空きが尽きた割り当ての
  全体 GC は step_limit で刻まれない。
- **`GC.interval_ratio` を 1000 に**: 変化なし。負債で起きている GC ではないため (上の機序と合う)。
- 「Shell の GC が遅いのは生存オブジェクトが多いから」: 生存は約 3,000 で、遅さの主は回数 (120 割り当てごと)。

## 見立てと違った点

- 遅れの主因は Shell の待ち方ではなく、VM の GC の回数 (空きスロットが尽きるたびの全体 GC) だった。
- 「エディタは速い」の差は、エディタが Spinel で GC の仕組み自体が別 (かつ打鍵あたりの CPU が小さい) ことで説明できる。
- ユーザの報告の組み合わせ (Shell + 4 本) は、今のファームではユーザ app の枠 (5、Services を含む) に収まらない。

## 案 (ここで止まる)

GC の手当ては指示書の候補に無く、Shell の外の範囲の大きい変更なので、案だけ挙げる。

1. **割り当て経路の回収条件にゆとりを持たせる (本命)**。`mrb_obj_alloc_core` の
   `live_after_mark + MRB_HEAP_PAGE_SIZE/2 < capacity` は、ページが 256 のとき余白 128 (容量の約 4%) しか見ない。
   たとえば `capacity / 4` 以上の空きが戻る見込みのときだけ回収し、そうでなければページを足す。Shell なら全体 GC が
   約 120 割り当てごと → 負債で回る通常の周期 (生存数 ≒ 3,000 割り当てごと) になり、打鍵では 6 打鍵に 1 回 →
   約 150 打鍵に 1 回になる見込み。**全 mruby VM (デスクトップ・Services・全アプリ) の GC が変わる**ので、
   lib/patch で当てるか、上流 (この条件を入れた fork) で直すかの判断が要る。プールの使用量はページ数枚分 (1 ページ
   数 KB) 増える。
2. **P4 の `MRB_HEAP_PAGE_SIZE` を 256 から上げる** (1024 など)。余白も大きくなるが、ABI に関わる定義で全 VM の
   メモリの増え方が変わる。1 の方が狙いが狭い。
3. **core 1 の詰まり (表示)**: Breakout.py の負荷で display_p4 が core 1 の 85-90% を使い、同じ core の優先度 2 の
   app が数 % しか動けない。GC を直しても、負荷時の Shell の 1 打鍵は数 ms の計算 × 数十倍になる。表示の
   描画の重さ (1 枚 36-42 ms) か、タスクの core の割り当ての見直しは別の主題として要る。
4. Shell 側で続けられること (効果は小さい): C が作る key_up の Hash を Shell が使わないなら作らない、など
   割り当ての削減。1 の後なら効き目が見えやすい。

## 残件

- 上の案の判断 (親とユーザ)。1 を入れたら (a)・(b) を同じ台本で測り直す。
- ユーザの目視 (打鍵の遅れ)。今の状態は「アプリ 0 個では GC に当たらない打鍵が速くなった、負荷時は変わらない」。
- 遠隔の入力で、まれに Enter や Backspace が 1 つ消えた (Shell 起動直後の最初のコマンドの Enter など)。直す前の
  ビルドでも起きていて、host の `Keyboard event dropped` は出ていない。追っていない。
- 実機に置いた試験ファイルは無い。実機は最終ビルドで、Shell だけが開いている (MML・Breakout.py・Monitor は止めた)。
