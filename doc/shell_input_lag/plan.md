# Shell のキー入力が遅い件

> 状態: 進行中 | 更新: 2026-10-01 | S1: 主因は待ち方ではなく mruby の GC。S2 (中断): GC 1 回の重さの主因は回収条件ではなく estalloc のデバッグ検査 (`est_free` が解放ごとにプールを全走査)。検査を外した試験で全体 GC 約 200 → 13 ms、負荷時の 50 ms 以上 98% → 9%。gc.c は入れていない (検査が残ると逆効果)。次は検査を外すかの判断

## 目的

FM-Shell で、打ったキーがすぐ画面に出るようにする (アプリを多く動かしているときも)。

## 分かっていること (2026-10-01、P4-Nano)

- ユーザの報告: Monitor・MML・Breakout.py・FM-Editor を動かした状態で、Shell のキー入力が遅い。エディタ (Spinel) は速い。
- 同じ状態で、Shell のタスクのスタックの残りが 1,068 B (12 KB 中)。遅さとは別だが、溢れると落ちる。
- 表示側のカーソルの遅れは doc/p4_cursor_lag で直した (表示の受信の詰まりは解消済み)。

## 見立て (コードを読んだだけ。S1 で確かめる)

- Shell (mruby) は、`on_event` で打鍵を `@input_buffer` に積み、REPL 側の `getch` が `sleep_ms @frame_ms` (33 ms)
  で眠りながら列を見に行く。描き直しは `on_update` (33 ms ごと) で `redraw_input_line`。待ちが重なると、
  1 文字あたり最大で約 70 ms と描画の時間がかかりうる。
- Shell は Breakout.py などと同じ core 1・同じ優先度 2 で動くので、CPU の取り合いで順番が遅れる可能性。
- エディタは Spinel で、打鍵から present まで 2 ms に詰めた改修 (editor_serious_mode P1) が入っている。

## 方針

- 推論で直さない。打鍵から表示までを区間ごとに測り (キーが app に届くまで、getch が拾うまで、描き直しが
  終わって present するまで)、どこで待っているかを数値で分けてから直す。
- 直し方の候補 (S1 で比べて決める): 眠って見に行く作りをやめて、打鍵が来たら起こす / 打鍵のあとすぐ描き直す /
  描き直しを軽くする (差分) / 優先度や core の見直し。Shell を Spinel にする、のような大きな変更は止まって案を返す。
- Retro (S3) と sim でも Shell は同じコードで動くので、どちらも壊さない。
- スタックの残り 1,068 B は S1 で最悪の経路を確かめ、要るなら `.app.toml` の `task_stack_kb` 等で手当てする
  (内蔵 RAM の増え方を書く)。

## 受け入れ条件

- アプリ 0 個と、4 本 (Monitor・MML・Breakout.py・FM-Editor) を動かした状態の両方で、打鍵から表示までの時間が
  直す前より大きく減る (数値で前後を示す)。目安はアプリ 0 個で 1 フレーム程度。
- Retro (sim) と標準・互換構成の sim で Shell が従来どおり動く。
- ユーザの目視で打鍵が遅れない (親が依頼する)。

S1 の判断 (ユーザ、2026-10-01): 推奨どおり、S1 の修正はマージし、GC の回収条件を lib/patch で試して実測する (効けば上流への PR も検討)。core 1 の詰まりは S2 の後。Shell のスタックは個別に +4 KB (他の小さな道具は 12 KB のまま)。
