## S2/S3 の設計判断

- **fmrb_log_port.h は fmrb_common に置いた** (指示書は fmrb_log.h 内分岐)。
  fmrb_task.c (fmrb_common) が fmrb_log を REQUIRES すると依存が循環する
  (fmrb_log → fmrb_common)。ログの継ぎ目を最下層 fmrb_common に置き、
  fmrb_log.h は FMRB_LOG* 規約をその上に積むだけにした。実装は
  components/fmrb_common/platform/wasm/fmrb_log_port_wasm.c (stub の中身を
  そのまま移設)。
- **ESP_LOG* 名は全 platform で見える**。ESP_LOG 直呼びの共有コード
  (posix HAL、fmrb_audio 等) を FMRB_LOG* に替えるとログバッファへの複写が
  増える = 挙動変更なので、呼び出しは変えず include だけ替えた。
- **heap の継ぎ目は esp_heap_caps.h のまま 1 本**。fmrb_mem 内は既に
  platform ガード済みで、残る共有ユーザ (fmrb_task の周期ダンプ、
  apu/display の PSRAM 確保) は wasm ではカーネル stub (heap_wasm.c) が
  実装する。fmrb_mem に空き容量 API を新設して寄せる案は新規 API 追加 =
  このテーマの範囲外として見送り (指示書の「可能なら」への回答)。
- esp_idf_version.h / esp_check.h: 共有コードの読者は無し
  (idf_version は lib/add const.c のガード内のみ、esp_check は 0 件)。

## 詰まった点・気づき

- **fmrb_common の層問題** (上記設計判断 1)。ヘッダ分岐案のままだと
  IDF ビルドで include が解決しない。
- **素の EXT_RAM_BSS_ATTR が 5 ファイルで間接 include 頼みだった**
  (mempool / fmrb_task / fmrb_app / debugd / sprite)。IDF ターゲットでは
  偶然解決し、wasm では stub の連鎖 include が支えていた。fmrb_attr.h への
  置換でこの偶然依存が消えた。
- **rake clean_all 後の rake wasm:poc が configure で死んでいた**
  (libmruby 不在ゲートが FATAL)。PoC は mruby を使わないので WARNING に
  緩めた (S4 コミットに同梱)。
- 検証中の見かけ回帰 1 件: S3 ビルドが flash/etc/system_conf.toml を
  Retro 構成 (320x240) に書き替え、直後の wasm 実行が 320x240 で起動した。
  seam と無関係の既知の構成 staging 問題 (doc/wasm/ P5 の課題そのもの)。
  linux ビルドで復元して 426x240 を確認。
- 改善メモ (持ち帰り、未実施): fmrb_task の周期ダンプ用に fmrb_mem へ
  空き容量 API を立てれば heap_caps の共有ユーザをゼロにできる。
  boot 画面 (esp_app_desc/chip_info/flash) は表示専用の esp32 島として
  残っており、fmrb_sysinfo に寄せる余地がある。
