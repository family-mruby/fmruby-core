# K3c 報告: P4-Nano で「入力が数秒止まる」の調査

> 状態: 原因は未特定 (host の待ち行列から先は起動直後も止まらないことを測った。残る候補は USB の受信機と USB のタスク、次に起きたときにログで分けられる計装を入れた) | 更新: 2026-11-11 (K3d: edit_lat がかなの読みのキーを数えない、ESP32 のかな・漢字の確定も host task が待たずに送る、起動直後から 5 分後までの測定) | 遠隔の入力で起動 19 秒後・1.5・3.5・5.5 分後に測り、cursor wait の max は 16-40 ms、host task の 100 ms 超えの回は 0 件。遠隔の入力の揺れはほぼ網 (ping p90 50-58 ms、最大 270-420 ms)

## 発端

ユーザが P4-Nano (NARYAv4) で漢字変換を使い始めた直後に「ときどきマウスとキーが数秒効かなくなる」と報告した。
起動直後の方が多い気がする (確証はない) とのこと。手がかりは次の 2 つだった。

- `I (10:47:35.745) spx: edit_lat: n=100 mean=219893us max=4792076us ... hist5ms=39,6,38,4,2,0,1,0,0,0,10`。
  かなモードの on (10:46:43) から off (10:47:29) の間で、漢字の引きは 4 回 (各 1-3 ms)。
- 起動直後の `W (10:45:38.618) rpc_core: Timeout waiting for Resp for Req[0x15e]` (C6 への RPC が 5 秒待って切れる)。

## 確認したこと

### 1. edit_lat の 4.8 秒は見かけの値 (止まりではない)

- エディタの `lat_key_arrived` (editor.app.rb) は、修飾キー以外の key_down が来た時刻を「まだ画面に出ていない最も古いキー」
  として記録し、次の描き直し (`redraw_if_dirty`) で差を取る。描き直しを起こさないキーは記録が残ったまま次の描き直しまで続く
  (render.rb の注記どおり)。
- 辞書があるときのかなモードでは、ローマ字のキーは host task (`host_kanji_key` が `HOST_KANJI_CLEAR_CHAR`) で文字を 0 にされ、
  scancode だけがエディタへ届く。エディタはこれで描き直さない。読みは画面下端の変換の 1 行 (host task が描く) に出るだけで、
  エディタが描き直すのは確定の文字が届いたとき。よって 1 標本は「読みの最初のローマ字 → 確定」の時間、つまり**人が読みを打って
  変換・確定するまでの時間**になる。hist の最後の桶 (50 ms 超) の 10 件は確定の回数と合う。
- 実機での再現 (遠隔の入力、`fmrb_rd_input.rb`): かなモードで `k` を打って 4 秒あけ、`anji`・変換・Enter と続けた。
  入力は普通に効き (変換の 1 行は進み、10:54:20 に引きが出て確定)、その窓の報告は
  `edit_lat: n=100 mean=66726us max=5540521us ... hist5ms=16,28,21,29,4,0,0,0,1,0,1`。あけた 4 秒がそのまま max に乗る。
- 辞書の無い古いビルド (2026-09-28) の `max=2789272us` も、直前に `kana mode=1 (set by app)` があり、かなモード中の値だった
  (子音のローマ字も描き直しを起こさないので、子音の後に手を止めると同じことが起きる)。

### 2. 漢字の確定の道は今日は止まっていない

- host task がアプリの待ち行列に詰まると、`fmrb_msg: msg_send TIMEOUT ... waiting=64` (間引いても 1 回は出る) と
  `host: Keyboard event dropped` が、host task の待ち行列が溢れると `Failed to send host message` が出る。今日の起動 2 回
  (09:00・10:45) のログに**どれも 0 件**。マウスの `Mouse move send to Kernel blocked` も 0 件。
- 1 行ずつの時刻の間が 2.5 秒を超えたところは無い (10:45 以降)。`display_local: render` は 5 秒ごとに途切れず出ている。
- カーソルの経路 (`display_local: cursor`) の wait の最大は、今日の全区間で 157 ms (09:50:40、Avatar の起動中)、77 ms、46 ms。
  ユーザの漢字の窓 (10:46:43-10:47:29) では最大 34 ms、マウスを動かした n=125 の 5 秒でも 27 ms。
- 遠隔の入力で負荷をかけた (エディタ、かなモード + 辞書):

| 試し | 内容 | 結果 |
|---|---|---|
| A | 1 打鍵 230 ms 間隔、6 語 × (読み・変換 1-2 回・Enter) にマウス移動を挟む | 引き 12 回すべて答え (1-8 ms)。cursor wait 最大 28 ms。警告 0 件 |
| B | 1 打鍵 50 ms 間隔 (押し 25 ms・離し 25 ms)、40 語 (約 600 の出来事) に打鍵ごとのマウス移動 | 引き 40 回すべて答え (最大 10 ms)。render 68-88 frames/5s、cursor wait 最大 65 ms、`TIMEOUT`・`dropped`・`Failed to send` 0 件。edit_lat max 496 ms (1 語を打つ時間。1 と同じ見かけ) |

- コードの上では K4c の「残件」のとおり、`host_send_kana_byte` は 1 バイトごとに最大 200 ms アプリの待ち行列を待つ。
  ただしこれが効くのはアプリの待ち行列 (64 件) が満ちているときだけで、今日のログでは一度も満ちていない
  (満ちれば上の TIMEOUT が出る)。確定は 1 回が数十バイトで、エディタは毎フレーム待ち行列を空けている。

### 3. 起動直後の RPC の待ちは入力の経路に無い

- `Req[0x15e]` は `ble_task.c` の `esp_hosted_get_coprocessor_fwversion` (C6 のファームの版を聞く) で、BLE を始めるタスクの中で
  呼ぶ。10:45:33.617 に出して 10:45:38.618 に 5 秒で切れ、BLE・Wi-Fi の立ち上げがその後に続く。
- 入力の経路 (usb_task → host task → カーネル/アプリ) と、メニューバーの描画 (デスクトップ) が読む状態はどれも RPC を呼ばない:
  - `FmrbApp.wifi_connected?`・`wifi_info` → `fmrb_platform_sys_net_*` → `wifi_is_connected` などは wifi_task.c の変数を読むだけ
    (Wi-Fi の強さは取っていない。`signal = -1`)。
  - `FmrbApp.ble_state`・`ble_settings_left` → `ble_ui_state`・`ble_settings_window_left` も変数を読むだけで、錠も取らない。
- その 5 秒の間も描画は進んでいる (10:45:36 の `render: 26 frames/5s`、`GFX STATS 107.7 cmds/s`)。
- その間に手の入力は無かった (最初のマウスの出来事は 10:45:39.107 の `usb_task: Screen size acquired` (最初のマウスの報告で
  初めて読む) と 10:45:39.951 の `Cursor made visible on first mouse event`)。遠隔の入力は Wi-Fi が上がった後
  (10:45:47) にしか使えないので、**この窓での入力の遅れは遠隔では測れない**。
- 過去のキャプチャ (約 300 回の起動で同じ RPC の待ち切れ) で、待ち切れから 400 行以内に入力の警告が出たのは 1 回 (13:29、
  カーネルからエディタへの送り、Shell の打鍵遅延の調査の時期のもの) だけで、RPC との結びつきは見えない。

## 撤回した仮説

- 「`edit_lat` の 4.8 秒は漢字の確定で host task がアプリを待って止まった跡」: 上の 1 のとおり計り方の見かけ。
  host task が止まれば出るはずの警告が 0 件で、描画とカーソルも止まっていない。
- 「K4c のブラウザ版と同じ待ち合い (host task がアプリの待ち行列を待ち、アプリのフレームが host task を待つ) が ESP32 の
  かな・漢字の確定でも起きている」: 機序はコードの上ではあり得るが、アプリの待ち行列が満ちた跡 (TIMEOUT) が無く、
  負荷をかけても再現しない。K4c の載せ替え (待たずに送る形) は今回はしていない (止まりの原因と示せていないため)。
- 「メニューバーの Wi-Fi の表示が起動時に C6 への RPC を同期で呼んで入力を止める」: 読むのは変数だけ (上の 3)。

## まだ確かめていないこと (ユーザに頼むこと)

ファームの入力の経路では止まりの跡が見つからないので、次は手元で起きたときの観測が要る。

1. 止まったら、**動き出した直後にメニューバーの時計の時刻** (分まで) を控える。シリアルのログと突き合わせる
   (そのときに `TIMEOUT`・`dropped` が出ているか、描画が止まっているかが分かる)。
2. 止まっている間、**マウスのポインタそのものが動かない**のか、**ポインタは動くがクリック・キーが効かない**のか。
   前者なら USB の受信機から報告が来ていない (ファームより手前) か host task の止まり、後者ならアプリの側。
3. 前にいたアプリ (エディタ・デスクトップ・ほか) と、かなモードだったか。
4. 受信機 (Logitech Unifying、2.4 GHz の無線) を P4-Nano の Wi-Fi・BLE (C6) から離して (USB の延長で 30 cm ほど) 起動直後を
   試す。起動直後は Wi-Fi の接続と BLE の広告が同時に始まるので、無線の受信機の取りこぼしなら起動直後に多いことと合う
   (今のところ推測。ファームのログには受信機の報告が届かないことは出ない)。

## 計り方について (提案。K3d で実施した)

- edit_lat は「打鍵 → 画面」の値なので、host task が文字を預かっている間 (かなの子音、漢字の読み) の時間も入る。
  かなモードの窓の max はそのまま止まりの証拠には使えない。必要なら、文字が 0 の key_down (host が合成中のキー) を
  標本から外すか、確定の文字の到着から測る形に分ける (エディタの計装の変更。ユーザの判断)。

## 測った環境

## K3d: 計り方の直し、ESP32 の確定を待たずに送る形、起動後の入力の応答の測定

ユーザの決定 (2026-11-11): (1) エディタの edit_lat がかなの読みのキーを 1 標本に数えないようにする、(2) ESP32 のかな・
漢字の確定も K4c と同じく host task がアプリの待ち行列を待たない形にする (内蔵 RAM の増分 0)、(3) P4-Nano を起動し直し、
起動直後と Wi-Fi の後に入力の応答を測る。ユーザの補足: 止まったときはマウスのポインタそのものも動かなかった。最近 P4 を
あまり確認していなかったので、漢字と関係ない変更や前からの原因もあり得る。

### 変えたこと

- **edit_lat** (`editor.app.rb`・`editor/render.rb` の `lat_kana_held?`): かなモード (ひらがな・カタカナ) の間、文字が 0 で
  scancode が文字のキー (0x04-0x27・0x2C-0x38、Ctrl・Alt なし) の key_down は時計を始めない。host が読みとして預かるキー
  (子音、辞書があるときの読み全部) がこれで、エディタは描き直さない。確定の文字 (scancode 0、文字あり) と、矢印・Enter・
  BS などは今までどおり時計を始めるので、1 標本は「確定の文字の到着 → 画面」になる。ログの行の形は同じ (回帰の道具は
  この行を読んでいない)。
- **確定の文字を待たずに送る** (`host_task.c`): K4c の待ち (`s_text_fifo` 2048 バイト、`host_text_pump`) を ESP32 にも入れ、
  かなの合成 (`host_send_kana_byte` は無くした) と漢字の確定 (`host_send_text_bytes`) をそこへ置く。アプリの待ち行列が
  待たずに受け取るだけ送り、host task はアプリを待たない。
  - 文字を作ったキー自身の出来事 (母音のキー。文字は 0 にしてある) は、文字が残っていれば文字の後ろに 1 件だけ預かる
    (`s_text_tail`)。今までは文字と同じく直接送っていたので、待ちに置いた文字を追い越さないための追加。
  - 文字が残っている間に来たキーは K4c と同じく後回しにする (`host_text_pending`)。後回しの数は 32 → 128 (PSRAM。人の打鍵で
    溢れて捨てることが無いように)。キーは待ちが空のときにしか処理しないので、1 回のキーの文字 (かな数バイト、漢字の確定は
    読みの長さまで) は必ず入る。入りきらないときはログを出して捨てる (起きない見込み)。2 秒受け取らないアプリには残りを
    捨てる (K4c と同じ)。
  - ESP32 の待ちと状態は PSRAM (`FMRB_EXT_RAM_BSS_ATTR`)。送り手が別タスクにいるのはネイティブ版・ブラウザ版だけなので、
    数え (`s_text_inflight`) の原子操作は `HOST_TEXT_IN` のときだけにした (S3 で原子操作を使うと IRAM に置かれた
    `__atomic_*` の助けが引き込まれ、DIRAM が +193 B 増えた。最初の組み立てで `regress:size` が落ちて分かった)。
- **計装を 2 つ足した** (ポインタが止まったときにどこで止まったかをログで分けるため。どちらも普段は出ない):
  - host task (`host_note_pass`): ループの 1 回 (最初のメッセージから回の終わりまで、待ち 10 ms は除く) が 100 ms 以上かかった
    回数と最長を、あれば 5 秒に 1 行 `host: slow loop passes: n=.. max=..ms (msgs=..)`。
  - USB (`usb_task.c` の `input_health_tick`): hid_host タスクのループの間隔 (普段は 100 ms の待ちで回る) の最長が 300 ms 以上、
    コールバックで報告を捨てた数 (装置の錠が 1 ms で取れない。今までは黙って捨てていた)、host の待ち行列がマウスの移動を
    断った数 (今までは黙って捨てていた) のどれかがあれば 5 秒に 1 行 `usb_task: input health: ...`。マウスの動きの報告の間の
    最長の沈黙も添えるが、手を止めたのと区別できないので、それだけでは出さない。

### 測り方

- 起動し直しは flash (app 区画だけ、`/home` はそのまま) の後のリセットを使った。dev remote にリセットの口は無い。
  1 回目: 11:43:57 ごろリセット、遠隔が答えたのは 11:44:13.5。2 回目: 12:17:52 ごろリセット、12:18:09.3。
- 遠隔 (`/ws`) の入力は Wi-Fi を通る。台本 (`measure.rb`、scratchpad) は 40 秒の間、マウスの移動を 50 Hz で送り続け
  (右側で円を描く)、エディタをクリックし、英字 27 打鍵、Ctrl+Space でかなモード、4 語 (読み・変換・確定)、かなモードを
  切り、以後 2 秒ごとにクリック。同時に `ping` を 0.2 秒ごと、`GET /app/list` を 1 秒ごとに計る (網の遅れ)。
  遠隔の入力は `rd_input.c` → `fmrb_host_send_mouse_move`・`fmrb_host_send_key_*` なので、host の待ち行列から先は USB の入力と
  同じ道。USB の受信機から host の待ち行列までは遠隔では通らない。
- 端末の側の数字はシリアルのログ: `display_local: cursor` (host が位置を送ってから表示のタスクがそれを読むまでの待ち。
  ポインタの絵はこのとき描き直す) の max、`render: .. frames/5s`、`spx: hid_lat` (カーネルの出来事の処理)、`edit_lat`、
  新しい `slow loop passes`・`input health`、行と行の間の空き。
- 比べる元として、古いファーム (6746b827、起動から 43 分) でも同じ台本を 1 回流した。

  edit_lat max が 43-78 ms、含まない 1 つが 31 ms で、**1 回の描き直しが 40-50 ms ほど延びる**程度。秒の止まりではない。

### 起動の後に時間がかかっているもの

ログの時刻 (09:00:xx は時計の合う前の起動からの時刻) から:

| 起動から | こと | 入力への影響 |
|---|---|---|
| 0.6 秒 | SD を 4 ビットで開けず 1 ビットでも失敗 (`ESP_ERR_TIMEOUT`、カードが無い)。0.05 秒 | 無し |
| 1.9 秒 | host task が動き出す。ここから入力は通る (USB の受信機は 1.6 秒で認識) | - |
| 3.2-4.6 秒 | ランチャーのアイコン 14 枚を `/flash/cache/launcher` から読む (1 枚 60 ms ほど) | 描画の 1 回の最長 87 ms。cursor の待ちは出ていない |
| 4.2-9.3 秒 | BLE を始めるタスクが C6 のファームの版を聞き、5 秒待って切れる (`Req[0x15e]`) | 入力の経路には無い (前の節の 3)。ただし **BLE と Wi-Fi の始まりがこの 5 秒だけ遅れる** |
| 9.6-17.2 秒 | Wi-Fi の接続 (AP に付くまで 5.3 秒、アドレスまで 2.1 秒)。遠隔が使えるのは 17.2 秒から | 無し (この間も描画の窓は途切れない) |
| 17-26 秒 | 時刻合わせ (NTP。1 回目は答えが無く再試行)、`svc[net] up` | 無し |
| 以後 | 10 秒ごとの状態の表示 (core 1 で約 170 ms) | アプリの描き直しを 40-50 ms 延ばすことがある |

- Asterism の受け取りは切ってある (`Transfer: receiving is off`)。起動の後に Asterism・転送の接続、ファイルの同期
  (`No files to sync`)、mDNS で目立って時間を使っているものは無い。
- 起動直後 (Wi-Fi の前) の入力の遅れは遠隔では測れない (遠隔の口が Wi-Fi の後にしか開かない)。その窓は、手でポインタを
  動かしたときのログ (`cursor: n=..`、`input health`、`slow loop`) で見る。

### 撤回した仮説 (K3d)

- 「起動直後や Wi-Fi が上がった後しばらくは端末の入力の処理そのものが遅い」: host task から表示までの待ちも、カーネルの
  処理も、描画の進みも、起動 19 秒後から 5 分後、43 分後まで同じ (上の表)。
- 「10 秒ごとの状態の表示 (約 200 ms) が入力を止める」: host task は core 0 で遅れない。アプリ (core 1) の描き直しが 1 回
  40-50 ms 延びるだけ。
- 「ESP32 のかな・漢字の確定で host task がアプリを待つ」: 今回の変更で ESP32 も待たない形にしたが、変更の前もその跡
  (`TIMEOUT`) は 0 件だった。止まりの原因だったとは示せていない (起きなくする変更として入れた)。

### 残っていること

- **ユーザが見たポインタの止まりは、遠隔の入力では再現しない**。host の待ち行列から先 (host task → 表示) は起動直後も
  止まらないことを測った。残る候補は host の待ち行列より手前: USB の受信機 (Logitech Unifying、2.4 GHz) が報告を
  送っていない、または USB host のタスク。今回足した `input health` は USB のタスクが止まった・報告を捨てたことを出すが、
  受信機が送らなかったことは端末からは見えない (手を止めたのと同じに見える)。
- 次に止まったときに見るもの (ログで分けられるようにした):
  1. その時刻の `display_local: cursor: n=..` が 0 か (手は動かしていたのに 0 なら、移動が host に届いていない)。
  2. `usb_task: input health: ...` の行が出ているか (出ていれば USB のタスクの止まりか捨て)。出ずに n=0 なら受信機の側。
  3. `host: slow loop passes` が出ているか (出ていれば host task の止まり。ポインタもキーも同時に止まる)。
- C6 の版の問い合わせの 5 秒の待ち切れ (`Req[0x15e]`) は毎回の起動で起きていて、BLE と Wi-Fi の始まりを 5 秒遅らせている。
  入力とは関係ないが、遠隔が使えるまでの時間 (17 秒) のうち 5 秒はこれ。
- 測った環境: 前の節と同じ端末と辞書。エディタを開いた状態 (1 回目は t0 だけデスクトップが前で、注入したキーで Shell が
  開いたので閉じた)。台本と結果のファイルは scratchpad の `k3d/` (リポジトリの外)。キャプチャは止めていない。
