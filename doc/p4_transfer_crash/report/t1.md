## 1. 要約

- develop (b44993fb、計装なし、`FMRB_HW_TARGET=NARYAv4`) を P4-Nano に焼き、m1 と同じ形 (64 KB の put / get / 照合を 5 回) を起動し直しを挟んで 5 周した。5 周目の 4 回目の put で core 0 が Instruction access fault で落ちた (24 回中 1 回)。352 KB の put は 1 回目で core 1 が Store access fault で落ちた。**計装とは関係なく develop で起きる**。
- 同じソースで `CONFIG_SPI_FLASH_AUTO_SUSPEND` だけを切ったビルドでは、同じ手順 5 周 (put 25 回) で 0 回。
- 回数が少なく差が出にくいので、試験用に「フラッシュの rodata を少しずつ読み続けるタスク」(3 章の増幅) を入れて比べた。自動中断ありで put 11 回に 6 回落ち、なしで 16 回 0 回。読んだ値の照合 (チェックサム) の食い違いはどの構成でも 0 回 (読めるか落ちるかのどちらかで、黙って違う値は返っていない)。
- 落ちたアクセスは、フラッシュの命令の取り込み、rodata の読み出し、PSRAM への書き込み、内蔵 RAM (.bss) への書き込み (m1)。**どれもキャッシュを通るアクセスで、書き込み (消去・書き込み) の最中にだけ起きる**。core 0 だけでなく core 1 (表示のタスクの PSRAM への書き込み) でも落ちた。
- ESP-IDF の release/v5.5 の文書は、自動中断の対応を「S3・C2・C3・C6・H2 のみ。P4 は将来」と書いている。master の文書は 2026-05 に「ESP32 と S2 以外すべて」に変わったが、P4 の中断の試験は CI で回っていない (test_apps/flash_suspend の pytest は C3、C5、C61、S31 だけ)。同じ flash (GD25Q128、0xC84018) の P4 で、消去中に関係の無い場所で access fault になるという報告が IDF に出ている (#18846、2026-07、未解決)。release/v5.5 の HEAD・master に、P4 の中断の不具合を直す修正は見当たらない (4 章)。
- **直し方はどれも sdkconfig の変更になる** (6 章)。main/ と components/ の中だけでは直せない (IDF が毎回の書き込みの開始で中断の設定を書き直すため。5 章)。指示書 4 章の止まる条件にあたるので、案を書いて止まる。第一案は `CONFIG_SPI_FLASH_AUTO_CHECK_SUSPEND_STATUS=y` を足すこと (自動中断は残るので、保存のちらつきは戻らない見込み)。

## 4. ESP-IDF の確かめ (v5.5.4 / release/v5.5 HEAD / master)

- 文書 (`spi_flash_optional_feature.rst`): v5.5.4 と release/v5.5 は「This feature is only supported on ESP32-S3, ESP32-C2, ESP32-C3, ESP32-C6, and ESP32-H2 for now. The support for ESP32-P4 may be added in the future.」。master は efd344e4 (2026-05-11) で「all Espressif chips except ESP32 and ESP32-S2」に変わった。対応する flash は「GD25QxxE series」ほか。
- P4 の中断の対応のコード: master の f022b674 (2025-09、「Support flash suspend on esp32p4 revision 3」、tRS の設定を分けた) は v5.5.4 にすでに入っている。release/v5.5 で v5.5.4 (2026-03-24) の後に spi_flash・hal・esp_hw_support に入った修正のうち、関係しそうなものは次で、どれも今回の件には当たらない。
  - 590a2f6b「keep program and erase paths in IRAM」: LL の関数に always_inline を付けただけ。v5.5.4 の今のビルドでも該当の関数は全部 IRAM にある (nm で確認)。
  - 8996d1ae / 3631cf25「disable branch prediction ... during flash ops」: キャッシュを止める経路 (自動中断なしの側) の修正。自動中断ありではキャッシュを止めないので通らない。
  - 3d76ced5「read wrong data via mmap when flash being erased/written while XIP on PSRAM」: PSRAM からの実行 (XIP) の構成の話。今は使っていない。
  - a033efcb「Fix esp32p4 120m flash suspend failed」: 120 MHz の話。こちらは 80 MHz。
- master の P4 の `spimem_flash_ll.h` と `spi_flash_hal_iram.c` (esp_hal_mspi に移動) も、中断の振る舞いを変える差は無い (tRS の単位の関数の追加と always_inline だけ)。
- 試験: `test_apps/flash_suspend/pytest_flash_auto_suspend.py` は v5.5 で C3、master で C3・C5・C61・S31。P4 の実機で中断を試す CI は無い。
- 報告: espressif/esp-idf #18846「Flash Auto Suspend & Resume support for ESP32-P4」(2026-07-14、open)。P4 v1.3 + GD25Q128 (0xC84018) + IDF v5.4.1 で、OTA 区画の消去中に PSRAM への memcpy が Store access fault になる、場所はばらばらで稀、と書いている。今回と同じ形。Espressif 側の返答は別の部品 (esp_flash_dispatcher) の案内だけ。

## 5. 原因の見立てと根拠

### 見立て

**P4 での `CONFIG_SPI_FLASH_AUTO_SUSPEND` (IDF の既定の、固定の待ち時間で中断の完了を待つ方式) の不具合**。消去・書き込みの最中にキャッシュの取り込み (フラッシュへの読み出し) が起きると、ときどきバスがエラーを返し、そのとき取り込みを待っていたアクセス (命令、rodata、PSRAM、内蔵 RAM のどれでも) が access fault になる。

根拠:

1. 自動中断の有無だけを変えると、落ちる / 落ちないがきれいに分かれる (計装なし 1/24 と 0/25、増幅つき 6/11 と 0/16)。
2. 落ちるのは put (消去・書き込み) の最中だけ。get (読み出しだけ) では落ちていない (m1 の「get の直後」も次の put の最中だった)。
3. 落ちた場所はタスク・コア・アクセスの種類がばらばらで、共通点は「キャッシュを通る」ことだけ。コードの誤りでは説明できない。
4. 読んだ値の照合の食い違いは 0。中断が効かずに消去中の値を読んでいるのなら、壊れた値を返すこともあるはずだが、そうはならず、バスのエラーとして返っている。
5. 中断の完了を固定の時間ではなく状態レジスタで確かめる方式 (`AUTO_CHECK_SUSPEND_STATUS`) にすると、同じ負荷で 0/16 (+352 KB 1 回)。違いはレジスタ 1 ビット (`flash_pes_wait_en`、下の表) だけ。
6. IDF の安定版の文書は P4 を対象外としており、P4 の実機での試験も無い。同じ症状の報告がある。

ハードウェアの中で何が起きているか (固定の待ちの方式で、なぜバスがエラーを返すのか) は、外から見えるレジスタだけでは確かめられない。ここは見立てのまま。

### 起動時の SPI1 のレジスタ (試験のビルドで読んだ値)

| | 既定 (自動中断あり) | TSUS 100 us | 状態で確かめる |
|---|---|---|---|
| `ctrl1` | 0x00020080 | 0x000200fc | 0x00020080 |
| `cs_hold_dly_res` (中断・再開の後の待ち、×128 クロック) | 32 (= 51.2 us) | 63 (= 100.8 us) | 32 |
| `cs_hold_dly_per_en` / `cs_hold_dly_per` | 0 / 32 | 0 / 32 | 0 / 32 |
| `flash_sus_ctrl` | 0x0b80213c | 0x0b80213c | **0x0b802134** |
| うち `flash_pes_wait_en` (中断の後に固定の時間待つ) | 1 | 1 | **0** |
| `pes_end_en` / `per_end_en` (SUS ビットを確かめる) | 1 / 1 | 1 / 1 | 1 / 1 |
| `sus_timeout_cnt` | 5 | 5 | 5 |
| 中断・再開・状態読みのコマンド | 75h / 7Ah / 35h (マスク 0x84 = SR2 の SUS1・SUS2) | 同じ | 同じ |

- コマンドとマスクは GD25Q128E のデータシート (SUS1 = S15、SUS2 = S10、75h / 7Ah) と合っている。

### 撤回した仮説

- **tRS の不足**: GD25Q128E のデータシートでは tRS (再開から次の中断まで) は最小 100 us、tSUS は最大 20 us。IDF の既定は TRS 50 us で、しかも P4 では `cs_hold_dly_per_en` を立てないので `CONFIG_SPI_FLASH_SUSPEND_TRS_VAL_US` は効かず、再開の後の待ちも `cs_hold_dly_res` (= TSUS の 51.2 us) が使われる (上の表。release/v5.5・master の `spimem_flash_ll_set_rs_delay` も同じ)。データシートに足りないので有力と見たが、TSUS を 100 us にしたビルド (中断・再開の後の待ちが両方 100.8 us) でも、増幅つきで 2 回とも 1 回目の put で落ちた (panic の処理まで止まって HW WDT のリセット)。少なくとも主因ではない。
- **同じコアでの割り込み (書いているタスクを core 0 の上位のタスクが割り込む)**: m1 の記録は全部 core 0 で、書き込みの httpd も core 0 なので疑ったが、core 1 の表示のタスクでも落ちた (develop の 352 KB と増幅つき)。コアは関係ない。
- **計装のせい**: 計装なしの develop で起きた。
- **mmap した区画の後始末 (書き込み後のキャッシュの無効化)**: /home の LittleFS は mmap していない (`CONFIG_LITTLEFS_MMAP_PARTITION` 無効)。`spi_flash_check_and_flush_cache` は何もしない。

### main/ と components/ だけでは直せない理由

IDF は書き込み・消去のたびに `spiflash_start_core` -> `dev_config` -> `spi_flash_hal_setup_auto_suspend_mode` で中断の設定 (`flash_pes_wait_en` を含む) を sdkconfig の値から書き直す。アプリ側でレジスタを書き換えても、次の書き込みの開始で元に戻る。IDF の関数をリンカの --wrap で差し替えれば直せるが、それは IDF を直すのと同じなので、ここでは案に留める。

## 6. 直し方の案

どれも `config/sdkconfig.defaults.naryav4` の変更 (sdkconfig.defaults* は編集禁止なので、案として書く)。適用は `rake clean_all` から。Tab5 (`config/sdkconfig.defaults.p4`) は自動中断を使っていないので、この仕組みでは起きないはず (未確認)。

| 案 | 中身 | 保存のちらつき | 速さ | 内蔵 RAM | 根拠の強さ |
|---|---|---|---|---|---|
| **A (第一案)** | `CONFIG_SPI_FLASH_AUTO_CHECK_SUSPEND_STATUS=y` を足す | 戻らない見込み (自動中断は残り、キャッシュは止めない。目視はまだ) | 変わらないか速くなる (中断の完了を 51 us 待たずに状態で判断する。put の時間は 16 KB で 0.45-0.9 秒、自動中断ありの 0.6-0.9 秒と同じ桁) | 増減 0 (.iram0 / .dram0 同じ。flash +10 B) | 増幅つきで 0/16 + 352 KB 0/1。ただし P4 は IDF の安定版で対象外のまま。回数を増やした確認と目視が要る |
| B | 自動中断を切り、f1 の CS (`CONFIG_LCD_DSI_ISR_CACHE_SAFE=y`) に替える | 消える (f1 で欠落 0)。ただし保存の間は両方の CPU が 33-49 ms ずつ止まる (入力・音・描画も止まる) | 消去ごとに CPU が止まる。保存の時間は同じ | 静的 0、実行時 約 -120 B (f1) | IDF の対応範囲の中の方式。今回の増幅つきの試験は自動中断なしだけで、CS 自体の組み合わせはまだ試していない |
| C | 自動中断を切るだけ | **戻る** (青いちらつき) | 消去ごとに CPU が止まる | 静的 -76 B (f1) | 0/25、0/16 |

- A を採るときの注意: IDF の Kconfig は「中断の後の WIP ビットの振る舞いが期待どおりかデータシートで確かめること」と書いている。GD25Q128E は「中断の後 tSUS 以内に WIP が 0、SUS1/SUS2 がすぐ 1」とあり、条件に合う。専用基板で flash の型番が変わるときは、f1 の注意 (対応表に無いと起動しない) とあわせて、この振る舞いも確かめる。
- A の後に残るもの: 計装なしの標準ビルドで、64 KB × 5 の手順を数周と 352 KB の put を数回 (今回は書き込みの量の都合で増幅つきでしか確かめていない)、保存のちらつきの目視 (f1 の手順)。
