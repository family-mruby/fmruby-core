# S1 報告: 状態を覚える共通の API と File Manager (止まった)

> 状態: 止まった (見立てと違う事実: /tmp はどの端末でもディレクトリを作れない平らな置き場で、`/tmp/.state/` が作れない。置き場所の決め直しを待つ。コードは未変更) | 更新: 2026-10-29 | 指示書は instruction_s1.md。ブランチは fmruby-core の feature/linux-native

## 止まった理由

指示書と plan.md (2026-10-29 の変更後) は置き場所を全端末で
`/tmp/.state/<app_handle_name>.toml` としている。しかし /tmp は設計として
**平ら (ファイルだけ、ディレクトリを置けない)** で、実機・sim・ネイティブ版・
ブラウザ版のどれでも `/tmp/.state` を作れない。

- 決まりの元: components/fmrb_hal/fmrb_tmpfs.h の説明 ("v1 is a flat
  directory: /tmp holds files, not subdirectories. Both platforms enforce
  that")。
- 実機 (ESP32-S3・P4): platform/esp32/fmrb_tmpfs_esp32.c の `tmpfs_name` が
  名前に `/` を含むパスを断り、mkdir/rmdir は「平らなので作るディレクトリが
  無い」として失敗する。
- Linux 版・ブラウザ版 (POSIX の HAL を共有): platform/posix/
  fmrb_hal_file_posix.c が mkdir で /tmp の中を断り ("/tmp holds files, not
  subdirectories")、open・rename も `fmrb_tmpfs_path_too_deep` で 2 段目を断る。
  実機と同じ振る舞いにするための、意図した制限。

直すには (1) 置き場所を平らな名前に変える (仕様の変更) か、(2) /tmp に 1 段の
ディレクトリを許すよう C の HAL を両方 (esp32・posix) 直す (新しい C の変更、
かつ文書化された不変条件の変更) かで、どちらも指示書の止まる条件に当たる。
サブでは選ばずに返す。

## 選択肢 (推奨を先頭に)

1. **平らな名前にする: `/tmp/.state_<app_handle_name>.toml`** (または
   `/tmp/<app_handle_name>.state.toml`)。C は触らない。ls で見えにくい
   ドットで始める形なら、利用者が /tmp に置く物と混ざりにくい。
   実機の名前の上限は 63 バイト (TMPFS_MAX_NAME) なので、handle 名は
   50 バイトほどまで入る。ファイルの数の上限 (Retro 24・Modern 64) を
   1 アプリ 1 枠ずつ食う点は残る。
2. /tmp に 1 段のディレクトリを許す (esp32 の tmpfs にディレクトリの概念を
   足し、posix の too_deep を 2 段まで緩める)。tmpfs の表の作りが変わり、
   内蔵 RAM ではないが PSRAM の表が増える。今回の目的に対して重い。

## 寿命 (どの案でも /tmp に置く限り同じ)

| 端末 | /tmp の実体 | 覚えている間 |
|---|---|---|
| 実機 (S3・P4) | PSRAM の tmpfs | 電源を切る・再起動するまで |
| sim | コンテナ内の flash/tmp (起動時に空にする) | core を再起動するまで (sim_down・sim_up をまたがない) |
| ネイティブ版 | キャッシュの根の下の tmp (起動時に空にする) | プログラムを終えるまで |
| ブラウザ版 | ページの中の flash/tmp (起動時に空にする) | ページを再読み込みするまで |

POSIX 側は fmrb_tmpfs_posix.c が起動時に中身を消す (実機の再起動と同じ意味に
揃えるため)。したがって受け入れ条件は「1 回の起動の中で閉じて開き直す」になる
(plan.md の変更どおり)。

## 調べて決めておいた API の形 (承認後にそのまま実装する予定)

- 既存の `app_settings` / `save_app_settings` (fmrb-app.rb、/home/<名前>.toml) と
  同じ並びにする: `app_state` (Hash を返す。無い・壊れているときは {})、
  `save_app_state({...})` (指定したキーだけ書き、ファイルの中身と同じなら
  書かない)、`app_state_path`。
- 基底は**メソッドだけで ivar を足さない** (Spinel で基底に ivar を足すと
  親子の ivar の並びがずれた前例がある。fmrb-app.rb の app_settings も同じ
  理由でメソッドだけ)。そのため「閉じるとき自動で書く」は基底ではせず、
  アプリが閉じるときに `save_app_state` を呼ぶ (中身が同じなら書かない)。
- mruby 側は FmrbToml.load / FmrbToml.update を使う。Spinel 側には FmrbToml の
  束縛が無い (fmrb_assoc_spinel.rb・FmrbColors と同じ事情) ので、平らな
  `key = value` (文字列・整数・真偽) だけを読む小さな行読みを、Spinel の基底
  (fmrb_app_base_spinel.rb) の FmrbApp にメソッドとして足す。内蔵 RAM の
  理由で新しい定数・module は足さず、パスは文字列リテラルで書く
  (ruby_writing_constraints.md の内蔵 RAM の項)。
- Spinel では文字列キーの Hash を引数で渡すとき波括弧を明示する
  (`save_app_state({"fm_dir" => dir})`)。
- File Manager はデスクトップの一部なので、名前はデスクトップの
  app_handle_name ではなく固定の `file_manager` で覚えるのが分かりやすい
  (keys のデスクトップの File Manager と同じファイルを共有できる)。これも
  承認をもらいたい点。
